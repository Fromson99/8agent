# 1번 과제 — 업무 구조 이해 및 엣지 케이스 정리

신탁계약서 ↔ 핵심상품설명서 대사(신규 계약 시나리오)를 코드로 만들기 전에, 업무 구조와 처리해야 할 엣지 케이스를 정리한 문서다. 실제 공개 신탁계약서·상품설명서 실물을 분석한 결과를 반영했다.

---

## 1. 업무 구조 이해

### 1-1. 신탁계약서는 어떻게 작성되나 — "빈칸 채우기"

실물 계약서는 두 부분으로 구성된다.

- **본문 조항 (고정)**: 회사 표준약관 기반이라 거의 고정. (제1조 신탁목적, 제5조 신탁재산 운용, 제8조 신탁보수, 제3조 신탁기간 등)
- **별지1 세부내역서 (가변, 빈칸)**: 신탁금액, 신탁기간, 수익자, 신탁보수율, 중도해지수수료율 등을 상품·고객별로 기재
- **별표2 운용지시서 (가변, 빈칸)**: 투자대상(운용자산 종류/종목), 운용방법을 지정

> **핵심**: 가변 정보(대사가 필요한 실제 값)는 별지·별표에 집중된다. 대사 로직의 주 타겟은 이 영역이다.

### 1-2. 핵심상품설명서 필수내용 — 검증은 두 종류

설명서 검증은 성격이 다른 두 가지로 나뉘며, 파이프라인에서 분리해야 한다.

- **(a) 존재 검증 (완결성)**: 설명서에 필수 항목(아래 13개)이 빠짐없이 있는가? → 설명서 "혼자" 보는 검증 (프로세스도의 3단계에 해당)
- **(b) 일치 검증 (정합성)**: 계약서와 설명서에 공통으로 있는 항목의 "값"이 서로 일치하는가? → 두 문서 "대조" (프로세스도의 2단계, 1번 과제의 메인)

> 사용자가 "12개 항목이 있는지 확인"을 원하는 것은 (a)이고, 1번 과제의 본질은 (b)이다. 둘 다 필요하지만 로직이 다르므로 분리 설계한다.

### 1-3. 상품설명서 필수 설명항목 13개 (대사 항목의 기준)

실제 공개 문서(신한 신규가입 신청서)에서 확인된 법정 필수 설명항목. 대사 체크리스트의 출발점이다.

1. 운용자산의 종류 또는 종목명
2. 운용방법 또는 운용제한(구조·성격)
3. 신탁보수, 비용 및 수수료
4. 조기·중도·만기상환 조건
5. 신탁계약의 해지·해제(위법계약해지권 포함)
6. 운용방법/특정 종목의 위험요인
7. 청약철회권
8. 예금자보호 여부
9. 민원처리 및 분쟁조정 절차
10. 연계·제휴 서비스
11. 유사 금융상품과 구별되는 특징
12. 소비자 숙지 필요사항
13. 위험등급 및 등급 산정기준

- **계약서에도 있는 항목(1·2·3·4·5·6 등)** → 양방향 대사 대상 (b)
- **설명서에만 있는 항목(7~13)** → 존재 검증 대상 (a)

### 1-4. 설계에 반영할 두 가지 요구 (사용자 지적)

1. **필수 항목은 하드코딩하지 않고 확장 가능해야 한다** — 회사·상품마다 필수항목이 달라, 13개 외에 추가할 수 있어야 함
2. **사용자가 명시하지 않아도 LLM이 대응 항목을 스스로 찾아 비교해야 한다** — "투자대상 비교해"라고 지정하지 않아도, 양쪽 문서에서 대응되는 부분을 의미 기반으로 매칭 (이것이 RAG가 아니라 LLM 대사인 이유)

## 2. 엣지 케이스 정리

실물 문서 분석에서 도출한, 처리해야 할 까다로운 케이스. 성격별로 그룹핑했다.

### 그룹 A — 매칭의 어려움 (어느 항목끼리 비교할지)

**케이스 1. 의미 기반 매칭 필요 (표현 다름)**
- regex로 안 되고 같은 의미의 다른 표현을 인식해야 함
- 예: 계약서 "신탁기간 3년" ↔ 설명서 "36개월", "명목금액" ↔ "Notional"
- → semantic matching (LLM 판단) 필요

**케이스 2. 1:N 분산 매칭**
- 한 항목이 여러 곳에 흩어져 있음
- 예: 계약서의 "신탁보수"가 제8조(계산방식) + 별지1(보수율%) + 중도해지수수료(별도)로 분산되어 있는데, 설명서엔 "수수료" 한 문단에 뭉쳐 있음
- → 계약서 여러 곳 ↔ 설명서 한 곳을 종합 비교. 1:1이 아님

**케이스 3. 참조로 된 간접 지정**
- 계약서 본문이 실제 값 대신 다른 곳을 가리킴
- 예: "[별표2]에 기재된 대로", "세부내역서에 기재된 금액"
- → 참조를 따라가야 실제 값을 찾음. 본문만 보면 값이 안 나옴

**케이스 4. 같은 단어, 다른 의미 (false match 위험)**
- 예: "신탁기간" vs "계약기간"이 같을 수도 다를 수도. "만기"가 신탁만기인지 편입 채권 만기인지 문맥 의존
- → 단어만 보고 매칭하면 틀림. 문맥 판단 필요

**케이스 5. 표(table) vs 서술(prose) 형태 차이**
- 계약서 별지는 표, 설명서는 줄글 서술인 경우. 같은 정보인데 구조가 달라 추출 방식이 다름

### 그룹 B — 판정의 어려움 (매칭 후 같은지 다른지)

**케이스 6. 수식·조건부 값 (단순 값 아님)**
- 실물의 중도해지수수료: `해지신탁원본 × 중도해지수수료율 × 중도해지기준일수 / 365`
- "0.5%" 같은 단순 값이 아니라 수식. 계약서 수식과 설명서 설명이 같은 의미인지 판단 필요

**케이스 7. 표기 체계 차이 (위험등급 등)**
- 위험등급이 회사마다 "1~6등급" vs "매우높음~매우낮음" vs "고위험" 등 체계가 다름
- → 매핑 테이블 필요

### 그룹 C — 필수 항목 정의의 어려움 (무엇을 봐야 하는지)

**케이스 8. 상품별 필수항목이 외부에 정의됨**
- 신탁계약 유형에 따라 필수 필요 항목이 달라지고, 그 정의가 다른 문서/규정에 있음
- → 필수항목 정의를 외부에서 주입받는 구조 필요

**케이스 9. 조건부 필수 (누락이 정상일 수 있음)**
- 필수 13개 중 일부는 해당 상품에만 필요. 예: "조기상환 조건"은 ELS 편입 신탁엔 필수지만 단순 채권형엔 없어도 정상
- → 누락을 무조건 오류로 잡으면 오탐. 상품 유형에 따라 필수 여부가 바뀜

### 그룹 D — 데이터 품질

**케이스 10. 문서 버전/개정 불일치**
- 계약서는 2024년 개정본, 설명서는 2021년 양식이면 항목 구성 자체가 안 맞을 수 있음
- "설명서에 없는 항목이 계약서에 있다"가 실제로는 버전 차이일 수 있음

## 3. 케이스 → 처리 방향 요약

| 그룹 | 케이스 | 처리 방향 |
|---|---|---|
| A 매칭 | 1 의미 매칭 | LLM semantic matching |
| A 매칭 | 2 1:N 분산 | 항목별 다중 소스 수집 후 종합 |
| A 매칭 | 3 참조 지정 | 참조 해석(별지/별표 연결) |
| A 매칭 | 4 false match | 문맥 기반 판단, 확신도 표기 |
| A 매칭 | 5 표 vs 서술 | 구조별 추출기 분리 |
| B 판정 | 6 수식·조건부 | 값 정규화 + 의미 동등성 판단 |
| B 판정 | 7 표기 체계 | 매핑 테이블 |
| C 정의 | 8 외부 필수항목 | 필수항목 정의 외부 주입 |
| C 정의 | 9 조건부 필수 | 상품 유형별 필수 규칙 |
| D 품질 | 10 버전 불일치 | 문서 버전·기준일 확인, 경고 처리 |
