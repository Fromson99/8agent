ID1000은 없다는 정정에 따라 문서·구조·본문·원문ID는 확인된 ID50으로, 게시/자료/그룹ID는 기존 ID100으로 맞췄다. 한글 내용3열은 기준1000×3=물리3000 BYTE를 분리 표기하고 이미BYTE로 기재된 문서명2250은 유지했다. 13표60열·PK·일반인덱스와 원천 문자열 의미를 보존하며 실측 초과0을 확인했다. DB/제품/MAIN/GENOS 반영은 미수행이다. R12/R13은 과거 작성·발송본으로 보존한다.

**최신 축소 설계 R12 — 2026-10-29:** 사용자 요청으로 [13표·60컬럼 안](../07_DOCS/REFERENCE/REPORTS/DATAIKU_GOLD_COMPACT_20261029_R12/DESIGN.md)을 작성했다. R10 기존49열+벡터11열이며 R11 대비28열 축소다. FTS는 기존 SRCH_ROW를 재사용하고 모델·판본·건수·입력 해시는 JSON에서 검증한다. 검색용 문서/원문 ID·일반 인덱스·HEAD PK/변경순번은 유지한다. 아래 R11의16표/88열은 이전 제안이며 전용 FTS3표·기존표 추출3열은 R12에 적용하지 않는다. 문서 변경만 수행했으며 개발계·제품·MAIN/GENOS와 실제 Oracle 성능은 별도다.

**2026-10-29 골드 재설계 후보:** 사용자 후속 사진과 소프트 FK·벡터 골드 포함 요청에 따라 [R11 설계서·등록 엑셀](../07_DOCS/REFERENCE/REPORTS/DATAIKU_GOLD_REDESIGN_20261029_R11/DESIGN.md)을 작성했다. R10의 B03/B05·ONTL·POST 및 기존49컬럼을 유지하고, 기존표 추출3컬럼·벡터3표·전문검색3표를 더한 최종16표/88컬럼이다. Gold는 PK/NOT NULL·일반 인덱스를 유지하고 물리 FK/업무 CHECK/PK 외 UNIQUE/함수 인덱스 대신 게시 전 코드 검증을 사용하도록 설계한다. 벡터의 활성 선택은 별도 HEAD PK와 변경순번으로 관리한다. 연결 ID·권한·원문 판본·해시 검증은 유지한다. **문서 설계이며 실제 생성/코드 전환은 미수행이다.** 현행 개발 SIDDS/SIDDA 계약을 일괄 변경하지 않는다. native VECTOR/ANN의 현장 지원·승인은 별도이며 성능 향상을 인증하지 않는다.

**향후 골드 레이어의 테이블·컬럼 설계와 생성 신청은 이 규약을 따른다.** 출처는 사용자가 제공한 사진 1~4의 내부 문서 **「AI데이터플랫폼 (AI데이터허브) 골드레이어」**다. 사진 1~2는 표준화·문자열 타입·등록 절차, 사진 2~3은 테이블 Description, 사진 4는 컬럼 Description 및 운영 테이블 생성 관련 댓글을 담고 있다. 화면에 안내된 참고 자료는 `삼성증권_메타마이너 사용자 가이드_v0.9.pptx`이며, 같은 날 가이드의 7~11·20~23쪽 사진 9장과 12~18쪽 사진 7장이 추가 제공되었다. 이어서 **골드 테이블 목록·Bizmeta·등록 대상·컬럼 정의의 엑셀 화면 사진 7장**이 추가되었다. PPTX·XLSX 파일 자체는 미제공이다. 아래는 사진에서 읽을 수 있는 규약을 정리한 것으로, 잘린 댓글이나 미제공 페이지의 내용은 추정하지 않는다. **[내용 정리·원본 사진 27장·출처 목록](../07_DOCS/REFERENCE/ARCHITECTURE/DATAIKU_GOLD_METADATA_20261022/README.md)**에 네 사진 묶음을 구분해 보관했다.

**추가 가이드의 설계 기준:** 표준용어는 등록된 표준단어로 `수식어 + 도메인` 형태를 구성하고 의미가 같은 기존 용어를 재사용한다. 단어는 명사형을 기본으로 하며 약어·동의어·금칙어를 표준사전에 맞춘다. 한글 용어명에는 띄어쓰기·언더바·특수문자와 변경을 유발하는 부서명·회사 상호를 사용하지 않는다. 해당 업무의 표준사전을 조회해 기존 표준을 활용하고, 없는 표준은 메타마이너의 신청·검토·승인 후 모델링에 사용한다. 가이드 9쪽·10쪽의 `이메일`/`E-mail` 예시 불일치는 상세 문서에 보존했으며 실제 승인 표준사전 확인 대상으로 남긴다.

**후속 12~18쪽의 설계 기준:** 물리명은 등록된 영문 약어를 대문자·숫자로 조합하며, 가이드는 용어 한글명·영문명 각각 최대 **30바이트**를 규정한다. 복합어·도메인 포함 조합의 우선순위와 길이 제한용 복합어의 예외를 따른다. 금액의 통화·단위, 일자·일시·일, 번호와 ID 예외를 구분하고 도메인을 타입·길이·정밀도에 연결한다. 코드 종류(일반·참조·개별)와 유형(일반·연관)을 구분하며 코드명·코드ID 중복 금지, 표준단어로 구성한 코드값명, 현업 코드 우선·문자형 일련번호·자리수와 선행 `0` 보존을 반영한다. 12쪽의 문자 제한 문구와 `TDNG_CNT` 예시의 언더바 차이, 30바이트 산정 문자셋·실제 DDL 매핑은 확인 사항으로 남긴다. 사진의 예시 타입·코드 재번호화를 현재 데이터에 일괄 적용하지 않는다.

#### 설계·명명·등록

- AI 에이전트의 지식 조회는 **골드 레이어만 참조**하도록 설계하고, 개발 초기부터 골드 모델을 정한다. 위의 **에이전트 레이어에 질의·판단·실행 로그를 보존하는 책임**은 그대로 유지한다. 지식 조회 대상과 실행 기록 저장 대상을 구분한다.
- **메타마이너**에서 표준화된 데이터 모델을 등록·관리하고, 등록된 테이블의 비즈니스 정보는 **데이터포탈**에서 추가·관리한다. 표준화를 적용하기 어려우면 Data거버넌스팀과 협의하며, 비표준인 경우에도 메타정보 작성·관리는 필요하다.
- 테이블 모델에는 테이블 정보를 작성한다. **표준용어는 컬럼명에 매핑**하며, 용어는 데이터 타입을 결정하는 **도메인 단어로 끝나야 한다**. 용어를 구성하는 **표준단어는 용어사전에 등록한 뒤 사용**한다. 여기서 전사 메타 표준용어·단어와 법령 RAG의 도메인 용어집은 목적이 다르므로 동일 등록부로 간주하지 않는다.
- DW 등에서 유입되는 정형 원천은 기존 표준화를 활용하고 메타 설명을 보강한다. 비정형 원천도 가능한 한 메타마이너를 사용해 표준 논리명·물리명으로 설계·관리한다.
- 신규 용어 등록 시 **기존 인포타입을 우선 사용**한다. `VARCHAR` 길이는 필요한 길이 이상의 가까운 기존 인포타입을 선택하고, 적합한 타입이 없으면 별도로 문의한다.
- 메타마이너 등록 정보는 **주말 배치 이후 데이터포탈에서 조회 가능**하다는 안내를 따른다. 그 전에 조회가 필요하면 담당 부서에 문의한다.
- 사진 4의 운영 안내에 따르면 **운영 골드 테이블은 메타마이너에서 테이블·컬럼 정보를 등록하고 DBA에 생성 신청**한다. 골드 이외의 테이블은 Dataiku에서 생성할 수 있다고 안내되어 있다. 개발 중 Silver에 둔 테이블도 운영 이관 시 성격에 따라 Gold·Temp·Agent를 구분하며, 개발용 위치를 운영 저장 책임으로 그대로 확정하지 않는다. 본 프로젝트의 구조화 데이터·온톨로지·`llm_wiki`와 실행 로그 배치는 위 레이어 기준을 따른다.

#### 문자열 타입·한글 길이

사진에 제시된 **해당 ADB 환경의 운영 규약**으로 적용한다. 다른 DB·문자셋의 일반 규칙으로 확대하지 않는다.

| 항목 | 적용 기준 |
|---|---|
| Dataiku 자동 생성 문자열 | `NVARCHAR`로 생성될 수 있으므로 **명시적으로 `VARCHAR`로 수정**한다. 사진은 `NVARCHAR`가 영문에도 2바이트를 사용하며 메타마이너에서는 허용하지 않는다고 안내한다. |
| 한글 저장 길이 | ADB 문자셋은 DW와 달리 한글에 **3바이트**가 필요하다는 안내다. 기존 메타 표준용어를 사용해도 한글 포함 컬럼은 기존 길이 대비 **1.5배가 필요할 수 있음**을 반영한다. |
| 기존 표준용어와 길이 조정 | 등록된 표준용어를 사용하되 한글 길이 조정 등 변경 사항은 모델 신청 시 **별도 설명과 수정 DDL을 첨부**해 생성 요청한다. |

물리 DDL을 작성할 때 실제 컬럼의 길이 단위(BYTE/CHAR)와 적용 문자셋을 확인해 위 규약을 반영한다. 사진의 타입 표기를 이 저장소의 모든 Oracle 컬럼에 일괄 치환하거나, 모든 문자열 길이를 일괄 1.5배 확대하는 데이터 이행 지시로 해석하지 않는다.

#### 테이블 Description 필수 작성 항목

메타마이너에는 일반 텍스트로 입력하며, 데이터포탈에서는 Markdown으로 입력할 수 있다는 안내다. 사진의 주식 체결 테이블은 **작성 양식의 예시**다. 예시의 PK·기간·갱신 시각·집계식은 우리 법령·온톨로지 테이블의 값으로 사용하지 않는다.

| 항목 | 각 테이블에 작성할 내용 |
|---|---|
| 요약 | 어떤 업무의 어떤 정보를 담는 테이블인지 |
| grain | **1행이 뜻하는 단위**와 PK |
| 답할 수 있는 질문 | 이 테이블로 실제 조회·분석할 수 있는 질문과 범위 |
| 포함·제외 | 포함하는 대상, 제외하는 대상·상태·예외 |
| 기간 | 보유 기간과 조회 가능한 기준 시점 |
| 갱신 | 갱신 주기·시각, 반영 완료 기준, 당일 데이터 포함 여부 |
| 산식 | 파생 값의 계산식, 금액·수량 등 단위, 포함·제외 비용 |
| 원천 | 원천 시스템·테이블과 결합하는 데이터 |
| 주의 | 중복 집계 방지, 고유 개수 계산 기준, 날짜·휴일 등 해석상 주의점 |
| 오너 | 소유·관리 부서명 |
| 예시 질의 | 실제 업무 질문과 이에 대응하는 SQL |

### 서빙 데이터 저장 금지 — 사용자 명시 2026-10-19

사용자가 "서빙쪽에는 데이터를 저장하면 안됨"을 명시했다. GENOS 코드서빙에 원문·용어·관계·색인을 전체 복제하거나 로컬 SQLite/파일/영속 볼륨에 보관하는 구조를 최종 운영안으로 사용하지 않는다. 서빙은 Oracle 또는 승인된 조회 API에 조건·판본·접근 범위를 전달하고, 필요한 결과만 받아 요청 처리 중 일시적으로 사용한다. 요청 간 재사용을 위한 데이터 캐시도 서빙 내부에 추가하지 않는다.

**사용자 변경(2026-11-06):** 질문마다 같은 게시 자료를 Oracle에서 다시 읽어 느린 문제로, 서빙 **프로세스 메모리**에 게시 자료 캐시를 두는 것을 허용했다("해당 코드서빙에 캐시 올려두는게 어때" → "싹다 해주고 메인에 반영해줘"). 대상은 고정한 릴리스의 내용 해시 기반 게시 표(원문·구조·검색 행·릴리스 명세)를 읽는 SELECT뿐이다. 채널 포인터·요청 상태·Agent 기록·온톨로지/벡터 현재 상태·시스템 뷰·시각 함수 SQL은 매번 Oracle로 보낸다. 서빙 디스크에는 쓰지 않는다. `GENOS_ORACLE_SHARED_CACHE=on|off`(기본 on), `GENOS_ORACLE_SHARED_CACHE_MIB`(기본 512). 구현 `02_BACKEND/semantic_runtime/oracle_shared_cache.py`, 로컬 MAIN167. 원문 전체 내려받기·로컬 SQLite 복원 금지는 그대로다.

기본 캐시는 Oracle DB 내부의 데이터 블록 캐시이며 DB 운영 영역이다. 별도 조회 결과 캐시는 성능 측정으로 필요성이 확인될 때 서빙 밖의 데이터 계층에서 검토하고, 데이터 버전·조회 조건·권한 범위·갱신/무효화 정책을 결속한다. Redis 등 특정 제품의 설치·사용 가능성은 확인되지 않았다. 서빙의 대화/실행 상태 보존도 필요한 범위를 외부 저장소에 연결해야 하며, 기존 로컬 상태 소비자는 별도 점검 대상이다.

Dataiku는 수집·구조화·용어 연결·색인·검증한 버전 게시를 담당하고, Oracle에서 검색·관계 탐색·원문 조회가 가능하도록 테이블과 조회 경로를 연결해야 한다. SQLite 색인 파일을 Oracle 자산 테이블에 보관한 것만으로 Oracle 직접 검색이 구현된 것은 아니다. 갱신은 새 버전의 게시 완료 후 신규 요청이 그 버전을 선택하고, 진행 중인 요청의 버전 결속을 유지하는 방향으로 설계한다.

**작업 코드 전환 — 2026-10-19:** `service.py`의 `DP=oracle`은 `oracle_query_service.Factory`로 연결되어 Oracle 원문·검색·관계를 요청별로 조회한다. 기존 `oracle_dp.resolve()` 전체 복원 유틸리티는 서빙에서 호출하지 않으며 SQLite 모드는 보존한다. Dataiku가 게시한 불변 query release와 활성 채널 revision을 요청 시작에 고정한다. 원문·색인 데이터의 파일/SQLite 복제와 요청 간 데이터 캐시는 없고, 실행 이력·로그는 명시한 외부 NFS/CIFS를 사용한다. 외부 마운트가 없으면 로컬에 쓰지 않고 실패한다. 로컬 Oracle 23과 모의 모델로 서비스 연결을 검사했으며, 실제 현장 ORDS·NFS·모델·배포 성능은 미검증이다. Oracle STATE 테이블의 CAS 포트도 제공하지만 기존 이력 소비자는 NFS에 유지한다. 이 작업은 선택 포인터·GENOS 리비전을 변경하지 않았다. 완료 시 별도 ADR-0917의 MAIN88 선택을 확인했으며 그 릴리스에는 새 Oracle 조회 모듈이 없다. 문서: 내부·외부 RAW → 전체 구조 복원 → 원문·좌표·버전 저장 → 명시 원문 통합
```text
용어집: 기존 사전 + 통합 문서의 정의 후보 → 기존 미검토·신규 후보 통합 검토
  → 검토된 초안으로 전체 용어 출현 연결 + 문서 정의 + 명시 조문 참조
  → 설정한 LLM의 모호한 참조 해소·자동 승인 → 탐색 색인
  → 용어 탐색 → 원문 확인 → 부족한 근거에 따른 추가 탐색/질문 → 답변
  → 실행·원문 세대에 연결된 피드백 후보
```

의미 추출로 문장을 Rule·조건·효과로 재작성하는 단계는 없다. 에이전트는 원문을 읽고 판단 상태를 생성한다. 용어 관계와 정의는 탐색 단서이며 법적 결론을 자동 확정하지 않는다.

Docling 모델을 다시 실행하지 않는다. [연결·실행 계약](../07_DOCS/REFERENCE/OPERATIONS/GENOS_PREPROCESSOR_PARSING.md).

GENOS의 공유 NFS 색인 세대 교체와 코드서빙 RAG 모델·출력 토큰 설정은
[세대 교체 서빙 계약](../07_DOCS/REFERENCE/OPERATIONS/GENOS_RAG_GENERATION_HANDOFF.md)에 기록한다.

2026-09-21 사용자 지시로 **작업 코드의 MAIN 기본 RAG는 `legal-agent-tools-v2`**로 연결했다. 기존 HTTP → Pipeline → 요청 세션 → Coordinator/StageRunner → outbox를 유지하며 도구 선택·정확 READ·현재 입력 전달·원문 평가·검토/반론 재진입을 수행한다. 내부 계약과 journal은 v2, 외부 Request/Result는 term-runtime-v1이다. 기본 모델 프로필은 미결속이며 실제 모델 요청에는 명시 설정이 필요하다. [배선·설정·복구](../07_DOCS/REFERENCE/OPERATIONS/TOOL_EXPLORATION_V2.md). 합성 계약 검증과 모델 품질/현장 검증은 구분한다.

2026-09-21 당시 로컬 활성 포인터는 `document-navigation-rag-20260921-v1`, generation 17, quality_certified=false였다. 현행 선택은 문서 상단의 2026-09-23 전환과 ACTIVE_RELEASE를 따른다. 해당 과거 frozen release와 명시 호환 경로의 `document-navigation-v1`은 질문을 목록·트리·목차·내용·매핑으로 먼저 해석한다.
문서 목록·폴더 트리·목차는 저장된 메타데이터로 답하고, 내용 질문만 여러 원문 읽기·검토·종합으로 넘긴다.
GENOS에서는 `GENOS_RAG_IMPLEMENTATION`으로도 명시 선택한다. [GENOS 반입·계약](../07_DOCS/REFERENCE/OPERATIONS/GENOS_DOCUMENT_TOOLS.md).

[현재 배선·운영 계약](../07_DOCS/REFERENCE/OPERATIONS/NAVIGATION_MAIN.md).

로컬 MAIN 릴리스 및 포인터의 최종 상태는 [문서 탐색 배선 기록](../09_ARTIFACTS/AUDITS/20260917-document-navigation-main-wiring/README.md)과 `01_DATA/ACTIVE/local/ACTIVE_RELEASE.json`을 따른다. 직전 탐색 루프 릴리스는 [탐색 루프 배선 기록](../09_ARTIFACTS/AUDITS/20260916-navigation-main-wiring/README.md)에 보존한다. 코드 변경·Git main 병합·데이터 세대 선택·로컬 MAIN 활성화·GENOS 배포는 각각 별도 상태다.

- 원문 159문서의 ID·본문·구조·해시를 그대로 새 원문 전용 세대로 옮겼다.
- 기존 의미 테이블·projection은 새 세대로 복사하지 않았다. 과거 세대·ADR·릴리스는 보존한다.
- 정의의 원문 블록과 해시를 검증하고, 인용·준용은 원문에 명시된 조문 표기를 색인한다. 구조 좌표가 완전한 단순 범위는 규칙으로 확장하고, 외부 문서·약칭·문맥·복수 후보는 검토 전까지 미확인으로 둔다.
- 원문·용어집·코드 변경은 새 세대와 색인을 만든다. 기존 파서 캐시는 사용한 파서 지문이 같을 때만 재사용한다.
- 품질 인증은 `false`다. 이번 변경의 검사는 구조·계약·배선 검사이며, 법률 답변 품질 통과를 의미하지 않는다.

전체 파이프라인 실험은 입력·설정·모델·프롬프트·코드와 변경하지 않은 단계도 함께 고정한다. 원문 근거·버전·감사·롤백·접근권한을 보존한다. 피드백에서 재구축·검증·MAIN 채택까지의 자동 루프는 미완성이다.

현행 구축 단위와 의존성은 `PIPELINE.json.authorities.document_build` 및 [실행 안내](../07_DOCS/REFERENCE/OPERATIONS/GENOS_FOUR_STAGE.md)를 따른다. 내규도 `RAW/internal`에서 형식별 처리한다. 구조화 단독 실행은 용어집을 읽지 않는다.

추가 문서의 통합 서빙 후보는 `TERM_RELEASES/<run>`에 생성한다. `document-release`가 동일 실행 명세의 후속 단위이며 활성화는 명시적 CURRENT CAS/롤백 절차다. [추가 문서 연결 계약](../07_DOCS/REFERENCE/OPERATIONS/GENOS_DOCUMENT_CONNECTIONS.md). 작업 코드의 이 연결은 기존 로컬 활성 릴리스나 GENOS 배포를 변경하지 않는다.
