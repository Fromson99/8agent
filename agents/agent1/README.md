# agent1 — 신탁계약서 ↔ 투자설명서 대사

**입력은 파일 두 개, 출력은 대사 리포트다.**

```bash
.venv/bin/python agents/agent1/src/cli.py run \
    --contract    agents/agent1/data/golden/contract_filled.pdf \
    --prospectus  agents/agent1/data/B1055656A.pdf \
    -o agents/agent1/output/agent1.report.json
```

앞단(용어 등록 · 형식 만들기)은 문서 종류당 한 번이고 이미 자산으로 있다.
런타임에 사람이 하는 일은 파일 두 개를 주는 것뿐이다.

## 1. 전체 아키텍처

```
 ┌─ 준비 (문서 종류당 1회) ────────────────────────────────────────────┐
 │  glossary/*.glossary.yaml    용어 등록 — section 용어 / fact 용어      │
 │  formats/*.format.json       마커 선언 — 반복은 정규표현식, 제목은 용어  │
 │  tasks/*.yaml                대사 규칙 — 어느 구역 ↔ 어느 구역          │
 └───────────────────────────────┬─────────────────────────────────────┘
                                 │ 자산으로 고정
 ┌─ 런타임 (파일 두 개 in → 리포트 out) ──────────────────────────────┐
 │                                                                   │
 │  계약서.pdf ─┐                                                     │
 │              ├─▶ ① 파싱·구조화   결정론   docling → section 트리      │
 │  설명서.pdf ─┘                            + fact                   │
 │                     │                                             │
 │                     ▼                                             │
 │              ② 범위 좁히기     결정론   rule 이 지정한 section 만       │
 │                     │                  꺼내 **증거 표**로 (ID 부착)   │
 │                     ▼                                             │
 │              ③ 판정           LLM     증거 표를 보고 값 대조          │
 │                     │                  근거는 **증거 ID 로만** 가리킴  │
 │                     ▼                                             │
 │              ④ 출처 되돌리기   결정론   증거 ID → page/bbox/cell       │
 │                     │                  없는 ID → 판정 무효화         │
 │                     ▼                                             │
 │              ⑤ 집계·리포트                                          │
 └───────────────────────────────────────────────────────────────────┘
```

### 왜 이렇게 나눴나

**세부 규칙으로 값 하나를 정확히 집어내려 들면 문서마다 규칙이 늘어난다.** 실제로 그렇게
늘어났었다 — 값 꼬리 길이 상한, 라벨 전용 줄 처리, 셀이 용어로 시작하는가… 임계값이
하나씩 붙을 때마다 "형식을 컴파일해서 stochastic 을 가둔다"는 설계가 무의미해진다.

그래서 역할을 갈랐다.

| 단계 | 누가 | 무엇을 |
|---|---|---|
| 좁히기 | 코드 | `제2부/13. 보수 및 수수료에 관한 사항` 안만 본다 |
| 고르기 | LLM | 그 안에서 어느 줄이 "총 보수"인지 |
| 출처 | 코드 | 증거 ID → 실제 page/bbox/cell |

"총 보수"는 66쪽 설명서에 여러 번 나오지만 그 구역 안에서는 후보가 손에 꼽는다.
**좁히는 일은 좌표가, 고르는 일은 판단이 한다.**

### 출처는 LLM 이 만들지 않는다

증거 표의 모든 줄에 `e-017` 같은 ID 를 붙여 넘긴다. 판단자는 **그 ID 로만** 근거를
가리킬 수 있고, 코드가 ID 를 실제 출처로 되돌린다.

```
LLM 이 "e-017" 이라고 답함
  └→ 코드가 되돌림: 제2부/13. 보수 및 수수료에 관한 사항, p35,
                    표 행 [2,0], bbox [101.81, 686.01, 554.76, 694.07],
                    "수수료선취-오프라인(A) | 0.30 | 0.30 | 0.02 | 0.00 | 0.62 | …"
```

출처 정밀도는 **문서 → 구역 → 쪽 → 행 → 화면 좌표**까지다. docling 이 논리 셀마다
bbox 를 주므로 행을 감싸는 사각형을 계산해 싣는다. 좌표계 함정이 하나 있다 —
**셀 bbox 는 TOPLEFT, 표 prov 는 BOTTOMLEFT** 기준이라 섞어 쓰면 세로가 뒤집힌다.
셀 원본을 그대로 두고 `origin` 을 함께 실어 쓰는 쪽이 해석하게 했다.

표에 없는 ID 를 대면 그 근거는 버리고 경고를 남기며, 양쪽 근거가 갖춰지지 않은
`MATCH`/`VALUE_MISMATCH` 는 `NEEDS_REVIEW` 로 강등한다 — **근거 없는 확정 판정은 나가지 않는다.**

> SPEC.md §4.1 과 AGENT1_SPEC §1 은 "판정에 LLM 금지"를 규정한다. 이 구성은 그 규정을
> 의도적으로 뒤집었고(사용자 결정), 대신 출처 위조를 막는 장치를 뒀다.

## 2. 실제 문서에서 어떻게 구체화됐나

### 입력

| | 파일 | 실측 |
|---|---|---|
| 계약서 | `contract_filled.pdf` | 7쪽, 값이 채워진 체결본 |
| 투자설명서 | `B1055656A.pdf` | **66쪽, 66,939자**, born-digital |

### 형식 — 측정으로 만든 것

투자설명서의 부 헤더는 **목차(p2~4)와 본문(p12~64)에 각각** 나온다.

```
p 2  제1부 모집 또는 매출에 관한 사항      ← 목차
p12  제1부. 모집 또는 매출에 관한 사항     ← 본문 (마침표)
```

패턴 `^제(\d+)부\.\s*(.+)$` 의 **마침표가 목차를 배제**한다. 감이 아니라 측정으로 확인했다.

항목 헤더는 더 까다로웠다. 순진한 `^(\d+)\.\s*(.+)` 는 같은 페이지의
`2011. 2.18`(연혁 날짜)과 `0.30`(요율)까지 전부 삼킨다. 조인 패턴:

```
^(\d{1,2})\.\s+([^\d\s].*)$
  \d{1,2}    4자리 연도 배제
  \s+        공백 강제 → "0.30" 배제
  [^\d\s]    제목이 숫자로 시작하지 않음
```

본문 p12~66 에서 **38건 적중, 오탐 0**.

### 구조화 결과

```
투자설명서   section 106개   fact 99개   잔여 0   게이트 91%
   표지 / 요약정보(p2,p8) / 제1~6부 / 제2부 아래 항목 14개
   제2부/13. 보수 및 수수료에 관한 사항   p35~37, content 34개 (표 4개)  ← 핵심
계약서       section 97개    fact 64개   잔여 0   게이트 100%
   본문/제1~32조 / 별지1 / 별지2
   별지1/신탁계약 세부내역               p5, 표 content              ← 핵심
```

### 파서 기준선 비교 (AGENT1_SPEC T-A1.2)

스펙은 "docling 은 pdfplumber 기준선 **이상일 때만** 교체"를 요구한다. p35 보수표로 비교:

| | pdfplumber | docling |
|---|---|---|
| 골든 값 (A/총보수) | 0.62 ✓ | 0.62 ✓ |
| C클래스 총보수 | 1.32 ✓ | 1.32 ✓ |
| 신탁업자보수 | 0.02 ✓ | 0.02 ✓ |
| 병합 2단 헤더 | 문자열 격자 — **forward-fill 필요** | 논리 셀 + span — **forward-fill 불필요** |
| 주석 표(주1~3) | 잡음 | 놓침 (fact 없음, 영향 없음) |

docling 채택. 부모 라벨 `지급비율(연간,%)` 이 이미 한 셀로 오고 span 이 덮는 열을 알려주므로,
스펙 §4-2단의 forward-fill 알고리즘이 **필요 없어졌다.**

### 좁혀진 범위가 실제로 어떻게 넘어가는가

`--term "총 보수"` 로 좁힌 결과 (LLM 에 그대로 전달되는 표):

```
[투자설명서] 범위: 제2부/13. 보수 및 수수료에 관한 사항
| 증거ID | 쪽 | 위치 | 내용 |
|  | p35 | 표 헤더 | 지급비율(연간,%)  /  클래스종류 | 집합투자 업자 보수 | 판매회사 보수 |
|              신탁업자 보수 | 일반사무 관리회사 보수 | 총 보수 | 동종유형 총 보수 | … |
| e-017 | p35 | 표 | 수수료선취-오프라인(A) | 0.30 | 0.30 | 0.02 | 0.00 | 0.62 | 0.79 | … |
| e-018 | p35 | 표 | 수수료후취-오프라인(B) | 0.30 | 0.70 | 0.02 | 0.00 | 1.02 | - | … |
| e-019 | p35 | 표 | 수수료미징구-오프라인(C) | 0.30 | 1.00 | 0.02 | 0.00 | 1.32 | 1.15 | … |
```

66쪽 문서에서 **49행**으로 좁혀졌고, 그중 3행이 답을 담고 있다.

## 3. LLM 판정 결과 (실행 실측)

```
계약서    contract_filled.pdf
투자설명서 B1055656A.pdf
판정      claude-opus-5
게이트    계약서 1.00 (통과) / 설명서 0.91 (통과)
LLM 호출  5회   입력 31,582 · 출력 2,089 토큰   오류 0
```

| 용어 | 판정 | 계약서 값 | 설명서 값 | 행 기준 |
|---|---|---|---|---|
| 기본보수 | `SOURCE_EXTRACTION_FAILED` | 기타특약사항에 기재 (요율 미기재) | **A 0.62** | ✓ 확인됨 |
| 수익보수 | `MISSING_IN_TARGET` | 연 3% 초과 이익의 15% | — | 확인 불가 |
| 중도해지수수료 | `SOURCE_EXTRACTION_FAILED` | — (공란 서식) | 90일 미만 이익금의 100분의 70 | — |
| 신탁기간 | `MISSING_IN_TARGET` | 2024.6.3 ~ 2027.6.2 | — | — |
| 신탁금액 | `NEEDS_REVIEW` | 100,000,000원 | 모집총액 10조좌 | — |
| 계좌번호 | `NOT_APPLICABLE` | — | — (규칙에 선언) | — |

```
총 6건 — 대조 0 (맞음 0 / 틀림 0)
  보류 1  누락 2  정답추출실패 2  해당없음 1
```

### 판정의 질 — 근거를 보면 판단이 보인다

**기본보수 → 보류 (임의 선택 거부)**

> 계약서의 기본보수는 구체적 요율 없이 '기타특약사항에 기재'로만 되어 있고(e-006),
> 설명서는 클래스별로 총보수가 0.62/1.02/1.32%로 나뉘어 있어(e-017~e-019)
> 단일 값 대조가 불가능하다.

세 후보를 **모두 인용하고 하나를 고르지 않았다.** AGENT1_SPEC §3 의 `AMBIGUOUS` 요구 —
"같은 section 에서 복수 매칭되고 값이 다르면 임의 선택 금지" — 가 그대로 지켜졌다.

**중도해지수수료 → 정답추출실패 (신뢰 비대칭)**

> 계약서의 중도해지수수료 항목(e-009, e-010)은 체크박스와 기간·요율이 모두 공란인
> 미기재 서식이어서 비교할 값을 확정할 수 없고 …

설명서 쪽에는 값이 있는데도 `MISSING_IN_TARGET` 이 아니라 `SOURCE_EXTRACTION_FAILED` 로
갔다. **정답 쪽 실패는 검증 결과가 아니라 시스템 경고**라는 AGENT1_SPEC §6 의 신뢰 비대칭이
동작했다. 둘을 뭉갰다면 "설명서에 없다"는 잘못된 결론이 나갔을 것이다.

**신탁금액 → 해당없음 (층위 구분)**

> 계약서의 개별 신탁금액 100,000,000원(e-002)과 투자설명서의 모집·매출 총액 10조좌
> (e-072~e-074)는 층위가 달라 직접 대조 대상이 아니다.

숫자가 다르다고 `VALUE_MISMATCH` 를 찍지 않았다.

### 행 기준(`row_anchor`) — 값을 뽑지 않고 검증만 한다

p35 보수표는 클래스별로 총 보수가 다르다(A 0.62 / B 1.02 / C 1.32). 앵커를 넣기 전에는
LLM 이 **셋 다 인용하고 보류**했다 — 올바른 동작이지만 자동화가 되지 않는다.

```yaml
target:
  section_any_of: ["제2부/13. 보수 및 수수료에 관한 사항"]
  term: 총 보수
  row_anchor: "수수료선취-오프라인(A)"    # 이 값으로 셀을 뽑지 않는다
```

앵커가 하는 일은 두 가지다.

1. **판단자에게 알려준다** — "이 행만 본다"
2. **고른 행이 그 행인지 코드가 대조한다** (`verify_row_anchor`, 결정론)

앵커로 셀을 직접 찍지 않는 이유는 조용히 틀리기 때문이다. 이 표 한 장에도
`총 보수` / `동종유형 총 보수` / `총 보수·비용` / `합성 총 보수·비용` 이 함께 있어
부분일치가 흔하고, 병합 헤더에서 열 오프셋이 밀리며, p8 요약박스처럼 레이아웃 격자를
표로 오인할 수도 있다. **그리고 앵커가 틀려도 그럴듯한 값 하나가 나올 뿐 신호가 없다.**
그래서 뽑기는 판단자에게 맡기고 코드는 대조만 한다 — 어긋나면 확정 판정을 보류로 강등한다.

앵커 도입 후 실제 변화:

```
기본보수  NEEDS_REVIEW  → SOURCE_EXTRACTION_FAILED
          후보 3개 인용   → e-017 하나만 인용 (A 0.62)
          !  행 기준 '수수료선취-오프라인(A)' 확인됨 ('수수료선취-오프라인(A)')
```

**앵커가 대상 쪽을 하나로 좁히자, 남은 문제가 계약서 쪽이라는 게 드러났다** — 계약서
기본보수는 "기타특약사항에 기재"라 요율 자체가 없다. 판정이 `NEEDS_REVIEW`(둘 다 애매)에서
`SOURCE_EXTRACTION_FAILED`(정답 쪽 문제)로 정확해졌다.

수익보수 행은 앵커를 확인할 수 없었고(`근거에 표 행이 없어 …`), 그 사실이 리포트에 남는다.

### 표 크기 실측 — 왜 표를 통째로 넣는가

실물 66쪽 설명서의 표 73개를 재보면:

```
행 수 중앙값 4
  1-5행    58개  ██████████████████████████████████████████████████████████
  6-10행    9개  █████████
  11-20행   5개  █████
  21+행     1개  █
```

**80%가 5행 이하다.** 앵커로 찍을 크기가 아니라 통째로 넣을 크기다. 지금 구성이
표 전체를 증거 표로 넘기는 이유이고, 좁히기는 section 이 이미 해준다.

### 출처 위조 검사

```
지어낸 근거 경고: 없음
```

LLM 이 댄 증거 ID **전부가 실제 표에 있었다.** 리포트의 모든 page/bbox 는 코드가
되돌린 값이지 LLM 이 쓴 값이 아니다.

### 이 결과를 어떻게 읽어야 하나

**대조 0건 — 맞음도 틀림도 없다.** 이건 실패가 아니라 이 문서 쌍의 성질이다.
`contract_filled.pdf` 는 특정금전신탁 **개별 계약서**이고 `B1055656A.pdf` 는 집합투자기구
**투자설명서**다. 같은 상품의 짝이 아니라 대조 가능한 항목이 거의 없다. 시스템은 그걸
"틀렸다"가 아니라 `NOT_APPLICABLE` / `MISSING_IN_TARGET` / `SOURCE_EXTRACTION_FAILED` 로
갈라 보고했다 — 오탐 0건이라는 점이 이 실행의 성과다.

**진짜 검증은 같은 상품의 (계약서, 설명서) 쌍이 필요하다.** 그 쌍이 들어오면 같은
파이프라인이 그대로 돌고, 그때 맞음/틀림 집계가 의미를 갖는다.

## 5. 남은 것

- **같은 상품의 (계약서, 설명서) 골든 쌍이 없다.** 지금 쌍은 상품이 달라 대조 항목이
  거의 없다. 맞음/틀림 집계의 의미는 그 쌍이 들어와야 생긴다.
- **판정이 결정론이 아니다.** 같은 입력을 두 번 돌리면 문구가 달라질 수 있다.
  AGENT1_SPEC §8-5(바이트 동일)는 지금 구성에서 성립하지 않는다.
- **행 안의 어느 칸인지는 여전히 LLM 이 읽는다.** 좌표는 행까지고, `0.62` 가 5열이라는
  정보는 리포트에 없다. `Table.cell_at(row, col)` 은 넣어뒀으니 열 앵커를 붙일 수는 있지만,
  행 앵커와 같은 이유(부분일치·오프셋)로 검증기로만 쓰는 게 맞다.
- **범위 상한 80행.** 넘으면 잘라내고 리포트에 `truncated` 로 남긴다. 조용히 자르진 않지만
  잘린 곳에 답이 있었을 가능성은 남는다.
- **비용.** 문서 쌍 하나에 LLM 5회, 입력 31.6k 토큰. rule 이 늘면 선형으로 는다.
