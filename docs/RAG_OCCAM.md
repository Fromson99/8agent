# 실마리 RAG 오컴 감사

## 원칙

단계를 많이 거치거나 LLM을 많이 부르는 것이 안전성은 아니다. 각 단계는 독립된
골든 이득, 오염 차단, 법적 완전성 중 하나를 입증해야 유지한다. 같은 정본 데이터를
두 LLM이 연속해서 해석하거나, 결과를 바꾸지 않는 재호출은 제거한다.

반대로 근거 주소 바인딩, 닫힌 후보 목록, 실제 사실문 공동출현, 명시적 행위 불일치
차단은 대조 실행에서 제거 시 오염이 확인됐으므로 유지한다.

## 2026-08-24 DB 역매칭 QueryGuide A/B

기존 질문 단독 Span 분해와, 질의 문자열에 실제로 맞은 Document·Section·Concept·
저자 정의·본문 조각 해석을 함께 보여 주는 `QueryGuide`를 한 변수로 비교했다.
같은 문자열 해석은 OR, 서로 다른 선택 Span은 원문 좌표 AND다. 문서·조문이 잡힌
경우 그 범위 출현 0인 의미 후보는 프롬프트에서 제거했다.

| 판 | 지표 | 기존 OFF | QueryGuide ON | 판정 |
|---|---|---:|---:|---|
| 독립 홀드아웃 검색 50건 | 양성 기대 좌표 재현 | 100% | 100% | 동일 |
| 독립 홀드아웃 검색 50건 | 호출 / 입력 / 출력 | 121 / 229,374 / 11,745 | 112 / 229,388 / 13,589 | 호출 -7.4%, 입력 동일, 출력 +15.7% |
| 독립 홀드아웃 검색 50건 | 지연 p50 / p95 | 3.76초 / 15.43초 | 3.78초 / 11.22초 | 꼬리 지연 감소 |
| 실제 답변 E2E 10건 | 법률 명제 / 조문 / 정밀 근거 | 10/10 · 10/10 · 10/10 | 10/10 · 10/10 · 10/10 | 동일 |
| 실제 답변 E2E 10건 | 과잉 근거 / 공유 상한 초과 | 0/10 · 0% | 1/11 · 10% | 안전 회귀 |
| 실제 답변 E2E 10건 | 호출/건 · 입력/건 | 4.4 · 21,118 | 4.5 · 24,422 | 비용 증가 |

검색 단품 비교기는 `mixed_more_efficient`, E2E 비교기는 `regressed`로 판정했다.
따라서 기능과 A/B 스위치는 유지하되 기본값은 OFF다. 검색 호출 감소만 보고 켜면
전체 답변 단계의 근거 과잉을 놓치므로, 다음 판단은 최소 3 trial의 E2E 반복에서
과잉 근거가 재현되는지 확인한 뒤 내린다.

## 검증 이름과 서열

`Concept 골든`은 **Concept 진입 부품검사**로 이름을 낮춘다. 질문에서 승인
Concept/OQL 근거 주소로 들어가는지만 검사하며, 최종 답·최종 인용·포섭·출력 잘림은
검사하지 않는다. 부품검사 통과를 전체 RAG 통과라고 보고하지 않는다.

현재 제품에는 서로 다른 두 실제 흐름이 있다.

1. **질의응답 E2E**: 운영 `/ask mode=vector`와 같은 쟁점 재작성 → 공용 검색 채널 →
   확장·회복 → 최종 답·인용을 검사한다.
2. **법률검토 E2E**: 사실 추출 → 쟁점 → 전용 규범 회수 → 요건 → 포섭 → 최종
   방향·basis를 검사한다.
3. **전체 프로세스 판정**: 위 두 E2E manifest를 합쳐 품질, 채널·단계 관측,
   데이터 준비율, 사건 수와 반복 trial을 동시에 검사한다.
4. **부품검사**: Concept 진입, source-shadow, 홀드아웃은 고장 위치를 찾는 보조 자다.

두 제품 흐름은 검색 배선이 다르다. 특히 법률검토는 현재 공용 `vecfirst`를 호출하지
않으므로 Concept·승인 키워드·문서 동반 스위치의 기여를 법률검토 러너로 측정할 수
없다. 이 스위치들은 반드시 질의응답 E2E에서 A/B한다.

릴리스 판에는 두 흐름 각각 최소 51개 고유 사건과 3 trial을 요구한다. 현재는

### 유효한 한 변수 실험

Concept가 실제 진입한 `/ask` 고정 명제 10건에서만 `concept_entry` 하나를 껐다.
같은 답을 재사용하지 않고 검색부터 최종 합성까지 다시 실행했다.

| 실행판 | 법률 명제 | 기대 node 회수·인용 | 최종 근거 과잉 | 호출/건 | 입력/건 | 제품 LLM 총 지연 |
|---|---:|---:|---:|---:|---:|---:|
| 기준 | 10/10 | 10/10 · 10/10 | 10/20(50.0%) | 4.8 | 36,214 | 161.8초 |
| Concept OFF | 10/10 | 10/10 · 10/10 | 13/23(56.5%) | 4.0 | 29,204 | 98.0초 |

이번 10건에서는 Concept의 최종 명제·정답 근거 순증가가 0이었고, OFF가 호출 16.7%,
입력 19.4%, 제품 LLM 지연 39.4%를 줄였다. 반면 과잉 근거율은 6.5%p 나빠졌다.
따라서 즉시 삭제가 아니라 51건 반복판에서 ‘정밀 근거 개선이 비용을 정당화하는가’를
다시 본다.

`/ask` 사건형 8건에서 승인 키워드 OFF는 정답 조문 회수를 90%→70%, 과잉 근거를
30.0%→53.3%로 악화시켜 유지한다. 문서 동반 OFF는 최종 컨텍스트 p95를 32→12,
입력을 56,071→45,063/건으로 줄였지만 정답 조문 회수가 90%→80%로 떨어졌다.
삭제 대신 `expand.doc_companion_max=20`을 낮추는 A/B가 다음 실험이다.

사건형 기준판에서는 Concept가 한 번도 진입하지 않았다. 그 판의 Concept OFF 결과
차이는 LLM 변동일 뿐 Concept의 인과 효과가 아니다. 또한 법률검토 러너로 돌렸던
Concept·키워드·문서 동반 OFF 네 판도 배선상 스위치가 회수에 닿지 않아 모두 무효다.
과거 표와 그에 근거한 채널 결론은 폐기했다.

### 부품검사가 드러낸 별도 결함

면접위원 제척 문항의 실제 제18조는 ‘이해관계가 있는 면접위원을 해당 지원자의
면접에서 제척’한다는 뜻이다. 과거 질문은 면접 대상자를 제척한다고 잘못 적혀 있어
틀린 node 76·77을 정답처럼 통과시켰다. 질문과 정답 node 74를 바로잡은 뒤 Concept
진입 부품검사는 정직하게 49/50이며, 이 한 건은 아직 미해결이다. 골든 자체의 의미
오류도 전체 검증 실패로 취급해야 한다.

법률검토 최초 기준 실행에서는 캐시에 없는 용어 17,547개를 CPU BGE-M3로 질의 중
컴파일해 첫 사건이 15분 넘게 멈췄다. 질의 중 컴파일을 금지하고 정확 문자열은 모두,
의미 이웃은 준비된 벡터만 사용하게 했다. 배치에서 `RAG_LEXICON_COMPILE_MISSING=1`로
완성하기 전까지 준비율 52.5%를 E2E readiness 실패로 남긴다.

## 제거·축소한 것

### 후보 카드 중복 정보

이전 Composer 입력은 후보마다 대표명·종류·발견 표현 외에도 정의, Assertion ID,
문서 전체 경로, 원문 두 개를 반복했다. 정본 Concept 42,435개 중 정의가 있는 것은
1개뿐이어서 `definition`은 사실상 빈 필드였다. 근거 주소는 질문 단위로 이미 확정되어
Assertion ID와 경로도 중복이었다.

현재는 대표명·종류·발견 표현·가능한 사실 자리와 첫 실제 문맥 하나만 보낸다.

- 어려운 10문항 입력: 143,781 → 73,063토큰(-49%)
- 블라인드 50문항 입력: 과거 두 실행 합계 570,692 → 344,380토큰(-40%)
- 10문항 결과: 8/10 → 9/10
- 블라인드 결과: 47/50 기준에서 축약 단회 48/50

### 후보 확대 재호출

8개 후보로 조립하지 못하면 12개로 넓혀 두 번째 호출하던 `EXPAND`를 제거했다.
블라인드 50문항에서 양성을 한 건도 회수하지 않았고, 작은 기준선에서는 틀린 문단
차단 문항을 오염 진입시키며 34,827 입력토큰을 썼다. 이제 조립 결정은 `SELECT`와
`NO_MATCH` 둘뿐이다.

### 같은 Frame 데이터의 중복 LLM

Concept 정본은 이미 Frame에서 승인·발행한 사실문을 포함한다. Concept가 근거를 찾은
질문에 다시 Frame 추출 LLM을 부르는 것은 같은 데이터를 두 번 해석하는 경로다. Frame
진입은 Concept가 빈손일 때만 실행한다. Concept가 다루지 못하는 넓은 질문에서는 기존
Frame 회수율을 그대로 보존한다.

### 효과가 약한 선택 호출

- 간선 항해는 과거 벡터 질의 164회 중 1회 호출되고 선택 0건이어서 기본 꺼짐으로
  바꿨다. 기능은 실험 스위치로 남긴다.
- 검색 전 쟁점 분해와 검색 후 쟁점 판정을 동시에 켠 활성 override를 제거했다.
  검색 후 판정은 원래 기본 꺼짐이며, 필요할 때만 비교 실험으로 켠다.

## 유지한 것

| 단계 | 유지 이유 |
|---|---|
| 근거 주소 검문 | 틀린 법령·조·항의 유사 사실문 진입을 결정론적으로 막음 |
| 닫힌 후보·개념 번호 검문 | LLM이 새 개념이나 자유 OQL을 만들지 못하게 함 |
| 종류·자리·사실 합류 검문 | 같은 단어만 겹친 다른 사실문 오염을 막음 |
| 명시적 행위 불일치 차단 | 완전 제거 시 반대 행위 차단이 12/12→8/12로 하락 |
| Frame 진입 폴백 | 과거 실제 질의에서 회수 구역 인용률 44%로 독립 기여가 있음 |
| 벡터 진입 | 패러프레이즈와 정본 미발행 영역의 최종 넓은 회수 채널 |
| 법적 필수 동반 | 배제·위임·준용·정의·제재 누락은 답 방향 자체를 바꿀 수 있음 |

과거 173개 질의 로그의 구역별 인용률은 벡터 37%, 프레임 44%, 승인 용어 2.8%,
정의 동반 0.9%, 문서 동반 5.6%였다. 낮은 인용률만으로 법적 필수 동반을 지우지는
않지만, 일반 후보 채널은 앞으로 이 수치와 골든 순증가를 함께 입증해야 한다.

## 남은 개선 순서

1. 채널 미세조정보다 먼저 `/ask` 사건형의 방향 37.5%·정밀 basis 70%와 법률검토의
   방향 50%·과잉 basis 57.9%를 문항별로 분해한다. 현재 병목은 Concept 부품점수가
   아니라 최종 판정과 근거 선택이다.
2. 질문 기억은 승인 데이터 0행인 동안 `미준비`로 표시한다. 실제 승인 데이터를
   만들 계획이 없다면 `memory_entry` 기본 ON과 채널 자체를 제거 후보로 올린다.
3. 문서 동반 상한 20을 12·8·4로 낮추는 한 변수 `/ask` E2E를 실행한다. 완전 OFF에서
   정답 조문 회수가 10%p 떨어졌으므로 삭제 실험은 끝났다.
4. Concept OFF는 고정 명제 10건에서 비용 이득과 과잉 근거 악화가 함께 나왔다.
   새로운 사건·구어·다중 조건을 포함한 51건, 최소 3 trial에서 다시 판정한다.
5. `review.issues` 8,000토큰 및 `rag.recover.descend.jo` 400토큰 잘림을 재현 문항으로
   고정하고, 출력 확대 전에 스키마·후보 수를 줄인다.
6. 용어집 벡터 캐시를 배치에서 완성하고 준비율 100% 판과 현재 52.5% 판을 비교한다.
7. 면접위원 제척 실패는 행위뿐 아니라 객체·상대 연결 문제다. 새 LLM을
   추가하기 전에 기존 단서와 선택 Concept의 표면·사실 자리 일치를 강화한다.
8. 두 흐름 각각 51개 고유 사건·3 trial을 채우고 평균뿐 아니라 최악 trial, 잘림률,
   채널·단계 커버리지까지 통과한 뒤 기본 스위치를 바꾼다.

## 성능 손잡이 감사

프롬프트 밖의 자름·개수·문턱 89개를 `lawrag/core/rag/controls.py`에 등록했다.
각 행은 단계, 단위, 회수율·정밀도·비용 위험, 실제 소유 모듈을 가진다. 골든 실행
manifest에는 값 전체와 16자리 설정 지문이 들어가므로 구조 변경 전후가 실제로 같은
조건인지 확인할 수 있다. 전체 흐름과 다이어그램 계약은 `docs/RAG_FLOW.md`에 있다.

AST 정적 감사도 함께 둔다. 현재 런타임 RAG·법률검토 경로에서 등록부 밖 숫자 후보는
210개다. 이 중 142개는 화면·로그용 문자열 발췌를 포함한 숫자 슬라이스이고, 32개는
이름 붙은 숫자 상수, 36개는 `max_tokens/topk/cap` 같은 호출 예산이다. 전부를 성능
손잡이로 오인해 자동 이관하지 않고 파일·줄·종류·값을 검토 원장으로 출력한다.

현재 자동 감사에서 나온 중요한 구조 충돌은 다음 네 가지다.

- Concept 4 + 기억 4 + 승인 용어 2 + Frame 최대 4 + 벡터 4가 가산되어 진입은
  이론상 18구역이다. 기존 주석의 “전체 상한 12”와 맞지 않았다.
- 문서 동반은 공유 풀 밖에서 최대 20구역을 추가한다. 거친 최종 상한은 38구역이다.
- Concept 원시 의미 풀은 단서 12 × 후보 8 × 배수 5로 질문당 최대 480행이다.
- 38구역 × 6000자를 단순 곱한 본문 거친 최악치는 228,000자다. 중복과 짧은
  구역 때문에 실측은 작겠지만 p50/p95를 반드시 기록해야 한다.

12를 바로 강제하거나 문서 동반을 바로 삭제하지는 않았다. 이는 결과를 바꾸는 구조
수정이므로 최종 답변 통합 골든에서 한 변수 A/B로 회수 이득과 토큰·지연을 확인한 뒤
결정한다.

## 평가 규약과 A/B 사용법

평가 방법과 측정축은 `lawrag/core/rag/evaluation.py`가 정본이다. 동결 골든,
개발 홀드아웃, 최초 블라인드, source-shadow, 한 변수 제거, 축별 슬라이스, 반복 실행,
비용·지연 측정을 같은 manifest 스키마로 관리한다.

### 현업 핵심 골든 — 최종 성능의 기준판

`data/review/cm_core_e2e_v1.json`은 CM본부가 실제 업무에서 사용한 질의응답
DOCX를 동결한 최종 RAG 골든이다. 원문에는 질문 표식이 52개, 직접 답변이 51개다.
첫 질문은 1.1~1.4를 묶는 제목성 질문이라 평가에서 제외하되 삭제하지 않고 제외 사유를
보존한다. 평가 51건은 다음을 한 행에 같이 가진다.

- 원문 질문 `source_question`과 업무 문맥을 붙인 실행 질문 `question`
- 당시 실제 답변 전문 `reference_answer`
- 결정적 법령·조문 `expected_articles`와 동결 당시 문서 좌표
- 업무영역·질문형태·답변형태·주소 범위·현재 재료 상태 슬라이스

원문 SHA와 51개 질문-답변 쌍은 먼저 읽기 전용으로 검증한다.

```bash
.venv/bin/python scripts/cm_core_golden.py
```

기준판을 실행하고 공통 manifest로 고정한다.

```bash
.venv/bin/python scripts/ask_e2e_golden.py \
  --suite data/review/cm_core_e2e_v1.json \
  --out var/eval/e2e/cm_core_baseline.raw.json
.venv/bin/python scripts/review_eval_manifest.py \
  var/eval/e2e/cm_core_baseline.raw.json \
  var/eval/e2e/cm_core_baseline.manifest.json \
  --suite data/review/cm_core_e2e_v1.json --flow ask --label cm-baseline --trial 1
```

구조 수정판도 같은 suite SHA와 같은 51건으로 실행한다. raw와 manifest 모두
`question`·`reference_answer`·`system_answer`를 함께 기록하므로, 점수뿐 아니라
실제로 어떤 답이 나와 왜 맞거나 틀렸는지 다시 읽을 수 있다.

```bash
.venv/bin/python scripts/ask_e2e_golden.py \
  --suite data/review/cm_core_e2e_v1.json \
  --out var/eval/e2e/cm_core_candidate.raw.json --query-guide
.venv/bin/python scripts/review_eval_manifest.py \
  var/eval/e2e/cm_core_candidate.raw.json \
  var/eval/e2e/cm_core_candidate.manifest.json \
  --suite data/review/cm_core_e2e_v1.json --flow ask --label cm-candidate --trial 1
.venv/bin/python scripts/rag_eval_compare.py \
  var/eval/e2e/cm_core_baseline.manifest.json \
  var/eval/e2e/cm_core_candidate.manifest.json --one-variable
```

최종 판정은 51건 전수 3회 반복의 의미 정확도, 조문 회수율, 최종 근거 회수율,
과잉 근거율과 지연 p50/p95를 본다. 현재 코퍼스에 없는 조문은 `material` 슬라이스에서
별도로 원인 귀속하며, 전체 점수에서 몰래 제외하지 않는다.

전체 판정은 실제 제품 흐름 manifest만 합친다.

```bash
.venv/bin/python scripts/ask_e2e_golden.py \
  --suite data/review/e2e_pilot_v1.json --out var/eval/e2e/ask.raw.json
.venv/bin/python scripts/review_golden.py \
  --suite data/review/e2e_pilot_v1.json --out var/eval/e2e/review.raw.json
.venv/bin/python scripts/review_eval_manifest.py var/eval/e2e/ask.raw.json \
  var/eval/e2e/ask.manifest.json --suite data/review/e2e_pilot_v1.json --flow ask
.venv/bin/python scripts/review_eval_manifest.py var/eval/e2e/review.raw.json \
  var/eval/e2e/review.manifest.json --suite data/review/e2e_pilot_v1.json \
  --flow legal_review
.venv/bin/python scripts/rag_e2e_portfolio.py \
  --out var/eval/e2e/portfolio_current.json
```

Concept 진입 부품검사는 전체 판정이 아니라 고장 위치 확인에만 쓴다.

```bash
.venv/bin/python scripts/concept_golden.py --no-shadow
```

비교기는 suite SHA와 case 순서가 다르면 A/B를 무효로 처리한다. 찾아야 할 근거
회수율, 막아야 할 오염 차단율, 근거 좌표 정확도, 오염률은 회귀 게이트다. 호출 수,
입출력 토큰, TTFT, 총 지연 p50/p95는 비용 축으로 따로 보고한다.

채널 한계 기여는 현재 설정에서 한 스위치만 바꾼 실행판으로 잰다. Concept·질문
기억·승인 용어·Frame·벡터·문서 동반·쟁점 재작성·재회수·정의·제재의 10개 판이
등록돼 있다.

```bash
.venv/bin/python scripts/rag_ablation_plan.py --output-dir var/eval/ablation
.venv/bin/python scripts/rag_eval_compare.py BASE.json CANDIDATE.json --one-variable
```

`--one-variable`은 숫자 손잡이와 엔진 스위치를 합쳐 차이가 정확히 하나가 아니면
비교를 무효 처리한다. 채널 A/B에는 공용 채널이 실제로 연결된 `ask_e2e_golden.py`를
쓴다. 두 러너는 실행 당시 설정 스냅샷을 raw에 직접 남기므로 나중에 다른 설정으로
manifest를 변환해도 실행 조건을 잃지 않는다.
