# 지시사항서 — 온톨로지 기반 문서 파싱 & 정합성 검증 파이프라인

> 이 문서는 Claude Code가 단독으로 구현할 수 있도록 작성된 자립형 스펙이다.
> 배경 대화 없이 이 문서만으로 작업을 시작할 수 있어야 한다.
>
> **아키텍처 원칙:** 이 파이프라인은 **온톨로지(제약) 기반**이다. 문서 종류와 무관한 **범용 인스턴스 계층**(추출된 fact) 위에, 도메인별 **선언적 제약 계층(온톨로지)** 을 얹어 검증·해석한다. Part A/B에 등장하는 스키마 고정·태깅 규칙·정합성 규칙은 전부 이 제약 계층에 속하는 공리(axiom)이며, §C에서 하나의 선언적 온톨로지로 통합한다. 새 문서 종류 대응 = 코드가 아니라 **온톨로지 파일 교체**.
>
> **Part A (§1–§12)** — 계약서 PDF를 구조화된 청크+태그 JSON으로 파싱·태깅한다(인스턴스 계층 생성).
> **Part B (§B1–§B13)** — 그 결과를 기준으로 투자요약서가 별지1의 값을 올바르게 담고 있는지 검증한다.
> **Part C (§C1–§C12)** — Part A/B의 제약을 하나의 선언적 온톨로지 계층으로 통합한다.
> **Part D (§D1–§D4)** — 같은 기반 위의 검색 소비자: 임베딩 없는 결정론 라우터(fact 직조회 + facet 필터 + BM25 + refs 확장).

## 0. 구현 순서 (빌드 오더) — 온톨로지 우선

아래 순서가 **스케줄링 기준**이며, 각 Part의 서술 순서(A→B→C)보다 우선한다. 도메인 모델(온톨로지)을 먼저 세우고 A/B가 그 위에서 동작하도록 구현하면 리팩터 비용이 최소가 된다. 각 단계는 `ss2207_special_trust.pdf`(구조)와 값이 채워진 골든 쌍(정합성)으로 즉시 검증한다.

1. **온톨로지 파일 + 로더** (C: T14) — 도메인 모델을 먼저 선언. `ontology/trust_contract.ontology.yaml` + `ontology.py`.
2. **Parse + 구조 복원** (A: T1–T3) — 인스턴스 계층 골격(파트 분리, 조/항/호 트리).
3. **청킹** (A: T4).
4. **온톨로지 구동 태깅** (A: T5 + C: T15) — role/topic/level/refs를 하드코딩이 아니라 온톨로지에서 로드해 채움.
5. **fact 검증** (C: T16) — 인스턴스 계층을 온톨로지에 대해 검증(타입·카디널리티·shape).
6. **(선택) LLM 세부역할 / 텍스트 공리 추출** (A: T6 + C: T17) — 플래그 뒤, 기본 off.
7. **Fact 추출 레이어 + 요약서 파서** (B: T8–T9) — 양쪽 문서를 공용 Fact로.
8. **매핑 · 비교기 · 정합성 엔진** (B: T10–T13) — 온톨로지의 `fields`(source_of_truth·equals·aliases)를 읽어 수행.
9. **(선택) 검색 소비자** (D: T21–T24) — 정합성과 독립적인 병렬 소비자. fact 조회 API(T22)는 T8에 의존하므로 7 이후 착수.

> 의존 원칙: 도메인 지식은 항상 온톨로지 파일에서 온다. A의 태깅 규칙과 B의 정합성 규칙은 코드에 상수로 박지 않는다(§C 완료 기준).

## 1. 프로젝트 개요

한국어 금융 계약서(특정금전신탁 계약서 유형)의 PDF를 입력받아, **검색·RAG에 쓸 수 있는 구조화된 청크(chunk) + 의미 태그 JSON**으로 변환하는 파이프라인을 만든다.

핵심 산출물은 청크 하나당 다음을 담은 레코드다: `{텍스트 + 구조 위치(조/항/호) + 의미 태그(role·topic) + 참조 간선(refs) + 출처(page/bbox)}`.

동봉된 `trust_contract_chunks_sample.json`이 **목표 출력의 정본(golden reference)**이며, `ss2207_special_trust.pdf`가 **1차 테스트 입력**이다. 두 파일은 저장소에 함께 둔다.

---

## 2. 입력 / 출력 정의

- 입력: `.pdf` 1개 이상. v1은 **born-digital(텍스트 레이어 존재) PDF만** 대상으로 한다(스캔 문서는 범위 밖, §10 참조).
- 출력: 입력 PDF 하나당 `{stem}.chunks.json` 1개. 스키마는 §4, 예시는 `trust_contract_chunks_sample.json`.
- 출력은 pydantic 모델로 검증한 뒤 직렬화한다(§9).

---

## 3. 대상 문서의 구조적 특징 (도메인 지식)

이 유형 문서는 다음 세 덩어리로 구성된다. 파서는 이 세 파트를 구분해야 한다.

1. **본문 계약서** — `제1조 ~ 제N조`. 계층은 `조 → 항(①②③…) → 호(1. 2. 3.)`. 대부분 단일 컬럼 산문이며 읽기 순서가 자명하다.
2. **[별지1] 세부내역** — 사용자가 값을 채우는 입력 양식(표). 병합 셀이 많고, "신탁자금 운용방법 1~24" 체크박스 그리드가 있다. **오른쪽에 `계약서제N조` 열이 있어 각 입력 필드가 본문 조항에 명시적으로 연결된다.**
3. **[별지2] 변경계약서** — 또 다른 입력 양식(표).

중요한 관찰:
- 본문의 상호참조가 촘촘하지만 **전부 명시적**이다: `제3조에서 정한`, `제2조 제2항에 따라`, `[별지1]` 등. 정규식으로 거의 다 추출된다.
- `조 제목`이 곧 그 조의 의미 주제다: `제2조(신탁금액)` → topic = 신탁금액. 따라서 **태깅 상당수가 규칙 기반(결정론적)으로 처리 가능**하다.

## 4. 태그 스키마 (2축 facet)

의미 태그는 트리가 아니라 **직교 2축**으로 모델링한다. 같은 `topic`(조)이 본문과 별지에 각각 나타나며 `role`만 다르다.

필드 정의:

| 필드 | 값 / 형식 | 채우는 방법 |
|---|---|---|
| `chunk_id` | 문자열, 고유 | 생성 규칙 (예: `body-a15-p1`, `app1-field-amount`) |
| `role` | `약관본문` \| `별지1_입력` \| `별지2_변경` | 문서 파트에서 결정 |
| `level` | `조` \| `항` \| `호` \| `필드` \| `표` | 파싱 위치 |
| `article` | `제N조` | 본문: 조 헤더 / 별지: `계약서제N조` 링크 |
| `article_title` | 조 제목 | 조 헤더 괄호 안 |
| `clause` | `①`~`⑳` (선택) | 항 단위 청크일 때 |
| `topic` | `{article_title}({article})` | 결정론적 조합 |
| `heading_path` | 문자열 배열 | 파트 → 조 → 항 순 |
| `refs` | 문자열 배열 | 정규식 추출 (§7) |
| `cross_ref_explicit` | 문자열 (선택) | 별지 표의 `계약서제N조` 셀 |
| `provenance` | `{page:int, bbox:[x0,y0,x1,y1]|null}` | 파서 출력 |
| `text` | 문자열 | 청크 본문 |
| `items` / `options` / `table_options` | 배열 (선택) | 호 리스트 / 체크박스 그리드 / 다단 표 |

정본 스키마와 6개 대표 레코드는 `trust_contract_chunks_sample.json` 참조. 구현은 이 파일의 구조를 그대로 재현해야 한다.

## 5. 파이프라인 아키텍처

5단계. 각 단계는 독립 모듈로 만들고 단독 테스트 가능해야 한다.

1. **Parse** — Docling으로 PDF → 구조화 요소(텍스트/제목/표) + 읽기 순서 + provenance. born-digital이면 텍스트 레이어를 그대로 사용(OCR 금지 — 한국어 법률 용어 재인식 오류 방지). 근거: 본문은 텍스트 레이어가 깨끗하므로 추가 인식이 불필요하고, 승부처는 별지 표뿐이다.
2. **Structure** — 본문 요소를 `조 → 항 → 호` 트리로 복원. 파트(본문/별지1/별지2) 분리.
3. **Chunk** — **순수 의미 단위 청킹, 토큰 예산 없음.** 본문은 조 단위 기본, 조가 매우 길면 항 단위로 분할(조 경계 절대 넘지 않음). 별지는 표/필드 단위. 임베딩을 사용하지 않으므로(§D 참조) 토큰 크기 조정(HybridChunker의 split/merge refinement)은 불필요하다 — 분할 기준은 오직 의미 경계(조/항/필드)다.
4. **Tag** — role/topic/level/refs를 규칙 기반으로 채움. LLM은 기본 off, 플래그로만 세부 의미역 보강.
5. **Emit & Validate** — pydantic 검증 후 JSON 출력.

도구 선택 근거(요약): 병합 셀 표 + 추적성(provenance) 요구 때문에 **단일 패스 VLM을 주 추출기로 쓰지 않는다.** Docling은 텍스트 레이어 활용 + 표 구조 인식(TableFormer) + provenance를 한 번에 준다. 청킹은 온톨로지의 `structure` 청크 선언을 읽는 자체 구현으로 하며(의미 단위만, §D 결정에 따라 토큰 refinement 불필요), HybridChunker는 쓰지 않는다. 별지 표 인식이 약하면 PP-StructureV3(PaddleOCR, CJK 표 강점)를 별지 페이지에만 보조로 붙인다.

## 6. 구현 작업 (순차, 증분)

각 태스크 완료 시 `ss2207_special_trust.pdf`로 즉시 검증하고 다음으로 넘어간다.

- **T0. 스캐폴딩** — 저장소 구조(§11), pydantic 스키마 모델, CLI 진입점(`parse.py <pdf> -o <out.json>`).
- **T1. born-digital 판별 + Parse** — PyMuPDF로 텍스트 레이어 유무 확인. Docling으로 변환해 요소 리스트(type, text, page, bbox, reading_order)로 정규화. 별지 표는 셀 구조를 보존.
- **T2. 파트 분리** — `[별지1]`, `[별지2]` 마커/페이지 기준으로 본문·별지1·별지2를 나눈다.
- **T3. 본문 구조 파싱** — 조/항/호 정규식(§7)으로 트리 복원, heading_path 생성.
- **T4. 청킹** — 의미 단위 청킹만: 본문 조/항 청크(온톨로지 `structure`의 chunk 선언을 읽어 실행) + 별지 표/필드/체크박스 청크. 토큰 기반 split/merge 없음.
- **T5. 규칙 기반 태깅** — role(파트), article/article_title/topic(조 헤더), level, refs(정규식), 별지 cross_ref_explicit로 topic 링크.
- **T6. (선택) LLM 태깅** — `--llm-roles` 플래그. 고정 enum + structured output(JSON schema)으로 세부 의미역만. temperature 낮게, 유효 라벨만 허용. 기본 비활성.
- **T7. 출력·검증** — pydantic 검증, JSON 직렬화, §9 완료 기준 통과.

## 7. 구조 인식 어댑터 (recognizers) & 엣지 케이스

> **인식(recognition) ≠ 제약(constraint).** 이 절의 패턴들은 원문 텍스트·레이아웃을 먹어 fact를 만들어내는 **추출 구현**이지 도메인 규칙이 아니다. "무엇이 참이어야 하는가"(제약·구조 모델)는 전부 온톨로지(§C)에 선언적으로 있고, 이 절은 그 선언을 **이 PDF 포맷에서 어떻게 알아보는가**만 다룬다. 판별 기준: 이미 추출된 fact에 대고 검사할 수 있으면 제약(→온톨로지), 원문을 먹어 fact를 만들면 인식(→여기).
>
> 정규식은 인식의 한 가지 구현일 뿐이다. 온톨로지가 구조를 추상적으로 선언하면(§C6 `structure`: "조는 번호+제목을 갖고 항→호를 포함", "별지 필드는 cross-ref로 조에 대응"), 그것을 만족시키는 방법은 정규식이든 레이아웃 단서든 LLM이든 어댑터가 고른다. 정규식에 묶이지 말 것.

정규식 예시(파이썬 기준 — 온톨로지 `structure` 선언을 이 문서에서 실현하는 recognizer. 실제 문서로 검증·보정):
- 조 마커 인식: `^제(\d+)조\(([^)]+)\)` → 번호, 제목 (온톨로지: 조 = 번호 + 제목)
- 항 마커 인식: 원문자 `①②③④⑤⑥⑦⑧⑨⑩⑪⑫⑬⑭⑮…` (U+2460~U+2473)로 시작하는 줄 (온톨로지: 조 contains 항)
- 호 마커 인식: `^\s*(\d+)\.\s` (온톨로지: 항 contains 호)
- ref 멘션 인식: `제\d+조`, `제\d+항`, `제\d+조\s*제\d+항`, `\[별지\d+\]`, `각\s*호` → `refs`에 수집. (제약 "refs는 존재하는 조/별지로 해소돼야 함"은 온톨로지 `properties.refs.range`에 있음 — 여기선 멘션만 찾는다.)
- 별지 링크 인식: 표 우측 셀 `계약서\s*제(\d+)조` → 필드의 `article`/`topic`/`cross_ref_explicit` 설정. (제약 "별지 필드 ↔ 조 대응"은 온톨로지, 여기선 셀 읽기만.)

엣지 케이스(인식 단계의 실무 문제):
- 여러 페이지에 걸치는 긴 조(제5·15·16·22조): 항 단위 분할, 조 경계 유지.
- 항 안의 호 리스트(제16조①, 제23조, 제25조): `items` 배열로 담되 부모 항의 heading_path 상속.
- 별지 병합 셀: 셀 구조 보존이 안 되면 실패 로그를 남기고 해당 페이지만 PP-StructureV3 폴백.
- 체크박스 그리드(운용방법 1~24): `structure: "checkbox_grid"`, 각 옵션 `{no, label, checked}`. 빈 템플릿이면 전부 `checked:false`.
- 라이브러리 API는 버전에 따라 다르므로, Docling 호출부는 **현재 공식 문서를 확인**하고 구현할 것(추측 금지).

## 8. 의존성 / 환경

- Python 3.10+
- `docling`, `pymupdf`(fitz), `pydantic`, (선택) `paddleocr`/PP-StructureV3, (선택 LLM) Anthropic SDK
- Docling은 최초 실행 시 모델을 내려받는다(네트워크 필요). 오프라인 환경이면 사전 캐싱 안내를 README에 남길 것.
- 결정론 확보: 규칙 기반 단계는 외부 호출 없이 동작해야 한다.

## 9. 검증 / 완료 기준 (acceptance criteria)

`ss2207_special_trust.pdf` 입력 기준, 아래를 모두 만족해야 한다.

1. 출력이 pydantic 스키마를 통과한다(모든 청크에 role·topic·level·provenance.page 존재).
2. 본문 제1~32조가 빠짐없이 청크로 존재하고, **어떤 청크도 조 경계를 넘지 않는다.**
3. `trust_contract_chunks_sample.json`의 6개 대표 요소(제2조②, 제15조①·③, 제16조①의 호, 별지1 신탁금액, 운용방법 체크박스)가 정본과 **구조적으로 일치**한다(text는 원문 일치, refs 집합 일치).
4. `제15조①`의 refs가 `{제3조, 제12조, 별지1}`을 포함한다.
5. 별지1의 각 입력 필드가 `계약서제N조` 링크로 올바른 topic에 연결된다.
6. 모든 청크 경계가 의미 경계(조/항/필드/표)와 일치한다 — 문장 중간·항 중간에서 잘린 청크가 없다.
7. `refs`의 모든 항목이 실제 존재하는 조 또는 별지로 해소(resolve)된다(미해소 참조는 경고 로그).

간단한 골든 테스트(pytest)로 3~5번을 자동화한다.

# Part B — 별지1 기준 투자요약서 정합성 검증 (Reconciliation)

## B1. 목적

체결된 신탁계약서의 **`[별지1] 신탁계약 세부내역`에 채워진 값**을 정답(source of truth)으로 삼아, 같은 건의 **투자요약서**가 그 값들을 올바르게 담고 있는지 대조한다. 계약서가 정답이므로 판정은 방향성이 있다 — **요약서 값이 계약서와 다르면 요약서가 틀린 것.**

검증 범위는 계약서 본문 32개 조가 아니라 **별지1의 필드 집합**이다: 계좌번호, 신탁금액, 신탁기간, 운용내역 통지여부, 신탁보수, 이익계산·지급, 중도해지수수료, 운용방법, 세부 운용지시. 본문 조항(약관, role=약관본문)은 값이 아니라 규칙이므로 비교 대상이 아니다.

> 주의: Part A에서 테스트에 쓴 `ss2207_special_trust.pdf`는 **빈 템플릿**이라 별지1 필드가 비어 있다. Part B는 **값이 채워진 체결본**을 대상으로 하며, 요약서와 짝을 이루는 (체결 계약서, 요약서) 쌍이 입력이다. 골든 테스트용으로 값이 채워진 샘플 쌍을 별도 준비한다(§B11).

## B2. 입력 / 출력

- 입력: (1) 체결 계약서 PDF → Part A 파이프라인으로 얻은 `chunks.json`, (2) 투자요약서 PDF.
- 출력: `{stem}.reconcile.json` — 별지1 필드별 대조 리포트(§B9). pydantic 검증 후 직렬화.
- 요약서는 "어느 정도 고정된 표/양식"이다. 값 추출은 규칙 기반 우선, 레이아웃이 흔들리는 부분만 LLM 보조.

## B3. 핵심 원칙

1. **두 문서를 직접 비교하지 않는다.** 양쪽을 각각 정규화된 **fact table**(`{field → 타입값 + 출처}`)로 투영한 뒤, 그 표에서 값을 대조한다.
2. **정답 문서(별지1) 기준으로 순회한다.** "요약서를 훑는다"가 아니라 "별지1 필드를 하나씩 돌며 요약서에 올바르게 있는지" 확인한다. 그래야 정답에 있는 값을 빠뜨리지 않는다.
3. **비교는 코드로, LLM은 추출·정규화·매핑 보조까지만.** LLM을 최종 비교자로 쓰지 않는다(자릿수 누락·환각 위험). 애매하면 auto-pass/fail 하지 말고 `판정 보류`로 뺀다.
4. **오탐은 줄이되 진짜 불일치는 절대 놓치지 않는다** — 이 둘이 상충할 땐 후자를 우선한다.

## B4. 검증 대상 정의

검증 대상 필드 = Part A 출력에서 **`role == "별지1_입력"` 인 청크 전체**. 별도의 필드 목록을 손으로 만들지 않는다. 각 청크는 이미 `topic`과 `계약서제N조` 링크를 갖고 있으므로 그대로 fact의 앵커로 쓴다.

## B5. 필드 매핑 (3층)

요약서 필드명과 별지1 필드명을 짝짓는다. 이름은 **기본적으로 같다고 가정**하고, 예외만 외부 별칭으로 주입한다.

1. **normalize** — 공백·괄호·단위·조사 제거 후 비교 (예: `"신탁 금액"`, `"신탁금액(원)"` → `신탁금액`).
2. **exact match** — 정규화된 이름이 같으면 자동 매핑.
3. **alias 조회** — 못 짝지으면 `aliases.yaml`(§B6, 다대일) 참조.
4. **실패 시 플래그** — 그래도 못 찾으면 조용히 넘기지 말고 `매핑 안 됨(UNMAPPED)`으로 리포트에 한 행 남긴다.

매핑은 "무엇과 무엇을 비교할지"만 정한다. **값이 같은지는 별개 단계(§B7)** 에서 판단한다.

## B6. `aliases.yaml` 포맷

별칭은 코드에 하드코딩하지 않고 외부 설정 파일로 뺀다. 구조는 `별지1_정규필드: [요약서_별칭들]`(다대일). 사용자는 새 요약서 템플릿이 나오면 코드 수정 없이 이 파일만 갱신한다.

```yaml
# aliases.yaml
# key   = 별지1(정답)의 정규 필드명
# value = 요약서에서 같은 의미로 쓰이는 이름들 (여러 개 가능)
version: 1
aliases:
  신탁금액:
    - 투자금액
    - 신탁원금
    - 투자원금
  신탁보수:
    - 보수율
    - 운용보수
  중도해지수수료:
    - 중도상환수수료
    - 해지수수료
  신탁기간:
    - 투자기간
    - 계약기간
```

## B7. 값 비교기 (타입별)

매핑된 필드는 원문 문자열이 아니라 **파싱된 타입값**으로 비교한다. 필드마다 `value_type`을 정하고 그에 맞는 비교기를 쓴다. 오탐의 대부분이 여기서 갈린다.

| value_type | 예시 필드 | 정규화 / 비교 규칙 |
|---|---|---|
| `number` | 신탁금액 | 단위(억·만·원, ₩, 콤마) 정규화 후 Decimal 동일성. 금액은 허용오차 0. |
| `date` | 이익지급일 | KR 포맷(`24년 1월 1일`, `2024-01-01`) → ISO 변환 후 동일성. |
| `date_range` | 신탁기간 | 시작·종료 두 끝점을 각각 date 비교. 한쪽만 있으면 부분 누락으로 표시. |
| `percent` | 신탁보수 | `연 1.5%`, `1.50%`, `1.5` → Decimal 1.5로 정규화 후 비교. |
| `range_tiers` | 중도해지수수료 | 다단 조건 `{구간: 요율}` 구조로 파싱해 구조 비교(구간·요율 쌍 집합). |
| `option_set` | 운용방법 | 체크된 항목의 **집합** 비교(순서 무관). 누락·추가 항목을 각각 검출. |
| `account_no` | 계좌번호 | 구분자(`-`) 제거 후 문자열 동일성. |
| `text` | 기타 | 정규화 문자열 동일성. |

파생값 주의: 요약서의 값이 별지1에 직접 없고 계산으로만 존재할 수 있다(예: 요약서 "만기일" = 별지1 "시작일 + 기간"). 이런 필드는 "동일"이 아니라 **"계산상 일관"** 으로 판정하고, 계산식을 리포트 note에 남긴다.

## B8. 판정(verdict) 5종

- `MATCH` — 매핑됐고 값이 일치.
- `VALUE_MISMATCH` — 매핑됐으나 값이 다름.
- `MISSING_IN_SUMMARY` — 별지1엔 있으나 요약서에 해당 값이 없음.
- `UNMAPPED` — 별지1 필드를 요약서에서 이름으로도 alias로도 못 찾음.
- `NEEDS_REVIEW` — 추출·정규화·매핑이 애매해 자동 판정 불가.

`MISSING_IN_SUMMARY`와 `VALUE_MISMATCH`는 사람이 취할 조치가 다르므로 반드시 구분한다.

## B9. 리포트 스키마

행마다 **양쪽 문서의 provenance를 함께** 실어 사람이 즉시 대조할 수 있게 한다.

```json
{
  "contract": "acct_123.pdf",
  "summary": "summary_123.pdf",
  "generated_at": "…",
  "rows": [
    {
      "field_name": "신탁보수",
      "topic": "신탁보수(제12조)",
      "value_type": "percent",
      "contract_value": "1.5%",
      "contract_source": { "doc": "contract", "page": 5, "bbox": null },
      "summary_value": "1.2%",
      "summary_source": { "doc": "summary", "page": 2, "bbox": null },
      "verdict": "VALUE_MISMATCH",
      "note": ""
    }
  ],
  "stats": { "total": 0, "match": 0, "value_mismatch": 0, "missing": 0, "unmapped": 0, "needs_review": 0 }
}
```

## B10. 구현 작업 (Part A 이후, 증분)

- **T8. Fact 추출 레이어** — 별지1 청크 → 타입값 Fact(`{field_name, topic, value_type, value, raw, source}`)로 정규화. 이 레이어는 계약서·요약서 **양쪽에 재사용**한다.
- **T9. 요약서 파서** — Part A §5 Stage1(Docling/PyMuPDF) 스택 재사용해 요약서에서 필드→Fact 추출. 고정 양식 부분은 규칙, 흔들리는 부분만 LLM 보조.
- **T10. 필드 매핑** — normalize → exact → `aliases.yaml` → UNMAPPED (§B5).
- **T11. 값 비교기** — value_type별 비교기 구현(§B7). 각 비교기는 단위 테스트.
- **T12. Reconciliation 엔진** — 별지1 Fact를 기준으로 순회하며 매핑·비교·판정. 방향성(계약서=정답) 고정.
- **T13. 리포트 출력·검증** — §B9 스키마로 직렬화, pydantic 검증, §B11 완료 기준 통과.

## B11. 완료 기준 (Part B)

값이 채워진 (체결 계약서, 요약서) 골든 쌍 기준으로 아래를 모두 만족한다.

1. **별지1의 모든 필드가 리포트에 정확히 한 행씩** 나타난다. 누락(MISSING)·미매핑(UNMAPPED)도 반드시 한 행으로 남는다(조용한 스킵 금지).
2. 판정은 항상 **계약서 기준**이다(요약서≠계약서 → 요약서 오류로 표기).
3. **포맷 차이가 MATCH로** 나온다: `금 1억원` vs `100,000,000원`, `24.1.1` vs `2024-01-01`, `연 1.5%` vs `1.50%` 는 모두 일치.
4. **실제 불일치는 반드시** `VALUE_MISMATCH` 또는 `MISSING_IN_SUMMARY`로 잡힌다(놓침 0).
5. 최종 판정은 **코드 결정론**으로 이뤄진다. LLM을 썼다면 추출·매핑까지만이고, 판정 로직에는 개입하지 않는다.
6. 모든 행에 양쪽 provenance가 있다(요약서 미기재 시 `summary_source: null` 허용).
7. 골든 테스트(pytest)가 기대 verdict 집합과 일치한다.

# Part C — 온톨로지 (제약) 계층

## C1. 아키텍처 원칙

이 에이전트는 **온톨로지 기반**으로 동작한다. 시스템은 두 계층으로 나뉜다.

- **인스턴스 계층 (범용):** 문서 종류와 무관하게 값·관계·출처를 추출한 fact 집합. Part A의 청크 JSON + Part B의 Fact가 여기에 해당한다. 이 계층에는 도메인 지식이 없다 — 그냥 "무엇이 어디에 있다"만 담는다.
- **제약 계층 (도메인 온톨로지):** 그 fact들을 **검증·해석**하는 선언적 공리 집합. 타입, 열거, 카디널리티, 값 제약, 동치(alias), 교차문서 일치, 텍스트에서 유도한 규칙 등. **문서 종류당 하나의 온톨로지 파일**로 존재하며, 코드가 아니라 데이터다.

핵심 이득: 추출은 범용으로 두고 도메인 지식은 전부 온톨로지 파일에 모으므로, **새 문서 종류 = 새 온톨로지 파일**이지 새 코드가 아니다. Part A/B에 흩어져 서술된 제약들은 모두 이 파일로 승격되어야 하며, `tag_rules.py`(A)와 `reconcile.py`(B)는 제약을 **하드코딩하지 않고 온톨로지에서 로드**한다.

**경계 원칙 — 인식(recognition) vs 제약(constraint):** 모든 규칙을 온톨로지로 빼는 것은 아니다. 원문 텍스트·레이아웃을 먹어 fact를 만드는 **인식/추출 로직(§7의 정규식 등)은 온톨로지가 아니라 어댑터 코드**에 남는다 — 정규식을 YAML에 옮겨 담아도 공리가 되지 않는다. 온톨로지에는 (a) **구조 모델**(무엇이 무엇을 포함하는가, §C6 `structure`)과 (b) **제약/공리**(fact가 만족해야 할 술어)만 선언적으로 들어간다. 판별 기준: *이미 추출된 fact에 대고 검사할 수 있으면 제약(→온톨로지), 원문을 먹어 fact를 만들면 인식(→코드)*. recognizer는 온톨로지의 `structure` 선언을 **읽어서** 동작하므로 구조의 단일 출처는 여전히 온톨로지다.

## C2. 해석 모델

제약의 의미론은 **검증형(validation)** 이다 — SHACL/shapes 계열에 가깝고, OWL 추론(entailment)이 아니다. 즉 온톨로지는 새 사실을 유도하기보다 **fact가 규칙에 부합하는지 검사**하는 데 쓴다(검증 단계에서는 closed-world 가정).

**그래프(RDF)는 필수가 아니다.** 이 2계층 개념은 표현 형식과 독립이다. 기본 구현은 **fact 레코드(JSON) 위에 선언적 규칙(YAML) + pydantic 검증**으로 하고, RDF/SHACL은 나중에 상호운용이 필요할 때의 선택지로 남긴다.

## C3. 기존 제약 → 온톨로지 대응

Part A/B의 규칙들은 이미 공리다. 아래 대응대로 온톨로지 파일에 표현한다.

| Part A/B의 규칙 | 온톨로지 구성요소 |
|---|---|
| `role ∈ {약관본문, 별지1_입력, 별지2_변경}` | 열거 클래스 (enum class) |
| `topic = 조 제목`, `level ∈ {조,항,호}` | 타입/파생 공리 |
| `refs`는 존재하는 조/별지로 해소돼야 함 | object property + range 제약 |
| "청크는 조 경계를 넘지 않음" | 구조 shape |
| "신탁금액은 양수 number 1개" | datatype + 카디널리티 제약 |
| `aliases.yaml` (투자금액 ≡ 신탁금액) | equivalentProperty (sameAs) 공리 |
| "별지1 = 정답, 요약서가 부합" | 방향성 있는 교차문서 일치 공리 |

즉 기존 `aliases.yaml`은 온톨로지 파일에 흡수되거나 그 일부로 참조된다(§C6).

## C4. TBox / ABox 대응 (본문 = 공리, 별지·요약서 = 인스턴스)

facet의 `role` 축이 그대로 지식표현의 TBox/ABox에 대응한다.

- **role=약관본문 (TBox):** 규칙/공리의 출처. 본문 조항은 값이 아니라 제약을 자연어로 서술한다.
- **role=별지1_입력 / 요약서 (ABox):** 공리가 구속하는 인스턴스(실제 값).

따라서 Part B의 정합성 검증은 "TBox(본문 공리) + 정답 ABox(별지1)로부터 만든 제약에, 요약서 ABox가 부합하는지 검사"로 재해석된다.

## C5. 제약의 출처

온톨로지 파일을 채우는 공리는 네 갈래에서 온다. 자동 귀납 가능한 것과 사람이 확정할 것을 구분한다.

1. **구조 제약** — 문서 구조에서 유도(표 헤더 → property, 조마다 번호 1개 → 카디널리티). LLM 초안 + 규칙으로 자동 귀납 가능.
2. **도메인/업무 제약** — 신탁금액>0, 만기>시작일 등. 수는 적고 가치가 큼. 사람이 확정.
3. **교차문서 제약** — 별지1 ≡ 요약서 필드(alias), "별지1=정답" 방향성. Part B에서 옴.
4. **텍스트 유도 공리** — 본문 조항이 서술한 규칙을 추출. 예: 제4조① "수익자를 별도로 기재하지 않을 때에는 위탁자와 수익자가 동일한 것으로 본다" → 기본값 규칙; 제2조① "신탁금액은 [별지1]에 기재된 금액으로 한다" → 동치 공리. LLM으로 후보 추출, 사람이 승인.

## C6. 온톨로지 파일 포맷

문서 종류당 하나. 선언적(YAML). 예시(발췌):

```yaml
# ontology/trust_contract.ontology.yaml
version: 1
doc_type: 특정금전신탁

classes:
  role:  { kind: enum, values: [약관본문, 별지1_입력, 별지2_변경] }
  level: { kind: enum, values: [조, 항, 호, 필드, 표] }

# 구조 모델 — "무엇이 어떻게 중첩되는가"를 선언적으로 기술(서술하듯).
# recognizer(§7)는 이 선언을 이 PDF 포맷에서 실현할 뿐, 여기가 구조의 단일 출처다.
structure:
  조:
    has: [번호, 제목]        # 조는 번호와 제목을 가짐
    contains: 항
    ordinal: true            # 번호는 순서를 이룸
    chunk: primary           # 조 = 기본 청크 단위
    chunk_boundary: hard     # 청크는 이 경계를 절대 넘지 않음 (shape와 동일 출처)
  항:
    contains: 호
    chunk: split_if_long     # 조가 매우 길 때만 항 단위 분할 (의미 경계에서만)
  별지:
    contains: 필드
    field_links_to: 조        # 별지 필드는 cross-ref로 조에 대응
    chunk: per_field         # 별지는 필드/표 단위

properties:
  refs:   { type: object_property, range: [조, 별지] }   # 존재하는 대상으로 해소돼야 함
  topic:  { type: derived, formula: "{article_title}({article})" }

# 별지1 필드 = 검증 대상 (Part B). source_of_truth·equals·aliases가 교차문서 공리.
fields:
  신탁금액:
    value_type: number
    constraints: [">0", "cardinality==1"]
    source_of_truth: 별지1_입력
    equals: 요약서.신탁금액
    aliases: [투자금액, 신탁원금, 투자원금]
  신탁기간:
    value_type: date_range
    constraints: ["end > start"]
  만기일:
    value_type: date
    derived: "신탁기간.start + 신탁기간.duration"   # 계산상 일관으로 판정

# 구조 shape (Part A)
shapes:
  - "no_chunk_crosses_조_boundary"
  - "every_조_has_exactly_one_번호"

# 본문(role=약관본문)에서 유도한 공리 — LLM 후보 추출 + 사람 승인
axioms_from_text:
  - id: 제4조①-수익자기본값
    source: 제4조①
    rule: "if 수익자 is null then 수익자 := 위탁자"
  - id: 제2조①-신탁금액정의
    source: 제2조①
    rule: "신탁금액 == 별지1.신탁금액"
```

## C7. 파이프라인 통합

1. 에이전트는 대상 문서 종류의 온톨로지 파일을 로드한다.
2. Part A 추출로 인스턴스 계층(fact)을 만든다 — 온톨로지 참조 없이 범용으로.
3. fact를 온톨로지에 대해 검증한다(타입·카디널리티·구조 shape). 위반은 리포트.
4. Part A의 태깅(role/topic/level/refs 유효성)은 온톨로지의 클래스·property 정의를 **읽어서** 수행한다.
5. Part B의 정합성 검증은 온톨로지의 `fields`(source_of_truth·equals·aliases)와 `axioms_from_text`를 **읽어서** 수행한다.
6. 새 문서 종류 → 새 온톨로지 파일만 추가. `tag_rules.py`·`reconcile.py`·비교기는 그대로.

## C8. 구현 작업 (Part A/B 리팩터링 포함)

- **T14. 온톨로지 로더/스키마** — YAML 온톨로지를 파싱·검증하는 모델(`ontology.py`). enum·property·field·shape·axiom 표현.
- **T15. A/B를 온톨로지 구동으로 전환** — `tag_rules.py`와 `reconcile.py`가 하드코딩된 제약 대신 온톨로지에서 로드하도록 리팩터. 기존 `aliases.yaml`은 온톨로지 `fields.*.aliases`로 흡수(하위호환 위해 로더가 둘 다 수용).
- **T16. fact 검증기** — 인스턴스 계층을 온톨로지에 대해 검증(타입·카디널리티·shape). 위반 리포트.
- **T17. (선택) 텍스트 공리 추출기** — 본문에서 `axioms_from_text` 후보를 LLM으로 뽑아 사람 검토 큐로. 기본 off.

완료 기준: (1) Part A/B 어떤 제약도 코드에 하드코딩돼 있지 않고 온톨로지 파일에서 온다. (2) 온톨로지 파일 하나만 바꿔 다른 문서 종류를 처리할 수 있다(코드 무변경). (3) fact 검증 위반이 리포트로 나온다.

## C10. 규칙 뭉치 vs 온톨로지 — 추론이 없을 때의 실익 (정직한 정리)

현재 온톨로지는 **제약형(추론 없음)** 이다. 이 상태에서 "그냥 rule을 만드는 것"과 "온톨로지로 관리하는 것"의 차이는 **오늘 시점에선 얇다** — 이 점을 과장하지 않는다. 그럼에도 지금 당장 유효한 이득이 셋 있다.

- **공유 어휘 → 참조 일관성:** 모든 규칙이 온톨로지의 같은 클래스·property·필드명을 참조하도록 강제된다. 임의 규칙 뭉치는 규칙마다 용어를 재발명해 "신탁금액"의 의미가 미묘하게 갈릴 수 있다.
- **한 모델, 여러 소비자:** 같은 온톨로지가 A의 태깅, fact 검증, B의 정합성을 함께 구동한다. 규칙 뭉치는 태스크별로 중복되기 쉽다.
- **단일 출처 + 편집성:** 도메인 지식이 코드가 아니라 한 파일에 있어 사용자가 안전하게 수정·리뷰한다.

핵심 구분: **규칙은 *제약*만 하고, 온톨로지는 *모델링*까지 한다.** `신탁금액 > 0`(규칙 하나)과 `신탁금액 = 금액 타입, 신탁계약 소속, 제2조 대응, 요약서.투자금액과 동치, 그리고 > 0`(그 규칙이 사는 타입·관계 이웃 전체)의 차이다. 이 여분의 구조가 (1) 여러 규칙의 상호 일관성을 유지하고 (2) 향후 추론을 가능케 하는 기반이 된다.

**한계도 명시한다:** 온톨로지의 더 큰 가치(모델 자체의 무모순성 분석, 표준 상호운용, 추론)는 대부분 미래 가치다. 오늘의 실운영 이득은 일관성 + 편집성 수준이며, 그렇기에 **제약형으로 시작하는 것이 옳다.** 온톨로지 프레이밍은 "지금은 일관성, 나중은 추론"이라는 투자다.

## C11. 향후 확장 — 추론(inference) 도입 시 가능한 혁신

제약형은 시작점이다. 도메인을 온톨로지로 **모델링해두면 추론은 재작성이 아니라 증분 업그레이드**로 붙는다. 이 프로젝트(신탁계약서 ↔ 요약서 비교)에 추론이 들어가면 다음이 가능해진다. (미래 페이즈 — 지금 구현하지 않는다.)

1. **파생값 재계산 검증** — 만기일 = 시작일 + 기간(제3조), 중도해지수수료 = 해지금 × 요율 × (잔여일수÷총일수)(별지1), 이익계산(제13조②)을 직접 재계산해 요약서 값이 *계산상 맞는지* 검증. 전사 오류를 넘어 산술 오류 검출.
2. **기본값 추론** — 제4조① "수익자 미기재 시 위탁자=수익자" 같은 default 규칙을 적용해, 요약서 누락을 오탐하지 않고 기본값으로 채워 검증.
3. **조건부 공시 완전성 추론** — 별지1 운용방법 선택이 함의하는 위험고지 요구를 유도. 예: 기업어음 선택(주4) → CP 실물인출 제한 고지가 요약서에 있어야; 정기예금(주5) → 중도해지 손실 고지. "값 일치"를 넘어 "요약서가 필요한 공시를 다 담았나".
4. **분류(subsumption) 추론** — 채무증권 등 22개 ⊑ 증권 계층을 두면, "증권 운용 시 제8조 원본손실 가능 고지 적용" 규칙을 하위 타입 열거 없이 상속.
5. **내부 일관성·모순 검출** — 단일 문서 안의 논리 모순(종료<시작, 수수료 면제인데 요율 기재 등) 검출. 교차문서 대조를 넘어 단일문서 논리 감사.
6. **설명가능한 판정** — 불일치에 유도 체인 첨부: "요약서 만기 ≠ 시작 + 기간 = 2025-01-01 (근거: 제3조·별지1)". 블랙박스 비교가 아닌 감사 추적.

요약: **spot-the-difference → 논리 감사**(계산 정확성·기본값·함의 공시·내부 정합·설명가능성)로의 질적 도약. 균형상, 추론은 복잡도·성능 부담이 있고 OWL 풀추론은 무겁고 취약할 수 있으므로 미래 페이즈로 둔다. `axioms_from_text`(C6)와 `derived`/`equals` 필드(C6)를 지금부터 온톨로지에 담아두는 것이 이 업그레이드의 사전 준비다.

## C12. 제약 디자인 방법론 — 수확·범위·성장·테스트 (라이프사이클)

> "도메인에 맞는 제약을 어떻게 만들 것인가"에 대한 답. 핵심 원칙: **제약은 발명(design)하지 않고 수확(harvest)한다.** 제약의 출처는 이미 세상에 존재하며, 문제는 창작이 아니라 채굴이다. 그리고 온톨로지는 선행 완벽 설계 대상이 아니다 — 최소로 출발해 실전 오류를 먹고 자란다.

### C12.1 수확 출처 (제약이 오는 곳)

| 출처 | 예시 | 수확 방법 |
|---|---|---|
| 문서 자신 | 제4조① 수익자 기본값, 제2조① 신탁금액 정의 | LLM 후보 추출 + 사람 승인 (§C5-4, T17) |
| **기존 검수 체크리스트** | 준법감시·검수 담당자가 이미 쓰는 요약서 점검 항목 | **그대로 제약으로 전사 — v1의 첫 작업** |
| 법규·내규 | 금소법 §46(청약철회 고지), 협회 규정 | 규정 조항 → 공시 요구 제약 |
| 실제 사고/오류 사례 | 과거 실제로 틀렸던 요약서 케이스 | 사례 1건 = 제약 1개 (회귀 방지) |
| 데이터 자체 | 체결본 N건에서 항상 성립하는 불변식 | 마이닝으로 후보 → 사람 확인 |

사람이 요약서 검수를 이미 수행 중이라면 그 체크리스트가 **proto-온톨로지**다. 백지 설계가 아니라 기존 검수 관행의 형식화가 출발점이며, v1 온톨로지 구축의 첫 태스크는 이 체크리스트의 전사다.

### C12.2 범위 제한 — competency question 방식

바다를 끓이지 않기 위해, **"이 시스템이 답해야 하는 질문(competency questions)"을 먼저 나열**하고 그 질문에 답하는 데 필요한 제약만 온톨로지에 넣는다. 질문에 쓰이지 않는 제약은 만들지 않는다. 예:

- CQ1. 요약서의 신탁보수가 계약과 일치하는가?
- CQ2. 별지1의 모든 값이 요약서에 누락 없이 반영됐는가?
- CQ3. 선택된 운용방법이 요구하는 위험고지가 요약서에 있는가? (추론 페이즈, §C11-3)

온톨로지 파일의 각 제약에는 근거 CQ를 주석으로 남겨 존재 이유를 추적 가능하게 한다.

### C12.3 성장 — 오류 주도(error-driven) 확장

v1은 최소 제약으로 출발한다: 타입·카디널리티·별지1 동치(§B) + 기존 체크리스트 전사분. 이후:

1. 운영 중 검증이 **놓친** 오류가 발견되면 → 그 케이스를 제약으로 승격하고 변이 테스트(§C12.4)를 함께 추가.
2. 제약이 **잘못 발화**(오탐)하면 → 정규화/비교기 보정 또는 제약 완화, 사유 기록.
3. 자동 판정이 불가능한 영역은 `NEEDS_REVIEW`로 사람에게 흘려보낸다 — 온톨로지는 처음부터 완전할 수 없고 완전하려 해서도 안 된다. **"불완전하지만 자라는 제약 집합 + 사람 검토 안전망"** 이 설계 목표다.

각 제약에는 provenance를 단다: `{origin: 조항/체크리스트항목/사고ID, approved_by, date}`. 감사 요구 대응과 제약 폐기 판단의 근거가 된다.

### C12.4 테스트 — 제약도 코드처럼 검증한다

두 종류의 죽은 제약을 걸러낸다: (a) 한 번도 발화하지 않는 제약(가치 검증 불가), (b) 잘못 발화하는 제약(노이즈).

- **변이 테스트(mutation testing):** 올바른 골든 쌍을 의도적으로 훼손(보수율 숫자 변경, 고지 문단 삭제, 날짜 오기)한 변이 케이스를 만들고, 해당 제약이 **정확히 그 위반을** 발화하는지 pytest로 검증한다. "이 제약이 잡아야 할 오류를 실제로 잡는가"의 자동 증명.
- **발화 모니터링:** 운영 리포트에서 제약별 발화 횟수를 집계한다. 장기간 미발화 제약은 주기 리뷰에서 유지/폐기를 판단한다.

### C12.5 구현 작업

- **T18. 체크리스트 전사** — 기존 검수 체크리스트를 확보해 온톨로지 `fields`/`axioms` 항목으로 전사. 각 항목에 CQ와 provenance 주석.
- **T19. 변이 테스트 하네스** — 골든 쌍 훼손 변이를 생성·관리하는 테스트 유틸 + 제약별 변이 케이스(`tests/mutations/`).
- **T20. 발화 카운터** — reconcile 리포트에 제약별 발화 통계 필드 추가.

완료 기준: (1) v1 온톨로지의 모든 제약에 CQ·provenance가 있다. (2) 값 관련 제약마다 최소 1개의 변이 테스트가 있고, 변이 주입 시 정확히 해당 제약이 발화한다. (3) 리포트에 제약별 발화 통계가 나온다.

# Part D — 검색 소비자: 결정론 라우터 (임베딩 없음)

## D1. 설계 결정 — 임베딩을 사용하지 않는다

이 시스템의 검색은 **벡터 임베딩을 사용하지 않는다.** 근거:

- **어휘가 닫혀 있다.** 도메인 용어(신탁금액·중도해지수수료 등)가 법정 용어로 고정돼 있고, 변형은 온톨로지 alias가 흡수한다.
- **질의 대부분이 값 조회형**이며 그 정답 경로는 fact store 직조회다 — 임베딩이 애초에 낄 자리가 없다.
- **topic이 이미 색인이다.** 모든 청크에 조 단위 topic·role이 붙어 있어 facet 필터만으로 후보가 극소수로 좁혀진다.
- **설명가능성.** 벡터 유사도 0.83은 감사가 안 되지만 "topic 필터 + 키워드 일치 + refs 확장"은 매 단계가 설명된다. 금융 검증 도메인에서 감사 가능성이 recall 수치보다 우선한다.

**부수 효과 — 토큰 예산 폐기:** 임베딩 모델의 입력 한계가 사라지므로 청킹의 토큰 크기 조정이 불필요하다. 청킹은 순수 의미 단위(조/항/필드)로만 한다(§5-3, T4에 반영됨). 남는 상한은 LLM 컨텍스트뿐이며 조 단위 청크는 그에 전혀 문제가 없다.

**미래 대비:** 청크 저장소(JSON)는 표현 방식에 중립이므로, 훗날 자유 서술 질의가 많아져 렉시컬 검색의 recall이 부족해지면 임베딩을 **추가 검색 채널 하나로** 꽂을 수 있다(소비자 플러그인 원칙). 지금 결정이 미래를 막지 않는다.

## D2. 검색 라우터 — 5단계 결정론 파이프라인

1. **질의 정규화** — 온톨로지 alias·어휘로 질의 속 용어를 정규 필드명으로 치환. LLM 사용은 여기 한 번만 허용: "이 질의가 어느 topic/role/field에 해당하고 값 조회형인가 해석형인가" 분류(structured output, 낮은 temperature). 벡터 인덱스는 없다 — 질의 시점 라우팅뿐이다.
2. **fact 직조회** — 값 질문(`얼마`, `언제`, `누구` 등)이면 `field=X, role=별지1_입력`인 fact를 조회해 `value`로 답하고 `raw`+`source`로 인용. 파생값(만기일 등)은 온톨로지 `derived` 공식으로 계산해 답한다(비교기 인프라 재사용). 여기서 해결되면 종료.
3. **facet 필터** — 해석 질문이면 `topic=X`로 청크 후보를 좁힌다. role 라우팅: 규정·조건을 물으면 `role=약관본문`, 실제 계약 내용을 물으면 `role=별지1_입력`.
4. **렉시컬 검색(BM25/키워드)** — 좁힌 후보 안에서(topic 분류가 애매하면 전체에서) 키워드 매칭. 결정론적이고 근거 제시 가능.
5. **refs 확장** — 선택된 청크의 `refs`를 따라 참조 조·별지를 컨텍스트에 합류(1-hop 기본, 깊이는 설정). 예: 제15조① 검색 시 제3조·제12조·별지1 동반. 서빙은 small-to-big — 항 단위로 매칭됐어도 컨텍스트에는 부모 조 전체를 담는다(`article` 필드로 공짜 구현).

응답에는 사용된 라우팅 경로(어느 필터·키워드·refs가 발화했는지)를 함께 기록해 감사 추적을 남긴다.

## D3. 구현 작업

- **T21. 질의 분류기** — 온톨로지 어휘 로드 + alias 치환 + (선택) LLM topic/role/의도 분류. 분류 실패 시 4단계 전체 검색으로 폴백.
- **T22. fact 조회 API** — field/role/topic로 fact 검색, `derived` 계산 답변 포함.
- **T23. 청크 검색기** — facet 필터 + BM25(예: `rank_bm25` 또는 SQLite FTS5, 한국어 토크나이즈는 형태소 분석기(예: kiwipiepy) 사용) + refs 1-hop 확장 + small-to-big 서빙.
- **T24. 검색 골든 테스트** — 대표 질의 세트(값 조회형·해석형·refs 필요형 각 수 개)와 기대 청크/fact를 골든으로 두고 pytest 자동화.

완료 기준: (1) 값 조회 질의가 임베딩·LLM 생성 없이 fact 직조회로 답과 출처를 반환한다. (2) 해석 질의 응답에 라우팅 경로가 기록된다. (3) refs 확장이 골든 질의에서 기대 참조 조항을 동반한다. (4) 어떤 단계에도 벡터 인덱스 의존이 없다.
