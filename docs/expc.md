# 법령해석 지식 — 수집·정리·위키 (expc·fsc·prec·moleg)

법제처 정부유권해석 사례를 코퍼스 법령 범위로 수집하고, 열람 색인과
LLM 위키로 정리한다. 조문 검색(RAG)과 층이 다르다 — 해석례는 "조문을
어떻게 읽었는가"의 **맥락 정보**라, llm-wiki 패턴(raw 불변층 + LLM 컴파일층)
으로 담는다.

```
 law.go.kr expc API ──lawrag/pipeline/collect_expc.py──▶ data/corpus/expc/           수집 정본 (XML)
                                            cases/<일련번호>.xml · manifest.json
 data/corpus/expc ──lawrag/pipeline/ingest_expc.py──▶ data/expc/index.json           열람 색인 (기계)
                            └──▶ data/wiki/raw/expc/*.md        위키 raw 층 (결정적 이관)
 rag 문답 ──lawrag/pipeline/wiki_triage.py(LLM 판정)──▶ data/wiki/raw/conversations/*.md
                                          └─ wiki/log.md "컴파일 대기"
 data/wiki/raw ──LLM 컴파일──▶ data/wiki/wiki/<주제>/*.md       위키 지식 층
                                └─ scripts/expc_wiki_check.py   grounding 검사
 data/expc + data/wiki ──lawrag/api/routers/expc.py──▶ /expc/ 화면 (위키·사례 두 판)
```

역할 분담: **법령 원문("무엇이라 쓰였나")은 구조 스토어·RAG 의 몫**이고,
**위키는 "어떻게 읽는가"의 도메인 지식** — 명확한 소속이 없는 해석 맥락의
그릇이다. 형태는 ~/llm_wiki 의 정본(karpathy-llm-wiki SKILL)을 그대로 따른다.

## API 실측 (2026-08-13)

- 목록: `GET /DRF/lawSearch.do?OC=<oc>&target=expc&type=XML&query=<키워드>`
  - 기본 `section=itmNm` — **안건명 부분일치**. `display` 최대 100, `page` 순회,
    `totalCnt` 제공.
  - `search=2`(본문 bdyText)는 형태소 OR 매칭이라 못 쓴다 — "자본시장과
    금융투자업에 관한 법률"이 8,028건(첫 행이 군인 퇴직급여금 안건).
- 본문: `GET /DRF/lawService.do?OC=<oc>&target=expc&ID=<일련번호>&type=XML`
  - `<ExpcService>`: 법령해석례일련번호 · 안건명 · 안건번호(`NN-NNNN`) ·
    해석일자(YYYYMMDD) · 해석기관코드/명 · 질의기관코드/명 · 등록일시 ·
    **질의요지 · 회답 · 이유** (몸통 3단).
  - **관련법령 필드는 없다.**
- 공개 화면: `https://www.law.go.kr/LSW/expcInfoP.do?expcSeq=<일련번호>` (실측 200)
- OC 는 law/admrul 수집과 같은 규약 — `LAW_OC` 환경변수, 기본 test.

## 수집 규율 (lawrag/pipeline/collect_expc.py)

- 질의 집합은 선언이 아니라 **코퍼스가 결정** — data/corpus/law/manifest.json 의
  kind=law 명칭. 부분일치 특성상 다른 명칭을 품는 명칭은 축약된다
  ("상법"이 있으면 "상법 시행령" 질의는 불필요 — plan_queries).
- 안건명 부분일치는 오탐이 실재한다: '상법' 질의가 「군인 재해**보상법**」·
  「기**상법**」 안건을 끌고 온다. 그래서 **관련 법령 판정은 본문의
  「법령명」 낫표 인용 완전일치**(cited_laws)다 — 닫는 낫표까지 맞추고,
  공백은 무시한다(「개인정보보호법」 붙여쓰기 표기 실재). 문서 무관 신호만
  쓴다는 원칙 그대로다.
- 멱등·부분 실패 허용·원문 보존·요청 규율(1초 간격·백오프·차단 감지)은
  lawrag/pipeline/collect.py 와 같은 공통 기반(lawrag/sources/common.py)이다. 인용이 없는 사례도
  원문은 보존한다 — 판정 기준이 바뀌면 재판정할 원본이 있어야 한다.

## 정리 두 층 — 색인과 위키

**색인(기계)**: `lawrag/pipeline/ingest_expc.py` 가 data/corpus/expc → `data/expc/index.json`.
관련 법령은 저장값을 믿지 않고 지금 코퍼스 명칭으로 재판정하고, 인용 없는
사례는 뺀다(`--keep-unrelated` 로 되살림). 이 파일이 /v1/expc API 의 정본.
같은 실행이 `data/wiki/raw/expc/<해석일>-<안건번호>.md` 도 결정적으로
이관한다 — 위키의 증거층(raw-template: Source·Collected·Published + 원문 3단).

**위키(지식 층)**: `data/wiki/` — llm-wiki **정본 형태 그대로**:

- `raw/<주제>/` 불변 소스층 (expc: 해석례 이관분 · conversations: triage 통과
  문답). LLM 은 읽기만 한다.
- `wiki/<주제>/<아티클>.md` — 개념 1개 = 아티클 1개, 헤더에
  `> Sources / > Raw / > Updated` 필드(Raw 는 `../../raw/…` 상대 링크).
  `wiki/index.md` 는 주제별 표(아티클·요약·Updated — 라우터가 이 표를 판다),
  `wiki/log.md` 는 append-only 연대기.
- 갈래 구도(2026-08-14 재편 · 2026-08-18 방법 추가): **해석원칙 = 해석기**
  (합성 배경) · **쟁점 = 쟁점기**(검색 전 질의 분해) · **방법 = 방법기**
  (회수 **결과**의 성격이 깨우는 읽는 법) · **법령갈래 = 지도**. 쟁점
  카드는 헤더에 `> 트리거:`(질문을 깨우는 낱말, 가운뎃점 구분) ·
  `> 판단 축:` · `> 조문 후보:` 를 더 단다 — wikictx.spot 이 이 메타를
  읽는다. 방법 아티클(과 신호를 단 해석원칙)은 `> 신호:`(단서·정의·제재·
  준용·위임·수임)를 단다 — wikictx.methods_for 가 회수 구역의 동반 kind와
  단서 유무에 비춰 결정론으로 고른다(트리거는 질문이, 신호는 회수가
  깨운다). 사례기는 위키가 아니라 raw + 사례 판이다 — 카드는 `#case/`
  링크로 그리로 떨어진다.
- 낡은 주장은 삭제 대신 Status(Outdated·Disputed) 마킹 — 역사 은폐 금지.
- 사례 인용은 `[안건번호](#case/일련번호)` 링크를 겸한다 — 화면에서 사례
  원문으로 떨어지고, `scripts/expc_wiki_check.py` 가 사례 링크·Raw 링크·
  인덱스 표 정합을 검사한다 (수정은 안 한다 — 보고만).
- 재컴파일 절차: raw 가 늘면(수집 갱신·triage 통과) 위키 세션(Claude)이
  log.md 의 "컴파일 대기"를 보고 병합 — triage(이미 아는 내용이면 위키는 안
  건드림) → 아티클 수정 → index.md Updated 갱신 → log.md 한 줄 → 검사 통과.

**대화 유입 관문**: `lawrag/pipeline/wiki_triage.py` — rag 문답 스트림을 LLM 이 판정
(New/Update/Disputed/No material)해서 통과분만 `raw/conversations/` 에
소스로 남기고 log.md 에 "컴파일 대기"를 쌓는다. 정본 SKILL 과 달리 탈락분은
raw 에 넣지 않는다(대화는 소스가 아니라 후보 스트림 — 판정 기록은
`data/wiki/triage_state.json`). 컴파일은 위키 세션의 일로 남긴다.

## RAG 연결 — 답 합성의 배경 맥락

질의응답(/v1/rag/ask)의 답 합성이 위키를 배경으로 끼운다
(lawrag/core/rag/wikictx.py → answer.synthesize):

- 고르기는 코드 결정론 — 회수 구역의 문서명이 아티클 본문에 등장(강신호,
  가중 2) + 질의 낱말이 제목·요약에 등장(약신호, 가중 1). 점수 0 이면
  빈손 그대로(억지 주입 없음). LLM 라우팅 콜을 더 얹지 않는다 — 답변
  지연에 라우팅 비용이 얹힌다.
- 최대 2편·편당 4,000자. 프롬프트에 `[해석 맥락 — 지식 위키]` 블록으로
  붙고, 시스템 규칙 ⑥이 못 박는다: **위키는 방향, 근거(refs)는 조문만,
  어긋나면 조문이 이긴다.**
- 관측: 응답 `wiki` 필드 + 사다리(ladder) "위키 맥락" 단 — 어떤 아티클이
  끼었는지 질의마다 남는다(진단 튜플·디버깅 화면에서 프롬프트 원문 확인 가능).
- 켜고 끄기는 사용자 몫 — 엔진 스위치 `wiki_context` (공리 화면, 기본 켜짐).

**쟁점기 — 세 시점** (wikictx, 2026-08-16 개정 · 원래 두 시점이었다):

- **① 검색 보조 — 검색 전, 트리거** (spot → expand_query, 스위치
  `issue_spot` 기본 켜짐): 질문을 쟁점/ 카드의 트리거에 비춰(코드 결정론,
  LLM 콜 없음) 카드 최대 2장을 고르고, 조문 후보를 질의 뒤에 덧붙인다 —
  검색 사다리 ①(색인값 ⊂ 질의)이 그 법령명을 물어, **질문이 법령명을
  몰라도 쟁점이 조문을 데려온다**. 회수는 확장 질의, 합성·기록은 원 질의.
  **트리거는 이제 폴백이다** — 낱말 겹침이라 오분류가 난다(실측: "법 바뀌기
  전에 등록한 회사인데…"가 '등록' 한 낱말로 「두 법의 관문」을 물었다.
  정답은 「경과조치의 존속」이고, 그 카드의 트리거에는 구어 "법 바뀌기 전"이
  없었다). 아래 ①′ 가 서면 그것이 이긴다.
- **①′ 검색 전 분해 — LLM** (spot_llm(sections=None), 스위치
  `issue_spot_pre` 기본 꺼짐): 질문만 보고 카드 메뉴에서 고른다. 메뉴에는
  카드마다 **그 카드의 조문 후보가 실제로 가리키는 조 제목**이 붙는다
  (wikictx.card_titles — 결정론 좌표 해소). 조 제목이 재료인 이유는 둘:
  카드 선택이 정확해지고, 아래 **조문질의**가 빌려 쓸 어휘가 코퍼스 실물이
  된다. 값은 싸다 — 15장 전체 조 제목 55개·987자(≈493토큰). 같은 조문을
  **전문**으로 넣으면 174,707자(≈87k토큰)라 컨텍스트가 터진다.
  판정 불가(무LLM·콜 실패)면 ①의 트리거 결과로 폴백.

  이 콜은 카드와 함께 **`조문질의`(법률문장)** 를 카드마다 쓴다 — 질문을 그
  쟁점의 법률용어로 옮긴 조문 문체 한두 문장이고, **벡터 채널이 이것을
  임베딩한다**(wikictx.vector_query). 사용자의 구어와 코퍼스의 조문 문체는
  낱말이 겹치지 않아 벡터가 헛돈다. 실측(같은 질문, 상위 20을 코사인이
  아니라 **무엇을 데려왔나**로 채점):

  | 벡터에 넣은 문자열 | 코사인 | 경과조치 조 | 「다른 법령의 개정」 조 |
  |---|---|---|---|
  | 구어 원문 | 0.582 | 0/20 | 1/20 (전부 본문 회사법으로 샘) |
  | 법률문장 + 법령명 | 0.706 | **0/20** | **16/20** |
  | 법률문장만 | 0.619 | **6/20** | 3/20 |

  **코사인 평균으로 고르면 정확히 틀린 것을 고른다.** 법령명을 붙이면
  코사인이 가장 높은데 내용은 최악이다 — 부칙 「다른 법령의 개정」 조가
  법령명을 수십 개 나열하는 조라서 표면이 겹친다. 규칙으로 굳히면:
  **벡터 질의에는 "찾으려는 조문에 실제로 쓰여 있을 법한 문장"만 넣는다.
  문서명·조 좌표 같은 메타데이터는 넣지 않는다** — 그것을 나열하는 다른
  조문과 겹친다. 법령명은 어휘 사다리(문자열 매칭)에만 남긴다.

  채널이 갈린다: 벡터 ← 법률문장 / 어휘 사다리 ← 원문 + 조문 후보.
  합류는 RRF(순위)와 슬롯 배분이라 질의가 달라도 안전하다(점수를 비교하지
  않는다).
- **② 쟁점 판정 — 컨텍스트 확보 후, LLM** (spot_llm, 스위치
  `issue_spot_llm` 기본 꺼짐): 회수·확장이 끝난 뒤 LLM(effort=low)이
  질문 + 회수 조문(경로·발췌)을 함께 보고 카드 메뉴에서 걸린 쟁점을
  판정한다 — **질문만 보고는 모르는 쟁점(조문이 드러낸 준용·부칙 구조)이
  여기서 잡힌다**. 판정이 서면(빈 판정 = "걸린 쟁점 없음" 존중) 그것이
  배경 주입을 이끌고, 판정 불가(무LLM·콜 실패)면 ①의 트리거 결과 유지.
  판정 콜 지연이 답변 앞에 얹히므로 기본 꺼짐 — 켜는 것은 사용자다.
- 최종 카드는 합성의 위키 블록 앞자리에 낀다(answer.synthesize 의 spots
  인자) — 카드는 쟁점의 법률용어 정식화 + 판단 축 + 선례 요지(사례기
  `#case/` 링크)를 도메인 배경으로 준다. 근거(refs)는 여전히 조문만
  (규칙 ⑥). pick 은 쟁점 카드를 건너뛴다(이중 경쟁 금지).
- 관측: 사다리 "쟁점 분해"(맨 앞, ①·①′)·"쟁점 판정"(회수 뒤, ②) 단 + 응답
  `wiki` 필드 — 적중 원장에 같이 접혀 쟁점기 실적이 해석기와 따로 잡힌다.
  진단 튜플의 `쟁점` 필드가 전모를 남긴다: 트리거가 무엇을 물었나(대조용,
  ①′ 가 이겨도 늘 기록) · LLM 이 무엇으로 고쳤나 · 조문질의 · 어휘 사다리에
  간 확장 질의 · 벡터에 간 질의. `콜` 필드에는 모든 LLM 콜의 system·user·
  응답 원문이 남는다. 판독은 `python scripts/rag_trace.py <qid> --split
  --calls`.
- **자가 수선 루프**: 문답이 쌓이면 ledger 부검(정답/오답)이 카드별로
  접히고 → wikilife 가 재컴파일 후보를 권고하고 → wiki_triage(LLM 판정,
  오답 우선)가 대화를 raw/conversations 로 걸러 "컴파일 대기"를 쌓고 →
  위키 세션이 카드(트리거·판단 축·사례)를 고친다. 쟁점 추출이 틀린
  자리는 이 길로 교정된다 — 카드는 코드가 아니라 위키라서 고칠 수 있다.
  트리거 품질 자체는 백테스트(질의요지 67건 발화·적중률)로 잰다.

## 추가 소스 — 같은 틀의 세 갈래 (2026-08-14)

expc 와 같은 규율(코퍼스가 질의를 결정 · 멱등 · 원문 보존 · 관련 판정)로
세 소스를 더 받는다. 전부 창고는 data/corpus/<소스>(수집 정본) →
data/wiki/raw/<소스>(위키 증거층)이고, 원장(lineage) 밖(phase_model 선언).

| 소스 | 수집기 | 규모 실측 | 관련 판정 |
|---|---|---|---|
| 금융위 회신사례 (better.fsc.go.kr — 법령해석·비조치의견서) | lawrag/pipeline/collect_fsc.py → lawrag/pipeline/ingest_fsc.py | 전량 12,067 · 질의 합집합 629 | 평문 경계 (cite.plain_mentions) |
| 판례 (law.go.kr prec) | lawrag/pipeline/collect_prec.py → lawrag/pipeline/ingest_prec.py | 질의 합집합 543 | 평문 경계 — 전문(방론)은 안 봄 |
| 입안·심사 기준 (moleg.go.kr — 법령 880쪽 · 행정규칙 152쪽, 2026년판) | lawrag/pipeline/collect_moleg.py (이관 포함) | 2권 | — (교과서 원천) |

- 금융위 질의는 코퍼스 중 **소관부처에 '금융'이 든 문서만** — 이 포털은
  금융위 소관이라 상법·개인정보법은 이 소스의 것이 아니다(그쪽은 expc).
  목록은 DataTables JSON(searchCondition=all 본문검색), 상세는 유형별
  POST(LawreqDetail·OpinionDetail·PastReqDetail). '현장건의 과제'는 뺀다.
- 평문 경계 판정: 낫표 관례가 없는 문서용. 명칭 앞 글자가 한글이면 꼬리
  일치('국가배상법' 속 '상법')로 보고 거르되, 경계는 **공백 제거 전 원문
  좌표**로 본다 — "구 자본시장과…법률"(옛 법 인용)이 살아야 한다.
- 판례 raw md 는 공식 요지(판시사항·판결요지·참조조문)만 — 전문은 corpus
  XML 이 정본이고 md 머리가 경로를 가리킨다. 교과서는 쪽 단위 텍스트로
  이관하고 통째 아티클화하지 않는다 — 위키가 개념을 다룰 때 장을 인용한다.

## 생애 주기 — 아티클의 공리 루프

llm-wiki 의 생애 장치(Status 블록·check_evidence·미참조 재고)에 이 저장소의
공리 루프(4기준 보고서)를 접합한 것. 상태를 저장하지 않는다 — 보고서는
언제나 파생이다 (lawrag/core/rag/wikilife.py):

| 축 | 신호 | 출처 |
|---|---|---|
| 성숙 | Raw 필드의 출처 등급 구성 (해석례 > 문답) | 아티클 헤더 |
| 안정 | Status: Disputed/Outdated 블록 수 | 아티클 본문 |
| 하중 | 답 합성 주입 횟수 | 적중 원장 (ledger.jsonl) |
| 부검 | 주입된 질의의 피드백 정답/오답 | 적중 원장 + /v1/rag/feedback |

권고(코드 결정론): 분쟁 중(Disputed 블록 또는 강등·보류 규칙 `rule:<id>` 인용)
→ 재컴파일 후보(오답≥2·오답>정답) → 재검증 필요(문답발만) → 유지.
고치는 것은 위키 세션·사람 몫 — 규칙의 정착 승격과 같은 이유다.

- **적중 원장** `data/wiki/ledger.jsonl` (lawrag/core/rag/wikiledger, append-only):
  답 합성에 아티클이 끼면 "주입", 그 질의에 피드백이 오면 "부검". 부검은
  그 질의에 끼었던 모든 아티클에 접힌다 — 개별 기여 분리는 추정이라 안 한다.
- **자기수선 파이프**: wiki_triage 가 피드백 오답 > 감사 지문·교정
  (verdicts.flagged_qids) > 피드백 있음 순으로 판정한다 — 시스템이 틀린
  자리가 위키가 메울 자리다.
- **규칙 ↔ 위키 왕복**: rules.set_status 가 정착 승격이면 위키 log.md 에
  "컴파일 대기"(규칙의 '왜'를 아티클로), 정착 강등이면 "재심"을 적는다.
  아티클이 규칙을 `rule:<id>` 로 인용하면 그 규칙이 강등·보류될 때 생애
  보고서가 자동으로 "분쟁 중"을 띄운다.
- **검사**: scripts/expc_wiki_check.py 가 grounding 에 더해 충실도(조문
  표기·수치가 Raw 원문에 있는가 — 의심만 보고)와 미참조 raw 재고(컴파일
  백로그)를 본다. 세션 관례는 CLAUDE.md.

## 화면 (/expc/)

위키·사례 두 판. 위키 판은 아티클 목록 + 마크다운 렌더(소형 렌더러 — 위키가
쓰는 부분집합만). 사례 판은 필터(본문 부분일치·법령·기관·연도) + 3단 원문.
사례 상세는 자기를 인용한 아티클을 역추적해 보여준다. 검색은 부분일치뿐 —
의미 검색은 질의응답(/rag/)의 영역이고, 여기는 열람이다.
