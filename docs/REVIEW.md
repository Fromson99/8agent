# 법적 검토 — 사실·쟁점·규범·포섭·결론의 뼈대

질의응답(`/v1/rag/ask`)은 "이 조문이 뭐라 쓰였나"에 답한다. 검토는 다른 일이다
— **사실을 요건에 대는 일**이고, 산출물이 산문이 아니라 **요건별 충족표**다.
이 문서가 그 뼈대의 정본이다 (2026-08-14 설계).

```
 사실(Fact) ──▶ 쟁점(Issue) ──▶ 규범(Norm) ──▶ 포섭(Sub) ──▶ 결론(Verdict)
   주체·행위      관문 질문        요건 트리       요건별 판정      가부·리스크
   ·대상         ·규제축         (AND/OR/단서)   충족|불충족       ·미충족 요건
                                                |불명 ★         ·액션
                     ▲                            │
                     └──── ★ 불명이 새 쟁점 ───────┘   (되먹임)
                                                  │
                                            Binding 원장 (자산↔조문)
```

핵심은 셋이다.

1. **파이프라인이 아니라 상태다.** 포섭에서 '불명'이 나오면 쟁점으로 되돌아
   간다. `ReviewState` 를 단계들이 갱신한다 — 일방향 흐름이 아니다.
2. **'불명'이 곧 메인 쟁점이다.** 실무에서 다투는 자리는 요건이 딱 안 맞는
   회색지대이고, 시스템에선 그게 다음 라운드의 회수 목표가 된다.
3. **회수의 목적이 바뀐다.** 조문을 모으는 게 목적이 아니라 **요건 트리를
   채우는 것**이 목적이다. 회복 루프의 진입 조건도 "빈손"이 아니라
   "요건 미충족"이 된다 (core/rag/recover.py 와 접속하는 자리).

## 다섯 타입 — 필드는 최종 크기, 구현은 지금 크기

`?` 는 스키마에만 두고 지금은 비운다. 나중 기능(타임라인·증거·리스크)이 그
칸을 채우면 파이프라인 구조는 그대로다 — 필드가 아예 없으면 전면 재작업이다.

| 타입 | 무엇 | 지금 | 나중 |
|---|---|---|---|
| `Fact` | 주체·행위·대상 + 시제 | 짧은 텍스트에서 3~5개 | 시점(타임라인)·증거·요건사실 구분 |
| `Issue` | 관문 질문 · 규제축 · 판단 축 | 위키 쟁점 카드 + 관문 | 청구권 경합(소송용, 우리는 불요) |
| `Norm` | 좌표 · 요건 트리 · 효과 | 조문 텍스트 + 참조 | 요건 분해(AND/OR/단서)·버전 |
| `Sub` | 요건별 판정 + 근거 | LLM 1콜 판정 | 요건 트리 기반 기계 대조 |
| `Verdict` | 가부 · 미충족 요건 · 액션 | 결론 + 미충족 목록 | 리스크 등급 · 샌드박스 등 출구 |

`ReqTree` 는 지금 "요건 목록 + 결합자"면 충분하지만 **재귀 트리로 정의**한다 —
중첩 요건이 나중에 들어온다. 코퍼스 실측(2026-08-14): 논리 표지가 정형적으로
6,355개 존재한다 (다만 3,030 · 각 호의 어느 하나 1,894 · 에도 불구하고 743 ·
로 한정한다 337 · 를 제외하고 200 · 각 호의 모두 151). 한국 법령은 입안·심사
기준이 규격화한 **준(準)형식 언어**라, 이 표지들을 결정론으로 승격할 수 있다.
이미 한 번 했다 — "에도 불구하고" → 배제 간선.

## 세 트랙 — 같은 코어, 다른 입구

| | 입력 | 출구 | 코어와의 차이 |
|---|---|---|---|
| **C 해석 검토** | 사실관계(과거) | 가부·조건부 | 기준형 |
| **B 적법성 검토** | 서비스 설계(계획) | 구조화·우회로 | `Fact.시제=계획` + 대안 복수 + **Binding 적재** |
| **A 개정 추적** | 규범의 변화(Delta) | 액션 아이템 | `Norm.버전` + `Delta` 타입 + **Binding 역인덱스** |

B1(아키텍처 해체 — 주체·객체·행위)이 C1(사실 추출)과 **자료구조가 같다.**
B3(마찰 지점)은 C4의 '불명' 판정이고, B4(구조화)는 C5의 액션이다. 즉 B 는
C 의 특수 사례이지 별도 파이프라인이 아니다.

A 도 같은 포섭 엔진을 쓴다 — **개정된 요건 × 기존 자산 = 재포섭**이다.
A3(부칙 분석)은 이미 위키에 있다(쟁점 「경과조치의 존속」·「시점의 경계」,
부칙은 마디로 파싱되어 있고 본문우선 규칙이 그래서 존재한다).
A4(파급 효과)는 관계망 역방향(수임 간선) 항해다.

## Binding — 두 트랙을 잇는 원장

```
Binding { 자산(서비스·파이프라인·약관·모델) ↔ 규범 좌표(조문)
          ↔ 쟁점 ↔ 판정·근거 ↔ 검토 시점 }
```

**B 가 생산하고 A 가 소비한다.** B 에서 "이 서비스가 전자금융감독규정
제15조에 걸리고 이러이러하게 통과했다"를 검토했으면 그 결과를 원장에 남긴다.
나중에 제15조가 개정되면 원장을 역인덱스로 뒤집어 **영향받는 자산 목록**이
즉시 나온다. 이게 없으면 A 는 개정마다 전수 재검토라 실무에서 안 돌아간다.

진단 튜플(data/rag/tuples)과 다르다 — 그건 **관측**이고 이건 **자산 원장**이다.
관측은 append-only 로 고쳐 쓰지 않지만, 원장은 자산의 현재 상태를 들고 있다
(재검토하면 갱신된다).

## 도메인 독립성

다섯 타입 중 법률 고유는 하나도 없다 — 사실·쟁점·규범·포섭·결론은 **규칙 기반
검토 일반**의 형태다(사내 규정 준수, 계약 검토, 감사에 그대로 간다). 법률
특수성은 플러그인으로 뺀다:

- 관문 질문·규제축(수평/수직) — 도메인 어휘
- 조-항-호 논리 표지 — 도메인 파서
- 위임·준용·배제 간선 — 도메인 관계망

`core/rag/recover_domains.py` 의 등록부와 같은 방식이다.

## 지금 접는 것 (필드만 두고 로직 없음)

규제 컴플라이언스가 목적이라 분쟁 해결 쪽은 접는다 — **청구권 경합·소송
전략**, **증거 태깅·입증책임 분배**(짧은 텍스트 입력엔 증거 개념이 없다),
**타임라인 재구성**(사실 3~5개면 정렬이 무의미), **내용증명·가압류류 액션**.

## 구현 순서 — 얇게 세로로 관통

한 단계를 깊게 파는 것보다 다섯 단계를 얇게 관통시키는 게 낫다. 구조가
맞는지 빨리 드러난다.

1. **얇은 관통** — 사실 추출(LLM 1콜) → 쟁점 선택(기존 카드) → 규범은 조문
   텍스트 그대로 → 포섭표(LLM 1콜) → 결론. **요건 분해 없이도 표 모양의
   산출물이 나오는지** 확인. Binding 적재를 여기서부터 포함한다.
2. **요건 분해** — 논리 표지 6,355개 승격. 1번에서 "요건이 텍스트라 매칭이
   흔들린다"가 실측되면 근거가 선다.
3. **되먹임** — 불명 → 쟁점 승격 → 재회수 (회복 루프 진입 조건 교체).
4. **리스크·액션** — 등급화와 출구(샌드박스·비조치의견서). 출구의 재료는
   이미 raw/fsc 에 대량으로 있다(비조치의견서).


2026-08-14 충돌의 기록).

스위치는 `review_binding`(원장 적재, 기본 켜짐).

## 실측 (2026-08-14 · 첫 관통)

입력: "증권사가 마이데이터 사업자와 제휴해 고객 동의로 투자성향 정보를 넘겨
맞춤 상품을 추천받게 하고, 결과는 우리 앱에 표시하며 데이터는 클라우드에 저장"
(track=적법성, asset=맞춤추천 제휴서비스)

최종(4회차): 사실 5 → 쟁점 4 → 규범 24 → **요건 46 판정** → 결론 전부 조건부 ·
원장 43줄. 쟁점마다 그 쟁점의 법이 회수됐다(개보법·신정법 / 업무위탁규정·
전자금융감독규정). 판단보류 0.

관통 과정에서 드러나 고친 결함 넷 — 전부 **실행이 지목한 것**이다:

| 결함 | 증상 | 고침 |
|---|---|---|
| 지목 조문이 검색으로 안 물림 | 개인정보 쟁점에 개보법이 회수 안 돼 판단보류 | 조문 후보를 **좌표로 해석**(`_coords_of`) — 색인값은 조문 제목이라 "「개인정보 보호법」 제17조제1항" 문자열은 검색으로 못 문다. 카드가 법과 조를 알려 준 이상 찾을 게 아니라 편다 |
| 카드를 트리거로 재발견 | 쟁점 도출이 고른 카드를 트리거 매칭으로 다시 찾다 놓침 | `_spot_for` — 슬러그가 곧 답이므로 조회로 끝낸다 |
| 삭제 조문 회수 | 시행령 제32조(삭제)에 포섭 콜을 씀 | `_is_deleted` 결정론 제외 |
| 포섭 출력 잘림 | 요건 27개에서 JSON 미완결 → **판정 전체가 버려짐** | `SUB_REQ_CAP=18` + max_tokens 4000 + 이유 한 문장 규율 |
| 쟁점 도출이 흔들림 | 같은 입력에 4→4→0개 (0이면 검토가 통째로 없어짐) | effort 상향 + 빈손이면 **카드 트리거 안전망**(`_issues_from_cards`) |

### 요건 단위를 마디로 (2026-08-14, 같은 날 후속)

첫 관통의 불명이 46건 중 42건(91%)이었다. 원인은 도메인의 불확실성이 아니라
**우리 요건이 가짜**였던 것 — `_reqs_from_text` 가 조문 텍스트를 정규식으로
잘라 판정 불가능한 조각(항의 머리글 등)을 만들었다. 측정이 오염된 상태였다.

그런데 쪼갤 필요가 없었다. **조·항·호가 이미 마디로 파싱돼 있다.** 호는 한국
법령에서 요건의 자연 단위다("1. 정보주체로부터 별도의 동의를 받은 경우").
파싱된 계층을 두고 문자열을 재파싱하고 있었던 셈이다.

`_reqs_from_nodes` 로 교체 — 항에 호가 있으면 **항은 가지, 호가 잎**이고 항의
자기 본문("각 호 외의 부분")은 잎의 맥락으로 붙는다. id 도 임의 해시가 아니라
**좌표**(`rD1-230`)에서 나와, 재검토해도 같은 요건이 같은 id 다(원장·되먹임이
조문을 직접 가리킨다).

| | 문장 자르기 | 마디 기반 |
|---|---|---|
| 요건 | 46 | 37 |
| 충족 | 1 | **7** |
| 불명 | 42 (91%) | **25 (68%)** |

수치보다 중요한 것은 **판정의 성격이 바뀐 것**이다. 전에는 불명이 잡음이었고
(판정할 수 없는 조각), 지금은 신호다 — "4. 개인정보를 제공받는 자의 보유 및
이용 기간 → 불명: 제휴사가 보유·이용하는 기간이 명시되지 않았다". 이게 설계가
노린 "보완할 사실"이고, 그대로 액션이 된다.

### 논리 표지 승격 — 2단계 (2026-08-14)

계층 위에 **연산자**를 얹었다. 결정론 파서(`_mark_logic`)가 줄기의 표지를 읽어
`Req.op` 를 채운다. 전 코퍼스 가지 요건 8,964개 중 **2,039개(23%)에 op 가
붙는다** — OR 1,513(16.9%) · AND 526(5.9%) · 미상 6,925(77.3%).

- 표지 우선순위는 **먼저 나온 것**이다. 한 줄기에 둘이 오는 일이 실재한다 —
  개보법 제18조제3항 "다음 각 호의 사항을 …알려야 한다(AND). 다음 각 호의 어느
  하나의 사항을 변경하는 경우에도…" — 뒤 문장의 '어느 하나'를 집으면 AND 를
  OR 로 뒤집는다(실측에서 잡아 고쳤다).
- **미상은 비워 둔다.** 77%가 표지 없는데, 추정으로 채우면 틀린 확신이 된다.
- 단서(다만, …)는 별도 요건으로 뗀다 — 본문과 예외는 다른 판정이다.

**값어치가 나는 자리는 결론이다** (`fold`): OR 가지는 하나만 충족되면 접히고
형제의 불명을 묻지 않는다. AND 는 하나라도 불충족이면 불충족. **미상은 전부
충족일 때만 충족이고 그 밖은 불명 — 불충족으로 단정하지 않는다**(관계를 모르는
채로 '불가'라고 말하지 않는 것이 이 시스템의 규율이다).

실측 검증: 개보법 제18조가 ②=OR(10개 선택지) · ③=AND(5개 고지사항)로 정확히
읽힌다. 종단 불명률은 회차마다 흔들린다(쟁점 도출이 매번 다른 쟁점을 세워
분모가 달라진다) — 구조적 이득은 단위 시험(`test_OR는_하나만_충족되면_접힌다`,
`test_결론이_트리를_알면_OR_형제의_불명에_흔들리지_않는다`)이 지킨다.

같은 회차에서 잡은 버그 하나: 상한(`SUB_REQ_CAP`)에 잘려 **포섭에 올라가지도
못한 요건**이 '미해결'로 세어지고 있었다(요건 37개인데 미해결 33개). 판정
대상이었던 것만 센다 — 안 그러면 다툼의 자리가 묻힌다.

## 골든 셋 — 오류율을 재는 자 (scripts/review_golden.py)

법제처 해석례 67건은 그 자체로 **정답이 붙은 검토 사례**다 — 질의요지가
사실관계이고 회답이 정답이다. 회답의 결론 방향을 LLM 이 한 번 라벨링해
캐시하고(`data/review/golden_labels.json`, 부정 31 · 긍정 30 · 조건부 6),
검토 파이프라인을 통과시켜 대조한다.

    python scripts/review_golden.py --label      # 라벨링 (1회)
    python scripts/review_golden.py --limit 8    # 실행 + 채점
    python scripts/review_golden.py --report     # 재집계 (무비용)

재는 것 셋과 **단계 귀속**이 핵심이다 — 틀린 사례를 쟁점 실패(2단계) ·
회수 실패(3단계) · 포섭 실패(4단계) 중 하나로 돌린다. 어디를 고쳐야 하는지가
곧 답이다. 유의: 질의요지는 대개 법령명을 이미 밝히므로 **법령 회수율은
상한으로 읽어야 한다**(실사용 질문은 더 어렵다).

### 3회차 (67건 전수 ×2 — 네 수정의 전후, 2026-08-16)

처음으로 전수를 돌렸다. 수정 전 67건이 기준선이고, 네 수정 뒤 같은 67건을
다시 돌렸다.

```
                     수정 전(전수)   수정 후(전수)
쟁점 발화             67/67 (100%)   66/67 (99%)
법령 회수             63/89 (71%)    81/89 (91%)
조문 회수             28/87 (32%)    52/87 (60%)
방향 결정             11/67 (16%)    48/67 (72%)
방향 일치(결정 대비)    8/11 (73%)    31/48 (65%)
전건 기준 정답         8/67 (12%)    31/67 (46%)
판단 유보             56 (84%)       19 (28%)
방향 분포             조건부52·미정10  부정30·긍정17
                     ·부정5·긍정0    ·조건부19·미정1
```

**수정 전 전수가 드러낸 것** — 시스템이 긍정을 **한 번도** 못 냈다(정답의
45%가 긍정인데). 원인 둘: ⑴ "전부 충족이어야 가능" × 사례당 요건 평균 36개
= 긍정 도달 불능. ⑵ 조문까지 회수하고도 유보한 사례 24건 — 요건×사실
대조(B트랙 기계)에 해석 질문을 넣으면 "사실이 딱 맞지 않으면 불명" 규율이
불명을 양산한다. 해석례는 사실이 부족해서가 아니라 **문언의 의미가
다투어져서** 어렵다. "B는 C의 특수 사례"의 역은 성립하지 않는다 — C는 B가
아니다.

**네 수정** (구현 위치는 core/casereview/pipeline.py):

1. **문면 인용 좌표 직행** (`_cite_coords`) — 질의요지 65/67건이 조문을 문면
   인용하는데, 회수가 LLM 재작성 질문으로 검색하며 그 좌표를 버리고 있었다
   (실측 26-0271: "같은 법 시행령 제41조제2항"이라 써 있는데 못 데려옴).
   결정론 상한 실측: 인용 직행만으로 근거 조문 91%(53/58).
2. **필수 동반 배선** — expand_floor(위임·배제·수임·준용)가 vecfirst 에만
   불리고 검토 트랙엔 없었다. 위임 간선 27,318개를 만들어 두고 안 쓴 것.
3. **해석 판정** (`interpret_case`) — 해석 트랙은 요건표 **위에** 사안 수준
   문언 해석 판정 한 콜을 얹는다(법제처 회답 형식 — 사안 하나에 방향 하나).
   코드가 접은 불충족은 판정을 구속한다(결정론이 먼저, LLM 은 남은 것만).
   요건표와 보수적 fold 는 그대로 남는다 — 그건 다툼 지점의 관측이고, 오류는
   그걸 답으로 쓴 데 있었다. ReviewState.overall 로 나간다.
4. **쟁점 카드 1장** — 「정보주체 권리 행사」(열람 경로·방법의 폭). 트리거
   백테스트 적중 74→77%, 열람 2건(26-0271·25-0653)이 미스에서 빠졌다.

**정직한 잔여** — ⑴ 오답 3→17로 늘었다: 결정을 4.4배 하니 오답도 는다.
결정 대비 오답률은 27%→35%. 특히 정답이 조건부인 6건 중 5건에 긍정/부정을
질렀다 — 수정 전엔 조건부를 다 맞혔는데, 그건 "모두 조건부로 내는" 시스템의
부산물이었다. ⑵ 조문 회수 60%는 91% 상한 아래 — 회답에만 나오는 조문(질문
무인용)이 잔여의 몸통. ⑶ 귀속의 최대 덩어리가 회수(23건)에서 **포섭·판정
(29건 = 오답 13 + 유보 16)** 으로 이동했다 — 다음 손은 판정 품질이다
(effort·근거 강제·조건부 판별 기준). ⑷ 경과조치 축이 여전히 약하다 —
17-0216·09-0242(주체 동일성 유지 → 긍정이 정답)를 부정으로 냈다.

### 2회차 (같은 8건, 세 수정 뒤)

첫 측정의 유보 6건을 열어 보니 원인이 **요건 분해가 아니라 쟁점 오지정**이었다.
25-0653("열람을 어느 경로로 요구하는가", 제35조제2항)에서 실행된 쟁점이
「동의와 정보이용」이었고, 회수된 것은 제15·17조(수집·제공 **동의**)였다.
요건 18개가 전부 불명이었는데 **그 판정은 옳다** — 동의 요건에 열람 사실을 댈
수는 없다. 남의 쟁점의 요건을 판정하고 있었던 것이다.

범인은 안전망이었다. LLM 쟁점 도출이 빈손을 내자 `_issues_from_cards` 가
트리거 하나("제공")로 엉뚱한 카드를 세웠다. **틀린 쟁점은 빈손보다 나쁘다** —
빈손은 '쟁점 실패'로 눈에 띄지만 틀린 쟁점은 그럴듯한 유보를 만들어 원인을
숨긴다. 세 가지를 고쳤다:

1. **안전망 문턱** — 트리거 2개 이상 물어야 선다(`NET_MIN_TRIGGERS`), 그리고
   안전망이 세운 쟁점은 `Issue.by_net` 으로 표시가 남는다.
2. **빈손이면 재시도가 먼저** — 재시도는 같은 품질을 다시 뽑고, 안전망은 다른
   품질로 대체한다. 같은 값이면 같은 것으로 메운다.
3. **지표를 조문 수준으로** — 25-0653 은 법령 수준으로는 '회수 성공'이었다
   (개보법을 가져왔으니). 회답이 근거로 든 조문(제35조)을 뽑아 대조하니 실패가
   보인다.

```
              1회차        2회차
쟁점 발화     8/8 (100%)   8/8 (100%)
법령 회수     7/12 (58%)   8/12 (67%)
조문 회수     —            3/6 (50%)   ← 신설. 법령 수준보다 엄격
방향 일치     2/2          2/2
판단 유보     6            6  → 원인: 회수 실패 2 · 포섭 실패 4
```

유보 수는 같지만 **원인이 분해됐다.** 이제 회수 실패(필요한 조문을 못 데려옴)와
포섭 실패(조문은 왔는데 판정 못 함)가 갈리므로, 다음 작업이 어디인지 다투지
않는다. 요건 분해(2단계 후속)는 **포섭 실패 4건**의 몫이고, 회수 실패 2건은
별개 문제다.

### 첫 측정 (2026-08-14, 8건)

```
쟁점 발화   8/8 (100%)     ← 안전망이 듣는다
법령 회수   7/12 (58%)     ← 3단계에 실질 공백
방향 일치   2/2 (100%)     ← 답한 것은 다 맞았다
판단 유보   6/8 (75%)      ← **지배적 실패 양식**
```

**오답이 0건이고 회피가 75%다.** 설계의 보수성이 그대로 나온 결과다 —
틀린 답을 주느니 "판단하지 못했다"고 하는 쪽으로 기울여 놨으니 예상된 모양이고,
초안 도구로서는 안전한 실패다. 다만 75%는 쓸모를 깎으므로, **앞으로 내려야 할
지표는 오답률이 아니라 판단 유보율**이다. 그리고 그 유보의 원인은 이미 안다 —
불명 요건(가지의 77%가 op 미상) + 회수 누락 42%.

즉 다음 작업의 우선순위가 감이 아니라 수치에서 나온다.
