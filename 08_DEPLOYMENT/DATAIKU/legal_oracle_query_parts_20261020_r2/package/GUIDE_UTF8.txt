추가 조회 데이터 반출 R2 — SQL 집계 최적화·실제 진행 로그·R1 중단 파일 재개
2026-10-20 / LEGAL_ORACLE_QUERY_PARTS_20261020_R2.zip

이번에는 추가본만 먼저 확인합니다. 전체본 FULL_PARTS R1과 별개입니다.
메일 ZIP은 실행 코드이며 현장 데이터가 들어 있지 않습니다.
R1을 종료한 상태에서 R2 코드를 별도 폴더에 풉니다. 기존 임시 DB·journal·로그를 삭제하지 않습니다.

1. 현장 관측과 수정
사용자 화면: ROWS_SAVED 2,448,000 이후 시간 로그만 지속, CPU78.9%/누적22:36, workspace10GB 중1.6GB 가용.
이 화면만으로 실제 Python/SQLite 스택을 확정하지 않았습니다.
코드의 FTS 길이 집계에서 fts5vocab에 문서 ID 조회 인덱스가 없어 문서마다 전체 토큰을 다시 읽는 실행 계획을 재현했습니다.
R2는 토큰을 한 번 문서별로 집계한 TEMP 테이블을 만들고 정수 기본키로 조회합니다. 게시 행의 값·해시·순서는 R1과 동일하게 보존합니다.
SQLite 정렬/집계 내부에서도 작업량과 자원·시간 제한을 확인하도록 progress callback을 추가했습니다.
타이머만 출력하던 로그를 처리 파일·테이블·단계·확인/추가 건수·SQLite 작업량·CPU/RSS·남은 공간으로 바꿨습니다.
압축은 ZIP을 별도로 저장하지 않고 49MB 조각에 직접 기록하여 완성 ZIP+조각의 압축 데이터 중복을 줄였습니다.
속도 배수/현장 완료 시간은 측정하지 않았습니다. 작은 모의 데이터 통과를 244만건 현장 완료로 간주하지 않습니다.

2. R1 중단 파일을 그대로 이어서 실행 — 이번 현장용
R1 프로세스가 종료되었는지 확인합니다. 다른 추출/전체본을 동시에 실행하지 않습니다.
새 ZIP을 실제 TRANSFER 폴더에 올리고 그 폴더에서 아래 세 줄을 실행합니다.

python3 -m zipfile -e ./LEGAL_ORACLE_QUERY_PARTS_20261020_R2.zip ./query-transfer-r2-tools
bash ./query-transfer-r2-tools/LEGAL_ORACLE_QUERY_PARTS_20261020_R2/CODESPACE_QUERY_50MB_RUN.txt check --output /workspace/QUERY_TRANSFER_20261020_R1
bash ./query-transfer-r2-tools/LEGAL_ORACLE_QUERY_PARTS_20261020_R2/CODESPACE_QUERY_50MB_RUN.txt export --resume-r1 --output /workspace/QUERY_TRANSFER_20261020_R1

출력 폴더명 R1은 오타가 아닙니다. 2.88GB 임시 DB와 기존 기록이 있는 폴더를 그대로 재사용하기 위해서입니다.
코드 폴더는 query-transfer-r2-tools, 실행 ZIP은 R2입니다. 원래 R1 코드 폴더를 덮어쓰지 않습니다.
TRANSFER의 절대 위치를 ~/TRANSFER 등으로 추정하지 않고 실제 업로드한 폴더에서 실행합니다. ~/DEV로 이동/코드 적용/Git push는 필요 없습니다.
기본 입력은 기존과 같은 /nfs-root/diamo/8-agent/term-releases/financial-risk-success-20261005-schema-r2/generation 입니다.
기존 실행에 --generation 다른경로를 사용했다면 위 check/export에도 정확히 같은 값을 붙입니다.

--resume-r1은 배포한 R1의 두 코드 해시가 정확히 일치하고 원본 generation/파일 해시/검색 선택표가 동일한 중단 작업에만 허용됩니다.
export-state.r1-preserved.json에 이전 기록을 보관하고 첫 deadline을 유지합니다.
이미 저장된 행을 처음부터 다시 계산·대조하고 동일한 행은 재삽입하지 않습니다. 재확인에 시간이 걸릴 수 있습니다.
ROWS_CHECKED: 기존 행을 대조 중. rows_added=0이면 중복 저장하는 것이 아닙니다.
ROWS_SAVED: 기존 지점을 지난 새 행을 저장 중.
한 행이라도 다르면 EXPORT_RESUME_CONFLICT로 중단합니다. 기존 데이터를 고쳐 맞추지 않습니다.
완성 query-data.db/ZIP/download가 이미 있는 R1은 이 업그레이드 대상이 아닙니다. R1 완료본과 중단본을 섞지 않습니다.
업그레이드 후에는 R2의 같은 명령을 계속 사용합니다. 보관된 상태 JSON을 수동으로 원복하거나 코드 해시를 고치지 않습니다.

완전히 새로 시작할 때만 아래처럼 새 output을 사용하고 --resume-r1을 생략합니다.
bash ./query-transfer-r2-tools/LEGAL_ORACLE_QUERY_PARTS_20261020_R2/CODESPACE_QUERY_50MB_RUN.txt export --output /workspace/QUERY_TRANSFER_20261020_R2
이번 사용자 중단 파일 재개에는 위의 기존 R1 output 명령을 우선 사용합니다.

3. 로그 읽기
콘솔 로그: 실제 실행 TRANSFER의 ./query-transfer-command-logs/run-*.log
구조화 기록: /workspace/QUERY_TRANSFER_20261020_R1/events.jsonl
상태/원본 결속: 같은 폴더 export-state.json, 이전 상태 export-state.r1-preserved.json

PHASE / PROGRESS의 주요 값:
phase: 현재 단계
asset/table: 처리 중인 파일과 테이블
phase_seconds: 현재 단계 경과 시간. 전체 ETA가 아닙니다.
rows_checked / rows_added: 이번 실행의 확인 행과 새로 추가한 행
sqlite_steps: SQLite가 실행한 작업량(10,000 VM 연산 단위로 누적). 저장 행 수가 아니며 해시/Python 처리에는 증가하지 않습니다.
cpu_seconds: 프로세스 누적 CPU 시간. 사용률 퍼센트가 아닙니다.
free_bytes: output 파일시스템의 남은 바이트
rss_kib: 프로세스 실제 메모리 사용
 temp_dir_hint/temp_free_bytes: SQLITE_TMPDIR 또는 Python 임시 디렉터리 기준의 참고 경로/공간. SQLite 빌드의 실제 파일 위치는 현장 설정에 따라 다를 수 있습니다.
bytes_done/bytes_total: 압축에 읽은 DB 바이트. 압축 단계에서 사용합니다.

주요 단계:
SOURCE_HASH_CHECK: 원본 파일 해시 확인
SOURCE_ROW_HASHES: 기존 Oracle 원문 릴리스 설명자 계산
TABLE_SCAN: 일반 테이블/view 행 처리
FTS_LENGTH_AGGREGATE: 토큰을 한 번 읽어 문서별 길이 집계
FTS_LENGTH_ROWS: 집계한 길이를 기본키로 연결
FTS_POSTINGS_SORT: 토큰 위치를 정렬하고 게시 행 생성
NATIVE_NAVIGATION: 문서 구조/용어 탐색용 행
ASSET_HASH_CHECK / SOURCE_FINAL_HASH_CHECK: 원본 불변 검사
VERIFY_DB: 최종 행·건수·해시 대조
ZIP_DIRECT_TO_PARTS: 별도 완성 ZIP 없이 직접 조각 압축
PART_READY: 검증 대상 조각 파일 하나 완성
EXPORT_COMPLETE: 전체 반출과 검증 목록 생성 완료

PROGRESS는 약15초마다 프로세스 측정값을 보여 주며 완료 증거가 아닙니다.
rows가 그대로여도 FTS_LENGTH_AGGREGATE/FTS_POSTINGS_SORT에서 sqlite_steps가 증가하면 SQL 내부 작업이 진행 중인 것입니다.
마지막 출력이 FAILED/PAUSED/INTERRUPTED이면 성공으로 보지 않습니다.

4. 다운로드 — R2에서는 전체 ZIP 파일이 없는 것이 정상

EXPORT_COMPLETE 이후 download의 모든 조각과 parts-manifest.json을 각각 우클릭 → Download합니다.
각 조각은 최대49,000,000바이트입니다. 조각 하나를 ZIP으로 압축해제하지 않습니다.
query-data.zip 자체는 R2 기본 명령에서 만들지 않습니다. Dataiku에서 조각을 병합하여 검증합니다.
부분 파일을 수동으로 지우거나 journal을 삭제하지 않습니다.

5. 공간·중단·재개
사용자 화면에서 남은1.6GB로 전체 완료를 보장할 수는 없습니다. DB의 남은 행과 조각 공간이 추가로 필요합니다.
R2는 완성 ZIP 중복을 없앴지만 데이터 자체의 저장 공간을 없애지는 않습니다.
output/참고 임시파일시스템 또는 RAM 여유가512MiB 미만이면 감지 지점에서 중단하고 상태를 보존합니다.
이 기준은 완료에 충분한 용량이라는 뜻이 아닙니다. DISK_LOW/TEMP_DISK_LOW이면 공간 확장/위치 검토 후 같은 기록으로 재개해야 합니다.
TEMP 집계/정렬도 디스크를 사용합니다. 실행 중 작업 DB/SQLite journal을 다른 위치로 임의 이동하지 않습니다.
한 번에 하나만 실행하고 코드스페이스 Python 주소 공간 한도6GiB를 유지합니다.
1회 export 기본6시간, 최초 작업 deadline7일을 유지합니다. 해시/일부 Python 구간은 다음 검사 경계에서 중단될 수 있습니다.
Ctrl+C는 중단 요청입니다. 실행 종료와 종료 로그를 확인한 뒤 다시 시작합니다. SQLite callback을 설치한 집계/정렬은 작업 중 취소를 확인합니다.
압축이 중단되면 같은 DB에서 다시 압축하며 완성된 조각은 바이트 해시를 대조해 재사용합니다. 실패 중간 파일은 보존합니다.
원본·실패 기록·이전 코드·완료 버전을 자동 삭제하지 않습니다.

앞서 발송한 전체본 FULL_PARTS R1 ZIP은 이번 R2 최적화를 포함하지 않습니다. 이번 현장 확인은 추가본 R2만 대상으로 합니다.
