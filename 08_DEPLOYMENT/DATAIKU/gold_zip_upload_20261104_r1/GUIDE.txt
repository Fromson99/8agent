Dataiku에 이미 보낸 데이터 ZIP 조각을 넣고 실행하는 방법
2026-11-04 / 기존 Gold ZIP Flow R1의 업로드 위치를 지정한 실행문

1. 넣는 위치
   Dataiku → LEGAL_RAG 프로젝트 → Flow → Managed Folder ehA8dpVm → Files/Upload
   아래 파일을 같은 폴더의 맨 위(루트)에 올립니다. 직접 압축을 풀지 않습니다.

   실행 코드: DATAIKU_GOLD_ZIP_FLOW_20261104_R1.zip
   데이터:    genos-rag-data-20261007T002029Z-7c0b050f.zip.part000000
              ...
              genos-rag-data-20261007T002029Z-7c0b050f.zip.part000033
   해시:      PARTS.sha256
              ORIGINAL.sha256

   코드1 + 데이터34 + 해시2 = 총37파일입니다. 기존 다른 파일은 그대로 두어도 됩니다.
   데이터가 이미 다른 Managed Folder에 올라가 있으면 옮기지 않고
   실행문의 INPUT_FOLDER_ID만 해당 폴더 ID로 바꿉니다.
   ehA8dpVm는 과거 전달에서 사용한 LEGAL_RAG의 폴더 ID입니다.
   새 프로젝트의 폴더 ID는 다르므로 EXPECTED_PROJECT/CODE_FOLDER_ID/INPUT_FOLDER_ID를 함께 맞춥니다.

2. 실행하는 위치
   LEGAL_RAG → Notebooks → 새 Python 노트북
   DATAIKU_GOLD_ZIP_UPLOAD_RUN_R1.txt 전체를 셀 하나에 붙여넣습니다.
   이 TXT는 Bash/SQL이 아니라 Python입니다.
   기존 적재 노트북과 별도의 새 커널에서 실행합니다.

3. 맨 위 설정
   반드시 입력: GOLD_OWNER = 실제 IDD_B003_LGL_* 테이블 소유 스키마명
   연결 기본값: ORACLE_CONNECTION='AIDP', EXPECTED_DB_USER='PIDD2APP'
   접속 계정(PIDD2APP)과 테이블 소유 스키마는 다를 수 있습니다.
   임베딩 기본값: openai:genos-embedding:embedding-kure-v1 / 1024차원
   위 연결/계정/모델 값은 과거 전달 기준이며 현재 현장 값이 다르면 수정합니다.

   WORK_DIR는 모든 Python 레시피가 읽고 쓸 수 있는 영속 Linux 절대경로를 권장합니다.
   Managed Folder ID나 S3 URL을 넣는 칸이 아닙니다.
   비워 두면 같은 DSS 호스트의 /tmp/legal-gold-zip-flow/LEGAL_RAG를 사용합니다.
   이 경우 레시피를 같은 호스트에서 실행해야 하며 /tmp 삭제 후 재개는 불가능합니다.
   컨테이너마다 로컬 /tmp가 다르면 공유 마운트 경로를 지정해야 합니다.
   이미 설치한 Flow의 설정/작업 경로를 임의로 바꾸면 기존 상태와 충돌하여 중단합니다.

4. 실행
   셀 실행 → 폴더/업로드 목록/코드 해시 확인 → Flow 설치 → Scenario 한 번 시작
   기본 RUN_AFTER_INSTALL=True입니다. False로 바꾸면 설치만 합니다.
   Scenarios → G19ZIP_RUN_ALL · ZIP부터 Gold 벡터까지 → 실행 상태를 확인합니다.
   설치만 한 경우에는 이 시나리오를 Run 합니다.
   실행 중 셀을 반복 실행하지 않습니다. 시작 응답이 끊겼으면 Scenarios에서 상태를 먼저 확인합니다.
   실패/중단 후 재개할 때는 동일한 설정/WORK_DIR로 같은 시나리오를 다시 실행합니다.
   임베딩 요청 결과가 불명확한 경우에는 자동 재호출하지 않고 중단됩니다.

5. 처리 내용과 결과 위치
   00_INPUT   입력 목록과 실제 Oracle 구조 확인
   01_RESTORE 각 조각·전체 ZIP SHA 검증, ZIP 병합, 선택된 generation 복원
   02_PREPARE 원문·검색 적재 자료 준비 및 컬럼 길이 검사
   03_SOURCE  DOC_VER/DOC_UNIT/DOC_BLK 적재
   04_SEARCH  SRCH_ROW 적재
   05_PUBLISH SRC_POST/SRCH_POST/SRCH_CHNL 게시 기록
   06_VECTOR  구조 단위 임베딩·VCTR_POST/VCTR_ITEM/VCTR_HEAD 적재
   07_REPORT  결과와 조회 연결 정보 출력

   Flow의 G19ZIP_07_REPORT_RESULT 폴더:
     latest.json             마지막 report 단계 상태
     report.json             적재 건수/게시 ID
     serving-mapping.json    실제 물리 테이블 연결
     documents.json          게시 문서 목록
     embedding-profile.json 적재 임베딩 프로필
   각 단계의 RESULT 폴더에는 latest.json 및 runs/의 실행 이력·로그가 있습니다.
   시나리오 성공과 report.json을 함께 확인합니다. 설치 셀 종료만으로 완료가 아닙니다.

6. 적용 범위
   IDD_B003_LGL_* 등록 테이블13개·최신 컬럼60개 기준입니다.
   RGLT_DOC_ID 100 BYTE, RGSN_ASTM, RFRN_DATA_HASH_VALU/CTNT, CHAN_NO를 사용합니다.
   운영 테이블은 미리 생성되어 있어야 합니다. 이 실행문은 DDL/삭제를 실행하지 않습니다.
   기존 *_1 개발계 적재와 다른 작업이며 과거 적재의 재개용으로 사용하지 않습니다.
   온톨로지는 구조 확인만 하고 지식을 자동 작성/승인하지 않습니다.
   벡터는 이번 검색 게시본에 연결합니다. 기존 서비스의 선택 채널은 전환하지 않습니다.
   기존 로컬/GENOS 원문을 다시 ZIP으로 만들거나 새로 다운로드할 필요가 없습니다.

7. 파일 형태가 다를 때
   이번 실행문은 확인된 34개 .zip.part 조각용입니다.
   통합 ZIP 한 개, 다른 날짜 ZIP, 별도 추출용 FULL_PARTS/QUERY_PARTS는 같은 입력으로 간주하지 않습니다.
   파일명만 바꾸거나 ZIP을 수동으로 풀어 넣으면 안 됩니다.

8. 확인 범위
   기존 엔진은 합성34조각과 실제 로컬 임시 Oracle에서 적재/재개/조회 검증 기록이 있습니다.
   이번 추가분은 업로드 위치 설정과 노트북 진입문이며 기존 적재 엔진 ZIP 바이트는 같습니다.
   이번 노트북 검증은 로컬 Dataiku 대역입니다. 현장 Dataiku/원본전체/실제 임베딩 실행은 미확인입니다.
   상세 결과는 VALIDATION.json을 확인합니다. 메일 발송 상태는 별도 EMAIL_SENT.json에 기록합니다.
