1. 이미 생성한 Dataiku Managed Folder에 업로드
폴더 최상위에 다음 파일들을 올립니다.
- genos-rag-data-20261007T002029Z-7c0b050f.zip.part000000부터 마지막 번호까지 모든 조각
- PARTS.sha256 (PARTS (1).sha256처럼 저장된 복사본도 지원)
- ORIGINAL.sha256 (사진의 ORIGINAL (4).sha256 등도 지원)
- 이번 LEGAL_ORACLE_EXISTING_ZIP_20261020_R2.zip (작은 실행 코드 ZIP)

사진의 조각명은 예시입니다. 실제 파일명은 체크섬 목록에서 읽으며 수동으로 바꾸지 않습니다.
체크섬 .sha256 파일은 압축해제 대상이 아닙니다. 그 안의 해시/목록을 편집하지 않습니다.
다른 묶음의 조각을 섞지 않습니다. 폴더 자체가 아니라 파일들을 Managed Folder 최상위에 올립니다.
로컬 파일이 모두 있다는 것을 사진으로 확정할 수는 없습니다. inspect가 누락된 번호/파일명을 알려줍니다.

2. Dataiku 새 Python 노트북 / 새 커널
별도 첨부 DATAIKU_EXISTING_ZIP_IMPORT_RUN.txt 전체를 한 셀에 붙입니다.
또는 ZIP의 DATAIKU_EXISTING_ZIP_IMPORT.ipynb를 가져옵니다. 두 코드 내용은 같습니다.
상단에서 우선 다음 두 값만 실제 값으로 설정합니다.
FOLDER_ID = 생성한 Managed Folder의 실제 ID (화면에 표시되는 이름과 구분)
ORACLE_CONNECTION = 기존 SIDDA 테이블에 연결하는 Dataiku Oracle 연결 이름

아래는 기본값 그대로 둡니다.
INPUT_MODE = "legacy_parts"
ACTION = "inspect"
ORIGINAL_SHA_FILE = ""
PARTS_SHA_FILE = ""
WORK_DIR = "./legal-existing-zip-r2-work" (충분한 공간이 있는 영속 경로, 재개 시 유지)
DATA_ZIP_NAME은 legacy_parts 모드에서 사용하지 않습니다.
사진의 SFTP 연결도 로컬 파일 경로를 추정하지 않고 Dataiku의 목록/다운로드 스트림 API로 읽습니다.
API 근거: https://developer.dataiku.com/latest/concepts-and-examples/managed-folders.html

3. ACTION 순서 — 매번 같은 셀 전체 실행
inspect : SHA 목록과 실제 업로드 파일명 확인. 큰 조각을 읽지 않습니다. 정상 결과 LEGACY_PARTS_READY.
merge   : part000000부터 숫자 순서대로 병합, 각 조각 SHA와 전체 원본 SHA 검증. 정상 결과 VERIFIED_ZIP_READY.
restore : 검증된 ZIP을 재사용하고 명시 generation 원문·용어집·색인을 Dataiku 작업 폴더에 복원/검증.
check   : 복원 데이터 및 기존 Oracle 테이블/조회 인덱스 확인. 데이터 쓰기 없음.
publish : 기존 원문/자산/조회 엔진으로 중복 대조·누락 적재 후 전체 읽기 대조. 정상 결과 FULL_DATA_VERIFIED.
status  : 이후 별도 전체 대조가 필요할 때만 사용. publish 성공 직후 불필요하게 반복할 필요 없습니다.

병합만 먼저 확인하려면 merge까지 실행하면 됩니다. Oracle 연결 설정은 check/publish 단계에서 사용합니다.
inspect/merge/restore는 Oracle에 데이터를 쓰지 않습니다.
완료 ZIP: WORK_DIR/legacy-joined/legacy-verified.zip
이 ZIP을 PC로 내려받거나 다시 업로드할 필요 없이 restore가 직접 사용합니다.

4. 같은 이름의 체크섬 복사본 처리
ORIGINAL (2).sha256 / ORIGINAL (3).sha256 / ORIGINAL (4).sha256처럼 여러 개가 있어도 검증 내용이 같으면 자동으로 사용합니다.
PARTS.sha256 / PARTS (1).sha256도 동일합니다. CRLF·UTF-8 BOM·UTF-16 BOM을 처리합니다.
서로 다른 내용이면 AMBIGUOUS_CHECKSUM으로 멈추며 임의로 최신 번호를 고르지 않습니다.
그때 확인한 정확한 파일명만 설정합니다. 예:
ORIGINAL_SHA_FILE = "ORIGINAL (4).sha256"
PARTS_SHA_FILE = "PARTS.sha256"
이는 예시이지 (4)가 항상 맞다는 뜻이 아닙니다. 최종 조각 SHA와 전체 원본 SHA가 모두 맞아야 다음 단계로 갑니다.
체크섬이 없는 묶음은 검증 목록 없이 임의 병합하지 않습니다.

5. 과거 끝 1바이트 문제
이 묶음은 과거 part000030 끝에1바이트가 붙었던 현장 기록이 있습니다. 현재 파일도 그렇다고 단정하지 않습니다.
기본은 조각 그대로 SHA 검증합니다.
한 조각만 끝1바이트를 제외했을 때 해당 원본 조각 SHA와 일치하면 새 출력 ZIP에서만 그 바이트를 제외합니다.
그 뒤 전체 ZIP의 SHA도 ORIGINAL 파일과 일치해야 VERIFIED_ZIP_READY가 됩니다.
TAIL_BYTE_CANDIDATE는 중간 상태이며 복구 완료가 아닙니다.
중간 바이트 변조/끝2바이트/여러 조각 오류/전체 원본 SHA 불일치는 중단합니다.
Managed Folder에 업로드한 조각·체크섬을 수정하거나 삭제하지 않습니다.

6. 공간·로그·중단
1MiB 단위로 Managed Folder 조각을 읽어 한 개의 로컬 ZIP에 바로 씁니다. 로컬에 전체 조각 복사본을 따로 만들지 않습니다.
Dataiku 작업 디스크에는 ZIP 크기 + 선택 generation 압축 해제 크기 + 작업 여유가 필요합니다.
가용 디스크/RAM이512MiB 미만이면 감지 지점에서 중단합니다. 이 수치가 완료에 충분한 공간이라는 뜻은 아닙니다.
병합 1회6시간, 최초7일 기한을 보존합니다. 네트워크 스트림 자체가 반환되지 않는 경우까지 즉시 강제 중단을 보장하지는 않습니다.
한 번에 한 작업만 실행합니다.

WORK_DIR/legacy-joined/legacy-join-state.json : 입력/코드/최초 기한, 검증 조각, 1바이트 처리, 완료/실패
WORK_DIR/legacy-joined/events.jsonl : 처리 파일·단계·조각 번호·바이트·CPU/메모리/공간 로그
약15초 PROGRESS와 조각별 PART_VERIFIED가 표시됩니다.
병합 실패 시 부분 ZIP은 보존합니다. 같은 ACTION/WORK_DIR로 재실행하면 병합은 첫 조각부터 다시 합니다.
실패한 부분 ZIP 때문에 공간이 더 필요할 수 있습니다. 종료/원인 확인 없이 파일을 임의 삭제하지 않습니다.
완성 ZIP이 있으면 전체 원본 SHA를 다시 대조해 재사용하며 다른 내용의 기존 파일을 덮어쓰지 않습니다.
복원·Oracle 적재는 이전 R1과 같은 체크포인트 재개 규칙입니다.

7. Oracle 중복 및 범위
같은 원문 버전/키/내용 및 자산 해시는 재사용하고 없는 항목만 삽입합니다.
조회 행은 같은 release/키에 없으면 삽입하고 있으면 내용을 대조합니다. 검사 SQL은 실행할 수 있지만 같은 행을 중복 저장하지 않습니다.
검색 선택표/publisher가 다르면 새 조회 릴리스가 될 수 있어 버전이 다른 조회 행은 별도로 생성할 수 있습니다.
기존 키의 값이 다르면 멈추며 DELETE/TRUNCATE/전체 덮어쓰기 기능은 없습니다.
ACTIVE/STATE·서빙 리비전/포인터 전환은 하지 않습니다. 마지막 전수 대조를 마친 FULL_DATA_VERIFIED가 완료 기준입니다.

ZIP에 명시된 generation 원문·navigation/fulltext/glossary·검색 선택표를 처리합니다.
runtime 대화/대사 이력, 옛 ZIP의 실행 코드, 다른 generation은 Oracle 적재 대상이 아닙니다.
10월7일 파일명·해시 일치는 10월20일 최신 자료라는 증명이 아닙니다. 실제 보유 파일 내용/최신성은 현장 확인 전입니다.
이 도구는 Dataiku 이관용이며 GENOS 서빙에 전체 DB를 저장하도록 바꾸지 않습니다.
