R5 — 기존 NFS 이관의 Oracle 원문 검증 조회 최적화
대상: Dataiku LEGAL_RAG / AIDP / 개발 SIDDS / 기존 R2·R3·R4 이관 작업
작성일: 2026-10-30

1. 변경과 확인 범위

본문을 1,000 UTF-16 단위 조각으로 여러 번 조회하던 경로에 Dataiku JDBC의
전체 CLOB 묶음 읽기를 추가했다. 예상 입력 길이로 SQL 반환량을 제한하고,
반환 길이/타입/키 및 모든 컬럼의 원래 내용을 대조한다.
드라이버가 문자열을 잘라 주거나 전체 CLOB 읽기를 지원하지 않으면 실패를 기록하고
그 실행에서는 원래 조각 조회로 돌아간다. 잘린 내용을 통과시키지 않는다.

verify/final_source만 배치를 최대20행에서 최대100행으로 늘린다.
기존256KiB 배치 기준은 유지하며 긴 행이 있으면100행보다 적게 처리한다.
실제 쓰기는 기존20행 단위와 동일하고 source/run의 쓰기 후 대조도 유지한다.
전체 원문 검증, 마지막 원문 재검증, 자산/검색행 검증을 생략하지 않는다.

로컬 실제 Oracle의 긴 본문20행 비교: 조각 읽기 SQL11회 -> 전체값 읽기1회,
모든 원문/메타데이터 내용 동일. 모의 전수검증205블록: SQL22회 ->10회.
시간 단축률이나 현장 완료시간을 뜻하지 않는다. 실제 Dataiku JDBC는 현장 미검증.

2. 파일과 업로드

- DATAIKU_EXISTING_NFS_CLIENT_20261030_R5.zip: 실제 전체 클라이언트 코드.
  압축을 풀지 않고 LEGAL_RAG 관리 폴더 ehA8dpVm에 이 이름 그대로 업로드한다.
- DATAIKU_EXISTING_NFS_RUN_R5.txt: notebook 실행 셀 전체.
- GUIDE.txt: 이 사용 안내.

바깥 전달용 ZIP이나 중첩 ZIP은 없다. 기존 R4 ZIP은 보존한다.
별도의 GENOS 코드서빙 반입/Git push/DB 테이블 생성은 필요 없다.
기존 NFS 데이터, 관리 폴더의 체크포인트, 원래 이관 디렉터리를 지우지 않는다.

3. 현재 실행에서 전환하는 순서

실행 중인 커널에 R5를 덮어씌우거나 같은 이관을 다른 notebook에서 동시에 실행하지 않는다.
현재 R4가 종료/PAUSED/STOPPED이고 커널 Idle인 경우 아래 순서를 사용한다.
검증 중인 R4를 전환하려면 Kernel > Interrupt로 중단을 요청하고, 현재 셀이 끝나
STOPPED/오류 기록이 저장되고 커널 Idle로 바뀌었는지 먼저 확인한다.
중단 요청 후 계속 Busy라면 다른 적재를 시작하지 않는다.

중요: 기존 R4의 verify는 행별 재개 커서를 저장하지 않는다.
R5로 전환해도 완료된 적재와 체크포인트는 보존되지만,
진행 중이던 verify 테이블 위치는 재사용하지 않고 해당 verify를 처음부터 대조한다.
예를 들어 본문51,537행까지 확인한 상태에서 중단해도51,538행부터 이어읽는 것은 아니다.
이미 완료된 source/assets/query 단계는 기존 영수증에 따라 재사용한다.
시작부터 다시 적재하거나 DB를 비우는 작업은 아니다.

4. 실행

이전 실행 종료 확인 후 Kernel > Restart한다.
DATAIKU_EXISTING_NFS_RUN_R5.txt 전체를 같은 프로젝트의 Python notebook 셀에 붙인다.
처음에는 파일 기본값대로 실행한다:

ACTION = 'check'
CLOB_BATCH_READS = 32
NATIVE_CLOB_READS = True
VERIFY_BATCH_ROWS = 100

NFS_READY_FOR_TRANSFER를 확인한다. 그 다음 같은 전체 셀의 ACTION만 바꾼다:

ACTION = 'load'

그 전체 셀을 한 번 실행한다. transfer나 기존00/01/02/03 전체 레시피를 다시 실행하지 않는다.
최초 작업의7일 기한, 누적 SQL/HTTP100만 호출 한도와 원래 pending 처리도 유지한다.

5. 실행 중 표시

SOURCE_NATIVE_CLOB=True; VERIFY_BATCH_ROWS=100
SOURCE_NATIVE_CLOB_CONFIRMED rows=...

뒤 표시는 첫 실제 전체값 대조가 성공했을 때 나온다.
드라이버의 제한이 있으면 SOURCE_NATIVE_CLOB_FALLBACK=...가 나온다.
이때 기존 조각 조회로 이어지며 기존 검증 기준을 유지한다.

block_payload: .../... verified; SQL calls=...;
rows_per_second=...; table_eta_seconds=...

table_eta_seconds는 해당 테이블에서 이번 실행이 처리한 평균 속도로 계산한 예상값이다.
본문 길이/DB 부하에 따라 변하며 이후 assets/query/final_source 시간을 포함하지 않는다.
검증 전체를100%로 오인하지 않는다. FULL_DATA_VERIFIED가 전체 이관 검증 완료다.
전체 이관 완료와 GENOS 서빙 활성화·실제 RAG 최종답변 통과는 별도다.

6. 호환 문제/중단/재개

실패 출력과 체크포인트를 보존한다. 같은 R5로 재개하며 파일/상태를 삭제하지 않는다.
전체 CLOB 방식만 끄고 싶다면 현재 실행 종료/Idle 후 같은 R5 셀에서
NATIVE_CLOB_READS = False로 바꿔 실행한다. 검증 배치는100행으로 유지할 수 있다.
원래 배치 크기까지 사용하려면 VERIFY_BATCH_ROWS = 20으로 설정한다.
조각 묶음 조회의 호환 문제이면 CLOB_BATCH_READS = 1로 설정할 수 있다.
이 세 옵션은 검사나 기한/누적예산을 해제하는 옵션이 아니다.

업그레이드 전 full-state 원본과 R4 호환 이력은 별도 백업/영수증에 남는다.
R5 전환 뒤 옛 R4 코드로 체크포인트를 강제 실행하지 않는다.
기존 방식으로 복귀할 때는 같은 R5의 위 옵션을 사용한다.

7. 적용 상태

기존 봉인 R2/R3/R4와 제품 MAIN·GENOS 서빙 코드는 변경하지 않았다.
로컬 Oracle + 모의 Dataiku/NFS/S3 포트 검사이며 실제 현장 반입/속도는 미확인이다.
발송 여부는 별도 EMAIL_VERIFIED.json이 있을 때만 확인된 것으로 본다.
