Gold 판본 선택 보완 플로우 R7f · 2026-11-09 (검색 행 이동을 인덱스 순서 구간 방식으로 개선) (사용자 프로젝트 직접 생성 · JSON 함께 ZIP · 버킷 쓰기 없음)

레시피는 입력 폴더의 판본 선택 JSON을 읽기만 하고 Oracle Gold만 UPDATE한다. 폴더·버킷에는 쓰지 않는다.
결과·진행은 레시피 실행 로그에만 남고, 되돌리기·재개에 필요한 원래 번호는 DB에서 다시 찾는다.

[개발계]
1) Dataiku에서 새 프로젝트를 직접 만든다(예: GOLD_SELECTION_FIX). 빈 프로젝트여야 한다.
2) 그 프로젝트에서 Python 노트북을 열고 DATAIKU_CREATE_GOLD_FIX_FLOW_R7.txt 전체를 셀 하나에 붙여 넣는다.
   PARAMS
   - REFERENCE_FOLDER : 비워 두기(권장). 입력 폴더를 DSS 서버 디스크(filesystem_folders)에 만든다.
                        → Export 때 폴더 안 JSON이 ZIP에 들어가고, 운영에서 가져올 때 버킷에 쓰지 않는다.
   - ORACLE_CONNECTION / EXPECTED_DB_USER / GOLD_OWNER : 운영 값 AIDP / PIDD2APP / SIDDG (프로젝트 변수로 들어감)
3) 실행 → 입력 폴더 gold_selection_input + 빈 출력 폴더 gold_selection_noop + 레시피 GOLD_SELECTION_FIX_R7 생성,
   '입력 폴더가 비어 있습니다' 안내. (Dataiku는 python 레시피에 출력이 꼭 있어야 해서 빈 폴더를 연결만 한다. 레시피는 쓰지 않는다)
4) 판본 선택 JSON을 gold_selection_input 폴더에 업로드(.json 하나만)
   JSON 만들기(GENOS 터미널 한 줄):
   cp /nfs-root/diamo/8-agent/term-releases/financial-risk-success-20261005-schema-r2/SEARCH_SELECTION/generation.json /workspace/TRANSFER/SEARCH_SELECTION_GENERATION.json && sha256sum /workspace/TRANSFER/SEARCH_SELECTION_GENERATION.json
5) 같은 셀을 다시 실행 → '입력 JSON 확인: ... term-source-533a15307cda1265e17e manifest bf643c59... 빠지는 옛 판본 N' 확인
6) 프로젝트 메뉴 > Export → '관리 폴더(Managed folders) 내용 포함'을 켜고 ZIP을 받는다.
   (새 프로젝트라 이 플로우만 들어간다. 노트북은 같이 가도 실행되지 않는다.)

- 새 프로젝트에 다른 폴더·레시피·데이터셋이 있으면 PROJECT_NOT_EMPTY 로 멈추고 무엇이 있는지 보여준다.
- 다시 실행해도 안전하다(있는 것은 재사용, 레시피 코드만 최신으로 맞춤, 바꾼 변수는 유지).
- 앞선 설치본으로 만든 레시피(출력 없음, 'Output role main is required' 오류)는 이 셀을 다시 실행하면 빈 출력 폴더가 연결된다.
  화면에서 직접 고치려면: 레시피 Inputs/Outputs > Outputs + Add > New folder 'gold_selection_noop'(filesystem_folders) > SAVE.

[운영]
1) + New Project > Import project > ZIP. 폴더 연결은 filesystem_folders 그대로.
2) gold_selection_input 폴더에 JSON이 들어 있는지 확인
3) 프로젝트 설정 > 변수: GOLD_FIX_MODE=APPLY(기본), GOLD_FIX_ORACLE_CONNECTION=AIDP, GOLD_FIX_EXPECTED_DB_USER=PIDD2APP, GOLD_FIX_GOLD_OWNER=SIDDG
4) 레시피 GOLD_SELECTION_FIX_R7 > RUN 한 번 → 로그 APPLIED → 코드서빙 재기동(DP_QUERY_CHANNEL 그대로)
   - UPDATE 전에 먼저 확인: 선택 파일이 운영 세대용인지, 권한이 있는지. 아니면 아무것도 바꾸지 않고 멈춘다.
   - 로그 PLAN 줄: documents 2121, search_rows 60971724
   - PRIVILEGE_REQUIRED 면 로그의 GRANT 줄을 DBA에 요청
     (UPDATE: IDD_B003_LGL_SRCH_ROW / VCTR_ITEM / VCTR_HEAD / SRCH_CHNL, INSERT: SRC_POST / SRCH_POST / VCTR_POST)
   - 끊기면 다시 RUN(남은 행부터). ALREADY_APPLIED 면 끝난 것. 확인만: GOLD_FIX_MODE=CHECK. 되돌리기: ROLLBACK.

[DBA 공유] 검색 행 60,971,724행의 번호 컬럼 UPDATE로 인덱스 5개가 함께 바뀌어 redo/아카이브 로그가 많이 생긴다. 시간 미측정.

[검증]
- 레시피: 폴더에 쓰면 실패하도록 막은 상태로 로컬 Oracle 23 임시 계정에서 12항목 통과(현장 오류 재현, 권한 없으면 쓰기 전 중단,
  다른 세대 파일 거절, 응답 유실 후 재개, 현재 MAIN 서빙 시작·벡터 검사 통과, 옛 판본 검색 제외, 되돌리기·재적용, 폴더 쓰기 0).
- 설치 스크립트: Dataiku API 대역 6항목 통과(프로젝트 생성·내보내기 안 함, 입력 폴더·레시피만 생성, 재실행 재사용·코드 갱신,
  업로드한 JSON 확인·JSON 2개 거절, 출력 필수 시 빈 폴더 연결, 다른 객체 있는 프로젝트 거절).
- 미확인: 실제 Dataiku(출력 없는 레시피 허용, Export의 폴더 내용 포함·가져오기), 운영 규모 시간·로그량, 큰 CLOB 읽기, 운영 권한.

[R7f 변경: 검색 행 이동 속도]
- 이전: UPDATE ... WHERE 번호=옛번호 AND ROWNUM<=20000 을 반복. 표 거의 전부가 옛 번호라 Oracle이 표 전체 읽기(FULL)를 고르면
  회차마다 이미 바꾼 앞부분을 다시 읽어 뒤로 갈수록 느려진다.
- R7f: 종류(RFRN_DTA_TYPE_VALU)별로 PK 인덱스(번호, 종류, ID) 순서를 따라
  ① 다음 5만 행의 끝 ID를 인덱스로 찾고 ② '지난 끝 < ID <= 이번 끝' 구간만 UPDATE 후 COMMIT.
  이미 바꾼 부분을 다시 읽지 않는다. 종류 목록 밖에 남은 행이 있으면 마지막에 기존 방식으로 마저 바꾼다.
- 로그: MOVE_START method=KEYED_BY_TYPE_ID, 1분마다 MOVE_PROGRESS(kind, done, total, rows_per_second, eta_minutes=남은 분)

[지금 돌고 있는 작업을 바꾸려면]
1) 먼저 확인(실행 아님): SQL 노트북에 아래를 넣고 EXPLAIN PLAN
   UPDATE SIDDG.IDD_B003_LGL_SRCH_ROW SET RFRN_POST_HASH_VALU = RFRN_POST_HASH_VALU
   WHERE RFRN_POST_HASH_VALU = (SELECT RFRN_POST_HASH_VALU FROM SIDDG.IDD_B003_LGL_SRCH_CHNL) AND ROWNUM <= 20000
   - TABLE ACCESS FULL 이면 바꾸는 것이 좋다. INDEX RANGE SCAN 이면 지금 작업을 그대로 둬도 된다.
   - 또는 MOVE_PROGRESS 두 줄에서 10분 동안 옮긴 행 수가 줄고 있으면 바꾼다.
2) 바꾸기: Jobs에서 지금 작업 Abort → 레시피 코드 전체를 recipe_gold_selection_fix_r7.py(R7f)로 교체 → SAVE → RUN
   - 이미 옮긴 행은 COMMIT 돼 있어 남은 행부터 이어서 한다(새 게시본 3행은 POST_EXISTS로 건너뜀).
   - 운영에서 코드 수정이 안 되면 개발계에서 설치 TXT(R7f)를 다시 실행 → Export → 운영에서 같은 프로젝트로 다시 Import.
