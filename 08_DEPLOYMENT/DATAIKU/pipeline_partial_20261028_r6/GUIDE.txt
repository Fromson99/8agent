2. GENOS 계산 서비스 코드 적용
진행 중인 02가 있다면 먼저 Dataiku에서 취소하고 계산 종료를 확인합니다.
legal_pipeline_serving의 기존 ~/DEV checkout을 사용합니다. 채팅 RAG checkout이 아닙니다.
  bash GENOS_R6_INSTALL.txt
이 TXT는 ZIP/기존 파일 검사 → 백업 → 적용 → staging → commit → 동일 checkout 검증 → push를 실행합니다.
다른 수정이나 알 수 없는 파일 충돌이면 중단하므로 강제로 덮어쓰지 않습니다.
이후 GENOS 화면에서 해당 commit의 새 코드서빙 리비전을 배포합니다.
프로세스 worker 1 / replica 1, 기존 service(config,data) 진입점입니다.
실제 현장 적용·push·리비전 배포는 이 전달 시점에 실행하지 않았습니다.

3. 이번 전체 Flow의 파서 선택
기본값: LEGAL_PIPELINE_PARSER_MODE=existing-http
원래 전체 Flow의 기존 HTTP 전처리기 연결을 사용합니다. 새 Pod YAML은 요구하지 않습니다.
기존 GENOS_PREPROCESSOR_ID 또는 URL, SHARED_ROOT, 필요 시 REMOTE_ROOT/API_KEY를 유지합니다.
ID=187일 때 주소는 http://preprocessor-187:8080/run이며 URL이 있으면 URL이 우선입니다.
SHARED_ROOT는 양쪽에서 같은 파일을 읽는 실제 공유 경로여야 합니다. /tmp가 공유된다고 추정하지 않습니다.
기존 GENOS 검수 모델 LLM_BACKEND=genos, GENOS_LLM_URL 또는 BASE_URL+SERVING_ID,
필요한 KEY/MODEL 설정도 유지합니다. 설정/연결 부재 자체는 건너뛰지 않습니다.
R6는 전체 Flow의 자식 프로세스에서 HTTP/response auto를 명시하며 외부 공개 모델로 대체하지 않습니다.

앞서 만든 같은 Pod 변환·파싱을 쓰려면:
  LEGAL_PIPELINE_PARSER_MODE=same-pod
  GENOS_STRUCTURE_CONFIG=<실제 Pod에 설치된 parser YAML의 절대경로>
실제 파서 의존성·변환기도 필요합니다. 이 모드는 HTTP로 자동 전환하지 않습니다.
기존 R5 네 문서 진단 기능은 유지되며 그 진단의 YAML 미발견 오류를 해결한 것은 아닙니다.
HTTP와 같은 Pod 모두 현장 실행 리비전에 환경변수를 설정해야 합니다.
00의 ready=true는 설정/코드 검사이며 실제 문서 파싱 성공을 뜻하지 않습니다.
