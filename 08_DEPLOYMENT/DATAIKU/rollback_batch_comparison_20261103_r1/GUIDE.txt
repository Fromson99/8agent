Oracle 추가 비교 검사 R1 — 2026-11-03

1. 목적과 범위
R3 화면의 17.68~23.50시간은 일부 종류의 요청시간을 환산한 가정값입니다.
전체 적재 완료시간이나 보장되는 최소/최대 시간이 아닙니다.
이번 검사는 같은 원본 행을 사용하여 다음을 실제 Oracle에서 비교합니다.
 - 정상 성공 응답 vs R3와 같은 진단용 예외 응답: 종류별 3쌍, 순서 교대.
 - 기존 5,000행/2MiB vs 확대 10,000행/4MiB: 종류별 같은 순서·같은 전체 행으로 3쌍.
 - 모든 배치의 전체 값·CLOB 대조, 롤백 후 잔여0 확인.
 - 같은 행 재전송, 값 충돌, 누락 검출: 별도 격리 트랜잭션에서 검사 후 롤백.

대상은 SRCH_ROW의 entry_corpus_link, occurrence_keys, unit_fts_posting, unit입니다.
종류별 앞쪽 최대10,000행이며 전체를 대표하는 무작위 표본이 아닙니다.
FTS는 최대256개 용어·용어당4,096위치까지 완전한 그룹만 사용합니다.
제한을 넘는 용어는 통째로 제외하며 위치를 잘라 넣지 않습니다.
행 수·바이트 제한 때문에 두 배치의 나뉨이 같으면 배치 비교는 미측정으로 남깁니다.
MiB 기준은 기존 loader.grouped()의 변환 전 projection JSON 바이트입니다.
실제 전송 JSON 크기도 따로 기록하며 한 요청의 CLOB 합계8MiB를 넘으면 중단합니다.

4. 실행 중 동작
실제 소량 INSERT/전체 값 검증/ROLLBACK을 수행합니다. 읽기 전용 검사는 아닙니다.
COMMIT·Oracle DDL·DELETE·quota 변경·임베딩·모델 호출은 하지 않습니다.
고유 시험 release만 사용하며 원래 적재 pending/진행 상태를 재개하거나 고치지 않습니다.
원래 state.json은 실행 전후 SHA-256이 같은지 확인합니다.
원래 job.lock을 잡을 수 없으면 중단합니다.

단일 동작60초/worker600초/부모660초에서 중단하도록 구성했습니다.
시작 전 파일·경로 결속 확인과 프로세스 정리 시간은 별도입니다.
보통 소량 검사지만 현장 실행시간은 아직 측정되지 않았습니다.
진행 화면은 갱신되며 종류·단계·SQL 요청 수가 표시됩니다.
공간 부족 또는 응답불명 오류가 한 번 나면 뒤의 INSERT를 자동 재시도하지 않습니다.
ROLLBACK을 하더라도 Oracle extent/UNDO 공간이 필요하므로 기존 용량 오류가 다시 날 수 있습니다.

5. 완료 확인 — 아래 셀은 저장 결과 표시만 하며 SQL을 다시 실행하지 않습니다.

SHOW_COMPARE_PAGE("요약")
SHOW_COMPARE_PAGE("응답")
SHOW_COMPARE_PAGE("배치")
SHOW_COMPARE_PAGE("정확성")
SHOW_COMPARE_PAGE("상태")

 - COMPLETE: 계획한 종류/비교를 완료. PARTIAL: 미측정 또는 제외 항목 있음.
 - ROLLED_BACK_VERIFIED: 해당 시도의 값 검증과 롤백 후 잔여0 확인.
 - 원래 state.json 내용 보존: True.
 - 정상/예외, 기존/확대의 3쌍이 모두 완료된 종류만 중앙값 비율을 표시.
 - 비율은 우측 요청초 / 좌측 요청초. 1 미만이면 이 표본에서 우측 요청이 짧았다는 뜻.
 - 요청초는 각 표본을 보내는 모든 배치 요청시간의 합.
 - JSON에는 준비/압축/SQL 생성, 전체 시험 경과, 실제 행/바이트/요청수도 남습니다.
 - 정상 응답의 DB 내부 세부 시간은 미측정입니다. 예외 영수증만 세부 시간을 받습니다.
 - 진단용 예외가 느리면 기존 R3 환산시간에 해당 비용이 섞였을 가능성을 검토합니다.
 - 결과는 표본 비교이며 전체 적재 개선율·p95·최종 소요시간으로 확정하지 않습니다.

6. 중단/실패 시
 - 셀이 멈추거나 KeyboardInterrupt/timeout이면 자동 재실행하지 마세요.
 - 클라이언트 프로세스 중단만으로 Oracle 서버 실행 취소를 확인한 것은 아닙니다.
 - 기존 적재 WRITE_UNCONFIRMED의 pending은 그대로 보존합니다.
 - COMPARISON.json, worker-result.json, worker.log와 표시된 상태를 확인합니다.
 - 시험을 시작했다면 같은 결과 폴더의 CHECK_PROBE_ROWS.sql에 시험 release별
   읽기 전용 SELECT가 저장됩니다. DBA가 해당 서버 작업 종료/롤백을 확인한 후,
   그 SELECT의 N=0을 확인하세요. 이 파일은 자동 실행되지 않습니다.
 - 잔여 행이 보이면 임의 DELETE/적재 재개하지 말고 결과를 전달하세요.
 - 실패 기록을 지우지 마세요. 재실행 필요 여부는 결과와 DB 상태 확인 후 결정합니다.

7. 여전히 별도 확인할 항목
최종 Oracle 물리용량(테이블/LOB/인덱스)과 계정 quota/테이블스페이스 여유는
이 코드로 측정하거나 해결하지 않습니다. 앞선 용량 조회에서 ORA-00942가 났던
segments/quota/space 항목은 DBA에게 정확한 대상 소유자와 함께 확인해야 합니다.
실제 전체 원본 생성·COMMIT·전수검증·임베딩 시간도 여기에는 포함되지 않습니다.
실제 원래 pending 배치의 재개 확인 역시 이 검사에 포함되지 않습니다.

검증 범위: 로컬 합성 계약·실패주입·첨부 부트스트랩 검사와 기존 배치 재개 단위 검사.
이번 비교 코드의 실제 Dataiku/Oracle 결과는 현장에서 실행한 뒤 확인합니다.
기존 R3 성공을 이번 코드의 현장 성공으로 대신 표시하지 않습니다.
