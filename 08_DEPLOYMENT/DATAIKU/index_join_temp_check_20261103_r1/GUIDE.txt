Oracle 인덱스·조인·TEMP 읽기 전용 확인 R1 — 2026-11-03

왜 필요한가
사용자 사진의 응답/배치 비교는 세 종류의 비교를 완료했습니다.
배치 요청 수는 절반으로 줄었으나 화면 비율상 요청시간 단축은 약1.8~2.4%였습니다.
이 결과만으로 인덱스 사용 여부, 조인 방식, 실제 처리 행수, TEMP 사용량은 알 수 없습니다.
이번 검사로 기존 저장 결과와 Oracle 메타데이터/캐시를 확인합니다.
기존 SQL에 인덱스 힌트를 넣거나 테이블/인덱스/통계를 변경하는 패치는 아닙니다.

2. 01_RUN_INDEX_JOIN_TEMP_CHECK_R1.txt — 새 Python 셀에 전체 복사할 실행 코드.

실행 환경과 순서
환경: Dataiku LEGAL_RAG, SQL 연결 AIDP, 이전 응답·배치 비교를 실행한 Python 노트북.
사진에서 notebook_13을 사용했다면 같은 노트북의 새 셀입니다. Python3.9 이상.
별도 pip 설치·Bash 실행·커널 재시작이 필요하지 않습니다.
1. 기존 적재/INSERT 작업이 종료된 상태에서 실행합니다.
2. 관리 폴더 ehA8dpVm에 새 ZIP을 원본 그대로 업로드합니다.
3. 01_RUN_INDEX_JOIN_TEMP_CHECK_R1.txt 전체를 새 Python 셀 하나에 붙여넣어 한 번 실행합니다.
4. COMPARISON_PATH는 우선 빈 값입니다. 같은 커널에 남은 이전 비교 결과를 사용합니다.

   COMPARISON.json이 정확히 하나인 경우에만 자동 선택합니다. 최신 시각으로 고르지 않습니다.
   경로가 없거나 여러 개면 COMPARISON_PATH에 이전 요약 화면에 표시된 정확한
   COMPARISON.json 절대경로를 넣습니다. worker-config.json도 같은 폴더에 있어야 합니다.

5. Run All은 누르지 마세요. 기존 INSERT/비교 셀의 재실행은 필요하지 않습니다.

확인하는 내용
- 시간: 이전 COMPARISON.json의 진단용 예외응답 3회에서 복원/INSERT/검증/롤백/전체요청
  항목별 중앙값. DB 시계는0.01초 해상도입니다. 항목별 중앙값 합은 전체 중앙값과 다를 수 있습니다.
  전체 요청에서 내부 시간을 뺀 잔여는 파싱/JDBC/연결 등을 포함하며 순수 네트워크 시간이 아닙니다.
  정상응답의 내부시간이 없으면 예외응답 세부시간으로 명시하며 새 측정처럼 표시하지 않습니다.
- 인덱스: 실제 SRCH_ROW 대상의 PK/UNIQUE 제약, 인덱스 열순서·상태·가시성·통계시각,
  테이블 통계와 컬럼 타입. 인덱스 존재는 실제 사용 증명이 아닙니다.
  PARTITIONED=YES면 개별 인덱스 파티션 상태는 이번에 수집하지 않습니다.
- 계획: 최근24시간 같은 접속계정이 파싱했고 대상 테이블 또는 그 인덱스를 참조하는
  캐시 SELECT/INSERT 최대12개. SQL 본문/원문/조건 값은 출력하거나 저장하지 않습니다.
  GV$ 뷰의 instance ID도 함께 결속해 여러 Oracle 인스턴스의 child cursor를 섞지 않습니다.
  PK조건은 각 열명이 접근/필터 조건에 있는지0/1로만 표시하며 의미 검증을 대신하지 않습니다.
  캐시 후보는 이전 비교 실행에 정확히 귀속된 SQL_ID가 아닙니다. 같은 계정의 다른 작업일 수 있습니다.
- 실행 통계: 마지막 starts/실제 행수/버퍼조회/디스크읽기/연산시간/작업영역 TEMP.
  수집되지 않은 통계는NULL/미확인입니다. 적응형 계획의 starts=0 연산은 실제 실행 증거가 아닙니다.
  연산별 중첩시간·최대 TEMP를 더해서 전체 시간/동시최대치로 만들지 않습니다.
- TEMP: 현재 같은 접속계정의 TEMP 세그먼트 한 시점. LOB_DATA/SORT/HASH 등을 구분합니다.
  같은 계정을 공유하는 다른 작업이 포함될 수 있어 우리 작업의 사용량으로 확정하지 않습니다.
  블록 크기를 추정하지 않고 블록 수 그대로 표시합니다.
  끝난 비교의 TEMP 최대치를 사후 빈 조회로 복원할 수는 없습니다.
  실행계획의 TEMP_SPACE는 예상치, LAST_TEMPSEG_SIZE는 작업영역 마지막 관측치이며
  압축 복원의 임시LOB 사용량 전체를 대변하지 않습니다.

접근권한과 결과 상태
COLLECTED: 허용된 조회를 수집. SQL 최적화 완료/적재 완료/부하 적정 판정이 아닙니다.
PARTIAL: 캐시 없음, 권한/뷰/컬럼 미지원 또는 행수 상한 등 미확인이 있습니다.
ORA-00942/01031/00904는 해당 조회를 UNAVAILABLE로 남기고 독립 조회를 진행합니다.
기타 오류는 자동 재시도하지 않고 STOPPED로 끝납니다.
DB 정체성/대상 object ID/기존 코드·계약·state 결속이 다르면 수집을 중단합니다.
캐시는 시간이 지나면 사라질 수 있습니다. 빈 결과를 인덱스 없음/전체스캔 없음/TEMP0으로 해석하지 않습니다.

저장 위치와 전달할 결과
현재 노트북 작업 폴더 아래 gold-sql-check-reports/<시각-고유값>/에 새로 저장됩니다.
- SQL_CHECK.json: 최종 전체 결과. 이 파일을 우선 전달합니다.
- DBA_READONLY_CHECK.sql: 동일 DB/PDB에서 DBA가 실행할 SELECT 전용 조회문.
  GV$SQL_PLAN 등의 권한이 없어도 준비 결속이 성공했다면 생성됩니다.
- worker-result.json, worker.log: 부분 결과와 실행기 기록. 실패 시 함께 보존합니다.
원문 데이터·payload·SQL 본문·비밀키는 결과에 포함하지 않습니다.

동작 한도와 중단
애플리케이션 표 데이터 전체조회, INSERT/UPDATE/DELETE/COMMIT/DDL/통계수집/
EXPLAIN PLAN/실모델/원래 pending 재개는 실행하지 않습니다. Oracle SELECT만 실행합니다.
메타 조회도 자원을 쓰므로 SELECT 최대40회, 캐시 후보12개, 조회당45초/worker240초/부모280초입니다.
행 상한은 반환량 제한이며 서버 내부 스캔시간을 보장하지 않습니다.
준비 파일 검증·프로세스 정리 시간은 별도입니다. 부모 종료는 서버 SELECT 취소 확인이 아닙니다.
중단되면 원본 기록을 보존하고 자동 재실행하지 않습니다. 서버 조회가 남았는지는 DBA 확인 사항입니다.
job.lock을 다른 적재가 사용 중이거나 state가 이전 비교 이후 바뀌었으면 우회하지 않습니다.

결과 이후 판단
실제 큰 처리량/반복 접근이 보이는 조인·JSON 처리·복원 구간을 대상으로 수정합니다.
FULL SCAN/HASH JOIN이 있다는 이유만으로 무조건 인덱스를 강제하지 않습니다.
통계 미수집·인덱스 불가 상태가 보이더라도 이 코드가 DB를 자동 변경하지 않습니다.
현재 캐시로 부족하면 DBA가 승인된 다음 실제 작업의 SQL_ID와 동시 TEMP 사용을 관찰해야 합니다.
이번 검사 자체는 새 INSERT 시험을 시작하지 않습니다.
기존 WRITE_UNCONFIRMED, 영구 저장공간 부족, unit 미측정, 실제COMMIT/재개/전수검증은 별도입니다.

로컬 검증은 합성 Dataiku 응답·실제 첨부 부트스트랩·읽기전용 경계 검사입니다.
실제 Dataiku/Oracle 메타 조회 권한·실행계획·속도·TEMP 사용량은 현장 실행 전 미확인입니다.
