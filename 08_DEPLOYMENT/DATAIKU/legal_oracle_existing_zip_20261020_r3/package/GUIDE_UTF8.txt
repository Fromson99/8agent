LEGAL_ORACLE_EXISTING_ZIP_20261020_R3 — 개발계 보조 인덱스 생성 보류

사진의 CREATE TABLE ... QUERY_STATE 성공/Empty resultset은 인덱스 목록 조회가 아닙니다. 기존 오류는 검사기가 SIDDA에서 지정한 이름의 보조 인덱스 4개를 찾지 못했다는 뜻입니다. 테이블 데이터가 없다는 뜻은 아닙니다.

이미 R2 inspect → merge → restore를 마쳤고 QUERY_SCHEMA에서 멈춘 경우:
1. 기존 Dataiku Managed Folder(LEGAL_DATA_ZIP_IMPORT)에 LEGAL_ORACLE_EXISTING_ZIP_20261020_R3.zip만 추가 업로드합니다. 데이터 조각/원본 ZIP을 다시 올릴 필요 없습니다.
2. 같은 Python 노트북에서 Kernel → Restart로 커널을 재시작합니다. 기존 WORK_DIR와 복원 파일, R2 코드 및 로그는 보존합니다.
3. 별첨 DATAIKU_EXISTING_ZIP_IMPORT_RUN.txt 전체로 실행 셀을 교체합니다. 이 TXT는 Python 노트북용이며 SQL/b​​ash용이 아닙니다.
4. FOLDER_ID는 기존에 성공한 값, ORACLE_CONNECTION은 기존에 사용한 Dataiku Oracle 연결 이름을 넣습니다. 테이블 이름을 넣지 않습니다.
5. WORK_DIR는 기존 ./legal-existing-zip-r2-work를 유지합니다. 다른 노트북으로 옮겼다면 기존 폴더의 정확한 절대경로가 필요합니다.
6. ACTION="check", ALLOW_MISSING_LOOKUP_INDEXES=True로 실행합니다. READY_FOR_FULL_IMPORT와 deferred_indexes의 네 이름을 확인합니다. 이 단계는 Oracle 데이터 쓰기가 없습니다.
7. ACTION="publish"로 바꾸어 같은 셀을 다시 실행합니다. FULL_DATA_VERIFIED가 나오면 선택된 데이터 세대의 원문·자산·조회 데이터 전체 대조까지 완료입니다. READY나 파일 복원 완료만으로 적재 완료가 아닙니다.
8. 다시 전체 대조하려면 ACTION="status". 시간 한도로 중단되면 같은 설정/폴더에서 publish를 재실행합니다. 파일/상태/로그를 지워서 한도를 초기화하지 않습니다.

보류 가능한 인덱스: LEGAL_Q_ROW_LOOKUP, LEGAL_Q_ROW_OWNER, LEGAL_Q_ROW_TARGET, LEGAL_Q_ROW_DOCUMENT.
True는 이 네 보조 인덱스가 없을 때만 허용합니다. PK/외래키/JSON 제약/열 타입/기존 인덱스 정의/데이터 해시 검사는 유지됩니다. 라이브러리 기본값은 False입니다. 기존 인덱스가 잘못 정의된 경우는 거부합니다. 인덱스를 새로 만들거나 테이블을 지우지 않습니다.

원문·자산은 같은 버전·키·내용이면 기존 데이터를 재사용하고 누락 행을 보충합니다. 조회 행도 같은 릴리스/키에서 내용 대조합니다. 코드 지문이 바뀌므로 R2에서 다른 작업으로 이미 게시한 조회 릴리스와는 별도 조회 릴리스가 만들어질 수 있습니다. 모든 버전의 의미상 중복을 제거하는 기능은 아닙니다. 충돌은 덮어쓰지 않고 중단합니다.

보조 인덱스가 없으면 문서/용어 조건 조회가 느려질 수 있습니다. 데이터 적재를 진행하는 개발계 옵션이며 운영 조회 준비 완료를 뜻하지 않습니다. 운영 조회 전 기존 9테이블 DDL의 보조 인덱스 생성과 실제 조회 성능을 확인하세요. 생성 후 False로 check하면 엄격한 스키마 검사를 다시 수행합니다.

R3 코드는 같은 WORK_DIR/code-r3, 로그는 oracle-import-r3에 저장합니다. R2 oracle-import의 정확한 봉인 코드/대상/세대/쓰기 전 QUERY_SCHEMA 실패를 확인하고 최초 7일 기한과 스키마 SQL 호출 수를 이어받습니다. 이미 쓰기 단계가 진행된 R2 작업, 다른 대상/세대 또는 알 수 없는 코드이면 IMPORT_UPGRADE로 중단하며 자동으로 우회하지 않습니다. R2 기록은 수정하지 않습니다.

처음부터 시작하는 경우 inspect → merge → restore → check → publish 순서를 사용합니다. legacy_parts는 part000000... 및 PARTS/ORIGINAL.sha256용입니다. 현재 사용자는 restore를 마쳤으므로 check부터입니다. ZIP_TRANSFER_RUN.txt는 필요할 때 쓰는 운영계 49MB 분할/병합용이며 이번 복원 완료 경로에는 불필요합니다.

전체의 범위는 ZIP manifest에 명시된 선택 generation입니다. 제외 파일 수는 Oracle 중복 제거 수가 아닙니다. 오래된 ZIP의 최신성, 선택 밖 데이터의 필요성은 별도 확인 대상입니다. ACTIVE 전환, STATE 이력 이관, 서빙 배포는 수행하지 않습니다.

로컬 모의 SQL/실제 전달 TXT 검증과 현장 Dataiku JDBC/Oracle19 검증은 별도입니다. 현장 실행 완료나 성능을 미리 보장하지 않습니다.
