보조 조회 인덱스 4개 없이 개발계 데이터 이관을 진행하는 R3 수정본입니다. 기존 R2 실행 TXT 대신 이번 R3 전체 TXT를 사용하세요.

현재 사진은 QUERY_STATE 테이블 생성 성공 화면입니다. Empty resultset은 생성문이 조회 결과를 반환하지 않는다는 뜻이며 인덱스 부재 조회 결과는 아닙니다. 기존 QUERY_SCHEMA 오류는 검사기가 지정된 이름의 보조 인덱스 네 개를 찾지 못했기 때문입니다.

지금 할 일
1. 기존 Dataiku Managed Folder에 첨부 LEGAL_ORACLE_EXISTING_ZIP_20261020_R3.zip만 추가 업로드하세요. 이미 올린 데이터 조각과 복원본은 그대로 사용합니다.
2. 같은 Python 노트북에서 Kernel → Restart 후, 실행 셀 전체를 첨부 DATAIKU_EXISTING_ZIP_IMPORT_RUN.txt 내용으로 교체하세요.
3. FOLDER_ID와 ORACLE_CONNECTION은 기존에 성공한 값으로 넣으세요. Oracle 연결 이름이지 테이블 이름이 아닙니다. WORK_DIR는 기존 ./legal-existing-zip-r2-work를 그대로 유지합니다.
4. ACTION="check", ALLOW_MISSING_LOOKUP_INDEXES=True로 실행해 READY_FOR_FULL_IMPORT를 확인한 뒤 ACTION="publish"로 실행하세요. FULL_DATA_VERIFIED가 적재 및 전체 대조 완료 상태입니다. merge/restore를 다시 할 필요 없습니다.

True가 허용하는 것은 LEGAL_Q_ROW_LOOKUP / OWNER / TARGET / DOCUMENT 네 보조 인덱스의 누락뿐입니다. 기본키·외래키·JSON 제약·열 타입·데이터 해시·기존 행 내용 대조는 유지합니다. 테이블 삭제/재생성이나 기존 데이터 덮어쓰기는 하지 않습니다. 빠진 보조 인덱스는 deferred_indexes로 표시합니다.

원문·자산은 같은 버전·키·내용이면 재사용하고 누락분을 보충합니다. 조회도 같은 릴리스/키의 내용을 대조합니다. 이번 검증 코드 지문 변경으로 이전에 다른 작업에서 게시한 조회 릴리스와는 별도 릴리스가 생성될 수 있으며, 모든 버전의 의미상 중복을 지우는 작업은 아닙니다.

R3는 code-r3 및 oracle-import-r3를 사용합니다. 정확한 R2의 쓰기 전 QUERY_SCHEMA 실패에 한해 원래 7일 기한과 스키마 SQL 호출 수를 이어받고 원본 실패 기록을 보존합니다. 이미 R2 적재 단계가 진행됐거나 다른 세대/대상이면 자동 우회하지 않고 중단합니다.

로컬 검사 69개가 통과했습니다. 실제 전달 TXT의 R2 실패 → R3 check → publish, 기존 복원 파일 유지, 누락 인덱스 허용, 제약/해시 오류 차단, 중복·재개·전체 대조를 검증했습니다. 최초 구현 검사에서 발견한 옵션 적용 위치 오류를 수정했고 실패 기록도 보존했습니다. 최종 ZIP의 실행 파일은 검사한 소스와 일치합니다. 현장 Dataiku JDBC/Oracle19 실행 및 대용량 성능은 아직 미확인입니다.

보조 인덱스가 없으면 문서·용어 조건 조회가 느려질 수 있습니다. 개발계 적재 옵션이며 운영 조회 준비 완료를 뜻하지 않습니다. 운영 조회 전 인덱스 생성과 실제 조회 성능을 확인하세요. 나중에 인덱스 생성 후 False로 check하면 엄격한 검사를 다시 수행합니다.

데이터 범위는 ZIP에서 선택된 generation 전체입니다. 선택 밖 제외 파일 수는 중복 제거 수가 아닙니다. ACTIVE 전환·STATE 이력 이관·서빙 배포는 별도입니다.

첨부 TXT는 Python 노트북용입니다. SQL 창이나 bash에서 실행하지 마세요.
