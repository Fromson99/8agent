운영계 Dataiku Gold 적재 · R3에서 R4로 교체
2026-11-05

대상
사진에서 R3가 RGSN_ASTM 사전 검사 중 멈췄던 기존 운영계 Dataiku 프로젝트와 Python 노트북을 사용합니다. R4는 원문·검색·게시·벡터 적재와 결과 확인을 같은 셀에서 순서대로 실행합니다.

실행 순서
1. 기존 운영 R3 노트북에서 실제로 사용한 PARAMS = { ... } 블록을 복사해 둡니다. 기존 R3 셀과 로그를 보존합니다.
2. 그 블록의 CODE_FOLDER_ID에 해당하는 기존 운영 Managed Folder에 DATAIKU_GOLD_ONECLICK_PROD_20261105_R4.zip을 압축된 채로 한 번 올립니다. 운영 입력 폴더에 이미 있는 34조각과 PARTS.sha256, ORIGINAL.sha256은 그대로 재사용합니다. 같은 폴더에 이 이름의 R4 ZIP이 이미 한 개 있으면 그대로 사용합니다.
3. 기존 적재가 종료된 상태에서 운영 노트북 커널을 재시작합니다. 새 셀에 DATAIKU_GOLD_PROD_RUN_R4.txt 전체를 붙인 후 맨 위 PARAMS 블록만 1번에서 복사한 실제 운영 R3 값으로 교체합니다. R4 TXT의 import hashlib부터 마지막 RESULT = run(PARAMS)까지 그대로 둡니다.
4. 그 셀을 한 번 실행합니다. 입력·스키마 검사 → ZIP 복원 → 자료 준비 → 원문 적재 → 검색 적재 → 게시 기록 → 임베딩·벡터 적재 → 결과 확인 순서로 진행합니다.
5. 마지막 출력의 PRODUCTION_GOLD_LOADED와 그 아래 표시되는 report.json 경로를 확인합니다. 보고서에서 최종 건수를 확인할 수 있습니다.

어떤 설정을 쓸지
코드·입력 폴더 ID, Oracle 연결명과 접속 계정, GOLD_OWNER, TABLE_PREFIX/TABLE_NAMES, 임베딩 모델·차원, WORK_DIR까지 운영 R3에 입력했던 값을 그대로 복사합니다. 개발 시험이 성공한 SIDDA.TST_B003_LGL_SRC_POST_R4는 개발용 테이블입니다. 운영 대상은 운영 R3의 GOLD_OWNER와 테이블 매핑으로 결정합니다. 별도 셸 명령이나 작업 디렉터리 이동은 필요 없습니다.

재실행
R4는 기존 입력 34조각을 읽고 R4 전용 작업 기록을 만듭니다. R3가 사진처럼 스키마 검사에서 멈춘 실행은 데이터 적재 전이었습니다. 다른 실행이 이미 같은 판본을 일부 적재했다면 R4가 기존 판본과 원래 체크포인트를 확인하도록 중단할 수 있습니다. 이때 기존 행과 체크포인트를 보존하세요.
R4 실행 중 중단되면 같은 PARAMS와 원래 WORK_DIR에서 같은 R4 셀을 사용합니다. 원래 작업 기록·임베딩 캐시·pending이 재개에 필요합니다. 임베딩 결과 UNKNOWN 또는 원래 체크포인트 필요 메시지가 나오면 작업 폴더와 로그를 보존하세요.

검증 범위
사내 개발계 사진에서 기본값 없는 TIMESTAMP(6) NOT NULL에 등록일시가 저장됐고 같은 키로 1행이 조회됐습니다. 로컬 실제 Oracle에서는 합성 34조각으로 R4 운영 실행기의 8단계와 재개를 확인했습니다. 운영 실데이터 전량 결과는 이번 실행의 최종 출력으로 확인합니다.
