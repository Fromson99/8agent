기존 NFS → Oracle 적재 R11: 일괄 INSERT + 기존 작업 재개

사진의 결과
전체 검색행 60,971,724행, 최근 16.7행/초, 500행 요청 약30초입니다.
현재 속도가 유지되면 남은 검색행 적재만 약41~42일이며, 전수검증 시간은 별도입니다.
FTS_POSTINGS_SORT라는 표시는 행 생성 단계의 표시이기도 합니다.
이 이름만으로 정렬이 병목이라고 단정할 수 없습니다.
요청 시간에는 Dataiku 전송/대기가 포함되므로 Oracle CPU 시간과 다릅니다.

파일 3개
1) DATAIKU_EXISTING_NFS_CLIENT_20261031_R11.zip : 관리 폴더에 올릴 실행 코드
2) DATAIKU_EXISTING_NFS_LOAD_ONLY_R11.txt : 노트북에 붙일 전체 실행 코드
3) GUIDE.txt : 이 안내문
ZIP은 압축 그대로 기존 LEGAL_RAG 관리 폴더 ehA8dpVm에 업로드합니다.
원문 데이터나 NFS 자료를 다시 업로드할 필요는 없습니다.

전환 순서
1. 먼저 위 R11 ZIP을 ehA8dpVm에 업로드합니다.
2. 현재 적재 셀에서 Interrupt를 한 번 누르고 셀이 종료될 때까지 기다립니다.
   중단 기록(NFS_STOPPED 또는 종료 예외)과 커널 Idle을 확인합니다.
   아직 실행 중이거나 JDBC 요청 결과가 불명확하면 즉시 Kernel Restart/강제종료하지 마세요.
   기존 마지막 출력만 캡처합니다. 이전 writer와 새 writer를 동시에 실행하면 안 됩니다.
3. 기존 적재가 종료된 같은 노트북에서 Kernel > Restart 합니다.
4. R11 TXT 전체를 새 셀에 붙여 실행합니다.
   ACTION='load_only', RESUME_ONLY=True, QUERY_WRITE_ROWS=5000 기본값을 유지합니다.
   같은 Dataiku 실행 환경/LEGAL_PIPELINE_SCRATCH/기존 작업 폴더를 사용합니다.
   재개 기록·로컬 수신 파일을 삭제하거나 새 작업을 만들지 않습니다.

재개 방식
저장된 기존 커서와 release/행 ID를 그대로 사용합니다.
응답 확인된 검색행 묶음은 건너뜁니다. 마지막 SQL이 커밋됐지만 응답을 잃은 경우
같은 행을 재확인하며, 값이 같으면 중복 삽입하지 않고 값이 다르면 실패합니다.
로컬 원본을 읽고 정렬하며 커서 앞부분을 다시 생성해 건너뛰는 준비 시간은 남습니다.
이것은 이미 적재한 모든 행을 다시 INSERT하거나 NFS를 다시 다운로드하는 과정이 아닙니다.
로컬 재개 기록과 관리 폴더 백업의 갱신 시점은 다릅니다. 같은 로컬 작업 폴더를 유지하세요.
기존 원문3종의20행 쓰기는 유지하며, 검색행만 최대5000행으로 묶습니다.
4MiB 묶음 목표와 파일 경계에 따라 실제 요청은5000행보다 작을 수 있습니다.

변경 내용
기존500행 요청은 행마다 조회·INSERT·CLOB 생성을 반복했습니다.
R11은 묶음당 payload CLOB 하나와 INSERT SELECT를 사용하고,
본문 전체·해시·메타데이터 일치를 묶음 단위로 확인합니다.
검사를 없애지 않았습니다. 불일치하면 요청 전체가 롤백됩니다.
원래 기한(7일)과 누적 SQL 예산은 유지하며, 기한/예산이 끝나면 자동 연장하지 않습니다.

짧게 확인할 출력
새로운 QUERY_LOADED 또는 진행 줄 2~3개만 캡처하면 됩니다.
확인할 값: 이번적재 행수/요청수, 최근요청 행수, 최근요청 시간, SQL생성, JDBC왕복.
JDBC왕복에는 전송·Dataiku·DB가 포함되므로 DB CPU만의 시간은 아닙니다.
로그를 추가로 대량 출력하거나 상세 SQL을 출력할 필요가 없습니다.
기존 빠른 진단 R1도 사용할 수 있지만, 아직 준비/정렬 중이면 속도 예상은 보류합니다.
새 적재가 충분히 진행된 뒤 같은 실행의 최근 속도로 남은 시간을 다시 계산합니다.

완료/실패
LOADED_UNVERIFIED는 적재만 완료한 상태입니다. 전수검증 완료와 다릅니다.
전수검증은 적재 완료 뒤 별도 계획으로 실행합니다.
재개 명세 누락/변경, 기한/예산 종료, Oracle 오류가 나면 마지막 몇 줄을 캡처합니다.
RESUME_ONLY=False 전환이나 재개 파일 삭제로 우회하지 않습니다.

검증 범위
로컬 Oracle23.26.3에서 실제 Dataiku용으로 렌더링한 SQL을 실행했습니다.
동일500행 ABBA 비교: 기존2.903/2.708초, R11 0.211/0.168초.
별도5000행 요청은5.980초, 전체 원문 바이트와 메타데이터 재조회 일치입니다.
중복/충돌 롤백/커밋후 응답유실/긴 한글·이모지/기존 재개 번호를 확인했습니다.
전달ZIP과 전체TXT를 실행한 모의 Dataiku 재개 시험도 통과했습니다.
현장 Dataiku/Oracle19에서의 실행·속도·전체 완료는 아직 확인되지 않았습니다.
위 로컬 비율을 현장30초에 곱해 완료 시간을 보장할 수 없습니다.
MAIN/GENOS/현장 DB는 변경하지 않았습니다.
