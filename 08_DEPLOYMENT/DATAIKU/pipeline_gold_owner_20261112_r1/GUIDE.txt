1. 플로우가 이렇게 되어 있나 — "S3 → GENOS 구조화·색인 → Oracle Agent → Gold 승격"
========================================================================
대체로 그렇다. 코드로 확인한 실제 순서:

  [Dataiku 01_SUBMIT]  S3(관리 폴더)의 원문 ZIP을 바이트 그대로 GENOS로 조각 전송, 비동기 작업 시작
  [GENOS]              구조화(build-data-stages structure) → 용어집 연결(document-release prepare)
                       → 본문 검색 색인(reindex, fulltext) → 결과 세대를 result.zip으로 묶음
                       → ORDS로 SIDDA.LGL_PIPE_RESULT_A 에 72KB 조각으로 INSERT, 마지막에 0번 '완료' 행
  [Dataiku 02_WAIT]    SIDDA 완료 행 확인 (GENOS가 꺼져 있어도 됨)
  [Dataiku 03_LOAD]    SIDDA 조각을 이어 붙여 해시 확인 → Gold 행으로 변환 → 원문·검색 적재 → 게시
                       → 벡터 임베딩(Dataiku 모델 연결 openai:genos-embedding:embedding-kure-v1) → 벡터 적재 → 건수 재조회

다른 점 두 가지 (말씀하신 그림과 차이):
  a. 벡터 임베딩은 GENOS가 아니라 Dataiku 03_LOAD에서 한다(같은 GENOS 임베딩 모델을 Dataiku 연결로 부름).
     → 2026-11-12 사용자 결정: 임베딩은 Dataiku 그대로.
  b. Agent 층에는 '행'이 아니라 처리 결과 묶음(ZIP 조각)이 들어간다. Gold 행으로 펼치는 것은 03_LOAD.
     (검색 행이 전체 기준 약 6,097만 행이라 GENOS→ORDS로 행을 하나씩 넣으면 매우 느림. 묶음 전달이 맞다고 본다.)
  c. 03_LOAD는 새 세대를 Gold에 넣고 자기 채널(g19_…)만 만든다. 서빙 채널(main) 교체·벡터 머리 연결은
     증분 activate(또는 수동 SQL)가 한다 — 적재만으로 서빙이 바뀌지 않는다.

현장 진행 기록: 11-06 GENOS 계정 권한 오류(ORA-00942) → 11-09 개발계 TEST_LEAGAL에서 02까지 통과(증분 안내 기록).

3. 증분 처리 — 어떻게 도나, 실험은 어떻게
========================================================================
도는 방식 (새 표 없음, 사람 승인 없음):
  decide    떨어진 파일 → 바뀐 파일만 작은 파이프라인 실행으로 구조화 → 지금 서빙 세대(main 채널이 가리키는 Gold)와
            조문 단위 비교 → 반영 / 보류(조문 급감·대량 삭제·변경률 50% 초과·별표 소실·시행일 문제) / 시행일 대기
  publish   지난 원문 ZIP에서 반영 문서만 바꾼 전체 원문 ZIP → 파이프라인 전체(GENOS→Agent→Gold) → 새 세대
            (서빙은 아직 그대로)
  activate  벡터 머리 연결 + main 채널을 새 세대로 (한 번에) → 업데이트 기록(최근 3개) → 옛 세대 정리(지금+이전 2개만)
            → 적재 끝난 Agent 조각 삭제
  rollback  최근 업데이트를 되돌림 (이전 세대가 남아 있으면 채널만, 지워졌으면 옛 원문으로 다시 게시)

실험은 표를 복사해서 — 맞다. 다만 데이터까지 복사할 필요는 없다:
  - 구조만 같은 빈 시험 복사본 13표(TST_B003_LGL_*)를 만들고, 작은 기준 세대(문서 몇 개)를 파이프라인으로 넣는다.
  - 6,097만 행을 복사하면 공간·시간만 들고, 증분이 비교하는 대상은 '시험 복사본의 main 채널이 가리키는 세대'라
    작은 세대로 충분하다. 원래 Gold(IDD_B003)와 서빙은 실험 내내 그대로다.
  - 시험 복사본은 같은 SIDDS에 이름만 다르게 둔다(사용자: SIDDS에 만들 수 있음, 권한 신청).
    만들 표·필요한 권한·SQL은 증분실험_표_권한신청_R1.txt. Agent 표는 새로 만들지 않고 기존 SIDDA.LGL_PIPE_RESULT_A를 쓴다.

개발계 실험 순서 (TEST_LEAGAL 프로젝트)
  1. 프로젝트 변수: LGL_GOLD_OWNER = SIDDS
  2. SQL 노트북: CHECK_TABLES_SIDDS_R1.txt Q01~Q07 → Q02 18행, Q03~Q05 0행 확인

     (CODE_FOLDER_ID, 원문 ZIP 이름·해시, 실제 지원 ZIP 이름) → FLOW_INSTALLED LGL_AGENT_R7_PROD_RUN_ALL
     프로젝트 변수 AGENT_PIPELINE_URL / AGENT_PIPELINE_TOKEN 은 지금 R6 GENOS 리비전 값 그대로.
