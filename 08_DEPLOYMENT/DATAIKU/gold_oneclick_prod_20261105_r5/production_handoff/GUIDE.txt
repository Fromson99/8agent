운영계 Dataiku Gold R5 · 기존 분할 ZIP 34조각 전체 이관

사용할 곳
기존 운영 R4가 실행됐던 Dataiku 프로젝트의 Python 노트북에서 실행합니다. 운영 R4의 PARAMS와 기존 코드·데이터 Managed Folder, WORK_DIR를 사용합니다. 개발계에서 검증한 R5와 동일한 코드 ZIP이며, 이번 실행 TXT는 전체 적재에 진입합니다.

1. 기존 운영 입력과 설정
운영 R4 셀의 PARAMS = { ... } 블록 전체를 복사해 둡니다. 실제 운영 CODE_FOLDER_ID, INPUT_FOLDER_ID, ORACLE_CONNECTION, EXPECTED_DB_USER, GOLD_OWNER, TABLE_PREFIX, TABLE_NAMES, 임베딩 모델·차원, WORK_DIR가 들어 있습니다.
코드 폴더(CODE_FOLDER_ID)에 DATAIKU_GOLD_ONECLICK_PROD_20261105_R5.zip을 압축 상태로 올립니다. 이미 동일한 R5 ZIP이 한 개 있으면 재사용합니다.
운영 데이터 폴더에는 기존 genos-rag-data-20261007T002029Z-7c0b050f.zip의 분할 34조각과 PARTS.sha256, ORIGINAL.sha256을 그대로 둡니다. 코드 폴더와 입력 폴더가 분리돼 있으면 운영 R4의 INPUT_FOLDER_ID를 유지합니다. R5가 조각을 확인하고 병합·복원합니다.

2. 운영 벡터 선언 확인
보내주신 사진에서 확인된 사내 개발계 SIDDA 시험 표는 VECTOR(*,*,DENSE)였고 1024개 좌표가 FLOAT32 그대로 저장됐습니다. 운영 표의 정의는 운영 연결에서 확인합니다. 이미 운영 정의를 확인했다면 3번으로 이동합니다. 아직 확인 전이면 기존 운영 R4의 PARAMS가 있는 커널에서 아래 읽기 전용 셀을 한 번 실행하세요.

import re
import dataiku
owner = PARAMS['GOLD_OWNER']
table = (PARAMS.get('TABLE_NAMES') or {}).get('VCTR_ITEM') or PARAMS.get('TABLE_PREFIX','IDD_B003_LGL_') + 'VCTR_ITEM'
if not all(re.fullmatch('[A-Z][A-Z0-9_]{0,29}', v) for v in (owner, table)):
    raise ValueError('운영 R4의 소유자와 테이블 이름을 확인하세요.')
sql = f"""SELECT COLUMN_NAME, DATA_TYPE, DATA_LENGTH, CHAR_USED, VECTOR_INFO
          FROM ALL_TAB_COLUMNS
          WHERE OWNER='{owner}' AND TABLE_NAME='{table}'
            AND COLUMN_NAME IN ('BODY_UNIT_ID','EMBD_VCTR')"""
print(dataiku.SQLExecutor2(connection=PARAMS['ORACLE_CONNECTION']).query_to_df(sql).to_string(index=False))

기본 1024차원 설정에서 시험한 EMBD_VCTR 선언은 VECTOR(*,*,DENSE), VECTOR(*,FLOAT32,DENSE), VECTOR(1024,FLOAT32,DENSE)입니다. BODY_UNIT_ID의 기준은 VARCHAR2, DATA_LENGTH=100, CHAR_USED=B입니다. 조회 결과가 다르면 전체 실행 전에 실제 정의를 확인하세요. 운영 R5의 자체 첫 검사는 VECTOR 타입명까지 비교하므로 768차원 고정이나 INT8 고정을 이 단계에서 구별해야 합니다.

3. 실행과 완료
기존 작업이 종료된 후 운영 노트북 커널을 재시작합니다. 새 셀에 DATAIKU_GOLD_PROD_RUN_R5.txt 전체를 붙이고 맨 위 PARAMS만 1번에서 복사한 운영 R4 블록으로 교체합니다. 새 셀을 한 번 실행하세요. 별도 셸 명령이나 작업 경로 이동은 필요 없습니다.
입력·스키마 확인 → 34조각 병합·복원 → 자료 준비 → 원문 → 검색 자료 → 게시 기록 → 임베딩·벡터 → 결과 확인 순서입니다. 마지막 출력 PRODUCTION_GOLD_LOADED와 그 아래 report.json 경로에서 적재 결과와 건수를 확인합니다.

4. 재개
R5는 전용 작업 기록을 사용합니다. 도중에 중단된 R5를 재개할 때는 같은 운영 설정과 원래 WORK_DIR를 사용합니다. 기존 판본이나 원래 체크포인트가 필요하다는 메시지 또는 임베딩 결과 UNKNOWN이 나오면 기존 기록과 로그를 보존해 확인하세요.
