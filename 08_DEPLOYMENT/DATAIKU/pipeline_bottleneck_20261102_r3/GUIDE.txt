Dataiku에서 원본 표본 실제 INSERT 계측 R3 / 2026-11-02

이번에 할 일
Dataiku의 원본 SQLite에서 서로 다른 행을 읽어 기존 적재 코드의 컬럼 매핑으로 변환한다.
100 → 500 → 2,000행씩 실제 Oracle INSERT, 전체 값/LOB 검증, ROLLBACK을 실행한다.
시험용 별도 release/키를 쓰며 마지막에 해당 시험 키가 0행인지 확인한다.
원본 본문을 32행씩 반복 복제하던 R2 방식은 쓰지 않는다.
원래 중단된 적재의 state/pending, 기존 저장 행, 서비스 선택은 바꾸지 않는다.
전체 적재 재개·전체 검증·임베딩 생성·DDL·COMMIT 시험은 하지 않는다.

GUIDE.txt
이번 직접 INSERT 계측에는 R2 대신 위 R3 ZIP/TXT를 함께 사용한다.
기존 적재 ZIP이나 현장 서비스 코드를 교체하는 파일이 아니다.

실행 환경과 순서
1. Dataiku LEGAL_RAG 프로젝트, 오류가 났던 기존 _1 적재 Python 노트북을 그대로 사용한다.
   기존 적재 셀은 다시 실행하지 않는다. 노트북 커널을 초기화하거나 상태 폴더를 지우지 않는다.
2. Managed Folder ehA8dpVm에 R3 ZIP을 압축 해제하지 않고 업로드한다.
3. 기존 노트북의 새 셀에 01_DIAG_AND_ROLLBACK_INSERT_RUN_R3.txt 전체를 붙여넣고 실행한다.
   OLD_JOB_DIR / STATE_DIR / PACKAGE_DIR 기본 빈 값은 자동 탐색이다.
   이전에 직접 지정한 경로가 있다면 동일한 실제 경로를 사용한다. 새 경로를 추측하지 않는다.
   RUN_INSERT_PROBES=True가 기본이므로 실제 작은 INSERT 시험을 실행한다.
4. 완료 후 새 셀에 아래 한 줄씩 실행해서 각 화면을 캡처한다.

SHOW_DIAG_PAGE("배치")

100·500·2,000행마다 실제 행 수 / 요청 시간을 한 화면에 비교한다.
2MiB 크기 제한 또는 원본 표본 부족으로 실제 행 수가 목표보다 적을 수 있다.
잔여 0행까지 확인한 성공 시험만 시간을 표시한다. 나머지는 사유가 표시된다.

SHOW_DIAG_PAGE("삽입")

각 종류 마지막 시험의 DB 복원 / INSERT / 검증 / 기타 요청 / 전체 요청 초를 본다.
DB 복원: 기존 JDBC 코드의 임시 LOB 생성·압축 해제·UTF-8 복원 구간.
기타 요청: 왕복·SQL 파싱·정리·진단용 예외 응답 등을 포함한 아직 분리되지 않은 시간.
기타 요청을 순수 네트워크 시간이라고 해석하지 않는다.
롤백 시간은 REPORT.json에 별도 보존되며 기타 요청을 계산할 때도 뺀다.

SHOW_DIAG_PAGE("준비")

원본 읽기·매핑 / 배치 JSON 준비 / 압축·SQL 생성 / 전송 크기를 본다.
원본 읽기는 종류별 한 번 최대 2,000행을 준비한 시간이다. 세 배치에 중복 합산하지 않는다.
SHOW_DIAG_PAGE는 저장된 숫자만 표시하며 SQLite 조회나 INSERT 시험을 다시 실행하지 않는다.

대상과 제한
- DOC_VER / DOC_UNIT / DOC_BLK를 원본 store.sqlite에서 읽는다.
- 계획 행 수 상위 5개 SRCH_ROW 종류와 이미 적재된 종류 1개(중복이면 제외)를 읽는다.
- 일반 테이블·VIEW: 최대 2,000개 원본 행. 기존 record/lookup/query_row 변환 함수를 재사용한다.
- FTS posting: 기존 SQLite 토큰·위치 값의 완결된 term/doc/col 그룹을 사용한다.
  최대 64개 term 조회, term당 위치 4,096개를 넘으면 그 term은 건너뛴다.
  전체 posting 정렬·COUNT·길이 집계를 실행하지 않는다. 잘린 위치 목록을 저장하지 않는다.
  따라서 FTS 표본은 드문 term에 치우칠 수 있고 전체 색인 구축 속도를 대표하지 않는다.
- 표본은 종류별 최대 8MiB·5초, INSERT payload는 최대 2MiB.
- 원본 파일의 준비계획 경로와 읽기 전후 파일 속성·SQLite header/data_version을 확인한다.
  WAL/journal이 있거나 읽는 도중 원본이 바뀌면 표본을 폐기한다.
  대형 원본 전체 파일 SHA를 이번 작은 시험에서 다시 읽지는 않는다.
- 별도 종류의 매핑/파일/시간 문제가 나면 해당 종류를 미측정으로 남긴다.
  Oracle INSERT 실패·결과 불명·롤백 잔여 행이면 후속 INSERT를 중단하며 자동 DELETE/재시도하지 않는다.

시간과 완료 확인
정상 연결이면 수분 단위 시험을 목표로 한다. 현장 소요시간을 보장하는 값은 아니다.
기존 SQLite 표본 진단 예산 90초 + Oracle 자식 전체 제한 210초가 설정돼 있다.
직접 표본/INSERT 묶음 내부 예산은 150초이며, 개별 활동이 30초를 넘으면 클라이언트 자식을 종료한다.
초기 ZIP 다운로드·경로/코드 검사·파일 I/O 시간은 위 두 예산 밖에 있다.
COMPLETE는 모든 시도 성공, PARTIAL은 일부 미측정, STOPPED는 오류 중단이다.
ROLLED_BACK_VERIFIED는 실제 INSERT/내용검증/롤백 뒤 시험 release 0행을 확인했다는 뜻이다.
CLIENT_TIMEOUT_DB_OUTCOME_UNCONFIRMED는 원격 SQL 취소/완료가 확인되지 않았다는 뜻이다.
이 경우 셀을 반복 실행하지 말고 요약과 REPORT.json을 확인한다.

결과 보관
현재 노트북 작업 디렉터리의 gold-bottleneck-reports/<시각-고유값>/REPORT.json.
실제 사용 코드·원본·검색 판본 결속과 모든 시험 크기·시간·중단 사유를 보관한다.
원문 값·전체 SQL·인증 정보는 보고서에 저장하지 않는다.

해석 범위
순서는 100→500→2000, 크기당 1회로 캐시와 순서 영향이 있다. p95나 일반 성능 인증이 아니다.
원래 데이터 본문은 유지하지만 시험 release와 PK는 충돌 방지를 위해 바꾼다.
실제 INSERT를 실행하지만 COMMIT 없이 롤백한다. COMMIT 포함 전체 적재 시간으로 외삽하지 않는다.
후속 전체 verify_publish / vector의 실제 계측은 별도 실행이다. 이번 시험 완료가 전체 적재 완료는 아니다.
R2의 원래 15회 성공과 이번 R3의 원본 표본 시험은 조건이 달라 개선율로 직접 합산하지 않는다.
