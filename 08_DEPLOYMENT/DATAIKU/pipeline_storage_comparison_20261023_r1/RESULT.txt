승호님 Dataiku 코드 대조와 현장 SFTP 저장 실패 판독 — 2026-10-23

결론
예전에는 됐다는 설명과 현재 결과는 모순되지 않는다. 이번 사진에는 이전 복구 기록이
phase=CREATED, api_calls=3으로 남아 있다. 우리 복구 R1은 API 호출 전에 같은
folder.upload_stream으로 기록을 쓰고 다시 읽어 확인한다. 이 기록은 복구 초반의 쓰기·읽기
성공을 뒷받침한다. 이후 옛 SUPPORT 2,267,000,459 bytes의 추가 보관이 실패했고,
15:55:42~44 KST의 2KiB 검사 네 건은 기존 부모와 루트까지 모두 UPLOAD에서 실패했다.
처음부터 쓰기 권한이 없었다거나 특정 하위 폴더만 문제라는 설명으로 확정할 수 없다.

승호님 최신 코드 확인
외부 Git integration을 fetch했고 c507cd450d90671858603e97f8849c8df3a7bc8d를 읽었다.
별도 dataiku 브랜치는 현재 원격 ref가 없어서 기존 보관 fa5328fc와 구분했다.
실제 GENOS/Dataiku 배포 코드를 조회한 것은 아니다. 파일별 SHA와 줄은 COMPARISON.json에 있다.

승호님 경로
- compute_ELS_QA_PREPROCESS.py: ElsQaSrc(ELS_QA_SOURCE)에서 get_download_stream으로 원문을 읽는다.
- 문서별 코드서빙 전처리 결과는 ELS_QA_LOAD_BUNDLE, ELS_QA_VDB_INPUT,
  ELS_QA_PREPROCESS_LOG 데이터셋에 write_with_schema로 저장한다.
- build_project.py의 upload_data('.keep', b'')는 최초 저장 폴더 준비용 0바이트 파일이다.
  전처리 결과나 2.27GB 보관 파일을 이 API로 올리는 코드가 아니다.
- dsskit.py의 기본 관리 폴더/파일 데이터셋 정의는 Filesystem과 filesystem_managed다.
  다만 설치 셀의 FS_CONNECTION으로 이름을 치환할 수 있으므로 현장도 로컬 Filesystem이라고
  단정할 수 없다. 승호님 현장의 실제 연결 설정은 미확보다.

우리 경로와 차이
- 새 배치가 BUSY로 막혀, 이전 FAILED / STRUCTURE의 입력·공개 로그를 보존한 뒤 ACK하도록 했다.
- 이전 SUPPORT와 현재 업로드가 다르면 옛 로컬 SUPPORT ZIP을 관리 폴더의
  _pipeline/recovery/<old job ID>/files/<old support sha256>.bin에 추가 보관한다.
- 이 추가 보관은 승호님 전처리의 원문 읽기/결과 데이터셋 저장과 다른 동작이다.
  여유 공간 확인 없이 추가 2.27GB 보관을 시도한 점은 우리 복구 코드의 한계다.
- 코드 기준 원문/상태 보존 목적이지만, 이 보관 시도 중 원격 용량·계정 쿼터가 찼는지부터
  확인해야 한다. 현재 증거로 우리가 공간을 채웠다고 확정할 수는 없다.
- upload_stream은 공식적으로 파일 스트림을 관리 폴더에 쓰는 API다. upload_data로 이름만
  바꾸면 해결된다는 근거는 없다. 승호님도 결과·로그는 별도 데이터셋에 쓴다.
  공식 API: https://developer.dataiku.com/latest/api-reference/python/managed-folders.html

현재 확인한 것과 미확인
확인: 기존 체크포인트 조회, 로컬 옛 SUPPORT 존재/크기 일치, 원격 .bin 경로 목록 포함,
네 작은 파일 UPLOAD 실패, ACK 의도 false, 이번 진단의 GENOS API0.
미확인: .bin 실제 저장 크기/완전성, 원격 여유 공간·쿼터, 실제 연결 계정과 변경 이력,
SFTP 서버의 구체 실패 사유. 목록에 있다는 것만으로 2.27GB 저장 완료가 아니다.
사진 시점에는 기존 복구 기한과 새 배치 기한 모두 미만료였다. 현재 시점에도 유효하다고
간주하지 않으며 재개 시 최초 기한/API·SQL 예산을 다시 확인해야 한다.

   이전 원본과 실패 이력은 임의로 삭제하지 않는다.
4. 쓰기가 회복된 후에 기존 복구 기한·예산, 보관본 해시·실제 서버 상태를 확인하고 재개한다.
   지금 RELEASE_FAILED R1/run 반복이나 무조건 ACK는 다음 조치가 아니다.
