5. Dataiku에 업로드

Dataiku 프로젝트 Flow에서 New dataset → Folder로 Managed Folder를 만들거나 사용 가능한 폴더를 선택합니다.
그 폴더의 최상위에 다음을 각각 업로드합니다:

- parts-manifest.json
- query-data.zip.part000001부터 마지막 조각까지 전부

추가 테이블 4개와 조회 인덱스가 만들어져 있고, 사용하려는 Oracle 연결에
기존 LEGAL_RAG_RELEASE_A 및 조회 4테이블 SELECT, QUERY_ROW/QUERY_RELEASE INSERT 권한이 필요합니다.
SQL 노트북에서 9개 CREATE문을 다시 실행하지 않습니다.

Dataiku Code → Notebooks → Python의 새 노트북/새 커널을 엽니다.
첨부 DATAIKU_QUERY_IMPORT_RUN.txt 전체를 한 Python 코드 셀에 붙입니다.
또는 코드 ZIP 안의 DATAIKU_QUERY_IMPORT.ipynb를 가져옵니다.
SQL 노트북과 bash 터미널에 붙이는 코드가 아닙니다.

셀 맨 위에서 설정할 값:
FOLDER_ID = Managed Folder의 실제 ID
ORACLE_CONNECTION = 사진의 AIDP(Oracle) 연결에 대응하는 정확한 Dataiku 연결 이름
WORK_DIR = 재시작 뒤에도 남는 쓰기 가능한 기록/복원 폴더

비밀번호를 코드에 적지 않습니다. Dataiku에 저장된 Oracle 연결을 사용합니다.
Managed Folder가 S3 등 원격이거나 컨테이너에서 실행되어도 다운로드 스트림을 사용합니다.
SQLite 복원 파일은 Dataiku 실행 환경의 파일 경로에 필요하므로 WORK_DIR 공간을 확보합니다.
WORK_DIR 기본값 ./legal-query-transfer-work의 실제 위치는 노트북 실행 폴더 기준입니다.
재시도할 때 WORK_DIR/연결명/폴더를 바꾸어 이전 기한과 기록을 우회하지 않습니다.

6. Dataiku 실행 순서

같은 셀의 ACTION 값을 바꾸어 한 번씩 실행합니다. 동시에 두 셀/두 커널로 적재하지 않습니다.

a. ACTION = "restore"
   코드/조각 다운로드 → 각 조각 크기·SHA → 전체 ZIP SHA → DB SHA → DB 내부 행/버전 검증.
   RESTORED_AND_VERIFIED가 나오면 다음 단계입니다. Oracle 쓰기는 없습니다.

b. ACTION = "check"
   실제 연결 사용자·DB·서비스 이름 출력, 기존 Oracle 원문 완료 릴리스와 패키지 버전 대조,
   추가 4테이블의 열/PK/FK/JSON검사/4인덱스 확인.
   READY_TO_IMPORT가 나오면 다음 단계입니다. INSERT 권한의 실제 성공은 publish에서 확인합니다.
   RELEASE_MISSING이면 기존에 올린 원문과 이번 generation/검색 선택표가 다른지 확인합니다.
   기존 5테이블을 다시 이관하거나 완료행을 임의 생성해 통과시키지 않습니다.

c. ACTION = "publish"
   20행/약4MiB 단위로 QUERY_ROW 삽입 또는 동일 행 재사용 → 전체 열/JSON 읽기 대조.
   모든 종류의 행 수와 전체 건수가 맞으면 QUERY_RELEASE를 게시하고 다시 읽어 확인합니다.
   COMPLETE가 나오면 조회 데이터 적재 완료입니다. ACTIVE/STATE는 그대로입니다.

d. ACTION = "status"
   완료 버전과 모든 조회 행의 내용/건수를 다시 읽어 대조합니다.
   QUERY_PUBLICATION_VERIFIED를 확인하고 release_id와 실행 기록을 보관합니다.
   기존 SQL Explore의 미리보기는 새로고침해야 최신 행이 보일 수 있습니다.

GENOS 서빙 환경의 DP_QUERY_RELEASE_ID/채널 선택 및 워크플로우 테스트는 별도 단계입니다.
이관 완료를 코드서빙 배포/실제 응답 성공으로 간주하지 않습니다.

7. 중단·재개·원복

추출 중 중단:
- 동일 코드·동일 generation·동일 --output으로 export를 다시 실행합니다.
- 이미 저장된 행을 원본에서 다시 읽어 비교하며 이어갑니다. 이전 입력과 다른 행은 거부합니다.
- export-state.json의 최초7일 기한을 유지합니다. 1회 최대21600초(6시간) 검사이며,
  파일 해시/압축처럼 한 작업이 진행 중이면 그 I/O 호출을 즉시 끊는 강제 타이머는 아닙니다.
- 기존 완료 DB/조각은 동일 해시일 때 재사용합니다. 다른 파일은 덮어쓰지 않습니다.

조각 누락/해시 불일치:
- 해당 조각을 코드스페이스 원본에서 다시 다운로드/업로드합니다.
- 실패 부분파일을 완료본으로 바꾸거나 manifest 해시를 새로 쓰지 않습니다.
- WORK_DIR의 잘못된 파일은 확인 후 별도 보존 위치로 옮긴 뒤 같은 restore를 재실행합니다.

Oracle 중단/권한/연결 오류:
- 원인을 해결하고 같은 WORK_DIR에서 같은 ACTION="publish"를 다시 실행합니다.
- DB가 쓰기를 끝낸 뒤 응답만 끊겨도 다음 실행에서 동일 행을 대조하여 중복 삽입을 막습니다.
- 매번 처음부터 읽고 확인하므로 시간은 다시 걸릴 수 있습니다. 최초7일/누적100만 SQL 한도는 유지됩니다.
- PAUSED이면 1회 시간을 1~21600초 범위에서 조정할 수 있습니다. 최초 기한이 끝나면 기록을 검토합니다.
- 해시/버전/행 충돌은 자동 수정하지 않습니다. ACTIVE를 변경하지 않으므로 기존 서빙 선택은 유지됩니다.
- 실패한 부분 QUERY_ROW는 비활성 버전으로 남습니다. 삭제/기존 데이터 덮어쓰기는 이 도구에 없습니다.

로그:
- 코드스페이스 명령 시작부터 ./query-transfer-command-logs/run-*.log, 종료 코드 기록
- 출력 폴더 events.jsonl, export-state.json, source-check.json
- Dataiku WORK_DIR/oracle-import/<원문릴리스>/state.json, calls.jsonl, events.jsonl
- SQL 호출 기록에는 SQL/값의 원문 대신 해시와 성공·불명 상태를 남깁니다.

8. 자원과 검증 범위

데이터 작업은 한 프로세스로 순차 실행합니다. 코드스페이스 실행기는 해당 작업 프로세스만
주소 공간6GiB로 제한하고 가용RAM/디스크가512MiB 아래이면 작업을 보류합니다.
SQLite는 작은 캐시를 쓰고 원본·조각은 스트리밍 처리합니다. 한 문서 구조 또는 한 큰 값은 메모리에 올라갑니다.
주소 공간 한도에 걸리면 실패 로그를 남기며 원본과 부분 저장물을 보존합니다.

코드스페이스: 조회 DB + 압축 ZIP + ZIP과 같은 총 크기의 조각 공간이 필요합니다.
Dataiku: 다운로드 조각 + 병합 ZIP + 복원 DB + 로그 공간이 필요합니다.
DB의 실제 팽창률은 원본 색인에 따라 달라지므로 고정 용량을 보장하지 않습니다.
완료 후 필요 없는 작업용 복사본 정리는 사용자가 다운로드/적재 검증 후 판단합니다.

이 외부 세션은 GENOS 내부 운영 데이터/현재 리비전/Dataiku JDBC 연결에 접속하지 않습니다.
동봉 VALIDATION.json은 로컬 검증 결과이며 현장 대용량 이관 성공을 뜻하지 않습니다.
코드 전달 ZIP에는 운영 DB·질문·인증키·.env·JavaScript 파일을 포함하지 않습니다.
