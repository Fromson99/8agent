2. 현재 사진이 증명하는 범위

사용자가 제공한 현장 화면:
  CONNECTION_SETUP_TIMEOUT
  ConnectTimeout / MaxRetryError / ConnectTimeoutError / TimeoutError
  elapsed_seconds: 8.01
  http_status: None
  effective_proxy_enabled: False
  relay_url: https://45.101.64.86:8443/law/DRF

이것은 해당 Dataiku Python 요청의 연결 수립 시간초과와 HTTP 응답 미수신 증거입니다.
법제처 본문을 받은 기록도, API의 인증 거절 응답을 받은 기록도 아닙니다.
stage=awaiting_response_headers는 요청 전 코드가 지정한 단계명입니다.
이 이름을 '서버가 요청을 받았고 처리 중이었다'는 증거로 사용하지 마세요.
MaxRetryError라는 예외 이름만으로 자동 재호출이 있었다고 해석하지 마세요.
기존 진단의 자동 재시도 설정은 0이며, 실제 횟수는 실행 기록으로 확인합니다.
effective_proxy_enabled=False는 requests가 명시적 HTTP 프록시를 선택하지 않았다는 뜻입니다.
중간 NAT·방화벽·투명 프록시가 없다는 뜻은 아닙니다.

현재 근거만으로 방화벽 차단을 확정할 수 없습니다.
방화벽 DROP, 라우팅/반환 경로 문제, 서버 무응답, 잘못된 개발 주소를 구분해야 합니다.

5. 핵심 결과 판독

TCP_TIMEOUT + curl exit 28 + time_connect=0 + HTTP 000
  → 해당 시각에 독립 TCP 연결도 완료되지 않음. 경로/네트워크/서버 계층 확인 근거가 강화됩니다.
  → 아직 '방화벽 확정'은 아닙니다. 방화벽 로그·양단 패킷으로 위치를 확인합니다.

TCP_CONNECTED
  → 그 TCP 검사 시각에는 해당 목적지와 연결을 수립했습니다.
  → curl의 TLS, HTTP 결과를 따로 확인합니다. 두 검사는 다른 소켓·시각입니다.

TCP_REFUSED
  → 연결 거절 응답입니다. 서버 리스너 없음 또는 중간/호스트 방화벽 REJECT 가능성이 있습니다.
  → 방화벽 DROP으로 단정하지 않습니다.

NETWORK_UNREACHABLE / HOST_UNREACHABLE
  → 로컬/중간 경로와 해당 오류 원인을 확인합니다. 이것만으로 특정 장비의 차단을 확정할 수 없습니다.

time_connect > 0, time_appconnect=0, curl exit 28/35/60
  → TCP 상대까지 연결된 뒤 TLS 또는 프록시 단계 문제를 확인합니다.
  → IP로 호출한 HTTPS 인증서 이름 불일치/신뢰 CA 문제도 확인 대상입니다.
    담당자가 제공한 정식 호스트명을 사용해야 하는지는 별도 확인하며 인증서 검증을 끄지 않습니다.

HTTP_RESPONSE_200/302/401/403/404/5xx
  → 이번 curl 경로에서 HTTP 응답을 받았습니다. 단순 TCP 차단만으로 설명할 수 없습니다.
  → 403은 API 권한, WAF, 프록시 등 여러 계층에서 발생할 수 있으므로 발신 주체/로그를 확인합니다.
  → HTTP 200만으로 정상 법령 데이터 수신이라고 판정하지 않습니다.

curl의 exit 28은 시간초과 일반 코드입니다. DNS/TCP/TLS/응답 대기 중 어디인지 시간을 함께 봅니다.
time_connect는 TCP 상대(프록시 사용 시 프록시)와 연결이 완료될 때까지의 시간입니다.
time_appconnect는 TLS 등 핸드셰이크 완료까지의 시간입니다. 공식 설명:
https://curl.se/docs/manpage.html#--connect-timeout
https://curl.se/docs/manpage.html#--write-out
https://curl.se/docs/manpage.html#EXITCODES

6. 방화벽 차단을 확정할 핵심 증거

가장 직접적인 근거는 이번 시도와 일치하는 방화벽 DENY/DROP 로그와 적용 정책 ID입니다.
맞춰야 할 필드:
  검사 시각(UTC/KST), 출발지 IP·포트, NAT 변환 후 IP·포트,
  목적지 45.101.64.86, 목적지 TCP 8443, 장비명/구간, DENY/DROP 액션, 정책 ID.
Dataiku 브라우저를 보는 사용자 PC IP가 아니라 Notebook 프로세스의 실제 실행 노드/컨테이너 경로입니다.
JSON의 local_ip는 실행 네임스페이스 내부 주소일 수 있습니다. NAT 후 IP는 장비에서 확인해야 합니다.
두 검사에서 출발지 포트가 달라지므로 TCP 검사와 curl 검사 각각의 시각/포트를 대조합니다.
실패한 curl의 local_ip/port가 비어 있으면 추정하지 말고 독립 TCP 기록과 패킷 캡처를 사용합니다.

보조 증거: 같은 실행 네임스페이스/노드와 중계 서버 양단의 패킷 기록.
클라이언트 SYN 재전송만 있고 SYN-ACK/RST가 없으면 무응답/드롭 경로 의심 근거입니다.
단독 캡처만으로 차단한 장비를 특정할 수 없습니다.
서버에 SYN이 도착했는지, 서버 SYN-ACK가 나갔는지, 클라이언트까지 돌아왔는지를 대조해야 합니다.
로그가 없다는 사실만으로 허용됐다고 판단할 수 없습니다(로그 미설정/다른 경로 가능).

관리자가 캡처 권한이 있는 쉘에서 사용할 제한 명령 예시:
  TZ=UTC timeout 45s tcpdump -nn -tttt -i any 'host 45.101.64.86 and tcp port 8443 and (tcp[tcpflags] & (tcp-syn|tcp-rst) != 0)'
관리자가 먼저 캡처를 시작한 다음 사용자가 증거 셀을 처음 1회 실행합니다.
이미 실행한 셀을 다시 누르면 저장 결과만 표시되므로 새로운 패킷은 발생하지 않습니다.
이 명령은 현재 실행 셀에서 자동 실행하지 않습니다. sudo 권한을 가정하지 않습니다.
이 예시는 IPv4 SYN/SYN-ACK/RST를 보는 용도입니다. 앱 응답/전체 TLS 진단용 캡처가 아닙니다.
NAT 밖 서버에서 보는 출발지 주소와 클라이언트 네임스페이스 주소는 다를 수 있습니다.
