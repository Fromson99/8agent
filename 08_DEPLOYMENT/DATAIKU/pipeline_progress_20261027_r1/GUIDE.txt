Dataiku 실행 중 작업의 수신 로그 확인 — 2026-10-27 R1

사용 방법
사진의 status를 실행한 같은 LEGAL_RAG 노트북에서 새 셀을 만든다.
DATAIKU_PROGRESS_READONLY_20261027_R1.txt 전체를 붙여넣어 실행한다.
이미 실행 중인 02를 재실행하거나 GENOS 리비전을 바꿀 필요가 없다.
이 셀을 다시 실행하면 직전 조회와 수신 로그 바이트/체크포인트 순번을 비교한다.

확인 범위
Dataiku 저장 단계, 체크포인트 순번, 수신 확인된 로그 바이트,
처음 1개와 마지막 4개 로그 조각의 PHASE 및 마지막 20행을 표시한다.
로그 조각은 최대 1MiB씩, 최대 5MiB만 읽는다. 입력 ZIP/반환 ZIP은 읽지 않는다.
GENOS HTTP 호출, S3/Oracle 쓰기, 설치, 재시도, 취소는 하지 않는다.
현재 코드의 control/controller 및 체크포인트 SHA256/충돌 검사를 재사용한다.
같은 노트북의 검증된 패키지 모듈을 전제로 하며 임의 새 코드를 설치하지 않는다.

해석
last_observed는 기존 controller가 단계 변경 때만 저장하므로 최신 관측이 아닐 수 있다.
사진의 log_bytes=0은 이 저장 필드다. 실제 수신량은 별도 log_offset과 로그 조각을 읽는다.
PHASE는 해당 단계 시작 기록이다. 최신 단계/완료/정상 진전의 보증은 아니다.
체크포인트 증가에는 HTTP 예산 예약도 포함되므로 문서 처리 건수로 해석하지 않는다.
로그가 없으면 입력 준비 중/무출력 처리/전송 지연/실패 등 원인을 확정할 수 없다.
lease_seconds=900은 연결 유지 유예 설정이며 남은 처리 시간이 아니다.
처리 건수/전체 건수 계측이 없어 전체 진행률/완료 예상 시각은 만들지 않는다.
단계별 소요 시간이 다르므로 네 단계 중 두 단계 진입을 50%로 환산하지 않는다.
02 STRUCTURED는 결과 저장, 03 COMPLETE는 실버 적재로 구분한다.

실패 계약
상태 없음은 미확인으로 표시한다. 잘못된 해시/순번 충돌/로그 범위 오류는 원래 예외로 중단한다.
자동 재시도와 상태 수정은 없다. 기존 원문/실패/작업 이력은 유지한다.

로컬 확인
Python 3.9 구문 검사, 실제 발송 R1 ZIP의 control/controller/config와 모의 Dataiku 읽기를 사용했다.
빈 로그, 오래된 log_bytes=0과 실제 수신 로그의 구분, 조각 경계에 나뉜 PHASE,
반복 조회 비교, capability token 미출력, 체크포인트 hash 불일치 거부를 확인했다.
현장 Dataiku 실행은 아직 확인하지 않았다. 실제 배포 코드나 실행 중 레시피는 바꾸지 않았다.
