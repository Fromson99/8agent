Dataiku 기존 원문에서 DOC / DOCX / HWP / HWPX 각 1개 테스트
2026-10-28 / 테스트 도구 R1 / 계산 서버 R5

이 도구가 하는 일
LEGAL_RAG의 기존 구조화 레시피 설정에서 원문 폴더와 결과 폴더를 찾습니다.
ehA8dpVm/RAW_INPUT.zip.receipt.json에 연결된 기존 RAW snapshot을 읽고,
DOC·DOCX·HWP·HWPX를 각 1개, 총 최대 4개 선택합니다.
Dataiku가 선택 파일의 바이트를 기존 LEGAL_PIPELINE_URL로 전송합니다.
GENOS 계산 Pod는 각 파일을 PDF로 변환한 뒤 파싱합니다.
Dataiku가 PDF·텍스트·Docling JSON·단계별 상태·오류 로그를 결과 폴더에 보관합니다.
전체 구조화 레시피, RAG 검수, 색인, Oracle 적재는 이 테스트에서 실행하지 않습니다.
GENOS는 S3에 직접 접속하지 않으며 테스트 파일은 계산 중 임시 사용합니다.

먼저 한 번 준비
현재 R4 API의 RUN은 전체 구조화 파이프라인을 실행합니다.
변환·파싱만 검사하려면 이번 R5의 전용 테스트 분기가 필요합니다.
R5는 R4의 기존 기본 파이프라인을 유지하고 테스트 분기를 추가합니다.

1. GENOS에서 전달 ZIP 압축을 풉니다.
사용 중인 TRANSFER 폴더에서 아래처럼 실행합니다. 경로는 임의로 추정하지 않습니다.

unzip DATAIKU_FOUR_FORMAT_TEST_20261028_R1.zip -d document_four_types_r1
cd document_four_types_r1
bash GENOS_R5_INSTALL.txt

이 명령은 기존 ~/DEV legal_pipeline_serving checkout을 검사·백업한 뒤 적용,
변경 파일 stage/commit, 동일 파일 검증, git push까지 실행합니다.
다른 checkout이거나 기존 코드가 수정돼 있으면 덮어쓰지 않고 중단합니다.
GENOS 화면에서 출력된 commit으로 새 코드서빙 리비전을 배포해야 합니다.
이 전달본을 만든 로컬 환경에서는 현장 push/배포를 실행하지 않았습니다.
기존 URL/TOKEN, worker 1 / replica 1을 유지합니다.
RAG 채팅 서비스에 적용하지 않습니다.

2. ZIP 안의 DATAIKU_COMPUTE_RECIPES_20261028_R5.zip을
Dataiku LEGAL_RAG의 기존 업로드 폴더 ehA8dpVm에 업로드합니다.
원문을 다시 업로드하거나 파일 경로를 지정할 필요가 없습니다.

3. LEGAL_RAG에서 새 Python 노트북을 열고
DATAIKU_FOUR_FORMAT_TEST.txt의 전체 내용을 한 셀에 붙여넣어 실행합니다.
기존 Dataiku API 권한·원문/결과 관리 폴더 권한·프로젝트 URL/TOKEN을 사용합니다.
RUN_NAME과 ACTION='run' 기본값을 그대로 사용합니다.

모의 테스트 통과는 HWP 등의 실제 렌더링 품질을 보증하지 않습니다.

YAML은 왜 필요했나
YAML은 입력 문서나 Dataiku 파일 목록이 아닙니다.
GENOS 파서가 사용할 layout/OCR 모델과 연결값을 담은 서버 설정입니다.
앞선 단일 파일 TXT는 새 Pod에서 파서를 직접 생성해서 --config를 요구했습니다.
이번 Dataiku 테스트에는 --config나 YAML 내용 입력이 없습니다.
1) Pod에 GENOS_STRUCTURE_CONFIG가 있으면 그 파일을 사용합니다.
2) 없으면 설치된 파서의 resource_dev/resource 표준 위치를 찾습니다.
3) 찾은 설정을 계산 중 임시 복사하고 출력만 Docling으로, enrichment만 끕니다.
원래 설정 파일은 변경하지 않으며 설정 파일 자체는 결과 ZIP에 담지 않습니다.

설정이 187번 전처리기 Pod에만 있으면 우리 계산 Pod에서 자동으로 보이지 않습니다.
우리 Pod에 파서 의존성·변환기·실제 모델 설정이 없으면 선행 준비가 필요합니다.
코드 ZIP이 모델/LibreOffice/한글 변환기까지 설치하는 것은 아닙니다.
R4의 환경 준비와 matching fork wheel 안내를 그대로 사용합니다.
특히 HWP/HWPX 변환은 이미지에 설치된 GENOS 변환 backend에 따라 달라집니다.
POD_EXISTING_PARSER_CONFIG_NOT_FOUND: 이 Pod에 기존 파서 설정 없음.
POD_EXISTING_PARSER_CONFIG_AMBIGUOUS: 서로 다른 설정이 여럿임.
  이 경우 사용할 기존 설정 파일을 Pod의 GENOS_STRUCTURE_CONFIG에 지정합니다.
POD_PARSER_OR_CONVERTER_NOT_READY: 파서 의존성/변환기 초기화 실패.
모델 주소/키를 추정해서 새 YAML을 자동 생성하지 않습니다.
PROBE_HEALTH 통과는 구성/초기화 확인이며 모델 접속 성공 검사는 아닙니다.

선택 범위와 제한
원문 폴더는 기존 LEGAL_02_STRUCTURE_GENOS_R1 또는 _NP 레시피에서 찾습니다.
동일 설정은 하나로 보고 서로 다른 후보가 여러 개면 임의 선택하지 않습니다.
직접 보관된 원문 중 확장자별 가장 작은 양수 크기 파일을 고릅니다.
크기가 같으면 경로순으로 결정합니다. 잠금/~$ 파일·숨김 파일·빈 파일은 제외합니다.
직접 원문에 없는 형식만 기존 내부 ZIP에서 보완 검색합니다.
ZIP은 작은 순서 최대 8개·각 512MiB 이하·한 단계 내부 파일만 조사합니다.
형식별 테스트 문서는 256MiB 이하, 최대 4개입니다.
형식이 없으면 NOT_FOUND, 직접 파일이 너무 크면 TOO_LARGE로 표시합니다.
ZIP 검색 제한은 notes에 남기므로 NOT_FOUND가 전체 저장소 부재 증명은 아닙니다.
DOC→DOCX 등으로 이름만 바꿔 없는 형식을 만든 것처럼 처리하지 않습니다.

취소와 재개
같은 셀에서 ACTION='status'로 상태 확인,
ACTION='cancel'로 현재 계산에 취소 요청을 보냅니다.
커널 Interrupt도 취소 요청을 보내도록 연결했습니다.
그 뒤 같은 RUN_NAME으로 ACTION='run'을 실행하면 종료 상태/진단을 수집합니다.
전송 응답이 끊겼을 때도 같은 RUN_NAME을 유지합니다.
완료된 테스트를 다시 실행하면 저장 결과를 보여주며 계산을 재시작하지 않습니다.
원래 deadline·사용량·동일 핸들을 보존하고, 새 이름으로 실패 예산을 초기화하지 않습니다.
선택 이후 전체 기한은 2시간이며 종료/반환 여유 120초를 둡니다.
GENOS 임시 핸들은 15분 연락이 없으면 만료되고 현재 자식 프로세스를 종료합니다.
Pod 재시작/핸들 소실/기한 소진은 자동 새 작업으로 재실행하지 않습니다.
부분 성공과 중단 상태를 보존하며 모델 호출 자동 반복은 추가하지 않았습니다.

기존 전체 Flow와 복원
R5 배포로 서버 코드 SHA가 달라집니다. 기존 R4 레시피의 해시 검사는 유지합니다.
전체 Flow를 다음에 사용할 때 DATAIKU_R5_INSTALL.txt를 별도 셀에서 실행하면
기존 레시피의 클라이언트/해시를 R5로 맞춥니다. 이 셀 자체는 Flow를 실행하지 않습니다.
이번 네 문서 테스트를 위해 00→02→03 전체 실행은 하지 않습니다.
전체 Flow에는 기존 R4의 명시적 GENOS_STRUCTURE_CONFIG와 검수 모델 설정이 필요합니다.
실패한 과거 전체 작업의 이행은 기존 audit·검수 호출0 증거·원래 기한·총3시도 조건을 보존합니다.

복원은 ROLLBACK_GENOS.txt로 이전 파일을 복원하고 검토/commit/push 후 이전 리비전을 선택합니다.
Flow 업데이트를 했다면 DATAIKU_R5_CONTROL.txt에서 ACTION='rollback'을 실행합니다.
Dataiku의 원문·기존 작업 기록·이번 테스트 결과는 지우지 않습니다.
로컬 RAG MAIN111/활성 데이터는 이 변경 대상이 아닙니다.
