NFS Oracle 이관 R9 — Python 호환 오류 수정·검색행 최대500행 전송

첨부 파일
DATAIKU_EXISTING_NFS_CLIENT_20261030_R9.zip: 실제 실행 패키지
DATAIKU_EXISTING_NFS_LOAD_ONLY_R9.txt: 전체 실행 코드
GUIDE.txt: 이 안내

수정 내용
1. hashlib.file_digest가 없는 현장 Python에서 오류가 난 contracts.sha를
   같은 SHA-256 결과의 1MiB 스트리밍 계산으로 교체했습니다.
   full_glossary의 같은 사용처도 수정했습니다. 입력 파일/해시값을 바꾸지 않습니다.
   시작 시 두 파일 해시 함수도 검사하고 실제 Python 버전을 표시합니다.
2. 검색행은 기존20행 논리묶음을 합쳐 최대500행을 한 Oracle 요청으로 보냅니다.
   재개 커서는 기존20행 논리묶음 번호를 계속 사용합니다. 성공 응답 후에만
   이번 요청에 포함한 마지막 묶음 번호를 저장하므로 기존 적재 부분을 누락하지 않습니다.
   파일 경계를 넘지 않고, 기존 JSON 누적4MiB 묶음 목표도 유지합니다.
   단일 큰 행은 기존처럼 별도 처리하며 실제 JDBC SQL 크기는 JSON 크기와 다릅니다.
3. R8의 완료 준비 명세는 동일 입력/기존 publisher/compiler 조건에서 재사용합니다.
   이번 변경은 검색행 내용·ID·순서·query release ID를 바꾸지 않습니다.
   R8의 정확한 executor hash만 호환 허용하고 알 수 없는 입력/코드는 재사용하지 않습니다.

실행
오류 난 셀이 종료되어 Idle인지 확인합니다. 실행 중인 적재가 있다면 중복 실행하지 않습니다.
LEGAL_RAG의 기존 반입 관리 폴더 ehA8dpVm에 R9 ZIP을 압축 그대로 올립니다.
Kernel > Restart 후 새 셀에 DATAIKU_EXISTING_NFS_LOAD_ONLY_R9.txt 전체를 붙여 실행합니다.
R8 대신 이번 R9 실행본을 사용합니다. 원문/S3/NFS/기존 receipt와 수신 generation은 유지합니다.
기존 레시피00/01/02/03을 다시 실행하는 절차가 아닙니다.

기본 실행값
ACTION='load_only': 적재만, Oracle 전수 재조회 검증은 나중으로 미룹니다.
QUERY_WRITE_ROWS=500: 검색행 쓰기 최대행수입니다. 필요 시20..500 범위로 바꿀 수 있습니다.
예를 들어100으로 바꿔도 재개 커서 의미와 query ID는 같습니다.
현장 JDBC 크기/컴파일 제한이 확인되면 결과를 확인한 후 값을 조정합니다.
자동으로 묶음을 줄여 재시도하지 않습니다. 응답 유실 때는 종료 상태를 확인하고 명시 재개합니다.
원문3종 쓰기 묶음은 기존20행 그대로이며, 이번 변경 대상은 대규모 검색행 적재입니다.
나중에 필요할 때만 ACTION='verify'로 별도 전수검증합니다.

현재 실패 지점과 재사용
사진의 search_selection.Selection → contracts.sha 실패는 검색명세를 계산한 뒤,
게시 명세를 확정하는 단계입니다. 이 경로에서는 완료 준비 명세가 저장돼 있을 가능성이 큽니다.
같은 로컬/S3 receipt에 그 명세가 남아 있고 입력/코드 조건이 맞으면
PROJECTION_PREPARATION_REUSED가 표시되며 긴 검색명세 계산을 재사용합니다.
원문 로컬 행수/해시 계산 등 앞단 확인은 여전히 있습니다.
명세가 없거나 손상/입력이 바뀐 경우에까지 재사용한다고 보장하지 않습니다.

진행 표시
15초 진행 줄과 원래 기한/자원 보호를 유지합니다.
QUERY_WRITE_ROWS=500: 선택한 요청당 최대행수입니다.
QUERY_LOADED의 rows_this_run/requests_this_run/last_request_rows가 실제 쓰기 진행입니다.
legacy_frames는 재개용 기존20행 묶음 번호이며 실제 요청 횟수와 다릅니다.
하트비트에도 이번 적재행수/요청수/최근 요청행수를 표시합니다.
LOADED_UNVERIFIED이면 적재 완료·전수검증 보류입니다.

효과와 한계
작은 행930만 개는 20행씩이면 약46만5천 요청, 500행씩이면 약1만8천6백 요청입니다.
본문 크기나 파일 경계 때문에 실제 묶음이500행보다 작을 수 있습니다.
요청 수 감소가 전체 실행시간25배 개선을 뜻하지 않습니다. DB 내부 행별 충돌 확인은 유지합니다.
현장 Dataiku/JDBC 속도와 전체 적재 완료는 아직 미확인입니다.
기존7일 기한/누적 SQL 예산을 초기화하거나 늘리지 않습니다. 6시간 실행 상한도 추가하지 않습니다.
기존 publisher와 다른 query plan은 계속 사전 거절합니다. 기록 삭제/ID 변경으로 우회하지 마세요.

검증
계약43개, 실제 Python3.10에서 전체 전달TXT를 실행한 모의 Dataiku/Oracle/NFS1개 통과.
Python3.10에서 R8 file_digest 오류를 재현하고 R9 사전검사·파일해시 통과를 확인했습니다.
로컬 실제 Oracle에서 동일 생성 PL/SQL로500행 한 요청, 전체 값 대조,
동일 요청 재실행,499개 신규행 뒤 충돌 시 전체rollback, commit후응답유실·명시재개를 확인했습니다.
현장 Dataiku Oracle에서 수행한 시험은 아닙니다. 시험용 로컬 schema는 정리했습니다.
기존 R8 모듈/실패 기록/MAIN/GENOS/실제 원문 데이터는 덮어쓰지 않았습니다.
