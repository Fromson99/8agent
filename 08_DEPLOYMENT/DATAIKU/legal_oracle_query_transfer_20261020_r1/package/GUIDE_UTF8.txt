실행 위치와 선행 조건
이전에 원문/자산 이관을 완료한 LEGAL_ORACLE_FULL_TRANSFER_20261019_R1.ipynb를 엽니다.
그 노트북에서 기존 desk 인증, SOURCE_SQLITE 원본 경로, LOG_DIR 기록 폴더를 그대로 사용합니다.
커널을 다시 켰다면 기존 노트북 00~03만 실행하여 연결하고 아래 새 셀로 갑니다.
원문 이관 05, 전체 대조 06, 자산 업로드 07을 무조건 다시 실행하지 않습니다.
이 셀은 기존 08 단계의 summary 함수를 호출해 완료 릴리스와 기록을 확인합니다.

CODE_ROOT 기본값 /workspace는 이전 현장 사진에서 확인한 기존 코드 checkout입니다.
실제 이관 실행 환경에서 코드 경로가 다르면 실제 경로로 바꿉니다.
해당 checkout에는 앞서 발송한 GENOS_WORKFLOW_PROGRESS_20261019_R1 또는
그와 동일한 Oracle 게시 모듈 13개가 설치되어 있어야 합니다.
이 묶음은 기존 게시 함수의 호출 코드입니다. 전체 앱 설치본을 중복 포함하지 않습니다.
CODE_PIN 오류이면 누적 코드 적용 상태와 실제 경로를 확인합니다. 해시를 수동 수정하지 않습니다.
코드/원본 generation/기존 이관 기록을 모두 읽을 수 있는 Jupyter 커널에서 실행합니다.
GENOS 코드서빙 프로세스에서 원문/색인을 내려받거나 적재하는 경로가 아닙니다.

실행 순서
1. 기존 이관 노트북 맨 아래에 새 Python 셀을 만듭니다.
2. LEGAL_ORACLE_QUERY_TRANSFER_20261020_R1.txt 전체를 붙여넣습니다.
3. 맨 위 ACTION = "check"로 실행합니다.
   READY_TO_PUBLISH이면 기존 원문 완료 버전과 조회 4테이블/4인덱스 계약이 확인된 것입니다.
   스키마 검사 성공만으로 INSERT 권한이나 전체 원문 적재의 새 검증을 뜻하지 않습니다.
4. 같은 셀 맨 위를 ACTION = "publish"로 바꾸고 실행합니다.
   검증된 원본 generation의 용어/정의/참조/문서 구조/전문검색 색인 행을 게시합니다.
   각 배치를 Oracle에서 재조회하고, 모든 종류의 건수와 릴리스 명세를 확인합니다.
   status=COMPLETE, release_id, receipt가 나오면 해당 결과를 보관합니다.
5. 같은 셀 맨 위를 ACTION = "status"로 바꾸고 실행합니다.
   QUERY_PUBLICATION_VERIFIED와 rows, kinds, release_id를 확인합니다.
   status는 완료 명세와 종류별 건수를 재조회합니다. 본문 전체 재검사는 publish가 담당합니다.

테이블별 동작
LEGAL_RAG_QUERY_ROW_A: 검색/용어/관계/구조/원문 검증 행 INSERT 및 재조회.
LEGAL_RAG_QUERY_RELEASE_A: 게시 전체 검증 후 완료 릴리스 INSERT 및 재조회.
LEGAL_RAG_QUERY_ACTIVE_A: status에서 main 포인터를 읽기만 함. 활성화는 별도.
LEGAL_RAG_QUERY_STATE_A: 스키마만 확인. 대화/대사/AD 이력을 옮기지 않음.
기존 원문 3개와 자산 2개 테이블의 데이터는 이 셀에서 삭제/덮어쓰기/재이관하지 않습니다.

실패와 재개
자동 네트워크 재시도/자동 활성화는 없습니다.
PAUSED/FAILED이면 해당 원인과 기록을 확인한 뒤 같은 설정/로그 폴더의 publish를 다시 실행합니다.
기존 게시기는 원본을 처음부터 다시 순회하며 이미 올라간 동일 행을 검증해 재사용합니다.
마지막 행 이후만 건너뛰는 방식은 아닙니다. 다른 값의 기존 행을 덮어쓰지 않습니다.
원본 해시/코드/접속 바인딩이 다르면 그대로 중단합니다.
같은 로그 폴더의 publish.lock, state.json, calls.jsonl을 사용하여 중복·예산을 관리합니다.
최초 7일 기한과 누적 SQL 호출 한도(현재 엔진 100만 회)는 재개해도 유지됩니다.
PUBLISH_SECONDS 기본 3600초는 호출 세션 예산입니다. 원본 순회/해시 계산 자체의
즉시 강제 종료를 보장하지 않으며, 다음 SQL 경계에서 예산 소진을 확인합니다.
기한/호출 한도 소진은 폴더를 바꾸거나 기록을 지워 우회하지 않습니다.

진행 확인
시작 시 출력한 calls.jsonl은 실제 SQL 호출의 시작/응답/실패 기록입니다.
state.json에는 단계와 종류별 검증 행 수가 남습니다. 원본 순회 중에는 SQL 기록이
늘지 않을 수 있습니다. 전체 크기에 대한 현장 처리 시간/디스크 사용량은 미측정입니다.
로그 최상위 legal_query_handoff_events.jsonl에는 check/publish/status 성공·실패와
인증값을 가린 traceback을 남깁니다. 실패/부분 업로드 기록을 보존합니다.
가용 RAM 1GiB, 로그 디스크 여유 512MiB 미만이면 시작하지 않습니다.
한 번에 이관 프로세스 하나만 실행하고 로그 공간과 RAM을 관찰합니다.
이 시작 조건은 실행 중 최대 메모리·총 로그 용량을 보장하는 상한이 아닙니다.

압축 해제
ZIP은 일반 압축 도구로 풀어 TXT를 열면 됩니다.
Linux 코드스페이스에서는 실제 업로드한 TRANSFER 폴더를 현재 위치로 두고:
python3 -m zipfile -e ./LEGAL_ORACLE_QUERY_TRANSFER_20261020_R1.zip ./legal-oracle-query-transfer-20261020-r1
압축 해제 후 TXT를 기존 이관 노트북의 Python 셀에 붙입니다.
