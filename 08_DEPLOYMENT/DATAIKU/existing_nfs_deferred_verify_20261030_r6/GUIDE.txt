1. 지금 화면에서의 판단
사진상 원문 document 2,121 / source_unit 356,537 / block_payload 477,055의
SOURCE_TRANSFER_VERIFIED=3/3 이후 별도 verify가 실행 중입니다.
원문을 삭제하거나 처음부터 재적재할 필요가 없습니다.
R6 load_only는 기존 원문 적재 cursor/chain을 이어받아 완료한 본문을 다시 읽지 않고,
나머지 색인 파일 조각과 조회용 구조화 행을 먼저 Oracle에 넣습니다.
완료한 source_unit의 전수검증을 지금 다시 시작하지 않습니다.
다만 나중의 verify에서는 그 시점의 실제 DB 내용을 확인하므로 원문 3테이블을
처음부터 한 번 대조합니다. 과거 검증 결과를 현재 데이터의 검증 결과로 재사용하지 않습니다.

3. 현재 R4/R5가 실행 중이면
실행 중인 셀의 코드를 바꾸거나 다른 노트북에서 같은 적재를 병행하지 않습니다.
먼저 현재 노트북에서 Kernel > Interrupt를 한 번 실행합니다.
NFS_STOPPED 또는 PAUSED/STOPPED로 종료되고 커널이 Idle인 것을 확인합니다.
응답이 아직 없으면 커널 강제 종료/Restart나 새 적재를 하지 말고 종료를 기다립니다.
진행 화면과 종료 메시지를 보관합니다. 중단 시 기존 기록은 별도 blob으로 저장됩니다.
그다음 Kernel > Restart로 이전 모듈을 내리고 R6 TXT 셀만 실행합니다.
이미 FULL_DATA_VERIFIED까지 끝났으면 R6로 다시 적재할 이유는 없습니다.

4. 실행 순서 (같은 TXT 전체에서 맨 위 ACTION 값만 변경)

첫 실행:
ACTION = 'check'
NFS_READY_FOR_TRANSFER 확인. 이 단계는 연결/스키마/고정 데이터 확인입니다.

구조화 자료부터 적재:
ACTION = 'load_only'
LOADED_UNVERIFIED를 확인합니다.
기존 적재된 원문은 유지하고 미적재분·색인 자산·조회 행을 이어 넣습니다.
SOURCE_LOADED_UNVERIFIED는 적재 단계 종료이지 전수검증 통과가 아닙니다.
PREPARING_LOCAL_PROJECTION은 이미 받은 로컬 자료에서 게시 ID/행 계획을 계산하는
단계이며 Oracle 본문 전수검증이나 원문 재구조화가 아닙니다.
QUERY_LOADED는 조회용 행 배치 적재 진행입니다.
원본 파일 hash, 대상/세대 일치, 행 수, PK·기존 값 충돌과 쓰기 트랜잭션 검사는 유지합니다.
큰 본문을 클라이언트로 되읽는 전수검증은 하지 않습니다.

상태만 확인:
ACTION = 'status'
phase=LOADED_UNVERIFIED면 적재 완료·검증 대기입니다.
status는 새 전수검증을 실행하지 않습니다.

시간 여유가 있을 때:
ACTION = 'verify'
원문 3테이블 → 자산 파일 조각 → 조회용 구조화 행/전체 행 수를 실제 Oracle에서 확인합니다.
원문 전체 검증은 한 번이며, 뒤에서 final_source라는 이름으로 다시 반복하지 않습니다.
누락/변조가 있으면 멈추며 verify가 데이터를 자동으로 채우거나 덮어쓰지 않습니다.
모두 통과한 뒤에만 source/query COMPLETE 게시 명세를 쓰고 FULL_DATA_VERIFIED를 표시합니다.
이 두 작은 게시 명세 기록은 verify에 포함되므로 완전히 읽기 전용인 명령은 아닙니다.
활성 채널·기존 서빙 설정은 자동 전환하지 않습니다.

적재와 검증을 바로 연속 실행하려면:
ACTION = 'load'
load_only 뒤 verify를 같은 실행에서 이어갑니다.
현재 요청에는 load_only 사용을 권합니다.

5. 중단·재개
load_only 중단: 종료/Idle 확인 후 같은 R6, 같은 ACTION='load_only'로 재개합니다.
확인된 원문 cursor/자산 part/조회 batch는 이어받으며, 쓰기 응답이 불명확했던 배치는
동일 PK·내용을 DB 안에서 대조하는 멱등 쓰기로 재개합니다. 다른 값이면 중단합니다.
자동 쓰기 재시도는 하지 않습니다.
verify 중단: 종료/Idle 확인 후 같은 R6 ACTION='verify'를 다시 실행할 수 있습니다.
verify의 진행 cursor는 저장하지 않으므로 전체 검증은 다시 시작합니다.
검증 완료 테이블을 건너뛰는 기능까지 추가한 것은 아닙니다.
최초 작업 7일 기한·누적 HTTP/SQL 예산은 이전 작업의 값을 유지합니다.
기한/예산 초과는 새 폴더나 새 작업 ID로 우회하지 않습니다.
R6 전환 뒤 R2~R5로 내려가 기존 상태 파일을 억지로 읽지 않습니다.

6. 검증 옵션
CLOB_BATCH_READS = 32
NATIVE_CLOB_READS = True
VERIFY_BATCH_ROWS = 100
R5의 전체 CLOB 조회/묶음 검증을 유지합니다. 현장 드라이버가 전체 CLOB을 자르거나
지원하지 않으면 원래 조각 조회로 대조합니다. 이 경우 시간이 더 걸릴 수 있습니다.
호환 진단이 필요하면 같은 R6에서 NATIVE_CLOB_READS=False,
VERIFY_BATCH_ROWS=20으로 원래 읽기 경로를 사용할 수 있습니다. 예산은 초기화되지 않습니다.

7. 완료 의미와 제한
LOADED_UNVERIFIED: 저장만 끝났습니다. 신규 게시 명세는 아직 생성하지 않습니다.
기존에 이미 존재하는 COMPLETE 게시 명세/활성 채널은 삭제하거나 변경하지 않습니다.
FULL_DATA_VERIFIED: 이번 고정 세대의 Oracle 데이터 대조와 게시 명세 기록이 끝났습니다.
두 상태 모두 전체 RAG 최종 답변/온톨로지 품질/GENOS 실제 화면 통과를 뜻하지 않습니다.
이 패키지는 기존 구조화 원문·색인·조회 자료 이관이며 KURE 벡터 전체 적재는 별도입니다.
현장에 직접 접속해 실행한 결과가 아닙니다. 삼성망 Dataiku/JDBC에서의 시간은 미측정입니다.
