2026-11-03 — R3 현장 사진의 예상시간 환산과 SQL 최적화 검토

결론
현재 6,097만 검색행을 사진의 작은 배치 처리율로 환산한 요청 구간 참고값은 약18~24시간이다.
실제 전체 완료시간이나 남은시간의 보장범위가 아니다. 기존 적재 진행분, 원본 재생성/묶음준비,
최종 원문·검색 전수검증, COMMIT, 벡터 임베딩/저장은 포함하지 않았다.
사진의 시험은 롤백 및 ORA-20084 진단 응답을 사용한다. 일반 성공 응답과 시간이 다를 수 있다.
실제 적재기는 검색 최대5,000행/2MiB 목표, 시험은 최대2,000행/2MiB이며
2MiB를 계산하는 지점과 시험 키 길이도 달라 동일한 배치 수/성능으로 볼 수 없다.

- 3,196ms/1,684행 처리율을 남은 모든 종류에 가정: 추가10.8957시간 →23.4955시간.
두 가정은 실제 최소/최대나 통계적 신뢰구간이 아니다. 남은 종류가 이 범위를 벗어날 수 있다.
원문835,713행은 앞선 현장 기록에서 완료 표시. 이번 사진은 현재 DB의 원문 전량 재확인 결과가 아니다.
현재 R3는 원래 적재 WRITE_UNCONFIRMED 유지. 완료된 정확한 검색행을 빼서 남은시간을 만들 수 없다.
최초100행 entry_corpus_link18.559초는 따로 관측된 일회성 값이다. 첫 요청/캐시/파싱 원인을 확정하지 않는다.

병목 해석
검색5종 마지막 시험의 INSERT+값검증은 요청초의8.96~11.55%.
DB복원은0~.01초, 기타요청은87.99~90.68%.
기타요청에는 Dataiku 실행 경계, SQL 파싱/컴파일, 임시LOB 정리, 오류 응답 처리가 섞여 있다.
핑 중앙값.070초가 요청 전체1.3~2.8초와 다르므로 나머지를 순수 네트워크라고 부르지 않는다.
R3의 DB타이머는 블록 실행 중에 시작되므로 블록 파싱/컴파일 시간을 분리해 측정하지 않는다.
SQL INSERT+검증만2배 빨라진다는 가정이면 해당 시험 전체요청 감소는 약4.48~5.77%다.
전체 적재가 같은 비중이라는 주장이나 실제 최적화 효과 인증은 아니다.

SQL/적재 최적화 후보와 우선순위

1. 전송 SQL의 큰 리터럴/파싱과 요청 경계 — 우선 확인
현재 jdbc_transport.render는 매 배치 JSON을gzip→hex로 SQL문 안에 넣고
DBMS_LOB.WRITEAPPEND를 반복하는 익명PL/SQL을 만든다. 값이 바뀔 때 SQL문도 바뀐다.
query_to_df('SELECT 1 FROM DUAL', pre_queries=[큰블록], post_queries=[COMMIT])로 실행한다.
고정 SQL+실제 bind/PreparedStatement 또는 Dataiku가 지원하는 연결 유지형 대량 writer를
사용할 수 있는지 확인할 가치가 있다. 현재 SQLExecutor2 공개 인자만으로 DBAPI executemany나
bind 대량 적재를 사용할 수 있다고 단정할 수 없다. 별도 암호를 노트북에 넣는 우회는 하지 않는다.
같은 행/배치에서 준비·렌더·DB요청·서버 parse/execute·commit·응답을 구분해 비교해야 한다.
지금 사진만으로 hard parse가90%라고 확정하지 않는다.

2. 현재 연결에서 배치당 실제 처리량 — 작은 수정 후보
이미 한행씩 왕복하지 않고 INSERT SELECT JSON_TABLE로 묶고 있다.
원문 최대1,000행/2MiB, 검색 최대5,000행/2MiB 목표다.
사진의 words1,370행/unit1,684행은 bytes 또는 원본표본 한도에 닿았다.
행수만 올려도 실제행수가 그대로면 왕복 감소가 없다. payloadbytes와 요청초를 같이 봐야 한다.
기존 R2의10,000행/4MiB 후보는 준비됐지만 ORA-01654로 적용 보류 상태이며
공간·원래pending을 확인하기 전 자동 적용/재실행하지 않는다. 새 동일배치 비교도 아직 없다.
prepared statement 100행 권고 등을 현재 JSON_TABLE5000행 방식에 그대로 적용하지 않는다.

3. 불필요한 표현을 전개하는 SQL·검색자료 — 작업량 감소 후보
occurrence_keys9,470,521 + entry_corpus_link12,712,168 + entry_definition_link325,885
=22,508,574행, 검색 전체의36.9164%다. 제외 가능 시38,463,150행으로 줄어든다.
현재 상태는 제외 검토이며 구현/전환 완료가 아니다. 소비자·원문/권한/좌표·manifest·재개순서
동등성 검증이 필요하다. 기존state에 skip만 끼우거나 이미 들어간 행을 삭제하지 않는다.
위 환산에서 앞의 두 종류가 차지한7.2076시간은 제거 후보의 작업량 참고값이며 실제 절약시간 보장이 아니다.
FTS term/doc/position 정보와 실제 소비하는 occurrence/reference는 보존한다.

4. INSERT/값검증 SQL 자체 — 후순위로 실행계획 확인
Contract.batch는 INSERT ... WHERE NOT EXISTS(PK) 후 같은JSON_TABLE을 다시 파싱해
PK JOIN+모든컬럼/CLOB(DBMS_LOB.COMPARE) COUNT로 누락·충돌을 검증한다.
JSON_TABLE의 두 번 해석과 PK탐색 비용은 후속 후보이나 현재 사진에서 이 구간은0.17~0.25초다.
같은 검증을 유지하는 데이터 조립 재사용/고정bind가 우선이다. PK/값대조 제거로 빠르게 하지 않는다.
SRCH_ROW의PK+보조4개는 매 INSERT에 갱신된다. 보조 인덱스 후생성은 전체순차 적재에는
후보지만 이후 생성시간/공간/중간조회/최종 검증까지 포함해 비교해야 한다. 지금 DDL 변경은 없다.
내부블록 COMMIT과 전송후COMMIT이 겹치지만 두번째는 이미끝난 트랜잭션일 수 있다.
COMMIT은 R3에서 미계측이므로 이를 병목이라고 단정하거나 임의 제거하지 않는다.

5. 최종 검증·벡터는 별도 시간을 계산
verify_publish는 원문/검색을 다시 생성·전송해 전체값 대조한다. 적재 요청 ETA에 빠져 있다.
벡터는800문자창/700문자간격, 최대16개씩 모델호출→저장·검증한다.
전체창수/호출당시간/완료캐시량이 없으므로 전체시간으로 계산하지 않는다.
전체 검증은 필요한 보장을 유지하며 중복 생성/전송을 줄일 경로를 별도 설계해야 한다.

추가 실행 없이 지금 확인 가능한 것
R3 같은 노트북에서 SHOW_DIAG_PAGE("준비"), SHOW_DIAG_PAGE("자료")는 저장된 결과만 보여준다.
REPORT.json에는92종계획/전체표본/요청량/시간/실패이력이 있어 사진의 누락을 줄일 수 있다.
새로 제공하는03_ANALYZE_SAVED_R3_TIME_R1.txt는 이 저장보고서만 읽어 종류별 시간비중과
전체 계획 중 실제 시험이 있는 행의 비중을 계산한다. SQL/INSERT/임베딩은 실행하지 않는다.
R3의02_PROFILE_EXISTING_STAGE_RUN_R3.txt는 실제 적재/검증/벡터를 실행할 수 있으므로
현재 원래 결과불명·공간 문제 상태에서 단순조회용으로 실행하지 않는다.

별도 용량 측정
01_CHECK_CAPACITY_RUN_R1.txt: 현재 테이블/인덱스/LOB, 계정quota, tablespace 여유만SELECT.
