법규 SQLite 원문 세 테이블 전체 이관 R1

지금 할 일
1. 이미 조회/표본 쓰기에 성공한 R6 노트북의 같은 커널에서 새 Code 셀을 만듭니다.
2. LEGAL_ORACLE_FULL_TRANSFER_20261016_R1_CELL.txt 전체를 붙여넣고 그 셀만 실행합니다.
   TXT는 Python 셀입니다. bash로 실행하지 않습니다. 인증값을 다시 넣거나 alias를 바꾸지 않습니다.
3. 기본 ACTION="run"은 실제 전체 이관을 실행합니다. 첫 화면에 원본별 총 건수와 기록 경로가 나옵니다.
   표본 시험과 달리 전체 SQLite를 읽고 Oracle에 배치 저장하므로 데이터 크기에 따라 오래 걸릴 수 있습니다.
4. SOURCE_TRANSFER_VERIFIED=3/3 및 status=SOURCE_COMPLETE이면 세 원문 테이블 이관을 완료했습니다.
5. ACTION="verify"로 바꾸고 같은 셀을 다시 실행하면 전 행 내용을 다시 조회·대조합니다.
   status=VERIFIED까지 확인합니다. Dataiku Explore는 Save and Refresh Sample로 갱신합니다.

중단과 재개
- 매 배치 저장/재조회 후 진행 위치를 기록합니다. 기본 1시간 실행 한도에 도달하면 PAUSED로 끝납니다.
  ACTION="run"인 같은 셀을 다시 실행하면 이어갑니다. 최초 전체 작업의 7일/누적 SQL 100만 회 한도는 보존합니다.
- 기존 표본 3행은 키와 전체 값이 같으면 재사용합니다. 다른 내용은 오류로 남기며 덮어쓰지 않습니다.
- 통신 오류로 응답을 못 받은 배치는 실패 이력을 남기고 중단합니다. 다음 명시적 실행에서 저장 여부를 먼저 읽고
  같은 기본키/전체 값의 멱등 INSERT로만 이어갑니다. 자동 통신 재시도는 없습니다.
- 이미 읽은 원본 파일이 변하거나 원본 해시가 다르면 중단합니다. 원본 SQLite와 기존 NFS manifest를 수정하지 않습니다.
- 원문/인증값은 로그에 넣지 않으며, 실패 문구와 DP_MIGRATION_RECEIPT 경로로 진단합니다.
- R6에 기존 쓰기 복구 대기 표시가 있으면 먼저 그 원인을 확인해야 합니다. 기존 hold를 강제로 해제하지 않습니다.

대상
SIDDA.LEGAL_SRC_DOCUMENT_A
SIDDA.LEGAL_SRC_SOURCE_UNIT_A
SIDDA.LEGAL_SRC_BLOCK_PAYLOAD_A
원본: /nfs-root/diamo/8-agent/term-releases/financial-risk-success-20261005-schema-r2/generation/store.sqlite
DATASET_VERSION: 원본 generation/manifest.json bytes의 SHA-256. 표본 시험과 동일합니다.
세 테이블 이외의 SQLite/색인/용어집은 이 실행의 대상이 아닙니다. DP 서빙 전환은 후속 전달입니다.

ZIP 사용
실제 업로드한 TRANSFER 폴더에서:
python3 -m zipfile -e ./LEGAL_ORACLE_FULL_TRANSFER_20261016_R1.zip ./LEGAL_ORACLE_FULL_TRANSFER_20261016_R1
풀린 폴더의 CELL.txt를 열고 전체를 노트북 Code 셀에 붙여넣습니다. ~/DEV 설치는 필요 없습니다.

검증
실제 임시 SQLite + 모의 Oracle/ORDS를 이용한 기능 검사 14건 통과.
큰 한글/보조문자 CLOB 분할 읽기, 빈 CLOB/NULL, 원문 JSON 보존, 중단/재개, 중복, 권한 거부,
커밋 전후 응답 유실, 기존 값 충돌/추가 행, 잘못된 해시/응답을 검사했습니다.
현장 Oracle SQL/ORDS 실행과 실제 전체 건수는 이번 실행 결과로 확인해야 합니다.
원문 한 값의 전송 상한은 64MiB이며 넘으면 원문을 자르지 않고 오류로 남깁니다.
