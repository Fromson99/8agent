Dataiku R6 결과 폴더 S3 404 복구 R1

사진의 실패 지점
01_SUBMIT가 trial-001/intent.json을 01_SUBMIT_OUT 폴더에 쓰는 도중
S3 "Either the bucket does not exist ... or you are not authorized", 404로 실패했습니다.
이 실패 호출에서는 GENOS OPEN·원문 ZIP 업로드 전에 멈췄습니다.
GENOS URL 설정을 바꾸는 작업이 아니라 Dataiku 결과 폴더 저장 설정을 확인하는 작업입니다.

R6 코드에서 확인한 부분
결과 폴더를 생성할 때 연결 이름만 지정했습니다. 새 폴더는 그 연결의 기본 버킷·경로를
받으며, 이미 ZIP을 읽은 원본 폴더의 개별 버킷·경로 설정은 복사하지 않았습니다.
사진의 버킷이 실제로 없는지, 접근 권한이 없는지는 사진만으로 구분할 수 없습니다.
복구 셀은 실제 읽기에 성공한 기존 ZIP 폴더의 버킷·경로를 확인해 세 결과 폴더에 적용하고,
각 결과 폴더에 작은 확인 파일을 쓰고 다시 읽어 성공 여부를 판단합니다.

실행 위치와 방법
1. 사진의 실패 작업이 종료된 상태에서 같은 Dataiku 프로젝트의 새 Python 노트북을 엽니다.
   기존 R6와 같은 공유 WORK_DIR를 보는 실행 환경에서 실행합니다.
2. DATAIKU_R6_S3_FIX_R1.txt 전체를 새 셀 하나에 붙여 넣고 실행합니다.
   별도 폴더 ID 입력이나 코드 ZIP 업로드는 필요 없습니다.
   이미 설치된 LGL_AGENT_R6_PROD 레시피에서 원본·결과 폴더 ID와 WORK_DIR를 읽습니다.
3. 출력에서 원본 ZIP 폴더, 원래 설정 백업 경로, 세 결과 폴더의 읽기/쓰기 확인을 봅니다.
   마지막 R6_S3_REPAIR_COMPLETE가 완료 기준입니다.
4. Scenarios에서 LGL_AGENT_R6_PROD_RUN_ALL을 기존 trial로 다시 실행합니다.
   원래 request.json·핸들·기한을 유지하며 기존 01_SUBMIT부터 이어갑니다.

사용 파일
DATAIKU_R6_S3_FIX_R1.txt                 실제 노트북 실행 셀
DATAIKU_R6_S3_FIX_20261105_R1.zip       동일 repair.py와 결속 manifest, 보관·검토용
GUIDE.txt                              이 안내
VALIDATION.json                        로컬 계약 검사와 현장 미확인 범위
SHA256SUMS.txt                         전달 파일 해시

보존하는 것
GENOS R6 코드 ZIP·배포 리비전·URL·토큰·Oracle 테이블은 변경하지 않습니다.
Dataiku 폴더 ID 3개·레시피·시나리오·예시 ZIP 두 개·WORK_DIR의 요청 기록을 유지합니다.
원래 S3 위치의 객체를 이동하거나 삭제하지 않습니다.
예전 버킷을 읽을 수 없으면 내용은 미확인으로 기록하고, 빈 것으로 간주하지 않습니다.
기존 요청이 GENOS에 이미 OPEN됐거나 읽을 수 있는 기존 결과 폴더에 업무 기록이 있으면
위치를 바꾸지 않고 중단합니다. 새 trial로 바꾸거나 원래 기록을 지우지 않습니다.

중단 후 재개와 원복
복구 중 실패하면 원래 설정과 진행 상태는 WORK_DIR/agent-r6-s3-fix 아래에 남습니다.
원인을 확인한 뒤 같은 셀을 다시 실행하면 이미 바뀐 폴더와 원래 백업을 대조해 이어갑니다.
복구만 원복하려면 같은 TXT 맨 위 MODE를 'ROLLBACK'으로 바꿔 실행합니다.
복구 뒤 실제 파이프라인 기록이 새 위치에 생겼으면 그 기록을 숨기지 않도록 원복을 차단합니다.

계속 오류가 나면
R6_S3_REPAIR_COMPLETE가 없으면 파이프라인을 다시 실행하지 않습니다.
셀의 첫 오류와 "읽기 확인된 ZIP 폴더" 출력, 백업 경로를 확인합니다.
SOURCE_S3_FOLDER_ID_PATH_TEMPLATE_REQUIRED는 원본 폴더 경로가 예상한 폴더별 템플릿과
달라 자동 변경하지 않았다는 뜻입니다. 이 경우 원본 폴더 Settings의 경로를 대조합니다.
저장 설정을 맞춘 뒤에도 S3 쓰기 404/403이 나면 해당 실제 버킷·결과 경로의 접근 설정을
확인해야 합니다. 복구 셀은 버킷을 만들거나 권한을 부여하지 않습니다.

로컬 검사
봉인한 원래 R6 설치 코드를 사용해 기본 버킷 오류를 재현하고, 전달 TXT 전체 실행,
반복·원복·부분 실패 재개·기존 기록·실행 중 작업·중첩 경로·설정 변경 보존을 검사했습니다.
Dataiku/S3 API는 대역이며 현장 S3와 DSS 14.7에서의 복구 성공은 셀 출력으로 확인합니다.
