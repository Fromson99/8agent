결과
Dataiku 전용 R3 클라이언트 ZIP, 전체 실행 TXT, 읽기 전용 진행 조회 TXT를 만들었다.
R2의 체크포인트 identity 코드/원문/기존 저장 위치를 보존하고 재개한다.
GENOS 서버/MAIN/데이터 스키마/원문 generation/기존 R2 전달본은 변경하지 않았다.

원인 증거
사용자 사진의 마지막 반복 SQL hash:
8554f318fb41795771c8910e68d4175713dfdb648d3f4c21ccf1ad7ba85bc5de
봉인 R2의 실버 매핑으로 재구성한 block_payload.SOURCE_JSON 후속 조각 SQL과 일치.
읽기는 최초 1000 UTF-16 단위 뒤에 행·컬럼별로 조각 하나씩 추가 요청하는 구조다.
사진의 PAUSED와 14:32~20:32, 코드의 21600초 제한은 6시간 중단 정황과 일치.
사진만으로 각 전체 단계의 소요시간 비중이나 현장 속도 배수는 확정하지 않았다.

수정
서로 독립된 행·컬럼의 다음 CLOB 조각을 최대32개 UNION ALL로 조회한다.
한 CLOB의 다음 위치는 실제 받은 UTF-16 길이로 계산한다. 전체 본문을 복원한 뒤
기존 compare_batch가 원본과 완전히 대조한다. 원문 대조·권한/판본·NULL/빈값·
누락/중복/길이/크기·원래 예산·잠금·실패·재개 검증을 생략하지 않는다.
새 모듈1, 기존 io와 Dataiku 실행기2, pin2=ZIP의5항목 변경/나머지73항목 보존.
full_package.py 및 oracle_migration.py의 바이트는 R2 그대로다.

검사 중 실패 및 수정
- 최초 패키지 계약/노트북 검사에서 저장소 테스트 helper의 import 경로가 부족했다.
  제품 경계를 유지하며 helper 격리·별도 프로세스로 수정했다. 최초 로그 보존.
- 재개 검사에서 이전 복원용 ZIP 이름과 새 체크포인트 ZIP 이름이 충돌하는
  기존 복구 결함(LOCAL_BLOB_CONFLICT)을 재현했다. 내용 hash를 임시 파일명에
  포함하고 원래 크기/hash 검사를 유지해 수정했다. R2의 이전 파일은 삭제하지 않는다.
- 로컬 Oracle 검사 준비에서 이전 임시 비밀번호 파일 부재, 합성 CLOB 표현,
  SQL*Plus의 줄바꿈/입력 줄 길이 제약을 만났다. 인증정보 변경 없이 로컬 컨테이너
  OS 인증과 읽기 전용 inline fixture로 수정했다. 모든 실패 로그를 보존했다.
- 작업 시작 전 전역 diff --check의 wire_schema.py:99 기존 공백 오류1개는
  병행 파일이라 보존했다. 신규 인계 파일의 공백과 Python3.9 문법은 별도 확인했다.

성과/적용의 한계
측정된 것은 계약·실제 로컬 SQL 호환성이다. 성능 A/B, 전체 이관 시간 비교,
현장 Oracle19/Dataiku 속도, 실데이터 전체 완료, 재배포를 수행하지 않았다.
32는 독립 조각 묶음 상한이다. 한 컬럼만 길게 남는 구간/INSERT/후속 검색 게시/
전체 검증에는 그대로 비용이 남는다. 전체 속도 배수나 남은 시간을 약속하지 않는다.
현장에서는 GUIDE.txt 순서로 R3를 업로드하고 check→load를 실행해야 한다.
명시적으로 CLOB_BATCH_READS=1을 선택하면 같은 R3/기록으로 기존 직렬 읽기를 쓴다.
전체 완료 표시는 FULL_DATA_VERIFIED. 6시간 실행 제한 및 최초 기한은 유지한다.
