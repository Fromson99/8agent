Shift+Enter를 한 번 눌러 실행 대기시킵니다. 여러 번 실행 대기시키지 않습니다.

브라우저/노트북 탭을 열어두는 편이 상태 확인에 좋습니다. 커널은 계속 살아 있어야 합니다.

파일 3개:

- TXT: 생략 없는 후속 셀 전체 코드.
- GUIDE.txt: 이 안내.

2. 자동 진행 순서

A. 같은 R11의 LOADED_UNVERIFIED 결과와 로컬 적재 완료 상태/원문·검색 판본 일치 확인
B. 기존 원문/파일/검색행 전수 대조. 검색행은 최대5000행·기존4MiB 묶음 목표
C. 모두 일치할 때만 원문·검색 COMPLETE 게시 명세 작성
D. 해당 원문에서 기존 방식대로 800자 창/700자 간격의 임베딩 조각 계산
E. 등록 KURE 모델에 최대64개/합계48000자씩 요청, 1024차원 FLOAT32/L2 벡터 영구 저장
F. 전체 개수·본문 좌표·벡터 대조 및 입력 파일 불변 재확인 후 VECTOR_READY

임베딩 대상은 6천만 검색행이 아닙니다. 선택된 원문 블록을 분할한 실제 조각입니다.
제목·본문·좌표·ID는 기존 정식 벡터 생성 방식과 같고, 원문을 잘라 버리지 않습니다.
등록 모델: openai:genos-embedding:embedding-kure-v1
저장: SIDDS.LGL_VCTR_SET_S / SIDDS.LGL_VCTR_ITEM_S (기존 테이블, 새 DDL 없음)
기존 Gold 벡터/활성 포인터는 변경하지 않습니다.

3. 시간 판단

이전 사진의 약2000행/초가 유지된다면 적재 전체는 약8~9시간 수준입니다.
이는 적재만의 추정치이며 검증·임베딩까지 포함한 완료 시간이 아닙니다.
새 사진 없이 현재 남은 시간을 정확히 알 수는 없습니다.

전체 남은 시간 = R11 남은 적재 + 원문/파일/검색 검증 + 조각 계산 + 임베딩/벡터 저장.
검색 전수검증도 약6100만행이므로 분 단위 완료를 보장하지 않습니다.
5000행이 한 묶음에 들어가더라도 검색 대조는 최소약12195회이며,
큰 JSON은 4MiB 기준으로 더 작게 묶이므로 실제 요청 수가 늘어납니다.

VERIFY_QUERY_ROWS: 현재 검증 행수/전체 행수, rows/s, remaining_hours.
EMBEDDING_TOTAL: 실제 임베딩 대상 수와 요청 묶음 수.
EMBED_TIMING: 첫 두 묶음의 SDK/DB 누적 시간과 남은 시간; 이후100묶음마다 보강.
EMBED_AND_STORE: 약60초 간격 진행률/남은 시간.
ETA는 지금까지 관측한 속도가 유지된다는 조건이며 전체 종료 시각 보장이 아닙니다.
원문·파일 검증과 조각 계산 같은 별도 단계 시간도 필요합니다.
현장 KURE 배치 처리시간은 아직 측정되지 않았으므로 임베딩 시간을 임의로 확정하지 않습니다.

로컬 소규모 Oracle 검사는 5000행 전수 대조를 요청1회/약1.75초로 통과했습니다.
현장61백만행·Dataiku/JDBC/서버 부하와 다른 조건이므로 이 시간을 현장 ETA로 쓰지 않습니다.
검색행/벡터 대조의 실제 로컬 실행 계획에서 기본키 INDEX UNIQUE SCAN을 확인했습니다.
현장 Oracle 버전/통계/권한과 장시간 부하는 별도입니다.

4. 성공·실패와 다시 실행

성공 화면: FULL_DATA_VERIFIED → VECTOR_READY → ALL_DONE.
마지막 NFS_FOLLOWUP_RESULT.status는 VERIFIED_AND_VECTOR_READY입니다.
VECTOR_READY는 저장 완료 상태입니다. GENOS 질의 임베딩의 모델/프로필 일치 확인,
검색 경로 연결과 최종 검색 시험은 이후 단계이며 서비스 활성화를 자동 변경하지 않습니다.
등록 모델 ID만으로 실제 모델 가중치 버전까지 확인된 것은 아닙니다.

R11 실패/미완료·판본 불일치면 후속은 시작하지 않습니다.
Jupyter가 앞 셀 오류 후 대기 셀을 취소할 수도 있습니다. 성공한 척 진행하지 않습니다.
검증에서 누락/내용변경/여분 행이 나오면 COMPLETE/임베딩으로 넘어가지 않습니다.
모델 오류/차원 오류/180초 응답불명은 자동 재전송 없이 중단합니다.
SDK 내부 재시도는 관찰할 수 없으므로 여기서 말하는 호출 수는 SDK execute 기준입니다.

벡터 응답을 받은 뒤 저장 응답만 유실된 경우에는 캐시와 DB 영수증으로 재개할 수 있습니다.
모델 응답 자체가 불명확하고 캐시가 없으면 EMBEDDING_UNKNOWN_NO_REPLAY로 차단합니다.
기록/캐시를 지우거나 새 작업으로 바꿔 우회하지 말고 STOPPED 화면을 먼저 확인합니다.
재개에는 기존 임시 폴더·원문·영수증이 필요합니다. 검증을 다시 수행할 수 있어 즉시 재개를
보장하지 않습니다. 완료한 벡터 구간은 동일 체인을 확인하며 다시 임베딩하지 않습니다.
기존 원문 적재의 기한/SQL 예산을 초기화하지 않습니다.
벡터 작업은 원래7일/SDK20000회/SQL1000000회 한도를 유지하며 자동 확대하지 않습니다.
입력 수가 이 호출 한도를 넘으면 모델 호출 전에 멈춥니다.

5. 로그와 확인 범위

화면은 최근14줄만 표시하며 원문/전체 벡터/긴 traceback을 출력하지 않습니다.
처음 표시한 전체 진단 파일 경로에 원래 출력이 남습니다.
실패 시 마지막 STOPPED 사유와 FAILURE_LOG 경로를 포함해 캡처합니다.
실행 파일은 새 Python 프로세스에서 로드하므로 R11이 쓰던 모듈을 재로딩하지 않습니다.
Dataiku 커널의 동일 Python 실행환경/환경변수/모듈 경로를 자식 프로세스로 전달합니다.
현장 자식 프로세스에서 DSS 인증이 상속되지 않으면 중단하며 우회하지 않습니다.

로컬 검사: 실제 Oracle23.26.3 격리 스키마, 합성 본문, 모의 Mesh로15개 계약 통과.
전달 ZIP/TXT 검사: R11 적재 완료→7종 손상 차단→검증 성공→벡터 단계 연결 통과.
전달 시험의 SQL/프로세스 경계는 모의이며, 벡터 저장·응답유실·UNKNOWN은 별도 실제 Oracle 검사.
실제 현장 Dataiku/GENOS 모델 호출, 전체 자료 검증, 서비스 검색 연결은 아직 실행하지 않았습니다.
MAIN/현장 실행 중 R11/기존 원문·Gold 내용은 이번 준비에서 변경하지 않았습니다.
