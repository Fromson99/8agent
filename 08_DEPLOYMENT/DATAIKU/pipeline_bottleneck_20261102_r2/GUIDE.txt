첫 셀이 측정하는 것
- 전체 검색 종류의 정확한 준비계획 행 수와 세 제외 후보 합계.
- SQLite 일반 표/VIEW 앞32행의 읽기+JSON 시간, 평균/최대 JSON bytes, gzip 시간/크기,
  EXPLAIN QUERY PLAN. 원문 저장표도 확인한다. 전체 행 COUNT/전체 FTS 정렬은 하지 않는다.
  표별 최대2초/전체90초. 제한에 걸리거나 파생 FTS인 항목은 미측정으로 남긴다.
- 기존 fresh1 로그 최대3파일/각4MiB의 관측 구간 속도. 하트비트 중복을 배치로 세지 않는다.
  과거 로그와 현재 세대의 결속은 미확인이므로 현재 실행 수치에 합산하지 않는다.
- AIDP 왕복3회, 17표의 통계·인덱스·LOB정보, 허용되면 현재 로그인 대상 V$SQL 상위8개.
  통계 행 수는 오래됐을 수 있고 V$SQL은 커서 수명 누계이지 이번 실행 전용 수치가 아니다.
- DOC_VER/DOC_UNIT/DOC_BLK와 큰 검색 종류5개 및 실제 적재된 검색 종류1개의 작은 시험.
  아직 해당 검색 종류가 DB에 없으면 NO_LOADED_SAMPLE로 표시한다. 빈 표를 느리다고 판정하지 않는다.

INSERT 시험 방식
RUN_INSERT_PROBES=True가 기본이다. 사용자의 작은 INSERT 시험 요청을 반영했다.
현재 저장된 앞32행의 본문을 표본으로 쓰고, 다른 진단 전용 release/PK를 만든다.
100 → 500 → 최대2000행 순차, payload가2MiB를 넘으면 실제 행 수를 줄인다.
반복 표본이므로 전체 본문 분포·키 분포·실제 COMMIT 처리량을 대표하지 않는다.
실제 적재기의 Contract.batch SQL/검증 조건과 JDBC gzip/hex 전송을 사용하되
SQL 내부 COMMIT을 제거하고 반드시 ROLLBACK한다. 임시 표/인덱스/DDL을 만들지 않는다.
DB 내부 INSERT/내용검증/ROLLBACK 시간을0.01초 단위로 나누고,
Python 준비/압축·SQL생성/전체 요청 시간 및 payload/SQL바이트를 따로 기록한다.
정상 시험은 ROLLBACK 뒤 ORA-20084 전용 영수증으로 시간을 전달하며 프로그램이 정상 처리한다.
이어 같은 진단 release 행 수0을 확인한 경우에만 ROLLED_BACK_VERIFIED로 표시한다.
실제 오류·행 잔존·공간/권한 오류가 나면 후속 INSERT 시험을 중지한다. 자동 삭제/재시도는 없다.
순수 읽기만 원하면 RUN_INSERT_PROBES=False로 바꾼다.
기존 적재 job.lock을 같은 방식으로 사용한다. WRITE_UNCONFIRMED/FAILED 기록 자체를
실행 중인 writer로 취급하지 않는다. 다른 writer가 실제로 살아 있어 잠금을 점유한 경우만 구분한다.
원래 WRITE_UNCONFIRMED/pending은 이 진단으로 해소하거나 성공 처리하지 않는다.

시간 제한과 결과 불명
Oracle 단계는 전체210초, 개별 호출 관측30초를 넘으면 진단 자식 프로세스를 종료한다.
이는 Oracle 서버 작업의 취소 완료를 증명하지 않는다. 타임아웃이면 OUTCOME_UNCONFIRMED로
남기고 추가 시험하지 않는다. 해당 probe_release가 JSON에 남으므로 결과 확인에 사용할 수 있다.
롤백 시험도 일시적인 UNDO/REDO/I/O와 공간을 사용한다. 실제 대량 적재 성공 보장은 아니다.

적재를 실제로 재개할 때 쓸 두 번째 셀
02_PROFILE_EXISTING_STAGE_RUN_R2.txt는 첫 진단과 달리 기존 실제 단계를 실행한다.
기본 PROFILE_STAGE=''는 실행하지 않는다. 준비가 끝나 실제 재개할 때 한 개를 선택한다.
  PROFILE_STAGE = 'load'            # 실제 적재 재개·계측
  PROFILE_STAGE = 'verify_publish'  # 실제 전체검증·게시 단계
  PROFILE_STAGE = 'vector'          # 실제 임베딩 호출·벡터 저장 (사용량 발생)
각 단계는 자동으로 다음 단계로 넘어가지 않는다. 별도 정상화되지 않은 pending은 원래
적재기의 동일 검증/재개 규칙에 따라 중단될 수 있다. 상태 삭제/강제 retry_missing은 하지 않는다.
동일 ZIP, 같은 노트북·OLD_JOB_DIR/STATE_DIR/PACKAGE_DIR을 사용한다.
입력해시/원문 읽기/검색행 생성/배치 구성/SQL준비/압축전송/DB요청/체크포인트/
임베딩 호출/벡터 SQL 구성/게시 시간을 실제 경로에서 계측한다.
계측 함수는 원래 함수의 인수·반환·예외를 그대로 전달하고 제품 파일·해시를 바꾸지 않는다.
화면은 한 카드로 갱신되며 원래 로그는 original-stage.log에 보존한다.
DB요청 시간은 왕복·파싱·실행을 포함한다. 진단만으로 모든 내부 대기 원인을 분리하지 않는다.
포함 시간은 부모/자식이 겹치므로 더하지 않는다. 자체(exclusive) 시간만 합산한다.
측정 자체의 비용은 제거되지 않았다. 이 결과만으로 개선율이나 새 파이프라인 품질을 인증하지 않는다.

결과 보관과 전달
현재 노트북 작업 폴더의 gold-bottleneck-reports/<시각-고유값>/REPORT.json에 전체 수치가 남는다.
원문 내용·전체 SQL값·임베딩 입력/벡터·비밀번호는 진단 보고서에 넣지 않는다.
worker-config.json은 같은 실행의 경로/명세/상태 결속 자료이며 원문 DB 자체는 아니다.
우선 요약/삽입/자료 화면을 캡처하면 된다. 추가 분석에는 REPORT.json 전체를 사용한다.
0행/미측정/권한거절/시간한도/실패를 구분한다. 화면에 없는 항목은 JSON에 보존한다.

중단과 복구
01 셀 중단/타임아웃 후 기존 적재 state/pending은 그대로 둔다. 결과 불명 INSERT는 자동 반복하지 않는다.
02 셀을 중단하면 원래 적재기의 미확정 상태가 남을 수 있다. 기존 재개/대조 규칙을 따른다.
이 진단은 행 축소·원문 재적재·인덱스 변경·공간 확장·서비스 전환을 수행하지 않는다.
