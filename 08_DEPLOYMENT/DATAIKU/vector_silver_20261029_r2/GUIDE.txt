대상과 컬럼 수
이번 신규 생성은 SIDDS.LGL_VCTR_PBLS_S(5), LGL_VCTR_SEG_S(6), LGL_VCTR_ACT_S(3): 3테이블 14컬럼.
기존 원문·검색 실버는 8테이블 41컬럼. 합계 실버 11테이블 55컬럼.
SIDDA.LGL_EXEC_ST_A(5컬럼)는 별도 Agent. 전체 정의목록은 12테이블 60컬럼.
위 숫자는 현재 코드 계약의 수이며 현장 DB 생성 여부를 조회한 값은 아니다.
1024차원 임베딩은 VECTOR 한 컬럼이다. JSON 내부 속성도 추가 물리 컬럼으로 세지 않는다.

먼저 할 일
1. 00_CHECK_TARGET.sql을 대상 Oracle 연결에서 실행해 DB 식별과 VECTOR/COSINE 지원을 확인한다.
2. 01_CREATE_VECTOR_SILVER.sql을 SQL Developer/SQLcl의 스크립트 실행으로 실행한다.
   / 는 클라이언트 구분자다. ORDS SQL로 실행하면 /를 보내지 않고 BEGIN..END; 블록 단위로 보낸다.
   기존 객체가 있으면 생성 오류 -955만 건너뛰며, 컬럼·제약이 다르면 후속 check가 거절한다.
   이전 18컬럼 벡터 테이블이 이미 있으면 비어 있을 때만 03_COMPACT_EMPTY_VECTOR_TABLES.sql을 사용한다. 데이터가 있으면 중단하며 자동 이관/삭제하지 않는다.
   기존 원문 테이블을 DROP/TRUNCATE/재생성하지 않는다. SIDDS 스키마 자체를 새로 만드는 SQL이 아니다.
   CREATE TABLE/인덱스·테이블스페이스 quota, 해당 테이블 SELECT/INSERT/UPDATE 권한이 필요하다.
   다른 계정에서 SIDDS 생성 권한이 없다면 DBA에게 이 SQL을 전달한다.
3. 02_CHECK_VECTOR.sql로 14컬럼과 PK/FK/색인을 확인한다.
   Python schema 모드는 동일 DDL을 실행하고 더 엄격한 컬럼·제약 검사를 수행하는 대안이다.

Dataiku Flow 설치 (설치만으로 DB나 모델을 실행하지 않는다)
4. VECTOR_SILVER_CODE_20261029_R2.zip 하나를 LEGAL_RAG의 ehA8dpVm 폴더 루트에 업로드한다.
   DATAIKU_INSTALL.txt를 Python 노트북 한 셀로 실행한다. Python 3.11+와 requirements.txt의 라이브러리가 필요하다.
   임베딩 정보가 아직 없으면 EMBED_* 공란으로 설치할 수 있다. 실행 전 실제 정보를 채워야 한다.
   기존 Flow의 LEGAL_03_LOAD_SILVER_R1 출력인 LEGAL_LGL_LOAD_RESULT_R1을 자동 확인한다.
   새 LEGAL_04_VECTOR_SILVER_R3와 S3 결과 폴더 LEGAL_VECTOR_SILVER_RESULT_R3를 추가한다.
   연결선: ehA8dpVm(코드) + 03 실버 적재 결과 -> 04 벡터 적재 -> 벡터 결과.
   실제 DB 쓰기는 기존 AIDP 연결의 SQLExecutor2/JDBC로 수행한다.
   네이티브 VECTOR 열을 DSS 문자열 쓰기 데이터셋으로 만들어 대체하지 않는다.
   기존 00~03 레시피와 기존 테이블/데이터셋은 변경하지 않는다.
5. 기존 프로젝트 보안 변수 GENOS_EMBED_KEY와 접속 변수 GENOS_BASE_URL, GENOS_EMBED_SERVING_ID를 설정한다.
   직접 임베딩 URL 환경은 GENOS_EMBED_URL 하나를 사용하며 BASE_URL+ID와 동시에 설정하지 않는다.
   모델명·불변 배포 revision/가중치 SHA256·실제 차원을 확인한 후 설치 셀의 EMBED_MODEL/REVISION/DIMENSIONS를 채운다.
   예시 차원 1024만으로 KURE/BGE를 추정하지 않는다. Dataiku 구축과 GENOS 질문 임베딩은 동일 모델/가중치여야 한다.
   새 커널에서 설치 셀을 다시 실행한다. 다른 revision의 Python 모듈이 이미 로드된 커널에서는 섞지 않고 거절한다.
   모델 프로필 LEGAL_VECTOR_PROFILE은 비밀값이 없으며 코드가 생성한다. 기존 다른 프로필은 자동 덮어쓰지 않는다.

테이블 이관 완료 후 실행
6. 기존 03 적재가 jobs/<job>/complete.json을 남겼는지 확인한다.
   status=COMPLETE, oracle_written=true, target=SIDDS.*_S, source_release_id/query_release_id가 있어야 한다.
   파일 복사나 테이블 일부 이관만으로 실행하지 않는다. 원문/조회 COMPLETE 릴리스와 source.integrity까지 필요하다.
   완료 기록이 여러 개면 LEGAL_VECTOR_LOAD_RECEIPT 또는 설치 셀 LOAD_RECEIPT_PATH에 정확한 경로를 지정한다.
   최신 파일 시각이나 main 채널로 임의 선택하지 않는다. 선택한 기록과 Oracle 원문/조회 manifest를 대조한다.
7. 설치와 같은 노트북의 새 셀에서 DATAIKU_RUN.txt ACTION="check" 실행. 임베딩 호출0·SQL 읽기 검사다.
   SQL을 따로 실행하지 않았다면 ACTION="schema"를 먼저 실행할 수 있다(신규 벡터 3테이블만 생성).
8. Flow 새로고침 -> LEGAL_04_VECTOR_SILVER_R3 -> Run(이 레시피만 실행).
   전체 상류 강제 rebuild를 선택하면 01~03까지 재실행될 수 있으므로 완료된 이관을 다시 돌리지 않는다.
   source 블록을 800자/100자 겹침으로 나누고 16개씩 내부 GENOS /embeddings를 호출한다.
   기존행 묶음조회, 최대 60,000 UTF-8바이트의 묶음 INSERT/COMMIT, 적재 후 메타/차원 읽기 대조를 수행한다.
   원문·문서 권한·분할·모델/판본 계약은 기존 MAIN116/117과 동일하다(물리 스키마/소비자만 변경). ANN 검색 색인 추가는 이번 범위가 아니다.
9. 결과 폴더 /vector/<work_key>/build-state.json에서 READY, publication_id, query_release_id, count 확인.
   02_CHECK_VECTOR.sql에서 READY와 stored 건수를 조회해 Dataiku 결과 count와 대조하고 FLOAT32·MANIFEST_JSON.profile 차원을 확인한다.
   /vector/<work_key>/sql-*.jsonl 및 timing-*.json으로 SQL/임베딩/상태저장 시간을 확인한다.
   sql_seconds 안에 호출예약 상태 업로드 시간이 포함되므로 숫자를 단순 합산하지 않는다.

기존 GENOS RAG에서 사용
10. 현재 GENOS 배포본에 MAIN112 이후 Oracle 조회 경로가 있어야 하며, 동봉 14컬럼 조회 패치를 먼저 적용해야 한다.
    GENOS_COMPACT_PATCH_20261029_R2.zip과 GENOS_COMPACT_APPLY.txt가 필요한 두 코드 파일과 엔진 pin만 변경한다.
    기존 DP=oracle 환경에서 GENOS_RAG_INITIAL_SEARCH=vector와 같은 임베딩 접속값을 설정한다.
    GENOS가 선택하는 query release를 READY 결과의 query_release_id와 일치시킨다.
    이 레시피는 해당 query release의 벡터 활성 포인터만 게시한다. 원문 조회채널은 바꾸지 않는다.
    실제 워크플로우 테스트에서 초기후보 -> 원문 READ -> 답변을 확인한다. HEALTH만으로 연동 완료로 판단하지 않는다.

실패·재개·기존 R1
- 같은 04 레시피를 다시 Run하면 동일 게시본에서 완료된 구역은 검증 후 재사용한다. READY 재실행은 임베딩0회.
- SQL 호출은 128회씩 먼저 예산을 보관한다. 비정상 종료 뒤 미사용 예약분도 보수적으로 사용량에 포함한다.
  임베딩은 매 요청 전 예약한다. 재개해도 총 SQL100만/임베딩2만/최초7일 기한을 초기화하지 않는다.
- 이전 LEGAL_VECTOR_SILVER_RESULT_R2 또는 LEGAL_VECTOR_RESULT_R1 폴더가 설치되어 있으면 같은 work_key의 상태·기한·예산을 읽어 이어간다.
  기존 R1/R2와 새 R3 벡터 레시피를 동시에 실행하지 않는다. 새 설정으로 예산을 회피하려고 기존 상태를 삭제하지 않는다.
- 정상 실패는 잠금을 해제한다. 강제 종료 뒤 LEASE_ID가 남으면 Dataiku에서 이전 작업 종료를 확인한 뒤
  해당 PUB_ID/LEASE_ID 하나만 운영자가 해제한다. 모든 게시본의 잠금을 일괄 지우지 않는다.
  UPDATE SIDDS.LGL_VCTR_PBLS_S SET LEASE_ID=NULL
   WHERE PUB_ID=:publication_id AND LEASE_ID=:old_lease AND STATUS='BUILDING'; COMMIT;
- 실패 중간 게시본은 BUILDING을 유지한다. 활성 전환 전에는 기존 READY가 계속 선택된다.
- 기존 게시본은 삭제하지 않는다. 롤백은 저장된 previous.PUB_ID를 동일 QUERY_ID의 READY인지 확인한 뒤
  LGL_VCTR_ACT_S의 현재 REVISION 조건으로 교체한다. 첫 게시의 previous가 없으면 keyword 설정으로 복귀한다.
- 상태/S3 저장 실패를 무시하고 계속 처리하지 않는다. 보관 기록을 보존하고 원인을 확인한다.

14컬럼 축소 내용
- PROFILE_JSON: MANIFEST_JSON.profile에 이미 같은 설정이 있어 중복 컬럼 제거.
- INPUT_HASH: META_JSON.input_sha256에 이미 같은 값이 있어 중복 컬럼 제거.
- EXPECTED_COUNT/ACTUAL_COUNT: 완료 시 원문 구역 수와 실제 COUNT(*)를 대조하는 검사는 유지. 결과 count는 Dataiku에 보관.
- DOC_ID/SOURCE_ID: 권한 선필터·조항별 그룹 정렬에 직접 필요하므로 유지.
- STATUS/LEASE_ID/REVISION: 불완전 게시 차단·동시 적재 방지·활성 버전 교체 충돌 방지를 위해 유지.
- 컬럼만 JSON으로 숨기는 추가 포장은 하지 않았다. 기존 JSON 안의 중복 사본을 제거했다.

GENOS 조회 코드 반입
현재 TRANSFER에서 아래를 실행한다. 코드를 적용할 대상만 실제 Git checkout인 ~/DEV로 지정한다.
bash ./GENOS_COMPACT_APPLY.txt check ~/DEV
bash ./GENOS_COMPACT_APPLY.txt apply ~/DEV
알려진 이전 두 모듈 해시와 현재 엔진/파이프라인 pin을 검사하고, 기존 파일 백업 후 변경한다.
CODE_BYTES_AND_PINS_VERIFIED는 코드 반입 결과다. 실제 checkout에서 git diff --check, diff 검토, commit/push 후
그 commit으로 코드서빙 리비전을 배포하고 query_release_id/임베딩 설정/배포리비전을 기록한다.
새 Reader는 기존 18컬럼 테이블도 읽을 수 있으므로 조회코드를 먼저 배포한 뒤 새 14컬럼 테이블/적재기를 사용한다.
이 경로는 Oracle 게시 릴리스를 사용한다. NFS generation 전체 복원 검사를 Oracle 연결 성공의 대체 증거로 쓰지 않는다.
실제 워크플로우에서 질문→벡터후보→원문 READ→답변을 확인하며 내부망 실행은 이 전달본에서 미수행이다.
코드 롤백은 vector-compact-backup-*의 RECEIPT.json/before 파일과 SHA256을 확인한 뒤 원래 경로에 복원한다.
14컬럼 상태에서 구버전 18컬럼 전용 Reader를 배포하면 실패하므로 DB/코드 호환을 함께 유지한다.
