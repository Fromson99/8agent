Oracle 개발계 ZIP 기준 재적재 / CLEAN R1 / 2026-10-20

이번 묶음은 기존 데이터 7개 테이블을 비우고 ZIP에 선택된 generation을 처음부터 적재합니다.
ACTIVE와 STATE는 삭제·수정하지 않습니다. ACTIVE가 사용 중이면 삭제 전에 차단합니다.
테이블·PK·FK·JSON 제약은 유지합니다. DROP/TRUNCATE/제약 비활성화는 하지 않습니다.
기존 R4 코드 ZIP, 복원 데이터, 실패/진행 기록은 보존합니다.
R4의 publish 셀과 새 replace/resume 셀을 동시에 실행하지 마세요.

1. 파일과 실행 위치
- LEGAL_ORACLE_CLEAN_IMPORT_20261020_R1.zip:
  기존 Dataiku Managed Folder LEGAL_DATA_ZIP_IMPORT 최상위에 업로드합니다.
  ZIP을 수동으로 풀 필요는 없습니다. 아래 실행 TXT가 고정 해시를 확인하고 읽습니다.
- DATAIKU_CLEAN_IMPORT_RUN.txt:
  별도 새 Dataiku Python 노트북에 전체를 붙여 실행합니다. SQL/Bash용이 아닙니다.
  기존 이관 노트북에서 커널을 먼저 재시작할 필요는 없습니다.
- STOP_OLD_IMPORT_RUN.txt:
  별도 새 Python 노트북에서 사용할 독립 종료 코드입니다. 코드 ZIP 없이도 실행됩니다.
- LOG_CLEAN_RUN.txt:
  별도 로그 조회 노트북에서 새 이관 상태를 10초마다 조회합니다.

데이터 ZIP/분할 파일은 다시 업로드하거나 병합할 필요가 없습니다.
기존 legal-existing-zip-r2-work/restored의 검증된 복원본을 재사용합니다.
데이터 파일이 삭제·변경됐으면 실행 전에 중단합니다.
예전 전체 ZIP에서 명시된 선택 generation의 원문·자산·조회 데이터가 대상이며,
ZIP의 다른 runtime/과거 generation/상태 이력까지 가져오는 뜻은 아닙니다.

2. 기존 프로세스 확인과 종료
STOP_OLD_IMPORT_RUN.txt에서:
  ACTION = "inspect"
로 실행합니다.
LOCAL_IMPORT_RUNNING이면 같은 TXT의 ACTION만 "stop"으로 바꾸고 실행합니다.
LOCAL_IMPORT_LOCKS_FREE이면 로컬 이관 잠금은 해제된 상태입니다.
종료 대상은 지정 작업 폴더의 잠금을 실제로 보유한, 같은 사용자의 ipykernel 프로세스뿐입니다.
TERM 후 5초 내 종료되지 않으면 PID 재사용 방지 핸들로 KILL을 보냅니다.
다른 Python 프로세스/다른 노트북/Oracle 세션을 일괄 종료하지 않습니다.
LOCK 소유 PID가 보이지 않거나 권한·pidfd 지원이 없으면 임의 PID 추정 없이 중단합니다.
노트북 서버가 종료된 커널을 자동 재생성할 수 있습니다. 기존 이관 셀을 다시 실행하지 마세요.

자동 경로 선택은 정확히 한 작업 폴더일 때만 동작합니다.
여러 개 또는 0개이면 WORK_DIR에 이전 로그에 나온 legal-existing-zip-r2-work 절대경로를 입력합니다.
GENOS 코드스페이스와 Dataiku 서버의 파일 경로는 다릅니다.

3. 적재 계획
새 적재 노트북의 DATAIKU_CLEAN_IMPORT_RUN.txt 설정:
  FOLDER_ID = "LEGAL_DATA_ZIP_IMPORT"
  ORACLE_CONNECTION = "AIDP"
  WORK_DIR = ""          # 자동 탐색 불가하면 확인된 기존 절대경로
  ACTION = "plan"

처음 plan에서는 ZIP 복원본 해시·스키마를 확인하고 로컬 원본에서 적재 건수와 조회 행을 계산합니다.
이 단계는 Oracle 기존 본문을 내려받아 대조하지 않으며 데이터 삭제·삽입도 하지 않습니다.
로컬 조회 데이터 생성 자체에는 시간이 걸릴 수 있습니다. PLAN_SOURCE/PLAN_QUERY 로그를 확인하세요.

CLEAN_PLAN_READY에서 before_counts / after_counts / delete_tables를 확인합니다.
삭제 대상(각 테이블의 기존 모든 버전):
  SIDDA.LEGAL_SRC_DOCUMENT_A
  SIDDA.LEGAL_SRC_SOURCE_UNIT_A
  SIDDA.LEGAL_SRC_BLOCK_PAYLOAD_A
  SIDDA.LEGAL_RAG_ASSET_PART_A
  SIDDA.LEGAL_RAG_RELEASE_A
  SIDDA.LEGAL_RAG_QUERY_ROW_A
  SIDDA.LEGAL_RAG_QUERY_RELEASE_A
보존:
  SIDDA.LEGAL_RAG_QUERY_ACTIVE_A
  SIDDA.LEGAL_RAG_QUERY_STATE_A
위 목록 밖의 테이블을 삭제하는 코드는 없습니다.

ACTIVE_IN_USE_NO_CHANGES이면 현재 활성 버전이 있습니다.
ACTIVE/STATE 값을 지우거나 이 오류를 우회하지 마세요.
표시된 active 목록을 바탕으로 기존 서비스 버전의 처리 방법을 별도로 정해야 합니다.
기존 연결 지문과 다른 Oracle 연결, 외부 참조 FK, 활성 트리거 등도 삭제 전에 차단합니다.

4. 삭제 후 새로 적재
계획 확인 후 같은 새 노트북에서:
  ACTION = "replace"
로 실행합니다.
활성 포인터가 비어 있는지 다시 검사하고, 7테이블을 잠근 뒤 한 트랜잭션으로 DELETE합니다.
DB 잠금이 바쁘면 NOWAIT로 실패합니다. 해당 오류를 숨기거나 자동 재시도하지 않습니다.
삭제 커밋 후에는 기존 DB 내용을 자동 복구하지 않습니다. 원본 ZIP으로 재적재하는 절차입니다.
DELETE 자체는 기존 데이터 크기와 Oracle undo/redo 환경에 따라 시간이 걸릴 수 있습니다.

정상 적재:
- 최대 100행 또는 약 512KiB 묶음. 큰 단일 행은 최대 8MiB에서 별도 묶음으로 처리합니다.
- 기존 행 중복 조회, 긴 본문 조각 다운로드, 전체 본문 반복 대조를 하지 않습니다.
- 원문 → 자산 조각 → 조회 행 → 최종 건수 → 릴리스 메타데이터 순서입니다.
- 문자 ID, 앞자리 0, NULL/빈 CLOB 구분과 기존 데이터 형식을 유지합니다.
- PK/JSON/타입/길이/SQL 오류는 묶음 롤백 및 상태 기록 후 중단합니다. 오류 행을 건너뛰지 않습니다.
- 처리 계획은 별도 plan.json, 작은 진행 기록은 state.json에 저장합니다.

5. 중단·재개
삭제 완료 이후 적재가 멈췄다면 기존 WORK_DIR와 같은 코드로:
  ACTION = "resume"
을 실행합니다. 완료된 삭제를 다시 수행하지 않습니다.
replace를 재실행해도 삭제 완료 기록이 있으면 재개로 동작합니다.
로컬 입력에서 완료된 접두 행을 재생성해 체크포인트 해시를 확인하고 이후 행부터 적재합니다.
정상 커밋 응답이 유실된 마지막 묶음만 Oracle에서 존재 여부와 전체 값을 확인해 중복을 막습니다.
한 묶음의 일부만 있거나 값이 다르면 덮어쓰지 않고 중단합니다.
1회 최대 6시간, 새 재적재 작업 최초 7일 및 누적 SQL 호출 한도를 보존합니다.

중요한 별도 오류:
- OLD_WRITE_UNCONFIRMED:
  이전 이관의 쓰기 종료 여부가 불명확합니다. 프로세스 종료만으로 Oracle 종료를 단정하지 않습니다.
  Dataiku/Oracle 쪽의 해당 요청 완료·취소를 확인해야 하며 새 삭제는 차단합니다.
- CLEAN_RESET_UNCONFIRMED:
  DELETE의 커밋 응답이 유실됐습니다. 같은 DELETE를 자동 반복하지 않습니다.
  기존 Dataiku/Oracle 트랜잭션이 끝났는지 확인해야 합니다. state.json을 지워 우회하지 마세요.
- IN_PROGRESS / OLD_IMPORT_RUNNING:
  해당 작업이 잠금을 보유하고 있습니다. 종료 코드로 확인합니다.

6. 완료와 조회
완료 상태: CLEAN_LOAD_COUNTS_CONFIRMED
이 상태는 성공한 INSERT, 테이블/조회 종류별 건수, 입력 해시와 릴리스 메타데이터 확인 결과입니다.
full_body_readback=false: Oracle 본문 전체를 다시 다운로드해 대조한 결과는 아닙니다.
ACTIVE 전환과 서빙 배포는 수행하지 않습니다. STATE도 그대로 둡니다.
보조 인덱스 4개는 누락 시 적재를 허용하되 운영 조회 전에 준비해야 합니다.

로그 위치:
  <기존 WORK_DIR>/oracle-clean-r1/events.jsonl
  <기존 WORK_DIR>/oracle-clean-r1/calls.jsonl
  <기존 WORK_DIR>/oracle-clean-r1/state.json
  <기존 WORK_DIR>/oracle-clean-r1/plan.json
BATCH_COMMITTED의 rows/total은 해당 단계의 실제 커밋 진행량입니다.
PROGRESS는 주기적 상태이고, 시간 증가만으로 처리 완료를 판단하지 않습니다.
LOG_CLEAN_RUN.txt의 WATCH=True는 10초 갱신, False는 한 번 조회입니다.
로그 조회 노트북의 ■ 버튼은 조회만 종료합니다.

7. 검증 범위
첨부 VALIDATION.json에 로컬 검사와 실제 현장 미확인 항목을 구분합니다.
망분리 Dataiku/Oracle에 접속해 실행한 결과가 아닙니다.
현장의 전체 소요 시간이나 배속을 사전 확정하지 않습니다.
