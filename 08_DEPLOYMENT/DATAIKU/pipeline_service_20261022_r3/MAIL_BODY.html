Dataiku에서 발생한 오류번호 36 / File name too long 수정본입니다.

이전 Dataiku 실행 R2 대신 첨부한 R3 TXT를 사용하세요. GENOS 파이프라인 전용 서비스는 R1 대신 첨부한 서비스 R2를 사용합니다. Dataiku 관리 폴더에 올려 둔 DATAIKU_PIPELINE_CLIENT_20261022_R1.zip은 그대로 유지합니다.

기존 코드가 긴 원문 파일명에 임시 식별자·해시를 추가하면서 길이 제한을 넘는 문제를 로컬에서 재현해 수정했습니다. 원문 이름·내용·해시·매핑을 보존하며, NFS 설정은 변경하지 않습니다.

지금 Dataiku에서 실행

  1. LEGAL_PIPELINE_WORKSPACE의 기존 파일 5개를 그대로 둡니다. 같은 작업 경로의 다운로드 파일을 해시 확인 후 재사용하므로 데이터를 다시 올릴 필요 없습니다.
  2. 진단은 끝났으므로 노트북 커널을 한 번 재시작합니다.
  3. LEGAL_RAG 프로젝트의 노트북 새 셀에 DATAIKU_PIPELINE_RUN_20261022_R3.txt 전체를 붙여넣고 아래 값으로 실행합니다. TXT는 Python 코드이며 bash로 실행하는 파일이 아닙니다.
ACTION = "prepare"
FOLDER_NAME = "LEGAL_PIPELINE_WORKSPACE"
WORK_DIR = "./legal_pipeline_work"
JOB_NAME = "run_20261022_01"

WORK_DIR는 이전 값 그대로 유지하고, 처음 출력되는 절대경로가 이전 로그와 같은지 확인하세요. 마지막 READY가 나오면 복원·준비가 완료된 것입니다. prepare 단계에서는 GENOS나 Oracle을 호출하지 않습니다.

GENOS 실행 전

GENOS에서도 같은 복원 코드와 원문 보관 코드를 사용하므로 GENOS_PIPELINE_SERVICE_20261022_R2.zip을 파이프라인 전용 코드서빙 저장소에 적용·배포해야 합니다. 기존 RAG의 DEV/service.py에 덮어쓰는 작업이 아닙니다.

실제 첨부 ZIP을 올린 TRANSFER 폴더를 현재 위치로 두고 압축을 풉니다.

python3 -m zipfile -e ./GENOS_PIPELINE_SERVICE_20261022_R2.zip ./

적용 파일·백업·커밋·검증·배포 절차는 첨부 GUIDE.txt의 2번을 따르세요. 실행 TXT도 별도로 첨부했습니다. 아래 경로는 실제 파이프라인 전용 Git checkout 절대경로로 바꿉니다.

bash ./GENOS_PIPELINE_SERVICE_20261022_R2/GENOS_PIPELINE_CHECK.txt /실제/파이프라인전용/Git체크아웃

새 서비스 R2 배포 후 프로젝트 변수 LEGAL_PIPELINE_URL, LEGAL_PIPELINE_TOKEN, LEGAL_ORACLE_CONNECTION(AIDP)을 확인하고 Dataiku 셀의 ACTION을 "run"으로 바꿉니다. 구 서비스 R1이면 코드 해시 불일치로 중단합니다. 해시를 임의로 바꿔 우회하지 마세요.

이번 사진처럼 prepare에서만 실패했다면 JOB_NAME은 그대로 사용합니다. 이미 GENOS를 시작해 client.json이 생성된 다른 작업은 기존 기록을 보존하고 새 JOB_NAME으로 실행하세요.
