Python/Jupyter 셀용이 아닙니다. 서버 경로 설정이나 관리 폴더 업로드는 필요 없습니다.

Q1과 Q2를 각각 별도 SQL 셀에서 실행합니다.
- Q1: 우리 적재기의 대상 이름으로 제한한 테이블 목록·생성 시각·마지막 행수 통계.
- Q2: 같은 대상의 테이블/인덱스/LOB 물리 할당량. DBA_SEGMENTS 조회 권한이 필요합니다.
각 결과는 최대11행이며, 오류가 발생하면 해당 Q 번호와 오류 코드만 캡처합니다.
모두 읽기 전용 SELECT입니다. 실데이터 전체 COUNT나 통계 갱신은 하지 않습니다.

현재 확인 대상
R11의 SIDDS 원문·검색·파일 보관8개, SIDDA 실행 상태1개, 후속 벡터2개입니다.
확정 Gold R19의13표로 전환하거나 새 테이블을 생성하는 코드가 아닙니다.
기존 개발계 대상에서 지금 보이는 현황을 확인합니다.

반드시 구분할 것
1. STATS_ROWS는 마지막 통계 시점의 값입니다. 현재 행 수나 이번 실행 적재 수가 아닙니다.
   NULL은 0이 아닙니다. 대량 적재 후 통계가 오래됐을 수 있습니다.
2. ALLOCATED_GIB는 GiB 단위의 물리 할당량입니다. 테이블 본체뿐 아니라 일반 인덱스와
   LOB 데이터/인덱스가 포함됩니다. 원문 문자열 크기와 다릅니다.
3. 공용 계정/공용 테이블에서는 이번 사용자가 넣은 분량만 이 쿼리로 분리할 수 없습니다.
   적재 전후 용량 기록이나 적재 식별자·감사 이력과 추가 대조가 필요합니다.
4. 접속 계정은 사진상 PIDD2APP, 대상 소유자는 SIDDS/SIDDA입니다.
   USER_SEGMENTS를 보면 접속 계정 소유 객체를 조회하므로 SIDDS 용량의 대체가 아닙니다.
5. Q2가 ORA-00942/ORA-01031이면 조회 권한 문제를 확인해야 합니다.
   이때 정확한 물리 용량은 현재 결과로 확인되지 않았으며 DBA에게 Q2를 전달합니다.
6. NO_SEGMENT_INFO는 정확한 할당량 정보가 없다는 뜻입니다. 0으로 바꾸어 해석하지 않습니다.
7. 생성 시각은 생성자를 알려주지 않습니다. 현재 표 이름은 우리 전달본에서 확인했지만,
   공용 계정에서 실제 실행한 개인을 식별하려면 별도의 감사/작업 이력이 필요합니다.

다른 사용자의 INSERT 영향
- 같은 테이블스페이스에서 새 extent 할당이 필요한 작업은 동일 공간 문제의 영향을 받을 수 있습니다.
- 이미 확보한 블록 안에 적재 가능한 여유가 있고 관련 인덱스/LOB도 확장을 요구하지 않으면
  INSERT가 계속될 수 있습니다. 다른 테이블스페이스를 쓰는 작업도 조건이 다릅니다.
- SIDDS 계정 Quota가 찬 경우에는 SIDDS 소유 객체의 추가 할당이 영향을 받습니다.
  같은 AIDP 접속 계정을 쓴다는 사실만으로 동일 소유자/테이블스페이스라고 단정하지 않습니다.
- 현재 자료로 다른 사람의 INSERT 실패나 우리 적재가 유일한 원인이라고 확정할 수 없습니다.

재실행/중단
진단에 별도 재개 지점은 없습니다. 필요하면 해당 SELECT만 다시 조회할 수 있습니다.
대기가 길면 SQL 실행을 취소하고 기록합니다. 기존 R11/R12 적재나 임베딩 셀은 재실행하지 않습니다.

검증 범위
정적 Oracle 문법·읽기 전용 구성 검사이며 현장 실행·정확 용량·성능 검증은 아닙니다.
SQL은 현재 전달본의 일반 테이블 구조 기준입니다. 현장에서 별도로 변경한 IOT/클러스터/
파티션 구조가 있다면 세그먼트 연결을 추가 확인해야 합니다.
