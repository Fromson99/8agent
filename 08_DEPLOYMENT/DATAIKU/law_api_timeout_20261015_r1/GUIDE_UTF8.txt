Dataiku TIMEOUT 추가 진단 / 2026-10-15 R1
기존 DATAIKU_LAW_API_20261015_R1 Notebook에 넣는 추가 셀입니다.

1. 사진에서 확인된 상태
첫 law_published_body 요청: TIMEOUT, 받은 본문 0바이트, HTTP 상태 미표시.
뒤의 law_search / admrul_search / law_effective_body: BLOCKED_OR_BUDGET_EXHAUSTED.
admrul_body: SKIPPED_NO_UNIQUE_CURRENT_ID.
첫 요청의 시간 초과 때문에 R1 코드가 후속 호출을 막았습니다. 후속 행은 각각 호출해 실패한 결과가 아닙니다. BLOCKED는 코드 내부의 중단 표시이며 사내 방화벽 차단이 입증됐다는 뜻이 아닙니다.
현재 사진으로는 OC가 잘못됐는지, 개발계 주소가 실행 환경에 맞지 않는지, 연결/프록시/TLS/중계 응답 대기 중 어디서 문제가 생겼는지 확정할 수 없습니다.

2. 기존 코드의 진단 한계와 이번 추가 셀의 역할
R1은 requests의 연결 시간 초과와 응답 시간 초과를 모두 TIMEOUT으로 저장했습니다. 원래 발생한 예외 종류를 그 기록에서 복원할 수 없습니다.
이번 셀은 같은 ID·target·OC·쿠키·CA·프록시 설정으로 추가 GET 요청을 수동으로 1회만 보내고, 실제 예외 종류·실패 단계·응답 상태·소요 시간·적용 프록시 유무를 남깁니다. 원래 실패를 덮어쓰지 않습니다.
처음 1KB의 응답까지만 확인합니다. HTTP 200이 나와도 법령 전체 수신이나 기존 5개 확인 성공으로 표시하지 않습니다.
요청 시간 설정은 기존과 같은 연결 8초 / 읽기 대기 20초입니다. 단순히 타임아웃을 늘려 성공처럼 보이게 하는 변경은 없습니다. 응답 이후 통신도 발생할 수 있으므로 대략 수십 초가 걸릴 수 있습니다.
자동 재시도는 0회, 추가 진단은 원래 run당 최대 1회입니다. 기존 카운터/실패 기록/차단 상태를 초기화하지 않으며, 진단 JSON에 기존 호출 수와 합산 호출 수를 남깁니다. 셀을 다시 눌러도 저장된 진단만 표시합니다.

⑦ 새 Code 셀에 TXT 전체를 붙여 넣습니다. 기존 1~8번 셀을 삭제하거나 교체하지 않습니다.
⑧ Shift+Enter 또는 ▶ Run을 한 번 누릅니다. OC를 다시 입력할 필요가 없습니다.

Managed Folder ID가 비어 있다면 기존 1번 셀의 MANAGED_FOLDER_ID만 채운 뒤 1번과 8번을 실행합니다. 3~6번을 다시 실행할 필요는 없습니다. 저장이 실패하면 8번만 다시 실행합니다.

4. 결과별 해석과 다음 조치
CONNECTION_SETUP_TIMEOUT:
requests가 연결 수립 시간 초과로 분류했습니다. 출력된 실제 relay_url을 기준으로 Dataiku의 실행 서버/컨테이너에서 중계 또는 적용 프록시로 가는 DNS·주소·포트·방화벽·경로를 확인합니다. 이것만으로 특정 방화벽이 원인이라고 확정하지 않습니다.

RESPONSE_WAIT_TIMEOUT:
HTTP 응답을 받기 전 응답 대기 계열 시간 초과로 분류됐습니다. Dataiku 쪽 오류 종류와 중계 로그를 대조해 요청이 중계에 도달했는지, 중계가 원본 API에서 기다리는지 확인합니다. 예외 종류만으로 모든 하위 연결 단계가 성공했다고 보증하지 않습니다.

BODY_READ_TIMEOUT:
HTTP 상태를 받은 뒤 첫 본문 바이트를 읽는 과정에서 시간 초과가 났습니다. http_status가 함께 기록됩니다. 전송 중단/중계/원본 응답 지연을 확인합니다.

PROXY_ERROR:
적용된 프록시 연결 오류입니다. effective_proxy_host에는 계정·암호를 제외한 호스트/포트만 표시됩니다. 해당 내부 주소를 프록시로 보내야 하는지 또는 승인된 NO_PROXY 설정이 필요한지 Dataiku 관리자에게 확인합니다. 코드가 프록시를 자동 제거하지 않습니다.

TLS_ERROR:
CA 인증서, 호스트명, 만료 여부를 확인합니다. 인증서 검증을 해제하거나 IP·도메인을 임의로 바꾸지 않습니다.

HTTP_401 / HTTP_403:
이번 추가 요청에는 실제 HTTP 인증/접근 거부 응답이 왔습니다. 중계 인증과 과제 OC, 원본 API 등록 IP/사용 범위를 확인합니다. 이전 TIMEOUT도 OC 오류였다고 소급 확정하지 않습니다.

HTTP_302 등 3xx:
다른 URL 또는 로그인 화면으로 보내는 응답입니다. 자동 따라가기는 꺼져 있습니다. 승인된 실제 중계 주소/인증 방법을 확인합니다.

HTTP_200_WITH_FIRST_BYTES:
추가 요청은 HTTP 200과 일부 바이트를 받았습니다. 전체 XML 본문/문서 검증은 하지 않았으므로 기존 R1의 TIMEOUT 표를 성공으로 바꾸지 않습니다. 원인 조치가 확인된 뒤 기존 결과를 보존하고 별도 새 진단으로 전체 5개 확인을 실행합니다.

HTTP_200_EMPTY_BODY:
200 상태지만 본문이 없습니다. API 자료 확보 성공이 아닙니다.

CONNECTION_OR_TRANSPORT_ERROR / TIMEOUT_UNCLASSIFIED:
exception_classes와 JSON의 safe_error_message를 함께 봅니다. DNS/연결 거부 등의 원인은 이 제한된 진단 결과와 담당자 로그로 확인합니다.

IN_FLIGHT:
사용자 중단 등으로 이번 추가 진단의 완료 여부가 확인되지 않았습니다. 다시 실행해도 자동 재요청하지 않습니다. 기존 파일을 지워 재시도하지 말고 실패 기록을 먼저 검토합니다.

5. 담당자에게 전달할 문구
“Dataiku Python Notebook의 법제처 중계 GET 요청 첫 호출이 TIMEOUT으로 종료되어 HTTP 상태와 본문을 받지 못했습니다. 뒤의 BLOCKED 행은 클라이언트가 후속 요청을 생략한 상태입니다. 첨부 timeout_diag_r1.json의 실제 relay_url, 프록시 적용 여부, 예외 종류와 시각을 기준으로 Dataiku 실행 노드/컨테이너 → 중계 연결 및 중계 요청 도달/원본 호출 로그를 확인 부탁드립니다. 개발계 샘플 45.101.64.86:8443이 현재 실행 환경에 맞는 주소인지도 확인 부탁드립니다.”

이 문구는 사용자가 담당자에게 전달할 초안입니다. 이번 작업에서 담당자에게 직접 연락하지 않았습니다.
기존 summary.json과 이번 timeout_diag_r1.json을 같이 전달하면 됩니다. OC나 Cookie 값을 전달문에 붙일 필요는 없습니다.

6. 검증 범위
추가 셀의 정상 수신, 연결/읽기/프록시/TLS/HTTP 실패, 중단, 중복 실행, 예산, 기존 결과 보존 및 기존 Managed Folder 업로드 연결을 14개 검사로 확인했습니다.
동일 TXT를 localhost의 실제 HTTPS 서버에 요청해 URL·target_url·파라미터 전달도 확인했습니다. 모의 인증값만 사용했습니다.
실제 사내 Dataiku·삼성 중계·GENOS 연결은 이 세션에서 실행하지 않았습니다. 원래 TIMEOUT의 근본 원인과 사내 연결 복구는 아직 미확인입니다.
기존 R1 Notebook·ZIP·발송 기록은 보존했습니다. 이번 자료는 원본 Notebook 전체를 교체하는 R2가 아니라 TIMEOUT 원인 분류용 추가 셀입니다.
