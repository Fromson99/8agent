실행 순서
1. Dataiku LEGAL_RAG 프로젝트의 기존 벡터 실행 셀이 종료된 것을 확인합니다.
   사진처럼 PROCESS_EXIT=1로 끝났다면 그 실행은 이미 중단된 상태입니다.
   아직 실행 중이면 Interrupt 후 종료를 기다립니다. 동시에 두 적재를 실행하지 않습니다.
2. 관리 폴더 ehA8dpVm에 이번 R4 ZIP을 파일명 그대로 업로드합니다. 직접 풀지 않습니다.
3. 기존 Python 노트북의 새 셀에 R4 실행 TXT 전체를 붙여 실행합니다.
   ACTION="vector"를 유지합니다.
   OLD_JOB_DIR은 이전에 지정했다면 같은 값, 빈 문자열이었다면 그대로 둡니다.
   내부 모델 openai:genos-embedding:embedding-kure-v1 / 1024차원도 유지합니다.
   라이브러리·모델을 현장에 추가 설치하지 않습니다. 별도 Bash 실행은 없습니다.

사진의 오류와 수정
사진은 구조 단위 준비 중 42,336자 구간이 8,000자 상한을 넘어 중단한 사례입니다.
원본 R3 코드에서 같은 길이/오류를 합성 원문으로 재현했습니다.
R3 코드 실행 순서상 이 실패는 이전 벡터 삭제와 임베딩 호출보다 앞입니다.
사진의 실제 원문 내용은 제공되지 않았으므로 해당 문서 자체를 검증한 것은 아닙니다.

R4는 구조 단위를 먼저 유지하고 다음 순서로 필요한 경우에만 나눕니다.
조문 전체 → 저장된 항·호 → 문장/줄 → 구·공백 경계 → 경계 없는 초장문 연속 조각.
한 문장·표·공백 없는 구간 자체가 한도를 넘으면 조각으로 나눕니다.
뒤를 버리거나 요약·생략하지 않으며 모든 문자의 원문 블록/시작/끝 좌표와 조각 순서를 기록합니다.
이는 “모든 조문을 반드시 벡터 하나에 넣는다”는 방식은 아닙니다.
각 조각은 같은 원문 source_id와 구조 경로를 유지해 전체 조문으로 연결할 수 있습니다.

짧은 상위 조건·예외는 자식 입력에 함께 넣습니다.
상위 본문 자체가 너무 길면 상위 본문도 별도 조각으로 전부 적재하고, 자식에는
한도 내 문맥과 전체 상위 원문의 구조 ID/범위 해시 연결을 남깁니다.
매우 긴 제목도 전체 제목을 메타데이터에 보존하고 입력에는 들어가는 완전한 제목만 씁니다.
입력 상한은 기존8,000문자이며 Mesh overflow="FAIL"을 유지합니다.
문자 수와 모델 토큰 수는 다르며, 현장 제공자의 실제 입력 한도/검색품질은 별도 확인 대상입니다.

한 화면 진행 표시
실행 셀의 상태판 한 개를 약1초 간격으로 갱신합니다. 오류·완료는 즉시 표시합니다.
표시 항목: 현재 단계, 원문 준비 건수, 전체/완료/남은 벡터, 진행률 막대,
행/초, SDK 호출수, 경과시간, 예상 잔여시간, KST 예상 종료시각, 최근 DB 묶음, 전체 로그 경로.
초기 몇 묶음의 DB 응답 전에는 속도/예상시간이 계산 중입니다.
재개 전의 완료행을 이번 실행 속도에 더하지 않습니다.
준비 진행률과 적재 진행률은 별도 단계라 준비 완료 후 적재0%로 바뀔 수 있습니다.

매줄 JSON/진단/표준출력은 노트북 작업 폴더 gold-progress-logs의 .log 파일에 저장합니다.
오류는 같은 상태판에 남고 상세 원문은 전체 로그와 .errors.jsonl에 보존합니다.
노트북 아래에 traceback을 계속 붙이지 않습니다. worker 종료 코드는 화면과 VECTOR_RESULT에 남습니다.
필요하면 별도 셀에서 VECTOR_RESULT를 조회합니다.
완료 신호 없는 exit0도 완료로 표시하지 않습니다.
최종 완료: VECTORS_STORED_INSERT_ACK_NOT_ACTIVATED / 상태판 “적재 완료 · 서비스 활성화 별도”.
행100%만으로 완료하지 않고 완료 명세 저장까지 확인합니다.
서비스 활성 판본 전환은 이 실행에 포함하지 않습니다.

삭제·재개 범위
전체 원문 준비/검사가 끝난 뒤, 같은 원문·검색판본·모델의 기존 R1/R2 게시ID에 해당하는
SIDDS.LGL_G19_VCTR_ITEM_S_1 / SIDDS.LGL_G19_VCTR_POST_S_1 행과 해당 임베딩 캐시만 삭제합니다.
NFS 원문, 원문·검색 적재표, 다른 판본과 새 R4 데이터는 유지합니다. 활성 HEAD 참조 시 삭제를 거절합니다.
R4 작업은 기존 원문 체크포인트 아래 vectors-structure-r4/<새 게시ID>에 저장합니다.
같은 R4를 재실행하면 완료 위치부터 재개하며 R4 적재분을 다시 지우지 않습니다.

R3 준비 단계에서 중단한 정확히 같은 코드/입력 상태이고 모델·DB 적재 시도0이면
R3 상태 감사 사본을 남기고 원래 deadline/예산을 R4로 이어받습니다.
R3 실패 기록/준비 파일은 그대로 보존합니다. R3 state를 직접 지우거나 고치지 않습니다.
R3에서 이미 모델/DB 작업을 시도했거나 UNKNOWN이 남았다면 자동 새 작업으로 우회하지 않고 중단합니다.
R4 정상 중단은 첫 Interrupt를 사용합니다. 현재 외부 응답/체크포인트를 저장한 뒤 멈춥니다.
두 번째 Interrupt나 강제 커널 종료는 결과 불명 상태를 남길 수 있습니다.
EMBEDDING_OUTCOME_UNKNOWN_NO_AUTOMATIC_RETRY는 중복 호출하지 않고 원인 확인이 필요합니다.

유지한 설정
SDK 최대16입력/요청, DB 최대512행/16MiB, 내부 모델/차원, 잠금, 원문/판본/DB 해시,
원래 deadline/호출 예산, UNKNOWN 무재전송, 범위 지정 삭제와 INSERT 응답 기준 완료.
