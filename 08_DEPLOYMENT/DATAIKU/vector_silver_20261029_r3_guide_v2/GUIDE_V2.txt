[2] 빈 벡터 테이블 생성 — DB SQL 실행 화면 / 지금 가능

준비:
  PC에서 이전 메일의 R3 ZIP을 풉니다. 안에 다음 파일이 있습니다.
    01_CREATE_VECTOR_SILVER.sql  ← 생성할 때 사용
    02_CHECK_VECTOR.sql          ← 생성 후 확인할 때 사용

DB 담당자가 생성하는 환경:
  담당자에게 01_CREATE_VECTOR_SILVER.sql과 다음 내용을 전달합니다.
  “개발계 SIDDS에 LGL_VCTR_SET_S, LGL_VCTR_ITEM_S를 생성하고
   SQL에 포함된 PK/FK/JSON 제약과 두 함수 색인도 함께 생성해 주세요.
   기존 테이블 변경/삭제는 없습니다. Dataiku AIDP 연결 계정의 읽기·적재·갱신 권한과
   GENOS 조회 계정의 읽기 권한을 확인해 주세요.”

직접 생성할 권한이 있는 환경:
  SQL Developer에서 해당 개발계 Oracle 연결의 SQL Worksheet를 엽니다.
  01_CREATE_VECTOR_SILVER.sql 전체를 열어 Run Script(F5)로 실행합니다.
  '/'는 SQL Developer/SQLcl의 스크립트 구분자입니다.
  Dataiku SQL Query 칸에 전체 파일을 넣는 방법으로 안내하지 않습니다.
  SQL Developer를 사용하지 않는 환경이면 DB 담당자에게 위 파일을 전달합니다.

생성 후 확인:
  02_CHECK_VECTOR.sql의 첫 SELECT 결과가 다음과 같아야 합니다.
    LGL_VCTR_SET_S  : PUB_ID, PAYLOAD_JSON                       2컬럼
    LGL_VCTR_ITEM_S : PUB_ID, SEG_ID, META_JSON, EMBEDDING         4컬럼
  마지막 SELECT에서 다음 두 색인의 STATUS가 VALID인지 확인합니다.
    LGL_VCTR_ITEM_IX_S
    LGL_VCTR_SET_ACT_IX_S
  아직 적재 전이므로 중간 두 SELECT에 데이터 행이 없는 것은 정상입니다.
  PK/FK/타입/JSON/색인 전체 구조는 [5]의 check에서 추가 확인합니다.

여기까지가 이관 전 준비입니다. 나머지는 원문 이관 완료 후 진행합니다.

[4] 벡터 적재 Flow 설치 — Dataiku / 이관 후

A. 코드 ZIP 올리기
  PC에서 풀어 놓은 R3 폴더에서 VECTOR_SILVER_CODE_20261029_R3.zip을 찾습니다.
  Dataiku LEGAL_RAG → 관리 폴더 ID ehA8dpVm → 최상위에 이 ZIP을 업로드합니다.
  올릴 것은 바깥 HANDOFF ZIP이 아니라 안쪽 CODE ZIP입니다.
  CODE ZIP 자체는 풀지 않고 업로드합니다.

B. 모델 값 준비
  실제 GENOS 임베딩 서비스 담당자/설정에서 아래 세 값을 확인합니다.
    EMBED_MODEL       : /embeddings 요청의 model에 넣을 실제 모델 ID
    EMBED_REVISION    : 배포된 모델·가중치를 식별하는 고정 버전
    EMBED_DIMENSIONS  : 그 모델이 돌려주는 벡터 길이(정수)
  이전에 언급한 모델명이나 1024를 확인 없이 넣지 않습니다.
  Dataiku 연결용 이름과 /embeddings API의 실제 model ID가 같다는 보장은 없습니다.

  접속 주소와 인증은 기존 LEGAL_RAG 프로젝트 변수에 둡니다.
    GENOS_BASE_URL + GENOS_EMBED_SERVING_ID + GENOS_EMBED_KEY
  또는 직접 주소를 쓰는 환경은:
    GENOS_EMBED_URL + GENOS_EMBED_KEY
  직접 주소에는 코드가 뒤에 /embeddings를 붙입니다. API 루트 주소를 사용합니다.
  직접 주소 방식과 BASE_URL+SERVING_ID 방식을 동시에 넣지 않습니다.
  문서 구조화 서비스용 토큰/주소를 임베딩용으로 추정해 넣지 않습니다.

C. 설치 셀 실행
  새 Python 노트북 또는 커널을 재시작한 노트북에서 진행합니다.
  R3의 DATAIKU_INSTALL.txt 전체를 첫 셀에 붙여넣습니다.
  맨 위 다섯 줄 중 필요한 값만 바꿉니다.
    EMBED_MODEL = ""             ← 확인한 모델 ID
    EMBED_REVISION = ""          ← 확인한 모델 버전
    EMBED_DIMENSIONS = 0          ← 확인한 차원 정수(따옴표 없음)
    LOAD_RESULT_FOLDER_ID = ""   ← 폴더가 위 표준 이름이면 공란 유지
    LOAD_RECEIPT_PATH = ""       ← 완료 파일이 여러 개면 [3]의 정확한 경로
  실행하면 설치만 진행됩니다. 임베딩 작업은 시작되지 않습니다.

정상 결과:
  출력에 FLOW_INSTALLED LEGAL_04_VECTOR_SILVER_R4가 표시됩니다.
  Flow 새로고침 후 다음이 생깁니다.
    LEGAL_04_VECTOR_SILVER_R4       Python 레시피
    LEGAL_VECTOR_SILVER_RESULT_R4   결과 관리 폴더
  전달 ZIP 버전은 R3, 레시피 이름은 R4가 맞습니다. 이름을 임의로 맞춰 바꾸지 않습니다.

참고:
  모델 값이 없어도 설치만 하는 것은 가능하지만 [5] check와 [6] build는 할 수 없습니다.
  값이 준비되면 커널을 재시작하고 같은 설치 TXT의 모델 값을 채워 실행합니다.
  LEGAL_VECTOR_PROFILE은 설치 코드가 저장하므로 직접 긴 JSON을 만들 필요가 없습니다.
  Python 3.11 이상 및 requirements.txt의 라이브러리를 사용할 수 있는 코드 환경이 필요합니다.
  누락 라이브러리 오류는 해당 Dataiku 코드 환경 관리자에게 확인합니다.

[6] 임베딩해서 Oracle에 넣기 — Dataiku Flow

어디서:
  LEGAL_RAG → Flow → LEGAL_04_VECTOR_SILVER_R4 선택 → Run.
  기존 다른 벡터 적재 레시피와 동시에 실행하지 않습니다.

무엇이 일어나는가:
  Oracle 원문 읽기 → GENOS 임베딩 요청 → Oracle 벡터 저장 → 전량 검사 → 활성 게시.
  이 단계부터 실제 임베딩 요청이 발생합니다.

정상 결과:
  작업 로그에 VECTOR_READY가 나옵니다.
  출력 폴더 LEGAL_VECTOR_SILVER_RESULT_R4의
  vector/<작업키>/build-state.json에서 다음을 확인합니다.
    status = "READY"
    count > 0
    query_release_id = [3]에서 선택한 조회 게시 ID
    publication_id에 값이 있음
  DB 담당자가 02_CHECK_VECTOR.sql을 다시 실행하면 저장 건수와 차원,
  READY 상태, 활성 게시본의 ACTIVE_REVISION 값이 확인됩니다.
  과거 비활성 게시본의 ACTIVE_REVISION은 비어 있어도 됩니다.

실패하면:
  같은 원문·모델 설정과 같은 레시피로 재개하면 이미 저장된 행을 검증해 재사용합니다.
  프로세스 강제 종료 뒤 VECTOR_BUILD_BUSY가 나오면 다른 작업이 끝났는지 먼저 확인합니다.
  잠금값을 임의로 지우지 않습니다. 오류·작업 기록은 그대로 둡니다.

[7] GENOS가 새 벡터를 검색하도록 연결 — [6] READY 확인 후

대상:
  채팅 RAG 서비스의 실제 Git checkout ~/DEV.
  문서 구조화 서비스 legal_pipeline_serving에 이 패치를 덮어쓰는 것이 아닙니다.

코드 반영:
  GENOS의 실제 업로드한 TRANSFER 폴더에 R3 HANDOFF ZIP을 둡니다.
  그 폴더에서 터미널을 열어 아래를 실행합니다.
    python3 -m zipfile -e ./VECTOR_SILVER_HANDOFF_20261029_R3.zip ./vector_silver_r3
    cd ./vector_silver_r3
    bash ./GENOS_COMPACT_APPLY.txt check ~/DEV
    bash ./GENOS_COMPACT_APPLY.txt apply ~/DEV
  check가 실패하면 apply로 넘어가지 않습니다.
  apply 성공 시 CODE_BYTES_AND_PINS_VERIFIED가 표시되고 백업 경로가 나옵니다.
  이미 vector_silver_r3 폴더를 만들어 작업 중이라면 임의로 다시 덮어 풀지 말고
  그 폴더의 기존 R3 ZIP/코드가 맞는지 확인해 check부터 실행합니다.

배포:
  적용한 ~/DEV에서 변경 파일을 확인하고 실제 배포 절차대로 commit/push합니다.
  코드서빙이 그 commit으로 새 리비전을 배포하도록 설정합니다.
  반입/apply 성공만으로 실제 서빙 코드가 바뀐 것은 아닙니다.

설정 — 이전 GUIDE의 오류 정정:
  사용해야 하는 값: GENOS_RAG_INITIAL_SEARCH=vector
  이전에 적었던 GENOS_RAG_VECTOR_ENABLED=on은 이 코드에서 읽지 않습니다.
  원문 검색으로 복귀할 때: GENOS_RAG_INITIAL_SEARCH=keyword
  설정을 반영하고 해당 프로세스/리비전을 다시 시작해야 합니다.

  GENOS도 [4]와 같은 임베딩 주소/인증 변수를 사용해야 합니다.
  기존 Oracle 직접 조회(oracle_query) 연결은 유지합니다.
  GENOS가 읽는 조회 게시 ID와 [6] query_release_id가 일치해야 합니다.
  이 단계에서 ORDS 주소를 추정하거나 새 DB를 만들지 않습니다.

최종 확인:
  GENOS 워크플로우 테스트 화면에서 실제 원문 내용 질문 한 개를 실행합니다.
  요청 기록의 INITIAL_VECTOR_CANDIDATES와 후속 원문 읽기·인용을 확인합니다.
  모델·Oracle 접속 오류가 없는지와 답변이 실제 원문에 연결되는지 확인합니다.
