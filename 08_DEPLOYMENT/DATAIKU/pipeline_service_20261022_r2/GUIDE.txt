Dataiku 파이프라인 실행 R2 — 기존 SFTP 폴더와 업로드 파일 재사용

1. 사용할 폴더
Dataiku 프로젝트: LEGAL_RAG
Managed Folder 표시 이름: LEGAL_PIPELINE_WORKSPACE
새 관리 폴더를 만들지 않습니다. SFTP 연결을 그대로 사용합니다.
폴더명으로 dataiku.Folder를 열고 get_download_stream으로 읽습니다.
S3/Filesystem도 같은 API를 사용하며 get_path()는 호출하지 않습니다.

폴더 최상위에 이미 올린 파일 5개를 유지하세요.
  DATAIKU_PIPELINE_CLIENT_20261022_R1.zip
  RAW_INPUT.zip
  RAW_INPUT.zip.receipt.json
  PIPELINE_SUPPORT.zip
  PIPELINE_SUPPORT.zip.receipt.json

새 DATAIKU_PIPELINE_RUN_20261022_R2.zip은 실행 코드와 안내를 묶은 전달용입니다.
PC에서 풀어 실행 TXT를 열면 됩니다. Dataiku 폴더에 추가 업로드할 필요는 없습니다.
R1 ZIP 안의 DATAIKU_RECIPE.py / DATAIKU_PIPELINE_RUN.txt 대신 이번 R2 TXT를 사용하세요.
R1의 client/restore/전송 코드는 유지하고, SFTP 파일 다운로드와 시작 절차를 보완했습니다.
GENOS 서비스 ZIP과 서비스 코드 해시는 기존 R1 그대로입니다.

2. 원문·용어집 준비
LEGAL_RAG 프로젝트에서 Python 노트북을 열고
DATAIKU_PIPELINE_RUN_20261022_R2.txt의 전체 내용을 한 셀에 붙여넣습니다.
처음에는 맨 위 값을 그대로 둡니다.
  ACTION = "prepare"
  FOLDER_NAME = "LEGAL_PIPELINE_WORKSPACE"
  WORK_DIR = "./legal_pipeline_work"
  JOB_NAME = "run_20261022_01"
셀을 실행합니다. 마지막 status가 READY이면 다운로드·검증·압축 해제가 끝났습니다.
prepare에서는 GENOS 호출과 Oracle 적재를 하지 않습니다. URL/토큰도 아직 필요 없습니다.

작업 폴더는 노트북 Python 프로세스의 현재 디렉터리 아래에 자동 생성됩니다.
실행 첫 줄의 WORK_DIR 출력이 실제 절대 위치입니다.
이 폴더는 SFTP Managed Folder 안에 생기는 것이 아닙니다.
  legal_pipeline_work/
    download/                    다운로드한 원본 ZIP과 receipt
    code/DATAIKU_PIPELINE_CLIENT_20261022_R1/   검증한 실행 모듈
    inputs/01_DATA/RAW/           원문
    inputs/01_DATA/INPUT_MAPPING/ 최신판 매핑
    inputs/01_DATA/LEXICON/       용어집
    inputs/01_DATA/CATALOG/       지원 메타데이터
    jobs/run_20261022_01/         GENOS 요청·반환물·Oracle 적재 상태
    runner-events.jsonl          준비/실패/재개 기록
위 폴더들은 코드가 만듭니다. 폴더 ID나 PACKAGE_DIR/INPUT_DIR를 따로 입력하지 않습니다.

WORK_DIR는 Dataiku 실행 계정이 쓸 수 있고 재실행 후에도 유지되는 파일시스템이어야 합니다.
기본 상대경로가 영속 저장소가 아닌 컨테이너 작업 경로라면 운영자가 지정한 영속 절대경로로
처음부터 바꾸세요. 결과 수신 후 Oracle 재개에 작업 상태가 필요합니다.
압축 ZIP 2.36GB뿐 아니라 압축 해제된 용어집·원문과 향후 반환물 공간도 필요합니다.
다운로드와 해제는 실제 크기 및 512MiB 여유를 검사합니다.
GENOS 반환물 전체의 최대 크기까지 이 단계에서 보장하는 것은 아닙니다.

3. GENOS 호출과 Oracle 적재
프로젝트 Settings의 Variables에서 아래 세 값을 설정합니다.
  LEGAL_PIPELINE_URL       새 파이프라인 전용 GENOS 코드서빙의 HTTPS JSON 호출 URL
  LEGAL_PIPELINE_TOKEN     해당 코드서빙 호출 토큰 원문 (Bearer 접두어 제외)
  LEGAL_ORACLE_CONNECTION  AIDP
URL은 기존 RAG 채팅 주소가 아닌 GENOS_PIPELINE_SERVICE_20261022_R1 배포 주소입니다.
이 문서에는 현장의 실제 새 URL과 토큰이 없습니다. 발급된 값을 입력해야 합니다.
AIDP는 기존 기록의 Dataiku Oracle 연결 이름입니다. SIDDA는 스키마 이름입니다.
토큰은 코드·출력·메일에 넣지 말고 접근 제한된 프로젝트 변수에서 관리하세요.

같은 노트북 셀 맨 위 ACTION만 "run"으로 바꾸고 다시 실행합니다.
폴더명·WORK_DIR·JOB_NAME은 유지합니다.
  ACTION = "run"
원문/지원 ZIP 전송 → GENOS 구조화·색인 → 결과 수신·검증 → 기존 Oracle 테이블 적재 순서입니다.
같은 작업을 재실행하면 기존 client.json과 적재 상태를 재사용합니다.
최종 COMPLETE를 확인하세요. READY는 준비 완료이며 Oracle 적재 완료가 아닙니다.
PAUSED/FAILED/중단은 완료로 취급하지 않습니다. 상태 파일을 보존하고 원인을 해결한 뒤 재실행합니다.

기존 적재 계약의 테이블 7개:
  SIDDA.LEGAL_SRC_DOCUMENT_A
  SIDDA.LEGAL_SRC_SOURCE_UNIT_A
  SIDDA.LEGAL_SRC_BLOCK_PAYLOAD_A
  SIDDA.LEGAL_RAG_ASSET_PART_A
  SIDDA.LEGAL_RAG_RELEASE_A
  SIDDA.LEGAL_RAG_QUERY_ROW_A
  SIDDA.LEGAL_RAG_QUERY_RELEASE_A
R1의 구조화/용어·정의·명시 참조 색인과 기존 테이블 적재 경로를 사용합니다.
LLM/VLM 호출, 별도 의미 온톨로지·llm_wiki 생성, 신규 골드 DDL 생성, ACTIVE 전환은 포함하지 않습니다.
기존 테이블 권한·구성과 GENOS 서비스 배포 상태는 현장에서 확인해야 합니다.

4. 재개와 원문 변경
다운로드가 중단되면 동일 설정으로 재실행합니다. 완료 파일은 해시 확인 후 재사용합니다.
중단된 다운로드 조각만 처음부터 다시 받으며 자동 무한 재시도는 하지 않습니다.
원문 ZIP/receipt가 바뀌면 기존 작업과 섞지 않고 INPUT_BINDING_CHANGED로 중단합니다.
새 데이터 묶음은 새 WORK_DIR와 JOB_NAME으로 시작합니다.
추가 내규를 준비된 inputs/01_DATA/RAW/internal/<이름_team>/에 넣는다면 최초 run 전에 넣으세요.
run 시작 후 추가한 자료는 같은 작업의 고정 입력에 포함되지 않습니다. 새 JOB_NAME으로 실행하세요.
이미 추출된 원문 자체가 기존 ZIP과 다르면 RESTORE_CONFLICT로 멈춥니다.
기존 입력을 수정·덮어쓰지 말고 원본 ZIP/매핑을 새 묶음으로 만들고 새 WORK_DIR를 사용하세요.
KERNEL_RESTART_REQUIRED가 나오면 노트북 커널을 재시작하고 이번 R2 셀을 다시 실행하세요.
DEPLOYED_CODE_MISMATCH이면 새 GENOS 코드서빙이 기존 서비스 R1 해시와 맞는지 확인하세요.
서빙 프로세스 변경, FAILED/CANCELLED/기한 소진은 단순 재실행으로 복구된다고 보장하지 않습니다.
기존 jobs 기록과 반환 ZIP은 지우지 마세요. 자동으로 새 job을 만들어 중복 실행하지 않습니다.

5. 검증 범위
배포 ZIP에 포함된 실제 R1 모듈로 SFTP/S3 형태의 비탐색 스트림 읽기, 해시 검사,
원문 복원, 재개와 오류 중단을 합성 데이터로 검사합니다. 자세한 결과는 VALIDATION.json입니다.
현재 세션에서는 망분리 GENOS와 Dataiku/Oracle 실제 연결에 접근하지 않았습니다.
