Gold 초기 적재분 초기화 → 처음부터 다시 적재 R7 / 2026-11-02

이번에는 이 R7 실행 TXT를 사용합니다. R6/이전 통합 TXT와 동시에 실행하지 않습니다.

이번 수정 이유
R6는 COUNT(*)가 int 형식이 아니거나 합계 10,000행을 넘으면 같은 오류를 냈습니다.
사진의 RESET_REFUSED_MORE_THAN_10000_SOURCE_ROWS만으로 실제 초과 여부는 알 수 없습니다.
화면의 3,854행은 이전 완료 기록이며 실제 DB COUNT 결과와 다릅니다.
R7은 정상 Decimal/정수형 float 행 수를 정확한 정수로 처리하며 소수값을 버림하지 않습니다.
임의의 10,000행 제한과 백업 총량 512MiB 제한은 제거했습니다.
대신 이미 결속된 이번 원본 명세의 표별 행 수와 실제 DB 행 수를 표시·대조합니다.
백업은 작은 묶음으로 처리하며 실제 디스크·메모리 여유 확인은 유지합니다.
이번 R6 오류는 삭제 시작 전 검사에서 발생한 것으로, R7은 해당 중단 상태를 직접 이어받습니다.
기존 reset-r6.json/old-state.json을 직접 수정하거나 지울 필요가 없습니다.
원래 R1 ZIP은 동일 바이트로 유지하고, 별도 R7 실행기가 승인된 초기화와 새 실행을 담당합니다.

실행 순서
1. 기존 적재/진단 셀이 종료됐는지 확인합니다.
2. Dataiku LEGAL_RAG 관리 폴더 ehA8dpVm에 아래 ZIP을 이름 그대로 올립니다.
   - DATAIKU_GOLD_SHAPE_20261102_R1.zip (이미 있으면 재업로드 불필요)
   - DATAIKU_GOLD_RESTART_20261102_R7.zip (이번 새 ZIP)
   압축을 풀거나 ZIP 안에 ZIP을 넣지 않습니다. 같은 정확한 파일명은 한 개씩만 둡니다.
3. 기존 Dataiku 환경변수/프로젝트 변수를 유지합니다.
   LEGAL_EMBED_LLM_ID=openai:genos-embedding:embedding-kure-v1
   LEGAL_EMBED_DIMENSIONS=1024
4. 같은 Dataiku Python/Jupyter 노트북의 새 셀에 DATAIKU_GOLD_RESTART_R7.txt 전체를 붙여 실행합니다.
   이전 OLD_JOB_DIR을 지정했다면 같은 값을 넣습니다. SQL 노트북용이 아닙니다.
   state.json을 직접 삭제하거나 RETRY_MISSING_BATCH를 True로 바꿀 필요가 없습니다.

실행 시 실제로 하는 일
① 기존 원본·코드·DB 접속 대상·DB 객체·실패 기록을 확인합니다.
② 이번 적재 세대의 아래 세 표에 실제로 남은 행 수와 백업 위치를 화면에 표시합니다.
   SIDDS.LGL_G19_DOC_VER_S
   SIDDS.LGL_G19_DOC_UNIT_S
   SIDDS.LGL_G19_DOC_BLK_S
③ 실제 DB 행 전체를 작은 묶음으로 gzip 백업하고, 복원 해시와 DB 내용 일치를 확인합니다.
   기존 state.json도 원래 바이트 그대로 백업합니다. 빈 CLOB과 NULL도 구분합니다.
④ 백업한 PK와 값이 여전히 일치하는 행만 묶음별 트랜잭션으로 DELETE합니다.
   다른 세대, 다른 표, 기존 LEGAL_*/LGL_DOC_*, Agent 기록은 삭제하지 않습니다.
   DROP/TRUNCATE/테이블 재생성/공간 확장/DDL은 없습니다.
⑤ 이번 세대의 세 표가 모두 0행임을 확인한 뒤 새 빈 진행 상태를 원자적으로 설치합니다.
   이번 명시적 처음부터 재시작에만 새 7일 기한을 부여하고 이전 기한·실패 기록은 백업에 보존합니다.
⑥ 원문 처음부터 적재 → 검색 자료 적재 → 전수검증 → Mesh 임베딩·벡터 저장을 이어 실행합니다.

초기화 범위를 넘으면 멈추는 조건
- 이번 세대의 실제 DB 행 수가 같은 표의 원본 명세 행 수보다 많은 경우(표·실제값·기준값 표시)
- 검색 적재/검증/게시/벡터 작업 이력이 이미 있는 경우
- 해당 세대/검색 판본의 게시 정보·채널·벡터 게시 연결이 DB에 있는 경우
- 원문 표에 활성 트리거 또는 참조하는 외래키가 있는 경우
- 코드/원본/DB/상태가 다르거나 백업 후 내용이 바뀐 행, 백업하지 않은 추가 행이 있는 경우
- 다른 실행이 같은 작업 잠금을 보유하거나 DB 테이블 쓰기 잠금을 즉시 얻지 못한 경우
이 조건에서는 범위를 넓히거나 강제 삭제하지 않고 이유를 표시합니다.

중단 후 같은 셀을 실행하면
- 백업 도중 중단: 이전 불완전 백업은 보존하고 새 백업 시도를 만듭니다.
- 일부 묶음 삭제 후 중단: 원래 상태를 유지한 채 같은 백업을 확인하고 나머지를 정리합니다.
  이미 삭제된 백업 행은 재삭제하지 않습니다. 여러 묶음 전체가 하나의 원자적 삭제는 아닙니다.
- 삭제 COMMIT 응답이 유실돼도 같은 PK/내용 검사로 재개합니다.
- 새 상태 설치 뒤 중단: reset_id를 확인해 초기화를 반복하지 않고 새 적재를 이어갑니다.
  이후 같은 셀을 다시 눌러도 이미 새로 적재한 행을 다시 지우지 않습니다.
- 백업 이후 변경된 행은 덮어쓰거나 삭제하지 않습니다. 오류 화면과 백업을 보존하세요.

백업/복구 기록
기존 gold-shape-<계약해시>/reset-backups/<초기화ID>/ 아래:
old-state.json, manifest.json, snapshot-*/<표>-<묶음>.json.gz
같은 gold-shape 폴더의 reset-r6.json이 최초 초기화 완료 여부를 기록합니다.
R7도 기존 작업을 식별하기 위해 이 파일명을 유지합니다.
사진과 같은 R6 BACKING_UP 중단은 같은 초기화 ID로 이어받고, 기존 제어 기록 원본을
reset-backups/<초기화ID>/control-r6-before-upgrade.json에 별도로 보존합니다.
이미 삭제 단계에 들어간 다른 R6 작업까지 임의로 전환하지 않습니다.
이 파일들과 백업은 삭제하지 마세요. 임의로 지우면 안전한 재개 근거를 잃습니다.
백업은 실제 삭제 전 DB 값이며 자동 원복 기능은 이 셀에 포함하지 않습니다.
기존 SOURCE/Gold 원본 파일 및 다른 세대는 유지합니다.

진행/완료 표시
RESET_TABLE_COUNT → RESET_SCOPE → RESET_BACKUP → RESET_DELETE_CONFIRMED → RESET_COMPLETE 이후 적재 진행이 나옵니다.
재실행 시 RESET_ALREADY_DONE이면 다시 삭제하지 않고 새 적재를 이어가는 정상 상태입니다.
처리 행 수·경과 시간·단계별 예상 잔여 시간을 표시하며 오류 상세와 전체 로그를 보존합니다.
최종 VECTORS_STORED_VERIFIED_NOT_ACTIVATED는 개발계 벡터 저장까지 완료라는 뜻입니다.
서비스 검색 전환·벡터 검색 전용 인덱스 DDL은 별도입니다.
