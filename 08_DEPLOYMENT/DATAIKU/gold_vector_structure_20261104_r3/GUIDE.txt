Dataiku 구조 단위 벡터 재구축 R3 — 2026-11-04

첨부 파일
1. DATAIKU_GOLD_VECTOR_STRUCTURE_20261104_R3.zip

기존 벡터 R1/R2 ZIP·실행문 대신 이번 R3를 사용합니다.
대상: Dataiku LEGAL_RAG 프로젝트, AIDP 연결, SIDDS의 기존 _1 벡터 표.

실행 순서
1. 기존 벡터 실행 셀을 ■/Interrupt로 중단하고 해당 실행이 끝난 것을 확인합니다.
   기존 원문·검색 적재와 벡터 적재를 동시에 실행하지 않습니다.
2. 관리 폴더 ehA8dpVm에 이번 ZIP을 파일명 그대로 업로드합니다. 직접 풀지 않습니다.
3. 기존 Python 노트북의 새 셀에 실행 TXT 전체를 붙여 실행합니다.
   ACTION="vector"를 그대로 사용합니다.
   OLD_JOB_DIR은 이전 셀에서 지정했다면 같은 값, 빈 문자열이었다면 그대로 둡니다.
   모델 openai:genos-embedding:embedding-kure-v1, 차원 1024도 이전과 동일합니다.
   새 라이브러리나 모델 가중치를 현장에 설치하지 않습니다.

자동 실행 순서
대상/판본/DB/단일 writer 잠금 확인
→ 구조 단위 전체 준비 및 건수 확정(이때 임베딩/삭제 없음)
→ 같은 원문·검색 판본/모델의 이전 R1/R2 벡터와 해당 임시 캐시 삭제
→ 별도 R3 판본 생성/적재 또는 이미 시작한 R3 재개
→ 완료 명세 저장.

삭제 범위
SIDDS.LGL_G19_VCTR_ITEM_S_1과 SIDDS.LGL_G19_VCTR_POST_S_1에서
이번 원문·검색판본·모델에 해당하는 이전 R1/R2 VCTR_POST_ID의 행만 삭제합니다.
vectors-fast-r1/<해당 게시ID>의 임베딩 캐시와 기존 작업 파일도 제거합니다.
삭제 영수증과 변경 전의 작은 상태 기록은 R3 작업 폴더에 보존합니다.
NFS 원문, 원문·검색 적재표, 다른 판본, 새 R3 데이터는 삭제하지 않습니다.
기존 판본이 VCTR_HEAD에서 활성 사용 중이면 삭제를 중단하고 사유를 표시합니다.
이 실행은 현재 800자 벡터 R1/R2를 대체합니다. 다른 과거 도구의 벡터 전체 삭제 명령은 아닙니다.

재실행과 중단
같은 R3 ZIP/TXT와 OLD_JOB_DIR/모델/차원으로 다시 실행하면 R3 완료 위치부터 재개합니다.
이전 R1/R2 삭제가 완료되었다면 반복 삭제하지 않습니다.
삭제 응답이 불확실했던 경우에도 같은 이전 게시ID만 다시 삭제하므로 R3에는 영향이 없습니다.
R3 작업 위치: 선택된 기존 원문 체크포인트/vectors-structure-r3/<새 게시ID>.
R3의 state.json, segment-plan.sqlite, embed-*.json은 직접 지우지 않습니다.
R3 셀의 첫 Interrupt는 작업 프로세스에 중단 요청을 전달합니다.
진행 중 임베딩 응답 캐시 또는 DB 완료 기록을 보존한 다음 멈춥니다.
두 번째 Interrupt나 커널 강제 종료는 결과 불명 상태를 남길 수 있습니다.
EMBEDDING_OUTCOME_UNKNOWN_NO_AUTOMATIC_RETRY는 재호출하지 않고 원인 확인이 필요합니다.
중단은 실패 완료가 아닙니다. 마지막 오류와 원래 deadline/호출수를 유지합니다.

임베딩 단위
- 짧은 조문: 연결된 원문 블록과 하위 항·호를 모두 포함한 조문 전체.
- 긴 조문: 저장된 source_unit 부모/자식 구조의 하위 항·호를 우선 사용.
- 긴 말단: 문장 끝이나 줄 경계로만 분할. 800자 위치에서 임의 절단하지 않음.
- 입력에는 문서명·구조 제목 경로와 해당 원문 범위 안의 상위 자체 본문을 붙임.
  따라서 자식 항·호에도 상위 도입문과 단서·예외가 함께 포함될 수 있습니다.
- 구조 ID가 없는 원문은 구조를 만들어내지 않고 UNSTRUCTURED로 표시하여 보존.
- 본문 구간과 추가 부모 문맥의 블록ID/시작/끝/해시는 각각 기록.
- 조립 입력은 로컬 준비 상한 8,000문자. 이는 모델의 토큰 한도와 다른 값입니다.
  공식 KURE-v1은 8,192 토큰 길이를 안내하지만 현장 서빙 설정과 같다는 보장은 없습니다.
  Mesh에 text_overflow_mode="FAIL"을 명시해 길이 초과 시 묵시적 절단을 허용하지 않습니다.
  한 문장과 필수 부모 문맥만으로 준비 상한을 넘으면 임베딩/삭제 전에 위치를 남겨 중단합니다.
  실제 Mesh의 더 낮은 한도는 호출 시 거절될 수 있으며 현장 한도는 미확인입니다.

큰 묶음 적재
DB 최대 512행/JSON 16MiB. 둘 중 먼저 도달한 한도로 INSERT/COMMIT합니다.
R2는 최대 128행/2MiB였고, 제공 사진에서는 실제 80행씩 처리했습니다.
임베딩 SDK는 검증된 기존 최대 16입력/요청을 유지합니다.
DB 요청 횟수 감소를 목표로 한 변경이며 전체 처리시간 단축률은 현장 미측정입니다.
입력이 길어지므로 R2의 행/초를 R3 완료시간에 그대로 적용하지 않습니다.

진행 표시
구조 단위 준비: 처리 원문/전체 원문, 준비 진행률, 준비 예상 잔여, 현재 계획 벡터 수.
전체량 확정 후: 완료 벡터/전체 벡터, %, 남은 행, 행/초, 이번 적재 경과,
예상 남은 시간, 예상 종료 일시(KST), SDK 호출수와 묶음 DB 시간.
속도는 이번 실행에서 새로 ACK된 행으로 계산합니다. 몇 묶음 처리 전에는 계산 중입니다.
재개할 때 기존 완료행을 이번 실행의 속도 분자에 더하지 않습니다.
예상 시간은 현재 관측 속도에 따른 값이며 입력 길이·모델 대기·DB 상황에 따라 변합니다.
진행 중 DB 묶음은 응답이 확인된 뒤 완료행에 포함합니다.
행 100% 뒤 완료 명세 저장까지 끝나야 최종 완료입니다.
최종 표시: VECTORS_STORED_INSERT_ACK_NOT_ACTIVATED.
이 단계는 적재 응답 기준 완료이며 서비스 활성 판본 전환은 별도입니다.
로그: 기존 노트북 작업 폴더/gold-progress-logs.

검증 범위
Python 3.9에서 정상·재개·UNKNOWN·중단·원문 변조·계획 변조·원문 무손실·진행 표시 검사.
실제 로컬 Oracle 23.26에서 512행×1024차원, 약13.3MB JSON/약6.7MB 전달SQL 적재와
중복·잘못된 차원의 롤백, 기존 판본만 삭제/활성 판본 삭제 차단/삭제 재실행을 검증했습니다.
격리 시험 스키마만 만들고 제거했으며 기존 DB 데이터는 변경하지 않았습니다.
로컬 NFS 대응 자료 33,443 원문/308,795 블록에서 79,586 벡터 입력을 구성하고
본문 범위 누락0을 확인했습니다. 이 수를 현장 NFS의 실제 전체량으로 확정하지 않습니다.
현장 실제 전체량은 실행 시작의 준비 단계에서 산출합니다.
내부 Mesh 호출, 현장 삭제·적재, 전체 속도와 검색 품질은 아직 검증하지 않았습니다.
