NFS 기존 자료 Oracle 이관 R8 — 누락 모듈 수정·15초 진행 표시

전달 파일
DATAIKU_EXISTING_NFS_CLIENT_20261030_R8.zip: 실제 실행 코드
DATAIKU_EXISTING_NFS_LOAD_ONLY_R8.txt: 노트북 전체 실행 코드, load_only 기본값
GUIDE.txt: 이 안내

해결한 오류
R7에서 native 정의문을 처리할 때 semantic_runtime.term_links 누락으로 실패했습니다.
같은 term_index/contracts 코드와 일치하는 원본 term_links.py를 패키지와 pin에 추가했습니다.
정의문이 들어 있는 시험에서 R7 오류를 재현하고 R8 정상 처리를 확인했습니다.
긴 작업 시작 전에 정의문 정규화 함수와 모듈 출처/해시를 실행 검사합니다.

실행 위치와 순서
1. LEGAL_RAG 프로젝트의 기존 반입 관리 폴더 ehA8dpVm에
   DATAIKU_EXISTING_NFS_CLIENT_20261030_R8.zip을 압축 그대로 업로드합니다.
   기존 R7 및 R3 정리 ZIP을 실행 대상으로 선택하지 않습니다.
2. 기존 오류가 난 노트북의 셀이 종료되어 Idle인지 확인한 뒤 Kernel > Restart합니다.
   다른 적재/검증 작업이 같은 자료를 쓰고 있으면 그 작업이 종료된 상태에서 진행합니다.
3. 새 셀에 DATAIKU_EXISTING_NFS_LOAD_ONLY_R8.txt 전체를 붙여 실행합니다.
   기본 ACTION='load_only'이므로 적재 후 전수 Oracle 재조회 검증은 자동 실행하지 않습니다.
4. LOADED_UNVERIFIED가 나오면 적재 완료·전수검증 보류입니다.
   나중에 필요할 때만 ACTION='verify'로 바꿔 전수 검증을 별도 실행합니다.
   기존 레시피 00/01/02/03을 다시 실행하는 절차는 아닙니다.

유지하는 자료와 기한
기존 NFS 수신 generation, Oracle에 완료된 원문, 동일 재개 디렉터리를 사용합니다.
현재 로컬 수신 파일이 크기/해시와 같으면 다시 다운로드하지 않습니다.
원문/검색색인/실패기록/S3 원본을 삭제하거나 이관을 초기화하지 마세요.
원래 작업의7일 기한과 누적 SQL 예산은 초기화하지 않습니다.
이전6시간 실행 상한은 계속 없으며, 개별 NFS 요청의120초 통신 제한은 유지됩니다.

새 진행 표시
DEPENDENCY_PREFLIGHT_PASS: 정의문 함수/모듈 출처/코드 hash 검사 통과.
[진행] 줄: 단계 전환 시 즉시, 작업 중에는 기본15초마다 출력합니다.
- SOURCE_DESCRIPTOR_TABLE: store.sqlite의 원문표 행수/해시 준비.
  해당표=처리행수/총행수 형태입니다. 전체 이관 완료 비율이 아닙니다.
- DESCRIBE_ASSET, TABLE_SCAN, NATIVE_NAVIGATION: 검색/용어집 자료의 명세 준비.
  파일명과 파일순서, 가능한 구간에서는 생성한 검색행 수를 표시합니다.
- FTS_LENGTH_AGGREGATE, FTS_POSTINGS_SORT: 검색어 위치 집계/정렬.
  정렬 SQL이 결과 행을 반환하기 전에도 SQLite작업량과 CPU누적, 경과 시간이 갱신됩니다.
- ASSET_PART_LOAD: 파일 보관용 조각 적재. 완료된 조각의 바이트 진행을 표시합니다.
- QUERY_LOADED: 검색행 적재 배치 진행.
- QUERY_VERIFIED: 사용자가 나중에 verify를 실행한 경우의 검색행 검증.
경과/단계 시간은 해당 추적 구간의 시간이며, NFS 파일 대조와 Oracle 이관 구간은 별도입니다.
하트비트가 나온다는 사실만으로 행 적재 완료나 정상 속도를 인증하지 않습니다.
처리행수/SQLite작업량/CPU/남은 공간이 함께 바뀌는지 확인하세요.
총 작업량을 알 수 없는 정렬에는 전체 퍼센트나 남은 시간을 임의로 표시하지 않습니다.
임시여유는 SQLITE_TMPDIR/기본 임시 디렉터리 후보의 실제 여유입니다.
실제 SQLite 정렬 파일이 놓인 정확한 경로를 확정한 값은 아닙니다.

기록과 중단
Oracle 이관 구간의 progress.jsonl/progress-latest.json은 기존 수신 작업의
oracle-import-r2 아래에 남고, 기존 receipt ZIP 보관에도 포함됩니다.
수신 파일 대조 단계의 진행 기록은 수신 작업 루트에 남습니다.
디스크/임시공간/RAM이512MiB 미만이면 기존 보호 조건으로 중단될 수 있습니다.
SQLite 집계/정렬에도 원래 기한/자원 중단을 확인하는 callback을 연결했습니다.
원인이 남아 있으면 오류를 숨기거나 계속 반복하지 말고 마지막 진행 줄과 오류를 확인하세요.
이번 R7 실패는 준비 계산 도중이므로 완료 준비 캐시가 없으면 준비를 다시 계산합니다.
완료한 원문을 새로 적재하는 의미는 아니며, 준비 계산의 중간행 커서는 구현하지 않았습니다.
검증 중 중단 시 검증은 다시 전수 수행합니다. 실패/미확인 쓰기를 성공으로 취급하지 않습니다.

호환/되돌림
원문 migration/full identity 모듈은 R7/R6B와 같은 바이트입니다.
검색 publisher 코드가 변경되어 새 query release ID를 씁니다.
이미 다른 query plan이 있으면 무거운 준비 전에 DEFERRED_BINDING으로 중단합니다.
그때 기록/원문을 지우거나 ID를 바꿔 우회하지 말고 계획의 호환 상태를 확인해야 합니다.
R8에서 새 plan을 만든 뒤 이전 R7로 되돌려 실행하는 것도 동일 조건을 확인해야 합니다.
MAIN/GENOS 코드서빙/Oracle DDL 변경은 이 패키지 준비 작업에서 수행하지 않았습니다.

검증 범위
계약21개+실제 전달TXT 모의진입1개 통과. 실제 정의문이 들어 있는 격리 재현,
누락 dependency 사전 거절, 주기 출력, 실제 SQLite VM 작업량, 단계별 카운터 초기화,
기존 검색행 동등성/준비 캐시/이전plan 거절, 완료 원문 재개/응답유실/변조 거절을 확인했습니다.
Python3.11 전체 구문 검사와 실제 정의문 정규화도 확인했습니다.
현장 Dataiku/Oracle의 전체 적재 성공, 대형 자료 속도/정렬 공간 효과는 아직 미확인입니다.
