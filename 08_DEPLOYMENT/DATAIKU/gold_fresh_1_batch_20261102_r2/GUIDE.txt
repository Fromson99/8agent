SRCH_ROW 배치 조정·기존 _1 재개 R2 / 2026-11-02

현재 적용 보류 — 후속 현장 사진에서 ORA-01654 확인
기본키 인덱스 X0_LGL_G19_SRCH_ROW_S_1의 extent 할당 실패로 적재가 중단됐다.
배치 확대는 이 공간 문제나 검색자료 중복 표현을 해결하지 않는다.
아래 사용 순서는 공간 문제·적재 구조를 확인하고 기존 pending을 검증한 뒤에만 해당한다.
행 종류를 줄이는 후속 projection은 본 R2와 별개 릴리스/검증이 필요하다.

목적과 범위
검색 INSERT/검증 묶음을 기존 최대5,000행/2MiB 목표에서 최대10,000행/4MiB 목표로 조정한다.
원본·검색 projection·행 ID/내용·전체 예정량·대상17표·인덱스 구성·임베딩 입력은 동일하다.
행 하나가 목표 크기를 넘는 경우의 기존 개별 행 제한은 유지한다. 4MiB는 실제 SQL 크기 제한이 아니다.
왕복 수는 줄일 수 있으나 같은 행의 DB 작업은 남는다. 속도2배/완료시간 절반을 보장하지 않는다.
VIEW 중복 저장 제거나 Oracle 소비자 변경은 이 수정에 포함되지 않는다.
현장에 적용하지 않았으며 실Oracle 10,000행 성능·장기부하는 미검증이다.

첨부
DATAIKU_GOLD_FRESH_1_BATCH_20261102_R2.zip
DATAIKU_GOLD_FRESH_1_BATCH_RUN_R2.txt
CAPACITY_READONLY_R2.sql (별도 SQL 노트북에서 선택 실행하는 읽기 전용 할당량 조회)

대상
현재 gold_fresh_1_20261102_r1의 _1 원문/검색 적재 또는 검증을 진행 중인 작업.
R1 코드 지문 하나만 명시적으로 전환 허용한다. 다른 코드/데이터/DB/계약/객체와는 합치지 않는다.
R1 벡터 작업이 이미 시작되어 vectors/*/state.json이 있으면 코드 전환 전에 중단한다.
그 경우 R1 코드와 벡터 상태를 유지한다. 이미 시작된 모델 작업은 이 배치 수정의 대상이 아니다.

사용 순서
1. ZIP을 Dataiku LEGAL_RAG 관리 폴더 ehA8dpVm에 정확한 이름으로 올린다.
2. 기존 적재 실행을 정상 중단하고 자식 프로세스 종료/커널 Idle을 확인한다.
   기존 실행이 살아 있는 동안 새 writer를 실행하지 않는다. 강제 커널 재시작으로 중첩 실행하지 않는다.
3. 기존 OLD_JOB_DIR을 유지하고 새 TXT 전체를 Python/Jupyter 새 셀에 넣어 실행한다.
   기본 QUERY_BATCH_ROWS=10000, QUERY_BATCH_BYTES=4*1024**2다.
4. R1_TO_R2_RESUME_BOUND: 동일 DB/객체/입력 확인 뒤 원래 state를 별도 파일에 보관하고
   코드 전환 영수증을 남긴다. 기존 완료행/원문 완료/실패/pending/최초deadline을 보존한다.
5. QUERY_BATCH_POLICY와 이후 LOAD의 batch_rows/request_s, JDBC_TIMING의
   render_seconds/request_seconds/sql_bytes/payload_bytes를 확인한다.
6. load → verify_publish → vector 순서와 단계 실패 시 후속 중단을 유지한다.

재개와 결과 불명
기존5천행/2MiB 배치 경계에 맞추지 않고 확인된 행 offset 이후부터 새 크기로 이어간다.
기존 pending이 있으면 원래 행 수·내용·해시로 그 묶음을 먼저 대조한다.
INSERT 결과 불명은 조회 검증만 수행하며, 누락/충돌이면 자동 INSERT하지 않고 원래 pending을 보존한다.
오류가 나면 전체 로그와 오류 파일을 보관하고 표시된 사유를 확인한다. state 삭제로 다시 시작하지 않는다.
완료 앞부분의 로컬 순차 재생성/건너뛰기는 남는다. 완료행을 다시 INSERT하지 않는다.

속도 비교와 복구
같은 단계의 완료행 차이/실제 시간으로 rows/s를 비교한다. 요청 한 번의 초만 비교하지 않는다.
더 큰 묶음이 유리한지는 현장 DB/전송 병목에 달려 있다. SQL 결과 불명 뒤 자동 크기 변경/재시도는 없다.
큰 묶음이 불리하면 종료 확인 후 같은 R2 TXT의 두 설정을5000,2*1024**2로 바꿔 재개한다.
R2 진행 뒤 R1 state 백업을 덮어쓰거나 옛R1 코드로 돌아가지 않는다. pending과 현재 완료 위치가 달라질 수 있다.
이전 크기로 복귀할 때도 R2의 동일 코드·기록과 pending 원래 묶음을 유지한다.

용량
6천만행만으로 실제 Oracle 할당량을 확정할 수 없다.
60,971,724행 × 평균 저장값500/1000/2000bytes = 약30.5/61.0/121.9GB의 가정값이다.
이는 테이블 전체 용량이 아니라 해당 평균값의 합계이며, 기본키·보조색인·행/LOB overhead 등은 별도다.
JDBC gzip은 전송 압축이며 Oracle의 영구 저장 압축을 켜는 설정이 아니다.
CAPACITY_READONLY_R2.sql은 해당 _1 검색표와 종속 인덱스/LOB의 현재 물리 할당량을 조회한다.
DBA_SEGMENTS 권한이 없으면 현 계정에서는 이 방법으로 확인할 수 없다. 다른 owner의 USER_SEGMENTS로 대체하지 않는다.
초기 적재 종류의 평균을 전량에 외삽하면 오차가 크며 벡터·다른표·UNDO/REDO/TEMP·복구 여유는 별도다.

로컬 검증
기존 계약/실행 TXT와 신규 재개 검사 통과 결과는 VALIDATION.json 참조.
실제 Dataiku/Oracle 대량 실행·속도 효과는 미검증. 운영 DB/DDL·MAIN·메일 변경 없음.
