GENOS 1차 성능 수정 — latency-20260928-r2 (2026-09-28)

버전 선택
기존 latency-20260928-r1은 진단 전용이었다. 이후 반입에는 이 R2 ZIP와 R2 실행 TXT를 사용한다.
R1이 적용된 기존 ~/DEV가 지원 기준이다. 파일 해시가 다른 checkout에는 쓰기 전에 거부한다.
전체 코드 교체 ZIP이 아니라 service.py + runtime 17개 파일의 부분 패치다.

수정
1. 문서 ID·팀(중복 문서 aliases 포함)·문서 분류를 한 번의 metadata SQL로 준비한다.
   절대 세대 경로, manifest 내용, DB/manifest 파일 상태에 결속한 프로세스 캐시다.
   이후 같은 worker·세대의 질문은 같은 불변 catalogue를 쓰고 팀 범위는 다시 확인한다.
   API의 중복 전체 JSON 조회와 팀 Query의 이중 계획도 제거했다.
2. 최종 bind_structure 결과를 불변 구조로 보존하고 성공한 문서의 부모·순환·span 검사를 재사용한다.
   부모 검사를 선형 탐색으로 바꿨으며 document→source 인덱스로 전체 source 순회도 줄였다.
   다른 팀 접근·원문 span 확인·파일 변경 감지·실패 거부는 유지한다.
3. stderr와 요청 공유 로그의 이벤트 write/flush를 별도 writer로 옮겼다.
   stderr 1,024건/2MiB, 요청 로그 512건/1MiB 한도이며 오류/최종 이벤트에 예약 용량을 둔다.
   포화 누락은 logging.queue.loss, 공유 쓰기 실패는 shared_live.write_failed로 기록한다.
   journal은 기존 동기 내구 저장을 유지한다. 강제 종료나 지속 저장 장애 시 진단 사본은 누락될 수 있다.
   공유 로그 파일 생성 자체는 기존 경로이며 전체 NFS 대기를 없앤 패치라는 의미는 아니다.
4. 무거운 계획 전에 기존 동시 요청 제한을 적용한다. 내부 lease를 세션에 전달하고
   실패·취소 시 한 번만 반환한다. 직접 open_session 호출도 동일하게 보호한다.
5. 기존 WARMUP도 catalogue와 최종 구조 검사를 준비한다. worker마다 최초 준비와 추가 메모리 비용이 있다.
6. FTS execute/first row/fetch/filter, 결과 위치 구성/페이지 프리뷰, journal begin/body/commit,
   모델 view 저장·구성/요청 생성/attempt 예약 시간을 기록한다.
   SQLite 버전·프로세스·mount 유형, 읽을 수 있는 cgroup CPU throttling delta도 남긴다.
   읽지 못하는 자원 값은 미확인이다. 질의나 원문을 새 진단 항목에 추가하지 않는다.

유지 사항 및 다음 단계
FTS OR 형태소, BM25 가중치, 동점 순서, 정확한 total/cursor, 전체 요청 deadline을 유지한다.
별도 20초 중단은 재도입하지 않는다. 데이터·용어집·NFS generation·CURRENT·모델을 바꾸지 않는다.
FTS 65초와 검색 후 약 50초의 원인은 아직 확정되지 않았다. 새 계측으로 구간을 확인한 뒤
읽기 DB 사본·검색 개선·원장 transaction 묶음을 다음 패치에서 결정한다.
첫/후속 요청의 GENOS 단축 시간이나 답변 품질은 외부 계약 테스트로 인증하지 않는다.

검증
로컬 WSL Python 3.14: 계약·회귀 135개, R1/R2 설치기 장애·원복 계약 16개 통과.
실제 R1 preimage 185개 파일로 만든 격리 Git fixture에서 적용·재적용·clean commit 코드 gate·
바이트 단위 원복 통과. GENOS 데이터 gate·Git push·코드서빙 리비전·현장 질의는 미확인이다.
Python 3.11 문법 검사, bash 문법 검사, ZIP inventory/해시 및 JS 제외 검사를 수행한다.

현장 적용 (Jupyter 터미널)
R2 ZIP와 R2 APPLY.txt를 ~/DEV/TRANSFER/code에 함께 둔다. TRANSFER 철자를 정확히 쓴다.
cd ~/DEV/TRANSFER/code
bash GENOS_LATENCY_20260928_R2_APPLY.txt

기본 반영 대상은 기존 ~/DEV다. 첫 단계부터 /tmp 또는 TMPDIR에 실행 로그와 종료 상태가 남는다.
적용 출력의 BACKUP_READY 경로와 apply receipt를 보존한다. 재실행은 ALREADY_APPLIED로 확인한다.
파일/엔진/스키마 hash 불일치가 나오면 중단하며 강제 덮어쓰기나 임의 rehash를 하지 않는다.

적용 후 변경된 service.py, runtime 파일, 엔진 manifest, 00_SYSTEM/PIPELINE.json을 검토해 commit한다.
TXT가 만든 ~/DEV/TRANSFER/latency-20260928-r2/applied-code.zip로 배포할 checkout를 검증한다.
아래 /actual/selected/generation은 현장에서 실제 선택된 절대경로로 바꾼다.
MODE=verify GENOS_GENERATION=/actual/selected/generation bash GENOS_LATENCY_20260928_R2_APPLY.txt

같은 검증 commit을 push하고 같은 generation의 새 코드서빙 리비전을 배포한다.
이번 패치는 워크플로우 Python 단계 변경이 없다. 현장 확인은 기존 워크플로우 테스트 화면에서 한다.
WARMUP → WARMUP_STATUS READY → 첫/후속 질문 및 다른 팀 질문 순서로 확인한다.
후속 요청에서 diagnostic_revision=latency-20260928-r2, catalogue.cache.hit,
sources.structure_ready checked_count=0을 확인한다. 다른 worker의 첫 요청은 별도 cold 준비다.
fulltext.sql.timings 및 journal.transaction.timings로 검색·쓰기 대기를 구분한다.

진단 요약
MODE=summary LOG_FILE=/actual/request.log bash GENOS_LATENCY_20260928_R2_APPLY.txt
이 요약은 허용한 수치·상태만 출력한다. 전체 로그에는 기존 상세 보고 정책의 질문/원문이 있을 수 있다.
중첩 step 시간을 합산하지 않는다. CPU가 낮다는 이유만으로 NFS 원인으로 단정하지 않는다.

원복
/actual/backup-directory를 적용 로그의 BACKUP_READY 경로로 바꾼다.
MODE=rollback ROLLBACK_FROM=/actual/backup-directory bash GENOS_LATENCY_20260928_R2_APPLY.txt
R2 적용 전 코드와 pins로 복원한다. 이후 수정된 파일은 보호하며 자동 원복을 거부한다.
이미 배포했다면 이전 검증 코드서빙 리비전으로 별도 복귀한다. generation 원본은 바꾸지 않는다.
