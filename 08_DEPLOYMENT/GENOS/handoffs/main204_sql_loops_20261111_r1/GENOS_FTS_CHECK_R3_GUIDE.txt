본문 검색 현장 검사 R3 (읽기 전용) — 2026-11-11
현장 질문에서 첫 본문 검색 SQL 2개(rank_top_sources 2.6초, _projection 2.3초)가 왜 오래 걸리는지 단계별로 잽니다.
같이 MAIN204의 조문 연결 목록 조회가 현장에서 예전과 같은 결과를 내는지, 얼마나 빨라졌는지도 확인합니다.
SELECT만 보냅니다. 쓰기·모델 호출 없음. SQL 문장·바인드 값·원문·인증 정보는 출력하지 않습니다.

1. 실행 (MAIN204 적용 뒤, TRANSFER 폴더에서)
  bash ./GENOS_FTS_CHECK_R3.txt
  결과는 화면과 같은 폴더의 GENOS_FTS_CHECK_R3_RESULT.txt 에 남습니다. 화면을 사진으로 보내 주세요(약 60줄, 1~2장).
  약 1~3분. 질문 시험이 없을 때 한 번만 실행해 주세요.

  - 이 터미널에 서빙 리비전과 같은 ORACLE_ORDS_* 환경변수가 있어야 합니다. 없으면 "ORDS 연결 정보를 읽지 못했습니다"가 나옵니다.
    그때는 서빙 설정값을 export 한 뒤 다시 실행해 주세요.
  - GENOS_ORACLE_TABLE_MAPPING 이 없으면 gold, GENOS_ORACLE_GOLD_OWNER 가 없으면 SIDDS 로 실행합니다.
  - 채널은 DP_QUERY_CHANNEL, 없으면 main 을 씁니다. 다르면 --channel 이름.
  - 코드 위치가 ~/DEV·/workspace 가 아니면 --code-root 폴더.
  - 파이썬 패키지가 없다고 나오면 PYTHON=<서빙 python3 경로> bash ./GENOS_FTS_CHECK_R3.txt
  - 다른 검색어로: bash ./GENOS_FTS_CHECK_R3.txt --set '자기자본|1천억원 이상' --set '주주총회 결의'  (| 는 검색어 묶음 구분)

2. 무엇을 재나 (검색어 4세트마다)
  낱말별 조문 수   검색 표에서 낱말이 나오는 조문 수. 묶음마다 가장 드문 낱말부터 읽습니다.
  드문 낱말 행 → +나머지 낱말 → +묶음 일치 → 조문 길이 행 → +점수 계산
                   서빙 SQL을 단계마다 잘라 잰 시간. (+)가 그 단계에서 늘어난 시간입니다.
  실제 상위 검색   서빙이 쓰는 rank_top_sources 호출 그대로
  같은 검색 다시   Oracle 캐시가 데워진 뒤 시간
  점수 묶음 조회   서빙이 쓰는 _projection 호출 그대로
  → 가장 오래 걸린 부분   단계 중 가장 많이 늘어난 곳. 전체 문장보다 오래 걸린 단계(단독 실행에서 실행 계획이 달라진 경우)는 비교에서 뺍니다.
  [연결 목록]      검색 결과의 조문 최대 6개로 예전·지금 조회를 나란히 재고 결과가 같은지 봅니다.

3. 결과로 판단할 것
  드문 낱말 행이 가장 큼          → 낱말 하나가 읽는 행이 많음. 재색인(FTS_CHECK_R2_GUIDE.txt 4번) 후보
  +나머지 낱말이 가장 큼          → 후보 조문이 많음. 후보 수를 줄이는 수정 후보
  +묶음 일치가 가장 큼            → 원문 글자 확인(CLOB)이 느림
  조문 길이 행이 가장 큼          → 조문 길이 행을 더 좁게 읽는 수정 후보
  키 확인이 "없음"                → MAIN204가 연결 목록을 예전 방식으로 읽습니다(동작은 정상, 빨라지지 않음). 이 결과를 알려 주세요.
  연결 목록 "다름"이 있음          → 알려 주세요. 수정이 필요합니다.

4. 로컬 시험
  실제 로컬 Oracle의 작은 게시본 + ORDS 모양 연결로 전체 실행 통과(검색어 2세트, 연결 목록 6개 결과 같음, 쓰기 없음).
  현장 Oracle에서는 아직 실행하지 않았습니다.
