왜 최근 수정 이후에도 같은 오류가 남았나
사진에는 모델 HTTP 200 이후 SELECT에서 원문 의존 조사 인용 검증이 최초/교정 모두

중단한 흐름이 보인다. 이전 MAIN62 변경은 JSON/스키마 공통 복구를 추가했지만,
investigation_scope의 원문 의존 조사 계약은 이전 MAIN61과 같았다.
원문 0개 상태에서도 DEPENDENCY가 선택지에 있었고 거절 원인이 일반 문구여서
같은 부적절한 인용을 반복할 수 있었다. MAIN62 선택 코드에서 이 경로를 모의 재현했다.
사진만으로 현장 배포 해시를 확정할 수는 없다.
직전 재현 근거: ../20261014-main62-dependency-recovery-review/FINDINGS_UTF8.txt

계획에 따라 적용한 수정
1. investigation_scope.py
   현재 전달한 원문이 없으면 DEPENDENCY를 선택지에서 제외한다. 자료 미리보기,
   빈 원문, 과거 원문은 현재 원문의 근거가 되지 않는다.
   오류에는 탐색 행·필드·대상·허용 원문 ID를 붙이고 독립 오류를 함께 수집한다.
   중복/누락 대상, 잘못된 쟁점 ID, 요청 인용, 필요 내용, 원문 ID/인용을 구분한다.
2. law_navigation.py
   기존 최대 1회 교정에 현재 원문 수·허용 조사 관계·원문 ID와 구체 오류를 전달한다.
   바깥 anyOf만 가리키던 스키마 오류는 같은 원래 스키마에서 필드별로 다시 수집한다.
   원문 없는 DEPENDENCY를 서버가 DIRECT로 바꾸거나 근거를 만들어 통과시키지 않는다.
3. output_contract.py
   InvestigationPending에 저장된 실제 하위 거절 원인을 최종 진단에 유지한다.
   반복 실패로 교정이 끝났으면 repairable=false로 표시한다.
   명시된 상태/해시/구현 오류가 있으면 단순 조사 미완료로 덮지 않는다.
4. case_repository.py — 추가 검사에서 발견한 결함
   동일 실패 요청을 재전송하면 source-request-route를 새 run에서 불필요하게
   한 번 더 호출하던 경로를 수정했다. 같은 요청 fingerprint와 principal/session,
   기존 PENDING goal을 확인해 resume_goal이 정해진 경우에만 분류를 생략한다.
   일반 실행과 숏컷 실행이 사용하는 공통 진입점에 적용했다.
   이후 기존 상태·바인딩·권한·재개 검증은 그대로 수행한다.

보존한 정상 동작

DIRECT의 근거로 쓰이지 않는 추가 주석 호환을 보존했다.

성공 응답 재사용, 미확보 원문을 부족 상태로 보존하는 동작을 유지했다.
