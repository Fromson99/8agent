도메인 프로필 기반 판단 축적 — 작업 코드 사용·검증 범위
2026-10-29

1. 적용 상태
기존 ontology-work CLI, WORK/EVT/PUB/HEAD/ANC 저장소와 Streamlit 관리 화면에 새 경로를 연결했다.
프로필 등록/승인 → 원본 수집 → 공통 LLM 구조화 → 원문 대조·누적 → 내용 승인 → 게시 준비 → 소비 검증 → 활성 전환이다.
기존 ontology-work-v1 시나리오는 그대로 읽고 게시한다. 새 typed graph를 v1 components/text/requires로 변환하지 않는다.
이 작업은 MAIN 선택 포인터·운영 DB/데이터 세대·GENOS 배포를 변경하거나 실제 모델을 호출하지 않았다.
작업 도중 별도 ADR1204가 MAIN117→MAIN118을 선택했다. 그 선택을 보존했으며 도메인 프로필 기능은 선택 MAIN에 승격하지 않았다.
아래 기능은 로컬 작업 코드다. 새 게시본의 실제 모델 판단 품질은 미인증이다.

2. 주요 진입점
06_TOOLS/pipeline.py ontology-work --help
구현: 02_BACKEND/semantic_runtime/ontology_work/
비활성 템플릿: 00_SYSTEM/ONTOLOGY_PROFILES/domain-profile-v1.json, business-profile-v1.json
두 제품 스키마: 00_SYSTEM/SCHEMAS/ontology-{domain,business}-profile-v1.schema.json
설계 예시 원본은 바꾸지 않았다. DESIGN_ONLY 예시는 제품 loader가 거절한다.
제품 템플릿도 DRAFT/runtime_enabled=false다. SQL 승인 없이 모델 작업이나 게시에 사용하지 않는다.
업무 부모 sha256은 semantic_runtime.contracts.digest의 canonical JSON 해시다. 설계 문서의 파일 바이트 해시와 구분한다.

설정 없이 검증만 실행:
.venv/bin/python 06_TOOLS/pipeline.py ontology-work profile-validate --input 00_SYSTEM/ONTOLOGY_PROFILES/domain-profile-v1.json --business 00_SYSTEM/ONTOLOGY_PROFILES/business-profile-v1.json

나머지 명령은 기존 GENOS_RAG_ONTOLOGY_CONFIG의 ontology-connection-v1 설정을 사용한다.
CLI의 GENOS_ONTOLOGY_OPERATOR는 운영자가 설정한 인증 주체이며 설정의 operators에 존재해야 한다.
화면은 기존 Dataiku browser session 인증 또는 로컬 운영자 identity를 따른다. 업로드 JSON에 actor를 넣어 권한을 얻을 수 없다.
source_reader는 운영자 document_ids와 원문 판본/전체 unit 본문을 매번 검증한다.

기존 설정에 추가할 domain_profile 예:

  "acl_ref": "운영자-권한-판본-ID",

이 예는 자리표시자이며 운영 설정 파일이 아니다. 최신 파일/데이터 세대를 자동 검색하지 않는다.
원격 Oracle reader는 기존 authenticated request의 Glossary 포트를 DomainWorkflow에 주입할 수 있다.
현재 설정 factory의 새 도메인 작업 연결은 명시적인 sqlite-local 용어집에 한정한다. 현장 Oracle mapping/실행 주체·S3 적재는 미검증이다.
GENOS 계산은 model.kind=genos일 때만 활성화된다. 로컬 외부 모델 자동 연결은 없다.

3. 작업 순서
profile-register --input DOMAIN.json [--business BUSINESS.json] [--revision 기존작업판본]
  검증한 프로필과 생성 prompt/schema/검증·조립 명세를 저장한다. 결과의 bundle_id/revision/work_hash를 보관한다.
profile-review --bundle ID --revision N --work-hash HASH --approve --reason '실제 검토 의견'
  정확한 프로필 작업 판본 승인. --approve를 빼면 반려한다.
import-raw --input RAW.json
  RAW.json: {"payload": 임의 JSON 또는 문자열, "event_id":"원본-ID", "run_id":"실행-ID", "sequence":0, "format_description":"선택 설명"}
  수동 가져오기의 확보/전달 영수증은 항상 빈 목록이다. 본문 속 '읽었다'는 문장으로 영수증을 만들지 않는다.
export-journal --journal 등록실행ID --after 마지막seq
  운영자가 등록한 정확 run binding을 검사하고 journal_storage reader로 압축을 복원한다.
  한 페이지 최대32이벤트; 반환 checkpoint 이후부터 다음 수집. heads만 추출하지 않아 철회·과거 판단이 보존된다.
normalize --bundle raw-ID --input NORMALIZE.json
  {"profile_id":"dp-ID", "profile_work_hash":"정확-승인-work-hash", "labels":["조회할 실제 표기"]}
  labels 생략/빈값은 원본 문자열·토큰의 최대16개 literal 후보 조회다. 동의어/정본을 생성하지 않으며 생략 수를 남긴다.
  lookup/inspect/entry_links 결과와 source/node 기반 concept ID·snapshot을 보존한다.
  라벨 후보의 검토·연결 의미는 LLM이 판단한다. 없는 ID를 수락하거나 다의어를 자동 동일시하지 않는다.
accumulate --input ACCUMULATE.json
  {"bundle_id":"cb-kb-선택ID", "expected_revision":0, "profile_id":"dp-ID", "profile_work_hash":"HASH", "observation_ids":["obs-ID"], "originals":[{"id":"S1","anchor":기존-원문-anchor,"text":"검증된-unit-전체본문"}]}
  기존 묶음 보완은 expected_revision을 현재 작업 판본으로 지정한다. 오래된 결과는 저장하지 않는다.
  비교는 용어/원문 좌표 후보 합집합이며 미조회 영역을 명시한다. 같은 concept ID는 동일 규칙의 증명이 아니다.
  save-accumulation --input ACCUMULATE.json --proposal PROPOSAL.json은 같은 검증으로 수동 검토 초안을 저장한다.
domain-preview --bundle cb-kb-ID
  타입/간선/의존/예외 closure, 정확 문장과 typed slots, 원문 인용, 미확인을 함께 표시한다. 수식을 실행하지 않는다.
domain-review --bundle ID --revision N --work-hash HASH --approve --reason '실제 원문 검토 의견'
  APPROVED는 사람의 내용 승인이다. 문장과 typed slot의 의미 일치까지 자동 증명한 것이 아니다.
stage-publication --bundle ID --revision N --work-hash HASH --expected-sequence 현재head순번
  승인 판본을 PUB/ANC에 저장한다. HEAD는 이동하지 않는다. 같은 결과의 재요청은 같은 게시 ID를 반환한다.
verify-publication --publication-id ID
  저장 JSON 재조회·현재 원문/용어집·결정론 재컴파일·소비용 binding을 검증해 receipt를 반환한다.
  이 JSON을 RECEIPT.json에 저장한다. 실제 모델 전달/claim사용은 false로 명시한다.
activate-publication --publication-id ID --expected-sequence 현재head순번 --receipt RECEIPT.json
  현재 원문·용어집 재검증과 SQL CAS 후에만 활성화한다.
  더 새 작업 판본이 생긴 오래된 게시본은 거절한다. 의도적인 이전 승인본 복구만 --rollback으로 명시한다.
withdraw --bundle ID --expected-sequence 현재head순번
  기존 명령으로 게시 중지. 기존 v1 즉시 게시 publish는 새 assembly package를 거절한다.
domain-status [--bundle ID] [--revision 과거판본] [--prefix raw-/obs-/job-/dp-/cb-kb-]
  정확한 작업·실패·현재/과거 판본을 확인한다. 전역 목록은 원문 권한/namespace를 필터링한다.
reconcile-result --work-hash SAVE_UNCONFIRMED의객체해시 --revision 현재작업판본
  보관한 동일 결과만 다시 저장한다. 모델을 재호출하지 않는다.

4. 보존·실패 계약
원본 locator는 canonical payload hash + JSON Pointer + Unicode code point [start,end) + 정확 인용이다.
원래 statement/reason/purpose/scope는 정확 인용을 보존하며 없는 값은 NOT_RECORDED다.
semantic_elements는 관찰의 의미 표현이고 법률 정답이 아니다.
MAIN123부터 누적 전에 SOURCE_ANALYSIS가 원문만 독립 분석한다. 이 요청에는 과거 관찰·기존 지식·용어 후보가 없다.
분석의 text는 모델의 해석, quote는 원문의 정확한 연속 구절이며 서로 구분한다.
그다음 누적 요청에서 원문 분석과 관찰을 비교해 지지/반박/부분/미확인을 제안한다.
모델이 선택한 규범의 행위/양태와 조건을 기존 canonical 그래프에 조립하고 선택·원본·결과 영수증을 보존한다.
새 정규화 요청의 recorded_reason/recorded_purpose는 명시된 원기록의 역할 증거가 있을 때만 작성하며, 부재는 null이다.
서버는 실제 필드명·인용 위치를 확인하고 null을 NOT_RECORDED로 저장한다. 특정 단어 목록으로 이유/목적을 판정하지 않는다.
비교 reason/coverage.reason은 새 처리 설명이며 원래 기록의 reason과 구분한다. 과거 저장 형식과 프로필은 호환한다.
coverage는 모든 입력 위치를 분류하나 의미 완전성의 증명은 아니다.
추출 판본은 입력·프로필·용어 후보·모델 receipt에 결속한다. 동일 event는 반복 구조화해도 독립 의견이 되지 않는다.
과거 관찰·반박·철회는 ledger와 비교 이력에 남는다. SAME은 그래프 불변, 다른 판본/범위는 별도 묶음이다.
이전 묶음이 없는 최초 누적 요청에는 SAME을 선택지로 제공하지 않는다. 기존 서버의 그래프 동일성 검사는 유지한다.
프로필 hash에는 부모·설정·생성 산출물·스키마·컴파일 코드가 포함된다.
자유 코드/SQL/eval, 임의 계산식 실행, 자동 신규 용어 승인, 빈도 다수결 채택은 제공하지 않는다.

각 NORMALIZE/SOURCE_ANALYSIS/ACCUMULATE 단계는 최초+보완 최대2호출, 단계 deadline360초, 개별 절대기한180초다.
따라서 새 누적은 원문분석+누적의 두 단계가 필요하며, 동일 입력의 완료 작업은 기존 규칙대로 재사용한다.
새 정규화부터 누적까지는 최소3회, 각 단계 보완이 모두 필요한 경우 최대6회다. 실험의 전체 물리 호출 한도는 별도로 적용한다.
SENT 전에 SQL에 작업 소유 토큰·시도·deadline을 저장한다. 같은 작업의 동시 호출은 하나만 진행한다.
같은 허용 자료로 한 번 보완한다. 원문 분석/누적은 지적된 의미 연결 불일치도 수정할 수 있지만 원래 관찰을 고쳐 쓰지 않는다.
원문·권한·용어집 변경은 BINDING_FAILED이며 모델 보완하지 않는다.
확정 HTTP 거절은 HTTP_REJECTED, 불완전 응답은 INCOMPLETE_RESPONSE, 통신 결과 불명은 UNKNOWN으로 기록한다.
SENT/UNKNOWN은 자동 재호출하지 않는다. RESERVED/REPAIR_READY/RESPONSE_RECEIVED는 저장된 상태와 잔여 예산으로만 재개한다.
모델 결과 후 DB 저장 실패는 SAVE_UNCONFIRMED이며 결과 객체 해시를 보존한다.
출력 토큰 상한은 추가하지 않았다. 운영 GENOS 어댑터는 한 물리 요청만 전송하며 별도 공급자 전환을 만들지 않았다.
설계의 E1/E2 각24건·외부 모델49회 실험 예산은 별도 실험 계획이다. 제품의 단계별2호출과 혼동하지 않는다.

5. RAG와 화면
온톨로지 기본 OFF와 DB없음/장애의 일반 RAG fallback을 유지한다.
새 요청은 원문 도착 시 활성 게시물만 조회하고, 문서 권한과 현재 판본을 확인한다.
ASSESS에는 현재 원문에 결속된 assembly_catalog를 보낸다. 필요한 전체 unit이 없으면 해당 path를 withheld한다.
제출·전달·최종claim·답변은 별도 상태다. 원문의 root만으로 하위 범위를 확보했다고 표시하지 않는다.
기존 requirement review와 accepted-content-v1 최종 조립을 유지한다. runtime에서 그래프를 다시 컴파일하지 않는다.
생성용 prompt/output_schema는 runtime package에 넣지 않는다. 승인 descriptor/hash와 typed graph·조립 결과는 유지한다.
기존 Streamlit 온톨로지 관리에서 '도메인 프로필·판단 축적'을 선택한다.
기존 90_RUNTIME의 Streamlit 1.50.0 AppTest로 실제 위젯과 rerun을 실행해 승인→게시준비→소비확인→활성→재조회를 확인했다.
이 검사는 영속 SQLite 작업 저장소를 사용한다. 실제 브라우저 화면의 시각 검토와 Dataiku 브라우저 인증 연동은 별도다.
