MAIN168 — 질문 처리 RECALL 단계 HTTP 500(QUERY_SQL_RESULT_BUDGET) 수정 (MAIN167 대체)

왜: MAIN166 적용 후 ORA-22806은 해결됐고, 그다음 단계 RECALL에서 QUERY_SQL_RESULT_BUDGET: use bounded consumer pages로 멈췄습니다 (memory_rag.py:198 → oracle_query_index.py:54 → oracle_query_db.py:185). RECALL 결과 기록에 요청 범위의 모든 원문 ID 목록을 넣고 있었는데(쓰는 곳 없음), Oracle에서는 이를 위해 범위 전체를 읽다가 한 조회 1만 행 한도에 걸립니다. MAIN167에도 같은 코드가 있어 MAIN167만 적용하면 같은 500이 납니다.

수정 (MAIN167 그대로 + 제품 2파일)

  • memory_rag.py: RECALL 결과에서 전체 원문 ID 목록 제거(검색·원문 선택·답변 내용 변화 없음).
  • unit_relations.py: 별표 인용을 별도 별표 파일에 연결할 때 범위의 모든 원문을 읽던 것을, 문서 이름으로 찾고 연결된 파일 하나만 읽도록 변경(연결 결과 동일).

MAIN167 대비 34파일(제품 2 + SQL 출처 메타 1 + PIPELINE + 엔진 pin 30). 실행 SQL 642개·매핑·워크플로우는 MAIN167과 같습니다. 환경변수는 지금 값 그대로, 새 환경변수 없음.

적용: 같은 TRANSFER 폴더에 ZIP과 TXT를 두고 그 폴더에서 bash MAIN168_ONECLICK_R1.txt → MAIN168_ONECLICK_DONE, MAIN168_EXIT=0 확인 → status / stage → commit → bash MAIN168_ONECLICK_R1.txt gate-code → push → 새 코드서빙 리비전 배포. 워크플로우(MAIN168_WORKFLOW.py)는 MAIN167과 같은 바이트라 바꿀 필요 없습니다.
