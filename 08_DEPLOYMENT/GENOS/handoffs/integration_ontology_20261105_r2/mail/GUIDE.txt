과제3·과제5 통합시험 온톨로지 R2 — 삼성메일 첨부 실행 안내

이번 메일의 정확한 첨부 파일
1. INTEGRATION_ONTOLOGY_B03_B05_R2.zip
2. GENOS_ONTOLOGY_SQLITE_R2.txt
3. DATAIKU_ONTOLOGY_INSERT_R2.txt
4. GUIDE.txt (이 안내)
5. VALIDATION.json (최종 전달·검증 결과)
6. SHA256SUMS.txt

검증한 ZIP과 실행 TXT는 기존 R2 바이트 그대로다. ZIP 안 GUIDE의 이전 실행 파일명 표기는
이 별도 안내의 GENOS_ONTOLOGY_SQLITE_R2.txt / DATAIKU_ONTOLOGY_INSERT_R2.txt를 기준으로 읽는다.
R1 로컬용 안내 대신 이번 R2의 실행 TXT를 사용한다. ZIP을 다시 ZIP으로 묶지 않는다.

지금 할 작업 — GENOS NFS SQLite
1) GENOS 코드스페이스의 ~/DEV/TRANSFER/에 ZIP과 GENOS_ONTOLOGY_SQLITE_R2.txt를 올린다.
2) 실제 코드 checkout은 ~/DEV이다. 링크라면 설치기가 실제 경로로 해석한다.
3) 코드스페이스 터미널에서 실행:
   cd ~/DEV/TRANSFER
   bash GENOS_ONTOLOGY_SQLITE_R2.txt
   코드스페이스에 GENOS_GENERATION이 없다는 메시지가 나오면, 사진의 코드서빙 값 그대로
   다음 명령의 꺾쇠 부분만 실제 절대경로로 바꾸어 실행한다:
   IT35_GENERATION='<코드서빙의 기존 GENOS_GENERATION 절대경로>' bash GENOS_ONTOLOGY_SQLITE_R2.txt
4) 원문 store 해시와 61단위 확인 → 원문 불변 → 온톨로지 사본/설정 배치 →
   실제 checkout 부분 패치와 해당 pin 대조 → 24묶음/46경로 소비자 확인 순서로 실행한다.
5) 완료 표시는 GENOS_ONTOLOGY_PREPARED다. ~/DEV/TRANSFER/ONTOLOGY_R2_RESULT/에
   INSTALL_RECEIPT.json, DEPLOY_CODE.zip, SERVING_ENV.txt, HANDOFF.json, 코드 백업이 남는다.
6) git diff --check와 변경 내용을 검토하고 필요한 변경을 commit한다. 기존 다른 staged 변경은 구분한다.
   배포 게이트 명령은 실행 TXT 끝 주석에 있다. PASS한 commit을 push하고 새 코드서빙 리비전을 적용한다.
   코드서빙에서 기존 GENOS_GENERATION / GENOS_RUNTIME_DIR은 유지하고
   DP=nfs, GENOS_RAG_ONTOLOGY_ENABLED=on, GENOS_RAG_ONTOLOGY_CONFIG=SERVING_ENV.txt의 실제 절대경로를 설정한다.
   코드스페이스 export만으로 코드서빙 환경변수가 바뀌지 않는다.
7) 새 리비전에서 원문 출처 열기와 과제3/5 실제 질문을 확인한다. 설치 완료와 현장 응답 통과는 별개다.

중단/재개와 원복
- 같은 파일로 다시 실행하면 동일 NFS 사본은 재사용한다. 기존 다른 내용/코드 수정은 덮어쓰지 않는다.
- 코드 부분 반영 중 중단됐으면 HANDOFF/출력에 나온 unpacked 경로의 genos_install.py와
  --code-root <실제 checkout> --output <기존 ONTOLOGY_R2_RESULT 경로> --rollback-code로 해당 백업을 복구한다.
  HANDOFF.json 생성 전 중단이면 터미널 출력/TRANSFER의 이번 ontology-r2-* 압축 해제 경로를 사용한다.
  후속 수정이 있으면 덮어쓰지 않으며, 복구 후 재시도에는 새 IT35_OUT 경로를 지정한다.
- 시험을 끄려면 코드서빙 GENOS_RAG_ONTOLOGY_ENABLED=off를 적용한다.
- 이전 코드 리비전과 기존 온톨로지 설정을 보관한다. 원문 generation은 변경/삭제하지 않는다.

내규 포함 범위
위험관리위원회운영준칙 단독 답변18문항 + 금융회사의 지배구조에 관한 법률과 비교1문항 = 19개.
로컬 등록 내규 원문을 직접 대조한 10묶음/17개 경로가 ZIP에 이미 들어 있다.
B05-27의 출처 열기 화면 검증은 별도 현장 항목이다. 정답검토표.csv는 ZIP의 payload/에 있다.
현장에 동일 판본·구조의 원문이 있으면 그대로 연결된다. 설치기가 문서ID·판본·조항/블록·본문해시를
대조하므로 현장 일치를 미리 가정하고 지식을 강제 적재하지 않는다.
새 Qwen 답변 시험은 0회이며, 이번 정답 확인은 등록 원문 대조다.

나중에 할 작업 — Dataiku Oracle
1) 같은 ZIP을 Dataiku 기존 관리 폴더에 그대로 올린다.
2) 해당 프로젝트 Python 노트북에 DATAIKU_ONTOLOGY_INSERT_R2.txt 전체를 한 셀로 붙인다.
3) FOLDER_ID는 ZIP을 올린 관리 폴더 ID, ORACLE_CONNECTION은 기존 Oracle SQL 연결명으로 바꾼다.
   PROFILE=B003은 운영 IDD_B003, PROFILE=G19는 개발 LGL_G19다.
   SOURCE_OWNER=SIDDS / ONTOLOGY_OWNER=SIDDA / AGENT_OWNER=SIDDA는 실제 등록 owner와 대조한다.
   DATASET_VERSION 빈 값은 정확한 다섯 판본이 모두 있는 유일한 세대만 자동 선택한다.
   없거나 복수이면 사용 중인 원문 게시의 dataset version을 직접 지정한다.
4) 기존 대상 5표가 있어야 한다. 없으면 ZIP의 ORACLE_TABLES_B003.sql 또는 ORACLE_TABLES_G19.sql을
   실제 등록 구조와 대조하여 먼저 생성한다. 적재 셀은 자동 DDL을 하지 않는다.
5) 셀을 실행한다. 읽기 전용 사전검사만 하려면 APPLY=False, 실제 적재는 기본 APPLY=True다.
6) 완료 표시는 ORACLE_IMPORT_COMPLETE. 영수증은 같은 관리 폴더의 _integration_ontology_r2/ 아래다.
   승인 작업 JSON은 objects/에 보존한다. 같은 셀 재실행은 동일 데이터를 대조하여 재사용한다.
   실패/응답유실은 자동 재전송하지 않는다. 영수증 확인 후 명시 재실행한다.
   철회/다른 내용/부분 저장 충돌은 보존하고 중단한다. 원문에 INSERT하지 않는다.
