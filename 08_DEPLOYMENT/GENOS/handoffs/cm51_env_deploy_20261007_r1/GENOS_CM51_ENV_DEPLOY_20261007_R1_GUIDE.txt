GENOS CM51 환경변수·배포 순서 보충 안내 R1 — 2026-10-07

대상: 이미 GENOS_CM_SHORTCUT_DATA_20261007_R4의 check/apply/verify를 끝낸 현장.
코드·데이터 실행 파일은 기존 최종 R4를 그대로 사용한다.
이번 첨부는 새 코드 패치가 아니라 환경변수와 후속 배포·등록 안내다.
CM 데이터 인계 R1/R2/R3로 돌아가지 않는다. 기존 R4 ZIP을 다시 덮어 풀지 않는다.

사진으로 확인한 상태
- CODE_APPLIED, ENGINE_BINDINGS PASS, CORE_SHORTCUT_ALL_PROFILES PASS, EXIT=0.
- 코드스페이스의 코드 적용·검증은 성공했다.
- CM 51건 data-import/data-verify, Git push, 새 코드서빙 리비전, workflow 질문 성공은 사진에서 미확인이다.
- CM_DATA_EXIT=0은 실행한 명령의 종료 상태다. CM 51건 등록 완료를 뜻하는 별도 표시는 아니다.
- R4 ZIP/RUN 해시는 OK. GUIDE_UTF8.txt/VALIDATION_SUMMARY.txt 두 문서는 FAILED였다.
  이번 메일에 같은 R4 원본 두 문서를 다시 첨부했다. 현장 문서가 다른 이유는 미확인이다.

0. 어디에 환경변수를 넣는가

현재 터미널의 export: 그 터미널과 여기서 실행하는 반입 명령에 적용된다.
코드스페이스 환경변수 설정: 개발 컨테이너용이다. 기존 터미널에는 export를 사용하면 명확하다.
코드서빙 새 리비전 환경변수: 배포된 실제 서비스용이다. 코드스페이스 값이 자동 전달된다고 가정하지 않는다.
분리 Python 워크플로우의 TEAM_ID/GENOS_MEMORY_ENABLED/코드서빙 주소·인증은 워크플로우 설정이다.
이번 CM 패치 때문에 기존 실행 모드, 시작 명령, workflow Python 단계를 바꿀 필요는 없다.

변수별 의미·필수 여부·설정 위치

GENOS_DEV_ROOT
  코드가 적용된 기존 Git checkout 폴더. 현재는 $HOME/DEV.
  터미널용. 생략하면 RUN은 GENOS_DEV 또는 $HOME/DEV를 사용한다.
  사진의 ~/DEV -> /workspace 링크는 정상적으로 해결됐다.

GENOS_GENERATION
  실제 서비스가 선택한 원문·navigation·fulltext generation 폴더의 절대경로.
  manifest.json 파일 경로가 아니다.
  gate/data-check/data-import/data-verify에는 필수. 터미널과 코드서빙 리비전에 같은 실제 값을 사용한다.
  사진의 값:
  /nfs-root/diamo/8-agent/term-releases/financial-risk-success-20261005-schema-r2/generation
  이 값이 현재 코드서빙 설정과 같은지 확인한다. 다르면 실제 선택된 경로를 사용한다.

GENOS_RUNTIME_DIR
  서비스가 사례·실행 기록을 보관하는 영속 runtime 폴더.
  이전 확인 값: /nfs-root/diamo/8-agent/runtime
  코드서빙 리비전에 설정한다. 터미널에서도 같은 실제 값을 사용한다.

GENOS_STATE_DIR
  사례 SQL DB를 runtime과 다른 저장소에 둘 때 사용하는 별도 state 폴더.
  선택 사항. 기존 서비스가 미설정이면 이번에도 추가하지 않는다.
  기존 서비스가 사용 중이면 반입 터미널에도 정확히 같은 값을 사용한다.
  임의의 새 폴더를 지정하면 기존 서비스가 읽는 DB와 달라질 수 있다.

CM_CODE_BACKUP
  R4 apply가 출력한 BACKUP= 뒤의 전체 절대경로.
  코드 backup receipt와 APPLIED_CODE.zip이 있는 폴더다.
  gate/코드 undo에 필수. 터미널용이며 코드서빙 환경변수에는 넣지 않는다.
  사진에서 전체 식별자를 확정할 수 없어 임의로 채우지 않았다.

CM_RUNTIME_DIR
  CM 자료를 등록할 runtime. 실제 서비스의 GENOS_RUNTIME_DIR과 같은 값이다.
  모든 data 명령에 필수. 터미널용. GENOS_STATE_DIR도 서비스와 맞아야 한다.

CM_PRINCIPAL_FILE
  등록 대상 user_id/team_id/authenticated/document_ids를 적은 JSON의 절대경로.
  모든 data 명령에 필수. 터미널용. 경로 설정 뒤 실제 파일을 만들어야 한다.
  로컬 jin/CM을 현장 사용자·팀으로 복사하지 않는다.

CM_RECEIPT_FILE
  data-import가 생성하는 등록 receipt JSON의 절대경로.
  모든 data 명령에 필수. 터미널용. 첫 등록 전에는 파일이 없어도 된다.
  대상 사용자·팀마다 별도로 보존한다. 코드 backup receipt와는 다른 파일이다.
  재실행/검증/데이터 retire에 사용하므로 삭제하거나 편집하지 않는다.

2. 실제 등록 대상 principal 파일 생성

user_id: workflow가 코드서빙에 전달한 실제 요청의 user_id.
로그인 이름을 추측해 넣지 않는다. 현재 멀티턴 workflow는 u-<SHA256> 형태로 전달할 수 있다.
team_id: 실제 요청의 team_id. workflow 환경변수 TEAM_ID가 있으면 그 설정이 입력보다 우선한다.
예: risk_team 또는 financial_team은 예시일 뿐이며 현재 요청과 동일해야 한다.

아래 코드에서 user_id/team_id 두 문자열을 실제 값으로 바꾼다.
이미 인증된 대상 사용자의 현재 팀별 문서 선택값을 읽는다.
authenticated=true는 확인한 대상의 기록이며 플랫폼 인증이나 ACL을 부여하지 않는다.
현재 기본 진입 경로의 문서 범위는 select_documents를 사용한다.
별도 사용자 문서 ACL을 적용 중인 환경에서는 JSON의 document_ids도 그 실제 허용 범위 내여야 한다.
CM 근거 21문서가 그 범위에 모두 포함되는지는 다음 data-check가 확인한다.

```bash
PYTHONPATH="$GENOS_DEV_ROOT/02_BACKEND" python3 - <<'PY'
import json, os
from pathlib import Path
from semantic_runtime.storage import Store
from semantic_runtime.team_scope import select_documents

user_id = "실제 요청의 user_id"
team_id = "실제 요청의 team_id"
if user_id.startswith("실제") or team_id.startswith("실제"):
    raise SystemExit("user_id와 team_id를 실제 요청 값으로 바꾸세요.")

store = Store(Path(os.environ["GENOS_GENERATION"]))
try:
    document_ids = select_documents(store, team_id)
finally:
    store.close()

target = Path(os.environ["CM_PRINCIPAL_FILE"])
value = {
    "user_id": user_id,
    "team_id": team_id,
    "authenticated": True,
    "document_ids": document_ids,
}
if target.exists():
    if json.loads(target.read_text(encoding="utf-8")) != value:
        raise SystemExit("기존 principal 내용이 다릅니다. 원본을 보존하고 대상별 새 파일명을 사용하세요.")
    print("기존 동일 principal 사용:", target)
else:
    with target.open("x", encoding="utf-8") as f:
        json.dump(value, f, ensure_ascii=False, indent=2)
    print("생성:", target)
print("대상:", user_id, team_id, "문서 수:", len(document_ids))
PY
```

4. 실제 push 대상 checkout의 코드 commit/gate/push

Git 변경 목록을 검토한다. 원문·DB·키·TRANSFER의 반입 기록을 Git에 넣지 않는다.
아래 stage 코드는 R4 backup receipt에 기록된 36파일만 선택한다.
기존에 staged된 다른 파일이 있는지도 git diff --cached --stat에서 확인한다.

```bash
cd "$GENOS_DEV_ROOT"
git diff --check
git status --short

python3 - <<'PY'
import json, os, subprocess
from pathlib import Path
root = Path(os.environ["GENOS_DEV_ROOT"]).resolve()
backup = Path(os.environ["CM_CODE_BACKUP"])
receipt = json.loads((backup / "receipt.json").read_text(encoding="utf-8"))
if receipt["state"] != "VERIFIED" or receipt["root"] != str(root):
    raise SystemExit("이 checkout의 VERIFIED R4 backup이 아닙니다.")
if receipt["revision"] != "GENOS_CM_SHORTCUT_DATA_20261007_R4":
    raise SystemExit("다른 코드 revision의 backup입니다.")
paths = [row["path"] for row in receipt["files"]]
subprocess.run(["git", "-C", str(root), "add", "--", *paths], check=True)
print("선택한 패치 파일 수:", len(paths))
PY

git diff --cached --stat
```

변경 목록 확인 후 아래 commit을 수행한다. 이미 동일 코드가 commit됐다면 중복 commit 대신 그 commit을 확인한다.
선행 shortcut/표시 패치가 아직 미커밋이면 그 변경도 따로 검토·commit해야 한다.
gate는 동일 checkout 전체가 commit된 상태인지 확인하며 남은 tracked 변경은 중단 사유다.
관계없는 변경을 무작정 함께 올리거나 git add .로 해결하지 않는다.

```bash
cd "$GENOS_DEV_ROOT"
git commit -m "Register CM51 curated shortcut support"
bash "$GENOS_DEV_ROOT/TRANSFER/GENOS_CM_SHORTCUT_DATA_20261007_R4_RUN.txt" gate \
  "$CM_CODE_BACKUP" \
  --generation "$GENOS_GENERATION"
```

RELEASE_GATE PASS가 나온 뒤 아래 push를 수행한다.
gate 뒤 코드가 바뀌면 새 commit과 gate가 필요하다.

```bash
cd "$GENOS_DEV_ROOT"
git push origin HEAD
git rev-parse HEAD
```

마지막 출력 커밋 해시를 기록한다. Git push만으로 코드서빙의 실행 코드가 바뀌지는 않는다.

5. GENOS 화면에서 실제 코드서빙 새 리비전 배포

1) 기존 RAG 코드서빙을 연다.
2) 새 리비전에서 방금 push한 정확한 commit을 선택한다.
3) 새 리비전 환경변수에 아래 값을 현재 서비스와 맞춰 설정한다.
   GENOS_GENERATION = 위 실제 generation 경로
   GENOS_RUNTIME_DIR = 위 실제 runtime 경로
   GENOS_STATE_DIR = 기존 서비스가 사용하는 경우에만 같은 실제 값
4) 기존 내부 LLM 주소·모델 서빙 ID·인증키·빌드·시작 명령·포트·실행 모드를 유지한다.
5) 배포 신청·승인을 진행하고 Online 상태를 확인한다.
6) 실제 요청 트래픽이 새 리비전으로 가는지 확인한다.
   동일 코드서빙의 새 리비전이면 기존 workflow 코드서빙 ID/토큰을 임의로 바꾸지 않는다.
7) 새 리비전의 ID, commit, generation 경로, runtime/state 경로를 함께 기록한다.

CM_CODE_BACKUP/CM_RUNTIME_DIR/CM_PRINCIPAL_FILE/CM_RECEIPT_FILE은
반입 명령에 전달하는 보조 값이므로 코드서빙 환경변수에는 추가할 필요가 없다.
workflow의 실제 TEAM_ID/user_id와 등록 principal은 일치해야 한다.
기존 workflow Python 단계와 채팅 앱 연결을 이번 안내 때문에 교체하지 않는다.


retire한 같은 import를 자동 재활성화하지 않는다.
코드 복귀가 필요하면 다음 명령 후 이전 검증 commit/리비전/generation으로 별도 재배포한다.

```bash
bash "$GENOS_DEV_ROOT/TRANSFER/GENOS_CM_SHORTCUT_DATA_20261007_R4_RUN.txt" undo "$CM_CODE_BACKUP"
```

정리할 실행 순서:
  현재 터미널 변수 → principal 생성 → data-check
  → 코드 commit → gate PASS → push
  → 코드서빙 새 리비전 환경변수/배포/트래픽 확인
  → data-import → data-verify → 같은 사용자·팀의 workflow 질문 확인

기존 최종 R4 실행 파일은 이번 메일의 독립 RUN.txt 그대로 사용한다.
이 보충 안내는 방금 대화의 환경변수·배포 설명을 파일로 정리한 것이며 새 코드 릴리스가 아니다.
