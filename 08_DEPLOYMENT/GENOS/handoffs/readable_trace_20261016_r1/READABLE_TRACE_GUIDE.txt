# vi용 요청 전체 과정 로그

2026-10-16 사용자 요청에 따른 작업 코드 구현이다. 사진의 `.llm_raw.jsonl`은 한 줄 원시 응답 원장이며, 운영자가 읽을 파일은 새 **`<요청기록명>.trace.txt`**다. 기존 코드서빙 진입점 `service.service` → `DeferredReport` → `_LiveLog`의 비동기 기록 경로에 연결했다. 별도 모델 호출·프롬프트 변경·검색 변경은 없다.

## 위치와 읽기

`GENOS_SHARED_LOG_DIR`이 설정된 실행에서 기존 날짜·팀 폴더를 사용한다.

```text
$GENOS_SHARED_LOG_DIR/YYYY-MM-DD/<team>/legal_agent/<request>-<suffix>.trace.txt
$GENOS_SHARED_LOG_DIR/YYYY-MM-DD/<team>/ad_mode/<request>-<suffix>.trace.txt
```

현재 폴더에서 정확한 파일명을 확인한 다음 `vi ./정확한요청파일명.trace.txt`로 연다. 기존 같은 이름의 `.txt` 요약과 `.json` 보고서에도 상세 파일 경로를 기록한다. 하나의 거대한 팀 공용 파일에 서로 다른 요청을 섞지 않고, 요청마다 새 파일을 만들며 이전 파일을 보존한다. `:e`로 누적 내용을 다시 읽고 `/실제 LLM 입력`, `/프롬프트에 들어간 정보`, `/찾은 정보`, `/답변 속도`, `/오류 요약`, `/ERR-0001`로 이동할 수 있다.

실제 작성기를 사용한 [모의 형식 예시](../../../09_ARTIFACTS/AUDITS/20261016-readable-process-trace/SAMPLE.trace.txt)는 GENOS 현장 실행 기록이 아니다.

## 기록 계약

- 요청 입력, 서비스 지점, agent 원장 이벤트와 생성 레코드를 문단과 구분선으로 누적한다. 기존 UI의 이벤트 생략·후보 수 제한을 상세 기록에 적용하지 않는다. DEBUG 단계 이벤트는 해당 요청의 상세 수집에만 포함하며 전역 로그 레벨을 바꾸지 않는다.
- 검색·열람 결과는 `찾은 정보` 구역에 기록한다. 이것만으로 모델 전달·근거 채택을 주장하지 않는다. 각 물리 호출의 저장된 **실제 전송 request.messages**를 읽어 `프롬프트에 들어간 정보` 구역을 만든다. 별도 model_view로 실제 전송 요청을 대체하지 않는다. 수정 요청의 추가 메시지도 포함한다.
- 전송 예약, 전송 시도, 응답 수신, 검증·보정·재시도, 상태 확정·발행을 구분한다. 응답 수신은 모델 제안이며 채택·정답 인증과 다르다. 과거 원장에 SENT가 없으면 `전송 시점 미기록`으로 표시한다.
- 응답 문자열·오류 응답·refusal·도구 호출·완료 사유·사용량은 생략하지 않는다. 읽기 위해 JSON 문자열을 필드별로 펼치고 줄 앞에 `|`를 붙인다. 제어 문자는 이스케이프하며 원본 전송 바이트는 기존 SQL·JSON 원장에 보존한다. 전송 content의 마스킹 후 SHA-256과 문자 수를 함께 기록한다.
- 시간은 전송 receipt.seconds가 있으면 이를 사용하고, 없으면 원장 started_at~finished_at의 차이를 쓴다. 후자는 저장 경계가 포함된 시간임을 표시한다. 입력·출력·합계 토큰과 호출별 시간, 확인된 누계를 표시한다. 미제공 사용량은 0으로 대체하지 않는다. 표시 속도는 출력 토큰/전체 호출 시간이며 순수 생성 속도나 첫 토큰 지연이 아니다. 실패·재시도도 별도 호출로 누적한다.
- 같은 traceback은 `ERR-0001`과 같은 번호를 부여해 최초 한 번만 펼친다. 이후 같은 traceback은 그 번호를 참조한다. 오류 코드·예외 종류·발생 단계·측정된 시간·명시된 재시도 여부를 먼저 보여준다. 서로 다른 오류·물리 시도·전파 이벤트는 합치지 않는다. 기존 `.log`의 중복 `failure_diagnostics`·`error_record`·traceback 출력도 같은 방식으로 연결한다. SQL·JSON 원본 오류는 수정하지 않는다.
- 서비스 이벤트와 SQL 원장은 별도 수집원이므로 누적 파일은 수집 순서이며 각 기록에 발생 시각·원장 seq를 남긴다. 늦게 열린 파일과 비동기 큐 누락분은 최종 보고서 생성 시 같은 요청의 캡처·원장에서 보충한다. 중복 이벤트를 다시 펼치지 않는다.
- RAG 원장은 실행 중 폴링한다. AD는 기존 계약대로 작업 종료 후 SQL의 실제 요청·응답·변경·오류를 같은 형식으로 내보낸다. AD 실행 중 실시간 프롬프트 파일 기록은 이번 범위에 포함되지 않는다.

## 실패와 복구

기록 소비자는 운영자와 기존 요청 보고서이며, 결과가 제품 context·답변·원문·성공 숏컷에 입력되지 않는다. 모델·도구 복구와 예산 정책은 유지한다. 로그 쓰기 실패 담당은 기존 비동기 보고서 작성기 한 곳이며, 로그 실패를 이유로 모델을 재호출하지 않는다.

공유 파일 열기·쓰기 실패는 `shared_process_trace.failed`로 남기고 원장·JSON을 보존한다. 동일 기록기에 무한 파일 재시도를 추가하지 않는다. 완성되지 않은 로그를 전체 기록 성공으로 간주하지 않는다. 프로세스 강제 종료, NFS 장애, 기존 보고서 용량 제한(`shared_report.skipped`)에서는 상세 파일이나 종료 구역이 없을 수 있다. 원장이 없는 처리의 토큰·중간 상태를 추정해 채우지 않는다. 요청 중단 시 최종 응답 미확정으로 표시한다.

기존 request/team/run 선택을 유지하고 파일 권한은 `0640`, 새 요청 파일은 배타 생성한다. 비밀번호·키·인증값은 기존 마스킹을 적용한다. 파일의 원문·프롬프트는 내부 운영 자료다. 재개·중복 요청은 기존 제품 멱등 계약을 따르며 이전 trace 파일은 덮어쓰지 않는다.

## 확인 및 적용 상태

[신규 계약 검사](../../../05_TESTS/CONTRACTS/test_readable_process_trace.py)는 모든 원장 단계, 실제 전송 맥락과 미전달 검색 결과의 분리, 수정 프롬프트, 긴 문단·깨진 JSON·이상 응답, 토큰 미제공, 중복 오류, 저장 실패, 늦은 파일 열기, 실제 `service.service`의 RAG 정상/실패·AD 성공/실패 연결을 모의 모델로 검사한다. 제품 요청·모델 호출 수와 원본 원장 바이트 보존을 확인한다.

작업 코드 의존 해시와 엔진/PIPELINE pin은 함께 갱신한다. [검증·코드 binding](../../../09_ARTIFACTS/AUDITS/20261016-readable-process-trace/VALIDATION.json)에 실제 결과를 기록한다. **선택된 로컬 MAIN76 및 GENOS 반입·commit/push·새 리비전 배포·워크플로우 검증은 이번 작업에서 변경하지 않았다.** 사진의 약180초 전송 timeout은 오류 표시 개선과 별개로 남아 있으며, 내부 모델·네트워크 지연 원인은 현장 근거가 더 필요하다.
