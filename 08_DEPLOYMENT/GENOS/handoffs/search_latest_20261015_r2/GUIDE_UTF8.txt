GENOS SEARCH_LATEST R2 — CURRENT.json 오류 및 현장 코드 호환 수정

사진 확인 결과
FACT_REASON R2는 CODE_APPLIED / FACT_REASON_EXIT=0으로 코드 적용 성공입니다.
그 작업을 반복할 필요가 없습니다. Git push·새 코드서빙 리비전·워크플로우 질의 성공은 별도입니다.
SEARCH_LATEST R1의 check/apply는 generation 선택에서 중단되어 코드 적용 전 실패했습니다.
SEARCH_LATEST R1 대신 이번 R2만 사용합니다.

실행 — ZIP을 업로드한 실제 TRANSFER 폴더에서 그대로 실행
python3 -m zipfile -e ./GENOS_SEARCH_LATEST_20261015_R2.zip ./GENOS_SEARCH_LATEST_20261015_R2
bash ./GENOS_SEARCH_LATEST_20261015_R2/GENOS_SEARCH_LATEST_20261015_R2_RUN.txt check
bash ./GENOS_SEARCH_LATEST_20261015_R2/GENOS_SEARCH_LATEST_20261015_R2_RUN.txt apply

독립 RUN.txt도 완전한 코드와 검증 내용을 포함합니다. ZIP에서 푼 TXT와 같은 코드입니다.
실행 위치와 코드 적용 위치는 다릅니다. 적용 대상은 기존 ~/DEV Git checkout이며 심볼릭 링크이면 실제 경로를 확인합니다.
GENOS_DEV_ROOT를 이미 설정했다면 그 checkout을 사용합니다.
로그: 현재 TRANSFER의 search-latest-r2-*.log
실행 상태·계획·적용 ZIP·receipt: 현재 TRANSFER의 search-latest-r2-state/
check는 계획만 만들며 검색 선택을 활성화하지 않습니다. apply는 코드 백업→검사→검색 선택 활성화 순서입니다.
성공 출력: CODE CHECK PASS, CODE APPLIED 또는 ALREADY_APPLIED, 검색 상태 ACTIVE, SEARCH_LATEST_R2 EXIT=0.
이미 적용한 뒤 apply를 다시 실행해도 이전 백업을 보존합니다.

무엇이 바뀌는가
서비스가 사용하는 00_SYSTEM/GENOS_SERVING_PATHS.json의 고정 generation을 같은 deployment_paths 모듈로 읽습니다.
generation manifest 해시를 검사하고, --generation을 명시했다면 서비스 설정과 같은지 검사합니다.
고정 설정이 있으면 서비스와 동일하게 그 설정이 예전 GENOS_DATA_ROOT보다 우선합니다.
고정 설정이 없을 때만 기존 환경·포인터 선택 규칙을 사용합니다. CURRENT.json을 만들거나 고치지 않습니다.
사진의 현장 코드에 맞춰 기존 검색 필터 변경만 적용합니다. 현장에 없는 로컬 데이터 구축 CLI는 요구하지 않습니다.
현장 코드와 다른 파일은 해시 오류로 중단합니다. 오류를 숨기거나 모든 해시를 임의 갱신하지 않습니다.
기존 FACT_REASON 문구, 서비스 설정, 팀 선택 구현, 나머지 복구 기능을 보존합니다.

데이터 처리
기존 DB의 문서 메타데이터에서 같은 폴더·제목의 8자리 파일명 날짜를 비교합니다.
구버전 문서를 검색에서 제외하는 SEARCH_SELECTION만 generation 옆에 기록합니다.
원본 파일·SQLite·navigation·fulltext·generation manifest는 그대로입니다. 재구축·모델 호출은 없습니다.
파일명 날짜는 법적 시행일 판정이 아닙니다. 날짜·별칭·최신 파일이 모호하면 제외하지 않고 경고를 남깁니다.
제외할 문서가 없으면 제외 수는 0입니다. 실제 개수는 현장 check 출력으로 확인합니다.

코드 검토·commit·같은 checkout 검증
아래는 위 실행을 완료한 같은 TRANSFER 터미널에서 실행합니다.
python3 - <<'PY'
import json,pathlib,subprocess
p=pathlib.Path('search-latest-r2-state/CODE_APPLIED.json')
v=json.loads(p.read_text());root=v['root']
subprocess.run(['git','-C',root,'diff','--check'],check=True)
subprocess.run(['git','-C',root,'diff','--stat','--',*v['files']],check=True)
print('아래 commit 단계는 위 변경 파일을 검토한 뒤 실행합니다. 적용 대상:',root)
PY

변경 파일 검토 후:
python3 - <<'PY'
import json,pathlib,subprocess
v=json.loads(pathlib.Path('search-latest-r2-state/CODE_APPLIED.json').read_text());root=v['root']
subprocess.run(['git','-C',root,'add','--',*v['files']],check=True)
subprocess.run(['git','-C',root,'commit','--only','-m','Apply verified GENOS latest-version search selection R2','--',*v['files']],check=True)
PY
bash ./GENOS_SEARCH_LATEST_20261015_R2/GENOS_SEARCH_LATEST_20261015_R2_RUN.txt gate

gate는 같은 committed checkout의 코드·엔진 pin·선택 generation과 검색 선택을 검사합니다.
통과 후 해당 checkout에서 기존 절차로 git push하고 그 커밋의 새 코드서빙 리비전을 배포합니다.
기존 NFS generation 경로와 서비스 설정을 유지하고 SSE 세션을 재시작합니다.
질의 확인은 워크플로우 테스트 화면에서 진행합니다. 코드서빙 직접 테스트 UI/API를 사용하도록 요구하지 않습니다.
이번 변경으로 워크플로우 Python 편집기를 추가 변경할 필요는 없습니다.
현장 코드 적용, Git push, 새 리비전, 워크플로우 질의 성공은 서로 별도 상태입니다.

실패·재개·원복
검색 활성화 실패 시 RUN_STATE.json에 CODE_APPLIED_SELECTION_FAILED를 남기며 성공으로 표시하지 않습니다.
검사/코드 검증 실패는 로그 원인을 보존합니다. 쓰기 후 코드 검증 실패는 변경 코드를 자동 원복합니다.
동일 입력 재실행은 apply로 진행합니다. generation이나 계획이 바뀌었다면 중단하며 새 --plan 경로가 필요합니다.
검색 선택 원복은 SELECTION_APPLIED.json의 receipt 값을 --receipt로 지정합니다:
bash ./GENOS_SEARCH_LATEST_20261015_R2/GENOS_SEARCH_LATEST_20261015_R2_RUN.txt rollback --receipt '<실제 receipt.json 경로>'
코드 원복은 CODE_APPLIED.json의 backup 값을 --backup으로 지정합니다:
bash ./GENOS_SEARCH_LATEST_20261015_R2/GENOS_SEARCH_LATEST_20261015_R2_RUN.txt undo-code --backup '<실제 코드 백업 경로>'
검색 선택을 먼저 원복하고 코드를 원복합니다. 이후 이전 검증 리비전으로 배포하고 SSE를 재시작합니다.
후속 변경·백업 변조가 있으면 원복을 거부하며 기존 파일을 보존합니다.

GENOS 내부에는 이 Codex 세션이 연결되지 않습니다. 현장 적용·리비전·실제 데이터 결과는 현장 로그로 확인합니다.
