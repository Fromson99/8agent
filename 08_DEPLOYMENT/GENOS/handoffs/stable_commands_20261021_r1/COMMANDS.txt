GENOS 고정 명령 — 구조화부터 내규·외규 연결 검토·운영 이관까지

명령은 기존 ~/DEV checkout의 pipeline.py를 사용합니다. 날짜/MAIN 번호별 ZIP 실행기를 매번 고르지 않습니다.
현재 유지하는 공유 SQLite/NFS 구축·조사·관계 이관 경로의 안내입니다.
Oracle 직접 조회 운영에는 아래 관계 SQLite apply나 source-apply를 사용하지 않습니다.
Oracle 목표 구조는 Dataiku/Oracle 게시 및 요청별 조회이며 이 도구가 그 적재를 대신하지 않습니다.

0. 이번 한 번 고정 명령 추가
실제로 업로드한 TRANSFER 폴더의 터미널에서 실행합니다. TRANSFER의 절대 위치를 추정하지 않습니다.
python3 -m zipfile -e ./GENOS_STABLE_COMMANDS_20261021_R1.zip ./GENOS_STABLE_COMMANDS_20261021_R1
bash ./GENOS_STABLE_COMMANDS_20261021_R1/GENOS_STABLE_COMMANDS_RUN.txt check
bash ./GENOS_STABLE_COMMANDS_20261021_R1/GENOS_STABLE_COMMANDS_RUN.txt apply
python3 ~/DEV/06_TOOLS/pipeline.py basis-work check

기존 ~/DEV에 명령 파일만 추가/수정합니다. MAIN95와 최신 ignore 패치는 보존합니다.
원문/색인/관계/조사 PLAN·STATE/모델/워크플로우/서빙 리비전은 설치로 변경하지 않습니다.
다른 checkout이면 설치 명령에 --root /실제/checkout을 붙이고, 이후 그 checkout의 pipeline.py를 호출합니다.
코드 패치를 새로 적용한 뒤에도 같은 명령을 사용합니다. 현재 엔진과 명령 manifest를 검증합니다.
후속 누적 코드 ZIP에는 이 명령 파일과 00_SYSTEM/BASIS_COMMANDS.json도 포함해야 합니다.
현재 명령 구현을 수정하는 패치는 이 명령 manifest의 해당 코드 해시도 함께 검증/갱신해야 합니다.
과거 ZIP으로 checkout을 되돌리면 이 기능도 없어질 수 있습니다. 영구 무조건 호환을 보장하는 우회 명령이 아닙니다.

1. 현재 경로/완료 작업 확인 — 모델 호출 없음
python3 ~/DEV/06_TOOLS/pipeline.py basis-work paths
python3 ~/DEV/06_TOOLS/pipeline.py basis-work jobs

paths의 data_root가 RAW/구축 산출물 위치, selected_generation이 현재 조사 원문,
runtime이 기존 외부 공유 조사/관계 저장 위치입니다. 폴더 날짜로 최신 자료를 자동 선택하지 않습니다.
이미 원문 구조화·색인·선택이 끝났다면 2~4번을 다시 하지 않고 5번 또는 6번으로 갑니다.
build-001, build-001-index, links-001은 예시 작업 이름입니다. 새 작업에는 새 이름을 정합니다.

2. 전체 원문 구조화
RAW 반입과 출처/문서 ID/판본/공개·내부 구분을 기존 01_DATA 안내대로 등록한 뒤 실행합니다.
전체 = 기존 BUILD_SCOPE/TEAM_LAYOUT/제외 정책으로 선택된 입력 전체입니다. 제외 문서를 임의로 다시 넣지 않습니다.
python3 ~/DEV/06_TOOLS/pipeline.py build-data-stages --run-id build-001 --stage structure --structure-vlm off --pdf-parser local --pdf-conversion off --latest-internal-versions --check-only
python3 ~/DEV/06_TOOLS/pipeline.py build-data-stages --run-id build-001 --stage structure --structure-vlm off --pdf-parser local --pdf-conversion off --latest-internal-versions --execute

기본 원본 파서/로컬 PDF 경로이며 LLM/VLM 구조 검토를 켜지 않습니다.
동일 입력·파서·코드에서는 같은 명령으로 완료된 결과를 재사용합니다.
실패 문서를 완료로 바꾸지 않습니다. 구조화가 미완료이면 통합/색인으로 자동 진행하지 않습니다.

3. 용어·정의·명시 참조 연결 및 전체 색인
python3 ~/DEV/06_TOOLS/pipeline.py document-release prepare --run-id build-001 --glossary-corpus-policy replace
python3 ~/DEV/06_TOOLS/pipeline.py document-release reindex --from-run-id build-001 --run-id build-001-index --fulltext-workers 1

기존에 선택한 용어집/지식 묶음과 이번 완료 원문을 사용합니다. 신규 용어집 외부 수집이나 의미 자동 승인은 아닙니다.
원문 source, navigation, 용어·정의·명시 참조, unit fulltext, 서빙 자원 검증이 연결됩니다.
무거운 구축/색인은 하나씩 실행합니다. 출력의 generation_path를 확인합니다.
일반 출력은 data_root/TERM_RELEASES/build-001-index/serving/baseline/generation입니다.
기존 내규–외규 LLM 조사/승인 관계와 이 결정론 참조 색인은 별개입니다.

2~3번을 한꺼번에 하는 기존 고정 명령도 있습니다:
python3 ~/DEV/06_TOOLS/pipeline.py build-all --run-id build-001 --no-models --check-only
python3 ~/DEV/06_TOOLS/pipeline.py build-all --run-id build-001 --no-models --execute
위 단계별 명령과 중복 실행하지 마세요. 제한 RAM에서는 fulltext-workers 1을 명시하는 단계별 방식을 사용합니다.

4. 새 원문 세대를 기존 공유 SQLite 조사 경로에 명시 선택
이미 선택한 세대를 그대로 쓸 때는 이 단계를 생략합니다.
아래 두 경로는 실제 출력/공유 마운트의 새 경로로 바꿉니다. 기존 활성 세대 폴더를 지정하지 마세요.
TASK_BUILT='/실제/generation_path'
TASK_GENERATION='/실제/외부공유경로/새세대/generation'

구축 결과가 DEV에 있으면 새 공유 폴더로 복사합니다. 원래 구축 결과와 이전 세대는 보존합니다.
mkdir -p "$TASK_GENERATION"
cp -a -n "$TASK_BUILT/." "$TASK_GENERATION/"
cmp "$TASK_BUILT/manifest.json" "$TASK_GENERATION/manifest.json"
cmp 또는 이후 검증이 실패하면 선택하지 않습니다. 이미 존재하는 다른 세대를 덮어쓰지 않습니다.

현재 판본 선택 계획/적용:
python3 ~/DEV/06_TOOLS/pipeline.py search-selection plan --generation "$TASK_GENERATION" --latest --plan ./LATEST_PLAN.json
python3 ~/DEV/06_TOOLS/pipeline.py search-selection apply --plan ./LATEST_PLAN.json

새 원문·색인 검증과 기존 설정 보존 계획:
python3 ~/DEV/06_TOOLS/pipeline.py basis-work source-plan --generation "$TASK_GENERATION" --output ./SOURCE_PLAN.json
계획의 before/after 경로를 확인한 후:
python3 ~/DEV/06_TOOLS/pipeline.py basis-work source-apply --plan ./SOURCE_PLAN.json --output ./SOURCE_APPLIED.json
python3 ~/DEV/06_TOOLS/pipeline.py basis-work paths

기존 GENOS_SERVING_PATHS.json의 generation/manifest 해시만 선택합니다. runtime/다른 설정은 유지합니다.
같은 apply 명령은 적용 영수증을 확인합니다. 설정이 다른 작업에서 바뀌면 중단합니다.
기존 실행 중인 채팅 서비스는 새 프로세스/리비전에서 선택을 확인해야 합니다. Git push/배포를 이 명령이 하지 않습니다.
운영 코드서빙 내부에 원문 전체를 복사하는 안내가 아닙니다. 위 복사는 기존 외부 데이터 계층의 SQLite 경로입니다.
원복:
python3 ~/DEV/06_TOOLS/pipeline.py basis-work source-rollback --receipt ./SOURCE_APPLIED.json --output ./SOURCE_ROLLBACK.json

5. 새 전체 내규–외규 조사와 지정 확정 연결 추가
전체 목록/구조 검사·20문서 단위 계획만 먼저 생성:
python3 ~/DEV/06_TOOLS/pipeline.py basis-work plan-all links-001

전에 지정한 위험관리기준시행세칙의 외규 연결 4건 확인/추가:
python3 ~/DEV/06_TOOLS/pipeline.py basis-work fixed-inspect links-001
python3 ~/DEV/06_TOOLS/pipeline.py basis-work fixed-stage links-001

지정 4건은 첫 번째 유효한 하위 계획의 CANDIDATES.json에 함께 보관합니다.
출력 FIXED_JOB이 실제 대상입니다. 전체 계획 권한 안의 문서/판본/원문을 다시 확인합니다.
같은 확정 연결을 재실행해도 receipt로 재사용합니다. 기존 일반 모델 후보의 ID·이력·미승인 상태를 보존합니다.
이는 사용자가 지정한 4건의 확정이며, 모든 모델 후보를 법률 정답으로 자동 승인하는 명령이 아닙니다.

전체 조사 실행:
python3 ~/DEV/06_TOOLS/pipeline.py basis-work all links-001
상태/중단 뒤 재개:
python3 ~/DEV/06_TOOLS/pipeline.py basis-work status links-001
python3 ~/DEV/06_TOOLS/pipeline.py basis-work resume links-001

all은 plan-all이 없으면 계획부터 생성합니다. 확정 4건을 먼저 넣으려면 위처럼 plan-all을 따로 실행합니다.
모델 조사는 GENOS 내부 모델로 순차 실행합니다. 구조 실패는 목록에 남기고 다른 문서를 조사합니다.
출력: runtime/basis-batch/pilot-review-user-links-001/parts/part-*/CANDIDATES.json
관계 원장에 자동 게시하지 않습니다. 구조 실패·부분 결과를 외규 부재로 처리하지 않습니다.
종료 0=전체 완료, 2=부분/실패 포함, 1=중단, 130=사용자 중단입니다.

일부만 조사할 때:
python3 ~/DEV/06_TOOLS/pipeline.py basis-work plan small-001 --count 3
python3 ~/DEV/06_TOOLS/pipeline.py basis-work run small-001
같은 status/report/export/resume 명령에서 작업 이름만 small-001로 바꿉니다.

6. 기존 조사 결과를 최신 코드에서 조회/export
예전 BASIS_RUN.txt all로 만든 작업은 같은 이름 all을 사용합니다:
python3 ~/DEV/06_TOOLS/pipeline.py basis-work status all
python3 ~/DEV/06_TOOLS/pipeline.py basis-work report all
python3 ~/DEV/06_TOOLS/pipeline.py basis-work export all

새 작업은 all 대신 links-001입니다.
이름을 모르거나 옛 pilot 기본 작업이면 jobs 출력의 실제 경로를 명시:
python3 ~/DEV/06_TOOLS/pipeline.py basis-work report --job /실제/runtime/basis-batch/작업폴더
python3 ~/DEV/06_TOOLS/pipeline.py basis-work export --job /실제/runtime/basis-batch/작업폴더

report: 현재 TRANSFER/basis-report-작업이름/INDEX.html
export: 현재 TRANSFER/basis-export-작업이름/생성시각-식별자/INDEX.html과 각 part의 검토 묶음/ZIP
전체 export는 여러 ZIP을 만듭니다. 첫 part만 옮기고 전체가 반영됐다고 판단하지 마세요.
반복 export는 새 스냅샷을 만들고 기존 검토 파일을 보존합니다.
모델 호출/재조사 없이 원래 PLAN/STATE/CANDIDATES와 원문·판본·권한을 검증합니다.
코드가 패치되어도 데이터 계약이 호환되면 과거 결과를 읽을 수 있습니다.
원문 세대를 바꿨다면 옛 결과를 새 원문에 자동 붙이지 않습니다. 판본 이행 검토가 필요합니다.

7. HTML 확인 → 이관할 연결 선택
INDEX.html에서 각 part의 검토·이관 묶음 LINKS.html을 확인합니다.
아래 TASK_BUNDLE은 해당 part 폴더의 실제 경로로 바꿉니다:
TASK_BUNDLE='./basis-export-all/실제생성폴더/part-00001-실제해시'
python3 ~/DEV/06_TOOLS/pipeline.py basis-work transfer review --bundle "$TASK_BUNDLE/RELATIONS.json" --all

일부만 선택하려면 --all 대신 --ids 연결ID1 연결ID2를 사용합니다.
검토 결과 REVIEW.json/REVIEWED.sql과 해당 폴더명_REVIEWED.zip이 생성됩니다.
선택한 각 part의 REVIEWED.zip을 운영 TRANSFER로 가져갑니다. 전체 DB/전체색인/다른 작업 이력은 포함하지 않습니다.
review는 이관 선택입니다. 원래 PROPOSED/APPROVED를 유지하고 법률 승인을 자동 추가하지 않습니다.
내부 원문이 포함된 검토 HTML/ZIP의 기존 공유 범위를 유지합니다.

8. 운영계 반영 — 현재 운영 checkout에도 0번 명령 추가 필요
운영 TRANSFER에서 실제 파일명으로 압축을 풉니다:
python3 -m zipfile -e ./실제묶음_REVIEWED.zip .
TASK_BUNDLE='./압축에서생긴실제묶음폴더'
python3 ~/DEV/06_TOOLS/pipeline.py basis-work transfer check --bundle "$TASK_BUNDLE/RELATIONS.json"
check가 ready인 경우:
python3 ~/DEV/06_TOOLS/pipeline.py basis-work transfer apply --bundle "$TASK_BUNDLE/RELATIONS.json"
python3 ~/DEV/06_TOOLS/pipeline.py basis-work transfer status --bundle "$TASK_BUNDLE/RELATIONS.json"

개발과 운영의 원문 세대/검색 선택/원문/판본/권한이 같아야 합니다. 저장 경로 자체는 달라도 됩니다.
현재 운영 코드의 manifest와 실제 관계 소비자를 검증합니다. 옛 export 당시 전체 코드와 같을 필요는 없습니다.
같은 ID/같은 관계는 재사용하고 다른 revision/승인 상태 충돌은 덮어쓰지 않습니다.
SQL 파일만 sqlite3로 직접 실행하지 않습니다.
원복:
python3 ~/DEV/06_TOOLS/pipeline.py basis-work transfer rollback --bundle "$TASK_BUNDLE/RELATIONS.json"
이번에 추가한 관계만 철회 revision을 남깁니다. 이후 운영에서 변경한 관계가 있으면 자동 원복하지 않습니다.

9. 반영 확인과 패치 후 재개 원칙
워크플로우 테스트 화면의 새 채팅에서 내규 → 연결 외규 → 실제 양쪽 원문을 확인합니다.
코드 반입/commit/push/코드서빙 리비전/워크플로우 편집기 적용/데이터 선택/관계 이관은 별도 상태입니다.
기존 저장 관계를 같은 외부 runtime에서 읽는 코드라면 다음 새 요청이 이관 결과를 조회합니다.
현장 모델·권한·NFS 잠금·대사 결과 확인은 로컬 합성 검사와 별도입니다.

명령 이름은 고정되지만, 이미 시작한 구조화·색인·모델 조사는 원래 코드/데이터/모델/예산에 결속됩니다.
그 결속이 바뀐 상태에서 resume을 강제로 통과시키지 않습니다. 옛 결과·실패 기록은 읽고 export할 수 있습니다.
새 코드로 새 조사가 필요하면 links-002처럼 새 작업 이름을 사용합니다. 새 전체 작업은 별도 조사·새 예산입니다.
같은 작업의 정상 재개에서는 완료 문서를 다시 호출하지 않습니다. 새 전체 작업에는 이 보장이 적용되지 않습니다.
원문/코드/상태 해시 오류를 해시 재작성이나 검증 해제로 넘기지 않습니다.

로그: TRANSFER/basis-work-logs/*.log 및 *.log.exit. 코드 루트에서 직접 실행하면 09_ARTIFACTS/AUDITS/basis-work-logs.
설치 로그: TRANSFER/stable-command-install-logs. 설치 백업/STATE.json은 패키지 폴더에 보존합니다.
GENOS는 python3를 사용합니다. WSL 개발의 .venv 경로를 현장 명령에 넣지 않습니다.
