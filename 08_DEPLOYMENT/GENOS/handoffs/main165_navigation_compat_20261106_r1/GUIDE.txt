MAIN165 — 옛 적재기로 만든 개발계 탐색 데이터를 그대로 읽도록 서버 검사 수정 (MAIN164 대체)

현재 로컬 릴리스: navigation-compat-20261106-r1 / MAIN165, 서빙 535파일(MAIN164 533 + 신규 2).
MAIN164에서 바뀐 것은 탐색 데이터 검사 관련 파일뿐이며 답변·탐색 기능, 테이블 매핑, 워크플로우는 MAIN164와 같습니다.

0. 왜 교체하나
현장 컨테이너 로그(2026-11-06 16:23 KST, 채널 지정 후):
  oracle_query_matcher.py line 250 __init__
  DPError: QUERY_STRUCTURE_COMPILER: republish derived navigation for this code
개발계 검색 게시본은 Dataiku 적재기(gold_fresh_1/gold_oneclick 계열)에 들어 있는 옛 navigation_match.py(f318d57b…)로 만들어졌고,
MAIN157~164 서버의 navigation_match.py(8d498d65…)는 함수 정리와 조회 함수 1개 추가로 해시만 다릅니다.
예전 서버는 파일 해시가 한 글자라도 다르면 무조건 멈췄습니다.

1. 이번 수정
- 서버는 "적재 결과가 같다고 검증된 코드 버전 묶음" 표(00_SYSTEM/ORACLE/navigation_compatibility.json)를 보고 판단합니다.
  같은 묶음이면 진행, 목록에 없는 적재기 버전이면 지금처럼 멈춥니다(조회가 조용히 0건이 되는 것을 막기 위해).
- 등록 근거: 로컬 전체 데이터(문서 1,547개)로 옛 적재 코드와 MAIN164 코드가 만든 탐색 데이터 1,200,306행이 행 단위로 동일.
  일부러 정규화 함수를 바꾼 대조군은 차이를 검출하고 등록이 거절됨.
- 앞으로 navigation 파일을 고쳐도: 적재 결과가 같으면 로컬에서 등록만 하면 되고 현장 재적재가 필요 없습니다.
  적재 결과가 바뀌는 수정은 로컬 핀 단계(엔진 사전점검)에서 먼저 걸리므로 현장에서 처음 발견되는 일이 없습니다.
- 채널 자동선택은 넣지 않았습니다.

3. GENOS 코드스페이스 적용 (MAIN164와 같은 절차)

5. 확인
새 리비전 배포 후 워크플로우 테스트 화면에서 새 요청 ID로 질문 1개를 보냅니다.
컨테이너 로그에 QUERY_STRUCTURE_COMPILER 가 없으면 통과입니다.
또 멈추면 로그 문구로 구분합니다.

      → 등록되지 않은 다른 적재기 버전으로 만든 게시본. 로그의 loader 해시를 보내 주세요.
