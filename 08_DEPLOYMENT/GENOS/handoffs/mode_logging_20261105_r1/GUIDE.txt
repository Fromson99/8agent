GENOS 조회방식 드롭다운 — 워크플로우 로그 확인 R1

사진의 왼쪽 '조회방식 → 내규' 드롭다운이 해당 설정입니다.
사진에는 내부 key가 보이지 않습니다. 실제 입력은 applied_fields.mode여야 합니다.
기존 워크플로우는 선택을 처리하지만 기본 출력 로그에 그 값을 기록하지 않았습니다.

1. 적용
현재 워크플로우 Python 편집기의 내용을 먼저 보관합니다.
11월 5일 MAIN142_LIVE_JUDGMENT_R1_WORKFLOW.py를 적용한 환경에서,
같은 편집기의 전체 내용을 GENOS_MODE_LOG_R1_WORKFLOW.py로 교체하고 저장·배포합니다.
이 파일은 해당 기존 전달본에 모드 진단 로그만 추가한 전체 Python 파일입니다.
적용 위치는 GENOS 워크플로우 Python 단계입니다. 기존 코드서빙 주소·인증 설정을 사용합니다.
로컬 MAIN 선택 포인터·서빙 코드·원문·generation은 이번 전달본의 변경 대상에 포함되지 않습니다.
다른 후속 버전이나 현장 별도 수정이 있다면 전체 교체 전에 CHANGE.diff와 대조합니다.

2. 진단 버전 확인
워크플로우 테스트에서 WORKFLOW_SETTINGS를 보내면 다음 값이 나옵니다.
  "mode_log_revision": "workflow-mode-log-20261105-r1"
이 확인은 설정 조회이며 법률 질문 실행이 아닙니다.

3. 실제 채팅 확인
사진의 채팅창에서 '내규'를 선택하고 질문을 한 번 보냅니다.
선택만 바꾸고 질문을 보내지 않으면 워크플로우 실행 로그는 생기지 않습니다.
해당 워크플로우 실행 로그에서 workflow.mode를 검색합니다.
같은 request_id인 아래 두 이벤트를 확인합니다. 아래 JSON은 설명용 축약 예시입니다.

  {"event":"workflow.mode.received","request_id":"같은 요청번호","mode_status":"SELECTED","received_mode":"내규","selected_mode":"내규"}
  {"event":"workflow.mode.forwarding","request_id":"같은 요청번호","outgoing_mode":"내규","source_category":"internal","transport":"sse"}

첫 줄: 화면에서 applied_fields.mode='내규'가 들어왔습니다.
둘째 줄: 실제 HTTP 요청에 '내규' 구분을 넣어 전송을 시도했습니다.
외규는 outgoing_mode='외규', source_category='external'입니다.
전체 법령은 source_category='ALL', 대사는 routing='compare'입니다.
SSE가 404/405라 JSON으로 전환되면 같은 요청의 forwarding이 sse/json 두 번 나올 수 있습니다.
forwarding은 전송 시도 기록입니다. 서버 수신·실제 문서 조회·최종 답변 성공은 후속 응답/서버 로그로 확인합니다.

4. 입력 이상 판독
MISSING_MODE: applied_fields는 있지만 mode 키가 없습니다. 화면 편집 설정의 key를 소문자 mode로 확인합니다.
doctype_present=true가 함께 있으면 doctype이라는 키도 전달됐다는 뜻입니다. doctype을 mode로 자동 변환하지 않습니다.
NO_APPLIED_FIELDS: applied_fields 객체가 전달되지 않았거나 null입니다.
EMPTY_MODE: mode는 있지만 값이 없거나 공백입니다.
INVALID_APPLIED_FIELDS / INVALID_MODE_TYPE / UNRECOGNIZED_MODE: 형식 또는 선택값이 현재 계약과 다릅니다.
SELECTED인데 forwarding이 없으면 질문 누락, 질문 앞 구분과 충돌, 대사의 팀·세션 누락, 준비 단계 실패 등의 후속 로그를 확인합니다.
두 이벤트가 모두 없으면 진단 버전과 실제 채팅앱이 연결한 워크플로우 리비전을 대조합니다.

5. 보존 범위와 복구
추가 로그에는 허용된 선택값과 요청번호·상태·전송 경로만 남깁니다.
질문 본문, 원문, 사용자 정보, 인증키, 인식하지 못한 임의 입력값을 추가 로그에 출력하지 않습니다.
선택값의 유효성 검사·요청 구성·모델 호출·예산·답변 표시 로직은 원본과 같습니다.
복구는 1번에서 보관한 원래 워크플로우 코드 또는 동일 MAIN142_LIVE_JUDGMENT_R1_WORKFLOW.py를 편집기에 복원해 저장·배포합니다.

전달 파일 자체의 합성 검사 30개 통과: 모드4개/영문별칭, 실제 run→SSE/JSON, 원래 요청과 동일성,
입력 누락·다른 키·잘못된 값·충돌, 비밀값 미출력, 전송 실패, 진단 버전 확인.
원래 모드 변환·요청 생성·본문 처리·표시 함수 불변을 AST로 대조했습니다.
