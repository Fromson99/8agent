MAIN167 — Oracle 게시 자료 메모리 캐시 + SQL 로그 정리 (MAIN166 대체)

현재 로컬 릴리스: oracle-shared-rows-20261106-r1 / MAIN167, 서빙 536파일(MAIN166 535 + 새 모듈 1).
MAIN166에서 바뀐 것은 Oracle 조회 캐시·SQL 로그 관련 제품 6파일(새 1 포함)과 SQL 출처 메타데이터·엔진 pin입니다.
실행 SQL 642개, 답변·탐색 기능, 테이블 매핑, 탐색 호환 등록표, 워크플로우는 MAIN166과 같습니다.

0. 왜 교체하나
현장 로그 사진(2026-11-06, MAIN166):
  - SQL 한 건마다 oracle.sql 줄이 두 번(STARTED / ACKNOWLEDGED) INFO로 찍혀 로그가 SQL로 덮였습니다.
  - previous_log_ms(바로 앞 로그 한 줄을 쓰는 데 걸린 시간)가 줄마다 5~10 ms였습니다. SQL 한 건 약 40 ms 중 약 14 ms가 로그입니다.
  - 첫 모델 호출 전 약 7초가 SQL(초당 약 25건)로 지나갔습니다.
  - 질문마다 같은 게시본(릴리스·원문 목록·구조·검색 행)을 Oracle에서 처음부터 다시 읽습니다.

1. 이번 수정
(1) 게시 자료 메모리 캐시
  - 질문마다 채널 포인터는 지금처럼 Oracle에서 새로 읽습니다.
  - 그 채널이 가리키는 게시본(내용 해시로 정해진 릴리스)의 원문·구조·검색 표만 읽는 SQL 결과를
    서빙 프로세스 메모리에 두고, 다음 질문부터 다시 씁니다.
    대상 표: DOC_VER, DOC_UNIT, DOC_BLK, SRC_POST, SRCH_POST, SRCH_ROW (개발계 SIDDS.LGL_G19_*_S_1 / Gold IDD_B003_LGL_*).
  - 항상 Oracle로 보내는 것: 채널 포인터(SRCH_CHNL), 대화·요청 상태(EXEC_ST), Agent 기록(AGT_*),
    온톨로지(ONTL_*), 벡터(VCTR_POST / VCTR_ITEM / VCTR_HEAD), 시스템 뷰(ALL_* 등), 시각 함수가 든 SQL, 모르는 표.
  - 채널 포인터가 새 게시본으로 바뀌면 바로 다음 질문부터 새 게시본을 읽습니다(로컬 시험으로 확인).
  - 서빙 디스크에는 아무것도 쓰지 않습니다. 재시작하면 캐시는 비고 처음 질문 때 다시 채워집니다.
(2) SQL 로그
  - SQL마다 찍던 oracle.sql 두 줄은 기본 로그에서 없앴습니다.
  - 1초 이상 걸린 SQL만 oracle.sql.slow (duration_ms, sql_family=SQL 문장 해시 앞 12자) 로 남깁니다.
  - 실패한 SQL은 WARNING oracle.sql (READ_FAILED / WRITE_UNCONFIRMED) 로 남깁니다.
  - 요청마다 한 줄 oracle.sql.summary 가 찍힙니다:
      sql_count(보낸 SQL 수), sql_ms(합계 ms), sql_slowest_ms, sql_cache_hits / sql_cache_misses(캐시 재사용/새로 읽음),
      sql_top(가장 오래 걸린 SQL 3개 "해시:횟수:ms"), cache_entries / cache_bytes / cache_evictions.

  DP_QUERY_CHANNEL=g19_7c1f8f4931c8be61b914f5bc

  GENOS_ORACLE_SHARED_CACHE_MIB=512     서빙 프로세스 하나가 캐시에 쓰는 메모리 상한(16~8192).

  GENOS_ORACLE_SQL_SLOW_MS=1000         oracle.sql.slow 로 남길 기준(ms).
  SQL마다 줄을 다시 보고 싶을 때만: GENOS_LOG_LEVEL=DEBUG (로그 양이 크게 늘고 느려질 수 있습니다).
