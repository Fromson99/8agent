MAIN186C = MAIN186 + CPU 측정 (측정만 추가, 답변·SQL·DB 동작은 그대로)

왜
R4 사진(12:14, 302.2초)에서 GENOS 프로세스 CPU가 149.2초였습니다. 그 외 106.8초는 대부분 GENOS 쪽 계산인데, 어느 코드인지는 R4로 알 수 없습니다. SQL을 기다리는 동안에도 다른 스레드가 약 30초 CPU를 썼습니다.
가장 유력한 후보(확인 전)는 화면 진행 표시 스레드입니다. 이 스레드는 1초마다 요청 기록 DB를 새로 여는데, 열 때마다 Oracle의 그 기록 전체를 메모리로 다시 만듭니다.

적용 (MAIN186과 같은 절차, TRANSFER 폴더에서. ZIP은 미리 풀지 않습니다)
bash MAIN186C_ONECLICK_R1.txt → MAIN186C_ONECLICK_DONE 확인 → stage·commit → gate-code → push → 새 코드서빙 리비전
환경변수는 바꿀 것이 없습니다(측정은 기본으로 켜짐, 끄기 GENOS_CPU_PROFILE=off). 워크플로우 파일도 MAIN186과 같습니다.

측정
① 가능하면 다른 질문이 없을 때 느린 질문 하나(R4 때와 같은 질문이면 비교하기 좋습니다)
② bash ./GENOS_CPU_REPORT_R1.txt list → bash ./GENOS_CPU_REPORT_R1.txt 번호 → 사진 3장
③ 같은 요청의 R4 사진 1장도 같이 보내 주세요: bash ./GENOS_ORACLE_REPORT_R4.txt 번호 --page 1

사진에서 보이는 것
사진 1: 스레드별 CPU(요청 처리 / 화면 진행 표시 등), 원장 다시 만들기 횟수·CPU, 판정
사진 2: 함수별 CPU · 사진 3: CPU를 쓴 코드 줄

원복: bash MAIN186C_ONECLICK_R1.txt undo --backup '출력된 백업 폴더'

로컬 검증: 실제 로컬 Oracle에서 한 질문으로 측정 결과 기록과 보고 사진 3장 확인, 원장 다시 만들기 계측 확인, 관련 회귀 23파일 MAIN186과 결과 동일(바뀐 검사 0), MAIN186 사본 설치 15개 명령 통과, 측정기 자체 CPU 약 1%. 현장 실행은 이번이 처음입니다. 자세한 내용은 GUIDE.txt를 보세요.
