MAIN186C — MAIN186 + CPU 측정 (측정만, 답변·DB 동작 그대로)
함께 보냄: CPU 보고 R1 (GENOS_CPU_REPORT_R1.txt, 사진 3장)

왜 하는가
  R4 사진(11-10 12:14, 302.2초): 모델 24.1초 · SQL 171.3초 · 그 외 106.8초, 그리고 GENOS 프로세스 CPU가 149.2초였습니다.
  즉 GENOS가 질문 처리 동안 계속 계산하고 있었는데, R4로는 어느 코드인지 알 수 없습니다.
  또 SQL을 기다리는 동안에도 요청 스레드는 CPU 7.4초인데 프로세스 전체는 37.0초여서, 다른 스레드가 약 30초를 썼습니다.
  로컬 코드로 본 가장 유력한 후보(아직 확인 전):
    화면 진행 표시 스레드가 1초마다 요청 기록 DB를 새로 열고, 열 때마다 Oracle의 그 기록 전체를
    메모리 DB로 다시 만듭니다(행 목록 SQL + 본문 JSON 전부 해석·해시 확인·다시 넣기). 질문이 길수록 기록이 커져
    한 번에 드는 CPU도 커집니다.
  이번 측정으로 이 후보가 맞는지, 요청 처리 스레드의 나머지 CPU는 어느 코드인지 함께 확인합니다.

0. 무엇이 바뀌나 (MAIN186 대비 제품 3파일 + 엔진 고정값)
  - semantic_runtime/cpu_profile.py (새 파일): 측정기
      20ms마다 프로세스의 모든 파이썬 스레드가 실행 중인 코드 위치와, 그 스레드가 그동안 쓴 CPU(/proc의 스레드 CPU)를 읽어
      "CPU를 쓴 시간"만 코드 위치별로 더합니다(기다리는 스레드는 세지 않음). 스레드는 이름으로 묶습니다.
  - oracle_record_sqlite.py: 원장 기록 DB를 열 때마다(전체를 메모리로 다시 만드는 일) 횟수·행 수·크기·CPU를 측정기에 알림
  - oracle_query_service.py: 요청 시작에 측정 시작, 질문 끝의 oracle.sql.summary 줄에 결과(cpu_profile) 추가
  질문 처리 순서·답변·SQL 문장·DB 데이터는 바뀌지 않습니다(SQL 계획 646 그대로).
  측정기 자체 CPU는 로컬에서 약 1%입니다. 기록되는 것은 코드 위치(파일:함수:줄)·스레드 이름·기록 파일 이름·숫자뿐이고
  질문·답변·원문·SQL·식별자는 남기지 않습니다.
  워크플로우 파일은 MAIN186과 같습니다(편집기 교체 필요 없음).

사진 읽는 법
  사진 1 [A] 서버 처리 = 모델 + SQL + 그 외, 프로세스 CPU, 스레드별로 잡은 CPU / 못 잡은 CPU
         [B] 스레드 묶음별 CPU — "화면 진행 표시"(Thread (_poll_loop)), "요청 처리(작업 스레드)"(AnyIO worker thread) 등
         [C] 원장 다시 만들기 — 기록 파일·스레드별 횟수, 행 합계·최대, 본문 크기, CPU, 시간
         [D] 판정 — 화면 진행 표시 스레드의 몫, 원장 다시 만들기의 몫, 요청 처리에서 가장 많이 쓴 코드 줄
             "같은 시간에 처리된 요청 수"가 2 이상이면 다른 질문의 CPU가 섞여 있습니다.
  사진 2 함수별 CPU(그 함수 안에서 부른 것까지 포함): 위가 바깥, 아래가 안쪽. 비율이 크게 줄어드는 곳이 갈라지는 지점입니다.
  사진 3 CPU를 쓰는 순간 실행 중이던 코드 줄(우리 코드 / 라이브러리 포함)과 많이 쓴 호출 경로
