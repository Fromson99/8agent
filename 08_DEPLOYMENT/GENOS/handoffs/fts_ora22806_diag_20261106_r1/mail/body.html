ORA-22806 원인 확인 B — GENOS 코드스페이스 진단 (현장 ORDS 경로, 읽기 전용)

앞서 보낸 A(Dataiku 노트북 SQL)는 DB에 직접 붙어 실행합니다. B는 서빙과 같은 GENOS → ORDS 연결로 실패한 본문검색 SQL을 다시 실행하고, SQL을 단계별로 잘라 어느 부분에서 ORA-22806이 나는지 찾습니다. A와 B 결과를 비교하면 원인이 갈립니다.

실행 — MAIN165가 적용된 ~/DEV가 있는 GENOS 코드스페이스, 첨부 TXT를 올린 TRANSFER 폴더에서:

bash ./FTS_ORA22806_DIAG_R1.txt
  • 서빙 리비전과 같은 ORDS 환경변수(ORACLE_ORDS_SCHEMA / CLIENT_ID / CLIENT_SECRET, 쓰는 경우 ORACLE_ORDS_BASE_URL)가 셸에 있어야 합니다. 없으면 CLIENT FAIL ... DP_CONFIG로 멈춥니다 → export 후 다시 실행.
  • 매핑은 development_g19_1, 채널은 g19_7c1f8f4931c8be61b914f5bc가 기본입니다(환경변수가 있으면 그 값).
  • MISSING_PYTHON_MODULE이 나오면 서빙 python으로: PYTHON=<서빙 python3 경로> bash ./FTS_ORA22806_DIAG_R1.txt
  • 코드 위치가 ~/DEV가 아니면 --code-root <폴더>. 관련 14파일이 MAIN165와 다르면 DB에 붙기 전에 멈추고 목록을 보여줍니다.

하는 일: SELECT만 (쓰기·모델 호출·재시도 없음). 서빙과 같은 순서로 채널 → 게시본 → 본문검색 객체를 연 뒤, '정관'(한 단어)·'주주총회 결의'(두 단어)로 실제 실패 함수 호출, 같은 SQL 직접 실행, 부분별 SQL, CLOB 바인드 유무 비교, A의 Q1 문장을 ORDS로 실행합니다.

보내줄 결과: 화면 사진(단계별 PASS/FAIL, ORA 번호, 오류 위치 줄:칸) 또는 같은 폴더에 생기는 FTS_ORA22806_DIAG_RESULT_R1.json. 결과 파일에는 SQL 문장·값·인증정보가 없고 단계 이름·결과·ORA 번호·오류 위치·행 수·SQL 해시만 있습니다.

로컬 확인: 로컬 Oracle 23.26.3에 MAIN165 개발계 매핑(실버 17표)과 같은 임시 표와 게시본을 만들고, ORDS 응답만 로컬 DB 연결로 바꿔 이 TXT 안의 python을 그대로 실행 — 22단계 모두 PASS(SQL 25회, SELECT만). ORDS 오류 응답 대역에서 오류 번호·위치만 남는 것, 코드 불일치·환경변수 없음·패키지 없음일 때 멈추는 것을 확인했습니다. 실제 ORDS·현장 DB 실행은 아직입니다.
