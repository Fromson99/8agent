GENOS 로그 롤백 해시 연결 수정 R3

사진의 오류: StageRunner.verify_profile / engine manifest hash mismatch / HTTP 422.
R1/R2가 엔진 JSON의 코드 해시는 바꿨지만 00_SYSTEM/PIPELINE.json에 등록된
엔진 JSON 해시를 갱신하지 않은 반입본 작성 오류입니다. 모델 호출 전 중단됩니다.
R2를 기존 인계본에 적용하면 실제 StageRunner에서 같은 오류가 재현됩니다.
사진에는 배포 커밋/코드 해시가 없어 현장 설치본의 정확한 버전은 미확인입니다.

이번에는 GENOS_DB_LOG_ROLLBACK_20261007_R3_RUN.txt 한 개를 사용하세요.
ZIP을 먼저 풀 필요가 없습니다. R2를 이미 적용했으면 원복하지 않고 R3를 적용합니다.
R1/R2 적용 후 상태에서는 query_latency.py와 unit_fulltext.py의 코드 바이트를
그대로 유지하고 PIPELINE 등록 해시와 설치 inventory만 복구합니다.
계측 R1~R4 원본 상태에서도 기존 로그 롤백과 등록 해시 복구를 함께 적용합니다.
system_logging R1 계열의 알려진 WORKSPACE 코드 pin 불일치 24개도 정확한
기존 파일 바이트에 결속합니다. WORKSPACE 파일과 설정은 변경하지 않습니다.
지원 범위는 알려진 원본 5종과 각각의 롤백 R1/R2 적용 결과, 총 15개 inventory입니다.
알 수 없는 코드/엔진/PIPELINE/inventory는 보존하고 중단합니다.

1. RUN TXT를 기존 ~/DEV/TRANSFER에 저장합니다.
요청이 끝난 뒤 기존 코드서빙 프로세스를 중지하고 다음을 실행합니다.

cd ~/DEV/TRANSFER
bash GENOS_DB_LOG_ROLLBACK_20261007_R3_RUN.txt check
bash GENOS_DB_LOG_ROLLBACK_20261007_R3_RUN.txt apply
bash GENOS_DB_LOG_ROLLBACK_20261007_R3_RUN.txt verify

GENOS_DEV_ROOT -> GENOS_DEV -> ~/DEV 순서로 checkout을 선택합니다.
~/DEV가 심볼릭 링크여도 실제 checkout을 해결하며 내부 코드 파일의 링크는 거부합니다.
이전 환경변수로 다른 checkout을 선택하고 있으면 각 명령 앞에 같은 값을 지정합니다.

GENOS_DEV_ROOT="$(cd .. && pwd -P)" bash GENOS_DB_LOG_ROLLBACK_20261007_R3_RUN.txt check

apply/verify에도 동일한 GENOS_DEV_ROOT 값을 사용합니다.
변경 전/후에 ENGINE_BINDINGS PASS; engines=30을 확인합니다.
이 검사는 PIPELINE->엔진 JSON->코드, 슬롯/입출력, 스키마 해시를 모두 확인합니다.
GENOS_QUERY_LATENCY=1이 남아 있어도 제거한 세부 계측은 켜지지 않습니다.
검색 캐시/순위/권한/원문/세션과 일반 진행/오류/감사 로그는 유지합니다.
NFS 데이터/generation/CURRENT/.env를 변경하거나 삭제하지 않습니다.

2. apply가 출력한 BACKUP=/절대경로와 APPLIED_CODE_ZIP을 보관합니다.
receipt.json에 실제 checkout/Python/변경 전후 해시가 기록됩니다.
로그는 ~/DEV/TRANSFER/db-log-rollback-r3/logs/에 남습니다.
정상 종료 표시는 DB_LOG_ROLLBACK_EXIT=0입니다.
재실행은 같은 파일을 확인하고 ALREADY_APPLIED로 끝납니다.

3. 기존 Git checkout에서 receipt.json에 기록된 이번 변경만 확인하고 commit합니다.
task_backup에는 apply가 출력한 BACKUP 경로를 넣습니다.

task_backup='/apply가 출력한/BACKUP/절대경로'
python3 - "$task_backup" <<'R3_STAGE_PY'
import json,subprocess,sys
from pathlib import Path
receipt=json.loads((Path(sys.argv[1])/'receipt.json').read_bytes())
paths=[row['path'] for row in receipt['files']]
subprocess.run(['git','-C',receipt['root'],'diff','--check'],check=True)
subprocess.run(['git','-C',receipt['root'],'add','-f','--',*paths],check=True)
subprocess.run(['git','-C',receipt['root'],'diff','--cached','--stat'],check=True)
subprocess.run(['git','-C',receipt['root'],'diff','--cached','--check'],check=True)
R3_STAGE_PY
task_checkout="$(python3 - "$task_backup" <<'R3_ROOT_PY'
import json,sys
from pathlib import Path
print(json.loads((Path(sys.argv[1])/'receipt.json').read_bytes())['root'])
R3_ROOT_PY
)"
cd "$task_checkout"
git diff --cached
git commit -m 'Fix DB log rollback engine registry bindings'

이미 stage되어 있던 다른 변경이 보이면 먼저 분리해서 이번 변경만 commit합니다.
코드 적용만으로 이미 실행 중인 코드서빙 리비전이 바뀌지는 않습니다.

4. 실제 서빙이 선택한 generation 절대경로를 지정하고 같은 checkout에서 gate합니다.

task_generation='/실제/선택된/NFS/generation'
bash ~/DEV/TRANSFER/GENOS_DB_LOG_ROLLBACK_20261007_R3_RUN.txt gate "$task_backup" --generation "$task_generation"

gate는 30개 엔진 결속 검사, APPLIED_CODE.zip과 commit한 checkout의 전체 파일 비교,
선택 generation E2E와 verify_assets를 실행합니다. 원문/DB를 재구축하지 않습니다.
PASS 뒤 기존 원격으로 해당 commit을 push하고 같은 commit/generation으로 새
코드서빙 리비전을 배포합니다. 기존 시작 명령/모드/환경변수/플랫폼 연결을 유지합니다.
분리 Python 워크플로우 편집기는 이번 수정 대상이 아닙니다.
현장 질의 확인은 워크플로우 테스트 화면에서 진행합니다.
engine manifest hash mismatch가 사라지고 기존 질의가 진행되는지 확인합니다.
배포 commit/리비전/generation manifest 해시/요청 ID/결과를 함께 기록합니다.

5. 이번 R3 적용만 되돌릴 때:

bash ~/DEV/TRANSFER/GENOS_DB_LOG_ROLLBACK_20261007_R3_RUN.txt undo "$task_backup"

R3 이전 상태로 정확히 복구합니다. R2 적용 후 R3를 실행했다면 R2의 해시 오류 상태로
돌아가므로 서비스 복구 목적에는 기존 검증된 리비전의 별도 재배포가 필요합니다.
이후 수정/백업 변조는 보존하고 원복을 거부합니다.

확인 결과: 15개 inventory에서 실제 실행 TXT 150회, 실제 StageRunner의 모든
profile 검사 15회, R1/R2 사진 오류 재현 10회, 모의 compact generation의 동일
checkout 배포 gate 5개가 통과했습니다. 모델 호출은 없습니다.
이전 R1/R2의 검사는 PIPELINE 등록 해시를 검사하지 않아 이번 오류를 놓쳤습니다.
이번 R3 검증을 이전 반입본의 성공으로 소급하지 않습니다.
로컬 MAIN45 포인터는 유지했습니다. GENOS 실제 apply/push/리비전 배포와 내부
질의 결과는 아직 미확인입니다. 메일 발송 여부는 별도 발송 기록에서 확인합니다.
