GENOS 내규 최신 판본 선택 R1 (2026-10-15)

같은 폴더에서 위험관리기준시행세칙(20190710).docx처럼 문서명 끝 날짜만 다른 파일은
유효한 8자리 날짜가 가장 큰 판본만 구조화합니다. 구버전 RAW는 보존합니다.
같은 판본의 DOCX/PDF는 기존 원본 우선 규칙을 유지합니다.
이름/폴더가 다르면 별개 문서입니다. 파일명 날짜가 법률상 현행 시행일이라는 뜻은 아닙니다.

1. 실제 업로드한 TRANSFER 폴더를 현재 위치로 두고 실행

python3 -m zipfile -e ./GENOS_LATEST_INTERNAL_20261015_R1.zip ./latest-internal-r1-package
bash ./latest-internal-r1-package/GENOS_LATEST_INTERNAL_20261015_R1_RUN.txt check
bash ./latest-internal-r1-package/GENOS_LATEST_INTERNAL_20261015_R1_RUN.txt apply

설치기는 기존 ~/DEV Git checkout의 구축 파일 7개만 적용합니다.
현재 폴더인 TRANSFER의 절대 위치는 가정하지 않습니다.
다른 실제 checkout을 쓰는 경우에만 GENOS_DEV_ROOT를 그 절대 경로로 명시합니다.
로그는 현재 TRANSFER의 latest-internal-*.log, 원본 백업은 콘솔의 BACKUP= 경로입니다.
알 수 없는 코드/의존성이나 전체 CODE_MANIFEST 충돌은 파일을 보존하고 REBASE_REQUIRED로 중단합니다.
검증을 건너뛰거나 해시를 수동 변경하지 마세요. 기존 구축 작업이 종료된 뒤 적용합니다.
설치 PASS는 실제 데이터 구축/검색 전환 성공이 아닙니다.

2. 코드 적용 후 DEV에서 최신본 선택 목록 확인

cd ~/DEV
python3 -B 06_TOOLS/pipeline.py build-all --no-models --latest-internal-versions --run-id latest-internal-20261015-r1 --check-only

같은 입력/정책으로 아래 실행을 이어갑니다. 입력 파일이나 판본을 바꾸면 새 run ID를 사용합니다.
기본/명시 BUILD_SCOPE와 충돌하면 임의로 포인터를 지우지 않습니다.
사진의 내규만 먼저 확인할 때는 별도 검사 run으로 다음 명령을 사용합니다.
python3 -B 06_TOOLS/pipeline.py build-data-stages --only-internal --latest-internal-versions --run-id latest-internal-inspect-20261015-r1 --check-only

코드가 해석한 논리 data root의 LOGS/<run-id>/inventory-*.json과 doc-status.html/CSV를 확인합니다.
TEAM_LAYOUT이 있으면 *_team 아래의 현재 선택 자료를 읽습니다. 사진의 원본이 실제 목록에
포함되었는지 확인합니다. 기존 비팀 폴더가 이력 복사본으로 제외되는 환경에서는
이미 사용하는 RAW 반입/팀 갱신 절차로 먼저 명시 반입해야 합니다.
임의로 옛 폴더와 팀 폴더를 모두 합치지 않습니다.
최신 날짜에 내용이 다른 복사본, 같은 제목의 무날짜/6자리 날짜 혼재, 잘못된 날짜는 중단합니다.
6자리 날짜만 있는 문서군은 이 패치로 최신 여부를 판단하지 않고 그대로 유지합니다.
문서 목록에서 선택 날짜/선택 경로/구버전 제외 사유(superseded_filename_version)를 확인합니다.
최신본 파싱이 실패해도 옛 판본으로 자동 대체하지 않습니다.

3. 유지할 내규/외규 전체 RAW 범위를 확인한 후 새 구조화·색인 생성

python3 -B 06_TOOLS/pipeline.py build-all --no-models --latest-internal-versions --run-id latest-internal-20261015-r1 --execute

기존 용어집/지식 묶음과 native 파서 의존성이 준비된 현재 build-all 경로를 사용합니다.
모델 없는 구조화 → 원문 통합/용어 근거 갱신 → compact-v2/단위 전문 색인입니다.
사전/지식 묶음 반입을 대신하지 않습니다. 필요한 명시 --glossary-dir는 기존 선택을 그대로 씁니다.
--base-generation은 구버전 재유입을 막기 위해 함께 쓰지 못합니다.
기존 검색 세대를 통째로 합치지 말고 유지할 외규도 포함한 RAW 범위에서 새로 구축합니다.
--only-internal/--team으로 만든 부분 후보를 전체 서비스 데이터로 오인하지 마세요.
기존 RAW·완료 세대·캐시는 보존되고 CURRENT는 이 명령으로 변경되지 않습니다.

4. 실제 새 generation 검증과 검색 전환

완료 출력의 generation_path를 사용합니다. 보통 reindex 산출물은
논리 data root/TERM_RELEASES/latest-internal-20261015-r1-index/ 아래이며,
정확한 generation 위치는 결과 receipt로 확인합니다. 날짜순 폴더를 자동 선택하지 않습니다.
CODE.zip은 위 TRANSFER에서 푼 패키지 안의 코드 7개를 봉인한 ZIP입니다.

DEV에서 git diff --check와 변경 파일 검토 후 기존 절차로 commit합니다.
다음의 <...>에는 확인한 실제 절대 경로를 넣습니다.
python3 -B 06_TOOLS/COMMANDS/genos_release_gate.py --code-zip <실제TRANSFER>/latest-internal-r1-package/CODE.zip --deploy-root <실제DEV> --generation <새generation절대경로>

같은 committed DEV의 코드/manifest/서빙 자원/선택 generation을 검사합니다.
게이트 통과 후 그 커밋을 기존 절차로 push하고 코드서빙 새 리비전을 배포합니다.
GENOS_GENERATION을 검증한 새 generation으로 명시 선택하거나, 기존 CURRENT 활성화 절차를
확인된 새 세대로 수행합니다. 명시 GENOS_GENERATION이 있으면 CURRENT보다 우선합니다.
코드스페이스에서만 보이는 경로라면 먼저 기존 NFS 반입 절차를 통해 두 실행 환경이
공유하는 새 generation 경로로 게시한 뒤 그 실제 경로로 게이트를 다시 실행합니다.
프로세스를 재시작해 이전 세대 캐시를 교체하고, 워크플로우 테스트 화면에서
선택 세대/요청 ID와 해당 규정 질문의 출처 날짜를 확인합니다. 직접 코드서빙 테스트 UI/API는 요구하지 않습니다.
워크플로우 Python 편집기 변경은 이 선택 기능에 필요하지 않습니다.

코드 적용 / 구조화 / 색인 / NFS 게시 / Git push / 새 리비전 / 실제 검색 확인은 각각 별도입니다.
현재 패키지는 외부 WSL에서 준비한 적용본이며 실제 GENOS의 이 단계들은 미확인입니다.

5. 원복

검색 전환 후 문제가 있으면 보존한 이전 코드서빙 리비전과 이전 generation 경로를 함께
복구하고 프로세스를 재시작합니다. 이전 세대를 삭제하지 않습니다.
구축 코드 원복은 실제 TRANSFER에서 다음처럼 정확한 BACKUP 경로를 지정합니다.
bash ./latest-internal-r1-package/GENOS_LATEST_INTERNAL_20261015_R1_RUN.txt undo <apply출력의BACKUP절대경로>

재실행은 설치된 동일 해시를 확인해 ALREADY_APPLIED를 표시합니다.
후속 변경으로 코드가 달라졌다면 자동 원복은 거부하며 그 파일을 보존합니다.
로그/선택 보고서에는 내부 파일명이 있으므로 GENOS 내부에서 보관합니다.
