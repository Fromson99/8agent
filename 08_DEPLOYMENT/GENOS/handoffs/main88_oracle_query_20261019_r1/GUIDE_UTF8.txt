2. TRANSFER에서 적용 — 사용자 현장 경로를 확인
ZIP/TXT를 실제 업로드한 TRANSFER 폴더를 현재 터미널 작업 위치로 둡니다.
TRANSFER의 절대경로를 추정하거나 압축 해제를 위해 먼저 DEV로 이동하지 않습니다.
아래 /workspace는 제공된 현장 사진에서 확인된 기존 checkout 실제 경로입니다.
현재 현장에서도 git rev-parse --show-toplevel 결과와 같은지 확인하고, 다르면 확인한 경로로 바꾸십시오.
~/DEV가 /workspace를 가리키는 심볼릭 링크여도 설치기는 실제 경로를 확인합니다.

python3 -m zipfile -e ./GENOS_MAIN88_ORACLE_QUERY_20261019_R1.zip ./GENOS_MAIN88_ORACLE_QUERY_20261019_R1
bash ./GENOS_MAIN88_ORACLE_QUERY_20261019_R1/GENOS_MAIN88_ORACLE_QUERY_20261019_R1_RUN.txt deps --root /workspace
bash ./GENOS_MAIN88_ORACLE_QUERY_20261019_R1/GENOS_MAIN88_ORACLE_QUERY_20261019_R1_RUN.txt check --root /workspace
bash ./GENOS_MAIN88_ORACLE_QUERY_20261019_R1/GENOS_MAIN88_ORACLE_QUERY_20261019_R1_RUN.txt apply --root /workspace
bash ./GENOS_MAIN88_ORACLE_QUERY_20261019_R1/GENOS_MAIN88_ORACLE_QUERY_20261019_R1_RUN.txt status --root /workspace

deps는 동봉된 sqlglot==30.23.0 wheel만 --no-index --no-deps로 설치합니다. 기존 런타임 의존성은 유지합니다.
실제 Python 실행 파일/버전이 로그에 남습니다. 최소 Python 3.11입니다.
별도 첨부 RUN.txt도 ZIP 옆에서 실행하면 압축 해제 후 같은 명령으로 연결합니다.
최초 실행부터 TRANSFER/main88-oracle-query-r1-logs에 로그와 종료 코드를 보존합니다.
설치 상태/실패는 패키지 폴더의 STATUS.json/LAST_FAILURE.json에 남습니다.
코드 백업은 기존 checkout의 09_ARTIFACTS/BACKUPS/code-replacement에 남습니다.
check 실패를 무시하고 apply하지 마십시오. 중단된 apply는 원본 복원 후 재시도하도록 연결했습니다.
다른 사용자가 이후 수정한 파일이 발견되면 덮어쓰거나 원복하지 않고 오류로 멈춥니다.

3. Git commit → 동일 checkout 코드 게이트 → push → 새 리비전
적용한 기존 checkout에서 git diff --check와 변경 파일을 검토해 commit합니다.
.env, 데이터, TRANSFER, 로그/백업은 Git에 추가하지 않습니다.
CODE_MANIFEST.json과 설치 receipt.units에 나오는 변경 코드 파일을 commit 대상으로 확인합니다.
그 후 TRANSFER에서 아래 코드 전용 게이트를 실행합니다.

bash ./GENOS_MAIN88_ORACLE_QUERY_20261019_R1/GENOS_MAIN88_ORACLE_QUERY_20261019_R1_RUN.txt gate-code --root /workspace

게이트는 APPLIED_CODE.zip의 모든 파일을 실제 checkout의 추적 파일 및 HEAD와 대조합니다.
후속 수정이 있으면 새 commit 후 다시 검사합니다. 통과한 commit을 기존 승인된 원격에 push하고
코드서빙 새 리비전이 그 commit인지 확인합니다. 이 스크립트가 자동 push/배포하지는 않습니다.

4. Oracle 조회 데이터 준비 — Dataiku에서 수행
기존 원문 이관 완료 release_id와 새 조회 release_id는 서로 다릅니다.
조회 테이블 4개를 허용한 전제로 DDL과 게시 명령을 포함했습니다. 기존 테이블 DROP/ALTER는 없습니다.
스키마 owner SIDDA와 ORDS 접속 schema b04를 혼동하지 마십시오.
이 패키지의 코드를 Dataiku 실행 코드에도 적용하고 sqlglot wheel을 같은 Python 환경에 설치한 뒤 실행합니다.
아래 <...>는 실제 경로/receipt 값으로 대체해야 합니다. 인증 정보는 기존 검증된 접속 설정을 사용합니다.

python3 06_TOOLS/pipeline.py oracle-query check-schema --log-dir <스키마확인로그>
python3 06_TOOLS/pipeline.py oracle-query create-schema --log-dir <스키마생성로그>
python3 06_TOOLS/pipeline.py oracle-query publish --generation <Dataiku검증세대폴더> --source-release-id <기존원문릴리스ID> --log-dir <새게시로그폴더>
python3 06_TOOLS/pipeline.py oracle-query activate --channel main --release-id <완료된새조회릴리스ID> --expected-revision 0 --log-dir <활성화로그폴더>

expected-revision 0은 채널 최초 생성에만 씁니다. 기존 채널 갱신/원복에는 현재 revision과
--expected-release-id <현재조회릴리스ID>를 함께 지정합니다. COMPLETE 결과와 receipt를 보존합니다.
기존 query 게시 결과가 있다면 현재 코드의 compiler/schema 지문에 맞게 다시 게시해야 할 수 있습니다.
법제처 갱신 Dataiku 스케줄 등록은 이번 패키지가 자동 수행하지 않습니다. 매일 배치는
수집/구조화/색인 → 원문 이관 → 조회 게시 COMPLETE 확인 → 채널 활성화 순서로 연결합니다.
게시 실패 시 이전 채널을 유지하고 같은 receipt로 재개합니다. 새 요청은 새 버전,
진행 중 요청은 처음 선택한 이전 버전을 끝까지 사용합니다. 이전 불변 릴리스는 자동 삭제하지 않습니다.

5. 코드서빙 설정 / 저장 방식
DP=oracle
DP_QUERY_CHANNEL=main
GENOS_RUNTIME_DIR=<실제 외부 NFS/CIFS runtime 절대경로>
GENOS_SHARED_LOG_DIR=<실제 외부 NFS/CIFS 요청 로그 경로; 별도 지정할 때>
ORACLE_ORDS_BASE_URL / ORACLE_ORDS_SCHEMA / ORACLE_ORDS_CLIENT_ID / ORACLE_ORDS_CLIENT_SECRET는 기존 접속 값을 사용합니다.
내부 GENOS 모델/팀 설정을 유지하고 시작 명령은 python3 main_router.py입니다.

채널 대신 특정 조회 버전 고정 시 DP_QUERY_CHANNEL을 제거하고 DP_QUERY_RELEASE_ID=<조회릴리스ID>를 씁니다.
두 설정을 동시에 넣지 마십시오. 둘 다 없으면 main 채널을 선택합니다.
DP_RELEASE_ID / DP_CACHE_DIR는 새 Oracle 서빙 경로에서 사용하지 않습니다.
원문/색인 전체 다운로드 및 서빙 데이터 SQLite 저장은 없습니다. 필요한 행/본문만 요청 메모리로 읽습니다.
대화·사건·대사·요청 로그 등 기존 상태는 외부 NFS/CIFS에 유지합니다. STATE 테이블로 이관한 것은 아닙니다.
외부 마운트가 빠지면 로컬 디스크로 대체하지 않고 오류를 반환합니다.
이전 GENOS_SERVING_PATHS.json은 보존하지만 Oracle 모드에서는 그 SQLite 경로 설정을 읽지 않습니다.
DP=sqlite 또는 DP 미설정은 기존 세대/SQLite 동작을 유지합니다.
