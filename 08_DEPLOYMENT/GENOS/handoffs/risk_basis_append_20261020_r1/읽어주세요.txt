위험관리기준시행세칙 — 선택된 한 판본에 검토한 외규 연결 4건 추가

이 ZIP은 기존 ~/DEV에 작은 오프라인 배치 코드를 추가합니다.
일반화된 자동 연결, 원문 재적재, 전체 색인, MAIN 전환, 서빙 배포는 실행하지 않습니다.
상세 계약/실패 복구/연결 목록은 RISK_BASIS_APPEND_20261020.txt를 참고하십시오.

1. 업로드한 TRANSFER 폴더에서 시작

python3 -m zipfile -e ./GENOS_RISK_BASIS_APPEND_20261020_R1.zip ./GENOS_RISK_BASIS_APPEND_20261020_R1
bash ./GENOS_RISK_BASIS_APPEND_20261020_R1/GENOS_RISK_BASIS_APPEND_20261020_R1_RUN.txt check
bash ./GENOS_RISK_BASIS_APPEND_20261020_R1/GENOS_RISK_BASIS_APPEND_20261020_R1_RUN.txt install

TRANSFER의 절대 위치를 가정하지 않습니다. 현재 폴더를 유지합니다.
install은 검증한 파일만 기존 ~/DEV에 적용하고 원본 백업과 영속 실행 로그를 남깁니다.
다른 DEV 경로라면 RISK_BASIS_DEV_ROOT에 실제 checkout 경로를 지정하십시오.
check가 다른 파일 해시를 발견하면 파일을 덮어쓰지 않고 종료합니다.
이때 나온 코드/로그로 차이를 확인해야 하며 CODE_MANIFEST를 임의 수정하지 않습니다.

2. config.json 설정

압축을 푼 폴더의 config.json에서 principal.user_id를 실제 현장 실행자 ID로 수정합니다.
principal.team_id=risk_team, basis_review=true는 이 고정 4건 추가를 실행하는 배치 권한입니다.
이 config를 일반 채팅 사용자의 입력으로 받는 API에 노출하지 않습니다.
table_map은 현장 관계 원장 테이블 이름과 일치시킵니다. 기본 SIDDA.LEGAL_BASIS_*_A는
제안 이름이며 기존 현장 테이블의 존재를 확인한 값이 아닙니다.
query_release_id/query_channel은 비워 두면 기존 DP_QUERY_RELEASE_ID 또는
DP_QUERY_CHANNEL 환경변수를 사용합니다. 기존 RAG와 같은 설정인지 확인하십시오.
두 선택 값을 동시에 설정하지 않습니다.
ORDS 접속 키는 기존 GENOS 환경변수를 사용하며 config/ZIP에 쓰지 않습니다.

Dataiku에서 실행할 경우 backend=dataiku, dataiku_connection에 기존 연결명을 지정하고
같은 CLI main을 Dataiku Python 환경에서 실행합니다. API/원문·쿼리 릴리스 선택은 동일합니다.
GENOS/Dataiku 환경 의존성은 기존 것을 사용하며 이 ZIP은 인터넷 설치를 수행하지 않습니다.

3. 문서 확인 → 계획/SQL 출력 (DB 쓰기 없음)

bash ./GENOS_RISK_BASIS_APPEND_20261020_R1/GENOS_RISK_BASIS_APPEND_20261020_R1_RUN.txt inspect
bash ./GENOS_RISK_BASIS_APPEND_20261020_R1/GENOS_RISK_BASIS_APPEND_20261020_R1_RUN.txt plan

현재 폴더의 GENOS_RISK_BASIS_APPEND_20261020_R1_STATE/db 아래에서 확인합니다.
documents.json: 기존 RAG 필터 후 문서 목록·문서 ID·원문 hash
resolved.json: 내규 4곳과 외규 7범위의 실제 ID 및 인용
plan.json: 고정 계획·해시·관계 이력 행
APPEND_ONLY.sql: 나중에 별도 운영 DB 세션에서 실행할 수 있는 SQL
REVOKE_THIS_BATCH.sql: 이 배치 신규 연결만 취소하는 SQL

필터 후 위험관리기준시행세칙이 없거나 여러 개면 종료합니다.
별표10 구조나 좌표가 다르면 실패 기록을 확인합니다. 과거 판본을 임의로 고르지 않습니다.
현장 ID가 확인되지 않은 상태에서 실행 SQL을 미리 채워 넣지 않았습니다.
원장 스키마가 없으면 plan은 쓰기 없이 실패합니다. 아래 명령은 DDL만 출력합니다.

bash ./GENOS_RISK_BASIS_APPEND_20261020_R1/GENOS_RISK_BASIS_APPEND_20261020_R1_RUN.txt schema

OPTIONAL_BASIS_SCHEMA.sql은 DBA가 누락된 관계 테이블만 검토/생성할 때 사용합니다.
기존 다른 스키마의 이름만 바꾸거나 DROP/CREATE하여 덮어쓰지 않습니다.

4. 추가 적용과 확인

bash ./GENOS_RISK_BASIS_APPEND_20261020_R1/GENOS_RISK_BASIS_APPEND_20261020_R1_RUN.txt apply
bash ./GENOS_RISK_BASIS_APPEND_20261020_R1/GENOS_RISK_BASIS_APPEND_20261020_R1_RUN.txt verify

apply는 plan.json으로 생성한 한 트랜잭션을 실행합니다.
성공 시 receipt-apply.json/receipt-verify.json에서 APPEND_VERIFIED,
resolver_endpoint_count=7을 확인합니다. 신규 관계는 4개보다 적을 수 있습니다.
이미 승인된 같은 관계는 재사용하기 때문입니다.

SQL만 나중에 실행하려면 APPEND_ONLY.sql을 SQL*Plus/SQLcl에서 실행할 수 있습니다.
그 후에도 이 도구의 verify를 실행하십시오.
SQL은 생성 당시 문서·원문·조회 릴리스·판본 필터에 고정되어 있습니다.
다른 데이터/ID/릴리스가 있는 운영 DB로 그대로 복사하지 않고 운영계에서 plan을 생성합니다.

전송 중 오류는 실패/미확정입니다. 같은 plan을 보존하여 verify로 먼저 확인합니다.
plan을 지우고 새로 만들면 새로운 UUID와 이력을 만들므로 원래 계획을 재사용하십시오.
같은 SQL은 idempotent이며 다른 계획/변경된 head 충돌은 rollback합니다.
원문/판본 선택이 바뀌었으면 이전 SQL은 거부됩니다.

5. 취소/코드 복원

bash ./GENOS_RISK_BASIS_APPEND_20261020_R1/GENOS_RISK_BASIS_APPEND_20261020_R1_RUN.txt revoke
bash ./GENOS_RISK_BASIS_APPEND_20261020_R1/GENOS_RISK_BASIS_APPEND_20261020_R1_RUN.txt verify-revoked
bash ./GENOS_RISK_BASIS_APPEND_20261020_R1/GENOS_RISK_BASIS_APPEND_20261020_R1_RUN.txt rollback-code

revoke는 신규 관계의 revision만 REVOKED로 전이하며 기존 이력을 삭제하지 않습니다.
다른 사용자가 해당 관계를 수정했다면 CAS 충돌로 멈춥니다.
rollback-code는 코드만 복원합니다. DB 취소와 별개입니다.
원래 선택 판본이 바뀐 뒤 취소가 필요하면 그 판본의 plan/receipt를 보존해 별도로 검토합니다.

6. 검증 범위

로컬 사진 기반 문서로 4관계/8연결선/7외규범위 회수와 기존 Service/resolver/API 계약을 검사했습니다.
선택된 MAIN92 코드 소비자와의 호환 검사 및 ZIP의 설치/재실행/수정 충돌/복원 검사를 수행합니다.
최종 실측 결과는 동봉한 LOCAL_VALIDATION.json을 참고하십시오.
현재 로컬 MAIN에는 이 내규가 없어서 MAIN 데이터/선택 릴리스는 변경하지 않았습니다.
현장 Oracle 엔진·GENOS는 접근 불가이므로 실제 SQL 실행/배포/채팅 사용은 미검증입니다.
verify의 rag_factory_deployment_verified=false는 현장 RAG 배선을 검증하지 않았다는 표시입니다.
GENOS가 같은 원장/table_map을 읽도록 배선되어 있어야 실제 채팅에서 활용됩니다.
현장 질문 확인은 워크플로우 테스트 화면에서 수행합니다. 코드서빙 직접 테스트를 요구하지 않습니다.
