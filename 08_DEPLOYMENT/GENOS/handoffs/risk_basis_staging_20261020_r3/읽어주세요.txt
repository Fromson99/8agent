확정 연결도 같은 JSON 검토함으로 — GENOS_RISK_BASIS_REVIEW_20261020_R3

이번 R3를 사용합니다. 앞서 보낸 Oracle R1과 SQLite 직접 적용 R2는 사용하지 마세요.
일반 조사 후보 + 위험관리기준시행세칙 확정 4건을 같은 job/CANDIDATES.json에 저장합니다.
LINKS.html 확인 → 선택 기록(REVIEW.json) → 검토된 묶음 ZIP → 운영 SQLite 순서입니다.
확정 목록은 사용자 지정 APPROVED로 JSON에만 저장합니다. SQLite 이관 승인과 별개입니다.
일반 모델 후보는 원래 PROPOSED 상태를 유지합니다. 법률 판단 정답 인증은 아닙니다.

기본 저장 위치
기존 ~/DEV/00_SYSTEM/GENOS_SERVING_PATHS.json의 runtime 아래
basis-batch/pilot-review-20261020-r1/CANDIDATES.json
공통 stage-plan의 위치와 같습니다. 다른 job을 쓰면 모든 명령에 --job 실제작업폴더를 붙입니다.
기존 PLAN.json, STATE.json과 일반 후보를 보존합니다. 현재 조회 가능한 내규 최종 판본 한 문서를 선택합니다.
확정 내규가 작은 모델 조사 목록에 없더라도 검토 HTML에는 추가하며 원래 조사 계획은 바꾸지 않습니다.
원문 전체·색인·CURRENT·MAIN과 기존 SQLite에는 stage-fixed가 쓰지 않습니다.

1) 실제 업로드한 TRANSFER 폴더에서 압축 해제
python3 -m zipfile -e ./GENOS_RISK_BASIS_REVIEW_20261020_R3.zip ./GENOS_RISK_BASIS_REVIEW_20261020_R3

이 도구는 기존 ~/DEV를 확인한 뒤 별도 도구 폴더에서 실행하며 checkout을 설치/덮어쓰지 않습니다.
~/DEV의 실경로 별칭은 지원합니다. 다른 checkout이면 --root 실제경로를 붙입니다.
별도 일반 배치 GENOS_BASIS_BATCH 최신 R3 소비자 코드 394파일과 해시가 일치해야 합니다.
이 ZIP에는 같은 JSON/HTML/이관 공통 도구를 포함하므로 이후 명령을 한 RUN.txt로 실행합니다.

2) 공통 검토 배치가 이미 있으면 아래 stage-plan은 생략합니다.
새 검토 배치가 필요할 때만:
bash ./GENOS_RISK_BASIS_REVIEW_20261020_R3/GENOS_RISK_BASIS_REVIEW_20261020_R3_RUN.txt stage-plan --count 3

일반 내규 조사 실행은 공통 stage-run/stage-resume입니다. 확정 4건만 넣을 때 stage-run은 필요 없습니다.
현재 직접 SQLite를 쓰는 옛 R3 배치를 이 명령이 자동 전환하거나 기존 저장분을 삭제하지 않습니다.
이미 있는 PLAN은 덮어쓰지 않습니다. 기존 JSON 검토 배치의 job을 그대로 선택합니다.

3) 확정 내규/외규 위치 확인 → 같은 JSON에 추가
bash ./GENOS_RISK_BASIS_REVIEW_20261020_R3/GENOS_RISK_BASIS_REVIEW_20261020_R3_RUN.txt inspect-fixed
bash ./GENOS_RISK_BASIS_REVIEW_20261020_R3/GENOS_RISK_BASIS_REVIEW_20261020_R3_RUN.txt stage-fixed

성공: STAGED 또는 STAGED_REUSED, published_to_sqlite=false.
모델 호출은 없습니다. 내규 제6-4조1항/2항, 제1-4조1항3호, 제2-1조1항3호의
기존 지정 연결 4건(외규 범위7개)을 현장 문서 ID/조항/원문으로 다시 찾습니다.
정확히 같은 후보가 있으면 같은 ID·발견 이력을 유지해 JSON에 승인 revision을 추가합니다.
이미 승인됐으면 재사용합니다. 반려·취소·중복 동일 후보는 변경하지 않고 중단합니다.
다른 외규/범위/관계 종류는 별도 경로로 유지합니다. 모든 의미상 중복을 병합하지 않습니다.
4건은 하나의 JSON 원자적 교체로 저장합니다. 중간 실패는 전부 미저장입니다.
응답을 잃었을 때 같은 stage-fixed를 재실행하면 receipt로 확인합니다. 후속 수정 상태는 덮어쓰지 않습니다.
다른 후보 기록과 파일 잠금이 겹치면 BUSY로 종료하며 다음 재실행 때 최신 JSON을 다시 읽습니다.

4) 일반 후보와 함께 HTML 및 이관 묶음 생성
bash ./GENOS_RISK_BASIS_REVIEW_20261020_R3/GENOS_RISK_BASIS_REVIEW_20261020_R3_RUN.txt report --output ./전체연결검토.html
bash ./GENOS_RISK_BASIS_REVIEW_20261020_R3/GENOS_RISK_BASIS_REVIEW_20261020_R3_RUN.txt export --output ./BASIS_REVIEW_ALL

BASIS_REVIEW_ALL/LINKS.html을 열어 확인합니다. 여러 외규 조항은 같은 연결 행에 표시됩니다.
HTML 생성/내보내기까지 SQLite는 변경하지 않습니다. 묶음은 해당 시각의 스냅샷입니다.
추가 후보가 생겼으면 다른 출력 이름으로 다시 export하고 새 HTML을 확인합니다.

5) 검토한 항목을 선택하고 데이터+실행코드 함께 포장
bash ./BASIS_REVIEW_ALL/APPLY_RELATIONS.txt review --all
일부만: --all 대신 --ids 연결ID1 연결ID2 ...

REVIEW.json / REVIEWED.sql / BASIS_REVIEW_ALL_REVIEWED.zip을 만듭니다.
이 단계도 SQLite에 쓰지 않습니다. 검토 기록 없는 apply는 거부합니다.
운영으로 옮길 것은 BASIS_REVIEW_ALL_REVIEWED.zip 하나입니다.

6) 운영의 실제 TRANSFER 폴더에서 검토된 묶음을 풀고 한 번에 적용
python3 -m zipfile -e ./BASIS_REVIEW_ALL_REVIEWED.zip .
bash ./BASIS_REVIEW_ALL/APPLY_RELATIONS.txt check
bash ./BASIS_REVIEW_ALL/APPLY_RELATIONS.txt apply
bash ./BASIS_REVIEW_ALL/APPLY_RELATIONS.txt status

운영 원문/판본/검색 선택은 개발에서 복사한 동일 세대여야 합니다. 경로는 달라도 됩니다.
운영 ~/DEV의 GENOS_SERVING_PATHS.json이 선택한 runtime/basis-links/authority.sqlite에 반영합니다.
선택한 일반 후보와 확정 연결을 같은 트랜잭션으로 추가합니다. 같은 ID/이력 재적용은 건너뜁니다.
같은 ID의 운영 상태/이력이 다르면 전체 중단합니다. 기존 운영 승인을 덮어쓰지 않습니다.
기존 SQLite의 다른 ID까지 의미상 중복을 합치지는 않습니다. 계획의 중복 확인은 같은 JSON 검토함 기준입니다.
되돌리기: bash ./BASIS_REVIEW_ALL/APPLY_RELATIONS.txt rollback
이번 묶음이 신규 삽입한 관계만 REVOKED 이력을 추가하며 이전 이력은 보존합니다.

실행 로그: TRANSFER/risk-fixed-review-logs 및 basis-transfer-logs.
고정 연결 receipt/실패 기록은 같은 job의 RISK_FIXED_*.json에 저장합니다.
개발 단계의 원래 JSON은 이관 후에도 보존합니다. 검토와 이관 기록도 함께 보존하십시오.
