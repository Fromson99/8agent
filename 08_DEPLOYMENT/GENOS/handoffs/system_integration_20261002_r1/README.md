# 전체 시스템 통합 반입 안내 — 2026-10-02 R1

최신 MAIN 작업 코드와 누적 멀티턴 정정 구현을 통합한 코드 반입본이다. 로컬 작업 코드 반영은 완료했으며 Git main 병합, 활성 MAIN 전환, GENOS 배포는 별도다. `CHECKLIST.md`가 전체 요구의 구현/검증/보류 상태 정본이다. 법률 도메인 온톨로지 전체 통제는 아직 설계 단계다.

## 묶음 구성

| 파일 | 용도 |
|---|---|
| `code.zip`, `CODE_MANIFEST.json`, `DELIVERY.json` | 현행 전체 코드, 파일별 해시, 정확한 반입 상태 |
| `evidence.zip`, `HISTORY_MANIFEST.json` | ADR0590~0613 및 관련 설계·실패·실험 코드의 보관본 |
| `migration-audit.zip` | 이번 변경의 이전 코드, 검증 로그·테스트·적용 영수증 |
| `WORKFLOW_PASTE_ALL.txt`, `WORKFLOW.py` | 워크플로우 Python 단계 전체 교체본 |
| `RUN.sh`, `apply.py`, `verify.py` | 지속 로그, 파일별 백업·적용·재확인·복구 |
| `GENOS_APPLY_VERIFY_ROLLBACK_UTF8.txt` | 현장 순서와 명령 |
| `VALIDATION.json`, `CHECKLIST.md`, `CURRENT_STATE.md` | 통과와 실패, 구현 범위, 남은 일 |
| `CHECKSUMS.sha256` | 배포 폴더의 최종 파일 해시 |

`code.zip`에는 원문 세대·환경 파일·인증키·실험 DB가 없다. 기존 코드가 실제로 참조하는 동결 도구 세대는 그대로 포함했다. `evidence.zip`의 과거 SQLite는 실험 증거이며 운영 온톨로지로 가져오지 않는다. 기존 NFS 원문/용어집/색인/선택 포인터와 승인 상태는 현장에 보존한다. 이 ZIP은 NFS 데이터 전체 복사본이 아니다.

## 적용 순서

반입 폴더를 터미널에서 연 뒤 `GENOS_APPLY_VERIFY_ROLLBACK_UTF8.txt`를 따른다. 기본 대상은 기존 `~/DEV`이며 임시 후보 폴더만 만드는 방식이 아니다. 실행 명령은 `python3`이고 Python 3.11 이상이 필요하다. 실행 시 실제 인터프리터와 버전을 기록한다. 의존성은 코드 ZIP의 기존 GENOS 의존성 명세를 유지한다. 현재 설치 환경을 임의로 업그레이드하지 않는다.

1. `bash RUN.sh check`: ZIP·설치기·워크플로우 동일성, 기존 경로 확인.
2. `bash RUN.sh apply`: 기존 파일을 백업하고 전체 코드 파일을 덮어쓴 뒤 모든 파일 해시 확인. 같은 명령을 다시 실행하면 이미 적용된 상태를 검증한다.
3. `bash RUN.sh generation`: 기존 설정이 선택한 generation의 원문/navigation/fulltext 결속을 읽기 전용 확인한다. 미선택은 종료 코드 3으로 남으며 구축 성공으로 처리하지 않는다.
4. 현장 Git 변경을 검토하고 해당 코드 파일을 커밋한다. 환경 파일·데이터·백업·증거 ZIP은 커밋 대상이 아니다. `bash RUN.sh gate`는 ZIP과 **커밋된 checkout** 및 선택 generation이 일치하는지 확인한다. 이 검사를 통과하기 전 push/배포 성공으로 기록하지 않는다.
5. 사용자가 관리하는 현장 절차로 push와 코드서빙 새 리비전을 수행하고 커밋·리비전·generation을 기록한다. 이 반입 스크립트는 push나 배포를 실행하지 않는다.
6. 워크플로우 Python 편집기에 `WORKFLOW_PASTE_ALL.txt` 전체를 별도로 반영한다. 코드 ZIP만 반영해서는 워크플로우가 바뀌지 않는다.
7. 실제 요청·warmup은 **워크플로우 테스트 화면**에서 확인한다. 일반 RAG, 내규/외규 범위, 진행 UI, 출처 표기를 먼저 확인한다.

모든 실행의 성공·실패 상태는 반입 폴더 `logs/`에 남는다. 미완료 설치가 있으면 새 적용을 막고 기존 영수증 복구를 요구한다. 현재 파일이 다른 작업으로 변경됐으면 재실행·롤백이 덮어쓰지 않고 중단한다.

## 멀티턴 설정과 입력 계약

새 기능은 워크플로우 `GENOS_MEMORY_ENABLED=0`이 기본값이다. 품질 평가와 신뢰 경계 확인 전 이 값을 유지한다. 활성화 시 아래 설정이 필요하다.

| 설정/입력 | 위치와 책임 |
|---|---|
| `GENOS_MEMORY_ENABLED=1` | 워크플로우 설정. 새 멀티턴 요청 경로 선택 |
| `GENOS_MEMORY_SIGNING_KEY` | 워크플로우와 코드서빙의 동일한 비밀 설정. 32자 이상, 채팅/소스/로그에 넣지 않음 |
| `TEAM_ID` | 워크플로우의 고정 실제 팀 폴더 ID. 사용자가 임의로 바꾸는 채팅 필드로 승인하지 않음 |
| 스튜디오 사용자·대화 ID | 플랫폼이 제공한 신뢰된 값인지 현장에서 확인. 익명 값은 거부 |
| `question`, `request_id` | 현재 발언과 논리 요청 ID. 재시도는 같은 ID, 새 발언은 새 ID |
| `expected_revision` | 선택 입력. 양의 정수, 충돌은 HTTP 409 |
| `document_ids` | 선택 입력. 서버의 허용 팀 문서 범위 안의 명시적 제한 |

팀 메타데이터 필터는 조직 인증·ACL 구현을 대신하지 않는다. 서명은 워크플로우가 결속한 값의 변조를 검사한다. 실제 플랫폼 신원이 신뢰된 값이라는 사실까지 증명하지는 않으므로 현장 확인이 필수다. 서명은 모델 입력·메모리 원장에 저장하지 않는다.

정정 상태는 선택된 runtime 아래 `corrected-memory/memory-v2.sqlite`에 새로 저장한다. 기존 prototype DB 자동 이행은 없다. 여러 리비전/인스턴스가 같은 사용자의 상태를 읽어야 한다면 runtime 경로의 영속성·공유 방식·쓰기 잠금 지원을 현장에서 확인해야 한다. 이번 검사는 로컬 SQLite 기준이다. 분산 동시성 검증을 주장하지 않는다.

응답은 기존 답변 text/claims/출처 표시 계약에 `response_schema=corrected-memory-response-v2`와 상태를 추가한다. 멀티턴의 문단별 생성 스트리밍은 미연결이며 일반 RAG SSE는 유지한다. 사용자 최종 확인은 개인 경험 승인이고 공통 법률 지식 승인은 아니다.

## 현장 멀티턴 확인 순서

품질·설정 확인 후 같은 스튜디오 대화에서 공개 모의 질문으로 시작 → 범위 정정 → 정정을 다시 정정 → 최초 조건 복원 → 표 변환 → 최종 확인 → 새 대화에서 경험 조회 → 잘못 연결한 경험 수정 순서로 확인한다. 각 턴의 요청 ID·goal ID·revision·실행 단계·답변 출처를 기록한다. 다른 사용자나 팀에서 해당 경험이 반환되지 않는지도 확인한다. 실제 내부 CM 품질은 GENOS 내부 모델로 별도 측정한다.

## 복구와 현재 한계

적용 로그에 나온 `~/DEV/09_ARTIFACTS/BACKUPS/code-replacement/<실제 폴더>`를 확인하고 `bash RUN.sh rollback <그 폴더의 절대경로>`로 복구한다. 코드 복구와 Git 복구·기존 서빙 리비전 재선택·워크플로우 편집기 복구는 각각 별도다. 기존 데이터와 새 memory-v2 DB는 삭제하지 않는다. 배포 전 리비전/워크플로우 원본을 보존한다.

작업 코드 검사 292개 중 290개 통과, 2개는 수정 전부터 존재한 ‘영업일’ 형태소 탐색 실패다. 정확한 범위는 `VALIDATION.json`을 따른다. 최신 과거 CM 실험은 Rejected(법률 일치 6/12)이고 새 통합본의 실제 모델 품질·지연은 미측정이다. 활성 MAIN 승격 조건은 충족하지 않았다. 온톨로지 catalogue compile·전체 판단 domain proof·긴 대화 계층 조회·문단 anchor는 구현 완료로 표시하지 않는다.
