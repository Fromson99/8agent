법제처 API 수신 요청 명세 — 2026-10-27

문서 상태: 담당자 확인·시험 요청안. 내부 연결 성공이나 운영 등록 완료를 의미하지 않는다.
첨부 JSON은 요청 내용의 구조화 표현이며 자동 실행·배포용 설정 파일이 아니다.

1. 목적과 역할

대상: 기존 확정 목록 중 법령 37종 + 행정규칙 12종 = 49종.
별표·서식 파일은 각 문서에 연결된 자산이므로 49종과 별도로 개수가 정해진다.
최초 수집 후 Dataiku 매일 배치로 변경을 확인하는 계획이다. 실제 주기·호출 제한은 협의한다.
중계 담당자에게 요청하는 범위: 원천 조회 전달, 응답 반환, 통신·경로·인증 계약 확인.
우리 시스템의 담당 범위: 전체 페이지 순회, 문서·판본 선택, 원문 검증·보관, 구조화, Dataiku 적재 연결.
거래소·금투협 웹 수집 19종과 입법예고·행정예고는 이번 네 요청에 포함하지 않는다.

2. 공통 요청 형식

HTTP 메서드: GET
원천 호스트: http://www.law.go.kr
응답: XML 원문. 일반 DRF 요청의 브라우저 Cookie는 기본 필수값으로 추가하지 않는다.
OC={LAW_OC}: 승인된 실제 OC로 치환. 이 자료에는 실제 인증값이 없다.
한글·공백 등 쿼리 값은 UTF-8 URL 인코딩하고 파라미터 대소문자를 유지한다.

기존 중계 샘플에 맞춘 전달안:
  GET {확인된_중계_BASE}/law/DRF?{아래_중계_GET_쿼리}
  target_url: {아래_헤더값}
  Accept: application/xml

기존 점검의 중계 BASE는 https://45.101.64.86:8443 이다.
GENOS에서 성공한 주소로 확정되지 않았으므로 담당자가 승인 도메인·포트·프로토콜을 회신해야 한다.
target은 target_url에 한 번만 넣고 중계 GET 쿼리에서 중복시키지 않는다.
해당 헤더의 원천 쿼리와 중계 GET 쿼리를 병합하는 계약은 기존 샘플 기준이므로 담당자가 확인한다.
원천 HTTP 안내만으로 중계 BASE를 HTTP로 변경하지 않는다.

3. 최초 수신 확인용 네 요청

[L1] 법령 목록 — 자본시장법
원천 URL: http://www.law.go.kr/DRF/lawSearch.do
원천 파라미터:
  OC={LAW_OC}&target=eflaw&type=XML&search=1&query=자본시장과 금융투자업에 관한 법률&nw=3&display=100&page=1
target_url 헤더:
  http://www.law.go.kr/DRF/lawSearch.do?target=eflaw
중계 GET 쿼리:
  OC={LAW_OC}&type=XML&search=1&query=자본시장과 금융투자업에 관한 법률&nw=3&display=100&page=1
확인: XML 목록의 정확한 법령명·법령ID·법령일련번호·공포일·시행일. 부분 일치하는 시행령·시행규칙과 구분한다.

[L2] 법령 현행 본문 — 자본시장법
원천 URL: http://www.law.go.kr/DRF/lawService.do
원천 파라미터:
  OC={LAW_OC}&target=eflaw&type=XML&ID=010513
target_url 헤더:
  http://www.law.go.kr/DRF/lawService.do?target=eflaw
중계 GET 쿼리:
  OC={LAW_OC}&type=XML&ID=010513
확인: 응답의 법령ID·정확한 법령명·시행일과 실제 조문·부칙. ID=010513은 기존 점검에 사용한 식별자로 L1 응답과 재대조한다.
공식 명세상 ID 모드에서는 efYd를 생략한다. 전체 본문을 받도록 JO도 생략한다.

[R1] 행정규칙 목록 — 금융투자업규정
원천 URL: http://www.law.go.kr/DRF/lawSearch.do
원천 파라미터:
  OC={LAW_OC}&target=admrul&type=XML&search=1&query=금융투자업규정&nw=1&display=100&page=1
target_url 헤더:
  http://www.law.go.kr/DRF/lawSearch.do?target=admrul
중계 GET 쿼리:
  OC={LAW_OC}&type=XML&search=1&query=금융투자업규정&nw=1&display=100&page=1
확인: 정확한 행정규칙명·행정규칙일련번호·행정규칙ID·발령일·시행일. 시행세칙과 구분한다.

[R2] 행정규칙 본문 — 금융투자업규정
원천 URL: http://www.law.go.kr/DRF/lawService.do
원천 파라미터:
  OC={LAW_OC}&target=admrul&type=XML&LM=금융투자업규정
target_url 헤더:
  http://www.law.go.kr/DRF/lawService.do?target=admrul
중계 GET 쿼리:
  OC={LAW_OC}&type=XML&LM=금융투자업규정
확인: 정확한 행정규칙명·일련번호·날짜·실제 본문. LM은 최초 확인용 공식 명칭 조회다.
반복 수집에서는 R1의 정확한 문서 행에서 받은 행정규칙일련번호를 ID로 넣고 LM은 생략한다.

4. 수신 확인 후 정기 수집에 적용할 내용

법령: target=eflaw, query=CSV 정식명, nw=2,3(시행예정·현행), display=100, page=1부터 전체 페이지.
법령 판본 본문: target=eflaw&type=XML&MST={목록의 법령일련번호}&efYd={목록의 시행일 YYYYMMDD}와 OC.
이 판본 지정 모드에서는 ID를 함께 넣지 않는다. 현행과 시행예정을 별도로 보관한다.
행정규칙: target=admrul, query=CSV 정식명, nw=1(현행), display=100, page=1부터 전체 페이지.
행정규칙 판본 본문: target=admrul&type=XML&ID={목록의 행정규칙일련번호}와 OC.
법령의 nw=3과 행정규칙의 nw=1은 각각 현행을 뜻한다. 필터 값을 공통으로 고정하지 않는다.
49종은 문서 수이며 호출 수가 아니다. 페이지·판본·첨부에 따라 요청 수가 증가한다.
기존 R3의 target=law는 과거 연결 점검용이다. 이번 시행일 기준 eflaw의 중계·OC 허용 범위를 확인한다.

5. 별표·서식 파일 추가 연동 요청

본문 XML의 별표서식파일링크·별표서식PDF파일링크·첨부파일링크에 실제로 나온 URL을 사용한다.
대표 경로: www.law.go.kr/LSW/flDownload.do?flSeq={응답에서 받은 값}
실제 링크의 스킴·호스트·경로·쿼리 및 리다이렉트 목적지를 확인하여 허용 범위를 협의한다.
flSeq·파일 확장자·판본 번호를 추측해서 만들지 않는다.
담당자에게 필요한 방화벽/중계 신청 항목과 바이너리 응답 전달 지원을 확인 요청한다.
LSW용 내부 중계 경로는 아직 확인되지 않았으므로 /law/LSW 같은 주소를 임의로 정하지 않는다.
응답은 원본 파일 바이트·파일명·Content-Type과 연결 원문 식별자로 보관한다.
HWP/HWPX/PDF 등 실제 제공 형식만 수집하며 오류 HTML을 파일 수신 성공으로 처리하지 않는다.

6. 우리가 전달할 값과 담당자 회신

우리 측 준비 자료:
  - 업무 목적·호출 시스템·일일 수집 계획: 본 문서.
  - 원천 주소·헤더·쿼리: 본 문서와 JSON.
  - 수집 문서 49종: CSV. 과거 일련번호를 현행으로 재사용하지 않도록 명칭 중심으로 작성.
  - 법제처 OC: 승인된 값의 존재·유효 범위 확인 후 별도 보안 경로로 제공. 본문/로그에 노출하지 않음.
  - GENOS 프로젝트/코드서빙 식별자와 허용 신청용 출발지: 실제 환경에서 확인한 값으로 신청서에 입력.
    사진의 컨테이너 로컬 IP를 NAT/출구 IP로 간주하지 않음.

담당자에게 받을 내용:
  - 네 요청별 호출 시각, HTTP 상태, Content-Type, 응답 XML 파일, 인증값을 뺀 실제 요청 예시.
  - GENOS용 승인 중계 도메인·포트·경로, TLS/SNI·CA·인증·프록시 요구, 허용 출발지.
  - 중계의 실제 외부 출구 IP와 해당 OC의 허용 서비스·IP 등록 확인.
  - GET 쿼리 병합/인코딩 규칙, 호출량·응답 크기·타임아웃 제한, 오류·리다이렉트 전달 방식.
  - LSW 방화벽/개발 요청 항목·담당·지원 경로.

성공 확인:
  HTTP 200만으로 완료하지 않고 오류/로그인 HTML 여부, XML 파싱, 요청 문서의 ID·명칭·본문을 확인한다.
  담당자 환경 성공 후 같은 요청을 GENOS 수집용 코드서빙의 워크플로우 테스트 화면에서 확인한다.
  이후 소량 결과를 Dataiku 관리 폴더에 보관·재조회하고 기존 구조화/적재 흐름에 연결한다.
  기존 Dataiku 관리 폴더 SFTP 쓰기 실패는 별도 미해결 기록이 있으므로 API 성공과 저장 성공을 각각 확인한다.
