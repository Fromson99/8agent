# 첫 요청 분류 (B1)

기준: MAIN181 (`definition-priority-20261109-r1`), 2026-11-09. 코드를 직접 읽어 정리했으며 실행 추적은 하지 않았다.

> 이 설명은 결정된 수정사항 1·2(자료 구분은 GENOS에서 준 값으로, 과거 기록 후보 없음)를 반영한 기준으로 적었다. 현재 MAIN181 코드와 다른 부분은 `수정사항.md`에 있다.

## 한 줄 요약

대화의 **첫 질문** 하나를 모델 호출 1번으로 읽어서, 이 질문을 어디로 보낼지(바로 안내 / 문서 목록 / 법률 조사), 무엇을 조사할지(목적·쟁점·사실), 어디서 어떻게 찾을지(검색 범위·검색 방식·검색어·정의 질문 여부)를 한꺼번에 정한다. 서버는 그 결과를 검사하고 조사 상태로 확정한다.

## 언제 실행되나

- 같은 대화에 진행 중인 질문·이전 대화·재개할 조사가 **없을 때만** 실행된다(`request_entry.eligible`).
- 두 번째 질문부터는 이 단계가 아니라 멀티턴 판단(B2, `corrected_memory.py`)이 맡는다.
- 프로필 조건: `request_entry_policy = "fused-title-v1"` (profile-unified-v6.json).
- 호출 위치: `legal_agent/case_repository.py` → `request_entry.run`.

## 세부 기능

### 1. 모델 호출 전에 서버가 준비하는 것 (모델 호출 0)

| 기능 | 하는 일 | 코드 |
|---|---|---|
| 자료 구분 | GENOS에서 준 값(mode: 전체 법령 / 내규 / 외규)으로 자료 구분(ALL / internal / external)을 정하고, 그 구분의 문서만 범위에 남긴다. 값이 없으면 전체. | `request_entry.run` |
| 법령 제목 단서 | 질문 속 법령 이름과 저장된 문서 제목을 맞춰 본다. 정확한 제목, 등록된 약칭, 일부 일치, 줄임말 추정을 구분해 모델에게 후보로만 준다(본문 검색 0, 범위 부여 0). | `law_title_hints.py` |
| 대사 하위 조사 | 대사 워크플로우가 시킨 내규·외규 하위 조사이면 상위가 정한 과제를 넣는다. 상위가 이미 결정을 만들어 왔으면 **모델을 부르지 않고** 그 결정을 바로 검사한다. | `workflow_execution.py` `task_context`, `entry_proposal` |
| 기능 안내 목록 | "할 수 있는 일/못 하는 일" 목록을 넣어 인사·사용법 질문에 답할 근거로 쓴다. | `source_query_planning.py` `CAPABILITIES` |

### 2. 모델이 한 번에 정하는 것 (`request-entry` 호출 1회)

**① 질문 갈래 (`routing.mode`)**

| 값 | 뜻 | 이후 |
|---|---|---|
| `DIRECT` | 인사·감사·사용법, 의미 없는 입력, 법률과 무관한 일상 대화 | `answer`에 쓴 짧은 안내로 끝. 검색 없음 |
| `BROWSE` | 원하는 결과가 문서 이름 목록·폴더 목록·제목 검색일 때만 | 서버가 목록을 만들어 보여 줌(`catalogue`: 문서/폴더, 전체/내규/외규, 제목 조건) |
| `CASE` | 법률·규정 내용 질문, 문서·조문 조회 | 아래 ②로 |

규칙: 인사와 법률 질문이 섞이면 CASE. "~가 있나요?"라도 내용(요건·비용·예외 등)을 묻으면 CASE. 찾을 문서를 몰라도 CASE.

**② 조사 시작 여부 (`command.method_id`)**

| 값 | 뜻 |
|---|---|
| `CASE_START` | 새 법률 질문 → 조사 시작 |
| `NEED_TARGET` | 이전 판단을 고치거나 다시 쓰라는 요청인데 대상이 없음 → 무엇을 말하는지 되묻기(사실·검색어 변경 금지) |

**③ 조사 내용 (`intent`, CASE_START일 때만)**

- `purpose`: 질문 목적. 실제 요청을 그대로 보존하고 배경 쟁점을 덧붙이지 않는다.
- `issues`: 쟁점 목록 Q1~Q12. 요구가 하나면 Q1 하나. 쟁점마다 종류를 붙인다.
  - `ACTOR`(누가), `TIMING`(시점·기한), `CLASSIFICATION`(해당 여부), `STRUCTURE`(조문 구조), `FORMULA`(계산), `AUTHORITY`(권한), `DEFINITION`(정의), `OTHER`
  - 일반 규칙 질문과 특정 사건 적용 질문을 구분한다. 질문 속 숫자만으로 계산 쟁점을 만들지 않는다.
- `concepts`: 핵심 개념어.

**④ 사건 정보 (`command`)**

- `facts`: 사용자가 말한 사건 조건·가정(최대 16개). 반드시 질문 원문 그대로의 인용(`user_quote`)을 함께 쓴다. 일반 설명 질문이면 비운다.
- `context_quotes`: 배경·업무 문맥 원문(최대 8개).
- `source_category`: 자료 구분. GENOS에서 준 값이 있으면 서버가 그 값으로 정한다(모델 판단보다 우선).
- `format`: 표를 요청하면 table, 아니면 prose.

**⑤ 검색 방법 (`search`, CASE_START일 때만)**

- `scope_decision` — **범위 판단의 유일한 자리**
  - `NAMED_SCOPE`: 사용자가 특정 법령·문서를 지목함. `targets`에 문서명과 조문 범위를 넣는다.
    - 조문 번호는 `selection`으로: 단일(제2조), 여러 개, 범위, 제외, 본문/부칙 구분.
    - 번호 없는 목차 제목은 `structure`로.
    - 약칭·대명사는 문서명으로 풀어 쓰되, 원래 질문 문구는 `user_quote`에 그대로 둔다.
    - 저장소에 없을 것 같은 법령이라도 사용자가 지목했으면 NAMED_SCOPE를 유지한다(없으면 뒤에서 "미확인" 처리).
  - `AUTHORIZED_SCOPE`: 지목한 문서가 없음 → 허용된 전체 자료에서 찾기.
- `mode`: `STRUCTURE`(번호·목차·제목 위치를 물음) / `FULLTEXT`(문서는 알아도 내용을 찾음).
- `queries`: 본문 검색어. 쟁점별로 가장 짧고 구별력 있는 표현 1개씩, 최대 4개. 법령명·질문 전체·"요건/기준/절차" 같은 넓은 말은 넣지 않는다(검색어는 OR로 합쳐지므로 넓은 말이 결과를 흐린다).
- `asks_definition` (MAIN181 추가): 질문이 용어의 뜻·정의·범위 **자체**를 묻는지.
  - true 예: "~란 무엇인가", "~는 어느 기관인가", "~에 해당하는 자의 범위는"
  - false 예: 요건·기준·절차·기한·수량·결정 주체·허용 여부·계산 방법을 묻는 질문

#### 사건 사실(`facts`)이란

법령 내용이 아니라 **사용자가 질문에 직접 적은 자기 상황의 조건 값**이다. 법령은 원문에서 찾고, 사건 사실은 사용자 말에서 가져온다.

| 질문 | facts |
|---|---|
| "사외이사 선임 요건은?" | 없음(일반 설명 질문) |
| "자산총액 3천억원인 상장회사는 사외이사를 몇 명 둬야 하나?" | `{자산총액: 3천억원}`, `{상장 여부: 상장회사}` |
| "임원이 아닌 직원이 500만원을 받았다면 보고 대상인가?" | `{지위: 임원 아님}`, `{금액: 500만원}` |

- 항목마다 이름(`name`), 값(`value`), 질문 원문 그대로의 인용(`user_quote`)을 쓴다. 서버는 인용이 실제 질문 안에 있는지 확인한다.
- "제3호에는 해당하지 않는다고 치고" 같은 가정도 사실로 적는다. 이것을 "제3호는 읽지 마라"로 바꾸지 않는다.
- 쓰이는 곳
  - 사건 상태로 저장되어 답변 단계에 "사용자 조건"으로 들어간다(`guided_answer.py`의 `user_facts`, 일반 모드 판단의 `current_facts`).
  - 답변에서 사용자 조건과 법령 근거를 구분한다. 사실을 법령 근거로 인용하지는 못한다(`memory_rag.py`).
  - 가정 질문 계산에서 규정의 기준값(예: 금액 한도)과 비교한다(`scenario_facts.py`).
  - 다음 턴에 "그럼 3년이면?"처럼 조건만 바꾸면 목적은 유지하고 사실만 바꿔 다시 판단한다(멀티턴 `FACT_UPDATE`).

### 3. 서버 검사 (모델 응답을 받은 뒤)

| 검사 | 걸리면 |
|---|---|
| 갈래별 필드 조합: DIRECT/BROWSE는 command·intent·search가 없어야 하고, CASE_START는 intent·search가 있어야 하고, NEED_TARGET은 사실·검색어를 바꾸면 안 된다 | `ENTRY_*_CONFLICT` |
| NAMED_SCOPE면 대상이 있어야 하고, AUTHORIZED_SCOPE면 대상·인용이 비어 있어야 하며, 범위 이유가 필요 | 거절 |
| 사실·배경 인용이 현재 질문 원문 안에 실제로 있는지 | 거절 |
| 쟁점 번호 중복, 모르는 제목 단서 번호 | 거절 |
| 조문 범위를 실제 원문 구조로 풀 수 있는지(상위 경로·끝 번호·단위 누락 등) | `ENTRY_STRUCTURE_*` → 경로를 다시 정하라고 보완 요청(가이드 모드는 아래 실패 처리) |
| 판단 이유와 실제 결정의 일치 검토 | 가이드 모드에서는 생략 |

**보완과 실패 처리**

- 가이드 모드가 아니면: 같은 입력으로 **보완 1회**. 그래도 틀리면 오류로 끝난다(재시도 예산은 조사 기록에 남아 재실행해도 초기화되지 않음).
- 가이드 모드(현재 현장 설정 `guided_loop: true`)이면: **보완 호출 없이** 바로 `NEED_TARGET`으로 바꿔 "요청을 조사 대상으로 정리하지 못했다, 아직 원문 조사를 시작하지 않았다"는 되묻기 안내를 한다(`REQUEST_ENTRY_GUIDANCE_REQUIRED` 기록).
- 권한·상태 오류는 모델 보완 대상이 아니다.

### 4. 결과가 어디에 쓰이나

| 결과 | 쓰는 곳 |
|---|---|
| 확정 기록 `REQUEST_ENTRY_ACCEPTED` (요청·권한·바인딩 해시로 묶임) | 조사 기록 |
| `intent`(목적·쟁점) | 다음 단계가 의도 정리 모델 호출 없이 그대로 사용(`completion_execution.py`, `REQUEST_ENTRY_INTENT_CONSUMED`) |
| `search.mode`, `queries` | 첫 검색: 키워드 검색(C1) 또는 벡터 검색(C2) |
| `scope_decision` | 검색 범위(B4, `query_scope.py`), 조문 번호 직접 진입(C6) |
| `asks_definition` | false면 정의 조문 미리 읽기 보류(`definition_entry.py`, `DEFINITION_ENTRY_DEFERRED`), 메뉴의 정의 항목은 "배경"으로 표시(`law_navigation.py`) |
| `facts` | 사건 사실로 저장, 이후 판단·가정 계산에 사용 |
| `format` | 답변 형식(문단/표) |

## 수정할 때 주의

- 지침 문장(`SYSTEM`, `ENTRY_SCOPE_PROMPT`, `INTENT_PROMPT`)을 바꾸면 모델 판단이 바뀌므로 실모델 실험(ADR)으로 확인한다.
- 스키마에 **필수 필드**를 추가하면, 점검 도구·시험의 가짜 첫 요청 응답에도 넣어야 한다. 단, 요청 스키마에 그 필드가 있을 때만 넣는다(MAIN181의 `asks_definition` 때 항상 넣었다가 이전 MAIN 점검이 깨진 적 있음). 공유 파일: `06_TOOLS/maintenance/oracle_scale_guard/guard_transport.py`.
- 저장된 이전 기록에는 `asks_definition`이 없다. 저장 스키마(`schema(model=False)`)에서는 필수로 만들지 않는다.
- 파일을 바꾸면 `02_BACKEND/ENGINES/` 해시 고정값을 다시 만들고 `main_release.py`로 반영한다.
