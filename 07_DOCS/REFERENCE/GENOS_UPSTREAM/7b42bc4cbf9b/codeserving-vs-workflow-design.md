# 코드서빙 vs 워크플로우 — 설계 의도 (양성호 프로, 2026-09-11)

출처: 양성호 프로 회신(POP 메신저, 2026-09-11 10:04). 조동국 문의(역할·책임 경계 / 워크플로우
코드가 코드서빙보다 적은 게 정상인지)에 대한 답변. 원문: `genos-역할분담-질문답변.txt`.

## 원래 설계 의도 (삼성증권 도입 시점)
- **워크플로우**(Flowise 등 노코드 도구 포함)가 **주력 AI 로직** 담당.
- **코드서빙**은 **MCP 이외 보조적 API 제공** 목적.

## 현 시점 — 역할이 뒤집힘 (코드서빙이 주력)
아래 이유로 코드서빙이 주력, 워크플로우는 **채팅 앱 요청·토큰 스트리밍 중계 정도**로 축소:
- 삼성증권에서 **Flowise를 거의 사용하지 않음**
- 워크플로우=단일 스크립트 vs **코드서빙=모듈화 구조로 설계·개발 가능**(개발 편의성)
- **Git 기반 CI/CD 이관·자동화** 등 형상 관리 용이
- **LangChain 등 외부 라이브러리**로 기개발된 에이전트 이식 용이
- 로직 확장성·활용성
- (코드서빙 **컨테이너 서비스** 기능 도입도 영향)

## 워크플로우 코드가 적은 게 정상인가 → **정상**
- 최근 신규 기능(**멀티 엔드포인트** 등)도 코드서빙 위주로 개발·개선.
- 워크플로우보다 코드서빙에 힘을 주는 경우가 많아, **워크플로우 코드가 상대적으로 적은 것도 정상**.

## 우리 프로젝트 시사점
- 과제6·8이 무거운 로직을 코드서빙에, 워크플로우는 얇은 브릿지/스트리밍만 둔 구조가
  **플랫폼 현행 설계 방향과 일치**.
- **모듈화 기획안**(코드서빙 표준화·모듈화)이 이 방향과 정합 — "코드서빙=모듈화 구조 설계 가능"이
  벤더/플랫폼 관점에서도 확인됨.
