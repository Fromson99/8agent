# 현재 RAG에 작업 명세·제약 기반 하네스 연결 검토

검토일: 2026-09-16. 코드·계약 읽기 기반 설계 제안이며 기능 구현·품질 실험·릴리스 변경은 수행하지 않았다. 작성자의 자체 검토이며 독립 감독 검토는 아니다.

## 판단

현재 원문·용어 저장소와 탐색 도구를 재사용하면서, retrieve 내부의 탐색 제어를 작업 명세와 완료조건 중심으로 교체하는 방식으로 연결할 수 있다. 단순 설정 추가로 끝나지는 않는다. 의미 해석, 작업별 확인 의무, 진척 관리, 중단·재개 계약이 필요하다. 일반 업무 DB 변경이나 외부 작업 실행은 현재 읽기 중심 RAG에 없는 별도 확장 범위다.

현재 온톨로지 자원은 원천 용어·정의·관계와 근거를 공급한다. 검토되지 않은 관계나 LLM 해석을 실행 제약으로 자동 승격하지 않는다. 첫 구현은 문서 범위, 근거 출처, 원문 전달 여부, 미확인 항목 등 명시적으로 검사 가능한 제약부터 적용한다.

## 확인한 현재 연결

- `service.py`: 환경의 명시적 세대 또는 게시 세대를 선택하며, 로컬 기본 경로는 활성 릴리스 manifest의 코드 묶음을 별도 패키지로 읽는다.
- 로컬 활성 포인터: `navigation-rag-20260916-v1`, generation 14. 작업 디렉터리 수정이 곧 활성 코드 변경은 아니다. 선택 릴리스의 navigation_agent와 navigation_loop도 확인했다.
- `app.py:ask` → `Pipeline.run` → PIPELINE의 retrieve/select/assemble/answer. `Pipeline.plan`은 질문·문서 범위·세대만 만들며 의도나 작업 명세를 생성하지 않는다.
- `ServingNavigationAgent.retrieve` → `NavigationSession`: 용어·정의·관계·구조·원문·참조 조회, 판단, 종료가 한 세션에 모인다.
- `stages.select`는 탐색기가 선택한 ID를 전달한다. 별도의 의미 검증기라고 볼 수 없다. `term_agent.answer`도 탐색 결과의 findings를 답변으로 조립한다.
- `NavigationSession.judge`는 인용 문자열이 전달된 원문 안에 있는지와 claim 존재 여부를 검사한다. 인용의 의미가 결론을 함의하는지는 별도 보장이 없다.
- 문서 범위 필터가 있지만 그것만으로 사용자별 권한 검증이 구현됐다고 볼 수 없다. 향후 권한은 신뢰할 수 있는 호출자 정보로부터 주입해야 한다.

## 변경 지도 — 모두 제안

| 지점 | 변경 책임 | 기존 소비자·호환성 |
|---|---|---|
| `pipeline.py` / `navigation_agent.py` | 명시적으로 선택한 새 탐색 구현을 생성 | 기존 legal-rag 실행기를 사용, 별도 중복 파이프라인을 만들지 않음 |
| retrieve 내부 | 질문 → 해석 후보 → TaskSpec 작성·검증 | 외부 Query에 임의 필드를 붙이지 않고 내부 버전 계약으로 관리 |
| `navigation_loop.py`의 제어 부분 | TaskState, 의무별 근거 상태, 허용 행동, 진척·종료 검사 | 기존 조회 함수를 도구 어댑터로 분리하여 재사용 |
| 작업 정의 저장소 | 작업 유형·확인 의무·도구 계약·전이·실패 처리·버전 저장 | 검토된 DB 정의를 해시 고정 묶음으로 게시하고 요청 시작 시 결속 |
| `stages.py` / `term_agent.py` | 검증된 findings·selected_ids·미해결 사유로 변환 | 기존 selection/assembly/answer 형태를 유지하는 명시적 어댑터 필요 |
| `app.py` / 실행 기록 | 작업 명세 버전, 제약 판정, 도구 실행·상태 전이를 저장 | 기존 run_id와 근거 세대에 연결; 영속 재개는 추가 구현 필요 |
| `feedback.py` / `learning_store.py` | 미정의 표현·충돌·실패를 검토 후보로 축적 | 기존 PROPOSED 원칙 유지; 과거 답변을 정답이나 승인 정의로 자동 사용하지 않음 |

DB 정의를 바꿔도 이미 진행 중인 실행에는 고정 버전을 사용한다. DB에는 지원되는 연산과 도구 ID를 저장하며 임의 Python·SQL 실행 문자열을 저장하는 방식으로 확장하지 않는다. 새 제약 연산 또는 새 시스템 연결은 실행기·어댑터 코드가 필요하다.

## 최소 내부 계약

아래 이름은 제안이며 현행 API가 아니다.

- `TaskSpec`: 작업 유형, 사용자 원문 span과 연결한 개념 후보, 적용 문서·버전, 확인 의무, 사용자 사실의 미확인 항목, 정의 묶음 버전, 실행 예산.
- `TaskState`: 각 의무의 미확인/근거후보/검토완료/충돌 상태, 전달된 원문 구간, 근거 판단, 시도 이력, 남은 예산, 다음 행동 제안.
- `ConstraintResult`: 제약 ID·버전, 검사 입력, PASS/FAIL/UNKNOWN, 판정 근거, 허용되는 후속 행동. 검사 가능한 형식 조건과 모델의 의미 판단을 구분한다.

모델은 개념 해석·근거 평가·다음 행동을 제안한다. 실행기는 ID·원문·범위·계약·허용 상태 전이·예산을 검사한다. 고정 의무의 ID와 문장은 실행기가 소유하고, 모델은 ID를 참조한다. 의무 수정은 별도 제안과 검증된 명세 개정으로 처리한다.

정의/요건/예외는 질문 유형에 맞는 확인 의무다. 모든 질문에 무조건 부과하지 않는다. 또한 참조 목록을 전부 조회했다는 사실은 필요한 예외를 모두 확인했다는 뜻이 아니다. 어떤 참조가 결론에 필요한지 판단한 근거와 미해결 상태를 남긴다.

## 대표 시나리오

입력: “여럿 돈을 모아 굴리는 방식이면 전부 같은 제도인가요?”

1. 사용자 문장을 그대로 보존하고 집합투자 등 가능한 개념을 후보로 기록한다. 기존 사전 매칭 부분을 삭제한 잔여 문자열만 새 개념으로 삼지 않는다.
2. 작업 유형을 개념·적용 범위 설명으로 제안하고, 정의/요건/제외·예외의 확인 의무를 만든다. 해석 후보가 경합하면 비교 조회 또는 사용자 확인으로 분기한다.
3. 기존 OPEN_TERM/LIST/READ/REFERENCES를 사용한다. 정의 출처와 원문 좌표를 활용해 읽을 구간을 선택한다. 첫 목록 항목을 자동 정답으로 간주하지 않는다.
4. 원문을 읽은 뒤 의무별 근거를 평가한다. 새 근거 없는 동일 호출 반복은 진척 없음으로 기록하고, 대안 조회 또는 한도 내 복구를 선택한다.
5. 충분한 근거와 검토된 결론이 있으면 답변한다. 사용자 정보 부족이면 확인 질문을 반환한다. 근거 부족·충돌·기술 실패는 서로 다른 사유로 표시한다.
6. 모든 결과를 run_id와 원문·정의 버전에 결속한다. 사용자의 후속 답변으로 같은 작업을 재개하려면 별도 request/resume 계약이 필요하다. 현재 질문 API가 이를 이미 지원한다고 설명하지 않는다.

## 실패 경계

| 상황 | 대응·남은 한계 |
|---|---|
| 모델이 의무를 바꾸거나 잘못된 ID 사용 | 실행 제안 거절, 구조화된 오류로 제한된 재시도. 전체 실행을 즉시 잃지 않되 반복 한도 유지 |
| 동일 목록 반복 | 결과 지문과 의무 상태로 진척 측정. 새 페이지·새 근거가 있는 정당한 재조회와 구분 |
| 잘못된 개념 연결 | 후보 상태 유지, 원문·다른 후보 대조. 추가 문맥 없이는 의미 판정이 여전히 틀릴 수 있음 |
| 모델·조회 장애 | 단계별 오류 기록, 조회에 한정한 제한 재시도. 중간 상태 저장 이후 재개 기능을 구현해야 프로세스 장애 복구 가능 |
| 문서·정의 버전 변경 | 실행 도중 자동 교체 금지. 새 버전으로 재평가할 경우 새 실행 계보 생성 |
| 권한 변경 | 호출 시점에 권한 재검사. 유효 권한을 확인할 수 없으면 실행 중단; 기존 문서 필터로 대체하지 않음 |
| 일부 근거만 확보 | 확보된 근거 보존, 완료 주장 금지, 미해결 의무와 확인 질문 표시 |

## 계약·데이터 이행

첫 후보는 기존 Query/Result 외형을 유지하고 내부 TaskSpec/TaskState를 독립 스키마로 검사한 뒤 기존 탐색 출력으로 변환하는 방안을 권한다. term_agent 객체가 유연하더라도 내부 계약을 생략하지 않는다. 외부 구조화 상태·재개 API를 노출하는 단계에서는 runtime 계약 버전과 UI·평가기·피드백 소비자를 함께 이행한다.

작업 상태와 실행 정책만 바꾸고 기존 조회의 의미를 유지하는 초기 후보는 원문 재수집·구조화 재실행을 요구하지 않는다. 실제 적용 전 manifest 의존성을 검사한다. 새 개념 대응이나 정의 출처 색인이 필요하면 영향받는 용어 색인·세대를 새로 만들고 기존 완료 세대는 보존한다.

현재 제거된 Rule/SemanticClause/조건식 기반 법률 의미 재작성 스키마를 복원하는 제안은 아니다. 사용자 요청을 처리하는 작업 명세는 원문을 대체하는 법적 정본 규칙과 책임이 다르다.

설정 선택은 새 implementation ID, 정의 묶음 경로·해시, 제약 집합 버전, 재시도·총 예산을 PIPELINE의 기존 retrieve 설정으로 연결하는 방식이 적합하다. 경로는 workspace 논리 root로 해결한다. 검증 전 후보가 운영 기본 경로에서 선택되지 않게 한다.

## 기대치와 검증

| ID | 구분 | 판단·근거 |
|---|---|---|
| O1 | 관측 | ADR0433: 작성 질문 6개×3arm에서 답변 성공 각 0/6. 현재 작업 코드·공개 단일 문서 범위·Gemini 단회 비교이며 운영 전체 품질로 일반화 불가 |
| O2 | 관측 | 같은 실험에서 reuse 양성 5개 중 4개는 고정 issue 문장 변경으로 첫 호출 후 종료. 코드 상태 소유권과 오류 복구를 바꿀 근거 |
| T1 | 설계 목표 | 잘못된 행동 제안이 실행 상태를 훼손하지 않고, 복구 또는 구체적인 미완료 종료로 이어지게 함 |
| U1 | 미확인 | 답변 정확도·호출·토큰·지연 개선율과 구현 일정. 아직 새 하네스 구현·측정 없음 |

새 의미 해석·검증 호출은 비용을 늘릴 수 있다. 총비용 비교에는 해석+탐색+검증+재시도를 모두 포함하고 성공 요청과 조기 실패를 분리한다. 총 추가비용보다 중복 탐색·오류 복구의 절감이 커야 비용상 이점이 생긴다. 현재는 절감률과 금액을 산정하지 않는다.

검증은 상태 전이·예산·범위·버전 계약 검사와 실제 질문 품질 평가를 나눈다. ADR0433은 개발용 실패 사례로 보존하고, 새 비교에는 분리된 질문·모호한 표현·근거 없는 질문·예외·버전 충돌·장애 사례를 포함한다. 성공 기준과 허용 회귀를 결과 전에 고정한다. 필수 원문 전달, 근거 의미 적합성, 답변 완성, 추가 질문 적절성, 반복 호출, 정상 완료 비용을 비교한다.

도입 순서는 읽기 중심 작업 유형 하나의 후보 구현 → 격리된 기준 비교 → 별도 질문 검증 → 승인된 릴리스/정의 묶음 게시다. 새 릴리스와 이전 릴리스·정의 묶음을 함께 보존해 롤백한다. GENOS 현장 배포·내부 모델 성능은 이 검토에서 확인하지 않았다.
