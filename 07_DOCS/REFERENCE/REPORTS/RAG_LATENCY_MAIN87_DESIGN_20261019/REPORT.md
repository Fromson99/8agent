# MAIN87 RAG 지연 원인과 개선 설계

2026-10-19 · 설계안 · 구현/추가 모델 호출/MAIN 변경/GENOS 배포 없음

## 1. 결론과 우선순위

현재 확인된 문제는 **조문마다 반드시 별도 LLM을 호출하는 구조가 아니라, 후보를 고르는 데 필요한 정보가 줄어든 상태에서 잘못된 위치를 반복 조사하는 것**이다. 실제 MAIN87 읽기 선택은 최대 네 범위를 한 번에 고른다. 이번 질문에서도 세 항을 한 번에 선택했다.

지연은 두 가지로 나누어 개선해야 한다.

1. **조사 호출 증가:** 후보 제목 누락, 모델이 추정한 조문번호로 시작한 조사, 같은 위치의 반복 조회를 먼저 고친다. 기존 묶음 읽기와 원문 판단을 유지하면서 올바른 근거에 빨리 도달하게 한다.
2. **모델 밖 처리 시간:** 검색·원문 로딩·상태 저장·입력 조립·계측 비용을 분리한다. 이번 저메모리 실행에는 매 생성 후 강제 GC가 포함돼 있으므로, 남은 시간을 제품 DB 지연으로 계산하면 안 된다.

일반적인 짧은 규정 질문에서 **5~7회 호출로 정상 답변에 도달하는 흐름**을 설계 목표로 둔다. 아직 검증한 성능이 아니며, 복잡한 질문까지 이 횟수에서 강제 종료하지 않는다. 초 단위 개선 폭은 계측 조건을 맞추기 전까지 산정하지 않는다.

첫 구현 범위는 후보 정보 보존·기존 묶음 읽기 연결·중복 조회 복구·가벼운 시간 계측이다. ASSESS/COMPOSE 통합, 참조 조사 자동 실행, 전체 인덱스 교체는 첫 범위에 넣지 않는다. 의미 판단과 검증된 답변을 유지하면서 원인이 확인된 부분부터 고친다.

## 2. 확인한 실행과 비교의 한계

|---|---|---|---|
| 기준 | ADR0717, MAIN50 기반 측정 후보 | ADR0900, 실제 선택 MAIN87 서비스 | 현장 코드/프로필 미확인 |
| 질문 | `정관 변경의 결의요건은?` + `주주총회와 이사회의 권한 배분` 문맥 | `정관을 변경할때 주주총회 결의 요건은 무엇인가요?` | 사용자 설명의 같은 질문 |
| 환경 | 로컬 외부 Qwen3.8 / Parasail FP8 / reasoning none | 로컬 외부 Qwen3.8 / Parasail FP8 / reasoning none | 내부 모델·현장 설정 미확인 |

| 데이터 | `native-cm-serving-20261008-r2-index/serving/baseline/generation` | `latest-selection-20261015-r1/generation` | 미확인 |

질문 문맥·데이터·코드·출력 방식·실행 시점·계측기가 다르다. **위 표는 통제된 성능 비교가 아니다. MAIN50→87 때문에 몇 % 느려졌다는 인과 추정에 사용할 수 없다.** 과거 기록은 사용자가 말한 정확한 현장 기준 버전이라고 확인된 것도 아니다.

오히려 이번 기록에서는 모델 전송 합이 과거보다 작다. 호출 증가와 전체 지연을 같은 원인 하나로 설명할 수 없다. 이번 실행의 `live.py`는 매 생성 후 `gc.collect()`와 `malloc_trim(0)`을 호출한다. 그 소요시간을 따로 재지 않았으므로 C2에서 강제 GC, 데이터 조회, 상태 저장 각각의 몫은 미확인이다.

자원 보호 중단은 없었고, 작업 프로세스 최대 RSS는 약 3.21GiB, 시스템 최소 가용 RAM은 약 10.36GiB였다 [M5]. **이번 실행은 RAM 부족으로 실패하지 않았다.** 이것이 과거 앱 종료나 GENOS 서버의 메모리 상태를 설명하지는 않는다.

## 3. 무엇이 달라졌고 어디서 시간을 쓰는가

### 3.1 후보의 제목을 잃는 입력 변환 — 코드로 확인

과거 MAIN50 호출 2의 후보에는 다음 정보가 함께 있었다.

```text
제433조 정관변경의 방법
미리보기: ①정관의 변경은 주주총회의 결의에 의하여야 한다.
read_action: 실제 실행 가능한 읽기 대상
```

이번 MAIN87 호출 2에는 이미 제433조·제434조 후보가 있었지만, 전달 형태는 다음처럼 번호 중심이었다.

```text
document: external > financial_team > law > 상법
coordinate: 제433조
target: 실제 실행 가능한 읽기 대상
```

`structure_query.catalogue()`는 구조 후보에 `title`을 넣는다. 그러나 `decision_projection.choose_read().walk()`는 `article/heading/preview/coordinate`만 복사하고 **`title`과 `surface`를 복사하지 않는다.** 구조 조회에서 들어온 후보의 제목이 모델 선택 입력에서 빠지는 경로가 있다. 이 네 관련 작업 파일은 선택 MAIN87 파일과 바이트가 같음을 다시 확인했다.

또한 동일 target의 마지막 행만 남기는 사전 변환은 앞선 행의 풍부한 정보를 뒤의 간단한 행으로 대체할 수 있다. 이 덮어쓰기 가능성은 코드에서 확인했지만, 이번 기록에서 별도 발생했다고 단정하지 않는다.

**해석:** 후보를 찾지 못한 문제가 전부는 아니다. 찾은 후보를 모델이 구분하기 어렵게 전달한 것이 유력한 기여 요인이다. 제목 복구만으로 선택 정확도가 회복되는지는 후속 검증이 필요하다.

### 3.2 처음부터 잘못된 번호에 끌린 탐색 — 실제 입력/출력으로 확인

과거 실행은 번호 없는 업무 문구로 FULLTEXT 검색을 선택했고, 처음 읽기에 제433조를 포함했다. 이번 최초 요청 모델은 STRUCTURE 검색과 다음 검색어를 만들었다.

```text
상법 정관 변경 주주총회 결의 요건
상법 제368조 정관 변경 결의
```

사용자 질문에 없던 제368조는 모델의 추정이다. 그 뒤 모델은 제368조 구조를 열고 세 항을 읽은 후 제368조의2로 이동했다. 제433조·제434조 후보가 있음에도 방향을 바꾸지 않았다.

STRUCTURE 자체가 항상 느리거나 FULLTEXT가 항상 낫다는 증거는 아니다. 문제는 **추정 번호와 실제 제목·원문 단서를 구분하지 못한 채 탐색을 이어간 조합**이다. 후속 설계는 검색 방법을 일괄 고정하기보다 단서의 출처와 후보 제목을 보존한다.

### 3.3 같은 조사로 돌아오는 데도 LLM을 사용 — 실제 호출로 확인

| 단계 | 이번 물리 호출 | 실제 행동 |
|---|---:|---|
| 요청 정리 | 1 | 검색어·쟁점·검색 방식 결정 |
| 원문 탐색 | 9 | 구조 열기 → 세 항 묶음 읽기 → 구조 재열기 → 위치 검색 반복 → 다른 조문 읽기 → 위치 검색 반복 |
| 탐색 수정 | 1 | `unchanged structure lookup` 오류를 받고도 같은 LOCATE 재선택 |
| ASSESS | 1 | 확보한 두 조문의 원문을 받고 주장 없음 반환 |
| COMPOSE | 0 | 근거 판단 실패로 진입하지 않음 |

`law_navigation.validate()`는 동일 조회를 거절한다. 따라서 중복 도구 실행이 전부 허용된 것은 아니다. 다만 **모델이 중복 행동을 생성한 뒤 거절하며, 같은 선택 공간으로 한 번 더 수정 호출**하는 비용은 이미 발생한다. 현재 `choose_read()`는 `output_contract.bounded_decision()`에 중복 행동별 수정 제한을 넘기지 않는다.

마지막 수정 호출 이후에도 읽은 원문은 ASSESS에 전달됐다. 하지만 필요한 근거를 못 고른 상태여서 최종 답변을 만들지 못했다. 검증기를 제거해서 해결할 상황이 아니다.

### 3.4 묶음 읽기는 이미 있다 — 이번 실행에서 확인

- 실제 read-choice 계약: `READ.selections` 최대 4개. 호출 3에서 제368조제1항·제2항·제3항을 한 번에 선택했다 [M6].
- 읽기 실행은 기존 `READ_ARTICLES`가 선택 대상을 순차 처리한다. 대상마다 LLM을 호출하는 루프가 아니다.
- 다음 모델 입력에는 세 범위 원문을 함께 전달했다. 세 카드가 서로 다른 세 조문을 의미하지는 않는다.
- 일반 canonical `READ_ARTICLES` 기본 최대 8과 실제 read-choice 최대 4는 다르다. 참조 판단의 `groups_per_batch=16`도 별도 계약이며 이번에는 그 분기를 실행하지 않았다.

따라서 첫 처방은 묶음 크기를 무작정 늘리는 것이 아니다. **필요한 서로 다른 근거를 한 묶음으로 고를 수 있게 후보 정보를 복구하는 것**이다.

### 3.5 정상 답변 경로의 추가 생성과 미확인 시간

현재 `answer_presentation=grounded-narrative-v1` 경로는 검증된 ASSESS 다음에 별도 COMPOSE 생성을 한다. 과거 7회 실행에는 그 호출이 없었다. 현재 정상 답변의 호출 증가 요인 중 하나지만, 이번 실패 실행의 12회에는 포함되지 않았다. GENOS의 19회 중 몇 회가 여기에 해당하는지는 현장 기록이 없다.

한편 `query_latency.py`의 상세 SQL/압력 계측은 과거 롤백으로 비활성 상태다. 옛 환경변수를 켜도 상세 분해는 생기지 않는다. 재개·상태 원장·입력 복사 등의 비용이 클 가능성은 있으나 현재 기록만으로 어느 부분이 병목인지 확정할 수 없다.

## 4. 문제별 수정 방식과 원하는 결과

| 문제 | 기존 방식과 실제 결과 | 제안 변경 | 원하는 결과·통과 조건 |
|---|---|---|---|
| 후보 제목 누락 | 구조 후보 `title`이 최종 read_candidates에서 빠짐. 필요한 후보가 있어도 다른 번호 선택 | `choose_read`에 공통 후보 조립 함수 추가. `title/surface/heading/article`의 실제 값을 보존하고 짧은 기존 적중문을 연결. 같은 target은 정보 병합 | 제목 있는 저장 후보는 모델 입력에도 제목이 있음. 중복 경로 순서가 달라도 제목 소실 없음. 번호·본문·출처를 생성하지 않음 |
| 추정 번호에 고착 | 사용자에게 없는 제368조를 최초 검색어에 넣고 STRUCTURE 탐색 지속 | 요청 단서를 사용자 명시/실제 저장 후보/모델 가설로 구분해 기존 조사 상태에 기록. 번호 없는 주체·행위 검색어 보존. 모델 가설만으로 다른 기존 후보를 제거하지 않음 | 임의 번호가 유일한 검색 범위를 결정하지 않음. 사용자 명시 번호·정확한 참조는 그대로 사용. 제목 선택 개선과 분리 평가 |
| 같은 조회의 반복 수정 | 중복 조회 생성 후 거절, 한 번 더 호출해 같은 선택 | 기존 반복 키에 근거 범위·generation·scope를 결속. 이미 실행한 고정 대상 메뉴는 재노출 방지. 동적 LOCATE는 실행 이력과 가능한 대안을 보여주되, 재발한 중복은 별도 동일 수정 호출로 보내지 않음 | 같은 바인딩/조회/읽기 범위에 새 정보가 없으면 도구 재실행 없음. 동일 충돌을 schema repair와 no-progress recovery가 각각 다시 소비하지 않음 |
| 묶음이 엉뚱한 범위에 쓰임 | 묶음은 동작하지만 같은 조문의 세 항을 읽고 필요한 다른 조문을 놓침 | 기존 최대 4개 READ 유지. 제목·적중 위치·전체/부분 읽기 범위·읽음 상태를 함께 표시하고 한 번에 고르게 함 | 필요한 여러 후보가 한 선택으로 기존 reader에 전달. 원문 확인 전 자동 채택 없음. 항·호 한정을 다른 범위로 확대하지 않음 |
| 모델 밖 시간이 불명 | 77.683초에 제품 작업과 관측기 GC가 섞임 | 기존 execution_metrics에 단계별 배타 시간/총 시간 집계를 소량 추가. 관측기의 GC·압축·파일 쓰기는 별도 필드. 기존 SQL 상세 로그를 되살리지 않음 | 모델/도구/입력 조립/상태 I/O/관측기/기타의 합계가 요청 벽시계와 설명 가능. 실제 단계가 아닌 잔차는 OTHER로 남김 |
| 정상 응답의 추가 생성 | ASSESS 뒤 COMPOSE에서 표현을 생성 | 우선 유지하고 독립 계측. 첫 개선 후에도 COMPOSE가 큰 비중이면 별도 후보에서 검증된 구조 답변 표시와 비교 | 답변 누락·인용·조건·예외 보존. 호출 한 번을 줄이려고 의미 검증이나 저장 일치를 생략하지 않음 |

후보 표현 변경은 모든 내규/외규 자식 RAG에 영향을 줄 수 있다. 같은 번호의 다른 법령, 별표, 제목 없는 항·호, 부분 준용, 다른 버전, 제목과 본문 내용이 어긋나는 사례를 반드시 포함한다. 제목은 위치 단서일 뿐 답변 근거가 아니다.

## 5. 기존 실행 경로 안에서의 구현 설계

담당 단계는 MAIN의 **용어 기반 RAG 중 요청 해석·원문 조사·답변**이다. 용어집 구축, 문서 수집/파싱, 원문 적재 계약은 이번 1차 변경 대상이 아니다.

```text
service.application / RAG_ASK
  → request_entry: 질문·쟁점·출처 있는 검색 단서
  → 기존 검색/구조 조회: 제목·적중 위치·실행 가능한 후보
  → choose_read: 필요한 원문 최대 4개 선택
  → READ_ARTICLES: 같은 요청의 reader로 순차 획득·검증
  → 원문 묶음 전달 → 필요하면 새 범위 조사, 충분하면 FINISH
  → ASSESS: 원문에 따른 주장·적용성·예외·미확인 판단
  → COMPOSE → 검증/저장/공개 응답 → GENOS 워크플로우 표시
```

새 별도 RAG 실행기나 병렬 reader를 만들지 않는다. 현재 선택 경로에 다음 변경을 연결한다.

| 기존 파일·함수 | 책임과 변경 | 소비자·계약·설정 |
|---|---|---|
| `request_entry.py: run/accept` | 출처 있는 단서와 추정 단서의 구분. 판단 결과와 기존 queries는 감사 원장에 보존 | 기존 요청 상태/SELECT 소비. 신규 선택 필드는 버전 부여, 이전 상태는 UNKNOWN으로 읽음. 근거 없는 번호를 실제 사용자 사실로 승격 금지 |
| `structure_query.py: catalogue/document_structure` | 이미 있는 title/coordinate/source binding을 제공 | 1차에는 색인 변경 없이 기존 메타데이터 사용. 제목 없는 노드는 상위 실제 제목과 자체 좌표를 구분해 표시 |
| `decision_projection.py: choose_read` | 후보 조립·중복 병합·읽기 범위 표시. 기존 READ 스키마와 호출 경로 재사용 | 새 후보 표현 버전을 판단 key와 저널에 포함. 프롬프트/스키마 해시 고정. `max_context_chars`와 기존 페이지 한도 유지 |
| `law_navigation.py: view/validate/execute_tool/run` | 동일 조회 이력과 읽은 범위를 메뉴·검사·루프에서 일관되게 사용 | 읽기 receipt, FINISH 원문 전달, SELECT 산출물 유지. 데이터/권한이 바뀌면 오래된 대상은 재사용 불가 |

새 함수·필드는 설계 제안이며 아직 구현되지 않았다. 1차는 코드/프로필/판단 입력 버전 변경이며 원문·용어·FTS 재구축은 필요 없도록 설계한다. 기존 저장 메타데이터로 정보가 부족한 경우는 누락으로 표시하며 새로운 데이터 이행은 별도 범위로 다룬다.

### 후보 정보와 원문 계약

후보는 같은 `target + document/version + read extent` 안에서만 병합한다. 다른 문서·권한·버전·범위의 후보를 번호가 같다는 이유로 합치지 않는다. 후보 카드에는 실제 문서명, 조문번호, 실제 제목, 읽기 범위, 기존 적중문, 읽음 상태를 둔다. 적중문이 없으면 만들지 않는다. 긴 제목·미리보기는 표시 상한 안에서 잘라도 원문과 receipt는 자르거나 대체하지 않는다.

후보 정보와 실제 원문은 명시적으로 구분한다. 원문을 읽었다는 상태는 reader의 성공 receipt로만 바뀐다. 읽음, 모델에 전달됨, 근거로 사용됨, 최종 주장에 인용됨은 각각 별도 기록이다.

### 반복 조회와 복구 계약

기존 복구 담당인 read-choice decision journal을 재사용한다. 동일 동작의 서명에는 문서/버전, 접근 범위, 조회 필터, 실제 읽기 범위, generation을 사용한다. 관련 원문 전달 범위가 늘어난 경우와 단순 상태 revision 증가를 구분한다. **로그 revision만 바뀌었다고 같은 조회를 새 조사로 허용하지 않는다.** 제목 조건을 제거한 조회처럼 결과가 달라질 수 있는 최초 대안은 허용하고, 결과/범위가 그대로인 반복은 progress로 세지 않는다.

중복 발생 시 원래 제안·오류·이미 확보한 원문을 보존한다. 아직 사용하지 않은 기존 no-progress 복구 기회가 있으면 유효한 다른 후보/범위를 한 번 선택할 수 있게 하되, schema repair를 추가로 겹쳐 소비하지 않는다. 기회를 소진했으면 원문은 후속 ASSESS로 전달하고 미확인을 남긴다. 주장이 없으면 조사 미완료, 검증된 주장이 있으면 제한 답변이다. 코드가 법률 결론이나 충분성을 대신 결정하지 않는다.

## 7. RAM과 시간 계측

대형 데이터 로딩/실제 모델 검증은 하나씩 실행한다. 같은 데이터 세대의 immutable 인덱스는 프로세스 안에서 공유하고, 요청별로 전체 색인이나 본문 사본을 만들지 않는지 먼저 측정한다. 전역 캐시 확대·추가 worker는 성능 개선의 기본 수단으로 삼지 않는다.

계측은 기존 request context에 소량의 카운터만 둔다. 단조 시계로 다음 항목을 구분한다: 초기화/검색/원문 획득/후보·모델 입력 조립/상태 I/O/모델 전송/발행/관측기. 중첩 구간은 inclusive와 exclusive를 구분해 합산 중복을 막는다. 미분류 비용은 OTHER로 남기고 평균값을 DB 시간처럼 붙이지 않는다. 원문·프롬프트를 계측 로그에 반복 저장하지 않는다.

강제 GC를 곧바로 제품 최적화라고 일반화하지 않는다. 다음 성능 검증에서는 먼저 동일 자원 보호 조건에서 GC/압축 비용을 따로 측정한다. 이후 호출마다 수행할 필요가 없다는 근거가 생기면 요청 종료/명시 압력 시점으로 옮기는 후보를 별도 검증한다. 계측기를 바꾼 결과와 RAG 코드를 바꾼 결과를 한 개선량으로 합치지 않는다.

로컬 검증 자원 경계는 이전 실행과 동일하게 프로세스 그룹 RSS 6GiB, 가용 RAM 4GiB 하한을 유지하고, 최대 RSS 4GiB 이하를 1차 목표로 둔다 [G2]. 환경별 적정치는 별도이며 GENOS의 동일 수치 적용을 의미하지 않는다. 저장은 한 원장을 참조하고, 종료한 자체 임시 파일만 해시 검증 후 무손실 압축한다.

시간의 기본식은 `T요청 = T초기화 + ΣT물리모델 + T도구/검색 + T조립/저장 + T발행 + T관측기 + T기타`다. 호출을 줄여도 각 입력이 길어지거나 다른 비용이 증가하면 전체 시간이 줄지 않을 수 있다.

손익분기는 `제거한 왕복 시간 > 제목/미리보기 증가에 따른 모델 처리시간 + 새 후보 조립/검사 비용`일 때다. 제목 복구로 탐색 횟수가 그대로이고 입력만 늘면 지연이 악화될 수 있다. 따라서 호출 수와 시간, 성공한 답변을 함께 측정한다. 호출 절감률을 토큰/비용 절감률로 바꾸지 않는다.

G1은 첫 읽기에 직접 근거가 포함되고 추가 조사가 0~2회인 조건이다. 참조의 계층·긴 원문·복수 쟁점으로 추가 조사가 한 번 늘면 최소 그 모델 왕복과 도구 시간이 추가된다. 실제로 7회 안에 끝난다고 보장하지 않는다. 구현 일정은 개발·회귀·모델 검증·현장 반영 대기의 소요자료가 없어 미산정이다.

## 9. 검증·적용·롤백 계획

**P0 — 비교 가능한 측정 기반.** 기존 ADR0900은 그대로 보존한다. 현장 자료가 제공되면 리비전/코드·프로필·데이터 binding, 전체/모델 시간, 호출 phase, retry/reentry, 실패/성공을 동일 표로 분류한다. GENOS 연결 재시도는 하지 않는다. 가벼운 계측 수정도 실제 서비스 진입점·동일 pin과 저장/표시 소비자로 검사한다.

**P1 — 후보 정보 보존과 반복 계약.** 제목 있는/없는 후보, 구조와 전문검색의 같은 target, 상위·하위 범위, 문서/버전 충돌, 이미 읽은 원문, 반복 조회, 복구 성공/실패, 예산 소진, 재시작·중복·stale·권한·해시를 합성 계약 검사한다. 단순 형식 검사와 의미 품질 검증을 구분한다. 현재 다른 작업 변경을 보존하며 필요한 파일만 통합한다.

**P2 — 실제 효과 확인.** 모델·프롬프트·검색 효과를 바꾸는 구현 및 첫 호출 전에 기존 두 실험 표준을 따라 같은 scope reservation 확인 → 새 ADR 선점 → 정확한 완료 부모/MAIN87 기준선 → snapshot/register/freeze를 수행한다. 첫 후보는 제목 보존만, 번호 단서 정책과 반복 복구는 별도 후보로 분리한다. 결과를 보고 만든 후보/재실행은 새 ADR이다. 원문과 색인은 공유하고 무거운 실행은 순차 처리한다.

정관 질문은 이미 본 진단 사례로 표시한다. 독립 평가에는 다른 문서/쟁점의 짧은 직접 규칙, 일반결의와 별개 업무, 정확한 번호 질문, 제목 없는 항·호, 명시 참조, 복수 법령, 부분 인용·예외·미확보를 포함한다. 같은 질문의 의역을 독립 표본으로 세지 않는다. 질문·평가기준·필수 근거·횟수·예산·정상/부분/실패 판정과 허용 회귀는 결과 전에 동결한다. 후보가 모델 입력에 정답 번호를 주입하지 않게 한다.

관측 항목은 성공/부분/실패, 실제 필요한 근거와 인용, 물리 호출/수정/재진입, 전체/모델/호스트 시간, 입력·출력 토큰, RSS다. 짧은 질문은 G1을 목표로 보고하되 의미 판단 미스는 별도 기록한다. 세부 의미 점수만으로 승격을 자동 차단하지 않으며, 인용·권한·해시·상태·예산·실제 서비스 배선의 심각한 회귀는 차단한다. 표본이 적으면 평균/p95/일반 정확도를 부풀려 보고하지 않는다.

**P3 — 작업 코드와 MAIN 연결.** 검증된 변경만 현재 작업 코드에 통합 → 동일 코드/프로필 검사 → accepted/out-of-sample/decision_eligible complete arm의 hash 고정 승격 plan → `rag_main_promotion.py`의 명시적 apply 절차 → 활성 포인터와 실제 `service.application` binding 확인으로 연결한다. 새 원문 세대가 불필요한 범위에서는 기존 generation을 그대로 결속한다. 이전 MAIN87 포인터/코드/프로필과 apply/rollback receipt를 보존한다.

**P4 — GENOS 반입은 별도.** 이후 현장 패키지를 만드는 작업에서는 genos-release-integrity 절차로 검증 코드와 실제 대상 일치를 확인한다. 기존 `~/DEV`에 적용하고 실제 업로드 TRANSFER에서 `python3`로 안내한다. 코드 적용·Git push·서빙 리비전·워크플로우 편집기 저장을 구분한다. 최종 질의 검증은 워크플로우 테스트 화면에서만 하며 내부 모델로 호출 수/시간/답변을 확인한다. 로컬 외부 모델 개선을 현장 개선으로 보고하지 않는다.

**롤백 조건:** 새 후보에서 원문/인용·권한·해시·저장 상태가 훼손되거나, 동일 요청 재개가 무제한 호출을 일으키거나, RAM 보호 경계를 넘으면 새 활성화 중단 또는 이전 선택으로 복귀한다. 후보 표시/스키마가 달라진 실행 중 요청을 임의로 새 버전에서 재생하지 않는다. 검증된 제한 답변과 실패 기록은 보존한다.
