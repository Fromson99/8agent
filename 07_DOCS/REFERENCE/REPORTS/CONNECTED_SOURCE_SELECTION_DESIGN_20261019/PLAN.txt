연결 원문 공동 판단과 문서 내 용어 추가 탐색 — 후속 구현 설계
작성일: 2026-10-19. 상태: 설계 제안. 이번 문서 작성에서 제품 수정·모델 실행·승격·GENOS 배포는 수행하지 않았다.

사용자 요청은 A만으로 판단하기 어려울 때 연결된 B를 읽고 A와 B를 함께 선택하며, 문서를 특정한 뒤 용어로 추가 탐색하는 흐름이다. 선행 후보에 구현한 탐색 경로를 기존 작업 코드에 통합하고, 미열람 후보가 실제 원문으로 오인되거나 부모 전달 중 사라지는 지점을 개선한다.
의미 판단은 LLM이 맡는다. 모든 후보 읽기, 특정 조문 강제 선택, 후보 처리 목록의 완성을 종료 조건으로 삼지 않는다. 불확실한 조사에서도 확보한 원문은 전달하고, 비교 결과에는 의견·이유·인용·미확인을 남긴다.

1. 현재 확인한 사실과 적용 범위

관측 기준은 다음과 같다. 수치·환경·해시는 동봉한 EVIDENCE.json과 10번 원장에서 구분한다.

- 활성 로컬 선택: MAIN88 / answer-first-followup-20261019-r1. workflow manifest 1.10.0. 선택 포인터와 release manifest를 확인했다. 이번 설계에서 실제 상주 서비스를 호출하지 않았다.
- 검증 후보: adr_0922/normalized/revisions/rev-001/snapshot. 연결 출발점 유지, 원문 읽기 선택지, 문서 한정 구문 검색이 들어 있다. ADR0923은 같은 코드의 재관측이다.
- 작업 코드: connected_exploration.py가 아직 없고, law_navigation.py·decision_projection.py·source_investigation.py는 해당 활성 파일과 같다. request_repair.py는 활성·후보와 별도로 변경돼 있어 그대로 덮어쓸 수 없다.
- 작업 코드에는 MAIN88에 없는 Oracle 요청별 조회 및 최신 진행·로그 수정이 존재한다. 후보 전체 복사로 통합하지 않는다. 아래 변경 지도는 검토 시점 파일을 기준으로 하며 구현 직전에 재대조한다.
- GENOS: 이 세션에서 현장에 접근하지 않는다. Oracle 조회·외부 상태 저장의 작업 코드와 현장 배포 완료를 구분한다.

선행 관측은 동일하게 알려진 레버리지비율 질문에서 나왔다. ADR0921 기준은 제3-6조만 확보했다. 첫 연결 후보는 제3-6조·제3-24조의4·제3-26조제7항을 모두 확보·반환·인용했다. 용어 정규화 수정 후 ADR0923은 후보를 노출했지만 뒤의 두 조항을 읽지 않았다. 모델은 후보 미리보기로 한도를 확인할 수 있다고 설명하며 종료했다. 분자·분모 판단 오류와 불완전한 내규 대사도 남았다. 단발 관측으로 개선율이나 원인의 크기를 산정하지 않는다.

2. 실제 실행 경로와 책임

service.py의 WORKFLOW_RUN 정규화 또는 대사 라우팅
→ /v1/workflows/run, workflow_bridge.install
→ workflow.runtime.Runtime.execute
→ risk_team_compare_workflow의 retrieval.discover
→ workflow_rag.execute, 내규·외규 자식 RAG
→ law_navigation._request_decision에서 source_handoff.enabled 확인
→ source_investigation.choose의 조사 행동 선택
→ 기존 READ/참조/구조/본문 탐색과 원문 receipt 저장
→ source_handoff.selection/commit/publish
→ workflow_evidence.compile_source_bundle 및 부모 근거 저장
→ task_board.review/research, 기존 항목별 추가 조사
→ compare/report와 기존 저장·응답·상태 조회 소비자.

대사 자식에서는 일반 RAG의 decision_projection.choose_read보다 source_investigation.choose가 먼저 선택된다. 일반 RAG의 FINISH 프롬프트만 수정하면 대사의 실제 종료 판단에 연결되지 않을 수 있다. 두 경로를 각각 검사한다.

자식의 책임은 필요한 원문 조사·전달이다. 부모의 책임은 항목별 관련성·조건·예외·내외규 차이 판단이다. 시스템은 출처·읽은 범위·전달 여부·허용 위치·권한·버전·중복·예산을 관리한다. 자식이 의미상 승인한 원문만 반환하는 과거 방식으로 돌아가지 않는다.

3. 문제별 기존 처리 → 제안 처리 → 확인할 결과

P1. 연결 출발점과 현재 원문의 시점 차이
기존: 현재 탐색 위치 중심의 출발점과 원문 전달 등록 시점이 달라, 정의 A를 확보했어도 연결 후보에서 빠질 수 있었다.
관측: ADR0921 진단에서 현재 페이지의 참조 범위 등록 누락을 확인했다. ADR0922가 수정했고 관련 계약을 통과했다.
제안: 후보의 지속 출발점 및 current_pages 검증 연결을 작업 코드에 병합한다. 새 B가 생기면 과거 A의 판단을 역사로 보존하면서 A와 B를 다시 함께 검토할 수 있게 한다.
목표/검증: 화면 복귀·중단 재개·정의 자동 읽기 뒤에도 A의 검증된 원문과 B의 읽기 선택지가 남는다. A의 이전 보류가 새 B를 본 뒤의 재판단을 자동 금지하지 않는다.

P2. 용어가 존재해도 검색 0건, 일반 용어의 많은 적중
기존: 붙여 쓴 용어를 분리된 색인에 그대로 질의했다. 문서 한정 이후에도 일반적인 등록 용어는 많은 후보를 만들 수 있다.
관측: 레버리지비율/레버리지 비율 불일치와 수정 후 문서별 3·5개 후보를 확인했다. 일반 용어의 범위 내 노이즈는 잔여 한계다.
제안: 색인과 같은 구문 정규화를 유지한다. 문서 특정 후 질문과 일치한 구체 용어를 먼저 사용하고, 같은 출처·범위의 중복 후보는 합치되 발견 경로는 모두 남긴다. 후보 순서는 기존 검색 순위와 미열람·경로 다양성을 사용하며 조항 번호별 가중치는 넣지 않는다.
목표/검증: 초기 전 문서 용어 확장을 하지 않고, 선택 문서의 제한된 페이지에서 후보를 제시한다. 0건·조회 실패·페이지 미조회는 각각 다른 상태이며 부재의 증명이 아니다. 용어 동의어 무제한 확장과 문서 전체 강제 열람은 최초 변경 범위에서 제외한다.

P3. 후보 미리보기를 원문 확보로 판단
기존: 후보에 citation_eligible=false가 있어도, 원문과 후보를 함께 본 모델이 미리보기로 충분하다고 종료했다.
관측: ADR0923의 실제 선택 이유에 후보 미리보기로 한도 확인 가능이라는 설명이 있다. 해당 두 원문은 읽지 않았다. 단순 경고 프롬프트만으로 안정화되지 않았다.
제안: 모델 입력을 확보한 원문, 추가 조사 후보, 남은 조회 범위로 명확히 나눈다. 기존 action/query/reason 응답 계약을 유지하며, 미열람 대상에 대해 실제 원문 읽기 선택지를 가까이 둔다. 종료는 원문 반환으로 표현하고 법률 검토 완료와 분리한다.
목표/검증: 미리보기는 근거 ID나 인용 목록에 들어가지 않는다. 모델이 여전히 조기 종료하면 이를 오류 수정 루프로 반복시키지 않고, 실제 원문과 미열람 단서를 부모에게 넘긴다. 필요한 자료를 안정적으로 읽는지는 별도 모델 실험으로 판단한다.

P4. 후보가 자식에서 발견돼도 부모에게 전달되지 않음
기존: source_handoff의 source-investigation-v1은 읽은 근거·종료 이유·acquisition·research_tasks를 보낸다. 이번 document_term_exploration 후보 목록은 반환 계약에 없다. 부모 locators는 현재 원문과 그 안에서 확인한 정참조를 중심으로 재구성된다.
확인 수준: 코드 연결로 확인한 계약상의 공백이다. 새 설계가 실제 모델의 누락을 얼마나 줄일지는 미측정이다.
제안: 반환 계약에 비인용 조사 단서 묶음을 추가하고 부모의 기존 ITEMS next_tasks와 연결한다. 역참조·용어 후보에도 검증된 위치를 제공하되 부모 근거로 승격하지 않는다.
목표/검증: 자식이 A만 읽고 반환해도 부모가 B 후보의 출처·현재 상태를 보고 B 읽기를 선택할 수 있다. B의 실제 원문을 받은 후 A+B를 같은 항목에서 검토한다. 원문 0개·후보만 있는 경우도 기존 항목 검토에 조사 단서만 제공하며 확인 내용은 미확보로 유지한다.

P5. 입력 압축과 재검토 키 때문에 연결 문맥 누락
기존: bounded_model_view는 한도 초과 시 dependency_cards 전체를 제거할 수 있다. 부모 task_board.review의 input_key는 원문·attempt_status 중심이므로, 원문이 같고 새로운 후보만 생기면 기존 검토로 간주할 수 있다.
확인 수준: 카드 제거는 코드·선행 실행에서 확인했다. 새 후보가 추가되는 계약에서는 input_key 수정이 필요하다는 것은 설계상 결론이며 신규 런타임 재현을 수행하지 않았다.
제안: 각 후보의 위치·연결 방향·출발 원문 ID·미열람 상태·읽기 선택지를 최소 카드로 유지한다. 긴 미리보기부터 줄이고, 초과 후보는 개수·커서로 남긴다. 부모 검토 키에 단서 묶음 해시와 확보 범위 revision을 포함한다.
목표/검증: 선택지는 있는데 왜 연결됐는지 알 수 없는 상태를 줄인다. 같은 원문·같은 단서·같은 상태는 재검토하지 않고, 새 B 또는 새 단서 revision에는 기존 검토 경로로 한 번 진입할 수 있다.

4. 제안 데이터 계약

새 이름은 모두 제안이며 현재 기능으로 간주하지 않는다. source-investigation-v2에 investigation_leads-v1을 포함하는 방식으로 설계한다. 외부 workflow-result-v1의 필수 필드는 유지하고 새 정보는 선택적 조사 설명으로 추가한다. 내부 bundle은 새 버전으로 producer/consumer를 함께 갱신한다.

시스템이 만드는 조사 단서 항목:
- lead_id: 동일 요청 binding·판본·문서·원문 범위에서 결정하는 안정 ID.
- target: 문서/원문/unit ID, source hash, 판본, 내규·외규, 정식 표시 위치.
- origins: OUTGOING_REFERENCE / INCOMING_REFERENCE / DOCUMENT_TERM. 같은 대상에 여러 경로가 있으면 병합한다. 문서·판본이 다르면 이름이 같아도 합치지 않는다.
- anchors: 실제 확보한 A의 근거 ID 및 연결 receipt. 용어 탐색은 조회 식·문서 범위·색인/조회 release·페이지 receipt를 출처로 둔다.
- acquisition: NOT_READ / PARTIAL / ACQUIRED. 실제 원문 receipt에서 계산하며 조 전체를 읽었는지 특정 항만 읽었는지를 포함한다.
- delivery: 어느 모델 입력과 부모 반환에 어떤 실제 span을 전달했는지의 기존 기록 참조. DB 확보와 모델 전달을 분리한다.
- availability: 현재 권한·판본에 유효한 읽기 위치와 조회 상태. 실행 가능한 action ID는 현재 presentation에서 재발행한다.
- preview: 짧은 탐색용 발췌. citation_eligible=false이며 evidence_id를 만들지 않는다.
- opinion: 선택 이유·보류·관련성 판단은 별도 모델 의견과 그 판단 당시 근거 revision으로 보존한다. 필수 완료 목록으로 만들지 않는다.

단서 묶음에는 catalogue_hash, omitted_count, page_cursor와 조회 성공/부분/실패를 둔다. 실행 상태의 저장 위치는 기존 repository를 사용한다. GENOS에서는 승인된 외부 상태 저장 계층을 사용하며 원문·색인이나 이 실행 상태를 코드서빙 로컬 디스크에 새로 저장하지 않는다.

원문 근거와 단서의 계약:
- 인용·비교는 실제 검증된 evidence/span에서만 선택한다.
- 단서로 선택할 수 있는 것은 원문을 읽을 위치다. 조사 과제의 origin_evidence_id를 꾸며서 검증을 통과시키지 않는다.
- 참조 후보는 저장 참조의 양끝·방향·witness hash를 검증한다. 역참조 B의 witness가 A에서 읽힌 것처럼 표현하지 않는다.
- 용어 후보는 문서 범위·조회 release·색인 hash·실제 결과 receipt로 위치를 검증한다. 법적 관련성은 보장하지 않는다.
- 부모에서 재실행할 때 허용 위치를 현재 권한·동일 판본으로 재검증한다. 구형 자식 action ID를 재사용하지 않는다.

호환/이행:
- v1 기존 완료 결과는 그대로 읽고 재현한다. 신규 필드가 없으면 조사 단서 미기록으로 표시하며 후보 없음으로 해석하지 않는다.
- 신규 요청만 v2 계약을 선택한다. 진행 중인 v1 요청은 기존 코드·계약 binding으로 재개한다. 중간 요청을 강제 이행하거나 과거 반환 hash를 다시 계산해 덮어쓰지 않는다.
- source_handoff.schema, publish/validate_export, workflow_rag의 허용 버전, compile_source_bundle/verify_export/compact_result, workflow manifest를 함께 변경한다. 선택된 기능 플래그와 스키마를 엔진 pin에 포함한다.
- retrieval.discover의 source_return_contract == source-investigation-v1 분기도 새 계약을 명시적으로 지원해야 한다. manifest만 v2로 바꾸면 return_mode=sources 진입이 빠질 수 있으므로 진입·반환 계약을 같은 변경에서 검사한다.
- 기존 원문·용어·참조/색인 데이터 재구축은 기본적으로 필요하지 않다. Oracle 조회 release의 포트가 해당 기능을 지원하는지는 별도 계약 검사한다.

5. 모델 선택과 실제 시나리오

정상 조사:
질문 → A 원문 확보 → 연결 B와 문서 내 용어 C를 후보로 표시 → 모델이 B 읽기 선택 → 검증 원문 receipt 저장 → A와 B를 함께 제시 → 부모가 필요한 인용·조건·차이를 선택.
정답 조항 번호는 평가 측 피드백에만 둔다. 원문을 읽을지는 질문·원문·발견 경로를 보고 판단한다.

조기 반환:
자식이 후보 미열람 상태에서 null을 선택 → 확보한 A와 단서 B/C를 함께 반환 → 부모 기존 항목 검토에 원문과 단서를 분리 입력 → 필요하면 기존 next_tasks로 정확한 위치를 읽음 → A+B 재검토.
부모도 추가 읽기를 선택하지 않을 수 있다. 그때는 확보한 범위의 답과 미열람/미확인 내용을 남긴다. 목록 잔여 수만으로 partial을 강제하거나 사용자에게 불필요한 사실 질문을 하지 않는다. 실제 질문의 충족 여부는 모델 의견으로 표시한다.

A만으로 관련성이 불명확:
A의 보류 의견과 원문은 보존 → B의 새 원문이 같은 쟁점의 문맥을 바꿈 → A의 이전 의견을 함께 보여 주고 재판단 → A+B 또는 일부를 선택. 새 원문이 생겼다고 시스템이 A를 자동 채택하지 않는다.

동일 원문·새 후보:
원문이 그대로여도 새 단서 hash가 있으면 부모의 review 입력이 바뀐다. 동일 hash를 다시 받아 검토·조회가 반복되지는 않는다. 같은 대상을 다른 설명으로 요청해도 acquisition_key는 의미 문구 대신 대상·scope·판본·범위를 기준으로 중복을 막는다.

긴 원문:
A와 B의 관계를 보여 주는 최소 카드와 실제 읽은 범위를 함께 배치한다. 같은 입력에 둘 다 들어가면 함께 검토한다. 넘으면 기존 원문 packet 경로로 분할하고 연결 ID·미전달 범위를 유지한다. 원문을 요약본으로 대체하거나 일부 span을 조 전체 열람으로 올리지 않는다. 긴 단일 원문 실패는 기존 크기 오류·부분 반환 계약으로 다룬다.

용어 노이즈:
문서 내 적중이 많으면 기존 순위의 제한 페이지와 다음 조회 선택지만 제공한다. 구체 용어·미열람·연결 경로를 참고해 모델이 선택한다. 모든 후보 읽기를 강제하지 않는다. 일반 용어의 문서 내 적중도 관련성이 낮을 수 있으며, 그 비율은 평가로 측정한다.

7. 실패·복구 계약

- 미열람 후보를 근거로 충분하다는 모델 의견: 조사/부모 단계가 의미 문제로 기록한다. 자동 반복 호출 없음. 확보 원문은 반환하고 부모의 기존 추가 조사로 선택할 기회를 제공한다.
- 후보 검색 실패 또는 중단: 해당 조회 담당이 FAILED/PARTIAL과 receipt를 기록한다. 같은 실패를 자동 반복하지 않으며 원문 부재로 기록하지 않는다. 다른 허용 경로 또는 부분 반환을 유지한다.
- READ 일부 성공 후 실패: 범위별 receipt와 커서 보존. 새 시도는 미완료 범위만 대상으로 삼고 기존 원문을 재확보했다고 중복 계산하지 않는다.
- 제공자 429/전송 오류: 기존 gateway가 effective retry policy 내에서만 담당한다. 부모·자식에 같은 전송 재시도 루프를 추가하지 않는다. 물리 시도와 대기 시간은 부모 예산에 포함한다.
- 구문/필수 필드/대상 위반: 기존 output.bounded_decision 또는 부모 model adapter가 자기 단계의 원래 스키마로 제한 수정한다. 의미 판단 불확실성을 스키마 오류로 바꾸지 않는다.
- 권한/판본/원문 hash/상태 revision 불일치: 결과 적용 차단, 기존 conflict/failed 상태 보존. 모델 수정으로 우회하지 않는다. 이전에 검증한 자료도 현재 권한 재검사 없이 보여주지 않는다.
- 중단·재개·중복: 같은 request/binding, 최초 deadline, 사용량, 발표 revision, 처리 receipt를 복원한다. 새 run ID나 설명 변경으로 한도를 초기화하지 않는다.
- 예산 소진: 추가 조회·모델 호출 중단. 기존 종료 예약 예산으로 검증된 원문과 미확인 범위를 반환한다. 원문 0건이면 0건 그대로 전달한다.
- 저장/표시 실패: 먼저 확정한 journal과 export hash를 보존하고 동일 결과의 발행만 복구한다. 이미 일부 전송된 답변에 새 생성 답변을 이어 붙이지 않는다.

추가 조사 횟수와 수정 횟수는 기존 선택 profile/manifest의 effective 값에서 읽는다. 조사마다 임의의 별도 예산을 만들지 않는다. 신규 단서 정리 자체에는 모델 호출을 넣지 않는 것이 설계 목표다. 부모의 추가 READ와 뒤따르는 검토는 기존 요청 총예산 안에서 과금한다.

8. 검증 계획과 판정

이번 단계에서는 새 실험을 시작하지 않았다. 구현 착수 시 실험 목적 변경 전에 저장소 실험 표준 두 문서를 끝까지 읽고 동일 scope reservation을 확인한 다음 새 ADR을 선점한다. 완료된 부모 ADR0922/normalized와 관측 ADR0923/observed, 구현 시점 활성 baseline 및 최신 작업 변경의 병합 근거를 구분해 동결한다.

기술 계약 검사:
- 구문 정규화, 문서 범위 밖 차단, 동일 조항 경로 병합/판본 분리, 역참조 방향과 witness.
- A 미승인 상태·화면 복귀 뒤 B 선택, B를 받은 뒤 A+B 동시 제시/선택.
- 후보 단독 인용 거부, 실제 원문의 일부/전체/미전달 범위 구분.
- 입력 압축 뒤 최소 카드와 읽기 행동의 동일 target 결속.
- 자식 조기 반환 → 부모 단서 위치 선택 → 실제 원문 → 기존 비교 결과·인용 연결.
- 단서만 추가된 경우 재검토, 같은 단서 반복/부모 재개 시 중복 조회 방지.
- v1 완료 결과 재현, v1 진행 요청 재개, v2 신규 반환·저장·상태 조회·중복 응답 일치.
- JSON 복구 성공/실패, 반복 충돌, 429 소진, 예산 소진, 부분 읽기, 권한·hash·revision 실패.
- SQLite와 Oracle 조회 포트의 동일 범위·구문·페이지·오류 계약. 로컬 검사와 현장 확인은 분리.
- 최소 한 검사는 후보와 동일 code/profile/pin의 service.py → WORKFLOW_RUN → 부모/자식 → 저장/최종 조회로 수행.

모델/검색 평가 계획:
- 레버리지비율 사례는 이미 본 진단 사례다. 사용자 필수 세 조항은 평가 측에만 둔다. 일반화 검증이나 holdout으로 계산하지 않는다.
- risk_cm 등록 질문은 승인 정답이 아닌 question_only다. 관련 원문과 필요 근거 범위를 평가 측에서 먼저 동결하고, 실제 모델 입력에는 해당 표식을 노출하지 않는다.
- 독립 단위는 규정·업무 사례다. 같은 사례의 의역을 독립 표본으로 세지 않는다.
- 연결 B를 읽어야 A의 의미가 달라지는 사례, 역참조만 있는 사례, 명시 참조 없이 용어로 찾는 사례, 연결됐어도 무관한 사례, 많은 용어 적중, 부모 추가 조사, 긴 원문, 버전/권한 변화 등 다른 실패 구조를 포함한다.
- baseline, 선행 연결/용어 후보, 새 전달/표시 후보를 같은 모델·질문·데이터·예산으로 비교하는 arm 구성을 실행 전에 동결한다. 효과를 분해하려면 별도 ablation도 호출 전에 계획하며 결과를 본 뒤의 후보는 새 ADR로 남긴다.
- 신규 외부 실험은 현재 정책의 ExperimentClient / qwen/qwen3.8-27b / Parasail FP8 / reasoning none / fallback 없음. 실제 호출 시 정책 파일과 backend ID를 다시 확인한다.

지표는 발견 → 모델 입력 노출 → 실제 READ → 자식 반환 → 부모 입력 전달 → 최종 인용을 각각 센다. 필요한 조항 누락, 불필요한 원문 읽기, 같은 대상 반복, 미리보기 의존 종료 의견, 내외규 비교의 의미 오류를 별도 기록한다. 의미 오류를 모두 해결해야 승격 가능하다는 새 기준을 만들지 않는다.

기술 통과 목표는 변경 범위에서 인용 출처·권한·hash·상태 보존 위반 없음, 원문 전달 유실 없음, 기존 부분 반환·재개·중복 계약 보존이다. 모델 품질의 허용 회귀와 수치 기준은 평가 집합·예산과 함께 첫 호출 전에 정한다. 현재 자료만으로 정확도 목표 수치를 꾸미지 않는다.

9. 구현·검증·반영 순서

단계 A — 병합 기준 확정
현재 작업 코드/활성 코드/ADR0922 후보의 파일별 차이와 Oracle·진행 로그 수정 목록을 확인한다. 예약·버전·실행 명세와 성공/회귀 기준을 동결한다. 후보 snapshot 전체 덮어쓰기를 하지 않는다.

단계 B — 공통 상태와 후보 표시
선행 연결·구문 검색 구현을 필요한 함수 단위로 통합한다. 원문/단서/미조회 구분과 입력 압축을 수정하고 기존 단위·계약 검사에 연결한다.

단계 C — 부모 전달과 추가 조사
v2 반환·저장·검증·locators·ITEMS 입력·재검토 키를 함께 구현한다. 일반 RAG와 대사 경로를 각각 확인하고 관련성 불확실성이 원문 반환을 막지 않게 한다.

단계 D — 동일 코드 검증
통합 코드와 동일한 snapshot으로 기술 검사·실제 서비스 진입 검사·동결한 모델 평가를 순차 수행한다. 결과를 본 뒤 수정하면 새 후보 계보를 남긴다. 최종검사와 graph의 기존 오류/신규 오류를 구분한다.

단계 E — 로컬 MAIN 반영
Accepted·out-of-sample·decision_eligible=true·complete 등 기존 승격 계약을 충족한 arm만 rag_main_promotion.py의 hash 고정 plan과 명시적 --confirm-main 절차로 처리한다. 작업 코드·검증 후보·release 코드/profile/데이터/검색 정책 지문, apply/rollback receipt를 연결한다. 선택 포인터를 읽고 실제 service.py의 선택 binding과 요청 결과를 확인한다. 현재 설계만으로 승격 승인이나 실행을 완료했다고 보지 않는다.

단계 F — GENOS 별도 인계·현장 확인
Oracle 요청별 조회, 승인된 외부 상태 저장, 내부 모델 조건으로 패키지를 별도 검증한다. 현장 적용은 실제 TRANSFER에서 기존 checkout으로 하는 지침을 따르고, 코드 적용·Git push·서빙 리비전·워크플로우 편집기 저장을 각각 확인한다. 실제 질의는 워크플로우 테스트 화면에서 확인한다. 이 세션에서 현장 접근이나 배포 성공을 가정하지 않는다.

롤백은 이전 선택 release와 코드/profile/스키마 바인딩으로 복귀한다. v2 요청 journal·실패 기록을 삭제하지 않고 해당 버전 reader를 보존한다. 단순 플래그 off로 v2 진행 요청을 v1 계약에 끼워 넣지 않는다. 데이터 재구축이 없다면 기존 원문/색인 세대는 유지한다.

10. 수치·기대치·자원 원장

N1 [관측] 선행 계약 검사 104개 통과. 분모는 ADR0922가 실행한 관련 소프트웨어/API 검사이며 별도 기준 코드에서도 실패한 기존 1개는 제외 기록이 있다. 모델 정확도 수치가 아니다. 출처: ADR0922 RESULT 및 검사 산출물.
N2 [관측] ADR0923 알려진 질문 한 번: 물리 호출 13회, 약 361초, 저장 근거 115건의 원문 일치. 출처: ADR0923 result/manual-review. 평균·p95·예상 현장 지연으로 사용하지 않는다.
N3 [기존 설정] 후보 문서 4개/용어 4개, 문서당 6조항/페이지, 단서 표시 10,000자 한도. 출처: connected_exploration.py. 실제 소비량이나 관련성 보장 값이 아니다. 최초 후속 비교에서 상속하고 변경 효과는 별도 계획한다.
N4 [관측] 같은 알려진 질문에서 실제 원문 확보: 기준 1/사용자 지정 3조항, 첫 후보 3/3, 최신 1/3. 서로 독립적인 품질 표본이 아니며 개선율을 계산하지 않는다.
N5 [목표] 상태 정리·후보 반환만을 위한 추가 모델 호출 0회. 기존 선택/ITEMS 호출 안에 입력을 연결한다. 실제 재조사에 따른 READ와 재검토 호출 증가는 별도로 측정한다.
N6 [계산식] 순 추가 지연 = 새 조회 시간 + 새 입력 처리 시간 + 추가 READ/검토 시간 - 제거된 중복 탐색 시간. 손익분기는 앞의 세 항 합과 절감 시간이 같을 때다. 미열람 후보가 대부분 무관하면 호출·지연이 늘 수 있다. 현재 각 항의 실측이 없어 수치 미산정이다.
N7 [미확인] 원문 누락 감소율, 불필요 읽기 증가율, Oracle/GENOS p95·비용·내부 모델 품질. 같은 코드/범위의 실험과 현장 기록이 필요하다. 비용은 호출 수가 아닌 실제 토큰·모델 단가·조회 비용을 분리해 계산한다.
N8 [실행 제약] 로컬의 대형 데이터·모델 검증은 무거운 프로세스 하나씩 순차 실행한다. 선행 실행의 중단 기준인 RSS 6GiB/주소 공간 8GiB/가용 RAM 4GiB/디스크 10GiB는 후속 실행 전 상태를 확인해 동결할 가정이며 보편적 용량 보장이 아니다. 기존 프로세스와 swap 압박을 확인하고 진행한다. 원문·색인·완료 기록은 공유·보존한다.
N9 [미산정] 인일·완료 날짜. 병합 충돌 범위와 Oracle 포트 검사 규모가 확정되지 않았다. 단계 A의 차이 목록과 단계 C의 소비자 변경 규모를 확인한 뒤 추정한다. 검증/현장 대기를 개발 시간에서 제외해 낙관적으로 보고하지 않는다.
