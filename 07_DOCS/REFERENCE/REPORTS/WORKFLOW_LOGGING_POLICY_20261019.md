# 워크플로우 진행 표시와 로깅 개선 계획

작성일: 2026-10-19 · 상태: 설계 제안, 구현·실험·승격·GENOS 배포 미수행

사용자가 알 수 있어야 하는 것은 **지금 어느 단계인지, 무엇을 확인했는지, 무엇을 기다리는지, 추가 조사가 왜 필요한지, 결과를 어디까지 사용할 수 있는지**다. 이를 기본 화면에 요약하고, 확인한 문서와 판단 이유는 펼쳐 보며, 모델·도구 원문과 오류 상세는 접근 통제된 진단 기록에서 추적하도록 한다.

대상은 GENOS 채팅의 진행 패널, 운영자가 보는 요청 요약 로그, 기존 상세 기록이다. 문서 입력·구조화·용어집·색인·RAG·피드백으로 이어지는 전체 MAIN 중 RAG/대사 실행의 관측·표시를 개선한다. Oracle 조회·문서 분류·검색·모델 판단 정책을 이 설계로 변경하지 않는다.

## 1. 현재 확인한 범위

- 선택 로컬 릴리스는 `answer-first-followup-20261019-r1`, generation 88이다. 최근 진행 표시 작업 코드와 선택 릴리스의 `progress.py`, `request_report.py`, `genos_rag_chat.py` 해시가 다르다. 선택 릴리스에는 새 `request_journals.py`도 없다.
- 최근 인계본은 `GENOS_WORKFLOW_PROGRESS_20261019_R1`이다. 그 검증 기록은 `LOCAL_DELIVERY_VERIFIED_FIELD_PENDING`이며 GENOS 실제 리비전과 워크플로우 편집기 적용 여부는 이번 요청만으로 확정하지 않는다.
- 현재 작업 코드의 등록 대사는 `risk_team_compare_workflow` 1.10.0이다. `comparison-research-v1` 선언에 따라 `flow.execute()`에서 `task_board.execute()`로 들어간다. 실제 순서는 `INTAKE → FIND_INTERNAL → FIND_EXTERNAL → ITEM_REVIEW ↔ ITEM_RESEARCH → VERIFY_BASIS → COMPARE → REPORT → END`다. 내규·외규가 동시에 실행되는 것처럼 표현하지 않는다.
- 아래 원인 분석은 작업 코드 정적 추적이다. 사용자 제보는 “로그 과다·내외규 혼재·일관성 부족”이며, 이번 현장 요청의 원본 로그와 실제 카드 수·바이트·지연은 미관측이다. 출력에서 구분이 사라지는 문제를 실제 검색 자료의 권한·분류 혼합으로 단정하지 않는다.
- 설계 근거 파일·작업 코드/선택 코드 해시는 [검토 지문](WORKFLOW_LOGGING_POLICY_20261019.sources.json)에 남긴다. 기존 완료 검증을 이번 설계의 신규 테스트 결과로 계산하지 않는다.

## 2. 문제별 기존 처리와 개선 목표

| 상황 | 기존 방식과 확인 결과 | 수정 방식 | 원하는 결과와 검사 |
|---|---|---|---|
| 대사에서 내규·외규 문서 활동 수신 | `request_journals.children()`은 `side`, `call_id`, 자식 `run_id`를 반환한다. 그러나 `ProgressCapture._poll_children()`은 자식 이벤트를 부모 `publish()`로 재발행하면서 이 출처 문맥을 함께 전달하지 않는다. 기존 검사도 화면 이벤트의 `run_id`가 모두 부모인 것을 확인한다. | 부모 상관 ID를 유지하면서 실제 생산자·자식 실행·조사 측을 별도 필드로 보존한다. | 같은 문서명이 있어도 내규/외규 활동을 구분하며, 자식 완료가 부모 완료로 바뀌지 않는다. |
| 문서별 카드가 계속 늘어남 | 기존 5단계 요약 외에 `WORKFLOW_CHECKPOINT`, `WORKFLOW_SOURCE_READ`와 원문 활동이 상세 경로로 들어간다. `_append_source_card()`는 새 카드를 추가하고 누적 배열 전체를 송신한다. 기본 화면 카드 수의 고정 상한은 이 경로에 없다. | 현재 상태와 고정 단계 요약을 갱신하고, 문서 목록은 해당 조사 측의 접힘 상세로 모은다. | 문서를 많이 읽어도 기본 화면 행 수는 늘지 않는다. 반복 수신은 카드를 복제하지 않는다. |
| 내외규 명칭·묶음이 일관되지 않음 | `_source_label()`은 `external / ...`, `internal / ...` 문자열 형식에서 분류를 추출한다. 일반 문서명만 온 경우 분류 묶음이 생기지 않는다. | 검증한 문서 메타데이터의 자료 구분과 자식 등록의 조사 역할을 별도로 전달한다. | 화면 명칭은 `전체·내규·외규·대사`로 통일한다. 출처 기관은 외규 상세의 별도 속성이다. 문자열에서 구분을 추정하지 않는다. |
| 운영 로그의 정보가 너무 많음 | `request_report._poll_journal()`은 부모·자식 기록을 같은 파일에 모으며 모델 view, 원시 응답, 해석한 응답과 도구 결과를 출력한다. `format_readable_report()`는 자식 timeline을 합치지만 행 제목은 공통 `[journal]`이다. | 같은 원장을 읽어 간결한 운영 요약을 별도 표현하고, 각 줄에 역할·단계·상태를 붙인다. 상세 파일은 드릴다운 대상으로 유지한다. | 운영자는 한 줄로 상황을 파악하고 상관 ID로 전체 원인을 찾는다. 기록 삭제나 오류 은폐로 양을 줄이지 않는다. |
| 대기 중 “계속 잘 돌고 있는지” 불명확 | 공유 로그 heartbeat는 마지막 기록 시각을 사용한다. SSE의 빈 대기는 `: keep-alive`이며 업무 진전 이벤트가 아니다. 화면은 heartbeat를 카드로 표시하지 않는다. | 연결 확인·현재 실행 중인 작업·마지막 성공 receipt/checkpoint를 각각 관리한다. | 연결 유지와 실제 진전을 구별한다. 모델 대기는 `모델 응답 대기`, 새 진행이 없으면 `추가 진행 확인 대기`로 표현한다. |
| 검토 후 재조사 또는 일부 미확인 | 일반 요약의 단조로운 단계 순서·중복 억제는 이전 단계의 재진입을 상세하게 설명하지 못한다. 대사에는 별도 반복 체크포인트가 있다. | 현재 위치는 실제 checkpoint/revision으로 갱신하고, 재조사는 대상·사유·회차를 기존 단계 상세에 기록한다. | “외규 추가 확인 — 적용 예외의 원문 확인 필요”가 보인다. 의미 불확실성을 실행 오류나 재시도 명령으로 바꾸지 않는다. |

적용 범위는 일반 RAG·대사·재개에 공통인 표시 계층이다. 문서명 충돌, 늦게 도착한 자식 이벤트, 같은 단계의 재방문에도 같은 문제가 생길 수 있으므로 문구만 바꾸는 것으로 끝내지 않는다. 기록의 출처와 상태의 소비 계약을 함께 바꾼다.

## 3. 사용자가 보는 화면

기본 진행 패널은 아래 5개 단계 슬롯을 사용한다. 이는 화면 구성 목표 P1이며 작업량의 20% 단위나 완료 예상시간을 뜻하지 않는다. 현재 단계는 눈에 띄게 표시하고, 완료한 단계는 짧게 접는다. 대기 중인 단계는 완료 표시를 하지 않는다.

| 기본 단계 | 현재 대사 상태와 연결 | 기본 화면 내용 |
|---|---|---|
| 요청 확인 | `INTAKE` | 비교 대상·질문 범위를 확인 중/확인함 |
| 내규 확인 | `FIND_INTERNAL`, 내규 후속 조사 | 내규 조사 상태, 원문 확보·전달 사실, 필요한 후속 확인 |
| 외규 확인 | `FIND_EXTERNAL`, 외규 후속 조사 | 외규 조사 상태, 원문 확보·전달 사실, 필요한 후속 확인 |
| 항목 검토·대사 | `ITEM_REVIEW`, `ITEM_RESEARCH`, `VERIFY_BASIS`, `COMPARE` | 비교 중인 항목, 추가 조사 대상·사유, 검토한 항목 수 |
| 결과 정리 | `REPORT`, `END`와 발행 결과 | 결과 준비·전송 상태, 완료/일부 미확인/중단 구분 |

일반 RAG는 기존 `요청 확인 → 관련 문서 찾기 → 선택한 원문 확인 → 근거 검토·답변 작성 → 결과` 요약을 유지하면서 같은 상태·문구 규칙을 적용한다. 내규/외규가 모두 관련 없는 질문에는 가짜 양쪽 단계를 만들지 않는다. 저장 결과 재사용·재개도 실제 수행한 범위만 표시한다.

표시 예시이며 문서명·개수·시간은 설명용이다.

```text
현재: 외규 원문 확인 중
내규: 확보한 원문 전달 완료 · 2개 문서 · 적용성 판단은 대사 단계에서 검토
외규: 필요한 조문 열람 중 · 지금까지 3개 문서 확인
대사: 양쪽 자료 수신 후 항목 검토 예정
마지막 원문 확인: 12초 전 · 전체 경과 1분 20초

▸ 내규 확인 상세
▸ 외규 확인 상세
▸ 추가 조사·판단 이유
```

검토 도중 되돌아가면 현재 상태가 `외규 추가 확인 중`으로 바뀌고 사유를 한 줄 붙인다. 내규에서 확보한 원문과 완료한 비교 항목은 보존한다. 조사 횟수는 실제 유효 예산에서 읽으며 화면이 새 호출이나 재시도를 만들지 않는다.

상세에는 권한이 확인된 문서명·판본·확인 위치·원문 확보/전달/근거 채택 여부·명시적으로 저장한 판단 이유·남은 확인 사항을 보여준다. 검색 후보, 실제 읽음, 답변 근거 채택은 다른 수치다. “원문 전달 완료”는 “법률 판단 완료”가 아니다. 미확보는 “해당 규정 없음”을 뜻하지 않는다. 모델의 숨은 추론이나 원시 모델 응답은 사용자 상세로 전송하지 않는다.

진행 문구는 기존 GENOS의 접이식 행위 패널에 두고, 답변 본문은 검증한 최종 답변을 사용한다. 최근 인계의 검증 후 답변 조각 전송을 모델 생성 중 토큰 스트리밍으로 설명하지 않는다.

### 화면 갱신과 GENOS 제약

- 상태가 실제로 바뀌면 즉시 갱신한다. 같은 상태의 문서별 소규모 변화는 묶는다. 종료·부분 결과·실패·복구 전환은 묶음 때문에 누락시키지 않는다.
- P2 제안: 비핵심 문서 집계는 요청별 최대 5초에 한 번 갱신한다. P3 제안: 변화 없는 장기 대기의 사용자 상태는 최대 30초에 한 번만 갱신한다. 기존 전송 keep-alive와 실행 deadline은 별개이며 변경하지 않는다.
- 같은 `nodeId`의 내용을 갱신할 때 GENOS가 기존 카드를 교체하는지는 현장 미확인이다. 기존 `Visible Reasoner` wire 모양을 보존하고 그 동작을 먼저 검증한다. 플랫폼의 `FINISHED` 필드를 업무 완료 의미로 재사용하지 않고 내용에서 실제 실행 상태를 표시한다.
- 교체를 지원하지 않으면 단계당 요약 카드를 한 번씩 내보내고 상세는 최종 접힘으로 제공하는 호환 모드를 사용한다. 실제 실패·부분 완료 같은 중요 종료 안내는 제한하지 않는다. 이 경우 실시간 현재 상태 갱신 목표는 미충족으로 남기며 카드 증식을 숨겨 성공으로 보고하지 않는다.
- 직접 `/chat` 소비자와 분리 Python 워크플로우는 송신 계약이 다르다. 패널 지원 확인 없이 직접 `/chat`의 token 계약을 바꾸지 않는다. 이번 우선 대상은 분리 워크플로우이며, 공통 표현 규칙과 전송별 차이를 각각 검증한다.

## 4. 기록의 역할과 공통 규칙

| 소비자 | 기본 내용 | 상세로 보내는 내용 | 보존 원칙 |
|---|---|---|---|
| 사용자 진행 패널 | 현재 단계·대상·최근 확인·대기·종료 상태 | 문서 위치, 저장된 이유, 미확인 사항 | 사용자 권한을 통과한 요약만 송신 |
| 운영 요약 | 요청 시작/종료, 업무 단계 변경, 조사 측별 집계, 복구/중단, 장기 대기 | 개별 SQL·모델 시도·스키마·전체 도구 결과 | 상관 ID로 기존 원장/상세 파일 추적 |
| 진단·감사 | 원래 모델 입출력, receipt, 예산, 코드/데이터/상태 결속, 실패 이력 | 별도 상세 출력 또는 조회 | 기존 원본 유지, 접근 통제·인증값 정제 |

INFO를 단순히 WARNING으로 올리는 설정만으로 해결하지 않는다. 심각도와 노출 대상을 분리한다. 정상 원문 읽기의 모든 세부 이벤트가 운영 요약에 필요한 것은 아니며, 일부 자료 미확보는 실행 실패가 아니다. 반복되는 저수준 사건은 운영 요약에서 건수·첫/마지막 시각으로 묶되 새로운 원인, 복구 전환, 종료 상태는 즉시 남긴다. 상세 기록에서는 개별 시도·실패를 구별한다.

운영 요약의 형식은 `시각 | 요청 | 역할 | 업무 단계 | 상태 | 사실 | 다음 작업`으로 통일한다. 예시:

```text
14:20:01 | 요청 A | 전체 | 요청 확인 | 진행 | 비교 범위 확인 | 내규 조사
14:20:18 | 요청 A | 내규 | 원문 확인 | 전달 완료 | 허용 원문 확보 | 외규 조사
14:20:36 | 요청 A | 외규 | 원문 확인 | 대기 | Oracle 조회 응답 대기 | 응답 수신
14:21:05 | 요청 A | 대사 | 항목 검토 | 추가 조사 | 적용 예외 확인 필요 | 외규 재조사
14:22:10 | 요청 A | 전체 | 결과 정리 | 일부 미확인 | 결과 저장, 미확인 항목 포함 | 답변 전송
```

운영 요약에는 원문 전체·모델 view·전체 traceback을 반복 삽입하지 않는다. 기존 전체 오류 로그 요구는 진단 원장에서 유지하고, 후속 실패 정책의 “화면에는 이해 가능한 상태와 요청 식별자, 상세는 접근 통제된 원장” 원칙을 따른다. 원본 오류를 generic 문장으로 덮어쓰지 않는다.

## 5. 기존 이벤트를 연결하는 계약

신규 실행기나 LLM 로그 요약기를 만들지 않는다. 기존 journal/receipt를 읽는 `ProgressCapture`와 요청 보고서 투영을 확장해 화면·운영 요약이 같은 사실을 사용하게 한다. 아래 필드와 표현은 **제안**이며 현재 `rag-progress-v1`에 모두 존재하는 것이 아니다.

| 문맥 | 제안 연결 | 규칙 |
|---|---|---|
| 요청·실행 | `request_id`, `workflow_run_id`, `producer_run_id`, `parent_run_id`, `call_id` | 요청 상관 ID와 실제 사건 생산자를 분리한다. 재개의 새 전달 요청 ID와 기존 업무 실행 ID를 보존한다. |
| 역할·자료 | `actor_role`, `research_side`, `source_category` | 조사 담당과 실제 문서 분류를 분리한다. 부모는 내규/외규로 강제 분류하지 않는다. 모르면 미분류로 둔다. |
| 단계·순서 | `stage`, `stage_attempt`, `state_revision`, `journal_seq`, `projection_revision` | 서로 다른 자식의 seq를 비교하지 않는다. 도착 시각만으로 현재 단계를 역행시키지 않는다. |
| 사건·현재 상태 | `event_kind`, `execution_status`, `coverage_status`, `publication_status` | 실행 진행·내용의 미확인·답변 저장/전달을 별개로 관리한다. 기존 wire 상태값에 대한 명시적 매핑을 둔다. |
| 관측 시각 | `occurred_at`, `observed_at`, `last_progress_at`, `last_transport_at` | 원래 발생·수신·실제 진전·연결 확인을 구분한다. heartbeat로 진전 시각을 갱신하지 않는다. |
| 집계·설명 | `documents_read`, `sources_delivered`, `items_reviewed`, `items_total`, `reason_ref` | 숫자의 근거가 된 receipt와 중복 제거 기준을 둔다. 총량 미확정이면 퍼센트를 표시하지 않는다. |
| 진단 연결 | `binding_ref`, `failure_ref`, `journal_ref` | 원본 해시·원인·복구 담당·예산의 출처로 연결한다. 공개 이벤트에 내부 경로·비밀을 싣지 않는다. |

저널 사건의 중복 키는 검증된 생산자 실행 ID와 journal seq의 조합으로 둔다. 같은 사건이 여러 표현으로 투영되면 표현 종류를 추가한다. 저널에 없는 서비스 사건은 생성 지점에서 고유 사건 ID를 붙인다. 문서 집계는 문서 ID+버전, 원문 구간 집계는 문서 버전+위치/receipt로 구별하며 같은 문서명만으로 합치지 않는다.

`request_journals.children()`의 경로·권한·부모/자식 binding 검사를 통과한 문맥만 사용할 수 있다. 조사 측은 자식 등록에서, 문서 구분은 검증한 문서 메타데이터에서 가져온다. 두 값이 상충하면 표시 계층이 임의 재분류하지 않고 원인 기록과 기존 실행 무결성 처리를 따른다.

`public_event()` allowlist, SSE, `_ChatProgress`, `main_workflow`/직접 chat의 최종 표시, 요청 보고서가 함께 새 계약을 소비하도록 변경한다. 기존 v1 소비자는 명시적인 호환 투영을 사용하고 없는 역할을 추정하지 않는다. 화면은 늦은 사건을 상세 이력에 보존하되 더 최신 상태를 덮어쓰지 않는다. 단계 재방문은 현재 revision과 실제 재진입 근거가 있으면 정상 표시한다.

## 6. 정상·대기·부분 성공·실패 처리

| 상황 | 사용자에게 보일 상태 | 복구 담당과 경계 |
|---|---|---|
| 도구 성공 receipt 또는 checkpoint 추가 | 무엇을 확인했는지와 현재 단계 갱신 | 기존 실행부가 확정하고 표시기가 읽는다. 수신·스키마 통과만으로 조사 완료를 만들지 않는다. |
| 모델/Oracle 호출 중 응답 대기 | 현재 대기 대상, 대기 시간, 마지막 확인 시각 | 호출 담당 어댑터/gateway가 기존 예산으로 관리한다. UI는 재호출하지 않는다. |
| 연결 heartbeat만 계속됨 | 연결 확인과 작업 진행 미확인을 구분 | 시간 경과만으로 “정상 진행”이나 “실패”를 확정하지 않는다. 경고 문구는 기존 호출 timeout/deadline·관측 상태에 연결한다. |
| 일부 원문 확보, 의미 불확실 | 확보 사실과 미확인 항목을 함께 표시 | 비교·적용성은 기존 LLM 판단 담당. 불확실성만으로 읽은 원문 전달이나 비교를 차단하지 않는다. |
| 형식 오류 뒤 허용된 복구 | 복구 중 대상과 사유를 요약, 성공 시 현재 단계 복귀 | 기존 단계/gateway 중 해당 실패 담당 한 곳만 재시도. 한도·deadline·이력 유지. |
| 반복 오류·예산 소진 | 확인 범위의 제한 결과 또는 중단 사유 | 현재 종료 계약을 소비한다. 표시를 완료로 바꾸어 통과시키지 않는다. |
| 권한·해시·stale 상태 오류 | 해당 결과 제공 불가와 요청 식별자 | 기존 무결성 검사 담당. 모델 재작성이나 UI fallback으로 우회하지 않는다. |
| 진행 로그 읽기/화면 송신 실패 | 가능하면 진행 표시 지연/연결 끊김을 구분 | 표시 전송만 복구한다. RAG 재실행 금지. 업무 원장 쓰기 실패와 선택적 표시 실패를 구분한다. |
| 중단 후 재개·중복 요청 | 기존 확인 범위 유지, 실제 재개 위치 표시 | 업무 실행/잠금/중복 정책 담당은 기존 runtime이다. 예산·최초 deadline 유지. |
| 결과 준비 후 일부 답변 송신 실패 | 답변 전달 미완료 | 검증된 저장 결과와 송신 기록을 보존한다. 새 답변 이어 붙이기나 성공 등록 금지. |

완료 표시는 부모 결과·원문 검증·저장/발행 계약과 연결한다. `HTTP 200`, 자식 답변 완료, `emit` 성공, 진단 파일 저장 완료는 각각 부모 대사 성공이나 브라우저 표시 성공을 대신하지 않는다. 일부 미확인 결과는 실행이 정상 종료될 수 있으며 내용의 완전성과 구별한다.

도입은 다음 순서로 진행한다.

1. 부모/자식 출처 보존과 용어 사전을 먼저 연결한다. 내규·외규를 식별할 수 없는 상태에서 화면 묶기부터 하지 않는다.
2. 화면과 운영 요약에 공통 상태 투영을 연결한다. 설정은 기존 진행 UI/로그 수준과 독립인 표시 정책 revision 및 대상별 모드로 명시한다. 구체 환경변수 이름은 구현 시 정하며 기존 `GENOS_LOG_LEVEL`만 바꾸는 방식은 사용하지 않는다.
3. 고정 카드 갱신과 대기·추가 조사·종료 표시를 구현하고 모의 서비스/SSE/소켓 소비자로 검증한다. 데이터 로딩 없는 작은 fixture부터 순차 실행한다.
4. 기존 원장·원시 응답의 소비자를 확인한 뒤 신규 상세 보고서의 중복 본문을 참조 기반/필요 시 내보내기로 줄일 수 있는지 별도 적용한다. 첫 도입에서 완료된 로그나 실패 이력을 지우지 않는다. 서버에 새 영속 로그/지식 저장소를 만들지 않고 기존 허용된 외부 데이터·로그 계층을 사용한다.
5. 같은 코드와 pin으로 로컬 실제 서비스 진입점을 확인한다. 사용자에게 구현·MAIN 반영까지 요청받은 경우 저장소 승격 절차를 거쳐 선택 포인터와 실행 binding까지 확인한다. 이번 계획 작성은 승격 절차 실행이 아니다.
6. GENOS 인계 때 코드와 전체 워크플로우 편집기본을 함께 결속한다. 반입·commit/push·리비전·편집기 저장·워크플로우 테스트 화면 확인을 따로 기록한다. 카드 교체와 실제 내부 모델 대기 표시는 현장 확인 전 완료로 보지 않는다.

원문·용어·색인의 재구축은 필요하지 않다는 설계다. 새 표시 계약은 버전으로 구분하고 기존 journal은 읽기 호환으로 지원한다. 롤백은 검증한 이전 코드·표시 정책·편집기본으로 함께 되돌리며, 새 원장/실패 이력을 삭제하지 않는다. 활성 실행을 서로 다른 binding 코드로 강제 재개하지 않는다.

## 8. 검증 기준과 자원

기존 `test_workflow_progress_logging.py`, `test_workflow_progress_api.py`, `test_genos_chat_progress.py`, `test_main_workflow_display.py`, `test_genos_request_report.py` 등에서 필요한 검사를 확장한다. 이 문서는 검사를 실행한 결과가 아니다.

| 검사 시나리오 | 통과 조건 |
|---|---|
| 부모+내규+외규, 같은 제목의 문서 | 역할·자료 구분·생산자 보존, 다른 측 집계와 혼합 없음 |
| 원문 후보/읽기/전달/채택 | 서로 다른 상태를 같은 완료 수치로 세지 않음 |
| 많은 원문 활동·지연·중복 수신 | 기본 단계 슬롯 증가 없음, 최신 상태 유지, 중요 종료 누락 없음 |
| 실제 추가 조사와 늦은 이전 사건 | 재조사는 현재 상태로 반영, 늦은 사건은 상세만 보완 |
| heartbeat만 반복/모델 대기/Oracle 대기 | 연결 유지와 진전 구별, 근거 없는 정상·실패 판정 없음 |
| 정상/복구 성공/반복 실패/예산 종료 | 기존 호출 수·예산·결과·실패 원인 보존, 정확한 사용자 상태 |
| 재개/중복 요청/stale/권한·해시 변경 | 재실행·중복 카드·권한 밖 자료 노출 없음, 실패 경계 유지 |
| SSE 큐 포화/표시 연결 끊김/원장 읽기 실패 | 최신 요약 합치기, 실패·최종 result 보존, 표시 오류 때문에 모델 재호출 없음 |
| 답변 조각 이후 송신 실패 | 저장/송신/사용자 표시 상태 구별, 미완료 성공 등록 없음 |
| 실제 서비스·분리 편집기·직접 chat | 같은 코드/pin의 API와 소비자 상태 일치. 모의 emit 성공과 현장 렌더 성공 구별 |

원문이나 인덱스를 새로 적재하지 않고 작은 합성 journal로 시작한다. 실제 데이터가 필요한 서비스 검사는 무거운 프로세스 하나씩 실행한다. 이번 읽기 시작 시 관측한 가용 RAM은 약 12 GiB, 디스크 여유는 약 228 GiB이며 swap이 이미 사용 중이었다. 다음 구현의 무거운 검사 직전에 다시 확인하고 RAM/swap 압박 시 범위를 줄인다. 전체 journal을 매번 다시 읽는 방식 대신 생산자별 cursor·작은 배치와 제한된 현재 상태를 유지한다.

### 수치·효과의 해석

| ID | 종류·지표 | 기준·산식·한계 |
|---|---|---|
| P1 | 목표: 기본 단계 슬롯 5개/요청 | 기존 요약 경험과 대사 흐름을 매핑한 UI 목표. 중요 오류 안내를 삭제하는 제한이 아님. 현장 카드 갱신 지원 확인 필요. |
| P2 | 제안: 비핵심 집계 갱신 간격 5초 | 같은 요청의 문서 이벤트를 묶는 초기 설정. 단계/실패/종료 전환은 즉시. 실제 체감은 미측정. |
| P3 | 제안: 변화 없는 대기 표시 갱신 간격 30초 | 화면/운영 요약의 반복 억제 기준. 전송 heartbeat·모델 timeout·실행 예산과 무관. |
| C1 | 계산: 카드 누적 배열 송신량의 구조 | N개의 카드를 하나씩 추가해 전체 배열을 보내면 카드 항목 전송 수는 N(N+1)/2. K개 고정 슬롯을 U회 갱신하면 최대 K×U. 항목 크기·기타 송신은 별도이며 실제 바이트나 시간 절감률이 아님. |
| M1 | 미확인: 실제 절감률·지연·구현 일정 | 현장 요청별 카드 수·요약/원시 로그 바이트·송신 횟수·writer 시간·최대 RSS를 측정해야 함. 현재 근거로 백분율이나 인일을 제시하지 않음. |

기본 화면의 양은 줄일 수 있어도 상세 원장을 전부 유지하면 전체 저장량은 같은 폭으로 줄지 않는다. 새 운영 요약을 추가하는 동안 저장량이 약간 늘 수 있다. 카드 갱신을 지나치게 자주 하면 C1의 이점이 사라지며, 원장 원문을 요약 파일에 다시 복사하면 비용이 증가한다. 따라서 첫 목표는 읽기 쉬운 진행 표시와 출처 구분이며, 성능·용량 효과는 별도로 측정한다.
