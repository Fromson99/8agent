## 1. 요약

본 보고서는 다음 두 기능의 구현 가능성과 설계를 검토한다.

1. **사용 중 발견한 표현을 용어 자산으로 축적:** 사용자가 정식 용어를 모르고 질문하더라도, 표현과 문맥을 기존 개념에 연결하고 새로운 용어·별칭·검색 표현 후보를 수집한다.
2. **검증된 탐색 절차 재사용:** 유사한 질문이 들어오면 적용 조건을 확인한 뒤 동일한 필수 확인 순서와 분기 규칙을 실행한다.

두 기능 모두 시스템적으로 구현 가능하다. 현재 시스템에는 등록 용어·출처별 정의·관계·원문 연결·명시 참조·실행 기록이 있어 이를 재사용할 수 있다. 추가 개발의 중심은 사용자 표현의 의미 연결, 절차의 적용 조건과 실행 제어, 후보의 검토·검증·새 버전 반영이다.

권고하는 첫 범위는 **자료가 충분한 업무 한 종류에 대해 표현 연결과 소수의 검토된 탐색 절차를 구현하는 것**이다. 사용 기록에서 절차를 자동 추출하는 기능은 초기 절차 실행의 효과를 확인한 뒤 도입한다.

현재 지식그래프를 완성된 도메인 온톨로지나 법률 자동 판단 체계로 간주하지 않는다. 필요한 범위에서 개념 식별, 관계의 의미·방향, 적용 범위와 검토 기준을 명시한다. 폐기된 법률 조건·효과 재작성 스키마를 복원하는 제안이 아니다.

## 2. 배경과 목표

### 2.1 해결하려는 문제

등록된 용어를 아는 사용자는 적절한 검색 시작점을 제시할 수 있지만, 실제 사용자는 줄임말·현업 표현·자연어 문장으로 질문한다. 등록 표기와 질문의 차이 때문에 관련 개념에 도달하지 못하거나, 같은 업무를 표현만 바꾸어 질문했을 때 탐색 경로가 달라질 수 있다.

또한 한 번 검토한 탐색 과정을 다음 요청에서 활용하지 않으면 반복적으로 같은 정의·문서·참조를 찾아야 한다. 반대로 과거 행동을 그대로 복사하면 상품·당사자·시점·규정이 달라졌을 때 잘못된 경로를 반복할 수 있다.

### 2.2 목표 동작

| 목표 | 기대 동작 |
|---|---|
| 표현 차이 흡수 | 다른 표현으로 제시된 같은 업무를 적절한 등록 개념 후보로 연결 |
| 의미 구분 | 같은 표기라도 출처·상품·업무 범위가 다르면 다른 의미로 유지 |
| 탐색 일관성 | 같은 조건의 질문은 같은 필수 확인 순서와 분기 규칙을 사용 |
| 예외 대응 | 절차 밖 쟁점이나 근거 부족이 드러나면 추가 탐색·질문으로 전환 |
| 지식 갱신 | 사용 기록을 근거 있는 수정 후보로 만들고 검증 후 새 버전으로 반영 |
| 재현과 감사 | 사용한 용어집·원문·절차·코드·모델 설정과 실제 행동을 추적 |

여기서 ‘같은 경로’는 모든 질문이 동일한 원문과 결론에 도달한다는 뜻이 아니다. **확인할 항목과 진행 규칙을 재사용하면서 실제 원문 선택과 판단은 해당 질문에 맞게 수행한다**는 뜻이다.

### 2.3 이번 제안에 포함하지 않는 사항

- 사용자 피드백이나 모델 출력을 검증 없이 정본에 자동 반영하는 기능.
- 과거 답변을 새로운 질문의 정답이나 원문 근거로 사용하는 기능.
- 금융·법률 전 영역의 개념을 일괄 통합하거나 법적 결론을 논리 규칙으로 자동 확정하는 기능.
- 별도 그래프 데이터베이스 도입을 선행 조건으로 삼는 전면 재구축.

## 3. 현재 구현 상태와 활용 자산

### 3.1 전체 MAIN과 로컬 선택 상태

MAIN은 공통 용어집을 기반으로 문서 입력·구조화, 문서–용어 연결, 탐색 색인, RAG, 피드백으로 이어지는 전체 흐름이다. 로컬 활성 릴리스는 이 중 서빙 부분이다. [내부 근거 I1](#내부-근거)

작성 시 확인한 로컬 활성 포인터는 `navigation-rag-20260916-v1`, 포인터 generation은 `14`다. 릴리스 품질 인증은 `false`이며, GENOS 현장 배포·내부 모델 실행 성공을 의미하지 않는다. [내부 근거 I2](#내부-근거)

서빙은 `service.py`에서 선택한 릴리스 코드·데이터를 검증하고 사용한다. 작업 코드 수정만으로 활성 릴리스가 바뀌지 않는다. 현재 작업 트리에는 후속 구축·연결 변경도 있으므로, 아래의 ‘선택 릴리스’와 ‘작업 코드’를 구분한다.

### 3.2 구성 요소별 상태

| 구성 요소 | 확인한 상태 | 확장에 활용하는 방식 |
|---|---|---|
| 질문의 표기·구조 역매칭 | 로컬 선택 릴리스에 연결 | 기본 시작점 탐색 유지 |
| 출처별 용어·정의 조회 | 로컬 선택 릴리스에 연결 | 표현 의미 후보 비교 |
| 등록 관계 탐색 | 로컬 선택 릴리스에서 최대 3홉 조회 | 관련 개념 탐색 |
| 용어–원문 출현 연결 | 선택 색인에 존재 | 개념에서 실제 근거로 이동 |
| 구조·명시 참조 조회 | 연결되어 있으나 미해결 참조 존재 | 원문 위치·참조 근거 확인 |
| 원문 읽기·채택·제외·보류 | 로컬 선택 릴리스에 연결 | 질문별 판단과 행동 기록 |
| 실행 기록 | 경로·읽은 원문·판단·모델 호출 기록 저장 | 후보 생성 및 절차 분석 입력 |
| 피드백 | 실행·원문 세대에 연결된 `PROPOSED` 후보 저장 | 검토 워크플로의 출발점 |
| 새 문서 정의의 용어집 초안 추가 | 작업 코드에서 확인 | 근거가 확보된 신규 용어의 검토 경로 재사용 |
| 사용자 표현의 의미 연결·영구 반영 | 별도 연결 필요 | 본 제안의 신규 기능 |
| 질문 유형별 탐색 절차 선택·실행 | 별도 연결 필요 | 본 제안의 신규 기능 |

선택 릴리스의 역매칭은 질문과 등록 표기를 정규화해 대조하는 방식이 중심이다. 임의의 자연어 표현을 문맥에 맞는 법률·금융 개념으로 연결하는 전용 의미 연결 기능과는 구분해야 한다. [내부 근거 I3](#내부-근거)

독립 검토에서 확인한 추가 차이는 다음과 같다. 이 차이는 정적 코드 대조 결과이며 실제 누출이나 GENOS 현장 실패를 관측했다는 뜻은 아니다.

| 지점 | 선택 릴리스 | 작업 코드·설계상의 주의 |
|---|---|---|
| `NavigationSession.term_card/graph/references` | 작업 코드에 추가된 일부 문서 범위 검사가 없음 | 작업 코드에는 `scope_document_id` 검사와 참조의 `document_id` 필터가 추가됨. 내부 용어를 도입하기 전 양쪽 차이를 검토하고 범위 회귀 검증 필요 |
| `glossary_assets()` | 설정의 glossary 결속을 사용 | 작업 코드는 세대 manifest의 glossary를 우선함. 어느 코드를 새 후보의 기준으로 사용할지 고정 필요 |
| 추가 질문 | 매 요청 새 세션, `question_for_user`는 빈 값으로 설정 | 대화 재개와 사실 확인은 새 상태·API·화면 계약이 필요 |
| 실행 파일 | 전체 파이프라인 성공 후 최종 경로에 직접 작성 | 원자적 완료·실패 실행 원장·후속 작업의 입력 준비 상태는 신규 구현 필요 |

첫 후보는 활성 릴리스의 코드·데이터를 정확히 부모로 고정하되, 위 작업 코드 변경 중 필요한 항목의 채택·제외를 명시해야 한다. 작업 트리 전체를 근거 없이 한 번에 신규 기능의 기준으로 삼지 않는다.

### 3.4 기존 설계와의 관계

기존 다기관 용어집 설계에는 표현·출처별 의미·근거를 분리하고 일상표현을 연결한다는 방향이 이미 있다. 본 제안은 이를 사용 중 발생하는 관측과 검토된 탐색 절차까지 확장한다.

다만 기존 문서의 구 `LEGAL_SCHEMA` 연결 설명은 작성 당시의 이력이다. 신규 계약은 현행 `DATA_MODEL.md`, `term-runtime-v1`, `GLOSSARY_SCHEMA.json`을 기준으로 설계해야 한다. [내부 근거 I5](#내부-근거)

## 4. 외부 사례와 적용 가능성

| 사례 | 확인한 기능 | 본 제안에 주는 근거 | 적용상의 한계 |
|---|---|---|---|
| LSEG Intelligent Tagging | 문서의 개체·관계 추출, 서로 다른 표현의 동일 대상 식별, 고유 ID 연결 | 표현과 등록 대상의 연결을 실제 금융 정보 서비스에서 사용 | 사용자 대화에서 신규 법률 개념을 승인하는 사례는 아님 |
| UBS 데이터 지식그래프 | 데이터셋·속성·소비자·배포 경로의 관계 관리 | 금융권에서 연결 구조를 조회와 데이터 운영에 활용 | 법률 질의응답이나 자동 절차 학습 사례는 아님 |
| Microsoft GraphRAG | 그래프의 개체·관계와 원문 조각을 결합한 검색 | 그래프를 통해 원문 근거를 회수하는 공개 구현 | GraphRAG 자체가 질문별 절차 재사용을 보장하지 않음 |
| Agent Workflow Memory | 과거 작업에서 반복 가능한 절차를 추출해 후속 작업에 제공 | 실행 경험을 절차로 일반화·재사용하는 연구 근거 | 웹 작업 벤치마크 결과이며 금융·법률 판단의 정확성 검증은 아님 |

LSEG는 표현 위치·문맥·고유 ID와 동일 대상 해소 과정을 공식 문서에 설명한다. [E1](https://developers.lseg.com/en/api-catalog/open-perm-id/intelligent-tagging-restful-api/quick-start/how-does-intelligent-tagging-work-)

UBS 사례는 구축 담당자의 발표이며, 그래프로 데이터 관계를 관리하고 조회하는 실제 구현 사례다. [E2](https://neo4j.com/blog/financial-services/creating-a-data-distribution-knowledge-base-using-neo4j/)

Microsoft GraphRAG의 local search는 지식그래프와 원문을 결합한다. [E3](https://microsoft.github.io/graphrag/query/local_search/)

Agent Workflow Memory는 경험에서 절차를 유도해 재사용하는 효과를 보고했다. 본 보고서는 해당 성능 수치를 우리 시스템의 기대 성능으로 전용하지 않는다. [E4](https://arxiv.org/abs/2409.07429)

**검토 판단:** 구성 기술의 구현 가능성에는 근거가 있다. 그러나 공개 사례만으로 본 제안 전체의 금융·법률 업무 품질이 검증됐다고 볼 수 없다. 효과와 허용 회귀는 우리 데이터·모델·업무 범위에서 확인해야 한다.

## 5. 목표 구조와 설계 원칙

### 5.1 질문 처리와 지식 갱신

```text
[질문 처리]
질문 + 허용 문서 범위 + 선택 세대
  → 기존 역매칭 + 검토된 표현 연결
  → 필요한 경우 의미 후보 검색·비교
  → 탐색 절차 후보 조회·적용 조건 확인
  → 절차 실행 또는 기존 탐색
  → 원문 확인·질문별 판단·답변
  → 실행 기록 저장

[지식 갱신]
실행 기록 + 사용자 수정 + 읽은 원문
  → 표현·용어·절차 후보 추출
  → 중복·의미·범위·근거 검토
  → 계약·회귀·효과 검증
  → 새 용어집·색인·절차 묶음 생성
  → 명시적 활성화
  → 이후 질문에서 사용
```

현재 질문에서 얻은 후보를 같은 실행의 승인된 입력으로 소급 반영하지 않는다. 질문별 임시 해석은 기록할 수 있지만, 지속 사용을 위한 승인은 별도다.

### 5.2 설계 원칙

1. **표현과 개념 구분:** 새로운 표현이 반드시 새로운 개념은 아니다.
2. **출처별 의미 보존:** 동일 표기의 정의를 기관·문서·버전 차이 없이 통합하지 않는다.
3. **검색 연결과 의미 관계 구분:** 어떤 용어를 찾아볼 필요가 있다는 사실이 동의어·상하위 관계를 뜻하지 않는다.
4. **절차와 결론 구분:** 확인 순서와 분기는 재사용하되, 근거와 판단은 요청별로 확인한다.
5. **모델 제안과 코드 검증 결합:** 모델은 후보·판단을 제안하고, 코드는 ID·범위·스키마·필수 단계·원문 좌표를 검증한다.
6. **명시적 미확인 상태:** 정보 부재나 모호함을 임의 추론으로 채우지 않는다.
7. **불변 세대와 이력:** 수정은 새 버전으로 남기고 활성화·롤백을 추적한다.

### 5.3 모델과 코드의 책임

| 모델에 맡길 작업 | 코드가 통제할 작업 |
|---|---|
| 중요한 표현·질문 쟁점 후보 추출 | 질문 span과 실제 문자열의 일치 |
| 주어진 정의 후보의 문맥 적합성 비교 | 등록 ID 존재·조회 범위·버전 검증 |
| 읽은 원문의 관련성·적용 가능성 검토 | 원문 읽기 여부·인용 위치·해시 검사 |
| 절차 후보와 분기 제안 | 허용 행동·필수 단계·예산·종료 조건 |
| 실행 기록의 절차 일반화 | 후보 상태·검토 이력·배포 결속 |

코드가 정확한 인용문 존재를 확인해도 그 인용이 법적 결론을 충분히 뒷받침하는지는 별도 검토 대상이다. 모델이 출력한 확신도 역시 검증된 오류 확률로 간주하지 않는다.

## 6. 데이터 계약 제안

아래 객체·필드는 설계안이다. 현행 스키마에 이미 존재하거나 구현되었다는 뜻이 아니다.

### 6.1 공통 객체

| 객체 | 필수 정보 | 소비자 |
|---|---|---|
| `ExpressionObservation` | 관측 ID, 표현·위치, 실행 ID·해시, 문맥, 발견 계기, 접근 범위 | 후보 검토 |
| `ExpressionMapping` | 표현, 대상 용어·의미 ID, 연결 종류, 적용 조건, 근거, 상태·버전 | 질문 시작점 연결 |
| `TermProposal` | 새 표제어, 출처별 정의, 기존 후보 비교, 문서·버전·범위, 검토 상태 | 기존 용어집 구축·검토 |
| `NavigationRecipe` | 절차 ID·버전, 적용 조건, 필수 정보, 단계·분기·종료 조건, 의존성 | 절차 선택기·실행기 |
| `RecipeExecution` | 실행 ID, 절차 버전, 조건 판정, 실제 단계·근거, 이탈 이유 | 관측·품질 검토 |
| `ReviewEvent` | 검토 대상, 이전·이후 상태, 검토 주체, 근거, 시각 | 감사·철회·재개 |
| `DependencyBinding` | 대상 객체와 용어·원문·절차 버전의 의존 관계 | 변경 영향 분석 |

### 6.2 표현 연결 종류

| 종류 | 의미 | 예시 |
|---|---|---|
| 검토된 별칭 | 정해진 범위에서 같은 개념을 지칭 | 부서 약어와 해당 업무 명칭 |
| 검색 연결 | 해당 개념을 확인할 필요가 있음 | 계약 만료 후 거래 지속 → 갱신 관련 개념 후보 |
| 문맥 의존 연결 | 상품·업무 조건에 따라 대상이 달라짐 | 돈을 중간에 뺀다 → 상품에 따른 중도해지·환매·매도 후보 |

질문용 검색 표현을 원문 출현 색인에 그대로 추가하지 않는다. 사용자가 특정 표현을 사용한 사실과 원문에 그 표현이 등장한 사실은 다른 증거다.

### 6.3 관계의 의미와 제약

별칭·동일 의미·상하위·관련·업무상 확인 관계를 각각 정의한다. 관계마다 방향, 적용 범위, 근거, 허용되는 탐색 용도를 명시한다. `관련` 관계를 추이적으로 연결해 동일성이나 적용 가능성을 도출하지 않는다.

한 의미가 여러 개로 분리되거나 합쳐질 때는 이전 ID와 새 ID의 대응·이유·시점을 기록한다. 이름이나 표제어 해시만으로 동일성을 판단하지 않는다. 순환 검사는 관계별로 적용하며, 모든 관계의 순환을 일괄 오류로 취급하지 않는다.

### 6.4 상태와 배포 분리

```text
관측 → 검토 대기 → 승인 / 보류 / 기각
승인 → 검증 대기 → 배포 가능 / 재검토
배포 가능 → 새 묶음 포함 → 활성화
문제 발견 → 철회 또는 대체 버전 발행
```

모델 검토 완료, 의미 승인, 검증 통과, 서빙 활성화는 서로 다른 상태다. 사용자 피드백은 발견·수정 근거가 될 수 있지만 법적 정의의 승인 자체를 대신하지 않는다.

## 7. 기능 1 — 사용 중 용어·표현 발견과 반영

### 7.1 단계별 실행

| 단계 | 입력 | 처리 | 출력·다음 소비자 |
|---|---|---|---|
| 관측 | 질문·사용자 수정·읽은 원문 | 기존 매칭과 비교해 의미 있는 미연결 표현 발견 | 관측 기록 → 후보 검색 |
| 후보 검색 | 표현·문맥·허용 범위 | 검토된 표현, 표제어·별칭, 정의 설명 순으로 조회 | 실제 등록 ID 목록 → 의미 비교 |
| 의미 비교 | 후보 정의·출처·문맥 | 동일 표현, 다른 의미, 범위 차이, 정보 부족 구분 | 임시 연결 또는 보류 → 현재 탐색 |
| 후보 축적 | 실행 결과·원문 근거 | 별칭·검색 표현·새 용어·불명확 표현 분류 | 검토 후보 → 검토자·검토 모듈 |
| 반영 준비 | 승인 후보 | 새 초안과 필요한 색인 생성 | 새 묶음 → 검증·활성화 |

### 7.2 후보 검색 전략

초기에는 현재 역매칭을 유지하고 승인된 표현 연결을 병행한다. 이 단계만으로 해결되지 않는 질문에 한해 정의·설명문 검색과 의미 비교를 후보로 검토한다. 모든 질문의 시작을 모델 생성 키워드로 대체하지 않는다.

이 구분은 기존에 초기 모델 표현 추출을 제거하고 전체 질문 역매칭으로 변경한 이력이 있기 때문이다. 온라인 의미 연결의 추가 효과·지연·누락은 별도 후보로 검증해야 하며, 과거 경로를 암묵적으로 복원하지 않는다. [내부 근거 I6](#내부-근거)

의미 검색을 도입할 경우 임베딩 모델·버전·전처리·색인 세대를 결속한다. 첫 구현의 필수 요건은 아니며, 외부와 GENOS에서 같은 모델을 사용할 수 있다고 가정하지 않는다.

### 7.3 기존 검토 경로와 연결

현재 용어집 검토는 출처 정의 쌍을 비교하는 계약을 갖는다. 사용자 표현에는 정의가 없을 수 있으므로 표현 연결 검토를 별도 계약으로 만들고, 근거가 확보된 신규 정의를 기존 검토 입력으로 넘긴다.

검색 결과가 없다는 이유만으로 새 용어를 생성하지 않는다. 기존 의미 후보 검색 실패, 실제 신규 개념, 사용자만의 표현, 문맥 부족을 구분한다. 근거가 부족한 후보는 보류한다.

### 7.4 재구축 범위

| 변경 | 필요한 후속 처리 |
|---|---|
| 질문용 표현 연결 추가 | 표현 연결 색인·절차 매칭 회귀 검사 |
| 원문 인식용 별칭·새 용어 추가 | 문서 출현 연결·탐색 색인 재구축 |
| 정의·의미 연결 변경 | 관련 의미 후보·색인·절차 재검증 |
| 관계 추가·수정 | 관계 계약 검사·영향받는 탐색과 절차 재검증 |

원문 파싱 결과가 달라지지 않는 변경만으로 모든 문서를 재구조화할 필요는 없다. 재사용할 산출물과 새로 만들 산출물의 입력 지문을 명시해야 한다.

## 8. 기능 2 — 탐색 절차 선택과 실행

### 8.1 절차의 구성

탐색 절차에는 목적, 적용 조건, 필요한 사실, 시작 개념, 필수 확인 항목, 단계별 행동, 분기·추가 탐색 조건, 종료 조건과 검증 이력을 둔다. 범용 코드나 자유 텍스트 지시를 실행하는 대신 허용된 탐색 도구와 선언된 조건으로 표현한다.

```text
절차 예시: 금융상품의 만기 전 현금화 검토

필수 사실: 상품 유형, 구체적인 상품·계약, 기준 시점
시작점: 상품 유형에 맞는 등록 용어 후보
확인 순서:
  1. 해당 행위의 정의 확인
  2. 상품 문서와 관련 원문 확인
  3. 비용·가격 결정 방식 확인
  4. 지급 시점과 제한 확인
분기:
  상품 유형 미확인 → 공통 확인 또는 사용자 질문
  대상 문서·버전 미확인 → 미확인 상태 유지
  추가 쟁점 발견 → 기존 탐색 도구로 확대
종료:
  필수 쟁점의 근거 확인 또는 미해결 사유 명시
```

이 예시는 법적 의무나 상품별 실제 비용을 확정하는 규칙이 아니다.

### 8.2 선택·실행 순서

1. 질문 의도·등록 용어·업무 대상·문서 범위로 절차 후보를 조회한다.
2. 필수 조건을 `일치 / 불일치 / 미확인`으로 평가한다.
3. 불일치 절차는 제외하고, 핵심 조건 미확인 시 공통 단계 또는 추가 질문으로 진행한다.
4. 현재 데이터 세대와 절차의 의존성이 호환되는지 확인한다.
5. 실제 등록 ID를 조회 범위 안에서 해소해 세션 시작점으로 등록한다.
6. 필수 확인 순서를 코드가 관리하고 모델이 원문 관련성·추가 탐색을 제안한다.
7. 조건 변경·새 쟁점·근거 부족 시 분기하고 이탈 이유를 기록한다.
8. 질문 전체의 미해결 항목을 확인한 뒤 답변 또는 미완료 상태로 종료한다.

절차 후보가 여럿이면 적용 조건으로 구분한다. 복합 질문은 쟁점별 적용이 가능하되, 첫 버전에서는 임의의 자동 절차 조합을 제한하고 해결되지 않는 부분을 기존 탐색으로 넘긴다.

### 8.3 현재 루프와의 결합

`OPEN_TERM`, `GRAPH`, `LIST`, `READ`, `REFERENCES`, `JUDGE`를 재사용한다. 절차 실행기는 다음에 가능한 행동과 필수 확인 사항을 관리한다. 프롬프트에 과거 행동을 넣는 것만으로 순서 준수를 보장하지 않는다.

현재 세션은 발견된 ID와 읽은 구간을 검사한다. 절차에 저장된 ID도 존재·범위 검증 없이 이 제한을 우회할 수 없다. 세션별 `T1`, `A3` 같은 별칭 대신 영구 등록 ID·조회 조건·원문 버전 결속을 저장한다.

질문에서 명시한 조문이나 독립적인 기존 매칭 결과를 절차가 임의로 제거하지 않는다. 추가 탐색도 전체 호출·행동·문맥·시간 예산 안에서 관리한다.

### 8.4 경험에서 절차를 만드는 후속 기능

```text
검토한 실행 기록
  → 업무·질문 유형과 적용 조건별 묶기
  → 필수 확인 단계·실패·우회·누락 분석
  → 개별 상품·문서·값을 매개변수로 일반화
  → 적용 조건·분기를 갖는 절차 후보
  → 사람이 검토
  → 별도 질문으로 검증
```

성공한 실행 한 건을 곧바로 표준 절차로 승격하지 않는다. 좋은 평가를 받은 답변에도 누락이 있을 수 있다. 과거에 제외한 원문은 다음 질문에서 필요할 수 있으므로 채택·제외 판단은 영구 규칙으로 복사하지 않는다.

## 9. 금융·법률 적용 예시

아래는 시스템 동작 설명을 위한 가상 사례이며 실제 규정 적용이나 법률 결론이 아니다.

### 9.1 계약 종료 후 거래 지속

- **질문:** “계약은 끝났는데 계속 납품하고 돈도 받았어요. 이전 계약이 적용되나요?”
- **표현 연결:** 계약 종료 후 거래 지속 → 갱신·자동연장·종료 후 이행 등의 검토 후보.
- **절차:** 계약 종류·기간 → 계약 조항 → 통지와 실제 행위 → 관련 원문 → 유지 여부와 범위 검토.
- **재사용:** “만료 뒤에도 거래처가 계속 발주해요”는 같은 절차 후보로 연결한다.
- **분기:** 계약 종류나 종료 통지 여부가 다르면 확인 경로가 달라진다.
- **금지할 자동화:** 거래가 지속됐다는 이유만으로 갱신을 확정하지 않는다.

### 9.2 금융상품의 만기 전 현금화

- **질문:** “만기 전에 돈을 빼면 얼마나 손해인가요?”
- **표현 연결:** 상품 유형을 확인한 뒤 중도해지·환매·만기 전 매도 등으로 분기.
- **절차:** 상품 → 행위 정의 → 약관·설명서 → 비용·가격 결정 → 지급 시점·제한.
- **재사용:** “중간에 현금화하면 얼마 받나요?”도 같은 공통 확인 단계로 연결한다.
- **금지할 자동화:** ‘돈을 뺀다’를 모든 상품에서 하나의 정식 용어와 동일하게 등록하지 않는다.

### 9.3 외부 AI를 이용한 상담 후처리

- **질문:** “고객 상담 내용을 외부 AI로 요약해도 되나요?”
- **표현 연결:** 상담 후처리, 정보 유형, 외부 처리·저장 관련 개념 후보.
- **절차:** 정보 종류 → 처리 주체·위치 → 저장·재사용 조건 → 법령·계약·내규 → 필요한 절차와 미확인 사항.
- **사용 중 갱신:** 담당자가 알려준 부서 용어를 관측하고 내부 정의와 대조해 검색 표현 후보로 등록한다.
- **분기:** 고객 정보 유무·처리 조건·업무 범위가 달라지면 해당 경로를 조정한다.
- **환경:** 실제 상담 내용과 내부 검토는 GENOS에서 처리한다.

## 10. 코드·API·운영 연결 설계

### 10.1 변경 책임

| 기존 연결 지점 | 제안 변경 | 영향·주의 |
|---|---|---|
| `navigation_match.py` | 검토된 표현 조회와 필요 시 의미 후보 검색을 연결 | 기존 질문 전체 역매칭 유지·비교 검증 |
| `navigation_agent.py` | 표현·절차 묶음의 버전·해시 검증 및 세션 전달 | 현재 세대와 호환되지 않으면 해당 기능 사용 차단 |
| `navigation_loop.py` | 절차 상태·분기·필수 항목·종료 검사 | 현재 도구의 ID·원문 검증 유지 |
| `feedback.py`와 후속 후보 처리 | 유형화된 관측·후보·검토 이벤트 | 기존 실행·원문 해시 연결 보존 |
| 용어집 구축·검토 모듈 | 표현 검토 계약과 승인 후보의 새 초안 반영 | 정의 비교 계약에 사용자 표현을 억지로 입력하지 않음 |
| `PIPELINE.json`·스키마·릴리스 | 새 설정·산출물·소비자·버전 결속 | 코드만 수정하고 활성화됐다고 보고하지 않음 |
| API·사용자 화면 | 해석 수정·추가 정보 응답·검토 기능 | 내부 구현 용어를 일반 사용자에게 요구하지 않음 |
| `genos_rag_chat.py → service.py._normalize → app.ask` | 전송 envelope와 질문 body 분리, 신뢰할 수 있는 사용자 주체 전달, 후속 응답 표시 | 현재 브릿지가 보내는 추가 필드를 질문 API가 거절하는 정적 계약 불일치부터 해결 |
| `contracts.write`·실행 기록 저장 | 임시 기록·원자적 확정 또는 트랜잭션 원장, 완료 해시 | 완료된 파일만 후보 처리 입력으로 소비 |

새 Python 모듈은 책임에 따라 분리할 수 있으나 진입점은 기존 질문 API와 `pipeline.py glossary` 흐름에 연결한다. 독립 실행기·별도 기본 검색 경로를 늘리지 않는다. 구체적인 CLI 하위 명령 이름은 구현 시 확정한다.

### 10.2 API와 대화 재개

현재 `/v1/rag/ask`는 질문·문서 범위·모델 사용 여부를 중심으로 엄격히 입력을 검사한다. `/v1/rag/feedback`은 실행 ID와 평가·사유를 받는다. 임의의 필드를 추가하는 것만으로 새 기능이 연결되지 않는다. [내부 근거 I7](#내부-근거)

후속 질문에는 이전 실행 ID, 구조화된 추가 사실·수정 내용을 받는 계약을 검토한다. 서버는 이전 실행과 사용 권한을 확인하고, 사실마다 사용자 진술·원문 확인·모델 추정을 구분한다. 이전 답변 전체를 확인된 사실로 재사용하지 않는다.

초기 설계는 **확인된 사실을 연결한 새 실행을 시작하는 방식**으로 한다. 중단된 Python 세션 객체나 과거의 원문 채택 상태를 직렬화해 그대로 복원하지 않는다. 제안 입력은 `parent_run_id`, `confirmed_facts`, 요청 멱등성 키이며, 허용 필드·자료형·사실 키를 스키마로 정한다. 인증된 주체는 서버의 신뢰 가능한 컨텍스트에서 전달한다.

기존 실행과 후속 실행에는 부모 ID, 원문·용어집·절차 버전, 사실별 출처·확인 상태를 남긴다. 세대나 권한이 달라졌으면 재검증하고, 이전 실행을 조회할 권한이 없으면 연결을 거부한다. 응답에는 `WAITING_FOR_FACTS`에 해당하는 명시적 상태와 필요한 사실·질문을 표현하는 새 계약이 필요하다.

현재 작업 코드의 브릿지는 `channel/session_id/user_id/request_id`를 보내고 `service.py._normalize()`는 이를 질문 body에 전달하지만, `app.ask()`는 해당 추가 필드를 허용하지 않는다. 따라서 브릿지→전송 envelope→정규화→질문 API→응답 표시를 함께 수정·검증해야 한다. 현장에 설치된 리비전의 실패 여부는 이 정적 대조만으로 단정하지 않는다.

현행 응답의 `term_agent`는 객체 확장을 수용하지만 무정형 데이터만 늘리지 않는다. 표현 연결·절차 실행의 내부 스키마를 명시하고 소비자가 검증하도록 한다. 공개 요청·응답 변경에는 버전·호환성·이행 검사가 필요하다.

### 10.3 비동기 후보 처리와 저장

답변 실행 기록을 영속 저장한 후 후보 추출 작업을 처리한다. 초기에는 기존 기록을 읽는 재개 가능한 배치로 시작하고, 필요하면 지속 작업자로 확장한다. 별도 메시지 브로커가 첫 구현의 필수 요건은 아니다.

- 실행 ID·추출기 버전·후보 내용을 이용해 재처리 중복을 방지한다.
- 여러 사용자의 동일 표현 관측은 보존하고 검토 후보를 묶는다.
- 작업 상태·실패 원인·재개 지점을 남긴다.
- 종료된 프로세스의 메모리 작업에만 의존하지 않는다.
- 서빙의 불변 읽기 묶음과 계속 갱신되는 후보 원장을 분리한다.

현재 `contracts.write()`는 최종 파일을 배타 생성하지만 쓰기가 원자적으로 완료되는 계약은 아니다. 제안 구현에서는 실행을 `STARTED/COMPLETED/FAILED`로 기록하고, 임시 파일 작성 후 같은 파일시스템의 원자적 이름 변경 또는 트랜잭션 원장을 사용한다. 완료 해시가 확정된 입력만 후보 작업자가 읽는다. 실패 실행은 불완전한 상태임을 표시한 별도 분석 입력으로 다룬다.

후속 작업에는 선점 소유자·lease 만료·재시도 횟수·마지막 오류를 둔다. 후보 저장 중 종료되면 동일 멱등성 키로 재개하고 이미 확정한 후보를 중복 생성하지 않는다. 성공 실행만 수집하면 실패 경로가 분석에서 누락된다는 점도 고려한다.

SQLite를 초기 저장소로 사용할 수 있다. 쓰기 경합·작업 선점·트랜잭션 경계를 설계해야 하며, 요청량에 따른 확장 필요성은 측정으로 판단한다.

### 10.4 접근 범위와 정보 보호

`document_ids`에 의한 조회 범위 제한을 완성된 사용자 권한 체계로 간주하지 않는다. 서버가 확인한 사용자·조직 권한과 문서 범위를 연결해야 한다. 후보·검토 화면·절차·캐시에도 동일한 경계를 적용한다.

특히 현재 `Pipeline.plan()`은 빈 문서 목록을 전체 문서로 바꾼다. 새 권한 연계에서는 **문서 필터 미지정과 서버 허용 문서의 빈 교집합을 구분**해야 한다. 허용 문서가 0건이면 RAG 진입 전 권한 없음 또는 명시적 빈 결과로 처리하고 `[]`를 기존 전체 범위 기본값으로 전달하지 않는다. 필터 미지정·명시적 빈 필터·권한 0건·권한 철회 후 0건을 별도로 검사한다. 부모 실행·피드백 목록·후보 검토·캐시에도 같은 규칙을 적용한다. 독립 감독 검토에서 확인한 설계 선행 조건이며, 제품 코드 수정이나 누출 재현은 수행하지 않았다.

내부 표현을 일반화했다고 공개 자료로 바뀌지 않는다. 원문이나 질문을 복제하는 대신 접근이 통제된 근거 참조를 사용하고, 원문 삭제·접근 철회 시 파생 후보와 절차의 처리 정책도 둔다. 후보 안의 텍스트나 원문 속 지시를 실행 규칙으로 취급하지 않는다.

| 반복 오류 축적 | 모델 출력이 다음 검토의 유일한 근거가 됨 | 원문·사용자 관측·모델 해석 분리, 후보 자동 승인 금지 |
| 개정·ID 변경 | 과거 절차가 다른 의미나 문서를 가리킴 | 의존 버전 결속, 이행 기록, 재검증 |
| 검토 병목 | 후보가 쌓이고 갱신이 멈춤 | 중복 묶기, 영향도·반복도별 우선순위, 기각·보류 관리 |
| 지연·비용 증가 | 해석·절차 선택이 모델 호출을 늘림 | 조회 우선, 조건부 모델 호출, 후속 추출 분리, 공통 예산 |
| 권한·범위 누출 | 부서별 표현이나 근거가 다른 사용자에게 노출 | 전 단계 권한 검사, 권한을 포함한 캐시 키·가시성 검사 |
| 모델 간 차이 | 외부 검증과 GENOS 모델의 선택·형식 준수 차이 | 같은 계약으로 현장 검증, provider 자동 대체 금지 |

가장 큰 난점은 ‘처리 성공’과 ‘의미·근거의 정확성’을 구분하는 것이다. JSON 형식이 맞고 도구 호출이 성공해도 개념 연결과 원문 판단이 틀릴 수 있다. 기능 계약 검사와 업무 품질 평가를 각각 수행해야 한다.

성능 측면에서는 현재 요청마다 수행되는 용어집 검증·역매칭 색인 구성 비용도 고려한다. 캐시는 세대 해시를 기준으로 불변 자원을 재사용하도록 설계하고, 요청별 판단·읽기 상태와 DB 연결의 스레드 안전성을 별도로 관리한다. 보고서 작성 중 성능 측정은 수행하지 않았다.

## 12. 검증 계획

### 12.1 비교 구성

| 구성 | 목적 |
|---|---|
| 기준: 현재 탐색 | 정확한 부모 릴리스·원문·용어집·모델·설정 고정 |
| 후보 1: 기준 + 표현 연결 | 올바른 시작점 확보 효과와 잘못된 확장 측정 |
| 후보 2: 표현 연결 + 검토된 절차 | 필수 근거 회수·일관성·누락·비용 변화 측정 |

결과를 확인하기 전에 가설·평가 데이터·성공 기준·허용 회귀·예산을 동결한다. 평가 결과를 보고 수정한 후보는 새 실험으로 남긴다.

### 12.2 평가 질문 구성

- 표현만 다르고 의미·조건은 같은 질문.
- 표기는 비슷하지만 상품·행위·당사자·시점이 다른 질문.
- 핵심 조건이 빠져 추가 질문이 필요한 사례.
- 기존 절차 밖의 쟁점이 포함된 복합 질문.
- 필요한 개념·원문·참조가 없는 사례.
- 규정 개정·용어 의미 변경 이후의 질문.
- 권한 범위가 다른 사용자에게 같은 질문이 들어온 사례.

동일 원질문을 바꿔 쓴 문장들이 학습·절차 생성용과 평가용에 나뉘어 들어가지 않도록 사건·질문 계열 단위로 분리한다. 정답 근거와 평가용 정보는 제품 입력으로 제공하지 않는다.

### 12.3 지표와 완료 판단

| 영역 | 확인할 지표 |
|---|---|
| 표현 연결 | 올바른 의미 연결, 후보 누락, 잘못된 확정, 적절한 보류 |
| 절차 선택 | 적합 절차 선택, 부적합 절차 적용, 미확인 조건 처리 |
| 탐색 | 필수 원문·예외 근거 회수, 불필요한 조회, 추가 탐색 성공 |
| 답변 | 주장–근거 정합성, 미답변 쟁점, 근거 없는 결론 |
| 성능 | 전체 지연, 호출·토큰·행동 수, 초기화 비용, 동시 요청 영향 |
| 운영 | 후보 중복, 검토 소요, 오류 복구, 변경 영향 추적 |
| 권한·버전 | 허용 범위 밖 접근 차단, 변경·롤백 후 올바른 버전 선택 |

목표 수치는 업무와 기준 성능을 확인한 뒤 실험 전에 정한다. 이 보고서에는 임의의 정확도나 비용 절감률을 약속하지 않는다. 코드가 검사할 수 있는 ID·스키마·범위·무결성은 필수 통과 조건으로 두고 의미 정확성·근거 회수는 별도 평가한다.

| 단계 | 작업 | 주요 산출물 | 다음 단계 진입 조건 |

| 0. 범위 선정 | 보유 원문·용어 연결이 충분한 업무 선택, 기준 확정 | 업무 범위·데이터 목록·기준 명세 | 대표 질문과 반례, 필요한 근거 확보 |

| 2. 절차 실행 | 소수의 검토된 절차와 실행기 연결 | 절차 계약·실행 로그·분기 검사 | 필수 확인 순서 준수, 부적합 조건 분기 |

첫 구현은 단계 0~2를 목표로 한다. 일정은 투입 인력, 검토 가능한 업무 담당자, 자료 연결 상태, GENOS 모델 환경을 확인한 뒤 산정한다. 병목은 코드량보다 의미 검토·평가 자료 준비·현장 확인에 생길 수 있다.

담당 책임은 다음처럼 나눈다. 한 사람이 여러 역할을 맡을 수 있지만 승인 근거와 작업 이력은 구분한다.

- **업무 담당:** 용어 의미·적용 조건·필수 확인 항목·반례 검토.
- **백엔드 담당:** 계약·후보 원장·검색·절차 실행·버전 결속.
- **평가 담당:** 독립 평가 질문·근거·회귀 기준과 결과 분석.
- **현장 운영 담당:** GENOS 모델·권한·영속 저장·활성화·롤백 확인.

## 14. 활성화·롤백 및 GENOS 인계

새 묶음은 원문 세대, 용어집, 표현 연결, 탐색 색인, 절차, 코드·프롬프트·모델 설정의 버전과 해시를 함께 기록한다. 후보 승인만으로 현재 서비스에 반영하지 않는다.

초기 변경 검증은 묶음 전체를 대상으로 수행하고, 의존성 추적이 검증된 후 영향 범위별 재검증으로 축소한다. 변경 도중 한 요청이 여러 세대를 혼합하지 않도록 요청 시작 시 사용 묶음을 고정한다.

활성화는 기대하는 이전 포인터가 일치할 때만 전환하고 영수증을 남긴다. 롤백은 호환되는 코드·데이터·표현·절차 묶음으로 복구한다. 런타임 캐시와 프로세스 재시작 필요 여부도 실제 선택 결과로 확인한다.

실험을 실제 시작할 때는 저장소의 실험 표준을 끝까지 읽고 동일 범위 예약 확인·ADR 선점·snapshot/register/freeze·최종 검사 절차를 수행해야 한다. 외부 신규 실험은 허용 데이터 범위 안에서 지정된 Gemini 실험 정책을 따르며, GENOS 실행은 내부 모델을 사용한다. 본 문서는 실험 실행이나 예약을 대신하지 않는다.

GENOS 인계 항목은 코드 리비전, 의존성, 설정 이름, 입력·출력 계약, 묶음 해시, 실행·재개·검증·활성화·롤백 방법이다. 실제 내부 질문·문서·사용 기록은 외부 반출하지 않는다.

Git main 병합, 데이터 세대 선택, 로컬 MAIN 활성화, GENOS 리비전 배포와 실제 요청의 선택 상태를 각각 보고해야 한다. 현재 Codex 세션에서는 GENOS 접속·현장 호출을 재시도하지 않는다.

## 15. 예상 시나리오와 구체적인 처리 결과

이 절의 함수명 중 `resolve_expression`, `select_recipe`, `execute_recipe`, `commit_run`은 제안 이름이다. 기존 구현으로 혼동하지 않도록 호출 책임을 설명하는 데만 사용한다.

### 15.1 정상 요청: 알려진 업무 표현과 유효한 절차

| 순서 | 입력·처리 | 현재 연결 또는 제안 변경 | 결과·관측 |
|---|---|---|---|
| 1 | 사용자 질문과 허용 문서 범위 수신 | 브릿지 envelope 분리 → `app.ask` → `Pipeline.plan` | 인증 주체·실행 ID·선택 묶음 고정 |
| 2 | 등록 표기와 검토된 표현 조회 | `ReverseMatcher.starts` + 제안 `resolve_expression` | 실제 용어 ID·매칭 원문 위치·연결 근거 |
| 3 | 질문 의도·대상·시점으로 절차 후보 조회 | 제안 `select_recipe` | 조건별 일치·불일치·미확인과 선택 이유 |
| 4 | 절차 의존 버전과 ID 해소 | `ServingNavigationAgent` 확장 | 현재 세대와 범위에서 발견 가능한 시작점 |
| 5 | 정의·원문·참조 순서 실행 | `NavigationSession` + 제안 `execute_recipe` | 도구 호출 기록, 단계별 요구 근거·완료 상태 |
| 6 | 질문별 판단·답변 | 기존 `select → assemble → answer` 계약과 연결 | 실제 읽고 채택한 원문에 연결된 답변 |
| 7 | 기록 확정·후속 후보 준비 | 제안 `commit_run` + 후보 작업 원장 | 완료 해시·작업 ID. 사용자 응답 후 후보 처리 가능 |

기대되는 변화는 초기 시작점과 필수 확인 순서의 일관성이다. 필수 원문 자체가 없거나 잘못 연결되어 있으면 절차 재사용만으로 답변 정확도가 개선되지는 않는다.

### 15.2 모호한 요청: 상품 유형이 빠짐

“중간에 돈을 빼면 얼마 받나요?”는 상품 종류가 미확인인 상태다. 표현을 `환매`로 확정하지 않고 공통 확인 절차를 선택한다. 필요 사실을 응답에 표시하고 실행을 `WAITING_FOR_FACTS` 의미의 상태로 저장한다.

사용자가 상품 유형을 알려주면 부모 실행의 접근권한과 입력 사실을 확인해 새 실행을 만든다. 질문 사실과 문서 사실이 충돌하면 충돌을 보존하고 추가 확인한다. 이 흐름은 기존 API에 부모 ID만 붙여 작동하지 않으며, 10.2절의 계약·브릿지·화면 변경이 선행 조건이다.

### 15.3 절차가 잘못 맞거나 새 쟁점이 나옴

문장은 유사하나 해당 업무·시점이 다르면 부적합 절차를 실행하지 않는다. 실행 도중 새 쟁점이 드러나면 해당 단계의 결과를 남기고 기존 탐색으로 확대한다. 이미 읽은 근거를 현재 요청 안에서 활용할 수 있으나, 잘못된 적용 조건에 기반한 판단은 다시 검토한다.

절차 단계의 호출 완료와 필수 근거 충족은 별도 상태로 관리한다. 각 단계는 `전제 / 허용 행동 / 요구 증거 / 완료 판정 / 실패 시 행동`을 가지며, 도구를 호출했다는 이유만으로 완료되지 않는다.

### 15.4 원문 개정·권한 변경

선택 절차가 참조하는 정의나 원문 버전이 달라지면 자동 ID 치환 대신 재검증 대상으로 분류한다. 해당 절차를 사용할 수 없어도 허용된 새 세대로 기존 탐색은 가능하도록 설계한다. 사용자가 접근할 수 없는 정의·관계·후보는 목록·미리보기·캐시에서도 제외한다.

실제 누출 검증은 선택 릴리스와 작업 코드의 차이를 반영한 별도 계약·회귀 검사로 수행한다. 이번 문서 검토는 누출을 실험한 결과가 아니다.

### 15.5 모델 장애·기록 실패·중복 요청

| 장애 | 사용자에게 보이는 결과 | 저장·복구 |
|---|---|---|
| 모델 호출 시간 초과 | 확인하지 못한 범위를 포함한 미완료 상태 | 실패 단계·실제 전송 횟수·소비 예산 기록. 자동 다른 모델 대체 없음 |
| 필수 근거 미회수 | 근거 부족·미확인 항목 표시 | 절차 성공으로 집계하지 않음 |
| 답변 후 후보 추출 실패 | 이미 확정된 답변은 유지 | 후보 작업만 같은 키로 재시도 |
| 실행 기록 확정 실패 | 성공 기록·피드백 연결을 보장했다고 표시하지 않음 | 미완료 임시 파일을 소비하지 않고 복구·운영 확인 |
| 네트워크 재전송·중복 요청 | 동일 요청 키이면 같은 확정 결과 또는 처리 상태 | 권한과 요청 내용 지문을 검사하고 중복 실행 방지 |

현재 `wall_seconds=300`은 루프가 호출 전후에 확인하는 한도이며 전체 응답 SLA가 아니다. 초기화 시간·진행 중인 provider 호출·재시도는 별도로 고려해야 한다. 제안 구현에서는 전체 deadline을 하위 전송 timeout과 연결하되, 플랫폼에서 취소가 실제 전파되는지도 검증한다.

## 16. 예상 기대치·부담과 수치 검토

### 16.1 값의 구분과 결론 범위

**아래 계산에 사용하는 적용률·호출 절감·검토 시간·개발 인일은 계획을 위한 가정이다. 현행 시스템 로그에서 추정한 값이나 통계적 예측 구간이 아니다.** 입력 가정에 대한 경험적 신뢰도는 아직 없다. 사용자가 기대 범위를 판단하고 무엇을 측정할지 정하기 위한 조건부 계산이다.

| ID | 항목 | 종류·현재 기대치 | 검증할 자료 |
|---|---|---|---|
| Q1 | 표현이 다른 동일 업무의 시작점 일관성 | 정성 가설: 승인 표현 연결이 있는 범위에서 개선 기대. 정확도 수치 미측정 | 정답 의미 ID·자동 확정 비율·확정 정확도 |
| Q2 | 필수 근거 회수 | 정성 가설: 검토된 절차에 포함된 확인 항목의 누락 감소 기대 | 질문별 필수 원문·예외 회수와 기존 대비 회귀 |
| Q3 | 법률·업무 결론 정확도 | 미확인. 절차 준수나 형식 검증으로 보장 불가 | 독립 업무 평가와 근거 검토 |
| C1 | 평균 모델 호출 절감 | 조건부 계산: 아래 가정에서는 요청당 -0.6~+1.5회 순 절감 | 실제 적용률·추가 호출·재시도·실패 포함 로그 |
| H1 | 후보 검토 부담 | 조건부 계산: 일 100건 요청·10% 고유 후보·건당 4분이면 40분/일 | 중복 제거 후 후보율·실제 검토 시간 |
| W1 | 초기 구현 작업량 | 계획 가정: 개발·통합·검사 합계 21~36인일 | 작업 분해·의존성·현장 환경 확인 후 재산정 |
| T1 | 전체 응답 지연·p95 | 미산정. 호출 수 절감만으로 시간 절감률 환산 불가 | 초기화·연결·절차·탐색·기록의 구간별 분포 |

### 16.2 C1: 모델 호출 절감의 조건부 산식

`순 호출 절감/요청 = H × S − L`

- `H`: 전체 대상 요청 중 검증된 절차가 실제 적용된 비율.
- `S`: 적용 요청에서 기존보다 감소한 탐색 모델 호출 수.
- `L`: 전체 요청에 평균 배분한 신규 온라인·후속 처리 모델 호출 수. 적용 요청에서만 드는 호출도 전체 분모로 환산한다.
- 양수는 절감, 음수는 추가 호출을 뜻한다. `S`는 기준 대비 탐색 호출 변화만 포함하고 `L`과 중복 계산하지 않는다.

아래 단순 계산은 절차 미적용 요청의 기존 탐색 호출량이 변하지 않는다고 가정한다. 미적용 요청의 탐색에도 변화가 있으면 `U = 미적용 요청당 탐색 호출 감소`를 측정하여 `순 절감 = H×S + (1−H)×U − L`로 확장한다. `U`는 악화 시 음수이며 이미 `L`에 포함한 부담을 중복 계산하지 않는다. 논리적 provider 호출과 실제 전송 시도는 별도 지표로 집계한다.

| 시나리오 | H: 적용률 가정 | S: 적용 요청당 감소 가정 | L: 전체 요청당 추가 가정 | 순 절감/요청 | 해석 |
|---|---:|---:|---:|---:|---|
| 낮은 적용·높은 추가 부담 | 0.20 | 1.0회 | 0.8회 | -0.60회 | 요청당 0.60회 더 호출 |
| 중간 가정 조합 | 0.40 | 2.0회 | 0.5회 | +0.30회 | 요청당 0.30회 절감 |
| 높은 적용·낮은 추가 부담 | 0.60 | 3.0회 | 0.3회 | +1.50회 | 요청당 1.50회 절감 |

중간 가정에서 손익분기 적용률은 `H = L/S = 0.25`, 즉 25%다. 적용률이 10%p 변하면 순 절감은 0.20회/요청 변한다. 이 결과는 단순 산술이며 세 가정 조합의 발생 확률을 뜻하지 않는다.

호출별 토큰·모델·단가·캐시·재시도 비용이 다르므로 위 표를 금액·지연 절감률로 바꿀 수 없다. 실제 비용 비교는 `후보 전체 실제 비용 − 기준 전체 실제 비용`으로 계산한다. 이때 실패·추가 질문·후속 추출·재시도와 구축/재구축·검토 비용을 포함하고 일회성 비용과 반복 비용을 분리한다. 후속 질문까지 포함한 전체 과업당 비용도 별도로 집계한다.

### 16.3 H1: 검토 적체 시나리오

`하루 검토 소요 분 = 하루 요청 수 × 요청당 신규 고유 후보 수 × 후보당 검토 분`

일 100건 요청, 중복을 제거한 후보 0.10개/요청, 후보당 4분이라는 가정에서는 `100 × 0.10 × 4 = 40분/일`이다. 월 20업무일이면 800분, 약 13.3시간이다. 후보율이 0.30개/요청이면 120분/일로 증가한다.

검토 가능 시간이 60분/일이면 후보를 15개/일 처리할 수 있다. 고유 후보가 30개/일이면 적체가 15개/일 증가한다. 문서 확인·의미 충돌·재검토가 필요한 항목은 4분을 초과할 수 있다. 이 값들은 인력 절감 효과가 아니라 새로 발생할 수 있는 운영 부담의 계산 예시다.

### 16.4 W1: 최초 적용 범위의 작업량 가정

전제는 한 업무 범위, 재사용 가능한 기존 코드, 개발자 1명, 업무 검토자 협조, 접근 가능한 검증 환경이다. 업무 전문가의 근거 작성·검토 시간과 GENOS 배포 대기, 실제 데이터 권한 정비, 광범위한 기존 장애 수정은 별도다.

| 작업 패키지 | 계획 가정 | 포함 범위 |
|---|---:|---|
| 기준 상태·계약 차이 확인 | 2~3인일 | 부모 버전·범위·브릿지·저장 계약의 수정 범위 확정 |
| 표현 연결·후보 처리 | 4~7인일 | 계약·조회·후속 후보·검토 연결과 단위 검사 |
| 절차 선택·실행 | 5~9인일 | 적용 조건·단계 상태·분기·기존 도구 연결 |
| 후속 요청·기록·기본 UI | 3~5인일 | envelope·새 실행 연결·원자적 기록·최소 검토 화면 |
| 통합·회귀·평가 지원 | 4~7인일 | 교차 모듈 검사·평가 도구 연결·결과 검토 지원 |
| 문서·묶음·롤백 인계 | 3~5인일 | 버전 결속·활성화/복구 절차·현장 인계 |
| 합계 | **21~36인일** | 각 패키지의 단위 검사는 포함, 통합 검사는 별도 행 |

하루 1인일을 온전히 투입하고 주 5일 근무한다는 가정에서 순 개발 작업은 4.2~7.2주에 해당한다. 이는 납기 약속이 아니며 검토·현장 대기와 병행 업무를 반영한 달력 일정은 아직 산정하지 않았다. 첫 패키지에서 기존 장애 수정 범위가 커지면 전체 추정을 다시 작성해야 한다.

### 16.5 평가 목표와 통계적 한계

초기 목표는 특정 정확도 숫자를 약속하는 것보다 **개선 원인을 분리하고 중대한 회귀를 발견할 수 있는 평가**를 마련하는 것이다. ID·스키마·범위·무결성의 알려진 위반은 해결 전 활성화하지 않는 조건을 제안한다. 이것은 운영 오류 확률 0을 주장하는 조건이 아니다.

예를 들어 독립적인 부적합 질문 20건에서 잘못된 절차 적용이 0건이어도, 독립·동일한 실패 확률을 가정한 단측 95% 이항 상한은 `1 − 0.05^(1/20) ≈ 13.9%`다. 100건에서 0건이면 약 3.0%다. 의역 질문은 상관될 수 있으므로 단순히 질문 수를 독립 표본 수로 바꿔 계산하면 안 된다. 이 계산은 표본 규모의 한계를 설명하며 본 시스템에서 관측된 오류율이 아니다.

### 16.6 수치 원장과 감독 판정

| 수치 | 입력 근거 | 산술 검토 | 예측으로서의 상태 |
|---|---|---|---|
| C1 세 시나리오·25% 손익분기 | 명시한 가정 | 식으로 재계산 가능 | 로그로 보정 전이며 예측 미검증 |
| H1 40분/일·13.3시간/월·15개/일 적체 | 명시한 요청·후보·시간 가정 | 단위·합계 재계산 가능 | 실제 후보율·검토 시간이 필요 |
| W1 21~36인일·4.2~7.2주 | 작업 패키지별 계획 가정 | 합계·환산 재계산 가능 | 범위·인력·현장 조건 확인 후 재산정 |
| 오류 0건의 95% 상한 | 독립·동일확률 이항 가정 | 공식으로 재계산 가능 | 실제 표본의 독립성이 확인되어야 적용 가능 |

독립 감독 검토는 같은 기반 모델을 사용하는 별도 에이전트의 문서·코드·산식 검토다. 외부 업무 전문가의 승인이나 성능 실험을 대신하지 않는다. 별도 검토서에는 대상 보고서 해시·발견사항·보완 상태·남은 측정을 남긴다.

실제 독립 검토 결과는 [설계 감독 검토서](GLOSSARY_NAVIGATION_DESIGN_REVIEW_20260916.md)에 기록했다. 문서에 위험과 수정안을 반영한 상태와 실제 구현에서 해결한 상태는 구분한다.

## 17. 검토 결론과 남은 확인 사항

기존 지식그래프와 탐색 루프를 활용해 두 기능을 단계적으로 구현할 수 있다. 우선 과제는 전체 온톨로지 완성보다 **업무 범위가 명시된 표현 연결, 적용 조건이 명확한 탐색 절차, 검토와 버전 반영의 연결**이다.

본 보고서에서 확인한 것은 저장소의 연결 상태와 공개 사례에 근거한 기술적 구현 가능성이다. 실제 개선 효과·필요 검토량·응답 시간·GENOS 내부 모델 품질은 미확인이다.

착수 전 결정할 사항은 다음과 같다.

1. 첫 대상 업무와 사용할 정확한 원문·용어집 세대.
2. 의미·절차를 검토할 담당자와 승인 범위.
3. 평가 질문·반례·필수 근거 및 허용 회귀.
4. 사용자·부서별 가시성, 대화 재개, 후보 보존 정책.
5. GENOS 현장 모델·저장소·권한·운영 확인 방식.
