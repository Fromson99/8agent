# MAIN50 CM51 결함 개선과 MAIN 연결 구현 계획

기준일: 2026-10-09 KST. 대상: WSL 로컬 RAG 서빙 MAIN50과 그 후속 후보. 상태: 구현 전 설계.

**우선 재진입 상태와 부족 근거의 추적을 고치고, 질문 범위·조사 대상·답변 내용을 하나의 요청 안에서 끝까지 연결한다.** 그다음 검증한 변경만 현재 작업 코드에 통합하고, 같은 코드로 검증한 새 릴리스를 실제 서비스가 선택하는 데까지 완료 범위를 잡는다. 입력량 축소는 이 연결을 보존하는 조건에서 진행한다.

첨부의 27개 항목을 아래 변경과 검증에 모두 배정했다. 이번 작성에서는 기존 기록 읽기와 해시 대조만 수행했다. 새 모델 호출, 후보 구현, MAIN 포인터 변경, GENOS 배포는 수행하지 않았다.

## 1. 현재 무엇이 MAIN에 연결되어 있는가

| 구분 | 확인 결과 | 설계에서의 의미 |
|---|---|---|
| 선택 릴리스 | `compact-input-20261009-r1`, 활성 포인터 generation 50 | 후속 변경의 기준선 |
| 구현 부모 | 완료된 `ADR-0712-experiment-v1/compact` | 후보 snapshot과 통합의 직접 코드 부모 |
| 최근 실행 | `ADR-0717-experiment-v1/measured-main50`, 완료된 인샘플 진단, `decision_eligible=false` | 문제의 관측 근거. 새 기능 승격 대상으로 사용하지 않음 |
| 코드 일치 | 릴리스 manifest의 서빙 287개 파일을 현재 작업 코드·선택 릴리스·ADR0717 후보와 다시 대조해 불일치 없음 | CM51 결과가 별도 미배선 구현의 결과가 아님 |
| 데이터 | `term-source-8729f978a28924cb8c5b`; 선택 data manifest SHA 일치 | 이번 우선 수정은 원문·용어집·색인 재구축 없이 가능 |
| 실제 서비스 기록 | ADR0712의 새 로컬 프로세스 `service.service` HEALTH/RAG_SEARCH 선택 확인 기록 | 이번 설계에서 실행 중인 프로세스를 새로 검증한 것은 아님. 다음 승격 때 다시 확인 |
| GENOS | 이 세션에서 접근 불가 | 로컬 검증·승격 이후 별도 반입과 현장 검증 |

MAIN50에는 이미 앞단 통합, 실제 제목·약칭 힌트, 선택형 구조/fulltext 검색, 선택 범위 읽기, 읽기와 채택의 구분, 부족분 재조사, SQL 재개, 승인 판단 기반 답변, 최대 5단계 진행 표시, 물리 호출별 계측, 탐색 입력 압축이 들어 있다. 이 기능을 다시 만드는 계획이 아니다.

**집계 정정도 실제 반환 자료에서 확인했다.** 저장된 51개 `result.json`의 승인 `answer_coverage`는 COVERED 39개, PARTIAL 7개, 실패 5개다. HTTP는 200 46개, 500 1개, 422 4개다. CM042의 최종 승인은 PARTIAL이다. ADR0717 README의 40/6은 수정 전 모델 상태를 읽은 과거 집계로 남아 있으므로, 이 설계의 기준으로 쓰지 않는다. 이번 대조는 정답 재채점이 아니다. [근거·해시 원장](EVIDENCE.json)

전체 MAIN의 용어집 → 입력·구조화 → 문서–용어 연결 → 색인 → RAG → 피드백 중 이번 변경은 **RAG의 요청·탐색·판단·답변과 피드백에 붙는 실행 근거**를 담당한다. 상위 데이터 구축 완료나 전체 MAIN 완성을 선언하는 범위로 확대하지 않는다.

## 2. 실제 호출 경로와 변경 책임

기존 실행 순서를 유지한다.

```text
service.service / service.py
  → 선택 릴리스·프로필·원문 세대 결정
  → semantic_runtime.app / Pipeline
  → unified_runtime → corrected_memory.Memory
  → INTENT → PLAN → RECALL → READ → SELECT → ASSESS → COMPOSE
       ↑ 새 질문 앞단 request_entry의 결과를 INTENT에서 소비
                                ↑ law_navigation.Investigation
                                └ ASSESS의 부족분으로 SELECT 재진입
  → unified_runtime.result_port
  → API / 현재 판단 보기 / 워크플로우·진행 표시 / 요청 요약
```

`SELECT` 안에서도 추가 원문 읽기와 구조·참조 조회가 일어난다. 별도 조사 실행기나 상시 평가 모델을 만들지 않는다. 모델은 질문의 의미, 필요한 근거, 원문에 대한 판단을 담당한다. 코드는 동일성, 실행 대상, 실제 읽기·채택, 상태 전환, 인용, 답변 내용의 전달을 검증한다. 코드 검증 통과를 법률 의미의 정답 보증으로 바꾸지 않는다.

| 작업 묶음 | 기존 파일·함수와 책임 | 함께 바꿀 소비자·계약 |
|---|---|---|
| A 재시도·재진입 | `corrected_memory.py`의 `Reenter` 처리; `law_navigation.py`의 `Investigation.__init__`, `request_decision`, `run`, `bounded_result` | selection checkpoint, SQL event/head, `completion_budget.restore`의 요청 예산 |
| B 부족 대상·조사 종료 | `completion_contracts.gap_key`; `completion_execution.completion_stage`, `gap_history`; `Investigation.gap_leads`, `execute`, `validate_gap_resolutions` | 부족 원장, 실행 receipt, 승인 ASSESS, 한계 문구 |
| C 질문 범위·원문 선택 | `request_entry.schema/accept/consume`; `investigation_contracts.intent_schema`; `Investigation.view`; `structure_query.resolve/catalogue`; `evidence_inventory` | INTENT/PLAN/SELECT/ASSESS의 동일 요구 ID, 선택 메뉴, 읽기 영수증 |
| D 판단·답변 내용 | `completion_contracts.assessment_schema/rule_schema/rule_errors/materialize_assessment/render_rule/render`; `completion_execution.completion_stage` | `unified_runtime.result_port`, `judgment_view.build`, API·재개·워크플로우·이력 출력 |
| E 입력·계측 | `Investigation.bounded_model_view`; `completion_execution`의 모델 입력 구성; `execution_metrics.py`, `request_report.py` | 실제 전송 payload 감사, 최종 상태 집계, 호출·시간·메모리 표 |
| F MAIN 연결 | `UnifiedRag.__init__`의 코드 binding, 엔진 manifest, `PIPELINE.json`, v6 프로필, `service.py` | frozen 후보 → 작업 코드 → 새 릴리스 → 활성 포인터 → 실제 서비스 binding |

표의 파일은 별도 표시가 없으면 `02_BACKEND/semantic_runtime/legal_agent/` 아래에 있다. `execution_metrics.py`, `request_report.py`는 그 상위 `semantic_runtime/`에 있다. 아래 새 필드·정책 이름은 모두 **제안**이며 현재 구현된 기능명이 아니다.

## 3. 첨부 27개 문제의 전후 설계

### 먼저 실행 상태와 조사 반복을 고친다

| 첨부 번호·상황 | 기존 처리와 실제 결과 | 수정 방식 | 같은 상황에서 원하는 결과와 검사 |
|---|---|---|---|
| 12 CM019 재진입 | 이전 `decision_retry`를 가진 checkpoint에 새 gap을 붙인다. 다음 화면 해시가 달라 `decision retry presentation changed`, HTTP500 | 수정 시도의 수명을 결정 단위로 분리. 새 조사 epoch에서 이전 수정 상태를 감사 이력으로 닫음 | 동일 결정 재개는 같은 수정 결과를 재사용하고, 새 조사는 이전 수정 상태와 충돌하지 않음. 중단 위치별 SQL 복원 검사 |
| 7 CM051 동일 부족 | `gap_key`에 가변 `material_id`와 kind가 포함된다. 같은 시행규칙 제14조 부족도 식별자가 달라짐 | 질문 요구·정규화한 문서 판본·조문 범위로 code-owned gap ID를 부여. material ID는 위치 단서로 분리 | 자료 ID 생략·약칭·표현 변경에도 같은 부족의 이력을 유지. 다른 판본·범위를 잘못 합치지 않음 |
| 8 CM051 무진행 | gap 배열의 해시 변화가 `no_progress`를 0으로 초기화. 새 원문 없이 FINISH를 반복해 회차별 횟수는 1 | 요청 단위 진전 원장을 유지하고 재진입은 초기화 사유에서 제외 | 새 근거·유효한 조사 결과가 없으면 회차를 넘어 누적. 한도 도달 시 구체적 미확인 범위로 종료 |
| 9 CM051 필요성 충돌 | ASSESS는 필요, SELECT는 불필요라고 하며 같은 문제를 재개. 중간 판단·수정에 129초 관측 | 필요성 불일치를 명시 저장. 조사 대상이 확인되면 해당 도구 후보를 제시하고, 근거 변화 없는 동의/반대만으로 재개하지 않음 | 같은 쟁점을 단계 사이에서 반복 논의하지 않음. 필요성을 확정 못하면 미해결 범위와 확인한 답을 반환 |
| 10 CM050 잘못된 부재 | gap ID에 붙은 완료 행동만 검사. 제6조 재독 receipt로 제15조의 NOT_AVAILABLE 통과 | receipt의 실제 문서·판본·좌표·조회 범위와 부족 대상의 관계를 검사 | 제6조 읽기는 제15조 부재 증명이 될 수 없음. 조사 한계는 UNRESOLVED로 기록 |
| 11 CM010·031·039 교정 반복 | 실행되지 않은 부족 조사에 대한 부재 판정을 한 번 더 생성하고 같은 오류 발생 | 정확한 대상별 가능한 행동과 금지 사유를 구조화. 완전히 같은 오류·제안 반복은 추가 교정 없이 한계 처리 | 같은 실패의 교정 연쇄를 늘리지 않음. 실제 행동이 가능한 경우 그 행동 선택을 검증 |
| 15 CM029·033 중복 채택 | 동일 채택 항목의 중복으로 각각 수정 호출 추가 | 같은 대상·상태·쟁점·근거·이유의 완전 동일 항목만 결정론 중복 제거 후 전체 재검증 | 이 구조 오류만 있는 경우 교정 모델 호출 불필요. 같은 대상의 상충 결정은 자동 선택하지 않음 |

원인 중 checkpoint의 상태 수명, 부족 키 구성, 무진행 초기화, 대상 검사 부재는 코드에서 확인했다. 모델이 경고를 따르지 않는 근본 원인과 새 설계의 실제 개선 폭은 후속 비교 대상이다.

### 질문이 요구한 대상과 실제 읽는 원문을 연결한다

| 첨부 번호·상황 | 기존 처리와 실제 결과 | 수정 방식 | 같은 상황에서 원하는 결과와 검사 |
|---|---|---|---|
| 1 CM014·042 배경 확대 | `context_quotes`는 있으나 issue가 질문 본문에 근거해야 한다는 연결이 약함. 부여요건·일반 구성요건 추가 | 요구 문장과 업무 문맥에 원문 위치를 붙이고, 명시 요구와 그 답에 필요한 조사 의존성을 구분 | CM014의 답변 요구는 기준시가로 유지. 배경에 실제 추가 질문이 있으면 보존. 괄호를 무조건 삭제하지 않음 |
| 2 CM014·041 조사 방향 | 관련 주제 조문을 직접 답변 근거처럼 취급 | 선택 이유에 요구 ID·답변할 항목·해당 원문 범위를 연결. 주변 설명과 직접 근거 역할 분리 | 전체 이사 수 질문에 독립이사 조건만으로 충분 판정하지 않음. 법률 의미는 원문 대조로 검사 |
| 3 CM016·032·046·050·051 조기 종료 | 원문을 읽고 FINISH한 뒤 ASSESS에서 위임 내용 부족 발견 | 종료 선택 화면에 요구별 읽음/채택/필요 참조 미확인 상태를 함께 제시. 열린 핵심 부족은 확인 또는 명시 한계로 닫음 | 관련 원문을 읽은 사실과 충분한 답변 근거를 구분. 모든 참조를 의무적으로 펼치지는 않음 |
| 4 CM050·051 대상에 도달 못함 | `gap_leads`는 일반 연결·법령·검색 버튼을 제공. 정확한 missing target과 일대일 결속 부족 | 허용 문서 안에서 제목·판본·좌표를 기존 구조 reader로 해소해 해당 gap의 실행 후보로 제시 | 제14조가 유일하게 확인되면 그 조문의 READ 후보로 이동 가능. 모호하면 후보 선택, 없으면 조사 실패 이유 보존 |
| 5 CM019·032·050 재독 | 원문 I/O는 `unit_reading.read`에서 재사용하지만 모델은 다른 범위 ID를 다시 선택 | 동일 세대·문서·블록·span 포함관계를 기존 `evidence_inventory.covers` 위에서 판단하고 메뉴에 이미 전달된 범위를 연결 | 같은 조문 안의 항·호를 새 근거처럼 계산하지 않음. 현재 호출에 본문이 없으면 재전달은 허용 |
| 6 CM006·050 이유와 행동 불일치 | 자유서술 이유와 구조화 실행 선택이 다름 | 사용자용 실행 사실은 실제 선택·receipt에서 생성. 모델 이유에는 대상·쟁점 참조를 연결 | 둘 채택했다고 표시하려면 실제 두 채택이 존재. “읽었다”는 설명만으로 읽기 완료 처리 금지 |
| 14 CM019·030 읽기와 채택 | READ 후 채택 없이 FINISH, CM030은 최종422 | `READ_AND_PRESENT → DECIDE/FINISH`에서 채택 대상을 명확히 제공. 재사용 읽기도 동일 채택 선택으로 연결 | 읽음을 자동 채택으로 바꾸지 않음. 기존 제한적 전달 원문 fallback은 표시·제외/보류 규칙을 보존 |

새 요구 원장은 모델이 관련성을 잘못 판단하는 문제를 완전히 막지 못한다. 다만 어떤 요구를 위해 무엇을 읽고 채택했는지 추적하고, 부족한 대상을 도구 선택에 연결할 수 있다. 비슷한 오류가 비교·정의·개정·목록 질문에도 적용되도록 CM 번호에 따른 분기나 정답 조문 하드코딩을 두지 않는다.

### 판단 구조와 최종 답변을 함께 고친다

| 첨부 번호·상황 | 기존 처리와 실제 결과 | 수정 방식 | 같은 상황에서 원하는 결과와 검사 |
|---|---|---|---|

최종 검토 모델을 상시 추가하지 않는다. 현재 `final_review_enabled=false`와 결정론 COMPOSE를 유지한다. 원문에 근거한 내용의 충실도는 별도 평가가 필요하며, 인용 문자열 일치만으로 통과 처리하지 않는다.

## 4. 구현할 상태와 계약

### 4.1 동일 결정을 고치는 것과 새 조사를 여는 것을 분리

기존 `completion_budget.restore`가 같은 request의 deadline·물리 호출 예산을 이어가는 정책은 유지한다. `request_id`, 사건 revision, 코드·데이터·프로필·권한 binding이 같은 요청 안에서 다음 상태를 구분한다.

| 상태 단위 | 제안 identity와 수명 | 보존·초기화 규칙 |
|---|---|---|
| 요청 | `request_id + case_revision + execution_binding` | 같은 요청 재개에서 예산·진전 원장 보존 |
| 조사 회차 | `investigation_epoch` | ASSESS가 유효한 새 조사 근거를 제시하면 증가. 전체 예산은 초기화하지 않음 |
| 한 번의 결정 | `epoch + presentation_id + input_hash + phase` | 이 identity 안에서만 수정 시도와 repaired 출력을 재사용 |
| 실행 행동 | 기존 action ID + 입력·대상 fingerprint | 접수·실행·receipt·checkpoint를 연결. 재개는 성공 행동을 새 행동으로 중복 집계하지 않음 |

새 epoch를 여는 시점에 이전 `decision_retry`는 완료 또는 폐기 사유와 함께 원장에 남기고 활성 슬롯에서 제거한다. 모든 예외를 잡아 상태를 지우는 방식은 사용하지 않는다. 같은 결정인데 input hash가 바뀌었거나, 권한·판본이 바뀐 경우는 실제 불일치로 거부한다.

중단 복구는 최소한 모델 수정 전, 수정 응답 저장 후, 행동 접수 후, 원문 일부 읽기 후, receipt 저장 후, ASSESS에서 SELECT로 돌아가는 경계에서 확인한다. 늦게 도착한 이전 epoch 결과는 새 head를 갱신하지 못한다. 새 사용자 질문·명시 재조사는 새 request로 시작하되 이전 route는 검증된 단서로만 사용한다.

### 4.2 부족한 대상을 코드가 소유하는 원장

제안 gap 항목은 다음 정보를 가진다.

```text
gap_id                    코드가 부여하고 이후 선택값으로 제공
request_requirement_id    질문의 요구
target                    문서 판본 + 조문/항/호/별표 + 요구 범위
target_resolution         EXACT / AMBIGUOUS / UNLOCATED
source_binding            선택 세대 + 권한 범위 지문
observations              모델의 kind·reason·material_id와 수정 이력
attempts                  실제 도구 대상·범위·cursor·결과·receipt
state                     OPEN / RESOLVED / NOT_AVAILABLE_IN_SCOPE /
                          DISPUTED / UNRESOLVED
```

문서 제목·약칭은 선택 세대의 기존 제목·좌표 resolver로 처리한다. 같은 판본·범위가 유일하게 확인된 경우만 동일 대상으로 결합한다. gap kind가 MISSING_SCOPE에서 UNRESOLVED_REFERENCE로 바뀌어도 같은 목표일 수 있으므로 kind는 관측 이력으로 둔다. 반대로 같은 조문이라도 질문 요구와 필요한 항·범위가 다르면 자동 병합하지 않는다. 좌표를 해소하지 못한 부족은 기존 `gap_id` 선택 또는 별도 미확인 항목으로 남기고, 문자열 유사도만으로 한데 합치지 않는다.

`NOT_AVAILABLE_IN_SCOPE`는 허용된 특정 판본·범위에서 확인한 결과다. 전체 법체계에 자료가 없다는 뜻이 아니다. 다음 조건을 둔다.

- 유일한 좌표가 있으면 해당 구조 조회·원문 읽기 경로의 실제 결과가 필요하다. 다른 조문의 읽기 완료는 사용할 수 없다.
- 조회가 중단·시간초과·권한거절·판본 모호·일부 페이지만 확인 상태면 `UNRESOLVED`다. fulltext 결과가 없다는 사실만으로 원문 부재를 확정하지 않는다.
- `RESOLVED`는 그 목표 범위를 다루는 검증된 span과 해당 요구의 채택 결정을 가리킨다. 엉뚱한 새 근거가 추가된 사실만으로 해결되지 않는다.
- 이미 전달된 원문을 새롭게 채택하거나 부족 범위를 재검토해 해결할 수 있다. “반드시 새 문서를 읽어야 한다”는 조건으로 재독을 강제하지 않는다. 어떤 상태가 새로 승인됐는지는 남긴다.
- SELECT의 `NOT_NEEDED`는 필요성 의견이다. ASSESS가 동의하지 않으면 `DISPUTED`로 남기고, 새로운 대상 조사 또는 제한 답변으로 끝낸다. 이유 문장 변화만으로 같은 조사를 다시 열지 않는다.

### 4.3 실제 진전과 읽기 재사용

두 수준의 진전을 분리한다. **탐색 진전**은 새 문서·좌표 후보, 새 범위의 확인된 조사 결과, 유효한 페이지 전진이다. **답변 근거 진전**은 새로 전달된 원문 span, 새 채택, 확인된 gap 해결, 사용자의 새 사실이다. 전자는 계속 탐색할 근거가 될 수 있지만, 그 자체만으로 같은 ASSESS를 재실행하는 근거는 아니다.

진전 fingerprint에는 실제 대상·범위·내용을 사용한다. turn 증가, 이유 바뀜, action ID 변경, 같은 gap의 표현 변경, FINISH 반복은 진전이 아니다. 무진행 한도는 현행 프로필 값 2를 초기 기준으로 보존하고 그 효과는 호출 전에 동결한다. 같은 request에서 gap 회차가 바뀌어도 누적 상태를 이어간다.

현재 원문 I/O 중복 제거는 유지한다. 추가할 부분은 **모델 선택 메뉴의 중복 읽기 판별**이다. 범위가 이미 전달됐고 현재 입력에도 해당 본문이 있으면 읽기를 새 조사처럼 제시하지 않고 해당 basis의 채택·보류 선택으로 연결한다. 현재 입력에서 빠졌으면 저장 원문을 다시 전달할 수 있다. 이때 `new_evidence=false`, `representation_refresh=true`로 기록한다. READ 캐시 적중과 모델 호출 절감을 같은 지표로 세지 않는다.

본문·span·판본 hash 또는 현재 권한이 다르면 재사용하지 않는다. 상위 조문의 도입문만 읽은 상태를 하위 항 전체 전달로 계산하지 않는다.

### 4.4 질문 본문과 업무 문맥

기존 `context_quotes`를 버리지 않고 다음 제안 필드로 연결을 보강한다.

- `requirements`: 원문 인용·위치, 요구하는 대상·행위·답변 형식.
- `background_spans`: 해석·검색을 돕는 업무 문맥. 독립 답변 요구로 자동 승격하지 않음.
- `dependencies`: 그 요구에 답하기 위해 필요한 정의·위임 조문·대안·예외. 어떤 요구를 위해 조사하는지 표시.

요구 원문의 위치와 현재 발언 일치는 코드가 검사한다. 그 인용이 모델의 쟁점을 의미상 뒷받침하는지는 오프라인 검토 대상이다. 괄호 안에도 실제 요구나 적용 조건이 있을 수 있으므로 구두점만으로 제거하지 않는다. 기존 사건의 정정·조건 추가 경로에도 같은 요구 표현을 연결하고, 과거 계약은 기존 reader로 해석한다.

### 4.5 답변의 한 정본과 간단한 조건 구조

신규 요청용 완료 계약을 `investigation-completion-v5`로 제안한다. 현재 v4의 model `claim.text`와 `rule.conclusion`이 서로 다른 내용을 가진 뒤 한쪽이 버려지는 구조를 줄인다.

1. 각 claim에 직접 답변인 `conclusion`과 필요한 `details`를 둔다. 목록·비교 대상·수치·권리는 근거 span을 가진 상세 항목으로 기록한다. 구체 내용을 담지 않은 “다음 각 호”, “상이하다”는 문장만으로 목록·비교 요구가 완료된 것으로 처리하지 않는다.
2. 조건은 중첩 식으로 작성하고 코드가 내부 ID와 root를 만든다. 예: `ANY(조건 A, ALL(조건 B, 조건 C))`. 모델이 ALL/ANY를 선택하며 UNKNOWN도 유지한다. 코드가 법률 논리를 추측해 연결하지 않는다.
3. 조건, 의무, 예외는 역할을 구분한다. 예외에는 적용되는 결론 또는 조건을 참조하게 하고, 참조가 불명확하면 확인 범위를 남긴다. 요청 안의 관측값이며 폐기된 전역 법률 의미 스키마를 되살리지 않는다.
4. 승인된 구조의 각 내용 항목을 COMPOSE가 한 번씩 표시한다. 원문→인용 span→승인 내용→출력 위치를 연결하고 API·판단 보기·워크플로우가 같은 결과를 소비한다.
5. 내용이 포함되었다는 검사는 법률 의미의 완전성 검사가 아니다. 목록의 모든 대상, 조건의 AND/OR, 예외 범위가 맞는지는 원문 기반 오프라인 검토로 확인한다.

완전 동일 항목 중복, 코드가 부여할 ID 등 의미를 바꾸지 않는 구조 문제만 자동 정규화한다. 조건을 잘못 연결한 답을 임의 수정하거나 의무를 조건으로 바꿔 통과시키지 않는다. 독립적으로 검증된 claim을 남길 수 있는 경우에만 해당 범위를 제한 답변으로 반환한다. 의미 의존성이 있는 부분을 안전하게 분리할 수 없으면 미확정 상태를 표시한다. HTTP200 비율을 높이려고 모든 오류를 답변 성공으로 바꾸지 않는다.

v4 기존 route·완료 답변은 당시 renderer로 검증·표시한다. 새 설정은 Boolean인 `completion_contract`를 문자열로 바꿔 억지 호환시키지 않고 별도 `completion_policy_version` 같은 명시 버전 선택으로 도입한다. 추가할 정확한 이름과 enum은 후보 동결 때 확정한다. v5 요청이 구버전 코드로 재개되는 경우는 호환 reader 또는 새 요청 전환이 필요하며, 이 상태를 조용히 재해석하지 않는다.

## 6. 이행 범위와 유지할 기능

원문·용어집·navigation/fulltext 세대는 최초 후보에서 유지한다. gap target 해소는 기존 구조 색인을 읽는다. 선택 원문 자체에 실제 누락이 발견되면 별도의 데이터 추가·새 generation 작업으로 분리한다. 성능 최적화를 위해 문서 범위를 무단 축소하지 않는다.

요청별 checkpoint·gap·승인 내용 계약은 새 버전으로 기록한다. 진행 중인 구버전 요청은 그 요청의 binding과 reader로 마치거나, 불가능하면 새 요청으로 분리한다. 완료 SQL 기록을 일괄 재작성하지 않는다. 롤백 시 이전 코드가 신규 기록을 무조건 읽을 수 있다고 가정하지 않는다. 새 필드는 기존 저장소의 버전 있는 payload에 두는 것을 우선하며 DB 테이블 이행이 필요해지면 별도 migration·복원 검증을 후보 범위에 추가한다.

보존할 기능은 새 질문 앞단 통합, DIRECT/CASE 분기, 제목 힌트, 구조/fulltext 자유 선택, 명시 범위 읽기·원문 span 인용, 보류·제외·복귀, 기존 사건 정정·멀티턴·숏컷, NFS/SQLite 정책, 물리 전송 예산, 오류 상세 로그 분리, 진행 카드·호출수·시간 표시다. 이번 설계는 개인 위키 자동 투입이나 기존에 실패한 온라인 경험 숏컷을 재활성화하지 않는다.

각 새 모듈은 `UnifiedRag`의 코드 identity와 해당 엔진의 file pin에 포함한다. 엔진 manifest가 바뀌면 소비하는 `PIPELINE.json` 해시도 갱신한다. 프로필·MAIN 선택·응답 소비자를 함께 검증해야 하며, 코드 파일만 복사해 완료 처리하지 않는다.

### 실제 모델 비교

1. **알려진 실패 회귀:** 첨부 CM 사례와 H02/R02, CM018은 설계에 노출된 사례다. 인샘플 회귀 묶음으로 쓰며 holdout으로 부르지 않는다. 과거 51문항 질문 그대로 외부 호출할 때는 ADR0717의 “이번 실행” 승인 범위가 새 실행까지 포함하는지 별도로 확인한다. 현재 설계만으로 반출 범위를 확대하지 않는다.
2. **분리 검증:** 제안 표본 N08은 새 공개 질문 12개 계열, arm당 2회 반복이다. 계열별 대표 질문을 단순 질문, 정확한 참조 이동, 복수 판본/목록/조건, 모호한 부족 사례로 구성한다. 표본·판본·정답 근거는 호출 전에 고정하고 알려진 질문의 의역은 같은 계열로 취급한다. 기본은 순차 실행이며 arm 순서를 균형 배치한다.
3. **대조:** 초기 후보는 MAIN50과 같은 데이터·모델·예산으로 비교한다. A/B 이후 후속 후보는 실제 채택한 완료 arm을 기준으로 하고 최종 통합 후보는 MAIN50 보존 항목까지 확인한다. 이미 결과를 보고 변경한 후보는 새 ADR에 남긴다.
4. **모델:** 현행 정책의 Qwen3.8 `qwen/qwen3.8-27b`, OpenRouter Parasail FP8, reasoning none, fallback 없음과 `ExperimentClient`를 사용한다. GENOS 내부 모델 결과로 환산하지 않는다.
5. **평가 분리:** 기준답변·과거 필수근거·오프라인 판정은 제품 입력에 넣지 않는다. 기준 원문과 질문 요구를 대조하고 인용 무결성, 실행 성공, 답변 완전성, 법률 의미를 따로 기록한다. `risk_cm` 105문항은 CM51과 다르며 이번 표본에 자동 포함하지 않는다.

**필수 차단 기준:** 인용·권한·코드/데이터 hash·상태 보존·서비스 선택의 심각한 위반은 허용하지 않는다. 새 계약의 알려진 구조 오류는 계약 검사에서 재발하지 않아야 한다. 신규 의미 오류는 원문·영향·회귀 여부를 기록하고 사전 동결한 허용 회귀 기준으로 판정한다. 세부 답변 100% 정답을 MAIN 조건으로 추가하지 않는다. 반대로 기존에 성공한 요청을 다수 미확정으로 바꿔 호출만 줄인 후보도 성공으로 보지 않는다.

**초기 비교의 제안 기준:** 반복 FINISH, 잘못된 target의 gap 종결, 재진입 상태 충돌은 목표 T01에 따라 제거한다. 분리 표본에서 신규 실행 실패와 근거 소실은 허용 0건을 제안한다(T02). 기존 의미 실패는 별도 원장에 남기며, 후보만의 의미 회귀가 있으면 총점 상쇄로 숨기지 않고 원인·허용 여부를 명시한다. 허용 회귀의 구체 범주와 지연·비용 상한은 실제 질문·scope와 함께 첫 호출 전에 확정한다. 이 항목이 빈 상태에서는 승격 검증을 시작하지 않는다.

현재 전체 graph에는 기존 오류 8건이 기록되어 있다. 새 ADR final 검증과 graph를 모두 다시 수행하고 새 오류·영향 계보를 확인한다. 기존 오류를 지워서 통과시키거나 “8건은 원래 있었으니 통과”로 대체하지 않는다. 승격에 필요한 검사가 막히면 원인별 정정 근거 또는 실제로 적용되는 절차가 마련될 때까지 그 단계는 미완료다.

계산 기준은 `순 절감 호출 = 없어진 재독 선택·중복 교정·무진행 판단 호출 − 새로 필요한 조사·교정 호출`이다. `순 절감 시간 = 제거된 호출 시간 − 추가 호출 시간 − 추가 코드 처리 시간`으로 계산하고, 입력·출력 토큰과 실제 공급자 비용은 별도로 비교한다. 호출 수가 줄었다고 같은 비율로 시간이 줄었다고 쓰지 않는다.

손익분기는 제거한 낭비 시간과 추가된 정당한 조사·검증 시간이 같을 때다. 단순 질문은 추가 모델 단계 없이 현재 경로를 유지하는 것이 목표다. 복잡한 질문은 빠른 불완전 답보다 제대로 된 참조 조사로 시간이 늘 수 있다. 따라서 최종 작성 제외 시간, 전체 요청 시간, 의미 회귀, 실제 조사 완료를 같이 본다. 현재 관측으로 “30% 개선” 같은 예상치는 제시하지 않는다.

메모리 계측은 요청 구간 peak RSS와 가능할 때 cgroup peak를 기록하고 첫 실행/공유 캐시 재사용을 구분한다. 과거 중단을 OOM으로 확정하지 않는다. 병렬 질문 처리 수를 늘리는 작업은 순차 검증과 구분한다.
