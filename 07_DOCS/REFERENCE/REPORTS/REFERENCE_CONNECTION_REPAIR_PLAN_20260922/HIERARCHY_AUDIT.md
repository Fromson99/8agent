# 목 아래 계층과 추가 연결 결함 점검

2026-09-22. 읽기 전용 DB·코드 진단. 제품 코드·원문 DB·관계 DB·활성 포인터 변경 및 모델 실행 없음.

## 결론

참조 연결은 원문의 실제 계층 경로를 따라야 한다. 그러나 **저장된 계층 자체도 일부 세부 번호를 놓치고 있어**, 기존 트리만 신뢰하는 수정으로는 충분하지 않다. 구조 복원 → 역할/좌표 보존 → 참조 표현 전체 해석 → 양 끝 범위 보존 순서로 연결해야 한다.

일반 구조 모델 `Node`는 자식과 깊이를 제한하지 않는다. 하지만 조사 DB의 공개 범위에서는 `hangul_dot` 마디 15,501개에 직접 자식 마디가 하나도 없었다. 원문에 `1)`, `2)`, `(1)`~`(5)`가 실제 존재하는 사례를 확인했다. **원문 번호가 없어서 끝난 트리가 아니다.** 이 수치는 선택 후보의 navigation 계층 점검이며 전체 저장소나 모든 현장 문서의 구조 품질 판정이 아니다.

## 대상과 재현

- 기존 PLAN과 동일한 후보: `01_DATA/TERM_RELEASES/adr0523-gemma-bound-fulltext-v1/generation`.
- ADR0523 product-cases의 공개 문서 145개, 공개 관계 133,116행. 로컬 활성 릴리스는 별도이며 포인터 변경 없음.
- 후보 DB 생성기는 ADR0522 rev002의 `semantic_runtime/term_references.py`이며 이번에도 파일 해시와 rebuild receipt가 일치함을 확인했다.

## 새로 확인한 사례

### 1. 목 아래 번호가 한 블록 안에 들어 있고 독립 마디가 없음

소득세법 시행령 제118조의6제3항은 `법 제59조의4제3항제1호나목2)`를 지목한다.

- 관계 `ref:580564c20a70f5017e35cb66`의 mention은 `제59조의4제3항제1호나목`에서 끝난다.
- 대상 소득세법 제59조의4의 unit702/block702는 나목 머리, `1)`, `2)`를 한 텍스트에 저장한다. 자식 마디가 없다.
- 관계는 `EXACT`이며 두 번호의 원문을 함께 읽는다. `2)`만을 지정한 범위가 보존되지 않는다.

이는 정규식에 `2)`를 추가하는 것만으로 해결되지 않는다. 블록 내부의 번호 구간을 원문 문자 span으로 찾아 별도 구조 좌표로 보존해야 한다. 기존 불변 원문을 재작성하거나 원문에 없는 의미 마디를 만들 필요는 없다.

### 2. 블록은 나뉘어 있지만 계층이 나뉘지 않은 경우도 있음

유가증권시장 상장규정 시행세칙 제92조제1항은 `규정 제113조제2항제5호가목(2)`를 지목한다.

- 관계 `ref:1c27f375846731a6f6b5d3b9`는 `가목`에서 끝나고 `EXACT`다.
- 대상 규정 unit1139 아래 별도 자식은 없고, 가목 머리 및 `(1)`~`(5)`가 block1240~1245로 같은 마디에 묶였다.
- 요청된 `(2)`는 block1242다. 현 연결은 여섯 블록을 모두 반환한다.

따라서 **블록 분리와 계층 분리는 다른 상태**다. 블록이 따로 있다는 사실만으로 세부 참조가 해결됐다고 볼 수 없다.

### 3. 항 없는 조의 호를 ‘항’으로 오분류하여 실제 있는 대상을 누락

책임준공확약 PF대출 관련 업무처리 모범규준 제7조는 조 바로 아래 `1.`, `2.`, `3.`이 있으며, 원문이 직접 ‘아래 각호’라고 부른다. 제2호의 `제1호` 인용은 관계 `ref:1cbfdb260b08cd18652d91e6`에 `PROVISION_NOT_IN_STRUCTURE`로 저장됐다.

실제로 제1호 unit20/block28은 존재한다. 하지만 문서 frame은 `dot_number:1 → 항`이다. 생성기의 `frame_roles()`가 조 아래 나타난 계열에 항→호→목을 순서대로 붙여, 항이 없는 문서의 호를 항으로 당겨 놓는다. `descend()`는 역할 불일치 때문에 대상을 찾지 못한다.

‘DB에 대상이 없다’와 ‘DB의 역할 매핑이 틀렸다’를 구분해야 한다. 문서별 첫 번째 깊이를 무조건 항으로 해석하면 안 된다. 모양·깊이·법적 호칭은 별개의 정보다.

### 4. ‘각 호 외의 부분’을 자식 호까지 포함한 범위로 저장

공공기관의 운영에 관한 법률 시행령 제8조제2항의 `법 제6조제1항 각 호 외의 부분 단서`가 사례다.

- 관계 `ref:ba4238302c755e21d6e8b978`는 `제6조제1항`까지만 읽고 `EXACT`다.
- 대상 block35는 항의 머리·단서이고 block36~37은 제1호·제2호다.
- 저장 범위는 세 블록 전부다. 원문이 제외한 자식 호까지 자동 탐색 범위에 들어간다.

단순히 더 아래 노드를 찾는 문제와 다르다. **마디 자체의 문언 / 자손을 포함한 전체 / 특정 문언 span**을 구분해야 한다. 조 전체를 확인용으로 보존하는 것과 이 관계로 이동한 범위는 별개다.

### 5. 역참조의 출발 범위도 넓어짐

상장규정 제113조제2항제5호가목 `(2)` 안의 시행령 인용은 `ref:e92198ce916add3b4a5b53a5`다.

- 인용을 실제 쓴 곳은 block1242의 `(2)`다.
- `source_unit_path`는 가목에서 끝나며 `source_block_ids`는 block1240~1245 전체다.
- 역참조로 돌아오는 원문 범위에도 가목 머리와 `(1)`~`(5)`가 모두 들어간다.

목적지만 좁혀서는 해결되지 않는다. 원문 mention이 속한 세부 구간과 역방향 반환 범위도 함께 저장해야 한다. 후보 런타임 `ReferenceNavigator._db_neighbors`의 incoming 경로가 `source_block_ids`를 소비함을 코드로 확인했다. 새 질문을 실행해 추가 회수량을 측정하지는 않았다.

### 6. 목 표기 여러 개가 한 줄로 합쳐진 구조 누락

부동산PF 수수료 모범규준 제2조의 block6에는 `가.`~`타.`가 한 텍스트로 이어져 있다. 해당 source의 마디는 조 아래 `1.`, `2.`뿐이며 목 마디는 없다. `ref:b5dcff4071c825a9cb2c35e2`의 source 원문과 구조에 보존했다.

이는 DB에서 확인한 목 구조 누락이다. 병합이 최초 파싱·전처리 중 어느 단계에서 발생했는지는 이번에 소급 확인하지 않았다. 줄 시작만 검사하는 후처리로는 모든 번호를 복원하지 못할 수 있다. 한글 글머리 자체를 무조건 목으로 승인하지 말고 원본 구조·앞뒤 번호·부모 문맥으로 검증해야 한다.

## 수정 범위에 반영할 사항

1. **구조 복원부터 점검:** `조 → 항(있을 때) → 호 → 목 → 1)/(1) → (가) …`는 가능한 예시이며 고정 깊이 규칙이 아니다. 실제 문서의 부모·자식, 원표기, 번호, 원문 span을 보존한다. 표는 표/행/열/셀과 소속 구조를 별도로 확인한다. 이번에는 표 좌표 정확성을 전수 검증하지 않았다.
2. **역할을 깊이와 분리:** XML의 명시 역할 등 원천 근거를 유지하고, 항 없는 조·문서별 반복 계열을 지원한다. 구조가 불명확하면 임의로 항·호 이름을 붙이지 않는다.
3. **하위 경로 길이를 제한하지 않기:** 후보 생성기의 `ROLE_ORDER = ('항','호','목')`, `SUBPATH`, `BARE_ENDPOINT`와 문서 틀 인용 경로를 함께 수정해야 한다. 공통 저장 모델의 깊이 자유도가 참조 해석에도 이어져야 한다.
4. **양 끝과 부분 범위:** 요청한 좌표 전체, 인용한 세부 구간, 목적지 구간, 머리/자손 포함 여부와 단서 등의 문자 span을 보존한다. 모호한 세부 범위를 부모 전체로 치환한 뒤 EXACT로 승인하지 않는다.
5. **문맥 보존:** 세부 번호만 읽으면 부모의 공통 조건을 잃을 수 있다. 확인에 필요한 조상 머리 원문을 함께 제공하되 형제 마디까지 자동 탐색 범위를 넓히지 않는다. 나열의 각 대상도 유지한다.
6. **재구축 범위 확대:** 이미 구조가 충분한 문서는 관계 색인 재생성이 가능하다. 위처럼 원문 구조가 빠진 문서는 새 구조 세대부터 만들고, 관계·역참조·전문검색·검토 기록을 그 세대에 다시 결속해야 한다. 기존 구조 DB를 복사하고 관계만 다시 생성하는 계획으로는 부족하다.

향후 검증은 목 아래 단일/나열/범위, 항 생략 구조, 같은 표기의 다른 부모, 머리만 인용, 한 블록의 여러 세부 번호, 역참조 반환, 조상 공통 문언 보존을 함께 다뤄야 한다. 기존 완료 ADR·DB는 보존하며 실제 후보 구현·모델 비교를 시작할 때 새 ADR 절차를 따른다.
