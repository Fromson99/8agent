# 구조·참조 연결 외의 증폭 구간 감사

2026-09-23. 완료된 실행 기록과 해당 실행 코드에 대한 읽기 전용 진단. 새 모델 호출·그래프 재실행·채점·코드 수정·DB 재구축·활성화 없음.

## 판단

**구조화와 연결 생성기 수정만으로 전체 증폭 문제가 100% 해결된다고 볼 수 없다.** 그 수정은 필요하지만, 실제 실행에는 정상적인 인용으로도 넓어지는 정·역참조 연결, 도착 경로별 상태 증가, 제외 검토의 계산·입력 비용, 자동 재개 및 완료 상태 관리가 함께 작용한다.

연결된 원문 수, 서로 다른 원문 범위 수, 경로 상태 수, 모델에 제시된 근거 수를 분리해야 한다. 큰 그래프 자체가 곧 잘못된 연결이라는 뜻은 아니며, 반대로 원문 좌표가 정확하다고 질문에 필요한 탐색이라는 뜻도 아니다.

- 네 gzip 그래프를 읽고 원래 `checkpoint_hash`를 재계산하여 모두 일치함을 확인했다. 모델 제시는 각 journal의 `model_view`와 `model_attempt.status`를 대조했다.

## 1. 한 블록에서 시작해도 역참조와 다른 인용을 통해 확장됨

ADR0524/cm-040은 상법 제361조(1블록), 제434조(1블록), 제433조(3블록)를 시작점으로 채택했다. 제434조 시작 상태에서 역방향 관계 27건과 정방향 1건을 기록했다. 세 시작점 전체의 미완료 그래프는 5,870개 source까지 도달했다. 이 전체를 제434조 한 개의 효과로 귀속하지 않는다.

실제 연속 경로:

`상법 제434조 → [역참조] 제516조의2제4항 → [다른 정방향 인용] 제418조제2항`

- 첫 관계: `ref:3c422964a89bc19933d739a3`. 신주인수권부사채 발행에 관한 제516조의2제4항이 제434조의 결의를 인용한다.
- 다음 관계: `ref:82537c3384a3ca9814bc4d71`. 같은 항이 제418조제2항 단서를 인용한다.
- 두 이동은 저장 그래프에서 target/from 상태가 이어진다. 이름 유사도로 만든 경로가 아니다.
- 단서 범위 문제는 따로 존재한다. 그 문제를 바로잡더라도 제434조를 인용하는 조문으로 역방향 이동하는 분기는 남는다.

`walk()`는 각 도착 범위에 `neighbors(..., 'both')`를 적용한다. `scoped_return()`은 **같은 관계를 즉시 반대 방향으로 돌아가는 경우**를 막으며, 다른 관계를 통한 계속 이동은 허용한다. 따라서 구조를 세분화하고 좌표를 정확히 해도 그래프 연결 성질에 따른 증가가 남을 수 있다.

정·역참조를 일괄 끊자는 뜻은 아니다. 정확한 DB 연결, 원문 보존, 다음 확장, 질문상 채택을 구분하고 각 단계의 이유·미완료 상태를 남겨야 한다.

## 2. 일괄 개정문이 많은 조문을 연결하는 통로가 됨

ADR0524/cm-025에 실제 기록된 경로:

`상증세법 시행령 제31조의3 → [역참조] 부칙 <제35947호, 20251230> → 제31조의2`

관계 `ref:1e1f66d991f5c19b7047ceb1`와 `ref:002048d8449af987f9e17c2e`는 동일한 긴 원문 블록을 공유한다. 이 원문은 여러 조문을 열거한 뒤 **“기획재정부령”을 각각 “재정경제부령”으로 한다**고 적고 있다. 저장된 출발 범위는 부칙 제6조 `<41>`의 block2381~2383이다.

이런 명시 인용은 원문에 실제 있으므로 삭제할 오류 관계로 일괄 처리할 수 없다. 하지만 하나의 개정문에 같이 열거되었다는 사실만으로 모든 조문이 질문에 필요한 실체적 근거라고 볼 수 없다. 일반 인용·준용·시행/적용례·일괄 개정의 **용도와 판본/시점 문맥**을 별도로 보존하고 확장 판단에 반영해야 한다. 이번에는 모든 부칙의 시점 적합성이나 개별 법률 적용을 판정하지 않았다.

## 3. 같은 원문 범위가 도착 경로마다 별도 상태로 쌓임

`state_key()`는 `(source_id, block_ids, return_guard)`를 포함한다. 동일 블록 집합이라도 들어온 관계가 다르면 별도 상태가 된다. 실제 코드에는 물리 범위별 neighbors 캐시가 있어 모든 상태마다 DB를 다시 조회하는 것은 아니다. 그러나 상태·관계 영수증 생성과 소유 시작점 전파는 커진다.

| 기존 실행 | 도달 source | 서로 다른 source+블록 집합 | 기록 상태 | 관계 영수증 |
|---|---:|---:|---:|---:|
| ADR0523/cm-009 | 1,027 | 2,276 | 3,471 | 5,188 |
| ADR0524/cm-025 | 1,826 | 4,778 | 10,218 | 30,650 |
| ADR0524/cm-040 | 5,870 | 16,876 | 40,426 | 139,852 |
| ADR0524/cm-009 | 4,635 | 14,903 | 34,604 | 156,184 |

ADR0524/cm-009에서는 자본시장법 시행령 별표22의 **동일한 119블록 범위**가 371개 상태로 저장됐다. 이는 별표가 371개라는 뜻도, 모델이 371번 읽었다는 뜻도 아니다.

반복 왕복 차단의 의미를 유지해야 하므로 `return_guard`를 무조건 지우면 안 된다. 물리 범위 확장과 경로·왕복 제한·시작점 소유 기록을 분리할 수 있는지 검토해야 한다. 위 그룹화 수치는 무조건 합쳐도 안전한 상태 수나 예상 성능 개선율이 아니다.

## 4. 처리 완료 상태가 대기열에 다시 남는 결함

네 그래프에서 `expanded_state_ids`와 `pending`의 교집합이 각각 **6·9·12·18개**였다. 교집합의 각 상태에 자신을 대상으로 하는 관계 영수증이 존재한다.

원인 경로는 `walk()`의 처리 순서와 일치한다. 현재 상태를 큐에서 뺀 후, 관계 대상을 `add()`하고, 마지막에야 `expanded.add(key)`를 한다. 이 사이 자기 자신을 대상으로 만나면 아직 완료 집합에 없으므로 다시 큐에 들어간다. 큐에서 꺼낼 때 이미 처리됐는지 건너뛰는 검사도 없다.

이것은 좌표 해석과 별개인 실행 상태 결함이다. 다만 관측 규모가 작으므로 수만 상태 증가의 주원인으로 단정하지 않는다. checkpoint 재개는 완료 상태를 제외해 큐를 복원하므로 이 사실을 무한 루프로 해석해서도 안 된다.

## 5. 출처 제외 영향 검토가 계산량과 모델 입력을 증폭

`source_selection.removal_preview()`는 먼저 `(source, block)`의 소유 시작점을 모은 뒤, **각 source마다 전체 coverage를 다시 훑는다**. `root_impacts()`는 시작점마다 이를 호출한다.

ADR0524/cm-040 저장 그래프 기준으로 source 5,870개 × source/block 39,294개 × 시작점 3개 = **691,967,340회의 내부 조건 검사**가 한 번의 root_impacts 호출에 해당한다. 이는 코드와 저장 그래프 크기에서 계산한 연산 수이며 실제 경과시간 측정이 아니다. 그래프 walk의 시간 제한은 이 후속 계산 전체를 감싸지 않는다.

모델 입력에서도 실제 경합이 있다. `workflow_tiers_views.build()`는 보통 `root_removal_impacts`를 원문과 관계 메뉴보다 먼저 채운다.

ADR0524/cm-009의 **성공 응답이 기록된 두 view**에서:

- 제외 영향 미리보기는 각각 38,404자·39,535자.
- 정확 원문 section은 각각 8,755자.
- 원문 evidence는 4개 제시, 10개 생략. 관계 메뉴는 4개/3개 제시, 62개/63개 생략.
- 이는 JSON section 문자 수이며 토큰 수가 아니다. 생략된 항목은 후속 페이지로 남는다. 영구 소실이나 해당 근거를 한 번도 제시하지 않았다는 뜻은 아니다.

따라서 원문을 서버에 잘 보존해도, 검토용 부가정보 때문에 이번 모델 입력의 원문·관계 가시성이 낮아질 수 있다. 제외 검토는 실제 제외 판단과 필요한 페이지에 연결하고, 원문 확인과 경쟁하는 크기를 점검해야 한다.

## 6. 자동 재개와 제외 조건이 큰 그래프를 정리하기 어렵게 함

- `view('investigate'/'select_sources')`가 `protected_graph(resume=True)`를 호출한다. 최종 출처 선택 화면을 만드는 동안에도 그래프 탐색이 계속된다.
- ADR0524/cm-040의 연속 저장 view에서 대기 범위가 **9,537 → 23,337 → 34,628개**로 증가했다. 시작점 세 개는 같다. 마지막 단계는 `select_sources`다.
- 한편 `review_removal()`은 그래프가 `COMPLETE`여야 시작점 제거를 허용한다. 그 전에 `verify_impact_delivery()`로 같은 preview hash의 모든 영향 페이지 제시도 요구한다. 그래프가 재개되면 graph hash 및 preview hash가 바뀐다.
- `DEFER`도 이미 채택된 시작점에는 그대로 유지하는 동작이다. 연결 evidence를 개별 제외하려 하면 ‘linked evidence is protected’로 거절한다. cm-040 trace에서 실제 해당 거절과 재시도는 확인했다.

**그래프가 커서 미완료 → 미완료라 시작점 제외 불가 → 다음 view에서 더 탐색**하는 제어 제약이 있다. 실제로 시작점 REJECT를 시도해 이 조건에 거절된 실행까지 확인한 것은 아니다. 완료 전 제거 금지와 hash 조건은 코드로 확인한 차단 경로이며, 실제 관측한 것은 linked evidence 거절 및 자동 증가다.

소유·유실 검토는 유지하되 탐색의 중단/재개, 새로운 확장 동결, 현재 확보분에 대한 검토를 독립 상태로 다룰 필요가 있다. 세부 설계·계약 검증 전까지 바로 제거 허용으로 바꾸면 안 된다.

## 7. 탐색 범위·전체 원문 보존·실제 모델 제시는 별도 규모

ADR0524/cm-040의 실제 도달 블록 합집합은 원문 약364만 자다. 도달 source의 전체 원문을 보존하면 약841만 자다. 후보의 `build_bundle()`는 이 전체 원문과 graph를 담도록 구현돼 있다.

그러나 ADR0524의 세 trace에는 실제 저장된 최종 `source_bundle`이 없다. **841만 자가 모델에 전송됐거나 최종 묶음으로 저장됐다고 주장하지 않는다.** ADR0523/cm-009에는 1,027개 source·1,792,153자의 전체 원문 묶음이 실제 저장돼 있다. 이 역시 모델에 모두 제시됐다는 뜻은 아니다. 전체 원문 보존은 의도된 기능이며 문제는 이것을 탐색 범위·모델 입력과 혼동하거나 매번 중복 직렬화하는 데 있다. 모델 입력 증폭에 대해서는 앞의 실제 view만 근거로 삼았다.

별도의 자동 READ 큐(`workflow_relations_tools.prefetch_direct`)는 읽기·문자 예산을 사용한다. protected graph는 자체 walk 예산과 checkpoint를 사용한다. 자동 READ가 제한됐다는 이유만으로 서버 그래프까지 같은 규모로 제한된다고 볼 수 없다. cm-040 trace의 evidence는 4개인데 graph source는 5,870개다. 둘을 같은 회수/제시 수로 보고하면 안 된다.

## 수정 범위와 남은 확인

| 층 | 확인한 문제/성질 | 필요한 확인 |
|---|---|---|
| 원문 구조 | 목 아래 번호·목 병합·역할 오분류 | 새 구조에서 원문 span·부모·역할 검증 |
| 참조 연결 | 잘린 좌표·나열 누락·머리/단서·정역 범위 | 전체 mention 해석 및 양 끝 범위 검증 |
| 확장 의미 | 공통 조문 역참조, 일괄 개정문을 통한 연결 | 관계 용도·시점·질문 채택과 DB 연결 분리 |
| 탐색 실행 | 도착 경로별 상태 증가, 자기 상태 재큐잉 | 왕복 제한·소유 관계를 보존하는 처리 중복 제거 |
| 제어 | 화면 생성 때 재개, 완료 전 제외 차단 | 동결·재개·미완료 검토·유실 확인 계약 |
| 제시/정리 | 영향 검토의 반복 순회·입력 점유, 종료 후 재조회 | 연산 공유·페이지 우선순위·deadline 후 안전한 결과 반환 |

이번 감사는 원인 전수 확인도, 수정 후 성능 인증도 아니다. 특히 모든 도달 관계의 좌표 정확도, 질문별 필요한 근거 판정, 모든 부칙의 시점 적합성, 새 구조의 표/각주/셀 참조, 전체 원문 묶음 직렬화의 실제 비용은 남아 있다.

후속 실험에서는 단계별로 **새로 발견한 원문 범위 / 기존 범위의 재방문 / 단순 보존 / 실제 제시 / 채택 / 인용**을 따로 측정해야 한다. 정·역참조를 임의로 잘라 개수만 줄이는 것을 성공 기준으로 삼지 않는다. 정확한 연결과 회수 보존을 확인하면서 증폭 원인별로 분리 검증해야 한다.
