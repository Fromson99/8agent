# 구조·참조·탐색 증폭 통합 수정 설계

2026-09-23. **제안 설계이며 제품 구현·새 실험·DB 재구축·활성화는 미실행.** 기존 조사 결과를 보존하면서 변경 책임과 검증 순서를 통합했다. `implementation-design-report` 스킬 적용, 자체 검토. 독립 검토·실행 성능 인증은 아니다.

## 1. 권고

기존 구조화·색인·요청 세션을 수정한다. 핵심은 다음 책임의 분리다.

`불변 원문 → 실제 계층/문자 범위 → 원문에 명시된 관계 → 요청별 탐색 범위/대기 경로 → 모델 제시 → 답변 채택`

원문을 보존했다고 모두 탐색하지 않고, 연결됐다고 모두 질문 근거로 채택하지 않는다. 정·역참조와 나열 대상은 보존하며 미처리 경로는 이유·재개 위치와 함께 남긴다. 개수 감소를 품질 성공으로 대체하지 않는다.

사용자 보완 방향을 반영했다. **구조화 때 적용한 틀과 실제 마디 경로를 기준으로 연결점 세트를 만들고, 이를 참조 해소와 탐색 진입점의 공통 기반으로 사용한다.** §3의 ‘구조화 틀 기반 연결점 세트’가 그 구체 계약이다. 나머지 실행 안정화·제어·제시·검증 방향은 유지한다.

## 2. 기준 코드·실행과 변경 지도

## 3. 공통 범위 계약부터 정의

아래 필드와 상태명은 모두 제안이다. `DATA_MODEL.md`, 구조 manifest, navigation schema와 consumer를 함께 버전 변경한다. 기존 HTTP의 질문·답변 형태는 유지하되 원문 범위·경로의 추가 계약을 명시한다.

### 구조화 틀 기반 연결점 세트 — 사용자 방향 반영

**확인한 기반:** 감사 대상 공개 문서 모두 `document.json`에 ladder, fingerprint, applied가 저장돼 있다(F-F, [저장 틀 확인 자료](frame_anchor_basis.json)). `source_unit`에는 실제 부모·마디·표면형·범위가 있다. 일반 구조화의 `fingerprint.Ledger`는 문서군 틀의 반복 관측/동결을 기록하며, recipe 경로의 `save_result()`는 recipe/규칙/tree hash와 coverage를 저장하도록 구현돼 있다. 이 recipe 저장 경로는 코드로 확인했으며 이번 공개 DB의 모든 문서가 recipe 방식으로 생성됐다는 뜻은 아니다.

**이미 있는 부분의 한계:** 후보 `term_references.compile_references()`의 frames/shapes는 조 아래 child/grandchild까지만 좌표 세트를 만들고, 표기 정규식도 하위 marker를 두 번까지만 받는다. 매치한 좌표를 못 찾으면 `whole[:cut]`을 줄여 앞부분이 유일한 대상에 연결한다. 별도 법문 SUBPATH는 항·호·목을 처리하지만 목 아래 세부 표기에는 이르지 못한다. `frame_roles()`는 문서 전역 틀의 계열에 항→호→목을 다시 붙여 원래 구조 의미를 잃을 수 있다. 그러므로 기존 틀 기반 기능을 전체 경로·문맥·span까지 완성하는 것이 변경의 중심이다.

제안 흐름:

`선택 세대의 적용 틀/영역 + 실제 source_unit 트리 → 연결점 세트 → 전체 인용 표현과 문맥 해석 → 유일한 경로·원문 범위 검증 → 정역 관계/탐색 진입점`

연결점 세트는 새로운 별도 DB나 별도 파이프라인으로 만들지 않는다. 기존 `compile_index()`가 원문 store에서 생성하는 navigation 산출물 안에 만든다. 정확한 저장 테이블/필드 버전은 후보 구현 전 schema에 고정한다.

| 제안 구성 | 내용 |
|---|---|
| 틀 결속 | generation/store hash, document version, 적용 parser/recipe의 명시 ID·hash, 영역/template ID(존재할 때), ladder hash, 구조 tree hash. 없는 recipe 정보를 생성하지 않음 |
| 연결점 | namespace + unit ID + 실제 부모 ID 체인 + 각 단계의 원표기/family/ordinal/검증된 역할 + own/subtree 문자 span |
| 조회 키 | 문서/버전/영역 및 부모 경로 아래 `(표기 계열, 번호, 가지번호)`; 검증된 역할이 있으면 `제N항/제N호/가목` 별칭도 같은 마디에 결속 |
| 시작점 후보 | 인용의 명시 문서·조/별표 또는 증명된 생략 문맥으로 좁힌 anchor ID 집합. 후보 수와 미해석 잔여 표현을 유지 |
| 확정 조건 | 전체 인용 소비, 문맥 증거, 실제 부모 경로, 원문 번호/span, 버전/권한이 모두 일치. prefix만 일치하면 정확한 연결로 승인하지 않음 |

세트는 **틀에서 가능한 모든 번호 조합**이 아니라 실제로 존재하는 마디의 경로 목록/트리다. 같은 `1)`이 여러 목 아래 반복되면 부모 경로로 구별한다. 조회는 접두 경로를 공유하는 트리 색인을 사용할 수 있지만, 긴 인용의 앞부분만 찾은 것을 성공으로 반환하지 않는다. 문서군 fingerprint는 틀 재사용의 단서이며 문서 버전·원문 동일성의 증명이 아니다.

문서 전역 ladder만으로 경로를 재생성하지 않는다. 한 문서의 본문·부칙·별표에서 틀이 다르거나 같은 family가 다른 층에 나타날 수 있다. 실제 적용 영역과 `source_unit.parent_id` 체인을 우선 대조한다. 구조 틀을 다시 항·호·목 고정 순서로 압축하지 않는다.

공통 좌표 해석은 기존 `lawrag.core.legal_coordinate`를 변경 지도에 포함한다. 현재 그 문법에도 호칭·별표·괄호 좌표의 지원 범위가 있으므로 그대로 완전한 parser라고 간주하지 않는다. 문서에 실제 있는 표기를 틀에서 인식하고, `같은 항`, 범위, 나열 등 공통 문법을 그 위에 적용한다. 동적인 표기와 법적 호칭의 연결은 검증된 역할로만 한다. 질문의 좌표 찾기·본문 참조·gap 검증이 서로 다른 규칙으로 재해석하지 않게 하되 최종 증명은 원문과 독립 대조한다.

예를 들어 원문과 보정 구조가 `제113조 → ② → 5. → 가. → (2)`를 보유하면 `제113조제2항제5호가목(2)`를 해당 anchor의 span으로 연결한다. 구조가 가목까지만 있으면 **남은 `(2)`를 STRUCTURE_GAP으로 남긴다.** 가목 anchor를 확인 후보로 제시할 수 있지만 정확한 목적지나 완료된 탐색 진입점으로 바꾸지 않는다. 틀에서 누락된 하위 번호는 구조 복원 단계에서 먼저 보완해야 한다.

‘시작점’도 두 종류를 구분한다. 이 세트가 찾는 것은 **인용을 해소하거나 원문 탐색을 시작할 구조 좌표**다. 질문의 검색 시작점은 검색/읽기/채택 경로와 이유를 별도로 가져야 한다. 한 문서의 모든 연결점을 만들었다고 그 모두를 질문의 SEARCH_ROOT로 등록하지 않는다.

검증에 추가할 항목: 동일 표기의 다른 부모·영역, 같은 틀의 다른 문서 버전, 문서 일부에만 있는 하위 계열, 존재하지 않는 번호, 인용의 뒤쪽만 미해석인 경우, 공통 문법과 저장 좌표의 일치, 구조 수정 후 anchor/검색 cursor/관계 재결속. 틀 존재 여부만으로 이 검증을 통과한 것으로 간주하지 않는다.

### 구조 마디

- `unit_id`, `parent_id`, `marker_surface`, `ordinal`, `marker_family`, `structural_role`, `role_basis`.
- `own_spans[]`: 마디 자체의 머리 문언. `subtree_spans[]`: 자손까지 포함한 범위. 부모·자식 범위의 포함 관계를 검사한다.
- span은 `(document_version, block_id, start_cp, end_cp, block_hash)`로 지정한다. Unicode 코드포인트의 반열린 구간 `[start_cp,end_cp)`이며 원문 정규화 후의 다른 문자열 offset을 쓰지 않는다.
- 목 아래 `1)`, `(1)`, `(가)`는 문서에서 확인한 계층을 사용한다. 깊이만으로 법적 호칭을 부여하지 않고, 역할이 미확인이면 표기·부모·번호는 보존하되 역할 확정은 보류한다.
- 한 블록의 여러 번호는 불변 원문을 그대로 두고 서로 다른 span으로 표현한다. block을 재분할해야 하는 입력 경로는 새 세대와 원본→새 블록 offset 대응을 함께 생성한다.
- 표/셀/주석은 기존 attachments·native_metadata와 실제 원본 좌표를 유지한다. 셀 주소를 찾지 못한 경우 표 전체를 정확한 셀 연결로 승인하지 않는다. 법령 XML만 수정하고 다른 형식에 같은 개선이 적용됐다고 보고하지 않는다.

`term_index.root()`의 조 중심 묶음은 전문 보존/검색 단위로 유지할 수 있다. 다만 별표/부칙/조가 없는 문서에도 각 구조 마디의 span을 인덱싱해야 한다. `top==uid`라 생략되는 마디의 상세 범위가 소비자에서 복구 가능한지 검사하고, 모든 문서를 조 구조에 강제로 끼워 넣지 않는다.

### 명시 참조 — 제안 `reference-scope-v2`

- 전체 `mention_spans`, `requested_path[]`, `context_proof`, `qualifiers`, `resolved_extents[]`, `coverage_state`.
- 원문상의 인용 출발 범위와 대상 범위를 모두 보존한다. 버전, namespace(본문/특정 부칙/별표 등), 원본 hash를 결속한다.
- `나목 및 다목`은 두 대상을 보존한다. 하나만 해석됐으면 성공한 구성요소와 미해석 구성요소를 분리하고 묶음 전체를 완료로 표시하지 않는다.
- `같은 항`은 인용 문맥의 선행 항에서 상속하며, 현재 인용문이 놓인 항으로 몰래 대체하지 않는다. 동률 후보는 모호 상태다.
- `단서`, `각 호 외의 부분`, `본문`은 범위 연산이다. 단서가 여러 개여서 유일하게 찾을 수 없으면 검사 대상으로 남긴다. 부모 전체로 대체한 EXACT는 금지한다.
- 일반 인용·준용·일괄 개정·시행/적용례의 단서는 술어 원문과 연결한다. 의미 재작성 Rule/조건식이나 법적 결론 정본을 재도입하지 않는다. 해석이 필요한 역할은 observation/UNKNOWN으로 유지한다.

| 범위 | 용도 | 자동 확장 권한 |
|---|---|---|
| 전체 원문 | 확인·감사·출처 열기 | 없음 |
| 문맥 범위 | 부모 머리, 필요한 앞뒤 문언을 함께 읽기 | 그 자체로 없음 |
| 탐색 범위 | 현재 조·항·호·목·세부 span에서 다음 참조 발견 | 이 범위와 증거 검증을 통과한 경로 |
| 제시/채택 범위 | 모델에 실제 전달한 구간·답변에 채택한 근거 | 각각 별도 판단/receipt |

예: `가목(2)`는 `(2)`의 span을 탐색하되 가목의 공통 조건은 문맥으로 함께 제시한다. 문맥에 형제 `(1)`을 확인 목적으로 포함했다는 이유로 `(1)`의 모든 인용을 탐색하지 않는다. 반대로 그 형제가 필요하다고 판단하면 이유를 남겨 탐색 범위를 확장한다.

## 4. 참조 발견과 자동 확장의 구분

정방향은 active span 안의 **전체 mention**을 확인한다. 문자 일부만 겹쳤거나 끝을 읽지 못하면 확정 이동이 아닌 확인 후보다. 필요한 선행 문맥은 별도 context proof로 검증한다.

역방향은 도착한 세부 범위와 DB target 범위의 관계를 반환한다. 같은 세부 대상을 지목한 경우와 조 전체 인용이 일부 겹치는 경우를 구분한다. 후자를 세부 규정에 대한 정확한 참조라고 표시하지 않는다. 단순 교집합을 근거로 source 전체에 자동 진입하는 경로를 없앤다. 후보 관계는 보존하고 추가 확인·범위 확장 판단이 가능해야 한다.

일괄 개정문은 개정 대상과 변경 문언을 유지한다. 한 개정문에 공동 열거됐다는 이유만으로 다른 모든 대상을 질문 근거로 자동 채택하지 않는다. 개정 이력이 쟁점이면 해당 경로를 계속 탐색한다. 역할·시점이 불확실하면 지우지 않고 확인 대기 사유를 남긴다. 역할명이 UNKNOWN이라는 이유만으로 연결을 일괄 차단하지 않는다.

공통 조문에 대한 역참조가 많으면 **정확히 연결된 관계도 계속 늘어날 수 있다.** 관계를 발견한 기록과 그다음 확장 필요 판단을 분리한다. 쟁점별 진전·범위·관계 용도에 따라 다음 작업을 배정하고 보류 목록을 보존한다. 검색 결과의 이름 유사도는 DB 관계를 대신하지 않으며 독립 시작점으로만 기록한다.

## 5. 탐색기의 안전한 수정

### 먼저 바꿀 사항

1. queue, in_progress, expanded를 구분한다. 처리 중인 상태는 다시 넣지 않고, 꺼낸 상태가 이미 완료됐으면 건너뛴다. 처리 완료 표시는 모든 관계 처리를 마친 뒤 한다. 미리 완료 처리해서 중단 후 누락되는 수정은 금지한다.
2. 큰 이웃 목록도 관계별 cursor로 처리한다. 상태·관계·소유 전파의 중간 진행 위치를 checkpoint에 보존한다. 시간 예산은 이웃 수집, 소유 전파, 영향 계산, 저장/정리까지 포함한다.
3. cache key는 세대·문서 권한 범위·정규화 span·관계 계약·gap receipt revision에 결속한다. 같은 블록의 서로 다른 문자 범위를 합치지 않는다.
4. 원문·물리 범위·관계 증거는 한 번 저장하고, 경로 영수증은 그 ID를 참조한다. 동일 물리 범위의 neighbors와 반증 가능한 증거를 공유한다.
5. 자동 READ 큐와 protected graph가 공통 범위/진행 기록을 소비하게 한다. 읽기 예산과 탐색 작업 예산은 구분하되 한쪽 제한이 다른 쪽도 제한한다고 보고하지 않는다.

### 도착 경로별 상태 병합은 별도 단계

초기 수정에서는 `return_guard`의 의미를 유지한다. 이를 state key에서 제거하는 한 줄 수정은 하지 않는다. 같은 범위라도 들어온 관계에 따라 허용되는 반환이 다르기 때문이다.

후속 최적화는 물리 마디와 `(도착 관계, 방향, 이전 범위, 소유 시작점)` 지원 기록을 분리하고, **새로 추가된 지원/소유 정보만** 전파하는 방식으로 설계한다. 한 시작점의 허용 경로를 다른 시작점에 잘못 전파하거나 동일 관계 왕복으로 부모 범위를 넓히지 않는지 증명해야 한다. 이 동등성 검증 전에는 메모리 공유·캐시와 동일 논리 상태의 재처리 방지만 채택한다.

소유 시작점 제거 시 단순 감소 카운터만으로 순환 그래프의 도달성을 판단하지 않는다. 남은 독립 시작점으로부터 유효 경로를 다시 검증하거나 동등성이 검증된 동적 도달성 방식을 사용한다. 서로를 인용한다는 이유로 독립 대체 근거가 생겼다고 보지 않는다.

## 6. 검토 중에는 그래프를 고정

`view()`와 최종 bundle 생성은 현재 revision을 읽기만 한다. 새 탐색 작업은 기존 요청 세션의 명시적인 advance 작업으로 실행하고 action/예산/결과를 journal에 남긴다. 새 별도 실행기를 만들지 않는다.

제안 상태:

- `RUNNING`: 진행 가능.
- `FROZEN_FOR_REVIEW`: 그래프·소유·대기 목록·preview hash를 고정하여 검토.
- `SUSPENDED_WITH_FRONTIER`: 확보 원문과 미확인 frontier를 유지한 채 추가 확장 보류.
- `COMPLETE`: 정해진 범위에 미처리 항목이 없음. 법적 충분성·전체 코퍼스 회수 인증은 별도.

시작점 관련성이 의심되면 먼저 그 시작점의 **추가 탐색을 보류**한다. 이미 확보한 근거, 다른 시작점과의 공유분, 미확인 frontier는 남긴다. 전체 그래프가 완성돼야만 보류할 수 있게 하지 않는다.

영구 제외·현재 답변에서의 비채택·추가 탐색 보류는 다른 결정이다. 영구 제외는 동결 snapshot의 실제 손실, 대체 근거의 독립성·질문 쟁점 충족, 미확인 frontier를 검토한 receipt를 요구한다. 미확인 부분을 남겨 두고 답변해야 한다면 그 한계를 기록하며 ‘전체 유실 없음/탐색 완료’로 바꾸지 않는다. 이미 인용한 근거를 제외하면 의존 claim을 무효화하고 재검토한다.

검토 중 범위·권한·gap 증명·데이터 세대가 바뀌면 기존 preview 승인과 cursor를 무효화한다. 단순 페이지 열기로 graph hash가 바뀌게 하지 않는다.

## 7. 영향 계산과 모델 입력

`removal_preview()`의 coverage를 graph revision당 한 번 만든다. `(source, span segment) → owners`와 `owner → exclusive segments` 역색인을 함께 만든다. 겹치는 문자 구간은 경계별로 분할해 실제 소유를 계산한다. 블록 전체를 소유 단위로 사용해 부분 손실을 가리지 않는다.

평상시 모델 입력은 쟁점, 현재 원문, 필요한 부모 문맥, 직접 관계와 미확인 상태를 우선한다. 제외 영향은 요약·해시·상세 페이지 위치만 보내고, 실제 제외 검토 모드에서 해당 시작점의 상세를 제시한다. 페이지마다 전달 여부와 revision을 기록한다.

큰 원문 자체도 부분 전달을 지원하되 원문을 임의 요약해 대신하지 않는다. 미제시 구간·다음 cursor를 유지하고 실제 전달되지 않은 문언을 읽었다고 표시하지 않는다. 서버 원문 보존 크기와 모델 입력 크기는 각각 계측한다.

요청 종료 시 검증된 journal/checkpoint로 PARTIAL 결과를 만든다. deadline 후 대규모 원문 재조회가 필요한 metadata 계산을 줄이고 미완료 항목은 미확인으로 반환한다. 권한 검증을 생략하는 최적화는 하지 않는다. 최종 묶음은 필요 시 hash가 고정된 조각으로 저장하되 기존 원문 열기·검증 API가 이를 읽도록 함께 이행한다.

## 9. 구현·재구축 순서

1. **계약·기준 고정:** 이번 단계는 설계다. 실제 후보 구현/효과 비교 전에 실험 표준을 끝까지 읽고 동일 scope reservation 확인, 새 ADR 선점, 정확한 부모·코드·DB·평가 기준 동결. 과거 Gemma 사용은 새로운 모델 선택의 자동 승인이 아니다. 새 외부 실험은 현행 모델 정책과 명시 사용자 지정에 따른다.
2. **범위 변경 없는 실행 안정화:** 자기 재큐잉 수정, 영향 역색인, view의 부작용 제거, 안전한 checkpoint·종료. 알려진 범위를 바꾸지 않고 실행 상태 계약부터 검증한다.
3. **구조와 parser 이행:** 명시 역할·하위 번호·문자 span, 전체 참조 해석, 양 끝 검증. 원문 텍스트 보존과 구조 의미를 독립 확인한다.
4. **새 세대 생성:** 구조가 빠진 문서는 구조부터 재생성한다. 정상 구조 문서는 검증된 재사용으로 비용을 줄일 수 있지만, 통합 세대에서는 관련 소비자를 모두 다시 결속한다.
5. **검색 소비자 재생성:** 관계·역참조·검토 후보뿐 아니라 구조 좌표, 용어 출현, 정의 연결, lexical/fulltext, 세대 manifest·서비스 설정을 확인한다. 조 ID가 unit ID에 의존하므로 노드 추가로 source ID가 바뀔 수 있다. 이전 ID/근거는 원본 hash·문자 범위로 이행 관계를 남기며 임의 동일시하지 않는다. 순수 관계 재생성도 fulltext navigation binding을 다시 검증한다.
6. **요청 제어·제시 통합:** 같은 Coordinator/StageRunner에서 탐색 advance·동결·검토·재개, 원문과 문맥, presentation receipt까지 연결한다. scope를 이해하지 못하는 구 reader에 상세 계약을 자동 축소해 넘기지 않는다.
7. **검증 후 별도 도입:** 기능/계약 → 고정 시작점 비교 → 전체 검색 실행 비교 → 별도 보류 문서/질문 확인. 통과한 후보만 저장소의 hash 고정 promotion·receipt 절차로 활성화한다. 코드·원문·navigation·fulltext·설정 조합으로 함께 롤백한다.

단계는 원인별 검증 단위이기도 하다. 수정 전체를 한 번에 실행한 결과만으로 어느 변경이 누락을 만들었는지 판단하지 않는다. 결과를 확인한 뒤 만든 후속 후보는 새 ADR 계보로 남긴다.

## 10. 검증 기준

**구조·참조 계약:** 발견 사례를 개발 회귀로 고정하고 원문으로 독립 작성한 예상 경로와 비교한다. 같은 parser의 출력을 정답으로 사용하지 않는다. 번호 반복·항 생략·나열·다단 범위·문맥 전환·표제·자기 인용·부칙 namespace·버전 모호성·한 블록의 여러 번호·표 셀/각주를 포함한다. 발견 사례 통과를 전체 법령 정확도로 확대하지 않는다.

**탐색 계약:** 부분 span 밖의 형제에 자동 진입하지 않음, 나열 target 보존, 정역 방향 일치, 같은 관계 왕복 방지, 다른 유효 경로 보존, 공유 소유와 순환에서 제거 영향 정확성, 처리 중단/재개와 일괄 처리의 결과 동등성, 완료/대기 집합 불일치 없음, 권한 밖 경로 없음. 구 코드의 잘못된 범위 확대까지 동등하게 유지하는 검사는 하지 않는다.

**제어 계약:** 같은 snapshot의 view 반복 생성으로 graph/frontier가 바뀌지 않음. 확장 보류는 완료를 전제로 하지 않음. 미확인 frontier를 탐색 완료로 바꾸지 않음. 선택 범위/근거 변경 시 관련 claim·preview가 무효화됨. 종료 정리가 이미 중단된 DB 쿼리에 의존하지 않음.

**품질·비용 비교:** 같은 시작점 및 원문 span 비교와 전체 검색 실행을 분리한다. 없어지거나 추가된 근거를 source 수가 아닌 원문 구간·관계·단계별로 판정한다. 별도 보류 표본은 같은 조문에서 파생된 질문을 독립 표본으로 과대 계산하지 않는다. 필요한 근거의 회수·제시·채택·인용과 미완료율, 새 물리 범위, 재처리, 대기량, 전체 지연/사용량을 함께 본다. 허용 회귀는 결과를 보기 전에 동결하며 지금 임의의 회수율/속도 목표를 확정하지 않는다.
