## 1. 결론

기존 코스닥 규정 사례 외에도 서로 다른 문서에서 **목 좌표 손실, 범위 인용의 상위 항 혼동, ‘같은 항’ 문맥 손실, 별지 가지번호 손실과 자기 표제 오인용**을 확인했다. 원문과 구조가 존재하는데 생성기가 다른 대상을 `EXACT`로 저장하는 경우다. 이름 유사도 검색이나 LLM의 탐색 결정을 원인으로 볼 사례가 아니다.

우선순위는 **참조 표현 전체 해석 → 잘못된 연결과 누락 동시 수정 → 새 DB 생성 → 범위 전달 검증 → Gemma 회수 검증**이다. 모델 프롬프트를 먼저 바꾸거나 연결 개수를 제한하면 이 결함이 해결되지 않는다.

특히 `나목 및 다목`이 상위 호 전체로 저장된 사례가 있다. 넓은 연결 덕분에 누락된 다목 원문까지 우연히 들어온다. 목 잘림만 수정해 나목으로 좁히면 다목을 새로 놓칠 수 있다. 사용자가 우려한 “과도한 탐색이 누락을 가렸을 가능성”이 실제 좌표 사례로 확인된다. 다만 기존 전체 회수 성능이 이 원인에 얼마나 의존했는지는 아직 측정하지 않았다.

| `context_proof` | 각 생략 좌표가 어느 앞선 표현·문서 버전에서 상속됐는지 |
| `qualifiers` | 단서·본문·전단·후단·각 호 외의 부분·제외 등. 문법과 대상 구조가 다르면 미확인 유지 |
| `resolved_extents[]` | 각 대상의 source/unit/block/필요시 문자 범위, 원문 증거와 버전 |
| `coverage_state` | 전체 표현이 해석됐는지, 구조가 빠졌는지, 문맥이 모호한지. 구체 enum은 구현 전 schema에서 동결 |
| `relation_role` | 인용·준용·위임 등 역할과 해당 술어 원문 span. 역할 UNKNOWN과 좌표 불확정을 분리 |
| `route_class` | 기존 SEARCH_ROOT / DB_REFERENCE / gap 보완의 구분과 소유 시작점·receipt |

**공통 규칙:** 원문에 더 구체적인 좌표가 있으면 상위 좌표로 대체한 결과를 EXACT로 승인하지 않는다. 부분 문언을 아직 찾지 못했더라도 조 전체 원문은 확인용으로 보존한다. 그 상태를 자동 재귀 탐색이 완료된 것처럼 처리하지 않는다.

`나목 및 다목`은 부모 호로 합치지 않고 두 범위를 저장한다. 다목을 해석하지 못하면 해당 구성 요소를 미확인으로 남겨 추가 확인하게 한다. 정상 나목 연결까지 무조건 폐기하는 방식은 피하되 전체 묶음의 미완료 여부는 유지한다.

단서가 한 블록 안에 있으면 `block_ids`만으로 충분하지 않다. 원문 문자 범위를 표현해야 한다. 여러 ‘다만’ 중 어느 부분인지 불명확하면 기계적으로 마지막 문장 등으로 정하지 않고 검사 대상으로 남긴다.

## 7. 탐색 원칙과 정상·실패 흐름

| 상황 | 처리와 결과 |
|---|---|
| 전체 좌표·문맥·대상 구조가 일치 | 유효한 DB 관계로 이동. 실제 들어간 범위를 유지하며 하위 정방향·역방향·준용·위임 탐색을 계속함 |
| 현재 DB가 잘린 좌표를 EXACT로 저장 | 새 계약 검사에서 gap 처리. 원문과 정확한 대상 확인 후 보완 receipt로 진행. 구 행을 그대로 신뢰하지 않음 |
| 항·호 구조가 DB에서 빠졌지만 원문 번호와 조상 범위가 유일 | 명시적인 DB 누락 판단과 번호·span 증명으로 요청 내 보완 연결. 영구 DB 반영은 새 세대의 검증 경로 |
| 이름만 비슷하거나 ‘같은 항’의 선행 문맥이 여러 개 | 연결로 확정하지 않음. 확인용 원문과 모호성 보존. 별도 검색이 필요하면 이유를 기록한 새 시작점 |
| 필요한 근거가 DB 연결로 충분히 나오지 않음 | 쟁점에 따라 검색·재검색 → 새 시작점 후보 → 채택/보류/제외 판단. 기존 연결인 것처럼 합치지 않음 |
| 연결이 공유됨 | 시작점별 소유를 보존. 한 시작점 제외 시 그 시작점만 소유한 근거의 손실·대체를 보여주고 판단 |
| 시간·입력 예산 종료 | 확보 원문과 frontier를 저장해 PARTIAL로 반환. 모든 출처 채택·탐색 완료로 바꾸지 않음 |
| 정상 범위에서도 큰 그래프 | 정당한 관계가 큰 것과 오연결을 구분해 측정. 임의 개수·깊이 제한으로 품질 통과를 만들지 않음 |

사용자 요구대로 **시작점에서만 역참조를 허용하는 제한은 넣지 않는다.** 하위에서 찾은 유효한 관계도 계속 탐색한다. 순환 중복 처리는 같은 범위·경로 상태의 재방문을 줄이는 것이며 새로운 범위나 다른 시작점의 소유를 지우면 안 된다.

4. 원문·제목·색인 정규화 입력이 동일하면 그 동일성을 전체 행으로 검증한 receipt를 전제로 전문검색 바이너리를 재사용하고 새 연결 manifest/config를 생성한다. 입력이 다르면 전문검색도 재구축한다. 단순 hash 문자열 교체는 허용하지 않는다.

## 9. 검증 순서와 합격 판단

### 9.1 모델 없이 먼저 검증

- A~F의 전체 표현과 정확한 target path를 원문 대조 회귀 자료로 고정한다. 발견 사례는 개발 사례이므로 일반화 성능으로 보고하지 않는다.

- 원문 숫자를 바꾸면 해당 대상만 바뀌는지, 목 뒤에 형제 목을 추가해도 그쪽으로 새지 않는지, `나목 및 다목`에서 두 대상이 모두 남는지 확인한다.
- 명시 부모와 현재 위치가 다른 범위, ‘같은 항/호’ 문맥 전환, 가지번호가 있는 별지, 여러 블록의 자기 표제, 인용 대상 구조 누락을 정상/실패 쌍으로 검사한다.
- 새 parser와 gap 증명기가 같은 코드를 쓴다는 이유로 통과시키지 않는다. 기대 경로는 원문·구조를 별도로 대조해 정한다.
- 기존 정·역참조 재귀, 공유 소유권, 순환 처리, gap 보완, 독립 새 시작점, PARTIAL 재개 검사를 유지한다. 기존 테스트의 구 article fallback 기대값도 새 계약과 대조한다.

Gemma는 사용자 지정 모델을 유지한다. 실제 model ID/provider/FP8·thinking 설정은 기존 완료 기록을 출발점으로 새 실험 전에 확인·고정한다. 자동 모델·공급자 fallback을 넣지 않는다. 이전 실험은429와 timeout이 섞여 있으므로 안정적인 기준 성능으로 사용하지 않는다. 안정적인 호출이 확보되지 않으면 해당 비교는 품질 미확인으로 남긴다.

### 9.3 통과 조건의 의미

- **계약 목표:** 확인된 잘못된 EXACT 연결을 반복하지 않음. 누락 좌표를 상위 좌표로 숨기지 않음. 증명되지 않은 후보가 역참조 확정 색인에 들어가지 않음.
- **회수 목표:** 기존에 필요하다고 확인한 근거가 빠지면 원문·부분 범위·빠진 단계를 설명하고 복구 경로를 검증함. 단순히 원문 수가 줄었다고 개선으로 판정하지 않음.
- **일반화 목표:** 이번 여섯 사례의 번호·문서명에 의존한 예외 규칙 없이 별도 보류 문서와 표기 변형에서도 계약이 유지됨.
- **성능 수치:** 90/90을 강제하지 않는다. 안정적인 기준 재측정과 사용자 쟁점 기준으로 허용 회귀를 사전 설정한다. 이번 계획은 기존 약100% 회수를 보장하지 않는다.
