## 1. 결정 요약 — 무엇을 만들 것인가

> 모델은 원문을 보며 필요한 법령을 찾아가고, 읽은 내용에 따라 질문의 해석과 잠정 결론을 고친다. 서버는 그 과정의 출처·권한·버전·예산·기록을 책임진다. 더블하네스는 이 탐색을 지원하고 통제하는 두 종류의 계약이지, 모델에게 작성시킬 두 개의 장부가 아니다.

사용자가 지향하는 것은 상위 검색 결과만 잘 요약하는 시스템이 아니다. 검색은 출발점이며, 원문에서 발견한 위임·예외·정의·충돌을 따라 더 찾아보고, 필요한 경우 이전 판단까지 수정하는 시스템이다. 더 많은 호출이나 더 많은 조문 채택 자체는 성공이 아니다.

이번 설계의 선택:

1. **탐색 부품을 먼저 보존한다.** 형태소 FTS·질문의 조문 지목·서버 선읽기·문서 구조·정의·양방향 참조를 새 경로에 실제로 연결한다. 이름만 같은 substring 검색으로 대체하지 않는다.
2. **본문을 두 종류로 노출한다.** 탐색 발췌는 읽기 선택용이며 인용 불가. 검증된 READ 결과가 모델 입력에 실제로 제시된 뒤에만 답변 근거로 사용할 수 있다.
3. **모델 프로토콜을 줄인다.** 모델은 짧은 카드/근거 별칭으로 검색·읽기·선택·작성·이의 제기를 한다. DB ID, expected_version, 임시 ID, 장부 갱신 순서는 서버가 관리한다.
4. **장부 완성을 답변 입장권으로 삼지 않는다.** 유효하고 제시된 근거가 있으면 작성할 수 있다. 조사 중 issue→assessment→finding을 모두 생성해야만 작성할 수 있는 v1 경로는 계승하지 않는다.
5. **검토는 고칠 곳을 지목해야 한다.** 읽을 자료가 부족하면 재탐색, 자료는 충분하지만 해석·표현이 틀리면 재작성한다. 형식 오류나 검토 누락을 법률적 부정 판정으로 바꾸지 않는다.
6. **한 번에 모두 활성화하지 않는다.** 탐색 복원+서버 기록 → 발췌 효과 → 표적 검토 순으로 효과와 회귀를 분리한다.

기술적으로 연결 가능한 설계지만 품질 개선은 미검증이다. 최초 구현 범위는 검색 동등성·서버 기록·실제 입력까지 도달하는 발췌 계약이다. 적극적인 검토 제어는 그 뒤 별도 관문을 둔다.

### 앞선 발췌 설계에서 바로잡는 부분

- cm-003을 일반적으로 “세칙을 읽지 않아 실패”로 설명하지 않는다. ADR-0461 run1에는 세칙 제23조를 읽고도 제외한 기록이 있고, ADR-0474에는 모두 읽은 뒤 검토에서 소실한 기록이 있다. 사례 ID뿐 아니라 ADR·arm·run·단계를 함께 쓴다.
- 현재 구 탐색 인덱스의 제26조 outgoing 참조만으로 세칙 제23조가 자동 해소된다고 보장할 수 없다. 역참조와 재검색이 별도로 필요하다. 미해소를 성공한 링크로 포장하지 않는다.
- READ_BATCH 반환값에 발췌를 추가하는 것만으로는 충분하지 않다. 현재 review_context에는 그 반환값이 그대로 실리지 않고 후속 context에는 이벤트 해시만 남는다. 최종 모델 요청까지 배선해야 한다.
- MultiSession.source_card는 add_candidate를 호출하는 비순수 함수다. 카드 생성 횟수로 자발 발견을 세면 안 된다. JUDGE 채택 후 해소된 outgoing 대상을 후보에 넣는 동작도 이미 일부 존재한다.
- board_offset=0이어도 검토 여부에 따라 정렬이 바뀐다. “항상 동일한 12개”와 “FTS 13위 밖 READ는 자발 탐색의 증거”는 일반적으로 성립하지 않는다. 실제 노출 경로로 판단한다.
- fulltext_rank 이후 concept_hits는 FTS 고유 순위끼리의 비교에는 영향이 없지만, 같은 unranked 값을 가진 후보 사이에는 작동할 수 있다.
- 467턴 통계는 저장된 여러 invoke 단계의 입력 통계다. 모든 값이 행동·검토 턴만의 통계이거나 새 더블하네스 전체 요청의 여유라고 간주하지 않는다.

## 3. 목표 구조 — 두 하네스는 병렬 책임, 실행은 하나

~~~text
원질문 + 서버 허용 범위 + 고정된 원문/색인 세대
                       ↓
             기존 Pipeline / 요청 Coordinator
             ↙                         ↘
 DomainHarness                         AgentHarness / Profile
 근거·권한·판본·주장 유효성              도구·탐색 전략·모델·예산·종료
             ↘                         ↙
       검색·지목·선읽기 → 원문이 보이는 탐색 화면
                            ↕
                  모델: 탐색 / 읽기 / 잠정 선택
                            ↓
                   근거 묶음 → 작성 → 표적 검토
                               ↑       │
                    재작성 ─────┘       └─ 필요한 추가 탐색

 전 과정 옆에서: 서버 소유 Journal + 별칭 해소 + 제시 영수증 + 버전·호출 회계
~~~

### DomainHarness: 무엇을 근거로 인정할 것인가

- 원문·좌표·해시·세대와 허용 범위를 결속한다. 탐색 필터는 접근권한을 대신하지 않는다.
- 발췌/제시된 읽기/잠정 선택/최종 주장을 구분한다. source 존재나 인용 문구 일치가 의미적 지지를 보증하지 않는다.
- 원질문 전체와 실제 답변을 대조한다. 조사 가설은 수정 가능하며, 가설 밖 자료의 접근을 막지 않는다.
- 단서·예외·사실조건·위임·충돌·법적 적용 시점은 모델이 판단할 대상이다. 코드가 법률 해석 정답을 인증하지 않는다.
- 미상 시행일·사실을 임의로 채우지 않는다. 확인한 부분과 한계를 분리한다.
- hard check와 semantic challenge의 효과를 다르게 정한다. Profile이 Domain의 인용·권한 규칙을 끌 수 없다.

### AgentHarness: 어떻게 도달하고 언제 멈출 것인가

- 기존 형태소 FTS·조문 지목·서버 선읽기를 시작점으로 제공한다.
- 목록/구조/정의/참조/역참조/재검색을 같은 원문 접근 경계 안에서 선택하게 한다.
- 새 원문을 보고 후보를 버리거나 다시 열고, 질문 해석·잠정 결론을 수정할 수 있다.
- 충분하면 일찍 작성한다. 근거가 모자라면 검색한다. 호출 수나 탐색 횟수를 채우게 하지 않는다.
- 실제 물리 호출, 도구 비용, 전체 요청 크기, deadline, 마무리 예산을 조정한다.

같은 모델이 조사·작성·검토를 수행할 수 있다. 더블하네스는 두 모델 사용을 뜻하지 않는다. 검토 모델을 분리해도 독립 정답 판정이 자동 성립하지 않는다.

SourceStore는 변경하지 않는다. FTS/navigation/reference/locator가 동일 source ID·좌표·generation을 가리키는지 부팅 시 검증한다. 기존 참조 resolver와 다른 색인을 쓰면 그 색인의 별도 fingerprint를 결속한다. 없는 capability는 실행 준비 실패로 보고하며 조용히 다른 검색으로 대체하지 않는다. 색인 변환이 필요하면 새 파생 세대만 만들고 MAIN/기존 세대는 보존한다.

## 5. 모델은 탐색하고, 서버는 장부를 만든다

### 5.1 근거 상태와 별칭

~~~text
발견 → 카드 발췌 제시(P) → 원문 READ 생성 → 원문 제시(E) → 잠정 선택 → 답변 주장(C)
       인용 불가           아직 미제시       인용 후보       정답 인증 아님
~~~

- P17/E4/C2는 요청 내 짧은 표시 별칭의 예다. 서버가 run/view/source/span/version을 해소한다. 영구 ID는 모델이 만들지 않는다.
- preview_complete=true여도 P는 E가 아니다. 전문 길이의 발췌도 READ 계약을 통과해야 인용할 수 있다. 단, 해시가 같은 캐시로 READ를 실현해 중복 디스크 읽기는 줄일 수 있다.
- 실제 모델 요청에 포함된 범위와 request hash를 제시 영수증으로 남긴다. 입력에 있었다는 뜻이지 모델이 이해했다는 증명은 아니다.
- 선읽기도 동일 READ 도구를 통해 evidence를 만든다. 모델 입력에 못 담은 선읽기는 presented로 세지 않는다.
- P의 “채택” 요청은 READ 예약+pending selection으로 해석한다. 아직 보지 않은 전문을 자동 채택하거나, 잘못된 별칭을 조용히 무시하지 않는다. 다음 입력에서 E를 본 뒤 선택을 확정한다.
- 모델에게 “다음 조사 행동 + 선택적 짧은 관찰 + 작성/계속 의사”만 요구한다. 순수 읽기, 변경 없음, 빈 노트는 정상이다. 현재 v1도 빈 updates를 허용하도록 바뀐 상태이므로 rev-035 결함과 구별한다.
- 모델은 E를 붙인 문단을 작성한다. 서버가 claim과 evidence 의존성을 만든다. 법적 supports/contradicts 관계는 명시적인 모델 관찰이 있을 때만 저장하며 서버가 추측해 채우지 않는다.

원질문 원문은 끝까지 보존한다. 질문 구간 ID와 조사 가설은 보조 색인이지 폐쇄된 필수 양식이 아니다. 새로운 원문으로 가설을 수정·분리·철회할 수 있고, 미처 등록하지 않은 쟁점도 답변에서 다룰 수 있다.

### 5.2 발췌 및 참조 계약

발췌 필드(제안): preview, preview_start/end, preview_length, source_chars, preview_complete, preview_suppressed. 기존 Task의 preview_chars는 전체 길이인지 표시 길이인지 모호하므로 두 필드로 분리한다. 원문 문자열과 좌표를 그대로 보존한다.

- 보드·검색·목록·직접 지목의 조문 카드: 기본 앞 200자. 첫 발췌 실험은 보드 크기 12를 유지한다.
- READ의 참조 묶음: target 카드·발췌, 출발 source/span, relation_kind, resolution, 생성 경로를 다음 모델 입력에 같이 노출한다. outgoing 최대 8건 등의 상한은 Profile 제안값이며 실제 입력 크기에 따라 더 줄인다.
- 명시적으로 해소된 참조, “이 조를 인용한 조문”인 역참조, 검색으로 얻은 위임 후보를 구별한다. 역참조/검색 후보만으로 위임의 법적 적용을 확정하지 않는다.
- 대상이 미해소이면 원문 단서와 미해소 사유를 보여 주고 정확한 지목 또는 재검색을 제안한다. 모델이 선택할 수 있게 한다. 임의의 조문을 대상이라고 채우지 않는다.
- 참조 대상이 긴 경우 앞 200자만으로 관련 항을 찾기 어렵다. 첫 실험은 위치 정책을 고정하고, 후속 후보에서 일치한 참조 span 주변 발췌를 별도 검증한다. 어느 경우에도 전문을 가장하지 않는다.
- 참조 카드가 생겼다는 이유로 자동 READ/채택하지 않는다. 서버 선읽기 정책과 모델 선택은 별도 이벤트다. C2 표시가 이후 읽기를 유발했는지는 별칭·행동·제시 영수증으로 연결한다.

### 5.3 provenance와 항법의 측정

각 후보에 initial_fts / explicit_locator / server_preread / outgoing_reference / incoming_reference / model_search / structure_navigation 경로들을 누적한다. 최초 발견 경로와 이후 노출 경로를 함께 보존한다.

model_found는 모델 행동으로 처음 추가된 후보라는 정의와 분모를 고정한다. 기존 후보를 모델이 재검색한 것, 서버 참조 확장으로 추가된 것, 단순 카드 생성은 따로 센다. “FTS 13위 이상 조문을 읽었다”만으로 자율 탐색을 입증하지 않는다.

### 5.4 저장·실패·재개

- run별 직렬 reducer, observation/decision ID 기반 중복 방지. 병렬 READ는 결과를 모아 각 성공·실패를 기록한다. 실패한 한 항목 때문에 성공한 READ 원문을 폐기하지 않는다.
- 최신 view의 별칭만 수락하고 실제 version은 서버가 검사한다. 늦은 응답·중복 이벤트는 기록하되 상태를 덮어쓰지 않는다.
- claim/근거/사실 변경 시 의존 검토를 무효화한다. 무관한 claim까지 일괄 삭제하지 않는다. 관계가 불분명하면 재검토 대상으로 남긴다.
- journal 실패를 “법률 근거 없음”으로 바꾸지 않는다. shadow 실험은 관측 실패로 무효 처리한다. active v2는 미기록 새 주장을 발행하지 않고 기존의 검증된 부분과 실행 한계만 반환한다.
- 중단 run은 interrupted로 보존한다. 자동 의미 재개를 최초 범위에 넣지 않는다. 재실행은 새 run으로 만들고 이전 run을 연결한다.
- 요청 도중 세대·허용 범위가 달라지면 결속 오류로 종료한다. 기존 observation을 새 세대 근거로 재사용하지 않는다. 실제 인증 주체 연동 없는 환경에서 사용자별 ACL 완성을 주장하지 않는다.

## 6. 작성과 검토 — 새로운 실패 병목을 만들지 않는 방법

### 6.1 작성 입구

원질문, 필요한 사용자 사실/미상 사실, 모델이 본 선택 근거, 선택적 조사 노트를 전달한다. 모든 finding/assessment를 먼저 작성하게 하지 않는다. 현재 조립기의 자유 서술+짧은 근거 별칭 방식부터 출발하고 서버가 문단별 claim을 만든다.

근거가 문맥을 넘으면 쟁점별로 나누되, 한 판단에 필요한 본칙·단서·예외·위임 부분을 함께 전달한다. 완전한 의미 단위를 담을 수 없으면 해당 판단은 미완료다. 원문의 일부만 전달하면서 “전체 검토”를 기록하거나 빈 pack을 유효 무근거 결과로 반환하지 않는다.

### 6.2 두 검사의 효과를 분리

| 검사 | 예 | 처리 |
|---|---|---|
| 서버 hard check | 없는 E, 미제시 span, 잘못된 세대, 접근 범위 밖 인용, stale claim | 해당 주장을 발행하지 않음. 형식 수리 또는 범위 제한. 다른 독립적 유효 주장 보존 |
| 모델 semantic challenge | 단서 누락, 제외와 다른 호 적용을 혼동, 사실 미상, 질문 일부 미답변 | 대상 C·원문 E/질문 구간·문제·필요 조치를 명시. 재탐색/재작성/조건부 답변으로 연결 |
| 운영 실패 | 검토 timeout, invalid JSON, 입력 초과 | 검토 미완료. “반박됨”도 “SUPPORTED”도 아님 |

검토자는 원질문 전체·실제 초안·관련 원문을 함께 본다. 스스로 만든 쟁점 목록만 검사하지 않는다. 필요한 추가 자료가 없다는 결론은 검색 0건만으로 내리지 않는다.

challenge는 문단 또는 질문 구간에 묶인 짧은 결함 보고다. 반박을 제시하면 반례 원문 위치를 요구하고, 누락·미상 사실은 질문 구간과 필요한 확인을 지목하게 한다. 서버는 지목의 유효성만 검사하며 그 해석의 진위는 품질 평가 대상이다.

처리 분기:

- RESEARCH: 판단에 필요한 원문이 없다. 구체적 다음 검색/읽기 목적을 갖고 돌아간다.
- RECOMPOSE: 원문은 충분하나 연결·조건·답변 표현이 잘못됐다. 검색을 반복하지 않고 관련 문단을 수정한다.
- BOUNDED: 예산·원문·사실이 부족하다. 독립적으로 확인한 답과 해결되지 않은 부분을 구분한다.
- CLARIFY: 사용자 사실이 있어야 달라지는 부분을 질문한다. 알려진 규정의 설명까지 모두 지우지 않는다.
- FINAL: 완료 조건을 서버가 계산한다. 모델의 “끝” 선언만으로 READY가 되지 않는다.

실제 Control 필드는 decision=RESEARCH/RECOMPOSE/FINAL과 gate=READY/BOUNDED/CLARIFY를 분리한다. 위 설명의 BOUNDED/CLARIFY를 새 decision enum으로 섞지 않는다. 의미 검토의 이견과 원문 부족도 동일한 오류 코드로 합치지 않는다.

현재 v1은 SUPPORTED claim만 통과시키는 계약이다. v2의 정책은 별도 버전으로 승인해야 하며 Profile 옵션으로 몰래 약화하지 않는다. v2에서도 미검토 claim을 확인된 법률 판단으로 승격하지 않는다. 긍정 검토와 최신 의존성이 유지된 독립 문단을 보존하고, 불확실한 문단은 제외·조건부 재작성하며 전체 상태를 BOUNDED로 둔다. 형식 실패가 전체 검토를 소실시키지 않도록 문단별 검증 가능한 단위를 저장한다.

첫 도입은 **검토 shadow**다. 검토 결과를 관측만 하고 기준 답변을 수정하지 않는다. 내부 기록에 legacy/unreviewed임을 명시하며 READY 인증으로 해석하지 않는다. 검토가 맞는 답을 지우는 비율·실제 수정 이득이 확인된 뒤 active 제어 후보를 검증한다.

| 상황 | 탐색·판단 흐름 | 사용자 결과 / 실패 처리 |
|---|---|---|

| 새 근거가 이전 판단과 충돌 | 관련 claim/검토 stale → 대조 → 수정·철회 | 최종 답변·인용·상태가 같은 revision에 결속 |
| 검토의 형식 오류/timeout | 물리 호출 기록, 제한 수리, 미완료 상태 | 오류를 반박이나 정답으로 취급하지 않음. active 정책에 따른 확인 부분만 제공 |
| 세대 변경/외부 전송 금지 자료 | 검색·preview·READ·모델 전송 단계에서 동일 경계 적용 | 전송 차단·run 결속 오류. 다른 provider fallback 없음 |

| N08 | 계산: 모든 51문항에 검토 1회 추가 시 최대 51회 추가 논리 호출 | 실제로 이전 검토를 대체하는지, 반복/수리 여부에 따라 순증 다름. 품질 이득 미검증 |
| N09 | 설계 목표: scope/미제시 인용 우회 0, 단일 send당 물리 호출 1 | 계약 fixture 통과 목표. 운영 위험 0%를 주장하지 않음 |

최초 후보는 14회 예산을 자동 확대하지 않는다. 선읽기·참조 동봉은 추가 모델 호출 없이 할 수 있지만 DB/CPU/입력 토큰·도구 예산은 소비한다. 모델이 더 많은 조문을 읽으면 전체 비용은 증가할 수 있다.

예약·실제 송신·응답 수신·형식 검증 성공을 서로 다른 상태로 기록한다. 송신 후 timeout은 과금 여부 UNKNOWN이며 무료 실패로 계산하지 않는다. 재시도는 새 물리 시도지만 중복 모델 응답이 장부에 두 번 적용되지 않게 한다. 이전에 이미 수정된 어댑터는 다시 구현하는 대신 이 계약으로 검사하고 남은 수리/영수증 경로만 보완한다.

AgentHarness는 “남은 호출 ≥ 다음 행동 + 필요한 작성·검토”일 때만 다음 행동을 시작한다. 예를 들어 새 조사 결정 1회+재작성 1회+재검토 1회는 3회가 필요하며 reserve 3을 수리에 쓰면 모두 할 수 없다. 따라서 reserve를 고정된 무료 재탐색권으로 설명하지 않는다. 재시도·형식 수리도 같은 물리 상한에서 차감한다.

각 READ 이후 별도 JUDGE를 무조건 호출하지 않고 다음 탐색 응답에서 선택/노트를 함께 받는다. 마지막 새 원문을 모델이 볼 호출도 확보한다. 못 보여준 원문은 발행 근거가 아니다. 같은 입력·질의·범위 반복은 결과 hash로 감지하되, 새 원문/사실로 검색 목적이 바뀐 경우까지 차단하지 않는다.

발췌 축소는 최종 요청을 조립한 뒤 모든 단계에 적용한다: 참조 발췌 80자 → 처리 완료 카드 발췌 제거 → 보드 발췌 80자 → 발췌 모두 제거. 줄어든 문자열 기준으로 complete/length/end를 다시 계산하고 suppressed 이유를 기록한다. 정본 evidence/journal을 잘라 저장하지 않는다. 필수 원문 자체가 초과하면 묶음을 재구성하거나 BOUNDED로 끝낸다.

전체 messages+schema+repair wrapper의 직렬화 문자·UTF-8 bytes와 가능한 경우 모델 tokenizer 기준 입력량을 따로 기록한다. 로깅·축소 기록은 도구 행동/진전 횟수를 늘리지 않는다.

비용 비교식: 후보-기준 = 입력 토큰 차×입력단가 + 출력 토큰 차×출력단가 + 도구/저장/검토 인건비 차. 토큰 단가·수리율·검토 시간의 현 실측이 없으므로 금액 절감률과 완료 일정을 제시하지 않는다. 절감 주장은 새 preview/review 비용보다 감소한 호출·입력 비용이 커지는 손익분기를 실측한 뒤 한다. 지연은 모델 시간만 아니라 요청 수신부터 최종 commit까지 E2E p50/p95로 비교한다.

## 9. 검증·도입 순서 — 먼저 항법을 살리고, 그다음 판단을 고친다

### S0: 구현 전 결속, 구현 후 모델 없는 계약 검사

진행 중 reservation 확인 → ADR 선점 → 정확한 부모/관계·가설/arm·성공 기준 등록 → 후보 snapshot/register/freeze. 과거 snapshot·기존 Task·v1 저널은 수정하지 않는다. 이 문서 작성 자체는 ADR 선점이나 유료 호출이 아니다.

| ID | 필수 검사 | 통과 의미와 한계 |
|---|---|---|
| T01 | 같은 source scope에서 FTS/locator/선읽기/참조 capability 동등성. cm-018/043형 명시 조문 | 검색 배선 확인. 정답 향상 증명 아님 |
| T02 | P/E/C 혼동, empty/STOP, 중복·stale 결정, 잘못된 별칭 | 장부 형식 실패가 탐색 전체를 막지 않음. 잘못된 인용은 거부 |
| T03 | finding 없이 E로 작성, 미제시/preview-only로 작성 시 인용 거부 | 가벼운 작성 입구와 근거 계약 동시 확인 |
| T04 | 모든 메시지/settings 보존, malformed 응답, timeout, 숨은 retry, usage 누락 | raw wire·physical attempt·예산 일치. unknown 비용을 0으로 집계 금지 |

### S1: 탐색 복원 + sidecar만

- A: 선택한 동일 모델의 기존 기준 프로파일. 과거 계보상 Qwen은 loop2c, Gemini는 loop3가 기준 후보이며, 새 ADR에서 정확한 snapshot·정책 승인을 다시 고정한다. ADR-0473 loop4는 실패 비교자료이지 자동 기준 승자가 아니다.
- B0: A의 모델 입력·탐색/작성 결정을 그대로 유지하고 서버 관측 장부만 덧붙인다. 저장된 응답으로 재생할 때 입력·출력 동등성을 검사한다. 장부는 모델에 노출하지 않는다. 새 검토·preview를 동시에 넣지 않는다.
- B1: B0와 같은 검색/선택/작성 정책에서 탐색 발췌를 노출한다. 보드 크기·정렬·title_query·물리 예산은 함께 튜닝하지 않는다.
- C2 후보 확장은 단순 preview와 구별한다. C1만 / C1+C2를 분리해 원인 귀속을 가능하게 한다. 기존 자동 후보 편입과 중복 여부를 기록한다.

S1 첫 품질 질문은 “필요 원문을 실제 입력으로 받고, 그 내용으로 추가 탐색 또는 적절한 선택을 했는가”다. 탐색 호출 ≥60, DISMISS ≥10 같은 수치를 제품 목표로 강제하지 않는다. 불필요한 탐색 감소도 개선일 수 있다.

### S2: 작성·표적 검토 — 원문 확보 후의 문제만

S1의 실제 입력/선택 근거를 고정한 소규모 진단으로 작성 손실과 검토의 잘못된 거부를 분리한다. 먼저 shadow, 그다음 active 제어를 각각 동결·비교한다. 원문이 부족한 사례를 근거 고정 검토의 효과로 섞지 않는다. 같은 모델의 자기채점은 정답 지표로 쓰지 않는다.

Gemini 평가 또는 수동 채점은 실행 전에 사용자와 확정한다. 기존 채점 계약을 재사용할지, 답변의 단서·부정·질문 직접성까지 평가할지 rubric을 고정한다. 기준답·decisive_source_ids는 사후 평가에만 쓰고 제품 입력·후보 확장에는 넣지 않는다.

### S3: 51문항 동시 기준군 및 별도 승격 검증

동일 시점·원문 세대·모델/provider·예산·채점 계약으로 A와 최종 후보를 함께 실행한다. 과거 26/51 또는 34~38/51만을 현재 기준군으로 대체하지 않는다. 변동 확인을 위한 반복 횟수와 회귀 허용치는 결과 전에 고정한다. Qwen 과거 변동을 고려하면 2회 이상 반복을 제안하되, 51문항×2회를 독립 102문항으로 세지 않는다.

핵심 지표는 의미정답/직접 답변, 정확한 인용과 조건 보존, baseline 정답→후보 오답, 빈 답변/미완료, 실제 비용/E2E다. 진단 지표는 decisive의 발견→제시→READ→선택→작성→검토 생존, provenance별 새 원문 읽기, 잘못된 reviewer 거부, 형식 실패와 수리율이다. 개별 회귀는 총점으로 숨기지 않는다.

설계상 최소 gate 제안: 계약/권한 위반 0, 동시 기준군 대비 의미정답 비열화, 빈 답변 증가 없음, 호출 상한 준수. 실제 Accepted 기준에는 최소 이득·허용 문항 회귀·비용/지연 상한을 새 ADR에서 수치로 확정해야 한다. 이 문서에는 아직 검증되지 않은 기대 점수나 확정된 배포 합격선을 넣지 않는다.

CM 51은 이미 설계에 사용된 인샘플이다. 전수 통과만으로 MAIN 승격 불가. 별도 out-of-sample과 decision_eligible/complete/Accepted, hash 고정 promotion plan·명시 승인·rollback receipt가 필요하다. GENOS 실제 실행은 내부에서 별도 검증한다.

## 10. 주요 위험과 대응

담당은 구현 시 지정할 책임 역할이며 실제 인력 배정이 아니다. 일정은 S0의 이식 범위·색인 호환 확인 뒤 산정한다. 법률 의미 규칙을 사전 추출해 별도 정답 그래프를 만드는 기능, 자동 학습, MAIN 자동 승격, 자동 provider 전환은 범위 밖이다.
