## 1. 판단

**역할과 데이터 모델의 큰 개편은 필요하다. 보존할 기반도 상당하다.** 변경의 중심은 위키 문장이나 생성 프롬프트보다, ‘기업이 채택한 지식의 단위’와 ‘검토·사용·수정의 연결’이다.

현재 구조에는 다음이 각각 존재한다.

- 질문·사실·조사·원문·답변 경로를 보존하는 숏컷 원장.
- 조사 기록을 쟁점별 지식 후보로 묶는 위키 컴파일러.
- 단계별 조사 방법을 기록하는 도메인 제어.
- 검토 방법·적용 조건을 초안 작성하고 게시하는 지식 관리 서비스.
- 내규–외규 관계를 승인·반려·철회하고 개정 시 위치를 연결하는 근거 관계 원장.
- 원문 전달·인용·상태·버전·권한을 검증하는 실행 기록.

이 기능들을 전부 버리는 것은 적절하지 않다. 반면 이들이 있다는 이유로 **‘기업이 채택한 관계를 어떤 답변의 어떤 해석에 사용했으며, 관계를 고치면 무엇을 재검토할 것인가’**까지 연결되었다고 볼 수 없다.

‘통제 가능’은 모델이 항상 조직의 기존 해석에 맞추게 한다는 뜻으로 정의하지 않는다. 무엇을 어떤 범위에서 채택했는지, 누가 왜 수정·철회했는지, 현재 답변이 무엇을 재사용하고 새로 해석했는지, 변경의 영향을 어디까지 확인했는지 관리할 수 있어야 한다. 불확실한 해석은 의견과 미확인으로 남기고, 원문 전달·제한 답변을 무조건 막지 않는 기존 정책을 유지한다.

## 2. 검토 범위와 실행 상태

### 선택 코드와 작업 코드

확인한 34개 경로 중 33개가 선택 릴리스에 존재하고 manifest에 결속되어 있다. 이 33개 파일의 선택본은 manifest 해시와 일치했다. 이 중 32개는 작업 코드와 같은 바이트이고, `00_SYSTEM/PIPELINE.json`은 작업본과 선택본의 전체 해시가 다르다. 온톨로지 v3 문서는 선택 릴리스 밖의 논의 문서다.

검토한 두 PIPELINE의 `legal_knowledge` 활성화 상태는 동일하게 꺼져 있다. 이 확인은 전체 저장소나 전체 릴리스의 검증이 아니다. 다른 진행 중인 작업 변경이 있으므로 현 작업 디렉터리 전체를 검증된 MAIN으로 취급하지 않는다.

[service.py:281](../../../../service.py)의 로컬 진입은 활성 포인터와 release manifest의 해시를 검사하고 선택 코드·데이터를 읽는다. 선택된 `semantic_runtime` 패키지를 별도로 import하는 경로도 있다. 이번에는 서비스 부팅이나 질의를 실행하지 않았으므로 ‘실행 중 서비스가 실제로 사용했다’는 관측 결과는 아니다.

## 3. 현재 코드의 실제 흐름

### 3.1 숏컷과 위키

```text
service → app/Pipeline → unified_runtime.open_cases
  → ShortcutCases
  → 질문·사실 수정·단계 기록·읽은 원문·답변 경로를 sw_* 원장에 보존
  → 성공 발행 후 core_evidence_route.finalize
      → 근거 위치 경로 저장 → 현재 원문 재확인 후 재사용
  → action-memory build --mode shortcut-v4
      → legal_wiki_compiler.compile_snapshots
      → 쟁점별 unit·claim·procedure·relation 후보와 검증 기록
      → DB 기준 legal_wiki projection·회수 카드
```

이 경로는 **경험과 후보의 축적**에 적합하다. 위키 게시와 법적 해석 승인은 코드에서도 구분한다. `core_evidence_route.finalize`가 만드는 경로에는 claims·procedures가 빈 배열이며, 성공한 답변의 근거 위치를 다시 찾는 역할이다. 이 점은 유지할 가치가 있다.

### 3.2 검토 지식 서비스

```text
legal-knowledge API/CLI
  → Service.command
  → definition 초안 → source·dependency 검증 → release 준비·게시
  → lk_record 불변 revision + lk_head + lk_lookup
  → (활성화 시) request_entry → knowledge_bridge.prepare
  → Service.plan → planning.assemble → 기존 모델 호출에 안내
  → public_metadata → 답변 발행 시 권한·원문 결속 재확인
```

이 서비스는 이미 기업 지식 관리의 일부 기반을 갖고 있다. 다만 현재 객체와 소비 계약의 중심은 **검토 방법과 원문 위치 안내**다. 원장에 등록된 지식과 답변의 적용 해석을 연결하는 통합된 지식 통제 경로까지 완성된 것은 아니다.

### 3.3 내규–외규 근거 관계

`basis_links.Service`는 관계 후보와 승인·반려·철회를 revision·행위자·이유·원문 범위와 결속한다. 실제 함께 인용된 내규·외규도 자동 승인하지 않고 후보로 남긴다. 개정 시 binding을 다시 연결하는 코드도 존재한다.

하지만 관계 종류는 `BASIS / IMPLEMENTS / RELATED`이고, 양 끝은 내규·외규 원문에 맞춰져 있다. 이를 바로 ‘합산 범위를 결정한다’, ‘금액 산정의 입력이다’, ‘예외가 적용을 바꾼다’ 같은 모든 도메인 관계의 실행 모델로 설명할 수는 없다.

### CTRL-01: 이름을 바꾸는 정도로는 부족하다

현재 `METHOD`는 purpose·inputs·evidence_needs·steps·policies를 저장한다. `APPLICATION`은 method_refs와 condition을 묶는다. 이는 ‘어떻게 검토할 것인가’에 가깝다. 외부 CONCEPT·DEFINITION 참조는 있지만, 이 관리 계층에서 독립적인 의미 관계를 작성하고 각 관계에 검토 상태를 붙이는 자체 객체는 없다.

위키의 claim에는 statement·condition·rationale·원문 인용이 존재한다. 그러나 이 claim은 위키 unit 아래에 속하고, 조직의 독립적인 검토 결정과 개별 답변의 적용 기록을 잇는 중심 객체로 사용되지는 않는다.

모든 용어를 새로 만드는 것은 필요하지 않다. 기존 용어·정의·원문 ID를 재사용하면서 기업이 관리할 주장·관계와 조건·예외·근거 역할을 별도 명세로 만든다. 기존 스키마는 닫혀 있으므로 임의 필드를 끼워 넣지 않고 버전 변경·변환·소비자 호환을 함께 설계한다.

### CTRL-03: 플래그를 켜는 것과 적용 가능한 지식을 소비하는 것은 다르다

`Service.plan`은 context·facts·as_of를 받을 수 있다. 그러나 검토한 native 호출은 질문과 source_binding만 전달한다. `planning.assemble`은 기준일이 없으면 `AS_OF_UNSPECIFIED`를 남기고, MATCHED인 항목도 UNRESOLVED로 바꾼다.

또한 `augment`가 모델에 제공하는 항목은 ref·title·description·steps·source_refs·application_status·missing·role이다. 계획의 모든 policy와 실행 receipt가 그대로 전달되는 구조도 아니다. 현재는 안내라는 경계를 지키는 코드이며, 이를 완성된 공리 실행으로 설명하면 안 된다.

조건 실행기도 제한적이다. 예를 들어 타입·단위가 다른 값의 연산을 허용하지 않고 multiply·divide는 무단위 decimal에 제한한다. v3의 ‘금액 × 담보 인정비율’ 예시는 현재 평가기로 그대로 실행할 수 있다고 가정하면 안 된다. 필요한 연산과 반올림·단위 의미는 별도 계약이 필요하다.

### CTRL-04: 제공된 지식과 사용된 지식은 다르다

현재 usage metadata에는 plan에 포함된 항목과 적용 상태가 들어간다. ‘제시된 지식’, ‘모델이 선택했다고 기록한 관계’, ‘실제 계산에 입력된 값’, ‘최종 주장에 연결한 근거’를 나누는 확장이 필요하다.

추가 기록은 LLM의 숨은 사고를 알아냈다는 표시가 아니다. 명시된 적용 해석, 시스템 실행, 근거 전달·선택, 사후 평가를 각각 식별해야 한다.

### CTRL-05: 게시·철회와 영향 조회의 단위를 맞춰야 한다

`Service._prepare_publication`은 기존 release refs에 새 refs를 합치고, `_retire`는 팀 채널을 중단한다. 개별 정의를 게시 집합에서 제거하거나 개별 의미 관계를 철회하는 명령은 이 API에 없다. 위키 원장과 basis 관계 원장에는 다른 단위의 철회가 이미 있으므로 ‘철회 기능 자체가 없다’는 진단도 부정확하다.

`impact`의 직접 의존 조회는 그대로 유지할 수 있다. 이를 전체 개정 영향이나 과거 답변에 대한 영향 추적이라고 부르지는 않는다. 추가로 간접 의존·실제 사용 이력·영향 미확인 범위를 연결해야 한다.

현재 `revalidate`는 사용한 고정 release의 무결성과 채널의 PUBLISHED 상태를 확인하며, 고정 release와 최신 active release의 동일성을 요구하지는 않는다. 이것만으로 결함을 단정하지 않는다. **정상적인 판본 갱신 중 진행 중인 요청을 허용할지, 개별 지식 철회가 진행 중 요청에도 즉시 효력을 가질지**를 명시하고 서로 다르게 처리할 필요가 있다.

## 7. 구체적인 정상·변경 시나리오

가상 거래 사례로 최소 개편의 동작을 정한다. 실제 법률 기준이 아니다.

1. 숏컷에는 질문, 실제 조회한 A·B·C 원문, 근거 경로와 답변 기록이 남는다.
2. 위키 컴파일러는 ‘거래 분류가 합산 범위를 결정한다’는 관계를 조직 지식 후보로 제안한다. 성공한 답변이나 위키 게시만으로 승인되지 않는다.
3. 기업이 정한 검토 정책에 따라 해당 관계의 근거·조건·범위·판본을 기록한다. 기준이 승인된 경우 그 범위에서 재사용 가능 상태로 둔다.
4. 다음 질문에서 검토된 관계를 제시한다. 모델은 이번 두 계약이 조건에 맞는지를 별도로 해석한다.
5. 답변의 ‘합산 대상’ 주장에 관계의 고정 버전, 계약 사실, 새 적용 해석을 연결한다. ‘12억’은 사용한 입력·연산에 연결한다.
6. 사용자가 계약 조건을 정정하면 합산 판단·계산·승인 결론을 재검토 대상으로 찾는다. 금액 기준의 원문까지 잘못된 것으로 바꾸지 않는다.
7. 관계가 철회되면 앞으로의 재사용을 멈추고, 그 관계를 명시적으로 사용한 답변·경로를 찾는다. 과거 답변을 자동으로 새 정답으로 덮어쓰지 않는다.

새 B-C-A 경로가 아직 조직 지식에 등록되지 않았더라도 원문 기반의 조건부 답변과 검토 후보를 만들 수 있다. 미적중은 곧 오류가 아니며, 새 연결을 막는 이유가 되지 않는다.

## 9. 데이터 이행과 실패 계약

### 기존 기록을 잃지 않는 이행

- 기존 숏컷·위키 unit·claim·원문·검증 receipt·실패 이력을 유지한다.
- 조직 지식 객체에 기존 ID·revision·hash와 출처 역할을 연결한다. 새 관계의 독립 ID와 경험의 ID를 혼동하지 않는다.
- `PUBLISHED` 위키, `STRUCTURE=PASS`, `SOURCE=PASS`, 사용자 확인을 조직의 법적 해석 승인으로 자동 변환하지 않는다.
- 기존 basis의 승인도 승인된 내규–외규 관계 범위만 승계한다. 새로운 계산·예외 관계까지 확대하지 않는다.
- 새 계약으로 표현하지 못한 옛 데이터는 보존하고 미이행 사유를 남긴다.
- 이행 후 기존 조회·철회 효력이 유지되는지 확인하고, 새 projection과 색인은 원장에서 재생성할 수 있게 한다.

### 실패·중단·재개

| 상황 | 제안 처리 |
|---|---|
| 잘못된 후보·해석 이견 | 원문과 이유를 가진 후보·이견으로 남김. 이미 확보한 원문 전달은 유지 |
| 게시 중 동시 변경 | 기존 CAS·작업 ID로 충돌 처리. 승인되지 않은 head를 적용하지 않음 |
| Oracle 응답 유실 | 같은 작업 ID의 처리 결과를 확인. 새 작업으로 중복 게시하지 않음 |
| 관계 철회·권한 변경 | 정해진 소비 시점에서 재확인하고 해당 재사용을 중단. 과거 기록은 보존 |
| 원문 개정·위치 변경 | 기존 migration/currentness 기능을 연결. 내용 해석까지 자동 승계하지 않음 |
| 적용 조건 미확인 | 조건과 제한을 표시하고 필요한 원문·사실만 확인. 무조건 추가 조사 루프를 돌지 않음 |
| 사용 기록 일부 누락 | 확인된 기록만 표시. 모델이 실제 사용한 것처럼 사후 경로를 꾸미지 않음 |
| 영향 조회 일부 실패 | 확인한 범위와 미확인 범위를 구분. 영향 없음으로 결론내리지 않음 |

영속 데이터는 Oracle 또는 승인된 데이터 계층에 둔다. 현재 숏컷의 SQLite 구현을 보존할 가치가 있다는 평가는 그 구현을 GENOS 서빙의 최종 영속 저장으로 채택한다는 뜻이 아니다. 데이터 계층의 조회·변경 계약으로 옮기는 작업과 현장 검증은 별도다.

## 10. 검증과 이번 작업의 한계

이번에 확인한 것은 코드·스키마·호출 경로·선택 파일 해시다. 제품 질의, 모델 품질 실험, 전체 원문 로딩, Oracle 접속, GENOS 배포는 실행하지 않았다. 개선률·정답률·일정·비용의 수치는 추정하지 않았다. 33개 파일 해시 일치는 해당 검토 파일의 결속 확인이며 전체 서비스 정상 동작의 증명이 아니다.

실제 변경 후에는 정상 등록·게시·사용뿐 아니라 후보 기각·개별 철회·중복 요청·동시 수정·원문 개정·권한 변경·진행 중 요청·재개·영향 조회·답변 표시를 같은 코드로 확인한다. 불확실성 때문에 근거 전달이 막히지 않는지, 실패한 경험이 성공한 지식으로 승격되지 않는지도 확인한다.

모델·프롬프트·검색 효과를 비교한다면 사전 동결한 신규 ADR로 진행한다. 평가에서는 단순히 온톨로지 적중률을 높이는 대신, 중요 근거 누락·미지지 주장·수정 범위 추적·사람의 검토 시간을 본다. 동일한 온톨로지가 만든 기준으로만 그 온톨로지의 정답성을 평가하지 않는다.

**최종 판정:** 방향은 조건부 타당하다. 필요한 기반은 존재하지만, 지금의 위키·온톨로지 역할과 조직 지식의 승인·실제 적용·수정 영향을 연결하는 계약은 개편이 필요하다. 이번 문서 작성으로 구현 격차가 해결된 것은 아니다.
