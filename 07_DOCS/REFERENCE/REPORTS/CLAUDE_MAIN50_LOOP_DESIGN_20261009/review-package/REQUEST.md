# 사용자 요청 — MAIN50의 불필요한 탐색·반복 행동·본헤드성 agent 루프를 줄이는 실제 설계

당신은 연결된 Claude Code의 **Opus 5.5(claude-opus-5-5)**로, Codex가 진행한 구현을 독립적으로 검토하는 설계자다. 사용자가 직접 다음을 요청했다.

> 우리 연결된 클로드 코드한데 현재 상황을 이야기해주고 어떤게 잘안되었는지. 나의 목표 불필요한 탐색이나 했던행위 본해드성 agent루프를 해결하고 싶다. 이내용을 전달해서 어떤걸 수정해야될지 설계해달라고 해줘. 모델은 opus5.5.

목표는 실제로 쓸모없는 조사 왕복과 같은 행동 반복을 없애는 것이다. 단순히 예외를 막거나 HTTP200을 늘리거나 호출 상한에서 강제로 끝내는 것만으로 목표를 달성했다고 보지 말아 달라. Codex의 현재 접근이 잘못된 부분도 지적해 달라.

## 작업 범위

- **읽기 전용 설계 검토**다. 제품 코드 수정, 테스트/실험 실행, 외부 제품 모델 호출, MAIN 승격, Git 작업, GENOS 접속은 하지 않는다.
- 이 `review-package` 내부 자료만 읽는다. 상위 저장소·사용자 홈·.env·인증 정보·실제 내부 CM 질문·원문·journal은 읽지 않는다. 패키지에는 그런 내용이 들어 있지 않다.
- `PACKAGE.json`에 실제 파일 출처와 해시가 있다. `main50/`는 현재 선택된 코드, `candidate/`는 아직 MAIN에 올리지 않은 실제 구현 후보다. `synthetic-tests/`는 모의 계약 검사다.
- `METRICS.json`은 질문·답변·법령 원문을 제외한 운영 수치다. 코드/실행 사실과 모델 의미 판단, 확인한 사실과 제안을 구분한다.
- 답변은 한국어로 이 채팅의 최종 응답에 완성된 설계를 써 달라. 파일 쓰기 도구는 필요 없다. 읽기 실패나 자료 부족은 정확히 밝히고, 확인하지 않은 현행 기능을 있다고 가정하지 않는다.

## 현재 선택 상태와 작업 경과

1. 실제 로컬 RAG MAIN은 아직 **generation50 / compact-input-20261009-r1**이다. 전체 MAIN(용어집→입력/구조화→문서 연결→색인→RAG→피드백) 중 이번 대상은 RAG의 조사/판단/답변 경로다. 원문 generation은 바꾸지 않았다.
2. 기준 서빙 코드287파일은 구현 시작 시 작업 코드·선택 릴리스·직전 진단 후보와 동일했다. 지금 수정은 별도 후보에만 있다. 아직 작업 코드 선별 통합·MAIN 승격·서비스 선택 확인을 완료하지 않았다. GENOS는 접근 불가다.
3. ADR0718: v5 요청/부족 근거/답변 계약 구현. 신규20검사 통과. 기존271개는 MAIN50 256통과/15실패, 후보도 동일15실패였다. 기존 실패를 성공 처리하지 않았다.
4. ADR0719: 새 공개 질문3개 A/B와 후보3개 반복,9요청 모두 응답. 주 비교 호출16→12, 입력139103→98484, 시간325.568→260.260초. 그러나 동일 결정의 수정 호출 중 통신이 끊긴 뒤 재개하면, 거절 이력이 입력을 바꿔 해시 불일치를 만드는 결함을 독립 검토에서 발견하여 승격하지 않았다.
5. ADR0720: 위 경우의 당시 입력·도구 메뉴를 불변 저장/복원하고, 새 사용자 요청의 gap 이력 경계를 보강했다. 신규23/23 통과. 전체294개 중279통과/15실패이며, 기존 MAIN50과 동일15실패다. 모델 호출 없이 검사했다.
6. ADR0721: ADR0720과 **동일한 최종 제품 코드**로 다른 새 공개 질문3개 A/B+후보3반복을 고정했다. 주 비교3/3→3/3, 호출12→12, 입력170892→130397(약24% 감소), 출력13302→16276, 시간268.436→317.784초(약18% 증가). 후보 반복2/3 완료, 마지막 S03의 세 번째 전송이 ConnectError로 즉시 실패해 HTTP502. 기준을 소급 완화하거나 그 run을 재실행하지 않았다. 인용·권한·상태·내용 보존 검사는 통과했지만 반복3/3 기준 때문에 승격하지 않았다. 이후 DNS와 모델 생성 없는 연결 확인은 정상200이었다.
7. ADR0722는 동일 코드의 후속 검증용으로 예약만 했다. 아직 제품 변경/동결/모델 호출이 없다. 사용자의 이번 Claude 설계 요청을 먼저 처리한다.
8. 별도 집계 스크립트에서 검사 수20→23 변경을 기계 치환하다 HTTP200 비교도230으로 바뀐 오류가 있었다. 원본을 보존하고 고쳐 실제3/3으로 집계했으며 제품 코드나 통과 기준은 바뀌지 않았다. 결과는 여전히 반복 실패로 미통과다. 이 집계 오류와 제품 결함을 섞지 말아 달라.

## 원래 문제와 현재도 잘 안 되는 점

직전 MAIN50 진단은 51문항에서 실제 승인 COVERED39/PARTIAL7/실패5였다(정답률 아님). HTTP20046,5001,4224. 질문 원문이나 내부 데이터는 이 검토에 포함하지 않았다. 관측된 유형은 다음과 같다.

- 배경 설명을 독립 질문으로 확대하거나, 관련 주제 조문을 직접 답변 근거로 삼는다.
- 필요한 대상 조문을 이유에 적고도 다른 조문을 읽거나, 이미 읽은 범위를 다시 읽는다.
- 원문을 읽은 사실을 채택/충분성 판단과 혼동하고 FINISH한 뒤, ASSESS에서 부족을 발견해 다시 조사한다.
- 같은 부족 근거가 이유 표현/optional material ID 때문에 새 gap처럼 생겼다. 재조사 때 무진행 계수가 초기화돼 같은 루프가 계속됐다.
- NOT_NEEDED로 닫았다가 근거 변화 없이 다시 열거나, 다른 조문 읽기 receipt로 대상 조문의 NOT_AVAILABLE을 승인했다.
- 같은 판단에 수정 호출을 반복하거나, 과거 decision_retry가 새 조사에 남아 500이 났다.
- 모델이 말한 이유/실행 사실과 실제 선택 행동이 다르다. 코드가 가진 전체 검색/원문/채택 이력을 모델 선택에 충분히 활용하지 못한다.
- 큰 메뉴·긴 행동 기록·원문 중복이 입력을 키운다. 구조 검색/범위 내 본문 검색 도구가 있어도 전역 탐색·되돌아가기·재탐색을 고른다.
- 조건 ID/root 연결을 고쳐도, 의무·결정 효과·예시를 적용 조건으로 쓰는 **의미 오류가 남는다**. 최근 공개 출력에서도 서로 다른 결정의 효과를 하나의 ALL로 묶거나 같은 의무를 조건/의무/상세에 반복했다.
- 조립 손실은 줄었지만 결론/상세/조건 중복으로 답변이 길고 느려진 사례가 있다. 이번 수정으로 agent의 본헤드성 행동 자체가 충분히 개선됐다고 주장할 수 없다.

## 후보에 이미 구현한 내용 — 그대로 믿지 말고 실제 코드를 확인

- `investigation-completion-v5`, 별도 `completion_policy_version`으로 선택. 기존 v1-v4 이력 renderer 유지.
- `request_repair.py`: investigation epoch, 수정 시도 퇴역, 정확 중복 판단 행만 정리, 세대/권한/문서/조문/span에 묶인 gap identity, 정확 대상 해결/부재 검증, 해당 대상 새 근거 없이 재개 금지, 요청 단위 진전 signature, 정확 대상 READ 메뉴, 현재 보이는 동일 원문 재독 메뉴 억제.
- `law_navigation.py`: 위 계약을 실제 조사 진입/메뉴/FINISH/수정/재개에 연결. 통신 중단된 수정 결정은 저장 입력·메뉴 복원, 결과 불명 시 세 번째 호출 금지. 새 사용자 요청은 옛 gap 이력을 감사용으로 보존하고 새 경계를 연다.
- `completion_v5.py`: 요구 원문 인용/배경 인용 검증, conclusion/details/중첩 condition_tree/obligations/exceptions, 코드가 내부 ID/root를 생성. answer_content 단일 정본을 최종 답변에 보존. 핵심 gap 기반 보수적 coverage 계산. 모델 제안 별도 보존. ASSESS 입력에서 source.text/adopted_spans 중복을 줄이고 evidence_options에 원문 구절 유지.
- `completion_execution.py`, `memory_rag.py`, `corrected_memory.py`: 조사↔평가 재진입과 요청 예산·상태 보존에 실제 연결.
- `unified_runtime.py`: 승인 ASSESS→COMPOSE→반환 해시·coverage·semantic_quality_certified=false 기록.
- `execution_metrics.py`: 요청 중 프로세스 RSS 표본(100ms). 하위 프로세스 합산/요청 독점 메모리 측정은 아니다.
- 새 모듈을 UnifiedRag 코드 identity, engine file pin, PIPELINE, 프로필에 연결. 후보 전체 서빙289파일.
- 여전히 최종 추가 검토 모델은 상시 사용하지 않는다. 총 호출40, wall1800초, max_no_progress2, 재진입2, 최종화 예산3이라는 기본 큰 경계는 유지한다.

## 원하는 설계 산출물

1. **현재 변경이 사용자 목표를 얼마나 해결했는지 결론부터.** 이미 막은 코드 결함, 여전히 선택되는 무의미한 행동, 모델 판단 책임을 구분하고 중요한 원인3~5개를 코드 함수/분기 근거로 설명.
2. **최소한의 다음 구현 구조.** 요청의 요구/부족 대상/원문 확보·제시·채택/이미 실행한 행동/그 행동으로 생긴 새 정보/종료 사유를 어떻게 연결해야 하는지. 기존 상태/원장을 재사용하고 중복 실행기를 새로 늘리지 말 것.
3. **같은 행동과 정당한 재방문을 구분하는 규칙.** 같은 검색어 변형, 같은 문서 다른 span, 재표시, 새 사용자 사실·버전/권한 변경, 지연 도구 결과, 다른 요구에서의 재사용을 다뤄 달라. 문자열 같은지만 보거나 모든 revisit를 금지하지 말 것.
4. **다음 행동과 종료/재진입 설계.** 왜 이 행동이 미해결 요구를 줄이는지, 어떤 target/expected observation을 가져야 하는지, 실제 outcome과 어떻게 대조하는지. 단순 무진행 카운터/상한으로 잘라내거나 모델 자유서술 이유만 믿는 방식의 한계를 해결해 달라. 정확 대상을 찾았는데도 전역 탐색하는 경우와 추가 참조가 실제 필요한 경우를 구분.
5. **추가 LLM 호출 없이 먼저 할 것과 모델 개선이 필요한 것.** 정답/조문 하드코딩·과거 답변 정답 승격·조건 논리 임의 수정은 금지. 판단 모델을 매 단계 늘려서 느리게 만드는 제안은 기본안으로 삼지 말 것.
6. **코드 변경 지도와 이행.** 파일/함수별 입력·출력·상태 변경, 구버전 요청 재개, 기존 행동 체인·반환·프로필·MAIN 배선/롤백까지. 필요한 타입/의사코드/작은 상태 전이표로 바로 구현할 수 있게.
7. **검증 설계.** 가짜 진행·반복 탐색·중복 읽기·잘못된 FINISH·정당한 재방문을 구분하는 반례와 측정 항목. 단순HTTP200/문자열인용 일치에 기대지 말고, 필요 원문 도달·반복 행동당 신규 근거·같은 gap왕복·실제 호출/지연·승인 내용 보존을 같이 볼 것. 사전에 동결할 최소 비교와 성공/회귀 기준 제안.
8. **우선순위.** 가장 먼저 바꿀2~3개, 당장 유지할 것, 이번엔 하지 않을 것과 이유. 통과를 위해 계속 새 질문으로 갈아 끼우는 검증이 되지 않도록, 현재 네트워크 실패와 본헤드성 agent루프를 분리한 효율적 검증 순서도 제안.

숫자 개선율을 근거 없이 예측하지 말고, 기존 후보를 칭찬하는 요약보다 실제 다음 수정과 사용자 목표에 집중해 달라.
