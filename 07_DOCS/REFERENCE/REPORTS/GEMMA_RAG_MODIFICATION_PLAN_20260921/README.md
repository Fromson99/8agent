# Gemma 에이전트 판단 보강계획

2026-09-21 · 판단 능력 중심 개정 · 설계안, 구현·모델 호출 미실행

**첫 수정은 Gemma가 질문에서 답해야 할 항목을 유지하고, 각 항목에 맞는 근거를 선택하며, 적용 조건과 예외를 바꾸지 않고 답하도록 만드는 것이다.** 명시 조건 추출·연결 설명·구체적 교정이라는 강점을 활용해 탐색 → 선택 → 작성 → 검토의 판단을 보강한다.

[LLM 능력 종합 리포트](../LLM_CAPABILITY_SYNTHESIS_20260921/README.md)를 근거로 작성했다. 사용자 지시에 따라 운영 장애 분석과 안정화 작업은 범위에서 제외했다. 아래 단계는 에이전트 판단의 수정 순서다.

## 1. Gemma에 대해 아는 것과 아직 확인할 것

|구분|관측|계획에 반영할 판단|
|---|---|---|
|Gemma가 잘한 사례|CM008 연결 조건 설명, CM009 예외·재량 보존, CM025 일반 차감/별도 조정 구별, CM050 OR 보존|이 능력을 활용하고 수정 뒤에도 유지되는지 회귀 확인|
|Gemma의 직접 보강 대상|CM029 질문을 특례로 좁힘, CM033 공식 해석 필요성 전달 부족, FSC009 확정·유보 배분 문제|질문 범위 유지, 적용 근거 확인, 주장별 보류를 우선 수정|
|다른 모델에서 드러난 위험|Qwen CM004 공식 누락, CM038 예외 범위 누락, CM050 OR→AND, CM043 결론과 근거 불일치|Gemma의 확정된 약점으로 단정하지 않고 예방·회귀 과제로 사용|
|구체적인 교정의 긍정적 신호|Qwen에서 유효한 수정 동작을 따른 성공|Gemma에서도 구체적인 의미 교정에 효과가 있는지 확인|
|검토의 한계|기존 자동 채점이 조건 오류를 통과시키거나 잘못된 이유로 지적|Gemma 자기검토를 정답 보증으로 취급하지 않음|

CM029는 일반 규칙을 모두 읽고도 오판한 것이 입증된 사례가 아니다. 따라서 ‘필요한 근거를 찾는 판단’과 ‘근거를 모두 줬을 때 적용하는 판단’을 분리한다. 완성 답변이 없는 문항은 의미 오답으로 세지 않는다.

후속 모델은 기존 실행의 **`google/gemma-4-31b-it`**을 기준으로 한다. ADR0498의 FP8·thinking off 설정을 출발점으로 삼으며 실행 시 정확한 provider·설정을 동결한다. 현재 공통 정책은 Qwen이고 Gemma 지원은 해당 연구 후보에 결속돼 있으므로 실제 실행 전에 모델 연결을 준비해야 한다. 이 연결 준비는 판단 개선의 성과로 계산하지 않는다.

## 2. 보강할 판단 흐름

```text
원래 질문
  → 무엇에 답해야 하는가: 요구 항목·대상·시점·주어진 사실
  → 무엇이 부족한가: 미확인 규칙·예외·사실
  → 다음 행동은 무엇인가: 그 부족분을 해소하는 검색·읽기·추가 질문
  → 어떤 근거를 쓸 것인가: 원칙·특례·정의·반례와 적용 이유
  → 어떻게 답할 것인가: 요구별 직접 답·조건·예외·확인 범위
  → 무엇이 틀렸거나 빠졌는가: 원문과 초안의 구체적 차이
  → 해당 부분 교정·재검토 또는 이유가 있는 부분 답변
```

별도 법률 규칙 DB를 만들지 않는다. 아래 판단 기록은 원문에 결속된 **요청별 observation**이며 승인된 정본이 아니다. 원문을 영구 조건식으로 바꾸는 폐기된 의미 스키마를 재도입하지 않는다. 전체 MAIN 중 RAG의 판단 단계를 바꾸고, 입력·구조화·용어집·문서 연결·색인은 동일 기준에 결속한다.

## 3. 우선순위별 수정 내용

### P1. 질문 요구를 끝까지 유지한다

**문제:** 관련 주제를 설명해도 실제 질문에 답하지 않거나, 찾은 특례에 맞춰 질문 범위를 바꾼다.

원래 질문을 보존하면서 작은 요구 목록을 만든다. 제안 필드는 `question_refs`, `required_answer`, `given_facts`, `missing_facts`, `status`, `claim_refs`다. 질문의 원문 구간 ID는 서버가 부여하고, 요구 해석은 Gemma가 제안한다. 배경 설명과 독립 질문을 구분하며, 원문에 없는 전제를 더하지 않는다. 목록 자체가 누락될 수 있으므로 최종 검토에도 원질문을 보여준다.

- ‘공식’을 물으면 공식·변수 또는 확인하지 못한 이유를 답한다.
- ‘위임 가능한가’를 물으면 대상별 가능 여부와 제외 범위를 답한다.
- ‘분류와 위법 여부’를 함께 물으면 두 항목을 각각 처리한다.
- 질문의 기준시점이 없으면 임의로 만들지 않고, 결론에 영향을 주는 경우 부족한 사실로 표시한다.

**첫 구현의 완료 조건:** 원질문 → 요구 → 근거 → 답변의 연결이 추적되고 미답변 항목이 남는다. 필드가 채워졌다는 이유만으로 요구를 충족했다고 판정하지 않는다. CM029·CM033·FSC009와 CM004·038을 확인 사례로 쓴다.

### P2. 탐색과 적용 규칙 선택을 보강한다

**문제:** 관련 자료를 발견한 것을 적용 근거 확보로 오해하거나, 필요한 일반 규칙·예외를 확인하지 않고 종료한다.

도구를 선택할 때 `해결할 요구`, `현재 부족한 정보`, `이 행동으로 확인할 것`을 간결히 연결한다. 새 모델 호출을 만들기보다 기존 탐색 결정의 `question_refs`, `expected_information`, `reason`을 활용한다.

Gemma가 읽은 원문을 질문 관련성에 따라 원칙·특례·정의·반례/예외·배경으로 설명하게 한다. 역할은 요청별 판단이며 문서 종류만으로 정하지 않는다. 특례를 채택하려면 질문의 사실 중 어떤 요건이 충족되는지 근거를 붙인다. 근거가 부족하면 일반 규칙을 더 찾거나 조건부 결론으로 한정한다. 관련성이 있어도 결론에 직접 쓰지 못하는 자료를 구분한다.

탐색을 끝내기 전에는 ‘모든 요구가 답변 가능하거나, 무엇이 부족한지 특정됐는가’를 확인한다. 같은 자료를 다시 읽는 경우 새로 확인할 항·호·단서가 무엇인지 밝힌다. 정보가 충분하면 추가 탐색을 요구하지 않는다.

**확인 사례:** CM029에서 일반 규칙·특례를 모두 제공한 과제와 실제 검색 과제를 분리한다. CM025의 개념 구분 성공은 유지하고, CM043처럼 결론만 같고 근거가 다른 답을 잡는지 확인한다.

### P3. 조건·예외를 보존하며 작성한다

**문제:** 설명을 정리하는 과정에서 OR/AND, 예외의 대상, 재량의 강도가 바뀌거나 빠진다.

기존 작성 단계에서 각 주장과 정확한 원문 span을 연결하고, 의미를 바꿀 수 있는 표현을 원문과 나란히 기록한다. 제안하는 최소 기록은 `source_span`, `source_expression`, `draft_expression`, `application_reason`이다. 원문에 해당 구분이 있을 때만 사용하며 모든 문장을 무조건 복잡한 구조로 쪼개지 않는다.

- ‘또는’를 ‘모두’로 바꾸지 않았는지 확인한다.
- 예외가 어느 대상·조건·본문에 붙는지 유지한다.
- ‘적용하지 않을 수 있다’를 확정적 면제로 바꾸지 않는다.
- 일반 계산식이 별도 조정 규정의 근거가 되는지 구분한다.
- 설명을 줄이더라도 결론을 바꾸는 수치·시점·범위는 남긴다.

서버는 span·인용·해시를 검사한다. Gemma는 원문과 초안의 의미를 비교한다. 단어 일치만으로 논리적 동치를 보증하지 않는다.

**확인 사례:** CM008·009·025·050의 Gemma 성공을 유지하며, 원문 조건 하나를 바꾼 질문에서 결론 변화가 적절한지 확인한다. 알려진 오류만 외우게 하지 않도록 새 사례도 별도로 동결한다.

### P4. 확정과 판단 보류를 주장별로 나눈다

**문제:** 전체 답에 막연한 단서만 붙이거나, 답할 수 있는 것은 유보하고 근거가 부족한 부분은 단정한다.

각 요구를 `답변 가능`, `명시 조건에 한정해 답변 가능`, `추가 사실 필요`, `근거 확인 미완료`로 설명한다. 이는 제안 상태이며 법적 효력의 등급이 아니다. 확률 점수를 임의로 붙이지 않는다.

FSC009 유형에서는 업무위수탁 분류와 위반 여부를 별도로 판단한다. 확인된 분류는 직접 답하고, 위반 여부에 필요한 사실이 없다면 정확히 무엇이 필요한지 말한다. CM033 유형에서는 문언상 적용 설명과 공식 해석 확인 필요성을 분리한다. ‘찾지 못했다’를 ‘규정이 없다’로 바꾸지 않는다.

추가 질문은 결론을 바꾸는 미확인 사실에 한정한다. 충분한 정보가 주어진 짝 과제에서는 직접 답해야 하므로, 유보가 늘어난 것을 개선으로 세지 않는다.

### P5. 자기검토를 구체적 차이 확인으로 바꾼다

**문제:** ‘다시 검토하라’는 지시와 채점 통과만으로는 조건 오류와 질문 누락을 놓친다.

기존 검토 호출에서 원질문·요구 목록·원문·초안을 함께 본다. 검토 결과는 `문제가 있는 주장`, `원문/질문과의 차이`, `수정해야 할 내용`, `추가 근거 필요 여부`로 제한한다. 이상이 없으면 무엇을 대조했는지를 짧게 남긴다. 생성자의 장황한 확신·자기평가는 검토 근거로 주지 않는다.

검토 예: “다시 확인” 대신 **“이 주장의 ‘모두’는 인용한 원문의 ‘또는’와 다르다. 한 조건만 충족한 경우의 결론을 보존하도록 수정하라.”** 모델이 원문과 이 지적을 확인한 뒤 해당 부분을 수정하게 한다. 오류 지적도 틀릴 수 있으므로 원문이 지적과 맞지 않으면 이유를 남겨 기각한다.

정상 답·명백한 조건 오류·잘못된 검토 지적을 함께 평가한다. 수정은 해당 주장과 영향받은 요구에 한정하고 재검토한다. 기존 검토를 우선 교체하며, 모든 답에 심판 호출을 추가하는 방식은 피한다. 같은 Gemma가 작성·검토하므로 오류 독립성은 보장되지 않는다.

## 4. 기존 코드에 연결할 위치

공통 접두사는 `02_BACKEND/semantic_runtime/legal_agent/`이다. 이름이 같은 작업 코드와 ADR0498의 frozen 사본을 구분하며, 실험은 완료 사본에서 분기한 새 후보에 구현한다.

|책임|확인한 기존 접점|제안 변경·소비자|
|---|---|---|
|질문 요구|`context.py::question_pieces`, `tools_protocol.py::TurnDecision.question_updates`|원문 좌표 유지, 요구·배경·사실 해석을 요청 상태에 기록. 탐색·작성·검토가 소비|
|다음 행동 판단|`tiers_policy.py::PROMPTS`, `tiers_session.py::apply_turn`, 후보의 도구 `question_refs/expected_information/reason`|부족한 요구와 행동 목적을 연결. 다음 탐색과 종료 판단에 소비|
|근거·범위 선택|`tiers_session.py::source_plans/commit_selection`(후보), `relations_session.py::relation_requirements`|원칙·특례·예외의 역할과 적용 이유를 검토. 읽음·관련성·결론 근거를 구별|
|작성 입력|`tiers_views.py::build`, `tiers_session.py::view`, `tools_session.py::view/commit_draft`|질문 요구·선택 원문·미확인 사항을 함께 제시. 실제 작성 화면에 전달된 span 기준으로 주장 결속|
|조건·유보 검토|`tools_protocol.py::Draft/ReviewDecision`, `tools_session.py::commit_review`, `relations_session.py::commit_review`|요구별 결론 상태와 원문 차이 검토 기록 추가. 기존 검토·교정 결정이 소비|
|판단 반복·종료|`tools_session.py::answer_and_review`와 `tiers_session.py`의 상속 경로|NEEDS_RESEARCH/NEEDS_REWRITE/UNCERTAIN을 부족한 근거·표현 오류·미확인에 맞게 사용|
|모델 연결 준비|`lawrag/research/experiment_client.py::load_policy/ExperimentClient`, 후보의 `ScopedGemmaClient`|Gemma 역할·정책 결속. 과거 ADR 한정 경로를 새 실행에 그대로 재사용하지 않음|

기존 프로토콜에 목적이 같은 필드가 있으면 활용하고, 없는 판단 기록만 추가한다. 제안 필드는 아직 구현되지 않았다. 내부 schema·profile·domain 및 소비자를 함께 바꾸고 해시를 결속한다. 초기에는 원문·용어집·색인을 재구축하지 않는다. 요청 기록 버전을 변경하면 새 run에만 적용하고 완료 기록은 보존한다.

실제 제품 연결은 `service.py → semantic_runtime.app/Pipeline → ServingLegalAgent → StageRunner`를 따른다. 연구 실행기의 세션 직접 호출만으로 이 연결 검증을 대신하지 않는다. 외부 응답 `term-runtime-v1`의 기존 답변·미확인 표현을 우선 사용하며, 새 외부 필드가 필요하면 소비자 변경 범위를 따로 명시한다.

## 5. 대표 실행 시나리오

|입력·상황|Gemma가 수행할 판단|답변·검토 기록|
|---|---|---|
|일반 질문인데 특례만 확보|특례 요건과 질문 사실 비교, 일반 근거 추가 탐색 여부 결정|확보 범위를 밝히고 질문 자체를 특례로 바꾸지 않음|
|두 조건 중 하나만 충족|원문의 OR/AND를 확인하고 사실을 적용|원문·적용 사실·결론 연결. 반대 조건 쌍도 평가|
|분류는 가능하고 위반 판단에는 사실 부족|요구를 분리해 확정·유보 결정|분류 직접 답변 + 위반 판단에 필요한 사실|
|공식 질문에 주변 설명만 작성|검토자가 원질문 요구와 초안 차이 지적|공식 보완 또는 명확한 미확인 사유|
|필요한 조건이 모두 확보됨|추가 탐색·질문 없이 답변 가능 판단|불필요한 유보·추가 질문 발생 여부 확인|
|검토자가 정상 답을 잘못 지적|지적과 원문을 대조해 수용/기각|근거 없는 수정으로 정상 답을 망가뜨리지 않음|
|원문 버전이나 기준시점이 맞지 않음|현재 근거로 적용 가능한 범위 확인|버전 불일치와 해석 불확실성을 구분, 근거 없는 단정 보류|

판단 기록을 형식적으로만 채우는 위험이 있다. 서버는 참조 무결성을 검사하고, 의미 검증은 실제 질문·원문·답변 대조로 수행한다. 모델이 분해한 요구 목록도 틀릴 수 있어 원질문을 항상 함께 본다.

## 6. 보강 효과를 확인하는 순서

실험을 위한 구현 수정·첫 호출 전에는 저장소 실험 표준 두 문서를 끝까지 읽고 동일 scope reservation 확인 → 새 ADR 선점 → snapshot/register/freeze 절차를 따른다. 이번 작업은 계획 작성이며 실제 실험은 시작하지 않았다.

1. **기준 고정:** 완료된 `ADR-0498-experiment-v1 / gemma / rev-001`을 연구 부모로 삼고 정확한 코드·자료·모델·프롬프트를 고정한다. 부모가 Rejected였다는 사실은 유지한다.
2. **P1부터 순차 수정:** 질문 요구, 탐색·규칙 선택, 조건 보존, 유보, 검토를 차례로 바꾼다. 한꺼번에 모두 바꿔 무엇이 효과가 있었는지 모르게 만들지 않는다. 결과를 본 뒤 변경한 후보는 새 ADR로 분리한다.
3. **고정 원문 판단 과제:** 필요한 원문과 사실을 같게 주고 수정 전후 Gemma를 비교한다. 특례 적용·논리·유보 판단을 직접 확인한다.
4. **에이전트 과제:** 같은 질문을 실제 탐색부터 수행해 다음 행동·선택·종료·답변에서도 효과가 유지되는지 본다. 고정 원문 성적과 합치지 않는다.
5. **성공 사례 회귀와 독립 과제:** 기존 Gemma 성공 사례를 유지하는지 보고, 개발 중 사용하지 않은 사례로 확인한다. CM51·FSC10을 새 holdout이라고 부르지 않는다.

|측정할 것|평가 단위·방법|개선 판단|
|---|---|---|
|질문 충족|요구 항목별 실제 응답 여부와 전체 질문 완결성|주변 설명만 한 답 감소, 원래 답한 요구의 누락 없음|
|규칙·범위 선택|원칙/특례와 적용 사실의 근거 대조|질문 범위 임의 축소·근거 없는 특례 적용 감소|
|조건 보존|필수 조건·논리·예외별 대조|결론을 바꾸는 조건 오류 감소|
|확정/유보|충분한 입력과 사실이 빠진 짝 과제|과잉 단정과 과잉 유보를 모두 감소|
|다음 행동|선택 당시 입력과 미해결 요구를 대조|새 정보 목적 없는 반복·근거 부족 상태의 종료 감소|
|교정·검토|틀린 답 수정과 정상 답 보존을 각각 측정|오답 승인·정상 답 오거부·잘못된 교정 감소|

기준답은 적용 시점·원문 버전을 확인하고 검토한 뒤 동결한다. 자동 채점은 보조이며, 작성·검토·채점이 모두 Gemma라고 해서 서로의 정답을 보증하지 않는다. 반복 실행과 파생 질문은 원사례 단위로 묶어 일관성을 보고한다. 답변 미관측과 의미 오답을 분리하고, 평가 가능한 답만의 성적과 전체 시도 기준 결과를 함께 남긴다.

구체적인 최소 개선폭·허용 회귀·표본 수·호출 상한은 결과를 보기 전에 새 ADR에 고정한다. 현재 제안은 중대 조건/범위 오류를 해소하고 기존 확인된 Gemma 성공 사례의 중대 회귀를 허용하지 않는 것이다. 전체 정확도 상승만으로 특정 중대 회귀를 덮지 않는다. 값이 미정인 상태로 실행하지 않는다.

## 7. 기대효과와 적용 범위

기대효과는 ‘설명은 맞는데 질문·조건·적용 범위가 틀리는 답’을 줄이는 것이다. 개선율은 미측정이다. 요구 분해 자체가 틀리거나 검토가 정상 답을 과도하게 거부하면 품질이 악화될 수 있다. 그래서 성공 사례와 충분한 근거가 주어진 과제를 함께 검사한다.

추가 비용은 `늘어난 입력·검토·교정 비용 − 줄어든 불필요한 탐색·재작성 비용`이다. 두 항이 같으면 손익분기다. 검토 기록만 길어지고 잘못된 판단이 줄지 않으면 비용과 지연이 늘어난다. 기존 호출에서 필요한 판단만 보강하고, 추가 호출은 분리 검증한다.

|ID|종류|값·근거·확인 방법|
|---|---|---|
|J1|관측|Gemma 긍정 사례 CM008·009·025·050. 사례 기반 신호이며 능력별 성공률 아님|
|J2|목표|동결한 기존 성공 사례에서 중대 의미 회귀 0건. 해당 사례 범위의 기준이며 보편적 무오류 보증 아님|
|J3|미확인|개선율·추가 비용·구현 인일 미산정. 동일 조건 비교와 작업별 기록으로 확인|

수정·검증 단위는 P1 → P2 → P3 → P4 → P5다. 처음 구현할 묶음은 **질문 요구 유지와 요구별 근거 연결**이다. 이 연결이 있어야 다음 행동, 조건 검토, 판단 보류의 이유를 같은 기준으로 평가할 수 있다.

작업 코드 기본은 현재 v2이고 로컬 활성 frozen release는 `document-navigation-rag-20260921-v1`의 `document-navigation-v1`이다. 연구 후보와 별도다. 검증한 후보만 표준의 Accepted·out-of-sample·decision_eligible·complete 요건, 최종 validate/graph와 명시적 promotion 절차를 거쳐 이행한다. 롤백은 코드·profile·데이터 결속 묶음으로 수행한다. GENOS 내부 모델·현장 성능은 별도 검증 대상이며 이번 계획으로 바꾸지 않는다.
