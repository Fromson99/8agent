# A8 아키텍처 초안 v0.5 상세 수정 검토

검토일은 2026년 10월 14일이다. 대상은 첨부된 19쪽 PPT이며, 우리 담당인 과제3 법·규정 챗봇과 과제5 리스크 규정, 이 두 과제에 적용되는 공통 설명을 검토했다. 다른 다섯 과제의 구현·성과는 이 저장소의 근거만으로 승인하거나 수정 대상으로 단정하지 않는다.

**공통 배치 구조는 유지할 수 있다. 그러나 과제3·5의 처리 흐름은 현행 v6를 기준으로 다시 작성해야 한다.** 과거 LegalClosure·의미 메타·비교 API 설명과 현행 조사 에이전트가 한 도식에 섞여 있다. 특히 구 API 파일이 저장소에 남아 있다는 사실을 현재 서비스에서 호출된다는 뜻으로 사용하면 안 된다.

이 검토서는 PPT 편집자가 바로 사용할 교체 문안, 박스·연결선 수정 지시, 개발자가 확인할 코드 근거를 제공한다. 원본 PPT와 제품 코드는 수정하지 않았다. 아래 상태는 모두 **수정안 작성 / PPT 미반영**이며, 별도로 지적한 기능의 재통합·현장 검증이 완료됐다는 의미가 아니다.

## 2 실제 호출과 데이터 흐름

### 서비스 선택

GENOS 파일 로더용 `service/service.py`는 저장소 루트의 `service.py`를 정확한 파일 경로로 적재한다. 루트의 `application()`은 먼저 실행 binding을 결정한다.

1. 명시한 `GENOS_GENERATION`이 있으면 해당 GENOS 데이터 세대를 선택한다.
2. 그렇지 않고 `GENOS_DATA_ROOT` 아래 CURRENT가 있으면 그 포인터와 manifest를 검증한다.
3. 두 설정이 없으면 로컬 ACTIVE_RELEASE에서 동결 코드와 데이터 경로를 선택한다.
4. 선택된 `semantic_runtime.app.create_app()`을 적재한다. 로컬은 해시로 검증한 릴리스를 별도 Python 패키지로 가져온다.

따라서 로컬 MAIN62가 GENOS의 최신 배포 리비전을 결정하지 않는다. GENOS의 선택 코드와 데이터는 현장 기록으로 별도 확인해야 한다. 근거 E01·E02.

### 질의 경로

```text
채팅앱
  → 워크플로우 입력·세션·표시 어댑터
      → AD 모드 확인
      → 법률 질의 SSE 요청
  → HTTP 어댑터 /stream
  → service.service
  → LEGAL_AGENT 요청을 /v1/rag/ask로 변환
  → semantic_runtime Pipeline
  → 선택 구현 legal-agent-unified-v6
  → legal-agent-rag-v6 엔진과 요청 상태
  → 원문 조사·근거 선택·쟁점 판단·답변 작성
  → 발행 검증·결과 저장
  → 진행·답변 조각·최종 상태를 화면에 표시
```

직접 채팅을 위한 `chat_adapter.chat()`과 공통 SSE 소비 코드는 존재한다. 그러나 확인한 `stream_app.py`의 실제 라우트는 /json·/stream이며, 이 파일 자체에는 /chat 등록이 없다. 플랫폼의 별도 main 또는 main_router가 어댑터를 호출하도록 연결됐는지는 해당 리비전의 라우터로 확인해야 한다. 따라서 “워크플로우 없는 직접 /chat”은 **보조 어댑터 구현 보유, 선택 라우터·현장 연결 확인 필요**로 표시한다. 유지 중인 워크플로우의 일반 질의는 SSE 호출을 사용한다. 플랫폼 표준 JSON 호출, 별도 SSE 서버, 직접 채팅 경로를 한 개의 동일한 API라고 표현하지 않는다. 근거 E03·E04·E23.

외부 엔진 계약은 retrieve → select → assemble → answer의 네 구간이다. 내부 상태 단계는 INTENT → PLAN → RECALL → READ → SELECT → ASSESS → COMPOSE다. **일곱 단계는 논리적 책임과 상태 구분이며, 매 질문마다 모델을 정확히 일곱 번 호출한다는 뜻이 아니다.** 요청 앞단 통합, 직접 안내, 기존 상태 재사용, 추가 조사에 따라 실제 호출이 달라진다. 근거 E05·E06·E07.

### 구축 경로

```text
원본·출처·문서 버전
  → 형식별 구조화
  → 원문·구조·좌표 보존
  → 선택 원문 통합
  → 선택 용어집·문서 정의·명시 참조 연결
  → navigation과 최소 구조 단위 본문 색인
  → 서빙 후보·검증·감사 기록
  → 별도 활성화 절차
```

기본 `build-all`은 `native-no-models` 정책을 읽어 구조화에서 VLM과 PDF 변환을 끄고 로컬 PDF 파서를 사용한다. 이어 `document-release prepare`와 별도 run의 `reindex`를 호출한다. 모델 검토 경로는 `--with-model-review`로 명시한다. S0~S6와 다른 파서 구현이 저장소에 있다는 사실은 보존하되, 모든 신규 문서가 그 하나의 경로를 통과한다고 쓰지 않는다. 근거 E08·E09.

## 4 페이지별 교체 문안과 도식 수정

### 2쪽 과제 요약 표

과제3 핵심 처리 셀의 `관계 간선·메타 태깅 → LegalClosure → 필수 동반 조문`을 다음 문안으로 교체한다.

> 용어집을 기반으로 원문·구조·정의·명시 참조를 연결하고 색인한다. 질의 시 허용 문서 안에서 구조·본문·용어 단서로 원문을 조사하고, 근거 선택과 쟁점 판단을 거쳐 답변한다. 부족한 근거는 재조사하고 인용·미확인 사항을 함께 표시한다.

과제3 출력 셀은 `답변 + 인용 원문 + 확인 범위·미확인 사항`으로 바꾼다. GenOS 경로는 `B 코드서빙 — 자체 원문·용어 색인과 상태 SQL`로 정리한다.

과제5 핵심 처리 셀은 다음처럼 현재와 별도 기능을 함께 표시한다.

> 공통 v6 엔진에서 내규·외규 범위와 팀별 문서를 선택해 질의한다. 관련 원문을 함께 조사하여 적용 조건과 차이를 설명한다. 전용 상충점검 엔진의 자동 수치 비교·요건 판정은 구 구현을 보유하며, 현행 서비스 재통합과 검증이 필요하다.

출력은 `현재: 근거 답변·확인사항 / 전용 상충점검: 재통합 후 별도 판정 출력`으로 구분한다. 전용 엔진의 네 상태가 현재 모든 리스크 질의의 고정 반환값인 것처럼 쓰지 않는다. 근거 R1~R4.

### 3쪽 공통 실행 아키텍처

상단의 채팅앱 → 워크플로우 → 코드서빙이라는 큰 배치는 유지한다. 제목의 “전 과제가 동일 뼈대로 구동”은 공통 배치 원칙이라는 뜻으로 한정하고, 개별 파이프라인·상태·저장소·반환 계약까지 동일하다는 뜻으로 확대하지 않는다.

워크플로우 박스 교체 문안:

> 질문·사용자·세션·팀 범위를 전달하고 진행 상태, 답변 스트림, 인용 출처, 최종 처리 상태를 표시한다. 법률 판단과 답변은 백엔드 결과를 사용하며, 화면에서 별도 모델로 다시 생성하지 않는다.

코드서빙 박스 교체 문안:

> 선택 코드와 데이터 세대를 확인한 뒤 요청을 처리한다. 법률 에이전트는 조사·근거 선택·판단·답변 작성을 수행하고, 코드가 스키마·근거·권한·버전·상태·예산을 검증한다. 결과는 상태와 함께 저장·발행한다. 배포 단위는 과제별 또는 공통 엔진별로 구성할 수 있으며 과제3·5는 공통 엔진을 사용한다.

모델 박스는 `GenOS 내부 LLM — 의도·탐색 행동·근거 선택·판단 제안·답변 작성`으로 바꾼다. 임베딩은 필요한 과제의 별도 자원으로 표시하고, 법률 v6의 모든 질의에 필수로 호출되는 것처럼 연결하지 않는다.

저장소는 법률 과제에서 두 종류로 나눈다.

- 원문·탐색 데이터: 문서, 구조, 본문, 용어집, 정의, 명시 참조, 본문 색인.
- 실행 상태: 세션, 질문 revision, 조사·판단 기록, 예산, 발행, shortcut·위키·AD 작업 상태.

`{code, data{status,text,sources…}}`를 7개 과제 공통 백엔드 정본이라고 고정하지 않는다. 법률 루트 서비스는 `{status, body}`를 반환하고 브릿지는 body/data/result 형태를 풀어 처리한다. 화면용 text와 내부 answer·claims·source ID는 서로 다른 소비자 계약이다. 발표 본문은 “공통 어댑터가 과제 응답을 화면 형식으로 변환”으로 줄이고, 정확한 JSON은 기술 부록에 둔다. 근거 E01·E03·E04, R4·R8·R9.

### 4쪽 품질과 안전 체계

제목은 `근거와 상태를 검증하고 미확인 사항을 드러내는 품질 체계`로 바꾼다. 여섯 영역은 유지하되 우리 과제에 적용되는 설명을 다음처럼 수정한다.

| 영역 | 교체 문안 |
|---|---|
| 평가 | 코드·데이터·모델·질문 집합을 고정해 평가한다. 근거 회수·인용 무결성·법률 판단 품질을 나누어 보고한다. |
| 근거 검증 | 허용된 현재 원문의 ID·인용 구간·버전·해시와 답변의 연결을 검증한다. 이 검증만으로 법률 의미의 정답을 보증하지 않는다. |
| 부족분 처리 | 원문 부족은 추가 조사, 실제 사용자 사실 부족은 확인 질문으로 연결한다. 검증된 주장이 있으면 한계를 포함한 제한 답변을 제공하며, 유효한 주장이 없으면 미완료·실패 상태를 반환한다. |
| 스트리밍 | 확인된 판단과 근거에 연결해 답변을 생성·전송하고 최종 구조·본문 일치를 검사한다. 일부 전송 뒤 실패하면 미완료로 남기고 다른 답변을 이어 붙이지 않는다. |
| 기록과 보호 | 원문·실행·실패 기록을 보존하고 화면 노출을 제한한다. 인증정보는 제거하며 개인정보 마스킹의 적용 범위는 별도 정책·구현 근거로 확인한다. |
| 운영 검증 | 정상·복구·중단·재개·중복 요청을 계약 검사한다. 부팅·HEALTH와 실제 모델 질의·답변 품질·현장 배포를 구분한다. |

“원문에 없는 값은 답 전체 폐기”와 “검증 완료 후 한 번에 반환”은 삭제한다. “근거 부재 시 답변 차단”은 “근거가 확인되지 않은 주장은 확정하지 않는다”로 바꾸면 현재 제한 답변과 양립한다. “환각 차단”은 검증의 목적과 범위로 설명하고 완전 방지 성과로 쓰지 않는다.

개인정보 마스킹은 다른 과제의 전처리 기능일 수 있으므로 삭제 범위를 우리 과제의 공통 적용 주장에 한정한다. 인증값 제거 코드는 개인정보 전체를 자동 비식별화한다는 증거가 아니다. 근거 E10·E11·E12·E17, R5·R10·R11.

### 9쪽 법률 질의 흐름 그림

제목 교체: `과제3 법·규정 질의 — 용어 기반 원문 조사와 근거 판단`.

기존 도식에서 다음 박스를 교체한다.

| 현재 박스 | 교체 박스 |
|---|---|
| 쟁점 분해 | 요청·쟁점·범위 확인 |
| 다채널 구조 착지 | 구조·본문·용어·정의·명시 참조를 이용한 원문 탐색 |
| 필수 동반 검색 | 필요한 연결 원문·조건·예외 확인 |
| 회복 사다리 | 부족분에 따른 추가 조사·종료 판단 |
| 착지 교정 | 필요한 구조 범위 읽기·근거 채택·보류·제외 |
| 답변 생성 | 쟁점 판단 → 근거와 한계를 보존한 답변 작성 |
| 커버리지 게이트 | 스키마·근거·상태 검증과 최종 발행 |

실제 배열은 위 표의 단순 일대일 치환보다 아래 순서로 다시 배치하는 것이 낫다.

```text
질문·정정
  → 범위·의도 확인 → 조사 계획 → 후보 회수 → 원문 읽기
                                            ↓
                               근거 선택 → 쟁점 판단 → 답변 작성
                                   ↑          │          ↓
                                   └─ 근거 부족 ┘     검증·발행

저장소: 원문·용어·정의·참조·단위 본문 색인
상태 SQL: 세션·질문 revision·단계·원문 확보·판단·예산·실패
재사용: 성공한 근거 경로 → 현재 원문·권한 확인 → 후보 회수
```

연결선 수정 지시:

1. 쟁점 판단에서 근거 선택·원문 조사로 되돌아가는 선을 추가한다. “중요 원문 부족·예산 허용 시”라고 적는다.
2. 실제 사용자 사실 부족은 사용자 확인으로 연결한다. 원문을 못 찾은 경우를 무조건 사용자 질문으로 보내지 않는다.
3. 원문·색인 저장소는 검색·읽기에 연결하고, 상태 SQL은 요청·단계·판단·발행에 연결한다.
4. 성공 경험 재사용은 점선으로 그리고 “기능 설정·권한·세대 확인 후”라고 적는다. GENOS에서 항상 켜져 있다고 그리지 않는다.
5. 용어집은 적재·질의 모두에 연결한다. 구축 시 문서 출현 연결을 만들고 질의에서 정의·관계 탐색에 사용한다.
6. LLM 선은 의도 확인·탐색 선택·근거 선택·판단·작성에 연결한다. 모든 선이 반드시 별도 호출을 뜻하지 않는다고 범례에 적는다.
7. 과거 LegalClosure, assertion 4채널, 고정 6종 동반 회수는 현행 기본 박스에서 제거하고 필요하면 “이전 연구 구조” 부록으로 옮긴다.

“관계 간선에 있는 6종을 반드시 모두 회수” 대신 다음 문장을 사용한다.

> 질문과 현재 근거에서 필요한 정의·명시 참조·조건·예외를 확인한다. 확보하지 못한 관련 근거와 그 영향을 보존하고, 추가 조사 또는 제한 답변으로 처리한다.

명시 참조를 색인하고 조회하는 기능은 현행에도 있다. 수정 대상은 참조 기능 자체가 아니라, 과거의 고정된 6종 자동 폐쇄가 현행 전체 검색 정책이라는 주장이다. 근거 E06·E07·E10·E13, R1·R4·R9.

### 10쪽 구축과 질의 상세 설명

적재 부분은 다음 여섯 단계로 바꾼다.

1. **원본 등록:** 문서 ID·출처·버전·원본 해시·공개/내부 구분을 남긴다.
2. **형식별 구조화:** 구조와 본문을 복원한다. 현재 통합 구축은 native-no-models가 기본이며 모델 검토는 별도 선택한다.
3. **원문 통합:** 선택할 문서와 완료 범위를 명시하고 원문·좌표를 보존한다.
4. **용어 연결:** 선택 용어집, 문서 내 정의, 용어 출현과 명시 참조를 연결한다.
5. **색인 생성:** navigation과 최소 구조 단위 본문 색인을 원문·용어집 해시에 결속한다.
6. **검증과 활성화:** 후보의 계약·무결성을 검사하고 별도 승격·포인터 전환을 수행한다.

S0~S6는 “형식별 구조화의 보유 구현·선택 경로”로 설명할 수 있으나 공통 필수 단계명으로 사용하지 않는다. Docling 서브클래스도 별도 확인 없이 현재 모든 문서의 흡수 경로로 표시하지 않는다. `lsDelegated` 원천 관계를 활용하는 코드는 남아 있으므로 관계 기능을 전부 삭제했다고 쓰지 않는다. 다만 외부 API를 GENOS 질의 때마다 실시간 호출하거나 법령이 자동 최신화된다는 의미로 그리지 않는다.

질의 부분의 교체 문안:

> 요청의 목적과 허용 문서 범위를 확인한 후 구조·본문 검색과 용어·정의·참조 조회를 조합한다. 법령별 후보와 필요한 원문 범위를 읽어 근거를 선택하고, 쟁점별 조건·예외·부족분을 판단한다. 보완 가능한 근거 부족은 조사로 되돌리고, 답변에는 인용과 확인 범위를 함께 표시한다.

현재 프로필에 `structure_first=true`가 있어도 모든 질문에서 구조 검색을 먼저 강제한다는 뜻은 아니다. `selectable_search=true`이며 요청 앞단이 STRUCTURE와 FULLTEXT를 선택할 수 있다. 따라서 “구조를 반드시 먼저 검색”으로 과도하게 고정하지 않는다. “질의마다 법령 전체 원문 탐색” 역시 문서 목록·메타 후보 조회와 본문 읽기를 나눠 증명해야 한다. 근거 E07·E13.

구성요소 표의 권장 설명:

| 구성요소 | 우리 과제의 역할 |
|---|---|
| 채팅앱 | 질문·정정 입력, 진행·인용 출처·답변·최종 상태 표시 |
| 워크플로우 | 팀·세션·요청 전달, AD/법률 분기, SSE 결과 표시 |
| 코드서빙 | 선택된 코드·데이터에서 v6 조사·판단·작성 실행, 계약 검증과 상태 저장 |
| LLM | 조사·근거 선택·판단·표현 제안. 서버가 제안의 형식·근거·권한·상태를 검증 |
| 데이터 저장 | 원문·용어집·navigation·unit fulltext와 별도 감사 자료 |
| 상태 저장 | 세션·revision·조사·실패·예산·발행·성공 경험과 관리 작업 |

현황 박스 교체 문안:

> 로컬 선택 릴리스는 MAIN62이며 v6 조사 엔진과 원문·용어·단위 본문 색인이 연결되어 있다. 선택 데이터 명세는 1,546문서다. 계약·코드 연결 검증과 법률 의미 품질 평가는 구분하며 quality_certified=false를 유지한다. GENOS의 최신 적용 상태는 현장 코드 리비전·데이터 세대·워크플로우 기록으로 별도 확인한다.

42문서 수치를 남기려면 “어느 시점, 어느 법령 부분집합인가”를 붙인다. 1,546문서도 전부 법령이거나 전부 외부 모델에 전송 가능한 자료라는 뜻으로 쓰면 안 된다. `6.7만 토큰`은 현행 모델·요청·입력 계측 기록이 확인되기 전에는 현재 평균값으로 사용하지 않는다. 근거 R2·R6·R7·R12.

### 13쪽 리스크 규정 흐름 그림

현재 연결된 질의와 전용 비교 엔진을 시각적으로 분리한다.

현재 질의의 실선 흐름:

```text
내규·외규 관련 질문
  → 팀·문서·출처 범위 선택
  → 공통 v6 원문 조사
  → 필요한 양쪽 근거 확인·선택
  → 조건·차이·적용 범위 판단
  → 인용·한계를 포함한 답변
```

별도 박스의 문안:

> 전용 상충점검의 과거 구현: 비교 대상 회수 → 정량 비교 → 정성·요건 검토 → 네 상태 판정. 현행 v6·데이터 계약에 재통합하고 API·화면 연결 및 품질을 검증해야 한다.

이 박스는 현재 질의 흐름과 같은 실선으로 이어 붙이지 않는다. `짝 찾기(LegalClosure)`·`정량=코드`·`정성=LLM`·`상충/미비/부합/재검토`는 해당 전용 구현의 설명으로 이동한다. 현재 일반 질의가 이런 고정 절차·고정 결과 스키마를 실행한다고 표현하지 않는다.

“검토요청서 항목별 점검”과 “신구판 조 단위 대비”가 이미 설계로 표시된 점은 유지한다. 업로드 파일을 받는 기능과 업로드 문서의 모든 항목을 자동 점검하는 기능도 구분한다. 근거 E14·R3.

### 14쪽 리스크 규정 상세 설명

제목 권장: `과제5 리스크 규정 — 공통 질의와 전용 비교 기능의 연결 상태`.

현재 기능 설명:

> 내규·외규 질의는 공통 v6 조사 엔진을 사용한다. 팀·문서·출처 범위 안에서 필요한 원문을 조사하고 근거에 연결된 판단과 확인사항을 제공한다. 일반 질의의 답변과 전용 상충 판정 API는 구분한다.

전용 비교 기능 설명:

> 구 비교 라우터에 /v1/rag/compare와 정량·요건 검토 구현이 보존되어 있다. 현재 선택된 semantic_runtime 앱에는 이 경로가 등록되지 않는다. 재사용하려면 현행 원문·용어·상태·권한 계약을 소비하도록 통합하고 API·워크플로우·발행 소비자를 함께 검증해야 한다.

“채팅 노출만 남음” 대신 남은 일을 다음 순서로 적는다.

1. 비교 입력의 내규 문서·원문 범위·판본을 현재 ID와 세대에 연결한다.
2. 비교할 외규의 선택·참조·범위를 현행 조사 엔진과 연결한다.
3. 수치 비교에서 대상·단위·시점·적용 범위가 일치하는지 확인한다. 단순 숫자 대소만으로 상충을 확정하지 않는다.
4. 상충·미비·부합·재검토 결과를 현행 근거·상태·실패 계약과 연결한다.
5. 전용 API, 서비스 분기, 화면 표시, 상태 저장을 같은 코드로 검증한다.
6. 합성 계약과 실제 내부 규정의 의미 평가를 분리해 기록한다.

이는 신규 구현을 했다는 설명이 아니라, 구 기능을 현행 기능으로 보고하기 전에 필요한 연결 조건이다. “실제 사내 내규 미반입”이라는 과거 문구도 현재 전체 상태로 유지하려면 현장 자료가 필요하다. 로컬 팀 RAW의 준비·선택 기록만으로 GENOS 실제 내부 원문의 반입·품질을 인증하지 않는다.

평가 설명은 다음으로 교체한다.

> 과거 합성 상충 사례와 현재 등록 질문을 구분한다. risk_cm 105문항은 정답·필수근거 승인 전 question_only 상태이며, 등록 완료를 평가 통과나 미사용 holdout으로 표현하지 않는다.

외규 질문 표시도 내부 질문의 외부 모델 반출 승인으로 사용하지 않는다. 실제 내부 규정의 처리·품질 검증은 GENOS에서 수행한다. 근거 E14·E20.

## 5 추가해야 할 아키텍처 책임

### 용어집과 원문 연결

용어집 구축·갱신은 전체 MAIN의 공통 기반이다. 기존 사전·별칭·정의·관계를 선택한 문서 세대와 연결하고, 출현 위치와 명시 참조를 보존한다. 구조화만 끝났다고 용어집 검토·정의·관계 수집까지 완료됐다고 쓰지 않는다. 문서 추가 시 어떤 범위의 연결·색인을 다시 만드는지도 표시한다.

### 세션과 조사 상태

질문·사용자·팀·문서 범위, 질문 revision, 단계 결과와 원문 확보 상태가 SQL에 저장된다. 정정은 필요한 단계부터 다시 실행할 수 있으며 중복 요청·오래된 상태의 발행을 검사한다. 멀티턴은 실제 사용자·대화 식별자와 설정이 필요하므로 모든 익명 요청에 자동 제공된다고 쓰지 않는다. 근거 E03·E06.

### 경험 재사용과 피드백

성공한 답변 발행과 현재 revision·근거 조건을 확인한 뒤 근거 경로를 재사용 자산으로 등록한다. 실패 기록은 보존하되 성공 경로로 등록하지 않는다. shortcut·위키 기능은 프로필뿐 아니라 SQL의 팀별 설정으로 꺼질 수 있다. 특히 현장 인계본의 wiki-recall 비활성 조건을 로컬 기본값으로 덮어 해석하지 않는다.

사용자 피드백은 answer ID·query ID·실행 파일 hash·원문 세대에 결속한 PROPOSED 후보다. 이후 REVIEW_AND_VALIDATE가 필요하며 피드백이 곧바로 원문이나 정답을 바꾸는 자동 학습 루프는 아니다. 근거 E06·E15·E16.

### 검증과 복구

모델 출력의 JSON·스키마 검사, 필드 간 판단 일관성, 근거·권한·버전, 상태 revision과 발행 검사를 나눈다. 같은 결정의 수정은 담당 경로가 정해진 예산 안에서 수행한다. 실제 원인 없이 재시도 횟수만 늘리거나 실패한 도구를 “원문 없음”으로 기록하지 않는다.

선택 프로필에는 모델 시도 40, 도구 1,024, 시간 1,800초, 추가 검색 8, 판단 후 재조사 2 등의 기본 한도가 있다. **이 값은 상한 설정이지 평균 사용량·처리시간 성과가 아니다.** 서비스 환경 override와 단계별 교정 담당에 따라 실제 effective policy를 확인한다. 자료에는 숫자를 본문에 나열하기보다 “요청 단위 예산·동일 오류 제한·상태 보존”으로 표현한다. 근거 E10·E18.

### 배포와 저장소

데이터 구축 완료, 서빙 후보 검증, 로컬 릴리스 활성화, GENOS 코드 적용, Git push, 코드서빙 리비전 배포, 워크플로우 편집기 반영은 별도다. 새 원문·색인을 만들었거나 작업 파일을 고쳤다는 사실만으로 실행 중인 서비스가 바뀌었다고 보고하지 않는다.

상태 SQLite는 로컬 WAL, NFS/CIFS DELETE와 synchronous FULL 정책을 갖는다. 파일 잠금·트랜잭션이 있지만 현장 NFS의 서버 간 잠금·fsync·장애 내구성은 별도 검증 대상이다. “NFS에 SQLite가 있으므로 고가용성·다중 서버 내구성 확보”라고 확대하지 않는다. 근거 E01·E19·E21.
