# 내부 법률 데이터 검색 전략 보강 설계

작성: 2026-09-22. 상태: **코드·선택 릴리스 대조에 근거한 설계안. 구현·새 실험·MAIN 승격·GENOS 배포 미실행.**

## 1. 권고안

현재 v5의 용어·원문 탐색 도구와 질문 요구 추적을 유지하고, **검색 결과의 전달 → 다음 검색 선택 → 원문 확인**을 보강한다. 공개 검색 skill에서는 절차를 가져오되, 별도 검색 서버나 대형 계획 장부를 추가하지 않는다.

우선 해결할 문제는 “검색 기능 자체가 없다”가 아니다. 현재 도구는 검색 조건과 전체 결과 수를 기록하지만 모델에게 주는 기본 화면에서는 그 정보가 빠지고, 최근 모델 도구 결과 두 개를 중심으로 표시한다. 여러 검색을 실행하면 먼저 나온 후보를 기본 화면에서 놓칠 수 있다. 또 전문 검색의 미리보기는 검색어 주변이 아닌 문서 앞부분으로 시작할 수 있다. 이는 코드에서 확인한 전달 구조이며, 실제 오답 중 차지하는 비율은 아직 측정하지 않았다.

권장 순서는 다음과 같다.

1. **찾은 결과를 제대로 보여준다.** 검색 영수증, 아직 제시하지 않은 결과, 검색어 주변 미리보기를 전달한다.
2. **기존 도구를 어떤 순서로 쓸지 짧게 가르친다.** 법령·조문 지정, 정확 표현, 용어 연결, 전문 검색, 명시 참조의 선택 기준을 기존 조사 프롬프트에 넣는다.
3. **불필요한 재검색·추가 선택 호출을 줄인다.** 같은 범위·질의·커서를 반복한 경우와 이미 결정이 끝난 원문을 다시 선택하는 경우를 구분한다.
4. 이후 별도 후보에서 모델 출력 계약을 줄인다. 기본 검색 성능이 여전히 부족할 때 색인·순위·벡터 검색을 비교한다.

| 품질 상태 | `quality_certified=false`, `USER_DIRECTED_CUTOVER` | 선택됐다는 사실을 품질 인증으로 해석하지 않는다. |

| 선택 색인 | navigation `term-navigation-index-v3`, fulltext `semantic-fulltext-v1` | 문서에 더 새 계약이 있어도 선택 데이터가 이행됐다고 가정하지 않는다. |

| 현장 | GENOS 접속·실행·내부 모델 성능 미확인 | 외부 정적 확인을 현장 검색 품질로 보고하지 않는다. |

[최초 근거 목록](source-inventory.json)은 읽은 파일 해시, 포인터, manifest 및 대조 범위를 기록한다. 포인터→릴리스 manifest, 릴리스→데이터 manifest의 해시 연결을 확인했으며 모든 DB 내용과 릴리스 파일을 재검증하지는 않았다.

조사 중 작업본 `PIPELINE.json`과 `profile-tools-v5.json`의 변경을 관찰했다. 선택 릴리스의 `max_context_chars`는 60,000이고, 후속 확인한 작업본은 100,000이다. 이번 작업이 변경한 값이 아니다. 아래 기준 예산은 선택 릴리스 값이며 최종 관찰은 [후속 기록](final-source-observations.json)에 남긴다. 이미 변경 중인 작업본을 실험 기준으로 그대로 사용하면 원인 비교가 섞이므로, 실제 구현 착수 시 부모 릴리스와 설정을 다시 동결해야 한다.

## 3. 지금 있는 것과 실제 연결

### 요청에서 출처 게시까지

```text
service.py: 환경별 데이터/구현 선택 또는 로컬 ACTIVE 릴리스 로드
  → app.py: /v1/rag/ask
  → Pipeline.run / ServingLegalAgent
  → legal_agent_adapter.py: v5 ObligationSession + TiersTools + ObligationRepository
  → Coordinator / StageRunner: retrieve → select → assemble → answer
  → 조사 중 기존 탐색 도구 실행, journal에 observation·evidence·decision 저장
  → workflow_tiers_views: 조사 화면 구성 → ModelGateway: 선택 프롬프트와 함께 호출
  → 질문 요구별 근거 선택·주장 검토 → source_bundle 검증 → 답변·출처 게시
```

진입점은 [service.py](../../../../service.py), [app.py](../../../../02_BACKEND/semantic_runtime/app.py), [pipeline.py](../../../../02_BACKEND/semantic_runtime/pipeline.py), [adapter](../../../../02_BACKEND/semantic_runtime/legal_agent_adapter.py), [coordinator](../../../../02_BACKEND/semantic_runtime/legal_agent/coordinator.py)다. 모델 설정은 명시적으로 연결해야 하며 선택 프로파일의 `model_binding=null`을 실행 가능한 모델 지정으로 해석하지 않는다.

**주의할 진단 경로:** `/v1/rag/search`의 기본 `use_llm=false`는 `ServingLegalAgent.retrieve`에서 상위의 메타데이터 탐색으로 연결된다. 에이전트 내부 `search(mode=fulltext)`와 동일한 경로가 아니다. `/ask`에서 LLM을 끈 경우도 조사 루프와 같지 않다. 이 응답을 보고 “BM25가 이 문서를 못 찾았다”거나 “에이전트 검색 재현율”이라고 판정하면 안 된다.

### 유지할 기반

| 현재 기능 | 확인된 구현·제약 | 판단 |
|---|---|---|
| 질문 요구 추적 | `question_obligations.py`: 기존 `question_plan`, 질문 구간과 요구 연결, 행동의 `question_refs`·`expected_information` | 유지. 별도 거대 SearchPlan 장부를 만들지 않는다. |
| 법령·조문 위치 찾기 | `locate`, 문서명·별칭, body/addendum/annex 분기, `browse` | 유지. 식별자가 있는 질문은 일반 전문 검색보다 먼저 사용하도록 가르친다. |
| 용어 연결 | `navigation_match.py`: 직접 매칭, MOLEG 일상어→동의어, 제한적 관련·상하위어 연결 | 유지. 이미 표현 연결이 있으므로 “동의어 검색 신규 도입”이라고 포장하지 않는다. |
| 전문 검색 | `fulltext.py`: Kiwi 형태소 OR 질의, FTS5 BM25, 표제/본문 가중치 | 유지 후 진단. 문장 전체를 긴 OR로 넣는 전략과 색인 품질을 구분한다. |
| 정확 표현·용어 출현 | `search(literal/title)`, `term_occurrences(any/all)` | 유지. `all`은 같은 source 안의 교집합이지 법률상 조건 AND나 같은 문장이라는 뜻이 아니다. |
| 정의·명시 참조 | `lookup_definition`, `follow_reference`, 관계 메뉴, 직접 참조 자동 읽기 | 유지. 용어집 설명은 탐색 힌트이며 원문 인용 자격과 구분한다. |
| 원문 확보 | `read`, 블록 범위·세대·해시, 실제 제시된 evidence | 유지. 검색 미리보기만으로 READ나 법률 근거로 승격하지 않는다. |
| 근거 선택·검토 | CORE/SUPPLEMENTAL 선택, 질문 적합성·범위·조건·예외 등 주장 검토 | 유지. 검색 개선을 이유로 답변 검증을 약화하지 않는다. |
| 반복·비용 방어 | 시도·도구·시간·무진전 예산, action ID 멱등성, READ 재사용 | 유지. 검색 중복 억제는 기존 방어에 추가한다. |
| 기존 피드백 학습 | `app.py`는 v1~v5를 기존 `learning.capture`에서 제외 | v5 자동 학습이 연결됐다고 설명하지 않는다. 검색 절차 재사용은 후속 후보·승인 경로가 필요하다. |

## 4. 보강·축소·제외 결정표

| 대상 | 결정 | 이유와 변경 범위 |
|---|---|---|
| 검색 조건·결과 수 전달 | **최우선 보강** | 저장된 `search_receipt`를 조사 화면에 축약 전달한다. 질의·범위·전체 건수·커서·표시 건수를 알아야 좁힐지 넓힐지 판단할 수 있다. |
| 미제시 검색 결과 | **최우선 보강** | 최근 두 observation 중심 표시를 미제시 결과 우선의 제한된 큐로 바꾼다. 이미 저장된 결과를 재검색하지 않아도 접근하게 한다. |
| 전문 검색 미리보기 | **보강** | 실제 매칭 어휘 주변의 원문 span을 보여준다. 생성 요약·가상 조문은 쓰지 않는다. |
| 검색 전략 playbook | **보강** | 기존 모델 호출에 짧은 신뢰된 지침을 주입한다. 공개 skill 설치만으로 제품에 연결되지 않는다. |
| 질의별 결과 비교 | **보강** | 요청 내부에서 새로 발견한 source와 이미 본 source를 구분한다. 법적 충분성을 서버의 건수 계산으로 대체하지 않는다. |
| 추가 source selection 호출 | **조건부 축소** | 조사 후 evidence가 있으면 별도 선택을 시도하는 경로를, 미결정·변경 근거가 있을 때의 복구로 좁힌다. |
| 동일 검색 반복 | **축소** | 동일 세대·권한·범위·mode·질의·cursor에 대한 재실행을 억제한다. 다른 범위·다음 페이지·요구가 달라진 경우는 보존한다. |
| 빈 `assessments`·`relation_assessments` 출력 | **후속 계약에서 제거** | 현재 비어 있어야 하는 필드도 모델이 출력해야 한다. 첫 후보에서는 호환성을 유지하고, 별도 버전 후보에서 모델 wire만 줄인다. |
| 원문·질문 장부·명시 참조 | **제거하지 않음** | 근거와 적용 범위 추적에 필요하다. 과거 장부 과잉 문제와 현행 최소 요구 추적을 구분한다. |
| QMD 별도 색인·검색 서버 | **이번 범위에서 제외** | 기존 세대·문서 ID·권한·원문 위치 계약을 이중 운영하게 된다. 질의 작성과 원문 fetch 패턴만 참고한다. |
| 외부 웹 검색·외부 RAG 서비스 | **제외** | 내부 법률 코퍼스의 검색 문제를 직접 해결하지 않는다. |
| HyDE·벡터·reranker | **후순위 비교 후보** | 현재 vector는 이 경로에서 사용되지 않는다. 먼저 전달 누락·검색 전략을 고친 뒤, 남은 의미 매칭 실패에 한정해 비교한다. |
| 자동 규칙 DB·조건 의미 스키마 부활 | **제외** | 현행 원문·용어·명시 참조 계약과 맞지 않는다. 모델의 질의 후보는 요청 내부 가설로만 둔다. |
| 모델별 대형 planner/검색 subagent | **제외** | 기존 조사 루프에 필요한 전략을 넣을 수 있다. 추가 호출·상태 동기화의 효과가 입증되지 않았다. |
| 과거 코드·ADR·데이터 | **삭제하지 않음** | 이 설계의 “뺄 것”은 런타임 부담·중복 기능이다. 이력과 실제 의존성을 파일명만으로 삭제하지 않는다. |

## 5. 제안 동작

### A. 질문 요구마다 다음 행동을 고르는 간단한 절차

기존 `question_plan`을 재사용한다. 주체·행위·대상·사건 시점·문서 범위를 원질문에서 보존하고, 빈칸을 모델이 임의로 확정하지 않는다.

| 질문의 단서/관측 | 다음 행동 | 피할 행동 |
|---|---|---|
| 법령명·조문 번호가 있음 | `locate` → 해당 범위 `read`; 동명·버전 불명확하면 후보 구분 | 전체 질문으로 전문 검색부터 반복 |
| 정확한 표현·용어가 있음 | `search(literal)` 또는 `match_terms` → `term_occurrences` → `read` | 용어집 정의만으로 적용 법률 확정 |
| 일상 표현만 있음 | 기존 bridge 확인 → 요구별 짧은 전문 질의 → 원문 용어로 재질의 | 모델이 추정한 법률 문구를 인용문 취급 |
| 결과가 너무 넓음 | 같은 허용 범위에서 주체/행위 단서를 나누어 질의, 알려진 문서·조 범위로 제한 | 모든 결과의 무조건 순차 읽기 |
| 결과 없음 | 별칭·활용형·명사 표현·검색 mode를 한 축씩 변경; 필요시 허용 범위 내에서 확장 | 날짜·문서·접근권한 제한을 몰래 제거 |
| 원문에 단서·준용·위임·별표 참조 | 관련 요구와 연결해 직접 참조 원문 확인 | 현재 질문과 무관한 용어 관계 연쇄 탐색 |
| 충분한 근거 또는 예산 한계 | 미충족 요구·버전·예외 상태를 명시해 합성/유보 | 검색 0건을 “규정 없음”으로 단정 |

이것은 고정된 모든 도구의 순회 순서가 아니다. 식별자가 있으면 바로 원문으로 가고, 추가 검색은 충족되지 않은 요구가 있을 때 한다. 법률의 적용 시점은 “가장 최신 문서”와 다를 수 있다.

### B. 검색 결과 전달 계약

첫 후보에서는 public API, 모델 행동 스키마, journal-v5 SQL을 유지한다. 기존 observation에서 서버가 계산하는 **model_view의 추가 정보**와 기존 이벤트 payload로 구현한다. 다음 필드는 설계 제안이며 현재 구현에 존재한다고 주장하지 않는다.

| 제안 정보 | 생산자 | 소비자·규칙 |
|---|---|---|
| 질의·mode·토큰·실제 검색 범위 | 도구 observation의 `search_receipt` 및 action | 모델이 질의를 바꾸는 판단; 권한 없는 문서명·건수는 표시 금지 |
| 전체 결과 수/반환 수/표시 수/남은 cursor | 도구 결과 + view builder | “없음”과 “아직 안 봄”을 구분. mode별 exact/unknown 여부도 표기 |
| 새 후보 수/중복 후보 수 | 세대·문서·source·범위 기반 요청 내 집계 | 탐색 효율 힌트. 새 후보 수가 곧 법적 충분성은 아님 |
| 미제시 결과 목록 | observation + 기존 model_view 제시 기록 | 가장 오래된 미제시 결과를 우선 배치하고, 길면 continuation으로 연결 |
| 원문 미리보기·매칭 span | 원문 블록과 검색 토큰 | 발견 후보로만 표시. 정확 READ와 인용 자격을 분리 |
| 요구별 미충족 정보 | 기존 question plan, 결정·검토 결과 | 모델이 의미 판단. 서버는 연결 누락만 검사 |

한 화면에는 새 행동의 receipt와 소수 후보를 먼저 보장하고, 실제 판단 중인 원문과 직접 참조 원문을 함께 유지한다. 긴 결과는 페이지를 나누며 **잘라낸 항목 수와 접근 방법을 숨기지 않는다**. 화면에 넣었다는 사실은 모델이 이해했다는 뜻이 아니다. “제시됨” 기록은 재검색 방지와 추적을 위한 전달 사실이다.

기존 `source_candidates.inventory`의 후보 분류를 재사용할 수 있으나, 게시용 조 단위 묶음만으로 검색 중복을 판정하지 않는다. 항·블록 범위가 다른 증거를 합쳐 없애면 안 된다. 신규 표시 참조는 기존 numbered references의 형식·수명·검증을 따라야 한다.

### C. 중복과 무진전

검색 재사용 키는 적어도 요청/접근 범위, 데이터·색인 세대, 문서·블록 범위, mode, 질의, cursor, 정렬·토크나이저 설정을 포함한다. literal의 공백·문장부호처럼 의미를 바꿀 수 있는 정규화는 임의로 적용하지 않는다. 요청 간 공유 캐시는 첫 후보에서 도입하지 않는다.

동일 실행은 결과를 재제시하고 실제 FTS 조회 여부를 기록한다. 그러나 모델의 같은 요구 반복에는 기존 무진전 방어를 유지한다. 새 action ID만 붙여 예산을 우회하거나, 질의 문구를 바꿨다는 이유만으로 성공적인 진전으로 처리하지 않는다. 0건 후 재시도는 기존 남은 예산 안에서만 허용하며 새로운 영구적인 “탐색 완료” 사실을 만들지 않는다.

### D. 선택 호출·참조 읽기

추가 선택 호출은 단순히 `choices`가 존재한다는 이유만으로 생략하지 않는다. 현재 제시된 관련 원문에 결정이 있고, 텍스트·범위·버전이 동일하며, 선택 오류·미해결 요구에 필요한 미결정 자료가 없고, 모델이 조사 종료를 요청한 경우에만 생략 후보가 된다. 그 외에는 기존 복구 호출을 유지한다. 생략 사유와 근거 fingerprint를 journal 이벤트로 남긴다.

직접 참조 자동 읽기는 유지한다. 현재 예산이나 페이지 한도를 넘으면 자동 읽기를 통째로 건너뛰고 수동 선택으로 넘기는 경로가 있다. 첫 후보는 이 상태를 분명히 전달한다. 이후 별도 후보에서 미충족 요구와 관계 witness에 따른 우선순위를 비교하되, 서버의 추정 관련성으로 나머지 참조를 영구 제거하지 않는다.

## 6. 구현 연결 지도

모든 항목은 제안이다. 별도 실행기 없이 기존 `/ask` → 동일 세션 → 동일 stage 연결을 사용한다.

첫 후보는 토크나이저·BM25 가중치·source 분할·navigation 스키마를 바꾸지 않으므로 데이터 재구축을 요구하지 않는다. 이후 이 항목을 바꾸면 새 색인 세대·manifest·하위 소비자 binding과 이전 세대로의 롤백을 별도로 설계한다. 경로 해석은 기존 workspace의 논리 root를 따른다.

빈 출력 필드 제거는 별도의 버전 계약 후보로 분리한다. 현재 v5 schema에서 그냥 삭제하면 폐쇄형 출력 검증을 깨뜨린다. 새 wire→기존 내부 객체 변환에서만 빈 배열을 보충하고, 레거시 journal·재생·출처 조회 호환성을 검사해야 한다. 새 repository VERSION까지 만들 경우 **`source_bundle.py`의 `(4, 5)` 분기에서 검증을 건너뛰지 않도록 반드시 수정**하고, `control.py`·`service.py` 구현 allowlist, `legal_agent_trace.py`, app의 journal 읽기까지 함께 확인한다. 번호만 올리고 완료 처리하지 않는다.

### 조사 프롬프트에 넣을 지침 초안

> 원질문의 요구·주체·시점·문서 범위를 보존한다. 다음 행동은 기존 question_refs와 expected_information으로 이유를 연결한다. 법령·조문이 지정됐으면 먼저 위치를 찾고 읽는다. 정확 표현과 용어 후보가 있으면 해당 도구를 쓰고, 없으면 요구별 짧은 전문 질의를 사용한다. 검색 receipt를 보고 범위·전체 수·새 후보·남은 페이지를 확인한다. 후보 미리보기는 근거가 아니므로 필요한 원문을 READ한다. 단서·예외·준용·위임은 해당 요구와 연결해 원문을 확인한다. 같은 검색을 반복하기 전에 미제시 결과와 커서를 확인한다. 검색 실패는 규정 부재가 아니다. 예산이 부족하면 미충족 요구와 확인 한계를 유지한 채 답변한다.

이 초안은 새 계획서 작성을 요구하지 않으며 별도 모델 호출을 추가하지 않는다. 검토 단계에는 실제 근거 공백 확인에 필요한 지침만 전달한다.

## 8. 수용 시나리오와 실패 처리

아래는 새 테스트의 설계이며 이번에 실행해 통과한 결과가 아니다. 법률 문구가 필요하면 모의 문서 또는 허용된 공개 원문을 쓰고 정확한 버전을 고정한다.

| 상황 | 기대 행동 | 거부/오류 처리 |
|---|---|---|
| 법령명+조문 번호 | locate → 범위 read → 요구와 연결 | 다른 법령의 같은 번호로 자동 대체 금지 |
| 일상 표현·전문용어 차이 | 기존 bridge와 짧은 전문 질의 사용 | 연결 결과를 법적 동치로 단정 금지 |
| 검색 배치의 앞쪽 결과에 정답 후보 | 미제시 큐로 접근 가능, 표시 수와 continuation 존재 | 최근 결과만 남겨 앞쪽 후보를 조용히 누락하지 않음 |
| 검색 0건 | mode·표현을 제한적으로 바꾸고 남은 공백 기록 | “해당 규정 없음” 자동 결론 금지 |
| 결과가 매우 많음 | 요구·허용 문서 범위로 좁히기 또는 다음 페이지 | 광범위 결과를 모두 context에 삽입하지 않음 |
| 같은 검색 재요청 | 요청 내 결과 재사용·재제시와 예산 기록 | 새 action ID로 무진전 제한 우회 금지 |
| 다른 cursor/범위의 검색 | 별개 작업으로 실행 | 부정확한 중복 판정으로 다음 페이지 차단 금지 |
| 같은 조의 다른 항·표 | 범위별 후보·READ 구분 | 조 단위 dedup으로 예외·별표를 삭제하지 않음 |
| 동명 문서·개정 전후 | 문서·버전 표시, 시점 불명확 시 유보/필요 사실 요청 | 최신 버전으로 무조건 통합 금지 |
| 권한 없는 문서 존재 | 검색 범위·건수·캐시·snippet 모두 권한 범위 내 | 이름·존재·전체 건수로도 노출하지 않음 |
| 참조 읽기 예산 초과 | 미읽음과 수동 선택 경로 표시 | 자동 읽기를 못 했는데 근거 확보로 기록하지 않음 |
| 미리보기에 지시문 포함 | 법률 원문 데이터로 취급, 시스템 전략과 분리 | 문서 내용을 도구 실행·권한 변경 지시로 취급 금지 |
| 선택 부분 성공 후 일부 오류 | 유효 결정을 보존하고 실패 부분만 복구 | 중복 적용·잘못된 선택 호출 생략 금지 |
| 합성 뒤 원문 binding 변경 | 기존 source bundle 검증 실패·재확인 | 오래된 근거로 새 세대 답변 게시 금지 |
| 문맥·시간 부족 | 제한·남은 후보를 명시하고 근거 있는 부분만 합성 | 무음 truncation·근거 없는 완결 답변 금지 |

| N7 | CORE 5 + SUPPLEMENTAL 5, 추가 선택 시도 최대 2 | 선택 프로파일·선택 검증 | 복합 질문의 충분성을 보장하지 않음; 이번에 상한 변경하지 않음 |
| N8 | 정확도 상승률·필수근거 재현율·평균 지연·비용·완료 일정 | **미확인** | 이 설계만으로 백분율·배수·일수 예측을 제시하지 않음 |

`max_context_chars`만 늘리면 저장돼 있지만 view에서 제외되는 필드가 자동으로 나타나지 않는다. 문맥 확대의 효과와 전달 계약 변경의 효과는 따로 비교해야 한다.

### 향후 비교의 측정 대상

평가 단위는 질문과 정확한 원문 버전이다. 검색 실패를 발견 실패, 표시 실패, 읽기 실패, 선택 실패, 합성/검토 실패로 나눠 기록한다. 정답 근거는 source뿐 아니라 필요한 조·항·블록과 대체 가능한 근거 집합을 사람 검토로 고정한다.

- 발견 재현율 = 고정 정답 근거 중 후보로 발견된 수 / 해당 정답 근거 수.
- 전달율 = 발견된 정답 후보 중 모델 화면에 제시된 수 / 발견된 정답 후보 수.
- READ 확보율과 최종 인용 충족률은 전달율과 별도로 계산한다. 분모가 0이면 0점으로 임의 대체하지 말고 해당 없음으로 기록한다.
- 질문 요구 충족·조건/예외 누락·잘못된 버전·근거 없는 주장을 분리하고 기존 검토기의 판정을 정답으로 자동 채택하지 않는다.
- 동일 검색 재실행, 무효 도구, schema repair, 추가 선택 호출, 모델 입력/출력 토큰, 단계별 지연과 전체 지연을 기록한다.

계약 수용 기준은 무권한 노출, 원문 binding 우회, 미리보기의 근거 승격, 잘못된 번호 참조를 허용하지 않는 것이다. 품질 성공 기준과 허용 회귀 수치는 실험 전 동결할 평가 집합·위험도와 함께 결정한다. 효과를 보고 기준을 바꾸지 않는다.

과거 [ADR-0474 trajectory audit](../ADR-0474_PHASE0_TRAJECTORY_AUDIT_20260920.md)은 장부 작성이 탐색을 밀어내는 위험을 보여주지만 구버전 기록이다. [CM003 도구 루프 진단](../CM003_TOOL_LOOP_DIAGNOSIS_20260921.md)의 불필요한 정의 추적도 참고하되, 현행 v5가 이미 보강한 관계 라벨·출처 위치 표시를 신규 기능으로 재제안하지 않았다. [v5 완료 기록](../LEGAL_AGENT_V5_COMPLETION_20260922/README.md)의 기존 검사 결과를 이번 설계의 성능 검증으로 재사용하지 않는다.

## 10. 비용·효과·일정 판단

기대효과는 “새 검색기를 넣어서 정확도가 오른다”가 아니라 **이미 찾은 후보의 전달 실패와 중복 작업을 줄인다**는 가설이다. 실제로 정답 후보를 못 찾는 경우에는 이 변경만으로 해결되지 않는다. 짧은 질의가 단어 관계를 잃거나 미제시 큐가 오래된 저품질 후보를 우선하는 역효과도 평가해야 한다.

호출별 실제 과금 단가를 `p_in`, `p_out`, 토큰을 `I`, `O`라고 하면 질의 비용은 `C = Σ(I×p_in + O×p_out) + 검색/저장 실행비`다. 단가 단위에 맞춰 환산하고 캐시 요금이 있으면 분리한다. 전략 지침·receipt 추가 토큰을 `A`, 생략한 선택 호출 비용을 `S`, 재검색·복구 감소 비용을 `R`라 할 때 `ΔC = A + 추가 계산비 − S − R`이다. **S와 R이 실제로 줄지 않으면 비용은 늘 수 있다.**

총 개발·검증·운영 전환비를 `F`, 질의당 확인된 절감액을 `d`라 하면 비용 기준 손익분기 질의 수는 `F/d`이며 `d>0`일 때만 의미가 있다. 현장 내부 모델은 외부 API 단가 대신 GPU 점유·처리량·운영비로 계산한다. 현재 F·d·실제 호출 토큰과 현장 부하는 미확인이므로 금액이나 손익분기 일수를 제시하지 않는다.

일정은 날짜 추정보다 선행 조건으로 관리한다. 화면·receipt 계약 검사 완료 → 공개/모의 데이터의 격리 후보 평가 → 현장 반입과 내부 데이터 검증 → 승격 판단 순이다. GENOS 평가 창구와 내부 정답 근거 준비가 완료일을 좌우한다.

## 11. 단계별 도입과 롤백

| 단계 | 수행 범위 | 완료 판단 |
|---|---|---|
| 현재 설계 | 코드·선택 릴리스·공개 skill 대조, 변경 지도·검증 계획 | 이 문서와 근거 파일. 제품 실행 변화 없음 |
| 첫 격리 후보 | receipt·미제시 결과·hit 미리보기, 기존 wire·journal 유지 | 전달 계약 검사와 고정 평가; 새 인덱스 불필요 |
| 후속 격리 후보 | 검색 전략 지침, 중복 억제·선택 호출 축소를 원인별로 비교 | 앞선 완료 arm을 정확한 부모로 기록; 질문 품질·비용 확인 |
| 계약 정리 후보 | 빈 모델 출력 필드 제거, 필요 시 버전 호환 | 구 journal 재생·출처 조회·새 계약 거부/복구 검사 |
| 조건부 검색 엔진 후보 | 의미 매칭 실패가 남으면 순위·벡터 등 비교 | 색인 세대·모델·권한·원문 정합성 및 전체 결과 확인 |
| 현장·MAIN | 내부 모델·임베딩, 실제 내부 데이터 검증 후 승격 판단 | 배포와 품질 인증을 구분하고 apply/rollback receipt 보존 |

실험을 시작할 때는 [EXPERIMENT_AGENT_PROMPT](../../../../04_EXPERIMENTS/LEGACY_ADR/EXPERIMENT_AGENT_PROMPT.md)와 [STANDARD](../../../../04_EXPERIMENTS/LEGACY_ADR/STANDARD.md)를 끝까지 읽고, 동일 scope 예약 확인 → stable runner로 ADR 선점 → 부모·데이터·설정·평가·성공 기준 동결 → snapshot/register/freeze를 수행한다. 이번 읽기 전용 설계는 신규 실험이 아니므로 ADR을 생성하거나 평가를 실행하지 않았다.

외부 실험은 허용된 공개 또는 명시적 모의 데이터에서 현재 모델 정책의 `ExperimentClient`, Qwen `qwen/qwen3.5-122b-a10b`, FP8, thinking off를 따른다. 선택 데이터의 `export_allowed=false`를 우회하거나 내부 질문·문서를 외부로 보내지 않는다. 실제 내부 데이터 평가는 GENOS에서 수행한다.

MAIN 승격은 Accepted·out-of-sample·decision_eligible·complete 요건과 `rag_main_promotion.py`의 hash 고정 plan/명시적 confirm 절차를 따른다. rollback은 이전 릴리스·프로파일·전략 hash·데이터 세대로 되돌리고 요청 journal 이력을 보존한다. Git 병합, ADR 상태, CURRENT 변경, MAIN 승격, GENOS 배포를 각각 기록한다.

## 12. 자체 검토와 산출물

- 현행에 없는 기능을 있는 것으로 설명하지 않았는가: 제안 receipt 필드·전략 파일·자동 피드백은 미구현으로 구분했다.
- 이미 있는 기능을 새로 만들지 않는가: 질문 요구, 용어 bridge, 위치 찾기, 명시 참조, READ, 주장 검토를 재사용한다.
- 비용을 줄이려 근거 검증을 제거하지 않는가: 축소 대상은 반복 검색·불필요한 선택·빈 출력 필드이며 원문 검증은 유지한다.
- 기존 경로를 우회하지 않는가: 동일 API·stage·세션·journal을 사용하고 별도 QMD/검색 executor를 만들지 않는다.
- 검증 범위를 과장하지 않았는가: 정적 코드·manifest 확인이며 새 모델 실험·현장 실행·품질 향상을 주장하지 않는다.

이번 검토는 **작성자의 자체 검토**다. 독립 감독 검토 또는 실험 통과가 아니다. 실제 구현 전에 활성 포인터·작업본 변경을 재확인해야 한다.
