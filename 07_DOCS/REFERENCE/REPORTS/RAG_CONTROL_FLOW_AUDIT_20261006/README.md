# RAG 적중 단위 조회와 탐색 루프 점검

**판정은 수정 필요다. 적중 단위가 작아진 것 자체보다, 읽기와 판단 사이의 상태 전달이 불완전하다.** 연결 메뉴의 다음 부분으로 진행하지 못하고 전체 검색으로 돌아가는 경로가 있으며, 반대로 같은 원문에서 새로 펼친 범위의 필수 연결을 놓치는 경로도 있다.

기본 설계는 **적중 단위 미리보기 → 필요한 단위 선택 → 필요할 때 전체·주변·상위·연결 범위 열람 → 확보된 근거로 충분성 판단 → 종료 또는 필요한 작업만 계속**을 유지한다. 제○조 전체를 기본 읽기 단위로 바꾸는 것을 해결책으로 삼지 않는다. 여기서 적중 단위는 항·호·목 등 현재 구조화에서 실제 검색에 걸린 가장 작은 단위다.

## 점검 대상과 확인 범위

2026년 10월 6일 작업 코드의 검색·읽기·선택·연결 탐색·단계 재진입·재개 경로를 자체 검토했다. 기존 계약 테스트의 모의 원문과 사전 지정한 판단 결과를 사용했으며 외부 모델을 호출하지 않았다. 새로운 모델 성능 실험이나 현장 검증은 아니다.

실행 경로는 `service.py` → 통합 runtime → `RuntimeModel` 및 `UnifiedExecution` → `NativeExecution.stage` → `SourceRecall` → `unit_reading` → `unit_selection` → `unit_relations` → ASSESS·COMPOSE·출력이다. 숏컷의 선택 결과 재사용은 `WikiExecution.invoke`에서 현재 입력 전체가 일치할 때만 성립한다.

로컬 활성 포인터는 `sql-ad-mode-v6-20261006-r1`, generation 41이다. 포인터가 선택한 동결 코드와 작업 코드가 다르다. 아래 재현은 **작업 코드**를 대상으로 했으며, 동결 릴리스는 별도로 대조했다. 데이터 경로는 `pecab-only-public-main-20260929-v1/generation`이다. GENOS의 실행 중인 리비전과 내부 데이터에 대한 발생 여부는 이 결과로 확정하지 않는다.

이 점검에서는 원본 설계서와 제품 코드를 변경하지 않았다. 파일 해시·활성 포인터·동결 코드와의 차이는 [EVIDENCE.json](EVIDENCE.json)에, 모의 재현 결과는 [probe-results.json](probe-results.json)에 고정했다.

점검 말미에 작업 코드 3개 파일의 해시가 변경되어 재확인했다. 읽기·선택 활동 이벤트가 추가된 코드에서도 진단 8개는 모두 재현됐다. 최종 합동 검사에서는 45개 통과·4개 실패했으며, 실패 원인은 `source_recall.py`의 engine code hash mismatch다. 최초 관련 계약 검사 41개 통과 기록과 이후 해시 불일치 실패를 구분해 보존한다. 코드와 엔진 명세의 불일치는 이 읽기 전용 점검에서 수정하지 않았다.

## 실제 반복이 발생하는 방식

### 연결 보류가 전체 검색으로 바뀌는 경우

현재 탐색의 다음 round는 FOLLOW로 읽은 target source들로 frontier를 만든다. 앞 메뉴를 모두 SKIP하면 frontier가 빈다. 메뉴 크기·문맥 한도로 제시하지 못한 CHECK 또는 REQUIRED 연결이 남아 있어도, 그 항목들의 다음 페이지를 여는 frontier는 없다. 따라서 SELECT는 pending을 반환하고 통합 실행기는 RECALL로 돌아간다.

ADR 0659에는 연결 그룹 20개 중 첫 10개만 제시된 기록이 있다. 제시된 항목은 적용되지 않는다고 SKIP했으나 나머지 10개는 확인하지 못했다. 답변 근거는 충분하다는 출력이 두 번 있었어도, 동일한 앞 10개를 재검색 후 다시 판단했다. **필수 확인을 생략하고 종료할 문제가 아니라, 아직 판단하지 않은 다음 10개를 제시해야 하는 문제다.**

### 확장이 새 판단으로 이어지지 않는 경우

모델이 “일반 승인 제한도 펼쳐 확인해야 한다”고 답하면 subtree READ는 실행한다. 그런데 충분성은 그 제한 규정을 보기 전에 반환한 `evidence_sufficient=false`를 그대로 사용한다. 남은 검색 후보가 없으면 전체 재검색 요구로 바뀐다. 남은 후보가 있으면 새 확장 원문의 검토보다 다음 후보 묶음 열람을 먼저 수행한다. 새 근거가 생긴 시점을 판단 상태에 반영해야 한다.

### 탐색 완료와 범위 완료가 다른 경우

두 원문의 작은 단위를 먼저 채택한 뒤 한 원문의 상위 범위를 FOLLOW로 읽으면, 그 상위 본문에 새 준용 관계가 드러날 수 있다. 이미 그 source ID를 스캔했다는 이유로 다시 확인하지 않으면, 새 witness가 존재해도 연결 탐색을 완료했다고 표시한다. P6은 실제 모의 참조 색인과 reader로 이 경로를 재현했다.

작업 코드에는 검토 선택으로 확장된 범위를 재탐색하는 `changed_anchors` 보완이 있다. 이 보완은 **별도 검토 뒤** 발생한 확장을 대상으로 한다. P6은 **navigate 내부 FOLLOW 중** 확장된, 이미 스캔한 원문을 대상으로 하므로 기존 보완으로 해결되지 않는다.

## 무한 루프 여부와 비용

이번 점검에서 무제한으로 계속 도는 루프는 재현하지 않았다. 작업 코드에는 후보 묶음 최대 8회, 연결 탐색 round 최대 2회, 단위 READ action 최대 1,024회, 요청 deadline이 있다. 통합 메모리 실행의 RECALL 재진입도 제한된다. 이 값들은 **설정 상한**이며 실제 호출 횟수가 아니다.

상한이 있어도 같은 작업을 재판단하고 잘못된 단계로 이동하면서 충분히 느려지거나 최종 실패할 수 있다. 페이지 READ의 여러 호출은 긴 본문을 분할해 읽는 정상 동작일 수 있다. 모델 판단 호출, 본문 페이지 호출, 같은 범위의 중복 읽기, 같은 연결의 재판단을 나눠 기록해야 원인을 구분할 수 있다.

추가 성능 검토 지점은 `workflow_relations_tools.py:263`의 coverage 처리다. 매 페이지마다 이전 coverage evidence를 다시 불러오고 각 대상 블록과 누적 span을 대조한다. 큰 source의 페이지가 많을수록 반복 비교가 증가한다. 원문 불변성 검증을 없애는 대신 검증된 구간 합집합을 점진적으로 갱신할 수 있다. 이 부분의 독립적인 개선 효과는 아직 측정하지 않았다.

| 관측 | ADR 0659 로컬 공개 질문: 131.157초, HTTP 422, 모델 10회·78.776초, fulltext discovery 2회 | 근거 충분 판단 뒤 동일 연결 메뉴가 반복되고 실패한 사례다. GENOS 성능 수치가 아니다. |

## 설계에 반영할 상태와 종료 조건

탐색 상태는 최소한 질문·근거 세대, 후보 커서, 읽은 span, 아직 읽을 span, 참조 witness별 결정, 연결 메뉴 커서, 미해결 의무, 근거 변경 번호, 실행 번호와 예산을 유지해야 한다. `needs_fulltext` 하나로 모든 미완료를 표현하지 않는다.

다음 작업을 다음과 같이 구분한다.

| 상태 | 다음 작업 |
| --- | --- |
| 미리보기만으로 범위가 불명확함 | 해당 적중 단위의 전체 또는 선택한 주변·상위 범위를 읽음 |
| 읽기·펼치기로 새 근거가 생김 | 새 근거를 제시하고 충분성·조건·연결을 다시 판단함 |
| 연결 메뉴의 미제시 항목이 남음 | 해당 메뉴의 다음 항목을 제시함 |
| 적용되는 필수 연결의 본문이 미확보됨 | 그 연결의 필요한 범위를 읽음 |
| 현재 후보에 근거가 부족하지만 미제시 검색 후보가 남음 | 다음 검색 후보를 제시함 |
| 현재 후보로 해결할 수 없어 새로운 검색어·대상이 필요함 | 새 검색을 실행함 |
| 확보한 근거로 답변 가능하고 적용되는 필수 확인이 해결됨 | 추가 탐색을 종료하고 답변 단계로 진행함 |
| 예산 한도 안에서 해결할 수 없음 | 미해결 항목과 진행 상태를 보존하고 명시적으로 종료함 |

마지막 미완료 상태의 출력은 기존 READY·답변·게시 계약과 함께 설계해야 한다. SELECT에 새 상태 문자열만 추가하면 충분하지 않다. 본문을 늘리거나 관계가 있다는 이유만으로 모든 연결을 읽게 하는 방식도 해결책이 아니다. 들어온 역참조는 적용 여부를 판단할 후보이고, 필요한 준용·정의·조건은 구체적인 witness와 현재 질문에 결속해서 확인한다.

수정 우선순위는 F01·F02·F03·F04의 상태 전환과 충분성 판단, F05의 실행 식별자, F06·F07·F09의 중복 작업, F08·F10의 후보 순서와 선계산, F11·F12의 시간·재개 계약 순이다. 실제 성능 비교를 시작할 때는 저장소의 ADR 선점·동결·검증 절차를 따른다.

## 재현 방법

저장소 루트에서 다음 명령을 실행한다. 데이터는 pytest 임시 경로에 생성하며 외부 서비스로 전송하지 않는다.

```bash
.venv/bin/python -m pytest 07_DOCS/REFERENCE/REPORTS/RAG_CONTROL_FLOW_AUDIT_20261006/probes.py -q
.venv/bin/python -m pytest 05_TESTS/CONTRACTS/test_unit_fulltext_adaptive_read.py 05_TESTS/CONTRACTS/test_progressive_grouped_reading.py 05_TESTS/CONTRACTS/test_batch_reference_navigation.py -q
```

`probes.py`의 assertion은 **현재 결함이 존재함**을 확인한다. 향후 수정 시 기대 동작을 검증하는 회귀 테스트로 전환해야 한다. 현재 모의 입력에서 8개 결함 경로를 확인했으며 발생률이나 현장 정확도를 추정하지 않는다.
