# CM 지식 시스템 구현 폴더와 RAG 연결 범위

새 기능은 `02_BACKEND/lawrag/legal_knowledge/`에 모은다. 기존 RAG의 검색·원문 읽기·법률 의미 판단 구현은 유지하되, 새 지식을 실제 질문에 적용하려면 질문 해석·조사 계획·상태·결과 소비 경계에는 연결 코드와 계약 확장이 필요하다. **관리 기능만 만드는 단계에서는 RAG 조사 경로를 바꾸지 않을 수 있지만, 실제 사용까지 RAG 무수정을 약속할 수는 없다.**

이 문서는 2026년 10월 21일의 폴더·연결 설계다. 아래 신규 경로·API·설정은 구현 제안이다. [전체 설계](README.md)와 [데이터와 실행 계약](CONTRACTS.md)을 보완하며, 기존 문서의 AD 관리 API 연결 제안은 이 문서의 변경안을 우선한다. 10월 20일의 근거·검사 기록은 당시 관측으로 보존한다.

## 현재 확인한 연결 상태와 변경 이유

| 항목 | 현재 코드와 관측 | 변경안과 원하는 결과 |
|---|---|---|
| 활성 로컬 릴리스 | `ACTIVE_RELEASE.json`은 MAIN96, `ad-management-disabled-20261021-r1`을 선택한다. 현장 GENOS 반영의 증거는 아니다 | 새 기능은 별도 후보로 검증하고 명시적으로 활성화한다. 작업 폴더 추가만으로 활성 릴리스가 바뀌지 않는다 |
| 기존 관리 API | `semantic_runtime/app.py`의 `/v1/rag/memory/query`, `/v1/rag/memory/command`는 `require_ad()`를 거친다. `PIPELINE.json`의 `ad_management.enabled=false`이면 403을 반환하도록 구현되어 있다. 이번 문서 작업에서 API를 실행하지는 않았다 | 기존 AD 비활성화를 유지한다. 별도의 인증·팀 범위·편집 권한을 적용하는 새 지식 관리 router를 같은 애플리케이션에 연결한다 |
| 기존 그래프 API | `lawrag/api/routers/knowledge.py`는 `/v1/knowledge` 아래의 읽기 전용 SQLite 그래프 조회 구현이다 | 이름이 비슷하다는 이유로 현행 업무 지식 관리 기능으로 간주하지 않는다. 새 경로는 `/v1/legal-knowledge`로 구분하며 Oracle 조회 계약을 사용한다 |
| 화면 위치 | `03_FRONTEND/README.md`는 백엔드에 포함된 뷰어를 `lawrag/api/viewer/`에 두도록 안내한다 | 같은 위치에 업무 지식 화면을 추가한다. 화면을 위해 별도 프런트엔드 서버를 기본값으로 만들지 않는다 |
| 실행 상태 | `research_state.py`는 기존 journal/checkpoint를 실행 정본으로 사용한다 | 새 방법·Wiki 버전·숏컷 참조를 기존 상태에 연결한다. 별도 조사 상태 DB나 실행기를 만들지 않는다 |

## 제안 폴더 구조

아래 트리는 구현 시의 배치안이다. 기존 파일의 이동이나 신규 코드 폴더 생성은 아직 수행하지 않았다.

패키지 안의 폴더는 코드 책임을 나눈 것이다. 온톨로지·Wiki·숏컷별 서버나 프로세스가 아니다. 공통 저장 계약·변경 이력·게시 버전으로 연결하고, 현업은 하나의 화면에서 해당 업무의 확인 사항·근거·제외 조건·실행 사례를 편집하거나 조회한다. 소규모 책임은 처음부터 여러 파일로 잘게 쪼개지 않는다.

`shortcut/`에는 기존 숏컷 저장소 전체를 복제하지 않는다. 사건 사실·불변 이벤트·정정 기록의 현재 소유자를 유지하고, 새 지식과의 참조·조회 기능을 추가한다. `wiki/`도 기존 컴파일러를 복사해 별도로 유지하지 않는다. 필요한 확장은 기존 컴파일러에 연결하고, 공통 코드를 옮길 필요가 생기면 호출자와 호환 경로를 함께 이행한다.

기존 `lawrag.ontology`와 관련 구축 기능도 사용 중인 의존성을 확인하기 전에는 이동·삭제하지 않는다. 새 패키지는 CM 업무의 검토 지식을 관리하는 책임으로 구분한다.

## RAG와 분리하는 책임

| 새 패키지가 맡는 일 | 기존 RAG가 맡는 일 |
|---|---|
| 어떤 값을 어떤 의미로 확인할지 정의 | 현재 질문·사용자 사실·실제 원문을 해석 |
| 조건에 따라 필요한 검토 항목 구성 | 부족한 근거를 조사하고 도구를 실행 |
| Wiki와 숏컷의 적용 범위·버전 참조 제공 | 실제 원문·판본·권한을 결속하고 재사용 가능성 확인 |
| 불필요한 탐색의 제외 조건과 재개 조건 제공 | 근거가 부족하거나 조건이 달라지면 기존 조사로 복귀 |
| 편집·변경 영향·게시·수정 후보 관리 | 법률 의미 판단·인용·미확인 사항·최종 응답 생성 |

온톨로지의 조건은 검토 항목을 구성하는 데 쓰인다. 법률상 적용성·충분성·예외·충돌을 모두 기계 규칙으로 확정하지 않는다. 새로운 질문에서 의미가 같다는 보장이 없으면 적용 미확인으로 유지하고 원문을 조사한다. 다른 에이전트도 같은 입력·출력 계약과 저장소 인터페이스를 구현해 사용할 수 있게, 공통 패키지 안에 현재 RAG의 도구명·journal 형식·LLM 프롬프트를 직접 박아 넣지 않는다.

의존 방향은 `관리 API 또는 knowledge_bridge → application → 공통 계약과 저장소 인터페이스`다. 애플리케이션을 구성할 때 Oracle 등 어댑터를 주입한다. 공통 패키지가 현재 RAG 엔진을 역으로 불러 실행하는 구조는 피한다. 조회 계약과 capability를 문서화하되, 실제 다른 에이전트 호환성은 별도 연결 검사로 확인한다.

## 실제 연결할 때 수정하는 경계

| 경계 | 필요한 변경 | 유지할 구현과 주의점 |
|---|---|---|
| 질문 해석 | `request_entry.py`와 필요 시 `memory_binding.py`에서 검토 방법·입력 항목 참조를 기존 해석 결과에 연결 | 기존 질문 해석 호출에 통합한다. 부모 `entry_proposal`을 재사용하는 경로에 온톨로지 선택만을 위한 모델 호출을 추가하지 않는다 |
| 조사 계획 | `domain_control.py`, `unified_rag.py`, `wiki_execution.py` 등 실제 선택 경로에서 `knowledge_bridge`를 통해 공통 계획을 소비 | 기존 계획에 합친다. 별도 planner를 병렬 실행하지 않는다. 기존 정확 일치 숏컷의 적용 제한을 유사 질문 전체로 풀지 않는다 |
| 조사와 출력 상태 | `research_state.py`, `investigation_chain.py`, 답변 소비자에 적용한 지식·누락 항목·제외 이유 참조를 전달 | 기존 journal/checkpoint와 호출·시간 예산을 유지한다. 의미 미완료만으로 이미 확보한 원문 전달을 차단하지 않는다 |
| 관리와 게시 | 새 관리 router를 `semantic_runtime/app.py`의 실제 `create_app()`에 등록하고 기존 CLI·구축 작업에 게시 기능 연결 | `lawrag/api/routers/`에 파일만 추가해 자동 연결됐다고 하지 않는다. 기존 AD API의 비활성화와 권한 경계를 우회하지 않는다 |
| 실행 설정과 릴리스 | `PIPELINE.json`, 스키마 소비자, 코드 패키징·해시 목록·binding에 신규 의존성을 포함 | 새 패키지가 검증 후보와 실제 선택 릴리스에 포함되는지 확인한다. 설정 선언이나 import 성공만으로 MAIN 적용 완료가 아니다 |

따라서 수정 파일을 두세 개라고 미리 제한하지 않는다. **업무 지식의 구현을 한 패키지에 집중하되, 기존 소비자의 계약 변경은 필요한 곳까지 연결한다.** 검색·임베딩·정렬·원문 읽기 알고리즘을 바꾸는 것은 이 분리 구현의 기본 범위가 아니다. 검색 효과나 모델 효과를 바꾸는 후속 변경은 별도 실험 절차를 따른다.

대사 흐름에 연결할 때는 질문에서 내규를 찾고, LLM이 실제 내규 원문에서 개념·조항 범위를 정한 다음 연결 외규를 조사한다. 새 검토 항목을 사용하더라도 내규·외규를 질문으로 각각 독립 검색하는 흐름으로 대체하지 않는다. 양측 실제 원문과 출처, 해석·미확인은 같은 비교 행에서 이어진다.

## 데이터와 실행 시간

코드·스키마·작은 모의 fixture만 저장소에 둔다. 업무 지식 정본·게시 데이터·수정 이력은 Oracle 또는 승인된 데이터 계층의 조회 계약으로 관리한다. GENOS 코드서빙은 필요한 범위만 받아 요청 중 일시적으로 사용한다. 전체 문서·색인을 로컬 파일이나 SQLite에 복원하지 않으며, 요청 간 결과 캐시는 데이터 계층에서 버전·권한 범위를 관리한다. 현재 숏컷 SQL 저장 책임의 Oracle 이행은 어댑터 이름만 붙여 완료한 것으로 보지 않는다.

게시 시 타입·참조·변경 영향·실행용 조회 데이터를 정리한다. 질문 처리 시에는 현재 업무에 해당하는 소수의 후보와 필요한 지식만 읽고, 기존 해석 호출·조사 계획에 합친다. 모든 규칙을 질문마다 읽거나 검증용 LLM을 상시 추가하지 않는다. 현재 `domain_control.select()` 자체는 이미 모델 호출을 하지 않으므로, 이를 교체하는 것만으로 호출 절감이 생긴다고 계산하지 않는다.

추가 조회·계획 조립에도 비용은 있다. 기대 효과는 절약한 중복 조사 시간이 추가 조회 비용보다 클 때 발생한다. 이번 설계의 지연·정확도 개선은 미측정이며, 같은 조건의 기준 대비 실제 호출·조회·지연·누락·잘못된 재사용을 비교해야 한다.

## 단계별 구현과 복구

1. **분리 구현:** 공통 계약·저장 어댑터·편집·게시·화면을 구현한다. 관리 활성화와 RAG 소비 활성화는 서로 다른 설정으로 제어하고 초기에는 비활성으로 둔다. 설정 이름은 구현 계약에서 확정한다. 게시해도 RAG가 자동 선택하지 않는다.
2. **후보 연결:** `knowledge_bridge`로 기존 질문·조사 경로에 연결한다. 원문 세대와 지식 버전의 조합을 실행 중 고정하고, 기존 상태·인용·권한·정정 소비자를 검사한다. 의미·검색 효과 비교는 ADR을 선점하고 동결한 뒤 실행한다.
3. **검증 후 적용:** 같은 코드·프로필·데이터로 계약과 실제 서비스 진입점을 확인한 뒤 MAIN 승격과 선택 포인터를 확인한다. 새 연결 해제와 이전 binding 복원으로 되돌릴 수 있어야 한다. GENOS 반입·인증·화면 노출·워크플로우 실행 확인은 별도다.

후보가 없거나 조건이 미확인이면 같은 요청 상태와 남은 예산으로 기존 조사에 돌아간다. 새 지식 조회 실패의 재시도 담당은 조회 어댑터 한 곳에 두고 상위 실행기가 다시 중첩 재시도하지 않는다. 실패한 지식을 근거로 소비하지 않으며, 원문 경로가 사용 가능하면 제한 범위에서 계속한다. 공통 원문 저장소까지 사용할 수 없으면 실제 실패·미확보를 표시한다.

권한 위반·변조·해시 불일치는 영향받는 데이터의 사용을 거부한다. 모델이 내용을 재작성해 통과시키지 않는다. 게시가 부분 실패하면 활성 지식 버전을 유지하고, 같은 작업 ID·revision으로 완료 여부를 확인해 재개한다. 초안·실패 기록은 유지하되 실행 성공 사례나 승인 지식으로 승격하지 않는다.

연결 검사는 비활성 시 기존 조사 경로 유지, 부분 적중·미적중 복귀, 변경된 사실·판본·권한에 대한 재사용 거부, 중복 게시·재개, 동일 근거 읽기의 중복 방지, 실제 인용·응답 소비까지 확인한다. 정상 경로만의 모의 검사로 적용 완료를 판단하지 않는다.
