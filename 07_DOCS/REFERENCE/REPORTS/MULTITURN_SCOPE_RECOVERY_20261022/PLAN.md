# 멀티턴 새 질문과 검색 범위 오류 수정 계획

작성: 2026-10-22. 상태: 구현 전 설계. 기준: 로컬 MAIN101 `compact-answer-reasons-20261022-r1`.

목표는 같은 대화에서 새 주제를 물으면 새 질문으로 조사하고, 법령명·목차가 없어도 주제 검색을 시작하는 것이다. 실제 후속 질문의 범위 유지, 명시한 법령·조항 제한, 권한·해시·재개 검사는 보존한다. 이번 산출물은 계획과 근거 결속이며 제품 코드·활성 포인터·GENOS 배포는 변경하지 않는다.

## 확인한 사실과 남은 가설

- 사용자 사진: 앞선 “상법에서 주주총회 특별결의 요건” 답변 뒤 “최대주주 의무 보유기간에 대해서 확인해줘”에 “법령명 또는 목차 중 하나가 필요합니다.”가 표시됐다. 사용자는 두 번째 발언을 별도 새 질문으로 명시했다.
- 로컬 재현: `CASE_START / target=null`에 `REPLACE / targets=[{document:null,structure:null,selection:null}]`를 넣으면 명령 정규화·입장 검증은 통과한다. 이후 `query_scope.resolve()`에서 사진과 같은 문구를 발생시킨다. `KEEP / targets=[] / user_quote=""`와 새 상태를 쓰면 별도 검색 제한 없이 통과한다. 실제 모델 호출·원문 전체 로딩은 없었다.
- 멀티턴에서는 `request_entry.eligible()`이 기존 goal이 있는 요청을 최초 통합 입력 경로에서 제외한다. 기존 요청 분류 → 멀티턴 명령 해석·검사 → 범위 확정 경로를 사용하며 새 질문 여부와 검색 범위는 별개 필드다.
- `corrected_memory._execute()`는 `UnresolvedScope`를 `CLARIFY`로 반환하고, `unified_runtime.result_port()`는 `reason`을 답변 본문으로 사용한다. 모델 출력의 잘못된 조합이 사용자 입력 부족처럼 표시될 수 있다.
- 현장 모델 원응답·판단 이유·실행 리비전은 미확인이다. 기존 질문으로 잘못 분류했는지, 새 질문 분류는 맞고 범위만 잘못 생성했는지는 사진으로 확정하지 않는다. 모델이 왜 그 값을 선택했는지도 추정으로 단정하지 않는다.
- 관련 핵심 모듈의 작업 코드·선택 릴리스 해시를 대조했다. 자세한 지문은 `SOURCE_BINDING.json`에 둔다. 이 일치는 현장 배포 코드의 동일성을 증명하지 않는다.

## 수정 후 동작 계약

| 입력·상태 | 질문 처리 | 직접 검색 범위와 상태 |
|---|---|---|
| 주총 특별결의 답변 → 최대주주 의무 보유기간 질문 | 별도 새 질문 | 이전 질문의 상법 제한·사실·조항을 복사하지 않고 현재 요청에 허용된 자료에서 검색 |
| 새 질문 “자본시장법에서 최대주주 관련 내용을 찾아줘” | 별도 새 질문 | 현재 발언에 지정한 법령으로 제한 |
| “그 요건의 예외는?” | 같은 질문의 후속으로 해석한 경우 기존 goal 사용 | 해당 질문의 법령·구조 범위와 조건을 보존하고 필요한 조사만 연결 |
| “그 법에서 최대주주 관련 내용도 찾아줘” | 새 목적 여부는 문맥을 보고 모델이 판단 | 문맥으로 지시한 법령이 확인되면 해당 범위를 결속. 새 질문이라는 이유로 지시어를 무시하지 않음 |
| “상법 제434조 말고 제435조를 봐줘” | 해당 질문의 범위 수정 | 지정한 조항으로 교체하고 기존 원문·변경 이력 보존 |
| “그 규정 전체를 봐줘” | 같은 질문 범위 확장 | 장·절 제한만 해제하고 문서 제한 유지 |
| 명시한 문서가 없거나 동명 후보가 여러 개 | 실제 조회 결과에 따라 처리 | 이름 미확인을 전체 검색으로 바꾸지 않음. 후보를 구분할 필요가 있으면 실제 후보에 관한 구체 질문 |

새 질문/후속 질문의 의미 판단은 LLM이 맡는다. “최대주주”, “그”, “다른 질문” 등 단어 규칙으로 분기하지 않는다. 대화 이력이 있다는 사실만으로 기존 질문을 선택하지 않는다.

## 문제별 전후 비교

| 문제 | 기존 방식과 관측 결과 | 수정 방식 | 원하는 결과·검증 |
|---|---|---|---|
| 새 질문과 빈 범위 지정이 함께 나옴 | 별도 필드로 생성하고 형식 검사만 통과. 로컬 합성 명령에서 뒤늦은 범위 오류 재현 | 질문 종류별 범위 계약과 공통 필드 검증을 모델 결정 채택 전에 실행 | 잘못된 명령은 검색·상태 변경 전에 내부 수정. 새 질문은 수정 후 주제 검색 시작 |
| 사용자 입력 부족처럼 표시 | `UnresolvedScope → CLARIFY → reason 본문` 연결 확인 | 모델 출력 오류, 실제 대상 모호함/미확보, 권한·무결성 실패를 분리 | 빈 모델 target 때문에 법령명·목차를 요구하지 않음. 실패는 실패로 저장·표시 |
| 이전 문서 범위가 새 주제로 넘어갈 위험 | 새 질문은 원래 새 state로 시작하므로 자동 상속 결함 자체는 미관측. 현장 오분류는 가설 | 새 질문은 빈 질문별 상태, 후속은 선택 goal 상태를 기준으로 범위를 계산한다는 계약을 명시·검사 | 새 goal 생성과 이전 goal 불변, 새 질문의 실제 검색 필터로 확인 |
| 과잉 복구로 범위를 넓힐 위험 | 과거 MAIN97은 특정 규정 전체를 CLEAR로 해석한 실패를 보존하고 수정함 | 빈 target을 무조건 KEEP/CLEAR로 바꾸지 않고 같은 문맥에서 모델 수정 요청 | 명시 문서·조항·제외·권한 범위를 보존하며 진짜 전체 해제만 적용 |

이 수정은 첫 질문과 멀티턴, 새 질문과 후속 질문의 공통 범위 계약에 적용한다. 법률 답변의 정확도나 모든 주제 전환의 의미 판단을 코드만으로 보장하지 않는다.

## 변경 지도와 처리 순서

전체 MAIN 중 RAG 요청 해석·상태·표시 단계의 변경이다. 입력·구조화·용어집·원문·색인 재구축은 필요하지 않다. 기존 `service.service → /v1/rag/ask → legal-agent-unified-v6`를 사용한다.

| 기존 위치 | 계획한 변경·책임 | 출력 소비자·이행 |
|---|---|---|
| `legal_agent/query_scope.py`의 `model_change_schema`, `resolve` | 순수 공통 검증 함수 추가(이름은 구현 시 확정). operation별 필드 조합, 빈 target, 구조 문자열과 selection 충돌을 검사. 진단에 오류 코드·필드 위치·복구 가능 여부를 부여 | 최초 입력과 멀티턴이 같은 검증기를 사용. 저장된 구형 명령은 원래 계약으로 읽되 실행 시 무결성을 재검증 |
| `legal_agent/memory_methods.py`의 `normalize` | 질문 종류와 범위 연산의 일관성 검사. 새 질문의 KEEP는 새 state의 제한 없음이며 이전 goal 범위 유지라는 뜻이 아님. 새 질문에 ADD/CLEAR가 나오면 수정 대상으로 분류 | 기존 method/action·target·stage 체계를 유지. 새 wire enum은 우선 도입하지 않음 |
| `legal_agent/corrected_memory.py`의 `resolve`, `_execute` | 기존 `command-resolver` 안에서 공통 검증을 실시. 새 질문/선택된 기존 질문별 기준 상태를 명확히 전달. 모델 출력 오류를 `_execute`에서 일괄 CLARIFY로 바꾸는 경계 수정 | DecisionJournal의 채택 전 검증, 실제 state commit, 기존 질문 revision 보존 |
| `legal_agent/request_entry.py`의 `decode_scope`, `accept`, `run` | 최초 입력의 NAMED_SCOPE/AUTHORIZED_SCOPE도 같은 빈 target·조합 검사를 받음. 최초/멀티턴에 서로 다른 허용 기준이 생기지 않게 함 | 기존 통합 입력과 모델 수정 소유자 `request-entry` 유지 |
| `legal_agent/unified_rag.py`의 `scope_state`, `open` | 실제 문서·구조 확정, 현재 권한·메타데이터·해시 검사 유지. 검증된 질문별 범위를 기존 검색/읽기 소비자에 결속 | 별도 범위 검색기나 전체 원문 복사 경로를 만들지 않음 |
| `legal_agent/unified_runtime.py`, API 실패 처리, `request_report.py`, GENOS workflow 표시 | 실패 종류를 기존 상태/오류 계약에 정확히 매핑. 내부 오류 문구를 사용자 요구로 출력하지 않음. 원인·request ID·실제 호출 횟수를 기존 보고에 연결 | `CLARIFY`는 실제 확인 질문에만 사용. 상태 변경 시 `legal.case-binding-v1`, Result, publication, workflow 소비자를 함께 검사 |
| `PIPELINE.json`, 관련 engine manifest, 선택 profile | 변경 모듈·검증 정책 버전의 지문 갱신 | 검증 후보·작업 코드·선택 릴리스·인계본이 같은 변경을 사용하도록 결속 |

권장 구현 순서:

1. 현재 재현을 고정된 모의 모델 응답의 계약/API 회귀 검사로 남긴다. 먼저 실패가 나는 기준 코드·입력·상태를 고정한다.
2. 공통 조합 검증과 오류 분류를 구현한다. 신규 모델 요청의 스키마에도 가능한 제약을 넣되 provider 변환과 무관하게 서버 검증이 정본이 되게 한다. 필수 범위 판단 필드를 없애서 문제를 숨기지 않는다.
3. 같은 응답 안에서 질문 관계 → 기준 goal/state → 범위 적용 순서로 해석·검증한다. 별도의 상시 분류 모델 호출은 추가하지 않는다. 새 질문은 `target=null`, 기존 질문은 실제 선택 goal을 사용한다.
4. 기존 `bounded_decision`의 검증 콜백 안에서 잘못된 조합을 거절하고 같은 요청/문맥/권한으로 수정한다. 현행 해석 → 명령 검사 구조에 결합하고 새 재시도 루프를 만들지 않는다.
5. 실제 범위 해소와 사용자 확인을 분리한다. 모델의 빈 지정·필드 모순은 복구 대상이고, 실제 저장 문서 후보의 모호함은 구체 확인 대상이다. 조회 실패·없는 문서를 사용자의 법령명 미입력으로 바꾸지 않는다.
6. 답변·실행 상태·로그·재사용 소비자까지 연결하고 동일 코드의 API 회귀를 검사한다.

프롬프트에는 새 주제와 실제 후속 질문의 대조 사례, 새 질문의 기본 검색 범위, 현재 발언의 지시어를 해석할 수 있는 조건을 짧게 반영한다. 수정 후보의 효과는 후속 ADR에서 검증한다. 사진의 두 질문을 하드코딩하거나 그 사례만 통과한 것을 일반화로 설명하지 않는다.

## 실패·복구·저장 계약

| 분류 | 복구 담당과 행동 | 최종 상태·보존 |
|---|---|---|
| 모델의 빈 target·필드 충돌 | 멀티턴 `command-resolver`, 최초 `request-entry`가 각 자기 결정만 담당. 해당 필드·규칙·원제안과 같은 문맥으로 제한 수정 | 성공하면 재검증 후 실행. 원제안·거절·수정·채택 해시를 기존 저널에 남김 |
| 수정 후 같은 충돌·예산 소진 | 기존 수정 한도에서 종료. gateway·상위 호출자가 같은 오류를 다시 수정하지 않음 | “질문을 처리하는 중 내부 오류가 발생했습니다”와 요청 식별자 등 실제 실패 안내. 법령명 입력 요구나 성공 답변으로 바꾸지 않음 |
| 실제 후보 모호함 | 실제 허용 후보와 요청 지시 대상을 대조하고 필요한 구분만 질문 | 사용자 확인 상태. 기존 질문·범위·원문을 보존 |
| 명시 문서/조항 미확보·조회 실패 | 명시 경계를 유지하고 실패/미확보를 구분. 기존 허용 조회·이름 복구 경로의 예산 내 처리 | 전체 검색으로 임의 전환하지 않고 확인한 범위와 미완료 원인을 표시 |
| 권한·해시·오래된 revision·변조 | 기존 계약 오류로 차단. 일반 모델 수정 대상으로 보내지 않음 | 원인과 바인딩 보존. 이전 성공 결과·현재 state를 덮어쓰지 않음 |
| 중단·동일 요청 재전송 | 기존 DecisionJournal·request/state 저장을 사용. outcome unknown이면 자동 재실행하지 않음 | 최초 deadline·호출·수정 횟수 유지. 실패 결과는 성공 숏컷/위키에 등록하지 않음 |

`resolve()`의 검증 중 발생하는 오류를 공통 실패 타입으로 바꿀 때 문자열 매칭으로 원인을 추정하지 않는다. 실제 사용자 모호함과 모델 제안 오류는 발생 지점에서 분류한다. 명령 검증 콜백은 상태를 바꾸지 않으며 실제 검색·도구 실행은 채택 뒤에 수행한다.

새 state를 만드는 기존 규칙을 유지한다. 기존 goal이 없는 새 질문은 질문별 검색 범위·사실을 초기화하지만 동일 요청의 물리 호출·deadline은 초기화하지 않는다. 대화의 이전 원문·질문은 보존하고, 참조 힌트와 강제 검색 제한을 구별한다.

| 검사군 | 통과 조건 |
|---|---|
| 새 주제 전환 | 앞 질문의 문서 제한·사실이 새 질문에 섞이지 않고 새 goal에서 실제 허용 검색 호출 발생. 앞 goal/state/revision 불변 |
| 새 질문+빈 범위 주입 | 최초 명령 거절 → 같은 결정의 수정 → 정상 검색까지 API에서 확인. 법령명/목차 필수 입력 문구가 나오지 않음 |
| 새 질문 의미 오분류 | 실제 모델 평가에서 새 질문/후속 판단과 선택 target·이유를 별도 기록. 계약 통과로 의미 정확도를 대신하지 않음 |
| 후속·지시어·범위 변경 | 예외 재질문, “그 법”, 조항 교체, 범위 추가·제외, 특정 규정 전체, 전체 해제를 구분하고 기존 검색 필터·읽기 권한 유지 |
| 실제 모호함·자료 없음 | 모호한 후보만 구체 질문. 없는 문서/조항 및 도구 실패를 구분하고 전역 검색으로 확장하지 않음 |
| 반복 실패·예산·재시작 | 제한 수정 후 종료, 기존 원인 보존, 같은 request 재개/중복에서 추가 예산·중복 호출·goal 생성 없음 |
| 무결성·호환성 | 권한 축소, 메타데이터/코드/상태 해시 불일치, stale revision 거부. 구형 완료 기록·구조화 selection·제외 및 검증된 참조 읽기 유지 |
| 최종 소비자 | 서비스/API → case/request/저널 → 응답·workflow 표시의 상태 일치. 실패의 성공 발행·숏컷·위키 등록 없음 |

실제 모델 효과 비교는 구현·실험 승인이 있는 다음 작업에서 수행한다. 시작 시 동일 scope reservation을 확인하고 두 실험 표준을 끝까지 읽은 뒤 ADR을 선점한다. 기준은 정확한 MAIN101 부모/arm과 당시 선택 지문으로 동결한다. 평가 단위는 개별 문장보다 대화 시나리오이며 같은 사례의 의역을 독립 표본으로 과대 계산하지 않는다. 사진 사례는 알려진 재현 집합으로 두고 별도의 미사용 주제 전환·후속 대화를 준비한다. 새 모델/프롬프트/범위 효과는 결과 확인 전에 성공 기준과 허용 회귀를 정한다.

외부 실험 모델은 당시 정책 정본을 확인해 `ExperimentClient`를 사용한다. 현재 정책은 Qwen3.8 / Parasail FP8 / reasoning none / fallback 없음이다. 공개·합성 자료로만 외부 평가하며, GENOS 내부 모델의 실제 결과는 현장 워크플로우 테스트로 별도 확인한다.

## 예산·기대치와 도입

| ID | 종류·지표 | 기준·검증 |
|---|---|---|
| B1 | 관측: 기존 공통 결정 수정 한도 | `output_contract.bounded_decision()`는 결정당 최초 시도 뒤 수정 최대 1회를 허용. 이 한도를 재사용하고 단계마다 추가하지 않음 |
| B2 | 목표: 정상 요청의 추가 상시 모델 호출 | 0회. 기존 해석·검사 안에서 처리하고 정상 경로 호출 기록으로 비교 |
| B3 | 미확인: 실패 요청의 시간·비용 | 수정 1회는 명령 해석+명령 검사 및 전송 재시도와 같지 않음. 모든 물리 호출·토큰·시간을 계측. 조기 차단 이익보다 복구 호출 비용이 클 수도 있음 |
| B4 | 미확인: 주제 전환 정확도·현장 지연 | 독립 대화 시나리오 비교 및 GENOS 내부 모델 확인 전 개선율·소요시간을 산정하지 않음 |

소규모 메타데이터·모의 데이터 검사부터 순차 실행한다. 무거운 실제 원문·fulltext 로딩은 한 프로세스씩만 실행하고 시작 전에 RAM/swap·진행 중 작업을 확인해 실행별 메모리 한도와 중단 조건을 동결한다. 원문·색인을 새로 복사하거나 재구축하지 않는다.

도입 단계는 다음과 같다.

1. 계획 확인 → 기존 작업 코드와 최신 활성 릴리스 차이 재확인 → 필요한 수정만 통합. 후보 전체를 덮어쓰지 않는다.
2. 동일 코드의 계약·실패 주입·API 검사 → 필요한 ADR 모델 검증 → 허용 회귀와 미확인 항목을 기록한다. 전역 기존 실패·과거 거절 판정은 보존한다.
3. 검증 코드·데이터·profile·검색 정책·스키마/엔진 지문을 결속하고 `validate --final`·graph를 확인한다. 새 결과가 승격 조건을 충족하는지 판단하며 과거 품질 우회를 새 통과 근거로 쓰지 않는다.
4. 이후 MAIN 반영을 수행하는 작업에서는 hash 고정 plan과 명시적 `--confirm-main` 절차로 선택 포인터를 바꾸고 실제 로컬 `service.service` binding/HEALTH 및 관련 요청 경로를 확인한다. 승인 없는 활성화는 이번 계획에 포함된 실행이 아니다.
5. GENOS 인계는 검증 코드와 workflow 변경 여부를 함께 결속한다. 실제 반입·Git commit/push·리비전 배포·편집기 반영·워크플로우 테스트를 각각 기록한다. 현재 세션에서 GENOS 접속을 시도하지 않는다.
6. 롤백은 직전 검증 릴리스 선택으로 복구하되 신규 감사·실패·질문 이력은 보존한다. 스키마/검증 정책 해시가 다른 ACCEPTED 결정은 새 요청에 재사용하지 않는다. 진행 중 구버전 요청은 원래 binding에서 마무리하거나 명시된 이행 절차를 사용하고 예산을 초기화하지 않는다. 구버전 reader 호환 여부를 배포 전 검사한다.

계획 자체 검토만 수행했다. 독립 감독 검토·수정 코드 검사·모델 실험·MAIN 승격·GENOS 적용 완료를 뜻하지 않는다.
