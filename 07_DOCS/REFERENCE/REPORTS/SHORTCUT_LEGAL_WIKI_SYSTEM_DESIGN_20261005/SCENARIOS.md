# 실제 보유 원문을 사용한 설계 시나리오

[전체 설계](README.md) · 사례 인물·회사·대화는 합성이다. 아래는 저장된 원문 버전으로 시스템 동작을 설명하는 예시이며, 현재 시행 법령 전수 확인이나 실제 사건에 대한 확정 자문이 아니다.

## 1. 사용한 데이터

로컬 선택 릴리스가 가리키는 원문 세대는 `term-source-1acfbe06921527e74a0b`다. 아래 자료는 그 세대의 `store.sqlite`에서 읽었다. 이번 설계에서 원문 데이터를 변경하거나 새 법률 답변 실험을 수행하지 않았다.

| 자료 | document ID | 확인한 원문 좌표 |
|---|---|---|
| 코스닥시장 상장규정 | `3521c3aaa5a735fd` | 제2조 전문투자자 정의 block 49, 제26조제1항제3호 block 301, 제4호 block 302 |
| 코스닥시장 상장규정 시행세칙 | `eae25aa6e8a83c58` | 제23조제4항 block 236·238, 제5항 block 245~248 |

원문 저장 위치: `01_DATA/TERM_RELEASES/pecab-only-public-main-20260929-v1/generation/store.sqlite`. 상대 위치와 해시 출처는 [조사 근거](evidence.json)에 기록한다. block ID는 이 세대의 좌표이며 다른 세대에서도 동일하다고 가정하지 않는다.

저장된 제26조제1항제3호는 상장예비심사 신청 전 일정 기간 내 제3자 배정 취득에 대한 의무보유와 세칙 예외를 규정한다. 제4호는 벤처금융·전문투자자의 취득 방식, 투자기간, 한도 및 별도의 예외를 규정한다. 따라서 한 조항의 단서 적용과 다른 조항의 성립을 구분해서 조사하는 사례로 적합하다.

## 2. 세션 A: 질문과 갈래가 생김

사용자: “A사가 코스닥 상장을 준비하고 있어. B가 제3자 배정으로 투자했는데 의무보유가 얼마나 돼?”

shortcut은 발언을 즉시 저장하고 `case-A / branch-lockup / issue-applicability`에 연결한다. 투자자 자격, 취득일, 상장예비심사 신청일, 취득 방식, 보유 범위와 예외가 미확인이라서 상태는 OPEN이다. legal_agent는 모르는 사실을 채워 넣지 않는다.

사용자: “B는 재무적투자자야. 18개월 전에 투자했어. 그리고 전문투자자면 뭐가 달라져?”

| 저장 내용 | 처리 |
|---|---|
| “재무적투자자”라는 사용자 표현 | 사실 진술로 저장; 규정상 전문투자자 자격으로 자동 치환하지 않음 |
| 18개월 전 취득 | 사용자 진술과 기준일 미확인 상태 보존 |
| 전문투자자의 의미 질문 | 같은 사건의 별도 `issue-investor-qualification`로 분리 |
| 자격이 의무보유 판단에 미치는 영향 | 두 issue 간 DEPENDS_ON 연결 |

도구 실행은 원문 문서 선택, 제26조 읽기, 정의와 시행세칙 읽기, 예외 확인으로 이어진다. 각 실행의 입력·원결과·사용한 source hash와 “왜 이 조항을 읽었는가”를 저장한다. 자격 설명과 기간 계산을 하나의 자유 요약으로 뭉개지 않는다.

## 3. 세션 B: 같은 사건을 이어가며 정정

사용자: “어제 A사 B 투자자 건 이어서. 취득은 18개월 전이 아니라 예비심사 신청일 기준 8개월 전이야.”

명시된 이전 사건 연결을 확인하고 세션 B를 case-A에 연결한다. 원래 18개월 진술은 보존하고 fact revision을 올린다. 취득일 조건을 사용한 판단만 stale로 표시한다. 전문투자자 정의 원문 자체가 취득기간 정정 때문에 바뀌지는 않는다.

사용자: “이 사례에서는 규정과 세칙상 전문투자자에 해당한다고 확인됐고, 모집·매출 취득은 아니야. 해당 보유분은 제4호 한도 안이고, 제4호 세칙 예외도 없어.”

이 발언은 조건 확인의 근거 이벤트다. 실제 서비스에서는 자격·취득 방식·한도·예외에 필요한 자료가 있으면 함께 검증하고, 없으면 ‘사용자가 제시한 조건’임을 유지한다. 사용자 말만으로 공통 법률 사실을 승인하지 않는다.

legal_agent는 이 snapshot에서 다음의 **조건부 해석**을 구성한다.

- 제3호는 우선 검토 대상이지만, 전문투자자의 취득에 해당하는 세칙 제23조제4항제2호 예외를 별도로 확인한다.
- 제3호 적용 제외만으로 전체 의무보유가 없다고 결론 내리지 않는다.
- 제4호의 투자자 자격, 모집·매출 이외 취득, 예비심사 신청일 기준 투자기간 2년 미만, 상장신청일 현재 자본금 기준 각각 100분의 10 한도 및 세칙 제5항 예외를 별도로 확인한다.
- 이 사례가 그 요건을 모두 충족하고 별도 적용 의무·추가 조건이 없다는 가정 아래, 해당 제4호 대상 주식등의 기간은 저장 원문상 상장일부터 1개월이다.

여기서 ‘1개월’만 저장하면 다음 질문에 잘못 적용될 수 있다. 저장 단위에는 전제, 한도, 예외 확인, 별도 적용 여부, 정확한 문서명·조항, 해석 지점과 tool trace가 함께 들어가야 한다.

## 4. legal_wiki가 만드는 지식 단위

대화가 끝나기 전에도 다음 후보들을 구성할 수 있다. 같은 원문을 여러 단위가 참조할 수 있다.

| 지식 단위 | 내용 | 사례 정보와의 관계 |
|---|---|---|
| W1 투자자 자격 확인 | 사용자 표현과 규정상 전문투자자 개념을 구별하는 질문·정의 확인 절차 | B의 실제 자격 증명은 case-A 범위에 유지 |
| W2 제3호 단서 적용 | 해당 호 적용 여부와 세칙 예외를 확인하는 절차·조건 | case-A의 취득·자격 사실 revision 참조 |
| W3 제4호 별도 판단 | 투자기간·방식·한도·예외를 검사하는 조건과 주장 | A/B 사례는 적용 예시 membership |
| W4 두 조항의 관계 | 한 호의 제외가 다른 호까지 자동 제외하지 않는 해석 지점 | W2/W3의 검토된 주장에 의존 |

W1~W4는 처음부터 공개 법률 지식이 아니다. 원기록의 권한을 유지하며, 개인 사실을 제거한 일반 규칙을 공통으로 제공하려면 별도 검토·공유 정책을 통과해야 한다. 사용자 확인·증거 검증이 부족한 부분은 draft 또는 제한된 사용 모드로 둔다.

W3의 procedure에는 “전문투자자라고 답했으니 종료”가 아니라 다음 단계가 들어간다.

| 단계 | 필요한 입력·도구 결과 | 분기·이유 |
|---|---|---|
| 현재 문서와 조항 해소 | durable doc/unit refs → 현재 source handles | 세대 변경 시 원문 재검사 |
| 자격 정의 확인 | 규정·세칙의 정의 및 사례 자료 | 재무적투자자라는 표현만으로 자격 확정 금지 |
| 제3호와 단서 조사 | 제26조제1항제3호, 세칙 제23조제4항 | 이 호 적용 여부를 명확히 함 |
| 제4호 요건 조사 | 취득 방식·기간·한도와 관련 자료 | 제3호 제외와 별개 적용 검사 |
| 제4호 단서 조사 | 세칙 제23조제5항과 해당 조건 | 예외 누락 방지 |
| 주장·답변 확인 | 정확한 법령명·인용·조건·한계 | 오래된 오답 문구의 재사용 차단 |

이것이 실제 trace에서 구성한 재사용 절차다. 다음 요청에서 실제 실행 결과가 달라지면 기록된 분기를 따라 재조사한다.

## 5. 세션 C: 같은 개념의 다른 사건

사용자: “C사 D 투자자도 전문투자자인데 예비심사 신청일 기준으로 2년 3개월 보유했어. 아까랑 같아?”

새 사건 case-C를 만들고 case-A의 사실을 복사하지 않는다. W3의 조사 절차는 후보가 될 수 있지만 ‘2년 미만’ 조건을 충족하지 않으므로 저장된 1개월 판단을 그대로 채택하지 않는다. 제4호의 해당 요건 불충족이 다른 조항·계약상의 의무까지 없앤다고 결론 내리지 않고 필요한 조사를 진행한다.

새 사실 때문에 case-A의 기존 결론을 정정하지도 않는다. 같은 개념과 다른 사건의 구분이 여기서 작동한다. 위키에는 조건 변형이나 반례가 추가될 수 있다.

## 6. 검증되지 않은 정답 확산 방지

사용자: “설명 맞네, 저장해.”

이미 저장 중이므로 confirmation 이벤트와 확인 범위를 추가한다. 만약 답변에서 실제 자본시장법 참조를 다른 법률명으로 표기했다면 source verifier는 문서명·조항 연결을 실패 처리한다. 사용자 확인은 유지하지만 그 주장 revision의 JUDGMENT 재사용을 막는다. 이후 정정이 검증되면 새 revision을 구성한다.

이 사례는 ADR-0619에서 잘못된 법령명이 확정 경험과 새 세션으로 전파됐던 실패를 회귀 조건으로 반영한 것이다. 사용자가 ‘완료’라고 한 시점과 검증 가능한 법률 지식이 된 시점을 분리한다.

## 7. 야간 작업과 중단·변경 시나리오

| 상황 | shortcut | legal_wiki·다음 답변 |
|---|---|---|
| 자격 질문만 하고 대화 중단 | 받은 발언·도구 결과 저장 | OPEN 후보; 야간에도 완결로 자동 변경 안 함 |
| 늦은 정정이 compiler 실행 중 도착 | 즉시 revision 변경·의존 무효화 | 이전 build 게시 거부, 다음 batch 재구성 |
| 원문 generation 변경 | source dependency 변경 이벤트 | 영향 단위 STALE, 다음 질문은 현재 원문 확인 |
| wiki renderer 실패 | DB revision·outbox 유지 | 기존 유효 상태 또는 원문 조사; projection 재시도 |
| 답변 생성 후 응답 연결 끊김 | answer commit 및 request key 유지 | 동일 요청 재전송 시 커밋된 답변 회수 |
| 팀 권한에서 제외된 사용자 조회 | 신뢰된 현재 권한으로 차단 | 검색 결과·단위 제목·artifact도 노출하지 않음 |

사용자 화면에는 무엇을 이어받았는지, 어떤 정정 때문에 다시 조사하는지, 무엇이 아직 확인되지 않았는지를 보여 준다. 내부 DB나 compiler를 사용자가 직접 관리해야 하는 흐름으로 만들지 않는다.
