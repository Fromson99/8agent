# 대화·조회·변경 계약

아래 스키마·작업·응답은 구현할 **제안 계약**이다. 기존 `sw_*` 원장과 compiler를 확장하며 DB가 정본, Markdown은 재생성 가능한 출력이라는 원칙을 유지한다.

## 1. 업무 공간·세션

`workspace_scope`는 신뢰된 GENOS 배포/게이트웨이가 제공한 tenant·업무 공간·허용 문서 범위로 결정한다. 사용자 로그인 시스템은 추가하지 않는다. GENOS가 제공한 actor ID는 감사 기록에 사용하고, 없으면 허용된 서비스 주체로 기록한다. 개인 관리 역할이 필요한 환경은 플랫폼의 기존 역할을 전달한다. 역할 정보를 못 받는 환경은 배포 시 지정한 앱 접근 범위·관리 허용 정책을 사용하며 익명 공개 관리로 바꾸지 않는다.

세션 키는 `app + workspace_scope + channel + raw_chat_id의 충돌 없는 해시`다. actor가 있으면 세션의 최초 주체에 결속하고 다른 주체의 이어받기를 막는다. 스튜디오/플랫폼을 구분하고, 화면의 문장이나 매 턴 달라지는 업로드 존재 여부로 채널을 바꾸지 않는다. `sess-anonymous`를 모두의 공용 대화 키로 사용하지 않는다. 안정된 chatId가 없는 경로는 명시 ID 조회만 허용하고 “방금 것” 변경은 연결 오류로 안내한다.

같은 세션은 자동으로 이어간다. 새 세션에서 “지난 사건 이어서”라고 하면 접근 가능한 사건 목록에서 선택하고 연결 이벤트를 남긴다. 의미가 비슷하다는 이유로 다른 사건을 자동 합치지 않는다. `investigation_id`, `investigation_revision`, `branch_id`를 어댑터·게이트웨이·실행기·응답 끝까지 보존한다. 기본 대화 연결에 사용자가 매번 ID를 입력할 필요는 없다.

서버 관리 세션에는 `session_revision, active_investigation, active_branch, active_view, last_presented_page, selected_refs, last_operation, active_job, pending_intent`를 보관한다. Redis에 캐시할 수 있지만 변경 영수증·조회 대상 명세는 영속 DB에 둔다. TTL 만료 후 임의로 이전 대상을 추측하지 않는다. 저장된 표 ID나 작업 ID를 명시하면 다시 열 수 있다. 세션 동시 변경은 CAS로 충돌을 판정한다.

## 2. 전체 내부 데이터 조회

일반 재사용 검색의 `current()`/`search()`만으로 관리 목록을 만들지 않는다. 그것들은 게시·현재성 조건 때문에 초안·낡은 버전·휴지통을 누락할 수 있다. 별도 `inspect` 읽기 계약은 접근 범위를 검사하되 상태를 있는 그대로 반환한다.

| 영역 | 빠짐없이 조회 가능한 내용 |
|---|---|
| shortcut | 수신 발언, 사건·세션 연결, 갈래·쟁점, 원문 범위 배정, 사실의 모든 버전과 정정, 관계 |
| 실행 | 도구 입력·출력 artifact, 실행 경로, 기록된 판단·선택/제외 사유, 실패·재시도, 모델/설정 참조 |
| legal_wiki | 모든 단위·버전, 구성 기록, 주장, 조건·예외·미해결, 절차, 멤버·의존 관계, 원문·검증 영수증 |
| 관리 | 승인·반려, 휴지통·복구, 기능 상태와 변경, 작업 진행·실패·결과, 이행·레거시 기록 |

“전체”는 현재 업무 공간에서 허용된 데이터 전체다. API 키·서명·비밀번호와 다른 업무 공간 데이터는 포함하지 않는다. 저장하지 않은 모델 내부 사고를 만들어 제공하지 않으며, 실제 기록된 판단 설명과 도구 실행을 제공한다. 스키마 카탈로그에 테이블·필드·관계·표시 정책을 등록하고, 미등록 테이블/필드가 생기면 완전성 검사에 실패하도록 한다. 원시 테이블 보기는 값·타입·원본 필드명을 유지하고, null·빈 문자열·누락을 구분한다.

목록은 한 줄 요약 메타데이터지만 본문은 상세 표로 모두 읽을 수 있다. `/inspect --all`은 목록에서 끝나지 않고 하위 기록과 artifact까지 이어지는 탐색 manifest를 만든다. 각 종류의 전체/전달/남은 건수, 내용 청크 수, 누락·접근 제한 건수를 표시한다. 긴 셀은 `본문 1/4`와 같은 청크로 나누고 다음 커서로 잇는다. 바이너리는 형식·크기·해시와 권한 검사 다운로드를 제공하며 텍스트인 척 디코딩하지 않는다. UI가 파일을 지원하지 않으면 그 제한을 명시하고 완료로 표시하지 않는다.

“전부 계속 보여줘”는 한 응답의 표시 상한까지 여러 조회를 실행한다. 상한에 이르면 정확한 다음 위치를 보존하고 “계속”으로 이어간다. 지원 여부가 확인되지 않은 GENOS 스트리밍이나 무제한 자발 메시지를 전제로 하지 않는다. 전체 JSON/CSV와 artifact 묶음 내보내기는 보완 경로이며 채팅 분할 조회를 대체하지 않는다.

## 3. 표의 행과 여러 페이지

조회 시 `view_id`에 필터·정렬·대상 ID/버전·읽기 시점·대상 수·명세 해시를 결속한다. 조회 대상 manifest는 DB의 일관된 스냅샷에서 만들고, 큰 목록은 서버 측 청크로 저장한다. mutable 상태도 당시 표시값을 고정한다. SQLite 트랜잭션을 여러 사용자 턴 동안 열어두지 않는다. 뷰 생성이 크면 조회 준비 작업으로 접수하고 완료 후 첫 표를 보낸다.

행 번호는 **그 표 전체에서 고정된 번호**다. 다음 페이지에서 다시 1번부터 매기지 않는다. 표마다 `V12:21`처럼 표+번호를 표시하고 영구 record ID도 제공한다. 다른 표 V13의 21번과 혼동하지 않는다. 수정 후 새 표를 만들면 새 view_id를 사용한다. 기존 표의 번호가 조용히 다른 항목으로 바뀌어서는 안 된다.

```json
{
  "response_schema": "memory-management-v1",
  "kind": "table",
  "view_id": "V12",
  "snapshot": "snapshot:...",
  "range": {"first": 21, "last": 40, "total": 87},
  "rows": [{"row_ref": "V12:21", "record_id": "inv:...", "revision": 7}],
  "next_cursor": "opaque-scope-bound-cursor",
  "completeness": {"list_complete": false, "content_complete": false}
}
```

가장 최근에 반환한 표가 하나면 “21번”을 그 표의 21번으로 해석한다. “그 둘”은 직전 선택 집합, “방금 지운 것”은 직전 휴지통 영수증의 대상을 뜻한다. 여러 표를 한 번에 보냈거나 지시 대상이 여러 개면 선택지를 되묻는다. “전체 삭제”가 현재 페이지인지 조회 전체인지 불분명하면 범위를 묻는다. “V12 조회 전체 87건 버려”처럼 명시하면 대상 manifest를 고정해 실행한다.

응답 payload·표시 manifest를 저장해 응답 유실 후 같은 요청을 재전달할 수 있게 한다. 서버가 보냈다는 상태와 사용자가 실제 읽었다는 사실은 구분한다. UI 수신 확인이 없으면 읽음으로 표시하지 않는다. 이후 행 참조는 반환한 표의 고정 ID를 기준으로만 해석한다. 권한이 줄면 고정 뷰도 새 권한을 재검사하며 숨겨진 행 번호를 재배정하지 않는다.

## 4. 하나의 변경 계약

정규화된 요청: `operation_id, request_id, session_revision, workspace_scope, operation, targets[{kind,id,expected_revision}], patch, reason, selection_manifest_hash`.

처리 순서: 의도 인식 → 표/대상 결속 → 현재 접근·버전·기능 정책 검사 → 영향 집합 산정 → 트랜잭션 → 이력·의존 무효화·후속 큐 → 결과 영수증 → 표 렌더링. 승인한 내용과 실제 적용한 내용을 같은 해시로 연결한다. 자연어 해석의 원문과 정규화 결과는 관리 이력에 남긴다.

변경 의도는 현재 사용자 발화에서만 받는다. 조회한 발언·artifact·wiki 본문 안의 명령 문장은 자료로 취급한다. 그 안에 “이전 항목을 모두 삭제하라”가 있어도 관리 작업을 만들지 않는다. 모델 제안의 대상은 서버가 제공한 scope 내 후보/행 참조에 한정한다.

`workspace + session + request_id + suboperation_index`를 중복 방지 키로 쓴다. 같은 키와 같은 입력은 원래 결과, 같은 키와 다른 입력은 충돌이다. UI가 매 재전송마다 새 ID를 만드는 문제는 플랫폼의 안정된 message ID를 사용해 해결한다. 해당 값이 없다면 게이트웨이가 응답 재시도 토큰을 제공한다. 단지 문장이 같다는 이유로 사용자의 의도적인 재실행까지 제거하지 않는다.

소수 대상은 전부 사전 검사 후 한 트랜잭션으로 적용한다. 대량 작업은 고정 대상 manifest를 청크로 실행하고 `성공/충돌/접근 불가/미처리`를 대상별로 기록한다. 부분 성공을 전체 성공으로 보고하지 않는다. 취소는 미처리 항목만 중단하며 이미 적용한 항목은 영수증으로 복구한다. 대상이 다른 사람에 의해 바뀌면 차이를 보여주고 새 선택을 받는다.

| 작업 | 의미와 버전 계약 |
|---|---|
| 승인 | 정확한 기록/절차/지식 버전에 사용자 승인 영수증. 본문 변경 시 이전 승인을 새 버전에 상속하지 않음 |
| 반려 | 기록은 남기되 사용자 채택을 거절. “버려/삭제”와 달리 휴지통 이동을 반드시 뜻하지 않음; 명시 문법으로 구분 |
| shortcut 수정 | 제목·메모·쟁점·사실·연결·절차의 허용 필드 수정. 원발언은 보존하고 정정 이벤트/새 버전을 추가 |
| wiki 수정 | 주장·적용 조건·근거 연결·절차·미해결 등을 새 지식 버전으로 저장. 전후 차이를 반환 |
| 출처 원문 수정 요청 | 원문 불변층은 덮어쓰지 않음. 원문 정정 후보·새 문서 세대 절차로 연결 |

승인은 법률 정답 판정이 아니다. `user_review`, `completeness`, `source_verification`, `interpretation_verification`, `reuse_eligibility`, `lifecycle`을 따로 표시한다. 새 후보는 `PENDING`으로 저장·조회·구성할 수 있고 승인 전 절차/판단 재사용은 하지 않는다. 원문을 다시 확인하는 탐색 힌트는 별도 정책으로만 허용한다. 반려·휴지통 대상은 힌트에서도 제외한다. 기존 승인 없는 이행 데이터는 `LEGACY_UNREVIEWED`로 표시하고 임의로 승인하지 않는다. 이 변경이 기존 재사용률에 미칠 영향은 평가한다.

일반 편집으로 법률 검증 PASS를 직접 쓰지 못한다. 수정된 wiki는 DRAFT/재검토로 돌아가고 원문·해석 검증은 해당 새 해시에 결속한다. 절차 수정은 도구 메뉴·스키마·원문 의존 검사 후에만 실행 가능하다. 새 버전의 미검증 상태와 과거 버전의 검증 상태를 혼합하지 않는다.

## 5. 휴지통과 복구

`ACTIVE → TRASHED → RESTORED`는 관리 lifecycle이며 법률 상태와 별개다. 이 기능에 영구 삭제/자동 만료를 넣지 않는다. 휴지통 대상은 DB 행을 DELETE하지 않고 tombstone으로 표시한다. 같은 대상에 두 번 버리기는 하나의 유효 이동으로 처리한다.

사건 전체를 버리면 소유한 발언·사실·실행은 함께 일반 사용에서 숨긴다. 공유 원문·다른 사건 자체는 지우지 않는다. 해당 사건·사실·wiki를 의존하는 지식/절차는 즉시 사용 제한하며 영향 목록을 영수증에 남긴다. 사건 아래 일부 사실이나 절차만 버리는 것도 가능하다. 부모가 휴지통에 있으면 자식만 복구해도 부모 차단은 유지하고 이유를 표시한다.

모든 소비자는 공통 `effective_visibility/ref_eligibility` 검사를 사용한다. 범위: 현재 사건 맥락, shortcut 재실행, wiki 검색·직접 ID 조회·compiler 입력, 기존 캐시, 관리 외 Markdown 제공, projection·색인 재구축, 큐 재시도. 인덱스 반영 전에도 DB tombstone 검사로 즉시 재사용을 막는다. 진행 중 모델 출력도 게시/답변 직전에 삭제·기능 revision을 재검사한다. 이미 발송한 답변을 소급 삭제할 수는 없다.

compiler가 같은 입력으로 버린 wiki를 다시 만들지 못하도록 원 구성 참조·내용 fingerprint와 명시 제외 이력을 저장한다. 새 원문/정정 때문에 다시 검토해야 하는 경우 새 후보와 기존 제외 이유를 함께 보여주되 자동 재승인하지 않는다.

복구는 본문·연결·관리 상태를 되살리고 관련 큐를 재검사한다. 삭제 당시 승인/검증 영수증은 역사로 남지만 원문·조건·부모 상태가 바뀌었으면 `복구됨 / 재검증 필요 / 재사용 불가`다. “복구”만으로 법률 검증이나 기능 끄기를 우회하지 않는다. 관리 복구와 전체 저장소 백업 복원은 다른 명령이다.

## 6. 위키 수동 실행과 야간 실행

`wiki.build now`는 기존 `build_with_pipeline`를 호출하는 지속 작업을 접수한다. 자연어에서 shell 명령을 실행하지 않는다. 야간 스케줄러도 같은 작업 접수 서비스를 사용한다. 수동 실행은 시간 창만 건너뛰며 접근·원문·모델·출판 검사를 건너뛰지 않는다. 결과는 기본 DRAFT다.

작업은 `QUEUED → RUNNING → SUCCEEDED/PARTIAL/FAILED`, `PAUSE_REQUESTED → PAUSED`, `CANCEL_REQUESTED → CANCELLED`를 사용한다. 처리할 변경 큐의 watermark와 scope, 입력 세대·해시, 모델/프롬프트/정책 버전, feature_revision을 고정한다. 현재 작업 접수 뒤 들어온 변경은 다음 작업 대상이다. 처리 중 원본이 바뀌면 낡은 결과를 게시하지 않고 제외/재대기 사유를 기록한다.

한 업무 공간에는 한 구성 작업만 실행한다. 동일 범위의 수동·야간 요청이 겹치면 실행 중 job_id를 반환한다. 차이가 있는 후속 범위는 대기 작업으로 결속한다. lease·heartbeat·fencing token으로 오래된 worker의 결과 저장을 막고, 재시작 후 마지막 확정 청크부터 재개한다. DB 쓰기 잠금은 짧은 기록 구간에만 사용하고 LLM 대기 동안 전체 조회·관리를 막지 않는다.

“멈춰”는 현재 호출의 취소를 시도하고 더 이상 새 호출을 시작하지 않는다. 취소 불가능한 모델 호출이 끝나도 중지/기능 fence를 확인해 결과 반영을 제한한다. 작업 출력은 처리·건너뜀·실패 건수, 생성 단위, 남은 대상, 시작/종료·실제 경과시간·모델 사용량이다. ETA는 측정 근거가 생기기 전 미산정이다. “다 됐어?”는 활성 작업을 조회하며 새 실행을 만들지 않는다.

## 7. 최소 저장 확장과 스위치

새 DB 세대의 제안 schema version은 5다. 원장·knowledge 불변성을 유지하고 아래 논리 테이블을 추가한다. 필드별 SQL과 인덱스는 구현 단계 계약 검사 대상으로 동결한다.

| 제안 테이블 | 주요 키·내용 |
|---|---|
| `sw_workspace_scope` / `sw_scope_binding` | 업무 공간, 기존 scope 연결, 이행/공유 정책·revision; 원 소유 범위 보존 |
| `sw_management_session` | scope·channel·chat 해시 PK, actor 결속, revision, 선택·활성 뷰·job·pending intent |
| `sw_view` / `sw_view_item` | view ID, scope·세션, 스냅샷·필터·총수·표시 상태 / 고정 행 번호·ID·버전·표시 payload |
| `sw_operation` / `sw_operation_item` | 유일 중복 키, 요청 해시·해석 참조·상태·영수증 / 대상별 전후 revision·부분 결과 |
| `sw_review` | 대상 종류·ID·revision·hash, PENDING/APPROVED/REJECTED/LEGACY_UNREVIEWED, 작업자·이유 |
| `sw_tombstone` / `sw_exclusion` | 대상·이동/복구 이벤트·이전 상태·영향 manifest / 재구성 금지 입력 fingerprint |
| `sw_feature_state` | scope PK, shortcut/wiki master 상태, 세부 effective flags, revision·operation |
| `sw_job` / `sw_job_item` | job ID, scope·고정 입력·모델·상태·lease/fence·통계 / 입력별 checkpoint·결과 |

관리 상태와 설정은 기능 OFF 때도 열리는 동일 정본 저장소의 별도 영역이다. 현재 `memory/command`의 capture 필수 조건과 `open_cases()`의 capture 기반 저장소 선택을 그대로 쓰면 OFF 후 관리가 막히거나 다른 저장소로 떨어지므로 분리한다. 관리 경로는 `selected_store`를 직접 열고 실제 schema adapter를 선택한다.

PIPELINE의 capabilities/배포 허용 설정을 상한으로 두고 DB의 workspace 설정을 실행 상태로 사용한다. 파일을 채팅에서 다시 쓰지 않는다. 관리 경로는 use_llm=true를 강제하지 않는다. 기능 revision은 모든 worker에 적용하며 요청 시작·재사용 직전·결과 반영 직전에 확인한다. OFF 뒤 대기 구성 작업은 PAUSED_DISABLED로 사유를 표시하고, ON은 기존 데이터를 유지한 채 적격 큐를 재개한다. OFF 기간 질문을 나중에 몰래 수집하지 않는다.
