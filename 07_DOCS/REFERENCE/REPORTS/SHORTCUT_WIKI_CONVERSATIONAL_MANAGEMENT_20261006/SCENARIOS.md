# 입력창에서 이어지는 관리 시나리오

모든 ID·건수·내용은 **설명용 가상 예시**다. 실제 실행 결과나 법률 판단이 아니다. 공통 흐름은 GENOS 대화 ID → 서버 관리 세션 → 정규화 작업 → 기존 저장소/worker → 표 렌더러다.

## 1. 전체 조회 → 다음 표 → 이전 표 항목 삭제 → 복구

사용자: **shortcut 전체 보여줘.**

응답: `표 V12 · 전체 43건 중 1–20번 · 승인·반려·휴지통 상태 포함. 본문은 번호로 열 수 있습니다.`

| 번호 | ID | 쟁점 | 버전 | 사용자 검토 | 보관 |
|---|---|---|---|---|---|
| V12:1 | S-a | 상장 관련 조사 | 4 | 승인 대기 | 정상 |
| V12:2 | S-b | 이전 질문의 정정 | 7 | 승인 | 정상 |
| V12:3 | S-c | 중단한 조사 | 2 | 반려 | 정상 |

실제 응답에는 해당 페이지의 모든 행을 보낸다. 위 표는 문서 설명을 위한 세 행 예시다. `view_item`에는 43건 전체의 ID/버전 대응을 고정한다.

사용자: **다음.**

응답: `같은 표 V12 · 21–40번`. 다음 페이지를 새 검색으로 만들지 않는다.

사용자: **첫 표 2번하고 3번 버려.**

해석: V12:2·V12:3 → S-b revision7·S-c revision2. 현재 권한과 버전을 다시 검사하고 휴지통으로 이동한다. 현재 페이지의 22·23번으로 해석하지 않는다.

응답: `OP18 · 2건 휴지통 이동 · 관련 위키 1건 재사용 중단.` 대상별 ID·기존 버전·새 관리 상태와 영향을 표로 돌려준다.

사용자: **방금 버린 것 중 첫 번째는 복구해.**

해석: OP18의 첫 대상 S-b. 새 목록을 검색해 첫 행을 고르지 않는다. 응답: `S-b 복구 완료. 관련 위키는 원문 변경이 있어 재검증 대기.` 원문이 실제로 그대로면 현재 조건 검사 결과를 따로 표시한다.

## 2. 내부 내용을 여러 번 나눠 읽고 수정

사용자: **2번 안에 있는 것 전부 보여줘. 도구 실행 내용까지.**

서버가 사건 상세 manifest를 만든다. 사건 정보 → 세션·발언 → 쟁점·사실 모든 버전 → 도구 입력·출력 → 판단 이유·근거 → wiki 연결 → 관리 이력 순서로 반환한다. 각 부분의 전체·읽은·남은 수와 이어보기 위치를 표시한다.

사용자: **계속.**

도구 출력 artifact의 다음 청크를 정확한 바이트 범위와 해시로 읽는다. 표 표시에서 개행·파이프를 escape하되 내보내기 원본은 그대로 보존한다. 표시 상한을 넘으면 다음 위치를 돌려주며 “전부 읽음”이라고 하지 않는다.

사용자: **사실 표의 4번은 지금 시점 말고 거래 당시 기준으로 바꿔.**

대상 사실과 필드는 특정되지만 “거래 당시” 날짜가 기존 사건에서 유일하지 않으면 날짜만 되묻는다. 유일하면 새 valid_time·사실 버전을 저장한다. 원발언은 보존하고 관련 지식 사용 제한을 즉시 적용한다. 변경 전후와 필요한 재검증을 보여준다.

## 3. 승인·반려·wiki 편집

사용자: **이 표에서 1번 승인하고 3번은 반려해.**

선택 버전에 사용자 승인/반려를 기록한다. 응답의 열을 `사용자 승인 / 원문 검증 / 해석 검증 / 재사용`으로 분리한다. “승인했으므로 법률적으로 맞음”이라고 표시하지 않는다.

사용자: **위키 1번의 적용 조건에서 A를 B로 고쳐.**

지식 revision3을 보던 상태라면 revision3의 해시를 확인하고 revision4 초안을 만든다. 어떤 주장·절차가 이 조건에 의존하는지 표시한다. 이전 검증 영수증을 revision4의 PASS로 복사하지 않는다.

사용자: **아니, 원래대로 돌려.**

직전 편집 영수증의 전후 차이에서 복원 패치를 만들어 새 revision5로 남긴다. 중간에 다른 편집이 있으면 덮어쓰지 않고 충돌 부분을 표시한다. 이를 휴지통 복구나 DB 전체 복원과 혼동하지 않는다.

## 4. 낮에 야간 작업 시작 → 다른 질문 → 상태 확인

사용자: **legal_wiki 야간 작업 지금 돌려.**

응답: `J7 접수. 현재까지의 변경 기록 18건 대상. 결과는 검토 전 초안으로 만듭니다.` 접수 응답 후 기존 compiler worker가 처리한다.

사용자: **진행하는 동안 shortcut 5번 내용 보여줘.**

J7과 별개의 조회를 처리한다. worker가 모델 응답을 기다리는 동안 전체 DB 쓰기 잠금을 쥐고 있지 않도록 한다.

사용자: **아까 작업 얼마나 됐어?**

응답 표: 처리 10, 남음 8, 실패 1, 생성 초안 6, 실제 경과시간, 마지막 갱신. 처리·실패·생성은 분모가 다르므로 합계 관계를 명시한다. 새 작업은 시작하지 않는다.

사용자: **멈춰.** → 중지 요청과 이미 완료한 범위를 반환.

사용자: **이어서 해.** → J7의 checkpoint부터 재개. 같은 입력으로 초안을 중복 생성하지 않는다.

## 5. 기능 끄기와 대화 유지

사용자: **shortcut하고 wiki 둘 다 꺼.**

응답: `현재 업무 공간 전체에 적용했습니다. 새 shortcut 기록·경험 재사용과 wiki 구성·사용을 중단했습니다. 데이터는 남아 있으며 관리와 복구는 가능합니다.` 진행 중 작업이 있으면 중지 반영 상태도 표시한다.

사용자: **휴지통 보여줘. 2번 살려.** → 관리 경로가 OFF와 독립이므로 실행 가능.

사용자: **wiki만 다시 켜.** → wiki 상태만 켠다. 기존 기록에서 만들 수는 있지만 OFF 기간에 저장하지 않은 shortcut 기록은 만들 수 없음을 표시한다. shortcut 캡처를 함께 켜지 않는다.

사용자: **새 법률 질문 …** → 기능 상태에 맞는 원문 RAG와 단기 세션 맥락을 사용한다. 관리에서 골랐던 휴지통 항목을 이 질문의 사건으로 자동 선택하지 않는다.

## 6. 여러 턴·여러 호출의 실패 경계

| 상황 | 처리 | 사용자에게 보이는 결과 |
|---|---|---|
| 표를 본 뒤 다른 사용자가 수정 | expected_revision 충돌, 해당 변경 보류 | 이전/현재 차이와 새 대상 선택 |
| 앞 표 두 개 중 “3번” 대상 모호 | pending_intent에 작업 보존, view 선택 요청 | “shortcut 표 V12와 wiki 표 V13 중 어느 쪽인가요?” |
| 200건 중 일부 청크 적용 후 장애 | 고정 대상과 개별 receipt로 재개 | 완료/실패/미처리 수, 완료한 것 복구 가능 |
| 삭제 응답만 네트워크 유실 | 같은 request key로 원 영수증 재전달 | 중복 이동 없이 동일 OP 번호 |
| Redis 중단 또는 세션 TTL 만료 | 단일 턴 관리 조회는 가능; 지시어 변경은 대상 재선택 | “이전 표를 다시 열어 대상을 선택해 주세요.” |
| 같은 chatId가 다른 채널/업무 공간에 등장 | 세션 namespace 분리 | 다른 공간의 표·선택 이력 미노출 |
| wiki 구성 중 원 shortcut 삭제 | commit fence에서 입력 제외/결과 무효화 | 삭제된 입력으로 만든 초안 미게시 |
| 삭제 후 과거 큐가 재실행 | tombstone·제외 fingerprint 검사 | 버린 지식 자동 부활 방지 |
| 기능 OFF 직전 시작한 재사용 응답 | 반환 직전 feature/lifecycle 검사 | 해당 경험 제외 후 재조사하거나 중단 사유 |
| 원문 변경 후 복구 | 자료는 복구, 과거 검증은 현재 통과로 간주하지 않음 | 복구됨·재검증 필요 |
| 자연어 해석 모델 실패 | 명령어 경로는 계속 가능, 변경 미실행 | 해석 실패와 정확한 명령 예시 |
| 일반 발언 안에 “위키 삭제라는 말”을 인용 | 관리 의도가 확정되지 않으면 변경 금지 | 일반 질문 처리 또는 대상 확인 |

이 사례들은 계약 시험과 실제 GENOS 워크플로우 화면 검증의 입력으로 사용한다. 이 문서를 작성한 것만으로 시험을 통과한 것으로 기록하지 않는다.
