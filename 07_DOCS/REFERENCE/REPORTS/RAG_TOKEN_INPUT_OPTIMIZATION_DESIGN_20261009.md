# MAIN49 모델 입력 진단과 토큰 최적화 설계

**후속 구현(2026-10-09):** 미선택 상세 메뉴·간결한 전체 행동 이력·탐색 원문 중복/빈 배열 규칙 축소를 [ADR0712의 로컬 MAIN50](../../../04_EXPERIMENTS/ADR/ADR-0712-compact-direct-read-context/MAIN_RESULT.md)에 반영했다. 신규 공개3문항 입력 38.3% 감소, 호출 12→12회. 최종 판단의 구절 표시·교정/참조 입력 추가 축소는 보류했다. 아래 본문은 구현 전 읽기 전용 진단·설계 기록이다.

2026-10-09. **저장된 요청 분석·설계·백로그만 수행했다. 제품 코드, 모델 입력 계약, 활성 MAIN49, GENOS는 변경하지 않았다. 신규 모델 호출 0회.**

사용자 요구: 선택 환경을 단순화하고 지금 판단에 필요한 정보만 제공한다. 과거에 수행한 행동은 보존하되 과거 화면·원문 전체를 이력으로 반복 전달하지 않는다. 별도 요약·선택·검사 LLM을 추가하지 않는다.

결론: 우선순위는 **미선택 법령의 상세 메뉴를 미리 펼치는 문제 → 같은 원문·규칙의 중복 표현 → 모든 행동의 간결한 이력 → 거절 교정 입력**이다. 이력에 과거 원문 전체가 항상 들어가는 구조는 아니다. 이미 원문 없는 이력 처리가 있으며, 관측한 최대 입력의 주성분은 현재 후보 메뉴다. 과도한 메뉴가 모델의 행동 오류를 일으켰다는 인과관계는 아직 검증하지 않았다.

## 1. 실제 실행 경로와 분석 범위

- 로컬 WSL 선택 포인터 generation **49**, `grounded-entry-20261009-r1`. 포인터·릴리스 manifest·프로필·데이터 해시를 [측정 원장](../../../09_ARTIFACTS/AUDITS/20261009-main49-token-input/input-sizes.json)의 `binding`에 기록했다. 현재 작업 코드와 선택 코드 **287파일 해시 일치**를 다시 확인했다.
- 서비스 경로: `service.service → service.py → /v1/rag/ask → app/execute_ask → pipeline/coordinator → unified_runtime → UnifiedRag → law_navigation → bounded_source_session.structured → gateway → transport`. 앞단 통합 해석 후 기존 조사·판단 경로에서 입력이 커진다.
- 원문 세대 `term-source-8729f978a28924cb8c5b`, 선택 데이터 `native-cm-serving-20261008-r2-index`, 모델에 허용된 공개 원문 65문서. 데이터·용어집·색인 재구축은 이 설계의 선행 조건이 아니다.
- **저장된 provider 요청 52개**를 읽었다: ADR0710 양쪽34개(그중 현재 MAIN49 검증 후보12개), ADR0708 실패4개, ADR0705 과거 CM018 실행14개. 새 질문 실행·재평가·답변 재채점은 하지 않았다. 과거 실패를 MAIN49에서 새로 재현한 것으로 취급하지 않는다.
- 실제 호출별 입력 토큰은 당시 provider `usage.prompt_tokens`다. 항목별 크기는 `ensure_ascii=False`, 공백 없는 JSON의 **유니코드 문자 수**다. 필드별 토큰 수와 문자 비율은 같지 않다. 출력 스키마의 직렬화 크기를 실제 과금 토큰 수로 환산하지 않는다.
- 원문·질문·전체 후보 목록은 새 보고서에 복사하지 않았다. 원장은 요청/응답/압축 원본 해시, 필드 크기, 중복 위치만 보존한다. ADR0710/0708 압축 원본은 기존 영수증 해시와 일치한다. ADR0705는 이번에 산출한 압축 원본 해시를 기록했다.

## 2. 확인한 입력 낭비

### A. 읽기 전부터 후보 전체의 상세 선택지를 펼친다 — 최우선

MAIN49 검증 H03의 첫 탐색 호출은 본문 검색 결과에서 원문을 고르는 단계였다.

| 관측·계산 ID | 값 | 출처·분모 |
|---|---:|---|
| M1 관측: 실제 입력 토큰 | 66,883 | ADR0710 `integrated/H03/provider/call-002-product-2-source-law-navigation-1` |
| M2 관측: 선택 환경 | 법령12개, 행동270개 | 같은 요청 `view.laws`, `view.actions` |
| M3 관측: 제공 원문 페이지 | 0개 | 같은 요청 `view.sources`; 검색 미리보기는 존재 |
| M4 계산: 판단 데이터 길이 | 153,769자 | `size(view)` |
| M5 계산: 법령 카드+행동 목록 | 142,418자, 92.62% | `(113,337 + 29,081) / 153,769`; 시스템 문구·스키마 제외 |
| M6 계산: 미리 펼친 구조 상세 | 62,958자 | 12개 `document_structure` 값 합계; 이 중 `shape` 28,198자, `children` 26,688자 |
| M7 관측: 함께 펼친 항목 | 본문 적중96개, 구조 하위48개 | 법령마다 적중 최대8개, 구조 하위4개 |
| M8 계산: 별도 출력 스키마 | 68,855자 | 실제 요청 `response_format.json_schema.schema` |

`law_navigation.build_view`는 보이는 모든 법령에 `document_structure`를 호출한다. 각 법령의 구조 형태·수준별 예시·하위 항목을 붙이고, 구조 이동/읽기·법령 열기·본문 검색·읽기 범위 선택을 모두 행동으로 등록한다. `article_menu`는 별도로 법령마다 최대8개 적중 조문을 붙인다. 따라서 `article_page_size=4`만 줄여서는 이 입력을 모두 통제할 수 없다.

**제안:** 첫 화면은 현재 순서를 유지한 법령 제목, 일치 단서, 가장 관련 있는 조문·좌표·짧은 적중 내용, 바로 읽기, 더 보기로 구성한다. 구조 상세는 현재 선택한 법령·위치에서 펼친다. 이미 명확한 조문은 법령 선택을 별도 모델 호출로 요구하지 않고 바로 읽을 수 있어야 한다. 나머지 후보는 서버에 보관하고 페이지·더 보기로 접근한다. 단순히 상위 몇 개를 삭제하거나 나머지를 없는 법령으로 취급하지 않는다.

구조 검색과 fulltext는 계속 동등한 도구다. 대략적인 위치를 알면 구조로, 세부 문구를 찾으면 fulltext로 간다. 메뉴 축소 때문에 구조→fulltext 고정 순서를 다시 도입하지 않는다.

### B. 한 번의 판단 안에서 동일 원문이 여러 표현으로 중복된다

MAIN49 H01의 158자 문단은 탐색2에서 `sources.text`, `sources.spans[].text`, `exact_evidence.text`, 조문 미리보기로 **4곳**에 들어갔다. 최종 판단에서도 `sources.text`, `sources.adopted_spans[].text`, `exact_evidence.text`, `evidence_options[].text`에 같은 문단이 4곳 들어갔다. 원장의 `duplicate_original_texts`에 문단 해시와 실제 위치를 기록했다.

현재 `gateway.compact_wire_view`는 `exact_evidence.spans` 안의 중복 text만 제거한다. `bounded_source_session.structured`가 `sources`를 바탕으로 `exact_evidence`를 추가하고, 최종 판단은 `completion_contracts.evidence_options`도 만들므로 여러 표현에 본문이 남는다.

**제안:** 한 호출에 원문 텍스트는 단일 근거 목록으로 한 번 제공한다. source/인용 선택/범위 영수증은 그 목록의 참조 번호·블록·위치로 연결한다. 서버는 기존 원문·span·해시·전체 검증용 객체를 그대로 보관하고 모델에 보낼 사본에서만 중복을 제거한다. 원문 텍스트가 없는 카드가 인용 근거로 승격되지 않도록 실제 전달 목록과 검증을 연결한다.

**호출 간 기억은 가정하지 않는다.** 현재 판단에 필요한 원문은 그 호출에 다시 한 번 온전히 제공한다. 과거 호출에서 읽었다는 ID만으로 최종 판단을 시키지 않는다. 제49조제1항의 구조를 묻는 요청은 해당 항의 본문·단서·호·목 전체를 읽는 계약을 유지한다. 요약으로 대체하거나 긴 원문을 임의로 자르는 설계가 아니다.

### C. 같은 판단 규칙을 행동 종류마다 복제한다

`decision_schema`는 공통 필드를 최상위에 두고, 다시 각 행동의 `anyOf` 안에 전체 계약을 복사한다. MAIN49 H01 탐색2는 행동 종류/종료 분기14개, 스키마51,019자였다. 그중 `anyOf`가46,798자다. 읽기 행동에서는 채택 배열이 `maxItems=0`인데도 상세 채택 규칙이 함께 존재한다.

이 중복에는 이유가 있다. 코드 주석대로 기존 구조화 생성기가 바깥 공통 속성을 분기와 제대로 합치지 않는 문제에 대응한 것이다. **중복을 바로 지우거나 `$ref`를 지원한다고 가정하면 안 된다.**

**제안:** 우선 빈 배열로 고정된 필드의 불필요한 상세를 줄이고, 현재 보이는 메뉴에 맞는 대상만 제공한다. 그다음 전송용 출력 계약을 공통 필드 한 번으로 표현할 수 있는지 검증한다. 전체 원본 schema와 서버의 행동–대상 결속·권한·상태 버전·원문 채택 검사는 유지한다. 구조화 출력 호환성과 교정 증가 여부를 통과한 경우에만 전송 사본에 적용한다. 별도 검사 LLM은 추가하지 않는다.

### D. 행동 이력은 원문 복사보다 판단·대상 객체의 반복이 문제다

`investigation_chain.context`는 전체 행동·목적·결과를 유지하고 과거 화면의 `data`/원문을 이력에 통째로 넣지 않는다. 원문이 포함된 화면은 서버의 frame에 보관한다. `saved_inventory`도 상태·범위 메타데이터다. `model_view`는 과거 basis의 text/spans를 이미 제거한다.

다만 `trail.compact`는 최근8개 행동을 상세 객체 그대로 둔다. 이전 CM018 실패(ADR0705)의 마지막 교정 입력에서는 이력9,554자, 판단 데이터의12.42%였다. 그 실행의 탐색10호출 모두 `sources`는 비어 있었고 입력 토큰 합계는342,890이었다. 원문 누적 없이도 후보 화면과 이력이 크게 반복됐다는 관측이다.

**제안:** 첫 행동부터 짧은 행으로 전달한다. 모든 단계의 순서를 남기되 상세 판단·대상 객체·긴 설명은 서버 로그로 이동한다.

| 모델이 계속 받는 정보 | 서버 로그에 보존하는 상세 |
|---|---|
| 단계 번호, 실행 도구, 대상 법령·조문·범위 참조 | 원래 선택 화면·도구 인자·전체 후보·원문 |
| 짧은 목적, 성공/거절/중단 상태 | 모델의 원래 이유·판단 JSON·오류 전문 |
| 실제 결과와 새 근거 참조, 확보/전달/채택 구분 | 블록 해시·span·전체 영수증·상태 전이 |
| 검색어 목록 한 사본, 신규 결과 여부, 남은 부족 | 중복 검색 키와 전체 비교 이력 |

형식 예시(새 실측 아님): `3 / READ / 법령A 제49조제1항 / 목적: 항의 전체 구조 확인 / 전달 12/12블록 / 미채택 / 근거E3 / 부족: 예외 적용 여부`.

거절된 제안은 실행 이력과 구별한다. “원문을 읽으려 했다”와 실제 `RESEARCH 거절·실행0`을 같은 사실로 합치지 않는다. 실패/미진행 원인도 짧게 남겨 동일 행동을 다시 고르는 것을 피하게 한다. 모델의 목적 문장을 읽고 서버가 임의로 행동을 바꾸지 않는다.

### E. 연결 근거와 교정에도 전체 메뉴가 따라온다

- H01 탐색2의 `references`는12,830자이며 그중 연결 카드16개가12,573자다. 읽은 원문 `sources`는949자였다. 연결 상세는 현재 쟁점에 필요한 직접 참조와 미해결 여부를 짧게 제시하고, 그 외 목록은 펼칠 때 제공하는 후보가 된다. 미해결 필수 참조를 감추거나 요약을 근거로 채택하지 않는다.
- ADR0708의 거절 교정은 284개 행동을 그대로 다시 제공했다. 교정 입력74,805토큰, 판단 데이터172,796자, 스키마82,628자다. 이전 실패 사례이며 MAIN49 새 실행 결과는 아니다.
- 제안: 같은 상태·화면에 묶인 교정에서 거절된 제안, 짧은 오류, 현재 유효한 대체 행동과 관련 대상만 제공한다. 읽기가 항상 정답이라고 강제하지 않는다. 필요한 다른 경로/보류도 남긴다. 행동을 바꾸면 대상·질의·채택 필드를 함께 검증하여 이전 행동 필드를 잘못 상속하지 않게 한다. 현재 1회 교정 한도와 재개 binding을 유지한다.

## 3. 변경 지도와 최소 구현 순서

새 실행기·분류기·요약 모델을 만들지 않고 기존 실행기의 표시 사본을 고친다. 아래 API/계약 변경은 모두 **제안, 미구현**이다.

| 순서 | 현재 연결 지점 | 제안 변경 | 소비자·유지할 계약 |
|---|---|---|---|
| 1 | `law_navigation.build_view/article_menu`, `structure_query.document_structure` | 미선택 법령은 간단한 카드, 선택 법령의 구조만 펼침. 직접 읽기와 페이지/검색 접근 보존 | 같은 탐색 모델→현재 화면에 등록된 action만 실행. 문서·좌표·버전 결속 보존 |
| 1 | `bounded_source_session.structured`, `gateway.compact_wire_view` | 최종 전송 사본에서 원문을 한 번만 표현 | 기존 save_view·실제 전달 기록·원문 해시·인용 검증은 원본 객체로 유지 |
| 2 | `decision_schema`, `local_gemma.provider_request` | 빈 필드 규칙·반복 schema 축소, 필요하면 전송 계약 별도 버전 | 원본 schema와 `Investigation.validate`의 교차 필드 검사 유지, provider 호환성 별도 확인 |
| 2 | `investigation_chain.compact/points`, `saved_projection` | 모든 행동을 짧은 행으로, 판정 상세·이유 중복 제거 | durable chain/frame 불변, 복귀가 현재 채택 상태를 되돌리지 않음 |
| 2 | `reference_overview`, `completion_execution.reference_leads` | 관련 참조 요약과 목록 펼치기 | 원문 미전달 상태를 유지하고 필수 미해결 참조 누락 금지 |
| 3 | `request_decision/repair_contract/correction_schema` | 거절 관련 필드·대상만 짧게 제시 | 화면·상태 버전·재시도1회·중복 검색/읽기 차단 유지 |

모든 축소는 같은 질문·같은 현재 상태를 입력으로 재현 가능한 코드 투영으로 한다. 앞단 법령 제목 힌트는 MAIN49 세 사례에서225~935자로 작고 별도 LLM도 없으므로 우선 삭제 대상이 아니다. 장기 ID를 짧게 바꾸는 것은 이후 검토할 수 있으나, 기존 번호 변환을 무조건 켜지 않는다. 이 경로는 `structured`에서 번호 변환을 꺼 두므로 계약 호환 확인이 필요하다.

현재 `max_context_chars=100000`은 완성된 요청 전체의 상한이 아니다. `bounded_model_view`는 후보 미리보기 등을 줄인 뒤에도 크기 초과를 허용하고, schema는 별도로 생성한다. 이후 `structured`가 exact evidence와 envelope를 추가한다. H03의153,769자는 최종 view에서 관측한 값이다.

따라서 한도 점검은 **최종 시스템 문구 + 전송 view + 전송 schema**를 구분해서 수행해야 한다. 원문을 자르기 전에 메뉴 상세·중복·메타데이터부터 줄인다. 여전히 넘치면 기존 범위 내 페이지 전달/재개를 사용하고 전달 완료로 오인하지 않는다. 실제 토큰 측정 전 문자 한도를 토큰 한도로 부르지 않는다.

## 4. 전후 행동·검증 기준

| 같은 상황 | 기존 실제 결과 | 제안 후 목표 | 검사·통과 조건 |
|---|---|---|---|
| 본문 검색 후 관련 조문이 보임 | H03: 원문0페이지, 법령12·선택270 | 간단한 목록에서 해당 조문을 바로 읽음 | 불필요한 법령 선택 모델 호출 추가0; 모든 나머지 후보는 확장 가능; 같은 필수 원문 도달 |

숨긴 후보를 다시 펼치느라 모델 호출이 늘면 토큰과 시간이 악화할 수 있다. 잘못된 초기 후보에서도 다음 후보·본문 검색·구조 검색으로 이동하는 사례를 포함한다. 이전 실패 질문은 회귀 자료이며 새 독립 검증의 증명으로 쓰지 않는다. 새 데이터/권한/상태 버전이면 옛 참조 번호를 무효화하고 현재 권한 안에서 화면을 다시 만든다.

## 5. 성능 해석·도입·롤백

현 관측에서는 MAIN49 H01/H02/H03 각4콜, 입력 토큰 합계144,356이다. H03 첫 탐색1콜이 전체의46.33%를 차지한다(66,883/144,356). **이 비율은 삭제 가능한 토큰 비율이나 개선 예측이 아니다.**

H03의 큰 첫 탐색 호출은7.459초, 전체 모델4콜은30.102초, 서버 요청 전체는81.659초였다. 입력 크기를 줄이는 것이 모든 비모델 시간을 해결한다고 볼 수 없다. 적은 토큰·빠른 시간·정확한 선택은 각각 확인해야 한다. 캐시나 tokenizer 추정으로 실제 usage를 대체하지 않는다.

효과 검증 지표: 요청당 실제 모델 전송 횟수(교정·실패 포함), 입력/출력 토큰, 각 호출 시간과 서버 E2E 시간, 준비/검색/원문 읽기 시간, 메뉴 크기, 같은 본문 중복 문자, 필수 원문 전달·채택·인용, 실패/재개 상태. 비용·절감률·응답 초 단위 목표는 이번 읽기 전용 진단에서 미산정이다. 직렬화 감소가 있어도 호출 증가나 재시도 증가로 총량이 같거나 늘면 E2E 개선으로 인정하지 않는다.

구현에 착수할 때 기존 reservation을 확인하고 새 ADR에 부모 `ADR-0710/integrated`·동결 조건·회귀 범위를 기록한다. 정량 예산과 허용 회귀는 실행 전에 동결한다. 우선순위1을 한 후보로 확인하고 관측 후 후속 변경은 새 ADR로 분리한다. 현재 정확히 일치하는 코드 위에 필요한 수정만 통합한다. 계약 검사와 독립 사례 E2E를 거쳐 동일 코드 검증→해시 고정 승격→활성 포인터→실제 로컬 service 선택까지 확인한다. GENOS 현장 적용은 별도다.

기존 MAIN49 릴리스·원문·로그는 보존한다. 새 입력 투영 버전은 journal과 요청에 결속하고 중단 요청이 다른 버전으로 조용히 재개되지 않게 한다. 문제가 생기면 기존 승격 도구의 rollback receipt로 MAIN49를 재선택하고 작업 코드 복구는 별도 해시로 확인한다. 기존 원문/색인 재구축이나 완료된 실험 기록 수정은 필요 없다.
