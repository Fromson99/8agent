# 로그 기반 관계·구조 보정과 질문별 탐색 제한 설계

후속 사용자 요구를 반영해 경험을 RAG 도구·에이전트·구조 세대와 분리한
[독립 데이터·어댑터 프로토타입](PORTABLE_INVESTIGATION_MEMORY_20260929.md)을 추가했다.
같은 원문 근거는 현재 노드로 재연결하고, 원문 변경·매핑 누락·모호함은 재검증 상태로 남긴다.
합성 계약 23개 통과이며 실제 MAIN·ingestion·GENOS 배선과 속도 검증은 아직 남아 있다.

2026-09-29. 아래 본문은 최초에 코드·계약을 읽고 작성한 설계 제안이다. 이후 사용자의 논의를 따라 **질문 전체 유사도보다 탐색 중 노드·행동 관측을 먼저 사용하는 경험 안내**를 격리된 프로토타입으로 구현했다. 구현 기록은 [ADR-0559](../../../04_EXPERIMENTS/ADR/ADR-0559-node-action-experience-concepts/README.md), 출력 형식 수정·재검증은 [ADR-0560](../../../04_EXPERIMENTS/ADR/ADR-0560-node-action-experience-wire-repair/README.md), 인용 식별자 계약 수정은 [ADR-0561](../../../04_EXPERIMENTS/ADR/ADR-0561-node-action-experience-citation-contract/README.md)에 있다. MAIN 변경과 GENOS 배포는 수행하지 않았으며 실제 GENOS 로그·서빙에는 접근하지 않았다.

## 후속 프로토타입의 연결 범위

최종 프로토타입의 흐름·계약·사용 방법은 [노드·행동 경험 기억 프로토타입](NODE_ACTION_EXPERIENCE_PROTOTYPE_20260929.md), 빈 목록·이탈·근거 연결 보완은 [ADR-0562](../../../04_EXPERIMENTS/ADR/ADR-0562-node-action-experience-closed-feedback/README.md)에 있다. 이전 실패와 재검증은 각 ADR에 독립적으로 보존한다.

v5 완료 journal에서 원문 검증·요구별 인용이 있는 조사 선분을 `node-action-experience-v1` 후보로 추출한다. 배치 통합은 같은 세대·범위·시작 노드·행동 안에서 조사 목적을 묶어 `investigation-concept-v1` SQLite 번들로 저장한다. 실제 `read` 관측 뒤에만 해당 개념과 다음 읽기 제안을 현재 요청의 view에 추가하며, 현재 도구 핸들을 다시 발급하고 원문을 새로 읽는다. 이탈 피드백을 남긴 개념은 그 요청에서 더 안내하지 않는다.

이 구현은 기존 MAIN의 피드백 단계 확장 후보지만 `PIPELINE.json`과 기본 서비스에는 아직 연결하지 않았다. 온라인 소비자는 명시적 연구 runner이고, 배치 통합을 야간 실행하는 스케줄러는 만들지 않았다. 관계·구조 정본 수정과 강제 관계 탐색 차단 역시 아래 본문의 제안 단계로 남아 있다. 이력의 근거 검증은 법률 결론의 정확성이나 최적 경로의 증명이 아니므로 모든 개념을 PROPOSED / UNVERIFIED로 보존한다.

## 판단

둘 다 가능하다. 같은 실행 기록에서 **데이터 보정 후보**와 **질문별 탐색 절차 후보**를 각각 만든다. 원문에 존재하는 관계·구조의 오류와 특정 질문에서만 유용한 검색 연결은 다른 계약으로 저장한다.

- 데이터 보정: 질문에서 드러난 누락·오연결·구조 오류를 원본 문서로 확인하고 새 데이터 세대로 반영한다.
- 탐색 절차: 적용 조건, 시작 원문, 필수 확인 항목, 허용 관계, 확장·종료 조건을 저장한다. 매번 현행 원문을 읽어 답변한다.
- 로그에 답변이 성공했다고 기록되어도 근거가 충분하거나 그 경로가 최소라는 뜻은 아니다. 채택·인용된 원문 외에 누락된 예외·정의·준용을 검증해야 한다.

## 1. 로그에서 관계·구조 수정 후보 만들기

### 오류 분류

| 유형 | 예시 | 반영 위치·재구축 범위 |
|---|---|---|
| 검색 표현 문제 | 질문 표현이 등록 용어·문서 별칭으로 연결되지 않음 | 범위가 명시된 표현/절차 번들. 원문 변경 없음 |
| 명시 참조 누락·오연결 | 원문이 가리키는 항·호·별표와 색인의 대상이 다름 | 원문 증거와 실제 대상 좌표를 확인한 참조 후보 → 새 navigation 및 fulltext 결속 |
| 구조 오류 | 항의 부모가 잘못되거나 표·별표가 다른 조문에 붙음 | 원본 표현본/페이지 확인 → 해당 문서 재구조화 → 새 source generation → 영향받은 용어·정의·참조·fulltext 재생성 |
| 질문별 유용한 연결 | 서로 명시적으로 인용하지 않는 두 규정을 비교해야 함 | 해당 질문 유형의 탐색 절차. 정본 명시 참조로 추가하지 않음 |
| 회수 후 판단 오류 | 필요한 원문을 읽고도 선별에서 버림 | 선별·충분성 판단 개선 후보. 데이터 구조를 임의로 고치지 않음 |

후보에는 `run_id`, 실행 해시, 코드·데이터·모델·정책 버전, 원본 문서/페이지/span 해시, 기존 연결, 제안 연결, 사유, 상태와 부모 후보를 저장한다. 동일 근거·동일 변경은 중복 집계하고 재시도는 기존 완료 결과를 재사용한다. 다른 수정과 충돌하면 새 버전에서 재검증한다.

질문 처리 중 발견한 연결은 우선 그 요청의 임시 탐색 단서로 사용한다. 영구 데이터 수정은 원문 검증과 새 세대 구축으로 분리한다. 원문에 없는 연결은 추정으로 표시하고, 원문 접근 불가·판본 모호·구조 불완전이면 미확인으로 보존한다.

실제 구조 수정은 원문 내용을 질문에 맞춰 다시 쓰는 작업이 아니다. 부모·순서·좌표·표 귀속을 원본에 맞추는 작업이다. source ID가 바뀌면 옛 로그·출처를 덮어쓰지 않고 구→신 대응과 부모 세대를 남긴다. 교차 문서의 역참조 등 소비자 의존성까지 재검증하며, 안전한 부분 재구축이 없으면 통합 색인을 새로 만든다.

## 2. 질문별 탐색 절차와 강제 실행 정책

다음은 신규 제안 계약 `question-route-v1`이다. 기존 스키마 이름이 아니다.

- 적용 조건: 질문 목적, 대상 문서/업무, 버전·시점, 필요한 조건, 부정·예외·비교 여부, 허용 문서 범위.
- 시작점: 논리 문서·조문 좌표와 해당 세대에서 해소된 source ID.
- 필수 확인: 정의·본문·예외·준용 등 질문 요구별로 필요한 증거. 원문이 요구하는 의존 관계도 확인한다.
- 허용 탐색: 관계 종류와 방향, 범위, 후보/읽기/호출/시간 예산. 관계 유형이 색인에 명확하지 않으면 원문에서 확인하기 전 의미를 단정하지 않는다.
- 확장 조건: 어떤 요구가 미확인이고 다음 어느 범위를 볼지, 필요한 이유.
- 종료 조건: 필수 확인 항목 충족 또는 미완료·추가 질문. 예산 소진 자체를 충분성으로 처리하지 않음.
- 결속: 근거 로그, 검증 기록, 데이터·원문·번들·정책 해시, 상태, 철회 및 대체 버전.

실행은 `질문 해석 → 적용 조건 검사 → 좁은 원문 회수 → 요구별 근거 확인 → 필요한 범위만 확장 → 답변`이다. 프롬프트 외에 회수기와 도구 실행부가 정책을 검사한다. 시스템 자동 관계 읽기와 global/scoped 분기 모두 같은 검사 대상이다. 최종 top-k만 줄여 앞단의 탐색 비용이 그대로 남는 구현을 피한다.

예를 들어 모의 내규 A의 특정 보고 기한 질문이라면 해당 조문과 기산일 정의·예외를 먼저 읽는다. 원문이 B를 준용하면 B의 해당 범위로 확장한다. A를 인용하는 모든 문서의 역참조는 기본 탐색에서 제외하되, 질문이 ‘영향받는 내규 전체’라면 역참조 탐색을 허용한다. 같은 키워드라도 목적에 따라 정책이 달라진다.

적용 조건이 모호하거나 여러 절차가 충돌하면 좁은 shortcut을 강제로 선택하지 않는다. 기존 기준 탐색 또는 사용자 조건 확인으로 연결하고 이유를 기록한다. 데이터·권한 범위가 바뀌면 절차를 재검증한다. 탐색 범위 확장은 현재 허용 문서 집합 안에서만 이루어지며, 팀 이름 자체를 접근권한으로 취급하지 않는다.

현재 bounded 경로는 최초 풀의 보류 후보 복구는 지원하지만 나중에 필요한 새로운 조사를 일반적으로 재진입시키지 않는다. 단계적 확장을 구현하려면 회수 상태·선별 상태를 명시적으로 갱신하고 기존 근거 중복 읽기·예산 초기화·무한 반복을 막아야 한다.

## 로그로 절차를 도출하는 방법

1. 질문 유형별로 완결된 실행·실패·사용자 정정을 묶는다. 요약표는 사례 탐색용, journal은 경로 복원용이다.
2. 시작점, 실제 읽힌 원문, 선택/보류, 전달 view, 최종 근거, 관계 경로와 비용을 추출한다. 완전성 정보가 없으면 후보만 만든다.
3. 근거가 된 경로를 절차 후보로 압축하되, 미인용 원문을 일괄 불필요 처리하지 않는다. 예외·반증 확인에 사용된 원문도 남긴다.
4. 원문으로 필수 확인 항목을 검증하고 적용·제외 조건을 작성한다. 반복 성공이나 긍정 피드백만으로 충분성을 확정하지 않는다.
5. 별도 검증을 통과한 불변 번들을 기존 릴리스 절차로 선택한다. 온라인 요청은 로그 전체를 다시 읽지 않고 이 번들을 소비한다.

후보 추출·검증 실패는 기존 응답 반환을 막지 않는 별도 작업으로 처리한다. 보고서 사본은 best-effort이므로 누락·부분 journal을 자동 성공 사례로 수용하지 않는다. GENOS 내부 로그 분석·모델 처리는 내부에서 수행한다.

## 도입과 검증

초기 범위는 조문 조회·정의·절차/기한처럼 요구와 원문을 대조하기 쉬운 반복 질문군으로 한정하는 안을 제안한다. 복합 법률 적용·광범위 영향 분석은 좁은 절차를 억지로 적용하지 않는다.

먼저 v5 journal → 후보 저장까지 연결하고, 다음에 좁은 회수와 확장 정책을 연결한다. 구조 오류는 확인된 문서부터 기존 구축 파이프라인으로 수정한다. 절차 번들만의 변경은 데이터 재구축이 불필요하지만 구조·참조 변경은 위 표의 재구축이 필요하다. 외부 Request/Result는 가능한 한 유지하고 내부 원장·번들 계약을 버전 관리한다.

효과 검증을 시작할 때는 저장소 실험 표준을 끝까지 읽고 ADR 선점·후보 격리·설정 동결 절차를 따른다. 데이터 수정 효과와 탐색 정책 효과를 분리한 비교, 조합 비교를 설계한다. 같은 사례의 의역 질문은 독립 표본으로 세지 않고 질문군·문서 단위로 분리한다. 절차 도출에 쓴 로그와 평가 질문을 분리한다.

필수 원문 회수, 예외·준용 누락, 근거와 답변 일치, 미완료율, fallback 비율, 읽은 원문·도구·모델 호출·토큰·전체 지연을 함께 측정한다. 속도만 좋아지고 필수 근거가 빠지는 후보는 채택하지 않는다. 구체적 허용 회귀와 성공 기준은 결과를 보기 전에 고정한다.

측정된 절감률·일정·비용은 없다. 시간 관점의 제안 손익 조건은 다음과 같다.

`요청당 기대 순절감 = shortcut 적용률 × 적용 요청당 절약 시간 − 모든 요청의 절차 선택 비용 − 실패 확장의 평균 추가 시간`

양수여야 지연 관점에서 이익이다. 구조 보정·후보 검증·재색인·운영 비용은 별도로 포함해야 한다. 잘못 맞춘 shortcut이 불필요한 선행 읽기와 fallback을 늘리면 악화될 수 있다. 이는 산식이며 실측 예측이 아니다.

활성화 책임은 데이터/절차 검증과 MAIN 전환을 구분한다. 번들 오류는 기능 해제로 기존 회수 경로로, 데이터 오류는 이전 release·generation 포인터로 복귀한다. 이전 로그·번들·세대·receipt는 보존한다. GENOS 실행 확인은 배포 후 워크플로우 테스트 화면에서 별도로 수행한다.

## 추가 검토: 질문의 법적 구조로 경로를 재사용할 수 있는가

사용자의 후속 구분은 (1) 과거 질문과 의미가 비슷한지 모델이 판단하여 경로를 추천하는 방식, (2) 질문을 법적 개념과 판단 요구로 분해하고 구조를 비교하는 방식이다. 현재 시스템에서 (2)는 구현 가능하지만 이미 동작하는 기능은 아니다.

### 현재의 분해와 필요한 분해

`question_obligations.py`와 `obligation_protocol.py`의 질문 계획은 원질문 조각을 요구와 배경으로 나누고 요구별 근거·주장 연결을 유지한다. 법적 주체·행위·객체·관계의 정규화된 비교 표현은 없으며, 요구 ID도 질문 조각과 요구 문구에서 만들어져 요청 간 개념 동일성을 제공하지 않는다.

더욱이 현재 `BoundedSourceSession.investigate`는 원문 회수·선별 뒤 `prepare_question_plan`을 실행한다. 검색을 조이는 목적에는 이 위치가 늦다. 기존 원질문 보존·요구 추적을 유지하면서 검색 전 임시 분해와 제한된 정의 조회, 원문을 본 뒤의 확정·수정이라는 두 단계를 연결해야 한다. 일반 모델 도구 탐색 경로의 첫 턴 계획과 현재 bounded 실행 순서를 혼동하지 않는다.

### 제안 표현과 비교

신규 질문 분석 계약은 다음 정보를 보존한다.

- 주체와 역할, 행위, 대상, 사건/시점, 관할·규정 범위.
- 판단 요구: 적용 대상 여부, 의무 존재, 허용 여부, 절차, 기한, 예외, 계산, 비교 등.
- 질문에 명시된 사실, 부정과 AND/OR, 가정, 빠진 사실. 질문 span과 모델 추론·원문 확인 여부를 구분한다.
- 해당 문서 정의에 결속한 개념 ID와 의미 범위. 매핑이 없거나 모호하면 미해소 상태와 복수 해석을 유지한다.
- 요구별 확인할 근거의 의존 관계: 대상 여부 → 일반 규정 → 예외 → 절차/기한 등. 순서는 실제 해당 규정으로 검증한 경우에만 고정한다.

JSON 필드로 나누는 것만으로 온톨로지가 되지는 않는다. 개념 식별자, 관계 유형, 문서별 정의 범위, 상하위 개념의 원문 근거와 변경 이력이 요청을 넘어 공유되어야 한다. 기존 용어집·정의·문서 구조·명시 참조를 기반으로 삼되, 역할·행위·의무 유형의 대응은 추가 검토가 필요하다. 기존 용어 관계를 법적 적용 가능성으로 간주하지 않는다.

비교 결과는 단일 유사도 대신 다음 상태로 만든다.

| 결과 | 허용하는 재사용 |
|---|---|
| 적용 조건과 필요한 근거 역할이 일치 | 시작점·검증 절차 재사용. 현재 원문과 버전을 다시 확인 |
| 공통 요구만 일치 | 공통 부분만 재사용하고 A에 추가된 요구는 별도 탐색 |
| 결정 조건 충돌 | 해당 절차의 제한 적용을 거부 |
| 주체·시점·정의 등 미확인 | 정의·분기 조건을 먼저 조회하거나 필요한 사용자 사실 확인 |

목적은 A와 B의 법적 결론이 같음을 증명하는 것이 아니라 B에서 검증한 조사 절차의 적용 조건을 A가 만족하는지 판단하는 것이다. 이 관계는 방향성이 있다. 복합 질문에서 검증한 절차 일부를 단순 질문에 쓸 수 있어도 단순 질문의 절차만으로 복합 질문의 추가 요구를 덮을 수는 없다. 상하위 개념 일치도 같은 예외·절차가 적용된다는 보장은 아니다.

### 실행과 로그 학습

`A 임시 분해 → 용어집/문서 정의의 제한 조회 → 개념·범위 결속 → 조건으로 절차 후보 조회 → 일치·차이·미확인 비교 → 허용 부분 실행 → 새 원문으로 재검증`으로 연결한다. 후보 검색에는 역색인·관계 조회 또는 보조 벡터 검색을 사용할 수 있다. 벡터 검색 사용 여부가 온톨로지 여부를 결정하지 않는다. 최종 제한 근거는 구조 비교와 원문 결속이다.

B 로그에서는 우연히 거친 모든 클릭 순서 대신 검증된 질문 구조, 요구별 필수 원문, 확인 순서, 적용/제외 조건을 추출한다. 내부 모델 판단이나 HTTP 성공을 정답 인증으로 사용하지 않는다. 과거 사례에서 필요한 조건이 관측되지 않았다면 적용 범위를 넓히지 않고 미확인으로 남긴다.

LLM은 임시 분해와 개념 대응·차이 설명을 제안할 수 있다. 코드는 ID·범위·버전·근거 존재·누락 요구와 절차 적용 조건을 검사한다. 형식 검사가 모델의 법적 해석까지 보증하지 않으므로, 검증 전에는 시작점 추천에 사용하고 강한 탐색 차단은 검증된 질문군에 한정한다.

이 제안은 현행에서 폐기한 전체 법령의 Rule/조건/효과 재작성 DB를 전제하지 않는다. 별도 버전의 질문·조사 절차 계약으로 시작하며 정본 원문과 구분한다. 영구 법률 규칙 온톨로지로 확장하는 작업은 별도의 아키텍처·데이터 계약 변경이다.
