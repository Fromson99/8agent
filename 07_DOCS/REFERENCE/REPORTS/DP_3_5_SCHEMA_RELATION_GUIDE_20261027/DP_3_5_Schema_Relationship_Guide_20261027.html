DP 구조와 질문 처리 흐름

3·5번 과제 공통 법규 RAG | 핵심 스키마·연결 탐색 설명서

한 질문이 용어·정의에서 출발해 관련 조항을 찾고, 명시 참조 또는 검토 관계를 따라 실제 원문을 확보하는 구조를 설명합니다. 핵심 데이터는 4개 물리 테이블이며, 버전 선택·상태·보관을 포함한 개발 스키마는 9개입니다.

01 전체 흐름

질문 + 인증된 문서 접근권한
↓
검색 게시 버전·원문 데이터 세대 고정
↓
용어·정의·본문 검색 → 내규 원문 읽기
↓
명시 참조 / 검토 관계 → 연결 외규 원문 읽기
↓
추가 연결 확인 → 인용·해석·미확인 사항을 함께 응답

02 핵심 테이블의 역할

물리 테이블저장 단위질문 처리에서 하는 일
LGL_DOC_VER세대 내 문서 1건문서명·문서 식별값·원본 해시 확인
LGL_DOC_UNIT문서 구조 단위 1건장·절·조·항·호·목과 상위 구조·본문 범위 확인
LGL_DOC_BLK본문 블록 1건답변 인용에 사용할 실제 원문 조회
LGL_SRCH_ROW종류별 조회 행 1건용어·정의·출현·참조·관계·전문검색 데이터 조회

03 저장 책임과 현재 상태

영역저장 내용·상태
Gold 지식구조화 원문·재사용 지식·온톨로지·LLM Wiki. 원문 판본·조항·span을 중심으로 관리합니다.
Agent / 작업 후보질문·판단·실행 로그는 Agent. 온톨로지 작업 후보는 Dataiku S3 관리 폴더의 JSON이며, 승인·신청·SQL 적재 후 Gold에서 사용합니다.
이 문서의 범위LGL_*는 AIDP/SIDDA 개발 실버 검증용 명명입니다. DDL·매핑·조회 코드를 대조한 설명이며 운영 Gold 승인·현장 적재·조회 전환 완료를 뜻하지 않습니다.

원문 데이터는 Oracle/조회 API에서 필요한 범위만 읽습니다. GENOS 서빙에 전체 원문·색인을 내려받아 보관하는 구조로 설명하지 않습니다.

조회 행 내부의 연결 스키마

LGL_SRCH_ROW가 여러 논리 테이블·뷰를 종류별로 담습니다

SRCH_PBLS_ID + ROW_KIND_CD로 조회 범위를 정하고, SRCH_KEY_ID·OWNR_REF_ID·TGT_REF_ID·DOC_ID로 후보를 좁힙니다. 실제 논리 필드와 연결 원문은 ROW_JSON_CN에 있습니다. 보조 키의 의미는 종류에 따라 달라지므로 모든 관계를 TGT_REF_ID 하나로 연결하지 않습니다.

용어에서 원문으로 내려가는 연결

term_surface / term → term_id
↓
occurrence.term_id → source_id
↓
source.id → document_id + unit_id + 본문 블록
↓
LGL_DOC_VER → LGL_DOC_UNIT → LGL_DOC_BLK

source_id는 탐색용 원문 묶음 ID입니다. DOC_ID·UNIT_ID·BLK_ID와 같은 키가 아니므로 source를 통해 위치를 확인합니다. 상위 구조는 PRNT_UNIT_ID, 본문 범위는 UNIT_JSON_CN의 span 등 저장 계약으로 해석합니다.

게시 종류는 native.* 또는 asset_<경로 해시 일부>.<논리 테이블명> 형태입니다. 해당 게시 manifest가 포함 목록과 구조를 고정합니다. compact 저장의 occurrence/reference가 뷰인 경우에도 소비자는 같은 논리 계약을 사용합니다.

명시 참조를 따라가는 과정

정방향·역방향·정의 연결 | 문서명·조항·ID는 설명용 가상 예시

내규 I 제10조(S_I10)가 “외규 A 제20조”를 인용하고, 외규 A 제20조(S_A20)가 “외규 B 제5조”를 인용한다고 가정합니다. 실제 법률 내용이나 실측 실행 결과가 아닙니다.

내규 I 제10조 · S_I10
↓
참조 R01 → 외규 A 제20조 · S_A20
↓
참조 R02 → 외규 B 제5조 · S_B05

정방향 OUTGOING: 현재 원문이 가리키는 대상

순서조회·검사다음에 얻는 값
1reference_end.source_id = S_I10참조 ID R01
2reference.id = R01출발 source_id·원문 문구·위치·해시·해결 상태
3reference의 출발 source_id == S_I10현재 원문에서 나가는 정방향임을 확인
4reference_target의 R01 또는 reference JSON의 targets대상 S_A20·unit_id·block_ids
5source.id = S_A20 → 원문 테이블외규 A 제20조의 실제 원문
6읽은 S_A20의 연결을 같은 방식으로 확인필요하면 R02를 거쳐 외규 B 제5조 읽기

현재 런타임은 reference JSON의 targets를 읽는 경로도 사용합니다. reference_target은 같은 대상의 논리 투영이며, 매번 이 테이블을 별도 SQL로 조회한다는 뜻은 아닙니다.

역방향 INCOMING: 현재 원문을 인용한 출발점

reference_end에는 (S_I10, R01)과 (S_A20, R01)이 함께 등록됩니다. S_A20에서 R01을 찾았을 때 reference의 출발점은 S_I10이므로 역방향입니다. S_I10의 실제 인용 문구가 속한 구조·본문을 읽습니다. 탐색 방향이 바뀌어도 “I가 A를 인용한다”는 관계 의미는 유지됩니다.

정의 연결: 질문의 용어에서 참조 대상까지

질문 표현 → definition(D01) → 정의 원문·용어 span 확인 → definition_reference(D01, R03) → reference(R03)의 원문 인용 확인 → 대상 위치 → 실제 원문 읽기. 같은 단어라도 문서·조항별 정의 범위를 합치지 않습니다.

연결 목록은 읽을 위치를 보여줍니다. 원문 열람과 답변 근거 채택은 별도 상태이며, 한 참조가 여러 조항을 가리키면 ordinal과 각 대상 범위를 보존합니다.

검토한 내규–외규 관계 원장

명시 참조와 별도로 관리하는 basis_* 논리 스키마

내규에 외규 번호가 직접 적혀 있지 않아도, 실제 양쪽 원문을 검토해 근거 관계를 제안·승인할 수 있습니다. 이 원장은 앞의 LGL_* 9테이블에 포함되지 않으며, Oracle 어댑터의 현장 매핑·적재·소비자 연결은 별도입니다.

논리 테이블키·주요 컬럼역할
basis_headPK link_id; team_id, revision팀별 관계의 현재 revision
basis_revisionPK(link_id, revision); payload CLOB, hash관계 종류·상태·이유와 내규/외규 끝점
basis_bindingPK binding_id; link_id, revision, generation, payload CLOB, hash현재 데이터 세대의 실제 원문 위치 연결. (link_id, revision, generation) 유일
basis_lineagePK version_id; family_id, payload CLOB, hash문서 판본의 계보

관계 payload의 핵심 항목

항목내용
kind / status / reasonBASIS·IMPLEMENTS·RELATED / PROPOSED·APPROVED·REJECTED·REVOKED 등 / 검토 이유
internal[] / external[]내규·외규 끝점 목록. document_id, document_version, generation_id, unit_id, side, source_artifact_hash
spans[] / endpoint_hashblock_id, start_cp, end_cp, text, block_hash, span_hash / 끝점 전체의 해시

현재 읽은 내규에서 외규로 이동

읽은 내규의 document_id + 실제 span
↓
팀별 원장에서 같은 내규·겹치는 범위의 관계 찾기
↓
basis_head → basis_revision: 현재 revision·상태·이유
↓
basis_binding: 같은 revision + 현재 generation의 위치 확인
↓
external[]의 권한·원문·해시 확인 → 외규 실제 원문 읽기

APPROVED 상태의 현재 근거 관계와 미검토 후보를 구분합니다. 일부 배치 조사 후보는 UNREVIEWED_CANDIDATE로 탐색에 쓰는 경로가 있으나 승인 관계로 표시하지 않습니다. 관계 revision·승인·접근권한이 바뀌거나 현재 위치 결속이 유효하지 않으면 이전 경로를 그대로 사용하지 않습니다.

질문 하나의 실행 시나리오

검색 → 내규 원문 → 연결 외규 → 추가 참조 → 해석

예시 질문: “우리 회사 레버리지비율 관리 기준과 관련 외규 근거를 알려줘.”

단계테이블·연결 경로확인·전달하는 것
1. 버전 고정LGL_SRCH_CHNL → LGL_SRCH_PBLS → LGL_SRC_PBLS검색 게시 ID, 원문 데이터 세대, 현재 문서 권한. 게시 ID 직접 지정 시 채널 조회 생략
2. 내규 후보LGL_SRCH_ROW의 용어·정의·전문검색문서·조항 후보. 이름·검색 점수는 적용 판단이 아님
3. 내규 읽기LGL_DOC_VER → LGL_DOC_UNIT → LGL_DOC_BLK문서명·조항·상위 문맥·선택 범위의 실제 원문
4. 연결 회수reference_end → reference → targets / 별도 basis_*명시 참조와 검토 관계를 구분하고 출발·도착·근거 확인
5. 외규 읽기대상 source → DOC_VER / DOC_UNIT / DOC_BLK선택한 외규 범위의 실제 원문·판본·인용 위치
6. 추가 연결정방향·역방향·정의 연결을 필요한 범위에서 반복다른 조항의 기준·예외·산정방법을 추가 확인
7. 응답확보 원문 + 연결 경로 + LLM 판단내규·외규 실제 원문, 해석과 미확인 사항을 같은 행에서 제시

연결 탐색에서 지키는 경계

상황처리
참조 대상 위치가 미해결찾은 것처럼 읽지 않습니다. 문서명·조문번호로 구조 조회하고 필요하면 추가 검색합니다.
조회된 연결이 없음현재 범위·색인에서 미확보임을 기록합니다. 관련 외규가 존재하지 않는다고 단정하지 않습니다.
선택 범위·권한·해시 불일치잘못된 연결 또는 원문을 전달하지 않고 오류·미완료 상태를 보존합니다.
이미 읽은 대상·남은 예산 제한확보 범위를 확인해 반복을 줄이고, 남은 자료는 미확인으로 표시합니다.
적용성·충분성에 불확실성읽은 원문은 전달하며 판단과 미확인을 함께 표시합니다. 불확실성만으로 확보 원문을 버리지 않습니다.
