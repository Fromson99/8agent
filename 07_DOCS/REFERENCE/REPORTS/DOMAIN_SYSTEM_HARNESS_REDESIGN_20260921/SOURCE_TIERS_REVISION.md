# 모델 채택 기반 출처 tier와 통합 실험 — 목표 수정안

작성일: 2026-09-21. 설계만 작성. 런타임 코드·완료 ADR·활성 릴리스 변경 및 신규 모델 호출 없음.

이 문서는 사용자의 후속 지시를 반영한다. **모델이 관련 원문을 채택하되, 법적 해석을 확정하지 못하더라도 정확한 출처가 최종 화면에 남도록 한다.** 회수한 자료 전체를 서버가 자동 채택하는 방식은 적용하지 않는다.

앞선 [DESIGN.md](DESIGN.md)의 보존·권한·페이지·반복 제어 계약은 유지한다. 원문 이해 관찰을 필수 통과해야 출처를 발행하는 부분과 여러 원인 분리 실험을 순차 실행하는 계획은 아래 내용으로 변경한다. 이전 문서는 당시 설계 이력으로 보존한다.

**구현 대조 기준:** 8절의 AS-IS → TO-BE 요구 ID, 9절의 시나리오, 10절의 판정표를 사용한다. 구현 후 코드·실행 기록·최종 화면을 같은 ID에 연결해 검증한다. 현재 모든 구현 판정은 미검증이다.

## 1. 성공 목표를 바꾼다

주 목표는 질문에 필요한 원문이 **모델의 선택을 거쳐, 제한된 수의 정확한 출처로 최종 화면에 도달하는 것**이다. 답변의 법적 정답률은 별도 보조 지표로 계속 기록한다. 정답률이 낮다는 사실을 출처 품질 개선으로 감추지 않는다.

출처의 정확성은 서로 다른 세 축으로 측정한다.

- **원문 무결성:** 문서·판본·조항·발췌·열기 대상이 실제 저장 원문과 일치하는가. 서버가 검증한다.
- **질문 관련성:** 해당 원문이 질문을 검토하는 데 필요한가. 모델이 선택하고 별도 평가에서 확인한다. 실제 존재하는 문서라는 사실만으로 관련성이 보장되지는 않는다.
- **해석 타당성:** 그 원문으로부터 생성한 결론이 맞는가. 앞의 두 축이 좋아도 이 축은 실패할 수 있다.

따라서 `SOURCE_SELECTED`는 “해당 주장을 법적으로 입증했다”가 아니다. 현재 source assessment의 ADOPT/SUPPORT와 별도의 질문 관련성 선택 계약을 둔다. 법적 주장으로 쓰려면 기존 출발·대상·예외·검토 계약을 추가로 충족해야 한다.

## 3. 출처는 세 단계로 관리한다

| 구분 | 모델 판단 | 기본 화면 | 해석 상태와의 관계 |
|---|---|---|---|
| **Tier 1: 핵심 원문** | 질문이 지정한 대상 또는 답을 확인하는 데 직접 필요한 원문으로 채택 | 앞에 표시. 정확한 위치·발췌·원문 열기 | 적용 결론이 미확정이어도 선택 가능 |
| **Tier 2: 보완 원문** | 정의·예외·준용·세부 절차 등 핵심 원문을 보완하는 자료로 채택 | 같은 출처 영역에서 구분 표시. 긴 원문은 접고 발췌와 연결 이유 제공 | 해당 관계가 법적으로 적용된다고 확정한 것은 아닐 수 있음 |
| **Tier 3: 미채택·확인 대기 후보** | 아직 선택하지 못했거나 추가 확인 필요 | 기본 출처 목록에서 제외. 건수·추가 탐색 메뉴로 접근 | 인용 출처로 집계하지 않음 |

Tier는 모델 confidence 점수의 단순 구간이 아니다. 질문과의 역할·필요성 기준이다. 내용이 어려워 이해하지 못했다는 이유만으로 직접 필요한 원문을 낮은 tier에 밀어 넣지 않는다.

**결론을 뒤집을 수 있는 예외·제외 조항은 핵심 원문에 올릴 수 있다.** 구조상 ‘시행세칙’이라는 이유로 항상 Tier 2에 넣지 않는다. 원칙과 예외를 한 묶음으로 선택할 수 있게 한다. 묶음은 단지 중요한 두 원문을 함께 보여주는 장치이며, 예외가 실제 적용된다는 자동 법률 판단이 아니다.

명백히 무관하다고 모델이 판단한 자료는 `REJECTED` 이력으로 보존하고 기본 Tier 3 메뉴에서도 숨길 수 있다. 새 목표·새 근거가 생기면 재검토할 수 있다. 서버는 권한·존재·판본·범위가 잘못된 채택을 거부할 수 있지만 관련성을 대신 승인하지 않는다.

### 모델의 최소 선택 계약

`SourceSelectionDecision` 제안 필드:

```text
goal_id / question_revision / view_id
selections[]:
  evidence_id 또는 evidence_group_id
  tier: CORE | SUPPLEMENTAL
  basis_span_ids: 실제 제시 원문의 선택 범위
  relevance_reason: 이 질문에서 확인할 내용
  relation_refs: 연결 원문을 고른 경우 출발 관계
  interpretation_status: UNASSESSED | UNCERTAIN | REVIEWED
pending[]: 대상 ID와 아직 판단하지 못한 이유
rejected[]: 대상 ID와 제외 이유
```

선택 이유는 짧게 받고 “정확히 어떤 법률 결론인지”를 필수로 작성시키지 않는다. 단, 모델이 아직 보지 못한 원문을 채택하려 하면 READ/제시 후 선택 단계로 돌린다. 전체 E를 다 읽지 않아도 실제 읽은 정확 범위를 채택할 수 있으며 `PARTIAL`과 남은 범위를 표시한다.

한 번에 후보 전체를 보내지 않고 현재 후보 묶음을 페이지로 제시한다. 핵심·보완 원문의 최대 수와 발췌량은 profile로 고정한다. 예시로 핵심 5개·보완 5개를 사용할 수 있으나 이는 **설계 예시값이며 성능으로 검증된 최적값이 아니다.** 첫 실험 전에 표시 수·모델 입력 수·관계 예산을 확정한다. 모든 자료를 선택하는 응답은 한도 검증 후 우선순위를 다시 요구한다.

## 4. 두 하네스의 역할 수정

### 도메인 하네스

무거운 해석 검증에 앞서 “이 질문을 검토할 원문으로 필요한가”를 모델이 결정하도록 한다. 정확한 문언을 짧게 선택하고 핵심/보완 역할을 붙인다. 이해 관찰·비교 기준·예외 판단은 검색 방향을 개선하고 선택 이유를 검토하는 데 사용하지만, 해석 완성도를 출처 목록 발행의 필수 관문으로 삼지 않는다.

모델이 원칙만 골랐을 때 직접 연결된 정의·예외 후보를 작은 메뉴로 다시 보여준다. 모델이 보완 원문으로 채택하거나, 제외·보류 이유를 남기게 한다. 서버가 대신 채택하지 않는다. 동의어·개념 매핑은 그대로 법령 출처가 되지 않고, 연결된 실제 원문을 READ한 경우에 그 원문을 선택한다.

### 시스템 하네스

`발견 → READ → 모델에 제시 → 모델 tier 채택 → 출처 묶음 검증·저장 → 최종 화면`을 독립 경로로 둔다. `채택 → 법적 주장 작성·검토`는 별도 경로다. source tier 목록을 claim의 `source_ids`에서 역산하지 않는다.

문서명·조항·판본·발췌·열기 링크는 모델이 자유 생성하지 않는다. 선택한 ID와 span을 서버가 원문·메타데이터에 대조해 출력한다. 모델의 관련성 설명은 원문 발췌와 시각적으로 구분한다. 불확실한 요약에는 해석 미확정 상태를 붙이고, 정리 문장 생성이 실패해도 채택된 출처 카드는 남긴다.

무진전·예산 경계에서는 탐색 도구를 더 늘리지 않고, 예약된 한도 안에서 **이미 제시된 후보의 짧은 tier 선택 단계**를 수행한다. 빈 선택 또는 schema 오류가 계속되면 기존 유효한 모델 선택만 발행한다. 유효한 선택이 한 건도 없으면 `NO_SELECTION`을 기록한다. 회수 결과를 자동 Tier 1로 승격해 성공처럼 만들지 않는다.

이 때문에 현재 설계의 “READ 뒤 이해 관찰 필수”는 **가벼운 관련성 선택 또는 pending 사유**로 완화한다. 정확한 법률 결론을 못 내리는 모델에게 긴 이해 장부를 강제하면 이전 실험의 병목을 되풀이할 수 있다.

| 현재 경로 | 확인된 제약 | 제안 변경 |
|---|---|---|

`FinalSourceBundle` 제안 위치는 외부 계약이 허용하는 `assembly.term_agent.source_bundle`이며 내부 `schema_version`을 둔다. 필수 값은 선택 ID/revision, goal, tier, source generation/hash, 문서·좌표, exact span/hash, 검증된 열기 대상, 선택 이유, 해석 상태다. raw 후보 전체나 숨겨진 모델 프롬프트를 넣지 않는다. 화면용 위치와 링크도 권한 검사 대상이다.

과거 v3의 기본 동작은 유지하고 신규 v4 opt-in 내부 계약으로 연결한다. 작업 범위는 기존 adapter/session/StageRunner/publication/UI이며 독립 실행기나 두 번째 서빙 파이프라인을 만들지 않는다.

원장에는 모든 발견·READ·제시·선택 이력을 보존하되 화면의 출처 목록은 모델이 선택한 제한된 집합이다. 권한·판본 변경 시 해당 선택을 stale로 처리한다. 발행 직전 선택이 바뀌면 bundle을 다시 만들고, 원자적인 outbox에 최종 결과와 같은 hash로 보존한다. 모델 실패·재시작 시 임의 선택을 복원하지 않고 마지막 유효한 모델 결정을 복원한다.

### CM003의 예상 화면 구조

이는 실행 결과가 아닌 예시다. 조항을 제품에 미리 주입하지 않는다.

- 핵심 원문: 모델이 선택한 상장규정 제26조의 관련 호와, 필요하면 결론에 영향을 주는 시행세칙 제23조의 해당 범위.
- 보완 원문: 모델이 추가 선택한 정의·다른 연결 원문.
- 각 카드: 문서·판본·조항 → 실제 발췌 → 원문 열기 → 왜 골랐는지.
- 해석: 확인되지 않은 적용 판단은 미확정으로 표시. 정확한 출처가 있다는 이유로 잘못된 결론을 검증된 것으로 표시하지 않음.
- 미채택 후보: 기본 출처 목록 밖의 추가 탐색 메뉴. 전체를 인용 출처처럼 출력하지 않음.

## 6. 한 번의 통합 실험으로 비교한다

사용자가 말한 ‘한 번에’는 여러 변경을 묶은 후보를 **하나의 새 ADR·사전 동결 계획·한 번의 배치 실행**으로 평가하는 방식으로 반영한다. 하나의 질문·한 번의 모델 호출로 모든 가설을 입증한다는 뜻은 아니다. 원문만 주는 이해 진단을 선행 필수 실험으로 반복하지 않는다.

| arm | 구성 | 목적 |
|---|---|---|
| baseline | 현행 v3 경로를 정확한 코드·데이터 binding으로 동결 | 기존 선택·최종 출처 상태 |
| tiered-source | 작은 선택 schema + 핵심/보완 채택 + 관계 메뉴 + 반복 복구 + 독립 source bundle·화면 | 묶음 변경의 최종 출처 품질·비용 효과 |

두 arm은 같은 질문·공개 승인 범위·source/index 세대·Qwen model/FP8/thinking off·총 자원 상한으로 실행한다. 실험 중 결과를 보고 프롬프트·한도·tier 정책을 수정하지 않는다. batch 안에 필요한 반복을 사전에 넣을 수 있다. N문항·2 arm·r회 반복이면 제품 실행 수는 `N×2×r`이고 모델 물리 호출 수와 다르다. 앞선 Qwen 변동을 고려하면 반복을 미리 포함하는 것이 유용하지만 N/r/비용 상한은 실행 전에 실제 데이터와 예산으로 동결한다.

CM 실패 사례와 기존 CM 전체의 허용 범위를 재사용하되, 그 결과는 in-sample이다. 이미 결과를 본 FSC holdout은 이제 이 설계에 대해서도 회귀 자료이며 새로운 out-of-sample로 부르지 않는다. 승격까지 판단하려면 별도의 미사용 질문을 같은 배치의 분리된 평가군으로 사전 지정한다. 공개 scope 밖 결정 조문은 접근 불가로 기록하고, 접근 가능한 분모와 전체 분모를 구분한다.

### 주 지표

1. **최종 출처 recall@K:** 사용자에게 제공한 제한된 tier 출처 중 결정 원문이 얼마나 남았는가. 핵심 tier와 핵심+보완 합계를 각각 측정.
2. **최종 출처 precision@K / 관련성:** 제한된 목록 중 질문에 유용한 출처가 얼마나 있는가. gold에 없는 출처를 곧바로 무관하다고 판정하지 않고 별도 관련성 판단을 병기.
3. **원문 무결성:** 문서·판본·좌표·발췌·열기 대상 일치율. 잘못된 위치와 접근 불가 링크를 별도 기록.
4. **선택·보존:** presented→model_selected→source_bundle→rendered 단계의 손실, 빈 선택률, 모델 미채택 자료의 자동 포함 건수.
5. **자원:** 호출·token·초기화 포함 지연·출처 카드 수. 모든 원문을 넣어 recall을 올리는 후보를 통과시키지 않음.

법적 정답률·근거 없는 단정·해석 미확정 처리도 기록하되, 주 성공 기준은 출처 품질이다. 실제 UI에서 보이지 않는 감사 원장이나 Tier 3 후보를 최종 출처 recall에 넣지 않는다. article-level 회수와 항·호/span-level 정확성을 별도로 계산한다. 원문이 없는 질문에는 불필요한 출처를 억지로 고르지 않는지도 확인한다.

통과 조건은 동일 K·예산에서 필요한 출처의 회수/보존이 개선되고 관련성의 허용 회귀를 넘지 않으며, 원문 무결성·권한·모델 채택 계약을 위반하지 않는 것이다. 구체적인 목표 수치와 허용 회귀는 첫 모델 호출 전에 등록한다. 도구→채택→출처 bundle→outbox→renderer 계약 검사는 같은 배치의 선행 검증으로 묶되, 의미 품질과 혼동하지 않는다.

결과 해석은 통합 변경의 효과에 한정한다. 어떤 부품이 몇 퍼센트 기여했는지는 이 두 arm으로 분리할 수 없다. 새 실험 착수 시 기존 ADR reservation 확인·신규 선점·snapshot/register/freeze·final validate·graph 절차를 따른다. 실패한 실험도 완료 기록으로 보존하고, 제품 MAIN 승격·GENOS 배포는 별도 절차다.

## 7. 이번 변경의 확인 범위

이 문서만 추가했다. 이전 설계·자기 검토·BASELINE hash는 변경하지 않았다. 완료 실험의 보고·지표와 현재 source 선택/최종화/UI 코드를 읽었으며 제품 실행은 하지 않았다. 위 tier 구조와 통합 실험은 아직 구현·실행되지 않은 제안이다.

후속 문서 보완으로 아래 AS-IS → TO-BE 대조표와 구현 검증 양식을 추가했다. 이 추가 역시 문서 작업이며 구현·실험 완료를 뜻하지 않는다.

## 8. AS-IS → TO-BE 구현 대조표

AS-IS는 앞선 코드 진단과 완료 실험에서 관찰한 경로다. 모든 요청에서 반드시 같은 실패가 발생한다는 뜻은 아니다. TO-BE는 구현이 충족해야 하는 동작이며, 향후 판정은 아래 고정 ID를 기준으로 한다.

### 8.1 도메인 하네스 — 모델이 무엇을 판단하는가

### 8.3 최종 출력 불변 조건

`M`은 현재 revision에서 모델이 선택한 원문 범위 집합, `V`는 그중 판본·권한·원문 무결성을 통과한 집합, `F`는 최종 핵심·보완 출처 집합으로 정의한다. 집합 단위는 단순 문서명이 아니라 source binding과 정확 범위다.

- `F ⊆ V ⊆ M`: 회수했을 뿐 모델이 고르지 않은 자료가 최종 채택 출처에 들어가면 미충족이다.
- 한도 안의 유효한 선택은 tier 표시 상태와 함께 보존한다. 한도·중복·stale 등으로 빠지면 항목별 이유가 있어야 한다. 조용히 사라지면 미충족이다.
- 핵심과 보완에 같은 원문 범위가 중복되면 한 번만 표시하고 선택 이력은 보존한다. 실제 다른 범위·판본을 같은 출처처럼 합치지 않는다.
- `claims=[]`는 `F=[]`의 조건이 아니다. 요약·법적 주장 실패만으로 F를 비우면 미충족이다.
- Tier 3과 감사 원장의 후보는 F가 아니다. 모델에 제시한 범위, 사용자 화면에 표시한 범위, 이어보기 안의 범위를 구분한다.
- 출처의 실재성·위치 일치가 법적 해석의 정답을 뜻하지 않는다. 해석 미확정 상태를 자동으로 REVIEWED로 바꾸면 미충족이다.

## 9. 구현 후 실행할 대조 시나리오

아래는 아직 실행하지 않은 검증 설계다. 계약 검사는 모의 응답으로 결정론적인 동작을 확인하고, 실제 Qwen 실험은 관련 원문을 스스로 고르는 능력을 별도로 확인한다. 모의 응답에서 채택을 주입한 성공을 모델의 선택 성공으로 보고하지 않는다.

| 시나리오 ID | 입력·조건 | TO-BE에서 기대하는 결과 | 요구 ID |
|---|---|---|---|
| T01 해석 미완료 | 모델이 정확한 원문을 CORE로 선택하고 해석은 UNCERTAIN. 법적 claim은 없음 | 핵심 카드와 정확한 위치·발췌·원문 열기가 남고 해석 미확정 표시 | D01·D02·S04·S05·S08 |
| T02 원칙과 예외 | 원칙 원문과 직접 연결된 예외 원문을 제시 | 모델이 둘을 CORE로 고를 수 있음. 실제 Qwen이 하나를 놓치면 모델 품질 실패로 기록하며 서버가 대신 추가하지 않음 | D03·D04·S02 |
| T03 많은 후보 | 표시 한도보다 많은 후보를 회수하고 모델은 일부만 핵심/보완으로 선택 | 선택 자료만 제한된 출처 목록에 표시. 나머지는 후보로 보존, 기본 화면에 원문 전체 투입 금지 | D02·S01·S06 |
| T04 미제시·잘못된 범위 | 모델이 보지 않은 span 또는 다른 호의 span을 채택 제안 | 유효 채택으로 기록하지 않고 정확한 READ/제시·재선택 또는 보류로 연결 | D02·S04 |
| T05 같은 조회 반복 | 이미 제시한 원문/관계를 동일 상태에서 다시 요청 | 한도 있는 복구·tier 선택으로 전환. 계속 실패하면 NO_SELECTION 또는 기존 선택 유지 | D05·S03 |
| T06 요약 실패 | 유효한 핵심·보완 선택 이후 compose 오류, 빈 답변 또는 해석 검토 실패 | 출처 bundle과 화면은 유지. 검토되지 않은 법적 주장은 승인 상태로 발행하지 않음 | D01·S05·S08 |

### CM003 AS-IS → TO-BE 사례 기록

AS-IS 관측은 ADR-0478의 기록이다. 필요한 두 원문을 모두 제시했으나 상장규정만 선택했고, 시행세칙은 compose/review 및 최종 출처에서 빠졌다.

```text
AS-IS 실제 기록:
상장규정 제26조 + 시행세칙 제23조를 READ/제시
→ 상장규정만 모델 채택
→ 시행세칙이 작성·검토 입력에서 제외
→ 최종 필요한 출처 1/2

TO-BE 검증 시나리오:
두 원문과 연결 이유를 제한된 후보 묶음으로 제시
→ 모델이 핵심/보완/pending/rejected를 선택
→ 두 원문을 핵심으로 선택했다면 정확한 관련 범위를 서버 검증
→ 적용 결론이 미확정이거나 요약이 실패해도 두 출처 카드 유지
```

TO-BE에서 “모델이 두 원문을 선택했다면 보존되는가”는 계약 검증이고, “모델이 실제로 두 원문을 선택하는가”는 Qwen 품질 평가다. 후자가 실패하면 출처 품질 목표 미달로 남긴다. 이 사례의 조항 ID·gold를 실제 제품 입력에 사전 주입해 회수 성공으로 집계하지 않는다.

## 10. 구현 완료 판정과 기록 양식

### 10.1 판정 규칙

- **미검증:** 증거가 없거나 실행하지 않음. 현재 모든 항목의 상태.
- **충족:** 해당 TO-BE 동작이 코드와 요구된 실행·저장·화면 증거로 확인되고 반례가 없음.
- **부분 충족:** 일부 소비자·실패 분기·환경만 확인했거나, 핵심 연결 일부가 남음. 빠진 범위를 적는다.
- **미충족:** 실행 반례가 있거나 요구 동작과 다른 구현을 확인함. 파일이 존재한다는 이유로 충족 처리하지 않는다.

설계대로 연결되었는지와 실험에서 출처 품질이 좋아졌는지는 별도 판정한다. 계약 검증이 충족이어도 Qwen이 필요한 원문을 고르지 못하면 품질 목표는 미달이다. 로컬 renderer 확인을 GENOS 현장 검증 완료로 표시하지 않는다.

### 10.2 검증 기록 헤더

구현 후 별도 `IMPLEMENTATION_VERIFICATION_<실행일>.md`를 만들어 아래 내용을 채운다. 이름은 제안이며 지금 생성·실행된 검증 결과가 아니다.

```text
대상 설계: SOURCE_TIERS_REVISION.md / SHA-256
검증 시각·검증자·검증 환경:
코드 revision + dirty 변경 manifest/hash:
실제 API/CLI 진입점·명령·선택 implementation/profile:
source/index/glossary generation·hash·scope:
schema/domain/profile/model binding·hash:
실험 ADR/arm/run/질문 집합·gold hash(모델 실험일 때):
tier별 표시 한도·발췌 한도·모델/도구/시간 예산:
계약 검증 결과 / 출처 품질 결과 / GENOS 현장 결과:
남은 미확인·반례·영향 범위·후속 조치:
```

설계나 통과 기준이 바뀌면 변경 이력을 남기고 새 hash에 결속한다. 실행 결과를 본 뒤 원래 기준을 고쳐 해당 run을 통과시키지 않는다. 기존 완료 실험은 그대로 보존한다.
