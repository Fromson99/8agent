# 원문 탐색·선택 v4의 구조적 설계 검토

2026-09-21 · Codex 자체 검토. [설계 타당성 검토 스킬](/mnt/c/Users/Jin/.codex/skills/design-reality-review/SKILL.md)을 사용했다. 별도 에이전트·외부 전문가 검토가 아니다.

**판정: 수정 필요.** 관련 원문을 찾는 판단과 프로토콜·표시·검토 상태를 맞추는 작업이 너무 강하게 결합되어 있다. 개별 오류를 재시도로 처리해도, 같은 구조에서는 불필요한 실패 조건과 호출 부담이 남는다. 다만 개선 폭·최적 예산·모델 능력의 한계는 이 기록만으로 추정하지 않는다.

검토 대상은 [출처 tier 수정 설계](../DOMAIN_SYSTEM_HARNESS_REDESIGN_20260921/SOURCE_TIERS_REVISION.md), [구현 검증서](../DOMAIN_SYSTEM_HARNESS_REDESIGN_20260921/IMPLEMENTATION_VERIFICATION_20260921.md), ADR-0488에 연결된 v4 코드다. 목표는 모델이 관련 원문을 선택하면 해석 미확정이어도 출처를 보존하는 것이다. **이 목표 자체와 원문 무결성·권한 검증은 유지할 가치가 있다.** 아래는 그 목표를 달성하는 계약·제어·검증 방식의 문제다.

경로는 기존 [엣지케이스 원장](README.md)의 `RequestContext → Repository/Sources/ModelGateway → investigate → select → assemble → answer_and_review → publication.prepare/export`를 따른다. 이번 검토에서는 저장 기록과 코드만 읽었고 모델 실행·재채점·제품 변경은 하지 않았다. 전체 MAIN의 입력·용어집·피드백을 전수 검토한 결과가 아니다.

## 발견사항

모든 항목의 문서 반영 상태는 **이 검토서에 기록**, 구현·검증 해결 상태는 **이번 작업에서 수정·검증하지 않음**이다. 이미 원 설계·검증서에 제약으로 적힌 내용은 새로운 문서 오류로 집계하지 않고 구현 선행 조건으로 구분한다.

## 정상 상황에서도 남는 문제

첫째, 모델이 질문에 맞는 조를 찾았어도 표시 범위와 검토 상태를 동시에 맞춰야 처음으로 선택이 저장된다. 이는 드문 입력을 처리하는 문제에 앞서 기본 작업의 난도를 높인 설계다.

둘째, 관련 조 전체를 선택하는 것과 그 안의 핵심 구절을 강조하는 것은 다른 작업이다. 현재는 작은 span을 골라야 출처 카드가 생기므로, 세부 강조를 못 하면 관련 조 선택도 잃는다. 사용자가 원하는 최소 성과인 ‘관련 조와 정확한 원문 접근’이 독립적으로 보존되어야 한다.

셋째, 도구의 실행 가능성과 지금 실행할 필요성은 다르다. 지금도 프롬프트·후보 read_action·관계 guidance는 있다. 부족한 것은 도구 설명의 총량보다 **현재 무엇이 미확인이고, 어떤 행동이 그 공백을 줄이는지**를 보여주는 상태와 제어다. 더 긴 가이드를 추가하는 것만으로 해결됐다고 보지 않는다.

넷째, 출처 선택 성공을 답변 성공으로 자동 변환하면 안 되지만, 답변 요청을 받고 출처만 고른 뒤 멈추는 것도 성공은 아니다. 출처 전용 결과와 법적 답변 목표를 구분하고, 어느 목표를 어디까지 완료했는지 반환해야 한다. bundle 독립 보존은 이미 구현된 장점이고, 이 장점을 유지하면서 제어 계약을 정리해야 한다.

## 보존할 설계와 수정 우선순위

원문 hash·판본·권한 검사, 모델이 선택한 출처와 단순 후보의 구분, 해석 미확정 출처 보존, 감사 이력·멱등 게시 자체를 없앨 이유는 없다. 문제는 이 보호를 적용하는 책임과 상태 경계다.

우선 **D01/D02/D06의 ‘조 선택은 단순하게, 서버가 좌표·표시·저장 책임’**을 정하고, **D03/D05의 ‘요청 목표·미완료 작업·종료 조건’**을 연결해야 한다. 그 다음 D04의 탐색 우선순위와 D07/D08의 의미·게시 검증을 같은 사용자 경로에서 확인한다. 개별 재시도 횟수나 입력 한도를 늘리는 것만으로 구조적 해결을 선언하지 않는다.

검토 대상 해시는 [design-review-binding.json](design-review-binding.json)에 저장했다. 기존 실험·설계·제품 파일은 수정하지 않았다. 외부 레퍼런스를 이용한 성능 주장은 하지 않았으며 웹 검색·현장 연결·새 모델 호출은 수행하지 않았다.
