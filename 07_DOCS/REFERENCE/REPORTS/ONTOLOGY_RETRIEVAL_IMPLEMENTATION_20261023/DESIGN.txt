사용 중 축적한 판단을 재사용하는 근거 탐색·답변 개선 설계
작성일: 2026-10-23
상태: 코드·저장된 실행 기록을 읽고 작성한 제안. 구현·신규 모델 실험·MAIN 반영·GENOS 배포 없음.
수정 R2: 사용자 정정 반영 — 의미 지식의 주된 생산자는 문서 반입 시 전수 추출이 아니라 실제 사용 중의 조사·판단·정정이다.
R1의 “문서를 넣을 때 의미 관계를 미리 만든다”는 전제를 수정한다. 아래 과거 실험 관측은 변경하지 않는다.

1. 만들려는 기능과 주장

목표는 실제 사용에서 얻은 판단·이유·근거·적용 조건·정정 경험을 축적하고, 다음 조사에서 필요한 부분을 재사용하는 것이다.
이 프로젝트에서 사용자가 말하는 “판단의 모음”은 이 축적 지식을 가리킨다. 원시 답변 로그 전체를 법률 정답이나 온톨로지로 취급하지 않는다.
개념 종류·관계 의미·범위는 공통 틀로 두되, 실제 법률 개념의 세부 관계와 판단 내용은 사용하면서 발견하고 원문에 연결한다.
문서 반입은 원문·판본·구조·명시 정의/참조·검색 기반을 준비한다. 모든 조건·예외·적용 판단을 미리 추출해야 사용 가능한 구조로 만들지 않는다.
에이전트는 현재 질문과 원문에 관련된 과거 판단을 참고하고, 이번 원문·조건에 맞는지 다시 검토한다.
저장된 설명을 길게 프롬프트에 추가하는 것만으로 속도·정확도 향상을 주장하지 않는다.

설계 설명에 쓸 문장:
“사용 중 확인한 판단·근거·정정 경험을 원문에 연결해 축적하고, 이후 관련 질문에서 재사용해 반복 탐색과 같은 누락의 재발을 줄이는 구조다.”
이는 구현 목표다. “응답시간 단축과 정확도 향상을 입증했다”는 문장은 아래 검증을 통과한 범위에서만 사용한다.

2. 확인한 현재 실행 상태

진입점: service.py의 RAG_ASK → /v1/rag/ask → semantic_runtime.app의 요청 분기 → 기존 legal_agent 실행기.
작업 코드에는 request_entry.py와 UnifiedRag.open에서 knowledge_bridge.prepare를 호출하는 연결이 있다.
prepare → Service.plan → Repository.candidates → planning.assemble로 안내 후보를 조립한다.
UnifiedExecution.invoke의 augment가 legal_review_guidance를 기존 모델 입력에 추가한다.
현재 후보 조회는 등록 lookup_terms의 INSTR 일치, object_id 순서, 기본 6개 한도다. 질문 목적에 따른 의미 선별 완료가 아니다.
현재 augment는 계획의 항목·steps를 직렬화 길이 한도까지 추가한다. 본문과 같은 항목의 중복을 제거하는 질문별 근거 묶음이 아니다.

선택 포인터: MAIN102 / selected-connection-coverage-20261022-r1.
릴리스 manifest SHA256: b7e29aac5121f3d97c7bf38cca0e81ddabc80694b53389b971fb6ef82f850e4d.
작업 코드와 선택 릴리스 모두 legal_knowledge.consumer_mode=off, management_enabled=false.
knowledge_bridge.py는 작업 코드·선택 릴리스 해시가 같다. unit_relations.py와 PIPELINE.json 전체는 서로 다르다.
따라서 작업 코드의 모든 동작을 선택 MAIN의 동작으로 취급하지 않는다. 이번에 서비스/현장 모델을 새로 실행하지 않았다.
ADR1019는 MAIN100 계보의 격리 후보이며, 그 snapshot을 MAIN102 이후 작업 코드에 덮어쓰지 않는다.

기존 축적 경로도 있다. action-memory build는 완료 요청 journal의 조사 이유·읽은 원문·선별 이유에서 episode와 조사 목적/GUIDES_TO 후보를 만든다.
LEGAL_LLM_WIKI.md에는 이 경험의 불변 기록·개념 페이지·연결 해제/중단 경로가 기록돼 있다.
이것은 법률 적용 판단 전체를 원문 중심으로 재사용하는 온라인 순환이 완성됐다는 뜻이 아니다. 관련 문서의 과거 릴리스 번호는 당시 기록이다.
이번에 기존 예약 작업을 실행·변경하거나 자동 축적이 현재 동작 중이라고 확인하지 않았다.

3. 실제 문제 → 제안 변경 → 확인할 결과

문제 A: 같은 원문 묶음의 항목을 넓게 전달한다.
관측 O1: ADR1019 CM010 최초 판단에 근거 항목 71개, 필수 검토 11개가 들어갔다. 최종 모델은 9개를 비적용으로 표시했다.
원인 확인: 원문 연결 항목을 질문별로 좁히기 전에 필수 처리 대상으로 만든다. 불필요한 입력이 실패를 유발한 정도는 미측정이다.
변경: 기존 SELECT/연결 선택 단계에 목적·범위가 있는 관계 후보를 제공하고 필요한 항목만 선택한다.
목표: “보유비율 산입 여부”를 물을 때 “보유기간 연장”을 자동 필수 항목으로 삼지 않는다. 미선택은 미검토로 보존한다.
검사: 같은 원문에 대해 서로 다른 목적의 질문을 넣고, 선택 이유·누락 근거·입력 길이·최종 정확도를 함께 대조한다.

문제 B: 같은 지식이 여러 입력 필드에 반복된다.
관측 O2: ADR1019 CM007 필수 메모 5개 모두 legal_review_guidance와 required_review_items에 중복됐다.
변경: 선택 항목은 하나의 목록에서만 설명하고, 나머지는 ID 참조로 연결한다. 원문은 중복 제거한 근거 목록에 둔다.
목표: 동일 메모의 중복 전달을 없애되, 실제 원문의 조건·예외·상위 문맥을 잘라내지 않는다.
검사: 실제 전송 payload의 항목·원문 일치와 중복 여부를 확인한다. 글자 수 감소를 정확도 개선으로 계산하지 않는다.

문제 C: 항목 연결 실패가 다른 설명을 지운다.
관측 O3: ADR1019 CM007 설명 충족이 기준 3/5에서 후보 0/5로 하락했다. 근거 연결 오류가 전체 판단 복구 경로에 결합됐다.
변경: 원문 검증을 통과한 claims 보존과 필수 항목 연결 검증을 분리한다. 실패한 항목 연결은 미확인으로 남긴다.
목표: 하나의 잘못된 항목 연결 때문에 관계없는 정상 claims가 사라지지 않는다.
검사: 유효 claim과 잘못된 항목 연결이 섞인 실제 API 입력, 재개·중복·예산 소진·표시/저장 소비자를 검사한다.
주의: 원문/권한/해시 자체가 무효인 claim을 유지한다는 뜻이 아니다. 같은 실패를 이유로 전체 모델 재호출을 추가하지 않는다.

문제 D: 관계 저장이 매번의 탐색을 얼마나 줄이는지 분리해 측정하지 못했다.
관측 O4: ADR0987은 평균 시간 141.13초→70.49초, 읽은 조항 합계 57→17, 모델 호출 27→23이었다.
그러나 핵심 항목 전부 충족은 양쪽 0/4, 항목 충족은 8/18→7/18이었다. 소표본 단회·준비시간·공급자 지연 차이가 있다.
변경: 관계 조회가 기존 탐색 왕복을 대체하게 하고, 기존 원문 조회와 같은 읽기·권한·상태 계약을 사용한다.
목표: 품질이 유지된 답변에서 실제 탐색 호출과 시간을 줄인다. 실패가 빨리 끝난 것을 속도 향상으로 세지 않는다.

4. 사용 중 판단을 축적하는 생산 경로와 저장 정보

운영의 저장 책임은 Dataiku Gold의 원문·구조화 지식과 Agent의 질의·판단·로그로 나눈다.
아래는 논리 계약 제안이다. 물리 테이블명·DDL·메타 승인·Oracle 현장 연결 완료를 뜻하지 않는다.

원문 기준 키: 문서 판본 + 조항/항/호/span + 개념 ID.
개념: 이름·정의·별칭·유형·적용 범위·근거. 같은 이름의 서로 다른 법률 개념을 분리한다.
관계: 출발/대상, 방향, 관계 종류, 실제 근거 span, 검토 상태, revision, 유효 기간.
사용 중 발견해 쌓을 관계 범위: 정의를 확인한 원문, 조건을 구체화한 원문, 예외 원문, 실제 조사에서 확인한 준용·위임 범위.
명시 인용과 모델이 제안한 의미 관계를 구분한다. 추출 성공을 승인으로 바꾸지 않는다.
각 관계에는 무슨 내용을 확인하는 연결인지와 정확한 대상 범위를 둔다. 관련 있다는 이유만으로 법률 적용을 확정하지 않는다.
조건·수치가 있으면 원문별 논리 관계·단위·기산점·적용 범위를 유지한다. 누락된 조건을 false로 채우지 않는다.
역색인: 원문 anchor → 관계/검토 항목, 개념·별칭·질문 목적 → 관계 후보.
질문은 발견 이력으로 저장한다. 질문 ID·과거 답변을 지식의 중심 키로 사용하지 않는다.

생산 순서:
  원문 반입·검색 준비 → 실제 질문 조사 → 원문을 읽고 내린 판단/미확인 → 실행 journal에 즉시 보존
  → 재사용할 판단 단위 추출·중복/충돌 확인 → 원문에 연결한 지식 후보 → 검토 상태별 게시·역색인 → 다음 질문에서 재검토.
응답 경로의 모델을 추가로 호출해 기억을 정리하는 것을 필수로 하지 않는다. 기존 구조화된 claims·근거·선택 이유를 먼저 재사용한다.
추가 의미 정리가 필요하면 기존 피드백 후처리 경로의 작은 배치에서 수행한다. 별도 실행 예산·기록을 두며 새 스케줄을 만든다는 뜻이 아니다.

판단 기록의 최소 내용:
  무엇을 판단했는지 / 어떤 원문을 읽었는지 / 내린 의견과 명시한 이유 / 적용 조건·예외·범위
  / 확보하지 못한 자료·충돌 / 사용자가 정정한 내용 / 원문·지식 revision / 발견 실행 ID / 검토 상태.
특정 사건의 회사·날짜·계약 등은 Agent 이력에 남긴다. 공통 개념의 정의나 다른 질문의 사실로 옮기지 않는다.
재사용 지식의 중심 키는 여전히 원문 판본·위치·개념이다. 질문은 발견 이력이며 여러 질문이 같은 원문 판단을 보완할 수 있다.

상태를 구분한다:
  관측/후보: 모델이 실제로 제시한 의견. 다음 조사에 단서로 제공할 수 있으나 법률 결론을 강제하지 않는다.
  검토됨: 원문·조건·범위 및 검토 근거를 기록한 지식. 현재 질문의 적용성 판단은 계속 필요하다.
  이견/철회: 정정·충돌·개정으로 재사용을 제한한 지식. 이유와 과거 기록을 남기고 정상 후보에 자동 복귀시키지 않는다.
원문 일치 검사나 사용자 동의만으로 법률 의미의 정확성을 자동 인증하지 않는다. 같은 판단을 반복했다고 확신을 자동 높이지 않는다.
실패·부분 답변도 Agent에 보존한다. 원문에 결속한 유효 부분만 별도 후보로 만들며, 실패한 실행 전체를 성공 경험으로 바꾸지 않는다.

첫 질문에서는 충분한 축적 지식이 없으므로 기존 RAG로 조사한다. 자주 사용하는 원문·개념부터 지식이 늘어난다.
저장만으로 모델 가중치가 학습되는 것은 아니다. 지식 저장소를 조회해 현재 판단에 활용하는 방식이다.
새 역색인은 누적된 원문 연결 지식 revision에서 증분 구축한다. 원문 전체 재파싱을 반복하지 않는다.

5. 질문 처리 흐름

① 기존 질문 해석에서 목적·대상·명시한 범위·기준 시점과 제공된 사실을 읽는다. 별도 필수 LLM 호출은 만들지 않는다.
② 기존 용어/본문 검색과 지식 후보 조회로 진입한다. 일반 검색으로 먼저 찾은 원문에서도 anchor 역색인을 조회한다.
③ 기존 SELECT/관계 선택 호출에서 후보의 근거·범위·연결 의미를 보고 이번 질문에 필요한 관계를 선택한다.
   시스템의 사전 필터는 권한·판본·철회·중복 등 확정 가능한 값에 적용한다. 법률적 관련성·충분성은 모델이 원문을 보고 판단한다.
   모든 후보마다 비적용 이유를 생성하도록 강제하지 않는다. 선택/명시 배제만 이유를 남기고 나머지는 미검토 상태다.
④ 선택한 관계의 대상 원문을 기존 reader로 모아 읽는다. 이미 읽은 같은 판본·span은 요청 내에서 재사용한다.
   DB에서는 필요한 행만 조회한다. 서빙 전체 복제·영속 캐시를 추가하지 않는다. 일괄 조회는 거대한 동시 메모리 로딩을 뜻하지 않는다.
⑤ 실제 원문 + 선택한 검토 항목 + 필요한 미확인만 기존 ASSESS에 전달한다.
   간단한 입력 형태: 현재 질문 / 근거 목록 / 관련 항목 목록(목적, 근거 ID, 필요한 설명) / 이미 확인한 사항.
   원문에 연결된 모든 메모, 전체 그래프, 관리용 해시·게시 이력을 모델의 법률 판단 입력에 반복하지 않는다.
   해시·권한·상태 검증은 서버에서 유지한다. 모델에 ID를 제공하는 계약도 유지한다.
⑥ 답변은 원문으로 판단한다. 선택 항목의 설명·비적용·미확인을 기록하고 인용을 검증한다.
   검토 항목 표시와 의미 정답을 별도로 평가한다. 미확인만으로 반복 호출하거나 정상 설명을 삭제하지 않는다.
⑦ 이번 판단·이유·근거·조건·미확인·정정은 Agent 이력에 남긴다. 재사용 가능한 부분은 원문에 결속한 Gold 지식 후보로 보완한다.
   과거 판단의 어느 부분을 재사용/수정/제외했는지도 기록한다. 자동 정답 승격은 하지 않는다.

정상 예: “보유기간 연장 조건” → 해당 개념/원문 → 조건 구체화 관계 → 관련 시행세칙 원문 → 연장 조건 설명.
위 예는 처리 방식의 설명이며 새로운 법률 해석·속도 실측이 아니다.
다른 예: 같은 조문에서 “보유비율 산입 여부”를 묻는 경우에는 제외 범위 관계를 선택한다. 연장 사유를 필수 설명으로 추가하지 않는다.
시간 순서 예: 첫 조사에서 A조와 B세칙을 함께 읽어야 한다는 판단을 발견하고 원문에 기록한다.
다음 관련 질문에서는 이 기록으로 근거 위치에 빨리 도달한다. 질문의 범위·판본이 다르면 과거 결론을 복사하지 않는다.
이후 “조건 하나를 놓쳤다”는 정정이 들어오면 기존 판단을 보존하면서 새 revision에 누락과 근거를 반영한다.

7. 실패·복구 계약

적중 없음/관련성 낮음: 기존 원문 검색으로 이어간다. 지식이 없다는 이유로 원문 답변을 막지 않는다.
판단 정리/저장 실패: 이미 완성한 응답을 다른 결과로 바꾸지 않는다. 기존 실행 ID를 참조한 미처리 정리 상태와 원인을 기록한다.
  재처리는 원래 기록·정리 버전·누적 작업 예산을 사용하고 같은 지식을 중복 생성하지 않는다. 실패한 게시를 게시 완료로 기록하지 않는다.
이전 판단과 새 판단의 충돌: 서로 다른 조건인지, 원문 개정인지, 판단 오류인지 근거를 보존해 검토한다. 최신 의견만 남겨 덮어쓰지 않는다.
관계 선택 불확실: 후보와 이유를 보존하고 원문으로 판단한다. 불확실성 자체를 중단 조건으로 쓰지 않는다.
관계 조회 장애: knowledge_bridge/조회 어댑터가 실패를 기록하고 기존 조사 실행기로 복귀한다. 같은 조회를 각 계층에서 재시도하지 않는다.
구판·권한·해시 불일치: 해당 지식 경로를 차단한다. 현재 허용 원문을 별도로 조회할 수 있으나 무효 근거를 정상 표시하지 않는다.
조건 충돌: 양쪽 원문·범위를 보존하고 해석 차이로 설명한다. 코드가 임의로 한 법률 결론을 고르지 않는다.
항목-claim 연결 오류: 무효 연결만 격리하고 다른 원문 검증 통과 claims를 보존한다. 잘못된 근거 ID를 비슷한 ID로 고치지 않는다.
예산 소진: 기존 deadline·누적 사용량을 유지하고 확인된 범위의 답변과 미확인을 반환한다. 원래 요청을 새 예산으로 재시작하지 않는다.
중복/재개: 기존 request·principal·원문/지식 revision 결속을 사용한다. 새 revision이나 권한 변경은 다시 검사한다.
발행 실패: 기존 멱등 발행과 미완료 상태를 따른다. 전송한 일부 내용에 다른 생성 결과를 이어 붙이지 않는다.

8. 속도·비용·정확도 가설

속도 개선은 그래프 이름 때문에 생기는 것이 아니라, 기존의 검색·재질문·원문 재읽기를 실제로 줄여야 발생한다.
관계 조회와 추가 선별 비용이 줄인 탐색 비용보다 크면 더 느려진다. 지식 미적중 요청도 비용에 포함한다.
효과가 생기는 주된 구간은 축적된 판단이 관련 있는 후속 질문이다. 최초 질문·생소한 주제까지 자동으로 빨라진다고 주장하지 않는다.
지식의 양이 늘수록 항상 개선되는 것도 아니다. 잘못된 판단·구판·중복 누적은 검색과 정확도를 악화시킬 수 있다.

F1: 요청 평균 순 시간 절감(초/요청)
  = p × S - L - M - (1-p) × F
  p: 검증된 연결이 유용하게 재사용되는 요청 비율.
  S: 적중 요청에서 절약한 기존 탐색·입력 처리 시간(초).
  L: 모든 요청의 관계 조회·조립 비용(초).
  M: 추가된 모델 선별·입력 처리 비용(초; 기존 호출에 합쳐도 토큰 비용은 0이 아님).
  F: 미적중/오적중 요청의 평균 추가 복귀 비용(초).
  손익분기: p×S = L+M+(1-p)×F. p가 낮아지면 이점이 줄고 복귀 비용이 커진다.
  현재 p/S/L/M/F는 비교 가능한 실측이 없어 미산정이다. 예측 초·배수·개선율을 제시하지 않는다.

F2: 요청당 평균 지식 구축·관리 비용 = (초기 저장·색인 준비 비용 + 사용 중 판단 정리·검토·갱신 비용) / 해당 기간 요청 수.
  온라인 비용 절감과 위 오프라인 비용을 함께 보고한다. 자동 추출·사람 검토 비용을 무료로 가정하지 않는다.

정확도 가설: 관련 조건·예외·참조 원문을 놓치는 오류가 줄어든다. 잘못된 관계를 저장하면 오히려 체계적으로 틀릴 수 있다.
원문 회수율, 최종 핵심 내용 충족, 적용범위/수치 오류, 잘못된 인용, 모순을 각각 평가한다.
선택된 체크리스트를 다 표시했다는 사실은 정답률이 아니다. LLM 해석 오류와 질문 범위 선별 오류는 남는다.

9. 검증·도입 순서

첫 단계: 현행 개발 경로에서 항목 연결 실패의 전체 claims 소실을 분리하고 정상·부분 실패·재개·권한·해시·표시 계약을 검사한다.
둘째 단계: 한 업무 영역의 실제 조사·판단·정정 기록에서 원문 연결 후보와 anchor 역색인을 만들고, 다음 질문의 선택·읽기·판단 소비자까지 연결한다.
셋째 단계: 신규 ADR을 선점한 뒤 모델 비교 조건·코드·데이터·질문·채점 기준을 호출 전에 동결한다. 이 문서는 실험 실행이 아니다.
  A: 공통 버그 수정·출력 정리만 적용한 기존 RAG. B: 같은 코드·모델·원문·예산에 관계 조회를 추가한 RAG.
  프롬프트 축약·복구 수정 자체의 효과를 온톨로지 효과로 계산하지 않도록 공통 변경을 동일하게 적용한다.
  질문 목적 선별이 기존 호출에서 이루어지는지, 실제 제거한 탐색 왕복이 무엇인지 기록한다.
  지식 구축에 쓰지 않은 질문, 같은 원문의 다른 목적, 미적중·오적중·개정·권한 변경을 포함한다.
  같은 원문의 의역 질문을 독립 사례처럼 부풀리지 않는다. 알려진 원문 재사용과 새로운 원문·관계 일반화를 별도로 집계한다.
  시간순으로 축적 구간과 후속 평가 구간을 나눈다. 축적 구간의 지식을 동결하고 이후 질문으로 재사용 효과를 평가한다.
  평가 정답·채점 피드백을 같은 비교 run의 지식에 섞지 않는다. 온라인 축적 자체를 시험하려면 갱신 순서까지 호출 전에 고정한 별도 ADR로 다룬다.
  첫 사용과 축적 후 사용, 반복 오류 정정 전후, 지식 미적중을 나누어 관측한다. 유리한 반복 질문만 전체 성능으로 보고하지 않는다.
  정답·필수 근거는 원문으로 사전 검토하고 제품 입력과 분리한다. 인샘플과 미사용 평가를 구분한다.
  시간은 준비 시간·모델 호출·DB 조회·재시도·전체 완료를 나누고, 실패율과 성공 답변의 지연을 함께 보고한다.
  평균/p50/p95·토큰·호출·원문 읽기 수를 측정하되 적은 표본의 꼬리 지연을 일반 성능으로 인증하지 않는다.
  관측할 합격 조건: 유효 설명 보존, 출처/권한/해시 불변, 필수 근거 누락 감소, 의미 품질 유지 또는 개선, 측정된 순 시간 절감.
  품질 허용 회귀·지연 목표·표본 수의 구체 값은 실험 실행 전 정하고 동결한다. 현재 수치 목표는 미산정이다.
넷째 단계: 기준을 충족한 후보만 현행 MAIN 변경과 통합해 동일 코드로 검증·승격·포인터·실제 서비스 binding을 확인한다.
  off/이전 검증 릴리스로 복원하고 지식 revision·실험 실패 이력을 보존한다. GENOS 반입·배포·내부 모델 검증은 별도다.
