# 외규 API 및 웹 문서 수집 구축 요청서

수신: 뭉타 구축 담당자 · 작성 기준: 2026년 10월 23일 · 버전: 1.0

## 1. 요청 목적과 범위

당사 AIDP에서 법령·감독규정·거래소 및 금융투자협회 규정을 정기적으로 수집하고, 원문과 판본 정보를 보존한 뒤 기존 구조화·색인·Oracle 적재 흐름에 연결한다. 뭉타의 기본 납품 범위는 수집기, 원본 파일, 문서·첨부 메타데이터, 배치·재개·실패 기록, AIDP 인계 인터페이스다. 조문 의미 해석·온톨로지 생성은 기존 후속 단계의 책임이며 수집기에서 임의로 작성하지 않는다.

이번 자동 수집 대상은 지정된 기본 문서 68종이다. 각 규정에 연결된 별표·서식·부칙·개정문·신구대비표는 기본 문서의 관련 자산으로 수집한다. 68종은 다운로드 파일 수나 전체 운영 RAG 문서 수가 아니다. 최신 판본에 따라 첨부 개수는 달라진다.

| 구분 | 기본 문서 수 | 수집 방식·요청 형식 |
| --- | --- | --- |
| A 법령 | 37 | 법제처 공식 API / XML 본문 + 원본 첨부 |
| B 행정규칙 | 12 | 법제처 공식 API / XML 본문 + 원본 첨부 |
| C 거래소 규정 | 9 | 웹 HTTP 조회 / 전체 HTML + 전문·첨부 원본 |
| D 금투협 규정 | 5 | 웹 HTTP 조회 / 전체 HTML + 전문·첨부 원본 |
| E 거래소 공개 별첨 | 5 | 게시판 변경 확인 + 첨부 원본 다운로드 |
| 자동 수집 합계 | 68 | API 49 + 웹 19 |
| M 별도 수동 반입 | 10 | 현업 제공 파일; 자동 수집 범위에서 제외 |
| X 이번 제외 | 2 | 금감원 기업공시서식 작성기준·별지서식 |
| 원래 지정 목록 | 80 | 68 + 10 + 2; 원본·기존 이력 보존 |

문서의 “요청”은 구현 요구사항, “제안”은 협의할 기본 설정, “확인”은 공식 명세 또는 기존 코드·보관 자료의 관측을 뜻한다. 운영 반영·사이트별 수집 허용·전체 최신 원문 확보를 완료했다는 의미는 아니다. API 주소는 공식 원천 주소이며 사내 중계 주소와 구분한다.

## 3. API 인증과 요청 명세

### 3.1 필요한 인증과 설정

법제처 OC는 공식 공동활용 사이트에서 신청·관리하는 API 인증값이다. 현재 공식 화면은 사용자 이메일과 OC를 별도 항목으로 표시하므로 이메일 앞부분이나 예제 test를 운영 인증값으로 추정하지 않는다. 공동활용 신청 시 대상 서비스·활용 목적·시스템과 서버 IP를 기재하고, 실제 외부 호출 주체가 중계서버라면 해당 출구 IP와 승인 범위를 담당자가 확인한다. | 사내 API 중계 | 중계 URL·포트·TLS 도메인·인증 방식·허용 원천·쿼리 전달 규약 | 중계 담당자; 토큰·인증서가 필요한지는 계약 확인 |
| 거래소 웹 | 세션 쿠키·페이지 CSRF·다운로드용 토큰 | 수집기가 정상 공개 접속에서 동적 취득·갱신 |
| 금투협 웹 | 필요 시 세션 쿠키 | 공개 조회 세션 유지; 별도 공식 API 키는 기존 경로에서 사용하지 않음 |
| AIDP 원본 저장소 | Dataiku 관리 폴더 ID·연결명·대상 경로 | AIDP 담당자; 실제 S3/SFTP 연결 선택 |
| S3를 직접 사용하는 경우 | 버킷·prefix·endpoint·승인된 접근 역할/자격정보 | S3 선택 시만 필요; 문서에 실제 키 기입 금지 |
| Oracle 적재 | Dataiku의 승인 DB 연결·테이블 매핑 | 당사 데이터플랫폼 담당; 수집기에 DBA 비밀번호 배포하지 않음 |

인증값은 코드·요청 URL 로그·오류 메시지·manifest·납품 문서에 남기지 않는다. 운영 설정에는 비밀 참조명만 둔다. 일반 DRF API 요청에 브라우저 Cookie를 기본 필수값으로 추가하지 않는다. 중계 자체 인증과 원천 사이트 세션은 별도다.

### 3.2 API 주소와 공통 응답

기본 원천: https://www.law.go.kr. GET 쿼리는 UTF-8로 인코딩하며 파라미터 대소문자를 유지한다. 아래 주소는 HTTPS 기준 요청안이다. 공식 예제에 HTTP 표기도 있으므로 중계의 target_url 허용값과 실제 HTTPS 연결을 확인하고, 임의 TLS 검증 해제나 다운그레이드를 하지 않는다.

[S1 시행일 기준 목록 공식 명세](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=lsEfYdListGuide) · [S2 시행일 기준 본문 공식 명세](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=lsEfYdInfoGuide)

| 요청 | 파라미터 | 요청값·의미 |
| --- | --- | --- |
| 목록·본문 | OC / target / type | 승인 인증값 / eflaw / XML |
| 목록 | search / query | 1 / 표 2.1의 정식명; 응답에서 정확 매칭 |

| 본문 권장 | MST + efYd | 목록의 법령일련번호 + 그 판본의 시행일 YYYYMMDD |
| 본문 대안 | ID | 법령ID로 현행 본문 조회. 이 모드에서는 MST·efYd 생략 |

요청 조립 예시다. 줄바꿈은 읽기용이며 실제 호출은 HTTP 라이브러리의 params로 전달한다. {…}는 실행 시 치환할 자리표시자다.

```text
GET https://www.law.go.kr/DRF/lawSearch.do
OC={LAW_OC}&target=eflaw&type=XML&search=1
query={정식법령명}&nw=2,3&display=100&page={PAGE}

GET https://www.law.go.kr/DRF/lawService.do
OC={LAW_OC}&target=eflaw&type=XML
MST={목록의_법령일련번호}&efYd={해당판본_시행일}
```

MST·efYd와 받은 본문의 법령ID·문서명·공포일·시행일을 대조한다. 시행예정 원문은 예정 판본으로 저장하며, 수집일 또는 “최신” 여부만으로 현행을 바꾸지 않는다. 조문별 시행일·부칙의 적용 시점은 원문 그대로 보존한다. 공포본 A3를 추가 수집하면 표현 유형을 별도로 기록한다.

### 3.5 별표와 파일 응답 처리

별표서식파일링크·별표서식PDF파일링크·첨부파일링크 등 실제 응답에서 제공되는 자산을 열거한다. HWP만 있고 PDF는 없는 경우처럼 원천 제공 범위를 기록한다. 같은 내용의 복수 형식은 표현본으로 연결하고, 제공되지 않은 HWPX를 원천 파일처럼 생성하지 않는다. 변환본을 만들면 원본 해시·변환 도구·버전을 별도로 남긴다.

파일명·확장자·Content-Type만으로 성공을 판단하지 않는다. 실제 포맷·크기·해시를 확인하고, HTML 오류 페이지가 .hwp로 저장되는 경우를 실패로 잡는다. 본문 또는 필수 첨부가 실패하면 문서 전체를 “완료”로 발행하지 않는다.

## 4. 크롤링 방식과 받는 구조

### 4.1 공통 구현 방식

기존 공개 사이트 요청을 이용하는 HTTP 수집기를 우선 사용한다. 화면 내부의 JSON 응답도 웹 크롤링 경로이며 공식 공개 API 계약으로 부르지 않는다. 사이트 기능상 브라우저 실행이 꼭 필요한 부분만 Selenium 등으로 처리하고, 캡차·접근 제한을 우회하는 용도로 사용하지 않는다.

뭉타가 전달할 HTML은 조문을 텍스트로만 뽑은 결과가 아니라 전체 원본 HTML이다. 본문에 필요한 이미지, 첨부 원본, 자산 URL 매핑과 판본 메타데이터를 함께 제공한다. 화면 캡처나 브라우저에서 출력한 PDF만으로 HTML 원문을 대체하지 않는다.

| 대상 | 필수 수집 산출물 | 구조 보존 기준 |
| --- | --- | --- |
| KRX·금투협 본문 | 전체 HTML + 제공되는 전문 원본 | 장·절·조·항·호·목, 제목, 부칙, 삭제·개정 표기, 원문 DOM 위치 |
| 표 | HTML table 구조 및 셀 텍스트 | tr/th/td, 행·열 위치, rowspan/colspan, 각주·단위 보존 |
| 이미지·수식 | 본문 의미에 필요한 원본 이미지 + 참조 매핑 | src·상대경로 기준 URL·파일 해시; 실패 시 누락 표시 |
| 첨부·별표 | 사이트에서 받은 실제 바이너리 | 원문 제목·파일명·역할·부모 문서·실제 판본 연결 |
| 목록·메타 | 원본 목록 응답 + UTF-8 JSON/JSONL 메타 | 원천 ID·판본·수집 시각·시행일·개정일·상태 구분 |

원본은 받은 바이트 그대로 보존하고, 파싱용 텍스트만 UTF-8로 정규화한다. 원래 응답 인코딩과 해시를 기록한다. HTML의 base URL·상대 링크를 잃지 않도록 한다. 표를 문장으로 펼치거나 이미지 OCR 결과만 남기는 것은 원문 구조 보존을 충족하지 않는다.

### 4.2 C 그룹 거래소 요청 순서

다음은 기존 krx.py에서 확인한 웹 요청이다. 공식 API 지원 보장은 없으므로 개발 착수 시 현재 화면과 요청을 대조한다. 출처: [S7 KRX 법무포털](https://rule.krx.co.kr/out/index.do).

| 순서·방식 | 전체 요청 주소 | 요청값·응답 |
| --- | --- | --- |
| C1 GET | https://rule.krx.co.kr/out/index.do | 없음 → HTML·세션 쿠키 |
| C2 POST form | https://rule.krx.co.kr/out/regulation/regulationMain.do | Menucd=BYLAW; index=law_rule; gbn=out; _csrf → HTML |
| C3 POST form | https://rule.krx.co.kr/out/regulation/getTreeNode.do | node=0 또는 하위 노드; statecd=현행; mtype=htree; Menucd=BYLAW; webgbn=OUT; gbnid=0; gbn2=out → JSON 트리 |
| C4 POST form | https://rule.krx.co.kr/out/regulation/regulationView.do | bookid; noformyn=노드 값(없으면 N); gbnid=0; mtype=htree; searchForm=빈값; Menucd=BYLAW; _csrf → HTML 본문 |
| C5 POST form | https://rule.krx.co.kr/web/regulation/downloadRuleFile.do | bookid; statehistoryid; filecd=JUN / GAE / SIN → JSON fileMap |
| C6 POST form | https://rule.krx.co.kr/out/regulation/regulationList.do | Menucd=BYLAW; mtype=byul; gbnid=BYUL; smType=byul; index=law_rule; gbn=out; _csrf → HTML |
| C7 POST form | https://rule.krx.co.kr/web/regulation/regulationListData.do | start=0부터; limit=100; mtype=byul; Menucd=BYLAW; stit=규정; gbnid=분류; gbn2=out → JSON result·total |
| C8 POST form | https://rule.krx.co.kr/login/getData.do | _csrf=현재 페이지 토큰; 헤더 X-CSRF-TOKEN → JSON data._csrf |
| C9 POST form | https://rule.krx.co.kr/Download.do | Serverfile; Pcfilename; folder=ATTACH; _csrf=새 토큰 → 원본 파일 바이너리 |

C1→C2→C3으로 현재 규정을 찾고 C4에서 본문과 판본을 얻는다. C5에서 전문·개정문·대비표 파일 정보를 얻고, C6→C7로 별표·서식을 열거한다. 각 파일은 C8→C9로 내려받는다. 페이지·JSON 응답에 새 토큰이 있으면 세션 상태를 갱신한다.

JSON 조회에는 기존 구현 기준 X-CSRF-TOKEN, X-Requested-With=XMLHttpRequest 및 Referer=https://rule.krx.co.kr/out/regulation/regulationList.do를 사용한다. 파일 다운로드 Referer는 규정 상세 경로다. Serverfile·Pcfilename의 대소문자와 실제 값을 유지한다. C7의 분류는 실제 사이트에 존재하는 목록을 확인하며, HTTP 오류나 JSON 파싱 실패를 “해당 별표 없음”으로 바꾸지 않는다.

KRX HTML은 조문 구조화에 유용하지만 표·이미지는 별도 보존이 필요하다. 기존 rulehtml.py는 장·조와 항·호·목을 나누는 경로를 제공한다. 조문 구조 파싱만으로 원문·표·수식의 완전한 추출을 증명하지 않는다. 현재 구현의 표 셀·이미지 처리 보완은 납품 검수 항목에 포함한다.

규정 seq, 판본 historySeq, 첨부 다운로드 seq는 서로 다른 값이다. D2의 historySeq=0은 현행 판본을 알아내기 위한 진입값이고, 저장할 본문·전문은 확인한 실제 historySeq에 묶는다. D6의 개정일을 시행일로 대신 저장하지 않는다. 시행일을 확보하지 못하면 null과 확인 필요 사유를 남긴다.

수집 대상은 표 2.4의 5종으로 고정한다. “모범규준” 분류 전체를 자동 확장하지 않는다. 개정문·대비표는 해당 파일의 실제 개정 판본을 보존한다. 과거 대비표만 있는 경우 그 이력을 명시하며 현행 대비표로 표시하지 않는다.

| 수시 처리 | 현업 개정 통지 시 | 같은 실행기와 문서 범위로 수동 트리거; 별도 수집 로직을 만들지 않음 |

1. 마지막 성공 시각과 문서별 판본·해시를 읽고 실행 ID·대상 목록·설정 버전을 고정한다.
2. 지정 문서 전체의 목록·현재 상태를 확인한다. 날짜 필터는 보조이며, 최근 수정일만으로 확인 범위를 제한하지 않는다.
3. 새 판본·본문 변경·첨부 목록 변경을 찾으면 해당 자산을 받는다. 같은 URL·파일명이라도 같은 내용이라고 판단하지 않는다.
4. 원문 명칭·판본·형식·크기·해시와 첨부 완전성을 검사하고, 원본 저장소 쓰기·재조회가 끝나면 완료 manifest를 발행한다.
5. AIDP가 manifest를 읽어 기존 구조화·용어 연결·색인·Oracle 적재로 전달한다. 실패한 문서는 이전 검증 판본을 유지하고 갱신 실패를 표시한다.

변경 확인용 ETag·Last-Modified·조건부 요청은 원천이 지원하고 검증한 경우만 활용한다. 서버의 변경 표식이 부정확할 수 있으므로 주간 재대조로 본문·첨부 해시를 확인한다. 수집일, 게시일, 공포·발령일, 시행일은 서로 다른 컬럼으로 보존한다.

일일 1회 방식의 갱신 지연은 원천 반영 지연 + 다음 배치까지의 대기(정상 주기에서 최대 약 24시간) + 처리·복구 시간이다. 특정 기관이 06:00 이전에 갱신한다는 가정이나 당일 모든 개정을 즉시 반영한다는 SLA는 두지 않는다.

## 6. 원본 저장과 AIDP 인계 규격

### 6.1 처리 흐름과 담당

당사 목표 흐름은 Dataiku 배치 → GENOS 파이프라인 실행 → 중계서버를 통한 외부 수집 → AIDP 원본 보존·기존 구조화 흐름 → Oracle 적재다. GENOS가 수집을 실행해도 원문·결과의 영구 보관 책임은 AIDP 데이터 계층에 있다. 외부 수집기를 별도 구간에 배치한다면 같은 인계 규격으로 연결하고 실행 위치를 협의한다.

| 구성 | 책임 | 확정할 연결 |
| --- | --- | --- |
| 뭉타 수집기 | API·웹 탐색, 다운로드, 원본·메타·실패 결과 생성 | 기존 수집 진입점 통합 또는 호환 어댑터 제공 |
| 중계서버 | 허용 원천 연결, 인증·HTTP 전달·필요한 원천별 세션 처리 | GET/POST form, 요청·응답 헤더, 쿠키, 바이너리, 크기·시간 한도 |
| Dataiku | 스케줄·중복 방지·상태 관리·파일 인계·DB 적재 흐름 | 관리 폴더와 기존 실행·재개 계약 |
| 원본 저장소 | XML·HTML·첨부·이미지·manifest 판본별 보존 | AIDP 승인 S3 등 또는 기존 SFTP 연결 |
| Oracle 골드 | 구조화 원문·용어·관계·온톨로지·llm_wiki | 당사 표준 명명·메타 등록·DBA 생성 절차 |
| 에이전트 레이어 | LLM 질의·판단·실행 기록 | 문서 판본·원문 위치와 연결 |
| GENOS RAG | Oracle/조회 API에서 필요한 원문 조회 | 서빙 컨테이너에 전체 원문·색인을 영구 복제하지 않음 |

Dataiku 관리 폴더는 S3·SSH 등 여러 저장소에 연결할 수 있다. 현재 확인된 현장 관리 폴더는 SFTP 경로이며 S3 연결 제공은 미확정이다. 저장소 종류를 문서만으로 바꾸지 않는다. 기존 현장 기록에는 작은 파일도 쓰기 실패한 사례가 있으므로 운영 연계 전 실제 대상 저장소의 쓰기·재조회·용량을 확인한다. [S10 Dataiku 관리 폴더](https://doc.dataiku.com/dss/latest/connecting/managed_folders.html)

### 6.2 원본 패키지 구성 요청

다음은 인계용 논리 구조 제안이다. 실제 버킷·폴더·Oracle 물리명은 AIDP 표준에 매핑한다. 기존 DatasetPackage·SourceSet 계약과의 변환을 납품하고 별도 정본을 병렬 운영하지 않는다.

```text
raw/{source}/{document_key}/{version_key}/
  body/original.xml 또는 original.html
  attachments/{asset_id}.{실제확장자}
  assets/{asset_id}.{실제확장자}
  manifest.json
runs/{run_id}/
  inventory.jsonl
  results.jsonl
  completion.json
```

원본 바이트가 같으면 파일을 공유하고 수집 관측·판본 매핑만 추가한다. 내용이 바뀌면 새 해시·판본 디렉터리에 저장한다. 같은 경로를 덮어써 과거 원문을 잃지 않는다. 업로드 중인 패키지는 소비자가 읽지 않으며, 파일 검증 후 완료 표시를 마지막에 발행한다. object storage의 폴더 rename을 트랜잭션으로 가정하지 않는다.

### 6.3 메타데이터 필드

아래 필드는 인계용 JSON 이름 제안이며 확정 Oracle DDL이 아니다. 날짜는 확인된 값만 채우고, 미확보는 null과 사유를 남긴다. 식별자는 앞자리 0·긴 숫자가 보존되도록 문자열로 전달한다.

| 필드 | 내용 | 필수 조건 |
| --- | --- | --- |
| schema_version / run_id | 인계 규격 버전 / 실행 ID | 항상 |
| document_key / title / source | 당사 문서키 / 정식명 / law·krx·kofia 등 | 항상 |
| source_document_id / source_version_id | 법령ID·규정ID / MST·historySeq 등 실제 원천 판본 | 확보 값; 없는 원천은 null과 식별 방식 |
| version_key / document_status | 원천 판본·해시로 결속한 키 / 현행·시행예정·연혁·미확인 | 항상 |
| promulgated_at / revised_at / effective_at | 공포·발령일 / 개정일 / 시행일 | 원천이 제공한 날짜만 |
| collected_at / last_checked_at | 다운로드 시각 / 변경 확인 시각; ISO 8601·시간대 | 항상 |
| source_page / source_url / request_method | 출처 화면 / 자격값을 제거한 요청 URL / GET·POST | 항상; POST 공개 파라미터도 별도 보존 |
| assets[] | asset_id·role·원본명·저장 URI·실제 형식·인코딩·byte_size·sha256 | 본문·각 첨부·각 이미지별 |
| parent_asset_id / source_ref | 본문과 첨부·이미지 연결 및 실제 원문 참조 | 관계가 있을 때 |
| security_class / access_scope | 공개·내부 분류 / 접근 범위 | 항상 |
| fetch_status / completeness | 수집 결과 / 필수 자산 확보 상태 | 항상 |
| error_code / error_message / retryable | 오류 분류·자격값 제거 메시지·재개 가능 | 실패·부분 성공 시 |

role은 body / attachment / image / amendment / comparison / index로 구분하는 인계 제안이다. 기존 내부 role 값과의 변환표를 제공한다. 본문·첨부가 서로 다른 판본이면 그 관계를 그대로 기록하고, “같은 폴더”라는 이유로 동일 판본으로 덮어쓰지 않는다.

문서 결과 상태는 COLLECTED(필수 원본 검증 완료), UNCHANGED(원격 확인 후 동일), PARTIAL(일부 미확보), FAILED(실패), BLOCKED(접근 차단)로 구분한다. 실행 단위는 전 대상의 성공·부분·실패 수와 미처리 목록을 보고한다. 실패를 첨부 없음이나 변경 없음으로 변환하지 않는다.

원본 JSON/XML과 구조화 JSON은 별도 자산이다. 뭉타가 구조화까지 맡는 경우 장·절·조·항·호·목의 부모 키, 표 셀 구조, 원문 위치와 해시를 포함하는 기존 구조 계약을 추가 합의한다. 기본 수집 납품만으로 RAG 품질·법률 판단의 정확성을 인증하지 않는다.

## 7. 중계와 웹 수집의 주의사항

### 7.1 중계 담당자에게 필요한 확인

기존 현장 자료에는 DRF 중계 경로 /law/DRF와 target_url 헤더가 등장한다. 정확한 base URL·요청 메서드·쿼리 전달·인증값·응답 포장 규약은 담당자가 확정해야 한다. /law/making은 별도 입법센터 경로로 이번 68종 DRF 수집과 섞지 않는다. 실제 인증키·사내 IP는 별도 비밀 설정으로 전달한다.

| 확인 항목 | 요청 내용 |
| --- | --- |
| 법제처 요청 | /DRF/lawSearch.do와 /DRF/lawService.do의 target·OC·한글 query·날짜 전달 |
| 첨부 다운로드 | /LSW/flDownload.do 및 실제 반환 주소의 바이너리 전달; 본문 API 허용만으로 완료 불가 |
| 웹 POST·헤더 | application/x-www-form-urlencoded, Referer, X-CSRF-TOKEN, X-Requested-With 전달 |
| 원천 세션 | Set-Cookie·Cookie의 원천별 유지·만료·갱신; 단순 requests.Session만으로 중계 뒤 세션이 보장되지 않음 |
| 파일·이미지 호스트 | www.law.go.kr, rule.krx.co.kr, law.kofia.or.kr, listing.krx.co.kr, file.krx.co.kr; 다른 실제 자산 호스트는 추가 확인 |
| 네트워크 | 허용 도메인·포트·TLS SNI·인증서 검증·원천 출구 IP |
| 응답 계약 | 원문 바이트·상태코드·필요 헤더 전달; JSON 포장 시 바이너리 전달·크기 한도 별도 합의 |
| 운영 한도 | 요청/파일 크기·timeout·호출 제한·장애 코드·상관 ID·동시 실행 정책 |

현장 기록의 TCP 연결 성공은 HTTPS/API 성공을 뜻하지 않는다. 기존에는 TLS 단계 reset 관측이 있으므로 원천 응답 수신·파일 저장까지 실제 경로로 검증해야 한다. 중계가 웹 POST·세션·파일 응답을 지원하지 않으면 승인된 외부 수집 구간에서 파일·메타를 AIDP로 전달하는 대안을 비교한다.

### 7.2 이용 조건과 부하 관리

뭉타는 실제 접근 호스트의 이용약관·robots.txt·재사용 조건·호출 제한을 확인하고 확인일·판단 근거를 제출한다. 공개 화면 접근 가능 또는 robots.txt 미확보만으로 자동 수집 허용을 단정하지 않는다. 현재 KRX·금투협 robots.txt는 이번 웹 조회에서 확인되지 않았으며, 과거 다른 호스트의 관측을 그대로 적용하지 않는다.

법제처는 과도한 단시간 호출 시 이용 제한 가능성을 안내한다. 아래 한도는 당사 제안이며 기관이 승인한 한도가 아니다. 원천이 더 엄격한 조건을 제시하면 이를 따른다. [S5 공동활용 주의사항](https://open.law.go.kr/LSO/usrJoin.do)

| 항목 | 제안 기본값·동작 |
| --- | --- |
| 동시성 | 수집 작업 전체 1개; 도메인별 동시 요청 1개 |
| 요청 간격 | 동일 원천 요청 시작 간 최소 1초; 세션·첨부 요청도 포함 |
| 요청 timeout | 연결 10초·읽기 60초; 큰 파일 예외는 측정 후 조정; 실행기 deadline 별도 |
| 재시도 예산 | 일시 네트워크·429·503 등만 요청당 최초 포함 최대 4회. 재개해도 누적 한도 유지 |
| 대기 | Retry-After 우선; 없으면 2·8·32초에 작은 무작위 지연. 긴 대기는 재개 시각으로 기록 |
| 자동 실행 기한 | 일일 실행 최초 시작 후 120분 제안. 대용량 초기 적재는 별도 예산·측정 |
| 차단·인증 | 명시적 접근 차단·캡차는 원천 작업 중단. 확인된 CSRF 만료만 1회 갱신 후 동일 요청 재시도 |
| 식별·접근 | 합의된 User-Agent·연락처·출구 IP 사용. 우회 계정·프록시 회전·TLS 검증 해제 금지 |
| 원문 보존 | 법제처·소관기관 출처 및 버전 표시; 원문 변조와 파생본 혼동 방지 |

브라우저 자동화는 세션 생성·동적 렌더링이 필요한 경우의 구현 선택지다. RPA·Selenium 사용 자체가 수집 허용이나 데이터 완전성을 보장하지 않는다. 원천 접근 제한을 받으면 실패 상태와 근거를 남겨 담당자에게 전달한다.

## 8. 기존 코드 활용과 필요한 보완

아래는 현재 로컬 작업 코드의 확인 결과와 요청할 보완을 구분한 것이다. 운영 현장에 이 보완이 적용됐다는 뜻은 아니다. 기존 수집 모듈을 활용하되, 납품 전 실제 AIDP 소비자까지 연결해 검수한다.

| 기존 방식·관측 | 요청할 변경 | 검수할 행동 |
| --- | --- | --- |
| lawgo.py: 목록 target=law, display=50, 단일 페이지 조회 | A1의 eflaw 목록·명시 nw·전체 페이지 처리와 파서 호환 검증 | 대상 49종 정확 매칭; 100건 초과 목록도 누락 없음 |
| 법제처 첨부 파서는 flSeq 링크와 HWP 경로 중심 | 실제 응답의 다른 파일 링크·포맷·PDF 등도 자산으로 수집 | 확장자 가정 없이 원천 제공 첨부 목록과 수신 파일 대조 |
| collect.py: 정상 로컬 파일이 있으면 원격 재확인 없이 skip 가능 | 원격 변경 확인과 로컬 다운로드 생략을 분리 | 원격 본문 교체 시 기존 파일이 있어도 새 버전 수집 |
| collect.py: discover의 RuntimeError 처리로 CrawlAborted를 일반 실패로 삼킬 수 있음; 합성 재현 이력 있음 | 차단 예외를 원천 작업 중단까지 전달 | 캡차·차단 후 같은 원천의 후속 요청이 발생하지 않음 |
| krx.py: 일부 목록 비JSON/오류 응답을 분류 없음으로 종료 | 정상 빈 목록과 조회 실패를 별도 상태로 처리 | 원천 500·깨진 JSON이 첨부 0건 성공으로 기록되지 않음 |
| common.py: 1초 간격은 클라이언트별이며 Retry-After·전역 실행 잠금 미구현 | Dataiku 실행 잠금·원천별 공통 한도·총 예산 연결 | 동시 배치와 재개에서도 한도 유지 |
| common.py: URL 전체 로깅 경로가 있어 OC 노출 가능 | 요청·예외·추적 로그 공통 자격값 제거 | 가짜 키를 넣은 검사에서 로그·manifest에 키가 남지 않음 |
| 기존 저장은 파일 경로/manifest 갱신 중심 | 판본별 불변 저장·완료 manifest·해시 검증 인계 | 갱신·실패·재실행 후 과거 원본 복원 가능 |
| rulehtml.py: 장·조 구조 파싱은 있으나 KRX 표 셀·이미지 표현은 부족 | 원본 HTML·이미지 보존 및 후속 구조 계약 보완 | 병합 셀·단위·각주·이미지가 원문과 대응 |
| 공개 별첨은 기존 수집 기록이 있으나 최신 게시물 탐색 계약은 미확정 | E1/E2의 현재 탐색·다운로드 규약 구현 | 새 게시물·동일 게시물 첨부 교체를 모두 탐지 |

연결 지도: sources/lawgo.py·krx.py·kofia.py와 common.py → pipeline/collect.py의 원본·manifest → 기존 DatasetPackage/SourceSet 반입 → 구조화(XML 또는 rulehtml) → 문서·용어 연결·색인 → Dataiku Oracle 적재다. GENOS 파이프라인 호출 및 API 중계 어댑터는 당사 현장 계약에 맞춰 연결한다.

수집기 보완으로 원문 해시·판본이 바뀐 문서만 후속 구조화·관련 색인을 재생성한다. 파서 구조 계약을 바꾸면 해당 파서로 만든 대상 문서의 구조화·하위 색인 범위를 명시한다. 코드 수정, 검수 통과, MAIN 선택, GENOS 현장 배포는 각각 별도 완료 상태로 보고한다.

## 9. 납품물과 검수 기준

### 9.1 납품 요청

1. 68종의 문서 등록부: 정식명·기관·API 그룹·원천 식별자·현행 판본 탐색 방식·허용 범위.
2. 수집 코드·의존성·설정 템플릿: 실제 인증값 제외, 실행·재개·중단·롤백 안내 포함.
3. 원천별 샘플: XML, HTML, 표·이미지, HWP/HWPX/PDF 등 실제 제공 포맷과 관련 manifest.
4. AIDP 인계 어댑터: 지정 저장소 적재, 원본 해시 재조회, 기존 DatasetPackage 연결, 결과 상태.
5. 운영 설정: 제안 배치의 확정 시각, 중복 방지, Retry-After·총 예산·기한, 실패 현황 출력.
6. 검수 기록: 실제 원천·중계·저장소를 통한 정상·실패·개정·재개 검사와 남은 제약.
7. 사이트 이용 조건 확인표와 관리 담당·장애 연락·사이트 변경 대응 절차.

### 9.2 검수표

| 검수 대상 | 통과 기준 |
| --- | --- |
| 범위 | API 37+12, 웹 9+5+5의 68종 전부 등록. 수동 10·제외 2의 자동 요청 0건 |
| 인증·중계 | 승인 OC로 실제 목록·본문·첨부 수신; TLS·POST·쿠키·바이너리 전달 확인 |

| 첨부 완전성 | 원천의 대상 첨부 목록과 수신 결과를 전수 대조. 미확보는 PARTIAL로 표시 |
| HTML·표·이미지 | 검수 대상 전체에 원본 존재. 각 원천의 조문·표·이미지 대표 사례를 원문과 대조; 정량 구조 검사와 사람이 보는 내용 검사를 구분 |
| 저장 무결성 | 필수 자산의 SHA-256·크기 재조회 일치. 이전 판본 덮어쓰기 없음 |
| 변경 탐지 | 새 판본, 동일 URL 파일 교체, 새 첨부·삭제, 문서명 변경 시나리오 확인 |
| 실패·차단 | 429·503·CSRF 만료·캡차·200 오류문서·파싱 오류를 구분하고 한도대로 종료 |
| 재개·중복 | 동일 run/package 재실행 시 중복 DB 행·파일 손실 없음; 예산·기한·실패 이력 보존 |
| 자격정보 | OC·Cookie·토큰·저장소 키가 로그·manifest·산출 문서에 노출되지 않음 |
| AIDP 소비자 | 원본 저장→검증→구조화→Oracle 적재·조회까지 대표 문서로 실제 경로 확인 |
| 운영 전환 | 수집 검수·구조화 검수·DB 적재·RAG 반영 상태 별도 기록, 이전 검증 판본으로 복구 가능 |

초기 인수에서는 68종 전체를 문서 단위로 점검한다. API 호출 수는 문서 수보다 많고 첨부·페이지·토큰·재시도가 추가되므로 “68회 호출”로 견적하지 않는다. 호출 수 = 목록 페이지 요청 + 본문 요청 + 첨부 요청 + 세션·토큰·파일 메타 요청 + 재시도 요청으로 측정한다. 저장량은 신규 원본 바이트 + 메타·실행 기록 + 승인한 파생본을 합산하며 동일 해시 원본은 중복 계산하지 않는다. 처리 시간·운영 비용·구축 인일은 실제 파일 수와 현장 한도를 확인한 뒤 업체가 산정한다.
