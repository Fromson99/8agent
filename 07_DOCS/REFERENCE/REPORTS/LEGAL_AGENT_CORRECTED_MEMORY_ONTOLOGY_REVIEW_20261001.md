# 멀티턴 정정 실험 결과와 도메인 온톨로지 통제 가능성

2026년 10월 1일 · WSL 로컬 · 모의 문서와 모의 질문 · 코드와 산출물을 확인한 자체 검토

**사용자가 말한 구조는 구현 가능하다. 문장 작성은 자유롭게 하면서, 판단은 우리가 정의한 도메인 개념·관계·검토 방법을 선택해 수행하도록 만들 수 있다. 현재 프로토는 정정 체인과 최종 경험의 저장·재사용까지 확인했지만, 모든 판단을 그 도메인 경로에 결속하지는 않는다.** 이 문서는 완료한 실험의 결과와 남은 원인을 정리하고, 다음 구현에서 사용할 온톨로지의 의미와 판단 계약을 제안한다. 이 제안 자체를 새로 구현하거나 실험하지는 않았다.

## 우리 온톨로지의 정의

**우리 온톨로지는 버전과 원문 근거를 가진 도메인 개념·정의·관계·적용 범위의 체계다. 에이전트의 판단 통제에는 이 체계 위에서 허용되는 검토 방법과 경로 계약이 함께 필요하다.** 사용자가 말한 “우리가 만들어 놓은 길만 선택한다”는 것은 이 온톨로지와 경로 계약을 결합한 실행 방식으로 정의하는 것이 적절하다.

| 구성 | 담는 것 | 통제에 사용하는 방식 |
|---|---|---|
| 개념과 정의 | 용어 ID, 문서 범위별 의미, 정의 출처, 버전 | 임의 개념명을 정본처럼 만들지 않고 제공된 개념을 선택 |
| 관계 | 어떤 개념·조문이 무엇을 정의·참조하는지, 관계의 타입과 방향, 관계 근거 | 존재하는 관계를 따라 이동. 단순 언급·참조와 법적 적용 판단을 구분 |
| 적용 범위 | 대상 문서·버전, 해당 정의나 관계의 범위, 현재 사건의 확인된 조건 | 다른 규정의 동일 용어를 그대로 적용하거나 미확인 사실을 가정하는 것을 차단 |
| 검토 방법과 경로 | 정의를 확인하는 방법, 원문 연결을 확인하는 방법, 요건·예외 검토의 선행 조건과 완료 조건 | 방법·경로를 선택해 실행. 경로마다 필요한 근거를 실제로 확보했는지 검사 |
| 판단 근거와 의존 관계 | 선택한 개념·관계·방법, 사건 조건, 원문 span, 판단 결과, 이전 판단에 대한 의존 | 이유를 도메인 용어로 설명하고, 정정한 대상을 소비한 후속 판단을 찾아 무효화 |

이는 모든 법령 문장을 미리 Rule·조건·효과로 재작성하자는 제안이 아니다. 현행 원문·용어·정의·명시 참조 계약을 유지하고, 읽은 원문에 대한 판단이 어떤 개념과 방법에 근거하는지 구조적으로 결속하는 제안이다. 현행 MAIN도 원문을 읽어 판단하며 용어 관계와 정의를 탐색 단서로 사용한다고 명시한다. [MAIN 정의](/home/jin/8-AGENT/00_SYSTEM/ARCHITECTURE.md:115)

## 자유로운 문장 작성과 제한된 판단 경로를 결합하는 방법

다음은 구현 전 제안이다. 에이전트는 현재 문서·질문 범위에서 사용할 수 있는 개념·관계·검토 방법의 목록을 먼저 받는다. 어떤 질문에 답하려고 어느 개념과 경로를 선택했는지 도구 실행 전에 기록한다. 시스템은 존재하는 ID·허용된 관계 타입과 방향·문서 버전·필요한 선행 검토를 확인한 뒤 실행한다. 읽은 근거로 조건을 확인하고 개별 판단을 확정하며, 이후 설명은 그 기록을 자연어로 표현한다.

길은 전체 답변 문장을 미리 작성하는 방식으로 만들 필요가 없다. 승인된 관계와 검토 방법을 조합하는 규칙으로 만들 수 있다. 다만 허용된 조합에도 해당 사건의 적용 조건이 필요하다. 등록된 경로를 골랐다는 사실만으로 그 사건에 맞는 판단이라고 할 수는 없다.

가상의 “이 규정의 대상자에 해당하는가” 질문에서는 다음처럼 결속한다. 아래 ID는 설계 예시이며 이번 실험에 구현된 계약이 아니다.

```text
질문 대상 규정 v1
  → 그 규정 범위의 대상자 개념
  → 해당 개념의 정의 관계
  → 정의 우선 검토 방법
  → 정의 조항 원문 읽기와 사건 사실 대조
  → 대상 해당 여부 판단
```

이유 문장은 “대상자 여부를 판단하려고 질문 대상 규정에 결속된 정의를 먼저 확인했다”처럼 자유롭게 쓸 수 있다. 시스템이 확인할 것은 이 문장이 가리키는 실제 개념·정의 관계·규정 버전·읽은 구간과 적용 사실이다. 다른 규정의 동명 용어 정의를 골랐다면 현재 규정에 적용 가능한지 추가 확인해야 한다. 확인되지 않은 상태를 확정 판단으로 통과시키지 않는다.

도구 선택 이유도 같은 방식이다. “관련 있어 보여서 읽었다”만 기록하면 정정할 대상이 흐릿하다. “대상자 개념의 정의를 확인하는 경로에서 이 정의 조항이 필요한 근거이므로 읽었다”는 관계·방법·원문 ID에 결속될 수 있다. 모델은 그 구조를 선택하고 표현하며, 실제 실행은 그 선택과 근거에 연결된다. 도구 실행 뒤 그럴듯한 이유를 새로 만들어 붙이는 방식으로 대체하지 않는다.

최소 판단 기록의 제안은 다음과 같다.

| 필드 | 역할 |
|---|---|
| question_id·judgment_id·revision | 어느 질문의 어느 개별 판단인지 |
| ontology_version·concept_ids | 사용한 도메인 체계와 개념 |
| relation_ids·method_id·path | 실제로 선택한 관계와 검토 경로 |
| facts·condition_checks | 확인된 사건 조건과 조건별 미확인 상태 |
| source_ids·basis_spans | 판단과 경로를 뒷받침하는 실제 원문 |
| depends_on·supersedes | 이전 판단 의존과 정정 대상 |
| disposition·reason | 채택·배제·보류와 자유롭게 작성한 이유 |

이유의 단어를 코드 목록으로만 제한하면 도메인적으로 틀린 선택을 그럴듯한 단어로 표현할 수도 있다. 따라서 **등록된 경로 검사와 그 경로를 현재 조건에 적용하는 근거 검사를 함께 해야 한다.** ID·버전·근거 전달 여부는 기계 검사로, 원문 의미와 사건 사실의 부합은 도메인 검토 계약으로 나누어 처리한다. 지금 있는 인용 일치 검사만으로 이 의미 검사가 완성됐다고 판단하지 않는다.

필요한 길이 없을 때는 새 관계를 정본으로 만들어 진행하지 않는다. 부족한 개념·근거·경로를 미확인 또는 추가 후보로 남긴다. 이 처리가 있어야 “우리가 만들어 놓은 길만 선택한다”는 조건을 지킬 수 있다.

## 온톨로지 통제와 정정 체인의 연결

현재 체인 구현은 최초 발언·정정 이벤트·유효 경로·퇴역 경로를 구분한다. 이 기반에 개별 판단의 도메인 의존 관계를 연결하면 정정 대상을 더 정확히 좁힐 수 있다.

| 정정 대상 | 변경할 구조 | 다시 확인할 범위 |
|---|---|---|
| 질문을 잘못 이해함 | 질문과 도메인 개념의 결속 | 해당 개념 선택과 그에 의존한 탐색·판단 |
| 적용 규정이나 정의가 잘못됨 | 문서 범위·개념·정의 관계 | 정의 확인 이후 이를 사용한 요건·예외·결론 |
| 사건 조건이 잘못됨 | 조건 값과 그 값을 사용한 판단 | 해당 조건을 소비한 판단과 이후 답변 |
| 과거 경험을 잘못 연결함 | wiki와 경험 묶음의 연결 | 연결을 소비한 현재 질문. 원래 경험 묶음의 무관한 판단은 유지 |
| 최초 정정이 다시 잘못됨 | 지정한 정정의 변경 내용을 새 버전으로 대체하고 불변 원본·이전 조건 확인 | 유효 조건을 다시 구성한 뒤 영향을 받은 판단만 재검토 |
| 표나 문장을 바꿈 | 표현 요청 | 현재 유효 판단에 결속된 COMPOSE |

예를 들어 2차 정정이 “1차 정정에서 바꾼 적용 규정이 잘못됐다”라고 하면, 시스템은 1차 정정 이벤트·바뀐 규정 범위·그 전에 유효했던 조건을 회수한다. 최초까지의 원기록을 통해 현재 조건을 재구성하고, 그 규정의 개념·정의·원문을 사용한 판단을 무효화한다. 새 최종 판단이 확정되면 같은 묶음의 유효 경로를 교체한다. 철회한 1차 정정과 최초 오답은 감사 기록으로 남지만 다음 질문의 정답 경로로 소비하지 않는다.

이번 실험은 이 중 체인 역추적과 단계 단위 재실행을 확인했다. 위 표의 도메인 판단별 의존 관계까지 완성한 것은 아니다. 개별 판단의 필수 결속이 추가되어야 “어떤 도메인 이유를 고치면 어떤 결과가 바뀌는지”가 직접 추적된다.

## 구현 가능성 판정과 필요한 후속 확인

**구현 가능성은 높다고 판단한다.** 근거는 기존 코드에 제공 ID 제한·문서 범위·원문 span·관계 근거·검토 의무·버전·의존 관계를 관리하는 구성 요소가 있고, 이번 후보에서 정정 체인·퇴역 처리·최종 저장·재사용의 연결을 실제로 실행했기 때문이다. 이는 코드 연결 가능성에 대한 판단이며 개발 기간·대규모 정확도·GENOS 성능을 추정한 결론은 아니다.

필요한 보완은 기존 용어·원문 RAG 위에 개별 판단의 도메인 경로 계약을 연결하는 일이다. 새 의미 스키마로 원문 전체를 다시 만들거나 별도 질문 서버를 추가할 필요는 없다. 현재 메모리의 단계 기록을 유지하되, 그 단계 안에서 생성하는 개별 판단과 도구 선택을 도메인 ID·방법·원문·조건에 결속해야 한다. 기존 하네스와 관계 프로토콜은 재사용할 기반이지만 과거 실패와 미연결 상태를 해결한 것으로 간주해서 가져오면 안 된다.

이후 구현 검증은 “ID가 맞는가”만 확인해서는 부족하다. 같은 경로를 다른 문장으로 설명해도 통과하는지, 다른 규정의 동일 용어를 적용하면 거부·보류하는지, 단순 참조를 곧바로 적용 근거로 취급하는지, 예외·사건 사실이 미확인인데 결론을 확정하는지, 등록되지 않은 길을 임의로 만드는지, 잘못된 관계를 정정하면 관련 판단만 다시 수행하는지를 확인해야 한다. 이 검증은 새 정의와 성공 기준을 먼저 동결하는 별도 실험으로 남길 범위다.
