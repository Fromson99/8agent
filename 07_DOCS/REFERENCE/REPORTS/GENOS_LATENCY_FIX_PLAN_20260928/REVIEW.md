# 수정 계획 자체 타당성 검토

검토 방식: 작성자가 원 코드·사진·공식 문서를 재대조한 자체 검토. 독립 에이전트/현장 시험이 아니다.
판정: **구현 방향은 조건부 타당**, 성능 개선률과 현장 병목의 최하위 원인은 **판단 유보**.
검토한 PLAN.md SHA-256은 EVIDENCE.json의 report_sha256으로 고정한다.

| ID | 중요도 | 근거와 영향 | 계획의 보완 | 문서 상태 | 실제 해결 |
|---|---|---|---|---|---|
| R1 | 높음 | 65초 rank의 CPU는 약 0.3초. NFS·잠금·throttling 원인이 구별되지 않음 | 구간 계측과 연결/mount/cgroup 대조 뒤 읽기 사본이나 lease 변경을 선택 | 반영 | 미실행 |
| R2 | 높음 | 정확 total·다음 페이지·동점 순서가 있는 현재 search를 LIMIT만으로 줄이면 계약 회귀 | 기존 완전 결과 계약 유지, 순위 캐시/동등 처리부터; 범위 pushdown은 별도 후보 | 반영 | 미실행 |
| R3 | 높음 | cached matcher.units는 최종 projection/structure binding에 따라 다를 수 있음 | 최종 불변 구조·projection/aliases 결속, 실패 시 검증 완료 캐시 금지 | 반영 | 미실행 |
| R4 | 높음 | journal의 선행 예약·FULL 동기 commit·복구 계약이 느려도 필수 | 의미 단위 batch, 기존 savepoint, 예약/결과 내구 경계와 HTTP 전 기록 보존 | 반영 | 미실행 |
| R5 | 높음 | 로컬 사본을 Store.path에 단순 대입하면 NFS 논리 binding/감사 경로가 달라짐 | 논리 세대와 물리 reader 분리, 복사 hash/상태 receipt 및 원복 | 반영 | 현장 로컬 저장소 미확인 |

| R8 | 중간 | rank→model.attempt 약 50초는 이벤트 공백이며 preview나 commit 한 항목의 측정이 아님 | 결과/프리뷰/원장/system drain/모델 view 시간 분할 | 반영 | 미실행 |
| R9 | 중간 | 기존 search는 반환 페이지의 preview만 만들지만 각 preview는 모든 block을 읽음 | 페이지 제한을 신규 개선처럼 설명하지 않고 block read/handle write 개선을 제안 | 반영 | 미실행 |

숫자 재검산:

- 문서 ID work 합: 23.420012 + 28.779313 = 52.199325초.
- 문서 ID CPU 합: 63.881 + 69.302 = 133.183ms = 0.133183초.
- 비CPU 차이는 약 52.07초지만 이 값을 모두 NFS 시간으로 해석할 수 없다.
- 네 반복 조회의 work 합: 첫 scan을 사진 근사 34.5초로 두면
  34.5 + 23.420012 + 42.904438 + 28.779313 = 129.603763초.
  과거 한 요청에서 관측된 비용의 합이며 새 코드의 절감 예측·p95가 아니다.
- rank work/CPU는 64.914512초/0.303707초. CPU를 제외한 시간에는 스케줄링·I/O·잠금 등이 포함된다.
- 약 153.6초 준비 시간, 약 65초 rank, 약 50.6초 후속 공백을 단순 합쳐 전체 답변 시간이나 예상 절감으로 제시하지 않았다.

외부 공식 문서는 rank/immutable/WAL/cgroup 구현 조건을 뒷받침한다.
우리 GENOS의 파일시스템·SQLite 실행계획·리소스 할당·성능 값을 대신하지 않는다.
현재 코드는 이미 ORDER BY rank와 요청별 fulltext 연결을 사용하므로, 그 기능이 없다고 전제한 수정은 제외했다.

다음 검증에는 선택 commit·generation·리비전 식별, 메모리/디스크 상한, 다음 페이지 전체 결과 동등성,
실패/취소/중복·팀/세대 변경, 진단 큐 장애, 원장 내구성과 publication recovery가 필요하다.
보고서 작성 요청에 따라 계획과 검토만 수행했으며 성능 실험·코드 수정·재배포는 시작하지 않았다.
