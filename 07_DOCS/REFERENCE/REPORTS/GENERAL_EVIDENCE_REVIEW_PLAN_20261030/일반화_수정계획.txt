최종 검토·원문 근거 연결의 일반화 수정계획
2026-10-30 / 설계안 / 구현·새 모델 실험·MAIN 승격 미실행

1. 목표와 기준 상태
특정 법률·조문·정답·표제 문자열에 대한 특례 없이, 법령·규정·매뉴얼 등에서 전체 자료를 확인하고 필요한 부분을 여러 요구에 나누어 사용하는 흐름을 지원한다.
자료 확보, 모델 전달, 의미 검토, 주장 채택, 답변 발행은 별도 상태로 유지한다. 한 단계 성공으로 다음 단계 성공을 추정하지 않는다.
선택 릴리스는 MAIN129다. 작업 코드에는 별도로 ADR1249 오류처리 수정이 있다. 구현 시작 시 양쪽 해시와 병행 변경을 다시 확인하고 수정 후보의 기준을 명시한다.
근거는 ADR1249 실제 실패와 09_ARTIFACTS/AUDITS/20261030-final-evidence-link-diagnosis/원인분석.txt 및 원인대조.json이다. 원래 검증 함수로 최초/보완 각각 같은 오류5개를 확인했다. 이 수치는 독립 품질 표본 수가 아니다.

2. 문제별 변경과 목표
가. 전체 읽기와 주장 인용을 같은 집합으로 검사
기존: 필요 근거 ∩ 주장 근거 ∩ 채택 판단 근거가 전체 읽기 목표를 덮어야 한다.
실제: 전체 원문이 있는데도 제목 또는 주장에 직접 사용하지 않은 항이 교집합에서 빠져 미완료가 된다.
수정: 확보/전달 영수증으로 읽기 범위의 완전성을 검사하고, 별도 범위 검토로 사용·제외·미해결을 남긴다. 각 주장은 자신을 뒷받침하는 근거와의 연결을 별도로 검증한다.
목표: 전체를 읽고 일부를 정당하게 사용하면 허용한다. 읽지 않은 예외나 핵심 미해결을 생략하면 계속 거절한다.

나. 자료 범위의 최초 쟁점과 의미상의 해결 연결을 혼합
기존: 읽기 목표의 최초 issue_id 하나를 최종 필요의 쟁점으로 고정하고, 연결된 모든 주장이 그 쟁점에 속하도록 요구한다.
실제: 같은 조문을 여러 쟁점의 주장에 사용하면서 다른 쟁점 주장 연결이 거절된다.
수정: 목표의 생성 목적/최초 쟁점은 불변 이력으로 남긴다. 요구·필요→해결 주장 관계와 주장→자료 범위 관계를 분리한다. 같은 자료를 여러 쟁점이 사용하는 것은 허용하되, 의미 필요의 해결은 해당 요구·쟁점과 연결된 주장으로만 증명한다.
목표: 다른 쟁점의 근거를 가져와 원래 필요를 해결했다고 주장하는 오류는 차단하면서, 공통 자료의 재사용을 허용한다.

다. 오류 안내 이후 같은 연결 반복
기존: 전체 필수 근거 목록과 포괄적 오류 문구를 전달한다.
실제: 보완 안내는 전송됐지만 needs/judgments가 그대로 반복됐다.
수정: 누락 범위, 실제 연결, 충돌한 주장·쟁점, 실패한 검증 단계와 허용되는 수정 종류를 함께 전달한다. 정답이나 의미 판단은 서버가 대신 채우지 않는다.
목표: 무엇을 바꿔야 하는지 기계적으로 특정한다. 안내 개선의 실제 모델 효과는 새 실험 전까지 미확인이다.

3. 제안 계약: 서로 다른 책임을 가진 검증 네 단계
아래 명칭은 설계상 책임 구분이며 새 API나 저장 스키마가 이미 있다는 뜻이 아니다.

A. 확보·전달 검증 — 서버 책임
기존 evidence_inventory의 좌표·판본·권한·본문 해시와 confirmed_pages를 재사용한다. 목표별 expected/acquired/presented 및 missing spans를 서버가 계산한다.
모델이 acquired=true라고 출력하거나 목표 ID만 나열해서 통과할 수 없다. 완전성은 해당 요청·판본·권한·전달 기록과 결속한다. 과거에 읽었지만 이번 검토 입력에서 원문을 확인할 수 없는 범위는 재제시 또는 별도의 검증 가능한 입력 결속이 필요하다.

B. 범위 검토 — 모델 판단, 서버 구조 검증
필요한 각 범위를 사용, 이번 요구에서 제외, 미해결로 명시한다. 같은 이유·처리를 가진 연속 구간은 묶을 수 있다. 범위 목록은 기존 문서 구조/좌표로 제공하며 모델이 새 원문 구간을 창작하지 못한다.
검토 대상 범위에서 빠진 구간, 상충하는 중복 분류, 미제시 자료에 대한 확인 완료 주장을 서버가 거절한다. 범위 밖 전체 corpus를 새 검토 대상으로 확대하지 않는다.
제목·표·부칙·조건문도 이름이나 정규식으로 자동 제외하지 않는다. 제외는 사용자 요구 또는 현재 원문에 연결된 명시적 이유를 가진다. 반대 근거·예외·기존 검토 목적은 처리 내역을 남겨야 하며, 전체 원문을 읽었다는 사실만으로 해결 상태가 되지 않는다.
서버는 분류와 참조의 완전성을 검사할 뿐 제외 이유의 법률적 타당성을 완전히 증명하지 못한다. 이는 별도 의미 평가의 대상이다.

C. 필요·주장·근거 연결 — 관계별 검증
원래 필요 ID/문구/선언 이력은 보존한다. 의미 필요와 자료 확보 작업을 구분한다. 복합 필요를 나눌 경우 원래 필요와 하위 항목의 대응·이유를 남기고 원래 요구의 누락 여부를 검토한다.
한 자료→여러 쟁점, 한 주장→여러 자료, 한 필요→여러 주장 관계를 지원한다. 자료 목표의 최초 issue_id를 모든 소비 주장에 강요하지 않는다.
각 해결 연결별로 실제 claim 존재, 관련 요구/쟁점, 그 claim의 근거, 채택 판단과 해당 근거의 연결을 검증한다. 서로 무관한 claim/judgment의 근거를 합집합으로 모아 한 주장을 정당화할 수 없게 한다.
전체 필요가 해결됐다는 판정에는 모든 필수 하위 요구의 처리와 미해결 여부가 반영되어야 한다. 단순히 어느 주장 하나가 Q1을 포함한다고 전체 필요가 해결되는 것은 아니다.

D. 최종 완료 판정 — 서버 책임
A/B/C와 기존 요구사항·본문·인용 검증을 모두 통과한 결과만 저장·발행한다. 핵심 미해결은 기존 gap/부분답변/보류 계약에 반영한다. 유효한 답변이 없는 경우 실패를 보존한다.
범위 검토 완료가 답변 내용 정확성 인증은 아니다. 모델이 선택한 규칙·조건·예외의 의미 검증은 기존 검사를 유지하고 평가에서 확인한다.

4. 변경 지도와 소비자
- need_continuity.py: extend_context/extend_schema/validate_review/resolution_links/pending_goals. 의미 필요와 확보 목표 분리, 검증 단계 분리, 여러 관계와 새 완료 영수증을 함께 반영한다. 현재 교집합 한 줄만 없애는 패치는 하지 않는다.
- evidence_inventory.py: 기존 expected/covers/confirmed_pages/check_presented_page 재사용. 새 중복 원문 저장소를 만들지 않고 부족 범위와 입력 결속을 계산한다.
- source_goal_control.py, read_judgment.py: 생성 목적·최초 쟁점·need_refs·원문 도착 이력 보존. 새 해결 연결이 원래 원문 목표를 덮어쓰지 않게 한다.
- read_judgment_final.py: context/schema/validate_review/retain 및 과거 review 재사용에 새 계약 연결. 구조 검증과 상태 검증 성공 후에만 새 영수증을 저장한다.
- completion_execution.py: ASSESS 최초/보완 경로, finish_assessment 및 pending_goals 소비를 수정한다. 새로운 보완 호출 담당자를 만들지 않는다.
- output_contract.py: 확보 부족, 검토 미처리, 요구-주장 불일치, 주장-근거 불일치를 별도 진단으로 제공한다. 실제 누락/충돌 대상과 필드 경로를 명시한다.
- numbered_references.py, stable_references.py, compact_model_input.py, decision_projection.py, minimal_output.py: 새 참조의 등록·표시·복원·축약·생략 기본값을 양방향 검증한다. 실제 전송값과 canonical의 의미가 같아야 한다.
- JSON 영수증/재개/보고 소비자: 새 버전 해시를 포함하고 읽기·중복 처리·오류 표시를 함께 확인한다. 상세 원문/전송 로그의 저장 정책은 기존 그대로 둔다.

5. 오류 처리와 재개
미확보/미전달은 필요한 범위 확보·재제시로 처리한다. 이미 확보된 자료의 연결 오류는 같은 입력에서 보완하며 무의미하게 다시 검색하지 않는다.
실제 내용·조건·예외가 미해결이면 기존 의미 재검토/조사 경로를 사용한다. 사용자 사실 질문은 실제 사건에 필요한 사실이 부족할 때만 한다.
기존 ASSESS 최초+보완1회와 전체 물리 호출·deadline 예산을 유지하는 것을 초기 구현 기준으로 한다. 같은 실패는 규칙·need/target/claim ID·범위·입력 버전으로 비교하고 문구 변경으로 예산을 초기화하지 않는다.
추가 조회가 필요하면 기존 independent_research의 정확한 미확보 조건을 유지한다. 동일 근거 연결 실패를 새 조사로 포장하지 않는다.
UNKNOWN/429 처리와 실패 원인 보존은 ADR1249 수정과 함께 회귀 검사한다. 예산을 늘려 통과시키는 방식은 채택하지 않는다.

6. 저장·버전 호환
새 검토 계약을 버전으로 구분한다. 과거 실패/완료 영수증을 새 규칙으로 재해석해 성공 처리하지 않는다. 기존 데이터를 일괄 변환하지 않는다.
새 요청만 새 계약을 사용하고 과거 완료 기록은 원래 버전으로 조회한다. 진행 중 구버전 요청은 해당 버전 실행기를 유지하는 방식과 명시적 중단 방식을 배포 전에 확정한다. 버전이 맞지 않으면 자동 재전송하지 않는다.
원문·벡터 재적재는 계획하지 않는다. 기존 구조화 JSON 저장 경로를 활용하며 DDL 불필요 여부는 실제 serializer/reader와 Oracle 저장 연결 확인 후 확정한다.
SQLite와 Oracle이 같은 검증 결과·영수증 의미를 가져야 한다. 저장소별로 다른 의미 규칙을 만들지 않는다. 새 기록을 읽지 못하는 구버전으로 단순 전환하지 않으며, 롤백 시 새 요청 라우팅과 기록 조회 호환성을 먼저 확인한다.

7. 검증 계획과 통과 기준 — 아직 실행하지 않은 목표
먼저 저장된 실패 입력/응답은 불변 회귀 근거로 둔다. 새 계약에서 과거 응답을 자동 정답으로 채택하는 것이 목표는 아니다. 정확한 재현과 새 구조의 올바른 제안 수락을 분리한다.
정상 사례: 전체 확보 후 일부 인용, 한 자료를 복수 쟁점에 사용, 여러 자료로 하나의 주장 구성, 범위 검토에서 정당한 제외, 여러 필요의 부분 해결.
반례: 예외 미확보, 중요 구간 검토 누락, 주장과 무관한 근거, 다른 쟁점으로 필요 대체, 다른 claim의 근거 빌리기, 미확보를 제외로 위장, 오래된 판본/권한/상태, 중복 ID/겹치는 상충 범위.
불변성: 문서명·조문번호·ID 이름·행 순서·분할 경계를 바꿔도 의미가 같으면 동일 판정. 분할 구간은 기존 covers 규칙으로 평가하고 한 문서의 근거를 다른 문서에 합치지 않는다.
연결 검증: canonical→실제 wire→복원, native API, 실패 후 조회, 같은 성공 요청 재조회 무호출, 상태/CAS/영수증 hash 및 예산 보존.
표본은 법령의 다른 구조뿐 아니라 일반 규정·매뉴얼을 포함한다. 개발에 사용한 질문과 미사용 질문을 분리하고 같은 질문의 의역을 독립 사건으로 세지 않는다.
필수 정상 구조 통과와 안전 반례 거절을 사전 기준으로 고정한다. 실제 답변은 원문 충실성·요구 충족·예외 누락·제외 타당성을 별도 평가한다. 성공률·비용 허용치와 중단 기준은 표본/예산을 확정한 뒤 첫 실험 전에 동결한다.

8. 실행 순서와 기대치
1) 새 ADR 선점, 기준 코드/데이터·실패 계약·회귀 사례 동결.
2) 격리 후보에서 새 계약·순수 검증기부터 구현.
3) 입력 투영·보완·상태 저장·재개·보고 소비자 통합.
4) 합성 정상/반례와 실제 저장된 실패 진단 및 native API 확인.
5) 별도 승인 범위의 실제 SQLite 모델 시험, 이후 Oracle 저장/API 동등성 검증. SQLite 결과를 Oracle 성능으로 확대하지 않는다.
6) 근거를 검토한 뒤 필요한 작업 변경 결합과 공식 MAIN 반영을 구분해 수행.
이번 요청은 계획 수립이며 위 구현·실험을 시작하지 않았다.
목표는 잘못 결합된 완료 조건을 바로잡는 것이다. 성공률/시간/비용 개선 수치는 미산정이다. 기본 모델 단계는 늘리지 않는 설계지만 범위 검토와 진단 정보가 늘어 입력·출력 토큰과 저장량이 증가할 수 있다. 기존 좌표와 동일 이유 범위 묶기를 사용해 중복을 줄이고, 범위가 커서 입력에 못 들어가면 검토를 생략하지 않고 기존 페이지/예산 경로로 처리한다.

설계는 자체 검토이며 독립 감독 검토나 실제 성능 인증은 아니다.
