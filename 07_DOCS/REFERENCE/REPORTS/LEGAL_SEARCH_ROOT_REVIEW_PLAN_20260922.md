# 조문 시작점 검토와 연결 원문 보존 — 구현 계획

상태: 설계 제안. DB 관계 생성 수정은 사용자가 담당한다. 이번 작업은 코드 읽기와 계획 작성이며 구현·모델 호출·신규 평가·MAIN 전환을 하지 않았다. 자체 검토이며 독립 감독 검토가 아니다.

## 결정할 구조

모델은 시작점의 필요성을 판단하고, 하네스는 그 시작점의 연결 묶음을 관리한다. 시작점을 제외하면 그 시작점만 소유하던 연결 조항을 최종 출처에서 제외한다. 다른 채택 시작점이 소유하면 유지한다. 연결 조항을 개별적으로 삭제하는 모델 호출은 없다. 원문과 제거 이력은 저장소에 보존한다.

핵심 구분은 **원문 보존 단위는 조 전체, 연결 탐색 단위는 실제 항·호·목 범위**라는 것이다. 한 조의 전문을 읽거나 보존했다고 그 조의 모든 항·호에서 새 탐색을 시작하지 않는다. 직접 시작점으로 검토하여 채택한 범위와 연결로 도달한 범위를 구별한다.

## 실행 순서

|단계|모델의 판단|코드의 책임·산출물|
|후보 등록|질문 요구와 후보의 예상 역할을 파악|직접 검색 시작점·회수 경로·반복 회수·원문 세대를 고정. 빈도는 법적 관련성의 증명으로 사용하지 않음|
|시작점 예비 검토|채택 후보 / 추가 읽기 / 제외 검토를 구분|발췌만 보고 확정 제외하지 않음. 누락된 응답은 보류. 후보 수 대신 입력 토큰에 맞춰 분할|
|원문·관계 확인|근거 범위와 필요한 문맥을 읽고 질문에서 담당할 역할 판단|정확 READ의 제시 범위·미제시 범위 기록. 연결 구조와 원문 확인을 도와 시작점의 역할을 파악하되 연결 조항 개별 삭제는 금지|
|시작점 최종 검토|KEEP / DEFER / DROP, 담당 질문 요구·근거·간단한 사유|DROP은 명시 판단만 반영. 대체를 이유로 제거하면 실제 남은 시작점 묶음의 근거를 지정. 연결 조항에만 결정 근거가 있는지도 검토|
|묶음 확정|추가 삭제 판단 없음|채택 시작점의 유효 연결 원문을 결합. shared owners 계산, 선택 취소 시 소유자 재계산, 순환·중복 제거|
|최종 축소 검토|선택한 시작점 중 역할이 겹치거나 무관한 것을 다시 검토|제거가 제안된 시작점의 묶음 차집합을 함께 제시. 유일한 요건·예외·반대 근거가 사라지면 보류. 유효한 대체가 있으면 원자적으로 교체|
|답변·출처|보존한 근거를 읽고 주장 작성·검토|시작점, 연결 출처, 실제 주장 인용을 구분. 관계 종류·방향·항호·원문 근거 표시. 제외된 묶음은 감사 기록에만 남김|

시작점의 역할 중복 여부는 조문 제목이나 source_id 중복으로 판단하지 않는다. 질문의 어떤 요구에 어떤 원문이 남는지 비교한다. 코드가 법적 충분성을 완전히 증명할 수는 없으며, 모델의 근거 지정·판단 기록과 별도의 답변 검토로 확인한다.

## 연결 확장 정책 제안

DB가 정확하더라도 올바른 관계 전체를 양방향으로 무제한 연결하면 검색 범위는 넓어진다. 다음은 DB 수정과 별개인 검색 정책 제안이다.

|경로|보존·확장 방법|
|채택 시작점의 직접 연결|검토한 항호 범위에 걸리는 확정 참조를 회수. 원문 전문은 보존하고 실제 연결 범위도 별도로 유지|
|정방향 참조·준용·위임 연결|도달한 항호 범위 안의 명시 참조를 연속 추적. 원문에 나타난 방향과 관계 종류를 유지|
|역참조|채택 시작점의 실제 범위에 대한 직접 역참조를 보존하고, 그 원문 범위의 정방향 의존을 추적. 연결로 도달한 모든 노드에서 역참조를 다시 열어 다른 가지로 번지게 하는 방식은 기본안에서 제외|
|새로운 역참조 탐색 필요|질문 요구가 해결되지 않은 경우 탐색 단계에서 추가 시작점 후보로 등록하고 별도 판단. 연결 조항을 몰래 새로운 시작점으로 승격하지 않음|
|항호 좌표가 없는 조 전체 참조|조 전체 범위임을 명시하고 넓은 연결을 허용. 필요한 원문을 임의의 개수로 자르지 않음|
|복수 대상|DB의 확정된 모든 target별 범위를 보존. 임의 한 대상 선택 금지|
|모호함·미회수·시간 부족|원문 확보·검토 완료로 표시하지 않음. 미완료 연결 목록과 재개 위치 기록|

위 역참조 규칙은 사용자에게 제안하는 기본안이며 확정된 기존 요구사항으로 간주하지 않는다. 핵심 불변식은 '정의한 유효 연결 묶음 안에서 모델이 자식을 따로 제거하지 않는다'이다. 전문 보존과 탐색 범위 축소를 혼동하지 않는다.

## 계약·상태

아래 명칭은 제안이다. DB 필드를 새로 강제하기보다 수정된 navigation 계약의 source/target별 좌표·범위·방향·relation ID를 어댑터에서 정규화한다.

- `RootDecision`: root ID, question revision, KEEP/DEFER/DROP, 읽고 제시한 근거 범위, 검토한 범위, 질문 요구별 역할, 사유, 대체 근거. 원문 범위가 부족한 판정은 DEFER.
- `RelationTraversalReceipt`: relation ID, source/target 좌표·항호 범위, 법적 방향과 탐색 방향, 원문 witness/hash, navigation generation/hash, 권한·해소 상태, root owner, 부모 경로. 방문 키에 source ID뿐 아니라 범위와 탐색 상태를 포함해 순환을 처리.
- `RootBundle`: root revision, 포함 원문 ID, 원문 읽기/모델 제시 범위, root별 유효 경로, pending 연결, traversal policy revision. 전체 집합과 페이지 표시를 분리.
- `RootReviewBundle`(새 공개 투영 버전 제안): 모델 선정 시작점과 시스템 보존 연결의 서로 다른 근거 유형, 원문 링크·해시·범위, owners, 관계, 실제 claim citations, 완료 상태. 기존 `source-tiers-v4`에 무단 필드를 추가하지 않고 새 버전과 소비자를 함께 연결.

연결 ownership은 relation generation, 질문/선택 revision, 탐색 정책에 결속한다. 시작점이 변경되면 기존 연결 선택·답변·출판 bundle을 무효화하고 해당 요청에서 재계산한다. 공유 조항은 owner 집합이 비었을 때만 최종 출처에서 사라진다. 순환이 자기 자신을 owner로 만들어 살아남지 않게 원래 채택 root까지 유효한 경로를 요구한다.

DROP 제안에 대한 새 판단이 실패하면 직전 검증 상태를 유지한다. 첫 검토 실패 시 전체 회수 원문을 보존하되 이를 전부 '최종 채택' 또는 '인용 근거'로 표시하지 않는다. 모델 응답 일부 누락은 보류로 처리하고 대량 삭제로 해석하지 않는다. 모델·provider 자동 fallback은 하지 않는다.

사용자 DB 수정본은 신규 navigation 세대와 해시를 제공해야 한다. 원문·source ID가 동일하면 검토 코드 변경만으로 원문 재수집은 필요하지 않지만 기존 경로·ownership·모델 판단 캐시는 무효다. source ID/좌표가 바뀌면 evidence 매핑과 평가 정답 좌표도 별도로 이행한다. 다른 세대의 관계와 원문을 한 요청에 섞지 않는다. 권한이 변경되면 출판과 원문 열기 단계에서 재검증한다.

## 검증·도입 순서

1. 수정 DB 계약과 조회 어댑터를 먼저 맞춘다. DB 내용을 이 작업에서 임의 수정하지 않는다.
2. 합성 계약 검사: root 제외/공유 owner/순환/항호 불일치/역참조 방향/미회수/권한·세대 변경/응답 누락/대체 실패를 확인한다. 연결 조항에 독립 DROP 호출이 없는지도 검증한다.
3. 실험 실행을 진행하기로 한 후 새 ADR을 선점하고 가설·모델·데이터·기준을 동결한다. abandoned ADR0519는 완료 부모로 사용할 수 없으며 진단 dependency로만 참조한다. 정확한 완료 부모 arm을 별도로 선택한다.
4. 비교 시 수정 DB·같은 원문·같은 모델을 기준/후보에 동일 적용하여 DB 수정 효과와 검토 코드 효과를 혼합하지 않는다. 기존 노출 문항은 회귀용, 독립 문서/질문군은 일반화 평가용으로 구분한다.
5. root 선택 필수 근거 손실, 유효 연결 손실, 배타적 가지 제거, shared 보존, 실제 모델 제시/인용 범위, 최종 답변 품질, 호출/토큰/실제 종단 p95를 따로 기록한다. 출처 풀 보존을 답변 인용 성공으로 계산하지 않는다.
6. 계약·성능 검증 뒤 서비스 통합 후보와 코드/데이터/설정 묶음을 만든다. MAIN 승격은 별도 절차이고 rollback은 코드·navigation·프로필을 함께 이전 묶음으로 되돌린다.
