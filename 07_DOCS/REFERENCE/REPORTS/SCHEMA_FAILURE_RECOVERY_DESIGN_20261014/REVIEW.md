# 모델 출력 계약 수정 설계 자체 검토

검토 방식: 같은 작성자가 현재 코드·과거 원기록을 대조한 자체 검토. 독립 에이전트 검토나 실제 성능 인증이 아니다. 대상은 [PLAN.md](PLAN.md), 근거는 [HISTORY.md](HISTORY.md)와 [EVIDENCE.json](EVIDENCE.json)이다. 최종 문서 hash와 링크·명령/파일 확인 결과는 [VALIDATION.json](VALIDATION.json)에 남긴다.

**구현 가능성: 조건부 타당.** 기존 실행기 안에 적용할 변경 지점과 선행 조건이 식별됐다. branch key 형식, 공급자별 문법 수락, 재개/DB 버전 이행은 구현·검증 전이며 그 조건을 충족해야 한다.

**예상 효과: 미산정.** 이번 자료로 전체 오류율·성공률·비용 절감률·일정을 예측하지 않는다. 과거의 작은 후보 성공과 스키마 문자 감소를 현재 GENOS 성공률로 전용하지 않았다.

## 발견사항과 반영

| ID | 중요도 | 직접 근거와 영향 | 문서 반영 | 구현·검증 해결 |
|---|---|---|---|---|
| RV01 | 높음 | 현재 control의 `correction_schema`는 full decision. 과거 부분 수정의 성공만 보고 sparse merge를 재도입하면 행동/근거의 상호 제약이 깨질 수 있음 | 기본안은 full correction, 부분 교정은 동일 binding·discriminant·원자적 의존 묶음의 별도 후보로 제한 | 미구현. 과거 반례와 실제 control API 검증 필요 |
| RV02 | 높음 | `NavigationReferences`는 객체 key를 변환하지 않으며 `relations_repository`는 wire와 저장 view를 재대조 | key codec·mapping receipt 버전·unknown/충돌 key 검사·원시 중복 JSON key 검사를 P2 선행 조건으로 추가 | 미구현. 객체 후보를 현행 codec에 바로 연결할 수 없음 |
| RV03 | 높음 | 참조 선택 `unit_relations._navigate`의 단계 재판단과 gateway 형식 교정이 함께 가능 | 7절에 실제 경로와 조건부 physical 4회 계산, 한 owner와 동일 결정 예산 검사 추가 | 미구현. 정상 참조 조회·재개·후검증까지 같은 owner로 통합 필요 |
| RV04 | 높음 | 전송에서 uniqueItems를 빼는 현재 계약은 서버의 원래 검증을 전제로 함 | 의미 동등 변환과 제약 이동을 분리; 무조건 느슨한 schema 금지 | 기존 동작 보존, 새 projection은 공급자별 별도 검사 필요 |
| RV05 | 높음 | strict 구조 검사에서 즉시 종료하면 완전 동일 중복의 허용 보정이 도달하지 못할 수 있음 | 안전한 shape/자원 한도 확인·위반 수집 → allowlist 보정 → 전체 재검증 순서 명시 | 미구현. 다른 구조·근거 오류가 보정으로 통과하지 않는 반례 필수 |
| RV06 | 중간 | 초안 변경 지도에 실제 모듈이 아닌 reference_navigation 이름이 있었음 | 실제 `unit_relations.schema/validate/_navigate`로 교정; profile validator도 실제 코드 명시 | 문서 수정 완료. 제품 변경 없음 |
| RV07 | 높음 | 현재 profile loader는 unknown key와 enum을 거절 | 설정 파일만으로 새 복구 정책 활성화 불가, validator·pin·프로필 이행 포함 | 미구현. 닫힌 소비자 schema 및 구버전 round-trip 필요 |
| RV08 | 높음 | 과거 축소 후보0730은 실제 기준 미충족. 에러 감소를 모두 PENDING으로 만드는 식으로 달성할 수 있음 | 정상 완료·제한·실패·의미 회귀와 토큰·시간을 별도 판정, 미확인 전환으로 지표 개선 금지 | 실제 비교 미실행 |
| RV09 | 높음 | runtime binding과 현장 설치 버전은 사진으로 확정 불가 | 작업/선택/GENOS를 분리, 현장 원인 세부와 코드 리비전 미확인 명시 | 현장 내부 모델/배포 검증 필요 |
| RV10 | 중간 | 기존 tests의 fixture/SQL/consumer 불일치가 남아 있음 | 삭제·xfail로 검사를 없애지 않고 현행 API에서 기존 보장 행동을 다시 검사 | 앞선 진단 6통과/1fixture 실패 및 BL-010 기존 실패를 해결로 계산하지 않음 |
| RV11 | 높음 | 로그·답변·shortcut 성공 상태가 서로 다르면 복구된 척할 위험 | 실제 발행·SSE·보고서·재사용 검사, partial는 의존 묶음과 gap까지 검증 | 구현과 API/저장 연계 검사 필요 |
| RV12 | 중간 | 분량·회귀 숫자는 모델·질문·시점이 서로 다름 | 빈도 통계와 과거 후보 수치를 분리. 전체 개선율/인일 미산정 | 현재 대표 원장과 독립 비교 필요 |

문서에 위험을 설명한 것은 구현 해결이 아니다. 이 표의 미구현 항목은 P0~P7의 종료 조건이며 모든 항목이 해결됐다고 보고하지 않는다.

## 수치 검토

- MAIN 포인터 generation 61은 상태 식별자이며 성능 수치가 아니다. EVIDENCE의 파일 대조는 저장 파일 해시 확인이고 실행 중 서버 검증이 아니다.
- 관련 53파일 중 44개 작업/선택 일치, 4개 차이, 5개는 서빙 릴리스 외 구축/CLI 범위다. 차이가 있는 기존 계측·보고·엔진 pin 변경은 후속 통합 시 보존할 대상이다. 같은 저장소라는 이유로 모든 작업 코드를 선택 릴리스 기능으로 계산하지 않았다.
- N01의 `2 × (1 + 1) = 4`는 단계 호출과 각 gateway 형식 교정의 조건부 상한 계산이다. 실제 발생 횟수나 전송 retry를 포함한 전체 상한으로 쓰지 않았다.
- T01~T07의 0건/0회는 동결 검증 범위의 목표다. 미래 전체 위험 0 또는 법률 정답100% 주장이 아니다.
- 이전 진단의 6통과/1실패는 해당 대화에서 수행한 검사 결과다. 이번 설계 작성에서 실행한 새로운 제품 테스트 수가 아니다.
- `순 호출 절감`은 호출 수/요청 단위로, 시간은 같은 환경의 요청 wall time으로 별도 측정한다. 문자→토큰, 호출→비용, 평균→p95 환산을 하지 않는다.
- 외부 가격·성능 전망을 사용하지 않아 외부 자료의 최신성 검증이나 수치 전용은 없다. 근거는 저장소의 당시 기록과 현재 코드다.

## 남은 결정과 실행 조건

1. P0에서 현장 원본 payload·실제 코드/모델·schema/consumer binding이 확보되지 않은 사건을 분리한다. 현재 알려진 제약 때문에 내부망 접근을 재시도하지 않는다.
2. 역할별 owner와 정본 계약을 명시하고, 객체 key 표현의 사용 여부는 공급자 호환과 비용·완료 회귀를 확인한 별도 동결 후보로 결정한다.
3. 실제 표본·허용 회귀·지연/비용 기준을 첫 호출 전에 확정한다. 과거 실패 질문을 holdout으로 선언하지 않는다.
4. 제품 코드 통합 후 같은 코드로 검증하고, 로컬 MAIN 선택 및 서비스 진입점, GENOS 반입·배포·워크플로우 결과를 각각 기록한다.

이번 검토는 계획의 구체성과 보존 조건을 확인한 것이다. 실제 배포 승인이나 모델 효과 검증 결과가 아니다.
