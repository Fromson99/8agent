Dataiku 개발 Silver → 운영 Gold 테이블·컬럼 명칭 전환 계획
작성: 2026-10-23 / 상태: 설계 초안, 메타 미승인, DB·런타임 미변경

1. 이번에 정할 기준

운영 Gold에 사용할 하나의 논리 모델과 물리명 세트를 먼저 정한다. 개발계 Silver에도
그 이름과 컬럼 구조로 새 테이블을 만들어 적재·조회·재개를 검증한다. 운영으로 갈 때는
동일한 코드와 이름 세트를 사용하고 연결·owner·권한·선택 release를 환경별로 지정한다.
개발용 이름에 _S를 붙였다가 운영에서 다시 _G로 바꾸는 방식은 기본안으로 사용하지 않는다.
실제 표준이 접두/접미사를 요구하면 승인된 규칙을 YAML의 물리 매핑에 반영한다.

운영의 저장 책임은 유지한다. 구조화 원문·온톨로지·재사용 위키는 Gold, 질문·판단·실행
상태는 Agent, 파일 분할 자산은 승인된 이관/보관 영역이다. 개발 Silver에 함께 존재해도
이 책임 구분은 YAML에 남긴다. 지원 메타데이터 3개의 운영 Gold 배치는 승인 검토 대상이다.
실버·골드 이름만 바꾼다고 배치의 중단 복구나 최종 적재 보장이 완성되지는 않는다.

기준은 기존 ORACLE_GOLD_SELECTION.md와 9테이블 DDL이다. 새로 병렬 모델을 만들지 않고
그 선정안에 후보 물리명·컬럼명·환경 매핑·코드 변경 계획을 추가했다.

2. 범위와 상태

1차는 지금 인계된 Dataiku/GENOS 파이프라인과 Oracle 직접 조회가 사용하는 전체
9개 테이블·46개 물리 컬럼이다. Gold 후보는 지식 4개와 지원 3개, 합계 7개·36컬럼이다.
Agent 1개·5컬럼과 이관/보관 1개·5컬럼도 누락하지 않고 같은 매핑 목록에 넣었다.
RELEASE.CREATED_AT은 INSERT에 명시되지 않아도 DB에 존재하는 기본값 컬럼이므로 포함한다.

코드 기준: GENOS 서비스 R2 및 Dataiku 실행 R3. 핵심 Oracle 모듈 6개는 검토한 작업 코드와
봉인 R2 ZIP의 바이트가 같다. 활성 로컬 MAIN102는 별도 동결 릴리스이며 이번에 수정하지 않았다.
현장 증거: 기존 9개 이름을 조회할 수 있는 사진과 입력 준비 READY까지. 실제 컬럼·권한·
전체 적재·조회·새 코드서빙 배포는 이번 작업에서 확인하지 않았다.

전체 온톨로지·위키 목표가 9개로 끝난다는 뜻은 아니다. lk_* 3개, basis_* 8개와 v3 설계
18개, 기존 sw_* 계열은 FOLLOWUP_SCOPE.csv에 구분했다. 현장 미생성/미연결 대상을
현재 Oracle 테이블로 집계하지 않았다. 이들의 실제 저장 모델 변경은 1차 개명과 별도다.

갱신·완료 기준, 산식·단위, 원천·결합, 주의, 오너, 예시 SQL을 작성했다. 46개 컬럼마다
한글 논리명, 업무 의미, 허용값·코드·범위, 산식·생성 규칙을 작성하고 명칭 선정 이유와
타입 유지 이유를 보강했다. 테이블의 MASTER/SNAPSHOT 분류 이유와 Gold 선정/제외 이유도
별도로 기록했다. 담당자·보유기간·고정 배치 시각·표준 승인값은 확인 필요로 명시했다.
설명 작성 완료를 전사 메타 승인이나 현장 데이터 전수검사 완료로 간주하지 않는다.

운영 검토 보완: 위 추가 6개 시트는 기존 등록 양식의 새 필수 항목으로 단정하지 않는다.
이 프로젝트의 개발 Silver 검증과 Gold 전환을 위해 코드 계약·기존 프로젝트 지침에서
추가한 검토 자료다. 추가 전 설명 보완본은 history/20261023_before_operational_details.zip에
보존했다. 물리 스키마는 여전히 9테이블·46컬럼이며 감사용 컬럼을 일괄 신설하지 않았다.

전사 표준사전의 실제 승인 목록은 확보되지 않았다. LGL, PBLS, DOC 등 영문 약어와
한글 논리명은 모두 후보이며 승인 물리명이라고 보고하지 않는다. 후보명을 Silver에
실제로 생성하기 전 사용자/표준 담당자의 명칭 확정이 필요하다. 메타 등록과 DBA 생성은 별도다.

5. 컬럼명과 타입의 변경 원칙

전체 46개는 엑셀/CSV/YAML에 일대일로 작성했다. 같은 문자열도 의미에 따라 매핑한다.
- DOCUMENT_ID → DOC_ID, PARENT_ID → PRNT_UNIT_ID, TEXT → BLK_TXT_CN.
- DATASET_VERSION → DATA_VER_ID. 기존 해시성 문자열을 숫자 버전으로 바꾸지 않는다.
- 원문 RELEASE_ID → SRC_PBLS_ID, 조회 RELEASE_ID → SRCH_PBLS_ID.
- SOURCE_JSON → DOC_JSON_CN / UNIT_JSON_CN / BLK_JSON_CN: 소유 테이블에 따라 구분.
- VALUE_JSON → ROW_JSON_CN 또는 ST_JSON_CN: 조회 지식과 실행 상태를 구분.
- REVISION → CHG_SEQ_NO: 동시 수정 순번이며 원문 법령 판본과 구분.
- CREATED_AT → REG_DTM: DB 등록시각이며 법령 시행일과 구분.

1차는 물리 이름만 바꾸고 기존 값·타입·NULL·PK·해시 생성법·CLOB 저장을 보존한다.
원문, 긴 이름과 JSON을 임의 길이 VARCHAR로 줄이거나 모든 문자열을 일괄 1.5배 늘리지 않는다.
현행 VARCHAR2(... BYTE), CLOB, NUMBER, TIMESTAMP WITH TIME ZONE을 후보 타입으로 기록했다.
최종 VARCHAR/VARCHAR2 표기, BYTE/CHAR, 인포타입은 승인 모델·현장 DB 문자셋과 대조한다.

중요한 개별 검토:
- DOC_NM의 현재 타입은 CLOB이다. 표준 명 도메인과 다르면 실제 최대 길이와 승인 타입을 검토한다.
- JSON_TXT_OMIT_YN의 현재 값은 NUMBER(1)이며 NULL도 허용한다. 표준 여부가 CHAR(1)인 경우
  0/1/NULL ↔ N/Y/NULL 같은 가역 변환을 별도 계약으로 정하고 왕복 검증해야 한다.
  현재 YAML의 codec은 identity이고 문자형으로 자동 변환하지 않는다.
- ROW_KIND_CD는 native.* 및 asset_*.논리테이블 등 기존 문자열 계약이다. 01/02 등 임의 코드화 금지.
- PART_SEQ_NO는 0부터 시작하고 ORG_BYTE_CNT는 압축 전 바이트 수이다.
- PART_B64_CN은 zlib 압축 뒤 Base64 인코딩한 값이다. 단순 Base64 원문으로 오해하지 않는다.
- ID 사용은 외부 인터페이스·불변 식별자의 예외 여부를 확인한다. 표준 논리명이 번호여도
  긴 문자열·해시·선행 0을 숫자로 바꾸지 않는다.

후보 영문 물리명은 30 ASCII 바이트 이내, 한글 컬럼 논리명은 초안 UTF-8 계산 30바이트 이내로
검사한다. 이는 내부 가이드의 실제 산정 문자셋이나 언더바 허용 여부의 승인 확인을 대신하지 않는다.
PK/FK/CHECK/index 이름도 함께 변경한다. 원문 3테이블의 논리 관계를 이번에 신규 물리 FK로
추가하지 않는다. FK 추가는 적재 순서·부모 누락·성능 검토가 필요한 별도 구조 변경이다.

6. YAML의 책임과 코드 정합성

YAML은 전사 메타 사전이나 법률 용어집을 대체하지 않는다. 승인된 논리 계약을 실제 DB
객체에 연결하는 배포 설정이다. 하나의 YAML에서 DDL 검토본·컬럼 정의서·스키마 검사·
SQL builder를 생성하도록 한다. 엑셀은 검토용 내보내기이며 승인 후 YAML이 실행 매핑 정본이다.
양쪽을 독립 편집하지 않고 검토 변경을 YAML에 반영한 뒤 엑셀을 다시 생성한다.

현재 초안은 다음을 포함한다.
- 논리 테이블 ID, 기존 이름, 후보 물리명, 역할, 전체 컬럼 매핑.
- 컬럼의 코드 키, 논리명, 타입·NULL·기본값·codec와 표준단어/용어/도메인/인포타입 승인란.
- 논리 키로 선언한 PK/FK/CHECK/index와 승인 후보 이름.
- legacy_sidda / dev_silver / prod_gold 프로필 및 역할별 owner.
- 테이블 metadata의 Bizmeta·Description 11항목·명칭/유형/레이어 선정 이유, 컬럼 metadata의
  업무 의미·허용값·산식·명칭/타입 이유·코드 근거. 엑셀과 붙여넣기 TXT는 같은 내용으로 생성한다.

legacy_sidda의 SIDDA만 기존 코드에서 확인한 owner다. 개발 Silver와 운영 Gold/Agent/보관
owner는 null로 남겼다. 접속 계정·ORDS alias·Dataiku connection 이름을 DB owner로 추정하지 않는다.
프로필별 비밀번호·토큰은 YAML에 저장하지 않고 기존 Dataiku/GENOS 보안 설정으로 주입한다.

제안하는 새 설정명: LEGAL_DB_MAPPING_FILE, LEGAL_DB_PROFILE, LEGAL_DB_MAPPING_SHA256.
이 설정과 로더는 아직 구현되지 않았다. YAML을 DEV에 복사하는 것만으로 현행 R2/R3가
매핑을 사용하지 않는다. 현재 physical_mapping.draft.yaml은 runtime_enabled=false다.

실행 배선의 제안:
  명시한 프로필 + 봉인 YAML
    → 엄격 파싱·승인/필수값·동일 이름 충돌·타입·참조 검증
    → 요청 동안 불변인 SchemaMap 생성
    → Dataiku 적재/검증과 GENOS Oracle 조회에 같은 논리 매핑 적용
    → 실제 DB의 owner/컬럼/PK/FK/CHECK/index·권한과 대조
    → 원격 구조화 요청 → 결과 수신 → 적재·다시 읽기 → 최종 완료

테이블/컬럼 식별자는 검증된 map에서만 만든다. 값은 기존 bind 계약을 사용한다.
SQL 전체를 .replace()하거나 정규식으로 컬럼명을 무차별 치환하지 않는다. JSON path,
문자열 값, alias, 다른 테이블의 동명 컬럼, PL/SQL 변수까지 바뀌는 것을 막아야 한다.
SELECT는 필요 시 새 물리 컬럼을 기존 내부 키로 alias한다. INSERT/UPDATE/조건/JOIN/정렬/
CLOB 길이·분할 읽기/해시 검증도 모두 같은 map을 사용한다.

기존 API·중간 SQLite의 논리 컬럼·SOURCE_JSON/VALUE_JSON의 키·manifest 논리 테이블명은
이번 물리명 변경에서 유지한다. 예컨대 DOC_ID AS DOCUMENT_ID로 읽고 내부 document_id는 유지한다.
이렇게 해야 데이터 내용 해시와 source integrity가 물리 개명 때문에 달라지지 않는다.

매핑의 세 가지 지문을 구분한다.
- logical_contract_version: 기존 원문·조회 데이터의 논리 필드와 의미 계약.
- logical_map_sha256: 공통 물리명·컬럼·타입·codec의 봉인 명세. Silver/Gold에서 같아야 한다.
- effective_target_map_sha256: 위 명세와 환경별 연결/DB identity/owner 역할을 결합한 대상 지문.

설명 문구·담당자 메모 같은 등록 메타데이터는 logical_map_sha256 계산 대상에서 제외하도록
설계한다. 전체 YAML 파일의 해시는 별도로 남겨 전달본을 검증한다. 설명 수정만으로 원문·조회
내용 해시나 논리 행 ID를 재생성하지 않는다. 실제 hash 계산·로더 구현은 후속 작업이다.
이번 operational_review도 실행 설정이 아닌 검토 설명이다. 향후 갱신·권한·검증 규칙을
실행 가능한 정책으로 옮기면 그 정책 버전을 실행 지문에 포함한다. 동작에 영향을 주는
설정을 단순 설명으로 분류해 지문에서 제외하지 않는다.

환경 이동 시 마지막 지문은 달라진다. Silver 적재 receipt를 Gold에 재사용해 완료로 처리하면 안 된다.
콘텐츠 해시는 그대로 보존하고 Gold에 새 적재 작업과 검증 receipt를 만든다. 기존
DataikuClient.identity()는 connection/project/database 식별 중심이므로 owner·매핑 지문까지
추가 결속해야 한다. job 재개 중 YAML/profile이 달라지면 같은 작업으로 계속하지 않는다.

Dataiku와 Oracle을 조회하는 GENOS RAG reader는 같은 map을 소비해야 한다. 구조화 전용
GENOS worker는 원격 DB 물리명을 사용할 필요가 없지만 요청·응답의 논리 계약 및 작업 binding을
돌려줘야 한다. 필드 추가로 서비스 핀이 바뀌면 기대 SERVICE_CODE_SHA256까지 함께 새로 봉인한다.
서로 다른 map을 한 프로세스에서 쓸 때 전역 상수 monkey patch를 사용하지 않는다.

7. 현재 문제 → 변경 → 확인 목표

A. owner/테이블/컬럼 고정
  기존: oracle_dp_io, oracle_dp_assets, oracle_query_catalog 등에 SIDDA·이름이 고정돼 있고,
  oracle_query_store도 직접 SIDDA를 붙인다. schema()는 고정 이름으로 DDL과 키를 검사한다.
  확인 결과: 개명 설정 경로가 코드에 없다. 새 이름 테이블만 만든 경우의 현장 오류는 미관측이다.
  변경: writer·reader·DDL·검증기 공통 SchemaMap. 원격 작업 전 대상 preflight를 수행한다.
  목표: 개명된 Silver 테이블에서 원문·용어·구조·검색 조회와 적재 검증이 같은 논리 결과를 반환.

B. 이름 변경과 내용 변경의 혼동
  기존: row hash, manifest, query projection은 기존 내부 키와 값의 계약에 의존한다.
  확인 결과: 무차별 컬럼/JSON 치환을 허용할 근거가 없으며 실제 실행 오류를 꾸며내지 않는다.
  변경: 물리 경계에서만 변환, 내부 키·ID·값 보존, alias로 원래 형태를 반환한다.
  목표: 동일 입력에 대해 논리 행 수·PK·관계·본문·정규화 hash가 동일하다.

C. 역할 혼재
  기존: 통합 9개에 지식·게시·실행 상태·이관 자산이 함께 있다. lk_record 등은 namespace 혼재다.
  변경: 저장 역할을 map에 명시하고 dev Silver / prod 역할별 owner를 구분한다.
  목표: 운영 지식 조회의 대상은 승인 Gold, 실행 상태 쓰기는 Agent, 파일 조각은 보관 영역.
  한계: namespace가 섞인 테이블의 행 단위 분리는 YAML 이름 변경만으로 구현할 수 없다.

D. 최종 저장 전에 원격 결과 정리
  기존: process()가 Dataiku 작업 폴더에 결과를 받은 뒤 ACK하고, 이어서 load_oracle()을 호출한다.
  확인 결과: 코드 순서 확인. 현장 데이터 유실이 발생했다는 증거는 없다.
  변경 계획: Dataiku 지속 보관 위치에 결과·작업 상태를 저장·검증한 뒤 ACK하거나,
  적재 검증 후 ACK한다. 실패 시 같은 작업의 남은 적재를 재개하고 성공 표시를 금지한다.
  목표: GENOS_COMPLETE, RESULT_STORED, LOAD_VERIFIED를 구분하고 최종 성공은 목표 DB 검증 뒤.
  한계: 자동 재개 실행 체계와 보관 위치 승인까지 별도 구현해야 하며 이번 매핑 초안에 구현되지 않음.

8. 단계별 실행과 통과 조건

단계 1 — 명칭·저장 책임 확정
  엑셀 9개/46개를 표준 사전과 대조한다. 과제/에이전트번호·owner·관리부서·기간·배치시각·
  표준단어/용어·도메인·인포타입·Description과 지원 테이블 배치를 확정한다.
  후보/메타신청/승인/DBA신청/생성/적재검증 상태는 분리한다.

단계 2 — YAML 계약 및 코드 적용
  기존 코드에 SchemaMap을 연결하고 명시 legacy 프로필로 현재 동작을 보존한다.
  승인 후보 dev_silver를 추가한다. 새 이름·NULL·유형·중복/누락·JSON/ID 의미를 검사한다.
  YAML은 안전한 기본 타입만 허용하고 중복 키·별도 사용자 태그·미지원 필드/매핑·미정 owner를 거부한다.
  실행 중 파일 변경을 따라가지 않고 시작 시 hash를 고정한다. 기존 경로로 자동 fallback하지 않는다.

단계 3 — 개발계 Silver 생성 및 사전 대조
  확정 이름의 새 테이블을 생성하고 기존 SIDDA 테이블은 보존한다.
  개발 생성 도구를 사용하더라도 승인된 타입·PK·FK·CHECK·인덱스를 명시하고 메타데이터로 확인한다.
  Dataiku의 자동 NVARCHAR 추론이나 자동 overwrite로 스키마가 바뀌지 않도록 검사한다.
  DDL 실행은 적재·서빙 기동과 분리한다. DDL 응답 유실/이미 존재는 성공으로 간주하지 않고 재조회한다.

단계 4 — 동일 데이터 계약 검증
  작은 고정 입력에서 기존 이름 경로와 새 이름 경로를 비교한다. 모델 평가를 새로 돌리지 않는다.
  외규 XML·내규 문서·한글/긴 본문·용어집·조회 릴리스가 포함되도록 명시 입력을 고정한다.
  행 수·PK·논리 참조·원문/용어 hash·조항/본문 조회·검색 조회·CLOB 왕복·권한 범위를 확인한다.
  이후 실제 Dataiku run → GENOS worker → 결과 → Silver 적재 → 동일 코드 reader까지 한 작업으로 확인한다.
  GENOS 현장 질문·warmup은 기존 지침대로 워크플로우 테스트 화면에서 확인한다.
  같은 코드·입력·YAML·프로필·DB identity·receipt를 결과에 남긴다.

단계 5 — 중단/재개와 전환 검증
  일부 테이블만 적재 후 중단, 응답 유실, 중복 실행, revision 충돌, 결과 다운로드 후 중단을 검사한다.
  이미 같은 내용의 행은 readback으로 재사용하고 다른 내용이면 충돌로 보존한다. 묵시 덮어쓰기 금지.
  재개가 owner/프로필/map hash/입력/결과 hash를 바꾸면 중단하고 별도 이행 작업으로 분리한다.
  최종 데이터 검증과 활성 채널 전환은 별도다. 현행 run_dataiku는 active_changed=false이므로
  적재 성공만으로 기존 RAG가 새 릴리스를 읽는다고 보고하지 않는다.

단계 6 — 운영 Gold 이관
  메타 승인·DBA 생성과 역할별 권한을 확인한다. 승인된 동일 물리명·타입으로 운영 preflight를 통과한다.
  개발 DB 자체를 바꾸는 대신 결과를 승인된 경로로 운영에 별도 적재·검증한다. 환경별 receipt를 구분한다.
  계정별 SELECT/INSERT/UPDATE 및 교차 스키마 참조 권한을 실제로 대조한다.
  지원 3개와 지식 4개의 Gold 조회 경로, Agent 상태 경로, 보관 자산 경로를 함께 확인한다.
  검증된 결과에 대해 명시적으로 채널을 전환하고 구 매핑·릴리스·테이블을 복원 가능하게 보존한다.

9. 실패 분류와 복구 담당

- YAML 누락/중복/미승인/식별자 오류: 로더가 외부 호출 전에 중단. 자동 추정·대체 이름 없음.
- DB 권한/스키마 불일치: Dataiku 사전 검사에서 표와 컬럼 차이를 기록. 원격 구조화 비용 발생 전에 해결.
- 전송 실패: 기존 전송 담당만 제한된 재개 수행. 동일 작업 입력·기한·사용량과 결과 hash 유지.
- 쓰기 응답 불명: 적재 담당이 기존 PK/내용/revision을 다시 읽어 확정. 맹목 INSERT 재시도 금지.
- 데이터/hash/권한 불일치: 성공 판정을 차단하고 원래 결과와 로그 보존. 스키마 검증을 꺼서 통과시키지 않음.
- map 변경 또는 잘못된 환경: 기존 receipt를 새 DB 완료 증거로 재사용하지 않음. 대상별 새 job이 필요.
- 데이터 일부 적재: 불변 행을 유지하고 미완료 단계를 재개. 전부 성공하기 전 활성 release 변경 금지.
- 운영 복귀: 이전 map/profile/리비전·채널의 명시 조합으로 복귀. 이름 변경을 이유로 기존 DB를 drop하지 않음.

10. 검증 목록과 의미

이번 정적 확인: 9테이블/46컬럼 누락·중복 없음, 후보 이름 길이, PK/FK/index 논리 참조,
YAML 저장·재읽기, 엑셀 저장·재읽기, 현행 DDL과 CSV의 출처 hash, 봉인 R2와 핵심 6모듈 일치.
설명 보완 검증: 테이블 9개 × Description 11항목 및 컬럼 46개의 의미·허용값·산식·선정 이유
작성 여부, YAML과 등록 설명 내보내기의 일치, Bizmeta/설명 시트의 건수를 대조했다.
이는 Oracle 실행·새 스키마 생성·내부 모델 품질·성능·운영 표준 승인을 뜻하지 않는다.

구현 후 필수 확인:
1) legacy/new 동일 입력의 원문·용어·구조·조회행·hash 동등성.
2) 신규물리명 SELECT alias, INSERT/UPDATE, CLOB, JSON_TABLE, JOIN/정렬과 metadata 검사.
3) 0으로 시작하는 ID, 한글/보충문자, 긴 CLOB, NULL, timestamp/timezone, NUMBER 순번의 왕복 보존.
4) 모든 객체 PK/FK/CHECK/index·권한 및 OWNER 구분. 잘못된 schema의 동명 객체를 거부.
5) mapping hash/profile mismatch, 중복 키 YAML, 부족 컬럼, 잘못된 타입, 실제 DB metadata drift 거부.
6) 부분 적재·중복 실행·revision 충돌·응답 유실·중단/재개·예산 보존.
7) Agent/Gold/보관 역할 누수 및 승인되지 않은 쓰기 경로 차단.
8) 실제 Dataiku 진입·GENOS 서비스 pin·RAG reader·최종 적재 상태의 동일 계약 연결.
9) 활성 전환 전 읽기 검증, 전환 후 현재 선택 확인, 구 버전 복귀.

단순 물리명 전환에는 모델 호출이 필요하지 않다. 검색 효과나 모델 품질 비교를 추가하면
기존 ADR 선점·동결 절차로 별도 진행한다. 요청하지 않은 실험은 이번 계획에서 시작하지 않았다.
독립 에이전트 검토를 수행하지 않았으며 이번 검토는 자체 정적 검토다.

11. 비용·공간·일정

관측 수치 N01: 현행 통합 DDL 9테이블/46컬럼. 분모는 명시된 Oracle 파이프라인 계약.
계산 수치 N02: 7개 Gold 후보 36컬럼 + Agent 5컬럼 + 보관 5컬럼 = 46컬럼.
관측 수치 N03: R2와 작업 코드 핵심 6개 모듈 바이트 동일. 전체 MAIN 동일성의 증거가 아님.
목표 N04: 동일 입력의 논리 행·PK·본문·해시 차이 0. 실제 검증 결과가 아니라 통과 기준.
목표 N05: raw 파일·용어집·구조화 결과를 물리 개명만으로 다시 생성하지 않음.

실제 DB 행 수·크기·처리시간·동시성·운영 승인 대기시간은 미확인이다. 개선율이나 완료일을 추정하지 않는다.
병행 보존 시 추가 공간 = 새 테이블·인덱스 크기 + 이행 로그/receipt + 필요한 반환물 보관.
원문/캐시는 동일 hash 불변 파일을 재사용하고 DB 이행은 작은 배치·단일 무거운 프로세스로 수행한다.
자산 분할 테이블을 같이 복제하면 공간 부담이 커질 수 있다. 보관 영역을 공유할 수 있는지는
권한·보유 책임 승인 후 결정하며 본문·원본·실패 기록을 임의 삭제하지 않는다.

이름 변경 자체의 검색 품질·속도 개선은 기대 효과로 잡지 않는다. 기대 효과는 매핑 누락 방지,
한 번 승인한 이름을 개발/운영에서 재사용, 대상 drift 사전 발견이다. SQL builder/alias/검사가
추가하는 지연은 현장 측정 대상이며 비용 절감이나 운영 안정성 인증으로 표현하지 않는다.

15. 제공 예시 양식과 상세 검토본의 구분 — 2026-10-23

앞선 TABLE_COLUMN_MAPPING_PLAN.xlsx는 사진의 작성 항목을 포함한 확장 검토표이며, 사진과
동일한 시트/열 배치가 아니었다. 사용자 확인 요청에 따라 원본 사진 7장을 다시 대조하고
DATAIKU_GOLD_EXAMPLE_FORMAT.xlsx를 별도 생성했다. 기존 상세 검토 내용은 유지했다.

- 사진1: 에이전트번호 → 스키마 → 테이블명 → 골드레이어 후보 테이블 → 비고.
- 사진2: No. → 에이전트번호 → 스키마 → 테이블명 → 데이터논리명 → 데이터출처 → 데이터유형
  → 데이터 가공 프로세스 설명 → 생성시각. 상단 작성 항목 설명과 본표를 구분한다.
- 사진3: 1차 메타 등록 대상과 2차 추가 검토후 등록대상을 좌우 목록으로 배치한다.
  우리 제외 대상은 실제 요청을 보내지 않았으므로 제외 제안(미요청)으로 표시한다.
- 사진4: 좌우 타입 대조 형태를 참고하되 우리 표의 현재/목표 후보를 명시한다.
  사진의 미확인 타입 변환 방향이나 다른 업무의 값은 복사하지 않는다.
- 사진5/6: 테이블별 시트의 순번 → 물리명 → 논리명 → 데이터 타입을 사용한다.
  사진7은 타입/논리명 순서가 다른 사례이며, 이번 통일 순서는 사진5/6을 따른다.

사진에서 확인하지 못한 필수 여부·O/0 범례·원본 숨은 열·수식·전체 시트 구조는 재현 또는
승인했다고 주장하지 않는다. 업무 의미·선정 이유는 셀 메모에 보존했고, 전체 텍스트와
추가 운영 검토는 상세 파일·TXT에서 확인할 수 있다. 후보명과 타입은 동일 YAML에서
생성하므로 예시용 표와 구현 매핑 계획을 따로 수정하지 않는다.
