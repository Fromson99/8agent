RAG 판단·도구·종료 계약 개선 설계
2026-10-07 / 상태: 설계 완료, 구현·새 실험·MAIN 변경·GENOS 배포 미실행

1. 결정 요약

현재 오류는 LLM의 법률 판단 실수와 실행기의 계약·상태 전달·검증 공백이 결합한 결과다. 도구가 있다는 사실만으로 모델에게 정상적인 선택지가 주어졌다고 볼 수 없다. 이번 설계는 기존 v6의 7개 판단 단계와 원문·권한·실행 기록을 유지하면서, 모델에게 맡긴 기계적 상태 관리를 코드로 옮긴다.

우선순위는 ① 제시한 도구와 실행 계약 일치 ② 확보·전달·채택 분리 ③ 반복 종료와 실제 마무리 예산 연결 ④ 질문별 부족 범위의 재조사 ⑤ 원문 인용 생성과 최종 표현 제한 ⑥ 장애·재개·게시·경험 재사용까지 연결하는 순서다. 모델 변경과 검색 순위 변경은 별도 효과 검증 대상으로 둔다. 기존 별도 최종 검토 모델은 기본으로 다시 켜지 않는다.

원하는 결과는 다음과 같다.
  - 읽겠다고 선택하면 실제 원문 또는 정확한 실패 사유가 다음 판단에 전달된다.
  - 같은 원문을 다시 읽는 이유가 없으면 끝없이 같은 행동을 반복하지 않는다.
  - 질문의 요구사항을 유지하고, 자료 부족과 사용자 사실 부족을 구분한다.
  - 답변 작성 단계에서 앞선 판단에 없던 법률 사실이 추가되지 않는다.
  - 답할 수 있는 범위, 조사 중단, 외부 장애를 서로 다르게 기록·표시한다.
  - 기존 정답, 복귀, 정정, 권한, 원문 버전, shortcut/wiki, AD, GENOS 배선이 유지된다.

이 문서는 읽기 전용 진단과 설계 산출물이다. 관측 결과와 목표를 구분한다. 개선 정답률·시간 단축·GENOS 현장 효과는 아직 측정하지 않았다. 자체 검토이며 독립 감독자·법률 전문가 검토로 표시하지 않는다.

2.3 이번 설계에서 추가 확인한 배선 문제

A. 마무리 예산: memory_binding.RuntimeModel.invoke는 모든 native stage를 session.structured로 보낸다. bounded_source_session.structured는 memory-assess와 memory-compose까지 save_view('investigate') 및 gateway.generate('investigate')로 호출한다. repository.reserve_attempt는 investigate에만 40-3 제한을 적용한다. 따라서 이 v6 경로는 ASSESS/COMPOSE에서도 남겨 둔 3회에 접근할 수 없다. 단순히 reserve 수치를 늘리면 오히려 모든 단계가 쓸 수 있는 호출 수가 줄 수 있다.

B. 재시도: 평가 프로필의 max_transport_retries=1과 실제 service 팩터리의 0 차이가 기록돼 있지만, structured 호출부도 로컬 profile을 0으로 덮어쓴다. 이 경로에서는 상위 설정 1만으로 재시도가 켜지지 않는다. IC25에서는 여기에 ExperimentProviderError가 일반 TransportError(unknown=True)로 바뀌며 429·retryable 정보가 소실됐다. 오류 분류와 유효 재시도 정책을 함께 고쳐야 한다.

C. 게시: unified_publication.validate_saved는 현재 READY goal, ACTIVE route, 7단계 refs, 채택 출처와 quote, 공개 claims 일치를 검사한다. 자유 생성 answer.text와 claims의 의미 일치를 검사하는 경로는 아니다. unified_runtime.result_port는 별도 review 상태를 SKIPPED로 고정한다. final_review_enabled 한 항목을 켜는 것으로 v6 전체 검증이 연결되지 않는다.

4. 전체 목표 흐름과 책임

기존 단계 순서는 INTENT → PLAN → RECALL → READ → SELECT → ASSESS → COMPOSE다. SELECT 안에서 추가 읽기·연결·복귀·재검색이 일어나며, ASSESS는 부족한 원문을 위해 SELECT/RECALL로 돌아갈 수 있다. READ와 SELECT를 뒤집거나 새 제품 실행기를 만들지 않는다.

  질문·현재 사건 revision·권한·선택 세대
     ↓
  INTENT: 원문 요청에 연결된 쟁점과 요구사항
     ↓
  PLAN/RECALL/READ: 기존 용어·본문 검색, 초기 원문 확보
     ↓
  SELECT: 실행 가능한 선택지 제시 → LLM 행동 선택 → 계약 검사
     ↓                                      ↘ 잘못된 제안: 한정 보정
  원문 확보 → 다음 입력에 실제 전달 → 쟁점별 채택/보류
     ↕ 다른 범위·명시 참조·과거 화면 복귀 / 진전·예산 감시
  ASSESS: 요구사항별 판단·근거·부족 범위
     ├ 핵심 원문 부족 + 실행 가능한 보완 → 기존 SELECT/RECALL
     ├ 사용자 사실 부족 → 조건부 판단/필요 사실 표시
     ├ 검증 가능한 일부 판단 → 한정 답변
     └ 판단 근거 없음/공급자 장애 → 조사 미완료, 재개 정보 보존
     ↓
  COMPOSE: 판단 ID를 선택·배치 → 코드가 원문 인용과 문장 렌더링
     ↓
  현재 권한·revision·원문 해시·현재 route·출력 일치 확인
     ↓
  API / 판단 화면 / GENOS 워크플로우 / 확인된 경험·피드백 소비자

| 책임 | LLM이 담당 | 코드가 담당 | 보장하지 않는 것 |
|---|---|---|---|
| 질문 | 질문의 쟁점·주체·조건 해석 | 원문 요청 보존, 요구 ID와 revision 결속 | 기계적 필드 검사만으로 질문 해석 정답 보장 |
| 조사 | 읽을 후보, 범위, 명시 참조, 복귀의 필요성 | 존재·권한·버전·실행 조건이 맞는 도구만 제시 | 후보 순위가 법적 적용 순위라는 보장 |
| 근거 | 읽은 자료의 관련성·채택 판단 | 확보·전달·채택 영수증과 범위 보존 | 전달 완료를 모델 이해 완료로 간주 |
| 충분성 | 규칙·예외·적용 사실의 의미 판단 | 선언된 gap/coverage 모순, 재진입·예산 제어 | 모델이 gap 자체를 잘못 생략하는 오류의 완전 제거 |
| 답변 | 근거에 기반한 판단 문장, 필요한 표현 구조 | 인용 복원, 승인 문장의 배치·출처 연결, 자유 추가 차단 | 올바른 인용을 붙인 잘못된 추론의 자동 완전 판별 |

5. 세부 계약 설계

아래 타입·함수·필드는 제안이며 아직 구현되지 않았다. 기존 계약과 이름이 비슷해도 현행 기능으로 해석하지 않는다.

5.1 단일 ActionOffer에서 화면·스키마·실행 검증 생성

제안 함수 compile_action_offers(state, presentation, principal)는 내부 명세를 한 번 만든다.
  offer_id, kind, law/document/version, branch/scope/page, issue_refs,
  presentation_id, state_revision, binding_hash, target_label,
  eligible_basis_refs, preconditions, expected_effect.

모델은 제시된 offer_id와 필요한 제한된 인자·이유만 선택한다. 사람과 모델이 보는 카드에는 법령명·조·항·호·읽기 범위·이미 전달 여부를 표시한다. 내부 좌표를 모델이 새로 조립하지 않는다. ADOPT의 eligible_basis_refs는 현재 입력에 실문장이 제공되고 같은 branch·권한·세대에 연결된 근거만 포함한다. 과거 채택의 KEEP은 이미 수락한 근거와 현재 권한을 재검사한다. 과거 열람을 새로 ADOPT하려면 재제시한다.

schema 생성과 validate는 동일한 명세를 사용한다. 현재 상태가 바뀌지 않은 제안이 스키마는 통과하고 실행 조건에서 막히는 일을 제거한다. 권한 변경·동시 정정·세대 변경 후의 거절은 STALE/PERMISSION_CHANGED로 명확히 구분한다. 자연어 이유의 법률적 정합성은 별도 의미 판단 대상이다.

읽기와 같은 branch의 채택/보류 변경을 한 제안에서 섞지 않는 방향으로 단순화한다. 이미 보류된 자료도 열람할 수 있고, 열람은 보류를 채택으로 바꾸지 않는다. READ_ARTICLES 묶음 선택도 같은 원칙을 적용한다. 호환 어댑터는 이전 명칭을 읽을 수 있으나 동일 효과를 내는 내부 읽기 명세로 변환한다. 기존 조문·명시 참조·복귀 기능은 유지한다.

5.2 확보·전달·채택·화면 위치를 서로 독립적으로 저장

| 축 | 제안 상태 | 갱신 주체 |
|---|---|---|
| 원문 확보 | NONE/PARTIAL/COMPLETE, scope+spans+hash | 원문 도구의 실제 결과 |
| 원문 전달 | 어떤 입력에 어떤 span을 넣었는지, 현재 보임 여부 | 모델 요청 빌더의 영수증 |
| 쟁점별 판단 | UNDECIDED/ADOPT/DEFER/EXCLUDE | 원문을 본 LLM의 명시 선택 |
| 화면 위치 | 현재 법령·조문·페이지·과거 복귀 지점 | 탐색 동작 |

현재 basis_history의 누적 전달 이력은 유지한다. 현재 화면 커서를 0으로 바꾸어도 누적 전달 사실을 지우지 않는다. '선택 범위 완료'는 '조문 전체 완료'와 별도다. 조문 전체 범위를 계산할 수 없으면 unknown으로 남긴다. 제목·상위 문맥만 본 상태에서 본문 전체 완료를 참으로 만들지 않는다.

읽기를 수락하면 결과 페이지가 보류 상태와 관계없이 다음 모델 입력의 전달 큐에 들어간다. 긴 원문은 기존 context/read/page 상한 안에서 나눠 전달하고 잔여 범위를 표시한다. 일부 읽기 실패 시 성공 범위만 영수증으로 남긴다. 자동 전달은 자동 채택이 아니다.

reason은 decision_id·issue_id·당시 evidence_revision에 연결한다. 과거의 '아직 읽지 않음'을 현재 상태 설명으로 재사용하지 않는다. 현재 화면에는 코드가 계산한 읽기 상태와 해당 시점의 판단 이유를 구분해 보여준다.

5.3 진전 검사와 종료

진전 서명은 질문 revision, 쟁점 집합, 세대·권한, 확보/전달된 span 집합, 새로운 유효 검색식, 실제 후보·페이지 전진, 새 채택/쟁점별 판단 변경을 사용한다. 문구만 바꾼 이유, 새 event ID, VIEW_SAVED_SOURCE의 커서 초기화는 진전이 아니다.

같은 자료라도 새로운 쟁점, 추가 범위, 변경된 질문·원문 버전, 이전 판단과 충돌하는 근거가 있으면 정당한 재검토로 허용한다. model이 이유 문자열만 새로 써서 반복 카운터를 초기화할 수 없게 한다. 유한 후보 목록 전진은 유효 행동이지만 모델·시간·검색 라운드 총예산은 계속 적용한다.

초기 후보는 기존 max_no_progress=2와 max_schema_repairs=1을 실제 SELECT에 연결한다. 한 번 경고한 뒤 동일 무진전이 반복되면 조사 확대·ASSESS·미완료 종료 중 가능한 경로로 옮긴다. 기준 숫자는 후보 실험 전에 동결할 값이며 성능 검증 결과가 아니다. 읽기 실패를 모델의 의미 오답으로 기록하지 않는다.

RETURN_TO와 재개는 누적 예산·무진전 서명·재진입 횟수를 보존한다. viewport를 돌리는 것은 판단 이력을 되감는 것이 아니다. 사용자 정정은 새 revision으로 분기하며 무관한 예전 쟁점의 연속 반복 수만 새 의미 범위에 맞게 재설정한다.

5.4 예산을 실행 단계에 연결

proposal에서 모델이 budget_class를 선택하지 못하게 한다. RuntimeModel/structured가 호출 목적을 코드로 분류한다.
  INVESTIGATE: INTENT 및 탐색·재탐색·조사 보정.
  FINALIZE: 조사 종료 후의 ASSESS, 해당 보정, COMPOSE.

기존 journal의 phase CHECK 제약과 충돌하지 않도록 native phase/source_stage를 보존하면서 budget_class를 버전 있는 필드·이벤트로 추가한다. repository.reserve_attempt는 phase 문자열 대신 검증한 budget_class로 reserve 접근을 통제한다. 파일에 'FINALIZE'를 임의 주입한 요청은 거절한다. 마무리 단계에서 검색으로 재진입하면 다시 조사 예산을 사용한다.

초기 총 상한 40과 reserve 3을 무작정 늘리지 않는다. ASSESS 최대 2회(최초+보정), COMPOSE 서식 선택 최대 1회와 코드 렌더링을 넣을 수 있도록 슬롯을 배정한다. 서식 선택이 실패하면 동일 판단을 기본 서식으로 코드가 렌더링한다. 채택 근거가 없으면 마지막 슬롯에서 근거 없는 답을 생성하지 않는다.

시간·도구 예산도 함께 예약한다. 현재 selection_time_reserve_seconds=30이 후속 모델 응답을 보장하지는 않는다. 후속 단계별 허용 대기와 전체 남은 시간을 기준으로 입장 가능 여부를 판단하고, 마감 안에 평가할 수 없으면 조사 미완료를 반환한다. 예약 횟수가 남았다는 이유로 전체 deadline을 연장하지 않는다.

5.5 질문 요구사항과 gap에 따른 재진입

INTENT의 issues를 원문 요청 span 또는 현재 사용자 조건 ID에 연결한다. 요구사항은 검색 결과에 맞춰 조용히 삭제하거나 축소하지 않는다. 주체·행위·적용대상·조건·예외·요청범위를 기록하되 질문하지 않은 모든 법률 쟁점을 자동 추가하지 않는다. 정정이 있으면 변경 이유와 새 revision을 남긴다.

| gap | 코드가 보장할 제어 | LLM 판단이 남는 부분 |
|---|---|---|
| UNREAD_SAVED | 현재 권한이 있는 저장 원문을 실제로 전달 | 이 원문이 질문에 충분한지 |
| MISSING_SCOPE/SOURCE | 제시 가능한 읽기/검색 행동과 예산이 있으면 SELECT/RECALL 재진입 | 필요한 범위가 무엇인지 |
| WRONG_SUBJECT | 기존 쟁점 유지, 다른 주체·행위의 조문으로 COVERED 종료 금지 | 주체·행위가 의미상 일치하는지 |
| MISSING_FACT | 자료 탐색으로 사용자 사실을 만들어 내지 않음 | 조건부 규칙으로 답할 수 있는지, 사실 확인이 필요한지 |
| VERSION_AMBIGUOUS | 선택 판본·적용 시점의 불확실성 보존 | 사용자에게 시점을 묻거나 조건부 분기할 필요 |
| UNRESOLVED_REFERENCE | 답변 주장에 필요한 연결일 때만 핵심 gap으로 처리 | 해당 참조가 질문 해결에 필요한지 |

핵심 gap은 issue_id·영향받는 claim ID·material 또는 탐색 대상에 연결한다. COVERED와 해당 요구를 막는 gap을 동시에 수락하지 않는다. LIMITED_ANSWER는 재조사 회피 수단으로 쓰지 않는다. 재진입은 자동으로 특정 조문을 정답으로 채택하는 것이 아니라, 부족하다고 선언한 자료를 조사하도록 제어하는 것이다.

초기 assessment_reentry_limit=2는 유지하되 사용 횟수·정지 사유를 기록한다. 제한 도달, 자료 없음, 시간 부족이면 확인한 주장만 한정 답변한다. 주장 전체를 뒤집을 수 있는 미확인 전제가 있으면 해당 주장은 확정문으로 반환하지 않는다. 무관한 연결 미해결을 전역 완료 차단으로 되돌리지 않는다.

5.6 정확한 인용과 의미 판단을 분리

제안 EvidenceRef는 document/version/generation, source_id, scope_id, block_id, start_cp/end_cp, block_hash, delivery_ref에 연결한다. 모델은 이미 제시된 문장·항·호의 span ID를 선택한다. 임의 좌표 생성은 기본 인터페이스에서 제거한다. 긴 블록은 원문 바이트를 바꾸지 않는 결정적 span 분할과 상위 범위 확장 선택을 제공한다.

서버가 원문 저장소에서 인용을 복원한다. Unicode NFKC 비교는 오류 진단용으로만 쓰고, 원문 聯을 聯으로 교체하지 않는다. 다중 출처·조건·예외는 여러 EvidenceRef로 표현한다. 서로 떨어진 span을 이어 붙여 연속된 원문 인용처럼 보이지 않게 개별 인용한다. 기존 quote/source_id 소비자는 정확히 복원한 인용으로 투영한다.

검증기는 독립적으로 검사 가능한 schema/issue/gap/ID/quote 오류를 목록으로 반환한다. 존재하지 않는 ID 때문에 확인할 수 없는 후속 검사는 '검사 불가'로 표시한다. 첫 오류만 고치고 두 번째 오류에서 실패하는 낭비를 줄인다. 자동으로 의미를 추정해 잘못된 인용을 올바른 것처럼 교정하지 않는다.

정확한 인용은 출처 일치 보장이다. 주장과 인용의 의미상 함의, 예외 누락, 적용 대상 오판은 여전히 평가해야 한다. 이 구분을 UI·영수증에도 유지한다.

5.7 답변 본문과 한계 설명을 닫힌 판단 목록에 결속

ASSESS 출력은 다음을 제안한다.
  claims: claim_id, issue_refs, text, evidence_refs, condition/fact_refs.
  limitations: limitation_id, kind, issue_refs, gap/fact/status refs.
  issue_assessments, gaps, disposition.

법률 사실을 설명하는 limitation은 claim으로 옮겨 동일한 근거 규칙을 적용한다. 단순 자료 부족·사용자 사실 미확인 문장은 상태/ID에서 코드가 생성한다. 진단 reason의 자유문장을 그대로 사용자 한계 설명으로 복사하지 않는다. 사소한 명칭 검색만으로 법률 사실을 분류하는 금칙어 방식은 사용하지 않는다.

COMPOSE 출력은 layout, blocks[{claim_refs, limitation_refs, style}]이며 새로운 법률 본문은 받지 않는다. 각 claim의 문장과 인용은 ASSESS의 수락된 값을 그대로 렌더링한다. 표·목록·순서 선택을 허용하고 제목은 고정 섹션명 또는 검증한 쟁점명에서 생성한다. 빠진 조건·한계, 중복된 주장, 관계없는 claim 배치는 검사한다. 사용자 표현 변경 요청이 주장 의미까지 바꾸면 COMPOSE만으로 바꾸지 않고 ASSESS를 새 revision에서 재검증한다.

공개 answer.text는 render(accepted_assessment, composition_plan)와 완전히 같아야 한다. 이 equality를 unified_publication.validate_saved/validate_current에서도 재계산한다. result_port가 검증 후 자유문장을 붙이는 경로는 제거하고, completion_limitations도 렌더러의 구조화 입력으로 넣는다. 답변 claims와 원문 인용 표시는 기존 외부 형식으로 투영할 수 있다.

기본 별도 최종 검토 모델은 disabled 유지다. 의미 검토 모델을 추가하는 후보는 별도 ADR에서 비용·오판 차단·정상 답변 회귀를 검증한 뒤 결정한다. 그러한 후보의 출력을 제품에 쓰면 offline evaluator가 아니라 제품 호출로 기록해야 한다.

5.8 공급자 오류와 재개

공통 오류 명세: provider/model, http_status, retryable, acceptance(KNOWN_REJECTED/UNKNOWN/ACCEPTED), retry_after, safe_public_code, 원시 응답 artifact ref. 요청 비밀값이나 내부 원문은 사용자 오류에 노출하지 않는다.

ExperimentClient 결과를 쓰는 실험 어댑터, LocalGemmaTransport, GENOS 내부 transport가 같은 의미로 오류를 매핑한다. 재시도는 gateway 한 계층에서만 수행한다. structured와 service에서 정책을 조용히 덮어쓰지 않고 최종 effective_profile과 override_reason을 남긴다.

429처럼 미수락이 확인된 일시 장애는 남은 호출·시간 예산과 Retry-After 안에서 제한된 1회 재시도를 초기 후보로 검토한다. 수락 여부 불명의 timeout·부분 스트리밍 이후는 자동 중복 호출하지 않는다. 모델/provider fallback은 추가하지 않는다. 공급자가 계속 제한하면 장애 상태와 재개 가능한 checkpoint를 반환한다.

같은 request_id의 완료 재호출은 기존 응답을 현재 권한으로 재검증해 반환한다. 실패 재개는 원래 단계·입력 해시·시도 원장을 확인한다. 재개마다 총 호출 예산을 새로 지급하지 않는다. 새 시도 예산이 필요한 사용자 재요청은 새 request_id와 retry_of 계보로 명시한다.

6. 결과 상태·저장·소비자 계약

6.1 종료를 정상 답변으로 위장하지 않는 상태 설계

현재 case-binding-v1.status는 READY/REUSED/STORED/CLARIFY만 허용한다. 여기에 임의로 PARTIAL/PENDING을 넣으면 닫힌 스키마가 깨진다. 다음과 같이 실제 판단 완료와 조사 중단을 분리한다.

| 내부 결과 | 기존 case/route와의 관계 | API·화면 제안 | 저장·재사용 |
|---|---|---|---|
| FULL | 7단계가 유효하고 현재 route READY | 정상 답변, answer_coverage=COVERED | 기존 확인·경험 정책 적용, 의미 품질 인증은 별도 |
| LIMITED | 일부 쟁점이라도 근거 있는 ASSESS/COMPOSE를 완료한 READY | 정상 답변 + PARTIAL/INSUFFICIENT 및 미확인 쟁점 | 범위·조건·gaps까지 묶어 보존. 전체 질문의 정답 경험으로 확대 금지 |
| NEEDS_FACT | 조건부 답이 있으면 LIMITED. 없으면 기존 CLARIFY 계약에 맞는 별도 경로 | 필요한 사실을 구체적으로 표시 | 조사 근거 유지, 사용자 답변은 새 revision에서 검증 |
| INVESTIGATION_PENDING | 완료 route를 만들지 않고 기존 pending 단계 유지 | 제안 오류 코드 SOURCE_INVESTIGATION_INCOMPLETE, HTTP422 및 구조화 diagnostics | 채택·예산·재개 단계 보존. READY/STORED로 만들지 않음 |
| UPSTREAM_UNAVAILABLE | 판단 실패와 구분, 완료 route 없음 | 미수락 공급자 장애는 HTTP503, 불명확 전송 실패는 기존 502 계열 + 분류 | attempt 원장·retry_of·checkpoint 보존 |
| INTEGRITY_FAILURE | 권한·해시·현재 revision 검사 실패 | 기존 무결성 오류 경로 | 게시·경험 활성화 금지, 안전한 재요청/복구 |

미완료 응답은 term-runtime-v1의 완성된 법률 답변을 가장하지 않는다. app.exception_handler의 기존 code/run_id/detail 응답에 버전 있는 diagnostics를 추가한다. API 상태와 GENOS workflow의 answer_status·화면 문구 매핑을 함께 바꾼다. 웹 화면에는 코드명보다 '어느 자료를 더 확인해야 하는지'를 보여주고 상세 진단은 접는다.

7단계가 없는 pending에 judgment_view.build를 호출하거나 빈 ASSESS/COMPOSE를 만들어 hash를 맞추지 않는다. 완료 화면은 현재 7단계 refs를 유지한다. 미완료 화면은 별도 조사 진행 투영으로 완료 단계·마지막 행동·읽은 자료·중단 사유·재개 지점을 보여준다. 전달 이력은 내부 사고 과정이 아니라 저장된 행동·짧은 이유·도구 결과다.

6.2 재개·동시성·이행

현재 조사 상태, stage_progress, stage_progress_evidence, native journal, case/shortcut DB는 서로 연결된다. 새 상태 필드에는 contract_version과 binding_hash를 붙이고, 새 reader는 구버전 완료 기록을 읽을 수 있게 한다. 구 기록의 hash를 바꾸는 현장 일괄 UPDATE는 하지 않는다.

새 실행은 새 계약으로 시작한다. 진행 중인 구 실행은 기존 코드·세대 binding으로 마치거나 안전하게 중단하고 새 요청으로 이어 간다. 새 코드가 구 checkpoint를 해석할 수 없으면 명시적으로 재시작 필요를 반환한다. 구버전이 모르는 새 기록을 구 코드로 실행하는 자동 downgrade는 금지한다. DB 변경이 필요하면 additive migration/새 테이블·namespace와 migration receipt를 사용하고, 롤백 시 구 코드가 새 레코드를 오독하지 않도록 reader 선택을 분리한다.

revision 충돌·권한 철회·늦게 도착한 응답은 기존 publication/currentness guard로 차단한다. 모델 호출 성공 후 checkpoint 저장 전 장애가 생긴 경우 attempt의 결과와 input hash를 대조해 중복 실행을 피한다. 원문 확보와 case DB 기록 사이에 장애가 생기면 원문 영수증은 남기되 채택·전달을 소급 꾸미지 않는다.

6.3 경험·위키·피드백

shortcut의 탐색 절차 재사용은 새 계약·원문 세대·질문·권한과 맞는지 확인한다. 예전 action ID를 새 presentation의 ID로 간주하지 않는다. 실제 실행 단계의 결과로 새 offer를 다시 생성한다. 상태 저장만 성공한 pending이나 오류 답변을 정상 법률 경험으로 활성화하지 않는다.

LIMITED 결과를 사용자가 확인하더라도 해당 조건·미확인 범위를 제거하지 않는다. legal_wiki/user_wiki와 피드백 proposal에는 원래 claim/evidence/issue/revision을 연결한다. 23개 자동 정답을 자동으로 법률 정본에 편입하지 않는다. AD의 shortcut/wiki 기능 토글과 사용자·팀 접근 경계는 유지한다.

| 응답 수락 불명 timeout | UNKNOWN 기록, 자동 재송신 중단 | 재개 전 기존 attempt 상태 확인 | 법률 오답으로 분류하지 않음 |
| 질문 정정 중 이전 응답 도착 | revision CAS 실패 → 늦은 응답 무시 | 이전 route를 현재 답으로 게시하지 않음 | 정정 후 질문 기준의 결과만 표시 |
| 읽은 뒤 권한 철회/세대 변경 | 게시 직전 다시 검사, 현재 권한 밖 근거 차단 | 저장 원문도 접근 권한을 우회하지 못함 | 안전하게 재요청·재검증 안내 |
| 재시작·원복 | 원래 binding으로 재개 또는 호환 불가 명시 | 다른 세대의 checkpoint를 조용히 이식하지 않음 | 재개 여부와 중단 단계가 일치 |

10.2 모델 실험과 평가 분리

현재 32문항과 회귀 8문항은 이미 결과를 보고 설계한 개발·회귀 표본이다. 수정 후 다시 맞혀도 독립 일반화 성능으로 부르지 않는다. 질문 문구만 바꾼 동일 조문을 여러 독립 사례로 세지 않는다.

실험 전 새 ADR에서 기준선=선택된 ADR0677 integrated와 후보의 정확한 코드·profile·schema·prompt·source generation·검색 정책·provider/error 정책을 동결한다. 기존 ExperimentClient 및 현행 Qwen3.8/Parasail FP8/no fallback 정책을 따른다. 공개 승인 범위와 질문 반출 적합성을 확인한다. GENOS 내부 자료를 외부 실험에 대입하지 않는다.

검증 집합을 다음과 같이 나눈다.
  A. 개발 재현: F01~F13 사례와 원래 40문항. 원인 제거와 기존 성공 손실을 확인.
  B. 독립 표본: 설계에 쓰지 않은 주체·행위·법령군·예외 구조·긴 조문·명시 참조·다중 턴. 질문/원문/기준답변 버전을 결과 보기 전에 고정.
  C. 장애/상태 표본: 모의 429·timeout·재개·권한 변경·동시 정정. 법률 정답 채점과 별도 집계.

독립 표본 수·허용 의미 회귀·비용/지연 한계의 수치는 후보 호출 전에 ADR에서 확정해야 한다. 현재 기록만으로 통계적 개선이나 예상 비용을 계산할 근거가 없으므로 이 문서에서 임의 수치를 성능 약속으로 쓰지 않는다. 계약 게이트 외 수치 기준이 미동결인 상태에서는 후보 실험을 시작하지 않는다.

원인 분리를 위한 arm은 처음부터 필요한 묶음만 동결한다.
  - 제어 계약 묶음: W01~W05, 상태·종료·게시 필수 소비자 포함.
  - 출력 무결성 묶음: span 인용·typed limitation·COMPOSE 렌더러, 필수 소비자 포함.
  - 검색 순위/제목 색인 후보: 필요한 경우 별도 분기. 모델 변경과 동시에 섞지 않음.
  - 각 묶음이 유효한 최소 통합 단위이며 무효 상태를 만들면서 파일별 효과를 억지로 분리하지 않음.

결과를 본 뒤 만든 후보·재채점은 새 ADR로 기록하고 기존 점수·실패 로그를 덮어쓰지 않는다. 여러 완료 분기를 합칠 때는 정확한 부모 arm의 merged_from과 채택/제외/충돌/롤백 기준을 동결한다. 최종 통합 코드에도 분리 평가를 연결한다.

| 평가 불일치 | 기준답변 버전·제공 근거·실제 답변과 채점 이유 대조 | 논쟁적 자동 채점 이유로 제품 오류를 부정하거나 점수를 소급 수정 |

로컬 명령은 .venv/bin/python 06_TOOLS/run_tool.py를 사용한다. 예전 표준의 scripts/·docs/adr 경로를 다시 만들지 않는다. 승격 source는 Accepted·out-of-sample·decision_eligible=true·complete여야 한다. 사용자의 2026-10-07 지시에 따라 세부 의미 판단 오류가 조금 남았다는 이유만으로 자동 차단하지 않는다. 어떤 의미 회귀를 허용하고 기록할지는 새 실험 전에 동결하며, 인용·권한·상태·해시·실제 서빙 연결의 심각한 문제는 별도 필수 게이트로 유지한다.

원복 조건: 새 권한/원문/게시 무결성 위반, 복귀·정정·경험 재사용 상태 손실, 필수 계약 파손, 실제 서비스의 다른 코드 선택, 사전 허용치를 넘는 실행·의미 회귀. 새 릴리스의 새 요청 유입을 멈추고 원래 활성 릴리스의 hash 고정 rollback 절차로 새 generation을 발행한다. 포인터 파일을 손으로 과거 generation 숫자로 되감지 않는다. 새 상태와 구 reader의 호환성을 확인하고 필요하면 새 요청으로 안전하게 재시작한다. 모든 실패 원장과 새 DB 기록은 보존한다.

GENOS는 코드 ZIP 적용, NFS generation, Git push, 코드서빙 리비전, workflow 편집기, 내부 질의 검증을 각각 별도 상태로 보고한다. 로컬 모델 성공으로 현장 완료를 대신하지 않는다. 현장 직접 코드서빙 테스트 UI/API를 요구하지 않으며 워크플로우 테스트 화면을 사용한다.

12. 기대 효과·비용·남는 한계

| 항목 | 기대 방향 | 현재 확정 가능한 것 | 남은 측정 |
|---|---|---|---|
| 계약 오류 | 스키마 허용 후 동일 상태의 실행 거절 제거 | 단일 ActionOffer로 기계적 동등성을 검사 가능 | 실제 모델의 제안 실패율·repair 수 |
| 반복 시간 | 같은 원문 재열람의 낭비 감소 | 무진전 한계를 코드로 보장 가능 | 전체 질문 지연·정당한 재열람 차단 비율 |
| 인용 오류 | 모델의 문자 재작성 오류 제거 | span에서 원문 그대로 인용 생성 가능 | 단서/예외 span 누락과 모델 의미 오류 |
| 최종 부가 오류 | COMPOSE의 새로운 사실 삽입 제거 | text가 승인 문장에서만 생성됨을 검사 가능 | ASSESS 단계 자체의 잘못된 추론·표현 품질 |
| 부분 답변 | 답할 수 있는 범위를 명확히 보존 | 완료·부분·미완료 상태와 route를 일치시킬 수 있음 | 부정확한 한정 답의 false pass/false block |
| 장애 | 429/timeout 원인 보존, 가능한 경우 제한 복구 | 오류 분류·attempt 기록·중복 방지 검사 가능 | 외부/GENOS 공급자별 실제 복구율·대기 |
| 정확도·비용·일정 | 개선을 검증할 수 있는 구조 | 지금 숫자를 약속할 근거는 없음 | 독립 표본 결과, 단계별 토큰/지연, 구현·검토·현장 대기 |

호출 변화의 계산식: 새 물리 호출 수 = 기존 호출 수 - 제거한 반복·보정 호출 + 추가 조사·재시도·선택 호출. 이는 계산 구조이며 현재 개선 예측치가 아니다. 반복이 없던 질문에서는 gap 보완 때문에 호출이 늘 수 있다. 별도 최종 judge를 기본으로 추가하지 않지만 새로운 전달 메타데이터가 입력 토큰을 늘릴 수 있다. 호출당 토큰·대기·단가가 달라 호출 수만으로 비용·지연 절감을 추정하지 않는다.

구현 순서는 W01~W04 기반 계약 → W05~W07 판단·게시 → W08~W09 장애·소비자 → W11~W12 통합·현장 순으로 의존성을 따른다. W10의 검색 정책 실험은 필요성이 확인된 뒤 분리한다. 인일과 달력 일정은 담당자·코드 충돌·현장 검증 대기 정보가 없어 미산정이다. 작은 설정 변경만으로 전체 문제가 해결된다고 견적하지 않는다.

남는 가장 큰 한계는 법률 의미 판단이다. 더 명료한 도구와 상태, 정확한 원문, 일관된 종료가 있어도 모델이 잘못된 적용 대상·예외·효과를 판단할 수 있다. 따라서 구조 검증과 의미 평가를 분리하고, 실패가 어느 단계에서 생겼는지 실제 입력·출력으로 확인할 수 있도록 한다.
