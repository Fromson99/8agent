에이전트 전체 의사결정 트리와 시스템 책임 검토

기준: 2026-10-07 로컬 MAIN investigation-completion-v6-20261007-r1, 포인터 generation 44.
이 문서는 현재 코드·저장 기록·기존 계약 검사를 이용한 자체 검토와 수정 설계다.
새 품질 실험·외부 모델 호출·루프 제품 수정·추가 MAIN 승격은 수행하지 않았다.
임의의 모든 질문 조합은 무한하므로, 현재 진입점·14개 조사 행동·7단계·오류 및 종료 유형을
72개 상태 전이 시나리오로 묶었다. 72개 전부를 실행해 통과했다는 뜻이 아니다.

1. 이번 작업의 경계

직접 /chat 통합 방식과 별도 Python 워크플로우 방식 모두 지원한다.
직접: main.py → chat_adapter.chat → service.service (같은 프로세스) → 공통 엔진.
별도: genos_rag_chat.py → 코드서빙 service.service → 공통 엔진 → 워크플로우 표시.
둘 중 하나를 제거하거나 필수로 강제하지 않는다. 각 경로의 설치·등록 방식만 다르다.
앞단 Socket.IO 통신은 사용자가 지정한 다른 에이전트의 작업이며 이번 수정 범위에 넣지 않는다.
앞단 연결 성공과 공통 에이전트의 판단·재개·종료 계약 성공은 별도 확인이다.

사용자 기준에 따른 책임 구분:
- 시스템 책임: 허용된 정보와 조회 수단, 실제 전달 범위, 선택지, 상태 보존, 일관된 종료,
  실패 사유와 복구 방법, 동일 의미의 출력. 이 경계가 깨졌으면 모델 탓으로 넘기지 않는다.
- 모델 책임: 필요한 정보와 정상 도구를 제공받고도 A 대신 B를 선택한 의미 판단.
  선택과 근거를 기록하고 사용자 가이드로 맥락 지정·재검토 방법을 제공한다.
- 결합 문제: 모델의 최초 실수 뒤에 시스템이 합당한 수정·복귀 선택지를 주지 못하거나
  미해결 상태를 지운 경우. 최초 실수와 복구 실패를 따로 기록한다.
‘정보를 다 줬다’는 것은 원문 전체를 매번 전송했다는 뜻이 아니다. 필요한 원문이 실제로
제공되었거나, 누락 사실과 유효한 조회 경로가 제시되었는지 영수증으로 판별해야 한다.

2. 현재 실행 구조

상위 경로: 요청/권한/AD 경계 → 사건·절차 재사용 → INTENT → PLAN → RECALL → READ
→ SELECT(법령·원문·참조 조사) → ASSESS → COMPOSE → 게시 현재성 검사 → 두 소비자.
SELECT의 RESEARCH는 RECALL로, ASSESS의 핵심 gap은 SELECT로 재진입한다.
JSON 형식 수정, 행동 수정, 참조 하위 반복, 재검색, 쟁점 재조사, 요청 재개가 서로 다른 층이다.
반복 종류 자체가 과도하다고 확정할 수는 없다. 현재 확인된 문제는 각 층의 미해결·완료·
실패 결과가 같은 계약으로 이어지지 않는 것이다.
기존 MAIN의 용어집/입력/문서 연결/색인 상위 단계는 유지한다. 이번 검토는 RAG 의사결정
서빙 루프와 피드백·경험 저장 경계이며 문서 수집·용어 정의 품질 인증을 대신하지 않는다.

3. 실제 확인된 문제와 바뀌어야 할 행동

F1. FINISH가 재조사 부족분을 작업 상태에서 제거한다.
기존: law_navigation.py:784에서 self.p.pop('assessment_gaps',None).
관측: REG-NG13에서 부족한 시행령을 해결하러 두 번 SELECT로 갔지만 새 원문 없이 FINISH.
원인: 조사 종료 행동에 미해결 과제 삭제가 결합되어 있다. 과거 사건 로그 자체가 삭제된
것은 아니지만 다음 작업 상태에서 해소 여부를 강제 확인할 재료가 약해진다.
제안: FINISH는 다음 단계로 전달만 한다. gap ID별 OPEN/RESOLVED/DEFERRED/NOT_REQUIRED/
BLOCKED와 이전 상태·변경 이유를 보존한다. RESOLVED는 관련 원문/사용자 사실/재판단
이벤트에 연결한다. 의미상 해결이 옳은지는 모델 책임이며 호스트는 연결·모순을 검사한다.
목표/검사: 해결 이벤트 없는 미해결 ID가 단계 이동·재개·출력에서 없어지지 않아야 한다.
부작용: 무관한 참조까지 필수로 강제하면 끝없는 탐색이 된다. NOT_REQUIRED나 제한 답변을
허용하되 해당 모델 판단을 기록한다. 새 원문이 없다는 이유만으로 합당한 범위 재판단을 금지하지 않는다.

F2. 판단 계약 실패가 추가 조사·부분 답변 경로보다 앞에서 요청을 종료시킨다.
기존: completion_execution.py:67~94의 한 번 수정 실패가 예외를 발생시키며,
96 이후의 재조사/부분 답변 분기에 도달하지 못한다.
관측: H05/H10은 관련 원문과 초안을 확보하고도 MISSING_SOURCE + material=false 충돌로 미답.
제안: 필요 여부(필수/선택/판단중)와 자료 상태(미확보/확보/부분전달/완전전달)를 별도 필드로
정의한다. 수정 실패에도 이미 확정된 이전 주장, 조사 상태, 실패 원인을 반환한다.
목표/검사: 선택적 상세를 잘못 분류한 오류가 모든 조사 성과를 사용자 화면에서 숨기지 않아야 한다.
부작용: 검증 실패한 새 claims는 확정 답변으로 자동 승격하지 않는다. 확정 claims가 없으면
법률 답 대신 조사 상태를 보여 준다. 법적 예외의 중요도를 코드가 임의로 낮추지 않는다.

F3. 선택 단계와 판단 단계가 같은 충분성을 따로 결정하고 충돌한다.
기존: SELECT의 evidence_sufficient/FINISH, ASSESS의 COVERED/gap/disposition이 각각 존재.
관측: REG-NG13은 SELECT ‘상법으로 충분’과 ASSESS ‘시행령 부족’ 사이를 반복했다.
제안: SELECT는 자료 확보/조사 중단 이유를 보고하고, 답변 coverage의 소유자는 ASSESS로
일원화한다. 복귀 시 부족분별 무엇이 달라졌는지 전달한다. 변화가 없으면 같은 루프를
계속 돌리지 않고 제한 답변/미완료를 반환한다.
목표/검사: 2회 재진입 여부보다, 각 재진입의 상태 변화와 실제 미해결 처리를 검사한다.
부작용: 이미 확보한 자료의 정당한 재해석도 변화로 인정하되 이유·관련 범위를 남긴다.

F4. 실패 결과를 사용자에게 전달할 때 상세 상태가 대부분 제외된다.
기존: app.py:81~88은 diagnostics 중 schema_version/stage/cause_codes/resume_available/
stop_reason만 반환한다. completion_execution.py는 해당 실패에서 resume_available=false.
관측: 저장 원문·부족분이 있는 미답 사례도 사용자 화면에서는 일반 미완료 문구로 끝난다.
제안: 공개 가능한 쟁점별 현황, 확보 자료 요약, 실패 대상, 다음 행동, 안전한 조회/재개 ID를
공통 결과 계약으로 제공한다. 내부 전체 로그를 노출하는 방식은 사용하지 않는다.
목표/검사: 직접 JSON/SSE와 별도 워크플로우에서 같은 미해결·중단 사유가 보존되어야 한다.
부작용: 다른 사용자의 자료명·원문·내부 경로·인증정보를 오류 응답에 담지 않는다.

F5. 반복 거절 이후 원래 화면 재선택이 보장되지 않는다.
기존: 같은 검색식은 거절, 수정 1회 실패하면 MODEL_DECISION_UNRESOLVED로 종료.
관측: REG-cm-039는 틀린 조문 가설을 반복하고 읽은 자료도 채택하지 못한 채 종료했다.
제안: 실패한 행동과 이전 성공 상태를 분리하고 해당 origin frame 및 아직 유효한 메뉴를
다음 판단에 제시한다. RETURN_TO 후 선택할 수 있게 하며 보류 자료를 자동 채택하지 않는다.
목표/검사: 한 행동 실패가 다른 성공한 읽기·채택 결과를 없애지 않아야 한다.
부작용: 무한 재시도를 허용하지 않는다. 예산 종료는 미완료 결과·checkpoint를 남기는 사건이다.

F6. 모델의 경쟁 맥락 누락은 시스템 결함과 분리해야 한다.
관측: REG-IC24는 INTENT에서 질문을 유지했고 첫 SELECT에서 감독기관 맥락 조사 필요를
스스로 기록했으나 이후 정정·삭제 조항만으로 완료했다. 기록은 후속 입력에도 있었다.
제안: 발견한 미해결 과제의 상태 전달은 시스템이 담당한다. 실제 어떤 제도가 맞는지와
어떤 근거가 충분한지는 모델 판단으로 남긴다. 답을 조문 번호로 하드코딩하지 않는다.
사용자 가이드: 업무 맥락·주체·행위·적용 시점·원하는 범위를 명시하고 잘못 선택한 경우
해당 쟁점과 근거를 지정해 재검토한다. 질문 원문·자료가 충분했는데 오판하면 모델 오류로 기록한다.

F7. 긴 이력/참조 메뉴의 정보 가용성은 별도 경계 검증이 필요하다.
코드 확인: action_chain은 현재 요청의 모든 행동/이유를 전달한다. dependency_cards는
16개, unresolved 요약은 8개로 제한하고 생략 메타데이터를 둔다. 참조 메뉴는 이력 결합
후 max_context_chars를 넘으면 reference_context_limit를 기록하고 종료할 수 있다.
이전 사건 이력은 첫 이벤트·최근 48개·지정 정정 차수를 남기고 history_partial로 표시한다.
확인 수준: 잘못된 무음 절단이 이번 실패의 직접 원인이라고 입증되지는 않았다.
제안/검사: 본문·이력·연결 각각의 전체량/제시량/생략량/추가 조회 수단을 검사하고 큰 입력에서
복구 가능한 페이지 전환을 확인한다. 근거가 사라지는 손실 요약을 기본 해결책으로 삼지 않는다.

4. 목표 전체 트리

[직접 /chat JSON·SSE] ─┐
                       ├─ 공통 service → /v1/rag/ask → 같은 사건·판단 엔진
[별도 Python 워크플로우] ┘           │
  ① 입력·권한·코드/데이터 판본 확인 ─ 실패 → 거절/충돌/운영 오류 + 공개 가능한 사유
  ② 새 질문인가 / 정정인가 / 이어서인가 / 직접 안내인가?
      ├─ 안내·필요한 확인 질문 → 안내/입력 대기 + 기존 사건 보존
      ├─ 완료 요청 재전송 → 현재성 검증 → 저장 결과 반환
      └─ 새 조사·정정·재개 → 요구사항 ID·현재 상태·기존 근거 연결
  ③ 검색/구조 탐색
      ├─ 0건 → 다른 표현·다음 경로·과거 화면 복귀 가능?
      │          ├─ 가능 + 모델 선택 → 다시 탐색
      │          └─ 종료 → '이 범위에서 못 찾음' 또는 부분 결과
      ├─ 도구 실패 → 부분 성공 저장 → 복구 가능/불명/불가 구분
      └─ 후보 있음 → 법령/조문/적중 위치 선택·다음 페이지
  ④ 원문 읽기
      ├─ 성공 → 확보 범위 ≠ 전달 범위 ≠ 채택 범위 영수증
      ├─ 일부 전달 → 이어보기 / 넓은 범위 / 다른 후보
      └─ 실패·권한 변경·원문 없음 → 사유 유지 → 복구/중단
  ⑤ 모델의 다음 행동
      ├─ 채택 / 보류 / 제외 → 해당 쟁점·이유·근거 기록
      ├─ 참조·정의 따라가기 → FOLLOW / SKIP / DEFER / 미해결
      ├─ RETURN_TO → 당시 선택지 + 현재까지의 자료·판단 보존
      ├─ 새 검색·추가 읽기 → ③/④
      └─ FINISH 또는 한도 중단 → '조사 종료 제안', 미해결 장부 유지
  ⑥ 쟁점별 판단
      ├─ 모순된 형식/연결 → 구체적 피드백 → 제한된 수정
      │      └─ 다시 실패 → 유효한 기존 결과 + 미완료 설명 (초안 미게시)
      ├─ 필요한 원문 부족 → 추가 조사 가능? → ③/④/⑤
      ├─ 사용자 사실 부족 → 조건부 답변 또는 사실 확인 질문
      ├─ 일부 근거만 확정 → 부분 답변 + 남은 쟁점·원인
      └─ 모든 요청 범위 판단 완료 → 완료 답변 후보
  ⑦ 인용·권한·세대·revision·출력 일치 검증
      ├─ 실패 → 게시 차단 + 복구 가능한 상태/조회 ID
      └─ 성공 → 동일 결과 계약을 직접/별도 경로에 전달
  ⑧ 사용자 결과: 답변 완료 / 부분 답변 / 추가 입력 필요 /
                 범위 내 못 찾음 / 조사 미완료 / 일시 실패 / 안전 중단

모든 화살표 공통: 실행 전 상태 → 시도 ID → 실제 결과 → 저장 → 다음 선택지.
어떤 실패도 완료로 자동 전환하지 않으며, 조사 종료가 모든 쟁점 해결을 뜻하지 않는다.

5. 하나의 공통 상태 계약 (제안)

7단계와 기존 영수증·RETURN_TO·원장을 유지하며 중복 파이프라인은 만들지 않는다.
서로 다른 상태를 하나의 완료 boolean으로 합치지 않는다.

작업 상태: RUNNING / WAITING_USER / STOPPED / FAILED / COMPLETED
답변 범위: NONE / PARTIAL / COVERED
중단 이유: MODEL_STOP / NO_MATCH / NO_PROGRESS / BUDGET / DEADLINE /
           MODEL_OUTPUT_INVALID / TOOL_ERROR / UPSTREAM / ACCESS_CHANGED /
           BINDING_CHANGED / USER_CANCELLED / PUBLICATION_CONFLICT
재개 정보: available, checkpoint_id, 필요한 선행조건, 사용한 예산, 최초 deadline.

쟁점별 장부(제안): issue_id, 원문 요구사항, 현재 status, missing_kind,
importance(REQUIRED/OPTIONAL/UNDETERMINED), evidence_refs, origin_frame_id,
last_decision_id, resolution_event_id, model_reason, updated_revision.
도구 관측(제안): action_id, input/view hash, target, execution_state,
success_receipts, failed_targets, retry_class, current_choices, successor_frame_id.
중단 응답(제안): 원 요청, 확정된 답변 범위, 미해결 목록, 실패/중단 사유,
공개 가능한 근거 요약, 사용자가 할 일, 안전한 조회·재개 handle.

금지할 상태 조합:
- 미열람인데 전달 완료/채택 완료로 표시.
- 해결 기록 없는 필수 쟁점이 사라졌는데 COVERED로 표시.
- UNKNOWN/FAILED 도구 시도를 성공 근거로 사용.
- 조사 종료만으로 전체 질문 해결을 표시.
- 부분 스트림·검증 실패 초안을 최종 정본으로 표시.
- 같은 요청 재개 시 예산과 deadline을 초기화.
- 권한/세대가 바뀐 과거 결과를 검증 없이 게시.

허용할 행동:
- 모델이 근거와 이유를 명시하고 범위 중요도를 재판단.
- 무관한 참조를 SKIP/OPTIONAL로 처리하고 현재 질문에 답변.
- 일부 근거로 제한 답변하고 남은 쟁점을 명시.
- 필요한 자료를 기존 화면으로 돌아가 다시 선택.
- 정상 선택지에서 모델이 의미상 잘못 고르면 모델 오류로 기록; 시스템이 법률 답을 강제하지 않음.

7. 검증 방법과 완료 기준

72개 행을 각각 새로운 법률 정답 실험으로 만들지 않는다. 가짜 도구·모델 출력과 작은 원문
fixture로 상태 전이를 결정적으로 검사한다. 그 다음 교차 상황을 선택해 실제 엔진을 통과시킨다.
각 검사에서 입력·제시 메뉴·모델 제안·실행 영수증·사건 DB·최종 응답을 동시에 대조한다.

필수 복합 시나리오:
1) 검색 0건 → 새 검색 → 부분 읽기 → 보류 → RETURN_TO → 채택 → 부분 답변.
2) 두 원문 중 하나 읽기 성공/하나 실패 → 프로세스 중단 → 같은 요청 재개 → 성공분 재사용.
3) ASSESS 핵심 gap → SELECT 즉시 FINISH → gap 유지 → 제한 답변 또는 명시적 범위 재판단.
4) 선택적 gap 분류 모순 → 수정 실패 → 확정된 기존 판단/조사 결과 보존.
5) 같은 검색 거절 → 원래 화면 → 다른 범위 선택; 다시 실패하면 중단 사유·재개 상태 표시.
6) 참조·행동 이력 문맥 한도 → 생략량·남은 큐·추가 조회 가능성 보존.
7) 읽기 이후 권한/세대/revision 변경 → 게시 거부 → 과거 상태 보존.
8) 게시 저장 후 네트워크 단절 → 같은 request ID → 저장 결과 검증·반환, 새 모델 호출 없음.
9) 동일 종료 결과를 직접 JSON/SSE와 별도 Python 워크플로우로 소비해 상태/본문/근거 비교.
10) 필요한 정보·도구가 모두 제공됐는데 모델이 오판 → 모델 오류로 분류하고 시스템 실패와 분리.

통과 목표: 미해결 항목의 무설명 유실 0, 실행 실패의 성공 처리 0, 권한/인용/세대 위반 0,
두 소비자의 결과 의미 차이 0. 이는 목표이며 아직 전 시나리오 실측 PASS가 아니다.
법률 세부 정답률 100%를 루프 완료 조건으로 삼지 않는다. 알려진 판단 오류는 가이드와 후속 기록으로 관리.
외부 모델 비교를 시작할 때는 별도 ADR·기준 동결·동일 코드 검증·MAIN 승격 절차가 필요하다.

이번 실행: 직접 소비자/직접 SSE/모델 경계 기존 검사 35 PASS, 별도 워크플로우 상태 검사 1 PASS,
동결된 워크플로우 HTTP 422/503 소비 2개 합성 경로 PASS. 외부 모델 호출 없이 확인했다.
직접 경로 검사에는 로컬 HTTP 연결이 포함되며, 외부 서비스나 GENOS에는 접속하지 않았다.
새 72개 시나리오 전체 실행, GENOS 내부 모델, 앞단 Socket.IO, 실제 현장 재개는 미검증이다.

8. 부작용 검토

모든 연결을 필수화 → 탐색 폭증: 쟁점 중요도와 링크 존재 분리.
형식 오류를 지나치게 허용 → 근거 없는 답 게시: 확정된 주장과 거절 초안 분리.
중단 후 재시도 확대 → 중복 호출·비용 증가: 도구/모델 수락 여부와 동일 요청 예산 유지.
부분 답변 확대 → 완료로 오해: 답한 범위와 미해결을 두 소비자에서 동일하게 표시.
과거 화면 복귀 → 오래된 권한/판본 사용: 메뉴는 과거 화면, 실행 검증은 현재 binding.
상태 장부 확대 → 긴 모델 입력·DB 증가: 원문 중복 복사 대신 ID/영수증 참조, 조회 가능성 유지.
스키마 이행 → 옛 checkpoint 재개 실패: 버전별 판독·명시적 재시작/롤백 경계.
프런트별 독립 상태 판단 → 표시 불일치: 공통 결과 계약을 소비하고 프런트 추론 최소화.

성능·비용·일정 개선 폭은 미산정이다. 늘어나는 상태 전송 토큰과 줄어드는 재시도를 함께
측정해야 하며 현재 값으로 속도 향상을 단정하지 않는다. ‘시나리오가 많다’는 이유만으로
검증을 생략하거나 모든 분기를 하나의 에러로 합치지 않는다.
