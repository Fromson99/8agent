우리 legal_agent를 LLM 입력과 한 번의 판단 단위로 풀어 설명
작성 기준: 2026-10-07, 로컬 MAIN 선택 포인터 generation 44
선택 릴리스: investigation-completion-v6-20261007-r1

이 문서는 설명을 위한 추가 문서다. 에이전트 코드나 MAIN 포인터를 변경하지 않았다.
현재 코드를 읽어 확인한 흐름과 아직 구현하지 않은 수정 목표를 구분한다.
아래 A규정·B규정·10일은 설명용 모의 자료이며 실제 법률이나 실행 기록이 아니다.

1. 가장 먼저 이해할 구조

우리 에이전트는 코드가 현재 상황을 모아 LLM 입력을 만들고, LLM이 다음 행동이나
판단을 제안하고, 코드가 그 제안을 검사하고 실행하는 구조다.

    코드: 현재 상황을 입력으로 조립
      → LLM: 이번 호출에 맡겨진 판단을 출력
      → 코드: 허용된 행동·원문·현재 상태와 맞는지 검사
      → 코드: 검색 / 원문 읽기 / 상태 기록 / 답변 구성 실행
      → 코드: 결과를 넣어 다음 LLM 입력 조립

검색 결과가 없다는 것, 읽기 도구가 실패했다는 것, 읽은 내용을 모델이 잘못
해석했다는 것, 출력 형식이 틀렸다는 것은 서로 다른 사건이다.
같은 '탐색 실패'로 묶으면 어떤 입력에서 무엇을 복구해야 하는지 보이지 않는다.

입력 블록은 한 번의 LLM 호출 안에 넣는 내용의 묶음이다.
블록마다 별도 LLM이나 별도 에이전트를 호출한다는 뜻은 아니다.

실제 요청의 큰 형태:
    system: 이번 판단의 역할과 지켜야 할 규칙
    user.view: 이번 판단에 필요한 질문·상태·자료·행동 메뉴
    response_format: 출력 JSON의 형식과 허용 ID

user.view 내부의 논리적 블록을 아래에서 풀어 쓴다. 원문 전체·전체 대화·전체
허용 문서 목록이 모든 호출에 반복 전달되지는 않는다. 현재 판단에 맞는 입력을
만든다. 일부 출력 스키마는 user 본문에도 포함되고, compact 설정에서는 중복을
줄인다. 출력 스키마는 법률 근거가 아니라 모델이 반환할 형식과 선택 범위다.

2. 전체 호출 순서

사용자 입력
 ├─ 코드: 입력·권한·요청 ID·선택 세대·기존 사건 확인
 ├─ 이미 게시한 동일 요청을 반환할 수 있음 → 현재성 검사 후 저장 결과 반환
 └─ 새 실행이 필요한 요청
     ├─ LLM 1: 조사할 요청인가, 짧은 안내로 답할 요청인가?
     │   ├─ DIRECT → 짧은 안내 반환
     │   └─ CASE → 사건 처리
     ├─ LLM 2: 새 질문인가, 사실 정정인가, 재개인가, 표현 변경인가?
     ├─ LLM 3: 고른 처리 명령이 사용자 요청을 제대로 반영하는가?
     ├─ 새 조사에서는 LLM 4: 무엇을 답해야 하는지 Q1·Q2 등으로 나누기
     ├─ 코드: 검색 계획 조립 → 후보 검색 → 읽기 준비
     ├─ LLM 5: 현재 화면에서 다음 탐색 행동 고르기 [반복]
     │   ├─ 후보 보기 → 원문 읽기 요청 → 코드 실행 → 바뀐 입력으로 LLM 5
     │   ├─ 원문 보기 → 이어읽기 / 범위 확대 / 채택 / 보류 / 제외
     │   ├─ 참조 조사 선택 → LLM 6의 참조 메뉴
     │   ├─ 새 검색 선택 → 코드 검색 → 바뀐 입력으로 LLM 5
     │   ├─ 이전 화면 복귀 → 현재 확보 자료를 보존하며 LLM 5 또는 LLM 6
     │   └─ 조사 종료 제안 → LLM 7
     ├─ LLM 6: 원문이 가리키는 참조를 따라갈지, 어느 범위를 읽을지 판단
     │   └─ 코드 읽기·기록 → 탐색 입력에 반영
     ├─ LLM 7: Q1·Q2 각각 무엇까지 근거로 답할 수 있는지 판단
     │   ├─ 필요한 원문 부족 + 조사 가능 → 부족한 사항을 넣어 LLM 5로 복귀
     │   ├─ 일부만 근거 확보 → 부분 답변과 미확인 사항
     │   ├─ 모두 답할 수 있음 → 완료 답변 후보
     │   └─ 형식·근거 연결 오류 → 제한된 수정 호출
     └─ 코드: 채택된 판단 문장으로 답변 구성 → 인용·권한·세대 검증 → 응답

현재 저장 단계는 INTENT / PLAN / RECALL / READ / SELECT / ASSESS / COMPOSE다.
저장 단계와 LLM 호출은 일대일이 아니다. PLAN·RECALL·READ는 여기서 코드가
수행하고, SELECT 안에서 LLM 탐색 판단이 여러 번 실행될 수 있다.
현재 completion 계약의 COMPOSE도 코드가 구성한다. 답변 문장은 ASSESS에서
모델이 작성한다. 별도 최종 의미 평가 LLM이 한 번 더 정답을 보증하지 않는다.

LLM 1~7은 설명을 위한 호출 종류 번호다. 모든 요청이 반드시 일곱 번 호출되는
것은 아니다. 사실 정정은 뒤 단계부터 재개할 수 있고, 표현 변경은 저장 판단을
이용할 수 있다. 동일 계약의 절차 재사용이 성립하면 호출을 재사용할 수 있다.
탐색 반복·참조·수정 때문에 호출 수가 늘기도 한다. 같은 실행의 예산과 시간
제약을 함께 사용한다. 저장 단계가 나뉘었다고 독립 모델 일곱 개를 돌리지는 않는다.

3. LLM 1 — 이번 입력에 조사 에이전트가 필요한가?

실제 phase: source-request-route

입력 블록:
 A. 이번 사용자 문장: question
 B. 진행 중인 사건의 목적·사용자 사실·상태: current_goals
 C. 시스템이 제공하는 기능과 조회 제한: capabilities

판단 단위:
 '인사·사용법 같은 짧은 안내인가, 원문 조사나 기존 사건 처리가 필요한가?'

출력:
 DIRECT: 짧은 안내 문장과 이유
 CASE: 사건 처리로 넘어갈 이유. 법률 답변을 이 단계에서 대신 작성하지 않는다.

코드 처리:
 DIRECT는 일반 안내 응답으로 반환한다.
 CASE는 다음 명령 결정 입력을 만든다.
 법률 근거가 당장 보이지 않는다는 이유로 짧은 안내 경로에 숨기지 않는다.

실패:
 형식이나 모델 호출이 실패하면 정상적인 CASE/DIRECT 판단을 받은 것으로
 처리할 수 없다. 성공한 기존 사건을 지우지 않고 실패 원인과 연결하는 것이
 목표다. 모든 예외가 풍부한 사용자 응답으로 연결되는 것은 현재 미완성이다.

4. LLM 2 — 이번 문장을 기존 작업에 어떻게 연결할까?

실제 phase: memory-resolve, 필요 시 memory-resolve-repair

입력 블록:
 A. 이번 원문 문장: utterance
 B. 현재 사건: 기존 목적, 사용자 사실, 단계, 저장 상태
 C. 변경 이력: 최초 기록·최근 기록·사용자가 지목한 정정 기록
 D. 조회할 수 있는 과거 질문·경험·위키 연결
 E. 이번에 허용된 처리 명령 목록: offered_methods

판단 단위:
 '새 사건을 만들 것인가, 기존 사건의 어느 부분만 바꿀 것인가?'

대표 출력:
 CASE_START: 새 질문 조사
 FACT_UPDATE: 사실만 수정
 PURPOSE_REVISE: 질문 목적 수정
 RESEARCH_REPLAN: 검색 계획 수정
 RESEARCH_REENTER: 특정 조사 지점 재개
 ANSWER_PRESENT: 현재 판단의 표현 변경
 HISTORY_EXPLAIN: 조사·정정 이력 설명
 STATE_RESTORE: 지정 기록의 지정 필드 복원

코드 처리:
 method를 내부 명령과 재개 단계로 정규화한다.
 이미 제공된 사건·경험 ID인지, 지정 기록이 존재하는지 등을 검사한다.
 사용자에게 '접수일만 바꾸라'는 요청을 받았으면 다른 목적이나 검색어까지
 임의로 바꾸는 명령을 허용하지 않는다.
 문서 접근권한은 코드가 관리한다. 모델에 허용 문서 ID 전체를 주고 모델이
 권한을 확대하게 하지 않는다.

실패:
 첫 명령이 거절되면 원래 문맥 + 거절된 명령 + 오류 이유를 수정 입력으로 준다.
 수정 후에도 실패하면 CLARIFY로 이어질 수 있다.
 재개·정정의 '시작 단계'는 그 단계에서 멈추라는 뜻이 아니다. 의존 자료를
 복구하고 답변 구성까지 이어가는 시작점이다.

5. LLM 3 — 방금 고른 명령이 원래 요청과 맞는가?

실제 phase: memory-command-check

입력 블록:
 A. LLM 2가 받은 사용자 문맥: context
 B. 코드가 정규화한 명령: command
 C. 실행 계약: 어느 단계부터 시작하며 어떤 순서로 완료해야 하는지

판단 단위:
 '사용자가 요청한 변경 범위와 실제 실행할 명령이 일치하는가?'

출력: valid + reason

코드 처리:
 valid=true이면 명령을 적용한다.
 valid=false이면 LLM 2의 제한된 수정으로 돌아간다.
 이 검사는 변경 명령의 적합성이다. 법률 답변이 정답인지 평가하는 단계가 아니다.
 형식·권한 등 코드 검사를 통과해도 모델의 의미 판단이 항상 옳다는 뜻은 아니다.

6. LLM 4 — 원래 질문에서 무엇을 답해야 하는가?

실제 phase: memory-intent

입력 블록:
 A. 이번 원문 질문: current_request
 B. 기존 상태에 반영된 현재 목적·질문: question
 C. 사용자 제공 사실: current_facts
 D. 해당 실행 단계의 등록 도메인·방법 정보

판단 단위:
 '사용자가 요구한 답변 항목, 대상, 조건과 예외를 무엇으로 나눌까?'

모의 질문: 'A규정의 신청 기한과 제출서류를 알려줘.'
 기대하는 요구 분리:
 Q1: 신청 기한
 Q2: 제출서류

일반 규정 설명 요청을 특정 신청 건의 적법성 판단으로 바꾸지 않는다.
검색에서 기한 조항만 나왔다고 Q2를 요구사항에서 없애지 않는다.
출력에는 목적·검색용 개념·쟁점이 들어간다. 이 단계에서 근거 없는 답을 쓰지 않는다.

코드 처리:
 쟁점 ID 중복 등을 검사하고 INTENT를 저장한다.
 PLAN: 상태의 검색어·질문·등록 문서명 등을 이용해 검색 계획을 구성한다.
 RECALL: 현재 색인에서 후보를 찾는다.
 READ: 후보·원문 읽기 계약과 근거 검증을 준비한다.
 현재 법령 탐색 경로에서는 초기 READ가 전체 원문을 모두 읽었다는 뜻이 아니다.
 SELECT의 행동에 따라 실제 원문 읽기와 전달이 더 발생한다.

7. LLM 5 — 지금 보이는 화면에서 다음에 무엇을 할까?

실제 phase: source-law-navigation-{turn}, 필요 시 ...-repair

이 부분이 탐색의 중심이다. 아래 5-A~5-E는 다른 에이전트가 아니라 같은 탐색
호출의 화면·판단 목적을 구분한 설명이다. 매번 현재 입력과 유효 선택지가 바뀐다.

공통 입력을 여덟 블록으로 읽으면 이해하기 쉽다.

 A. 질문과 쟁점
    question, issues, assessment_gaps
    무엇을 알아봐야 하는지, 판단 단계에서 무엇이 부족하다고 했는지.
    SELECT에는 현재 task·facts로 만든 질문과 쟁점이 들어간다.
    이번 원문 current_request가 별도 필드로 모든 탐색 호출에 반복되는 것은 아니다.

 B. 현재 검색 후보
    search_queries, laws[].articles, article_matches, previews, more_laws
    어느 검색으로 어떤 문서·조항이 나왔는지, 다음 후보 페이지가 있는지.
    검색 미리보기는 실제 원문 읽기·전달 완료와 다르다.

 C. 이번에 실제로 보여주는 원문
    sources, basis
    읽기 요청 이후 모델에게 제시한 원문 페이지와 연결 ID.
    법률 근거로 판단할 때는 실제 전달된 범위를 사용한다.

 D. 자료 상태와 읽기 상태
    saved_inventory, read_receipt, branches, adopted_evidence
    저장했는지, 어디까지 확보·전달했는지, 어느 쟁점에 채택·보류·제외했는지.
    저장 원문 목록은 내용 자체가 아니다. 저장되었다고 이번 모델이 본 것도 아니다.

 E. 이전 행동과 이유
    investigation_chain, notes, search_expression_history
    왜 이 후보를 읽었는지, 무엇을 보류했는지, 이미 시도한 검색은 무엇인지.
    전체 과거 원문을 매 호출마다 반복 복사하는 대신 필요한 기록을 전달한다.

 F. 돌아갈 수 있는 이전 화면
    return_points, chain_frame_id
    보류했던 당시 후보·읽기·참조 메뉴를 다시 선택할 수 있는 출발 지점.
    이후의 확보 자료나 판단을 통째로 되돌리는 롤백과 다르다.

 G. 지금 허용된 행동 메뉴
    actions, branches[].allowed_decisions
    실제로 선택 가능한 행동 ID, 대상, 표시 문구와 효과.
    모델이 없는 행동·없는 자료 ID를 만들면 코드가 거절한다.

 H. 현재 상태와 한도
    presentation_id, state_version, progress, reading_rule, completion_contract
    어느 화면에 대한 결정인지, 진전 없는 반복인지, 읽기와 채택을 분리해야 하는지.
    출력 스키마도 현재 메뉴의 유효 ID와 형태를 제한한다.

5-A. 후보를 보고 무엇을 읽을지 결정

입력 예:
    요구: Q1 기한 / Q2 서류
    후보: A규정 제5조, C규정 제8조
    A규정 미리보기: '신청은 ... / 제출서류는 ...'
    C규정 미리보기: 다른 업무의 신청
    이번에 실제 받은 원문: 없음
    가능한 행동: A 읽기 / C 읽기 / 다음 후보 / 새 검색 / 제시된 복귀

판단:
    어느 후보가 질문의 대상·업무 맥락에 맞는가?
    어느 원문 범위를 먼저 읽을까?

출력:
    READ_ARTICLES / READ_PARENT / READ_SCOPE / OPEN_LAW 등 + 대상 ID + 이유

코드:
    유효한 대상과 권한을 검사 → 읽기 또는 후보 화면 변경
    → 실제 결과를 넣어 다음 탐색 입력 생성

분기:
    관련 후보 있음 → 원문 읽기
    후보 있지만 질문과 무관함 → 다른 후보 / 새 검색 / 제시된 복귀
    검색 0건 → 다른 검색 / 구조 탐색으로 이어지는 메뉴 / 제시된 복귀
    가능한 경로 소진 → PENDING 또는 한도에 따른 중단
    검색 도구 오류 → 검색 결과 0건과 구분하여 실패 처리

'0건'은 이번 검색과 자료 범위에서 찾지 못했다는 뜻이다.
'해당 규정이 존재하지 않는다'는 법률 판단으로 바꾸면 안 된다.
도구 예외 뒤 항상 같은 화면으로 복구하는 공통 흐름은 현재 완성되지 않았다.
수정 목표는 성공한 결과를 유지하고 실패한 검색·이유·가능한 다음 행동을 제공하는 것이다.

5-B. 읽은 원문을 어디까지 더 볼지 결정

입력 예:
    A규정 제5조 본문 일부가 이번 sources에 들어옴
    앞 문장에서 신청 기한을 찾음
    뒤 문장·다른 항·참조 문서는 아직 전달되지 않음
    읽기 상태: 확보 범위와 실제 전달 범위
    가능한 행동: 이어보기 / 상위 전체 읽기 / 다른 항 읽기 / 이후 결정

판단:
    현재 본 범위로 이 조항의 조건·예외를 파악할 수 있는가?
    어떤 범위를 더 읽어야 하는가?

코드:
    선택한 원문 범위를 확보·검증하고 다음 입력으로 전달한다.
    현재 계약에서 READ/VIEW 호출의 채택·보류 결정 배열은 비워야 한다.
    원문을 가져온 동작을 채택으로 처리하지 않는다.

분기:
    원문 전달 성공 → 다음 입력에서 내용을 보고 결정
    일부만 전달 → 이어보기나 범위 확대
    읽기 실패 → 성공한 다른 자료는 유지; 실패한 자료를 읽었다고 표시하면 안 됨
    시간·분량 한도 → 실제 확인한 범위와 미확인 범위 구분

5-C. 읽은 자료를 채택·보류·제외할지 결정

입력 예:
    요구: Q1 기한 / Q2 서류
    읽은 A규정 제5조: '신청 기한은 10일 ... 서류는 B규정 제2조 ...'
    B규정 제2조: 아직 읽지 않음
    가능한 결정: A의 해당 전달 범위를 Q1에 채택 / 보류 / 제외

판단:
    A의 읽은 범위가 어떤 쟁점의 근거인가?
    왜 채택하거나 아직 보류할까?

출력:
    DECIDE와 branch_decisions의 ADOPT / KEEP / DEFER / EXCLUDE,
    쟁점 ID, 실제 원문 연결 ID, 이유

코드:
    실제 전달한 원문으로 가능한 결정인지 검사 → 자료별·쟁점별 상태 기록
    Q1의 근거 채택이 Q2까지 해결했다는 뜻은 아니다.
    모델은 맥락에 맞는 후보를 고를 책임이 있다. 코드가 인용 ID를 검증했다고
    선택한 조항의 의미가 질문에 맞는다는 것이 자동 보증되지는 않는다.

5-D. 보류했던 자료를 다시 선택

입력:
    보류 당시 화면을 가리키는 return_points
    현재까지 읽고 채택한 자료의 상태
    저장 원문 목록과 별도 재열람 선택지

판단과 코드:
    RETURN_TO → 보류 당시의 후보·읽기·참조 메뉴로 돌아가 재선택
    VIEW_SAVED_SOURCE → 저장된 특정 원문을 다시 전달

두 행동은 목적이 다르다. 화면 복귀가 이후 조사 결과를 지우지는 않는다.
재열람만으로 보류·제외 상태를 채택으로 바꾸지도 않는다.
다시 보고 모델이 채택·보류·제외 판단을 따로 제출한다.

5-E. 계속 조사할지, 판단 단계로 넘길지 결정

입력:
    요구 Q1·Q2, 채택 근거, 보류 자료, 참조 상태,
    이전 조사 기록, 판단 단계에서 돌려보낸 assessment_gaps,
    반복·검색 한도와 현재 가능한 행동

출력:
    RESEARCH: 검색어를 바꿔 후보 검색으로 돌아가기
    READ...: 필요한 원문 범위를 더 읽기
    FOLLOW_CONNECTION: 참조 메뉴 조사
    RETURN_TO: 이전 화면 복귀
    FINISH: 탐색을 마치고 판단으로 넘기기
    PENDING: 이 탐색 실행에서 진행을 완료하지 못함

현재 출력에는 evidence_sufficient와 sufficiency_reason도 있다.
선택과 판단이 각각 충분성을 결정하면 '충분 → 부족 → 충분'이 반복될 수 있다.
수정 목표: 여기서는 확보 자료·조사를 멈춘 이유를 보고하고,
실제 답변 가능 범위는 LLM 7에서 쟁점별로 결정한다.

현재 결함: FINISH를 적용할 때 현재 assessment_gaps를 제거하는 코드가 있다.
따라서 'Q2의 B원문 부족'을 추가 조사 입력으로 받았더라도 FINISH만으로 현재
부족 목록이 사라질 수 있다. 과거 로그 전체 삭제와는 다르지만 현재 상태 연결은 끊긴다.
수정 목표: 조사 종료 뒤에도 부족 항목을 보존하고 해결·보류·불필요 판단의
이유를 기록한다. 영속적인 gap ID와 처리 상태는 아직 새로 구현하지 않았다.

탐색 판단 출력이 거절될 때:
    원래 화면 + 원래 행동 메뉴 + rejected_decision + contract_error + repair_contract
      → 한 번의 수정 제안 → 코드가 전체 결정을 다시 검증
    잘못된 최초 제안은 실행하지 않는다.
    수정도 실패하면 현재는 예외로 종료될 수 있다.
    원래 화면·유효 선택지·성공한 작업을 일관되게 돌려주는 것은 수정 목표다.

8. LLM 6 — 읽은 원문이 가리키는 다른 자료를 따라갈까?

실제 phase: source-reference-* 계열

입력 블록:
 A. 현재 질문: question
 B. 이번 연결이 나온 출발 원문: sources
 C. 출발점과 참조 대상: groups[].anchor, target
 D. 원문에 실제 연결이 있다는 확인 자료: connections
 E. 필요한 읽기 의무와 제공 가능한 범위: reading_obligations, read_options
 F. 보류·미해결 참조와 아직 제시하지 않은 연결 수
 G. 현재까지의 행동 이력과 복귀 문맥, 한도

판단 단위:
 '이 참조가 현재 질문에 필요한가? 필요하면 제시된 어느 범위를 읽을까?'

모의 입력:
    A규정 제5조에 '서류는 B규정 제2조에 따른다'라는 문장이 있음
    참조 대상: B규정 제2조
    B 본문: 아직 없음
    읽기 선택지: 제시된 조·항 또는 부모 범위

출력:
 FOLLOW: 참조 대상의 선택 범위를 읽는다
 SKIP: 관련 없다는 이유와 함께 건너뛴다
 DEFER: 판단을 보류하고 출발 화면을 남긴다
 적용 판단: APPLIES / DOES_NOT_APPLY / UNDETERMINED 및 이유

코드:
    메뉴에 제시된 연결과 범위인지, 읽기 의무와 한도에 맞는지 검사
    → 원문 읽기·검증·기록 → 탐색에 반영
    연결을 따라 읽는 것과 최종 답변 근거로 채택하는 것은 구분한다.

분기:
    FOLLOW 성공 → B 원문 확보; 탐색에서 실제 전달 범위 확인 후 채택 판단
    질문과 무관한 참조 → 근거 있는 SKIP; 모든 참조를 필수로 만들지 않음
    아직 판단 못함 → DEFER와 출발 지점 유지
    대상 못 찾음 → 미해결 참조로 구분; B 내용을 추측하지 않음
    읽기·모델·시간 실패 → 성공한 A 자료와 미해결 B 상태를 남기는 것이 목표
    참조가 메뉴에 없음 → 이 색인의 확인 범위에서 검증된 연결이 없다는 뜻

'A가 B를 참조한다는 사실을 확인'과 'B 원문을 읽어 내용을 확인'은 다르다.
참조 성공이 질문의 모든 요구사항 해결을 의미하지도 않는다.

9. LLM 7 — 이제 쟁점별로 어떤 답을 쓸 수 있는가?

실제 phase: memory-assess, 필요 시 memory-assess-repair

입력 블록:
 A. 이번 사용자 원문: current_request
 B. 처음 정리한 원래 요구사항: original_requirements
 C. 현재 쟁점과 사용자 사실: issues, current_facts
 D. 채택된 자료의 원문: sources
 E. 실제 인용 가능한 원문 조각의 선택 ID: evidence_options
 F. 저장되었지만 채택하지 않은 자료의 목록: saved_inventory
 G. 보류·미해결 참조와 조사 이력: reference_navigation, investigation_chain
 H. 추가 조사 가능 횟수 상태: reentry_budget
 I. 수정 호출일 때만 거절된 판단과 오류: repair_feedback

판단 단위:
 'Q1과 Q2를 각각 어느 근거로, 어느 조건에서, 어디까지 답할 수 있는가?'

출력:
 claims: 답변할 판단 문장 + 쟁점 ID + 근거 S ID
 issue_assessments:
    COVERED: 해당 요구를 설명할 근거를 갖춤
    PARTIAL: 일부만 설명할 수 있음
    INSUFFICIENT: 해당 요구에 필요한 근거가 부족함
 gaps: 무엇이 왜 부족하고 어떤 다음 행동이 필요한지
 disposition: ANSWER / LIMITED_ANSWER / NEEDS_INVESTIGATION

모의 정상 입력:
    Q1: 신청 기한
    Q2: 제출서류
    S1: 채택된 A규정 제5조의 기한 원문
    S2: 채택된 B규정 제2조의 서류 원문
    출력: Q1 COVERED + Q2 COVERED + 근거에 연결한 판단 문장

모의 부분 입력:
    Q1: 신청 기한
    Q2: 제출서류
    S1: A규정 제5조의 기한 원문
    B규정 원문: 미확보
    출력: Q1 COVERED, Q2 INSUFFICIENT,
          Q2 MISSING_SOURCE 또는 UNRESOLVED_REFERENCE,
          추가 원문 조사 행동

코드 분기:
    필요한 원문 부족 + 조사 예산·시간·횟수 남음
      → 판단과 gaps·기존 investigation_state를 묶어 SELECT로 복귀
      → 다음 탐색 입력 A블록의 assessment_gaps에 부족 사항 추가
    필요한 원문 부족 + 더 조사할 수 없음 + 유효한 claims 있음
      → LIMITED_ANSWER와 확인된 설명·남은 요구사항
    특정 사건 적용에 필요한 사용자 사실 부족
      → MISSING_FACT와 조건부 설명/확인할 사실
      → 법령 내용 부족을 사용자 사실 부족으로 바꾸지 않음
    근거 있는 claims가 하나도 없음
      → 미완료 처리; 답을 꾸며내지 않음
    모두 답할 수 있고 계약 검사를 통과
      → 코드 답변 구성으로 이동

모델 판단 오류와 출력 계약 오류는 구분해야 한다.
출력 계약 검사는 쟁점 누락·중복, 근거 ID, 근거 범위와 상태 충돌을 검사한다.
여기서 통과했어도 다른 업무 맥락의 조항을 의미적으로 골랐을 가능성은 남는다.

현재 형식 오류 경로:
    첫 판단이 계약과 충돌 → 원 입력 + 거절된 판단 + 모든 오류 이유로 수정
    수정도 실패 → InvestigationPending으로 종료
    이 분기는 추가 조사·부분 답변 분기보다 앞에 있다.
    따라서 이미 확보한 조사 성과가 있어도 사용자에게 일반 미완료만 보일 수 있다.

수정 목표:
    이전에 검증된 자료와 판단은 보존
    확정하지 못한 새 판단은 답변에 섞지 않음
    해결되지 않은 쟁점과 형식 실패를 구분
    사용자에게 확인한 범위·미확인 범위·중단 이유·다음 행동 제공

10. 답변 구성과 게시 — 현재 계약에서는 새 LLM 판단 호출이 없음

입력:
    저장된 ASSESS 판단 문장, 근거 연결, 쟁점별 상태, 미확인 사항, 표현 형식

코드:
    COMPOSE에서 선택된 판단 문장을 정해진 방식으로 구성
    → 판단 문장·인용 원문·권한·코드/데이터 결속·현재성·답변 일치 검사
    → 공통 결과를 API와 별도 워크플로우 소비자에 전달

실패:
    게시 검사 실패 → 해당 결과를 정상 게시하지 않음
    성공한 조사·현재 미해결·검사 실패 이유·복구 정보는 보존되어야 함
    현재 API 예외 응답은 진단을 일부 필드로 축소한다.
    두 경로에서 풍부한 실패 성과를 같은 방식으로 표시하는 것은 수정 목표다.

11. 한 질문을 처음부터 끝까지 따라가기

사용자: 'A규정의 신청 기한과 제출서류를 알려줘.'
    → LLM 1: CASE
    → LLM 2: CASE_START
    → LLM 3: valid=true
    → LLM 4: Q1 기한, Q2 서류
    → 코드: 후보 검색

탐색 입력 1:
    Q1·Q2 + A제5조 후보 + 미리보기 + READ 행동 메뉴
    모델: A제5조 원문 읽기
    코드: 실제 원문 확보·검증·전달 준비

탐색 입력 2:
    Q1·Q2 + A본문 '10일 / 서류는 B제2조' + 읽기 상태 + 결정 메뉴
    모델: A의 기한 부분을 Q1 근거로 채택
    코드: 채택 이유·쟁점·원문 연결 기록

탐색 입력 3:
    Q1 채택 상태 + Q2 + B참조 정보 + FOLLOW_CONNECTION 메뉴
    모델: 참조 조사
    코드: 참조 메뉴 조립

참조 입력:
    질문 + A 출발 원문 + B 대상 + 유효 읽기 범위
    모델: B의 제시 범위 FOLLOW
    코드: B 읽기

B 읽기 성공:
    → 탐색 입력에 B 실제 원문 제시
    → 모델: Q2 근거로 채택
    → 모델: FINISH로 판단 단계에 넘김
    → 판단 입력: 원문 요청 + Q1·Q2 + A/B 채택 근거 + 참조 현황
    → 모델: Q1·Q2 설명과 근거를 연결
    → 코드: 구성·검증·응답

B 읽기 실패 또는 끝까지 못 찾음 — 원하는 수정 후 흐름:
    → A의 Q1 성과 유지
    → Q2의 B 원문 부족 유지
    → 가능하면 다른 범위·검색·출발 화면에서 재선택
    → 더 조사할 수 없으면 판단 입력에도 Q2 부족 전달
    → '기한은 확인 / 서류는 미확인 / B 읽기 실패 또는 탐색 범위에서 못 찾음'
    → 다음 행동과 함께 부분 답변

주의: 위 실패 흐름을 모든 예외에서 현재 이미 보장하는 것은 아니다.
현재는 PENDING·도구 예외·수정 실패가 ASSESS 전에 실행을 종료할 수 있다.
그 공통 실패 경로까지 기존 성과를 사용자에게 연결하는 것이 이번 수정 목표다.

12. 이번 수정 목표를 LLM 입력에 연결하면

문제 A: 추가 조사 후 FINISH로 현재 부족 목록 제거
 현재: assessment_gaps 전달 → FINISH에서 pop → 현재 상태에서 사라질 수 있음
 목표: Q2/gap 식별자를 유지; 해결·보류·불필요 판단의 이유를 별도로 기록
 영향: SELECT 입력, ASSESS 복귀, 저장 상태, 결과 소비자
 확인: 같은 미해결 항목이 단계 이동·종료·재개 후에도 추적되는지

문제 B: 선택은 충분, 판단은 부족으로 반복
 현재: 선택과 판단이 각각 충분성 출력
 목표: 선택은 자료 현황·조사 중단 이유; 판단은 쟁점별 답변 범위
 영향: 탐색 출력 계약과 ASSESS 입력·복귀 계약
 확인: 동일 자료·동일 검색의 반복을 진행으로 세지 않는지

문제 C: 판단 형식 수정 실패가 성과를 가림
 현재: 수정 실패에서 예외; 추가 조사·부분 답변 분기에 도달하지 못함
 목표: 검증된 기존 자료·판단은 유지, 확정 실패한 부분만 미완료로 표시
 영향: completion_execution, 진단 저장, API/워크플로우 소비자
 확인: 거절된 새 문장을 게시하지 않으면서 기존 성과가 동일하게 보이는지

문제 D: 행동 거절·도구 실패 후 복구 일관성 부족
 현재: 일부 메뉴 수정은 구현되어 있으나 실패 후 원래 선택지 복귀는 통일되지 않음
 목표: 원래 화면·유효 행동 + 실패 대상·이유 + 성공한 자료로 복구 입력 조립
 영향: law_navigation, 참조 메뉴, 공통 예외 계약
 확인: 실패한 행동 재실행·중복 호출·예산 초기화가 생기지 않는지

문제 E: 사용자 실패 응답 축소
 현재: 내부 기록이 있어도 API 진단 일부 필드로 축소 가능
 목표: 확보 자료·미해결 쟁점·중단 이유·다음 행동을 두 경로에 같은 계약으로 전달
 영향: app.py, 통합 결과/진단, workflow.py의 소비·표시
 확인: 동일 내부 결과가 두 경로에서 같은 답변 범위·실패 정보를 갖는지

문제 F: 자료가 있는데 다른 맥락의 조항 선택
 현재: 근거·형식 검증만으로 의미 판단의 정답을 보증할 수 없음
 목표: 후보 채택 이유와 질문 맥락을 연결해 보이고 사용자 정정으로 재검토 지원
 영향: 선택 이유·이력·맥락 입력; 정답 조문을 코드로 강제하지 않음
 확인: 사용자 맥락 정정이 다음 명령·탐색·판단 입력에 실제 반영되는지

이 수정안들은 상태·입력·출력 계약에 함께 연결되어야 한다. 프롬프트에
'기억하라'를 넣는 것만으로 코드가 삭제한 상태나 API가 버린 필드를 복원할 수 없다.
영속 gap 상태를 추가하면 스키마와 재개 이행도 함께 설계해야 한다.
자료 본문은 해시로 공유하고, 입력에는 필요한 페이지와 상태를 전달하여
같은 원문을 사건 기록·입력·보고서마다 반복 복사하지 않도록 확인해야 한다.

검증·도입 목표는 작업 코드 통합 → 동일 코드 계약·연결 검증 → 적격 후보의
MAIN 승격 → 선택 포인터와 실제 로컬 서비스 결속 확인이다. GENOS 현장 적용은
별도다. 이 설명 문서 작성에서는 구현·새 모델 실험·MAIN 승격을 실행하지 않았다.
지연·토큰·비용 개선 수치는 측정하지 않았다.
