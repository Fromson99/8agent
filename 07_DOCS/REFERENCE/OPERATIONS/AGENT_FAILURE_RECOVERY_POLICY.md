# 에이전트 실패와 충돌 처리 코딩 지침

2026-10-13 사용자 지시로 정한 필수 개발 기준이다. MAIN의 입력·구조화·용어 연결·색인·RAG·피드백에서 모델 제안을 받아 실행하거나 저장하는 코드에 적용한다. 구체 연결 예시는 현재 법률 RAG 실행 경로를 기준으로 한다.

목표는 **복구 가능한 오류를 정해진 경로로 처리하고, 복구할 수 없는 오류는 원인과 상태를 보존하며 종료하는 것**이다. 오류를 없애기 위해 근거·권한·무결성 검사를 끄지 않는다. 지침은 개발 계약이며 모든 항목이 현재 런타임에 구현됐다는 뜻은 아니다. 현재 연결과 남은 구현은 마지막 절에 구분한다.

## 1. 코딩 전에 결정할 실패 계약

기능 추가·수정 설명에는 다음 항목을 포함한다. 기존 공통 경로가 있으면 확장하고 별도 재시도 실행기를 만들지 않는다.

| 항목 | 반드시 답할 내용 |
|---|---|
| 입력과 소비자 | 어느 단계/API가 무엇을 받고, 누가 결과를 실행·표시·저장하는가? |
| 실패 분류 | 사용자 입력, 전송, JSON, 스키마, 필드 충돌, 근거, 상태 충돌 중 무엇인가? |
| 복구 담당 | 검출 함수와 복구 결정 함수는 어디인가? 같은 실패를 재시도하는 담당은 한 곳인가? |
| 보정 범위 | 바꿔도 되는 필드와 절대 바꾸면 안 되는 의미·근거·식별자는 무엇인가? |
| 예산 | 최대 물리 호출·수정·도구·복귀 횟수, deadline, 종료에 남길 예산은 얼마인가? |
| 상태 | 확정한 단계·원문·도구 receipt·미처리 대상·실패 출력·사용량을 어디에 보존하는가? |
| 종료 | 성공, 제한 답변, 사용자 사실 질문, 재개 대기, 최종 실패 중 어떤 결과를 내는가? |
| 검증 | 복구 전후 불변조건과 실제 소비자 연결을 어떤 실패 주입 검사로 확인하는가? |

“두 번 실패하면 예외”만 정하고 복구 가능한 오류와 중단해야 할 오류를 구별하지 않은 코드는 불완전하다. 같은 문자열의 오류라도 근거·상태·전송 결과가 다르면 복구 가능성이 다르다.

## 2. 검증 순서와 경계

1. 응답 수신 결과와 완료 상태를 확인한다. HTTP 200, JSON 파싱 성공, 모델 제안 채택, 최종 답변 발행은 각각 별개다.
2. JSON 구문과 기대하는 객체 타입을 검증한다. 불완전 출력·거절·필터·모델 바인딩 오류를 빈 객체로 바꾸지 않는다.
   2026-10-20 사용자 지시에 따라 GENOS 내부 응답의 `model` 문자열 차이·누락은 바인딩 실패로 분류하지 않는다.
   인증된 serving endpoint와 요청 모델 선택은 유지하고 요청/응답 모델 ID를 구분해 기록한다.
   일반 응답·스트리밍·재개·AD는 같은 `genos-serving-model-metadata-v1`을 사용하며 원문 응답을 보존한다.
   이 호환 정책은 본문·권한·endpoint/코드/데이터/상태 해시 검사나 외부 실험의 정확한 모델 고정을 완화하지 않는다.
3. 요청에 사용한 버전의 원래 스키마로 검증한다. 필수 필드, enum, 배열 개수, 타입, 허용 필드와 참조 목록을 검사한다.
4. **필드 간 계약**을 검사한다. `kind ↔ suggested_action`, `material ↔ coverage`, `disposition ↔ claims`, `source_ref ↔ evidence_refs`를 개별 필드 검증과 별도로 다룬다.
5. 원문·span·실제 사용자 사실·권한·문서 버전·코드/데이터 바인딩을 검증한다. 문법상 맞는 ID나 인용문이라는 이유로 허용하지 않는다.
6. 현재 request·state revision·presentation·checkpoint와 맞는지 확인한다. 검증 후에도 commit 직전에 revision/소유권을 다시 확인한다.
7. 허용된 보정을 했다면 변경한 객체에 3~6의 해당 검증을 다시 적용하고 소비자 스키마까지 확인한다. 검증된 결과만 단계 상태와 발행 경로에 연결한다.

프로바이더 호환을 위한 전송 스키마 투영은 원래 스키마를 완화하는 승인이 아니다. 예를 들어 전송에서 `uniqueItems`를 제거해도 서버의 원래 제약은 유지한다. enum/별칭 복원은 그 요청에서 제시한 목록에만 결속한다.

## 3. 오류별 처리 기준

| 실패 종류 | 허용되는 처리 | 반드시 지킬 경계 |
|---|---|---|
| JSON·타입·필수 필드 오류 | 같은 view·스키마와 검증 오류로 제한된 전체 객체 수정 요청 | 없는 필드를 의미 추정으로 채우거나 실패 출력을 실행하지 않음 |
| 알려진 필드 충돌 | 사전 허용된 결정적 보정 후 재검증, 불가하면 담당 단계가 수정 요청 | 보정 전후·규칙·근거를 기록하며 요구사항/실제 부족을 삭제하지 않음 |
| 근거 부족 | 허용 scope의 원문·저장 자료·연결·구조 탐색으로 복귀 | 조사 실패를 원문 부재로 단정하지 않으며 동일 실패 반복을 차단 |
| 실제 사용자 사실 부족 | 요청한 사건 적용에 꼭 필요한 사실을 특정해 질문 | 일반 규칙 질문에 개인 사실을 요구하거나 법령/서식 확보를 사용자에게 떠넘기지 않음 |
| 법률 주장·예외·버전의 의미 충돌 | 양쪽 근거와 적용 범위를 보존해 검토·추가 원문 조사 | 마지막 출력 우선, 임의 다수결, 충돌 주장 삭제로 정답을 만들지 않음 |
| 일시적 도구 실패 | 실패 receipt와 미완료 대상을 남기고 허용된 다른 경로로 조사 | 일부 읽은 원문은 보존하되 완료·채택과 구분 |
| 모델 전송 거절·429 | 어댑터가 재시도 가능·미수락을 확인한 경우에만 담당 gateway가 제한 재시도 | 실제 호출과 대기 시간도 같은 예산·deadline에 포함 |
| 타임아웃·연결 종료·실행 결과 불명 | 알려진 완료 receipt/checkpoint를 확인하고 중복 안전성이 보장될 때만 재개 | `unknown`을 미실행으로 간주해 상태 변경 도구를 다시 실행하지 않음 |
| 상태 revision·소유권·동시 실행 충돌 | 늦은 출력을 적용하지 않고 현재 상태를 다시 읽어 명시된 재개 절차 사용 | 같은 request ID의 다른 입력·principal·binding을 기존 요청으로 합치지 않음 |
| 권한·해시·변조·출처/모델 바인딩 실패 | 해당 결과를 차단하고 운영 원인과 바인딩 기록 | 모델 재호출·스키마 완화·무조건 해시 재작성으로 우회하지 않음 |
| 최종 저장·발행 충돌 | 기존 성공 결과와 저널을 보존하고 동일 결과의 멱등 발행만 복구 | 다른 답변 덮어쓰기, 저장 실패 후 성공 표시 금지 |
| 일부 답변 송신 후 실패 | 송신 기록을 보존하고 미완료 상태로 종료 | 새 생성 결과를 뒤에 이어 붙이거나 부분 답변을 성공 결과로 등록하지 않음 |

알 수 없는 예외는 분류가 확인될 때까지 일반 복구 대상으로 확대하지 않는다. 예상한 예외 클래스만 좁게 처리하고, 원래 예외 연결(`raise ... from exc`)과 내부 진단을 유지한다.

## 4. 자동 보정의 허용 범위

자동 보정 함수는 입력 객체를 변경하지 않는 순수 함수로 만든다. 결과와 변경 기록을 반환하고, 원래 모델 응답은 저널에 보존한다. 동일 입력에 여러 번 적용해도 추가 변화가 없어야 한다.

| 예 | 처리 |
|---|---|
| 원문 gap의 `suggested_action=REQUEST_FACT` | gap 종류·대상·사유·부족 상태를 보존하고 `RESEARCH`로 연결 가능. 실제 조사는 기존 scope·예산·도구 계약을 따름 |
| `COVERED`와 핵심 gap이 동시에 존재 | 근거 있는 주장 유무에 따라 `PARTIAL`/`INSUFFICIENT`로 낮춤. gap을 비핵심으로 바꾸어 통과시키지 않음 |
| 완전히 동일한 중복 행동 제안 | 동일성 확인과 기록 후 중복 제거 가능. 반대 판단·다른 근거/버전을 합치지 않음 |
| 알 수 없는 enum·근거 ID·잘못된 인용 | 가장 비슷한 값을 임의 선택하지 않음. 수정 요청 또는 중단 |
| `MISSING_FACT`가 저장 법령 자료를 가리킴 | 원문 부족인지 실제 사실 부족인지 자동 추정하지 않음. 오류를 명시해 재판단 |
| 허용을 의무로 바꾸는 주장, 예외 제거, 사실 창작 | 자동 보정 금지. 원문과 연결된 재판단이 필요 |

보정은 검증을 대체하지 않는다. 특히 이번 `REQUEST_FACT → RESEARCH` 변경은 답변을 완성했다는 표시가 아니다. `NEEDS_INVESTIGATION`으로 기존 조사에 돌아가거나, 예산이 없으면 검증된 주장과 남은 부족을 함께 제한 답변으로 처리한다. 검증된 주장이 없으면 답변을 꾸미지 않는다.

## 5. 재시도 담당과 총 예산

각 호출에서 전송, JSON 수정, 판단 수정, 추가 조사는 다른 사건으로 기록하되 **같은 실패에 대한 모델 수정 담당은 하나**로 정한다. 내부 gateway가 이미 수정한 오류를 상위 단계가 새 최초 오류로 취급해 반복하는 구조를 새로 만들지 않는다. 단계가 복구를 맡는 경로는 gateway의 동일 오류 수정이 꺼지는 실제 배선을 확인한다.

- JSON 수정: 원래 task/view, 요청 schema 버전, 문제 필드 경로, 검증 실패 원인, 이전 제안을 전달한다. 동일 참조 목록과 권한을 유지한다.
- 판단 수정: 독립적인 충돌들을 한 번에 설명한다. 첫 오류만 고치고 다음 오류로 계속 왕복하지 않도록 제한한다. 수정 프롬프트만 강화한 뒤 해결됐다고 보고하지 않는다.
- 동일 충돌 판정: 단계·규칙·문제 필드·대상·입력/상태 바인딩으로 식별한다. 문구 변경이나 새 임의 ID가 예산을 초기화해서는 안 된다.
- 추가 조사: 새 대상 또는 그 대상에 대한 새 근거가 있어야 한다. 무관한 자료 추가를 같은 부족의 무한 재개 이유로 쓰지 않는다.
- 재개: 물리 모델 시도·도구 사용량·최초 deadline·수정 횟수·처리된 target receipt를 복원한다. 프로세스 재시작·새 run ID를 새 예산으로 취급하지 않는다.
- 예산 소진: 원문에 연결된 확인 범위만 반환하거나, 필요한 실제 사실을 묻거나, 명시적으로 중단한다. 부족을 숨기고 `ANSWER`로 바꾸지 않는다.

횟수는 선택된 profile과 실제 effective policy에서 읽고 로그에 남긴다. 현재 작업 profile의 `max_schema_repairs=1`, `max_transport_retries=1`을 모든 단계/현장에 동일하게 적용한다고 가정하지 않는다. `bounded_source_session.structured()`는 completion의 ASSESS/COMPOSE와 법령 탐색에서 gateway의 `max_schema_repairs=0`을 적용한다. ASSESS의 최초 판단+수정 1회는 `completion_execution`이, 탐색 수정은 조사 단계가 담당한다. 전송 재시도는 gateway가 담당한다. **이 담당 분리를 유지하고 다른 호출 경로도 별도로 검사한다.**

## 6. 상태와 최종 응답

실패한 제안은 기록하되 채택된 head·claim·원문 receipt로 저장하지 않는다. `제안 수신 → 검증 → 허용 보정/수정 → 재검증 → 단계 commit → 최종 발행`의 경계를 유지한다. 도구 부작용 전에는 승인된 대상과 실행 의도를 기록하고, 실행 후에는 실제 결과 receipt를 기록한다.

| 종료 상태 | 저장·표시 기준 |
|---|---|
| 성공 | 단계·근거·소비자 검증과 최종 발행 완료 |
| 제한 답변 | 검증된 주장만 사용하고 미확인 요구와 이유를 함께 보존. 전체 해결로 표시하지 않음 |
| 사실 질문 | 특정 사건 판단에 필요한 미제공 사용자 사실만 질문 |
| 재개 대기 | 실제 checkpoint와 복구 조건이 있을 때만 `resume_available=true` |
| 실패 | root cause와 중단 단계·미완료 작업을 보존하고 일반 사용자에게는 이해 가능한 상태와 요청 식별자 제공 |

이 표는 개념적 종료 계약이다. 새 wire enum을 임의 추가하라는 지시가 아니다. 기존 `disposition`, `answer_status`, publication 상태와의 매핑을 확인한 뒤 소비자 계약과 함께 변경한다. 사용자가 보지 못하는 HTTP 상태만 성공으로 바꿔서는 안 된다.

실패 요청·불완전 출력·미발행 답변을 재사용 가능한 성공 숏컷·위키·정답으로 등록하지 않는다. 제한 답변도 해당 소비자의 성공·근거·권한 정책을 별도로 통과해야 한다. 과거 실패 원문과 저널은 삭제하지 않는다.

## 7. 진단 기록

복구를 추가할 때 다음 정보를 기존 저널·진단 구조에 연결한다. 새 필드 이름을 도입하면 그 필드를 읽는 로그/보고서/화면과 버전을 함께 다룬다.

- request/run/attempt, 업무 단계와 실제 호출 단계, 모델·프로필·스키마·코드/데이터 바인딩.
- 오류 종류·원래 예외·문제 필드와 충돌 규칙, 원래 제안 hash와 보정 후 hash.
- 복구 담당, 선택한 행동, 자동 보정 규칙과 변경 필드, 허용된 근거 목록의 바인딩.
- 사용한 재시도·도구·복귀 횟수, 남은 예산·deadline, 중단 또는 재개 조건.
- 검증/commit/발행 상태와 원본 저널 위치. 이미 송신한 답변이 있으면 송신 상태.

전체 요청·원문·오류 원문은 접근 통제된 기존 원장에 둔다. 화면에 traceback·인증 정보·다른 팀 자료를 보내지 않는다. 화면 오류를 간결하게 만들더라도 내부의 구체 원인을 generic 메시지로 덮어쓰지 않는다. 운영자가 최종 422만 보고 사진을 반복 수집해야 하는 진단은 개선 대상이다.

## 8. 필수 실패 주입 검사

변경과 관련된 행마다 실제 검사 이름과 결과를 남긴다. 해당되지 않는 항목은 이유를 적는다. “예외가 발생하지 않음”만 검사하지 말고 채택 상태·남은 gap·원문·예산·호출 수·발행과 재사용 상태까지 확인한다.

| 검사 | 확인할 결과 |
|---|---|
| 정상 입력 | 기존 답변·근거·호출 수 보존 |
| 구문/스키마 오류 후 수정 성공 | 같은 허용 범위로 고치고 한 번만 채택 |
| 두 번째 실패·같은 충돌 반복 | 추가 무한 호출 없이 정해진 종료, 최초 원인 보존 |
| 원문 gap과 사실 질문 충돌 | 원문 조사 또는 명시된 부족 상태. 사용자 사실로 변조하지 않음 |
| 실제 사실 부족 | 사실 질문 유지. 법령 읽기로 사실 충족을 가장하지 않음 |
| 수정과 독립적인 다른 오류 | 행동을 보정해도 잘못된 인용·근거·권한·사실은 거부 |
| 일부 성공 뒤 도구 실패 | 성공 receipt 보존, 실패 부분만 재개, 중복 부작용 없음 |
| 예산/시간 소진 | 추가 호출 차단, 검증된 부분만 반환, 주장이 없으면 실패 |
| 프로세스 중단과 재개 | 같은 요청 바인딩·카운터·deadline·checkpoint 유지 |
| 중복 요청과 동시 revision 변경 | 동일 결과 재사용 또는 명시된 충돌, 중복 호출/저장 방지 |
| 스트리밍 이후 실패 | 미완료 표시, 다른 답변 연결과 성공 등록 금지 |
| 실제 소비자 연결 | API/서비스 → 상태 저장 → 답변/로그 소비자의 최종 상태 일치 |
| 선택 코드와 해시 | 수정한 동일 파일·엔진 pin으로 검사. 다른 checkout의 통과 결과 전용 금지 |

공통 helper를 고치면 사용하는 현행 계약 버전을 모두 검사한다. 테스트를 통과시키기 위해 검증기를 무시하거나 모의 객체에서만 허용되는 반환형으로 바꾸지 않는다. 정상/복구/중단은 합성 응답으로 검사할 수 있다. 실제 모델의 정확도·검색 효과·프롬프트 비교는 [저장소 실험 절차](../../../AGENTS.md#실험--검증--main)를 따른다. 외부 합성 테스트 통과는 GENOS 내부 모델 성공 증거가 아니다.

위 파일은 `02_BACKEND/semantic_runtime/`와 그 아래 `legal_agent/`에 있다. 전체 실행 책임은 [ARCHITECTURE.md](../../../00_SYSTEM/ARCHITECTURE.md), 단계 선언은 [PIPELINE.json](../../../00_SYSTEM/PIPELINE.json)을 따른다.

이번 작업은 `source_gap_actions()`를 v5/v6의 스키마 검증 뒤에 연결했다. v7/v8은 기존 v6 준비 경로를 통해 같은 보정을 사용한다. 보정 감사는 `model_proposal.gap_action_corrections`로 남고 원래 모델 제안은 변경하지 않는다. 기존 구버전 `normalize_assessment()`와 엄격한 `assessment_errors()`는 유지한다.

다음 항목은 이 문서만으로 구현 완료가 아니다: 모든 실패에 대한 공통 오류 코드/필드 경로의 구조화, 단계별 재시도 담당의 전역 단일화, generic 422의 사용자 안내 개선, 모든 도구와 저장 소비자의 실패 행렬 자동화. 현재 담당/예산이 여러 계층에 있는 경로는 위 기준에 따라 별도 확인해야 한다. 기존 실패 기록을 보존하고 필요한 구현은 별도 작업으로 추적한다.

이번 확인에서 신규 원문 gap 계약/API 검사 63개가 통과했다. 확대 검사에서는 276개 통과, `test_unified_memory_recovery.py`의 4개 실패가 남았고, 이번 수정 3파일을 이전 바이트로 되돌린 격리 코드에서도 같은 4개가 실패했다. 구 `cases-v3.sqlite`의 `request`/`goal` 테이블 기대, unified 응답과 shortcut 응답 기대 불일치, 현재 선택 가능한 경험 ID와 재사용 제안 사이의 충돌이다. 이를 이번 수정의 해결 항목이나 전역 복구 성공으로 계산하지 않는다.
