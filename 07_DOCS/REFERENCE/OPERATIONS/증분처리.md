# 증분처리 — 법제처 규정 문서 증분 처리

갱신 2026-11-06 · 상태: **로컬 작업 코드 구현·검증 완료. 개발·운영 Oracle DDL, Dataiku 현장 실행, GENOS 반영은 아직 안 함.**

**원칙: 입구가 달라도 같은 조문 비교·승인·활성화 엔진을 타고, 바뀐 조문만 새 판본으로 올린다.**
옛 판본은 지우지 않고 시행 구간만 닫는다. 그래서 과거 시점 질의에도 답할 수 있다.

## 2. 전체 흐름

`수집 → 입력 검증 → 구조화 → 기존 현행본 조회 → 조문 비교 → 게이트 → 승인 → 색인 준비(숨김) → 활성화 → 영향 전파`

처리 상태:

`DETECTED → PARSED → DIFFED → PREVIEW → APPROVED → INDEXING → ACTIVATED`

| 예외 상태 | 뜻 |
|---|---|
| `NO_CHANGE` | 원문 파일은 바뀌었지만 조문은 모두 같다. 여기서 끝난다 |
| `REJECTED` | 승인자가 거절 |
| `BLOCKED` | 이전 시행일, 같은 시행일 재업로드 등 자동 반영 금지 |
| `BLOCKED_PENDING` | 아직 시행 전인 조문을 다시 개정 |
| `FAILED` | 색인 준비·활성화 실패. 같은 명령으로 재시도 |

같은 문서에 같은 원문(sha256)이 들어오면 같은 작업으로 본다. 다시 넣어도 새로 만드는 것이 없다.

## 3. 입구: 법제처 법령·행정규칙

**문서 식별.** 이름이 아니라 법령ID·행정규칙ID로 관리한다. 문서코드는 `LAW:012338`, `ADMRUL:21828` 형태다.
행정규칙ID는 발령이 바뀌어도 그대로다. 전자금융감독규정은 2026-7호와 2026-29호 모두 21828이고, 외부감사 및 회계 등에 관한 규정도 21840으로 같았다. 반면 행정규칙일련번호는 발령마다 바뀐다.

**변경 감지.**
1. 같은 문서·같은 원문 sha면 이미 처리한 것이므로 끝낸다.
2. sha가 다르면 그 문서만 직전 현행본과 조문 단위로 비교한다.
3. XML만 바뀌고 조문이 같으면 `NO_CHANGE`로 끝낸다. 보유 판본 중 이런 묶음이 21개 있었다.

**별표·서식.** 법령 XML의 별표내용은 머리 한 줄뿐이다. 예를 들어 지배구조법은 `■ 금융회사의 지배구조에 관한 법률 [별표]`만 들어 있다.
그래서 별표 변경은 수집기가 받은 HWP 첨부의 sha로 판정한다. 본문 XML의 링크 번호(`flSeq`)로 첨부와 별표를 맞춘다. 첨부 sha 없이 머리 줄만 비교한 별표는 경고로 표시한다.

**수집 방식은 문서마다 하나로 고정해야 한다.** 같은 공포번호라도 '공포 전문'과 '시행일 기준 조회본'은 내용이 다르다.
- 상법 제20991호의 2026-07-23 기준본은, 공포가 더 늦은 제21448호(2026-03-06 시행) 개정을 이미 담고 있다.
- 자본시장법 제21324호의 2026-02-03본은 제166조 개정 문안이 이미 들어 있다. 반면 2026-08-04 기준본은 개정 전 문안이다(제166조는 2027-02-04 시행).

두 방식을 섞어 받으면 판정이 뒤집힌다. 시행 예정 조문을 미리 넣으려면 '공포 전문 + 부칙 판독'으로 고정한다. 현재 수집기는 시행일 기준 현행본(eflaw)으로 받는다.

## 4. 공통 구조화

모든 입력을 같은 형태로 맞추면 뒤 단계(비교·승인·활성화)는 공용이다.

| 필드 | 설명 | 예 |
|---|---|---|
| 문서코드 | 불변 ID | `LAW:012338` |
| 조문키 | 문서 안에서 유일 | `165의3`, `1-1`, `별표1`, `별표1의2`, `별표`(번호 없는 별표), `서식3`, `전문`, `부칙:21065` |
| 제목 | 조문 제목 | `임원의 자격요건` |
| 내용 | 조문 원문(항·호·목 포함) | |
| 내용해시 | 공백을 모두 빼고 NFKC 정규화한 sha256 | |
| 비교해시 | 자기 번호를 떼고 인용 번호를 가린 값의 해시 | |
| 계보ID | 번호가 바뀌어도 유지 | |
| 시행시작·종료일자 | KST `YYYYMMDD` | |

**처음 설계에서 바꾼 점**
- **가지번호:** `165-3`이 아니라 `165의3`으로 쓴다. 행정규칙에는 `제1-1조` 같은 하이픈 번호 체계가 따로 있어서 겹치기 때문이다.
- **부칙:** 하나로 묶지 않고 공포번호별로 따로 둔다(`부칙:19700`, `부칙:19913`, `부칙:21065`). 옛 부칙은 그대로 남고, 새 부칙은 신설로 나온다. 마지막 부칙이 이번 개정분이다. 실제 XML도 부칙이 날짜 오름차순으로 온다.
- **공백 처리:** 해시는 공백을 모두 뺀 값으로 만든다. 지배구조법 옛 부칙의 `제2조 부터`→`제2조부터`처럼 띄어쓰기만 다른 것은 같은 내용으로 본다.

**파싱 규칙**
- **조문 시작으로 인정하는 줄:** `제N조(제목)`, `제N조 삭제`, `제N조 <삭제…>`, 제목 없는 `제N조` 단독 행만 조문 시작이다. 실제로 `제26조 삭제<2025. 2. 5.>`처럼 제목 없이 삭제 표시가 붙은 행이 있다. 기존 구조화 파서는 이 행을 조문 시작으로 잡지 못한다.
- **본문 계속행:** `제1조에 따른…`, `제2조제1항에 따라…`로 시작하는 줄은 조문 시작이 아니라 본문이다.
- **장·절 제목:** 조문 본문에 넣지 않는다.
- **전문:** 첫 조문 앞의 문장은 `전문`으로 보존한다.
- **법령 XML의 항·호·목:** 문서 순서대로 모은다. 목이 호의 자식이 아니라 항 아래 호의 형제로 오는 판본이 있다(지배구조법 제21065호 제5조제1항제6호 가~다목).
- **거절:** 조문이 0건이거나 조문키가 겹치면 그 파일은 받지 않는다.

## 5. 변경 판정

번호보다 계보가 중요하다. 번호가 밀려도 같은 조문이면 계보를 유지해야 룰·참조 연결이 끊기지 않는다.

**판정 순서**
1. 자기 조문 번호를 떼고, 인용 번호(제N조·제N항·제N호)를 가린 비교값을 만든다.
2. 같은 키·같은 내용인 쌍은 먼저 확정한다. 대부분의 조문은 그대로이므로 600조 규모 법령도 수 초 안에 끝난다.
3. 나머지끼리 2글자 조각(bigram) 겹침으로 후보를 거른다. 조문마다 상위 8개, 겹침 0.30 이상만 남긴다.
4. 조문 순서를 유지하는 전역 정렬로 대응 쌍을 찾는다. 같은 키에는 +0.05 가산점을 준다. 다른 키끼리는 유사도 0.60 이상만 대응으로 인정한다.
5. 정렬에서 빠진 쌍 중 유사도 0.90 이상은 순서를 벗어난 실제 이동으로 회수한다.
6. 같은 키인데 유사도가 0.50 미만이면 전면 개정으로 표시한다. 번호 재사용인지 승인 때 확인한다.
7. 남은 것은 삭제 또는 신설이다. `제N조 삭제` 표시는 내용이 없는 자리로 보고, 그 번호의 옛 조문은 삭제로 판정한다.

| 판정 | 의미 | 새 행 | 룰 재검토 |
|---|---|---|---|
| `SAME` | 내용 동일 | 아니오 | 아니오 |
| `AMEND` | 같은 번호, 내용 개정 | 예 | 예 |
| `MOVE` | 번호만 이동 | 예 | 아니오 |
| `MOVE_AMEND` | 번호와 내용 변경 | 예 | 예 |
| `REF_ONLY` | 번호 밀림에 따른 인용 번호만 변경 | 예 | 아니오 |
| `ADD` | 신설 | 예 | 해당 없음 |
| `DELETE` | 삭제 | 아니오(구간만 닫음) | 예 |

**`REF_ONLY`는 엄격하게 쓴다.** 바뀐 인용 번호가 이번 비교의 조문 이동으로 모두 설명될 때만 쓴다. 다음은 `AMEND`로 처리한다.
- 「상법」 제5조 → 제6조처럼 다른 법령을 가리키는 인용이 바뀐 경우
- `법 제9조`, `시행령 제7조`, `같은 법 제3조`, `부칙 제7조`처럼 다른 문서를 가리키는 인용이 바뀐 경우
- `제2조제1항` → `제2조제2항`처럼 항·호 번호가 바뀐 경우

반면 `이 법 제7조`는 같은 문서 안의 인용으로 본다.

**실제 판정 예**
- **지배구조법 제19913호 → 제21065호:** 제26조 하나만 `AMEND`이고 나머지는 부칙 신설이다. 실제 개정은 다른 법(정부조직법)의 부칙 제7조 <602> "제26조제1항제2호라목 전단 중 '기획재정부'를 '재정경제부'로 한다"이다. 법제처의 변경 표시(Y)도 제26조 하나였다.
- **전자금융감독규정 2026-7호 → 2026-29호:**
  - 제56조의8·제56조의9 신설
  - 제57조는 191자 → 585자 확장 개정이라 유사도 0.48로 전면 개정 경고가 붙음
  - 제60조·제72조의2 개정
- **신설로 번호가 밀린 합성 예:** 제3조 신설로 옛 3·4·5조가 4·5·6조가 된 경우다. 옛 3·4조는 `MOVE`, 벌칙 금액이 바뀐 옛 5조는 `MOVE_AMEND`로 판정되고, 세 조문 모두 계보가 유지된다. 옛 4조 안의 "제3조에 따라"→"제4조에 따라"는 이동으로 설명되므로 개정으로 세지 않는다.

**법제처 `조문변경여부` 표시는 대조용이다.** 직전 공포 대비로 일부만 표시한다.
지배구조법 시행령 제34584호에서 제19조 제2항 삭제(`<2024.6.18>`)와 제26조 "별표 1"→"별표 1의2"는 실제 변경인데 N으로 표시돼 있었다. 그래서 Y로 표시된 조문을 놓치지 않는지(재현율 하한)만 검사하고, 표시 밖의 추가 변경은 오탐으로 세지 않는다.

**기준값.** 0.60, 0.90, 0.50은 합성 데이터 기준이다. 실제 판본 28쌍에서 번호 이동(MOVE)은 1건뿐이라 이동 기준을 다시 맞출 근거가 아직 적다.

## 6. 시행일

**조문별 시행일은 부칙이 정본이다.**
법령 XML의 `조문시행일자` 태그는 보유 94개 판본 전부에서 문서 시행일자를 그대로 복사한 값이었다. 예를 들어 자본시장법 제21324호는 다음 두 조문이 늦게 시행되는데, `조문시행일자`는 596개 조문 모두 20260203이다.
- 제50조제1항 단서: 공포 후 6개월 → 20260804
- 제166조: 공포 후 1년 → 20270204

**배정 순서**
1. 문서 시행일: 공식 메타데이터(시행일자) → 없으면 마지막 부칙
2. 조문별 시행일: 마지막 부칙의 예외 → 문서 시행일

**읽는 부칙 문형**
- `이 법(영·규칙·고시·규정…)은 공포한 날부터 시행한다`
- `…은 2026년 10월 1일부터 시행한다`
- `공포 후 N개월(년·일)이 경과한 날부터`: 초일은 넣지 않으므로 공포일 + 기간 + 1일이다. 자본시장법 실측과 일치한다(20260203 + 6개월 + 1일 = 20260804).
- `다만, 제56조의8 및 제56조의9의 개정규정은 …부터 시행한다`
- `제10조부터 제12조까지의 개정규정`: 범위로 편다
- `다음 각 호(목)의 개정규정은 …`: 뒤의 번호 항목이 앞 날짜를 잇거나 자기 날짜(`2. 제30조의 개정규정: 2027년 1월 1일`)를 쓴다

못 읽은 예외 문장이 있으면 '시행일 판독 불가' 강한 경고를 붙인다.

**타법개정 부칙.** `부칙(정부조직법) <제21065호>`처럼 다른 법의 부칙이면, 그 안의 제19조·제23조는 그 법의 조문이다. 그래서 이 문서의 조문 예외로 쓰지 않고, 문서 시행일자를 적용하고 알림 경고만 붙인다.

**구간 닫기.** 옛 조문의 종료일은 새 시행일 - 1일이다. 시행 예정 조문은 미리 넣어 두고 조회 시점으로 거른다. 그래서 시행일 전환 배치가 필요 없다.

```text
OPEN_YN = 'Y'
AND ENFC_STRT_DT <= :기준일
AND (ENFC_END_DT IS NULL OR ENFC_END_DT >= :기준일)
```

날짜는 KST `YYYYMMDD` 문자열이다. 문자열 비교가 곧 날짜 비교라서 시간대 변환이 끼지 않는다.

**멈춤 조건**

| 상황 | 처리 |
|---|---|
| 기존 최신 판본보다 이른 시행일 | `BLOCKED`, 자동 반영 금지 |
| 같은 시행일로 내용이 다른 재업로드 | `BLOCKED`, 정정 절차 대상 |
| 아직 시행 전인 조문을 다시 개정 | `BLOCKED_PENDING`, 사람 판단 |
| 옛 조문 종료일이 시작일보다 앞서게 되는 경우 | `BLOCKED` |

사람이 판단하면 멈춤을 풀고 대비표 검토(PREVIEW)로 넘긴다. 승인은 별도로 한다.

정정·소급 처리에 필요한 기록 시점은 컬럼(등록일시·대체일시)만 만들어 두었다. 절차는 아직 없다.

## 7. 게이트와 승인

자동으로 끝나는 것은 전부 `SAME`인 경우(`NO_CHANGE`)뿐이다. 실제 변경은 신구조문 대비표를 보여 주고 승인을 받는다.

**강한 경고** — 승인할 때 '확인함'을 따로 표시해야 통과한다.

| 경고 | 기준 |
|---|---|
| 변경률 과다 | 50% 초과. 이동·인용 번호만 변경·부칙은 빼고 센다 |
| 조문 수 급감 | 새 조문 수가 옛 조문 수의 80% 미만 |
| 삭제 과다 | max(5건, 옛 조문의 20%) 초과 |
| 별표 사라짐 | 별표·서식 삭제 |
| 시행일 판독 불가 | 문서 시행일 없음, 또는 부칙 예외를 못 읽음 |

**알림 경고:** 같은 번호 유사도 0.5 미만, 첨부 sha 없는 별표, 법제처 변경 표시와 다른 판정, 행정규칙 메타 시행일과 부칙 시행일 불일치, 타법개정 부칙.

**실측 사례.** 7개 조문만 든 잘린 자본시장법 업로드본은 조문 수 급감, 삭제 627건, 별표 소실 경고가 함께 걸려 자동 반영이 막혔다.

**대비표에 나오는 것**
- 문서명, 문서코드, 공포번호, 시행일, 원문 sha
- 판정별 건수, 변경률, 경고, 멈춤 사유
- 부칙에서 읽은 조문별 시행일
- 조문별 구조문·신조문(바뀐 줄 강조), 유사도, 판정 이유, 시행일, 룰 재검토 여부

**승인 규칙**
- **해시 일치:** 승인할 때 대비표 해시를 함께 낸다. 그 사이 비교 결과가 바뀌었으면 해시가 달라져 거절된다.
- **기준 판본 변경:** 비교 기준이었던 판본이 그 사이 다른 작업으로 바뀌었으면 거절한다. 같은 파일을 다시 적재해야 한다.
- **수동 계보 연결:** 짧은 조문의 번호와 내용이 함께 바뀌면 계보가 끊겨 삭제+신설로 나온다. 이때 승인 전에 '옛 키=새 키'로 직접 이어 줄 수 있다. 이으면 이동·개정(`MOVE_AMEND`)으로 바뀌고 계보가 유지되며, 대비표와 해시는 새로 만들어진다.

## 8. 반영 순서

옛 판본을 먼저 닫고 색인을 나중에 만들면 그 사이에 공백이 생긴다. 그래서 **색인을 먼저 숨김으로 준비하고, 활성화를 한 번에** 한다.

1. 승인된 변경으로 새 조문 행을 숨김(공개여부 N)으로 만든다. 참조 관계 행도 함께 만든다.
2. 외부 색인(Gold 새 세대 게시·벡터)은 '대기'로 두고, 확인되면 '준비 완료'로 표시한다.
3. 전부 준비되면 하나의 트랜잭션에서 아래를 처리한다.
   - 작업 상태를 바꾼다(상태변경번호가 그대로일 때만).
   - 문서의 활성 판본을 새 판본으로 바꾼다(기준 판본이 그대로일 때만).
   - 옛 판본과 옛 조문의 시행 구간을 닫는다.
   - 새 조문을 공개한다.
   - 재검토 대상을 등록한다.
   - (선택) Gold 조회 채널 포인터를 바꾼다(예상 값과 같을 때만).
4. 하나라도 어긋나면 전부 롤백한다. 기존 현행본은 그대로이고, 같은 명령을 다시 실행하면 된다.

**실패 처리**
- 색인 준비 중 실패: 기존 현행본을 유지하고 재시도한다. 숨김 행은 재시도 때 지우고 다시 만든다.
- 활성화 실패: 전체 롤백. 작업은 색인 준비 상태로 남고 오류 내용만 기록한다.
- 멱등성: 적재작업ID = 문서코드+원문 sha, 조문판본ID = 판본ID+조문키라서 다시 실행해도 같은 행이 된다.

**캐시 무효화.** 활성화 결과로 해당 문서코드와 새·옛 Gold 문서ID를 돌려준다. 이것을 받아 서빙 쪽 캐시를 지우는 연결은 아직 없다.

**물리명 규약.** 운영 Gold 규약(`IDD_B003_LGL_` + 약어, 30바이트 이내)을 따른다.

- **고칠 때:** 표준 사전과 다르면 테이블 정의 한 곳만 고친다. DDL·정의서·코드가 함께 바뀐다.

**어느 스키마에 두나.** 각 환경에서 Gold 조회 채널 표(SRCH_CHNL)가 있는 스키마와 같은 곳을 권장한다.
- 개발계: `SIDDS`(현재 개발 Gold 대응 13표가 있는 곳)
- 운영계: 운영 Gold 소유자(실제 이름은 아직 기록 없음)
- 같은 스키마여야 활성화 한 트랜잭션에서 채널 포인터까지 바꿀 수 있다. 다른 스키마면 그 표에 UPDATE 권한이 필요하다.
- `SIDDA`(Agent 레이어)는 대화 부산물 전용이라 두지 않는다.

**운영계 생성 절차.** 메타 등록과 DBA 생성 신청을 거친다. 개발계는 DDL을 대상 스키마 계정으로 실행하면 된다.

## 10. 기존 테이블과의 관계(조인)

**서빙(GENOS 답변)에는 조인이 필요 없다.** GENOS는 지금처럼 조회 채널이 가리키는 Gold 세대 13표를 읽는다. 증분 테이블은 변경 관리·이력·승인·영향 전파용이다.

**다만 키 대응은 반드시 필요하다.** 현재 Gold의 법령 `RGLT_DOC_ID`는 본문 XML sha256의 앞 16자리라서 개정할 때마다 문서ID가 바뀐다.
예) 금융회사의 지배구조에 관한 법률
- 제19700호 판본: `240dac7491eec3f8`
- 제19913호 판본: `1ab2b728e6280db5`
- 제21065호 판본: `c4b33879c7dc5554`

그래서 "같은 법"을 잇는 불변 코드(`LAW:012338`)와 판본별 Gold 문서ID를 대응시키는 표가 따로 있어야 한다. 그 역할을 규정판본내역이 한다.

| 증분 테이블 | 기존 Gold | 채우는 시점 |
|---|---|---|
| 규정판본내역.규정문서ID | `DOC_VER.RGLT_DOC_ID` | 적재 때 원문 sha 앞 16자리로 미리 채움 |
| 규정판본내역.명세해시값 | `DOC_VER`·`DOC_UNIT`·`DOC_BLK`·`SRC_POST`의 `DTLS_HASH_VALU` | Gold 새 세대 게시 후 연결 |
| 조문판본내역.구조단위ID | `DOC_UNIT.STRC_UNIT_ID` | 컬럼만 있음, 채우는 연결 미구현 |

외래키 제약은 걸지 않고 값으로만 잇는다.

**기존 표를 실제로 읽거나 쓰는 곳은 두 곳뿐이다.**
1. **Gold 게시 확인:** 새 세대에 그 판본 문서가 들어갔는지 `DOC_VER` 1건과 `DOC_UNIT` 건수로 확인한다.
2. **활성화 때 조회 채널 교체:** 같은 트랜잭션에서 `SRCH_CHNL`의 게시해시를 바꾼다. 채널명·옛 게시해시·변경번호가 예상과 같을 때만 바꾸고, 1행이 아니면 활성화 전체를 롤백한다.

**이름 차이 문제.** 증분 10표는 이름이 같으니 문제가 생기지 않는다. 기존 13표는 여전히 개발 `SIDDS.LGL_G19_*_S_1`, 운영 `IDD_B003_LGL_*`로 다르다. 위 두 곳에서 기존 표를 부를 때만 기존 매핑 파일로 이름을 바꾼다. 개발계에도 `IDD_B003_LGL_*` 13표를 만들면(2026-11-02 정정 방향) 매핑 하나로 끝난다.

## 11. 파생 데이터와 영향 전파

| 대상 | 처리 |
|---|---|
| 조문 판본 | 바뀐 조문만 새 행. 옛 행은 구간만 닫고 지우지 않음 |
| 참조 관계 | 새 조문 행의 인용을 다시 추출. 같은 문서 인용은 계보ID로 잇고, 「법령명」 인용은 등록된 문서명으로 대상 문서를 찾음 |
| 번호 이동 | 참조가 계보ID로 이어져 있어 끊기지 않음 |
| 청크·임베딩·검색 행 | Gold 새 세대 게시로 처리(기존 적재기). 조문 단위 Gold 반영은 미구현 |
| 조건·판단·실행 룰 | 자동 수정 없이 재검토 표시 |

**영향 전파(1단계만, 내용은 자동으로 바꾸지 않음)**
- **룰:** 개정·이동개정·삭제된 조문의 계보마다 재검토 대상을 올린다.
- **인용 조문:** 바뀐 계보를 인용하는 현행 조문을 올린다. 다른 문서가 번호만 이동한 조문을 인용하는 경우도 올린다. 같은 문서 안의 번호 이동은 그 비교에서 `REF_ONLY`로 처리되므로 빼고 센다.
- **연결 문서:** 문서연결관계에 등록된 위임 하위 규정·내규를 상충·위임 점검 대상으로 올린다.

**실측.** 지배구조법 제19913호 반영 때 룰 12건, 인용 조문 33건이 재검토 대상으로 등록됐다. 제21065호 반영 때는 룰 1건(제26조), 인용 조문 5건이었다.

**위임 연결망.** 법제처 lsDelegated·lsStmd도 sha가 바뀐 경우만 다시 전사하는 것이 원칙이다. 테이블과 전파 로직은 있고 적재기는 아직 없다.

## 12. 운영 주기

- **법제처:** 하루 1회 배치로 시작한다. 방화벽·API 승인이 풀린 뒤 Dataiku→중계서버→법제처로 연결한다.
- **내규:** 담당자가 업로드할 때 처리한다(입구 미구현).
- **시행 예정 건:** 시행 예정 조문이 미리 들어가 있으므로, 시행일이 가까운 문서를 대시보드에 표시하면 된다.
- **Dataiku 실행:** 쓰기는 PL/SQL 블록 하나를 보내고 COMMIT한다. 기존 운영 Gold 적재기와 같은 방식이다. 값은 UTF-8 16진수로 넣어 원문의 따옴표·백슬래시가 SQL 해석에 끼지 않게 했다.

**모니터링 지표:** 적재 성공률, 색인 반영 시간, 판본 오류 수, 파서 실패율, 게이트 차단 건수, 승인 대기 시간, 재검토 대기 수.

## 14. 남은 일 (우선순위 순)

1. **운영 Gold 반영 방식 결정.** 지금 Gold는 세대 전체 스냅샷이다. 바뀐 문서도 기존 적재기로 세대 전체를 다시 게시해야 하고(채널 교체 없이 게시 → 연결 확인 → 활성화에서 채널 교체), 검색 행 규모(로컬 Gold 기준 약 439만 행)의 복사 부담이 남는다. 문서 단위 세대 분리나 Gold 행에 판본 구간을 넣는 방식은 13표 등록 변경이라 별도 설계·신청이 필요하다.
2. **수집 방식 고정과 중계서버 경유 수집 연결.** 문서마다 공포 전문 또는 시행일 기준본 중 하나로 정한다.
3. **표준단어 확인·신청 → 개발계 생성 → 운영계 메타 등록·DBA 생성 신청.**
4. **승인 화면.** 지금은 HTML 대비표 + 해시 승인으로 대신한다.
5. **GENOS 과거 시점 질의 연결.**
6. **위임 연결망(lsDelegated·lsStmd) 적재기**와 외규↔내규 대응 입력.
7. **내규 docx 입구와 내규 두 판본 검증.** 파일명 규칙 `<문서명>_<시행일YYYYMMDD>.docx`, 등록된 정식 명칭과 일치 확인, 추적변경 거절.
8. **정정·소급 절차.** 기록 시점 컬럼은 이미 있다.
9. **HWP·PDF 입구.** OCR 문서는 자동 반영 금지.
10. **유사도 기준(0.60/0.90/0.50) 재조정.** 실문서 이동 사례를 더 모아서 한다.
11. **조문 구조단위ID 채우기, 서빙 캐시 무효화 연결, 파이프라인 명세 등록.**
