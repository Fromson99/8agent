위험관리기준시행세칙 고정 연결 4건의 증분 추가 — 2026-10-20

사용 중단: 이 문서는 잘못 지정했던 Oracle R1의 과거 기록이다.
사용자가 SQLite로 정정했으므로 RISK_BASIS_SQLITE_20261020.txt와
GENOS_RISK_BASIS_SQLITE_20261020_R2.zip을 사용한다. 아래 R1 절차는 실행하지 않는다.

범위
사용자가 지정한 내규 한 문서에 로컬 ADR0954에서 회수 경로를 확인한 관계만
추가한다. 일반 문서 탐색·의미 관계 추론·전체 재색인·전체 문서 대사는 포함하지 않는다.
관계 APPROVED는 사용자가 지정한 연결의 승인이다. 법률상 일치/충돌의 정답 인증은 아니다.

기존 RAG와 동일한 판본 선택
DP_QUERY_RELEASE_ID 또는 DP_QUERY_CHANNEL을 기존 서빙과 동일하게 사용한다.
기존 Oracle select_release → Snapshot → request → Store의 제외/최종 판본 필터를
적용하고 require_latest 및 risk_team 범위를 확인한다. 파일 날짜나 가장 큰 ID로
최신 문서를 다시 고르지 않는다. 위험관리기준시행세칙이 0개 또는 2개 이상이면
documents.json을 남기고 쓰기 없이 종료한다. 필터를 우회하여 과거 판본을 고르지 않는다.
명시적인 principal.document_ids 범위가 있으면 그 안으로 추가 제한한다.
빈 목록은 인증된 배치 실행자의 기존 risk_team 범위를 사용한다는 뜻이다.

내규 위치 → 외규 위치 (코드의 고정 목록)
1. 제6-4조제1항 → 금융투자업규정 제3-24조의4제2항
2. 제6-4조제2항 → 금융투자업규정시행세칙 별표10의
   유동성비율(3개월), 조정유동성비율(3개월), 유동성비율 산정 원칙
3. 제1-4조제1항제3호 → 금융투자업규정 제3-6조제4호
4. 제2-1조제1항제3호 → 금융투자업규정 제3-6조제4호,
   제3-24조의4제1항, 제3-26조제7항
4개 관계, 8개 연결선, 중복 제거한 외규 범위 7개다.
내규/외규 문서 ID·조항 ID·인용 span·해시는 현장 원문에서 결정한다.
사진 목업의 ID를 현장에 주입하지 않는다. 필수 내용 단서가 달라지면 자동 승인하지 않는다.
이 범위가 법률상 적용 가능한 모든 외규라는 주장은 하지 않는다.

실행 진입점/계약/소비자
저장소: python3 06_TOOLS/pipeline.py basis-links seed-risk ACTION --config CONFIG --output OUTPUT
현장 TXT: 같은 lawrag.pipeline.risk_basis_seed_cli.main을 ~/DEV 코드에서 호출한다.
계약은 risk-basis-append-v1이고 기존 basis_links Service의 propose/review를 이용하여
PROPOSED→APPROVED revision, 원문 binding, event, receipt 행을 조립한다.
임시 메모리 SQLite에는 이 4건의 관계 이력만 들어간다. 원문/색인 전체를 내려받거나
GENOS 서빙의 영속 로컬 원문 DB를 만들지 않는다. 필요한 문서·조항만 Oracle에서 읽는다.
결과 소비자는 기존 basis_links Service와 resolver.snapshot/targets이다.
OracleReader는 같은 원장 행을 읽어 이 소비자 계약으로 7개 외규 범위를 검증한다.
GENOS 채팅 런타임의 basis_factory/동일 table_map 연결은 별도 배선이다.
이 배치 코드 적용만으로 기존 서빙 팩토리 배포가 완료되거나 다음 채팅이 사용한다고
보고하지 않는다. 실제 워크플로우 테스트 화면의 회수 기록으로 현장 사용을 확인한다.

데이터 변경 경계
기존 원문 LEGAL_SRC_* / 조회 LEGAL_QUERY_* / 색인 / ACTIVE는 변경하지 않는다.
DB의 8개 basis 원장 테이블에 신규 행만 추가한다. 같은 연결이 APPROVED로 있으면
재사용하며 반려/취소/후보 관계를 되살리지 않는다. 동일 팀·선택 판본의 고정 연결 묶음은
동일 operation ID로 결속한다. 동일 계획 재실행은 receipt를 먼저 확인하여 중복을 막는다.
원장이 없으면 plan/apply는 실패한다. schema 명령은 검토용 DDL 파일만 생성한다.
이미 있는 다른 스키마를 덮어쓰거나 기존 테이블을 자동 생성/변경하지 않는다.
운영 DB가 같은 데이터/릴리스/필터/테이블 구조일 때 추출 SQL을 별도 실행할 수 있다.
다른 ID나 판본인 운영계에는 이 도구의 inspect/plan을 운영계에서 다시 실행해야 한다.

단계별 산출물
inspect: documents.json(필터 후 문서·버전·원문 hash), resolved.json(조항·인용·연결)
plan: DB 쓰기 0건. plan.json, append.statement.sql, append.binds.json,
      APPEND_ONLY.sql, REVOKE_THIS_BATCH.sql, schema-check.json 생성
apply: 원문 행·조회 manifest·선택 포인터·기존 관계 충돌을 확인한 단일 Oracle 트랜잭션
verify: commit receipt, 원장 행/해시, 승인 revision, 원문 위치, resolver 7범위 확인
revoke: 이 배치가 새로 만든 관계만 REVOKED revision으로 전이. 기존 이력·재사용 관계 보존
verify-revoked: 취소 receipt 및 신규 revision 확인
rollback-code: 코드 백업 복원만 한다. DB 연결 취소는 revoke와 별개다.
APPEND_ONLY.sql은 실제 Oracle에서 plan을 통과한 뒤 생성되므로 ZIP에 가짜 현장 ID를
넣은 실행 SQL을 포함하지 않는다. DDL은 OPTIONAL_BASIS_SCHEMA.sql로 분리한다.

실패/복구
대상 부재·다중 대상·다른 원문/필터·권한·해시·PK/UNIQUE 불일치: 쓰기 없이 실패,
documents/resolved/실패 파일을 보존한다. 수동으로 필터/원문/스키마를 확인한다.
쓰기 요청: 물리 호출 1회, 자동 재시도 없음. SQL 내부 오류는 전체 ROLLBACK.
전송 단절로 결과가 불명확하면 같은 plan.json으로 verify를 먼저 실행한다.
apply 재호출도 동일 receipt가 있으면 재쓰기 없이 확인한다.
동시 계획의 다른 무작위 link ID는 동일 operation receipt 충돌로 전체 rollback된다.
선택 채널 포인터는 트랜잭션 동안 최대 5초 대기로 잠그고 판본 변경을 막는다.
같은 출력 폴더 동시 실행은 flock으로 거부한다.
SQL 호출 수/첫 deadline은 budget.json 및 sql-events.jsonl에 보존하며 재개로 초기화하지 않는다.
예산 소진 시 기록 보존 후 중단한다. 계획/예산을 삭제하여 재실행하지 않는다.
기본 현장 설정은 총 10,000 SQL 호출, 첫 실행부터 86,400초다. 승인된 운영 창에 맞춰
첫 실행 전에 설정한다. 별도 운영 창에서는 이전 기록을 보존하고 원래 plan을 참조해
새 OUTPUT으로 verify부터 시작한다. 예산 변경은 명시적인 운영 행위로 기록해야 한다.
실패 파일은 error_type/code와 코드 위치를 남긴다. 접속 키·드라이버 SQL 본문은 출력하지 않는다.
진짜 source 조회 실패를 원문 부재로 처리하거나 관계 성공으로 보고하지 않는다.

로컬 확인과 현장 확인의 구분
로컬 사진 시험 세대의 단일 문서에서 관계/원문/소비자 계약을 검사했다.
현재 선택된 로컬 MAIN92 데이터에는 위험관리기준시행세칙이 없다. 따라서 MAIN DB를
수정하지 않았고 선택 릴리스/포인터도 바꾸지 않았다.
PL/SQL 생성·escaping·행 계약 검사와 실제 Oracle 엔진 실행은 구분한다.
현재 Codex 세션은 망분리 GENOS/Oracle에 접근할 수 없으므로 현장 SQL 실행 및
실제 채팅 응답 사용은 미검증이다. 원문 내용의 법률 판단은 별도 대사 결과로 남긴다.
