# 이어가기·중간 저장·잠금 규칙

"서버가 중간에 죽어도 이어서 할 수 있게" 넣은 로직이 질문 하나에 커밋 수백 번, 기록 전체 재구성, 32분짜리 잠금, 진행 표시와의 교착을 만들었다. 사용자 결정(11-10): **처리 중 서버가 죽으면 그 질문 작업은 잃어도 된다.**

## 기본값

- 질문 처리 중 상태는 프로세스 메모리에만 둔다.
- 질문이 끝나면 다음 질문에 필요한 것(대화)만 1번 저장한다.
- 실패하면 사용자가 다시 질문한다. 재개 경로를 만들지 않는다.
- 저장본은 최신 1개만 둔다(새 저장 성공 후 이전 것 삭제). [사례 27]

## 하지 말 것

### 1. 단계마다 저장점
- 일어난 일: 모델 호출 직전·잠금 해제 직전마다 업로드, 커밋 249회 43.7초. [사례 12, 13]
- 대신: 저장점 없음. 질문 끝 1번.

### 2. 진행 표시를 위해 커밋
- 일어난 일: 진행 표시가 커밋된 기록에서만 단계를 만들어 화면이 "요청 확인"에서 멈춰 보임. 중간 업로드와 진행 표시가 서로 잠금을 기다려 교착(현장 MAIN191). [사례 12, 16]
- 대신: 로그 이벤트로 즉시 표시. 진행 표시는 메모리 값만 읽는다.

### 3. 재개용 영수증·원장·세대를 습관적으로 추가
- 일어난 일: 상태 원장·영수증·판본 기록이 쌓여 기록 SQL이 SQL 시간의 대부분, 저장본이 대화 길이의 제곱으로 증가(10턴이면 55턴 분량). [사례 14, 27]
- 대신: 다시 읽는 곳이 없는 기록은 만들지 않는다. 감사가 필요하면 로그.

### 4. 긴 DB 잠금
- 일어난 일: 공용 잠금 1개를 모든 사용자가 같이 써 47.6초 뒤 500 [사례 9]. 잠금 유지 시간이 남은 요청 시간 + 120초(약 32분) [사례 21].
- 대신: 프로세스 안 잠금(채팅별). DB 잠금이 꼭 필요하면 짧게(90초) 잡고 연장. 같은 채팅 동시 질문은 409로 바로 돌려준다.

### 5. 공용 상태 1개
- 일어난 일: 모든 사용자의 대화가 기록 DB 1개를 같이 써서 서로 막고, 읽는 도중 남이 바꿔 실패(AGENT_SQL_CHANGED). [사례 3, 9]
- 대신: 채팅별로 나눈다. 서로 무관한 요청이 같은 행·잠금을 잡지 않게.

## 중간 저장이 진짜 필요할 때

아래가 모두 참일 때만 넣는다.

1. 그 단계를 다시 하는 비용이 크다(예: 모델 호출 수 분, 외부 수집 수십 분).
2. 실패가 실제로 자주 일어난다(현장 기록으로 확인).
3. 저장 비용(횟수 × 왕복·커밋) < 다시 하는 비용 × 실패 확률.
4. 재개 경로를 실제로 쓰는 소비자가 있다.

예: Dataiku 배치 적재(수십 분, 조각 단위 재개)는 해당한다. 채팅 질문 하나(수십 초)는 해당하지 않는다.

넣었으면 완료 보고에 1~4의 답을 남긴다.
