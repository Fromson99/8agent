# Oracle·ORDS 접근 규칙

현장 Oracle은 ORDS(HTTP)로 접근한다. 로컬 Oracle 왕복은 약 0.2ms지만 현장은 5~10ms, 커밋은 약 130ms다. 로컬에서 안 보이던 횟수가 현장에서 수백 초가 됐다. **SQL 문장의 품질보다 SQL을 보내는 횟수와 읽는 양이 먼저다.**

각 규칙 끝의 `[사례 N]`은 [cases-20261110.md](cases-20261110.md)의 번호.

## 하지 말 것 → 대신 할 것

### 1. 반복문 안의 SQL
- 하지 말 것: 조문마다, 문서마다, 후보마다 SQL 한 번.
- 일어난 일: 문서 하나를 지정한 질문이 SQL 8,521회·602초. 근거 확인을 한 건씩 해 ReadTimeout. [사례 1]
- 대신: ID 목록을 모아 한 문장으로 읽는다(`IN (SELECT … FROM JSON_TABLE(:ids …))` + 목록 크기 힌트). 문서·부모·키 단위 조회(`for_document`, `children_for`, 점조회).

### 2. 파일·SQLite 방식을 Oracle 위에서 흉내
- 하지 말 것: Oracle 행을 전부 불러와 메모리 SQLite를 다시 만들고, SQL을 SQLite식으로 쓴 뒤 번역하고, 파일 잠금을 DB 행으로 흉내.
- 일어난 일: DB를 열 때마다 기록 전체 재구성, 커밋마다 잠금·업로드, 질문당 SQLite 문장 약 2,290개, 현장 기록 SQL이 SQL 시간의 68~70%. [사례 14, 23, 28~30]
- 대신: Oracle에는 Oracle SQL을 직접 쓴다. 질문 중 상태는 프로세스 메모리의 일반 파이썬 객체로 둔다. 저장이 필요한 것만 질문 끝에 한 번 쓴다.

### 3. 쓰고 나서 다시 읽어 확인
- 하지 말 것: INSERT 뒤 같은 행 SELECT, 커밋 뒤 영수증 재조회.
- 일어난 일: 커밋 1번에 왕복 약 6번, 한 질문 왕복 1,386회. [MAIN176, 사례 2]
- 대신: 쓰기 성공 응답을 믿는다. 응답이 유실·불명일 때만 1번 대조한다.

### 4. 잠금·최신 확인·커밋·해제를 각각 다른 SQL로
- 일어난 일: 왕복 896회. [사례 2]
- 대신: 한 문장(또는 한 PL/SQL 블록)에서 끝낸다. 더 좋은 것은 DB 잠금 자체를 안 쓰는 것(프로세스 안 잠금).

### 5. 질문 처리 중 커밋
- 하지 말 것: 상태가 바뀔 때마다 커밋, 모델 호출 전마다 저장.
- 일어난 일: 현장 커밋 431회(평균 142ms), 249회 43.7초. 중간 업로드 방식(MAIN191)은 진행 표시와 서로 기다리는 교착. [사례 12~14]
- 대신: 질문 중 Oracle 쓰기 0, 질문이 끝나면 1번.

### 6. 범위·문서 전체를 펼쳐 돌기
- 하지 말 것: Oracle의 `units`·`tools.sources`·좌표·용어 목록에 `items()`·`sorted()`·`set()`·`for`.
- 일어난 일: 현장 1만 행 한도 오류(500), 전체 목록 거절. 로컬 소형 자료에서는 안 보임.
- 대신: 필요한 키로 조회. 범위 전체 ID 목록을 결과에 싣지 않는다(읽는 곳이 없던 `corpus_ids`).

### 7. 100행씩 잘게 나눠 읽기
- 일어난 일: 문서 목록 12왕복 9.0초, 약칭 상태 17왕복 6.0초. [사례 11]
- 대신: 행 크기에 맞춰 한 번에 많이(현재 `PageSizer`, 최대 500행·약 2MB).

### 8. 같은 계산을 여러 번
- 일어난 일: 첫 검색이 같은 점수 계산 SQL을 3번(각 3.0초). [사례 20]
- 대신: 한 문장으로 상위 결과를 받는다.

### 9. 질문마다 집계 SQL
- 일어난 일: 질문마다 기록 용량 합계 조회(현장 가장 느린 SQL 0.5초). [사례 8]
- 대신: 시간 단위로 재사용하거나 저장 시점에만.

### 10. 질문과 무관한 공통 자료를 첫 질문 때 읽기
- 일어난 일: 재시작 후 첫 질문만 SQL 206~207회. [사례 15, 24]
- 대신: 서버 시작 때 백그라운드로 준비(문서 목록·조문 목록·형태소 분석기). 원문 전체 내려받기는 여전히 금지.

### 11. 실행 계획 확인 없이 큰 표 조인
- 일어난 일: 결과 0행인데 6만 행 표를 통째로 훑음(HASH JOIN + FULL SCAN 28.8ms, 표가 클수록 증가), 개발계는 병렬 4로 돎. [사례 8]
- 대신: 큰 표 조회는 EXPLAIN으로 PK·인덱스 접근인지 본다. JSON 목록 조인은 `CARDINALITY` 힌트 + `NO_PARALLEL`.

### 12. 진단용 데이터를 운영 DB에
- 일어난 일: 진단·수집용 이벤트 190종까지 Oracle 작업 기록에 저장 → 커밋 224회. [사례 7]
- 대신: 진단은 로그나 NFS 파일, 기본 꺼짐.

### 13. 폴링이 DB를 읽기
- 일어난 일: 실시간 로그가 1초마다 Oracle 기록 읽기(23.7초), 진행 표시가 1초마다 기록 DB 재구성. [사례 5, 6]
- 대신: 폴링은 메모리 값만 본다. 바뀌었을 때만 읽는다.

## SQL 문장 작성 규칙

- SQL 문자열에 f-string 조각을 넣지 않는다(`f'SELECT …{x}…'`). 계획 목록에 새 문장으로 잡혀 stage가 멈춘다. 숫자는 글자로 바꿔 고정 문장 몇 개 중 하나가 되게 한다.
- 서빙 코드에 새 SQL을 넣으면 `06_TOOLS/maintenance/prepare_oracle_queries.py`로 계획을 다시 만들고 `--check`.
- WITH + NUMBER 바인드 모양은 현장 ORDS에서 ORA-22806이 났다. 통계 숫자는 리터럴로.
