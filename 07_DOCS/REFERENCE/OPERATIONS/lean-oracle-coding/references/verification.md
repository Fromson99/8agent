# 검증을 넣는 기준

검증은 공짜가 아니다. 11-10 현장 CPU 측정에서 요청 CPU의 41.5%(65.2초)가 캐시를 꺼낼 때마다 한 전체 해시였고, 16.7초가 원문을 읽을 때마다 한 해시였다. 둘 다 "혹시 바뀌었을까 봐" 넣은 것이었다.

## 넣는 곳: 신뢰 경계에서 1번

신뢰할 수 없는 값이 안으로 들어오는 지점에서만 검증한다.

| 경계 | 검증 |
|---|---|
| 모델 출력 | JSON 구문·스키마, 제시한 근거 ID가 실제로 준 것인지, 인용이 원문과 맞는지 |
| 외부 입력(사용자·API·파일) | 형식, 크기, 권한 |
| DB에서 처음 읽은 게시 자료 | 판본·권한 결속 1번 |
| 다른 프로세스·세션이 바꿀 수 있는 공유 상태 | 쓰기 시점에 버전 비교 1번(DB 문장 안에서) |

경계를 통과한 값은 같은 요청 안에서 믿고 재사용한다.

## 넣지 않는 곳

### 1. 같은 객체를 다시 해시·검증
- 일어난 일: 캐시 확인마다 릴리스 명세 전체 해시 6,002번(65.2초) [사례 4]. 원문 읽을 때마다 스냅숏·허용 목록 전체 해시, 호출 지점 90곳(16.7초) [사례 10]. 캐시 열쇠(SQL + 29KB JSON)를 꺼낼 때마다 SHA(6.7초) [사례 18].
- 대신: 요청 객체당 1번. 객체가 바뀌면(다른 객체·크기·판본) 다시. 캐시 열쇠는 튜플.

### 2. 바뀌지 않는 것을 요청마다 검사
- 일어난 일: 엔진 코드 해시 검사가 요청마다 475파일 경로를 풀고 다시 읽음(80.6ms) [사례 31]. jsonschema가 응답마다 스키마 자체를 표준에 대조(CPU 5.9초 중 3.7초) [사례 17].
- 대신: 프로세스당 1번. 바뀔 수 있으면 stat 같은 싼 신호로만 감지.

### 3. DB 제약·트리거를 코드로 흉내
- 일어난 일: 메모리 기록 표에서 SQLite 트리거·NOT NULL 흉내, 매번 정렬·해시 비교(행 3,000개 733ms) [사례 32].
- 대신: 메모리 객체는 그냥 파이썬 객체. 중복 방지가 필요하면 dict/set 색인 하나.

### 4. 저장 직후 재조회·영수증 재확인
- 일어난 일: 왕복 1,386회 [oracle-sql.md 3번].
- 대신: 성공 응답을 믿는다. 불명일 때만 1번 대조.

### 5. 바뀌지 않았는데 다시 직렬화·저장
- 일어난 일: 선택 진행 저장 48회, 매번 전체 상태를 두 번 직렬화 [사례 19].
- 대신: 1번 직렬화, 같으면 쓰지 않음.

### 6. 같은 요청에서 단계마다 같은 검증
- 한 단계가 검증한 결과를 다음 단계가 다시 검증하지 않는다. 결과 객체를 넘긴다.

## 새 검증을 넣을 때 보고에 남길 것

- 어느 경계인가 (위 표 중 어디)
- 무엇이 깨지면 잡나, 실제로 일어난 적이 있나
- 질문당 몇 번 도나, 한 번에 얼마인가
- 이미 다른 곳에서 하고 있지 않은가

위에 답이 없으면 넣지 않는다. "안전하게"는 이유가 아니다.

## 끄지 않는 것

권한(허용 문서 밖 원문 노출), 원문 인용 일치, 판본 결속, 모델 출력 스키마. 이것들은 경계에서 1번 하고 재사용한다. 줄이는 것은 반복이지 검사 자체가 아니다.
