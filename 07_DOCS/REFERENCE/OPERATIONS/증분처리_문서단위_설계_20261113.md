## 2. 1개만 처리하는 것을 막는 것

1. **Gold 행 번호가 "몇 번째 행"이다.** `oracle_query_publish._asset_rows`가 `row_id = digest([ordinal, value])`, 본문 검색 행은 SQLite rowid로 만든다.
   문서 하나가 빠지고 들어오면 그 뒤 행 번호가 전부 바뀌어, 안 바뀐 문서 행도 재사용할 수 없다. R7 적재기도 같은 함수(`engine/fast_export.py`).
   서빙은 행 번호를 계산하지 않고 정렬·이어 읽기에만 쓴다(`oracle_query_catalog.Records.page`) — 바꿀 수 있다.
2. **용어집이 전체 문서로 다시 만들어진다.** R6 prepare가 `--glossary-corpus-policy replace`로 문서 안 정의("이하 ~라 한다")를 용어집에 넣는다.
   바뀐 문서만 따로 처리하면 용어집이 달라지고, 기존 합치기 `lawrag/pipeline/document_append.py`는 용어집이 다르면 거부한다.
3. **참조 해소가 전체 문서 이름표를 쓴다.** `term_references.compile_references`가 모든 문서 이름·조문으로 인용을 푼다.
   바뀐 문서를 가리키던 다른 문서의 인용, 새 문서 때문에 새로 풀리는 인용이 있다. `document_append`는 기존 문서 인용을 다시 풀지 않는다.
4. **벡터 구간 번호가 세대마다 바뀔 수 있다.** `source_segments(store, item, dataset_version, …)` — 재사용은 "같은 본문이면 예전 벡터" 기준이어야 한다.

이미 있는 것: `document_append.py`(기존 행 그대로 복사 + 새 문서만 합치기, 시험 `05_TESTS/CONTRACTS/test_document_append.py`) — 추가만, 교체·삭제 없음.

## 3. 계획 — 표 구조는 바꾸지 않는다

Gold 13표 이름·컬럼·키 그대로. 세대마다 행 사본이 생기는 것도 지금과 같다(공유 구조로 바꾸려면 메타 재신청·서빙 수정이 필요해 하지 않는다).

### A. Gold 적재를 차이만 (시간이 가장 많이 줄 부분, 3번 어느 방식이든 필요)
- A1 행 번호를 **내용 기준**으로: 일반 표는 `digest([value])`(같은 내용 중복은 순번), 본문 검색 행은 rowid 대신 단위 키(logical id).
  **바꾸면 Gold 전체 행 번호가 한 번 바뀐다 → 첫 1회 전체 재적재 필요.**
- A2 적재: 새 세대 행을 로컬에서 계산(지금도 함) → 이전 세대 행 목록과 비교 →
  같은 행은 Oracle 안에서 `INSERT … SELECT`로 복사, 새 행만 올림, 없어진 행은 복사 제외. 세대 명세(행 수·체인)는 로컬 계산.
- A3 벡터: 이전 세대 구간 벡터를 본문 해시로 찾아 재사용, 새 본문만 임베딩.
- 이때 GENOS는 여전히 전체를 다시 돈다(75분+구조화) — 연결·용어집·통계는 전체 빌드라 정확하다.

### B. GENOS도 바뀐 문서만
- B1 구조화 결과를 파일 해시별로 보관(decide가 이미 `structured/<sha>.json.gz`로 만듦)하고 바뀐 파일만 구조화.
- B2 세대 합치기에 **교체·삭제** 추가(`document_append` 확장): 옛 문서의 원문·탐색·본문 색인 행 삭제 → 새 문서 행 추가.
- B3 참조는 **전체를 다시 푼다**(수 분, 전체 빌드와 같은 결과). 용어 통계는 다시 센다.
- B4 용어집 문서 정의: 바뀐 문서의 정의만 빼고 넣는 방식 — 정의 검토(모델 호출)가 걸려 있어 따로 설계.
- 이전 세대 SQLite는 S3 관리 폴더에 보관해 다음 증분의 기준으로 쓴다(GENOS는 상태를 갖지 않음).

### C. 증분 흐름 연결
- publish: 전체 원문 ZIP 대신 바뀐 문서 묶음 + 기준 세대 → 합친 세대 → A의 차이 적재 → activate는 그대로.

### S. 검색 속도 지키기 (사용자 요구 2026-11-13: "색인·캐시 때문에 검색 속도 문제 안 생기게")
증분이면 세대 전환이 매일 생길 수 있다. 지금 코드에서 확인한 문제와 대책:

| 어디 | 지금 (MAIN226 코드로 확인) | 대책 |
|---|---|---|
| Oracle 통계 | 새 세대 행이 들어와도 통계는 옛 세대 기준. 11-10 R7f 때 같은 문제로 나쁜 실행 계획 위험 → GOLD_STATS_R1 레시피를 붙였음 | 적재 뒤, **채널 바꾸기 전**에 Gold 표 통계 갱신(`no_invalidate=>FALSE`). 주요 서빙 SQL 실행 계획을 새 세대로 확인하고, 계획이 나빠지면(전체 읽기 등) 채널을 바꾸지 않음 |
| Oracle 색인·물리 순서 | 전체 적재 때 세대 행이 연속으로 들어감 | 복사도 세대 하나를 한 번에 색인 순서대로 넣어 같은 배치를 유지. 색인 추가·삭제 없음(X0~X4 그대로) |
| 옛 세대 삭제 | activate 직후 정리 | 새 세대가 서빙에 자리 잡은 뒤, 작은 묶음으로 나눠 삭제(묶음 사이 쉼). 큰 삭제를 질문 처리와 겹쳐 돌리지 않음 |
| 시작 때 미리 읽은 조문 정보 | `oracle_metadata_preload` 세대별, **서버 시작 때 한 번만** — 채널이 바뀌면 새 세대는 조문마다 Oracle 조회(약 0.12초씩) | 서빙이 새 세대를 보면 **뒤에서 미리 읽기를 끝낸 뒤에 새 세대로 넘어감**. 그동안 질문은 이전 세대로 답함(이전 세대는 Gold에 남아 있음). 넘어간 뒤 이전 세대 메모리는 비움 |
| 약칭 목록 | 색인 해시별. 새 세대면 **첫 질문이 질문 처리 중에 직접 만듦**(로컬 1,547문서 약 47초) | 위 미리 읽기에 포함. 문서 내용이 같으면 이전 세대 목록을 그대로 씀(문서 ID가 내용 해시) |
| 공유 행 캐시 | 세대 번호가 키라 새 세대는 전부 처음부터 | 위 미리 읽기가 자주 읽는 행을 채움. 이전 세대 항목은 넘어간 뒤 비움 |

## 4. 검증 기준
- 같은 입력으로 **증분 결과 = 전체 다시 빌드 결과**(행 내용 기준)를 시험으로 확인한다.
- Oracle 경로라 `06_TOOLS/maintenance/oracle_scale_guard/run.py` 통과, 행 번호 정렬이 바뀌므로 질문 답변 비교.
- 실제 시간: 개발계에서 전체 다시와 차이만을 같은 변경으로 잰다.
- 검색 속도: 로컬 Oracle에서 전체 적재 세대와 증분(복사) 세대로 같은 규모 점검 시나리오를 돌려 질문별 SQL 수·시간이 같거나 줄어야 한다.
  서버를 끄지 않고 채널을 바꾸는 동안과 바꾼 직후 질문 시간이 평소와 같아야 한다(미리 읽기 끝나기 전 새 세대 조회 0).
