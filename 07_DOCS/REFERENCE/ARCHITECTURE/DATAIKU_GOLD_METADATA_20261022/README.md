## 표준단어와 표준용어

**표준단어는 용어를 구성하는 재료이고, 표준용어는 DB 엔터티를 구성하는 속성명에 해당한다.** 용어를 구성하는 모든 단어는 표준단어 사전에 등록되어 있어야 한다. 우리 법령 RAG에서 수집하는 법률 개념·정의의 용어집과 전사 DB 명명용 표준사전은 역할을 구분한다.

### 단어의 종류·유형 — 사진 5, 7쪽

| 구분 | 의미와 예시 |
|---|---|
| 단일어 | 하나의 형태소로 구성된 단어. 가이드는 고유명사·지명과 접사가 결합된 단어도 이 범주에서 설명한다. 예: 고객, 도시, 기관, 가격, 시설. |
| 복합어 | 둘 이상의 단일어 조합. 예: 계좌번호 = 계좌(Account) + 번호(Number). |
| 외래어 | 외국어가 국어 체계에 동화된 단어. 예: 코드, 온라인, 오프셋. |
| 관용어 | 관용적으로 자주 쓰이는 표현. 예: 경기버스, 경기회수권. |
| 접사 | 접두사·접미사. 예: 재발급의 재-, 지급처의 -처. |
| 동음이의어 | 표현이 같지만 의미가 다른 단어. 예: 수신(Receive), 수신(Deposit). |
| 이음동의어 | 표현이 다르지만 의미가 같은 단어. 예: 이수(Completion), 수료(Completion). |
| 금칙어 | 사용을 제한하는 단어. 예: 화일(X), 파일(O). |

### 한글단어 사용 — 사진 6, 8쪽

- 단일어 형태의 낱말을 표준단어로 정의한다. 예: 보험, 기관, 성명.
- 모든 단어는 **명사형**으로 정의한다. 동사·부사·접속사·조사·복수 표시 또는 소유격 형태는 사용하지 않는다. 예: 예상되는금액 → 예상금액.
- 구두점·괄호 등 특수문자는 사용하지 않는다. 단어 지침에는 **`&`를 예외적으로 허용**하는 예시 `S&P`가 있다.
- 한글 약어를 사용하지 않는 것이 원칙이다. 예: 주민번호 → 주민등록번호.
- 접두사·접미사는 별도로 분리하지 않고 단일어로 등록하는 것이 원칙이다. 예: 재발급, 비정상.

### 영문단어 사용 — 사진 7, 9쪽

- 가급적 한글화한다. 예: FAX → 팩스, EMAIL → 이메일.
- 한글화할 때 현업에 익숙한 단어를 사용한다. 예: ERROR → 오류.
- 관용적으로 자주 쓰는 약어는 허용한다. 예: Structured Query Language → SQL.
- 한글보다 익숙한 영문 표현은 그대로 사용할 수 있다. 예: 인터넷프로토콜·아이피 대신 IP.

### 복합어·숫자·금칙어 — 사진 8, 10쪽

- 기관명·상품명 등 고유명사와 관용 표현, 단일어로 나누면 의미 전달이 불명확해지는 표현, 물리명 길이 제한 때문에 축약 약어를 사용하는 경우 등은 복합어를 하나의 단어로 등록해 사용하는 예외를 둔다.
- 숫자는 기본적으로 **아라비아 숫자**를 사용하고 영문으로 옮길 때도 유지한다. 사진 예: `1단계 → Step 1`, `1억 → 1 Hundred Million`.
- 이음동의어는 자주 쓰는 표현을 표준단어로 정하고 나머지는 금칙어로 등록한다. 사진 예: 비씨·BC·BC카드 대신 비씨카드.
- 영문단어는 기본적으로 한글화하되 영문 표현이 더 많이 쓰이는 경우에는 영문을 표준단어로 선정할 수 있다.
- 고유명사 등은 전체 표현을 표준단어로 정의하고 약어 등 다른 표현을 금칙어로 등록한다. 사진 예: 주총(X), 주주총회(O).

**원문 예시의 불일치:** 9쪽은 `EMAIL(X) → 이메일(O)`이지만, 10쪽은 `이메일(X) → E-mail(O)`로 제시한다. 어느 하나를 임의로 최종 표준으로 확정하지 않는다. 해당 업무의 실제 승인 표준사전과 표준 담당자의 해석을 확인하고, 이 문서에서는 두 예시와 출처를 모두 보존한다.

### 표준용어의 한글 구성 — 사진 9, 11쪽

| 규칙 | 적용 내용 |
|---|---|
| 구성 | **`수식어 + 도메인`** 형태로 정의한다. 사진 예: 결재완료 + 일시, 로그생성 + 여부. |
| 단어 등록 | 표준단어 사전에 등록된 단어만 사용한다. 없는 단어는 표준 담당자와 협의해 신규 요청·등록한다. |
| 의미 중복 방지 | 같은 의미의 용어는 재사용한다. 다른 의미가 필요하면 수식어를 추가해 차이를 분명히 한다. |
| 표기 | 한글 용어명에는 띄어쓰기·언더바·특수문자를 사용하지 않는다. 사진 예: 개인 법인 구분코드(X), 개인법인구분코드(O). |
| 변경에 취약한 이름 | 부서명·회사 상호처럼 컬럼명 변경을 유발할 수 있는 단어를 사용하지 않는다. |

**적용 단위를 구분한다.** 단어 사전의 `&` 예외와 영문 약어 허용을 한글 용어명 전체의 특수문자 허용으로 확대하지 않는다. 단어 분류에 고유명사가 포함된다는 설명도 부서명·회사 상호를 컬럼명에 자유롭게 사용한다는 뜻은 아니다. 앞서 7~11쪽만으로 확인하지 못했던 물리명 대소문자·길이 기준은 후속 12쪽에서 아래와 같이 보완했다. 언더바는 규칙 문구와 예시를 함께 확인해야 한다.

### 물리명 명명 규칙 — 후속 사진 1, 12쪽

| 구분 | 사진의 규칙·예시 |
|---|---|
| 문자 | 영문 대문자와 숫자를 사용한다. 원문에는 **대문자와 숫자만 사용**한다고 적혀 있다. |
| 조합 | 표준단어 사전에 정의된 단어의 **영문 약어**를 조합한다. |
| 길이 | **용어 한글명과 영문명 각각 최대 30바이트**로 제한한다. |
| 복합어 우선 | 등록된 복합어를 단일어보다 우선 적용한다. 예: 신용 + 거래 + 일자(X), 신용 + 거래일자(O). |
| 복합어가 겹칠 때 | **도메인을 포함하는 복합어**를 우선 적용한다. 예: 신용거래 + 일자(X), 신용 + 거래일자(O). |
| 길이 제한용 복합어의 예외 | 길이 제한 때문에 생성한 복합어보다 단일어 조합을 우선한다. 사진은 거래 + 건수의 `TDNG_CNT` 예시를 제시한다. |

**문자 규칙과 예시의 차이:** 같은 12쪽에 “영문 대문자와 숫자만”이라는 규칙과 언더바가 들어간 `TDNG_CNT` 예시가 함께 있다. 이를 근거로 언더바를 일괄 금지하거나 모든 특수문자를 허용하지 않는다. 실제 메타마이너의 약어 결합·구분자 규칙을 확인할 항목으로 보존한다. 30바이트는 이 가이드의 **용어명 규약**이며 데이터 값의 길이나 모든 Oracle 버전의 식별자 한도로 확대하지 않는다. 한글명 바이트 계산에 적용할 문자셋은 사진에 명시되지 않았다.

### 금액·날짜와 유형별 용어 — 후속 사진 2~3, 13~14쪽

| 유형 | 사용 원칙 | 사진의 예시 |
|---|---|---|
| 금액·통화 | 원화만 발생하면 금액을 사용하고, 원화·외화 구분이 필요하면 해당 수식어를 붙인다. | 세전원화거래금액, 세전외화거래금액 |
| 금액·단위 | 금액이 원 단위가 아니면 단위를 나타내는 수식어로 용어명을 명확히 한다. | 백만 + 단위 + 금액, 십만 + 단위 + 금액 |
| 일자 | 연·월·일의 날짜 값을 갖는 용어는 일자를 사용한다. | 가입년월일 → 가입일자 |
| 일시 | 날짜와 시간 값을 함께 갖는 용어는 일시를 사용한다. | 가동일시, 종료일시 |
| 일 | 매월 특정 일처럼 일 자체의 의미가 유효할 때 사용한다. | 결제일 |
| 연·년 | 숫자가 앞에 오면 년, 숫자 없이 쓰면 연을 사용한다. | 1999년말, 연말연시 |
| 총·합계 | 같은 의미를 중복하지 않는다. | 총합계금액(X) → 총금액 또는 합계금액 |
| 현재·현 | 현재 시점을 나타내는 기본적 수식어는 사용하지 않는다. | 현재주소 대신 주소: 현재 주소의 의미를 내포 |
| 율·률 | 모음이나 ㄴ 받침 뒤에는 율, 그 밖에는 률을 사용한다. | 이율, 환율, 수익률 |
| 식별자·식별번호·ID | 기본적으로 번호를 사용한다. **MDM 시스템·외부 I/F 용어는 예외**이며 ID의 고유한 성격이 있으면 ID를 사용한다. | 거래식별자(X) → 거래번호(O); 계좌ID·사용자ID 등은 예외 예시 |

13쪽의 **금액 관련 용어 어순**은 다음과 같다.

`기간 수식어 → 기간·시간 → 대상 → 장소 → 전·후 → 총 → 누적 → 금액 수식어 → 원화·외화 → 도메인`

사진 예시는 `최근 + 3개월 + 해외 + 총 + 누적 + 이용 + 금액`이다. 기간 수식어는 최근·과거·이전·최초·최종, 기간·시간은 당월·3개월·익일·전년말, 장소는 해외·국내 등의 예시를 든다. 의미에 필요한 요소를 이 순서로 조합하며 이름에 표시한 통화·단위·기간은 Description의 실제 값 설명과 일치시킨다.

ID 예외를 포함한 위 내용은 전사 **용어 명명 규약**이다. 이 문서 보완만으로 기존 API의 `document_id` 등 필드나 원문·판본·근거 식별자를 변경하지 않는다. 물리 스키마에 적용할 때 기존 계약과 매핑을 별도로 검토한다.

## 표준도메인 — 후속 사진 4, 15쪽

도메인은 속성이 가질 수 있는 값들의 집합이다. 공통 특성을 묶고 허용 값을 제한해 **데이터 형식과 명명을 함께 표준화**한다. 사진은 도메인 그룹 → 도메인 → 사용 예 → 타입·길이가 결합된 도메인 → 실제 데이터 타입을 연결한다.

| 도메인 그룹 | 도메인 | 사진의 사용 예 | 타입·길이 결합 표기 | 사진의 데이터 타입 |
|---|---|---|---|---|
| 금액 | 금액 | 신용카드금액 등 | 금액NM15 | `NUMBER(15)` |
| 금액 | 수수료 | 카드할부수수료 | 수수료NM12.4 | `NUMBER(12,4)` |
| 번호 | 거래번호 | 분리거래번호 | 거래번호VC10 | `VARCHAR2(10)` |
| 번호 | 팩스번호 | 지점팩스번호 | 팩스번호VC20 | `VARCHAR2(20)` |

이 표는 **가이드 예시**이며 우리 법령·온톨로지 테이블에 같은 길이와 타입을 일괄 지정하는 표가 아니다. 기존 인포타입·승인된 도메인을 우선 조회하고 실제 데이터 길이·정밀도·허용값에 맞춰 선택한다. 앞선 골드 안내의 `NVARCHAR → VARCHAR` 표기와 이번 예시의 `VARCHAR2` 표기를 각각 보존하며, 실제 Oracle DDL 타입명과 BYTE/CHAR 의미는 현장 승인 모델에서 확인한다.

## 표준코드 — 후속 사진 5~7, 16~18쪽

### 구성 요소와 구분

가이드는 **코드 종류**를 일반코드·참조코드·개별코드로 나누고, 별도로 **코드 유형**을 일반코드·연관코드로 구분한다. 코드명과 코드ID는 중복을 허용하지 않는다고 명시한다. 중복 검사 범위를 전사·업무·사전 중 어디까지로 잡는지는 사진에 추가 설명이 없다.

| 구분 | 의미 | 사진의 예시 |
|---|---|---|
| 일반코드 | 정보를 나타내기 위한 기호 체계 | 배송방법코드·지역코드와 각각의 코드값 |
| 참조코드 | 같은 사전의 일반코드 값을 그룹화해 만든 코드. 일반코드에 등록된 코드값 범위에서 구성한다. | 국가코드의 대한민국·중국·일본을 아시아국가코드로, 프랑스를 유럽국가코드로 묶는 예시 |
| 연관코드 | 같은 사전의 코드 간 연관관계와 전·후 관계를 표현한다. | 시·도코드 → 시·군·구코드 → 읍·면·동코드 |
| 개별코드 | 스키마의 코드성 테이블을 참조해 표준코드로 사용한다. | 국가코드·은행코드 → 스키마 코드테이블 |

코드 이름의 표준 등록, 코드가 허용하는 값 목록, 코드 사이의 관계를 구분해 기록한다. 참조코드의 그룹화와 연관코드의 관계를 같은 개념으로 취급하지 않는다.

### 코드값명과 코드값 부여 원칙 — 후속 사진 7, 18쪽

- **코드값명**은 표준단어의 조합으로 작성한다. 필요한 단어가 사전에 없으면 표준단어를 추가하는 절차를 따른다.
- **코드값**은 원칙적으로 문자형 일련번호를 부여하며, 자료 발생 순서로 나열해 추가하기 쉽게 한다.
- 특별한 사유가 없으면 현업에서 부여한 코드값을 최우선 사용한다.
- 가능한 한 연속적으로 부여하되, 숫자에 업무 의미를 담은 비연속 부여는 원칙적으로 허용하지 않는다. 사진의 비권장 예시는 신규=0·해지=9처럼 생략 구간에 의미를 둔 방식이다.
- 코드값 길이는 향후 확장성을 고려한다.
- 숫자 모양의 코드도 **문자형 숫자**로 코드 길이를 맞추고 앞자리를 `0`으로 채운다. 사진은 `CHAR(2)`의 `01`, `02`를 제시한다.

| 취미코드 예시 | AS-IS | TO-BE (`CHAR(2)`) |
|---|---|---|
| 운동 | 1 | `01` |
| 테니스 | 2 | `02` |
| 영화감상 | 10 | `04` |
| 수영 | 11 | `05` |

위 표는 원본에서 중간 행을 생략한 **설명용 변환 예시**다. 실제 코드 변경은 현업 코드 우선 원칙과 함께 판단해야 하며 기존 값을 임의로 재번호화하지 않는다. 프로젝트에 적용할 때는 코드값·코드값명·사용 도메인·버전·기존 값 매핑을 확인하고, 코드가 숫자로 변환되어 선행 `0`이 사라지지 않게 설계한다.

## 데이터표준 활용·신청 절차

### 표준 조회에서 모델링까지 — 사진 1, 20쪽

존재하는 표준은 PowerDesigner에서 바로 모델링에 활용한다. 없는 표준은 메타시스템 웹 클라이언트에 접속해 표준을 요청하며, 별도 승인·결재를 통과해야 모델링에 사용할 수 있다.

```mermaid
flowchart LR
    A[표준 조회] --> B{표준 존재?}
    B -->|예| C[PowerDesigner 모델링 활용]
    B -->|아니요| D[메타마이너 표준 요청]
    D --> E{승인·결재}
    E -->|승인| A
    E -->|미승인| D
```

위 그림은 원본의 개요를 요약한 것이다. 표준 신청이 승인되었다는 사실과 골드 테이블을 DBA가 실제 생성했다는 사실은 별도 상태로 기록한다.

### 신청·검토·적용 — 사진 3, 22쪽

사용자 작업 순서는 **표준작업 → 요청서 작성 → 결재 상태 확인 → 후속 조치**다. 흐름도는 작업 및 신청·검토·적용의 세 구간으로 나뉜다.

| 담당·단계 | 사진에서 확인되는 역할 |
|---|---|
| 신청자(개발자) | 표준작업, 유효성·변경 영향 검토, 요청서 작성과 승인 요청 |
| 변경관리자 | 데이터·변경 영향 검토와 승인·반려 판단 |
| 데이터표준관리자 | 데이터·변경 영향 검토와 승인·반려 판단 |
| 기준정보실무자 | 기준정보에 해당하는 분기의 검토. 기준정보 여부에 따라 이 검토를 거치거나 EDA 검토로 진행 |
| EDA | 후속 검토·승인 판단 |
| 메타마이너(DBMS) | 승인된 표준 적용 |

검토에서 승인되지 않은 경로는 표준작업으로 돌아간다. 사진에서 별도로 정의하지 않은 `EDA` 약어의 풀이나 실제 담당자·처리 기한은 추가로 가정하지 않는다.

### 화면에서 작업할 순서 — 사진 4, 23쪽

1. **신청관리 → 표준신청**에서 용어·코드·도메인·단어 중 신청 대상을 선택한다.
2. **업무 탭에서 업무를 선택**한다. 하나의 업무는 하나의 사전을 참조하므로 선택한 업무에 따라 작업할 표준사전이 자동으로 정해진다.
3. 해당 사전에서 표준데이터의 신규 생성·기존 데이터 변경·삭제 작업을 작성한다.
4. 앞의 신청 절차에 따라 요청서 작성, 결재 상태 확인, 필요한 후속 조치를 수행한다.

화면에 변경·삭제 기능이 있다는 설명을 기존 표준이나 프로젝트 데이터를 임의로 변경·삭제하라는 지시로 사용하지 않는다.

## 우리 골드 레이어 설계에 반영할 순서

아래는 네 사진 묶음을 기존 프로젝트 규약에 연결한 적용 절차다. 현재 테이블의 표준 준수나 현장 등록 완료를 판정한 결과는 아니다.

1. 대상 업무와 표준사전을 확인하고, 필요한 표준단어·표준용어·도메인·인포타입을 먼저 조회한다.
2. 원문 판본·구조 단위·개념·관계·위키 테이블의 실제 행 단위와 PK를 정의한다. 질문·판단·로그는 에이전트 레이어, 재사용 지식은 골드 레이어에 둔다.
3. 등록된 단어를 사용해 `수식어 + 도메인` 형태의 논리명을 구성한다. 동의어·금칙어·의미 중복과 한글·영문 예외를 확인한다. 미등록 단어·용어는 승인 절차를 거친다.
4. 논리명·물리명·도메인·인포타입을 연결한다. 등록 영문 약어·대문자·용어명 30바이트 기준과 유형별 용어·코드값 규칙, 기존 규약의 `VARCHAR` 및 해당 ADB의 한글 길이 기준을 실제 DDL에 맞게 검토한다. 구분자·문자셋 등 남은 확인 사항은 승인 모델과 대조한다.
5. [테이블 목록·Bizmeta·컬럼 정의 양식](TABLE_SCHEMA_WORKBOOK.md)에 따라 에이전트·스키마·테이블·골드 후보, 데이터논리명·출처·유형·가공 과정·생성시각, 등록 대상·검토·제외 요청, 컬럼 순번·물리명·논리명·타입 대조를 작성한다. [테이블·컬럼 Description 규약](../../../../00_SYSTEM/ARCHITECTURE.md#dataiku-gold-schema-convention)에 따라 원천·기간·갱신·산식·주의·오너·예시 질의와 컬럼 의미·허용값도 작성한다.
6. 메타 등록·표준 승인, 운영 골드의 DBA 생성 신청·생성, Dataiku 적재·검증을 구분해 진행하고 실제 반영 결과를 기록한다.
