# 법률 에이전트 골드 테이블과 컬럼 작성 가이드

3번·5번 공통 | 음성 녹취와 메타마이너 PPT·안내 사진 통합 | 2026-10-28

## 1. 작성 순서부터 잡기

골드 정의서는 **무엇을 저장하는지 정하고 → 기존 표준을 찾고 → 이름·타입·제약을 맞추고 → 업무 설명을 채운 뒤 → 용어·모델 등록과 테이블 생성을 진행**하는 순서로 작성한다. 이름만 비슷한 표준을 가져오거나 영어 약어부터 만드는 방식은 재검토를 늘린다.

이 가이드는 3번·5번 법률 에이전트가 공동 사용하는 데이터에 적용한다. 2번 ELS 과제는 엑셀 양식과 검토 사례의 참고 자료다. ELS 상품코드·조건·벡터 테이블을 법률 에이전트의 등록 대상으로 가져오지 않는다.

| 순서 | 할 일 | 남길 결과 |
|---|---|---|
| 1 | 저장 목적, 1행 단위, 실제 사용자를 정한다 | 테이블 용도·PK·소비자 |
| 2 | 골드 지식, 에이전트 기록, S3 작업물을 구분한다 | 활용테이블 목록·제외 사유 |
| 3 | 실제 값의 의미·형식·길이·NULL을 조사한다 | 현재 컬럼·타입·허용값 |
| 4 | 같은 의미의 표준용어와 구성 단어·도메인을 조회한다 | 재사용 근거 또는 신청 후보 |
| 5 | 논리명·물리명·타입·제약을 함께 작성한다 | 테이블·컬럼 시트 |
| 6 | 출처·가공·갱신·오너와 업무 설명을 채운다 | Bizmeta·Description |
| 7 | 유효성·중복·기존 계약과의 차이를 검토한다 | 수정 내역·남은 확인 사항 |
| 8 | 표준 승인 → 모델 등록 → DBA 생성 → 적재·조회 검증을 진행한다 | 단계별 신청번호·확인 결과 |

**작성 기준과 실제 반영 상태를 나누어 적는다.** 엑셀의 ‘반영’은 표를 고쳤다는 뜻일 수 있다. ‘표 작성 반영 / 표준 미승인 / DB 미반영’처럼 무엇이 끝났는지 구체적으로 쓴다.

현재 통합 마스터는 기존 골드 후보 7표·36컬럼과 온톨로지 게시 3표·13컬럼을 합친 **10표·49컬럼**이다. 이 숫자는 이번 등록 검토 범위이며 모든 후속 위키·숏컷 설계가 끝났다는 뜻은 아니다.

기준 자료는 앞서 붙여넣은 **00:00–30:27 음성 녹취**, 메타마이너 PPT 사진 16장, 골드 안내 사진 4장, 테이블·Bizmeta 화면 사진 7장이다. 음성 원본을 재청취한 기록은 없으며 불명확한 전사어는 사진과 대조하거나 확인 항목으로 남겼다.

근거: 녹취 01:47–03:53, 29:04–30:27 / PPT 11·20·22·23쪽 / 골드 안내 사진 4.

## 2. 기존 표준을 찾고 재사용 여부 정하기

| 구분 | 의미 | 작성할 때 확인할 것 |
|---|---|---|
| 표준단어 | 용어를 만드는 재료 | 한글명·영문명·등록 약어·정의·단어 유형 |
| 표준용어 | 컬럼이 나타내는 업무 속성 | 논리명·물리명·의미·도메인·타입·길이 |
| 도메인 | 값의 성격과 허용 범위를 묶는 기준 | ID·번호·명·내용·일시·여부·값 등의 의미 |
| 인포타입 | 타입·길이 등이 결합된 적용 형식 | 해당 DBMS의 실제 타입·길이·정밀도 |

‘법규 + 문서 + ID’는 구성 예시다. 세 단어와 그 조합 용어가 실제 사전에 등록되어 있다는 뜻은 아니다. 전사 DB 명명용 표준사전과 RAG가 검색하는 법률 용어집도 구분한다.

먼저 **신청관리 → 표준신청 → 업무 선택**에서 대상 업무의 사전을 확인한다. 해당 업무가 참조하는 사전에서 전체 용어를 찾고, 없으면 구성 단어·동의어·도메인 순으로 확인한다. 단어 유형이나 도메인 구분이 맞지 않아 조합이 안 되면 이름이 비슷한 항목을 억지로 선택하지 말고 표준 담당자에게 정의와 사용 예를 제시한다.

| 조회 결과 | 처리 방법 |
|---|---|
| 의미·타입·길이·허용값이 모두 맞음 | 기존 승인 용어를 재사용하고 표준 식별정보를 기록한다 |
| 같은 의미지만 한글 저장 바이트가 달라짐 | 기존 용어를 기준으로 길이 조정 근거와 모델 예외 처리를 협의한다 |
| 이름은 같지만 값의 의미·생성 방식이 다름 | 업무 수식어로 구분한 용어를 검토한다. 타입 차이만으로 의미를 꾸며내지 않는다 |
| 용어는 없지만 구성 단어·도메인이 있음 | 기존 단어를 조합한 신규 용어를 신청한다 |
| 필요한 단어 또는 적합한 도메인이 없음 | 정의·예시·재사용 범위를 제시하고 신규 단어·도메인 신청을 협의한다 |

예를 들어 사전에 ‘문서ID’가 있어도 우리 문서 ID가 UUID 36자가 아니라 원천 문자열이고 현재 계약이 512 BYTE라면 그대로 치환할 수 없다. 원천·의미·길이를 설명하고 ‘법규문서ID’ 후보의 재사용 또는 신규 등록 여부를 검토한다. 녹취의 청크ID 240도 **우리 본문조각ID와 같은 의미인지, 길이가 충분한지 확인한 뒤** 적용한다.

검토표에는 `검색한 용어 / 사전·업무 / 기존 의미·타입·길이 / 우리 값과의 차이 / 재사용·신규 판단 / 담당자 확인 결과`를 남긴다. 조회 전 항목을 ‘기등록’이나 ‘표준 준수’로 표시하지 않는다.

근거: 녹취 00:00–01:47, 05:04–11:10, 13:17–15:59 / PPT 7·11·15·23쪽.

## 3. 논리명과 물리명 작성하기

컬럼 논리명은 **수식어 + 도메인**으로 작성한다. 마지막 단어가 그 값의 성격을 드러내야 한다. ‘키’, ‘항목’, ‘필드’에서 끝내지 말고 실제 값이 식별값인지 내용인지 순번인지 정한다. 이름을 도메인으로 끝내는 것과 그 도메인의 타입·길이에 맞추는 것은 함께 검토한다.

| 검토 전 이름 | 우리 데이터에 맞춘 후보 | 고친 이유 |
|---|---|---|
| 문서ID | 법규문서ID | 기존 범용 문서ID와 원천·길이 차이를 설명 |
| 구조단위식별자 | 법규구조단위ID | 장·절·조·항·호를 가리키는 원문 구조 식별값 |
| 검색키 | 법규검색키값 | 용어 표기와 식별 문자열을 담는 조회키 값 |
| 좌표내용 / bbox내용 | 원문좌표해시값 | 우리 컬럼은 이미지 영역이 아닌 원문 좌표의 해시 |
| 조회자료유형값 | 법규조회유형값 | 다른 업무에서도 값의 의미를 구분할 수 있게 상세화 |
| 문서명 + CLOB | 법규문서명내용 | 현재 긴 원문 이름을 내용 도메인으로 보존하는 안 |
| 승인 작업 판본 | 지식작업판본번호 | 증가하는 작업 판본 번호임을 표시 |
| 활성 포인터 변경 순번 | 지식변경순번 | 원문 판본·게시 ID와 다른 동시 변경 검사용 순번 |

위 이름은 우리 마스터의 **검토 후보**다. 담당자가 승인한 단어 약어·용어가 있으면 그 명칭을 우선 적용한다. `내용→CTNT`, `값→VALU`, `일시→DATE_TIME`도 참고 양식에서 가져온 후보이지 전사 승인 확인을 대신하지 않는다.

한글 용어명은 띄어쓰기·언더바·특수문자 없이 명사형으로 작성하고, 쉽게 바뀌는 부서명·회사명을 넣지 않는다. 통상적인 영문 약어·외래어와 복합어는 실제 사전의 허용 형태를 따른다. 기존 의미의 용어를 재사용하며, 단어를 길게 늘려 구별하는 방식은 피한다.

물리명은 **등록된 영문 약어를 조합**한다. PPT의 용어 한글명·영문명 30바이트 규약을 확인한다. 이것은 데이터 값의 30바이트 제한이 아니며 모든 DB 버전의 식별자 한도도 아니다. 한글명의 UTF-8 길이 검사는 사전 점검으로 사용하고 메타마이너의 산정 기준을 최종 확인한다.

운영 테이블명은 참고 양식의 `IDD_과제코드_업무명` 형식을 따르되 **_G 같은 레이어 접미사를 붙이지 않는다.** 개발계 `_S`·`_A` 이름은 현재 값으로 보존한다. 3·5번은 공통 소비자로 적고 대표 명명 과제를 별도로 확정한다. 현재 R3의 A03·A05와 3번 대표명은 잠정안이다.

## 4. 타입과 길이를 정하기

타입은 값의 의미·실제 형식·최대 길이를 조사하고 기존 인포타입과 대조해 정한다. **길이가 맞는다는 이유만으로 의미가 다른 용어를 선택하지 않는다.** 여유가 필요한 경우 필요한 크기를 설명하고 적합한 기존 인포타입을 우선 사용한다.

| 값의 종류 | 우리 작성 기준 |
|---|---|
| 문서·구조·본문 ID | 현행 512 BYTE 계약과 원천값 보존. UUID 36 또는 참고 청크ID 240으로 임의 축소하지 않음 |
| SHA-256 해시 | 생성 규칙을 확인하고 64자리 문자열 계약을 기록. 숫자형으로 바꾸지 않음 |
| 원문·가변 JSON | CLOB 사용 사유를 정의에 적음. 길이가 짧다고 확인된 항목만 제한형 문자열 전환 검토 |
| 한글 포함 문자열 | BYTE/CHAR 단위와 현장 문자셋·실제 최대 저장 바이트를 함께 확인 |
| 여부 | 승인 도메인의 값 체계와 타입 확인. 현재 0/1/NULL이면 Y/N/NULL 변경 시 값 변환·역변환 필요 |
| 일자·일시 | 날짜만인지 시간·시간대까지 필요한지 구분. 시간대 포함 값을 설명 없이 제거하지 않음 |
| 코드·번호 | 숫자 모양이어도 식별값·코드는 문자형과 선행 0을 보존. 증가 순번과 구분 |
| 벡터 | 별도 컬럼을 실제 설계할 때 안내된 벡터 도메인 대조. 이번 10표에는 새 벡터 열 없음 |

사진과 녹취의 대상 ADB 안내는 **한글 3바이트, 기존 DW 표준의 한글 2바이트 산정과 차이**가 있다는 것이다. 기존 한글 20자를 40 BYTE로 잡았다면 같은 20자에 60 BYTE가 필요할 수 있다. 이는 설명용 예시이며 모든 문자열을 1.5배 늘리는 규칙이 아니다. 이미 UTF-8 바이트로 관리한 512 BYTE 식별자, 영문 해시, CLOB에 같은 배율을 적용하지 않는다.

문자열 실측 시 일반 문자 열에는 `MAX(LENGTH(컬럼))`와 `MAX(LENGTHB(컬럼))`를 구분해 사용한다. NULL·빈 값·허용된 원천 전체의 범위도 확인한다. CLOB은 일반 문자열과 같은 방식으로 바이트 길이를 계산한다고 가정하지 말고 별도 측정 방법을 사용한다.

Dataiku 자동 생성에 맡겨 NVARCHAR 계열이 생기는 경우를 피하도록, **승인된 VARCHAR/VARCHAR2 계열 모델과 DDL로 먼저 생성하고 Dataiku는 해당 표에 적재**한다. 정확한 타입 표기·BYTE/CHAR·국가 문자셋 동작은 대상 환경 기준으로 확인한다.

한글 길이 때문에 표준 모델과 달라지는 경우에는 `변경 전 길이 / 필요한 길이 / 실측 근거 / 문자셋 / 예외 사유 / 수정 DDL`을 함께 제출한다. 유효성 경고는 사유에 맞춰 담당자와 예외 처리를 협의한다. 녹취의 특정 길이 예외 설명을 모든 경고의 일괄 통과 지시로 사용하지 않는다.

근거: 녹취 05:04–07:50, 13:17–15:59, 18:02–19:24, 21:12–26:38 / PPT 13–15·18쪽 / 골드 안내 사진 2.

## 5. 테이블 시트 8개 열 채우기

현재 제공된 원본 엑셀의 열 이름과 순서를 유지한다. 현재 이름과 운영 후보 이름이 다르면 둘 다 남겨 이행 대상을 추적한다.

| 열 | 작성 방법 |
|---|---|
| 에이전트번호 | 3번·5번 공동 사용을 표시. 공식 접두어와 대표 등록 과제는 별도 확인 |
| 스키마 | 이 행이 신청할 운영 골드 스키마. 현재 초안은 참고 양식의 SIDDG 기준 |
| 테이블명(현재) | 현재 개발 계약의 owner.테이블명. 현장 실재 확인 전에는 DDL 기준이라고 명시 |
| TOBE 테이블명 | 승인 규칙에 따른 운영 물리명 후보. 레이어 접미사 제외 |
| 논리명(한글명) | 무엇을 담는 테이블인지 드러내는 업무 명칭 |
| 테이블 정의 | 무엇을 왜 저장하는지, 1행 단위와 판본·이력 처리의 핵심을 설명 |
| 원천테이블 | 실제 원천 테이블 또는 파일·관리 폴더·생성 단계. 파일 원천이면 ‘없음’만 쓰지 않음 |
| 반영내용 | 바꾼 사항·이유·남은 확인 상태. 표 수정과 DB 반영 구분 |

## 7. Bizmeta와 Description 작성하기

Bizmeta는 업무 사용자가 데이터의 출처와 생성 방식을 이해하도록 쓴다. 데이터논리명 설명과 컬럼의 표준용어 논리명은 작성 목적이 다르다.

| Bizmeta 항목 | 작성할 내용 |
|---|---|
| No.·에이전트·스키마·테이블 | 활용테이블 목록의 같은 객체와 연결 |
| 데이터논리명 | 무엇을 담은 업무 데이터인지 설명 |
| 데이터출처 | 원천 시스템·테이블 또는 문서 파일·가공 단계 |
| 데이터유형 | MASTER / HISTORY / SNAPSHOT / SUMMARY 중 저장·갱신 방식에 맞게 선택 |
| 데이터 가공 프로세스 설명 | 입력 → 검증·변환·결합 → 적재·갱신 순서 |
| 생성시각 | 실제 배치 주기·시각 또는 생성 사건. 미정이면 미정으로 기재 |

우리 설계의 실무 판정 예시는 활성 게시 선택=MASTER, 생성·승인 사건 이력=HISTORY, 불변 게시본=SNAPSHOT, 집계 결과=SUMMARY다. 이는 업무 적용 예시이며 사진에 분류의 상세 판정 기준 전체가 제공된 것은 아니다. `NUMBER`, `CLOB`은 이 분류가 아니라 컬럼 타입이다.

| 보유기간·기준시점 | 게시 이력 보존. 공식 기간·삭제 기준은 업무 오너 확인 |

| 주의 | 원문 판본·권한 확인. 승인만으로 조회 가능하다고 해석하지 않음 |

## 8. 표준 신청부터 DB 사용까지 진행하기

| 단계 | 담당·작업 | 완료로 기록할 근거 |

| 모델 작성·등록 | 승인 용어를 골드 모델 컬럼에 선택하고 PK·관계·타입 확인 | 모델 유효성·중복 검토 결과 |
| 예외 검토 | 한글 길이 등 차이에 사유·실측·수정 DDL 첨부 | 담당자 확인·예외 처리 결과 |
| DBA 생성 신청 | 모델·테이블/컬럼 정보·Description·접근권한 요청 전달 | 생성 신청 및 처리 결과 |
| 실제 생성 확인 | owner·타입·길이·NULL·PK·FK·CHECK·인덱스 대조 | 현장 DB 메타데이터 결과 |
| 적재·조회 연결 | 승인 매핑으로 적재하고 재조회·권한·해시·소비자 확인 | 적재 영수증·실제 RAG 조회 결과 |

녹취의 흐름은 **용어가 등록되어야 모델에 가져다 쓸 수 있다**는 것이다. 화면의 유효성 통과와 경고 메시지를 함께 확인하고, 다른 뜻의 동명 용어·타입 불일치·중복은 해당 사유에 맞춰 해결한다. 예외 처리를 입력했다는 사실만으로 거버넌스 승인이나 DB 생성이 끝난 것은 아니다.

**두 종류의 승인을 따로 관리한다.** 표준·모델 승인은 테이블과 컬럼을 어떤 정의로 만들지에 대한 승인이다. 온톨로지 내용 승인은 원문을 검토해 어떤 지식을 게시할지에 대한 승인이다. 전자가 끝나도 지식 내용이 승인된 것은 아니고, 후자가 끝나도 DB 게시 전에는 RAG 사용 대상으로 삼지 않는다.

온톨로지의 내용 처리 순서는 `S3 초안 → 원문·시나리오 검토 → 내용 승인 → 게시본·색인·활성 선택·감사 기록 저장 → RAG 조회`다. 초안과 작업 이력은 유지하고 새 판본마다 재검토한다.

현재 구현은 개발계 온톨로지 5표를 같은 owner와 고정명으로 접근한다. 운영 골드 3표·에이전트 2표로 나누고 새 이름을 쓰려면 테이블·컬럼 매핑을 구현하고 게시·활성·감사 기록의 트랜잭션을 유지해야 한다. **정의서의 이름을 고친 것만으로 실제 조회 경로가 바뀌지는 않는다.**

PPT·사진에 나온 테이블스페이스나 업무 코드가 불명확하면 원본 안내·담당자에게 확인한다. 생성 권한·테이블스페이스 값을 추정해 신청서에 확정값으로 쓰지 않는다.

## 10. 제출 전 점검과 남은 확인 사항

|---|---|

| [ ] 도메인 종결 | 모든 컬럼 논리명이 실제 값에 맞는 도메인으로 끝나는지 |

| [ ] 변환 | 타입·값 변경에 적재·역변환·재조회·소비자 수정 계획을 적었는지 |

| [ ] 담당자 | 대표 과제·업무 오너·보유기간·권한·배치시각·테이블스페이스를 확인했는지 |

**우리 통합본에서 담당자와 확정할 항목**

1. 3번·5번의 공식 A/B 접두어와 공통 테이블의 대표 등록 과제. 참고 파일명 A02와 본문 B02의 불일치를 그대로 승계하지 않는다.
2. 34개 용어 후보의 실제 사전 조회 결과, 등록된 약어·도메인·인포타입, ID 예외 적용 여부.
3. 문서명 CLOB과 일시의 시간대 보존에 맞는 표준 타입, 한글 문자열 실측 및 필요한 길이 예외.
4. 여부형의 Y/N 전환 승인과 실제 적재·조회 변환, Gold/Agent 분리 매핑 및 트랜잭션 구현.
5. 관리 부서·보유기간·운영 생성시각·접근권한·테이블스페이스와 실제 신청·승인 상태.
