# 대화 요구사항 대응표

[v4 목차](../ONTOLOGY_V4.md)

이번 대화의 개념·실패·사용자 수정 방향을 보존한다. 아래 발언은 의미를 요약한 것이며 원문 전체를 복사한 대화 로그가 아니다. 실제 실행 사실은 기존 ADR에 연결하고, 아래 설계 항목은 구현 완료로 취급하지 않는다.

| 대화에서 확인한 요구·질문 | v4 결정 | 상세 |
|---|---|---|
| 연결 목록을 4회 왕복한 행동을 코드에서 막아야 한다 | 같은 상태·대상의 조회 중복은 코드가 억제하고 실제 receipt를 재사용. 변화가 생긴 재조회와 구분 | [컴파일](COMPILATION_AND_SCENARIOS.md), [검증](VALIDATION_AND_ROLLOUT.md) |
| 중단 로직과 처음 세운 목표가 실제로 연결돼 있는가 | 초기 목표는 잠정 상태. 원문을 읽으며 검토 항목을 구체화하고 남은 항목·종료 이유 표시 | [개념](CONCEPT_AND_DECISIONS.md), [판단](JUDGMENT_AND_CORRECTION.md) |
| 갱신할 때마다 별도 LLM 호출을 하지 않았으면 한다 | 기존 판단 호출에서 의견을 받고 코드가 상태·표시를 갱신. 필요한 정규화만 묶어서 호출 | [통제](CONTROLLED_KNOWLEDGE.md) |
| 대통령령 위임이 명시되면 세부 내용을 확인해야 한다 | 명시 관계를 근거 있는 후보로 제시하고 필요성·미확인을 기록. 검토된 묶음 선택 후 확정 조회 | [개념](CONCEPT_AND_DECISIONS.md), [컴파일](COMPILATION_AND_SCENARIOS.md) |
| 연결 2개 정도는 자동으로 가져오되 너무 많으면 터질 수 있다 | 초기 자동 동행 제안은 이후 “확정 이동은 안 될 것 같다”는 정정 반영. 모든 관계·고정 hop 강제 이동을 최종 정책으로 채택하지 않음 | [개념](CONCEPT_AND_DECISIONS.md) |
| 최소 단위와 상위 항·조 본문에 있는 조건도 읽어야 한다 | 선택 단위와 실제 적용 상위 본문 조건을 함께 결속. 조 전체 하위 내용을 일괄 확보하지 않음 | [개념](CONCEPT_AND_DECISIONS.md), [컴파일](COMPILATION_AND_SCENARIOS.md) |
| 이 연결들이 질문에 모두 필요한가 | 관계 존재·필요성 판단·선택·실행·최종 사용을 분리. 관련됨만으로 필수 근거 승격 금지 | [판단](JUDGMENT_AND_CORRECTION.md) |
| 읽을 때 핵심 근거 여부·이유·부족·다음 행동을 판단하고 마지막에 다시 검토 | 현재 원장 활용, 중요한 판단·이견 보존, 최종 사용 원문과 실제 claim 결속 | [판단](JUDGMENT_AND_CORRECTION.md), [현재 상태](CURRENT_STATE.md) |
| 이전 판단 누락·충돌에 조심해야 한다 | revision·명시적 해결·반대 근거·CAS. 빈 목록/마지막 쓰기로 상태 삭제 금지 | [판단](JUDGMENT_AND_CORRECTION.md) |
| 토큰 상한을 메인·실험 모두 제거했다 | MAIN103과 신규 외부 실험의 출력 상한 없음 유지. 호출·시간·도구 예산과 불완전 출력 검증은 별도 유지 | [검증](VALIDATION_AND_ROLLOUT.md), [현재 상태](CURRENT_STATE.md) |
| 온톨로지를 다시 LLM이 해석해야 하면 같은 문제가 아닌가 | 자유 설명과 실행 계약 분리. 검토된 의미·입출력·의존을 코드가 조립하고 동일 구조에서 설명 | [컴파일](COMPILATION_AND_SCENARIOS.md) |
| 질문을 의도한 모양으로 처음부터 분해하기 어렵다 | 거친 요구로 시작하고 도달한 원문·개념에서 검토 지식을 확장. 완전한 초기 슬롯 채우기를 요구하지 않음 | [개념](CONCEPT_AND_DECISIONS.md) |
| 과거 path와 위임·준용·세부 내용을 조합해 묶음 설명을 제시 | 원문 중심 METHOD·관계·적용 조건으로 선택 가능한 경로 묶음 구성. 없으면 일반 탐색 | [개념](CONCEPT_AND_DECISIONS.md), [프로토타입](PROTOTYPE_DESIGN.md) |
| 공리는 단서조항·관계에 담긴 내용 아닌가 | 법률 문장과 형식 제약을 구분. 검토한 조건·적용 범위·예외는 공리/규칙 후보, 사건 의견은 관찰 | [개념](CONCEPT_AND_DECISIONS.md), [통제](CONTROLLED_KNOWLEDGE.md) |
| 설명은 탐험하면서 남겼고 사람이 수정한 내용이어야 한다 | 당시 제시한 이유·실제 실행·정정 이력에서 설명. 사후 설명은 별도 표시 | [판단](JUDGMENT_AND_CORRECTION.md) |
| 워크플로우를 조립하거나 범위·관계를 바꾼 영향을 보고 싶다 | 근거 경로, 영향 분석, 제한된 재계산을 세 단계로 구분. 모두를 법률 결론 계산으로 표현하지 않음 | [컴파일](COMPILATION_AND_SCENARIOS.md) |
| 한도 100만 원을 200만 원으로 바꾸면 영향을 한 번에 보고 싶다 | 기준 snapshot + 시나리오 overlay, 역의존·조건 평가·전후 그래프. 수치 조건만으로 전체 적법성 결론 금지 | [컴파일](COMPILATION_AND_SCENARIOS.md) |
| 실제는 100인데 200짜리를 찾았으면 제대로 수정해야 한다 | 잘못 선택한 원문·범위 결속 정정. 가정 변경 및 사건 사실 변경과 분리 | [판단](JUDGMENT_AND_CORRECTION.md) |
| 대화를 통해 지식이 축적·보완돼야 한다 | 질문은 발견 이력, 원문 판본·span이 일차 anchor. 다른 질문에서도 같은 검토 지식 재사용 | [통제](CONTROLLED_KNOWLEDGE.md), [프로토타입](PROTOTYPE_DESIGN.md) |
| 현재 구조와 함께 가능성을 봐 달라 | 기존 판단·관계·게시·평가기를 재사용하고 비활성·미연결·미구현 경계를 명시 | [현재 상태](CURRENT_STATE.md) |
| LLM 판단이 사용자에게 잘 전달되고 기록돼야 한다 | 주장·이유·실제 근거·범위·미확인·다음 행동·정정 대상을 하나의 표시와 원장에 결속 | [판단](JUDGMENT_AND_CORRECTION.md) |
| 대화는 자유롭게, 온톨로지 반영 시 제한된 형태로 | 관찰 → 정규화 후보 → 검토된 지식 → 실행. 미매핑 보존, 등록 타입·연산자만 사용, 스키마 확장은 별도 검토 | [통제](CONTROLLED_KNOWLEDGE.md) |
| 온톨로지 v4와 실제 프로토타입 설계를 저장 | 이 목차·설계·코드 근거·수용 기준을 저장. 제품 코드 변경과 실험은 이후 작업 | [v4 목차](../ONTOLOGY_V4.md), [프로토타입](PROTOTYPE_DESIGN.md) |
| 이력 수정뿐 아니라 조문 도착 후 관계를 컴파일하고 설명·목적 원문을 가져오는 것도 구현해야 한다 | 별도 필수 기능으로 명시. 수정 이력 없는 첫 조사 → 관계 회수 → 목적별 컴파일·자동 설명 → 묶음 선택 → 원문/상위 조건 확보. P2에서 독립 검증 | [조문 진입 구현 계약](SOURCE_ENTRY_COMPOSITION.md), [프로토타입](PROTOTYPE_DESIGN.md) |

수정 대화를 축적하면 검토된 범위의 지식을 보완할 수 있다. 사용자 피드백이 있다는 이유만으로 원문이 옳게 연결됐거나 지식이 완비됐다고 판정하지 않는다. 반례·예외·미확인·범위 차이와 잘못된 과거 경로도 함께 남긴다.
