# 컴파일과 변경 시나리오

[v4 목차](../ONTOLOGY_V4.md) · [프로토타입 구현](PROTOTYPE_DESIGN.md)

## 컴파일할 대상

선택한 목적·원문에 연결된 지식·현재 입력을 받아, 필요한 근거 조회와 조건 처리의 의존관계를 검사하고 실행 계획으로 만든다. 설명문을 실행 코드로 바로 번역하지 않는다. 설명과 계획은 같은 구조를 공유한다.

첫 번째 소비자는 [조문 도착 후 설명과 원문 묶음 제공](SOURCE_ENTRY_COMPOSITION.md)이다. 이력 정정·가정 시나리오 없이도 원문 anchor → 관계 합성 → 설명 생성 → 선택한 경로 실행을 수행한다. 아래 변경 영향·수치 재평가는 같은 기반의 별도 소비자다.

| 작업 | 산출물 | 법률 판단의 경계 |
|---|---|---|
| 근거 경로 조립 | 최소 원문·상위 조건을 읽는 계획 | 실제 적용 여부는 별도 |
| 영향 분석 | 변경 항목에서 이어지는 영향 후보·재검토 대상 | 영향 있음이 결과 변경은 아님 |
| 제한된 재평가 | 조건·계산의 전후 값과 실행 receipt | 원문 해석과 사건 분류가 미확인이면 최종 결론도 미확인 |

## 계획의 입력과 출력 계약 제안

입력은 지식 release/revision, 선택한 원문 anchor와 목적, 현재 typed facts, 기준 시점, 권한, 시나리오 변경, 예산이다. 임의 문서 ID나 자유 코드를 입력으로 받지 않는다.

계획에는 다음을 고정한다.

- 원문·지식·식·입력·시나리오의 버전과 hash.
- 각 노드의 역할, 입력/출력 타입·단위·개념 범위.
- 실행할 기존 capability와 확정 원문 범위, 상위 조건 결속.
- 선행 의존, 캐시/원문 재사용 조건, 해석이 필요한 중단점.
- 결과·미확인·충돌의 전파 방식과 변경 전후 대응.

현재 contracts의 STEP은 id·label·capability·after만 가진다. 노드별 typed 입출력과 결과 결속을 포함하는 실행 계획 확장이 필요하다. 기존 review-plan-v1을 실행 완료 계획으로 재명명하지 않는다.

## 조립과 실행 순서

1. 선택한 원문·목적에 맞는 검토 지식만 회수한다. 최초 질문 분해가 확정되지 않았으면 묶음을 제시해 선택하게 한다.
2. 근거 수집 관계와 계산/판단 의존관계를 분리한다. 관련됨만으로 입력 의존을 만들지 않는다.
3. 같은 개념·범위·판본·시점·단위인지 검사한다. 준용·예외·상위 조건은 등록된 합성 규칙이 있는 경우만 연결한다.
4. 의존 그래프를 구성하고 목적·관계·목표 원문·상위 조건·종료 기준에서 실행 전 설명을 생성한다. 중복 원문은 합치되 조건·정정 이력은 지우지 않는다. 실행 DAG의 순환은 자동 반복하지 않고 설명 가능한 미실행 블록으로 남긴다.
5. 최초 근거 조립에서는 선택한 계획의 원문 조회를 실행한다. 변경 시나리오에서는 변경된 노드에서 역방향 의존 색인으로 후속 노드·사용한 답변을 찾는다. 권한과 선택 지식 범위 내 결과이며 전역 완전성을 주장하지 않는다.
6. 유효한 기존 원문/결과를 재사용하고 새로 필요한 조회·변경 입력에 의존한 평가만 수행한다. 의미 해석 노드는 재검토 후보로 분리한다.
7. 결과·미실행·미확인·실패를 저장한 뒤 같은 계획으로 그래프와 설명을 만든다. 응답 실패 후 다른 계산 결과를 이전 결과에 이어 붙이지 않는다.

## 100만 원에서 200만 원으로 변경

다음은 합성 예다. 실제 법률·업무 한도를 뜻하지 않는다. 규칙의 의미를 단순히 한도라는 이름으로 추정하지 않고, 여기서는 **지출액이 지원 한도 이하인가**로 명시한다.

~~~text
원문 연결 기준값: 지원 한도 = 1,000,000 KRW
사건 입력: 지출액 = 1,500,000 KRW
조건식: 지출액 <= 지원 한도
시나리오 변경: 같은 지원 한도 필드 = 2,000,000 KRW
~~~

| 상태 | 한도 | 금액 | 조건 결과 | 표시 |
|---|---:|---:|---|---|
| 현재 기준 | 100만 원 | 150만 원 | FALSE | 이 수치 조건 미충족 |
| 변경 시나리오 | 200만 원 | 150만 원 | TRUE | 이 수치 조건 충족 |
| 입력 부족 | 200만 원 | 미확인 | UNKNOWN | 금액 확인 필요 |

이 비교만으로 지원 대상·증빙·예외까지 충족했다고 결론 내리지 않는다. 후속 판단에 다른 조건이 있으면 함께 표시한다. 변경 영향 화면은 한도 노드와 비교 노드, 그 결과를 사용하는 후속 판단만 강조하고 영향받지 않은 원문은 유지한다.

기존 MAIN103의 evaluate 함수로 위 비교 세 가지를 단위 확인할 수 있다. 전후 그래프 저장·대화 정정·UI·Oracle 연결까지 검증된 것은 아니다. 재현 방법은 [검증 문서](VALIDATION_AND_ROLLOUT.md)에 둔다.

## 규정 조회를 잘못한 경우

실제 대상은 100만 원 규정인데 시스템이 다른 대상의 200만 원 규정을 골랐다면 source binding 오류/잘못된 선택을 바로잡는다. 기존 200 값을 100으로 덮어써 같은 원문의 내용처럼 만들지 않는다.

올바른 원문·개념·대상 범위를 새 결속으로 저장하고, 잘못된 결속을 사용한 조건식·해석·답변을 재검토한다. 기존 결과는 이전 revision의 결과로 남긴다. 다른 대상에서는 200만 원 규정이 유효할 수 있으므로 정정의 범위를 전체 데이터로 확대하지 않는다.

## 법령 근거를 묶는 경우

실험의 제97조 자본적지출액 분기에서는 범위 위임 → 시행령 제163조 제3항의 구체화 → 선택 범위에 적용되는 상위 본문 조건을 묶는다. 이 경로의 끝은 원문과 조건의 확보다. 특정 지출의 해당 여부까지 코드가 판단했다는 뜻이 아니다.

금액 비교와 달리 자연어의 준용·예외 적용은 정형화되지 않은 부분이 남을 수 있다. 그 부분은 원문·기존 의견·사용자 사실을 전달하는 명시적 검토 단계로 둔다. LLM이 제안한 새로운 경로는 후보이며 현재 실행에서 확인된 범위를 넘어 공유 공리로 자동 승격하지 않는다.

## 의미와 계산의 분리

| 상태 | 의미 | 후속 처리 |
|---|---|---|
| TRUE/FALSE/VALUE | 고정한 입력과 식의 평가 결과 | 결과를 소비하는 노드로 전달 |
| UNKNOWN | 미입력·단위 불일치·지원하지 않는 계산 등 | 부족 원인 보존; FALSE로 대체 금지 |
| CONFLICT | 동일 범위에 서로 양립하지 않는 사실/해석 | 양쪽 근거 유지, 자동 합산/선택 금지 |
| 검토 필요 | 자연어 적용·예외 우선순위 등 미형식화 | LLM/사람 검토 후 새 판단 revision |
| 실행 실패 | 도구·저장·연결 실패 | 미확보와 부재를 구분하고 부분 결과 보존 |

위 표의 설명 상태들은 개념 설계다. 기존 enum과 새 실행 계약의 매핑은 구현 시 명시한다. 형식적으로 닫힌 지원 범위만 실행하며 자유 텍스트에서 조건식을 그때그때 암묵적으로 생성하지 않는다.

## 변경·복원·캐시

시나리오는 기준 지식과 입력 snapshot에 변경분을 얹는다. 기준 지식이 바뀌면 기존 시나리오를 그대로 최신 상태로 표시하지 않는다. 이전 기준으로 재현하거나 차이를 검토해 새 시나리오 revision을 만든다.

결과 재사용 키에는 지식/식 버전, 원문 판본, 실제 의존 입력, 권한 범위, 시점, 시나리오를 포함한다. 의존관계가 수정되면 역색인과 결과 캐시를 함께 무효화한다. 무효화를 계산할 수 없으면 결과를 오래된 것으로 표시하고 현재 기준으로 다시 실행한다.

공유 결과 캐시와 영속 시나리오는 서빙 밖의 데이터 계층에 둔다. 로컬 프로토타입의 작은 합성 저장소를 GENOS 배포 구조로 설명하지 않는다.
