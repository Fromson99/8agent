## 구축 결정 반영 — 2026-10-24 (최신)

- MAIN 반영은 [구축 순서](BUILD_PLAN.md)의 **단계 1·2(판단 기록 통합, 재지시·턴 분류)를 묶어 먼저** 하고, 단계 3 이후는 그 뒤에 반영한다. 아래의 "운영은 통합 전환" 문구는 이 반영 묶음 단위로 읽는다.
- 순서: 단계 1·2 구현과 코드 검사 → ADR 선점 → 샘플 13문항을 현행 Qwen3.8(Parasail FP8, reasoning none, fallback 없음)로 실행 → MAIN 반영. CM·risk_cm 자료는 2026-10-24 반출 승인을 받았다. 기준답변·판정은 평가 쪽에서만 쓴다.
- 샘플은 이미 알려진 질문이라 ADR은 `in_sample=true`, `decision_eligible=false`다. `rag_main_promotion`은 Accepted·decision-eligible·out-of-sample만 받으므로, MAIN 반영은 MAIN103처럼 사용자 지시 전환(`USER_DIRECTED_CUTOVER`, `quality_certified=false`)으로 한다.
- 단계 1·2의 필수 검사는 [멀티턴 확인 시나리오](MULTITURN_LEGAL_AGENT.md#확인할-시나리오)다. 최소 한 검사는 실제 `/v1/rag/ask` 또는 `service.py` 진입점으로 한다.
- 스키마 확장의 시뮬레이션(형식·변환 손실·저장 기록 재생·골드 규약)은 모델 호출 없이 한다. 모델 호출이 필요한 품질 비교는 별도 ADR이다.

## 성능 입증과 기능 검증의 분리 — 2026-10-24 후속

[성능 주장의 검증 설계](PERFORMANCE_EVIDENCE_PLAN.md)는 벡터 진입 적중과 후속 근거 묶음 확보, 모델 교체와 구조 효과, 문서 추출과 사용 중 축적, 같은 교정의 메모/온톨로지 재사용, 조건 변경 영향을 구분한다. 강한 검색·반복 조사·명시 참조 그래프·대형 모델·동일 피드백 메모를 기준군으로 포함한다. 아래 기능 수용 검사가 통과하더라도 이 비교 성능이 입증된 것은 아니다.

원문·위키·온톨로지의 같은 정보를 공유한 통제 비교와 전체 제품 전략 비교를 별도로 보고한다. 알려진 실패 사례는 개발 진단으로, 새 조문 가족·새 사건 질문은 독립 평가 또는 명시적 전이 평가로 구분한다. 구체 모델/예산·표본·수치 기준·실행 버전은 후속 ADR에서 동결하며 현재 문서는 실행 준비 완료 manifest가 아니다. “벡터 불가능”, “비법률 모델이라 실패”, “온톨로지의 현실 인과 예측”을 결론으로 선결하지 않는다.

## 정상·실패 검사의 최소 묶음

아래 검사는 단계 1~8 전체의 목록이다. 단계 1·2에서 반드시 할 것은 [멀티턴 확인 시나리오](MULTITURN_LEGAL_AGENT.md#확인할-시나리오)이며, 원문 정정·시나리오·값 변경 항목은 단계 4~8에서 한다.

| 검사 | 관찰할 결과·필수 보존 |
|---|---|
| 멀티턴 분기·선택·정정 | 첫 턴의 부분 답·미확인·경로 안내·기록, 후속 선택에서 같은 case/표시 revision·원문 재사용, 변경 영향만 갱신 |
| 명확한 단일 경로 | 필요한 조회를 수행하며 모든 원문 읽기를 사용자 선택 대기로 바꾸지 않음 |
| 미읽은 대상·미확인 목적지 | 실제 원문 요약/조사 목적 안내/탐색 과제 구분, 가짜 대상 본문·조항 번호 없음 |
| 당시 행동과 사후 권장 | 당시 이유 미기록을 생성으로 채우지 않음, 실제 receipt와 사후 검토 구분 |
| 정상 턴 반환과 실패 | 사용자 선택 대기는 정상 부분 결과, 권한·무결성 실패는 별도 실패. 원문만 확보한 경우 법률 결론을 만들지 않음 |
| 같은 요청 재개와 새 턴 | 같은 요청은 deadline/누적 예산 유지. 새 사용자 요청도 사건 누적 사용량·동일 실패 한도 보존 |
| 그래프 없는 채팅 | 텍스트/표와 자연어 선택으로 동일 상태·후속 행동 전달 |
| 값 변경의 새 분기 | 알려진 비활성 경로 활성화, 미등록 관계는 조사 후보, 지급액/지출액 혼동 없음 |
| 조문 첫 방문·이력 없음 | 원문 A 도착 → 위임/세부 범위/상위 조건 묶음 제시 → 선택 → B와 적용 본문 확보, 무관 C 제외 |
| 자동 설명과 실행 동일성 | 실행 전 설명·선택 ID·도구 대상·결과 묶음이 같은 plan revision에 결속. 실행 예정과 확보 완료 구분 |
| 확정 경로의 조립·실행 | 기본 설명·중간 조회마다 새 LLM 호출을 하지 않음. 최초 목적 선택과 새 의미 분기 판단은 별도 계수 |
| 경로 없는 조문·목적지 다중 후보 | 원문 관계/묶음 없음 또는 미확인으로 표시하고 기존 직접 탐색을 사용. 목적 조항 번호를 생성해 실행하지 않음 |
| 지원 한도 <= 비교 | 150만 원 입력에서 한도 100→200이면 FALSE→TRUE. 조건식·단위·입력 hash 남음 |
| 조건 의미 반례 | 같은 한도 이름이라도 >= 승인 기준이면 효과가 달라짐. 이름만으로 연산자 추정 금지 |

| 시나리오 변경 | 원본 Gold/head 불변, scenario overlay·결과 별도 저장 |
| 상위 조건·예외 | 선택 호의 상위 본문 조건을 반영. 관련 없는 다른 호는 필요성 판단 없이 자동 확장하지 않음 |
| 범위·판본·시점 다름 | 다른 상품·대상·기간의 같은 금액을 병합하지 않음. 개정 판본은 기존 이력과 분리 |
| 임의 타입·연산자·근거 ID | 형식/원문 검증(시뮬레이션)에서 실행·적재 차단, 원래 후보와 원인 유지 |
| 행동 검증 실패·판단 보존 | 원문과 제안 보존; 유효성 검사 전 제안을 승인 상태로 남기지 않음 |
| 이전 판단·부족·이견 누락 | 새 빈 목록으로 삭제되지 않음. 해소는 대상 ID·이유·근거 필요 |
| 동시 수정·stale 화면 | expected revision/view hash 충돌. 최신 기록과 사용자 제안 모두 보존 |
| 저장 성공 후 응답 유실·중복 요청 | 같은 operation ID에서 같은 receipt, 중복 revision/계산 없음 |
| 순환·동일 상태 반복 | 유한한 계획 검사·중복 억제. 순환 블록은 미실행 이유 표시 |
| 권한 철회·원문 hash 변경 | 해당 근거/결과 재사용 거부, 접근 불가 내용·숨은 노드 수 노출 금지 |
| 도구 실패·시간/호출 예산 소진 | 미확보를 부재로 처리하지 않음. 부분 성공·실패·재개 가능 상태 분리 |
| 재개·저장 재로드 | 누적 사용량·deadline·원문/지식 binding·실패 이력 유지 |
| 화면·답변 소비자 | 표시 revision이 저장 원장 및 실제 계산 결과와 일치; 실패한 전송을 완성 답변으로 확정하지 않음 |
| 다른 질문의 재사용 | 같은 원문 검토 지식은 회수하되 이전 질문의 사실·결론은 정답으로 복사하지 않음 |

최소 한 묶음은 실제 /v1/rag/ask 또는 service.py와 같은 선택 코드·pin을 사용하는 API 연결로 수행한다. 신규 UI는 router·service factory·권한·저장과 연결한 왕복 검사까지 한다. 함수별 mock 검사만으로 전체 연결 완료 처리하지 않는다.

[조문 진입 전용 검사](SOURCE_ENTRY_COMPOSITION.md)의 첫 방문·목적 경로·상위 조건·설명/실행 일치를 P2 완료 조건으로 둔다. 이력 정정과 조건 변경을 모두 시험했어도 이 검사가 빠지면 v4 프로토타입 완료가 아니다.

2026-10-24부터 P2에는 [멀티턴 수용 기준](MULTITURN_LEGAL_AGENT.md)의 정상 턴 반환·후속 선택도 포함한다. P5는 API·저장·발행·UI·후속 요청을 같은 계약으로 결속한 통합 전환/롤백 검사다. 이번 문서 작업은 이 검사들을 실행하지 않았다.

## 복구 책임과 한도 제안

[에이전트 실패 복구 정책](../../OPERATIONS/AGENT_FAILURE_RECOVERY_POLICY.md)을 적용한다. 아래는 신규 단계의 제안이며 기존 총 호출·도구·시간 예산 안에 들어가야 한다.

| 실패 종류 | 복구 담당 한 곳 | 허용 복구와 최종 상태 |
|---|---|---|
| 개념 묶음 LLM 출력의 구문·스키마·ID | 개념 묶음 작업(`bundling`) | 같은 입력·오류로 1회만 다시 요청. 그래도 실패하면 그 anchor들은 처리하지 않은 채로 두고 워터마크를 넘기지 않음. 실패 기록 보존 |
| S3 쓰기 실패·`HEAD.json` 예상 revision 불일치 | 작업 폴더 포트(`store`) | 쓰지 않고 최신 내용을 화면에 보여줌. 새 revision 파일은 이미 있으면 덮어쓰지 않음 |
| 적재 SQL 실행 실패 | 사람(GENOS) / `load-local`(로컬) | 상태는 `MAPPED`로 남김. 실패 내용을 적재 기록에 남기고 `LOADED`로 바꾸지 않음 |
| 골드 조회 매핑과 실제 표 불일치 | 골드 조회 포트(`gold_reader`) | 그 묶음을 쓰지 않고 기존 조사로 진행. 불일치를 서비스 상태 확인에 표시 |
| 재지시 대상 불명·불가능 | 턴 분류·실행(`corrected_memory`·`completion_execution`) | 지시별 "불가능함(이유)" 보고, 나머지 지시는 실행. 재시도 없음 |
| 새 의미·관계·적용성 불확실 | 검토/정정 단계 | 근거와 이견 제시. 기계적 모델 재호출로 승인하지 않음; 현재 답변·확보 원문은 유지 |
| 계획 타입·순환·입력 결속 | compiler | 결정적 검사, 자동 의미 보정 0회. 해당 블록 미실행/검토 필요; 무관한 유효 부분 보존 |
| 전송·도구 일시 실패 | 기존 실행 gateway | 기존 허용 재시도와 총 예산 재사용. 상위 service/normalizer가 중복 재시도하지 않음 |
| 저장 outcome 불명 | application operation 관리자 | 같은 operation ID 조회. 결과 불명이면 미확인 표시; 새 ID로 재작성하지 않음 |
| stale/CAS·권한·hash 오류 | 저장/참조 검증 계층 | 쓰기·해당 재사용 거부. 최신 상태 재조회 또는 접근 불가. 모델 보정으로 우회 금지 |

허용된 결정적 보정도 원래 제안·보정 이유를 남기고 전체 검증을 다시 한다. 재개해도 기존 예산·deadline·동일 실패 횟수는 초기화하지 않는다. 실패한 지식 게시가 RAG 전체 원문 전달을 막지 않도록 단계 결과를 분리한다.

## 기존 계산기의 작은 단위 확인

다음은 선택 MAIN103의 기존 함수를 그대로 불러오는 합성 단위 확인이다. 실제 법률 근거·새 모델 호출·전체 검색 데이터 로딩·Oracle 접속은 없다. 이 확인은 그래프 컴파일러나 프로토타입 구현 검증을 대신하지 않는다.

저장소 루트 /home/jin/8-AGENT에서 실행한다. 아래 script의 출력은 [UNIT_CHECK.json](UNIT_CHECK.json)에 기록한다.

~~~python
import json
import sys
from pathlib import Path

root = Path.cwd()
selected = root / "08_DEPLOYMENT/RELEASES/output-unlimited-20261023-r1/code/02_BACKEND"
sys.path.insert(0, str(selected))
from lawrag.legal_knowledge import ontology

assert Path(ontology.__file__).resolve().is_relative_to(selected.resolve())
expression = {"op": "lte", "args": [{"field": "amount"}, {"field": "limit"}]}

def fact(value):
    return {"status": "ASSERTED", "origin_ref": "synthetic-unit-check",
            "value": {"type": "money", "value": str(value), "unit": "KRW"}}

cases = [
    ("base", {"amount": fact(1500000), "limit": fact(1000000)}, "FALSE"),
    ("scenario", {"amount": fact(1500000), "limit": fact(2000000)}, "TRUE"),
    ("missing", {"limit": fact(2000000)}, "UNKNOWN"),
]
results = []
for name, facts, expected in cases:
    result = ontology.evaluate(expression, facts, binding={"scope": "isolated-synthetic-unit-check"})
    assert result["status"] == expected, (name, result)
    results.append({"case": name, "expected": expected, "result": result})
print(json.dumps({"kind": "existing_function_synthetic_unit_check",
                  "module": str(Path(ontology.__file__).relative_to(root)),
                  "model_calls": 0, "results": results}, ensure_ascii=False, indent=2))
~~~

## 품질·비용·자원 측정 설계

| 구분 | 기준 |
|---|---|
| 실측 | ADR-1037 알려진 질문 1개: 호출 7, 입력 214,852토큰, 서비스 264.935초, 최대 RSS 약 3.11GiB. 새로운 방식의 기준 성능·일반화 인증으로 사용하지 않음 |
| 계산 가능 | 고정 식/입력의 전후 결과, 실행 노드 수·의존 경로·중복 억제 수, 호출/토큰/지연/저장량 합계 |
| 가정 | 같은 원문·조건을 다시 사용하는 요청이 있고 일부 지식이 검토된 형식으로 축적된 경우 경로 재사용 가능 |
| 목표 | 정정 대상 오류·원문/판본 불일치·상태 유실·무권한 소비 0. 다른 질문 재사용·부족 보존·전후 비교를 검증 |
| 미확인 | 질문별 검색 비용 감소, 법률 정답률·필수 근거 회수 개선, 개념 묶음 작업 성공률, 사람 검토 시간, 실제 Oracle/GENOS 지연 |

호출 수만 줄어도 입력이 길어지거나 개념 묶음 작업·검토 비용이 늘 수 있다. 요청별 비용은 기존 조사 + 지식 조회 + 개념 묶음 작업 + 검토/보정 + 실행/저장으로 분리한다. 재사용 1회당 절감액을 S, 추가 조회/검증비를 L, 구축·정규화·사람 검토비를 K라 하면 S > L일 때만 누적 N회에서 N × (S − L) > K를 손익분기 조건으로 본다. 사람이 쓰는 시간과 모델 비용은 별도 보고하며 필요할 때 명시한 단가로 환산한다. 현재는 S·L·K·N을 측정하지 않아 절감률이나 기간을 제시하지 않는다.

품질 측정은 근거 일치, 필요한 근거 회수, 부족/이견 보존, 정정 전후 일관성, 설명과 실행의 일치를 나눠 평가한다. 등록된 지식이 적어 생긴 coverage 부족과 잘못된 컴파일·상태 보존 오류도 분리한다. 원문 검증 통과를 법률 정답률로 보고하지 않는다.

사용 중 축적은 문서 단독 추출과 비교할 경우 같은 원문·사용 목적·평가 기준을 호출 전에 고정하고, 피드백을 받은 사례와 독립 평가 사례를 분리한다. 멀티턴 평가는 요청 하나의 호출 감소뿐 아니라 사례 전체의 완료·추가 턴·누적 비용·사람 검토 시간·불필요한 선택 요구를 측정한다. 결과를 다음 턴으로 넘긴 것만으로 품질/효율이 개선됐다고 판정하지 않는다. 아직 새 방식의 품질·비용 수치는 미산정이다.

자료·인덱스 전체를 동시 로딩하지 않는다. 무거운 실행은 한 개씩 수행하고 시작 전 디스크·RAM·swap·기존 프로세스를 기록한다. 현재 지식 bundle의 128개/깊이 16, 식의 깊이 8/노드 64 같은 한계를 참고해 프로토타입의 그래프·시간·메모리 한도를 호출 전에 동결한다. 제한을 넘으면 전체 영향으로 표시하지 않고 미완료 범위와 continuation을 남긴다. RAM 여유·swap 압박의 중단 기준도 실행 명세에 명시한다.

출력 토큰 상한은 재도입하지 않는다. MAIN103·신규 외부 실험의 max_output_tokens=null과 실제 요청의 상한 필드 생략 정책을 유지한다. 전체 호출·도구·시간 예산, 서버 자체 한도 및 불완전 출력 검증은 별개다. 판단 표시 갱신은 코드가 하고 정규화가 필요한 후보만 추가 LLM 호출을 사용한다.

## 도입과 복원

1. 기존 작업 코드·선택 MAIN·후보 차이와 실제 호출 진입점을 기록한다. 작은 fixture와 계약 검사로 [구축 단계](BUILD_PLAN.md#단계) 순서대로 구현한다.
2. 기본 비활성의 통합 후보에서 단계별 개발·검사를 수행하고 factory·권한·에이전트 레이어/S3/골드 저장 포트를 명시적으로 주입한다. 운영 활성화는 반영 묶음(단계 1·2 먼저) 단위로 하며, 묶음 안의 조사 제어·턴 원장·발행·화면·후속 재개는 동일 계약으로 묶는다. 개별 개발 flag를 사용자에게 혼합 계약을 노출하는 수단으로 사용하지 않는다.
3. 현재 지식 계약은 계속 읽고 신규 계약은 지원 소비자에서만 사용한다. 필요한 원문/개념/의존 색인만 새 버전으로 구축하고, 과거 답변이나 실패 경로를 일괄 승인 지식으로 바꾸지 않는다.
4. 서비스·표시·저장·복구를 같은 코드와 pin으로 검증한다. 실모델/프롬프트/검색 효과 비교는 실험 표준의 ADR 선점·동결·후보 격리·역할 분리·최종 validate/graph를 별도 적용한다.
5. MAIN 반영 요청이 있을 때는 승격 계약, 명시적 plan/apply, 선택 포인터와 실제 로컬 service binding을 확인한다. 세부 의미 판단 오류와 심각한 인용·권한·상태 결함을 구분하며 과거 품질 우회를 재사용하지 않는다.
6. 실패 시 코드·계약·프로필·골드 조회 매핑(`ONTOLOGY_GOLD_MAPPING.json`) 선택을 호환 가능한 이전 조합으로 함께 복원한다. 진행 요청은 시작한 binding을 유지하거나 명시적으로 중단/이행한다. 생성된 턴·후보·정정·시나리오·실패 receipt는 삭제하지 않고 읽기 가능한 버전으로 보존한다. 구 소비자가 새 상태를 해석하도록 강제하지 않으며 복원 상태에서도 중복 operation 조회가 가능해야 한다.
7. GENOS 반입·리비전 배포·워크플로우 화면 검증은 별도 수행한다. 로컬 성공을 GENOS 검증 완료로 보고하지 않는다.

2026-10-24 구축 결정 반영의 문서 검사는 [VALIDATION_BUILD_PLAN_20261024.json](VALIDATION_BUILD_PLAN_20261024.json)에 있다.

이번 작업은 설계 저장·코드 근거 확인·문서 검증이다. 독립 검토나 성능 인증은 하지 않았으며 작성자가 경로·상태 구분·계약 일관성을 자체 확인했다. [VALIDATION.json](VALIDATION.json)은 2026-10-23 기록으로 보존한다. 2026-10-24 변경은 [VALIDATION_MULTITURN_20261024.json](VALIDATION_MULTITURN_20261024.json)에 문서·링크·지문 보존과 미실행 범위를 별도로 기록한다.
