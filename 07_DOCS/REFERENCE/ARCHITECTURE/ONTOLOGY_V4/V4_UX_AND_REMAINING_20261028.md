# v4 재대조 — 검토 UX 보완과 시각화 외 남은 구현

**최신 화면 r4 — 표형 기록:** 모인 기록·검토 목록과 선택한 조사 판단을 표로 정리했다. 행 선택 후 상세에서 기존 초안 생성·사람 승인으로 이어진다. [r4 구현·검증과 남은 과제](APPLICATION_READINESS_20261028.md). 아래 r3는 3단계 연결 당시 기록이다.

**최신 사용자 요청 r3:** 승인만 보이던 r2에서 모인 기록 확인·초안 생성 진입점을 복원했다. `사람 기록 선택 → 사람 생성 시작 / LLM 초안 작성 → 사람 검토·승인`의 3단계이며 그래프·재지시·가정 비교·JSON 편집은 복원하지 않았다. 현재 읽는 대상은 기존 온톨로지 준비함이고 전체 숏컷 자동 수집·병합은 별도 과제다. [r3 구현·검증](APPLICATION_READINESS_20261028.md)

**최신 사용자 정정:** 복잡한 기능을 빼고 승인만 이해할 수 있게 하라는 요청에 따라, 실제 UI는 목록·내용/원문·승인/반려·골드 후속 안내의 한 화면으로 축소했다. 아래 시각화·확장 UX는 과거 설계로 보존한다. [현재 적용 상태](APPLICATION_READINESS_20261028.md) · [r2 설치 안내](../../../../08_DEPLOYMENT/DATAIKU/ontology_dashboard_20261028_r2/GUIDE.txt)

**최신 잔여 목록:** [첫 실제 적용 / 반복 축적 / v4 확장으로 나눈 적용 계획](APPLICATION_READINESS_20261028.md)을 따른다. 실제 화면 구현의 제한, 영속 이관 원장·골드 적재/검증/전환·GENOS 소비 연결과 최신 ADR1178의 001 통과/007 미완성/009 미실행을 반영했다. 아래 1175 대조와 시안 API 검토는 당시 기록이다. 최종1178 수정 후 실모델 재검증·MAIN 반영은 완료되지 않았다.

**후속 2026-10-28 — 대시보드 구현:** [Dataiku 설치 안내](../../../../08_DEPLOYMENT/DATAIKU/ontology_dashboard_20261028_r1/GUIDE.txt) · [검증 기록](../../../../09_ARTIFACTS/AUDITS/20261028-ontology-dashboard/VALIDATION.json). 별도 요청으로 native Streamlit 검토 대시보드와 기존 관리 앱 진입점을 연결했다. 관계도 선택·원문·이전 작업 판본 비교·내용 승인·이관 요청 자료 저장을 구현했고, 새 화면/기존 워크플로 41검사와 Chromium 선택 왕복을 확인했다. 골드 SQL 적재·사용 전환, 재지시 실행, 실제 가정 계산 엔진은 여전히 후속이다. 합성 데이터 로컬 실행과 현장 Dataiku 설치를 구분하며 MAIN112는 유지했다. 아래 본문은 이 구현 이전의 설계·잔여 목록이다.

작성일: 2026-10-28. 범위: v4 설계 재검토, 설명용 시안 수정, 현재 코드/선택 릴리스 대비 잔여 기능 확인. **제품 코드·MAIN·데이터·모델 실행·현장 배포 변경 없음.**

기준 선택은 MAIN112 `vector-initial-20261028-r1`이다. 이번에 확인한 온톨로지 작업 모듈 10개와 관련 조사·메모리 모듈 6개는 작업 코드와 선택 코드가 같았다. 격리 ADR1173/1175 수정은 MAIN112의 현행 기능으로 합산하지 않았다. v4 본문에 남은 MAIN103 시점의 미구현 표와 호출·시간 예상치는 현재 상태로 재사용하지 않는다.

이 문서는 [상세 Streamlit·골드 설계](STREAMLIT_DATAIKU_GOLD_UI_DESIGN_20261028.md)를 보완한다. 내용 승인과 표준·모델 승인은 별개이며, 승인 후 골드 매핑·적재·검증·사용 전환 절차는 그대로 유지한다.

## 1. v4를 다시 보고 보완한 사용자 경험

v4의 핵심은 원문에 붙은 지식을 재사용하면서, 그 지식을 만든 판단과 아직 못 본 범위를 설명하고 사용자가 특정 부분을 고칠 수 있게 하는 것이다. 이전 화면은 승인·적재 상태를 잘 보여주지만 **연결 이유, 조건·예외의 공통 요소, 변경 영향, 정정 대상**이 약했다.

| UX | 기존 시안·현재 결과 | 이번에 반영한 시안 | 제품 연결 시 종료 조건 |
|---|---|---|---|
| U01 원문 중심 관계도 | 원문과 제안이 두 글상자여서 어느 항목이 어떤 원문에 기대는지 한눈에 보기 어려움. 사용성 실측은 없음 | `원문 → 검토 요소 → 업무 경로` 구조, 노드 선택과 우측 상세 동기화 | 모든 선이 실제 basis/requires/path 멤버십 또는 검증된 관계 ID로 설명됨 |
| U02 변경 위치 확인 | 수정이라는 라벨만 있고 변경 대상과 원문 대응이 약함 | `전체 / 이번 변경 / 미확인` 강조, 선택 노드의 r1→r2 차이 표시 | 동일 안정 ID의 변경 전후를 비교. 좌표/문자열 유사성으로 다른 항목 병합 금지 |
| U03 미확인에서 다음 검토로 | 미확인 설명을 읽은 뒤 다시 대상을 찾아야 함 | `다음 미확인 보기`, 대상 미확정/본문 미열람/판단 보류 구분 | 숨겨진 원문·번호를 만들지 않고 실제 미확인 항목에 초점 이동 |
| U04 성립·예외 경로 비교 | 전체 조립 텍스트는 있으나 공통·추가 구성요소가 잘 드러나지 않음 | 복수 경로 선택과 필요한 조건/추가 조사 표시 | 시나리오 ID와 필요 원문·공통요소가 실제 조립 패키지와 일치 |
| U05 발견과 판본의 계보 | 승인 이력은 있지만 다른 질문의 관찰이 어떻게 합쳐졌는지 약함 | 질문 관찰→원문·개념 묶음→새 판본의 계보 표시 | 관찰마다 run/request/판단ID/revision·주체·실제/재생 구분 |
| U06 대상 고정 재지시 | 자유 의견만 있어 무엇을 다시 읽을지 대상이 흐려짐 | 별도 `조사·재지시`에서 J 항목을 다음 요청 초안에 담음. 실제 실행은 비활성 | 동일 세션·표시 hash·판단 revision에 결속한 명령만 실행 |
| U07 가정과 정정 분리 | 조건 변경 효과를 미리 볼 화면 없음 | 별도 합성 가정 비교: 한도 100→200, 금액 150, UNKNOWN 처리, 영향 경로 | 실제 구현은 typed input/식/단위/원문·시나리오 판본 결속. 골드/기존 판단 불변 |
| U08 그래프 대체 보기 | 그래프를 이해하거나 조작하기 어려운 사용자를 위한 경로 없음 | 같은 항목의 표 보기와 버튼 선택, 작은 화면에서는 세로 목록 | 그래프 없이도 근거·상태·정정 대상을 동일하게 확인 |

이번 UX 시안의 도식·이력·승인·관찰은 합성 예시다. CM001은 업무 맥락 식별에만 사용하며 새로운 법률 결론·인용문을 만들지 않았다. 가정 비교는 v4 문서의 합성 산술 예시이고 실제 업무 조건 변경 엔진이 아니다.

### 현재 데이터로 바로 그릴 수 있는 것과 새로 필요한 것

현재 `schema.published`의 snapshot에는 `relations=[]`, `evidence_judgments=[]`, `glossary_ref=None`이 들어간다. 반면 사전 조립 레시피에는 `components[].basis`, `requires`, `paths`가 있다. 따라서 먼저 그릴 수 있는 것은 **인용 근거·구성 의존·경로 포함 관계**다. 이를 위임·준용·법률상 예외가 승인된 의미 관계 그래프로 바꾸어 그리면 안 된다.

| 연결 종류 | 현재/제안 데이터 | 표시·행동 |
|---|---|---|
| 근거 인용 | 현재 `basis.source/quote` + 원문 anchor | 인용 구절·정확한 판본을 펼침 |
| 구성요소 의존 | 현재 `requires` | 선행 요소가 필요한 이유와 소비 경로 표시. 법률상 위임으로 재명명하지 않음 |
| 경로 포함 | 현재 paths의 conditions/calculations/outcomes/notes | 해당 목적의 조립 결과를 미리 봄 |
| 명시 참조·법률 관계 | 기존 원문 연결 원장 또는 별도 승인된 relation record 필요 | 연결 타입·근거·방향·출발/대상 판본이 있을 때만 의미 관계로 표시 |
| 판단·재지시 계보 | 현재 저널의 일부 기록 + 추가 관찰/영구 ID 계약 필요 | 당시 이유·사후 제안·실행 결과를 구분 |
| 미확인 조사 후보 | 대상 미확정 또는 미열람 상태 | 본문 대신 조사 목적·부족 사유. 확정 계획과 분리 |

시안은 선을 실선/점선과 설명으로 구별하고 선택 상세에 `연결 의미`를 둔다. 제품 첫 구현에서는 edge 종류를 선택할 수 있는 관계 목록도 함께 제공한다. 많은 노드를 처음부터 펼치지 않고 현재 개념 묶음·선택 경로만 표시한다. 권한 밖 노드 수·문서명은 요약 집계에서도 노출하지 않는다.

## 2. 화면 동선과 정보 밀도

기존 관리 앱 안에서 `검토함 → 개념 검토 → 골드 이관 → 게시·사용`의 주 흐름을 유지한다. `조사·재지시`와 `가정 비교`는 상세의 보조 화면이다. 시안에서는 차이를 쉽게 비교하도록 위쪽 탐색에 노출했다. 최종 Streamlit 메뉴는 주 흐름을 우선하고 보조 기능은 해당 대상에서 연다.

개념 검토의 읽는 순서:

1. 개념·작업 판본·현재 사용 판본·다음 할 일 확인.
2. 관계도에서 현재 경로와 미확인 위치 확인. 선의 수를 지식 품질 점수로 쓰지 않음.
3. 노드 선택 → 근거·당시 기록·다음 검토 → 같은 항목의 변경 전후.
4. 성립·예외 경로의 공통 근거와 추가 조사를 비교.
5. 필요한 수정만 저장하고 전체 조립본을 확인한 뒤 내용 승인.
6. 골드 이관함에서 준비 상태에 따라 기존 모델 재사용 또는 새 모델 신청.

사용자에게 보이는 판단 이유는 실제 제출된 설명이다. 내부 추론이라고 부르지 않으며, 없으면 `당시 사유 미기록`이다. 다른 검토자가 뒤에 쓴 의견은 `사후 검토 제안`으로 표시한다. 읽음/선택됨/모델 입력 전달/답변 사용/사람 승인/골드 적재는 서로 다른 사건이다.

`그거 빼`는 이번 답의 근거 제외, `관계 정정`은 검토 지식의 변경 제안, `한도를 바꾸면`은 가정 시나리오다. 화면에서 이 행동들을 하나의 편집 버튼으로 묶지 않는다. 사용자 정정은 같은 세션에 먼저 적용하고 공유 골드는 별도 검토·이관 절차를 거친다.

## 3. Streamlit에서 구현할 방식

원문·항목표·변경 비교는 기존 Streamlit 기본 요소로 구성한다. 관계도는 `st.plotly_chart`의 노드 point selection을 사용하고, 선택 ID를 동일 항목표·상세 패널에 전달하는 안을 우선한다. 선 선택은 별도 관계 목록을 사용한다. raw HTML의 브라우저 callback만으로 서버 승인 상태를 쓰지 않는다.

Streamlit 1.50의 `on_select`와 point selection API는 확인했다. `graphviz_chart`의 정적 표시를 Python 클릭 이벤트가 있는 것처럼 설명하지 않는다. 저장소 requirements는 현재 Streamlit만 고정하므로 Plotly의 검증 버전·망분리 wheel 반입은 구현 단계에서 추가해야 한다. 이 시안은 외부 라이브러리 없이 HTML/SVG와 로컬 상태로 상호작용을 설명한다. [Streamlit 1.50 Plotly API](https://docs.streamlit.io/1.50.0/develop/api-reference/charts/st.plotly_chart), [Graphviz API](https://docs.streamlit.io/1.50.0/develop/api-reference/charts/st.graphviz_chart).

제안 화면 투영 계약은 다음과 같다. 기존 영속 스키마에 필드를 바로 추가한 것이 아니다.

| 항목 | 내용·검사 |
|---|---|
| binding | run/request, bundle/work revision, publication ID, source version, projection hash, ACL scope version |
| node | 안정 ID, 종류(source/component/path/judgment/gap), label, 상태, 실제 근거 ref, 변경 종류 |
| edge | 안정 ID, from/to, 인용/구성의존/경로포함/승인관계/조사후보 구분, 근거 ref, 확정/미확인 |
| diff | old/new stable ID·revision·value, 근거 변경, 추가/삭제/수정/유지, 사유·주체 |
| action | 서버가 허용한 action·target·expected revision·view hash. 시안의 J 번호를 영구 ID로 사용하지 않음 |
| provenance | 관찰 원본·실행 receipt·사용자 의견·검토 결정 참조. 표시 여부와 실행 여부 분리 |

그래프·표·설명은 같은 투영에서 만든다. 위치/색상/사용자 선택은 파생 UI 상태이며 지식 hash에 섞지 않는다. 과거 source 카드의 표시 ID를 내용 hash에 섞었던 오류를 재도입하지 않는다. 확대·필터·노드 선택은 읽기만 하며 모델 호출·원문 자동 전수 조회·승인 사건을 만들지 않는다.

모바일/좁은 화면에서는 항목 목록과 상세를 세로로 제공한다. 스크롤·키보드로 동일 대상을 선택할 수 있고 hover에만 핵심 근거를 넣지 않는다. 큰 그래프는 범위/경로별로 나누고 `더 보기`의 데이터 조회에 기존 권한·페이지 계약을 적용한다. 제안하는 노드 표시 제한은 실제 데이터 크기·레이아웃 검증 후 정하며 처리 속도를 임의 보장하지 않는다.

## 4. 시각화 외에 이미 있는 기반

| 기능 | 현재 확인한 구현 | 남은 경계 |
|---|---|---|
| 읽기 판단 수집 | `capture`가 실제 원문·유효 head로 ONTOLOGY_WORK_INPUT 이벤트 생성. 기본 off | 연결 판단·미판단·재지시·정정·용어 관찰 전체 수집은 아님 |
| 작업 저장·생성 | Dataiku Folder/local store 포트, 입력 enqueue, 고정 레시피 생성·형식 보완, 새 revision | 현장 S3/생성 모델 배선, 여러 질문의 같은 개념 통합은 별도 |
| 검토·게시 | preview·승인/반려·정확한 판본 확인·PUB/HEAD/ANC/EVT transaction | 운영 Gold/Agent 분리·메타 신청·컬럼 매핑·단계적 게시 없음 |
| 원문 도착 후 시나리오 | anchor 조회·사전 조립 패키지·복수 경로 선택·충분성·기존 탐색 복귀 | 데이터 미포함/기본 OFF. v4 전체 typed 계획·의미 관계 실행과 동일하지 않음 |
| 일반 멀티턴 | 기존 12종 명령, 사실/목적/계획 변경·재답변·세션 소유권 검사 | 개별 판단 재지시 JUDGMENT_OVERRIDE 없음 |
| 질문 맥락 | 현재 context는 해당 세션 goal들을 조회하고 최근 4개에 이전 응답 요약을 덧붙임. CaseRepository가 이벤트 이력을 줄임 | v4의 최근 10개 질문 요약 + 선택 질문의 판단 그래프 계약은 미연결. ‘직전 1개만 있음’은 과거 문서 설명 |
| 첫 검색 | 기존 용어 역매칭·정확 조문 조회와 MAIN112 Oracle 초기 벡터 검색 연결 | 실제 임베딩/전체 적재·현장 사용, 승인 별칭·착지 예시의 v4 경로는 별도 |

따라서 ‘화면만 만들면 v4 완성’도 아니고 ‘온톨로지 기능이 전부 없다’도 아니다. 고정 시나리오를 생산·검토·소비하는 기반에 **축적·정정·골드 운영·현장 데이터·검증**을 연결해야 한다.

## 5. 시각화 외 잔여 작업 — 우선순위와 종료 조건

우선순위는 이번 구현 제안이다. 작업 실행·일정 확정·MAIN 승격 지시가 아니다.

R01은 시각화 문제가 아니며 새 그래프가 해결하지 않는다. R08~R11은 v4 확장이고 처음부터 모두 완성해야 최소 사용이 가능한 것은 아니다. R02~R07 중 한 개념의 작은 흐름을 먼저 완성해 실제 사용으로 연결하는 것을 제안한다.

### 먼저 닫을 한 바퀴

**질문 A/B의 실제 관찰 → 같은 원문·개념 r2 제안 → 원문/변경/충돌 검토 → 실제 사람 승인 → 기존 승인 골드 모델에 적재·검증 → 후속 질문 C에서 정확한 게시본 재사용.**

이 흐름의 종료 조건은 화면 버튼이 바뀌는 것이 아니라 세 질문과 관찰·작업·승인·골드·사용 receipt가 연결되는 것이다. 현장 골드 모델이 준비되지 않았다면 로컬 기술검증과 실제 이관 대기를 구분한다. 새 모델이 불필요한 고정 레시피 개념부터 시작하면 범용 스키마 확장보다 먼저 검증할 수 있다.

제안 구현 순서: 원문/답변 실패 정리와 관찰 계약 → 축적/검토 새 판본 → 골드 매핑·작업 잠금·단계적 게시 → Dataiku 실제 연결 및 후속 질문 → 재지시·스키마·용어/착지·가정 비교를 계약별로 확장. 기존 사용자 결정의 MAIN 반영 단위는 실제 구현 시 최신 승인·실험 기준을 다시 확인한다. 본 문서로 과거 USER_DIRECTED 전환 지시나 완료 실험을 새 승격 권한으로 전용하지 않는다.

## 6. 이번 시안 파일과 확인 범위

- 새 시안: `09_ARTIFACTS/AUDITS/20261028-ontology-accumulation-plan/ontology-v4-review.html`.
- 이전 골드 시안·스크린샷은 보존한다. 새 파일에서 관계도·상세·변경·계보·경로 선택·재지시 초안·합성 가정 비교를 추가했다.

- 정적 문서·근거 hash 확인: 같은 폴더 `v4-ux-evidence.json`.
- 실제 Streamlit/Plotly 왕복·Dataiku 설치·LLM·SQL·골드·GENOS 실행은 하지 않는다. 그림과 frontend 계산 예시를 제품 기능 통과로 세지 않는다.

인수 시에는 관계도 선택·표 선택의 동일 대상, 당시 설명의 원본 보존, 원문 미열람 표시, 현재/제안 판본 비교, 정상·예외 복수 선택, 화면 재실행/권한 변경, 재지시 대상 잠금, 시나리오가 골드/원문을 바꾸지 않는지 확인한다. 실제 RAG가 사용한 경로와 사용자에게 보여준 경로가 동일한지도 별도로 검증한다.
