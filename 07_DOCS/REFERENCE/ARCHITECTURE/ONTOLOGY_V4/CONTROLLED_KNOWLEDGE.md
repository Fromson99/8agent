# 제한된 지식 형식과 통제

[v4 목차](../ONTOLOGY_V4.md) · [판단 전달과 정정](JUDGMENT_AND_CORRECTION.md)

## 자유 대화와 게시 지식의 경계

사용자는 자연스럽게 설명하고 정정한다. 대화 내용을 받기 위해 매번 정적 양식을 채우게 하지 않는다. LLM도 기존 조사에서 의견·이유·새 개념 후보를 표현할 수 있다. 다만 다음 세 가지는 자유롭게 생성하지 못한다.

1. 실행할 도구·SQL·코드·외부 목적지.
2. 정본 스키마·객체 타입·관계 타입·조건 연산자의 신설.
3. 존재하지 않는 원문 ID·판본·인용·검토 승인.

대화 내용을 재사용 지식으로 반영할 때 별도의 제한된 정규화 절차를 거친다. 이 절차는 대화 응답의 선행 조건이 아니다. 변환 실패 시 사용자 답변과 확보 원문은 유지하고 지식 후보에 미반영 이유를 남긴다.

## 네 단계의 상태

| 단계 | 허용하는 표현 | 소비 가능 범위 |
|---|---|---|
| 대화 관찰 | 자연어 주장·이유·이견·발견 표현 + 서버 메타데이터 | 현재 대화와 검토 화면 |
| 정규화 후보 | 허용 타입에 매핑한 값·관계·조건, 미매핑 원문 포함 | 차이 검토·형식 검사; 자동 실행 불가 |
| 검토된 지식 | 원문·범위·판본·검토 결정·revision이 결속된 레코드 | 원문 중심 회수, 허용 능력 내 계획 조립 |
| 실행 산출물 | 고정한 지식·입력·계획에 대한 receipt와 결과 | 답변·비교 화면; 법률 정답 정본으로 자동 승격 금지 |

형식 유효성, 원문 지지, 사람 검토, 현재 사안 적용성, 실행 가능성은 서로 다른 상태다. 하나의 approved 또는 confidence 값으로 합치지 않는다. 기존 불변 레코드와 채널 게시 계약을 재사용한다.

## 스키마를 늘리지 않는 방법

현재 [contracts.py](../../../../02_BACKEND/lawrag/legal_knowledge/contracts.py)는 FIELD, METHOD, APPLICATION, WIKI_LINK, SHORTCUT_LINK를 지원한다. 기존 CONCEPT·DEFINITION과 source reference도 재사용한다. v4의 화면 노드·대화 판단·시나리오를 모두 새로운 골드 객체 타입으로 만들지 않는다.

| 논리 역할 | 기존 구조 활용 또는 제한된 변경 제안 |
|---|---|
| 원문·판본·span | 기존 원문 저장소·읽기 receipt 참조; 본문 복제 금지 |
| 개념·정의 | 기존 CONCEPT·DEFINITION 참조; 새 개념 후보는 기존 수명주기 적용 |
| 입력·한도·금액 | FIELD의 타입·dimension·legal_purpose 활용 |
| 조건과 적용 | APPLICATION의 condition·input_refs·method_refs 활용 |
| 근거 수집 묶음 | METHOD의 목적·입력·evidence_needs·steps·dependencies 활용 |
| 위키·경험 경로 | 기존 WIKI_LINK·SHORTCUT_LINK 참조와 권한·revision 활용 |
| 명시적 의미 관계 | 기존 계약으로 불충분한 경우에만 RELATION 타입 하나를 제안; 아래 등록 절차 선행 |
| 판단·정정·시나리오 | Agent 실행 기록·별도 제한된 명령 봉투. 골드 객체 타입을 매번 추가하지 않음 |

RELATION은 아직 지원되는 kind가 아니다. 프로토타입 첫 단계에서 계약 확장의 필요성과 기존 관계 저장소의 소유권을 확인한다. 채택 시 기존 v1 소비자와 분리된 명시적 버전 계약으로 추가하고, v1 레코드는 그대로 읽는다. 기존 내규–외규 basis_link는 원문 연결의 정본으로 유지하며 새 객체에서 참조한다. 두 저장소가 같은 관계를 서로 수정하게 하지 않는다.

FIELD의 값도 현재 계약에는 독립적인 source_value로 정의돼 있지 않다. 프로토타입에서는 source receipt에 결속한 기존 typed fact를 입력 snapshot으로 사용한다. 공유 기본값을 영속화하려면 타입·단위·기간·대상·원문 근거를 포함하는 value binding 확장을 별도로 검토한다. 설명 문자열에 값을 숨겨 자동 실행하지 않는다.

## 제한된 관계 카탈로그 제안

아래 의미 이름은 설계용 카탈로그 후보이며 런타임 enum을 추가한 결과가 아니다. 기존 관계 계약과 중복 여부를 확인한 뒤 하나의 registry에서 관리한다.

| 의미 | 요구하는 내용 | 실행 경계 |
|---|---|---|
| 정의함 | 정의 대상 개념·정의 원문·적용 문서 범위 | 같은 이름의 다른 개념을 자동 병합하지 않음 |
| 범위를 위임함 | 출발 원문·위임한 대상/속성·목적지 확인 상태 | 목적지 미확인이면 탐색 후보만 생성 |
| 위임 내용을 구체화함 | 위임 원문과 대응되는 세부 원문·속성 | 동일 개념·범위 확인 후 조회 경로로 사용 |
| 준용함 | 준용 대상 범위·적용 대상·변경해서 읽을 사항 | 중간 관계를 무제한 전이하지 않음 |
| 조건을 부과함 | 제한되는 대상·조건 원문·적용 범위 | 같은 상위 조라는 이유만으로 전체 적용 금지 |
| 예외로 변경함 | 대상 규칙·예외 조건·효과·우선순위 | 미확인을 예외 없음으로 바꾸지 않음 |
| 계산·판단의 입력임 | 제공하는 값·소비할 변수·타입·단위·시점 | 입력/출력 의미가 맞는 경우에만 조립 |

조회 실행과 논리 추론의 합성 허용표는 분리한다. 초기 프로토타입은 검토된 세부 범위 조회·상위 조건 결합·typed expression 입력 의존부터 실행한다. 다른 관계는 설명·검토 후보로 둘 수 있다. 지원하지 않는 관계도 원래 표현을 보존하지만 자동으로 가장 가까운 유형에 끼워 넣지 않는다.

## 정규화 제안의 필수 내용

하나의 제한된 후보 봉투에 다음을 담는다. 확정 JSON Schema·DDL은 구현 단계에서 registry와 함께 작성한다.

- 원래 대화/판단/원문 참조와 실제 표시 revision.
- 대상 원문·개념·관계 또는 신규 후보임을 나타내는 상태.
- 선택한 등록 타입·템플릿 버전, 값·단위·조건·범위의 변경 내용.
- 변경 이유, 근거 span, 미확인·충돌·미매핑 표현.
- 생성자와 검토자, 기존 지식의 expected revision, 작업 멱등 ID.
- 허용 소비 능력: 설명만, 근거 조회, 제한된 조건 계산 중 검증된 범위.

ID·hash·권한·실제 도구·출발/도착 원문은 서버가 선택 가능한 목록과 원문 receipt에서 결속한다. LLM은 목록 선택과 의미 제안을 맡는다. 임의 JSON key를 형식 확장으로 수용하거나 eval·임의 SQL·자유 코드 실행을 허용하지 않는다.

## 검증과 반영

1. 봉투와 등록 타입 검사: 미등록 필드·타입·연산자는 정본 반영 금지.
2. 단위·차원·연산 입력 검사: 돈, 비율, 기간, 수량과 대상 개념을 구분. 원 단위를 만 원으로 바꾸면 명시적 검증된 변환을 사용한다.
3. 원문·판본·span·권한 검사: 실제 확보한 범위만 근거로 사용한다.
4. 의미 검토: 원문이 관계·조건을 지지하는지, 빠진 예외·상위 조건이 있는지 사람/LLM 의견과 근거를 표시한다. 스키마 통과로 대체하지 않는다.
5. revision·충돌 검사: 기존 의견과 범위가 같은지 확인하고 정정/분기/충돌 중 하나로 기록한다.
6. 게시 전 소비 계약 검사: 표현만 지원하는 관계를 실행 가능으로 승격하지 않는다. 기존 게시 묶음과 적용 기간·의존 버전을 고정한다.
7. 반영 receipt와 사용자 표시: 후보 보존·정정 저장·공유 게시·실행 적용을 각각 표시한다.

매 단계마다 별도 LLM 호출을 만드는 설계가 아니다. 결정적 검사는 코드가 수행한다. 정규화가 필요한 후보만 묶어서 호출하고 변경 없는 후보는 재사용한다. 원래 의견과 정규화 결과의 의미 차이는 검토한다.

## 표현할 수 없는 판단의 처리

등록 형식으로 손실 없이 담을 수 없으면 미매핑 후보로 둔다. 사용자는 원래 설명과 보류 이유를 계속 볼 수 있다. 반복되는 새로운 요구가 생겼을 때만 스키마 확장 제안을 만든다.

스키마 변경 제안에는 사용 사례·반례·기존 타입으로 표현할 수 없는 이유·producer/consumer·이행·롤백·검사를 포함한다. 스키마 책임자가 기존 규약과 중복을 검토하고 승인된 코드 릴리스로 배포한다. LLM이나 대화 한 번이 운영 registry를 바꾸지 않는다. 기존 레코드를 자동 재해석하지 않고 영향받는 후보만 명시적으로 재정규화한다.

## 저장 책임과 변경 관리

Agent 레이어: 질문·LLM 외부 판단·도구 실행·사용자 정정·정규화 후보·시나리오 입력과 결과. Gold 레이어: 원문·검토된 개념·관계·조건·방법·LLM Wiki. 후보가 승인되면 골드 revision을 만들고 Agent의 발견/검토 이력과 연결한다.

서빙에는 전체 원문·지식의 영속 복제를 만들지 않는다. Oracle/조회 API를 통해 필요한 데이터만 사용한다. 로컬 프로토타입의 임시 fixture 저장은 운영 구조와 구분한다.

물리 스키마가 필요해지는 단계에서 [골드 메타 규약](../DATAIKU_GOLD_METADATA_20261022/README.md)과 [테이블 정의서 기준](../DATAIKU_GOLD_METADATA_20261022/TABLE_SCHEMA_WORKBOOK.md)을 적용한다. 현재/목표 레이어, grain·PK, 논리명·물리명·표준단어·도메인·타입·한글 길이·Description·권한·출처·이행을 작성하고 메타 등록·DBA 생성 상태를 구분한다. 이 문서는 새 운영 테이블명이나 DDL을 확정하지 않는다.
