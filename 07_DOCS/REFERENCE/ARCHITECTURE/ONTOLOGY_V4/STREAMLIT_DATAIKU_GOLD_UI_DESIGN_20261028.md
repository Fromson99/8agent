# 온톨로지 검토와 골드 이관 — Dataiku Streamlit 상세 화면 설계

**최신 r4 화면 계약 — 기록은 표로 표시:** 모인 기록과 검토 목록의 열은 `항목명·상태·기록 수·근거 원문`이다. 카드 대신 넓은 목록 표를 두고 행 왼쪽을 선택하면 바로 아래에서 상세를 확인한다. 조사 판단은 `번호·판단 내용·판단 이유·근거 원문`을 같은 행에 놓고 긴 내용은 줄바꿈한다. 근거 원문 전문과 승인 폼은 상세에서 확인한다. 정렬·필터 후에도 선택된 작업을 유지·확인하고 모델 실행·승인은 별도 버튼으로만 시작한다. 모바일은 표 내부를 가로 스크롤한다. [r4 안내·검증](APPLICATION_READINESS_20261028.md). 아래 r3의 사람/LLM 역할·골드 절차는 유지한다.

**최신 r3 화면 계약:** `1 모인 기록`에서 사람이 준비함의 원문·조사 판단을 확인하고 한 묶음을 선택 → `2 초안 만들기`에서 사람이 생성 시작, 연결된 LLM이 초안 작성, 시스템이 원문/구조를 검증해 검토 대기로 저장 → `3 검토·승인`에서 사람이 내용·원문 확인 후 승인 또는 사유를 적어 반려한다. 단계별 사람/LLM 역할을 문장으로 표시한다. 기록을 선택하거나 화면을 열기만 해서는 모델을 호출하지 않는다. 생성 후 승인과 골드 반영은 자동 수행하지 않는다. 전체 숏컷 저장소 자동 수집·병합은 연결 전임을 화면에 표시한다. 데모는 `예시 초안 만들기`이며 실제 모델을 호출하지 않는다. 운영 미설정/실패를 데모로 대체하지 않는다. [r3 안내](../../../../08_DEPLOYMENT/DATAIKU/ontology_dashboard_20261028_r3/GUIDE.txt). 아래 한 개 승인함은 r2 기록이며 그래프·가정 비교 등 복잡한 메뉴는 r3에도 복원하지 않았다.

**최신 사용자 결정 — 승인 중심 한 화면:** 여러 메뉴를 제거하고 `검토 대기 / 승인 완료 / 반려 / 전체` 상태 필터와 항목 목록, 선택한 내용·원문, 승인/반려 버튼만 둔다. 승인에는 원문 확인 체크, 반려에는 사유가 필요하다. 승인 뒤 골드 적재·검증은 별도라는 안내를 표시하며 실제 반영 완료 여부를 추정하지 않는다. 그래프·재지시·가정 비교·JSON 편집·생성/업로드·이관 요청 폼·별도 이력 메뉴는 현재 UI에서 제거했다. 아래 S01~S07은 이전 확장 설계로 보존하며 기본 화면의 구현 요구로 사용하지 않는다. [최신 r2 안내](../../../../08_DEPLOYMENT/DATAIKU/ontology_dashboard_20261028_r2/GUIDE.txt)

작성일: 2026-10-28. 상태: **목표 설계 + 실제 Streamlit 구현 범위 반영 / 코드·규약 대조에 의한 자체 검토**.

**최신 반영 — 대시보드 구현과 실제 적용:** [구현 상태·첫 적용 P1~P6·후속 v4 기능](APPLICATION_READINESS_20261028.md). 검토 대시보드, 개념 검토, 조사·재지시, 골드 이관, 게시 이력, 가정 비교의 6화면을 작업 프런트엔드에 구현했다. 아래 S01~S07은 전체 목표 계약이며 7개 상세 화면의 완전 구현을 뜻하지 않는다. 실제 검증은 새 화면19+기존 워크플로22=41검사와 로컬 브라우저 상호작용이다. Dataiku 현장·운영 골드 적재·GENOS 배포는 미확인이다.

| 현재 화면 기능 | 실제 구현 | 아직 설계인 부분 |
|---|---|---|
| 목록·검토 | 권한 확인 목록/검색, 원문 인용·항목표, 실제 basis/requires/path 관계도 선택, 조립 경로 표시, 이전 작업 판본 비교 | 서버 페이지 조회, 현재 활성 판본 기준 구조 차이, 다음 미확인 이동, 보류·분할·병합 |
| 수정·결정 | JSON 레시피 수정, 정확한 판본에 대한 승인·반려 | 업무 필드 편집과 제안한 역할 분리 전체 |
| 골드 이관 | 승인 판본의 불변 이관 요청 저장·다운로드 | 승인 모델/실제 DB 매핑 검증, 영속 이관 원장·재접속 조회, Dataiku 적재·검증·사용 전환 |
| 보조 화면 | 판단 기반 재지시 초안·다운로드, 기존 게시 이력, 합성 산술 비교 | 재지시 실행, 실제 RAG 사용 관찰, 법률 조건 변경 계산 |

새 골드 화면은 `PREPARED_NOT_APPLIED`이며 입력한 모델 참조도 `OPERATOR_SUPPLIED_NOT_VERIFIED`다. 요청 객체는 저장되지만 그 hash의 화면 재조회는 세션에 의존한다. 기존 CLI/구 UI의 직접 게시 경로까지 운영 골드 게이트를 적용하는 일은 남아 있다. [설치 안내](../../../../08_DEPLOYMENT/DATAIKU/ontology_dashboard_20261028_r1/GUIDE.txt) · [41검사·브라우저 기록](../../../../09_ARTIFACTS/AUDITS/20261028-ontology-dashboard/VALIDATION.json)

**같은 날 v4 재대조 보완:** [원문·판단·경로 검토 UX와 시각화 외 잔여 기능](V4_UX_AND_REMAINING_20261028.md)에 관계도/항목표, 근거·변경 동기화, 경로 비교, 미확인 동선, 재지시 초안, 합성 가정 비교 시안을 추가했다. 아래 골드 절차는 유지한다. 새 시안의 상호작용은 실제 브라우저로 확인했으며 실제 Streamlit/Dataiku 구현·배포와 구분한다. 아래 최초 시안의 검증 당시 기록은 보존한다.

사용자 요구: Dataiku에 올릴 Streamlit 화면을 상세하게 설계하고, 승인 데이터의 후속 골드 이관 절차를 반영한다. 이 문서는 [앞선 축적 계획](KNOWLEDGE_ACCUMULATION_PLAN_20261028.md)의 화면·승인 이후 절차를 구체화한다. 앞선 시안의 `승인 → DB 게시`는 운영 골드 절차를 충분히 표현하지 못했다. 운영 화면은 아래 절차를 따른다.

**내용 검토·승인 → 승인된 모델·매핑 확인 → 필요할 때 표준/모델/DB 생성 신청 → 적재 패키지 확정 → Dataiku 적재 → 저장·조회 검증 → 사용 판본 전환.**

내용 승인과 표준·모델 승인은 서로 다른 승인이다. 기존 승인 모델에 내용만 추가하면 표준 신청과 DBA 생성을 반복하지 않는다. S3 작업 JSON과 에이전트 이력을 삭제해서 골드로 이동시키지 않는다. 승인한 지식의 불변 게시본과 원문 연결을 골드에 적재하고 출처·승인·작업 이력은 보존한다.

선택 릴리스는 MAIN112 `vector-initial-20261028-r1`, 온톨로지 기본 OFF다. 같은 날 후속 요청으로 작업 프런트엔드는 위 범위만큼 구현했고 MAIN 선택은 유지했다. 운영의 실제 승인·신청·적재·모델 호출·배포는 수행하지 않았다. 운영 owner·대표 과제 코드·계정·Dataiku 버전은 현장 확인 전이며 설계 예시를 실제 운영값으로 사용하지 않는다.

## 1. 현재 코드와 이번 설계의 차이

| ID | 상황 | 기존 방식과 확인된 결과 | 바꿀 방식·원하는 결과 | 검증 방법 |
|---|---|---|---|---|
| G1 | 승인한 작업을 운영에 반영 | `ui.render`는 APPROVED이면 `승인 판본을 DB에 게시`를 표시하고 `Workflow.publish` 호출. 메타 등록·운영 매핑 게이트는 없음. 코드 확인이며 운영 사고는 미관측 | 내용 승인 직후에는 `골드 이관함으로 이동`. 모델·실제 DB·매핑·적재·검증을 통과한 판본만 사용 전환 | 승인만 한 판본이 소비자 조회에 나타나지 않음 |
| G2 | 개발 5표를 Gold/Agent로 분리 | `Repository`는 5표를 같은 owner와 고정명으로 접근. `draft/review`도 게시용 HEAD를 잠금으로 사용 | 에이전트 작업 잠금과 골드 활성 선택을 분리. 검토 계정에 골드 쓰기 권한을 주지 않아도 초안 저장 가능 | 골드 읽기/쓰기 권한 없는 작성 계정으로 초안·검토 수행 |
| G3 | 승인 모델의 내용 갱신 | 기존 화면에 표준·모델 재사용 판정 없음. 새 운영 절차 실행은 미관측 | 기존 승인 모델 재사용 / 모델 변경 신청 경로 분리 | 내용만 바뀐 r2는 기존 모델에 결속, 새 컬럼 요청만 등록 절차 진입 |
| G4 | 작업 수가 늘어남 | `Repository.list`는 257번째 행을 읽으면 범위 축소 오류. UI는 목록의 작업 JSON·원문을 개별 확인 | ACL이 적용된 요약 색인에서 페이지 조회 후 선택 건만 상세 로딩 | 256건 초과에서도 범위·페이지 이동; 목록 전체 S3/원문 로딩 없음. 속도는 별도 실측 |
| G5 | Streamlit 재실행·새로고침 | 기존 UI가 버튼 안에서 직접 생성/게시. 장기 작업 재접속 상태 화면은 없음 | 화면은 명령 접수·영수증 조회, 실행은 Dataiku 작업. DB 멱등 키로 중복 실행 차단 | 새로고침/중복 클릭 후 물리 모델 호출·적재가 늘지 않음 |
| G6 | 저장된 자료를 사용했다고 판단 | 현재 게시 receipt와 RAG 조회는 있지만 한 검토 화면의 골드 이관·실사용 증거는 연결되지 않음 | `내용 승인 / 골드 저장 / 사용 판본 / 실제 사용 관찰`을 구분 | 적재만 된 자료, OFF 상태, 조회만 된 자료를 사용 완료로 표시하지 않음 |

G1~G6은 최초 설계의 문제·목표다. 후속 대시보드에서 G1의 승인 후 이관 요청 준비와 G6의 상태 구분 일부를 구현했다. G1의 운영 적재·검증·전환, G2의 저장 책임 분리, G3의 실제 모델 검증, G4의 페이지 조회, G5의 영속 작업, G6의 실사용 관찰은 남아 있다. 전체 완료 판정은 상단 최신 구현 표와 적용 계획을 따른다.

## 2. 저장 위치와 이동 범위

| 자료 | 작업·개발 위치 | 운영 역할 | 화면에서의 표현 |
|---|---|---|---|
| 원문·구조·검색 | 개발 `SIDDS.*_S` | 기존 골드 후보 7표의 승인 모델/실제 게시 세대 사용 | 원문 판본, 조회 경로, 사용 가능 여부 |
| 관찰·질문·판단·생성/검토 이력 | Dataiku 관리 S3 JSON + 에이전트 영역 | 에이전트 영역에 보존 | 발견 이력 / 검토 이력 |
| 작업 판본·운영 사건 | `SIDDA.LGL_ONT_WORK_A`, `LGL_ONT_EVT_A` | 에이전트 영역에 보존 | 내용 상태와 사건별 영수증 |
| 승인 시나리오 게시본 | 개발 `SIDDA.LGL_ONT_PUB_A` | 골드 이관 대상 | 승인된 지식 내용 |
| 원문–게시본 연결 | 개발 `SIDDA.LGL_ONT_ANC_A` | 골드 이관 대상 | 문서·판본·조항 연결 |
| 활성 게시 선택 | 개발 `SIDDA.LGL_ONT_HEAD_A` | 골드 이관 대상 | 현재 사용 판본 |
| 용어·별칭 | 별도 작업 JSON·검토 절차 | 승인·신청·SQL 적재 후 사용 | 별도 대상 유형. 온톨로지 승인으로 함께 승인하지 않음 |

최신 R3 마스터의 **골드 후보는 10표·49컬럼**, 그중 온톨로지는 PUB 5 + HEAD 3 + ANC 5 = **3표·13컬럼**이다. 등록 후보 수이며 현장 생성 수가 아니다. 제외 목록의 4표·20컬럼은 보관/감사 책임을 유지한다. 이번 화면은 온톨로지 3표 이관에 집중하고 원문 7표의 준비 상태를 의존성으로 확인한다. 온톨로지 한 건마다 원문 전체를 다시 복사하지 않는다.

운영 이름은 R3의 `SIDDG.IDD_A03_LGL_ONT_{PUB,HEAD,ANC}`가 **신청 후보**다. SIDDG·A03을 확정 설정으로 넣지 않는다. 승인된 실제 이름을 매핑 등록부에서 읽는다. 운영 이름에 임의로 `_G`를 붙이지 않는다. DB 표준용어 사전과 RAG 법률 용어집은 별개다.

## 3. 메뉴와 공통 화면 틀 — 목표 계약

기존 앱의 `배치 모니터 / 구조화 누락 승인 / 숏컷 승인 / Legal Wiki / 온톨로지 관리 / 시뮬레이션` 위치를 유지한다. 이번 구현 대상은 온톨로지 관리와 해당 시뮬레이션 연결이다. 다른 메뉴의 기존 시안 데이터를 실제 연결 결과로 바꾸어 표시하지 않는다.

온톨로지 내부 메뉴는 **검토함 / 골드 이관 / 게시·사용 이력**이다. **내용 검토**는 검토함에서 선택한 한 건의 상세 화면으로 연다. 골드 이관 상세 안에는 **모델·매핑 → 패키지 → 적재·검증** 단계가 있다. 사용자는 항상 `어떤 자료 / 어느 판본 / 어디에 반영 / 다음 할 일`을 볼 수 있다.

```text
Dataiku · 법률 지식 관리                       사용자 / 역할
온톨로지 관리    검토함 | 골드 이관 | 게시·사용 이력
환경: 개발 또는 운영    연결 상태    마지막 조회 시각
────────────────────────────────────────────────────
목록: 필터 → 조회 → 결과 표 → 선택 건 요약 → 상세 열기
상세: 원문·개념명 / 작업 r2 / 현재 사용 r1 / 다음 할 일
      상태: 내용 승인됨 · 모델 확인 중 · 미적재 · r1 사용 중
      선택한 화면의 작업 영역
      결정/실행 영역 → 처리 결과와 영수증
```

UI 원칙:

- 개발/운영 연결은 배포 설정으로 고정한다. 화면의 환경 이름은 표시값이며 일반 사용자가 드롭다운으로 쓰기 대상을 바꾸지 못한다.
- 개념명·문서명·조항을 먼저 표시하고 내부 ID/hash/SQL은 `기술 상세`에 둔다. 필요한 판본 번호와 처리 번호는 바로 표시한다.
- 상태와 함께 다음 할 일, 담당 역할, 막힌 이유를 한 문장으로 표시한다. 예: `내용은 승인됐습니다. 골드 모델 생성 확인 후 적재할 수 있습니다.`
- 검토 버튼은 화면 하단의 일반 영역에 둔다. 고정 떠다니는 버튼이나 Streamlit 내부 DOM CSS 조작에 의존하지 않는다.
- 기본 상세는 **원문 45% / 변경 검토 55%의 2열**, 결정은 전체 폭이다. 긴 한국어 원문을 이전 3열 시안에 억지로 넣지 않는다. 사용자 선택 `나란히 / 세로로`를 제공하고 좁은 화면에서는 세로 보기를 기본 안내한다.
- 색상만으로 상태를 구별하지 않는다. 변경 종류는 `추가 / 수정 / 삭제 / 유지 / 미확인` 텍스트로도 표시한다.
- 첫 버전에서 일괄 내용 승인·일괄 사용 전환은 제공하지 않는다. 목록 다운로드는 현재 조회 권한 범위만 포함한다.

## 4. 한 개 상태 대신 네 가지 상태를 함께 표시

아래 값은 **제안 계약**이다. 기존 WORK의 `INPUT/DRAFT/APPROVED/REJECTED` CHECK에 이관 상태를 끼워 넣지 않는다.

| 축 | 상태와 의미 | 영속 책임 |
|---|---|---|
| 내용 | 수집됨 → 초안 → 검토 중/보류 → 승인 또는 반려 | 기존 WORK + 제안 review-task 메타. 승인판본/hash/영수증 고정 |
| 모델 | 미확인 / 기존 승인 모델 사용 가능 / 표준 신청 / 모델 등록 / DBA 생성 대기 / 실제 DB 확인 / 불일치 | 제안 mapping registry + 외부 절차 증빙 |
| 이관 | 미준비 → 패키지 확정 → 적재 대기 → 실행 중 → 검증 대기 → 검증 통과. 별도 실패/결과 불명/취소 요청 | 제안 transfer 작업 + Dataiku 실행 영수증 |
| 사용 | 미사용 / 현재 사용 / 이전 판본 / 사용 중지. 실제 관찰은 조회됨/선택됨/답변 반영됨 별도 | 골드 HEAD + 감사 사건 + 사용 관찰 |

정상적인 조합 예: `작업 r2 내용 승인 / 모델 사용 가능 / 적재 대기 / 현재 r1 사용 중`. r2가 대기 중이라는 이유로 r1을 내려서는 안 된다. 데이터가 없으면 `0건`, 조회에 실패하면 `조회 실패`다. 서로 대체하지 않는다.

중요한 상태 경계:

1. 승인 후 내용을 고치면 새 작업 판본이며 새 승인이 필요하다. 기존 승인 영수증을 이월하지 않는다.
2. 패키지 확정 후 내용·매핑·대상 DB 계약이 달라지면 새 패키지를 만든다. 진행 중 패키지를 덮어쓰지 않는다.
3. 최신 작업 판본이 바뀌면 아직 사용 전환하지 않은 이전 패키지를 `재검토 필요`로 막는 것을 첫 버전 기본 정책으로 한다. 이미 사용 중인 판본은 별도 중지 결정 전까지 유지한다.
4. 원문 판본 변경은 해당 근거와 소비 세대의 호환성을 검사한다. 역사 판본 자료를 자동 삭제하거나 새 원문에 자동 재결속하지 않는다.
5. `취소 요청`과 `취소 완료`를 구분한다. Dataiku가 작업/GENOS 프로세스 종료를 확인한 뒤 완료한다. 이미 커밋된 적재는 취소 요청으로 지워지지 않는다.

## 5. 화면별 상세 계약

### S01 검토함 — 무엇을 검토할지 고르기

**기본 진입:** 담당 또는 내가 볼 수 있는 미완료 건. 필터는 개념/문서/조항 검색, 제안 종류, 검토 상태, 담당자, 발견 기간이다. 필터를 입력한 뒤 `조회`로 적용한다. 출처 질문 번호도 상세 검색에서 지원하되 목록의 주키는 개념 묶음이다.

| 기본 열 | 의미 |
|---|---|
| 개념·검토 제목 | 묶음의 개념명과 짧은 변경 요약 |
| 원문 | 대표 문서·조항, 추가 원문 수 |
| 제안 | 신규 / 기존 갱신 / 충돌 검토 / 변경 없음 |
| 새 관찰 | 중복 제거 후 관찰 수 / 서로 다른 실행 수. 실제와 재생을 구분 |
| 판본 | 현재 사용 r1 → 검토 r2. 신규는 현재 없음 |
| 검토 상태 | 초안 / 보류 / 승인 등과 미확인 여부 |
| 담당·갱신 | 담당자와 마지막 변경 시각 |

기본 페이지 크기 25건은 화면 설계 값이다. 다음 페이지 커서를 사용하고 조회 결과의 안정 ID·revision을 보관한다. 행 선택만으로 승인/생성하지 않는다. `검토 열기`가 S02를 연다. 정렬·필터·페이지 변경 시 이전 행 선택은 해제한다. 집계와 검색 결과에도 동일한 원문 권한을 적용한다.

빈 상태: `아직 수집된 관찰이 없습니다`와 연결 상태를 표시한다. 조회 실패: 현재 필터를 보존하고 `다시 조회`. 초안 생성 모델 미설정: 저장된 초안은 검토 가능하되 생성 버튼 비활성 사유를 표시한다. 원문 권한 밖 건은 이름·건수로도 노출하지 않는다.

### S02 내용 검토 — 원문과 변경을 비교하고 정확한 판본 승인

상단: 개념명, 작업 판본, 비교 기준인 현재 사용 판본, 제안 작성 주체, 마지막 저장 시각, `목록으로`. 중간의 두 열은 아래처럼 구성한다.

```text
원문·발견 이력                        현재 내용 → 이번 제안
문서 / 판본 / 조항 선택                변경 항목 목록
원문 본문과 인용 범위                  [수정] 적용 조건
인용 앞뒤 문맥 펼치기                  이전 문장 / 제안 문장
                                    근거: 원문 구절·관찰
관련 관찰 선택                        [추가] 예외 또는 미확인
실행 / 판단 / 읽음·미열람              주장·근거·변경 이유
사용자 의견 원문 / 모델 해석 분리       전체 조립 결과 보기
────────────────────────────────────────────────────
검토 결정: 원문 결속 검사 결과 / 남은 확인 사항
의견 + 확인 항목       보류 | 반려 | 내용 승인
```

**원문 패널:** 문서명·정확한 판본·조항·본문/부칙을 구별한다. 인용 선택 시 저장 좌표와 현재 검증된 원문으로 범위를 강조한다. 문자열 검색으로 비슷한 구절을 임의 대체하지 않는다. 사용자가 볼 수 있는 실제 원문만 표시한다. 원문을 읽지 않은 판단은 `미열람`이며 근거 확인 완료로 표시하지 않는다.

**변경 패널:** 항목별로 종류, 이전 값, 제안 값, 변경 이유, 근거 좌표, 관련 관찰, 충돌/미확인을 보여준다. `근거 보기`는 좌측 원문 선택을 바꾼다. 동일 조항의 다른 개념은 `별도 묶음으로 분리` 후보를 만들 수 있지만 기존 자료를 삭제·이동하지 않는다. 편집은 조건·효과·예외·근거 등의 업무 필드로 한다. 원시 JSON은 고급 조회에 둔다.

**편집 모드:** 한 항목을 선택한 뒤 편집 폼에 들어간다. 폼 내부의 `수정 저장`과 `취소`만 활성화하고 목록 이동·다른 판본 선택·자동 새로고침은 중지한다. 저장은 예상 revision을 검사해 새 작업 판본으로 만든다. 자동저장이라고 표시하지 않는다. 브라우저 종료 전 미제출 입력 보존은 보장하지 않으며 `마지막 저장 시각`을 표시한다. 제출한 값이 검증에 실패하면 입력값을 유지하고 해당 필드 오류를 보여준다.

**미리보기:** 전체 조립 경로를 선택해 조건·예외·근거·미확인이 실제로 어떻게 전달되는지 보여준다. 이는 저장 자료의 조립 검사이며 모델 답변 품질·계산 결과가 아니다. 실제 모델 질문 버튼은 별도 실행 계획과 예산을 가진 Dataiku 작업으로 연결하며 첫 화면 설계만으로 실행하지 않는다.

**결정:** 읽기 모드에서만 가능하다. 승인 전 서버가 권한, 최신 revision/hash, 원문 판본/인용, 참조/조립 검사를 다시 확인한다. 의견은 필수, 원문·적용 범위·예외 확인 항목을 기록한다. 확인 체크 자체가 원문 검증을 대신하지 않는다. 상충한 핵심 결론을 확정 규칙으로 내보내는 초안은 보류한다. 명시적 제한/추가 조사 경로를 포함한 시나리오는 그 제한을 검토한 뒤 승인할 수 있다.

`보류`는 사유·담당·필요 원문을 가진 별도 review-task 상태로 남긴다. `반려`는 현재 초안 판본의 결정이며 재작성하면 새 판본이다. `내용 승인` 성공 문구는 **“r2 내용 승인을 저장했습니다. 골드 이관 전에는 새 판본이 사용되지 않습니다.”**이다. 다음 버튼은 `골드 이관함 열기`다.

### S03 골드 이관함 — 승인됐지만 아직 사용할 수 없는 이유 파악

대상은 내용 승인된 판본과 그 이관 이력이다. 첫 화면은 표로 `개념 / 승인 판본·승인자 / 대상 환경 / 모델 준비 / 적재·검증 / 현재 사용 / 다음 할 일 / 담당`을 보여준다. 기본 필터는 미완료다. 기존 r1과 후보 r2를 동시에 보여준다.

상세 상단에는 네 상태와 아래 단계 목록을 둔다. 진행률을 임의 60%로 만들지 않고 완료 증거가 있는 단계만 `확인됨`으로 표시한다.

| 단계 | 완료로 볼 증거 | 다음 화면 |
|---|---|---|
| 내용 승인 | exact revision/hash/승인 영수증, 취소·후속 변경 여부 | S02 |
| 대상 모델 확인 | 등록 모델·승인 매핑·실제 DB metadata 검증 | S04 |
| 패키지 확정 | 고정 manifest/hash/대상/행수/SQL/rollback 명세 | S05 |
| Dataiku 적재 | 실제 run/attempt와 동일 패키지 적재 영수증 | S06 |
| 재조회 검증 | 해시·좌표·권한·소비자 후보 조회 검사 | S06 |
| 사용 전환 | HEAD 변경+감사 commit, 실제 소비자 상태 | S07 |

`현재 사용 없음`과 `기존 r1 계속 사용`을 구별한다. 이관 완료와 실제 질문 사용 관찰은 다른 정보다. 이관 중 실패하더라도 검토했던 작업과 승인 이유를 여기서 바로 열 수 있다.

### S04 모델·매핑 — 기존 모델 사용 또는 신규 신청

첫 선택은 자동 대조 결과 `기존 승인 모델 재사용 가능 / 모델 변경 필요 / 확인 자료 없음`이다. 사용자가 근거 없이 완료 상태를 직접 선택하지 못한다. 동일 계약인지 비교하고 승인된 매핑 판본을 선택한다.

**기존 모델 경로:** 승인 모델 ID·매핑 판본·대상 owner/table/column·실제 DB 검사 시각·권한 검사 결과를 읽는다. 변경이 내용뿐이면 신청서를 재발행하지 않는다. 실제 스키마가 승인 모델과 다르면 불일치 목록을 표시하고 적재를 막는다.

**변경 경로:** `표준 조회 → 미등록 표준 신청 → 표준 승인 → 모델 작성·등록 → 필요한 예외 처리 → DBA 생성 신청 → 실제 생성 확인`을 행별로 관리한다. 각 행에 담당, 외부 신청/승인번호, 증빙 파일, 처리일, 비고를 둔다. 외부 시스템 API 연결은 현재 없으므로 **담당자 등록 증빙**과 **자동 검증 결과**를 구분한다. 증빙 등록만으로 시스템이 외부 승인을 자동 확인했다고 쓰지 않는다.

골드 정의서의 기존 양식을 재사용한다. 별도 비호환 신청 양식을 만들지 않는다.

| 하위 보기 | 화면과 파일 계약 |
|---|---|
| 테이블 | 기존 8열: 에이전트번호·스키마·현재 테이블명·TOBE 테이블명·논리명·정의·원천·반영내용 |
| 컬럼 | 기존 15열 원본을 유지. 화면은 현재/목표 이름·타입·PK/NULL·변환을 우선 표시하고 나머지는 상세 |
| 표준용어 | 단어·동의어·금칙어·도메인·인포타입·실제 등록 식별정보와 검토 결과 |
| Bizmeta·Description | 기존 Bizmeta 항목, 테이블 Description 11항목, 컬럼 Description 4항목 |
| 등록관리 | 외부 절차 상태·담당자·증빙. 미확인 값은 미확인으로 남김 |
| 개발운영매핑 | 테이블/컬럼 변환, 소비자 역변환, 실제 DB 차이 |

매핑은 내용 검토자 화면에서 임의 수정하지 않는다. 메타 담당이 수정안을 저장하고 승인 모델과 결속한 뒤 별도 매핑 판본을 발급한다. 신규 운영 식별자는 허용 목록으로 검증하고 SQL 값은 bind한다. DDL 문자열을 모델 출력이나 사용자 텍스트에서 바로 실행하지 않는다.

### S05 적재 패키지 — 무엇을 어디에 쓸지 고정

상단: 개념·승인 판본·대상 환경·모델/매핑 판본. 표: 대상별 쓰기 종류와 예상 행수. PUB 1건, ANC는 검증된 고유 anchor 수, HEAD 변경은 별도의 사용 전환 단계로 표시한다. 예상 행수는 실제 payload에서 계산하며 고정 예시값을 실제 값으로 쓰지 않는다.

패키지에 포함할 항목:

| 구성 | 계약 |
|---|---|
| manifest | package ID, 생성 주체·시각, 내용 승인 receipt, work hash/revision, payload canonical hash |
| 대상·매핑 | target environment ID, 확정 owner/table/column, 모델/매핑/소비자 계약 버전과 실제 DB 검사 증거 |
| 데이터 | 불변 PUB/ANC payload, 원문 세대·문서판본·좌표·본문 검증값 |
| 적재 자료 | 매핑된 DML 계획과 bind 데이터. DDL은 별도 신청 자료이며 데이터 적재와 섞지 않음 |
| 검증 자료 | 예상 PK/행수/hash/참조·권한 검사 및 consumer preview 결과 계약 |
| 사용 전환 | 기대 HEAD 변경 순번, 이전 publication ID, 전환·중지·복원 절차 |
| 계보 | 관찰·작업·승인·표준/모델 증빙 참조. 권한 밖 원문은 패키지 열람·내보내기에도 제외/차단 |

버튼: `패키지 검증`, `패키지 확정`, `적재 자료 받기`, `실행 결과 확인`. 확정 후 수정은 새 패키지다. 첫 도입에서는 담당자가 Dataiku의 지정 레시피/SQL 실행 절차로 적재하고 이 화면에서 결과를 확인한다. 실행 API와 권한이 현장에서 연결·검증된 이후에만 `Dataiku 적재 실행`을 노출한다. 버튼 이름만으로 레시피 실행이 연결된 것으로 보지 않는다.

### S06 적재·검증 — 부분 성공과 결과 불명을 처리

상단에는 Dataiku 실행 ID·attempt·패키지·시작/마지막 갱신/종료 시각·실행 단계·요청자/실행 계정을 표시한다. 진행은 `대기 → 입력 검증 → PUB/ANC 저장 → 재조회 → 소비자 확인`의 실제 사건 기준이다. 로그에는 민감한 연결정보나 권한 밖 본문을 노출하지 않는다.

검증 표의 열은 `검사 / 기대 / 관측 / 결과 / 증거`다. 필수 항목은 승인판본 유지, 모델/실제 스키마 일치, PK·FK·중복, PUB/ANC 행수, canonical hash, 원문 좌표/판본, 인용 본문, 조회 권한, 소비자가 동일 게시본을 역매핑해 읽는지다. `SQL 성공` 하나로 통과시키지 않는다.

| 결과 | 화면 행동 |
|---|---|
| 전체 검증 통과 | `사용 전환 검토` 활성화. 현재 사용 r1은 그대로 |
| 일부 저장/검증 실패 | 실패한 단계와 저장된 publication ID 표시. 같은 패키지로 상태 확인 후 재개 |
| 응답 유실·결과 불명 | `결과 확인`만 우선 허용. 새 패키지·새 모델 호출로 재시작하지 않음 |
| 취소 요청 | Dataiku 취소 접수 표시. 완료 여부를 조회, 이미 저장된 불변 자료는 이력에 보존 |
| 원문/매핑/승인 변경 | `재검토 필요`. 변경한 대상과 S02/S04 링크 표시 |

화면을 닫아도 Dataiku 작업은 계속되며 재접속은 영수증 조회로 복원한다. 자동 갱신은 읽기만 하며 실행·재시도 명령을 만들지 않는다. 고정 5초 갱신은 초기 제안값이고 정지 버튼을 제공한다. 편집 폼에서는 자동 갱신을 중지한다.

### S07 게시·사용 이력 — 현재 사용과 실제 효과를 구분

한 개념에 `현재 사용 판본`, `검증 완료 후보`, `이전 판본`을 나란히 비교한다. 후보 선택 시 승인자·근거 판본·변경 요약·대상 소비자·검증 결과·기대 HEAD 순번을 보여준다. 사용 전환은 운영자에게만 제공하고 서버가 전 조건을 다시 확인한다.

`사용 판본으로 전환` 성공은 HEAD와 감사 기록 커밋 및 재조회를 확인한 뒤 표시한다. 그 다음에도 **“사용 판본 r2 / 소비자 연결 확인 / 온톨로지 OFF / 실제 사용 관찰 없음”** 같은 조합이 가능하다. OFF를 자동으로 ON으로 바꾸지 않는다. 기존 요청은 시작할 때 고정한 판본을 유지하고 다음 요청부터 새 선택을 적용한다.

이력 표: 시각, 원문/개념, publication ID, 행위(승인/적재/검증/전환/중지/복원), 요청자, 실행 계정, 결과, 영수증. 사용 관찰 표: 질문/실행, 실제 도달 원문, 조회 게시본, 선택 경로, 답변 반영, 미확인, 실제/재생 구분. 조회·선택·최종 발행을 합쳐 성공 건수 하나로 만들지 않는다.

`사용 중지`는 HEAD를 미사용으로 전환하고 이력을 보존한다. `이전 판본 복원`은 대상 판본의 현재 원문·권한·호환성을 재확인하고 현재 HEAD 순번을 조건으로 수행한다. 과거 적재 영수증 재조회가 복원된 HEAD를 다시 최신 판본으로 돌려놓지 않도록 한다.

## 6. 버튼·권한·부작용 계약

역할은 구현용 제안이며 실제 Dataiku 그룹/운영자 설정에 매핑한다. 한 사람이 여러 역할을 가질 수 있다. 별도 결재 규정이 확인되지 않았으므로 무조건 2인 승인을 새 요건으로 만들지 않는다. 버튼을 숨기는 것 외에 서버에서도 매번 검사한다.

| 버튼 | 역할 | 서버 선행 조건 | 쓰기/실행과 성공 기준 |
|---|---|---|---|
| 조회·상세 열기 | 열람 가능자 | 현재 문서 ACL, 대상 존재 | 읽기만. 조회 실패와 빈 목록 분리 |
| 변경 초안 생성 | 작성자 | 허용 원문·관찰, base revision, 같은 작업 중복 없음 | Dataiku 작업 접수 receipt. 생성 완료와 구분 |
| 수정 저장 | 작성자 | 예상 revision/hash, 입력 계약·참조 유효 | S3 불변 새 작업 + 에이전트 새 판본. 일부 실패는 저장 확인 대기 |
| 보류·반려 | 검토자 | 최신 대상, 사유, 권한 | 보류 task 또는 반려 결정 receipt |
| 내용 승인 | 검토자 | 저장 완료, 최신판본·원문/조립 검사, 검토 사유 | 승인 receipt만 생성. 골드 적재/HEAD 변경 없음 |
| 신청 증빙 등록 | 메타 담당 | 대상 모델·외부번호·파일·권한 | 담당자 등록 증빙. 외부 시스템 자동 승인으로 표시 금지 |
| 실제 DB 확인 | 메타/적재 담당 | 등록된 연결·읽기 권한 | 읽기 검사 결과. DDL 실행 없음 |
| 패키지 확정 | 적재 담당 | 현재 승인판본·승인 모델·매핑·DB 확인 | immutable manifest와 멱등 작업 키 |
| Dataiku 적재 실행 | 적재 담당 | 현장 실행 연결 검증, 확정 패키지, 동일 작업 실행 없음 | Dataiku 접수·실행 영수증. 미연결이면 버튼 미노출 |
| 결과 확인·검증 | 적재/운영 담당 | 원래 패키지와 실행 권한 | 저장 확인·읽기 검사. 새 생성 호출 없음 |
| 사용 전환 | 운영자 | 검증 통과, 현재 승인/모델/원문 유효, expected HEAD, 소비자 계약 | 골드 HEAD+에이전트 감사 commit, 재조회 |
| 사용 중지·복원 | 운영자 | 대상·이유·expected HEAD, 복원판본 재검증 | 포인터 변경+감사. 데이터 삭제 없음 |
| 실행 취소 | 해당 작업 운영자 | 현재 실행/대상 소유권 | Dataiku 취소 요청. 실제 종료 확인 후 완료 |

명령 공통 제안: `command_id, actor_principal, execution_principal, target_env, bundle_id, revision, work_hash, approval_receipt, mapping_version, package_id, expected_sequence, reason`. 행동에 필요한 필드만 제출하고 나머지는 서버가 검증된 저장값으로 복원한다. actor를 입력창이나 URL에서 신뢰하지 않는다.

멱등성은 세션 변수에만 두지 않는다. 명령 수락 전에 DB의 고유 키로 작업을 예약한다. 같은 키는 같은 영수증을 반환하고, 실패 후 재개는 원래 package와 별도 attempt로 기록한다. 최신 상태가 바뀐 오래된 명령은 충돌로 거절한다.

## 7. 골드 적재와 사용 전환의 실제 연결 설계

### 7.1 기존 publish를 그대로 사용하면 안 되는 이유

현재 `Repository.publish`는 PUB·ANC 삽입, HEAD 변경, EVT 기록을 한 트랜잭션에서 한다. 운영 화면에서 이 함수를 호출한 뒤 `검증 대기`라고 표시하면 이미 RAG가 읽을 수 있으므로 순서가 뒤집힌다.

제안은 **불변 데이터 준비와 실제 게시를 구분**하는 것이다. `stage_publication`은 PUB/ANC를 적재하되 HEAD를 바꾸지 않는다. 준비 완료 영수증·감사 사건을 남긴다. `verify_staged`는 정확한 후보를 직접 읽어 검증한다. 일반 RAG는 HEAD와 조인하므로 미활성 후보를 읽지 않는다. `activate_verified`는 동일 후보의 유효성을 재확인하고 HEAD 변경과 감사 기록을 원자적으로 커밋한다. 함수 이름은 신규 제안이며 현행 구현에 없다.

이는 기존의 한 번에 게시하는 계약을 **준비 단계 + 최종 게시 단계**로 확장하는 변경이다. 골드 마스터의 process 설명도 실제 구현과 함께 수정해야 한다. 문서만 바꿔 구현된 것으로 처리하지 않는다.

### 7.2 작업 잠금 분리

현재 `Repository.draft`는 골드 후보 HEAD에 NULL 행을 만들고 `review`도 그 행을 잠근다. 제안하는 agent 작업 제어 행은 bundle별 최신 작업 revision·잠금/변경 순번을 담당한다. 앞선 축적 계획의 IDX와 역할을 통합해 불필요한 두 잠금 테이블을 만들지 않는다. 이름·DDL은 에이전트 스키마 검토 대상으로 확정한다.

기존 작업은 최신 revision을 agent 제어 행에 이행한다. 기존 HEAD와 활성 publication은 보존한다. 새 bundle의 동시 생성은 agent 제어 PK 충돌/재조회로 처리한다. 게시 전환에서만 골드 HEAD를 잠그고 expected sequence를 확인한다.

### 7.3 owner·테이블·컬럼 매핑

현재 `ontology-connection-v1`의 단일 owner를 바꿔 모든 표를 골드에 보내면 WORK/EVT도 이동하게 된다. 신규 연결 계약은 agent/work/control/event와 gold/publication/head/anchor를 역할별로 분리하고, 승인된 테이블·컬럼 매핑 판본을 필수로 둔다. 설정명은 구현 시 버전 계약으로 추가한다. 현행 v1 연결은 개발용으로 호환 유지한다.

R3의 온톨로지 컬럼 매핑 후보:

| 역할 | 현재 컬럼 | 후보 골드 컬럼 |
|---|---|---|
| PUB | PUB_ID / BNDL_ID / REV_NO | ONT_PBLS_ID / ONT_BNDL_ID / ONT_WORK_VER_NO |
| PUB | PKG_HASH_VAL / PKG_JSON_CN | ONT_PKG_HASH_VALU / ONT_PKG_JSON_CTNT |
| HEAD | BNDL_ID / PUB_ID / CHG_SEQ_NO | ONT_BNDL_ID / ONT_PBLS_ID / ONT_CHG_SEQ_NO |
| ANC | PUB_ID / ANC_HASH_VAL | ONT_PBLS_ID / SRC_ANCHOR_HASH_VALU |
| ANC | DOC_ID / SRC_VER_ID / UNIT_ID | LGL_DOC_ID / SRC_VER_ID / LGL_UNIT_ID |

이 매핑은 model.json의 후보를 인용한 것이며 승인값이 아니다. INSERT에 명시적 컬럼 목록을 사용하고 SELECT 결과는 기존 내부 계약으로 역매핑한다. 원문 reader도 SIDDS 고정명에서 승인된 원문 매핑을 선택할 수 있어야 한다. 문서/판본/구조 ID의 512 BYTE 계약, hash 64문자, JSON CLOB 의미와 정규화 해시를 보존한다. 한글 바이트 길이·VARCHAR 계열·여부형 변환은 승인 모델과 실제 DB를 따르며 자동 축소·일괄 변환하지 않는다.

### 7.4 트랜잭션과 배포 경계

첫 구현의 조건은 **같은 Oracle DB에서 필요한 교차 owner 권한을 가진 한 트랜잭션**으로 HEAD와 agent 감사 사건을 커밋할 수 있는 것이다. Dataiku 연결 이름이 같다는 것만으로 이 조건을 충족했다고 보지 않는다. 현재 연결 API가 동일 connection/transaction을 유지하는지 실제 확인한다.

다른 DB 연결로 나뉘어 한 트랜잭션을 만들 수 없다면 자동 사용 전환을 막는다. 별도 outbox·상태 대조·복구 계약을 설계·검증한 다음 지원한다. 첫 버전에서 두 commit을 원자적이라고 주장하지 않는다.

GENOS는 Oracle/조회 API에서 필요한 게시본만 읽는다. 골드 전체를 GENOS 로컬 SQLite나 영속 파일로 복제하지 않는다. 작업 실행·재시도·상태·로그·S3 저장은 Dataiku가 관리한다. GENOS 호출이 필요할 때는 계산 수명만 유지하고 GENOS→S3 직접 접속이나 영속 job registry를 추가하지 않는다.

## 8. Streamlit·Dataiku 구현 규칙

저장소는 `streamlit==1.50.0`을 고정한다. Dataiku의 실제 DSS 버전·코드 환경·Webapp 권한은 현장 확인 대상이다. [Dataiku Streamlit 문서](https://doc.dataiku.com/dss/latest/webapps/streamlit.html)의 네이티브 Webapp 구조를 사용하고, 백엔드·스키마·프런트엔드는 같은 검증 버전으로 반입한다.

| 화면 요소 | 구현 방식 | 피할 오류 |
|---|---|---|
| 내부 메뉴·단계 전환 | `st.radio` 등 선택값으로 분기해 현재 화면만 조회 | 숨겨진 단계까지 S3/Oracle를 매번 읽지 않음 |
| 목록·선택 | `st.dataframe` 단일 행 선택 + 상세 열기 | 위치 인덱스는 해당 화면 snapshot의 안정 ID로 변환; 정렬·필터 변경 후 과거 선택 사용 금지 |
| 편집·검토 의견 | `st.form` + 명시적 제출 | 폼 밖 클릭으로 미제출 입력이 자동 저장됐다고 간주하지 않음 |
| 구조화 편집 | 선택 항목의 필드 입력 또는 제한된 `st.data_editor` | 원문·ID·hash·상태·승인자 직접 편집 금지 |
| 세션 상태 | 필터·선택ID·편집 중 UI 상태 | 승인·진행·현재 사용의 원장으로 사용하지 않음 |
| 캐시 | 안전한 공통 자원 또는 권한 범위·판본을 키에 포함한 제한된 읽기 | actor가 결속된 Workflow/원문 reader/작업 전체를 전역 공유하지 않음 |
| 작업 갱신 | 읽기 상태 화면에서만 주기 조회, 사용자가 중지 가능 | 화면 렌더링/조회에서 생성·적재·재시도 명령 실행 금지 |
| 오류 | 짧은 원인·다음 행동·correlation ID | 토큰·접속 문자열·권한 밖 원문을 예외 문자열에 노출하지 않음 |

폼 입력은 제출 전 서버에 전송되지 않는다. 편집 화면 밖의 자동 갱신을 중지하고 탐색도 잠근다. 서버 세션만으로 브라우저 닫기·새로고침에 대한 미제출 입력 보존을 약속하지 않는다. [Streamlit 폼 동작](https://docs.streamlit.io/develop/concepts/architecture/forms), [Session State 수명](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.session_state).

`st.cache_resource`는 사용자·세션 간 공유되므로 인증된 actor의 문서 권한이 결속된 객체를 전역 캐시하지 않는다. 권한 검사는 변경 명령 직전에 다시 수행한다. [Streamlit 1.50 자원 캐시](https://docs.streamlit.io/1.50.0/develop/api-reference/caching-and-state/st.cache_resource).

Dataiku Webapp의 백엔드 실행 계정과 브라우저 사용자는 다를 수 있다. 현재 코드의 browser headers 인증 조회를 유지하되 현장 인증 응답에서 principal 필드를 확인한다. 사용자 principal과 실제 작업 실행 계정을 함께 기록한다. 헤더 원문·비밀값은 기록하지 않는다. 인증 실패 시 설정된 운영자 이름으로 우회하지 않는다. 로컬 operator 테스트 경로는 운영에서 비활성화한다. [Dataiku Webapp 보안](https://doc.dataiku.com/dss/latest/webapps/security.html), [공식 사용자 식별 예제](https://developer.dataiku.com/latest/tutorials/webapps/common/impersonation/index.html).

S3는 Dataiku Managed Folder의 업로드/다운로드 스트림을 사용한다. S3 폴더에 로컬 `get_path()`가 있다고 가정하지 않는다. 세션을 벗어나 보존해야 할 편집 결과·승인·패키지·실행 영수증은 S3/DB에 저장한다.

## 10. 실제 질문 한 번과 화면의 연결

첫 질문 후보 CM001: **“벤처금융 및 전문투자자의 100분의 10 한도는 합산 기준인가? (업무 문맥: 신규상장 의무보유 - 코스닥시장 상장규정 제26조)”**. 질문 원문은 저장소 사례이며 아래 화면 흐름은 실행 계획이다. 법률 결론을 이 문서에서 새로 판단하지 않는다.

| 순서 | 사용자·시스템 행동 | 볼 화면·증거 |
|---|---|---|
| 질문 실행 | 구현 검사 후 새 ADR로 후보·입력·예산 동결, 실제 질문 1회 | 실제 답변 상태·읽은 원문·판단·미확인. 과거 ADR1173 실패와 별도 |
| 관찰 도착 | 기존 이벤트에서 수집, 원문·개념별 후보 대조 | S01 신규/갱신/충돌. 실제 run ID와 재생 이력 분리 |
| 내용 검토 | 새 제안과 현재 내용 비교, 근거 없는 합산 결론이면 보류/수정 | S02 원문·차이·미확인. 실패한 최종 답변을 승인 지식으로 수입하지 않음 |
| 내용 승인 | 검토자가 실제 판본 승인 | S03 `내용 승인 / 미적재`. 승인 클릭을 자동 재연하여 실제 승인으로 세지 않음 |
| 모델 분기 | 기존 승인 모델이면 재사용, 새 컬럼 등 계약 변경이면 신청 | S04 기존 모델 확인 또는 외부 신청 증빙. 골드 미준비 상태도 정상 표시 |
| 적재·검증 | 패키지 고정, Dataiku 담당 절차로 실행, 재조회 | S05/S06. DB·권한 미준비면 여기서 대기하며 MAIN/GENOS 사용 완료라 하지 않음 |
| 사용 전환 | 검증된 후보로 HEAD+감사 commit | S07 `사용 판본`, 설정/소비자 연결과 실제 관찰은 별도 |
| 후속 재사용 | 별도 실제 후속 질문이 같은 원문·개념에 도달 | 조회·선택·발행 영수증. 저장응답 재생만으로 실제 재사용 성공이라 하지 않음 |

한 번의 새 질문으로 수집·제안 흐름을 확인할 수 있다. 실제 사람의 검토, 외부 표준/DB 절차, 골드 적재와 후속 질문은 각각 별도의 완료 증거가 필요하다. 같은 원문을 다룬 보관 실제 관찰이 있으면 새 관찰과 통합할 수 있지만 합성 이력을 과거 실행으로 표시하지 않는다.

도입은 기존 v1 개발 연결/게시본을 읽을 수 있게 유지하고, 운영 이관 기능은 새 설정에서 먼저 닫아 둔다. 검증된 후보를 공식 MAIN 절차로 선택한 뒤 현장 반입한다. 롤백은 신규 이관 명령 중지 → 진행 작업 확인 → 필요 시 검증된 이전 HEAD 복원 → 이전 검증 코드 선택이다. 작업·승인·실패·패키지를 삭제하지 않는다.

## 12. 수치의 의미와 자체 검토 — 최초 설계 당시 기록

이 절의 `미구현`·브라우저 미검증·라이브러리 부재는 최초 HTML 시안 시점 기록이다. 이후 실제 Streamlit 구현과 검증 범위는 상단과 [실제 적용 계획](APPLICATION_READINESS_20261028.md)을 따른다. 과거 실패·검증 파일은 보존한다.

| ID | 수치 | 종류·근거·한계 |
|---|---|---|
| N1 | Streamlit 1.50.0 | 저장소 requirements 고정. 실제 Dataiku 설치 버전은 미확인 |
| N2 | 골드 후보 10표·49컬럼, 온톨로지 3표·13컬럼 | R3 model.json 집계. 승인/현장 생성 건수가 아님 |
| N3 | 목록 25건, 상세 45:55, 상태 갱신 5초 | 초기 화면 설정 제안. 성능 실측/보장 아님 |
| N4 | 추가 생성 모델 호출0 | 단순 조회·검토·매핑·적재·검증·상태 갱신의 설계 계약. 초안 생성·실질문은 제외 |
| N5 | 속도·개발기간·정확도·운영비 | 미산정. 목록 SQL/S3 횟수, 화면 지연, 검토 소요, 현장 승인 대기를 실제로 측정 후 판단 |

목록 최적화는 기존의 전체 작업별 읽기를 줄이는 목표이며 새 색인의 유지 비용을 추가한다. 작업이 적거나 권한 색인 유지가 비싸면 총비용이 증가할 수 있다. 메타·DBA 대기 시간과 개발 작업 시간을 합쳐 단축률로 발표하지 않는다. 금액/속도/품질 개선율을 가정으로 채우지 않는다.

| 자체 검토 발견 | 문서 반영 | 구현·검증 상태 |
|---|---|---|
| 내용 승인 뒤 골드 절차가 생략됐음 | 두 승인·모델 분기·7개 상세 화면 계약 추가 | 미구현 |
| 작업 잠금이 골드 HEAD에 의존 | agent 제어로 분리, 이행·동시성 정의 | 미구현 |
| 기존 publish로는 검증 전에 활성화됨 | 준비/검증/최종 게시 분리, master process 변경 대상 명시 | 미구현 |
| 역할·컬럼 매핑 없이 owner만 변경하면 오동작 | 표별 owner·컬럼 역매핑·source reader 포함 | 미구현 |
| Streamlit 세션/캐시에 승인·권한을 두면 위험 | DB 원장·현재 ACL·폼 제출·공유 캐시 경계 | 미구현 |
| 이관 완료를 실제 사용/품질로 오인 | 설정·소비자·조회·선택·발행 관찰 분리 | 미구현 |

이번 검토는 같은 작성자의 코드·규약 대조다. 독립 에이전트 검토·실행 성능 검증·업무 승인·배포 승인이 아니다. 동반 화면 시안은 설명용 로컬 상태만 바꾸며 실제 원문/승인/신청/적재와 연결되지 않는다. 브라우저 렌더링·현장 Streamlit 상호작용은 미검증이다.

동반 시안은 `09_ARTIFACTS/AUDITS/20261028-ontology-accumulation-plan/ontology-gold-review.html`이다. 문서 내부 파일 링크, HTML ID 참조·중복, 외부 API 호출 부재, JavaScript 구문을 확인했다. 최소 DOM을 모사한 실행에서 승인 전 차단·승인 후 기존 판본 유지·새 모델 대기·적재/검증/사용 전환 분리·복원 등 8조건을 확인했다. 이는 브라우저 클릭/렌더링 또는 Streamlit 검증이 아니다. 앞선 브라우저의 `libnspr4.so` 부재는 해소하지 않았으며 같은 실행을 반복하지 않았다. 검사 범위와 최종 문서/시안/근거 해시는 같은 폴더 `gold-ui-validation.json`에 남긴다. 선택 MAIN 포인터 hash는 `e44a1e05479f2dff2501a6d380d028937a4b1cb8fe6dd5bd7f098b604d729311`로 유지됐다.
