# 멀티턴 Legal agent

[v4 목차](../ONTOLOGY_V4.md) · [구축 순서](BUILD_PLAN.md) · [지식 축적](CONTROLLED_KNOWLEDGE.md) · [조문 진입](SOURCE_ENTRY_COMPOSITION.md) · [검증](VALIDATION_AND_ROLLOUT.md)

2026-10-24 사용자 결정으로 재작성했다. 에이전트는 매 턴 확인한 답·미확인·다음에 갈 수 있는 연결을 보여주고, 사용자는 같은 세션에서 판단을 바로잡거나 더 조사하게 할 수 있다. 이 문서는 설계이며 MAIN103과 GENOS의 실행 방식은 아직 바뀌지 않았다.

## 이미 있는 것

멀티턴의 뼈대는 MAIN103에 이미 있다. 아래 파일은 작업 코드와 MAIN103이 같다.

| 기능 | 현재 코드 |
|---|---|
| 턴 시작에 LLM이 요청 종류를 고름 | [corrected_memory.Memory.resolve](../../../../02_BACKEND/semantic_runtime/legal_agent/corrected_memory.py)가 [memory_methods.py](../../../../02_BACKEND/semantic_runtime/legal_agent/memory_methods.py)의 12가지 중 하나를 고른다 |
| 세션 구분 | [case_repository.py](../../../../02_BACKEND/semantic_runtime/legal_agent/case_repository.py): 세션 → 질문(goal) → 이벤트. 세션 소유자(user·team)를 검사한다 |
| 이전 질문 참고 | 같은 세션의 **직전 질문 1개**의 조사 요약, 현재 질문의 최근 수정 이력 6개 |
| 저장 | 로컬 SQLite |

12가지 요청 종류: `CASE_START`(새 질문), `FACT_UPDATE`(사실만 변경), `STATE_RESTORE`(이전 조건 복원), `PURPOSE_REVISE`(질문 목적 변경), `RESEARCH_REPLAN`(검색 계획 변경), `RESEARCH_REENTER`(지정 단계부터 재조사), `ANSWER_PRESENT`(판단 유지·표현만 변경), `HISTORY_EXPLAIN`(수정 이력 설명), `EXPERIENCE_CONFIRM`(확인된 판단 발행), `EXPERIENCE_REUSE`(동등한 확인 경험 재사용), `WIKI_RELINK`(위키 연결 정정), `NEED_TARGET`(대상 불명, 확인 요청).

빠진 것은 세 가지다.
1. 이전 질문을 최대 10개까지 보는 연결 판단.
2. 판단 기록 하나를 지정해 바꾸는 명령. 지금의 수정 명령은 질문·사실·검색어·문서 범위만 바꿀 수 있다.
3. GENOS 에이전트 레이어 저장.

## 턴 시작 분류

턴이 시작되면 LLM이 먼저 과거 질문과의 연결을 본다.

~~~mermaid
flowchart TD
    A["새 발화"] --> B{"같은 세션의 과거 질문과 연결되는가"}
    B -- 아니오 --> N["새 질문 (CASE_START)"]
    B -- 예 --> C["연결된 질문의 판단 그래프를 봄"]
    C --> D{"경로를 바꾸라는 요청인가"}
    D -- 예 --> M["경로 수정: 판단 재지시 / 검색 계획 변경 / 재조사"]
    D -- 아니오 --> R["기존 경로로 재답변: 표현 변경 / 경험 재사용 / 이력 설명"]
~~~

| 분류 | 쓰는 요청 종류 | 하는 일 |
|---|---|---|
| 새 질문 | `CASE_START` | 처음부터 조사 |
| 경로 수정 | 새 `JUDGMENT_OVERRIDE`(제안), `RESEARCH_REPLAN`, `RESEARCH_REENTER`, `FACT_UPDATE`, `PURPOSE_REVISE` | 지정한 부분만 다시 조사하고 이미 읽은 원문은 재사용 |
| 기존 경로로 재답변 | `ANSWER_PRESENT`, `EXPERIENCE_REUSE`, `HISTORY_EXPLAIN` | 새 조사 없이 기존 판단으로 다시 답함 |

답변 첫 줄에 분류 결과를 한 줄로 보여준다. 예: "② 질문(양도 필요경비)의 경로를 수정해 답합니다 — 시행령 제163조를 추가로 읽었습니다." 분류가 틀리면 사용자가 "새 질문이야"라고 말해 바로잡는다. 그러면 LLM은 `CASE_START`에 `source_turn`(바로 앞 턴 번호)을 넣고, 서버는 그 앞 턴의 발화를 새 질문으로 다시 처리한다. 잘못 분류된 턴의 결과는 지우지 않고 이력으로 남긴다.

조건 변경 비교("한도가 200만 원이면?")는 단계 8 전에는 지원하지 않는다. 그런 발화에는 "불가능함: 조건 변경 비교는 아직 지원하지 않습니다"라고 답하고 기존 답을 유지한다.

## 분류에 넘기는 내용

분류 호출에는 원문 본문을 넘기지 않는다. 사용자에게 보여줬던 판단 그래프를 그대로 넘겨서, 사용자가 "두 번째 거"라고 말한 대상과 LLM이 보는 대상이 같게 한다.

넘기는 양은 두 층이다.

| 층 | 대상 | 내용 | 한도 |
|---|---|---|---|
| 턴 목록 | 같은 세션의 최근 10개 질문(goal). 질문마다 그 질문의 가장 최근 턴 기준 | 질문 번호, 질문(300자), 답 요약(150자), 읽은 조항 이름 목록 | 질문당 약 250토큰 |
| 판단 그래프 | 가장 최근 질문의 가장 최근 턴 1개 | 아래 표 전체 | 약 2,000토큰 |

"질문"은 사건 기록의 goal 하나이고, "턴"은 그 질문 안의 발화 하나다. 한 질문에 후속 턴이 여러 개 있을 수 있다. LLM이 가장 최근 질문이 아닌 이전 질문을 고르면, 그 질문의 가장 최근 판단 그래프로 분류를 한 번 더 한다. 대부분의 후속 발화는 직전 질문을 가리키므로 보통 호출 1회로 끝난다.

토큰 수는 추정이다. 실제 한도는 글자 수로 자르고, 단계 2 ADR에서 실측한다. 참고로 ADR-1037의 호출당 평균 입력은 약 3만 토큰이었다. 위 두 층을 합하면 약 4,500토큰이 늘어난다.

### 판단 그래프에 넣는 것

**읽은 조항마다 연결 목록을 만든다 (2026-10-24 추가).** 조항을 읽으면 코드가 그 조항의 정방향 연결(이 조항이 인용한 곳)과 역방향 연결(이 조항을 인용한 곳)을 바로 모아 판단 그래프에 넣는다. 모델 호출은 없다. 지금은 연결 목록이 조사 흐름의 특정 시점에만 만들어져서, ADR-1037처럼 제97조를 읽고도 "시행령 제163조 → 제97조" 연결이 그래프에 나오지 않을 수 있다.

| | As-Is | To-Be |
|---|---|---|
| 제97조를 읽음 | 제92조 기준 목록만 있음. 제163조는 그래프에 없음 | 제97조 기준 목록을 만듦. "J5 소득세법 시행령 제163조 — 제97조를 인용, 아직 안 읽음"이 보임 |
| 사용자 | 지시할 대상이 없음 | "J5 읽어" 가능 |
| 별표 | 별도 파일 별표는 연결되지 않음 | 같은 법령 폴더의 별표 파일로 연결(2026-10-24 구현) |

ADR-1037 한 질문의 규모: 원문 조회 기록 95건, 읽은 정규 조문 15개, 최종 인용 2개, 판단 5건. 이 규모를 기준으로 정했다.

| 항목 | 넣는 범위 | 이유 |
|---|---|---|
| 턴 머리 | 턴 번호, 분류, 질문, 답 요약, 상태(완료/부분/미확인 n건) | 대상 턴 식별 |
| 읽은 조항 | 전부. 문서명·조항, 읽기 판단(핵심/보조/조건부/보류/안 씀), 사유 1줄(80자) | "그거 가져와"의 대상 |
| 판단한 연결 | 전부. 출발 조항 → 대상(확인/미확인), 연결 타입, 따라감/안 감/보류, 사유 1줄 | "그거 읽어"의 대상 |
| 판단하지 않은 연결 후보 | 읽은 조항당 최대 3개, 턴 전체 최대 20개. 나머지는 "외 N개" | "그 연결 가"의 대상. 전부 넣으면 너무 큼 |
| 전문 검색 결과 | 검색어와 결과 건수만. 모델이 후보로 받았지만 읽지 않은 결과는 최대 5개 제목만 | 검색 결과 전체는 너무 큼 |
| 미확인·부족 | 전부. ID와 내용 1줄 | 다음 행동 안내 |
| 원문 본문 | 넣지 않음 | 재지시로 대상이 정해진 뒤 그 조항만 읽음 |

"외 N개"로 줄인 후보나 검색 결과를 사용자가 지정하면("다른 연결도 보여줘"), 다음 턴에 그 목록을 펼쳐 보여준다.

## 판단 기록 기반 재지시

사용자는 판단 그래프의 항목을 지정해 판단을 바꾸게 할 수 있다.

| 사용자 말 | 대상 판단 | 하는 일 |
|---|---|---|
| "그거 읽어" | 연결 판단 안 감·보류 | 대상 조항을 읽고 다시 판단해 답함 |
| "그 연결 가" | 판단하지 않은 연결 후보 | 대상 조항을 읽고 다시 판단해 답함 |
| "그거 가져와" | 읽기 판단 안 씀·보류 | 이미 읽은 원문을 근거 후보에 넣고 다시 판단해 답함. 새로 읽지 않음 |
| "그거 빼" | 읽기 판단 핵심·보조·조건부(답에 쓴 원문) | 그 원문을 근거에서 빼고 다시 판단해 답함. 새로 읽지 않음 |

읽는 범위는 그 연결의 기존 읽기 범위다. 기존 규칙대로 연결이 요구하는 블록(`required_block_ids`) 전체, 즉 대상 본문과 그에 붙은 단서·상위 항·호의 조건을 함께 읽는다.

"그거 가져와"는 지시대로 그 원문을 다시 판단에 넣는다. 다시 판단해도 그 원문이 질문의 근거가 되지 않으면 억지로 인용하지 않고 "불가능함: 이 원문은 ○○에 대한 근거가 되지 않음 — 이유"로 보고한다.

"그거 빼"는 그 원문을 이번 답의 근거에서 뺀다. 그 원문에만 기대던 주장은 답에서 빠지고 미확인으로 표시된다. 이미 답에 쓰지 않은 원문이면 "불가능함: 이미 답에 쓰지 않는 원문"으로 보고한다. 원문 자체나 다른 질문의 판단은 바꾸지 않는다.

잘못 가져온 조문을 바른 조문으로 바꾸는 정정("200만 원짜리 말고 100만 원 규정")은 "빼"와 "읽어" 두 지시로 처리한다.

**사용자가 문서와 조문을 직접 말하면 그래프에 없어도 읽는다 (2026-10-24 변경).**

| | As-Is (이전 규칙) | To-Be |
|---|---|---|
| "시행령 163조 읽어", 그래프에 제163조 없음 | "불가능함: 판단 그래프에 없는 조문 — 다음 턴에 찾아달라고 요청" | 서버가 "소득세법 시행령 제163조"가 실제로 있는지 정확한 조문 조회로 확인하고 읽음 |
| 어느 법의 시행령인지 말하지 않음 | — | 연결된 질문이 읽은 문서들에서 찾음. 하나면 읽고, 여럿이면 되물음 |
| 문서·조문 번호 없이 "그 규정 읽어" | — | 그래프에서 대상을 찾고, 없으면 "불가능함: 대상을 특정하지 못함" |

조항 번호는 사용자가 말한 것만 쓴다. LLM은 사용자의 말에서 문서명·조문을 옮겨 적을 뿐 번호를 만들지 않는다. 서버는 그 조문이 요청 범위의 문서에 정확히 하나 있을 때만 읽는다. 이 지시는 `change: "READ_NAMED"`로 표시하고 3개 한도에 포함한다.

동작 규칙:
- **개수.** 한 발화에 재지시는 3개까지 실행한다. 4개 이상이면 발화에 나온 순서대로 앞 3개만 실행하고, 답변에 "한 번에 3개까지 가능합니다. 실행하지 않은 지시: …"로 나머지를 그대로 보여준다. 나머지는 다음 턴에 다시 요청하면 된다.
- **실행 결과 보고.** 지시마다 결과를 따로 보여준다: 실행함 / 불가능함(이유). 불가능한 지시가 있어도 나머지 지시는 실행한다.
- **대상 특정.** 사용자는 "시행령 163조 읽어"처럼 자연어로 말한다. LLM이 판단 그래프에서 대상을 찾는다. 후보가 여럿이면, 지시가 하나뿐인 발화는 `NEED_TARGET`으로 후보 2~3개를 보여주고 되묻는다. 여러 지시 중 하나만 모호하면 그 지시만 "불가능함: 대상을 특정하지 못함"과 후보를 보여주고 나머지는 실행한다. 화면에는 항목마다 번호(J1, J2 …)를 붙여 "J3 읽어"도 되게 한다.
- **범위.** 지정한 조항만 읽는다. 그 조항에서 새 연결이 나오면 따라가지 않고 다음 턴 안내로만 보여준다. 계속 번지는 것을 막기 위해서다.
- **재사용.** 이미 읽은 원문과 바뀌지 않은 판단은 그대로 쓴다.
- **기록.** 원래 판단, 재지시, 바뀐 결과를 모두 남긴다. 재지시는 [지식 축적](CONTROLLED_KNOWLEDGE.md#모으는-판단)의 재료가 된다.

제안하는 요청 종류(아직 없음):

LLM이 내는 형식:

~~~json
{
  "method_id": "JUDGMENT_OVERRIDE",
  "targets": [{"label": "J3", "change": "READ"}],
  "not_executed": [],
  "utterance": "시행령 163조 읽어"
}
~~~

- `label`은 판단 그래프의 화면 번호 중에서만 고를 수 있다(스키마의 enum). 서버가 `label`을 그 그래프의 `judgment_id`로 바꾸고 `view_hash`를 붙여 저장한다. LLM은 `judgment_id`·조항 번호를 쓰지 않는다.
- `change`는 `READ`(안 감·보류 연결 읽기), `FOLLOW`(미판단 후보 따라가기), `USE`(이미 읽은 원문 사용), `EXCLUDE`(답에 쓴 원문 빼기), `READ_NAMED`(사용자가 말한 문서·조문 읽기) 중 하나다. `READ_NAMED`는 `label` 대신 `{"document": "소득세법 시행령", "article": "제163조"}`를 쓰고, 서버가 정확한 조문 조회로 대상을 정한다. 대상 판단의 종류와 맞지 않으면(예: 이미 읽은 원문에 `READ`) 서버가 그 지시를 "불가능함: 지시와 대상이 맞지 않음"으로 처리한다.
- `targets`는 최대 3개다. 4개 이상이 나오면 서버가 발화 순서대로 앞 3개만 남기고 나머지를 `not_executed`에 넣어 응답에 보여준다.

### 재지시 실패 처리

| 상황 | 처리 |
|---|---|
| 대상을 못 찾음·여럿 | 그 지시는 "불가능함: 대상을 특정하지 못함"으로 보고하고 후보 2~3개를 보여준다. 다른 지시는 실행한다 |
| 한 발화에 4개 이상 | 앞 3개만 실행. "한 번에 3개까지 가능합니다"와 실행하지 않은 지시 목록을 보여준다 |
| 대상 조항이 미확인(예: "대통령령"만 있고 대상 조문이 확정되지 않음) | 구조 조회로 대상을 찾는다. 못 찾으면 "불가능함: 대상 조문을 찾지 못함"으로 보고하고 기존 답을 유지한다 |
| 읽기 실패·권한 없음·원문 해시 불일치 | "불가능함"과 실패 이유를 보여주고 기존 답을 유지한다. 실패를 "근거 없음"으로 기록하지 않는다 |
| 예산 소진 | 실행한 지시까지 답하고, 남은 지시는 "불가능함: 이번 턴 예산 소진"으로 보여준다 |
| 같은 대상을 같은 상태에서 다시 지시 | 기존 결과를 다시 보여준다. 새로 읽지 않는다 |

## 턴마다 보여주는 것

| 항목 | 내용 |
|---|---|
| 분류 한 줄 | 새 질문 / 몇 번째 질문의 경로 수정 / 재답변 |
| 확인한 답 | 실제 읽은 원문에 연결된 내용 |
| 미확인 | 무엇을 못 봤고 답에 어떤 영향이 있을 수 있는지 |
| 판단 그래프 | 위 표의 범위. 항목 번호(J1…) 포함 |
| 다음에 할 수 있는 것 | 읽을 수 있는 연결, 재지시 방법 |

읽지 않은 조항은 내용을 요약하지 않는다. 연결 근거에서 알 수 있는 것만 쓴다. 예: "자본적지출액의 세부 범위를 정한 시행령 조항 — 아직 읽지 않음." 대상 조항 번호가 확정되지 않았으면 "대통령령의 대응 조문 찾기"처럼 할 일로 쓴다.

그래프를 그리지 못하는 화면에서는 같은 내용을 표와 번호 목록으로 보여준다.

## 세션과 저장

- 멀티턴은 **한 세션 안에서만** 된다. 다른 세션의 질문은 분류 대상에 넣지 않는다.
- 세션 ID는 GENOS 채팅 앱의 세션 ID를 그대로 `session_id`로 쓴다. 보존 기간은 현장 정책을 따른다.
- 대화 중 사용자가 알려주거나 정정한 용어("스톡옵션은 주식매수선택권 말하는 거야")는 용어 관찰로 기록하고 **그 세션 안에서만** 바로 검색에 추가한다. 다른 사람·세션에는 용어 후보 승인과 골드 적재 뒤부터 적용된다. [용어집](LANDING.md#용어집--별도-도구).
- 세션·턴·질문·답·판단 기록·재지시·보여준 판단 그래프는 모두 사용자 로그이자 LLM 판단이므로 에이전트 레이어에 둔다. 온톨로지 작업 JSON(S3)과 섞지 않는다. [저장 위치](CONTROLLED_KNOWLEDGE.md#저장-위치).
- 로컬: 기존 SQLite 구조(세션 → 질문 → 이벤트)를 그대로 쓴다.
- GENOS: 에이전트 레이어 테이블에 세션 키로 나눠 쌓는다. GENOS 서빙에는 저장하지 않는다. 턴이 시작되면 그 세션의 최근 10개 질문만 조회한다.
- 테이블 설계는 [골드 메타 규약](../DATAIKU_GOLD_METADATA_20261022/README.md)의 이름·타입 규칙을 따른다(단계 7).

## 예산과 재개

- 턴 하나의 예산은 현행 프로필의 요청 예산(모델 호출 40회, 도구 1,024회, 1,800초)을 그대로 쓴다. 분류 호출도 이 안에 들어간다.
- 같은 요청의 네트워크 재시도는 처음 마감 시간과 누적 사용량을 그대로 쓴다.
- 세션 누적 사용량은 기록만 하고 이번 단계에서 한도는 두지 않는다. 같은 대상·같은 상태의 같은 실패는 턴이 바뀌어도 다시 시도하지 않는다.
- 출력 토큰 상한은 두지 않는다(현행 정책).
- 발행 계약은 그대로다. 턴마다 기존처럼 FINAL로 발행하고, 부분 답은 기존 PARTIAL/LIMITED_ANSWER를 쓴다.

턴 종류별 예상 시간 (ADR-1037 호출당 평균 약 38초 기준, 외부 Qwen 수치. GENOS 내부 모델은 다름):

| 턴 | 호출 | 예상 |
|---|---|---|
| 기존 경로로 재답변 | 분류 1 + 답변 1 | 약 1분 |
| 재지시로 조항 1개 추가 | 분류 1 + 읽기 판단 1 + 재평가 1 + 답변 1 | 약 2~3분 |
| 새 질문 | 처음 조사와 같음 | ADR-1037은 약 4.4분 |

| "그거 가져와" (안 씀 판단) | 새 조회 없이 그 원문을 근거로 재판단 |

| 다른 세션 | 분류 대상에 안 들어감 |
| 읽기 실패·권한·해시 | 기존 답 유지, 실패 이유 표시 |

실패 처리는 [실패 복구 정책](../../OPERATIONS/AGENT_FAILURE_RECOVERY_POLICY.md)을 따른다. 실모델 확인은 단계 2 뒤 ADR로 한다.
