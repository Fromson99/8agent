비LLM 1초 목표와 판단 ID·복구 수정 계획
2026-10-27 / 설계안 / 기준: 선택 MAIN106

먼저 볼 요약

1. 행동·원문·답변을 보존하는 성능 수정부터 묶어서 검증한다.
2. 불필요한 용어 조회 → 스키마 준비 재사용 → 묶음 원문 조회 → 검색 재사용 → 20개 선준비 순이다.
3. 이후 문서·판단·근거 번호를 고정하고, 새 판단만 쓰는 입력으로 바꾼다.
4. 보완 오류는 행·대상까지 알려준다. 실패한 판단은 pending으로 보존한다.
5. 실패한 판단의 재시도와 별개인 추가 원문 확보를 분리한다.
6. 최종 통합 코드 검증 → MAIN 승격 → 실제 service 진입점 확인까지 계획에 포함한다.

이번 문서는 계획이다. 제품 코드 수정·새 실험·LLM 호출·MAIN 변경은 실행하지 않았다.
1초는 사용자 목표이며, 아직 달성 가능 시간이나 성공률을 실측해 예측한 값이 아니다.


1. 기준과 측정 범위

[관측 M1] 이전 실제 질문: 비LLM 82.254초, 초기 준비 18.054초, 탐색 자료 구성 41.269초.
[계산 C1] 나머지 = 82.254 - 18.054 - 41.269 = 22.930초.
[계산 C2] 초기 준비 전부를 제외해도 82.254 - 18.054 = 64.200초.
초기 준비에는 용어집 외 구조·매칭·색인 준비도 있으므로 C2는 낙관적인 하한 비교다.

[목표 G1] 용어집 로딩을 제외한 요청 전체 비LLM 시간 합계 1.000초 이하.
첫 화면, 페이지 이동, 도구 실행, 입력 조립, 응답 파싱·검증, 복구, 저장·발행을 포함한다.
1초/화면으로 기준을 바꾸거나 전체 session.prepare를 빼서 달성했다고 하지 않는다.
용어집 외 초기 준비가 요청 안에 남아 있으면 그 비용도 포함한다.
새 질문의 검색 캐시 miss도 평가하며 같은 질문의 재조회 hit만으로 통과시키지 않는다.

계산은 요청 경과시간에서 실제 모델 통신 구간의 합집합과 용어집 로딩 구간의
겹치지 않는 합집합을 빼는 방식이다. 파싱·스키마 검사·전송 직전 조립은 비LLM이다.
모델 장애의 backoff/재시도 대기는 별도 표시하고 유리하게 숨기지 않는다.
프로세스 초기 시작·용어집 캐시 준비·일반 요청 상태를 각각 표시한다.

기존 9응답/4화면은 known-case 재현 기준으로 사용한다.
다른 질문, 문서 범위, 긴 조사, 캐시 miss는 별도로 측정해 적용 범위를 보고한다.
소수 반복으로 일반 p95나 모든 질문의 1초 보장을 주장하지 않는다.
목표 미달이면 실제 잔여를 기록한다. 결과를 보고 성공 기준을 낮추지 않는다.

      finding: 모델이 원문을 읽고 확인한 내용

  read_judgment_final.py / completion_execution.py의 판단·최종 답변 소비자

호환/이행:
  번호 원장은 기존 조사 checkpoint/entity 저장을 사용하고 별도 서비스는 만들지 않는다.
  번호 배정은 조사 상태의 기존 소유자·revision 트랜잭션에서 한 번만 확정한다.
  전송 전 저장 view와 같은 mapping/hash를 결속하고 동시 변경이면 늦은 응답을 적용하지 않는다.
  compact 입력·별칭·판단 응답 계약 버전을 함께 올린다. 정상/preview/보완이 같은 버전을 쓴다.
  기존 요청은 이전 버전으로 이어가거나 보관 mapping이 입증되는 명시적 이행만 허용한다.
  과거 자연어의 D번호를 정규식으로 임의 치환하지 않는다. 당시 문서 mapping을 따로 표시한다.
  다시 나타난 후보, 문서 제외/추가, 재시작에서도 번호 충돌·재번호 부여가 없어야 한다.

순서 F. 구체적인 보완 안내와 추가 원문 확보의 분리

기존 → 실제 결과:
  read_judgment.validate_review는 일반 오류 문자열만 던졌다.
  보완 호출은 오류 행·중복/누락 ID 없이 전체 잘못된 응답을 다시 받았다.
  모델은 판단 7행을 그대로 반복했고, 이후 추가 원문 조사도 같은 보완 예산에 막혔다.

수정 → 원하는 결과:
  기존 OutputContractError/issue를 사용해 오류 코드·필드 경로·관련 행·허용 근거를 모두 전달한다.
  예: 6/7행 J1 중복, 새 J6 미제출, J2의 현재 근거 E4/E7과 제출 E20 불일치.
  새 계약에서 미제출 pending은 오류와 구분한다. 실제 제출한 중복/오연결만 수정 대상이다.
  같은 view·스키마와 1회 보완 담당은 유지하고, 전체 응답을 다시 받아 재검증한다.
  과거 응답은 보존하되 수정해야 할 곳을 앞에 짧게 제시한다.

  판단 결과와 원문 확보 상태를 분리한다.
  잘못된 판단은 채택하지 않는다. 새로 제시된 유효 원문 부족 대상이 있으면
  그 대상을 읽는 제한된 행동 선택을 기존 조사 실행기로 연결할 수 있게 한다.
  실패한 판단에 의존한 행동, 잘못된 ID를 임의로 바꾼 행동은 실행하지 않는다.
  대상·원문 결속·새 확보 범위로 독립 조사를 식별하고 같은 부족의 표현 변경은 재시도로 센다.
  추가 원문도 없고 같은 오류만 반복되면 제한 답변/중단으로 끝낸다.

변경 위치:
  read_judgment.py, output_contract.py::bounded_decision/CorrectionBudget
  request_repair.py, law_navigation.py::request_decision/run/bounded_result
  completion_execution.py 및 기존 gap/reentry journal 소비자

검증:
  합성 잘못된 응답 → 정확한 오류 위치 → 1회 보완 성공/반복 실패를 모두 검사한다.
  원문·권한·상태 hash 오류는 복구 대상으로 완화하지 않는다.
  새로운 유효 gap이면 실제 READ와 receipt가 남고, 동일 실패면 호출이 늘지 않는다.
  판단 pending, 미확인, 최초 deadline, 모델/도구 카운터는 재개·중복 요청에서도 보존한다.
  정상 HTTP만으로 성공 판정하지 않고 PARTIAL/LIMITED/충분한 답변 상태까지 확인한다.


4. 자원·SQL와 캐시의 공통 조건

묶음별 키와 수명:
  스키마 검증기: 정확한 스키마+검증 설정, 요청 수명, 제한된 LRU/메모리.
  원문 재사용: 세대+판본+권한+블록, 일관된 준비 작업/요청 수명, 실패 결과 저장 금지.
  검색 결과: 세대+색인+정책+검색어+허용 범위, 제한된 메타데이터만 저장.
  페이지: 검색 결과 결속+정렬+페이지+메뉴 계약, 조사 checkpoint 수명.
  별칭: 조사+정본 객체/판본/근거 범위, 재개에 복원되는 기존 원장 수명.

키에 법률 답변이나 사용자별 사실을 섞어 다른 요청의 정답처럼 재사용하지 않는다.
cache miss/첫 구축/삭제/무효화 비용과 메모리 점유도 측정한다.
캐시의 손익분기는 '줄인 재계산 시간 > 키 계산+저장+조회+무효화 시간'이다.
거의 반복되지 않는 큰 범위에서는 임시 결과를 만드는 쪽이 느릴 수 있으므로 비교한다.

로컬은 SQLite의 실제 권한 TEMP VIEW가 연결된 동일 환경에서 실행 계획을 확인한다.
Oracle은 반복 점조회를 그대로 N번 원격 호출로 옮기지 않고 묶음 조회·필터 선적용을 설계한다.
Oracle 바인드/배치 크기·임시 결과 기능은 실제 어댑터와 실행 계획 확인 뒤 정한다.
개발 지식 조회는 SIDDS.*_S, 판단·로그는 SIDDA.*_A 책임을 유지한다.
GENOS에 전체 원문·색인을 내려받거나 공유 캐시를 영속 저장하는 구조는 제안하지 않는다.
공유 결과가 필요하면 서빙 밖 데이터 계층에서 버전·권한을 관리한다.
로컬 1초 측정과 Oracle/GENOS 현장 1초 검증은 별도다.
