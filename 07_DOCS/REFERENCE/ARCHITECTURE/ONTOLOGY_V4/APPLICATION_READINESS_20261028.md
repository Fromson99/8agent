# 온톨로지 실제 적용 — 구현 상태와 남은 작업

**실제 숏컷 연결 후속:** 현재 게시된 실제 숏컷 51개 중 50개를 숏컷 결속 원문 판본·span과 대조하여 로컬 준비함의 44개 원문 묶음으로 연결했다. 1개는 128원문 단위 한도 초과로 보류했고 STALE/RETIRED 153개는 제외했다. 로컬 화면은 `http://127.0.0.1:8519`이며 공개 예시 터널과 분리했다. 실제 LLM 초안 생성은 외부 전송에 대한 자동 승인 검토 거절로 미실행, 모든 묶음 INPUT·사람 승인0·Gold 게시0이다. ADR1187은 승인 대기·미완료이며 현장 Dataiku 연동이나 현행 RAG 판본으로 재결속한 것이 아니다. [상태 기록](../../../../09_ARTIFACTS/AUDITS/20261028-ontology-real-shortcuts/현재상태.txt).

**최신 r4 — 표형 기록:** 모인 기록·검토 목록은 `항목명 / 상태 / 기록 수 / 근거 원문`, 선택 묶음의 조사 기록은 `번호 / 판단 내용 / 판단 이유 / 근거 원문` 표다. 행 왼쪽 선택 → 아래 상세 → 기존 초안 생성·사람 승인으로 연결된다. 긴 판단 내용은 줄바꿈하고 모바일은 표 안에서 가로 스크롤한다. 기존 23검사 통과, 외부 HTTPS에서 실제 행 선택·정렬 후 선택·상태 필터·생성·승인과 1280/390폭을 확인했다. [r4 설치 안내](../../../../08_DEPLOYMENT/DATAIKU/ontology_dashboard_20261028_r4/GUIDE.txt) · [검증 기록](../../../../09_ARTIFACTS/AUDITS/20261028-ontology-table-ui/VALIDATION.json). 표 변경만으로 새 수집 연결·서버 페이지 조회·골드 반영을 구현한 것은 아니며 아래 후속 과제는 유지한다.

**최신 r3 — 기록 확인·생성·승인 연결:** 사용자 요청으로 단순한 3단계 `모인 기록 → 초안 만들기 → 검토·승인`을 복원했다. 첫 단계는 기존 온톨로지 준비함의 원문·판단 입력을 읽으며 전체 숏컷 저장소를 자동 가져오거나 여러 묶음을 병합하지 않는다. 생성은 사람이 버튼을 누를 때 기존 `Workflow.propose`를 호출하고 DRAFT로 저장한다. 운영 모델 미설정은 비활성, 합성 데모는 명시적인 예시 생성 어댑터를 사용한다. 사람의 원문 확인·승인/반려와 골드 후속 절차는 별도다. 실제 화면 흐름 23검사와 외부 브라우저의 3단계·1280/390폭을 확인했다. [r3 설치 안내](../../../../08_DEPLOYMENT/DATAIKU/ontology_dashboard_20261028_r3/GUIDE.txt) · [검증 기록](../../../../09_ARTIFACTS/AUDITS/20261028-ontology-create-approve-ui/VALIDATION.json). 아래 r2의 생성 진입점 제거는 이전 상태다. 전체 숏컷 수집/개념 병합, 다중 세션 생성 멱등성·Dataiku 장기 작업 원장, 실제 Gold/GENOS 연결은 여전히 후속이다.

**후속 사용자 정정 — 승인 중심으로 단순화:** 실제 화면을 한 개 승인함으로 교체했다. 목록 → 내용·근거 원문 → 승인/반려 → 골드 반영 안내만 남겼다. 그래프·재지시·가정 비교·JSON 편집·생성/업로드·이관 요청 작성·별도 이력 메뉴는 화면에서 제거했다. 기존 원문·권한·판본 검사와 승인 저장은 유지한다. 승인 시 원문 확인 체크가 필요하고 의견은 선택이며, 반려 이유는 필수다. 골드 적재 완료를 표시하거나 실행하지 않는다. 아래 6화면 표·41검사는 이전 r1 기록이다. 최신 화면은 [r2 설치 안내](../../../../08_DEPLOYMENT/DATAIKU/ontology_dashboard_20261028_r2/GUIDE.txt)와 [승인 UI 검증](../../../../09_ARTIFACTS/AUDITS/20261028-ontology-approval-ui/VALIDATION.json)을 따른다. P1~P6의 실제 적용 과제는 유지한다.

기준일: 2026-10-28. 범위: 실제 코드·선택 릴리스·검증 기록을 대조한 설계 반영과 적용 계획. **이번 문서 작업에서 제품 코드·데이터·MAIN 선택·현장 배포는 변경하지 않았다.**

현재는 **고정 시나리오 생성·검토·개발 DB 게시·원문 도착 시 조회 기반과 Streamlit 대시보드**가 있다. 실제 적용의 남은 핵심은 **승인 데이터 준비, 운영 골드 이관, 현장 조회 연결, 다른 질문에서의 재사용 확인**이다. 화면 구현이나 ON 설정만으로 실제 적용 완료가 되지는 않는다.

## 2. 완료 목표를 세 단계로 나눈다

| 단계 | 실제로 보여야 할 결과 | 이 단계의 필수 범위 |
|---|---|---|
| A. 첫 실제 적용 | 질문 A의 관찰로 만든 한 개념을 검토·골드 반영한 뒤, **다른 질문 B**가 같은 원문에 도착해 해당 판본을 재사용 | 아래 P1~P6. 단일 개념·제한된 업무 범위로 시작 가능 |
| B. 반복 축적 운영 | B의 새 관찰이 같은 개념의 r2 제안에 연결되고, 재승인·골드 반영 뒤 질문 C에서 사용 | 안정 개념 ID, 관찰 중복 제거, 판본/충돌/보류/분할·병합, 작업 재접속 |
| C. v4 확장 | 사용자가 특정 판단을 재지시하고, 새로운 구조를 제안·검토하며, 조건 변경 영향을 계산 | 대상 지정 명령·턴 계약, 동적 스키마·매핑, 용어·별칭/랜딩, 실제 계산·영향 분석 |

B·C 전체 구현을 A의 선행 조건으로 두지 않는다. A도 개발 DB 데모 성공과 운영 골드에서의 실제 사용 성공을 구분해 기록한다.

| 순서 | 현재 문제·관찰 | 구현·현장 작업 | 종료 조건·책임 역할 |
|---|---|---|---|
| P1 승인할 지식 한 건 | 배포본에 실제 온톨로지 데이터 없음. 과거 알려진 질문 성공을 새 품질 인증으로 사용할 수 없음 | 업무 범위·원문 판본·조항·인용·필수 원문·성립/제외 경로·미확인을 고정한 씨앗 묶음 준비. 검토자가 정확한 판본 승인 | 원문과 경로별 근거를 재검증할 수 있는 승인 영수증. 업무 검토자·개발 |

| P3 운영 골드 모델 | 현재 5표는 SIDDA 고정명·동일 owner. 골드 3표 후보와 승인된 실제 모델은 다름 | 승인 모델 재사용 여부 확인. 필요하면 표준·모델·DBA 신청. 실제 owner/표/컬럼/타입/설명/권한 매핑과 원문 읽기 매핑 검증. 작업 잠금을 골드 HEAD와 분리 | 승인 증빙과 실제 DB metadata가 일치하고 검토 계정은 골드 쓰기 없이 작업 가능. 메타 담당·DBA·개발 |

| P5 GENOS 조회 연결 | 개발 GENOS는 실버 조회 가능, SIDDA 온톨로지 소비 권한 미확인. 운영 골드 소비 매핑도 없음 | 승인된 직접 조회 또는 허용된 점조회 API를 확정·구현. 원문 도착→권한 확인→게시본 조회 경로와 설정·재시작·실제 배포 리비전 확인 | 대상 게시 ID/hash를 실제 GENOS가 읽고, OFF/빈DB/조회 실패는 기존 RAG로 돌아감. 현장 운영·DB 담당·개발 |
| P6 다른 질문으로 실사용 확인 | 게시 영수증과 실제 답변 사용을 한 흐름으로 추적하지 못함. 경로 선택·필수 원문 확보 실패도 남음 | 동일 후보 코드/원문/게시판본으로 B 실행. run→도착 원문→게시본→선택 경로→실제 원문→답변·미해결을 기록. 비교가 필요하면 같은 조건의 OFF/ON 계획을 먼저 고정 | 모든 인용/권한/판본 일치, 사전 정의한 필수 원문과 답변 완료 조건 통과. 첫 사례의 성공 범위만 보고. 개발·업무 검토자 |

P1·P2·P3 준비는 병행할 수 있다. P4는 승인된 매핑에 맞춰 만들고, P5 소비자 계약과 함께 검증한다. P6은 같은 최종 코드와 데이터로 실행한다. 운영 스키마 이름·권한을 문서 예시에서 추정해 채우지 않는다.

`LEGAL_ONTOLOGY_WORK`는 논리적 관리 폴더 이름이며 실제 ID를 확인한다. 원문 업로드 폴더 `LEGAL_RAG/ehA8dpVm`를 온톨로지 작업 폴더로 임의 재사용하지 않는다. 수집 스위치 `GENOS_ONTOLOGY_CAPTURE_ENABLED`와 소비 스위치 `GENOS_RAG_ONTOLOGY_ENABLED`는 별개다. 수집을 켜도 RAG 사용이 자동으로 켜지지 않는다.

## 4. 승인 이후의 정확한 저장·사용 절차

```text
질문·읽기 판단 → 에이전트 로그 → Dataiku 입력 → S3 작업 JSON
 → 생성/수정 → 정확한 작업 판본 내용 승인
 → 승인 모델 재사용 확인 또는 표준·모델·DB 생성 신청
 → 실제 DB·매핑 확인 → 고정 적재 패키지
 → Dataiku가 PUB/ANC 적재 → 저장·원문·권한·소비자 조회 검증
 → 활성 HEAD와 감사 기록 전환 → 새 질문의 원문 도착 시 사용
```

S3 작업 JSON·관찰·승인 이력은 보존한다. 운영 골드에는 승인된 게시본(PUB)·원문 연결(ANC)·활성 선택(HEAD)을 적재한다. 작업/판단/실행 로그는 에이전트 영역에 남는다. 용어·별칭도 별도 검토 후 같은 승인·신청·SQL 적재 절차를 거친 다음 사용한다.

현재 이관 요청에는 `model_reference_verification=OPERATOR_SUPPLIED_NOT_VERIFIED`가 들어간다. 운영자가 모델 번호를 입력했다고 승인 모델 확인이 완료된 것이 아니다. 요청 JSON은 작업 저장소에 남지만, 화면의 요청 hash는 `st.session_state`에만 있다. **재접속 후 요청 검색·처리 상태 복원·적재 재개는 아직 없다.** 이 요청을 검증된 SQL 적재 패키지로 부르지 않는다.

제안 영속 원장에는 요청 ID, 승인 revision/hash/영수증, 매핑 판본, 패키지 hash, 대상 DB 계약, Dataiku run/attempt, 단계별 상태/오류/검증/활성 전환 영수증을 둔다. 구체 테이블·컬럼은 승인 모델에 맞춰 확정한다. 화면은 명령 접수와 영수증 조회를 맡고, 작업·재시도·취소·결과 저장은 Dataiku가 맡는다. GENOS는 계산만 수행하며 S3 직접 접속·영속 작업 레지스트리·전체 로컬 DB 복원을 추가하지 않는다.

사용 전환 시에는 최신 승인·매핑·검증 결과·예상 HEAD를 재검사한다. HEAD와 필수 감사 기록을 같은 DB 트랜잭션으로 기록할 수 있는 구조를 정한다. 에이전트 쪽 관찰 복제는 별도 확인 가능하게 한다. 분산 DB 사이에 원자성이 있다고 가정하지 않는다. 기존 `Repository.publish`를 운영 매핑으로 이름만 바꿔 호출하는 것은 이 절차의 구현이 아니다.

## 6. 첫 적용 검증과 실패 처리

| 상황 | 요구 결과 |
|---|---|
| 승인만 완료, 또는 PUB만 적재 | 새 HEAD 없음. 현재 r1 유지 |
| 승인 후 수정·동시 검토 | 이전 승인 상속 없음. 늦은 명령 충돌 표시, 이전 대기 패키지 재검토 |
| 원문 판본·인용 변경 또는 권한 회수 | 근거 검증 실패/권한 제한. 유사 문자열로 임의 대체하지 않음 |
| 적재 후 응답 유실·중복 클릭·재접속 | 원래 요청/패키지 ID로 영속 상태 확인. 새 생성/중복 적재/자동 재활성화 금지 |
| 원문 연결 일부 저장 실패·해시 불일치 | 활성 전환 차단. 부분 상태/재개 지점 표시, 기존 판본 보존 |
| 온톨로지 없음·조회 불가·맞는 경로 없음 | 일반 RAG로 복귀. EMPTY와 UNAVAILABLE을 화면/로그에서 구분 |
| 게시 중지·롤백 | 새 요청부터 선택 변경. 진행 중 요청의 판본 고정과 현재 원문 권한 검사는 유지 |
| 경로를 선택했지만 필수 원문 부족 | 부족 사유·제한 답변. 선택·게시 성공을 답변 완성으로 표시하지 않음 |

첫 적용 시나리오는 **A 관찰 저장 → 한 묶음 생성·수정·승인 → 골드 적재·검증·사용 전환 → 다른 질문 B의 재사용 → 중지/복원 확인**이다. 같은 원문에 도착하기 전의 검색 성공과 도착한 뒤의 온톨로지 효과를 나눠 본다. 전체 응답 시간, 모델 호출·도구 수, 필수 원문 확보, 인용 일치, 미해결 범위를 기록하되 단일 사례로 품질·속도 개선율을 일반화하지 않는다.

운영 도입은 최종 후보의 계약·동시성·실제 DB 검증 → 공식 코드 선택/현장 반입 → 제한 범위 적용 순서다. 문제 발생 시 신규 이관 명령 중지, 진행 작업 확인, 필요 시 검증된 이전 HEAD 복원 또는 소비 OFF, 이전 검증 코드 선택을 수행한다. 작업·승인·실패 이력은 지우지 않는다. 이번 문서 반영 자체는 이 실행이나 승격을 수행하지 않는다.

## 7. 질문 조사 품질의 최신 미해결 상태

[ADR1178 결과](../../../../09_ARTIFACTS/AUDITS/20261028-response-contract-recovery/수정과_재시험결과.txt)를 기준으로 **001은 8호출/146.752초로 완료 조건 통과**, **007은 11호출/360.868초로 두 시장 상장규정 13조 미확보**, **009는 이 최신 연속 시험에서 미실행**이다. 이전 1175의 009 실행 결과와 구분한다.

최종 1178에는 상위 원문에 포함된 하위 블록의 충족 판정을 추가했다. 기술 263검사 통과, 회귀 211건 중 189통과/기존 실패9/준비 오류13 동일·새 회귀0이다. **최종 포함 판정 수정 후 실제 모델 재검증·작업 제품 통합·MAIN 승격·GENOS 확인은 미수행**이다. 007의 필요한 문서 선택/제외 판단 문제가 해결된 것으로 확대하지 않는다.

이 작업은 첫 적용 범위의 필수 원문·답변 완료 조건을 충족하는지 확인할 때 함께 다룬다. 모든 일반 RAG 문제 해결을 작은 온톨로지 적용의 선행 조건으로 두지는 않으며, 미통과 사례는 별도 회귀·품질 과제로 유지한다. 신규 실험을 한다면 당시 정책과 예산·최종 코드/데이터를 고정한 뒤 실행한다. 이번 문서 작업의 모델 호출은 0회다.
