# 판단 전달과 대화 정정

[v4 목차](../ONTOLOGY_V4.md) · [제한된 지식 형식](CONTROLLED_KNOWLEDGE.md)

## 사용자에게 전달할 판단

외부에 설명할 판단은 결론 한 문장이 아니라 주장·이유·근거·범위·미확인의 묶음이다. 정형 화면을 위해 대화의 모든 문장을 객체로 강제하지 않는다. 중요한 판단과 정정 대상은 작은 메타데이터 봉투에 연결한다. 아래는 제안하는 논리 항목이며 신규 DB 테이블이나 확정 wire 스키마가 아니다.

| 항목 | 사용자 표시 | 기록 책임 |
|---|---|---|
| 현재 판단 | 무엇이 확인됐고 무엇을 잠정적으로 보는가 | LLM의 외부에 제시한 주장 원문 |
| 이유 | 질문·원문과 어떻게 연결되는가 | 판단 시 제출한 설명; 사후 생성이면 별도 표시 |
| 실제 근거 | 문서명·판본·조항과 인용 원문 | 서버가 기존 source receipt에서 조립 |
| 적용 범위·가정 | 대상·시점·상황, 사용자가 준 사실 | 출처를 사용자 사실·원문·가정으로 구분 |
| 미확인·이견 | 부족한 자료, 다른 해석, 제외한 경로의 이유 | 상태·이전 버전·반대 근거 보존 |
| 다음 행동 | 무엇을 더 확인하려는가 | 선택한 도구·대상 ID와 실행 결과 연결 |
| 정정 대상 | 이 판단·이 근거·이 연결을 수정 | 안정된 ID, revision, view hash |

이유는 검토 가능한 설명이다. 모델의 비공개 내부 추론이나 완전한 인과 설명으로 표현하지 않는다. 설명이 없으면 사유 미제공으로 표시하고 새 문장을 만들어 원래 이유처럼 저장하지 않는다.

## 원장과 화면의 일치

저장은 기존 journal/checkpoint를 실행 정본으로 삼는다. 사용자가 보는 화면은 현재 head와 source receipt에서 만드는 읽기 전용 투영이다. 화면 JSON을 다시 정본으로 덮어쓰지 않는다.

각 표시에는 현재 run·판단 revision·원문 binding·projection hash를 붙인다. 제시됨, 선택됨, 원문 확보됨, 모델 입력에 전달됨, 사용한다고 명시됨, 의미 검토됨을 별도로 남긴다. 사용자 화면에 실제로 표시됐는지는 presentation 이벤트로 구분하며 모델 입력 포함만으로 사용자 열람을 주장하지 않는다.

화면은 요약과 원문·수정 이력을 펼쳐보는 형태로 구성한다. 현재 답변에서 사용하지 않은 과거 판단도 접근권한 안에서 이력으로 찾을 수 있게 한다. 부적합·철회·충돌 지식을 현재 승인 지식처럼 표시하지 않는다.

## 정정과 가정 변경

| 발언 | 처리 의미 | 영향 |
|---|---|---|
| 100만 원 규정인데 200만 원짜리를 가져왔다 | 선택한 근거·값 결속의 정정 | 올바른 판본·대상 확인 후 의존 판단 재검토 |
| 이 연결은 잘못됐고 다른 항을 봐야 한다 | 관계 또는 원문 범위 정정 | 기존 연결 철회·대체 revision, 관련 경로 무효화 |
| 현재 사실은 150만 원이 아니라 80만 원이다 | 해당 사건 사실 정정 | 사건의 결과 재평가; 공통 법령 지식은 불변 |
| 한도를 100만 원에서 200만 원으로 올리면 | 가정 시나리오 | 원본 지식 유지, scenario overlay에서 비교 |
| 법이 개정돼 이제 200만 원이다 | 새 판본 주장 | 개정 원문 확인·유효시점 결속 후 새 판본 지식 |
| 두 번째 판단이 잘못됐다 | 표시 대상 참조 | 현재 view와 대화 맥락으로 유일하게 식별; 모호하면 확인 |

자연어의 숫자만 전체 검색·치환하지 않는다. 한도라는 이름도 통화·단위·대상·기간·이상/초과/이하와 묶어야 한다. 200만 원짜리 다른 규정을 선택한 오류는 값만 100으로 바꿔 해결하지 않는다.

## 정정 처리 순서

1. 현재 표시한 판단·관계와 사용자 발언을 연결한다. 서버가 대상 ID·예상 revision을 조립한다. 문서 밖 임의 ID를 모델이 작성하게 하지 않는다.
2. 의미가 정정인지 가정인지 분리한다. 모호한 변경은 현재 기준을 보존한 채 차이 미리보기·짧은 확인으로 좁힌다. 명확히 요청한 정정에 같은 승인을 반복 요구하지 않는다.
3. 원래 표현과 구조화 변경 제안을 함께 남긴다. 수정된 근거·값·적용 범위·사유·영향 후보를 비교한다.
4. 원문·권한·판본·타입·상태 revision을 검증한다. 사용자의 의견만으로 원문 값을 바꾸거나 새 법률 결론을 확정하지 않는다. 근거가 없으면 이견/검토 후보로 보존한다.
5. 명시적으로 허용된 변경을 새 revision으로 저장한다. 이전 의견·반대 근거·실패 이력은 유지한다. 공유 지식 게시에는 기존 권한과 검토 계약을 적용한다.
6. 해당 변경에 의존한 경로·계산·판단을 추적해 재검토 또는 재실행한다. 관련 없는 정상 판단·확보 원문은 보존한다.
7. 사용자에게 변경된 부분, 다시 계산한 결과, 아직 검토 중인 부분, 재사용 지식 반영 상태를 각각 표시한다.

## 중요한 상태 분리

- 원문 획득과 모델 판단 채택은 별도다. 다음 도구 제안이 틀렸어도 실제 읽은 원문 receipt는 유지한다.
- 판단 제안 보존과 유효 판단 commit도 별도다. 동일 응답의 행동 오류가 있으면 원래 판단은 제안으로 남긴다. 판단 자체의 근거·권한·revision 검증을 통과한 경우만 독립 commit을 허용하는 변경을 설계·검사한다. 응답을 임의로 부분 성공시키지 않는다.
- 기존 needs/conflicts는 새 빈 목록으로 제거하지 않는다. 종료·제외·해결은 해당 ID에 이유와 근거를 남긴다.
- 자유 설명에만 등장한 부족도 후보화할 수 있으나, 추출된 부족은 모델 관찰이다. 이전 상태와 자동 동치 처리하거나 원문 확인 없이 해결하지 않는다.
- 원문에 확인된 명시 관계와 검토된 지식이 있으면 검토 후보로 노출한다. 그 모든 후보를 강제 조회하지 않고 필요/불필요/보류 이유를 기록한다.

## 대화가 끝난 뒤의 축적

대화의 판단·사용자 정정·실제 원문·행동 receipt를 후보 생산의 입력으로 삼는다. 원문별로 재사용 가능한 관계·조건·검토 사항을 분리하고 질문·사건 사실·결론은 발견 이력으로 연결한다. 일반 답변 로그 전체를 정답 지식으로 게시하지 않는다.

같은 개념·원문에 다른 의견이 나오면 단순 마지막 쓰기로 덮어쓰지 않는다. 재진술·수정·적용 범위 차이·충돌을 구분하고 각각의 근거를 남긴다. 한 사람의 확인을 조직 전체의 법률 승인으로 확대하지 않는다. 여러 질문에서 나온 같은 원문 지식은 하나의 ID와 revision 계보로 관리한다.

## 실패와 동시 수정

| 상황 | 처리 |
|---|---|
| 다른 대화가 먼저 수정 | expected revision 불일치로 commit하지 않고 최신 head와 사용자 제안을 함께 표시 |
| 이전 화면 번호로 정정 | view hash·소유자·revision을 검사; 다른 항목에 적용하지 않음 |
| 저장 응답 유실 | 같은 operation ID의 receipt 조회, 다른 ID로 재작성 금지 |
| 원문·권한 변경 | 해당 결속 재사용 차단; 허용 원문 재조회 또는 미확인 표시 |
| 재평가 중 실패 | 지식 정정 저장 성공과 계산 미완료를 분리; 이전 결과는 이전 버전으로 유지 |
| 충돌 해소 실패 | 양쪽 의견·근거 유지, 제한 답변 또는 판단 보류; 반복 모델 호출로 밀어붙이지 않음 |

상세 복구 한도와 담당은 [검증·도입](VALIDATION_AND_ROLLOUT.md)을 따른다.
