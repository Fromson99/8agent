# 공통 클러스터에서 온톨로지 구성으로

[전체 목차](../ONTOLOGY_V3.md) · [원문 중심 저장](SOURCE_ANCHORED_STORAGE.md) · [질문과 온톨로지 매칭](QUESTION_MATCHING.md)

## 1. 공통 판단의 역할을 구체화한다

논의의 출발점은 “질문이 금액 산정에 관한 것이면 금액 산정 기준으로 공통 묶음을 만드는가”였다. 이어 “법 질문마다 계산이 다른데 공통 판단의 가치는 무엇인가, 미리 마킹한 곳으로 빨리 가는 데 의미가 있는가”라는 문제가 제기됐다.

`금액이 나오면 산정 기준을 확인하라`는 일반 지침만으로는 실제 근거의 위치나 적용 조건이 정해지지 않는다. LLM이 이미 할 수 있는 말을 반복하는 수준일 수 있고, 모든 금액 관련 항목을 조사시키면 비용이 늘 수도 있다. 이에 따라 공통 묶음의 역할을 다음처럼 둔다.

| 역할 | 이 설계에서 하는 일 | 이것만으로 확정하지 않는 것 |
|---|---|---|
| 사용자용 클러스터 | 원문에 붙인 검토 지식을 `금액 산정`, `승인 요건`, `보유기간` 등으로 찾아보기 쉽게 묶음 | 같은 묶음의 규정들이 같은 정의·계산법을 사용한다는 결론 |
| 지식 정리 틀 | 산정 대상·입력·합산·제외·시점처럼 반복되는 요소를 비교하고 정리 | 모든 원문에 해당 요소가 존재하거나 모든 질문에서 조사해야 한다는 의무 |
| 조회 보조 | 질문·개념에서 관련 원문과 지식 후보로 진입하도록 도움 | 검색 적중만으로 현재 사안에 적용된다는 판단 |

한 원문의 검토 지식은 여러 클러스터에서 보일 수 있다. 클러스터 이름이나 소속이 바뀌어도 원문·개념에 연결된 지식의 정체성과 근거는 유지한다. 질문을 반드시 한 클러스터에 배정하지 않으며, 묶음이 없더라도 기존 원문 검색을 사용할 수 있다.

공통화하는 대상은 우선 **근거를 정리하는 표현 틀**이다. 구체적인 정의·계산식·조건은 각 규정의 범위에 둔다. 재사용 효과가 확인된 검토 방법은 별도 지식으로 관리할 수 있지만, 클러스터의 이름만으로 실행 순서를 고정하지 않는다.

## 2. 서로 다른 역할을 구분한다

기존 v3에서 함께 논의했던 기능은 아래처럼 연결된다. 모두가 동일한 종류의 온톨로지 공리는 아니다.

| 역할 | 관리할 내용 |
|---|---|
| 원문 마킹 | 이 구절이 정의·계산·합산·예외 등 어떤 판단 역할을 가지는지 |
| 클러스터·공통 정리 틀 | 사람이 관련 지식을 찾는 묶음과 반복되는 검토 요소 |
| 근거 경로 | 어떤 판단에 필요한 원문이 어디에 있고 어떤 조건에서 재사용 가능한지 |
| 개념·관계·조건 모델 | 대상의 의미, 포함·정의·계산 의존, 적용 범위와 제약 |
| 새로운 관계 발견 | 기존 관계를 따라 현재 판단에 필요한 다른 근거를 발견하고 합성 가능성을 검토 |
| 실행 상태 | 근거의 확보·전달·검토·미확인과 중복 조사·예산·재개 |
| 설명·평가·변경 관리 | 주장과 근거·해석의 연결, 수정 영향, 핵심 누락과 근거 지지 상태 |

온톨로지 구성은 이 가운데 개념·관계·조건 모델을 원문 근거와 함께 구체화하는 작업이다. 근거 경로와 실행 상태를 연결해야 실제 RAG에서 활용할 수 있고, 검토·변경 관리가 있어야 재사용할 지식을 유지할 수 있다.

## 3. 원문에서 온톨로지를 만드는 과정

전체 MAIN의 원문 구조화·용어집·문서–용어 연결을 기반으로 기존 지식 관리 경로를 확장한다. 별도 병렬 파이프라인을 새로 선언하는 것이 아니다.

| 단계 | 입력 → 처리 → 다음 소비자에게 전달할 것 |
|---|---|
| 1. 중요한 검토 사항 발견 | 원문 검토 또는 질문·답변·정정 이력 → 핵심 개념·조건·누락한 근거 후보 → 해당 원문 위치에 연결한 검토 지식 |
| 2. 사용자용 묶음 구성 | 원문 검토 지식 → 공통 주제·역할로 클러스터링 → 찾아보기 화면과 조회 보조 색인 |
| 3. 개념과 의미 식별 | 검토 지식 + 기존 용어집·정의 → 같은 개념과 문서별 의미 차이를 검토 → 범위가 명시된 개념 참조·정의 후보 |
| 4. 관계·조건 구성 | 개념 + 실제 원문 → 포함·정의·계산 의존·예외 등의 관계와 적용 조건 작성 → 근거가 결속된 관계·규칙 후보 |
| 5. 검토·게시 | 후보의 구조·원문·범위·이견 검토 → 재사용 가능한 범위와 버전을 선택 → 조회·RAG가 소비할 지식과 근거 경로 |
| 6. 사안 적용·보완 | 현재 질문·사실 + 게시 지식 → 관련성·적용성을 판단하고 사용 기록 생성 → 답변과 원문에 연결할 수정 후보 |

여기서 클러스터는 유용한 정리 단계이지만 온톨로지 생성의 필수 통과 조건은 아니다. 원문에서 명시적 정의·참조 관계가 확인되면 먼저 개념·관계 후보로 만들 수 있다. 반대로 클러스터에 자료를 많이 모았다는 사실만으로 의미 관계가 생성되지는 않는다.

질문·검토된 답변·사용자 정정은 중요한 내용을 발견하는 단서다. 원문을 직접 검토해 후보를 만들 수도 있다. 과거 답변의 성공 여부만으로 관계를 승인하지 않으며, 질문별 답변 묶음을 Gold 지식의 일차 저장 단위로 만들지 않는다.

LLM은 의미·관계·적용 범위의 후보를 제안한다. 시스템은 문서 판본·조항·span·해시·권한·revision 등 확정 가능한 참조를 결속한다. 스키마 검사와 원문 일치만으로 의미 검토가 끝난 것으로 처리하지 않는다. 검토 담당·채택 범위·이견·미확인 상태를 보존하고, 구체적인 검토·게시 정책은 기존 관리 계약에 연결해 확정한다.

저장 책임은 [원문 중심 기준](SOURCE_ANCHORED_STORAGE.md)을 따른다. Gold에는 원문과 재사용 개념·관계·검토 지식을, Agent에는 발견 질문·사건별 사실·판단·사용·정정 이력을 둔다. 원문 개정은 새 판본과 근거 연결 검토로 처리하고 이전 기록을 덮어쓰지 않는다.

## 4. 하나의 사례로 보는 변화

다음은 구조 설명을 위한 **가상 규정**이며 실제 법률의 해석·승인 기준이 아니다.

| 원문 | 발견한 검토 사항 |
|---|---|
| A조: 산정 거래금액이 기준 이상이면 승인이 필요하다. | 승인 판단의 입력은 산정 거래금액이다. |
| B조: 거래금액은 해당 거래에 포함된 계약금액을 합산한다. | 합산할 계약의 범위를 먼저 알아야 한다. |
| C조: 동일 프로젝트이며 계약 이행이 서로 조건인 계약들을 하나의 거래로 묶는다. | 두 조건을 함께 확인해야 한다. |

클러스터에서는 이 자료를 `금액 산정`으로 모아 볼 수 있다. A조는 `승인 요건`, C조는 `거래 범위`에서도 찾을 수 있다. 이때까지는 관련 지식의 묶음이다.

온톨로지 구성에서는 `계약`, `거래`, `계약금액`, `거래금액`, `승인`을 구분하고 다음 의미를 표현한다.

| 관계·조건 후보 | 원문 근거 |
|---|---|
| 거래는 하나 이상의 계약을 포함할 수 있다. 포함 범위는 C조 조건을 따른다. | B조·C조 |
| 이 규정의 거래금액은 해당 거래에 포함된 계약금액의 합계다. | B조 |
| C조의 묶음 조건은 동일 프로젝트 AND 계약 이행의 상호 조건이다. | C조 |
| A조의 승인 필요 여부는 이 거래금액과 기준의 비교에 의존한다. | A조·B조 |

```mermaid
flowchart LR
    C["C조: 거래로 묶는 조건"] --> S["합산 대상 계약 범위"]
    S --> B["B조: 계약금액 합산"]
    B --> V["산정 거래금액"]
    V --> A["A조: 승인 기준 판단"]
```

각 연결에는 적용 문서·판본·대상·시점·조건·예외·검토 상태와 정확한 근거 위치를 둔다. 동일한 `거래금액` 표기라도 다른 규정이 다른 뜻으로 사용하면 범위를 구분한다. 단순 동시 출현이나 클러스터 소속으로 법적 관계를 만들지 않는다.

계산식은 입력·단위·범위가 확정된 부분에서 명시적으로 실행할 수 있다. **현재 두 계약이 C조 조건을 만족하는지**는 사건 사실과 원문을 대조할 적용 판단으로 남는다. 사실 미확보를 FALSE로 바꾸지 않으며, A←B←C 경로를 찾았다는 사실과 현재 사안에서 C→B→A가 성립한다는 판단을 구분한다.

## 5. 속도와 정확도가 좋아질 수 있는 이유

관계가 현재 사안에 맞고 필요한 원문이 실제 판단 입력으로 전달된다면, 속도와 정확도 모두 개선될 가능성이 있다. 이는 작동 원리에 대한 가설이며 성능 보증이 아니다.

| 재사용하는 정보 | 기대 효과 | 효과가 약하거나 반대로 나빠지는 경우 |
|---|---|---|
| 필요한 근거의 위치와 의존관계 | 승인 기준을 찾은 뒤 계산법·합산 범위를 다시 발견하는 검색과 재조사 감소 | 관계 조회·검증 비용이 절감한 검색 비용보다 큼 |
| 개념의 의미와 범위 | 계약금액·거래금액 등 비슷한 용어를 혼동할 가능성 감소 | 다른 규정의 정의를 가져오거나 낡은 판본을 적용 |
| 조건·예외와 원문별 검토 사항 | 결론을 바꾸는 핵심 근거의 누락 감소 | 관련 없는 항목까지 조사하거나 잘못된 관계에 고착 |
| 확보·전달·검토 상태 | 이미 읽은 원문 재사용, 불필요한 반복 조사 감소 | 회수만 성공하고 모델 입력·최종 판단에서 핵심 원문이 빠짐 |

같은 조문을 이미 읽었다면 추가 조회 감소보다 중요한 구절의 명시와 재독해·누락 감소가 효과의 중심일 수 있다. 검색량 감소만으로 답변 품질 개선을 추정하지 않는다. 정확한 원문을 갖춰도 적용 해석은 틀릴 수 있다.

지식 구성·검토·개정 관리에는 사전 비용이 든다. 반복되는 판단에서 재사용하면 그 비용을 나눌 수 있지만, 자주 쓰이지 않거나 모델이 이미 잘 처리하는 일반 지침은 추가 가치가 작을 수 있다. 전체 응답시간·호출·핵심 누락·의미 오류와 유지 비용을 함께 보아야 한다.

## 6. 확인된 결과와 남은 과제

[CM E2E 기록](CM_E2E_RESULTS.md)은 원문에 붙인 지식을 다른 질문에도 회수하는 경로를 실행했다. 4문항의 소규모 비교에서 탐색량·응답시간 감소를 관측했지만 핵심 항목을 모두 설명한 답변은 양쪽 모두 0/4였고, 정확도 개선을 확인하지 못했다. 수작업으로 구성한 연구 후보이며 자동 온톨로지 생성·독립 일반화 검증·MAIN100 반영 결과가 아니다.

따라서 이 문서의 3~5단계가 자동으로 완성됐거나, 관계를 저장하면 6단계의 답변 품질이 보장된다고 설명하지 않는다. 다음 설계·검증은 원문별 지식의 조회, 실제 원문 전달, 적용/비적용 이유, 최종 주장 연결을 함께 다뤄야 한다. 질문과 원문에서 지식에 진입하는 구체 과정은 [질문과 온톨로지 매칭](QUESTION_MATCHING.md)을 따른다.

후속 효과 비교는 [기존 평가 과제](INTEGRATION_AND_VALIDATION.md#v3-15)와 저장소 ADR 절차로 별도 동결한다. 이번 반영은 문서 갱신이며 새 모델 호출·평가·런타임 변경·릴리스 승격을 수행하지 않는다.
