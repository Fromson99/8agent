# 전체 흐름과 구현 검증 과제

[전체 목차](../ONTOLOGY_V3.md)

원래 논의의 절 번호를 유지했습니다. 설계 제안과 구현·검증 상태는 각 절의 구분을 따릅니다.

<a id="v3-13"></a>

## 13. 이를 하나의 흐름으로 묶으면

<a id="v3-13-1"></a>

### 13.1 지식을 만드는 흐름

```text
원문·용어·정의·명시 참조 수집
  → 문서·위치·버전·권한 결속
  → 질문·정정 또는 원문 검토에서 개념·중요 검토 사항 발견
  → 원문에 연결한 지식을 사용자용 클러스터·공통 표현 틀로 정리
  → 개념·의미 관계·조건·근거 경로 후보 구성
  → 원문·범위·조건·이견 검토 후 버전 게시
  → 질문/개념 진입 색인 + 원문 anchor 기반 지식 조회
  → 변경 시 영향받는 바인딩·경로 재검토
```

클러스터는 구성 재료의 정리와 사용자 탐색을 돕는 층이다. 원문에서 바로 확인되는 정의·관계는 클러스터를 선행하지 않고 후보로 만들 수도 있다. 질문별 답변을 Gold 지식으로 복제하지 않는다. 단계별 입력·출력과 가상 사례는 [온톨로지 구성 과정](CLUSTERING_AND_CONSTRUCTION.md#construction)을 따른다.

개념 이름과 범위를 사람이든 LLM이든 원문을 보고 제안할 수 있다. 시스템은 선택한 근거와 버전을 결속하고 확정 가능한 식별자·위치·해시를 조립한다. LLM의 제안과 검토 결과, 실행 가능한 규칙은 서로 구분한다. 같은 묶음에 있다는 이유로 개념을 병합하거나 법적 관계를 확정하지 않는다.

모든 법령의 모든 세부를 먼저 형식화하기보다, 반복되는 근거 누락과 탐색 비용이 큰 판단부터 시작하는 것이 제안이다. 아직 성공이 입증된 도입 순서라는 의미는 아니다.

<a id="v3-13-2"></a>

### 13.2 질의에서 쓰는 흐름

1. 기존 질문 해석에서 판단 목적·대상·제공된 사실·시점과 미확인을 파악한다.
2. 질문/개념으로 지식 후보를 찾거나 기존 용어·본문·참조 검색으로 진입 원문을 찾는다.
3. 실제 원문을 확보하면 그 판본·위치에 연결된 개념·검토 사항·근거 경로도 조회한다.
4. 현재 질문에 관련된 항목을 선택한다. 검색 매칭과 사안의 적용 판단을 분리하고 클러스터의 모든 항목을 강제하지 않는다.
5. 이미 확보·전달한 원문은 재사용하고, 필요한 위치만 추가 조회한다.
6. 판단 중 새 근거 필요가 생기면 그 필요와 맥락으로 기억을 조회한다.
7. 기억이 없거나 유효하지 않으면 범위를 좁힌 일반 조사를 수행한다.
8. 결론을 바꿀 수 있는 입력·조건이 드러나면 B-C-A 형태의 의존관계를 추가 확인한다.
9. 확보한 근거로 판단하고, 미확인 범위와 적용 가정을 함께 답한다.
10. 이번에 확인한 경로와 실패·부분 성공을 구분해 피드백 후보로 남긴다.

이 흐름은 논의의 종합안이다. 현재 서비스에 이 순서가 모두 연결되어 있다는 뜻은 아니다. [질문 매칭 상세](QUESTION_MATCHING.md)는 두 진입 경로, 미적중·오적중 처리와 현재 조회 코드의 한계를 구분한다.

<a id="v3-13-3"></a>

### 13.3 저장량을 늘리지 않는 원칙

- 원문 불변층은 공유하고 기억은 해당 원문을 가리키는 위치와 역할을 중심으로 둔다.
- 클러스터와 공통 표현 틀은 같은 지식 참조를 공유하고, 구체적 정의·계산·조건과 근거는 원문별 범위에 둔다.
- 질문마다 본문과 전체 탐색 로그를 별도 지식으로 복제하지 않는다.
- 경로는 근거·버전·조건을 유지하되, 원문 변경 시 유효성을 다시 확인한다.
- 영속 데이터와 공유 캐시는 데이터 계층에서 관리하고, 서빙은 요청에 필요한 자료를 일시적으로 사용한다.

## 14. 현재 구현과 이번 제안의 경계

문서 확인 기준은 [활성 포인터](../../../../01_DATA/ACTIVE/local/ACTIVE_RELEASE.json)와 해당 선택 릴리스의 코드다. 작업 코드나 이전 설계 문서에 기능이 있다는 사실만으로 선택 릴리스에서 사용 중이라고 단정하지 않는다.

**아래 표와 선택 릴리스 코드 링크는 초기 MAIN99 검토 시점의 기록이다.** 2026-10-22 후속 문서 갱신에서는 활성 포인터 MAIN100을 확인했다. ADR0987은 MAIN99에서 동결한 별도 연구 후보이며 MAIN100 통합·승격을 수행한 결과가 아니다. 후속 작업 코드의 검색어 포함 조회와 연구 후보의 실제 연결, 원문별 추가 조회의 미구현 범위는 [매칭 구현 상태](QUESTION_MATCHING.md#implementation)와 [CM 실행 결과](CM_E2E_RESULTS.md)에 정리했다.

| 영역 | 확인한 현재 상태 | 이번 논의에서 추가로 필요한 것 |
|---|---|---|
| 용어·정의·명시 참조 | 원문과 용어집을 연결하는 생성·색인 경로 존재 | 판단별 필요 근거의 의미·조건 연결 |
| 도메인 선택 | 선택 릴리스의 `DomainCatalogue.select`는 단계별 방법을 고정하고 `DISCOVERY`, 빈 `concept_ids`·`relation_ids`를 기록 | 법률 개념·관계를 활용한 실제 판단별 선택과 재사용 |
| 기억 회수 | `wiki_recall`에 조건부·제한된 기억 조회와 경로 선택 코드 존재 | 조사 도중 새 근거 필요가 생길 때의 일반화된 회상 연결 |
| 요청 진입·기억 도구 | `request_entry`와 `wiki_execution`에 회수 진입 연결 존재 | 공통 확인 규칙·조문별 바인딩·현재 조사 상태의 일관된 소비 |
| 핵심 근거 경로 | 인증·기능 플래그·질문·사실·출처 결속 등의 조건을 확인하는 `core_evidence_route` 존재 | 유사한 판단 필요의 재사용, 조건 있는 경로 합성 |
| 지식 관리 소비 | 선택 릴리스 설정에서 `legal_knowledge.management_enabled=false`, `consumer_mode=off` | 관리·검토 지식을 실제 소비하는 배선과 검증 |
| 최초 진입과 B-C-A | 기존 검색·관계·기억 코드가 기반이 될 수 있음 | 이번에 설명한 전체 기능과 성능은 미검증 |

현재 기억 기능의 존재를 부정하는 것도, 이를 이미 완성된 의미 추론·중간 회상 체계라고 설명하는 것도 부정확하다. 기능 플래그와 인증·출처 조건이 있으므로 개별 실행에서 실제 사용되었는지는 실행 기록으로 확인해야 한다. 설정의 선언만으로 동작과 성능을 증명하지 않는다.

## 15. ‘빠르고 더 잘 찾는다’를 어떻게 확인할 것인가

성공 기준은 그래프 크기나 기억 적중률만이 아니다. **기억을 조회하고 검증하는 비용까지 포함한 전체 응답 과정이 개선되는가**가 중요하다. 기억 조회만 빨라도 이후 원문 확인·LLM 호출이 늘면 전체는 느려질 수 있다.

아래는 향후 평가 제안이며, 이번 문서 작성에서 실행한 실험이 아니다.

| 관점 | 확인할 항목 |
|---|---|
| 최초 진입 | 적절한 판단 기준 조문을 찾기까지 시간·호출 수, 잘못된 진입에서의 회복 |
| 근거 확보 | 필요한 원문 누락, 중복 조회·재독해, 확보한 원문의 판단 입력 전달 여부 |
| 전체 비용 | 처음부터 답변까지 지연, LLM·검색 호출, 읽은 본문량, 기억 조회·검증 비용 |
| 판단 품질 | 결론·적용 범위·예외·계산의 적절성, 원문 인용의 정확성 |
| 반복 조사 | 같은 상태에서 같은 부족을 되풀이한 횟수와 종료 결과 |
| 새로운 연결 | 추가 경로가 실제 결론·조건 설명을 개선했는지, 무관한 경로를 늘렸는지 |
| 변경·실패 | 개정·권한 변경·기억 미적중·잘못된 바인딩에서 원문 조사로 전환되는지 |
| 검토 가능성 | 중요한 해석 의존 지점을 사람이 찾고 수정하는 시간, 근거와 수정 영향의 추적 가능 여부 |
| 모델 변화 | 각 모델에서 같은 원문·질문으로 비교한 추가 효과와 지식 갱신 비용 |

같은 질문만 반복하면 답변 암기 효과와 경로 재사용 효과를 구분하기 어렵다. 동일 문제, 표현이 달라진 문제, 비슷하지만 조건이 다른 문제, 처음 보는 조문, 기억이 잘못되거나 낡은 경우를 나누어 봐야 한다.

향후 효과 비교를 한다면 기준과 후보, 데이터, 성공 기준을 사전에 고정하고 저장소의 ADR 절차를 따른다. 상세 의미 판단 실패는 원인과 범위를 기록하며, 그 자체를 모든 MAIN 반영의 자동 차단 조건으로 만들지 않는다. 인용·권한·버전·해시·상태 보존·실제 서빙 연결의 심각한 문제는 별도로 검증한다.

속도·정확도의 기대 원리와 비용·역효과는 [기대 효과](CLUSTERING_AND_CONSTRUCTION.md#value)를 따른다. 이미 완료된 [CM 소규모 비교](CM_E2E_RESULTS.md)는 탐색량·응답시간 감소를 관측했지만 핵심 항목을 모두 설명한 답변은 양쪽 모두 0/4였고 정확도 개선을 확인하지 못했다. 이를 일반적인 배속·법률 정답률 개선으로 바꾸지 않는다. 이번 문서 갱신에서는 새 실험이나 재채점을 수행하지 않았다.

<a id="v3-16"></a>

## 16. 아직 결정하지 않은 사항

1. 사용자용 클러스터의 분류·복수 소속·수정 관리와 공통 표현 틀을 어디까지 둘지. 역할은 정리했으나 자동 클러스터링 방식과 계약은 미확정이다.
2. 최초 진입에서 기억·용어·본문·의미 유사도 검색을 어떻게 결합하고 순위를 정할지. 검색 매칭과 적용 판단의 경계, 원문 anchor 조회는 유지한다.
3. 근거 필요가 생겼다는 판단을 기존 에이전트 상태와 어떤 인터페이스로 연결할지.
4. LLM이 제안한 조문별 바인딩을 누가 어떤 기준으로 검토하고 언제 재사용 가능 상태로 둘지.
5. 여러 관계 중 어떤 조합을 안전하게 합성할지. 계산·정의·예외·유사성 관계에 같은 전이 규칙을 쓰지 않는다.
6. 개정 시 어떤 기억·바인딩·합성 경로가 영향을 받는지 추적하고 갱신하는 방법.
7. 이미 확보한 원문의 전달과 의미 판단을 어떻게 분리하여 누락·무한 재조사를 줄일지.
8. 새로운 연결의 탐색 예산을 어떤 상황에서 늘리고 언제 제한된 답변을 낼지.
9. Oracle 조회 계약과 기존 기억 저장·관리 기능을 어떻게 통합할지.
10. 개선 효과를 검증할 실제 질문·필수 근거·경로 평가 자료를 어떻게 마련할지.
11. 조직의 검토 상태·적용 범위·재검토 이력과 개별 질의의 해석을 어떤 단위로 연결할지.
12. 원문 지지·미지지·모순·판정 불가를 어떤 평가 규약으로 구분하고, 주장 단위와 답변 단위를 어떻게 함께 보고할지.
13. 실행 중 남긴 기록과 답변 후 재구성한 설명을 어떻게 구분해 보여줄지.

이 항목들은 문서화로 해결된 것이 아니다. 사용자와 정리한 문제의식을 실제 시스템에 연결하기 위한 후속 과제다.
