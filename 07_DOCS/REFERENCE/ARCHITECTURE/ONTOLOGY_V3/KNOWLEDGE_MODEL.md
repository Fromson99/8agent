[전체 목차](../ONTOLOGY_V3.md)

원래 논의의 절 번호를 유지했습니다. 설계 제안과 구현·검증 상태는 각 절의 구분을 따릅니다.

<a id="v3-3"></a>

## 3. 현재 우리의 기반은 어떻게 만들어지는가

전체 MAIN의 기준은 [시스템 아키텍처](../../../../00_SYSTEM/ARCHITECTURE.md)다.

```text
용어집 구축·갱신
  → 원문 수집·구조화
  → 문서–용어 연결
  → 용어·정의·명시 참조 색인
  → 용어 기반 RAG
  → 근거와 세대에 연결된 피드백
```

<a id="v3-3-1"></a>

### 3.1 용어집과 원문 구조

법령·행정 분야 용어, 금융·조세 분야 용어와 수집된 외부 지식 자원을 공통 기반으로 사용한다. FIBO, Wikidata, NLSH 등의 자료를 수집했더라도, 그 자료에 존재하는 모든 관계가 곧바로 우리 업무에 적용되는 승인된 법률 관계가 되는 것은 아니다. 출처, 식별자, 관계의 종류와 방향, 번역·정의의 근거를 보존해야 한다.

원문은 문서·장·절·조·항·호·목·표 등으로 구조화하고 원문 위치, 문서 버전, 해시를 유지한다. 용어는 ‘어느 문서의 어느 위치에 어떤 표기로 등장했는가’에 연결한다. 정의와 명시 참조도 원문 범위와 함께 보존한다.

같은 이름을 가진 용어라도 문서별 정의가 다를 수 있다. 따라서 문자열이 같다는 이유만으로 하나의 법적 개념으로 합치거나, 다른 법령의 정의를 자동 적용하지 않는다.

<a id="v3-3-2"></a>

### 3.2 지금 되는 일과 별도 판단이 필요한 일

현재 용어 기반 생성의 기본 경로는 원문과 선택된 용어집으로 색인을 만드는 경로다. [`term_generation.py`](../../../../02_BACKEND/lawrag/pipeline/term_generation.py)의 생성 경로는 모델 호출 없이 수행하는 것으로 명시되어 있다. 용어 출현, 정의, 명시 참조를 연결하는 작업과, LLM이 규정의 적용성·예외·의무를 의미적으로 해석하는 작업은 구분한다.

‘이 조문이 저 판단의 계산 근거다’, ‘이 조건이 예외를 발생시킨다’ 같은 의미 관계는 별도의 추출·검토 대상이다. LLM 추출은 근거를 가진 관찰 또는 후보이며, 추출에 성공했다는 이유만으로 정본이 되지 않는다.

현재 기반은 **용어와 원문을 찾아가는 구조 및 일부 조사 경험 재사용**으로 설명하는 것이 적절하다. 모든 법률 개념과 공리를 실행해 결론을 내리는 완성된 도메인 추론 엔진으로 설명하지 않는다.

<a id="v3-3-3"></a>

### 3.3 저장·서빙의 전제

목표 인프라는 Dataiku에서 수집·구조화·색인·갱신하고, Oracle에 법령·용어·관계를 저장하며, GENOS 에이전트가 Oracle 또는 조회 API에서 필요한 근거를 받아 응답하는 구조다. 원문·색인 전체를 GENOS 코드서빙의 로컬 파일이나 SQLite로 복원하는 것을 목표 구조로 삼지 않는다.

아래의 기억·숏패스·연결도 이 데이터 계층에서 버전과 권한을 관리하는 방향이다. 현재 로컬 또는 기존 저장소 구현이 있다는 사실만으로 Oracle 연동과 GENOS 현장 적용이 완료된 것으로 보지 않는다.

관련 기준: [데이터 모델](../../../../00_SYSTEM/DATA_MODEL.md), [용어집 파이프라인](../../OPERATIONS/GLOSSARY_ALIGNMENT.md), [용어 지식 번들](../../OPERATIONS/GLOSSARY_KNOWLEDGE_BUNDLE.md), [전체 지식 인프라 설계](../LEGAL_KNOWLEDGE_INFRA_20261017/ARCHITECTURE.md).

## 4. “온톨로지인가, 행동 지침인가”

사용자의 문제의식은 다음과 같다.

> 기본적으로 데이터 간의 관계가 아니라 어떻게 행동해야 하냐를 만든다. 용어 기반으로 만들라고 하니 용어 간 관계는 만들 수 있지만, 정의나 공리를 매핑하는 것은 감이 안 온다.

이 구분은 타당하다. 현재 논의하는 시스템에는 서로 다른 종류의 지식이 들어간다.

| 종류 | 담는 내용 | 이번 논의의 예 |
|---|---|---|
| 용어·개념 체계 | 어떤 개념이며 어떤 개념과 구분되는가 | 계약금액, 거래금액, 잔액, 위험액의 구분 |
| 도메인 온톨로지 | 대상·속성·관계의 의미와 제약 | 하나의 거래에 여러 계약이 포함될 수 있음 |
| 법적 규칙 | 어떤 조건에서 어떤 법적 효과가 발생하는가 | 산정금액이 기준 이상이면 특정 승인을 요구 |
| 조사·판단 방법 | 판단에 어떤 근거를 확인해야 하는가 | 금액이 결론을 좌우하면 산정 기준을 확인 |
| 경험 기억 | 실제로 어디서 어떻게 근거를 찾았는가 | A조 판단에 필요한 합산 기준은 C조 제2항 |
| 실행 제어 | 언제 조회하고, 재시도하고, 종료하는가 | 이미 읽은 근거 재사용, 미확인 사항 설명, 중복 조사 억제 |

‘금액 판단이면 산정 근거를 확인하라’는 주로 조사 방법이다. ‘이 규정에서 거래금액은 특정 계약들의 합계다’는 도메인 정의·법적 규칙이다. ‘A조에 필요하면 C조를 가져와라’는 근거 경로다. 모두 필요할 수 있지만, 같은 종류의 공리로 취급하지 않는 편이 명확하다.

또한 **온톨로지가 반드시 행동 순서를 정하거나 가지치기를 해야 하는 것은 아니다.** 형식적 개념·관계·공리만으로도 온톨로지가 될 수 있다. 사용자가 원하는 실행 효과는 온톨로지에 규칙, 조사 방법, 기억, 실행 상태를 연결해서 만들어진다. 반대로 임의의 정보를 간선으로 연결했다고 해서 그 관계의 의미나 추론 가능성까지 확보되는 것도 아니다.

Breuker와 Hoekstra의 법률 온톨로지 연구도 FOLaw의 문제 해결·추론 의존관계와 도메인 자체의 개념화를 구분한다. ‘온톨로지라고 부르지만 실제로는 문제를 푸는 방법을 기술하고 있다’는 이번 문제의식과 직접 맞닿아 있다. [연구 원문](https://pure.uva.nl/ws/files/55499960/29910_paper2.pdf)

<a id="v3-5"></a>

## 5. 용어에서 정의·공리로, 공리에서 실행으로

<a id="v3-5-1"></a>

### 5.1 용어 관계만으로 부족한 이유

‘거래금액 → 관련 → 보고’만 있으면 컴퓨터는 무엇을 비교하고 어떤 근거를 확보해야 하는지 알기 어렵다. 실행하려면 최소한 다음 질문에 답할 수 있어야 한다.

1. 어떤 문서·시점·대상에 적용되는 의미인가?
2. 어떤 사실이나 값이 입력인가?
3. 정의가 필요한 조건인가, 충분조건인가, 동치인가?
4. 계산·분류·법적 효과의 규칙은 무엇인가?
5. 예외나 우선하는 규정이 있는가?
6. 원문 근거는 어디이며, 사실 또는 근거가 없을 때 어떻게 표시하는가?

모든 내용을 한꺼번에 형식화할 필요는 없다. 반복적으로 필요한 판단부터, 검토 가능한 범위의 규칙과 근거 경로로 구체화한다.

<a id="v3-5-2"></a>

### 5.2 컴파일하거나 실행할 수 있는가

**명시적으로 형식화한 범위는 가능하다.** 다만 ‘법령을 읽어 자동으로 완전한 공리를 만든다’와 ‘검토한 공리를 실행한다’는 다른 문제다.

| 표현·기술 | 할 수 있는 일 | 이 시스템에 적용할 때의 한계 |
|---|---|---|
| SKOS | 용어·레이블·상하위·관련 개념 정리 | 이것만으로 금액 계산이나 법적 의무를 실행하지는 않음 |
| OWL | 형식적 개념·관계·공리와 논리적 추론 | 일반 프로그램, 임의 계산, 법적 예외 우선순위 전체를 대신하지 않음 |
| OWL 2 QL / RL | 제한된 표현에서 질의 재작성 또는 규칙 기반 처리 | 필요한 표현력이 해당 프로파일에 맞는지 확인해야 함 |
| LegalRuleML | 의무·허용·금지, 예외·우선순위, 시간·관할 등의 법규 표현 | 표현 표준이며, 그 자체가 완성된 실행 엔진은 아님 |
| Catala | 법률 규칙을 명시적인 프로그램으로 작성·컴파일 | 자연어 법령의 해석을 자동으로 보증하지 않음 |
| DMN | 의사결정과 규칙·입출력의 구조화 | 원문에서 올바른 법적 규칙을 뽑는 과정은 별도 |

OWL의 일부 프로파일에서 SQL 질의 재작성이나 규칙 처리가 가능하므로, Oracle RDB라는 이유만으로 이런 구조를 만들 수 없는 것은 아니다. 그렇다고 일반 OWL 공리나 모든 법률 규칙이 자동으로 Oracle SQL 하나로 변환된다는 뜻도 아니다.

Catala는 법률 원문과 형식화된 프로그램을 대응시키는 실례다. 중요한 구분은 ‘컴파일러가 정해진 의미를 보존한다’와 ‘작성한 규칙이 법률을 올바르게 해석했다’가 같지 않다는 점이다. 법률 해석·사실 적용의 검토는 남는다.

근거: [SKOS](https://www.w3.org/TR/skos-reference/#secskosandowl), [OWL 2](https://www.w3.org/TR/owl2-primer/), [OWL 2 프로파일](https://www.w3.org/TR/owl2-profiles/), [LegalRuleML](https://docs.oasis-open.org/legalruleml/legalruleml-core-spec/v1.0/os/legalruleml-core-spec-v1.0-os.html), [Catala 논문](https://arxiv.org/abs/2103.03198), [Catala 구현 구조](https://assets.catala-lang.org/api-doc/catala/), [DMN](https://www.omg.org/dmn/).

<a id="v3-5-3"></a>

### 5.3 형식화의 작은 예

다음은 설명을 위한 가상 규정이며, 실제 법률이나 보고 기준이 아니다.

```text
정의: 고액거래 ↔ 거래이고, 이 규정의 원화환산금액이 1억 원 이상
기본 규칙: 적용 대상인 고액거래 → 보고 필요
예외 규칙: 이 기본 규칙에 우선하는 유효한 면제 조건 충족 → 해당 보고 의무 면제
```

실행에 필요한 것은 숫자 하나뿐이 아니다. ‘이 규정의 원화환산금액’을 어떤 환율·시점·범위로 계산하는지, 적용 대상인지, 면제의 적용 범위와 우선순위가 무엇인지가 연결되어야 한다.

금액이 없으면 ‘고액거래가 아니다’로 처리하지 않는다. 금액 미확보와 기준 미충족은 다른 상태다. 예외 근거를 확보하지 못한 것도 예외가 존재하지 않는다는 증명이 아니다.

이 미확인 상태가 항상 전체 응답 중단을 뜻하지는 않는다. 확보한 근거를 전달하고, 확정할 수 있는 범위와 추가로 필요한 사실·근거를 설명할 수 있어야 한다.

<a id="v3-5-4"></a>

### 5.4 먼저 정할 것은 답하려는 질문

용어를 많이 모은 뒤 어디에 쓸지 찾는 방식만으로는 공리의 범위가 정해지기 어렵다. 온톨로지가 답해야 할 구체적 질문, 즉 competency question을 먼저 둔다. 예를 들면 다음과 같다.

- 이 승인 판단에 쓰이는 금액은 계약금액인가, 합산 거래금액인가?
- 내규의 보고 대상 범위가 특정 외규의 보고 대상 범위를 포함하는가?
- 현재 근거로 결정할 수 있는 부분과 아직 조건이 확인되지 않은 부분은 무엇인가?

두 번째 질문도 대상·시점·예외·정의가 정리된 범위에서는 형식적 포함관계 검토를 도울 수 있지만, 서로 다른 문서의 자연어 표현만으로 전체 포함관계를 확정할 수는 없다. [Ontology Development 101](https://protege.stanford.edu/publications/ontology_development/ontology101-noy-mcguinness.html)

<a id="v3-5-5"></a>

### 5.5 공통 묶음에서 의미 관계로 넘어간다

후속 논의에서는 공통 판단 묶음을 **사용자용 클러스터와 온톨로지 구성 재료를 정리하는 층**으로 구체화했다. `금액 산정`으로 자료를 모아 놓은 상태에서, 원문별로 어떤 금액인지·무엇을 합산하는지·어떤 조건과 판단에 연결되는지를 표현하는 단계로 이어간다.

클러스터 소속은 탐색·정리 정보다. 개념·정의·관계·조건은 각각 원문 근거와 적용 범위를 가진 지식 후보이며 별도 검토가 필요하다. 다른 규정의 같은 표기를 자동 병합하지 않는다. 클러스터를 먼저 만들지 않아도 원문에서 확인한 정의·명시 관계를 후보로 구성할 수 있다.

전체 과정과 가상 사례는 [공통 클러스터에서 온톨로지 구성으로](CLUSTERING_AND_CONSTRUCTION.md#construction), 실제 질의에서의 선택·적용은 [질문·원문 매칭](QUESTION_MATCHING.md)을 따른다.
