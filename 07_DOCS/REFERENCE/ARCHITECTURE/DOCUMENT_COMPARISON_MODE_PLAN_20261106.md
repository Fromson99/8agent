# 문서 대사 모드 구현 계획 — 2026-11-06

사용자 요청: "문서 전체를 넣어도 잘 작동하나? 1번 문서 전체 넣기, 2번 질문만 하기. GENOS에서 mode를 넣을 수 있으니 이 두 개를 구별하게 해서, 문서 대사로 질문하면 해당 문서를 찾아 전체를 돌리게 하고 싶다."

이 문서는 계획이다. 아직 코드를 고치지 않았다. 기존 대사 개발 상태는 [대사 인계 문서](COMPARISON_HANDOFF_20261106.md)를 따른다.

## 0. 결론

- **지금 대사에 문서 전체를 넣으면 제대로 돌지 않는다.** 지금 대사는 질문에서 쟁점을 뽑고, 그 쟁점에 걸리는 조문만 본다. 문서 이름을 넣어도 "문서 전체"를 보지 않는다. 한 요청의 한도도 문서 하나를 감당하지 못한다(1장).
- 그래서 GENOS 조회 방식에 **"문서 대사"를 새로 추가**하고, 기존 "대사"는 질문 대사로 그대로 둔다(2장).
- 문서 하나에 모델 호출이 수백 번(추정 350~600회), 시간은 1시간 안팎이 걸린다. 한 번의 채팅 응답 안에서는 끝낼 수 없으므로 **묶음 단위로 저장하면서 끝까지 이어 가는 실행**으로 만든다. 실행 방식(뒤에서 자동으로 끝까지 / "계속"으로 이어 가기)은 사용자가 정해야 한다(4장, 추천: 자동).

## 1. 지금 문서 전체를 넣으면 어떻게 되나

### 지금 대사가 하는 일

화면에서 "대사"를 고르고 질문하면 아래 순서로 돈다. 출발점이 **질문의 쟁점**이다.

1. 질문에서 쟁점 뽑기 → 2. 쟁점에 맞는 내규 조사 → 3. 읽은 내규로 개념 정하기 → 4. 개념별 외규 조사 → 5. 항목 대조 → 6. 비교 → 7. 보고서

예: ADR-1435 질문 "모의 유동성리스크 관리지침의 유동성비율 유지 기준, 기준 미달 시 조치, 위기상황분석 주기가 외규와 맞는지 …"는 쟁점 3개 → 개념 4개 → 모델 호출 12회, 94초였다. 질문에 없는 제5조(한도 초과 거래 승인)는 대사하지 않았다. 그게 맞는 동작이다.

### 한 요청의 한도 (지금 대사 워크플로우 manifest)

| 한도 | 값 |
|---|---:|
| 모델 호출 | 24회 |
| 전체 시간 | 600초 |
| 개념 수 | 12개 |
| 하위 조사 모델 호출 | 6회 |

### 문서 하나의 크기

- 로컬 내규 11개를 읽기 묶음으로 나누면 323묶음·6,970행이다. 문서당 평균 약 29묶음·634행이다.
- 11개 중 "제○조" 형식은 2개뿐이다. 나머지 9개는 "1. / 가. / (1) / ①" 번호 체계다. 조·항 이름이 아니라 저장된 구조 트리로 다뤄야 한다.

### 실제로 확인된 것: 묶음 읽기 단계만 (ADR-1425)

공개 문서 「금융투자회사의 리스크관리 모범규준」(654행)을 묶음으로 나눠 실제 Qwen에 주고, 각 행을 "대사 단위 / 대상 아님 / 보류"로 나누게 했다.

| 묶음 행 한도 | 묶음 수 | 첫 응답에 모든 행 배치 | 보완 후 | 대사 단위 | 대상 아님 | 호출 p50 | 합계 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 30행 | 32 | 31/32 | 32/32 | 201 | 131행 | 7.7초 | 287초 |
| 60행 | 17 | 17/17 | 17/17 | 155 | 133행 | 10.6초 | 213초 |

- 모델이 묶음 안의 행을 빠짐없이 처리하는 것은 확인했다.
- **외규 조사·대조·비교까지 문서 전체를 끝까지 돌린 적은 없다.** 둘째 문서는 자원 보호 장치로 멈춰 실행하지 못했고, 행 한도 권장값도 정하지 못했다.

### 문서 하나를 끝까지 돌리면 (추정, 실측 아님)

- 대사 단위가 문서당 150~200개 나온다(위 표).
- 단위 하나에 지금 대사 방식대로 항목 대조 1회 + 비교 1회 + 외규 조사 0~1회를 쓰면 단위당 2~3회다.
- 문서 하나: 묶음 읽기 17~32회 + 단위 150~200개 × 2~3회 = **약 350~600회**.
- ADR-1435 기준 1회 약 7~8초, 약 0.0023달러 → 순차로 **약 45~75분, 약 0.8~1.4달러**.
- 한 요청 한도 24회·600초로는 문서 하나에 요청이 15~25번 필요하다. 그래서 묶음 단위 저장과 이어 가기가 꼭 필요하다.

## 2. 두 모드 구분

| 화면 조회 방식 | 사용자 입력 예 | 동작 |
|---|---|---|
| 대사 (지금 그대로) | 모의 유동성리스크 관리지침의 유동성비율 유지 기준이 외규와 맞는지 비교해 주세요 | 질문 쟁점만 대사 |
| **문서 대사 (새로)** | 리스크관리규정 대사해 줘 | 질문에서 내규 문서를 찾아 확정하고, 그 문서 전체를 대사 |

### 지금 연결 경로

1. GENOS 화면 드롭다운(키 `mode`) 값이 `applied_fields.mode`로 들어온다.
2. 워크플로우 파이썬 `08_DEPLOYMENT/GENOS/workflow/genos_rag_chat.py`의 `_selected_question`이 질문 앞에 `대사: `를 붙인다. 대사는 대화 식별자와 팀이 없으면 화면 오류를 낸다.
3. 백엔드 `02_BACKEND/semantic_runtime/chat_adapter.py`가 `대사:`로 시작하면 세션 요청으로 보낸다.
4. `02_BACKEND/workflow/contracts.py`의 접두어 검사(`^\s*대사\s*[:：]`)가 `risk_team_compare_workflow`로 보낸다.

### 새로 추가할 것

- 드롭다운 선택지 `문서 대사`(영문 `document_compare`)를 추가한다. 질문 앞에는 `문서 대사: `를 붙인다.
- 백엔드는 `문서 대사:`를 먼저 검사해 새 워크플로우 `risk_team_document_compare_workflow`로 보낸다. 지금 접두어 검사는 `문서 대사:`에 걸리지 않으므로 기존 대사와 섞이지 않는다.
- 화면에서 "문서 대사"를 골랐는데 질문 앞에 `대사:`를 직접 적었으면 지금처럼 충돌 안내를 낸다.
- 새 워크플로우를 따로 두는 이유: 예산·저장 상태·보고서 구조가 다르다. 기존 대사의 회귀 위험이 없다. 외규 이름 먼저 읽기·항목 대조·비교 단계는 기존 대사 모듈을 그대로 부른다.
- GENOS 현장에서는 화면 드롭다운에 선택지를 추가하고, 워크플로우 편집기의 파이썬을 바꿔야 한다. 코드 ZIP 적용과 별도다.

## 3. 사용자 화면 흐름

**첫 질문**: `리스크관리규정 대사해 줘`

1. 문서 찾기(모델 0회). 질문에 나온 등록 내규 이름을 찾는다. 팀에 허용된 내규만 본다. 이름이 겹치면 긴 이름을 우선한다(ADR-1433·1435에서 쓴 방식).
   - 하나로 정해짐 → `「리스크관리규정」(읽기 묶음 29개, 예상 약 1시간)으로 문서 대사를 시작합니다.`
   - 여러 개이거나 이름이 없음 → `어느 문서로 대사할까요? 1. 리스크관리규정 2. 리스크관리규정 시행세칙 3. … 번호로 답해 주세요.` 다음 턴의 `1`로 확정한다.
   - 못 찾음 → `등록된 내규 중 찾지 못했습니다.` 비슷한 제목 후보가 있으면 함께 보여 준다. 문서가 없다고 단정하지 않는다.
2. 실행 중 진행 표시: `묶음 7/29 · 대사 단위 41개 · 차이 6건 · 외규 못 찾음 2건`
3. 끝나면 보고서(6장)를 보여 준다. 보고서 끝에 보류 항목을 번호로 묻는다.

## 4. 실행 방식 — 사용자가 정할 것

문서 하나가 1시간 안팎이라 한 번의 응답으로 끝나지 않는다. 두 방식 모두 **묶음 단위로 저장**하므로 저장 구조는 같다. 차이는 다음 묶음을 누가 이어 가느냐다.

| | A. 채팅 "계속"으로 이어 가기 | B. 뒤에서 끝까지 자동 (추천) |
|---|---|---|
| 동작 | 한 요청에 정해진 양만 하고 저장. 사용자가 `계속`을 보내면 다음 묶음부터 | 시작하면 서버가 저장된 실행을 끝까지 이어 감. 사용자는 `진행 상황`을 묻거나 끝난 뒤 결과를 봄 |
| 사용자 부담 | 문서 하나에 `계속` 5~25번(요청당 한도에 따라) | 시작 한 번 |
| 기존 코드 | 내규 근거 조사 워크플로우의 `continuation_of` 방식 그대로 | 서빙 안의 기존 백그라운드 작업 방식(`ad_jobs.py`: 저장된 작업표·중단 후 재시작)을 사용 |
| 현장 확인 필요 | 적음 | GENOS 코드서빙에서 긴 작업을 돌릴 수 있는지(재시작, 시간 제한, 다른 질문과 동시 처리) |

추천 순서: **이어 가기 실행기를 먼저 만들고(A와 B 공통), B는 그 실행기를 서버가 자동으로 부르게 붙인다.** B를 현장에서 못 쓰면 A로 그대로 쓸 수 있다.

어느 방식이든 공통으로 지킨다.

- 저장은 Oracle(또는 로컬 SQLite) 실행 기록에만 한다. 코드서빙 디스크에 저장하지 않는다.
- 공급자 결과 불명(UNKNOWN)이나 확정 429가 나오면 다시 보내지 않고 실행을 **일시정지**한다. 실패로 덮지 않는다. 사용자가 다시 시작하면 그 묶음부터 이어 간다.
- 문서 하나의 호출·비용 상한을 둔다. 넘으면 일시정지하고 알린다.
- 같은 문서를 같은 사람이 동시에 두 번 시작하지 못하게 한다.

## 5. 서버 처리 단계 (새 워크플로우)

| 단계 | 모델 | 하는 일 |
|---|---:|---|
| DOCUMENT_SELECT | 0회 | 문서 확정. 문서 ID와 판본 해시를 고정한다 |
| INVENTORY | 0회 | `reading_groups.build`로 묶음 목록을 만든다. 모든 원문 문단이 정확히 한 번 들어갔는지 검사한다. 판본이 바뀌면 이어 가기를 거절한다 |
| GROUP_READ | 묶음당 1회 | 묶음 원문(상위 제목·머리/꼬리 문장 포함)을 주고, 행마다 "대사 단위 / 대상 아님(이유) / 보류(이유)"로 나눈다. 단위마다 개념 이름, 확인할 항목(정의·조건·의무 등), 외규에서 찾을 내용을 낸다. 빠진 행이 있으면 보완 1회 |
| EXTERNAL | 단위당 0~1회 | ① 그 내규 문서에서 읽은 원문에 적힌 외규 이름으로 그 문서를 먼저 읽는다(ADR-1435에서 확인). ② 기존 승인된 근거 연결·명시 참조를 쓴다(데이터에 내규→외규 참조 186건). ③ 없으면 "내규 내용 + 사용자 질문"으로 검색한다. **같은 실행에서 이미 읽은 외규 문서는 다시 조사하지 않고 재사용한다** |
| ITEM_REVIEW, COMPARE | 단위당 2회 | 기존 대사 모듈 그대로. 쟁점 하나씩 부른다(ADR-1429에서 여러 쟁점을 한 번에 보내면 중복 오류가 났다) |
| 묶음 저장 | 0회 | 묶음 결과를 저장한다. 다시 시작해도 끝난 묶음은 부르지 않는다 |
| REPORT | 0회 | 전체 보고서와 보류 번호 질문 |

외규 재사용이 중요하다. 문서 전체에서 같은 감독규정을 단위마다 새로 찾으면 호출이 크게 늘어난다.

## 6. 보고서 모양

- 맨 위: 문서명·판본·기준일과 집계. `전체 634행 · 대사 단위 180 · 부합 120 · 차이 35 · 외규 못 찾음 12 · 대상 아님 130행 · 보류 8`
- 차이가 있는 단위를 먼저 보여 주고, 부합은 접어 둔다. 각 단위는 지금 대사표와 같은 칸을 쓴다: 내규 출처·원문 | 외규 출처·원문 | 판정·의견 | 미확인.
- "대상 아님" 행은 이유와 함께 접힌 목록으로 둔다. 빠뜨린 것이 아님을 사용자가 확인할 수 있게 한다.
- 끝에 보류 항목 번호 질문을 둔다(인계 문서 5.3).
- 수백 행이라 채팅 한 화면에 다 넣으면 길다. 장(章)별 접기를 먼저 하고, 파일 내려받기가 필요한지는 GENOS 화면에서 확인한다.

## 9. 위험과 미확인

- 시간·비용: 문서 하나 약 45~75분, 약 0.8~1.4달러(추정). 실험 2에서 실측한다.
- 단위 수: 60행 묶음이 30행보다 단위를 적게 만들었다(155 대 201). 단위를 더 크게 잡게 하면 호출이 줄지만 비교가 거칠어질 수 있다.
- 단위별 호출: 항목 대조·비교를 묶음 단위로 한 번에 하면 호출이 크게 준다. 대신 ADR-1429의 중복 오류가 다시 날 수 있다. 처음에는 단위별로 만들고, 묶음 단위 호출은 따로 실험한다.
- 공급자 장애: 수백 번 호출하면 429가 날 가능성이 크다. 지금 정책은 확정 429에 다른 공급자로 한 번만 바꾼다. 그 뒤에는 일시정지되므로 재개 경험이 중요하다.
- GENOS 현장: 긴 백그라운드 작업 가능 여부, 화면 드롭다운 추가, 워크플로우 편집기 교체, 보고서 길이 표시.
- 병행 세션: MAIN과 작업 폴더가 자주 바뀐다. 구현은 선택 MAIN 사본에서 하고 테스트도 사본에서 돈다(인계 문서 부록 C).
