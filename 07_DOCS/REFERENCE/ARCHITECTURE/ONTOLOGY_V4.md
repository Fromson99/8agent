## 무엇을 만드는가

에이전트가 실제 질문을 조사하며 남긴 판단(어떤 조문을 읽었고, 어떤 연결을 따라갔거나 안 갔고, 무엇을 답에 썼는지)과 사용자의 재지시·정정을 에이전트 레이어에 남긴다. LLM이 이를 개념 단위로 묶고 필요한 새 스키마를 제안해 Dataiku S3에 JSON으로 저장한다. 사람이 승인·수정한 JSON을 골드 표에 SQL로 적재하면, 원문(조항)에 붙은 온톨로지가 된다. 다음 질문은 그 온톨로지로 필요한 조문 묶음을 바로 찾는다.

처음에는 온톨로지가 거의 없어 조문을 하나씩 읽는다. 대신 사용자는 멀티턴으로 "그 조문 읽어", "그 연결 가", "그거 가져와", "그거 빼"처럼 판단을 바로잡으며 답을 찾아간다. 이 재지시가 다음 온톨로지의 가장 좋은 재료가 된다.

## 전체 흐름

v4의 목표 흐름이다. 대상 지정 재지시·범용 새 스키마·운영 골드 이관 전체가 이미 구현됐다는 뜻은 아니다. 내용 승인 뒤 모델 확인·필요 신청·Dataiku 적재·검증·사용 전환을 거친다. 가정 시뮬레이션은 별도 보조 기능이며 모든 승인 건의 필수 이관 단계로 두지 않는다.

## 먼저 할 것: 핵심 MVP — 초기 계획 기록

현재 개발 기준은 [행동별 최소 입력·응답 계약](ONTOLOGY_V4/ACTION_CHOICE_CONTRACT_20261026.md)이다. ADR1066 후보의 743파일 rev-002에서 구현·동일 동결본 합성 계약/API 80개 검사를 완료했다. 실모델은 미실행이고 실제 생성 호환성·법률 품질은 미확인이다. 입력 문자 차단 해제·출력 토큰 상한 없음을 유지한다. [구현 상태](ONTOLOGY_V4/MVP_EXECUTION_REPAIR_STATUS_20261026.md)의 앞선 결과와 이번 개발 상태를 구분하며 MAIN103·GENOS는 변경하지 않는다.

[핵심 MVP](ONTOLOGY_V4/MVP.md): ① 도착한 조문의 연결을 **컴파일한 묶음**으로 주면 에이전트가 더 잘 찾는가(연결만 준 경우와 비교) ② 온톨로지가 일부만 있을 때, 없는 곳을 에이전트가 직접 판단한 뒤 온톨로지화 제안(기존 스키마에 넣거나 새 스키마 제안, 사용자 수정 가능)으로 채울 수 있는가. 아래 단계는 MVP 결과를 본 뒤 진행한다.

## 원칙

- **지식은 원문(조항)에 붙는다.** 질문은 발견 이력이다. 다른 질문이 같은 조항에 오면 같은 지식을 쓴다.
- **판단 기록은 재료이고, 승인되어 골드에 적재된 것만 온톨로지다.** 사용자의 선택이나 침묵을 승인으로 보지 않는다.
- **저장 위치가 정해져 있다.** 사용자 로그·LLM 판단은 에이전트 레이어, 온톨로지 작업 JSON은 Dataiku S3, 사용하는 온톨로지는 골드. GENOS 서빙에는 저장하지 않는다.
- **스키마는 한 번에 만들지 않는다.** 연결 타입 14종은 그대로 쓰고, 조항 안의 구조는 샘플에서 시작해 승인 절차로 늘린다. LLM은 제안만 한다.
- **한 턴의 답과 조사 전체의 완료는 다르다.** 확인한 것·못 본 것·갈 수 있는 연결을 함께 보여준다.
- **읽지 않은 조항의 내용은 지어내지 않는다.** 연결 근거로 알 수 있는 조사 목적만 쓴다.
- **정정과 가정은 다르다.** 잘못 고른 조문의 정정은 지식 수정이고, "200만 원이면?"은 별도 시나리오다.
- **원문은 바뀌지 않는다.** 수정 전 판단·이견·실패 이력을 보존한다.

## 현재 상태

- 기존 코드에 턴 분류(12종)·세션 구조·연결 타입 14종·Streamlit 승인 화면이 있고, v4는 이를 이어서 쓴다. 기존 `legal_knowledge` 저장소(초안·게시, 꺼져 있음)는 v4 경로에서 쓰지 않는다. 근거는 [현재 상태](ONTOLOGY_V4/CURRENT_STATE.md).
- 판단 재지시, 10개 질문 연결, 개념 묶음, S3 작업 폴더, 제안 스키마·시뮬레이션·골드 매핑·적재, 적재 묶음의 경로 조립은 미구현이다.
- 지식 설정은 MAIN103에서 `management_enabled=false`, `consumer_mode=off`다.
