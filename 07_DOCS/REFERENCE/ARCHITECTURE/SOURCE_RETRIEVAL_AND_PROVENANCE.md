# 원문 관계 추적 우선 · 결정론적 최종 출처표 설계

> 후속 설계: [데이터 기반 연결과 고난도 문제 점검](DATA_LINKAGE_AND_HARD_CASES.md). 관계 발견·해소는 데이터 구축 시점의 세대 결속 색인이 중심이고, 아래 요청별 SourceFollowup은 읽기 진행 상태로 한정한다. 기존 작업 코드의 정밀 참조/공식 위임 기능과 실험 세대의 반영 여부도 후속 문서에서 구분했다.

- 작성: 2026-09-20
- 상태: 제안 / 코드·스키마·운영 미변경 / 모델 실험 미실행
- 기준: ADR-0479 linked-context rev-001, revision SHA-256 `5871b6b33a1e0c345f73528933688744908699451533c7c16330911836ac6fe6`

## 1. 핵심 결정

**도메인 하네스의 첫 책임을 ‘법률 정답을 만들어 내는 것’이 아니라 ‘질문과 관련된 본칙·단서·위임·준용·대상별 분기·수치 참조 원문을 놓치지 않고 가져오며 출처를 보존하는 것’으로 둔다.**

법률 판단은 그 다음이다. 검색 후보가 아니라 실제 READ한 원문을 확보하고, 답변에 사용된 범위를 서버가 최종 표에 연결한다. 출처 표의 법령명·조항·발췌문·버전·좌표는 모델이 작성하지 않는다.

세 가지를 분리한다.

1. **원문 확보:** 관계의 출발 문장과 도착 원문을 읽고, 못 찾은 것은 미확인으로 남긴다.
2. **답변 사용:** 모델이 설명에 사용할 근거 핸들을 선택하거나, 원문 제공 응답이 검증된 발췌를 명시적으로 제시한다.
3. **출처 확정:** 최종 살아 있는 문단/발췌 항목의 핸들만 원문 저장소와 결합해 서버가 표를 만든다.

결정론이 보장하는 것은 같은 최종 사용 기록·같은 원문 세대·같은 렌더러 버전에서 같은 출처 행/표가 나온다는 것이다. 질문을 다시 모델에 보내도 같은 답변·같은 출처를 선택한다는 보장이나, 그 출처가 법률 결론을 의미적으로 지지한다는 보장은 아니다.

## 2. 현재 사실과 과거 실패에서 가져갈 제약

| 확인된 사실 | 설계에 반영 |
|---|---|
| ADR0479: 두 결정 조문을 작성·검토에 제시하고 인용했지만 저장 기준답변과 불일치 | 출처 정합성과 의미 정확도를 별도 상태·검증으로 둔다. 표가 있다는 이유로 정답 인증 금지 |
| 이전 더블하네스는 모델의 장부·ID·finding 작성이 병목 | 탐색 작업·연결·버전·출처 장부는 서버 소유. 모델은 짧은 핸들과 선택/탐색 요청만 사용 |
| 현재 linked_context는 이미 읽은 원문만 최대 2개/3000자로 보존 | 이것은 수집기가 아니다. 새 후보에서는 미독 위임 대상도 정상 READ 경로로 확보하며 이 보존 상한을 근거 완결성 기준으로 쓰지 않는다 |
| ReferenceResolver는 주로 조(article-root)까지만 해소, 단일 target 반환과 기존 targets[0] 사용 경로 존재 | 항·호·목·별표·복수 대상 해소를 별도 보완. ‘정확히 해소됨’이라는 과거 라벨만으로 정밀 좌표 확보를 선언하지 않는다 |
| final claims는 source_ids만 내보내며 evidence spans는 내부 장부에 남음 | 출처표 생성은 source_ids로 나중에 추측하지 않고 최종 claim의 evidence/span을 잃기 전에 수행 |
| term-runtime-v1 Answer/Claim은 additionalProperties=false | 임의 필드 추가 금지. 후보 전용 v2 계약과 입력·출력 소비자를 함께 이행 |
| 현재 /rag/ 화면은 answer.text 뒤에 확인 필요 문구를 다시 붙임 | 그대로 두면 표가 맨 마지막이 아니다. 서버 최종 텍스트와 화면 순서를 같이 수정 |
| 현행 MAIN은 의미 Rule/조건/효과 스키마를 제거한 원문·용어 기반 | 법률 의미 그래프를 정본으로 재도입하지 않는다. 관계 신호는 원문 좌표에 묶인 요청별 탐색 단서 |

운영 기본값 document-navigation-v1은 유지한다. 현재 후보는 명시적 객체 주입 경로이며 작업 코드·완료 후보·활성 릴리스를 구분한다. GENOS 현장 접속/검증은 이 설계 범위가 아니다.

## 3. 도메인 하네스가 ‘가져와야 할 것’

| 원문에서 발견한 신호 | 확보할 최소 의미 단위 | 놓치면 안 되는 연결 |
|---|---|---|
| “대통령령/세칙으로 정한다”, “위임한다” | 위임 문장 + 실제 하위 규정의 대상 항목 | 하위 규정이 다시 위임하면 필요한 범위에서 계속 추적 |
| “다만”, “제외한다”, “에도 불구하고” | 본칙 + 단서/예외 + 예외가 지목하는 본칙 | 같은 조의 다른 항에 있는 예외, 역참조로 드러나는 예외도 후보화 |
| “제N조를 준용한다” | 준용 출발 문장 + 대상 규정 + 읽어 바꾸는 문구 | “이 경우 A는 B로 본다”, 적용 제외 단서. 대상 조문만 가져오고 치환 문구를 버리지 않음 |
| “X는 …, B는 …”, “각 호에 따라” | 공통 머리 문장 + 관련 분기와 조건 | 대상 유형이 미확인인 경우 양쪽 분기/구분 기준 확보, 임의로 한쪽만 확정 금지 |
| “비율은 제N조/별표에 따른다” | 참조 문장 + 비율값 + 단위·분모·적용 구간·단서 | 표의 행·열 제목/주석/시점도 함께 확보. 수치만 떼어 오지 않음 |
| “같은 항”, “전항”, “위 비율”, “이 경우” | 지시 문장 + 선행 대상 | 구조·문맥으로 유일하게 풀리지 않으면 모호함으로 기록 |

분류는 탐색용이다. 단어 일치만으로 법적 예외나 적용 우선순위를 확정하지 않는다. 같은 표지가 없어도 모델이 추가 탐색을 요청할 수 있다. 정규식에 안 걸렸다는 것을 ‘예외 없음’으로 기록하지 않는다.

## 4. 실행 흐름

### 4.1 관련 원문을 확보하는 루프

1. 기존 FTS·조문 지목·용어/정의·참조/역참조로 출발 후보를 만든다. 질문 분류 결과가 다른 자료 접근을 막지는 않는다.
2. 후보의 발췌/목차로 선택한 범위를 **정상 SourceSession READ**로 읽는다. preview는 계속 인용 불가다.
3. 실제 읽은 원문에서 명시 지목과 관계 신호를 발견한다. 서버가 출발 span, 원문 표기, 해소 후보, 후속 읽기 상태를 기록한다.
4. 요청 범위 안에서 정확히 해소된 **현재 조사 초점의 직접 참조**는 도구 예산을 차감하고 읽기 큐에 넣는다. 관련성이 아직 없는 모든 검색 결과를 일괄 재귀 확장하지 않는다.
5. 조번호 없는 위임이나 모호한 참조는 locator/검색 후보를 만든다. 모델은 필요한 후보/범위를 선택한다. 이름·판본이 모호하면 임의 첫 대상을 택하지 않는다.
6. 읽은 도착 원문에 다시 필요한 참조가 있으면 이어간다. 1홉 고정이나 2개 보존 고정으로 종료하지 않는다. 동일 세대·좌표 중복 읽기를 합치고 순환 참조를 감지한다.
7. 완결된 근거 묶음을 작성 입력으로 넘긴다. 아직 필요한 대상이 미독/미해소/범위 밖이면 그 상태도 넘긴다. 예산 소진은 ‘확보 완료’가 아니다.

자동 추적은 새 모델 호출 없이 가능한 해소·읽기에 한정한다. 모든 단서마다 별도 모델 호출이나 독립 finding을 요구하지 않는다. 모델이 노트를 못 만들었다는 이유로 이미 확보한 원문 응답을 막지 않는다.

### 4.2 요청별 추적 기록 — 제안

새 `SourceFollowup`은 서버 기록이며 LLM의 필수 출력 JSON 장부가 아니다.

- origin: source_id + 실제 읽은 block/Unicode code-point span + hash.
- cue: 원문 문자열과 탐색용 종류; 모델 제안이면 observation임을 표시.
- target: 원문 locator, 문서/판본 후보, 확정된 조·항·호·목/별표 위치.
- resolution: exact / ambiguous / not_found / outside_scope / unsupported_structure.
- reading: pending / partial / complete / failed / budget_exhausted.
- provenance: 사용 resolver 버전·reference_id·검색/읽기 observation·도착 evidence/span.
- relevance: 현재 조사 초점·근거 연결 또는 명시적 보류 사유. 법적 적용 판정과 분리.

완료 조건은 ‘서버가 발견한 관련 추적 항목이 해소됐는가’이지 ‘모든 법률 예외가 존재하지 않는가’가 아니다. 미발견 관계는 검출률 평가의 대상이다. 보류 사유를 적었다고 원문을 확보한 것으로 세지 않는다.

### 4.3 전문 대신 필요한 원문 단위

항·호·목/표 행을 읽을 때 상위 머리 문장과 적용 단서·관련 분기를 묶는다. 블록 경계와 문자열 좌표를 보존하고 서로 떨어진 구절을 한 문장처럼 접합하지 않는다.

SourceSession._read는 현재 source_id가 있으면 조 전체 블록을 택하고, source_id 없는 unit handle이면 해당 구조 범위를 읽는다. 따라서 기존 카드에서 uid만 바꿔도 정밀 읽기가 된다고 가정하지 않는다. **제안 subunit/range handle을 canonical source에 검증해 정상 READ로 연결**하고 exact-span 검증을 유지한다.

LegalIndex의 Paragraph.full()은 탐색/범위 결정에 재사용할 수 있지만 문자열 재조립 결과 자체를 원문 증거로 승격하지 않는다. 인용 원문은 Store의 검증된 블록에서 다시 읽는다. 구조가 불명확하면 더 넓은 원문 범위를 읽되, 항·호를 추측하지 않는다.

## 5. 최종 답변과 ‘사용했다’의 정의

### 5.1 두 종류의 최종 내용

- **원문 제공 항목:** 요청에 필요한 자료를 확보했다는 결과. 검증된 원문 발췌와 연결 경로를 제공하며 법률 적용 결론을 주장하지 않는다. 의미 검토가 미완료라도 정확한 원문 제공 자체는 유지할 수 있다.
- **해석 문단:** 모델이 작성한 요약·적용 설명. 필요한 evidence/span 핸들을 선택하고 별도 의미 검토 상태를 갖는다.

최종 사용 집합은 이 두 종류의 **최종 살아 있는 출력 항목**이 명시적으로 참조하는 검증된 span의 합집합이다. 내부에서 읽은 모든 자료, 참고 카드, 반려·철회된 초안의 근거를 사용 출처로 올리지 않는다.

서버가 모델의 잠재적 사고 과정 전체를 알 수는 없다. 따라서 표 제목은 ‘최종 답변의 명시적 인용·제시 근거’로 하며, 모델이 실제로 머릿속에서 사용한 모든 정보를 추적했다고 주장하지 않는다.

예외를 모델이 인용하지 않았다고 확보 기록까지 없애지 않는다. 필요한 예외 원문은 원문 제공 항목으로 명시적으로 출력할 수 있다. 이 경우 표의 용도는 ‘원문 제공’이지 ‘해석 결론을 지지함’이 아니다. 필요한 원문을 직접 보여주는 것이 1차 결과다.

### 5.2 핸들과 발췌 선택

모델은 법령명·조번호·발췌 텍스트·표 행을 생성하는 대신, 서버가 발급한 **실제로 읽고 제시된 단위 핸들**을 선택한다. 원문 제공 항목은 검증된 서버 선택 기록으로 만든다.

정밀 단위는 조·항·호·목·문단·표 셀/행의 실제 구조와 exact spans를 보유한다. 도입 시 기존 E만 선택된 기록은 ‘그 E 전체가 인용 범위’로 정직하게 표시한다. 사후에 사용한 항/호를 모델로 추측해 좁히지 않는다. 부분 인용은 검증된 하위 핸들을 명시적으로 선택했을 때만 가능하다.

현재 P/E 체계와 서버 장부를 재사용한다. 새로운 자유형 원문 인용 JSON이나 모델 생성 source ID를 요구하지 않는다.

## 6. 결정론적 출처표 계약

### 6.1 행 생성 절차 — 모델 호출 없음

1. 최종 출력 항목/claim의 순서와 버전을 동결한다.
2. 각 항목의 evidence/span 핸들을 해소하고, 원문 제공 또는 모델 입력의 실제 제시 이력을 확인한다.
3. scope·generation·원본 해시·block hash·span hash·좌표·claim/review 최신성을 재검증한다.
4. 문서 정식명은 해당 세대 document metadata, 조·항·호·목 경로는 source_unit 계층과 실제 span의 block→unit 매핑에서 조회한다. article-root unit_id만으로 세부 항·호를 추정하지 않는다.
5. 발췌는 `source_block.text[start_cp:end_cp]`에서 복원한다. 여러 span은 별개 인용 구간으로 표시한다.
6. 같은 판본·source·동일 exact span 집합은 한 행으로 합치고 사용 문단 번호를 모은다. 서로 다른 판본과 별도 구간은 법령명/조번호가 같아도 함부로 합치지 않는다.
7. 최종 문단의 최초 등장 순서 → 문서 ID/판본 → 원문 구조 순서 → start/end/hash로 정렬한다. 임의 run UUID나 DB 반환 순서로 번호를 정하지 않는다.
8. 서버가 [근거 1] 등의 번호와 본문 연결을 생성한다. 모델이 번호를 미리 붙여 출처 순서를 바꾸지 못하게 한다.
9. 답변 본문 → 미확인/적용 한계 → **출처표를 맨 마지막** 순으로 렌더링한다. 서버 결과를 다시 모델에게 넘겨 고쳐 쓰게 하지 않는다.
10. 표와 본문을 함께 publication.prepare 이전에 동결·검사·해시 결속한다. 재개는 저장된 결과를 재수출하며 현재 최신 DB로 출처를 다시 생성하지 않는다.

`표의 span 집합 = 최종 명시 인용·제시 항목의 검증된 span 집합`을 양방향 검사한다. 빠진 행도, 사용하지 않은 행도 허용하지 않는다. 연결 경유지만 있고 최종 출력에 쓰이지 않은 원문은 내부 추적에만 남긴다.

### 6.2 사용자에게 보이는 예시 — 합성, 실제 법령·비율 아님

본문: 관련 비율의 위임 문장과 위임 대상 비율표를 확보했습니다. 적용 대상의 구분은 추가 확인이 필요합니다.

| 근거 | 사용 위치/용도 | 법령·문서 | 조문·구체 위치 | 실제 발췌 | 원문 판본·위치 |
|---|---|---|---|---|---|
| 1 | 원문 항목 1 / 참조 출발 | 예시 규정 A | 제10조제2항 | “비율은 예시 세칙 B 제5조에 따른다.” | 저장 판본 A / 검증된 원문 위치 |
| 2 | 원문 항목 2 / 참조 대상 | 예시 세칙 B | 제5조제1항 | “X의 비율은 별표 1에 따른다.” | 저장 판본 B / 검증된 원문 위치 |
| 3 | 원문 항목 3 / 비율 자료 | 예시 세칙 B | 별표 1, X 행·비율 열 및 주석 | “X / 10%”와 실제 분모·조건 주석 | 저장 판본 B / 검증된 표 위치 |

비율표의 값만 인용하고 분모·조건을 빼지 않는다. 화면상의 대표 인용이 길어 접힌다면 펼치기/구조 JSON에는 전체 선택 발췌를 보존한다. 축약 표시를 원문 전체처럼 제시하지 않는다.

### 6.3 표시값의 정직성

- 항·호 경로가 없으면 ‘제N조, 블록 K, 문자 a–b; 세부 항호 미확인’으로 출력한다.
- 공포/시행일은 저장소에서 확인된 경우만 표시한다. 없으면 판본 해시와 ‘시행일 미확인’; 현재 법령으로 자동 표기하지 않는다.
- PDF 페이지/좌표는 실제 매핑이 있을 때만 표시한다. 구조 블록 번호를 PDF 페이지로 바꾸지 않는다.
- 링크는 서버가 관리하는 버전 결속된 원문 조회에서 만든다. 현재 /section 또는 /document/read는 활성 Store를 읽으므로 과거 generation 링크로 그대로 사용하면 안 된다.
- 버전 결속 조회 endpoint/접근제어는 신규 제안이다. 구현 전에는 검증되지 않은 URL 대신 문서·조문·블록 좌표를 출력한다.
- HTML/Markdown 표의 파이프·개행·태그·링크는 이스케이프한다. 표시 이스케이프 전 원문 문자열과 hash가 정본이다.
- 근거가 없으면 빈 표에 자료를 채우지 않고 ‘확인된 인용·제시 근거 없음’이라고 마지막에 명시한다.

## 7. 서버 산출물과 실제 연결 지점

신규 이름은 모두 **제안**이다.

- `source_followups.py`: 원문 기반 후속 읽기 큐·해소·미확인 상태. source_first_navigation/SourceSession을 호출하며 별도 검색 파이프라인을 만들지 않는다.
- `source_provenance.py`: 최종 항목/claim → 검증된 exact spans → 출처 행. 법적 정답 판정 없음.
- `answer_renderer.py`: 본문·한계·출처표의 순서와 안정적 번호·escaping. 모델 호출 없음.
- `Answer.provenance`: 정책/renderer 버전, 원문 generation/store hash, 최종 내용 revision/hash, rows, rows hash, 미확인 연결.
- row 내부: citation ID, 최종 항목/claim ID·version, 용도, document/source IDs, 구조 path, exact spans·hashes, 판본 metadata, 원문 조회 식별자. 모델이 쓴 이름은 canonical field로 채택하지 않는다.
- `Answer.body_text`: 출처표를 제외한 서버 확정 본문. `Answer.text`: body + limitations + footer를 담은 완성 출력. 기계 소비자는 provenance.rows를 사용한다.

### 계약·데이터 이행

- v1 답변·완료 run은 그대로 읽는다. 후보에는 새 schema ID/Answer 버전과 후보 계약 root를 사용하고, 같은 포트 이름을 쓸 경우 후보 전체 Contracts의 매핑·엔진 해시를 맞춘다. 공용 v1 schema에 몰래 필드를 추가하지 않는다.
- stage input/output, publication, API, 화면, 복사/다운로드, 피드백(run hash)의 연결을 함께 검사한다. provider_receipt에 출처 구조를 숨기는 우회는 쓰지 않는다.
- 원문 원본의 전면 재구축은 요구하지 않는다. 기존 구조가 있으면 요청별/파생 인덱스로 정밀 해소한다. 구조 자체가 없거나 파싱 오류이면 해당 데이터의 별도 새 세대 재구축이 필요하다.
- 요청 장부는 신규 테이블/형식이 필요하면 버전 올리고 기존 읽기·재생을 보존한다. 기존 SQLite/완료 ADR을 수정하지 않는다.
- generation/권한이 바뀐 경우 같은 읽기/출처 캐시를 재사용하지 않는다. 게시 후 원문 링크 조회도 현재 사용자 권한을 재검사한다.

| 참조가 여러 판본·여러 대상 | 범위를 모두 유지하거나 판본 선택 요청 | 첫 검색 결과를 자동 정답으로 확정 금지 |
| A→B→A 순환 | 세대·source·범위 기준 재방문 감지, 신규 범위만 읽기 | 순환 감지가 원문 확보 실패/성공 자체를 뜻하지 않음 |
| B는 확보했지만 C 참조가 미완료 | B까지의 상태와 C의 누락 보존 | 전체 확보 완료 표시 금지; 확인한 원문 응답은 유지 |

| 텍스트에 HTML/가짜 출처표 포함 | 원문은 데이터로 취급, 안전한 렌더링 | 모델/원문이 공식 출처 행·표 순서를 덮어쓰지 못함 |

해석용 최종 인용의 잘못된 제거와 원문 제공의 과도한 폭주를 함께 측정한다. 모델의 검토 판정 하나가 확보한 원문 전체를 지우는 예전 병목으로 돌아가지 않는다.

## 9. 문맥과 자원 — 토큰 절감 대신 완결성

N1 [사용자 목표/설계 해석]: 70,000토큰은 모델 한 호출의 전체 문맥(입력+예약 출력) 허용 상한으로 해석한다. 전체 실행 누적 토큰 한도가 아니다. 실제 endpoint/model이 허용하는 더 작은 한도는 별도로 준수한다. 구현 시 이 단위를 설정·보고에 명시한다.

N2 [관측]: 현재 후보는 max_context_chars=60,000 **문자**이며 output 상한은 별도다. 70,000으로 숫자만 바꾸면 토큰 제한이 되지 않는다. 모델 토크나이저/검증된 제공자 계산을 연결해 system·도구/schema·원문·출력 예약 전체를 측정해야 한다. 계산 방법 미확정 상태를 토큰 상한 준수로 보고하지 않는다.

N3 [이전 단회 관측]: ADR0479는 추가 2,331자, 모델 3콜, 누적 입력 42,889토큰이었다. 이 값은 새 다중 참조 추적의 비용/정확도 예상치가 아니다.

N4 [구조적 목표]: 출처표 작성에 새 모델 호출 0회. 서버 원문 재조회·hash 검사·렌더링 CPU/IO는 발생한다. 관계 해소가 모호할 때 추가 모델 탐색 호출은 발생할 수 있으며 무료라고 하지 않는다.

문맥 선택 우선순위는 현재 질문의 원문 묶음 → 그 단서/대상 조건 → 위임·준용/수치 참조의 필요 구간 → 미확인 연결이다. 관련 없는 과거 탐색 기록은 서버에 두고 필요한 요약 상태만 모델에 전달한다. 원문 묶음이 상한을 넘으면 판단 단위를 나눠 읽되 조합 단계에 필요한 근거를 재제시한다. 전체 문서 무차별 적재나 글자 수로 단서 중간 절단은 금지한다.

금액·지연·개발 일정·회수율 개선은 미산정이다. 후속 실험에서 추가 READ/검색, 호출별 입력·출력, 최종 row 수·크기, source verification IO, E2E 지연을 계측한다. 참조망이 큰 질문은 비용이 증가할 수 있다. 이 설계는 절감을 성공 조건으로 삼지 않는다.

## 10. 검증 기준과 도입 순서

### 먼저 고정할 구조 계약

- T01 위임 2단계, 같은 조의 단서, 준용 치환, X/B 분기, 별표 비율·분모·주석을 각각 원문 좌표로 가져오는 fixture.
- T02 모호함·복수 판본·미수록·권한 밖·역참조 오연결·순환·부분 READ·timeout을 완결 상태와 구별.
- T03 최종 인용/제시 span 집합과 출처표 span 집합의 정확한 양방향 일치. 검증 대상 각 fixture에서 누락·과잉 행 0 [계약 목표, 실제 시스템 무오류 추정 아님].
- T04 법령명/조번호/발췌를 모델이 틀리게 출력해도 공식 행은 원문 metadata/spans만 사용. 본문 법률 서술의 의미 정확도는 별도 평가.
- T05 같은 확정 출력·세대·renderer에서 순서·문자열·rows hash 동일. DB 입력 순서, 무작위 run ID, 재시작을 바꿔도 표 내용/순서 불변. 의도된 generation/version 표시는 그대로 유지.

### 회수 품질과 의미 품질을 분리

1차 지표는 필요한 **원문 구간/관계 대상 확보율**, 정확한 연결율, 거짓 완료, 최종 발췌-출처 정합성이다. 단순 조 root 2/2로 항/호/표 주석 확보 성공을 대신하지 않는다. 참고 정답 좌표는 실행 종료 뒤 결합한다.

2차 지표는 본문 답변 품질과 예외 적용 정확도이며, 출처표 성공으로 대체하지 않는다. 의미검토 모델이 SUPPORTED라고 한 비율을 정답률로 쓰지 않는다. 동일 질문의 여러 실행을 독립 법률 사례 수로 부풀리지 않는다.

도입 순서:
1. 서버 출처 산출물과 최종 표 계약을 합성 데이터로 구현·확인.
2. 위임/단서/준용/분기/비율 추적을 기존 읽기에 연결, 원문 제공 경로 검증.
3. CM003과 관계별 사례에서 실제 모델의 확보·사용·출처 흐름을 소규모 동결 검증. 채점 방식은 별도 결정.
4. 같은 시점 기준군과 전체 51문항 비교 후 승격 여부 판단. 기능상 출처 보장이 품질 승격 절차를 생략하지 않음.

실험 전 ADR 선점, 후보 격리, 부모/스키마/renderer/resolver/모델/데이터 버전 동결. 실패 후 변경은 새 후보 이력으로 남기며 운영에는 별도 명시 승인·릴리스·rollback 절차만 사용한다.

## 11. 자체 설계 검토와 남은 경계

- R1 [높음 / 설계 반영, 구현 미해결]: 조 단위 참조 해소를 항·호·별표 확보로 과장할 위험 → 실제 좌표·부분 완료 상태 요구.
- R2 [높음 / 설계 반영, 구현 미해결]: source_ids만으로 발췌를 재구성하면 잘못된 세부 인용 → final claim/span 원장 기준 생성.
- R3 [높음 / 설계 반영, 구현 미해결]: v1 닫힌 스키마·publication hash·화면 순서 불일치 → 후보 v2 계약부터 API/UI까지 동시 연결.
- R4 [높음 / 설계 반영, 품질 미검증]: 올바른 출처표에 틀린 해석이 붙을 수 있음 → provenance_verified와 semantic_review 상태를 분리, 정답 인증 금지.
- R5 [중간 / 설계 반영, 구현 미해결]: 70,000문자/토큰 혼동 및 다중 참조 폭주 → 실제 토큰 계산·추적 예산·미완료 표기.
- R6 [중간 / 설계 반영, 구현 미해결]: 현재 원문 조회 링크가 옛 답변에 최신 문서를 보여줄 수 있음 → generation 결속 조회 전에는 좌표만 제공.

같은 작성자의 자체 검토이며 독립 감독·법률 전문가 검증은 아니다. 구현/API 호출/모델 평가/배포는 이 문서 작성에서 실행하지 않았다.
