## 3. 현재 흐름의 상태

| 구간 | 확인한 사실 | 미확인·문제 |
|---|---|---|

기존 답변에서 “빈 DP가 기본 RAG로 넘어간다”는 표현의 실측 범위는 저장소 open과 lookup의 NO_RULE_MATCH 확인이었다.
ADR-0206 runner는 실제 HTTP 질문→전체 retrieval→유료 답변 합성까지 실행하지 않았다.
운영 ontology retrieve 코드에는 fallback이 있지만 이 사실만으로 최신 전체 E2E 통과를 주장하지 않는다.

## 4. RAG 코드 흐름

활성 `legalclosure.retrieve`는 정확 구조/용어 탐색 → Assertion 트리 탐색 → 키워드 조문 검색 → 법적 필수 관계/참조 보완 → 좌표 병합을 수행한다. 채널을 도식에서 나누더라도 구현상 모두 병렬 실행이라는 뜻은 아니다.
Graph/semantic 추가 탐색, 검색 feedback, recovery는 switch/조건에 따른 선택 경로다.
`ontology_rag_v1.retrieve`는 기존 LegalClosure 결과를 먼저 보존하고 검증된 정의 ClauseSpan 좌표를 추가한다. 불일치·모호성·실패 시 기본 결과를 유지한다.
API는 최종 scope 처리 뒤 `answer.synthesize`로 LLM 답변을 만든다. 위키는 선택적인 해석 배경이며 법령 원문 인용의 대체가 아니다.
일반 관련성 filter는 LegalClosure 확정 좌표에 재적용하지 않는다. 인용 좌표는 코드가 만들지만 이것이 답변의 모든 주장에 대한 논리적 검증은 아니다.

## 5. 수정 우선순위

1. 문서 서두 보존과 예시/구판/운영 문서 범위 분리를 명시한다.
2. 두 매뉴얼의 heading-parent 경계, 은행 시행세칙 별표 종료 경계를 우선 검토한다.
3. 정상 구조에 대해서만 배치를 다시 만들고 큰 표·긴 본문을 좌표 보존 분할한다.
4. 반출·비용·검토 경계 연결 후 소규모 실제 LLM 표본을 검증한다.
5. 동일 입력·authority로 운영 후보를 묶고 실제 질문 E2E/OOS를 통과한 뒤 명시적으로 승격한다.
